Zeus-Doc-复现学习路线图

Posted on 2026-08-17 In 项目实战 Word count in article: 2.3k Reading time ≈ 8 mins.

目标：把”照着复现项目”变成”系统性技术提升”。核心方法是每个技能块的
四步学习闭环：读 → 写 → 验 → 答。

  • 读：原理资料 + 参考实现（现有文档 + 代码，对照《Zeus-Doc-技能点与代码落点索引》）
  • 写：不抄代码，先遮住参考实现自己写，写不出再看
  • 验：跑实验/单测/验证脚本，让结果说话
  • 答：用面试题自测（《Zeus-Doc-项目面试实战手册》），能讲清楚才算掌握

熟练度定义：了解（能说原理）/ 掌握（能写出代码）/ 熟练（能讲清并答追问）/ 精通（能讲设计取舍与缺陷）。

一、学习闭环总览

铁律：

  1. 每个技能块必须走完四步才算完成，禁止”读完了就当会了”；
  2. “写”时参考实现只允许看接口签名和注释，禁止直接抄方法体（抄了=没练）；
  3. “答”用口头复述（不是默写），对着镜子/录音讲，讲不顺的地方就是没懂的地方；
  4. 每周末做一次”上周技能块总复习”：随机抽 3 个面试题盲答。

Tomcat 深度解析：连接器、类加载与调优排障

Posted on 2026-08-13 In 框架 Word count in article: 3.8k Reading time ≈ 14 mins.

「你的应用是怎么跑起来的？」——Spring Boot 内嵌的 Tomcat 替你回答了这个问题的全部复杂度，但面试官问的就是这些被藏起来的细节：一个 HTTP 请求从网线到你的 Controller 经历了什么？为什么 Tomcat 要打破双亲委派？maxThreads/maxConnections/acceptCount 三个参数怎么配合？ 本文按「整体架构 → 线程模型 → 类加载 → 调优排障」四层讲透 Tomcat：每个概念配可运行验证，读完你能在面试中画出请求旅程图，并在线上「Tomcat 线程打满/连接堆积」时知道先看什么。

联动：本文是 Spring 深度解析（应用框架层）之下、Java 并发编程 与 Netty 原理与实践（IO 模型）之上的中间层——Tomcat 是两者的交会点；连接器调优的压测验证见 Zeus-Doc 性能压测实战；类加载与 JVM 原理与调优 的类加载机制直接相关。

1. 定位：Tomcat 在面试里的三个位置

面试问题 本质考点 本文章节
Tomcat 的架构？一个请求怎么走？ 连接器 + 容器两段式，IO 线程与业务线程分离 §2
maxThreads / maxConnections / acceptCount 什么关系？ 连接缓冲深度与线程模型的配合 §3
Tomcat 为什么打破双亲委派？ 类加载器的隔离设计 §5

因果链主线：Tomcat 的全部设计都围绕一个矛盾——「Web 容器要同时服务很多请求（并发），但每个请求的 IO 很慢（网络）」。解法：IO 线程只做读写不干活，业务线程池干活（连接器两段式）；应用之间/应用与容器之间的类要隔离（WebappClassLoader）。记住这两条，所有参数和机制都能推出来。

2. 整体架构：连接器 + 容器

2.1 两段式架构

flowchart LR
    C["客户端"] -->|"TCP 连接"| AC["Acceptor<br/>(接收连接)"]
    AC -->|"socket"| PP["Poller<br/>(NIO 多路复用)"]
    PP -->|"可读事件"| WC["工作线程池<br/>(执行业务)"]
    WC -->|"解析后的请求"| EN["Engine<br/>(顶层容器)"]
    EN --> H["Host<br/>(虚拟主机)"]
    H --> CT["Context<br/>(Web 应用)"]
    CT --> W["Wrapper<br/>(Servlet)"]
    W --> S["Controller/Servlet<br/>业务代码"]

两个半场：Connector（连接器）管「网络 IO + 协议解析」，把 socket 变成 Request/Response 对象；Container（容器）管「请求分发 + Servlet 生命周期」，从 Engine 逐层下钻到 Wrapper。IO 与业务彻底分离——这是 Tomcat 能扛高并发的架构根基。

组件 职责 对应
Connector 接受连接、IO、协议解析（HTTP/1.1、HTTP/2、AJP） 端口监听（如 8080）
Engine 顶层容器，处理所有请求入口 一个 Tomcat 一个
Host 虚拟主机，按域名区分 server.xml 里一个 <Host>
Context 一个 Web 应用（一个 WAR/应用目录） Spring Boot 内嵌时就是你的应用
Wrapper 一个 Servlet 的包装 Spring MVC 的 DispatcherServlet

因果链：容器分层（Engine → Host → Context → Wrapper）的粒度 = 「一个 Tomcat 可以跑多个应用（多 Context），一个应用由多个 Servlet 组成」——分层就是为了「多应用共存 + 每个应用独立管理」。Spring Boot 内嵌 Tomcat 只有单应用，但分层结构不变（面试常考「内嵌与独立部署的区别」，分层答案通用）。

2.2 动手验证：看一个请求的旅程

观察点：lsof -i :8080 能看到 ESTABLISHED 连接（Acceptor 接收）、Tomcat 是普通 Java 进程（一切跑在 JVM 上）。判定标准：理解「Tomcat = 一个 Java 程序，用线程处理并发，用 socket 收发数据」——它没有魔法，就是 JVM 上的多线程网络程序，所以 Java 并发编程 的线程模型知识全部适用。

3. 连接器：NIO 线程模型与三大参数

3.1 三个线程的职责分工

线程 职责 数量
Acceptor 只做 accept() 拿新连接 1 个（每端口）
Poller NIO Selector 多路复用，检测 socket 可读/可写 1-2 个（每端口）
工作线程池 解析请求、执行业务 maxThreads（默认 200）

因果链：NIO 模型下「一个 Poller 线程服务几千个连接」（Selector 多路复用，IO 模型：阻塞、多路复用与零拷贝 的原理），所以 maxThreads 是「同时处理的请求数」，不是「连接数上限」——连接可以有几万个，同时干活的最多 200 个，其余在队列等待。

3.2 maxThreads / maxConnections / acceptCount 三参数（面试核心）

参数 含义 默认值 超了会怎样
acceptCount TCP accept 队列长度（OS 层 backlog） 100 队列满 → connection refused（直接拒绝新连接）
maxConnections 连接器保持的最大连接数（含等待中的） 10000（NIO） 满了不再 accept，连接在 accept 队列排队
maxThreads 工作线程池上限，同时处理的请求数 200 线程全忙 → 新请求在等待队列（内部队列）排队

三者的配合（面试必画）：

flowchart LR
    A["新连接"] -->|"连接数 < maxConnections"| B["accept 进来"]
    B -->|"有线程空闲"| C["立即处理"]
    B -->|"线程全忙"| D["内部等待队列"]
    A -->|"连接数 ≥ maxConnections"| E["accept 队列<br/>(acceptCount 长度)"]
    E -->|"队列满"| F["connection refused"]

因果链：三参数是三级缓冲——maxThreads 管「同时干活的」，maxConnections 管「连接能堆多少」，acceptCount 管「拒绝前的最后缓冲」。压测时先触达哪个，取决于负载形态：请求密集但执行快 → 先触达 maxThreads；连接数暴涨（慢客户端多）→ 先触达 maxConnections。

3.3 动手验证：压测观察三参数排队

观察点：jstack 里 http-nio-8080-exec-N 线程数变化；ab 结果里的 failed/complete 比例。判定标准：能说出「调 maxThreads 是调吞吐上限，调 acceptCount 是调拒绝时机」——别一压测失败就盲目调 maxThreads（Zeus 压测实战 有完整调参案例）。

4. 请求处理：Pipeline 与 Servlet 生命周期

4.1 Valve 责任链与 Servlet 三段生命周期

Pipeline/Valve：容器每一层（Engine/Host/Context/Wrapper）都有一条责任链，请求逐层穿过 Valve（如 AccessLogValve 记录访问日志）——这是 AOP 思想的容器版（Spring 深度解析 的拦截器是同一模式）。

Servlet 生命周期三阶段：

阶段 时机 说明
init 首次请求或启动时 只执行一次，做初始化
service 每次请求 线程池中的线程并发调用（多线程共享实例）
destroy 应用卸载 只执行一次，释放资源

因果链（面试高频）：Servlet 是单实例多线程——一个 Servlet 实例被所有请求共享，实例变量必须线程安全（这就是 Java 并发编程 的线程安全问题在 Web 层的具体落点：controller/service 里的实例字段就是共享状态）。面试答「为什么 Controller 不该有实例变量」：单实例多线程 + 线程池并发调用，实例字段就是竞态源。

4.2 动手验证：看 Servlet 实例与线程

观察点：instance= 每次一样、thread= 每次不同——单实例多线程的现场。判定标准：亲眼确认「Servlet 实例只有一个、线程是池里随便抽的」，理解实例变量的危险性。

5. 类加载：为什么打破双亲委派

5.1 双亲委派 vs Tomcat 的破坏

JVM 双亲委派（JVM 原理与调优 详细讲）：类加载先委托父加载器，父类找不到才自己找——保证核心类不被篡改。

Tomcat 的 WebappClassLoader 打破双亲委派：先自己找，找不到再委派父加载器（对 web 应用类目录）。为什么？

理由 场景
应用类隔离 同一 Tomcat 部署两个应用，各自带不同版本的 Spring——双亲委派会让先加载的版本被所有应用共享，版本冲突
热部署 应用重新部署时旧类加载器整体作废换新的——双亲委派下父加载器会缓存类，无法替换

因果链：双亲委派保证「核心类唯一」；Tomcat 需要「应用类可替换、可隔离」——两者目标冲突，所以 WebappClassLoader 对应用类先自己加载，但对 javax.servlet、JVM 核心类仍然委派（容器自身规范类不能重载）。面试答：『打破双亲委派有两个原因——多应用类隔离 + 热部署；但规范类与核心类仍走委派』，两个原因+边界都说全才是完整答案。

5.2 动手验证：打印类加载器链

观察点：顶层是 WebappClassLoader 而非 AppClassLoader——你的类默认由 WebappClassLoader 加载。判定标准：能指着这条链讲「WebappClassLoader 先找自己、再委派」，并说出为什么 JVM 核心类（java.lang.String）不经过它。

6. 调优与排障：实战三件套

6.1 调优参数速查

场景 参数 建议
接口执行慢、线程全忙 maxThreads 先确认瓶颈在业务不在容器，再调大（默认 200 常见够用）
连接堆积、TIME_WAIT 多 maxConnections 加大 + 客户端复用连接（keep-alive）
高峰直接 connection refused acceptCount 适度加大（TCP 队列），但别指望它扛洪峰
慢客户端拖垮连接 connectionTimeout（默认 20s） 调小，快速释放坏连接
IO 密集 vs CPU 密集 线程池策略 IO 密集线程数可 = CPU×2 以上；CPU 密集 ≤ CPU 核数
请求体过大 413 maxPostSize / maxHttpHeaderSize 按业务实际放宽

6.2 排障路径（症状 → 先看什么）

症状 第一步
请求全部超时 jstack 看 http-nio-8080-exec 线程都在哪（业务阻塞 vs 池满排队）
新连接 refused 看是 acceptCount 满了还是连接数触顶（ss -s 看队列）
CPU 100% 区分 GC 线程 vs 业务线程（JVM 调优 的 jstack/jstat 流程）
偶发 500 看是否线程池拒绝（RejectedExecutionException）→ 调队列/降级
重启后还是慢 检查是否有连接泄漏（未归还的连接池）

因果链（排障核心）：Tomcat 故障的本质只有三类——线程池耗尽（业务慢/死锁）、连接池耗尽（连接泄漏）、accept 队列满（洪峰/慢客户端）。先判断是哪一类，再对症调参，不要一慢就调 maxThreads。

6.3 动手验证：制造并定位线程池耗尽

观察点：线程数到 maxThreads 后请求开始排队；jstack 显示线程全在业务代码里——瓶颈是业务慢，不是容器参数。判定标准：能说出「调 maxThreads 是治标，治本是查业务为什么慢」——容器参数只决定排队深度，不决定处理速度。

7. 面试应答：Tomcat 五连问

7.1 完整话术

面试题 回答要点
Tomcat 架构？ 连接器 + 容器两段式：Connector 管 IO 与协议解析，Container（Engine→Host→Context→Wrapper）管分发与 Servlet 生命周期
NIO 线程模型？ Acceptor 收连接 → Poller 多路复用 → 工作线程池执行业务，IO 与业务分离
三参数关系？ maxThreads 管同时干活数、maxConnections 管连接上限、acceptCount 管拒绝前缓冲；三级缓冲
为什么打破双亲委派？ 多应用类隔离 + 热部署；但规范类与核心类仍委派
Servlet 为什么单实例多线程？ 容器设计如此；实例变量是共享状态，必须线程安全
内嵌 Tomcat 与独立部署区别？ 架构相同；内嵌单 Context、生命周期由 Spring Boot 管理（Spring 深度解析）

7.2 深挖：与 Netty 的对照（跨篇联动）

维度 Tomcat Netty
定位 Web 容器（HTTP 应用服务） 通用网络框架（任意协议）
线程模型 Acceptor + Poller + 工作线程池 Boss + Worker EventLoop（Netty 原理与实践）
IO 模型 NIO（BIO 可切换） NIO/EPOLL 原生
业务执行 线程池（可阻塞） EventLoop 内不可阻塞（阻塞会拖死同 EventLoop 的所有连接）

一句话：Tomcat 是「Netty 思想的服务化产物」——都用多路复用 + 线程池，但 Tomcat 允许业务线程阻塞（用线程池隔离），Netty 的 EventLoop 模型不允许（阻塞即灾难）。面试被问「Tomcat 和 Netty 的线程模型区别」，答出「业务可阻塞 vs 不可阻塞」就是区分点。

8. 总结

短链系统设计：从方法论到落地

Posted on 2026-08-13 In 系统设计 Word count in article: 3.3k Reading time ≈ 12 mins.

「设计一个短链系统」是系统设计题的常青树——它看着简单（不就是个映射吗），但面试官真正在考的是三件事：长 URL 怎么变成 7 位短码（发号与进制转换）、短码怎么存（分表 + 缓存分层）、跳转用 301 还是 302（状态码背后的业务意图）。 秒杀篇讲的是「写」场景（削峰、防超卖），短链篇讲的是「读」场景（缓存、布隆、热点）——两篇合起来，方法论的两个极端就都有了。读完你能在面试现场把这道题从头推到尾，并且说清每个选择的理由。

联动：本文是 系统设计方法论（需求澄清/容量估算/评估权衡）的第二个完整案例；与 秒杀系统设计（写场景）对照形成读写双案例；缓存分层与布隆过滤器复用 Redis 深度解析；发号器与分表复用 MySQL 高可用与分库分表实战、分布式系统核心理论（分布式 ID）。

1. 定位：这道题考什么

短链系统的需求一句话：输入任意长 URL，输出 7 位短码；访问短链时重定向到原长 URL（如 t.cn/Ab3dE9 → 长链接）。

它为什么高频：短链表面是「字符串映射」，实际覆盖了系统设计的读路径全部考点——容量估算、哈希与冲突、发号器、分库分表、缓存分层、布隆过滤器、热点防护、301/302 语义。一题考完「读场景」所有基本功，这是它和秒杀（写场景）互补的原因。

与秒杀的核心对照（面试立论用）：

维度 秒杀（上一案例） 短链
场景类型 写密集（下单） 读密集（跳转）
核心矛盾 瞬时流量洪峰 热点 key 与缓存击穿
关键中间件 Redis 预扣 + MQ 削峰 Redis 缓存 + 布隆过滤器
容量估算重点 峰值 QPS（10 万级） 总量与读放大（百万级）

2. 需求澄清与容量估算（方法论第一步）

面试先做需求澄清，别急着画架构——短链的四个关键问题：

问题 默认假设（可主动询问） 影响
每天新增多少长链接？ 1000 万条/天 决定发号器吞吐与表容量
短链跳转 QPS？ 峰值 2 万 QPS 决定缓存层级与热点策略
短码长度？ 7 位（字母+数字 62 进制） 决定容量上限
数据保存多久？ 长期（10 年） 决定总量与淘汰策略

容量估算（写出数字，面试加分）：

因果链：容量估算的结论直接决定架构——「总量 365 亿 → 单表扛不住 → 分 64 表；读 2 万 QPS → DB 扛不住 → 缓存扛 90%」——每一步架构决策都是上一步数字的推论，这是方法论的核心（完整流程见 系统设计方法论）。

3. 核心机制一：短码生成——发号器 + 62 进制

3.1 为什么不用 MD5 截断

方案 问题
MD5 长 URL 截 7 位 哈希冲突概率随数据量上升，冲突要重算（循环）
随机短码 碰撞检测麻烦，每次生成要查重
发号器 + 62 进制 无冲突（号唯一）、可预测、可支持批量

短码 = 发号器拿到的自增 ID，转成 62 进制：ID=1 → "1"，ID=1000000 → "4c92"……7 位最多 62^7≈3.5 万亿个短码，用不完。

3.2 发号器三方案（面试核心）

方案 机制 优缺点
Redis INCR 单 key 自增 简单；Redis 挂影响发号，可持久化兜底
DB 号段（segment） 每次取一批号（如 1 万），内存发完再取 无网络往返、DB 压力小，生产主流
雪花算法 时间戳+机器号+序列号 无序、不可预测；但短码要「短」反而用它少见

因果链：发号器选型的关键是「发号频率 = 写入频率 = 日增 1000 万」——每次取号都打 Redis/DB 会打死存储，号段模式把「1 万次取号」合并成「1 次 DB 查询」（与 MQ 批量消费同一个思想：批量换吞吐）。面试答发号器：「DB 号段 + 内存发号」是标准答案，补一句『发号是写路径唯一瓶颈，所以必须批量』就是完整逻辑。

3.3 动手验证：号段发号的最小实现

观察点：前 1 万次调用只触发 1 次 DB 更新（UPDATE ... + 10000），之后全部内存返回。判定标准：能说出「DB 压力 = 日增 1000 万 ÷ 号段 1 万 = 每天 1000 次写」——发号从「每秒 115 次」降到「每天 1000 次」，这就是号段的威力。

4. 核心机制二：存储与读取——分表 + 缓存分层

4.1 存储设计

层 方案 理由
主表 MySQL，按短码 hash 分 64 表（short_url_0 ~ short_url_63） 10 年 365 亿条，单表 ~5.7 亿超阈值
路由 hash(short_code) % 64（或按 ID 段路由） 短码定表，读路径直查
冗余 主从 + 读写分离 读多写少，从库扛查询
索引 短码唯一索引 跳转按短码精确查

为什么分 64 表而不是 4 表：10 年数据量 × 单表 5.7 亿超红线（MySQL 单表 5000 万经验线）——分表数 = 总量 ÷ 单表容量，先把十年算完再定（细节见 MySQL 高可用与分库分表实战）。

4.2 缓存分层与布隆过滤器

flowchart LR
    C["客户端"] -->|短链访问 2W QPS| NG["网关/本地缓存<br/>(Caffeine, 毫秒级)"]
    NG -->|未命中| R["Redis 缓存<br/>(命中率 ~95%)"]
    R -->|未命中| BF{布隆过滤器<br/>短码存在?}
    BF -->|不存在| E["直接返回 404<br/>(拦掉无效短码)"]
    BF -->|可能存在| DB[("MySQL 分表")]
    DB -->|回填| R
    R -->|回填| NG

因果链（这一层是全题精华）：缓存未命中的请求会打到 DB——但无效短码（用户乱拼的）每次都不存在，会绕开缓存直接打 DB（缓存穿透），2 万 QPS 里若有 10% 无效请求，DB 每秒要扛 2000 次无效查询 → 布隆过滤器在 DB 前拦一层：不存在直接 404，存在才放行。布隆的代价是「可能误判存在」但不误判不存在——宁放行一次空查，不放过一次真查（布隆过滤器原理与实现见 Redis 深度解析）。

4.3 动手验证：布隆拦截无效短码

观察点：无效短码在布隆层即被拦，DB 零压力；写入短链时 BF.ADD 与 DB 同步（失败可容忍——误判只是多查一次）。判定标准：能说出布隆过滤器的取舍——「不存在的必拦，存在的可能漏拦（误判），所以它只防穿透、不防击穿」。

5. 核心机制三：301 vs 302 与热点防护

5.1 301 还是 302（面试高频追问）

状态码 语义 对短链的影响
301 永久重定向 浏览器/客户端缓存跳转结果，下次直接访问长链——后续请求不经过我们，但无法统计点击量、无法修改跳转目标
302 临时重定向 每次访问都先打我们的服务——可以统计、可以改目标，但服务压力大

面试标准答案：选 302——短链是营销/内容运营工具，点击统计和可修改性是产品刚需，牺牲一点服务压力换这两个能力。因果链：301 把控制权交给了客户端缓存，302 把每次访问留在自己手里——「要数据就要 302」。

5.2 热点短链防护

短链符合「二八定律」：20% 的短链扛 80% 的点击（爆款链接）。防护层次：

层 手段
本地缓存 Caffeine 短 TTL（秒级），挡住大部分热点
Redis 热点 key 天然被缓存吸收；单 key 打爆加本地缓存兜底
热点识别 计数器识别 topN 热点 → 加大本地缓存 TTL
限流 网关限流保护后端（见 秒杀篇 的限流章节）

因果链：读场景的雪崩风险是「热点 key 过期瞬间，大量请求同时打到 DB」——本地缓存（Caffeine）是第一层盾：Redis 挂了热点还在本地挡着。面试答「读场景高可用」的标准句式：「多级缓存 + 热点识别 + 网关限流」。

6. 完整架构图（读路径全景）

flowchart LR
    U["用户"] -->|"t.cn/Ab3dE9"| LB["负载均衡"]
    LB --> W["短链服务集群"]
    W --> C1["Caffeine 本地缓存"]
    W --> R["Redis（短码→长链）"]
    W --> BF["布隆过滤器"]
    W --> DB[("MySQL 64 表")]
    R -->|回填| C1
    DB -->|回填| R
    DB --> ID["发号器<br/>(DB 号段)"]
    ID -->|"长链写入时取号"| DB
    W -->|302| U
    U --> L["长 URL 目标站"]

完整链路：写入（长链 → 发号取号 → 62 进制转短码 → 落 64 表 → 布隆 ADD → 缓存回填）；读取（短码 → 本地缓存 → Redis → 布隆 → DB → 逐级回填 → 302 跳转）。

7. 面试应答：短链六连问

7.1 完整话术

面试题 回答要点
短码怎么生成？ 发号器（DB 号段）取自增 ID → 62 进制转 7 位短码，无冲突
为什么不用 MD5？ 截断有冲突率，冲突处理复杂；发号器确定性无冲突
数据怎么存？ 按总量算分表（10 年 365 亿 → 64 表），短码唯一索引，主从读写分离
缓存穿透怎么防？ 布隆过滤器拦无效短码：不存在必拦，存在可能误判放行
301 还是 302？ 302：要点击统计与可修改性，每次访问留在自己手里
热点怎么防？ 多级缓存（Caffeine + Redis）+ 热点识别 + 网关限流
发号器挂了怎么办？ 号段模式 DB 压力极小；DB 用主从，主挂从顶上（号段不丢）

7.2 深挖：与秒杀的双案例对照（跨篇联动）

维度 秒杀（写场景） 短链（读场景）
核心矛盾 瞬时洪峰（写放大） 热点 + 穿透（读放大）
第一防线 限流（令牌桶/双层） 多级缓存（Caffeine→Redis）
中间件 MQ 削峰 + Redis 预扣 布隆过滤器 + Redis
容量重点 峰值 QPS 与库存原子性 总量 × 生命周期与命中率
最终兜底 对账 + 降级 302 语义 + 限流

一句话：秒杀教你怎么扛「一分钟的十万并发」，短链教你怎么扛「十年的每天两万」——一个是打（洪峰），一个是磨（长尾）。面试把两篇的对照讲出来，等于证明「方法论不是背的，是用的」。

8. 总结

8.1 面试速答表

面试题 一句话答案
短码生成方案？ 发号器（DB 号段）→ 62 进制，无冲突、可批量
号段发号原理？ 一次取 1 万号内存发放，DB 压力从每秒降到每天
为什么 64 张表？ 10 年 365 亿条 ÷ 单表 5.7 亿超线，分表数由总量反推
缓存穿透怎么防？ 布隆过滤器：不存在的必拦，存在的可能放行
301 vs 302？ 302：要统计与可改目标；301 把控制权交给客户端
热点怎么护？ 本地缓存 + 热点识别 + 限流，Redis 挂热点仍挡得住
缓存击穿怎么防？ 热点 key 永不过期 + 重建互斥锁（Redis 深度解析的经典方案）

8.2 实战避坑表

症状 原因 处理
短码偶尔跳错 62 进制实现有歧义字符 去掉 0/O、1/l/I 等易混字符
无效短码打爆 DB 缓存穿透 布隆过滤器（先写后读，注意写入同步）
热点链接雪崩 热点 key 过期同时回源 本地缓存 + 互斥重建 + 热点识别
发号器并发重复 号段分配无锁 内存分配 synchronized/乐观锁，DB 唯一索引兜底
改短链跳转目标 301 被客户端缓存 业务上不给改（301）或用 302 保修改能力
短码被遍历 顺序号可预测 号段偏移加盐（如 ID×随机步长）或哈希混淆

8.3 工具速查表

工具 用途
RedisBloom（BF.* 命令） 布隆过滤器落地
Caffeine / Guava Cache 本地缓存第一层
MySQL 分表（sharding-key 路由） 64 表路由
Nginx/Gateway 限流 网关层保护

Redis 集群与高可用实战：主从、哨兵与 Cluster

Posted on 2026-08-13 In 数据存储 Word count in article: 3.1k Reading time ≈ 11 mins.

单机 Redis 能用，但「扛不住」时只有两个问题：机器挂了怎么办（高可用），数据量大了怎么办（扩容）——分别对应哨兵和 Cluster。 本文按「单机 → 主从 → 哨兵 → Cluster」的演进线讲透：主从为什么选异步复制、哨兵怎么避免误判（主观下线 vs 客观下线）、Cluster 槽位怎么路由与迁移、以及脑裂在 Redis 里怎么发生。读完你能独立搭出一套哨兵集群，并能在面试中画出主从切换的完整时序。

联动：本文是 Redis 深度解析（数据结构/持久化/缓存设计）的高可用续篇；主从复制与 MySQL 高可用 的主从是同一思路；哨兵选举与 ZooKeeper 原理与实践 的选主机制呼应；脑裂防护与 ES 原理深挖 的 minimum_master_nodes 是同一个「过半」思想。

1. 定位：演进线就是面试线

Redis 高可用是一个「一步步加组件」的演进过程，每个阶段解决一个问题、引入一个新概念：

阶段 解决什么 关键机制 代价/限制
单机 基本可用 无 单点故障、容量单机上限
主从 数据冗余 + 读扩展 异步复制 主挂需人工切换
哨兵 自动故障转移 监控 + 选举 仍是单主写（写不扩容）
Cluster 自动分片扩容 槽位路由 跨槽多键操作受限

因果链：主从解决「数据不丢」和「读扛不住」→ 但切换要人工 → 哨兵自动化 → 但写仍是单点 → Cluster 分片让写也能扩容。面试答 Redis 高可用，按这条演进线讲，逻辑自动闭环。

2. 主从复制：异步复制的真相

2.1 复制流程

sequenceDiagram
    participant S as 从节点
    participant M as 主节点
    S->>M: 1. 建立连接，请求同步
    M->>S: 2. 全量同步（RDB 快照 + 缓冲）
    S->>S: 3. 载入 RDB，应用缓冲增量
    Note over M,S: 此后：M 每写一条就异步推给 S（增量同步）
机制 说明
全量同步 首次/断连太久：主节点生成 RDB 快照传输
增量同步 断连短暂：repl_backlog 缓冲补发
复制偏移量 主从各自维护 offset，比对差异

2.2 为什么默认异步复制（面试核心）

维度 异步复制 同步复制（WAIT 命令可选）
主节点写延迟 无（写完就返回） 等从节点确认
一致性 弱一致（从节点可能短暂落后） 强
故障窗口 主挂瞬间，未复制的数据丢失 不丢（但主也写不快）
生产选择 默认（性能优先） 严格不丢数据的场景（罕见）

因果链：Redis 定位是缓存/高速存储，性能优先于强一致——所以默认异步。「主节点挂了丢几秒数据」是异步复制的已知代价，用「哨兵秒级切换 + 业务容忍短暂不一致」接受它（这与 MySQL 半同步 的选择逻辑对比着看：MySQL 数据价值高所以有半同步选项，Redis 缓存容忍丢）。

2.3 动手验证：主从复制与主挂现场

观察点：主挂后从节点只读拒绝写入——「主从不做自动切换，必须靠哨兵」的现场证据。判定标准：亲手确认「主从只解决读扩展与冗余，故障转移需要哨兵」，这是理解为什么需要哨兵的第一课。

3. 哨兵：自动故障转移

3.1 三个哨兵能力 + 主观/客观下线

能力 机制
监控 每秒 PING 主从节点，检查存活
通知 主节点变化通知客户端
自动故障转移 主挂了：选举新主 → 通知其他从切换主

下线判定两级：

判定 条件 动作
主观下线（sdown） 单哨兵发现主节点超时（down-after-milliseconds） 标记 sdown，开始投票
客观下线（odown） 多数哨兵（quorum）都认为挂了 触发故障转移

因果链：单哨兵可能误判（网络抖动）→ 必须多数派确认才真切换 → quorum 防误判。这与 ES 脑裂防护、ZooKeeper 选主是同一个「过半」思想（ES 原理深挖 已讲过 minimum_master_nodes=N/2+1）。

3.2 故障转移的完整时序（面试必画）

sequenceDiagram
    participant S1 as 哨兵1
    participant S2 as 哨兵2
    participant S3 as 哨兵3
    participant A as 主节点
    participant B as 从节点B
    S1->>S1: A 超时 → 主观下线
    S1->>S2: 投票：A 挂了？
    S1->>S3: 投票：A 挂了？
    S2-->>S1: 同意
    S3-->>S1: 同意（达到 quorum=2）
    S1->>S1: A 客观下线 → 触发故障转移
    S1->>B: 选 B 为新主（slaveof no one）
    S2->>B: 其他从节点重定向到 B
    Note over S1: 客户端感知新主地址（Sentinel 客户端订阅通知）

选举规则（面试加分）：新主选择优先级 = 复制偏移量最大（数据最新）→ 优先级 → runId 最小——「数据最新者优先」防止选举后丢数据。

3.3 动手验证：模拟主挂自动切换

观察点：主节点停止后 5-10 秒内，get-master-addr-by-name 返回的不再是 6379——故障转移自动完成，无需人工。判定标准：亲手复现「主挂 → 哨兵自动选新主」，理解「哨兵把人工切换变成了自动化」。

3.4 哨兵的两大坑：脑裂与误切换

坑 场景 后果 防护
脑裂 主节点网络分区（假死），哨兵选新主；老主恢复后两个主并存 客户端写入分裂，老主数据丢失 min-replicas-to-write：主节点写前要求至少 N 个从节点可达，否则拒写
误切换 单哨兵抖动误判（quorum=1） 不必要切换、短暂不可写 quorum ≥2 且哨兵数 ≥3（奇数）

因果链：脑裂的根源是「老主不知道自己已被判死刑」——用 min-replicas-to-write 让老主在失去多数从节点时自动拒写，「宁可拒绝写入也不接受分裂」与 分布式事务 的「牺牲可用性保一致性」同理。面试答 Redis 脑裂：min-replicas-to-write + 说明「老主被分区时拒写，恢复后数据不丢」。

4. Cluster：分片让写也能扩容

4.1 槽位路由：16384 个槽

Cluster 把 key 空间切成 16384 个槽（slot），每个节点负责一段槽：

flowchart LR
    K["key"] --> H["CRC16(key) % 16384"] --> S["槽号"]
    S --> N1["节点A: 槽 0-5460"]
    S --> N2["节点B: 槽 5461-10922"]
    S --> N3["节点C: 槽 10923-16383"]
机制 说明
路由 客户端算 CRC16 找槽，槽→节点映射表（或经代理）
重定向 请求打到错误节点 → MOVED/ASK 错误告知正确节点
槽迁移 扩容/缩容时槽从旧节点搬到新节点（在线）
副本 每个节点可有从节点，主挂自动升（类哨兵，内置）

4.2 Cluster 的限制与应对

限制 原因 应对
多 key 操作受限 不同 key 在不同槽/节点 哈希标签（hash tag）：{user:1}:cart 强制同槽
跨槽事务 同上 hash tag 或应用层补偿
批量命令受限 mget 跨节点 hash tag / 客户端分片聚合

因果链：分片的代价是「数据分散」→ 关联数据必须「强制同槽」（hash tag）——面试答 Cluster 的坑，先说「多 key 操作受槽位限制」，再补「用 hash tag 让关联 key 同槽」就是完整答案。

4.3 动手验证：起一个三主三从 Cluster

观察点：CLUSTER SLOTS 显示 16384 个槽分成 3 段；-c 模式下 SET 自动完成路由与重定向。判定标准：亲手确认「Cluster 按槽路由、客户端无需知道槽映射」——扩容只迁移槽，不用改客户端（配合代理/客户端集群感知）。

5. 面试应答：Redis 高可用五连问

5.1 完整话术

面试题 回答要点
主从复制怎么工作？ 全量 RDB + 增量 backlog；默认异步（性能优先，容忍短暂落后）
为什么异步？ 同步写要等从节点确认，延迟高；Redis 缓存语义接受弱一致
哨兵怎么防误判？ 主观下线（单哨兵）→ 投票多数派 → 客观下线才切换；quorum ≥2、哨兵奇数
新主怎么选？ 复制偏移量最大（数据最新）→ 优先级 → runId
Redis 脑裂怎么防？ min-replicas-to-write：老主失去多数从节点时拒写
Cluster 怎么路由？ CRC16(key) % 16384 定槽；MOVED/ASK 重定向；hash tag 让关联 key 同槽
什么时候用 Cluster？ 数据量超单机内存或写吞吐不够；否则哨兵够用

5.2 深挖：与 MySQL 高可用的对照（跨篇联动）

维度 MySQL Redis
复制 binlog 异步/半同步（MySQL 高可用） RDB/backlog 异步
自动切换 MHA/Orchestrator 哨兵
脑裂防护 半同步 + 仲裁 min-replicas-to-write
扩容 分库分表（人工） Cluster 槽迁移（在线）
数据价值 高（强一致优先） 缓存/高速（性能优先）

一句话：MySQL 与 Redis 的高可用是同构的——复制 → 自动切换 → 脑裂防护，三件套一样，差别只在「一致性 vs 性能」的权重不同。跨库对照是面试差异化亮点：「MySQL 选半同步因为数据贵，Redis 选异步因为要快，但脑裂防护思想完全一致」。
