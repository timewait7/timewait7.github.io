一、数据库选型与分片总览

Zeus-Doc 采用 MySQL 8.0 作为持久化存储，通过 ShardingSphere-JDBC 5.4.1 实现透明分库分表。核心配置位于 zeus-doc-service-doc/src/main/resources/application-sharding.yml。

1.1 库表分布全景

逻辑库 物理库 服务归属 是否分片
zeus_user zeus_user user-service 否（单库）
zeus_doc zeus_doc（ds0） doc-service 否（主表单库）
doc_history zeus_doc_history_0..3 doc-service 是（4 库 × 月表）
zeus_audit zeus_audit_0..3 audit-service 是（按租户分库）
doc_audit_cold 全库广播 audit-service 广播表

1.2 分片策略摘要（application-sharding.yml:56-101）

  • doc_history：分库列 doc_id（MOD 4），分表列 created_at（INTERVAL 按月，后缀 yyyyMM）
  • doc / share_link：不分片，落在 ds0
  • doc_audit_cold：广播表，4 库均存全量
  • 主键生成：雪花算法 SNOWFLAKE

四、分库分表策略详解

4.1 doc_history：按 doc_id % 4 分库 + 按月分表

配置（application-sharding.yml:59-73）：

分库算法：MOD 类型，sharding-count: 4，即 库序号 = doc_id % 4。

分表算法：INTERVAL 类型，按 created_at 月份生成 yyyyMM 后缀，范围 2026-08 ~ 2027-12，间隔 1 个月。

为什么这样分：

  • 按 doc_id 分库：查某文档历史版本时只命中 1 个库，避免广播；
  • 按月分表：单表数据量控制在千万级，便于按时间范围归档冷数据；
  • doc_history 写入 QPS 高（每次保存一条），分片后单库写入压力降为 1/4。

4.2 doc_audit：按 tenant_id 分库 + 按 created_at 分表

审计表按租户分库（tenant_id % 4），保证同一租户的审计数据落在同一库，便于按租户聚合查询。按 created_at 月份分表，便于按时间范围清理过期审计。

注：doc_audit 与 doc_history 分库策略不同，前者按租户（查询维度是租户），后者按文档（查询维度是文档版本），体现了「按查询维度选分片键」的原则。

4.3 广播表 doc_audit_cold

冷备审计表作为广播表（application-sharding.yml:108-110），4 库均存全量。JOIN 时无需跨库，适合更新少、读多的字典/冷数据。

翻页深度 OFFSET 方案 RT 游标方案 RT 提升

7.2 ShardingSphere 路由归并原理

doc_history 按 doc_id % 4 分库。本 SQL 不带分片键 doc_id 的等值条件，ShardingSphere 无法精确定位单库，触发全库路由，将 SQL 改写后下发到 4 个分片库：

归并（Merge）阶段：ShardingSphere 对 4 个分片返回的 GROUP BY 结果执行聚合归并：

  1. 各分片结果按 doc_id 排序（流式归并要求各分片自身有序）；
  2. 归并引擎按 doc_id 分组，对同一 doc_id 的 MAX(version) 取最大值；
  3. 输出最终合并结果。

7.3 路由归并流程图



flowchart LR

    Parse --> Route[路由引擎<br/>无分片键等值条件<br/>全库路由]
    Route --> Rewrite[SQL 改写<br/>下发 4 库]

    Rewrite --> DS2[ds2 GROUP BY doc_id]
    Rewrite --> DS3[ds3 GROUP BY doc_id]

7.4 优化建议

  • 带分片键查询：若能传入具体 doc_id，路由到单库，避免广播；
  • 避免跨库 GROUP BY：本例全库路由 + 归并代价高，可在 doc 主表冗余 latest_version 字段，避免查 doc_history；
  • 流式归并：ShardingSphere 对 ORDER BY + LIMIT 采用流式归并，内存占用 O(分片数) 而非 O(总行数)。

十、主键生成策略

统一采用雪花算法（SNOWFLAKE），配置于 application-sharding.yml:103-106：

雪花 ID = 时间戳(41bit) + workerId(10bit) + 序列号(12bit)，单机每毫秒可生成 4096 个，趋势递增利于 B+ 树插入（避免页分裂）。workerId 由 Nacos 分配，保证集群内唯一。

SnowflakeIdUtil.gen()（zeus-doc-common）在 TCC 编排中生成 auditId、recycleId（DocDeleteTccFacade.java:58-59）。

本数据库设计文档与 application-sharding.yml 配置一一对应。分片键选择与归并原理详见《06-面试手册第3问》，慢 SQL 拦截器实现见 SqlCostInterceptor.java。

附3、分库分表策略详解

3.1 doc_history：按 doc_id%4 分库 + 按月分表

配置文件： zeus-doc-service-doc/src/main/resources/application-sharding.yml

策略说明：

维度 分片键 算法 路由规则
分库 doc_id MOD（取模） ds{doc_id % 4}
分表 created_at INTERVAL（时间区间） doc_history_{yyyyMM}

为什么这么分？

  1. 按 doc_id 分库：历史版本查询 99% 场景是”查某文档的所有版本”，doc_id 是天然的高基数查询维度。按 doc_id%4 分库后，同一文档的所有版本落在同一库，避免跨库归并。doc_id 由雪花算法生成，分布均匀，4 库数据平衡。
  2. 按月分表：历史版本按时间持续增长，按月切分便于冷热分离（旧月表可归档/删除）。INTERVAL 算法支持范围查询路由（如查近 3 个月版本只需扫 3 张月表）。
  3. 数据节点表达式 ds$->{0..3}.doc_history_$->{202608..202712}：Groovy 表达式声明 4 库 × 17 月表共 68 个真实数据节点，ShardingSphere 自动路由。

路由示例：

  • 查 doc_id=1001, created_at=2026-08-15 → 库 ds{1001%4}=ds1，表 doc_history_202608
  • 查 doc_id=1001（不带时间）→ 库 ds1，所有月表广播

3.2 doc_audit：按 tenant_id%4 分库 + 按月分表

配置文件： zeus-doc-service-audit/src/main/resources/application-sharding.yml

策略说明：

维度 分片键 算法 路由规则
分库 tenant_id INLINE（表达式） ds{tenant_id % 4}
分表 created_at CLASS_BASED（自定义） doc_audit_{yyyyMM}

为什么选 tenant_id 分库（而非 doc_id）？

  1. 审计日志查询以租户为维度：管理员审计页面按租户筛选”本租户所有操作记录”，tenant_id 是必带过滤条件，分库后精确命中单库。
  2. 多租户隔离：不同租户数据物理隔离，避免大租户日志拖慢小租户查询。
  3. **allow-range-query-with-inline-sharding: true**：允许 INLINE 算法处理范围查询（虽不精确路由，但避免全库广播）。
  4. 自定义 MonthlyShardingAlgorithm（CLASS_BASED）：实现 StandardShardingAlgorithm，同时支持精确分片（= created_at，命中单表）与范围分片（BETWEEN created_at，命中多月表），用于时间区间审计追溯。

绑定表优化：

doc_audit 与冷备表 doc_audit_cold 使用相同分库键 tenant_id，声明绑定表后，两者 JOIN 不会产生跨库笛卡尔积，路由到同一分片。

5.2 游标分页优化

代码位置： DocService.listByCursor（DocService.java:135），DocMapper.selectByCursor（DocMapper.java:29）。

为什么用 id 作游标而非 updated_at？

  • id 是主键，唯一且单调递增（雪花），id < lastId ORDER BY id DESC LIMIT 20 走主键索引范围扫描，恒定扫描 20 行。
  • 若用 updated_at 作游标，同一时间戳可能有多条记录，需联合 id 做复合游标 (updated_at, id)，SQL 复杂。

优化后执行计划：

  • type=range，rows=20，只扫描满足条件的 20 行，O(1) 恒定，无论翻到第几页。

7.6 collab 为何用 StatefulSet（statefulset.yaml 注释）

协同服务 Netty WebSocket 维持有状态长连接，会话（光标、在线用户、OT 操作序列）存 Pod 本地内存。StatefulSet 提供：

  1. 稳定网络标识：Pod 名 collab-0/1/2，DNS 可解析，客户端重连路由到同一 Pod 恢复会话；
  2. 稳定持久存储：每 Pod 独立 PVC，会话快照不丢；
  3. 有序启停：启动 0→1→2，停止 2→1→0，避免同时重启致全部会话中断。

Gateway 通过一致性哈希按 docId 路由到固定 collab Pod。

应用关闭流程（ThreadPoolConfig.java:99-101, 121-126）：

  1. K8s 发送 SIGTERM（terminationGracePeriodSeconds: 30，gateway 60s）；
  2. Spring Boot 优雅停机，拒绝新请求；
  3. 线程池 waitForTasksToCompleteOnShutdown=true，等待队列任务完成（最多 30s）；

三、排障方法论

面试官真正想听的，不是”我修了 40 个 bug”，而是**”你面对一团乱麻时，大脑怎么运转”**。以下是这次实战沉淀的六条方法论。

3.1 先静态审计，再动手启动 —— 避免”启动-失败-修复”死循环

教训来源：改造初期我陷入了”启动 → 报错 → 修一处 → 再启动”的循环，连续多轮失败后，被明确要求”换思路，重新分析”。重启分析后一次性通过。

方法：动手启动前，完成四件事：

  1. 配置全量静态校验：所有 yml 的 YAML 语法（ruby/python 批量跑）；所有 ${ENV:default} 占位符与中间件实际凭证逐一对照（密码、端口、模式）；
  2. 依赖树冲突检查：mvn dependency:tree 按关键构件过滤，找出版本被覆盖/缺失的构件；
  3. 运行时状态盘点：中间件容器健康、端口占用、数据库库表完整性、ES 索引、MQ 注册、Seata 可达；
  4. 代码级静态分析：启动类扫描范围、配置类接线、Feign 契约、Bean 依赖图。

一句话：让”启动”成为验证手段，而不是定位手段。 定位靠静态分析，启动只负责确认。

3.2 分层定位：把问题钉在某一层

40 个问题看似杂乱，但全部可以归入六个层，且**每层有专属的”证据源”**：

层 证据源
环境层 docker ps、lsof -iTCP:port、launchctl list、Maven 日志
构建层 jar 清单（unzip -p xxx.jar META-INF/MANIFEST.MF）、jar 内依赖（unzip -l）、mtime
启动层 Spring 启动日志、APPLICATION FAILED TO START 的 FailureAnalysis、bean 创建栈
数据层 SQL 日志（ShardingSphere sql-show 的 Logic SQL / Actual SQL）、MySQL 错误、反编译配置类
链路层 服务间调用栈、Feign 错误体、MQ 消费日志、ES 文档内容
脚本层 最小复现实验、bash -x 追踪

关键动作：报错时先问”这是哪一层的错？”——同一个”创建文档 500”，可能来自数据层（表不存在）、链路层（MQ 发送失败）、框架层（Seata 包装异常），每层往下挖一层 Caused by，直到出现可行动的根因（表名、字段名、类名、地址）。

3.3 最小复现：把问题从系统里”抠”出来

当问题发生在 5 服务 + 7 中间件的复杂系统里时，在系统里调试是低效的。方法：构造一个只含问题要素的独立环境。

实战案例：ShardingSphere 路由到不存在的表。我没有在 doc 服务里反复重启调试，而是：

  1. 从 fat jar 抽出全部 362 个依赖 jar 到独立目录；
  2. 写 30 行 Java 程序，用完全相同的配置构造 ShardingSphereDataSource；
  3. 执行同一条 SQL，直接看到了 ShardingSphere 打印的 UNION ALL 全部 105 张表名——问题一目了然。

收益：复现成本从”重启整个服务（2 分钟）”降到”跑一个测试类（2 秒）”，且可以安全地迭代配置变体（改一版测一版），不污染线上环境。这是”快速试错”的正规姿势。

3.4 证据链思维：不猜，看证据

排障中最容易犯的错是基于经验猜测。这次我反复踩到”猜错方向”的坑，最终收敛到一套证据链打法：

  • 报错信息是线索不是答案：NoClassDefFoundError: org/apache/commons/lang3/Strings —— 先确认类在哪个 jar、哪个版本存在（unzip -l 逐个版本查），发现 Strings 只在 3.18.0 有，而依赖树给的是 3.13.0；
  • 反编译是终极证据：javap -p -c 看字节码，确认 Seata 自动配置的 @ConditionalOnProperty 条件、ShardingSphere 配置类的字段名、StorageUnit 从哪个 Map 取 "url"；
  • SPI 注册表是隐性依赖：META-INF/services/ 文件决定了”功能是否存在”，检查它解释了”为什么标签解析失败”（sharding-core 里只有 1 个 construct，其余在未引入的构件）；
  • **日志要抓”改写前后”**：ShardingSphere 的 Logic SQL → Actual SQL 是路由真相，比任何猜测都可靠。

3.5 变更隔离：”改了没生效”的三个陷阱

这次最大的时间浪费，是修改后没有真正生效，导致在错误版本上反复定位。三类陷阱：

  1. repackage 跳过优化：Spring Boot 的 repackage 目标发现输入 jar 未变就跳过——依赖（BOOT-INF/lib）变化不会触发重新打包，只有 classes/resources 变化才会。后果：改了 pom 以为生效，实际 fat jar 还是旧的。**对策：改依赖一律 clean package**，并养成”改完验证 jar 内容”的习惯（unzip -l | grep 版本号）；
  2. 陈旧进程：改完重启，但旧 JVM 没杀干净（pkill -f 模式不匹配），新请求打到旧进程；
  3. 工作目录错误：启动命令的 cwd 不在项目根，相对路径 jar 找不到——日志里只有一行 Unable to access jarfile，而它解释了”为什么又没变”。

方法论：先确认”你的修改真的在运行的系统里”，再开始分析”为什么没生效”。 两个检查：jar 内容、进程启动时间。

3.6 从现象反推配置契约

当”配置看起来对、运行报错”时，往往是配置与代码的契约不一致——且这种不一致通常藏在”文档没有、代码才有”的地方。这次的代表：

  • bash 3.2 的中文标点 bug：$HTTP，非 000 中 $HTTP 被多字节逗号污染成未定义变量。通过最小脚本 A/B 对照（有中文逗号报错、换成英文逗号正常）五分钟锁定；
  • Feign 415：@RequestParam 的 Feign 默认发 application/x-www-form-urlencoded，对端却是 @RequestBody —— 契约在注解里，不在任何文档里；
  • 字段名错位：authorId vs author，报 Unrecognized field，看 DTO 定义即知。

排障时始终带着一个问题：**”代码期望什么，我给了什么？”** 这条能解决一半的”灵异”问题。

4.0 真实排障时间线

先看整体节奏，再进入单案例。整个改造约分六个阶段，前两个阶段是分析，后四个阶段是验证与修复——注意时间与问题的分布规律：

两个规律值得注意：

  1. 问题密度按层递减：启动层的坑最多最密（框架配置与历史欠债），数据层其次（分片契约），链路层最少（接口契约）——这符合”存量代码问题集中在集成点”的一般规律；

案例 1：ShardingSphere 5.4.1 与 Spring Boot 3.2 的版本战争

现象：doc 服务在 ShardingSphere 数据源创建成功之后（日志已打印”分片数据源初始化完成”），紧接着抛 NoSuchMethodError: Representer: method 'void <init>()' not found。

证据：

  • 堆栈指向 YamlEngine.marshal → ShardingSphereYamlRepresenter.<init> → new Representer()；
  • mvn dependency:tree 显示 snakeyaml 2.2（Boot 3.2.5 强制）。

思维链：

  1. 先确认是谁调用无参 Representer()——是 ShardingSphere 的配置持久化（即使 Memory 模式也会 marshal 全局配置）；
  2. 关键判断：这是两个库的 API 兼容问题，不是我们的配置问题。snakeyaml 2.x 移除了无参构造器，ShardingSphere 5.4.1 编译期绑定的是 1.x API；
  3. 能否降级 snakeyaml 到 1.33？不行——Spring Boot 3.2 自己的 YAML 加载用了 snakeyaml 2.x 的 Yaml.createYaml()，降级会反过来破坏 Spring；
  4. 结论：必须升级 ShardingSphere。查 Maven Central metadata（curl maven-metadata.xml），发现 shardingsphere-jdbc-core 的版本止步于 5.4.1——5.5.x 换了构件名（shardingsphere-jdbc）；
  5. 升级 5.5.3 后，又连锁暴露了 6 个”聚合器 test scope”构件缺失（sharding-core、broadcast-core、hikari 池元数据、standalone 模式、MySQL SQL 解析器、authority）——逐一 dependency:tree 验证补齐；
  6. 最后 commons-lang3 也因 ShardingSphere 5.5.3 需要 3.18.0 的 Strings 类而强制升级。

启示：

  • 版本兼容性排查的顺序：确认 API 归属 → 确认谁强制了哪个版本 → 确认升级/降级的连锁影响 → 用中央仓库 metadata 验证构件存在性；
  • 一次升级会连锁暴露多个问题，用依赖树 + 启动冒烟验证闭环，而不是逐个试；
  • 面试时这个案例可以完整展示”依赖管理能力”：从 NoSuchMethodError 到构件演化（jdbc-core 终止于 5.4.1、5.5.x 改名、特性 test-scope）的全链路推理。

案例 2：105 张表 vs 17 个月 —— 路由配置的”数字陷阱”

现象：创建文档报 Table 'zeus_doc_history_0.doc_history_202613' doesn't exist。当时是 2026 年 8 月，路由却指向”2026 年 13 月”。

证据：

  • ShardingSphere sql-show 日志：SELECT MAX(version) 的 Actual SQL 是 UNION ALL 链接了 202608、202609、…、202613、…、202700、…、202712 共 105 个表；
  • 对比配置：actual-data-nodes: ds$->{0..3}.doc_history_$->{202608..202712}。

思维链：

  1. 先排除算法问题：写独立测试程序直接调 IntervalShardingAlgorithm，传入 2026-08-04 与无界范围——算法返回 17 个月，正确；
  2. 那 105 从哪来？观察 UNION ALL 的表名序列：202608 → 202609 → … → 202699 → 202700 → … → 202712，这是 202608 到 202712 的连续整数（105 个），不是月份（17 个）；
  3. 顿悟：$->{202608..202712} 是 ShardingSphere 表达式的数字连续范围展开，不是”月份集合”；无分片键查询（WHERE doc_id=? 没有 created_at）走全路由，广播了这 105 个节点，而数据库里只有 202608 一张；
  4. 顺带解释了 5.5.x 为什么把 INTERVAL 归为 auto 算法：它本应配 autoTables（表名由算法生成），但 autoTables 不支持分库策略（doc_history 还需要按 doc_id 分库），所以正确解是 tables + 显式枚举 17 个月表；
  5. 最后补全数据库：批量生成 4 库 × 17 月 = 68 张表（并落库为 deploy/sql/06_doc_history_shard_tables.sql 幂等脚本）。

启示：

  • “看起来像语义的东西不一定是语义”：{202608..202712} 人读是”月份”，引擎读是”数字区间”。排障要以引擎视角核对配置的每个 token；
  • 无分片键查询走全路由是 ShardingSphere 的标准行为——设计表结构时就要问”哪些查询会不带分片键”，并确保广播路径可达；
  • 独立复现环境（案例方法论 3.3）在这里是决定性武器：把路由结果完整打印出来，问题自现。

案例 3：静默失效的 scanBasePackages —— 服务”能启动”但”功能全挂”

现象：注册/登录正常（白名单接口），但创建文档报 Column 'tenant_id' cannot be null；直连 doc 服务手动带 X-Tenant-Id: 1 请求头依然 500。

证据：

  • 直连测试（绕过网关）也失败 → 排除网关透传问题；
  • 网关代码确认透传了 X-Tenant-Id；JWT 解码确认 tid: 1 存在；
  • common 的 RequestContextFilter 代码正确（读 X-Tenant-Id → 写入 UserContext）；
  • 于是怀疑：过滤器根本没有执行。

思维链：

  1. 链路”JWT → 网关 → 请求头 → 过滤器 → UserContext → service”每环单独验证，最后只剩”过滤器没挂到链上”一个可能；
  2. 检查各服务启动类：@SpringBootApplication 默认扫描 com.zeus.doc——只扫自己的包；而 RequestContextFilter 在 com.zeus.common.config，根本没被扫描；
  3. 对照 audit 服务（scanBasePackages = "com.zeus"，能正常用 UserContext）——差异即根因；
  4. 顺藤摸瓜发现这是全项目系统性缺陷：user/doc/search/file/collab 全部只扫自己的包，common 的全局异常处理器（返回统一错误体）、参数解析器（@CurrentUserId）也全部静默失效——这就是为什么之前接口报错是裸 500 而不是统一包装体。

解法：所有服务启动类统一 @SpringBootApplication(scanBasePackages = {"com.zeus.xxx", "com.zeus.common"})。

启示：

  • “能启动”≠”功能正常”：这类缺陷没有报错，只会让功能悄悄坏掉。排查方法是逐环行为验证（每环打点确认数据是否流经）；
  • 修复后立刻出现可观察信号：报错从”裸 500”变成”统一错误体”，证明 GlobalExceptionHandler 生效——用行为变化验证修复生效；
  • 面试亮点：这是典型的”系统性缺陷 + 行为驱动定位”案例，且修复收益立竿见影（一处修复，五个服务功能恢复）。

案例 4：”改了没生效”三部曲 —— 排障中最贵的学费

现象：连续多轮”修改 → 重启 → 症状依旧”，一度怀疑方向错误。

三个根因（按发现顺序）：

  1. repackage 跳过：改 pom（依赖版本）后 mvn package 显示 BUILD SUCCESS，但 fat jar 的 BOOT-INF/lib/commons-lang3-3.14.0.jar 一直没变——用 unzip -l 对比 jar 内容才确认。从此依赖变更一律 clean package，并验证 jar 内版本；
  2. 陈旧进程：pkill -f 'xxx.jar' 的匹配模式与实际命令行不一致，旧 JVM 没死，新请求由旧进程处理；
  3. 工作目录错位：启动命令的 cwd 在 /tmp/ss-test，相对路径 jar 找不到，日志只有 Unable to access jarfile——进程根本没启动，自然”症状依旧”。

启示：

  • **排障第一问永远是”我的修改真的在运行的系统里吗？”**——验证手段：jar 内容、jar mtime、进程启动时间、日志文件时间戳；
  • 这条经验直接指导了后文的”证据链思维”：先确认事实，再分析原因。

案例 5：bash 3.2 的中文标点解析 Bug —— 最小复现的教科书案例

现象：verify-chain.sh 间歇性报 line 60: HTTP�: unbound variable，同一脚本有时正常有时报错；bash -n 语法检查通过。

证据：

  • 直接执行报错，bash -x 追踪却显示 HTTP=404 赋值正常——报错在赋值之后的行；
  • 逐行对照：报错行 ok "网关可达 (HTTP $HTTP，非 000 即存活)" 中 $HTTP 后紧跟中文逗号；
  • 构造最小脚本 A/B：$HTTP， 报 unbound，$HTTP,（英文逗号）正常——五分钟锁定根因。

根因：macOS 自带 bash 3.2.57 按单字节处理变量名边界，$HTTP 后紧跟的多字节 UTF-8 字符（， = U+FF0C）污染了变量名解析，set -u 下报”变量未定义”。

解法：全项目脚本用 ${VAR} 花括号显式定界（正则批量替换 $VAR+非ASCII字符 模式），bash -n 验证。

启示：

  • A/B 最小复现是解决”间歇性/环境相关”问题的最快路径：把问题压缩到 5 行脚本，把变量隔离到单一差异；
  • 脚本兼容性要当成一等公民：macOS bash 3.2 没有关联数组（declare -A）、cd 会回显、多字节解析有 bug——跨平台脚本要用 POSIX/兼容子集 + 显式定界；
  • 面试价值：展示”从环境差异反推工具链缺陷”的能力，比背八股生动得多。

案例 6：Seata 的 CGLIB 代理危机 —— 反编译找开关

现象：doc/audit 在数据源创建成功后，报 Cannot subclass final class ShardingSphereDataSource（CGLIB 无法子类化 final 类）。

证据：

  • 堆栈指向 SeataAutoDataSourceProxyCreator.wrapIfNecessary —— Seata 在给数据源建 AOP 代理；
  • 尝试配置 seata.datasource.proxy-type: NONE 无效——属性根本没被读取；
  • 反编译 SeataDataSourceAutoConfiguration 的注解：@ConditionalOnProperty(value = "${seata.enabled:true} && ${seata.enableAutoDataSourceProxy:true} && ${seata.enable-auto-data-source-proxy:true}")——**正确的开关名是 seata.enable-auto-data-source-proxy**。

思维链：

  1. 第一反应”关掉 Seata 数据源代理”是对的，但猜错了属性名——从字节码读条件注解，而不是从文档猜；
  2. 为什么可以关？项目用 TCC 模式（@LocalTCC + @GlobalTransactional），AT 数据源代理（DataSourceProxy 包装）对 TCC 无用，关闭不影响事务功能；
  3. 顺带发现 Seata 客户端 registry 配的是 nacos，而 server 是 file 模式——配置契约不一致，一并修正为 file + grouplist 直连。

启示：

  • “关掉某个功能”之前，先确认它为什么存在、关掉会影响什么——这里是”TCC 不需要 AT 代理”的架构判断；
  • 框架配置的真相在字节码里：javap -v 看注解常量池，比翻文档快且准；
  • 这类”框架 A 与框架 B 的隐性冲突”是微服务项目的高频难点，也是面试官爱听的”跨框架集成排障”故事。

案例 7：Nacos 鉴权 403 —— 服务端开了门禁，客户端没带门卡

现象：user 服务启动后注册失败，日志反复出现 code=403, msg='user not found!'；gateway 的动态路由监听同样 403（好在代码有静态路由兜底，未阻塞启动）。

证据：

  • 报错来自 NacosServiceRegistry.register 与配置订阅的 ClientWorker——注册与配置两个客户端都被拒；
  • docker-compose 里 NACOS_AUTH_ENABLE: "true"（服务端开了鉴权）；
  • 所有服务的 bootstrap.yml 只有 server-addr/namespace，没有任何 username/password。

思维链：

  1. “user not found” 不是”用户不存在”，而是客户端没有完成认证——Nacos 2.x 鉴权开启后，未携带凭证的请求统一返回这个误导性文案；
  2. 先验证服务端确实开了鉴权（compose 环境变量），再查客户端是否配置了凭证——两端配置对齐检查；
  3. 确认全项目 7 个服务的 bootstrap.yml 全部缺凭据——这是”服务端开启、客户端没跟上”的配置契约不一致，与案例 6 的 Seata registry 问题同构（服务端 file 模式 vs 客户端 nacos 模式）。

解法：7 个 bootstrap.yml 统一补 ${NACOS_USER:nacos} / ${NACOS_PWD:nacos}（沿用项目 ${ENV:default} 风格，保留环境变量覆盖能力）。

启示：

  • **鉴权/注册类问题的第一反应是”两端配置是否对齐”**：开关、模式、凭证、命名空间，逐项对照；
  • 框架的错误文案常常有误导性（”user not found” 实为未认证），要结合服务端配置解读，而不是对着文案猜。

案例 8：Metaspace OOM —— 资源预算要按实测，不按直觉

现象：doc/audit 进程启动日志显示 Started，但随后各线程逐个抛 OutOfMemoryError: Metaspace，health 探针从 200 变成 000。最迷惑的是：它”启动了，然后慢慢死”。

证据：

  • 日志：Exception in thread "redisson-timer-4-1" java.lang.OutOfMemoryError: Metaspace，多个线程连锁死亡；
  • 我的启动参数：-XX:MaxMetaspaceSize=128m——基于”低内存机器要省”的直觉。

思维链：

  1. “Started 但慢慢死”是资源类 OOM 的典型症状——启动成功只代表 bean 装配完成，不代表类加载完毕；
  2. 为什么 128m 不够？ShardingSphere 5.5.3 升级后引入了上百个 sharding/parser/authority 构件，类数量级远超 5.4.1；-XX:MaxMetaspaceSize 限制的是元空间，与堆无关——我之前把”堆省内存”的经验错误套到了元空间；
  3. 修正为 256m 后稳定——参数调整用实测验证（连续多轮冒烟无 OOM），而非继续猜。

启示：

  • JVM 资源参数要区分堆、元空间、直接内存三个池，各自有独立的耗尽症状（OOM 文案不同）；
  • 依赖升级会改变类加载量——升级后要重新评估资源参数，这是版本升级的隐性成本；
  • 面试价值：”启动成功 ≠ 稳定运行”的认知，配合 Metaspace 的具体症状，比空谈”我调过 JVM 参数”可信得多。

案例 9：RocketMQ brokerIP1 —— 容器网络的”地址可见性”

现象：创建文档走到 MQ 发送时失败：Send [3] times, still failed, Topic: zeus-doc-sync, BrokersSent: [broker-a]；而 mqadmin clusterList 从 namesrv 容器内查询一切正常。

证据：

  • broker 注册到 namesrv 的地址是 rocketmq-broker:10911（容器主机名）；
  • 微服务跑在宿主机，解析不了容器内主机名 → 连接被拒；
  • broker.conf 里赫然写着 brokerIP1=rocketmq-broker。

思维链：

  1. “namesrv 里查得到，客户端连不上” → 问题在客户端拿到的 broker 地址——RocketMQ 客户端从 namesrv 获取 broker 地址后直连，该地址必须对客户端可见；
  2. 容器内主机名对容器内客户端可见，对宿主机不可见——地址可见性随网络命名空间变化，这是容器化服务通信的经典问题（与”容器内 localhost 不是宿主 localhost”同理）；
  3. 修复 brokerIP1=127.0.0.1 后，还要重启 broker（重新注册）和 doc（producer 路由缓存）——“改了配置要重启持有方”是第二个坑。

启示：

  • 排查网络类问题先画通信路径图：客户端 →（namesrv 给地址）→ broker，每一跳的地址对谁可见；
  • 配置修改的传播链要完整：注册方（broker）→ 路由持有方（namesrv 缓存）→ 调用方（producer 缓存），缺一环就”改了没生效”。

案例 10：Feign 契约三连 —— 415、字段名、序列化

现象：doc 服务消费 MQ 后调 search 建索引，连续三轮报错，每修一个露出下一个：

  1. HttpMediaTypeNotSupportedException: Content-Type 'application/x-www-form-urlencoded' is not supported；
  2. 改成 JSON body 后：Unrecognized field "authorId" (class DocIndexDTO)；
  3. 字段对齐后：JsonException: Jackson exception（Java 8 date/time type not supported）。

思维链（每轮都遵循同一模式：以对端错误信息为输入，看对端契约定义）：

  1. 415 根因：Feign 的 @RequestParam 参数默认编码为 form-urlencoded，而 search 端 @PostMapping("/index") 用 @RequestBody 接收——方法签名就是契约，两端注解必须一致；改用 Map<String, Object> 作 body；
  2. 字段名根因：Feign 侧叫 authorId，DTO 侧叫 author——字段名契约以 DTO 定义为准；
  3. 序列化根因：DTO 含 LocalDateTime，而 elasticsearch-java 的 JacksonJsonpMapper 用无参构造的 ObjectMapper，没有注册 JavaTimeModule——Spring Boot 自动配置的 mapper 是注入的，这里手动 new 了一个裸 mapper，丢了 Boot 的默认模块。

解法：DTO 字段对齐 + ObjectMapper mapper = new ObjectMapper().registerModule(new JavaTimeModule())。

启示：

  • 服务间调用的契约 = 注解 + 字段 + 序列化三件套，每一环都可能断，且断点由对端报错暴露——按对端错误信息逐层推进，不要一次改三处（改一处验证一处，才能定位准确）；
  • 手动 new 框架组件时，要意识到丢失了框架自动配置的默认能力（本例丢失 JavaTimeModule）——优先注入 Spring 管理的实例；

案例 11：雪花 ID 与 useGeneratedKeys —— “想当然”的代价

案例 19：审计服务”陈旧进程” —— 一个 NoClassDefFoundError 引发的全站 504

现象（用户反馈 4 个问题，3 个同根因）：

  1. 知识库删除文档：第一次点击无响应，第二次报”请求失败”；
  2. 文档编辑触发 POST /api/doc 一直 pending，直到 504；
  3. 点击历史版本 / 分享按钮报”文档创建失败”（新建文档模式下先自动创建、创建即超时）；
  4. 侧边栏底部头像 / 退出登录（独立 UI 小任务，与本次根因无关）。

证据（按时间顺序）：

  • doc 日志：[RT] 慢接口 create cost=60290ms + feign.RetryableException: Read timed out executing POST http://zeus-doc-service-audit/api/audit——60s 恰好是 Feign 默认读超时，主链路在等一个下游调用；
  • 堆栈关键帧全在 io-9002-exec-10（请求线程）：DocService.create → DocService.auditAsync → auditFeignClient.record——标了 @Async 的方法却在请求线程同步执行；
  • audit 日志：869 次 Exception: java.lang.NoClassDefFoundError thrown from the UncaughtExceptionHandler in thread "NettyClientScan_thread_N"，每 ~3 秒新建一个线程即死（崩溃循环）；
  • curl 直打 audit 服务（绕过网关）：
  • jstack：audit 的 Tomcat 工作线程全部 WAITING 空闲——请求根本没进 controller（矛盾点，见思维链）；
  • JFR 抓到缺失类名（869 行日志只有异常类型、没有类名，换 JFR 才拿到真名）：
  • 矛盾点：unzip -t 校验 jar 完整，AnnotationCollector$TwoAnnotations.class 确实在 jackson-databind-2.15.4.jar 里，单独 Class.forName 也能加载——类在磁盘产物里，运行时却加载不到；
  • 铁证：lsof -p 看进程实际打开的文件：
  • 时间线复核：audit 进程启动 23:30:51，jar mtime 23:33——jar 在进程运行期间被 mvn package 重建替换；瘦 jar（57KB，无 BOOT-INF/lib）是 jar:jar 阶段的中途产物，spring-boot repackage 还没跑完。

思维链：

  1. create 60s 超时 → 60s 是 Feign 读超时的特征值 → 主链路在等下游 → 堆栈指出等的是审计服务；
  2. @Async 为何不生效？Spring AOP 代理只拦截外部调用，create() 里直接调同类方法（this.auditAsync()）属于自调用——代理静默绕过，审计 Feign 变成请求线程上的同步调用；
  3. audit 进程活着但业务接口挂 → jstack 却显示 Tomcat 线程空闲 → 请求死在更早的阶段：JFR 显示异常发生在 http-nio-9006-exec-2 的序列化路径上（AnnotationCollector$NCollector.asAnnotations() 首次 introspection 需要 TwoAnnotations）——类加载失败发生在请求处理的早期，且异常处理本身也加载失败（ModelAndViewDefiningException / ThrowableProxy 全缺），响应永远写不出去，客户端只能等 60s 超时；
  4. 类存在却加载不到 → 文件系统真相与进程真相不一致 → 用 lsof 看进程打开的文件 → 陈旧瘦 jar 实锤；
  5. 崩溃循环的 NettyClientScan_thread 同理：RocketMQ 客户端扫描线程想打日志，logback 类加载失败 → 线程死 → 3 秒后新线程再死——连错误本身都打不出来，只能靠 JFR 绕过日志层取证。

难点（本次最费时的三个坑）：

  1. UncaughtExceptionHandler 日志只有类型、没有缺失类名：869 行 NoClassDefFoundError thrown from... 全是重复噪音（Netty 默认 handler 只打 e.getClass().getName()）。解法：JFR 的 jdk.JavaErrorThrow 事件带完整 message + 调用栈——日志层失效时，取证要下沉到 JVM 层；
  2. “进程活着”的假象：/actuator/health 200 会让人误判服务正常——健康检查只证明 Spring 容器活着，证明不了接口可用；删除/创建的 60s 挂起都发生在”容器活着”的前提下；
  3. “类在 jar 里但加载不到”的矛盾：unzip -t、Class.forName 验证的是磁盘上现在的文件，而进程运行在启动那一刻打开的文件（inode）上——文件系统验证与进程运行时隔离，必须 lsof -p <pid> 直接看进程的文件句柄。

解法：

  1. 重启审计服务到正确产物（mvn clean package 后重启，lsof -p 确认打开的是 fat jar）；
  2. 代码加固一——修复 @Async 自调用：拆独立 Bean AuditLogService.recordAsync()，DocService 注入调用。@Async 经代理生效；audit-executor 已被 TTL 包装，UserContext 自动回放到异步线程；
  3. 代码加固二——审计接口永不挂起：syncSend 加 3s 超时（此前无超时，客户端异常时无限挂）；AuditController.record() 捕获投递失败后降级直写 DB——审计是所有主链路的旁路，必须可超时、可降级；
  4. 前端：移除侧边栏底部用户卡片（独立小任务）。

启示：

  • 陈旧进程是”改了没生效”的终极形态：前两轮（案例 4/18）是”改了没重新部署”，这次是”构建进行中被启动”——进程从出生起就是错的。验证运行产物的金标准是 lsof -p <pid> 看进程实际打开的文件，jar mtime 与进程启动时间的对照只能作为线索；
  • 服务可用性要拆三层：进程活着 ≠ 接口可用 ≠ 业务正确——health 200 只证明第一层。删除、创建这类”有下游调用”的功能，必须直接打业务接口验证；
  • @Async 自调用是最隐蔽的异步失效：代码注释写得再对，自调用让代理静默失效，还伴生双重风险——① 旁路变同步拖垮主链路（本次 create 被拖 60s）；② 异常被 try/catch 吞掉，接口”伪成功”；
  • 旁路调用必须按最坏情况设计：审计这类非核心调用，永远不该有能力拖垮主链路——3s 超时 + 失败降级是标配，不是锦上添花；
  • 用户反馈的多个问题先找共同根因：4 个问题里 3 个是同一因果链的投影（审计服务挂 → 创建/删除/版本/分享全挂），先修根再谈个例，避免在症状上打补丁。

  • 注意：先 JFR.start 再触发复现，抓取窗口要覆盖到异常时刻；jdk.JavaErrorThrow 只记录 Error（jdk.JavaException 记录 Exception）。

6.1 “你做过最有价值的一件事” —— 叙事模板

  1. 先做完整的静态审计（依赖树、配置一致性、代码接线），再动手启动——把启动当作验证手段而非定位手段；

  3. 用证据链定位（日志、反编译、SPI 注册表、中央仓库 metadata），不猜；
  4. 修复遵循变更隔离（一次一个变量，改依赖必须 clean package 并验证 jar 内容）。

结果：最终以 6 个中间件 + 5 个微服务跑通全部核心功能，冒烟测试 9/9 全绿；产出最小化编排、一键启动脚本和双模式运行指南；全链路定位并修复 40+ 个存量缺陷。

沉淀：这套”静态审计先行 + 分层定位 + 最小复现 + 证据链”的排障方法，我后来在别的项目里也一直在用——它把”调试”从碰运气变成了工程方法。

6.2 “项目中遇到的难点，怎么解决的” —— STAR + 方法论框架

选 1-2 个案例（推荐案例 2 分片路由或案例 1 版本战争），按四步讲：

  1. S（情境）：一句话讲清技术背景（如”doc_history 按月份分表，无分片键查询会全路由”）；
  2. T（任务）：要解决的问题是什么（”创建文档一直报表不存在，且表名指向 13 月”）；
  3. A（行动）：重点讲思维过程，不是操作流水——“我先用独立环境复现，看到 UNION ALL 的 105 张表名，意识到 {202608..202712} 是数字范围而非月份集合；再对照算法测试确认不是算法问题，最终定位到配置契约”；
  4. R（结果）：量化结果（68 张表批量建齐、路由正确、链路全绿）。

面试官追问”你怎么想到的？”时，诚实还原推理链比展示”我很聪明”更可信——包括走弯路的部分（比如我一开始也以为是算法 bug，是复现实验纠正了我的方向）。

6.3 高频追问攻防

追问 应答要点
前端怎么避免雪花 ID 精度问题？ 双保险：后端 common 全局 Long→String 序列化（JacksonConfig），前端类型层把 ID 一律声明为 string 并禁止 Number() 转换——19 位雪花 ID 超出 JS 2^53，任何数字路径都会静默丢精度且”更新 0 行不报错”伪装成成功
Seata TCC 的 Confirm 无限重试怎么止损？ 先确认 actionContext 是否有参数（Seata server 日志对比发起方/参与者分支）；框架缺陷无法根治时，Confirm/Cancel 缺参数返回成功终止重试——Try 已提交的数据保持不变，业务以 Try 结果为准，状态停留 PENDING 可接受
为什么不直接把表结构改成自增 ID？ 雪花 ID 是跨库全局唯一的设计约束（分库分表下自增会撞号），代码生成 + 显式插入才是正解——改动要尊重架构约束
为什么升级 ShardingSphere 而不是降级 snakeyaml？ 降级会破坏 Spring Boot 3.2 自身的 YAML 加载（它依赖 snakeyaml 2.x 新 API），升级是唯一双向兼容路径——升级/降级要评估连锁影响
这些是历史遗留问题，为什么你发现了？ 因为我把”启动成功”定义为”功能可验证”，而不是”进程活着”；冒烟测试 + 行为验证（如错误体从裸 500 变成统一包装）把隐性缺陷暴露出来
40 个问题怎么保证没有漏网？ 三层闭环：静态审计（依赖/配置/接线）→ 启动冒烟（verify-chain 9 项）→ 功能验证（verify-infra 的 ES/MQ 链路）
最小化方案和全量方案如何共存？ 同一套端口/数据卷/命名，lite 编排只减服务不减契约，切换不丢数据——设计上为两种模式留了无缝切换

6.4 面试官可能的深挖路径

面试官不会只满足于你讲的故事，一定会顺着往下挖。以下是按”从具体到抽象”排列的深挖方向及应答准备：

深挖方向 可能的问法 应答准备
技术细节 “ShardingSphere 无分片键查询为什么走全路由？” 标准策略需要分片键做精确路由；缺失时降级为广播所有 actual-data-nodes——顺带讲 INTERVAL 范围路由的区间计算
架构理解 “为什么不用 autoTables？” autoTables 只支持表策略，不支持分库策略；doc_history 需要 doc_id%4 分库 + created_at 分表双维度，只能 tables + 显式枚举
权衡取舍 “升级到 5.5.3 会不会引入新问题？” 会，所以我用依赖树 + 冒烟闭环验证：6 个缺失构件逐个补齐、commons-lang3 强制 3.18、升级后元空间参数重新评估——升级是决策，验证是闭环
工程纪律 “你怎么防止这类问题再次发生？” 三层防线：①建表/启动/验证脚本落库，环境可重建；②依赖升级必须过冒烟（CI 关卡）；③”启动成功 ≠ 功能正常”的验证意识（统一错误体、行为断言）
团队协作 “如果同事遇到类似问题，你推荐的第一步是什么？” 先做 10 分钟静态审计（依赖树 + 配置对照 + 进程归属），再决定是否启动调试——把”启动”从定位手段降级为验证手段
反思能力 “重来一次，哪里会做得不一样？” ①第一次冒烟前先做全量静态审计（能省掉大半轮次）；②改依赖后立刻 clean package 并验证 jar 内容（避免”改了没生效”的无效循环）；③验证脚本先写好再启动服务（让每一次启动都有明确的验收标准）

  1. 主线叙事：用 6.1 的模板讲”最有价值的事”，方法论（第三节）+ 时间线（4.0）支撑”怎么做的”；
  2. 单案例深挖：任选一个案例（推荐 2/1/3），按【现象→证据→思维链→根因→解法→启示】完整讲 2 分钟，展示”过程而不是结论”；
  3. 方法论文档化：把”静态审计先行、分层定位、最小复现、证据链、变更隔离、契约反推”六条方法论背熟——它们能在任何”项目难点”问题上复用，比具体技术更有迁移价值。

6.6 一句话总结

“我做的最有价值的一件事，是把一个从未在真实环境完整运行过的微服务系统，在 8GB 的机器上跑通并全部验证——过程中定位了 40 多个横跨依赖、配置、代码、脚本的存量缺陷。我最大的收获不是修了多少 bug，而是沉淀了一套’静态审计先行、分层定位、最小复现、证据链驱动‘的排障方法，以及’能启动 ≠ 功能正常’的验证意识。”

七、沉淀与反思

工程层面：

  1. 文档与现实的差距：项目文档描述的能力（分库分表、TCC、搜索链路）在真实环境从未完整验证过——“文档声称的”和”代码实际的”要分开对待，以运行验证为准；
  2. 版本管理是隐性债务：5.4.1 与 Boot 3.2 的组合从未被验证，说明依赖升级缺少”启动即验证”的关卡；建议 CI 加入最小化冒烟；
  3. 可复现性：分片表建表脚本、一键启动脚本、验证脚本落库后，整个环境可从零重建——这是比”修好”更重要的资产；
  4. ID 精度与幂等是前端/删除链路的隐性债：雪花 ID 精度问题在”只做演示”时永不暴露（ID 恰好在安全范围内），一上真实数据（19 位）就炸；删除链路的多重幂等（唯一键 upsert、TCC 幂等跳过）应在设计时内置而非排障时补齐；
  5. 框架缺陷要有”证据 + 止损”两级应对：Seata 2.0 参与者侧 actionContext 收集失效属框架缺陷，用”发起方 vs 参与者”日志对比钉死证据后，降级止损（缺参成功 + 状态停留 PENDING）优于无限重试——业务正确性优先，完美方案后置；
  6. 进程级产物验证是最后一道防线：”代码改了、jar 重建了”都不够——进程可能运行在构建中途的旧产物上（案例 19：mvn package 进行中启动，进程从出生起就用着 57KB 瘦 jar）。验证运行产物的金标准是 lsof -p <pid> 看进程实际打开的文件，jar mtime 与进程启动时间对照只能作为线索；重启类操作前必查；
  7. 旁路调用要按”最坏情况”设计：审计这类旁路（异步 Feign + MQ）一旦被自调用变成同步（@Async 代理失效），故障就传染为主链路超时——异步边界（独立 Bean）与超时降级（3s + 直写 DB）缺一不可；服务可用性要拆三层看：进程活着 ≠ 接口可用 ≠ 业务正确。

思维层面：

  1. 排障的 80% 是问对问题：”这是哪一层的错？””我的修改真的生效了吗？””代码期望什么，我给了什么？”三个问题能覆盖绝大多数场景；
  2. 慢即是快：第一次陷入”启动-修复”循环时，效率反而最低；系统性静态审计花的时间，在启动阶段成倍赚回；
  3. 把弯路讲成方法论：面试中展示”我犯了什么错、如何纠正”比展示”一路顺风”更有说服力——真实性和反思能力是面试官最看重的信号。

Posted on 2026-08-06 In 项目实战 Word count in article: 5.9k Reading time ≈ 21 mins.

一、项目概述

Zeus-Doc 是面向多租户企业的知识库文档中台，提供文档创作、协同编辑、全文检索、文件存储、审计追溯等完整能力。系统采用 Spring Cloud 微服务架构，按业务边界拆分为 6 大核心服务 + 1 个网关，背后由 MySQL、Redis、Elasticsearch、MinIO、RocketMQ 等中间件支撑。

核心业务能力：

  • 文档 CRUD + 版本管理（全量快照 + Diff-Match-Patch 增量补丁）
  • 三级缓存（Caffeine → Redis → MySQL）+ 布隆过滤器 + 互斥锁重建
  • 实时协同编辑（Netty WebSocket + OT 算法合并）
  • ES 全文检索（高亮 + 聚合 + Sentinel 熔断降级）
  • 大文件分片上传 + 零拷贝合并（MinIO）
  • 审计日志分库分表（ShardingSphere）+ Seata TCC 分布式事务

二、需求分析与系统边界

1.1 业务背景

Zeus-Doc 是面向中大型企业的「知识库文档中台」，提供文档全生命周期管理：创建、富文本/Markdown 编辑、多人协同编辑、版本回溯、全文检索、文件附件、细粒度权限审计与回收站。系统采用 SaaS 多租户模型，需要支撑单租户日均 50 万次文档读、峰值 3000 QPS、千人同时在线协同编辑。

1.2 核心功能需求

模块 关键需求 性能指标
文档管理 CRUD、版本历史、回收站、分享链接 读 RT < 50ms（命中缓存）
协同编辑 实时多人协同、OT 冲突合并 WebSocket 5000 连接/节点
全文检索 ES 倒排、高亮、聚合 搜索 RT < 200ms
文件存储 大文件分片上传、断点续传 单文件最大 2GB
审计日志 全量行为留痕、租户隔离 异步落库不阻塞主流程
用户权限 RBAC + 租户隔离 JWT 鉴权 < 5ms

1.3 系统边界

  • 做：文档中台业务能力、多租户隔离、跨服务最终一致事务、协同编辑冲突合并。
  • 不做：即时通讯（IM）、视频会议、OA 审批流；这些由上游系统通过 OpenAPI 接入。

1.4 非功能性约束

  • 可用性 ≥ 99.9%，核心读链路支持同城双活；
  • 数据一致性：金融级强一致非目标，业务最终一致 + 审计可追溯即可；
  • 可扩展性：水平扩容无状态化，分库分表承载亿级 doc_history。

五、微服务拆分说明

4.1 拆分原则

  1. 领域驱动（DDD）：按业务领域而非技术分层拆分；
  2. 生命周期独立：每个服务可独立部署、扩容、故障隔离；
  3. 数据 ownership：每个服务独占自己的数据库，跨服务仅通过 RPC/MQ 通信。

4.2 职责边界矩阵

服务 核心领域 数据所有权 对外能力

collab 协同会话 Redis（会话态） WebSocket、OT 合并、在线广播
search 检索索引 Elasticsearch 全文检索、聚合统计
file 对象存储 MinIO 上传/下载/秒传/分片
audit 审计/回收站 zeus_audit 分片库 审计查询、回收站恢复、TCC 编排

4.3 服务间依赖

依赖方向严格单向：gateway → 各业务服务；doc → audit（Feign，TCC 分支）；doc → collab（协同触发）；doc → search（MQ 异步解耦）。审计侧 DocDeleteTccFacade 作为 TCC 编排方开启 @GlobalTransactional，doc 侧 DocDeleteTccActionImpl 作为分支参与同一 XID，XID 经 Feign 拦截器透传，不存在反向同步依赖。

六、技术选型决策理由

3.1 为什么选 MySQL 而非 MongoDB

维度 MySQL 8.0 MongoDB
事务 强 ACID，InnoDB 行锁 4.0+ 多文档事务性能差
生态 DBA 成熟、运维成本低 适合 schema-free 场景
一致性 文档元数据强一致要求高 最终一致为主
分片 ShardingSphere-JDBC 透明路由 内置 sharding 但运维黑盒

结论：文档元数据、审计、回收站需强事务保证（删除走 TCC 跨库），MySQL 更稳妥。文档正文虽是「大文本」，但正文存储于 Redis/MinIO 缓存层，DB 只存元数据 + 摘要，MySQL 完全胜任。MongoDB 在 schema 多变场景更优，本项目 schema 稳定，故不选。

3.2 为什么选 MinIO 而非 FastDFS

维度 MinIO FastDFS
协议 标准 S3 API 私有协议
运维 单二进制、K8s 友好 Tracker/Storage 双角色复杂

3.3 为什么选 Tomcat

  • 协同服务已用 Netty：collab 服务长连接用 Netty，HTTP 接入层用 Tomcat 避免技术栈分裂。
  • 生态成熟：jstack/arthas/GC 调优经验沉淀多，max-threads/max-connections/accept-count 三参数模型清晰（见 application.yml 第 3-11 行）。
  • 压测拐点可控：见《03-性能压测报告》，max-threads=200 时 TPS 拐点出现，调到 500 边际收益递减。

1. 主存储：MySQL 8.0 而非 MongoDB

决策维度 MySQL 8.0（采用） MongoDB
团队熟悉度 高，DBA/运维链路成熟 中等，需重建排障体系
事务能力 InnoDB 强一致性事务，原生 XA 4.0+ 多文档事务性能损耗大、限制多

决策维度 MinIO（采用） FastDFS

结论： 文件服务需要”前端直传 + 签名 URL + 分片上传”能力，MinIO 的 S3 兼容性让这些能力开箱即用，且部署轻量、与 Spring 生态集成度高。ZeroCopyStorage（zeus-doc-service-file/.../minio/ZeroCopyStorage.java）通过 FileChannel.transferFrom 调用 Linux sendfile 实现分片零拷贝合并，与 MinIO 配合良好。

3. Web 容器：Tomcat 而非 Undertow/Netty

决策维度 Tomcat（采用） Undertow Netty（裸）
Spring Boot 默认 是，零配置即可用 需替换 starter 需自行实现 HTTP 协议栈

十三、高可用与容灾

9.1 无状态化

业务服务（user/doc/collab/search/file/audit）无本地会话状态，会话存 Redis，支持 K8s 水平扩缩容。collab 的 WebSocket 会话通过一致性哈希路由 + Redis pub/sub 跨节点广播。

9.2 限流降级三道防线

  1. Gateway 全局限流：Sentinel 集群限流，挡住异常流量；
  2. 接口级限流：@RateLimit 注解 + Redis Lua（RateLimitInterceptor）；
  3. 热点降级：QPS>100 的热点文档仅查 L1+L2 不回源 DB（CacheService.shouldOnlyHitCache）。

9.3 优雅关闭

线程池配置 setWaitForTasksToCompleteOnShutdown(true) + awaitTerminationSeconds=30（ThreadPoolConfig.java:100-101），Spring Boot 优雅停机 + K8s preStop hook 等待 30s 处理完在途请求。
