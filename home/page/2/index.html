5年后端进阶方向

Posted on 2026-09-11 Word count in article: 2.2k Reading time ≈ 8 mins.

工作 5 年左右的后端，最危险的状態是：什么都会一点，但什么都不精；能写业务，但扛不住事；能完成需求，但做不了技术决策。

这个阶段的核心不是“学更多”，而是从“实现者”变成“负责人”。如果只能选三个重点，我的排序是：

系统设计 > 问题定位 > 性能调优 > 工程能力 > 源码 > 项目实践

项目实践不是单独的能力，而是训练以上能力的载体。没有项目实践，其他都是纸上谈兵；但只有项目实践，没有刻意训练，就是重复劳动。

一、先看清 5 年经验的分水岭

阶段 核心能力 评价标准
1-3 年 实现能力 能把需求变成代码，能改 Bug
3-5 年 负责能力 能独立负责一个模块/系统，能定位线上问题，能做小范围设计
5-8 年 决策能力 能做技术选型、架构设计、带小团队、对稳定性负责
8 年以上 业务/战略 技术驱动业务，定方向，控成本

5 年经验如果还在拼“谁写的代码多”，方向就偏了。你应该拼的是：谁能让系统更稳、更快、更省、更好维护。

二、各项能力优先级与训练方法

🥇 第一优先级：系统设计（决定天花板）

这是 5 年经验最该补的课。不是画几张架构图，而是在约束下做权衡。

要训练的具体能力：

  • 能独立设计一个中型系统：电商订单、支付、IM、Feed 流、权限系统等。
  • 能画清楚：部署拓扑、调用链路、数据流向、存储选型。
  • 能做容量估算：QPS、存储、带宽、机器数。
  • 能权衡：CAP、一致性、可用性、成本、开发效率。
  • 能设计高可用：限流、熔断、降级、隔离、重试、幂等。
  • 能设计数据层：分库分表、缓存策略、读写分离、冷热分离。
  • 能设计消息链路：顺序、幂等、堆积、死信、最终一致性。

训练方法：

  1. 复盘现有系统：画出你当前负责系统的架构图，标出单点、瓶颈、故障域。
  2. 做重构方案：假设流量涨 10 倍，哪里会挂？怎么改？写一份方案。
  3. 读经典：《数据密集型应用系统设计》《凤凰架构》《高性能 MySQL》。
  4. 用 C4 模型：Context、Container、Component、Code，逼自己分层表达。
  5. 参与设计评审：主动旁听或主导，学习别人怎么权衡。

自测标准： 给你一个模糊需求，你能在 1 小时内给出可落地的架构草案，并说清取舍。

🥈 第二优先级：问题定位与线上排障（决定信任度）

5 年经验，如果线上出问题你还只会重启，那很难让人放心。能快速定位问题，是资深工程师的入场券。

要训练的具体能力：

  • CPU 飙高：top → jstack → 定位线程 → 代码行。
  • 内存泄漏/OOM：jmap dump → MAT 分析 → 大对象/GC Roots。
  • 死锁/线程阻塞：jstack 看 BLOCKED/WAITING。
  • 慢 SQL：explain → 索引 → 锁 → 执行计划。
  • GC 问题：看懂 GC 日志，判断 YoungGC/FGC 频率与耗时。
  • 网络问题：tcpdump、netstat、连接池、TIME_WAIT。
  • 中间件问题：Redis 热 key、大 key；MQ 堆积；ES 慢查询。
  • 全链路追踪：TraceId 串起日志，定位跨服务延迟。

工具必须熟练：

  • Arthas：watch、trace、jad、tt。
  • jstack、jmap、jstat、jcmd。
  • MAT、VisualVM、Async Profiler。
  • explain、show processlist、慢查询日志。
  • tcpdump、wireshark、iftop。

训练方法：

  1. 主动参与线上值班，不要怕出事。
  2. 建故障演练：模拟 CPU 100%、内存泄漏、慢 SQL。
  3. 写故障报告：现象 → 影响 → 排查 → 根因 → 修复 → 防复发。
  4. 复盘历史故障：把公司过往事故拿出来，自己推演一遍。

自测标准： 线上 CPU 100%，你能在 10 分钟内定位到具体代码行。

🥉 第三优先级：性能调优（决定系统上限）

调优不是背参数，而是一套方法论：监控 → 瓶颈 → 假设 → 验证 → 固化。

要训练的具体能力：

  • JVM 调优：堆大小、GC 选择、GC 参数、内存布局。
  • MySQL 调优：索引优化、执行计划、锁、事务隔离、分库分表。
  • Redis 调优：大 key、热 key、持久化、集群、缓存策略。
  • MQ 调优：批量、压缩、分区、消费并行度、堆积处理。
  • 线程池调优：核心/最大/队列/拒绝策略，隔离不同业务。
  • 全链路压测：JMeter、wrk、 Gatling，找 TP99 瓶颈。
  • 操作系统调优：文件句柄、TCP 参数、内存交换。

训练方法：

  1. 本地造数据：50 万行 MySQL，压测不同索引。
  2. 线上灰度：小流量验证调优效果。
  3. 读源码：线程池、HashMap、ConcurrentHashMap、Netty。
  4. 看监控：Prometheus + Grafana，建立性能基线。

自测标准： 接口 TP99 从 500ms 降到 100ms，你能说清每一步做了什么、为什么。

🏗️ 第四优先级：工程能力（决定协作效率）

5 年经验不能只对自己负责，还要对交付质量、团队效率负责。

要训练的具体能力：

  • CI/CD：GitLab CI、Jenkins、Docker、K8s 基本编排。
  • 可观测性：日志规范、Metrics、Tracing、告警。
  • 测试策略：单元测试、集成测试、契约测试、混沌工程。
  • 代码质量：CheckStyle、SonarQube、Code Review 规范。
  • 发布策略：蓝绿、灰度、金丝雀、回滚。
  • 文档能力：设计文档、接口文档、故障报告、复盘。
  • 协作推动：跨团队沟通、需求评审、技术方案宣讲。

训练方法：

  1. 主导一次小项目：从需求到上线，完整走一遍。
  2. 写一份技术方案：让不懂的人也能看懂。
  3. 推动一个改进：比如引入 SonarQube、优化发布流程。

自测标准： 你能带 2-3 个人完成一个中等项目，并保证按时高质量交付。

📖 第五优先级：源码（按需，不要为了读而读）

源码是解决问题的手段，不是目的。5 年经验应该有选择地深入。

重点源码：

  • JDK：HashMap、ConcurrentHashMap、AQS、线程池、ArrayList。
  • Spring：Bean 生命周期、循环依赖、AOP、事务。
  • MyBatis：Mapper 代理、SQL 解析、缓存。
  • Netty：Reactor 线程模型、ByteBuf、粘包拆包。
  • 中间件：RocketMQ/Kafka、Redis、Elasticsearch 核心机制。

训练方法：

  • 带着问题读：线上遇到循环依赖，再去看三级缓存。
  • 画流程图：把核心流程画出来，比读十遍强。
  • 写 Demo：手写一个简化版线程池、IOC 容器。

自测标准： 能说清 Spring 循环依赖为什么需要三级缓存，而不是两级。

🚀 项目实践：不是能力，是训练场

项目实践本身不构成能力，刻意练习才构成能力。

正确姿势：

  • 不要只做 CRUD，主动认领有挑战的模块。
  • 不要只完成需求，主动思考为什么这么做、有没有更好的方案。
  • 不要只写代码，主动参与设计、评审、排障、调优、复盘。
  • 不要只做新功能，主动做重构、稳定性、性能优化。

自测标准： 你能否说出过去一年，你负责的系统在稳定性、性能、可维护性上具体提升了多少？

三、时间分配建议（每周 10 小时学习）

方向 时间 具体动作
系统设计 3h 读 1 篇经典 + 画 1 张架构图 + 写 1 份方案
问题定位/调优 3h 本地模拟故障 + 分析 GC/慢 SQL + 写复盘
源码 2h 带着问题读 1 个核心流程 + 画图
工程/软技能 2h 写文档、推动改进、参与评审

项目实践贯穿始终：把学习内容直接应用到当前项目，哪怕只是优化一个接口、加一个监控。

四、常见误区

  • ❌ 只刷题：算法是敲门砖，5 年经验更看系统设计和稳定性。
  • ❌ 只读源码：读了一堆，线上问题还是不会定位。
  • ❌ 追新框架：学不完，底层原理和设计思想才是根本。
  • ❌ 忽视业务：不懂业务，设计就是空中楼阁。
  • ❌ 只做不说：不会写方案、不会汇报，影响力上不去。
  • ❌ 重复劳动：三年经验用五年，而不是五年经验。

五、一句话总结

5 年经验的后端，重点训练三件事：能设计（系统设计）、能兜底（问题定位）、能优化（性能调优）。工程能力是放大器，源码是工具箱，项目实践是训练场。

如果只能选一个立刻开始的动作：画出你当前负责系统的架构图，标出三个最可能挂的点，并写出改进方案。 这一步做完，你就已经进入资深工程师的思考模式了。

CLI&Vim 快捷操作

Posted on 2026-08-25 Word count in article: 1.8k Reading time ≈ 6 mins.

CLI

Linux 默认的 CLI（Bash/Zsh）使用的是 Emacs 风格的快捷键，所有操作都能在主键盘区完成，手完全不用离开打字位。

光标移动（告别方向键）

快捷键 作用 记忆法（谐音/联想）
Ctrl + A 跳到行首 A = Ahead（开头）
Ctrl + E 跳到行尾 E = End（结尾）
Alt + B 向左跳一个单词（单词首） B = Back（向后）
Alt + F 向右跳一个单词（单词尾） F = Forward（向前）
Ctrl + XX 在当前位置和行首之间来回跳 （用于临时看开头）

Mac 用户：Mac 的 Alt 键默认不生效，需要开启 Terminal -> Settings -> Keyboard -> 勾选 “Use Option as Meta key”，或者将 Alt 替换为 Esc 键（先按 Esc 再按 B/F）。

命令修改（删除与撤销）

方向键只能移到错误字符处按 Delete，太慢了。直接用以下组合按词删除或整行删除：

快捷键 作用 使用场景
Ctrl + U 删除光标前的所有内容（剪切） 输错密码或不想要前半段了
Ctrl + K 删除光标后的所有内容（剪切） 保留开头，删掉后面
Alt + Backspace 删除光标前的一个单词 删掉刚输错的参数
Alt + D 删除光标后的一个单词 删掉光标后面的单词
Ctrl + W 删除光标前的一个路径/大块字符 比 Alt+Backspace 切得更狠
Ctrl + Y 粘贴（黏贴）刚才 Ctrl+U/K/W 剪切的文字 相当于“剪切板”粘贴

💡 救命的撤销：Bash 默认没有 Ctrl+Z 撤销，但你可以按 **Ctrl + _**（下划线）来撤销上一次编辑操作。

命令历史（告别上下键翻找）

按几十次 ↑ 方向键找旧命令是最大的时间杀手。

快捷键 作用 说明
Ctrl + R 反向历史搜索（最核心） 输入关键字，实时匹配历史命令。按多次 Ctrl+R 会在匹配项间跳转。
Ctrl + P 上一条 等同于 ↑ ，但手不用移开主键区。

进程控制（命令行常用）

快捷键 作用 说明
Ctrl + C 强制中断当前命令/进程 卡住时按（发送 SIGINT）
Ctrl + D 退出终端 或 发送 EOF 相当于输入 exit；在命令行中空按会注销会话
Ctrl + Z 挂起当前进程（放到后台） 误操作大文件打开时，按 Z 挂起，再用 bg 放后台跑
Ctrl + L 清屏 等同于输入 clear，屏幕瞬间清爽

高阶彩蛋

这几个属于“不用记，但用一次就回不去”的技巧：

  • Alt + .（点号）：粘贴上一条命令的最后一个参数。
    • 场景：刚 cat /etc/nginx/nginx.conf 看完，想用 vim 改它。输入 vim，然后按 Alt + .，路径自动补全。
  • **Alt + 数字键 + 快捷键**：重复执行操作。
    • 场景：按 Alt + 3 + Alt + D，会向后删除 3 个单词。
  • **!!**：代表上一条完整命令（虽不是快捷键，但极常用）。
    • 场景：apt install nginx 权限不够，直接输入 sudo !! 回车，完美。

iTerm2 独门“超能力”

选中即复制，右键即粘贴（省去 Cmd+C/V）

  • 设置：Preferences -> General -> Selection -> 勾选 **Copy to pasteboard on selection**。
  • 用法：鼠标选中任何文字，自动复制到剪贴板；点击鼠标中键（滚轮按下去）或 Shift + 右键，直接粘贴。手完全不用去够 Cmd 键。

强大的“智能补全” (Cmd + ;)

  • 输入前半截命令，按 Cmd + ;（分号键），iTerm2 会弹出一个下拉框，模糊匹配你的历史命令和目录结构。想找几天前一串很长的 docker run... 命令？敲几个字母，按这个组合，比 Ctrl+R 搜得还直观（可视界面）。

粘贴历史 (Cmd + Shift + H)

  • 按 **Cmd + Shift + H**，会弹出你最近复制过的所有文本片段（不仅仅是命令行里的，系统全局复制过的都在）。找密码、找路径、找刚才复制的一长串 JSON，极其方便。

命令“即输即显”极速定位

  • 按住 Cmd 键，鼠标点击命令行中的任意路径/文件名，iTerm2 会自动识别并尝试打开它（ls 出来的文件，按住 Cmd 点击就用默认编辑器打开了，非常酷）。
  • 按住 Shift 键，鼠标框选文本，可以进行矩形块状选择（对于复制表格日志非常有用）。

切换标签页和分屏

  • 切换上一个/下一个标签页：Cmd + 左方向键 和 Cmd + 右方向键。（如果嫌手要挪到方向键，可以改为 Cmd + Shift + [ 和 Cmd + Shift + ]，和 Chrome 浏览器逻辑一致）。
  • 垂直/水平分屏（把同一个窗口切成两块独立终端：左边用 vim 改代码，右边用命令行执行编译，不用切来切去）：
    • Cmd + D：垂直左右分屏。
    • Cmd + Shift + D：水平上下分屏。

1. 系统信息与性能排查

1.1 排查顺序：先看全局，再钻进程

服务器变慢时，顺序永远是「负载 → CPU → 内存 → IO → 进程 → 线程」，从粗到细逐层收敛。四类资源的快捷判定：

graph TD
    S[Server Slow] --> L[uptime: load average]
    L --> C[top / vmstat: us sy wa]
    L --> M[free: mem and swap]
    L --> I[iostat: await and util]
    C --> P[top -Hp: hot thread]
    P --> J[jstack: match hex TID]
    I --> D[du / lsof: who writes the disk]
    M --> O[dmesg: OOMKiller]

1.3 生产实践案例：服务器卡顿，页面打开缓慢

场景：业务反馈服务器卡顿，页面打开缓慢。

处理结果：发现是某个定时任务与业务高峰叠加，临时降低任务频率，并优化了代码中的死循环。

复盘结论：r 队列、us/sy、单核打满这三条线索都指向 CPU 竞争；如果 wa 高而 us 低，方向就要换到磁盘（见第 3 章）。

1.4 动手验证：亲手复现一次「CPU 打满」

预期观察点与判定标准：

观察点 正常 异常判定
uptime 的 load 1 分钟值 ≈ 任务数 持续 > 核数 × 1.5 视为过载
us（用户态） 与业务量匹配 yes 这类纯计算会顶到接近 100%
wa（IO 等待） 个位数 持续 > 20% 说明磁盘是瓶颈
si/so（Swap） 0 只要非零，立即查内存
r 列（vmstat） ≤ 核数 持续 > 核数 = 有任务排队

ln：软链接与硬链接

命令 说明 生产场景

3.3 深挖：df 和 du 对不上账的三种原因

排查磁盘时最常见的困惑是「du -sh 加起来才 40G，df 却说用了 90G」。原因就三类：

现象 机制 处理
有进程还开着已删除的文件 Linux 文件在最后一个引用关闭前不释放块（inode 链接数为 0 但 fd 仍存在） lsof +L1 找到进程 → 重启进程 / truncate -s 0 /proc/<pid>/fd/<fd>
文件系统保留块 ext4 默认给 root 保留 5%（tune2fs -m） tune2fs -l /dev/sda1 | grep -i reserved 查看
目录被挂载覆盖 有数据写进了覆盖隐藏的目录，挂载点下的原始数据不可见 umount 后能看到，或 findmnt 排查嵌套挂载

这与 文件系统与磁盘 IO 里讲的「inode + 块指针 + 引用计数」是同一套机制的生产投影：删除只是解除目录项引用，引用计数归零才真正回收块。

3.4 动手验证：亲手复现「删除文件后空间不释放」

判定标准：lsof +L1 能列出 (deleted) 文件即命中；kill 掉持有进程后 df 立即回落。生产上清理这类文件**不要用 rm**（已经删过了），要么重启进程，要么 truncate -s 0 /proc/<pid>/fd/<fd>。

5.2 生产实践案例：Nginx 频繁 502，worker 不断退出

场景：Nginx 频繁返回 502，检查发现 worker 进程不断退出。

处理结果：后端 PHP-FPM 进程数不足导致 Nginx 502，扩容后服务恢复。后续增加 PM 监控。

深挖一层：worker 死于 signal 9 有两种来源——OOM Killer（查 dmesg -T | grep -i oom）或 pm.max_children 这类自身限额。前者是内存真的不够，后者是配置的并发上限，处理方向完全不同。

6.3 深挖：TIME_WAIT 与 CLOSE_WAIT 是两回事

ss -s 里两个高频「异常」，机制完全不同：

状态 谁产生的 机制 正确处理
TIME_WAIT 主动关闭方 等 2MSL（约 60 秒）确保最后的 ACK 到达、旧包在网络中消散 大量短连接客户端角色（网关、爬虫）会攒；开 tcp_tw_reuse=1、用连接池、长连接
CLOSE_WAIT 被动关闭方 对端已 FIN，本端应用没有调用 close() 这是应用 bug：连接池没归还、异常分支没关流；ss -tnp state close-wait 找到进程去查代码

回到 TCP 协议本身：四次挥手要求主动关闭方等待 2MSL，因为「对方没收到我的 ACK 会重发 FIN」。这跟 TCP 协议 里讲的可靠传输是同一套机制——TIME_WAIT 不是故障，是协议在保证可靠性；把 tcp_max_tw_buckets 调小只会让内核直接丢弃 TIME_WAIT 并打日志，属于拆掉保险丝。

9.4 深挖：cron 的环境为什么和登录时不一样

cron 不经过登录流程，**不会读 /etc/profile、~/.bashrc**，拿到的是一份极简环境（PATH 通常只有 /usr/bin:/bin）。这是「手动执行成功、cron 执行失败」的第一大原因。四类差异与对策：

差异 表现 对策
PATH 不同 command not found 脚本开头 source /etc/profile，或全用绝对路径
工作目录不同 相对路径文件找不到 开头 cd /data/scripts
没有终端 tput、read、交互命令失败 脚本里禁用交互
环境变量缺失 JAVA_HOME 等未定义 在 crontab 顶部或脚本里显式定义

调试口诀：cron 任务就是「无 TTY、无 profile、无工作目录」的三无进程。写定时脚本时把自己当成一个刚登录的陌生用户来考虑。

11.4 深挖：ExitCode 137 与容器 OOM

容器进程退出码不是随便编的：137 = 128 + 9，即被 SIGKILL 杀死。在容器里，能发出 SIGKILL 的通常就是内核 OOM Killer——因为 cgroup 的内存上限触发了内核的强制回收。串起来的因果链：

cgroup 限制了容器可用内存 → 进程超限时内核在 cgroup 内选「最胖」的进程杀 → 容器主进程（PID 1）被杀 → docker ps 显示 Exited (137) / K8s 显示 OOMKilled。

证据 来源 含义
docker inspect -f '{{.State.ExitCode}}' = 137 Docker 被 SIGKILL
kubectl describe pod 里 Reason: OOMKilled K8s 明确是内存超限
dmesg -T | grep -i oom 内核 宿主层面 OOM（可能是整机，不一定是容器）
docker stats 的 MEM USAGE / LIMIT Docker 实时逼近上限
JVM 场景：-XX:MaxRAMPercentage JVM 容器内默认只按 25% 限额用堆，堆外（元空间/线程栈/直接内存）超了照样 137

与 Docker 容器实战 里 cgroup 章节的呼应：--memory 限制的是整个 cgroup（堆 + 堆外 + 页缓存），不是 JVM 堆。Java 应用在 K8s 里 OOMKilled，一半的锅要分给「堆外内存没算进 limit」。

11.5 动手验证：复现一次容器 OOM（观察 137）

实验需要 Docker 环境；dmesg 那一步要有 Linux 宿主机权限（云主机上最直观）。macOS 上用 Docker Desktop 也能复现 137，只是看不到内核日志。

判定标准：Exited (137) + dmesg 里出现 Memory cgroup out of memory: Killed process ... 即复现成功。这个实验解释了生产上「容器反复重启、日志里什么都没有」的现象——被 SIGKILL 的进程没机会写任何日志，所以必须靠 describe/inspect 的退出码和内核日志定性。

15. 速查总表

15.1 面试速答表

面试题 一句话答案
load average 多少算高？ 和 nproc 对比：持续超过核数说明有任务在排队，超过 1.5 倍视为过载
vmstat 的 r 列、b 列分别是什么？ r = 可运行队列长度（含运行中+等待 CPU），b = 不可中断睡眠（多为 IO 等待）
iostat 的 %util 和 await 哪个更可信？ await（平均等待毫秒数）更可信；%util 在 NVMe 多队列下会失真
df 显示满但 du 加起来不大，为什么？ 三种可能：删除未释放的文件（lsof +L1）、文件系统保留块、目录被挂载覆盖
TIME_WAIT 和 CLOSE_WAIT 的区别？ TIME_WAIT 是主动关闭方等 2MSL（协议的可靠性保证）；CLOSE_WAIT 是被动关闭方应用没调 close，是 bug
tcp_tw_reuse 为什么有时没用？ 只对主动发起的连接生效，且依赖 tcp_timestamps=1；服务端被动连接用不上
SIGTERM 和 SIGKILL 的区别？ 15 可被捕获、进程能优雅清理；9 不可捕获、直接杀，先 15 后 9
kill -0 是干什么的？ 不发信号只做存在性检查，脚本探活的基础
为什么 cron 里执行脚本总失败？ cron 没有登录环境（无 profile、PATH 极短、无工作目录），用绝对路径或显式 source
find 配 xargs 为什么必须加 -print0/-0？ 文件名含空格/换行时会被二次切分，-print0 用 NUL 分隔才安全
SUID 文件为什么危险？ 以文件属主权限运行（如 root），是提权的主要利用面
容器 ExitCode 137 是什么？ 128+9 = 被 SIGKILL，容器里通常是 cgroup 内存超限触发内核 OOM Killer
CrashLoopBackOff 的排查顺序？ get pods → describe（看 Events/Reason）→ logs --previous → 查 resources limit
top -Hp 找到的 TID 怎么用？ 转十六进制后在 jstack 里搜 nid=0x...，栈顶即热点方法
jstat -gcutil 看什么？ O 区（老年代）使用率持续高位 + FGC 频繁增长 = 内存问题或 GC 参数问题
Arthas 的 redefine 有什么限制？ 只能改方法体，不能改签名/字段；且是临时的，重启即失效
git reset --soft/--mixed/--hard 区别？ soft 只动 HEAD；mixed（默认）再退暂存区；hard 连工作区一起丢
已推送的提交写错了怎么救？ 用 git revert 生成反向提交；改写公共历史必须 --force-with-lease 且通知协作者
误删分支/误 reset 怎么恢复？ git reflog 找 sha，重建分支或 reset 回去（未提交的改动无法找回）
SQL 慢查询排查的入口？ 慢查询日志 + pt-query-digest 聚合 + EXPLAIN 看执行计划，最后才谈加索引

15.4 实操建议

  1. 把这份手册当成索引而不是教材：遇到故障先看第 15.3 的工具速查表定位「用什么工具」，再回对应章节看选项和案例。
  2. 动手验证章节至少做一遍：CPU 打满、删除文件未释放、cron 环境差异、容器 OOM 137、jstack 定位热点，这五个实验覆盖了最高频的排查范式。
  3. 建三份基线：监听端口清单（ss -tulnp）、crontab 清单、SUID 文件清单——没有基线就无法判断「异常」。
  4. 危险命令三件套：rm -rf 前替换成 ls -ld 预览、rsync --delete 前加 -n、sed -i 一定带 .bak。
  5. 内核参数别抄偏方：改之前 sysctl <key> 看真实默认值（随内核版本变化），改之后有监控验证；tcp_tw_recycle 这类已移除的参数出现在教程里，说明该教程过时了。
