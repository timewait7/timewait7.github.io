线程池：core、max、queue 的组合陷阱

Posted on 2026-10-26 In Java Word count in article: 2.9k Reading time ≈ 11 mins.

core=2, max=10 的线程池，提交 50 个阻塞任务后，线程数只有 2。因为队列是 LinkedBlockingQueue（无界），任务全进了队列，maximumPoolSize 永远不会生效——实测 getLargestPoolSize()=2。

这篇把线程池的三个陷阱量成数字：无界队列让 max 失效、拒绝策略静默丢任务（10 个任务只执行 3 个且不报错）、shutdownNow() 会中断正在跑的任务并丢弃排队任务。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM → ④ 伪共享 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数（本文） → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：② 的「线程数-吞吐曲线」是本文的公式依据；⑦ 的阻塞队列是本文队列参数的实现；⑪ 会讲虚拟线程如何替代「大池 + 阻塞」。

1. 七个参数与执行流程

参数 作用 常见坑
corePoolSize 常驻线程数 设太小，任务排队
maximumPoolSize 最大线程数 配合无界队列时永远不生效
keepAliveTime 超过 core 的线程空闲存活时间 设太短，线程反复创建
workQueue 任务队列 无界队列是「max 失效」的元凶
threadFactory 线程创建 不命名，出问题难排查
handler 拒绝策略 Discard 会静默丢任务
allowCoreThreadTimeOut core 线程是否超时回收 低频服务可开 
flowchart TD
    A["execute(task)"] --> B{"running < core?"}
    B -- yes --> C["create core thread"]
    B -- no --> D{"queue offer ok?"}
    D -- yes --> E["enqueue, wait for a thread"]
    D -- no --> F{"running < max?"}
    F -- yes --> G["create new thread"]
    F -- no --> H["reject: handler"]

注意流程顺序：先 core → 再队列 → 最后才扩到 max。队列不满就不会扩线程，这是理解所有陷阱的钥匙。

2. 陷阱一：无界队列让 max 失效

2.1 实测对比

同样提交 50 个「睡 200ms」的任务：

配置 poolSize active queue 曾达最大线程 拒绝数
core=2, max=10, LinkedBlockingQueue()（无界） 2 2 48 2 0
core=2, max=10, ArrayBlockingQueue(5) 10 10 5 10 35 
flowchart LR
    subgraph UB["Unbounded queue"]
        U1["core 2 threads busy"] --> U2["48 tasks queued"] --> U3["max=10 never used"]
    end
    subgraph BB["Bounded queue(5)"]
        B1["core 2 busy"] --> B2["5 queued"] --> B3["grow to max=10"] --> B4["35 rejected"]
    end

结论：

你想要 队列怎么选
任务不丢、慢慢排 无界队列（但要接受 max 失效）
背压、快速失败 有界队列 + 明确的拒绝策略
固定并发度 core = max，队列容量自己定

生产建议：Executors.newFixedThreadPool(n) 内部就是 LinkedBlockingQueue() + core=max=n——它靠「core 已经等于 max」绕开了这个坑；而 newCachedThreadPool 用的是 SynchronousQueue，max=Integer.MAX_VALUE，高并发下会疯狂建线程（① 实测创建 32 µs/个）。

3. 陷阱二：拒绝策略会静默丢任务

3.1 四种策略实测（池 1、队列 2、提交 10 个任务）

策略 执行数 拒绝数 总耗时 行为
AbortPolicy（默认） 3 7 163 ms 抛 RejectedExecutionException
CallerRunsPolicy 10 0 322 ms 调用线程自己跑，变慢 2 倍
DiscardPolicy 3 0 158 ms 静默丢弃，不报错
DiscardOldestPolicy 3 0 160 ms 丢掉队列里最老的，也不报错

最危险的是 DiscardPolicy 和 DiscardOldestPolicy：rejected=0，看起来「没被拒绝」，实际 10 个任务只执行了 3 个，剩下 7 个凭空消失。如果你的日志里没有任何异常，根本发现不了。

3.2 选型

场景 策略 理由
不能丢任务 CallerRunsPolicy 或自定义（落库/重试） 用调用线程的阻塞换取不丢
可以丢（如监控埋点） DiscardPolicy 但要打日志/计数
快速失败 AbortPolicy + 上层重试 默认策略，行为最明确
宁可丢老任务 DiscardOldestPolicy 少用，行为隐晦

4. 池大小怎么算：两条曲线

4.1 CPU 密集：峰值在核数

固定总工作量，池大小从 1 到 64：

池大小 耗时 加速比
1 550 ms 1.00×
4 148 ms 3.72×
8 73 ms 7.53×
15 39 ms 14.10×（峰值）
16 45 ms 12.22×
32 42 ms 13.10×
64 41 ms 13.41×

和 ② 的结论一致：池大小 ≈ 核数，再大只是增加切换。

4.2 IO 密集：可以远超核数

每个任务睡 5 ms，共 400 个：

池大小 耗时 吞吐
1 2,426 ms 165 tasks/s
8 303 ms 1,320 tasks/s
16 152 ms 2,632 tasks/s
32 78 ms 5,128 tasks/s
64 42 ms 9,524 tasks/s
128 24 ms 16,667 tasks/s 
flowchart LR
    A["CPU-bound<br/>pool = cores + 1"] --> B["15 cores -> peak 14.1x"]
    C["IO-bound<br/>pool = cores x (1 + W/C)"] --> D["W/C=5ms/0 -> unbounded<br/>limited by memory/downstream"]
    D --> E["measured: 128 threads<br/>16,667 tasks/s"]

公式验证：IO 密集的理论值是 核数 × (1 + 等待/计算)，等待 5 ms、计算几乎为 0 → 理论上限很高；实测到 128 线程仍在增长（165 → 16,667，约 100 倍），说明此时瓶颈不是 CPU，而是内存（1 MB 栈/线程）与下游。

4.3 池大小的三步定法

步骤 做法
1 算 CPU 密集：核数+1；IO 密集：核数×(1+W/C)
2 测 压测画「池大小-吞吐」曲线，找拐点
3 限 用有界队列 + 明确拒绝策略兜底

    H --> I

5. 陷阱三：关闭线程池会丢任务

shutdown() 与 shutdownNow() 的实测（池 1、10 个 50ms 任务、提交后立刻关闭）：

方法 启动数 完成数 被中断 3 秒内终止
shutdown() 10 10 0 true
shutdownNow() 1 0 1 true

  • shutdownNow()：中断正在运行的任务，并返回队列里未执行的任务列表（这 9 个任务不会被执行）。

6. 动手验证：四个可复现实验

6.1 动手验证：无界队列让 max 失效

预期观察点：pool=2 queue=48 largestPool=2（max=10 完全没用到）。

判定标准：

  • largestPool 达到 10 → 你用的不是无界队列，或有 core=max；
  • queue=0 → 队列被设成了 SynchronousQueue。

6.2 动手验证：四种拒绝策略的行为

预期观察点：CallerRuns 执行 10 个但更慢；Discard/DiscardOldest 只执行 3 个且 rejected=0。

判定标准：

  • Discard 的 rejected 大于 0 → 你用的是自定义策略，不是 JDK 的 Discard；
  • 所有策略都执行 10 个 → 队列容量给大了，减少容量再试。

6.3 动手验证：池大小与吞吐

预期观察点：加速比在 池大小 = 核数 处见顶（本文 15 → 14.10×）。

判定标准：

  • 峰值远低于核数 → 任务里有隐式锁竞争；
  • 超过核数后还持续上升 → 任务其实是 IO 密集（有阻塞）。

6.4 动手验证：shutdown 与 shutdownNow 的区别

预期观察点：shutdown 完成 10 个；shutdownNow 只启动 1 个、被中断 1 个、完成 0 个。

判定标准：

  • 两者都完成 10 个 → 你关闭时任务已经跑完了，缩短任务时间或提前关闭；
  • interrupted 为 0 → 任务没有响应中断（catch 里没检查），这也是常见 bug。

7. 总结

7.1 面试速答表

面试题 一句话答案
线程池的执行流程 core → 队列 → max → 拒绝策略
为什么 max 不生效 队列无界，任务永远排得进去，不会扩到 max（实测 largestPool=2）
四种拒绝策略 Abort（抛异常）、CallerRuns（调用线程跑）、Discard（静默丢）、DiscardOldest（丢最老的）
哪个策略最危险 Discard/DiscardOldest：不报错但任务消失
池大小怎么定 CPU 密集 = 核数+1；IO 密集 = 核数×(1+W/C)，再用压测校准
CPU 密集池开大会怎样 15 核峰值 14.10×，16 线程掉到 12.22×
IO 密集能开多少 实测 128 线程仍有 16,667 tasks/s，瓶颈变成内存与下游
shutdown 与 shutdownNow 区别 前者跑完队列，后者中断运行中任务并丢弃队列
线程池为什么不能用 Executors 默认工厂 无界队列（OOM 风险）或无界 max（线程爆炸）
队列满了怎么办 有界队列 + 明确拒绝策略（落库/重试/降级）

7.2 实战避坑表

症状 原因 处理
并发上不去、CPU 很低 无界队列导致只有 core 个线程 改有界队列或 core=max
任务莫名丢失 Discard 策略 换 Abort/CallerRuns，或自定义
服务重启后任务全丢 shutdownNow 强杀 先 shutdown + awaitTermination
线程池 OOM newCachedThreadPool 无上限 设 max + 有界队列
排查困难 线程没有命名 自定义 ThreadFactory 加前缀
池大小拍脑袋 没算 W/C 也没压测 用 4.3 的三步法

7.3 工具速查表

工具 看什么 判定标准
getPoolSize() / getActiveCount() 实际线程数 远小于 max = 队列在拦
getQueue().size() 积压 持续增长 = 处理能力不足
getLargestPoolSize() 历史峰值 等于 core 说明 max 没生效
getCompletedTaskCount() 完成数 与提交数对比看丢失
JFR jdk.ThreadPoolExecutor 事件 任务提交与执行 结合 ② 读法

7.4 实操建议

  1. 别用 Executors 的默认工厂，手工 new ThreadPoolExecutor 并显式给队列与拒绝策略。
  2. 队列必须有界，否则 max 是摆设；容量按「能容忍的积压时间 × 处理速率」定。
  3. 拒绝策略优先 AbortPolicy + 上层兜底，CallerRuns 次之；Discard 只能用于可丢数据。
  4. **关闭用 shutdown + awaitTermination**，超时才 shutdownNow，并记录丢弃数。
  5. 给线程命名，排查时 jstack 一眼就能看出是哪个池。

AQS 与并发容器：size() 为什么不准

Posted on 2026-10-26 In Java Word count in article: 3k Reading time ≈ 11 mins.

ConcurrentHashMap.size() 在并发写时只是估计值。实测：4 个线程各写 20 万条，边写边采样 200 万次，其中 121 万次（60%）采样到的 size 与实际写入数不一致，最大差值 724（总量 80 万，误差 0.09%）。

这篇把 AQS 与三个并发容器量成数字：为什么自旋锁在 16 线程下比 ReentrantLock 慢 24 倍、ConcurrentHashMap 在 1 线程时反而比 synchronizedMap 慢一倍、CopyOnWriteArrayList 的写放大到底有多夸张。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排 → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器（本文） → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：⑥ 的 ReentrantLock 背后就是 AQS，本文拆开它；⑤ 的 LongAdder 与 CHM 的分段计数是同一个思路。

1. AQS：一个 state + 一个队列

1.1 结构

AQS（AbstractQueuedSynchronizer）用两个东西管理所有同步器：

组件 作用
volatile int state 同步状态（锁次数、信号量许可数、读写锁的读写计数）
CLH 变体队列 没抢到锁的线程排队，park 等待
exclusiveOwnerThread 独占模式下的持有者 
flowchart LR
    A["thread calls lock()"] --> B{"CAS state 0->1?"}
    B -- yes --> C["acquired, owner = self"]
    B -- no --> D["enqueue node (CLH)"]
    D --> E["LockSupport.park()"]
    F["unlock(): state 1->0"] --> G["unpark successor"]
    G --> E
    E --> B

1.2 为什么队列比自旋好：24 倍差距

自己写一个最朴素的自旋锁（AtomicBoolean + onSpinWait），和 ReentrantLock 对比（16 线程 × 20 万次自增）：

锁 ns/op 说明
自旋锁（AtomicBoolean） 226.4 所有线程疯狂抢同一条缓存行
ReentrantLock（AQS 队列） 9.2 抢不到就排队 park，不再消耗 CPU

差 24 倍。原因就是 ④ 的伪共享：自旋锁让 16 个核不停地 CAS 同一个 AtomicBoolean，缓存行在所有核之间来回弹；AQS 让失败的线程「睡觉」，只留一个在抢。

1.3 独占与共享

模式 代表 state 含义
独占（Exclusive） ReentrantLock 重入次数（0 = 空闲）
共享（Shared） Semaphore、CountDownLatch 剩余许可数
组合 ReentrantReadWriteLock 高 16 位读、低 16 位写

2. ConcurrentHashMap

2.1 为什么快

机制 说明
桶级锁（CAS + synchronized 单桶） 只锁冲突的那个桶，不是整表
分段计数（CounterCell） size 用类似 LongAdder 的方式累加
无锁读 get 不加锁，靠 volatile 读 + 节点不可变 
flowchart LR
    T1["Thread 1 put(k1)"] --> B1["bucket 1 (locked)"]
    T2["Thread 2 put(k2)"] --> B2["bucket 2 (locked)"]
    T3["Thread 3 get(k1)"] --> R["volatile read, no lock"]
    B1 -.->|"different buckets<br/>no contention"| B2

2.2 实测：put 的 ns/op

线程数 ConcurrentHashMap Collections.synchronizedMap
1 31.7 15.3
4 9.1 54.5
16 31.2 79.2
64 19.9 67.1

两个反直觉点：

  1. 单线程下 synchronizedMap 更快（15.3 vs 31.7）——CHM 每次 put 要做 CAS、计数、可能的扩容检查；
  2. 4 线程时 CHM 快 6 倍（9.1 vs 54.5），但 16 线程反而退化到 31.2——因为扩容、计数竞争、桶冲突都变多了。

结论：CHM 的优势在「多线程并发」，单线程场景用它反而多付了开销。

2.3 size() 为什么不准

ConcurrentHashMap 的 size() 是「base + 所有 CounterCell 的和」，而并发时这些计数是分散更新的：

实测（4 线程各写 20 万条，主线程每毫秒采样）：

指标 实测
采样次数 2,019,482
size 与实际写入不一致的次数 1,211,162（60%）
最大差值 724
最终 size（写完后） 800,000（准确）

为什么：sumCount 遍历 Cell 数组时，其他线程正在更新 Cell，读到的是「某一瞬间的近似值」；而且 size() 明确不保证准确（Javadoc 写的是 estimate）。

用法 是否可取
判断「是否为空」 可以用 isEmpty()（也是估计，但足够）
精确计数 自己维护 LongAdder/AtomicLong
监控/告警 可以用（误差 0.1% 以内）
分页/遍历边界 不可用（遍历时也会变化）

3. CopyOnWriteArrayList

3.1 写放大：每次 add 复制整个数组

操作 CopyOnWriteArrayList Collections.synchronizedList
写入 2 万次 40 ms（2.0 µs/次） 0 ms（0.04 µs/次）
读取 200 万次 4 ms（2.1 ns/次） 16 ms（8.5 ns/次）

写慢 50 倍，读快 4 倍。而且写成本随列表长度增长：

add 次数 总耗时
5,000 4 ms
10,000 14 ms
20,000 34 ms
40,000 91 ms

这是 O(n²) 的典型：第 n 次 add 要复制 n 个元素，n 次 add 总共复制 n²/2 个元素。4 万次 add 复制了 8 亿个引用。

flowchart LR
    A["old array (n elements)"] --> B["new array (n+1)"] --> C["copy all n"] --> D["swap reference (volatile)"]
    E["readers"] -.->|"always read old or new<br/>never blocked"| A
    E -.-> D

3.2 读为什么快

读不加锁、不复制，直接读 volatile 引用指向的数组快照。读多写少 + 数组小是它的适用区间：

场景 适合吗
配置项列表（几乎不变，频繁读） ✅ 非常适合
监听器列表（注册/注销少） ✅ 适合
消息队列 / 缓存 ❌ 写太频繁
元素很多（10 万+） ❌ 一次 add 就要复制 10 万个 
flowchart TD
    A["Need a concurrent container"] --> B{"map or list?"}
    B -- map --> C{"single thread?"}
    C -- yes --> D["HashMap (fastest)"]
    C -- no --> E["ConcurrentHashMap<br/>preset capacity"]
    B -- list --> F{"writes frequent?"}
    F -- yes --> G["synchronizedList /<br/>ConcurrentLinkedQueue"]
    F -- no --> H{"list small?"}
    H -- yes --> I["CopyOnWriteArrayList<br/>2.1 ns read"]
    H -- no --> G
    E --> J{"need exact size?"}
    J -- yes --> K["own LongAdder counter"]

5. 动手验证：四个可复现实验

5.1 动手验证：CHM 与 synchronizedMap 的对比

预期观察点：单线程 synchronizedMap 更快；4/16/64 线程 CHM 明显更快（本文 9.1 vs 54.5）。

判定标准：

  • CHM 在所有线程数都更快 → 你的 JDK 版本较老（8 之前 CHM 实现不同）；
  • 两者都 > 200 ns/op → 机器繁忙或 JIT 未预热，加预热轮次。

5.2 动手验证：验证 size 的不准确性

预期观察点：mismatch 比例很高（本文 60%），maxDiff 在几百的量级，最终 size 准确。

判定标准：

  • mismatch=0 → 采样发生在写入完成之后，或线程数太少没有并发；
  • maxDiff 达到几千 → 你的写入速率更高，误差被放大。

5.3 动手验证：COW 的写放大

预期观察点：COW 的耗时近似按平方增长（本文 4/14/34/91 ms），synchronizedList 是 0 ms。

判定标准：

  • COW 耗时线性增长 → 你的列表很小，O(n²) 还没显现；
  • 40k 次超过 1 秒 → 列表里元素更大（引用复制成本高）或机器较慢。

5.4 动手验证：自旋锁 vs AQS

预期观察点：自旋锁比 ReentrantLock 慢一个数量级（本文 226 vs 9.2）。

判定标准：

  • 两者接近 → 线程数太少（≤4），自旋还没产生缓存行风暴；
  • 自旋锁极慢（>1000 ns）→ 核数多、竞争极端，属于正常现象。

锁的演化：偏向锁移除之后，synchronized 还慢吗

Posted on 2026-10-26 In Java Word count in article: 2.9k Reading time ≈ 10 mins.

JDK 21 里已经没有偏向锁了：-XX:+PrintFlagsFinal | grep -i biased 是空的，加 -XX:+UseBiasedLocking 直接报 Unrecognized VM option。这意味着「无竞争时 synchronized 几乎免费」这条老经验，在 21 上要重新校准。

用 JOL 能看到锁的三个真实状态：未加锁是 non-biasable、synchronized 内是 thin lock（指向 Lock Record 的指针）、有竞争后膨胀成 fat lock（ObjectMonitor）——而且膨胀之后不会退回去。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排 → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化（本文） → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：⑤ 的「64 线程下 synchronized 与 AtomicLong 打平」本文给出解释（都卡在缓存行争用）；⑦ 会接着讲 AQS 与 ReentrantLock 的内部。

1. 四种状态：JOL 实测

用 jol-core 0.17 打印对象头（mark word）：

场景 Mark Word JOL 解读
新建对象 0x0000000000000001 non-biasable；age: 0
synchronized 内（无竞争） 0x000000016d892ad0 thin lock（指向 Lock Record）
调用过 hashCode() 0x0000000066d33a01 hash: 0x0066d33a
有竞争时 0x00000009fcd1f1e2 fat lock（ObjectMonitor）
竞争结束后 0x00000009fcd1f1e2 仍是 fat lock，不回退 
stateDiagram-v2
    [*] --> Unlocked: new Object()
    Unlocked --> Thin: synchronized (no contention)
    Thin --> Fat: contention detected
    Fat --> Fat: never reverts
    Unlocked --> Hashed: hashCode()
    Thin --> Fat: hashCode() + contention
    note right of Unlocked: non-biasable (JDK 21)

1.1 「non-biasable」是什么意思

JOL 输出的 non-biasable 直接说明这个 JVM 的 mark word 里没有偏向锁位。

版本 偏向锁状态
JDK 8~14 默认开启（-XX:+UseBiasedLocking）
JDK 15 标记废弃（JEP 374）
JDK 18+ 移除
JDK 21 参数都不存在（本文实测）

影响：以前「始终只有一个线程访问的锁」几乎零成本；现在每次 synchronized 至少要走一次 CAS 把 mark word 换成 thin lock。

2. 无竞争时，synchronized 到底多贵

2.1 实测：四种写法（ns/op，每线程 100 万次，3 轮取最优）

线程数 synchronized ReentrantLock（非公平） 无锁（对照）
1 1.10 3.40 0.05
4 5.80~6.5（稳定后） 7.94 0.03
16 6.46 7.95 0.02
64 5.94 6.93 0.02

三个结论：

  1. 无竞争时 synchronized 只要 1.10 ns——比 ReentrantLock 快 3 倍（后者每次 lock/unlock 都要一次 AQS CAS）；
  2. 有竞争后两者打平（6~8 ns），瓶颈变成缓存行争用（④ 的机制）；
  3. 无锁是 0.02~0.05 ns，因为它被 JIT 折叠了（不代表真实成本，只作为对照）。

2.2 深挖：为什么 ReentrantLock 无竞争也慢 3 倍

flowchart LR
    S["synchronized<br/>lock"] --> S1["CAS mark word<br/>(thin lock)"] --> S2["CAS restore"]
    R["ReentrantLock<br/>lock"] --> R1["AQS CAS state<br/>+ owner check"] --> R2["setState +<br/>unparkSuccessor check"]

2.2 深挖：为什么 ReentrantLock 无竞争也慢 3 倍

步骤 synchronized ReentrantLock
加锁 一次 CAS（thin lock） compareAndSetState + 检查持有者
解锁 一次 CAS（恢复 mark word） setState + unparkSuccessor 检查
对象开销 0（复用对象头） 一个 Sync 对象 + state + 队列节点

所以「ReentrantLock 比 synchronized 快」是 JDK 5 时代的话。JDK 6 之后 synchronized 做了大量优化，无竞争场景反而更轻。

3. 有竞争时：首次膨胀 31 ns，之后 6 ns

3.1 实测：同一个基准连跑 5 轮

前两轮 30 ns，之后掉到 6 ns。原因是锁膨胀（thin → fat）：第一次遇到真正竞争时，JVM 要分配一个 ObjectMonitor、把等待线程挂到队列上，这一步是一次性成本；膨胀完成后（JOL 实测第 5 步仍是 fat lock），后续都走轻量路径。

sequenceDiagram
    participant T1
    participant T2
    participant L as ObjectMonitor
    T1->>T1: thin lock (CAS mark word)
    T2->>T2: CAS fails, spins
    T2->>L: inflate (allocate monitor)
    Note over L: 一次性成本 ~25 ns
    T1->>L: release, wake T2
    T2->>L: acquire
    Note over L: 之后稳定 ~6 ns/op

生产含义：锁膨胀是「一次性」的，不用担心；但它不会退回——一个曾经竞争激烈的锁，之后即使没人抢也走 fat lock 路径（比 thin 慢一点点）。这也是为什么「先把热点锁拆掉，再谈优化」比「反复调 JVM 参数」有效。

3.2 和 ⑤ 的数据对上了

⑤ 测出 64 线程下 synchronized（5.98）与 AtomicLong（5.54）打平。这里能解释：两者的瓶颈都是「多个核争抢同一条缓存行」，锁和 CAS 只是不同包装。

4. 公平锁：2.7 微秒一次（慢 340 倍）

锁类型 4 线程（ns/op） 16 线程（ns/op）
ReentrantLock(false)（非公平） 7.94 7.95
ReentrantLock(true)（公平） 2,683 2,800

公平锁比非公平锁慢约 340 倍。原因是公平锁每次解锁都要「把锁交给队列里的下一个线程」并唤醒它（涉及 LockSupport.unpark 与内核调度），相当于每次加锁都做一次线程切换（①实测切换 2.43 µs）。

选择 建议
绝大多数业务 非公平锁（默认）
严格 FIFO 需求的场景 公平锁，但要接受 300+ 倍开销
想「减少饥饿」 用非公平锁 + 合理超时，而不是公平锁

5. 锁消除：JIT 能把锁变没

指标 实测
2000 万次耗时 3 ms
折算 0.20 ns/op

JIT 做了什么：逃逸分析发现 o 不会逃出方法，于是把「加锁/解锁」直接删掉，连对象分配都可能被标量替换。这就是「锁消除」——代码里写了 synchronized，机器码里却没有。

能消除的前提 说明
对象不逃逸 只在方法内使用
锁对象唯一 每个迭代新建
没有同步副作用 临界区里没有 wait/notify

反例：如果 o 是成员变量或传给了别的方法，锁就消除不了。

原子性：i++ 的丢失与 CAS 的代价

Posted on 2026-10-26 In Java Word count in article: 3k Reading time ≈ 11 mins.

i++ 不是原子操作，它是三步：读、加、写。三个线程同时执行时，两个线程会读到同一个旧值，最后只加了一次。③ 已经量过 volatile++ 丢 61.4%；这一篇把「怎么修」算成账：**LongAdder 在 1 个线程时比 AtomicLong 慢 2.7 倍，在 64 个线程时快 16 倍**。

还有一个反直觉的实测：synchronized 与 AtomicLong 在 4/16/64 线程下几乎一样（6 ns/op 左右），谁也没赢——因为瓶颈都变成了「缓存行争用」。真正的赢家是把写分散开的 LongAdder。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排 → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS（本文） → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：③ 的「volatile++ 丢 61.4%」是本文的起点；④ 的伪共享解释了「为什么 LongAdder 快」；⑥ 会接着讲锁的实现。

1. i++ 为什么不是原子的

sequenceDiagram
    participant T1
    participant T2
    participant M as Memory (i=100)
    T1->>M: read i -> 100
    T2->>M: read i -> 100
    T1->>M: write 101
    T2->>M: write 101
    Note over M: two increments, result 101 (lost 1)
操作 是否原子 说明
i = 1 是（32 位以内） 单次写
i++ 否 读-改-写三步
volatile i++ 否 volatile 只保证可见性，不保证三步整体
AtomicInteger.incrementAndGet() 是 CAS 循环
synchronized { i++ } 是 互斥

2. 四种写法，四种并发度

2.1 实测：ns/op（每线程 200 万次，3 轮取最优）

线程数 synchronized AtomicLong LongAdder
1 1.19 1.55 4.14
4 6.11 5.82 1.11
16 6.16 5.53 0.52
64 5.98 5.54 0.34

这张表有三个反直觉点：

反直觉 数据 原因
单线程下 LongAdder 最慢 4.14 vs 1.19（3.5 倍） 它要做 Cell 探测、哈希、分段写入，开销比一个 CAS 大
高并发下 synchronized 与 AtomicLong 打平 6.0 vs 5.5（64 线程） 瓶颈都是缓存行争用，不是锁本身
LongAdder 越并发越快 4.14 → 1.11 → 0.52 → 0.34 写分散到多个 Cell，每个核改自己的行 
flowchart LR
    A["LongAdder<br/>base + Cell[]"] --> B["thread 1 -> Cell 0"]
    A --> C["thread 2 -> Cell 1"]
    A --> D["thread 3 -> Cell 2"]
    B -.->|"each cell padded<br/>to own cache line"| E["no contention"]
    C -.-> E
    D -.-> E

2.2 深挖：LongAdder 为什么越并发越快

LongAdder 维护一个 base 和一个 Cell[] 数组：

机制 作用
按线程哈希选 Cell 不同线程写不同 Cell，避免同一变量争用
Cell 内部有 @Contended 填充 不同 Cell 不共享缓存行（④ 的机制）
读时求和 sum() 牺牲「读的实时精确性」换「写的扩展性」
特性 AtomicLong LongAdder
写扩展性 差（单点） 好（分段）
读开销 O(1) O(Cell 数)
读的精确性 强（读到最新） 弱（并发写时 sum 可能不准）
适用 需要精确值、序列号 统计计数（QPS、访问量）

结论：**统计类计数用 LongAdder，需要精确读值的用 AtomicLong**。本文 64 线程下差 16 倍，但如果你要「读一个精确的总数做判断」，LongAdder 的 sum() 在并发写时可能少算。

3. CAS 的代价：重试率

3.1 实测：一次成功要尝试几次

自己实现 increment（get + compareAndSet 循环），统计尝试次数：

线程数 总尝试次数 尝试/成功
1 500,000 1.00
4 6,262,092 3.13
16 57,727,878 7.22
64 224,723,365 7.02

4 个线程就要试 3 次以上——因为一条 CAS 成功会让其他核的缓存行失效，其他线程的 CAS 全部失败重试。这就是「无退避的 CAS 惊群」。

flowchart TD
    A["read cur"] --> B["compute next = cur+1"]
    B --> C{"CAS(cur, next)?"}
    C -- success --> D["done"]
    C -- fail --> A
    D -.->|"invalidates<br/>other cores' line"| A

问题：CAS 只比较「值」，不比较「这段时间里发生过什么」。值从 A 变回 A，CAS 就以为什么都没变。

4.2 修复：加版本号

4.3 什么时候会踩 ABA

场景 风险
对象池 / 连接池复用 同一个对象被借出、归还、再借出
无锁栈 / 链表节点复用 节点被弹出再压回，指针被复用
余额、库存这类数值 低（值从 100 变回 100 通常无害）

判断：只有「值的身份」重要（指针、引用）时才需要 stamp；纯数值计数通常不需要。

5. 选型与动手验证

5.1 一张选型表

场景 选择 依据（本文实测）
统计计数（QPS、PV） LongAdder 64 线程 0.34 ns/op
需要精确读值 AtomicLong 读是 O(1) 且精确
序列号 / ID 生成 AtomicLong 需要严格递增
临界区有多步操作 synchronized / 锁 CAS 只能保证单变量
无锁数据结构 AtomicReference + stamp 防 ABA
低并发（1~4 线程） synchronized 就够 1.19 ns/op，实现最简单

5.2 动手验证：四种写法的曲线

预期观察点：单线程 LongAdder 最慢；64 线程 LongAdder 最快（本文 0.34 vs 5.5 ns/op）。

判定标准：

  • 三个数字都接近 0 → JIT 把循环优化掉了，加大 ops 或检查是否有 SINK 消费；
  • LongAdder 在高并发下没有优势 → 线程数不够（<4）或 CPU 核数太少。

5.3 动手验证：量 CAS 重试率

预期观察点：1 线程 1.00，4 线程 > 2，16 线程接近 7（本文 7.22）。

判定标准：

  • 所有线程数都是 1.00 → 你的线程没有真正并发（屏障没用上，或 CPU 只有 1 核）；
  • 16 线程重试率超过 20 → 竞争极度激烈，必须换 LongAdder 或分段。

5.4 动手验证：复现 ABA

预期观察点：T1 CAS: true，最终栈是 C -> B -> null，A 丢失。

判定标准：

  • CAS 返回 false → 你的时序没构造对（T2 必须在 T1 读完之后、CAS 之前完成）；
  • 用 AtomicStampedReference 替换后 CAS 变 false → 修复生效（见 5.5）。

5.5 动手验证：stamp 修复 ABA

预期观察点：plain CAS: true，stamped CAS: false。

判定标准：

  • stamped 也返回 true → 你在两次 CAS 之间没更新 stamp，检查参数顺序（期望值、新值、期望 stamp、新 stamp）。

6. 总结

6.1 面试速答表

面试题 一句话答案
i++ 为什么线程不安全 读-改-写三步，可能读到同一个旧值
volatile 能保证 i++ 安全吗 不能，只保证可见性不保证原子性（③ 实测丢 61.4%）
AtomicLong 怎么实现的 CAS 循环：读值、算新值、compareAndSet 失败重试
CAS 有什么问题 自旋消耗 CPU、ABA、只能保证单变量
ABA 是什么 值从 A 变 B 又变回 A，CAS 以为没变过
怎么解决 ABA AtomicStampedReference / AtomicMarkableReference
LongAdder 为什么比 AtomicLong 快 分段（Cell 数组）+ 缓存行填充，写分散到多个核
LongAdder 的缺点 sum() 不是精确实时值，读开销 O(Cell)
什么时候用 synchronized 而不是 Atomic 临界区有多步操作，或低并发下实现更简单
CAS 重试率有多高 本文 4 线程 3.13 次/成功，16 线程 7.22 次
单线程下 LongAdder 和 AtomicLong 谁快 AtomicLong（1.55 vs 4.14 ns/op，本文）
64 线程下差多少 LongAdder 0.34 vs AtomicLong 5.54 ns/op（16 倍）

6.2 实战避坑表

症状 原因 处理
计数总是少一点 用了 int++ 或 volatile++ 换 AtomicLong/LongAdder
高并发下计数性能差 单点 CAS 争用 换 LongAdder
读到的总数不准 LongAdder.sum() 非实时精确 需要精确值用 AtomicLong，或停写后再 sum
无锁栈偶尔丢节点 ABA 加 stamp
CAS 循环 CPU 飙高 无退避自旋 Thread.onSpinWait() 或降并发

6.3 工具速查表

工具 看什么 判定标准
AtomicLong / LongAdder 计数实现 高并发统计优先 Adder
AtomicStampedReference 带版本号的 CAS 防 ABA
VarHandle 更底层的原子操作 JDK 9+ 替代 Unsafe
JFR 线程状态与竞争 结合 ② 读法
本文的 Retry 脚本 CAS 重试率 > 3 就该考虑分段

6.4 实操建议

  1. **统计计数一律 LongAdder**，需要精确读值的才用 AtomicLong。
  2. i++ 出现在多线程代码里就是 bug，换成原子类或锁。
  3. 临界区超过一行就别用 CAS，用锁更清晰（⑥ 会讲锁的成本）。
  4. 无锁结构遇到「节点复用」必须加 stamp，否则 ABA 一定会在某天出现。
  5. 压测时观察 CAS 重试率，它是「该分段了」的早期信号。
