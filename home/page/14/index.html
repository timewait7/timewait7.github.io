一、项目概述

1.1 项目名称

智能工单处理 Agent（Intelligent Ticket Processing Agent，以下简称 ITPA）

1.2 项目背景

随着企业数字化转型的深入，客服系统积累了海量的用户咨询工单。传统的人工处理方式存在响应慢、人力成本高、知识利用不充分等问题。本项目建设一个基于 Model Context Protocol（MCP）的智能 Agent，能够自动处理用户工单，包括工单分类、相似问题检索、答案生成和工单创建，将人工从重复性工单处理中解放出来。

1.3 核心功能

功能模块 功能描述 MCP 能力类型
工单分类 根据工单内容自动分类（技术问题/账单问题/账号问题/产品咨询/投诉建议） Tool
相似工单检索 基于向量相似度检索历史工单，提供参考解答 Resource
回答生成 结合检索结果和工单内容生成回复建议 Tool
工单创建 将工单写入数据库，自动分配优先级 Tool
知识库管理 管理 FAQ 条目，用于增强检索 Resource

完成本项目后，你将系统掌握：

  • HTTP 服务：使用 FastAPI 实现健康检查、指标暴露、管理接口
  • 环境配置管理：使用 pydantic-settings 管理多环境配置
  • 容器化部署：编写 Dockerfile 和 docker-compose.yml
  • 监控与日志：集成 Prometheus 指标、结构化日志输出
  • 错误处理：完善的异常捕获、重试机制、熔断降级

1.5 真实业务场景

ITPA 适用于以下场景：

  • 企业客服系统中台，作为智能路由层自动处理简单工单
  • 开发者在 Claude Desktop、Cursor IDE 等支持 MCP 的应用中直接调用
  • 作为通用的工单处理微服务，通过 HTTP/gRPC 供其他系统调用

MCP与Agent Skill：AI Agent能力标准化的双轮驱动

Posted on 2026-05-31 In AI大模型 Word count in article: 4.6k Reading time ≈ 17 mins.

摘要

随着大语言模型从对话工具向自主智能体的演进，如何让AI高效、安全地接入外部工具和数据源，已成为工程实践中的核心挑战。在此背景下，Anthropic先后推出了Model Context Protocol（MCP）和Agent Skills两个重要技术规范。MCP定位为AI工具连接的“通用语言”，解决了外部系统接入的标准化问题；Agent Skills则聚焦于能力编排与按需加载，将复杂工作流封装为可复用的技能单元。两者并非竞争关系，而是分工明确的互补架构——MCP负责“接什么”，Skills负责“怎么用”。本文系统梳理两者的诞生背景、核心原理与协同机制，并通过流程图、时序图与深度对比，为开发者提供清晰的选型决策框架和最佳实践指南。

关键词：MCP；Agent Skills；AI Agent；工具调用；能力标准化

一、引言

大语言模型的能力边界正在被快速拓宽。从最初只能进行文本对话，到如今可以调用外部函数、访问数据库、操作文件系统，AI智能体正在成为真正的“执行者”。然而，这种能力扩展背后隐藏着一个长期被忽视的工程难题：连接碎片化。在MCP问世之前，每一个AI模型要接入一个新的工具或数据源，都需要开发一套定制的连接代码。一个团队如果同时使用Claude、GPT-4和Gemini三个模型，而工具库包含GitHub、Slack、Postgres等十个应用，就需要维护多达三十套互不兼容的集成方案。

传统API虽然稳定可靠，但在AI动态调用场景中缺乏灵活性，无法适应LLM输出的非结构化请求。OpenAI引入的Function Calling虽然允许模型调用外部函数，但它是具体实现而非通用协议，不同框架、不同模型之间的规范并不统一。正是在这种“各自为政”的混乱局面下，MCP和Agent Skills应运而生。

二、MCP：AI工具连接的“USB-C”标准

2.1 诞生背景与演进脉络

Model Context Protocol（MCP）是由Anthropic于2024年11月25日推出的开源协议，旨在实现大语言模型与外部数据源和工具的标准化集成。MCP的设计理念被业界形象地比作“AI领域的USB-C接口”——正如USB-C用一个通用端口替代了五花八门的专用充电器，MCP用一个统一协议替代了无数点对点的定制化连接。

MCP的推出恰逢其时。2024年，各大AI厂商都在探索如何让模型真正“动手做事”，但各自的方案互不兼容。Anthropic从一开始就将MCP设计为厂商中立的开放规范，这一战略眼光在随后的生态发展中得到了验证。2025年3月，OpenAI宣布其Agent SDK支持MCP协议；Google DeepMind随后将其集成到Gemini智能体栈中；微软在Copilot Studio中也加入了MCP支持。短短一年间，MCP迅速成长为智能体AI领域的事实互联标准。截至2025年3月，已有超过1000个社区服务器投入实际使用，MCP服务器的月度下载量从发布初期的约200万次飙升至2025年4月OpenAI接入后的2200万次。2025年12月，Linux基金会成立Agentic AI Foundation（AAIF），MCP被正式移交至该基金会管理，标志着其进入了更广阔的开源治理阶段。

2.2 架构设计与核心机制

MCP采用客户端-主机-服务器的三层架构，每个核心组件承担明确的职责：

  • MCP主机：面向用户的应用层，如Claude Desktop、Cursor编辑器或自定义的Python智能体。主机决定连接哪些服务器，并向用户展示工具调用的确认信息。
  • MCP客户端：运行在主机内部，每个客户端对应一台MCP服务器，通过JSON-RPC 2.0协议进行通信。
  • MCP服务器：独立进程，向外暴露一组能力，包括工具（可调用的函数）、资源（只读的数据源）和提示词模板。

MCP定义了三种核心能力原语：

  1. Tools（工具） ：可供AI模型调用的可执行函数，如查询天气、发送消息、执行计算等，并支持参数传递和结果返回。
  2. Resources（资源） ：只读数据源，如数据库记录、本地文件、API响应等，AI可以读取但不能修改。
  3. Prompts（提示词模板） ：可复用的用户交互模板，便于标准化常见对话场景。

在通信层面，MCP提供两种传输协议：

  • STDIO：主机以子进程方式启动服务器，通过标准输入输出进行JSON-RPC消息交换。适用于本地服务，零网络暴露面。
  • Streamable HTTP：用于远程调用场景，2025年3月发布的规范修订版中取代了SSE成为推荐的远程传输方式。

2.3 解决的问题与价值

MCP解决了两大核心痛点：

其一，M×N集成爆炸问题。开发者只需要为每个工具编写一次MCP服务器代码，就能供所有支持MCP协议的AI模型使用，将集成复杂度从线性增长降为常数级。

其二，上下文的“饥荒”问题。传统AI模型无法访问实时数据，被局限在用户粘贴到对话框的有限文本上。MCP通过标准化接口，让模型能够动态获取所需的上下文信息，真正打通了模型推理与真实世界之间的壁垒。

三、Agent Skills：AI能力的“模块化封装”

3.1 从Prompt到Skills的演进

如果说MCP解决了“如何连接”的问题，那么Agent Skills解决的则是“如何高效使用能力”的问题。

在MCP推出一周年之际，Anthropic发现了一个新的瓶颈：当MCP工具数量激增时，大量Token被消耗在工具定义的传递上。一个会议记录下载并转存的操作，可能因为反复传递工具定义而导致Token消耗成倍增长。

与此同时，Prompts本身也存在明显局限：Prompt是一次性注入的静态文本，会随着对话轮次的增加而被稀释，难以持久化复用。各AI框架（LangChain、AutoGen等）之间互不兼容，使得能力无法跨平台共享。

正是在这一背景下，Anthropic在2025年初提出了Agent Skills的概念。2025年12月18日，Anthropic正式将Agent Skills发布为跨平台的开放标准，同步开源了包含16个生产级技能库的参考实现。

3.2 核心架构：渐进式披露

Agent Skills采用极简但强大的设计：每个Skill就是一个文件夹，其中必须包含一个SKILL.md文件（含YAML元数据和Markdown指令），并可附带脚本、模板、文档等任意资源。

Skills的核心工作机制被称为 “渐进式披露”（Progressive Disclosure） ：

  • 第一阶段（浏览） ：Agent最初只读取Skill的YAML元数据（名称、描述、触发条件），每条Skill仅消耗约30-50个Token。
  • 第二阶段（加载） ：当用户意图匹配某个Skill时，Agent读取完整的SKILL.md文件内容，将操作指令注入推理上下文。
  • 第三阶段（使用） ：如需执行脚本或读取附带的资源文件，Agent在需要时再动态加载这些内容。

这一设计使Agent可以同时“拥有”数十个Skills，而不会造成上下文窗口的过度占用。

3.3 演进动力：从封闭到开放

Agent Skills的一大里程碑发生在2025年12月——Anthropic将其发布为开放标准。这一举措迅速得到生态响应：OpenAI随即在Codex文档中加入了Skills支持；LangChain在DeepAgents中实现了Skills集成；特赞等团队推出了首个Skills管理基础设施。截至2026年5月，主流技能共享平台上的技能数量已突破5万个。

更重要的是，Agent Skills提供了一套完整的能力治理体系：企业版用户可以集中管理技能库、控制技能发布权限、审计使用记录，使AI能力的部署从“用户自建”走向“平台化运营”。

5.2 协作关系：不是“谁取代谁”

一个常见的误解是Skills会“淘汰”MCP。事实上，Anthropic官方的立场非常明确：Skills和MCP解决的是不同层面的问题，二者协同使用才能发挥最大价值。

可以这样理解三层架构：

  • MCP层：工具连接的基础设施，统一了“AI与外部系统如何通信”的规范。
  • Skills层：能力编排的框架，定义了“在何种条件下、按照什么顺序、以什么方式使用这些工具”。
  • Function Calling层：LLM原生能力，是前两者得以执行的底层手段。

一个精心设计的高级Skill，其底层往往就是在调用多个MCP工具。在这种架构下，Skills是“指挥官”，MCP是“执行者”，两者构成了完整的AI智能体能力闭环。

六、注意事项与最佳实践

6.1 MCP实施注意事项

安全性方面，MCP服务器通常拥有文件系统、数据库或外部API的访问权限，应将其视为不可信的执行方。实践中应注意：对MCP工具的调用权限进行分级管理（如只读与可写分离）；在主机层面实现用户确认机制，防止AI自动执行敏感操作；对MCP Server进行沙箱隔离，限制其系统资源访问。MCP主机应单独处理工具调用的身份验证和授权，不应将这些职责委托给LLM。

性能与选型方面，STDIO适用于本地服务，具有零网络风险和生命周期可控的优势，应该是默认首选。HTTP远程调用适用于跨网络场景，但需额外考虑认证、审计和速率限制等企业级需求。强烈推荐部署MCP网关来处理这些横切关注点，包括认证、审计和护栏控制，避免在每个服务器中重复实现。

设计规范方面，工具定义应包含清晰的语义化描述和准确的参数Schema，这直接影响LLM正确选择工具的准确率。每个MCP工具应保持单一职责，避免设计过于庞大臃肿的“万能工具”，以提高调用的可预测性。建议为工具添加丰富的错误信息，帮助LLM在调用失败时做出合理的恢复决策。

6.2 Skills实施注意事项

版本管理是Skills工程化的核心。建议在SKILL.md的YAML元数据中明确记录技能版本、作者、依赖关系等元信息，支持平滑升级和回滚。

Skill颗粒度设计是一大难点：技能太细会导致管理成本上升；太粗则降低了复用性。一个较为合理的实践是参考“30-50 Token元数据”原则，确保元数据足够精简，让Agent在浏览阶段就能准确判断技能是否适用。Skill正文（SKILL.md）则应当详细描述完整的操作流程、异常处理路径和预期输出格式，确保LLM即便面对不完美的输入也能给出合理的响应。

性能调优方面，应充分利用渐进式披露机制：元数据中只放最关键的信息（名称、简短描述、触发关键词），完整指令和资源都放在正文中按需加载。附带的脚本应当优先使用确定性强的代码（如Python数据处理）而非纯LLM推理，以提升结果的稳定性。

安全考量则与MCP类似，需要注意Skill中附带的脚本可能执行任意代码，应对其进行沙箱隔离和输入校验。企业环境中应建立技能审批制度，避免未经审查的Skill进入生产系统。

七、结论与展望

MCP和Agent Skills共同构成了当前AI智能体能力标准化的基础框架。MCP通过统一连接协议，将AI与外部系统的集成从“各自为战”推向“标准互通”；Agent Skills通过渐进式披露的能力封装，将专业工作流从“手写Prompt”推向“工程化复用”。

两者的关系并非竞争，而是一种精妙的分工协作：MCP负责连接性（Connectivity），Skills负责能力性（Capability） 。MCP让每一种工具都可以被标准化接入，Skills让每一种专业知识都可以被标准化封装。对于AI应用开发者而言，理解并善用这两项技术，将成为构建下一代智能应用的关键能力。

展望未来，随着MCP进入Linux基金会治理、Agent Skills逐步被更多平台采纳，这两项标准化工作有望催生真正的“AI应用商店”生态——就像Android应用商店一样，开发者可以自由发布Skill和MCP Server，企业可以按需购买和部署，而AI智能体则能够自动发现、加载、调用最适合当前任务的能力组合。

AI大模型核心概念综述

Posted on 2026-05-31 In AI大模型 Word count in article: 1.9k Reading time ≈ 7 mins.

引言

随着大语言模型（LLM）的发展，单一的文本生成已无法满足复杂的应用需求。现代AI系统正朝着具备记忆、检索、工具使用和自主决策能力的智能体（Agent） 方向演进。本文将梳理构成这些系统的 12 个核心概念，并展示它们如何协同工作。

一、核心概念详解

1. LLM (大语言模型)

定义：LLM是基于海量数据预训练的大规模神经网络模型，具备理解和生成自然语言的能力。它是整个智能系统的“大脑”。

  • 核心能力：语言理解、文本生成、推理、代码编写、知识问答
  • 代表模型：GPT-4、Claude、LLaMA、文心一言、通义千问

2. Prompt

定义：Prompt是与LLM交互时输入的指令或问题。它是“与大脑对话的语言”。精心设计的Prompt能极大提升输出质量。

类型 示例 特点
零样本 “把‘你好’翻译成英文” 直接指令
少样本 “例子：苹果→Apple；猫→Cat；狗→？” 提供示例
思维链 “先分析，再回答：…，让我们一步步思考” 强制推理过程
角色扮演 “你是专业医生，请分析…” 设定角色约束

3. Context

定义：Context是模型在一次推理中能够“看到的所有信息”，包括系统指令、历史对话、检索结果等。

  • 关键参数：上下文窗口长度（如128K、200K tokens）
  • 挑战：窗口有限，长对话会丢失早期信息

4. Memory

定义：Memory是系统对历史交互的持久化存储与检索机制，让模型“记住用户”。

5. Search

定义：Search是主动从外部信息源获取实时或深度数据的能力，解决LLM知识陈旧或缺失的问题。

  • 搜索对象：网页、内部文档库、数据库、API
  • 触发时机：用户问实时信息、领域专业知识、超出训练截止日期的问题

6. Agent

定义：Agent是一个能够自主决策、规划步骤、调用工具的AI系统，是以上所有能力的整合者。

7. RAG (检索增强生成)

定义：RAG是一种技术架构，在生成回答前先从知识库检索相关文档，作为上下文注入LLM。

8. Function Calling (函数调用)

定义：Function Calling是LLM结构化输出API调用参数的能力，让模型能“使用外部工具”。

  • 工作流程：LLM输出函数名和参数 → 系统执行真实函数 → 结果返回LLM → LLM生成最终回复

9. MCP (模型上下文协议)

定义：MCP（Model Context Protocol）是Anthropic提出的开放协议标准，统一了AI应用与外部数据源、工具的连接方式。

  • 意义：避免每个工具都要写适配代码，实现“一次适配，处处可用”

10. Workflow

定义：Workflow是预定义的、结构化的多步骤任务序列，将复杂任务分解为可管理的步骤。

类型 结构 适用场景
顺序 A→B→C 数据清洗→分析→报告
路由 条件判断分支 客服：根据意图分发
并行 A,B,C同时执行 多源信息采集
循环 重复直到满足条件 代码调试迭代

11. SubAgent

定义：SubAgent是被主Agent调用的专用化Agent，遵循主从模式（Master-Slave）。

12. Agent Skill

定义：Skill是Agent可调用的原子能力单元，类似“插件”或“函数库”。

  • 内置技能：文本摘要、情感分析、翻译
  • 扩展技能：发送邮件、创建日历、调用企业ERP接口
  • 技能定义：自然语言描述 + 可执行代码/API规范

三、完整工作流程

下图展示了从用户输入到最终输出的完整AI大模型智能体工作流程：

流程说明

  1. 用户输入 → 前端：用户在界面输入提示词（文本、文件或多模态内容）。
  2. 后端接收与安全检测：后端收到请求后立即进行输入安全过滤，防止注入或不当内容。
  3. 并行上下文加载（提高响应效率）：
    • 记忆系统：获取短期对话历史与长期用户画像（如偏好、已存事实）。
    • MCP（Model Context Protocol）：通过标准化协议从外部数据源（数据库、实时API、企业内部系统）获取动态上下文。
    • RAG：基于提示词从知识库中检索最相关的片段，增强事实性。
  4. 构造增强提示词：将系统指令、记忆、MCP上下文、RAG片段与用户输入合并为完整的模型输入。
  5. 模型初始推理：大语言模型返回首次响应，可能直接生成文本，或请求调用外部工具（Agent Skill）。
  6. Agent技能与工具循环（可多次）：
    • 若模型要求调用工具（如搜索、计算、代码执行、发送邮件等），后端将请求转交给 Agent Skill 调度器。
    • 调度器执行对应的 外部工具/API，获取结果。
    • 将工具结果追加到对话中，再次调用模型继续生成。
    • 循环直到模型不再请求工具调用。
  7. 输出安全检测：对最终模型响应进行安全过滤（敏感词、伦理合规）。
  8. 记忆更新：异步将本次问答对存入短期记忆，并根据策略更新长期记忆。
  9. 返回前端：响应以流式（SSE）或完整形式返回，前端逐步渲染并展示给用户。

关键组件角色

  • MCP：为模型提供实时、按需的外部上下文，避免模型知识滞后。
  • Agent Skill：将模型的能力扩展到“行动”（如修改文件、查询天气、调用企业ERP），实现智能体行为。
  • 记忆系统：区分短期（会话内）与长期（跨会话）记忆，保持对话一致性。
  • RAG：解决知识幻觉，从私有或最新文档库中检索事实。
  • 安全模块：贯穿输入与输出，保障内容合规。

面向 Java 开发者的一篇 K8s 入门文章：从架构原理讲起，以 Spring Boot 应用部署为主线，覆盖网络、存储、可观测性与常见问题排查。

1. 为什么需要 Kubernetes

从 Docker 到 K8s：单机到多机编排的演进

作为 Java 开发者，你一定经历过这样的阶段：

阶段一：裸机部署。 把 Jar 包 scp 到服务器，nohup java -jar app.jar & 启动，进程挂了靠人肉重启，端口冲突靠口头约定。

阶段二：Docker。 解决了”环境不一致”的问题——镜像打包了 JDK、依赖、配置，docker run 一下就跑起来。但 Docker 只解决”怎么跑”，不解决”跑在哪、跑几个、挂了怎么办”。

阶段三：Docker Compose。 可以用一份 YAML 描述多个容器（MySQL + Redis + App），一键启动。但 Compose 是单机的，服务多起来之后：

  • 无法跨多台机器调度
  • 没有自动故障恢复
  • 没有滚动更新
  • 没有服务发现与负载均衡

阶段四：Kubernetes。 K8s 把”多台机器”抽象成一个资源池，你只需要声明”我想要什么”（声明式配置），K8s 负责”怎么达成”（控制循环）。

K8s 的核心价值

能力 说明 对 Java 开发者的意义
声明式配置 用 YAML 描述期望状态，而非一步步执行命令 配置即代码，可以走 Git 版本管理、Code Review
自愈 容器崩溃自动重启、节点宕机自动迁移 Pod 不再需要人肉守护进程
自动扩缩容 按 CPU/内存或自定义指标水平伸缩（HPA） 应对突增流量不用半夜起来加机器
服务发现与负载均衡 Service 提供稳定的虚拟 IP，自动转发 服务间调用不再硬编码 IP
滚动更新与回滚 新版本分批上线，失败自动回退 发布变成 kubectl rollout 一条命令

一句话总结：Docker 解决”怎么打包”，K8s 解决”怎么运维”。 打包你已经在做了，运维这件事交给 K8s。

2. 核心概念与架构

2.1 架构图

  • Control Plane（控制平面）：集群的”大脑”，负责决策（调度、状态维护、对外暴露 API）。生产环境通常 3 个副本高可用部署。
  • Worker Node（工作节点）：集群的”手脚”，真正跑你的业务容器。

2.2 核心组件

组件 职责 通俗理解
API Server 集群唯一的操作入口，提供 REST API，所有组件（包括 kubectl）都通过它通信 集群的”行政中心”，所有状态变更都要它批准
etcd 分布式键值存储，保存集群全部状态 集群的”数据库”，保存着”世界应该是什么样”
Scheduler 为新 Pod 选择合适的节点 集群的”调度员”，看哪台机器资源够、亲和性满足
Controller Manager 运行各种控制器，让”当前状态”收敛到”期望状态” 集群的”纠偏员”，发现偏离就修复
kubelet 节点上的代理，负责启动/停止 Pod，向 API Server 汇报状态 节点的”管家”，执行控制平面下达的指令
kube-proxy 维护节点上的网络规则，实现 Service 的负载转发（iptables/IPVS） 节点的”路由器”

2.3 一个 Pod 的创建流程

你在终端执行 kubectl create -f deployment.yaml 之后发生了什么：

  1. kubectl → API Server：kubectl 把 Deployment 对象通过 HTTPS 发给 API Server，API Server 校验并存入 etcd。
  2. Deployment Controller（属于 Controller Manager）发现”期望的副本数是 3，实际是 0”，于是创建 ReplicaSet。
  3. ReplicaSet Controller 发现”期望 3 个 Pod，实际 0 个”，于是创建 3 个 Pod 对象（此时 Pod 处于 Pending）。
  4. Scheduler 监听到新 Pod，为每个 Pod 选择合适的节点，把调度结果写回 etcd（Pod 绑定到某节点）。
  5. kubelet 从 API Server 感知到本节点有新 Pod，通知容器运行时（containerd）拉取镜像并创建容器。
  6. 容器启动后，kubelet 持续汇报状态（Running/Ready），控制面确认”期望状态已达成”。

整个过程都是控制器驱动的：没有谁命令谁，每个组件都在 watch 状态变化，然后朝着期望状态收敛。

2.4 Pod：最小的调度单元

  • Pod 是 K8s 中最小的调度和部署单元，一个 Pod 可以包含一个或多个容器。
  • 同一 Pod 内的容器共享网络命名空间（共享 IP、端口空间）和存储卷（Volume），通过 localhost 即可互相访问。
  • 容器崩溃时，kubelet 会重启它（RestartPolicy），但 Pod 整体不会重建——Pod 是”金丝雀”，即使容器反复重启，Pod 仍在原节点原地运行。
  • **永远不要让一个 Pod 只包含一个临时容器概念上的”多个进程”**——合理设计是多进程拆分到多个容器。

Sidecar 模式：一个 Pod 里除了主容器，再放一个”辅助容器”来扩展功能，二者共享网络与存储。典型场景：

  • 日志采集：主容器写日志文件，Sidecar（Filebeat）转发到 Elasticsearch
  • 代理注入：主容器被代理劫持流量，实现服务网格（见 4.3）
  • 配置刷新：Sidecar 监听配置变更并 reload 主容器

2.5 Service：稳定的访问入口

Pod 的 IP 是动态的（重建就变），所以不能直接用 Pod IP 通信。Service 提供稳定的虚拟 IP（ClusterIP），通过 Label Selector 选择后端 Pod，实现服务发现与负载均衡。

Service 类型 作用 使用场景
ClusterIP（默认） 集群内部虚拟 IP，仅集群内可访问 微服务之间互相调用
NodePort 在每台节点上开放一个端口（30000-32767），外部可通过 节点IP:NodePort 访问 测试环境、临时暴露
LoadBalancer 依赖云厂商，自动创建负载均衡器（SLB）并绑定外部 IP 云上生产环境
ExternalName 把 Service 映射到外部域名（CNAME），集群内可通过别名访问外部服务 对接外部老系统、第三方 API

流量转发原理（kube-proxy）：kube-proxy 监听 Service/Endpoint 变化，在每台节点上维护规则：

  • iptables 模式：为每个 Service 生成一组 iptables 规则，DNAT 到随机选择的后端 Pod IP。简单稳定，但更新大量规则时性能一般。
  • IPVS 模式：在内核实现负载均衡，支持多种调度算法（rr、lc 等），规则更多、吞吐更高。生产环境推荐。

3. 核心工作负载

3.1 Deployment：无状态应用首选

  • Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。这是一个两层结构：Deployment 负责”版本”，ReplicaSet 负责”副本数”。
  • 滚动更新（RollingUpdate）：默认更新策略，先起新 Pod，等就绪后再销毁旧 Pod，分批进行，全程服务不中断。
  • 回滚：每次发布都会记录历史版本（revision），kubectl rollout undo deployment/xxx 一键回到上个版本。

3.2 StatefulSet：有状态服务

数据库、消息队列等有状态服务需要稳定的网络标识和持久存储，StatefulSet 提供：

  • 稳定的 Pod 名称：Pod 名为 name-0、name-1、name-2，顺序创建、逆序删除，重建后名称不变。
  • 稳定的网络标识：配合 Headless Service（ClusterIP 为 None），可用 podname.svcname 直连某个实例。
  • 稳定的存储：每个 Pod 绑定独立的 PVC（持久卷声明），Pod 重建后数据不丢。

K8s 官方不提供内置的数据库，但可以通过 StatefulSet + Operator 方式部署（如 redis-operator、clickhouse-operator）。对大多数应用，数据库建议使用云厂商托管服务（RDS），自己运维 StatefulSet 的成本很高。

3.3 DaemonSet：每节点一个 Pod

  • DaemonSet 保证每个节点上运行一个 Pod 副本（新节点加入自动补上）。
  • 典型用途：日志采集 Agent（Filebeat/Fluentd）、监控 Agent（node-exporter）、网络插件（Calico/Felix）。

3.4 Job 与 CronJob

  • Job：执行一次性任务（批处理、数据迁移、备份），任务成功完成即退出，失败可自动重试（backoffLimit）。
  • CronJob：按 Cron 表达式定时执行 Job（定时同步、每日报表），格式与 Linux crontab 相同：*/5 * * * *。

4. 网络

4.1 网络插件：Flannel / Calico

K8s 网络模型要求：每个 Pod 都有独立 IP，且任意 Pod 间可直接通信（无需 NAT）。这个能力由 CNI（Container Network Interface）插件实现，常见两类：

Flannel（Overlay 网络）

  • 在每个节点上维护一个子网，Pod IP 跨节点访问时通过 VXLAN 隧道封装转发。
  • 简单、稳定、性能略低（封装开销），适合中小规模集群。

Calico（纯三层网络）

  • 基于 BGP 协议直接路由，不用隧道封装，性能更好；天然支持网络策略（NetworkPolicy）做微隔离。
  • 生产环境主流选择。

4.2 Ingress 与 Ingress Controller

Service 只解决”到哪个 Pod”，而 **Ingress 解决”从外部怎么进来”**：七层（HTTP/HTTPS）路由，按域名/路径把请求分发到不同的 Service。

理解要点：Ingress 只是声明（一份 YAML），真正干活的是 Ingress Controller（Nginx Ingress、Traefik、云厂商 SLB）。工作流程：

TLS 终止：HTTPS 证书放在 Ingress 上，Ingress Controller 负责解密，转发给后端的是 HTTP，后端服务不需要自己处理证书。

4.3 Service Mesh 简介

Service Mesh 把网络能力（限流、熔断、重试、灰度、链路追踪）从业务代码中剥离出来，下沉到 Sidecar 代理（Envoy）：

  • 每个 Pod 注入一个 Envoy 代理容器，所有进出流量都经代理转发。
  • 控制平面（如 Istiod）统一下发规则，实现流量的精细治理。
  • 与 K8s 的关系：Service Mesh 是 K8s 之上的附加层，用 Sidecar 注入（MutatingWebhook）实现，对业务代码零侵入。

对 Java 开发者来说：Service Mesh 相当于把 Spring Cloud 的 Ribbon/Hystrix/Feign 能力挪到了基础设施层。学习成本较高，中小团队建议先用好 K8s 原生能力（探针、HPA、rollout），再引入 Mesh。

5. 存储

5.1 Volume 类型

容器文件系统是临时的（容器重启数据就丢），Volume 用于给容器挂载持久或共享存储：

类型 生命周期 场景
emptyDir 随 Pod 创建/删除，容器间共享 同一 Pod 内容器交换数据（Sidecar 日志采集）
hostPath 节点目录，跨 Pod 不共享 单节点测试、读宿主机日志
nfs 网络文件系统，跨节点共享 自建 K8s 的共享存储
PVC 持久卷声明，数据保留 数据库、文件服务

5.2 PV 与 PVC

  • PV（PersistentVolume）：集群里的存储资源，由管理员（或云厂商）提供，比如一块 100Gi 的云盘。
  • PVC（PersistentVolumeClaim）：应用声明”我要一块 10Gi 读写的存储”，K8s 自动把满足条件的 PV 绑定给 PVC。

供给方式：

  • 静态供给：管理员预先创建 PV，PVC 去匹配（按容量、访问模式、StorageClass）。
  • 动态供给（推荐）：PVC 指定 storageClassName，K8s 通过 CSI 驱动自动创建云盘/NFS 目录，用完删除 PVC 即回收。

5.3 ConfigMap 与 Secret

把配置从镜像中剥离出来，实现配置与代码解耦：

  • ConfigMap：存放普通配置（明文），如 application.yml 片段、环境变量。
  • Secret：存放敏感信息（Base64 编码存储，仅存储层编码而非加密，生产需配合加密插件），如数据库密码、Token。

6.3 健康检查：三种探针

探针（Probe）是 K8s 判定容器健康的手段，Spring Boot 应用配合 spring-boot-starter-actuator，暴露 /actuator/health 即可。

探针 用途 失败后果 建议
startupProbe 判断应用是否启动完成 失败则重启容器（替代早期版本的 initialDelaySeconds） 慢启动应用（如 Spring Cloud 拉配置）必须配置，failureThreshold 给足
readinessProbe 判断应用是否就绪可接流量 失败则从 Service 端点中摘除（不重启） 依赖数据库/缓存就绪后才能接流量，必须配置
livenessProbe 判断应用是否存活 失败则重启容器 配置时务必小心：不要在探针路径上做重操作，避免”探针慢导致误杀”

最佳实践：

  • 启动慢的 Spring Boot 应用：startupProbe 探测 /actuator/health，periodSeconds 5、failureThreshold 30（即最多等 150 秒），启动完成后 liveness/readiness 才开始工作。
  • livenessProbe 与 readinessProbe 共用 /actuator/health 即可；如需区分，readiness 可以带组件状态（如数据库），liveness 只查应用本身存活。
  • 不要把 /actuator/health 之外的重接口当探针路径。

6.4 资源限制与 JVM 内存设置

requests 与 limits：

7. 可观测性

7.1 日志

基础用法：

日志采集（EFK/ELK）：Pod 删除后日志就没了，生产环境需要集中采集。常见方案：

  • 架构：Fluentd/Filebeat（DaemonSet 形式采集）→ Elasticsearch → Kibana。
  • 采集方式：容器 stdout/stderr → 节点 Docker/containerd 日志目录 → Fluentd 转发。Java 应用把日志打到 stdout 即可，不要写本地文件，否则采集要额外配置。

7.2 监控：Prometheus + Grafana

标准监控方案：

  • node-exporter（DaemonSet）：采集节点指标（CPU、内存、磁盘、网络）。
  • cadvisor / kubelet metrics：采集 Pod 与容器指标。
  • Prometheus：抓取指标并存储，内置 Alertmanager 告警。
  • Grafana：可视化仪表盘，社区有大量现成模板（如 8932 号的 Java 指标面板）。

Java 应用接入：

Prometheus 通过 ServiceMonitor（Prometheus Operator 生态）或静态配置抓取 /actuator/prometheus 指标。即可看到 JVM 堆内存、GC 次数、线程数、HTTP 请求量等指标。

7.3 健康检查与就绪探针的最佳实践

  1. 三种探针分工明确：startup 管启动、readiness 管流量、liveness 管重启，不要混用。
  2. 探针路径必须轻量：探针只查存活/就绪，不做重操作（不要调数据库做 liveness 检查——数据库抖动会导致容器被反复重启）。
  3. 配置探针超时与容错：timeoutSeconds、failureThreshold 给足，避免慢启动被误杀。
  4. 探针失败要有区分：依赖缺失（DB 连不上）→ readiness 失败（摘流量），而不是 liveness 失败（重启也起不来，还会雪崩）。
  5. 每次发布前在测试环境验证探针路径确实可用（curl http://localhost:8080/actuator/health）。

8. Pod 调度机制与调度故障排查

8.1 调度器如何选节点

调度（Scheduling）：新 Pod 创建后，kube-scheduler 负责选一个节点运行它——不是随机选，而是两阶段：

flowchart LR
    P["新 Pod<br/>(Pending)"] --> F["预选 Filter<br/>排除不满足硬性条件的节点"]
    F --> S["优选 Score<br/>给剩余节点打分"]
    S --> B["选最高分节点绑定"]
阶段 机制 典型规则
预选（Filter） 过滤掉硬性不满足的节点 资源够不够（requests）、端口冲突、节点亲和/反亲和、污点容忍
优选（Score） 给候选节点打分排序 资源余量（LeastRequested）、Pod 分布均衡（Spread）
绑定 写 etcd：Pod → node 绑定 节点上的 kubelet 收到后开始拉镜像创建容器

因果链：调度只看 requests（预留值），不看 limits（上限值）——这是调度与运行时的重要区别：requests 决定「节点敢不敢接这个 Pod」（资源账本），limits 决定「跑起来后最多能用多少」。requests 写小了 → 节点超卖 → 运行时 CPU 被限流、内存被 OOMKilled（详见 9.3）。

8.2 污点与容忍：主动「赶走」Pod

概念 作用
污点（Taint） 打在节点上：「我这里有特殊标签，不匹配的 Pod 别来」
容忍（Toleration） 打在 Pod 上：「我知道这个污点，允许被调度到这里」

常用污点类型（节点自动打的）：node.kubernetes.io/not-ready（节点故障）、node.kubernetes.io/unreachable（网络隔离）、NoSchedule（不调度新 Pod）。

动手验证：给节点打污点

观察点：打 NoSchedule 污点后新建 Pod 不会落到 node1（事件里可见 0/N nodes available + 污点原因）；NoExecute 会驱逐已有 Pod。判定标准：理解「污点让节点主动挑人，亲和让 Pod 主动挑节点——两者是调度控制的正反两面」。

8.3 调度故障排查：Pod 一直 Pending

Pod 卡在 Pending 是调度问题最典型的信号——99% 的原因就三类：

症状 原因 定位命令
Pending + 事件提示资源不足 节点 CPU/内存 requests 不满足 kubectl describe pod <name> → Events；kubectl top nodes 看余量
Pending + 事件提示污点不匹配 节点有污点，Pod 没容忍 Events 里 taint 关键词；检查 spec.tolerations
Pending + 节点不可调度 节点 NotReady / cordon kubectl get nodes 看 STATUS

因果链：Pending 的本质是「预选阶段没有节点通过」——describe 的 Events 会直接告诉你被哪个规则挡了（资源/污点/存储卷未绑定）。先看 Events 再动手，不要盲猜——这是调度排查与 9.1 三板斧衔接的第一原则。

8.4 节点亲和与反亲和

类型 用途 示例
nodeSelector 最简单：按 label 选节点 nodeSelector: {disk: ssd}
nodeAffinity 软/硬亲和，支持表达式 requiredDuringScheduling（硬）vs preferredDuringScheduling（软）
podAntiAffinity Pod 之间互相远离 高可用：同应用副本分布在不同节点

动手验证：要求 Pod 落在 SSD 节点

观察点：节点没有 disk=ssd 标签时 Pod 一直 Pending；打上标签后立即调度成功。判定标准：亲手验证「硬亲和不满足 = Pending」，理解 affinity 是「资源过滤之外的业务约束」。

解决思路：

小结

给 Java 开发者的学习路线建议：

  1. 先跑通：Docker Desktop 或 minikube，用第 6 节的 YAML 把 Spring Boot 应用部署起来。
  2. 理解三大抽象：Pod（调度单元）、Deployment（无状态应用）、Service（访问入口），掌握 9.1 的三板斧排查。
  3. 再上生产：Ingress、PV/PVC、HPA、滚动发布，配合监控告警逐步完善。
  4. 最后进阶：StatefulSet、Service Mesh、自定义 CRD——等前 3 步都踩过坑再学。

K8s 的学习曲线确实陡，但它解决的是分布式部署的通用问题——掌握之后，部署、扩容、发布这些曾经头疼的事，都会变成几行 YAML 和一条命令。
