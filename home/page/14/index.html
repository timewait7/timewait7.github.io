Netty 原理与实践

Posted on 2025-07-22 In 中间件 Word count in article: 15k Reading time ≈ 53 mins.

Netty 是 Java 网络编程绕不开的高性能基石，也是高级 Java 工程师面试的必考环节。本文从 BIO 的阻塞困境讲起，逐层剖析 Netty 的线程模型（Reactor 演进）、ChannelPipeline 责任链、编解码器、TCP 参数调优、心跳与断线重连、ByteBuf 内存管理，再到启动/连接/读数据三大源码链路，最后用 15 个类的完整代码手写一个可运行的 RPC 框架，并盘点 Dubbo、RocketMQ、gRPC、Elasticsearch 中 Netty 的真实应用。

1. 从 BIO 到 NIO 到 Netty

1.1 BIO 的阻塞困境

这个”一连接一线程”模型的三个致命问题：

  1. 线程数 = 连接数。每个连接占一个线程，线程栈默认 1MB，1 万个连接就是 10GB 虚拟内存，还要加上线程上下文切换的 CPU 开销。连接数达到 C10K（1 万台客户端同时在线）时系统直接崩溃。
  2. 线程大量阻塞空转。大多数连接处于”等待数据”状态，线程阻塞在 read() 上不干活，却占着栈内存和调度资源。
  3. 连接数不可控。高并发下创建线程本身就会触发 OOM，且无法优雅降级。

1.2 NIO 的复杂性

Java 1.4 引入 NIO，核心思想是用少量线程通过 Selector 多路复用管理大量连接：Selector 上注册感兴趣的连接，内核帮你监听，有事件了才通知。

模型对了，但直接用 NIO 写生产代码，坑多到让人想辞职：

  • Selector 空轮询 bug（JDK 6462197 / Linux epoll bug）：select() 在没有事件时也可能立即返回 0，导致 CPU 空转 100%。这个 bug 在部分 JDK + Linux 内核组合下依然存在，必须自己加”空轮询计数 + 重建 Selector”的兜底逻辑。
  • 粘包/半包：TCP 是字节流协议，没有消息边界。你 send 了两次 "hello"，对端可能一次收到 "hellohello"（粘包），也可能先收到 "hel"（半包）。每条消息的边界全靠自己解析。
  • ByteBuffer 难用：flip()、compact()、rewind()、clear() 四个方法转换位置状态，写错一次指针，数据就错乱；Buffer 还没有自动扩容能力。
  • 缺乏高层次抽象：没有”处理器链”、没有编解码器、没有心跳、没有优雅停机，所有东西都得从零手写，还容易写错。

1.3 Netty 的设计目标

Netty 的设计目标一句话：把 NIO 的复杂度全部封装掉，给你一个事件驱动的高性能网络编程框架。它做到了：

痛点 Netty 的解法
线程模型复杂 统一的 EventLoop 事件循环模型，一个连接的所有 IO 都在同一线程串行执行
Selector 空轮询 rebuildSelector() 自动重建 Selector，无感
粘包半包 ByteToMessageDecoder + 各种现成 FrameDecoder
ByteBuffer 难用 ByteBuf 读写双指针、自动扩容、池化、引用计数
无处理器抽象 ChannelPipeline 责任链 + 丰富的 ChannelHandler
内存开销大 直接内存 + 对象池 + 零拷贝
无配套能力 心跳（IdleStateHandler）、断线重连、超时控制、优雅停机、内存泄漏检测一应俱全

还有一个隐性价值：Netty 屏蔽了底层 IO 模型的差异。同样的代码可以跑在 NIO（多路复用）、Epoll（Linux 原生）、OIO（阻塞，已废弃）、KQueue（Mac）、甚至 io_uring 上，换一个 EventLoopGroup 和 Channel 类型即可。

2. Netty 线程模型

面试官想问什么：Reactor 三种模式的演进逻辑是什么？BossGroup/WorkerGroup 各干什么？为什么 boss 线程 1 个就够？EventLoop 和线程是什么关系？为什么说”一个 Channel 绑定一个 EventLoop 后不会变”？业务耗时操作写在 handler 里会有什么后果？

2.1 Reactor 模式回顾

Reactor（反应堆）模式的核心：一个线程（或者几个线程）负责监听和分发所有 IO 事件，事件到了再调用对应的处理器，而不是为每个连接开一个线程。分三个演进阶段：

单 Reactor 单线程：一个线程既负责 accept 新连接，又负责读写和业务处理。问题：一个业务阻塞，所有连接都卡死。只适合 Demo。

单 Reactor 多线程：Reactor 线程只负责 IO 事件的监听和分发，业务处理丢给工作线程池。问题：高并发下 Reactor 单线程依然是瓶颈（accept、read、write 都在它身上），且可能出现并发操作同一连接的问题。

主从 Reactor 多线程（最成熟）：主 Reactor 只负责 accept 新连接，把连接交给从 Reactor；从 Reactor 负责该连接的读写，业务仍交给业务线程池。Netty 就是这种模型。

生产经验：如果业务 handler 里都是纯异步操作（最常见的场景），可以直接用一个 group，把 accept 和 IO 混在一个 EventLoopGroup 里，省掉一半线程。但如果业务里可能出现阻塞操作，务必拆开，否则一个慢连接会拖垮 accept。

一个经典的坑：

引用计数的核心规则：ByteBuf 实现 ReferenceCounted 接口。release() 一次计数减一，减到 0 就归还池子。规则很简单——谁最后消费了消息，谁负责 release：

  • 用 SimpleChannelInboundHandler 业务处理，框架自动释放；
  • 用 ChannelInboundHandlerAdapter，处理完调 ReferenceCountUtil.release(msg)；
  • 消息继续往下游传播（调了 fireChannelRead(msg)）时，不要 release，让下游处理；
  • 把消息引用存到成员变量长期使用（非引用计数对象包装）时，必须 retain() 一次，防止被其他 handler 释放；
  • 分发给多个消费者时，每个消费者 retain()，最后每个都 release()。

排查内存泄漏：启动参数加 -Dio.netty.leakDetection.level=paranoid（默认是 simple 抽样检测），Netty 会在泄漏的 ByteBuf 被 GC 时打印创建它的堆栈（LEAK: ByteBuf.release() was not called before it's garbage-collected）。

面试官追问：pipeline 中一个 handler 抛异常会怎样？异常沿入站方向传播，exceptionCaught 事件从抛错点向后传播，直到有 handler 处理它；如果没有任何 handler 处理，最后会到 tail，Netty 只打一条 warn 日志（不会自动关连接）。所以一定要在 pipeline 尾部加一个兜底 exceptionCaught handler，统一打日志 + 关闭连接，防止半开连接堆积。

4.1 ByteToMessageDecoder 与 MessageToByteEncoder

ByteToMessageDecoder（入站）：入站处理的基类。核心机制是字节累积（cumulation）：

write() 流程：acceptOutboundMessage(msg) 检查消息类型（类型不匹配直接透传）→ 分配 ByteBuf（默认用 Channel 的 ALLOCATOR，即池化分配器）→ encode() 往 Buffer 里写字节 → writeAndFlush 交给下一个出站节点。

子类选择：两个典型的中间形态——MessageToMessageDecoder<I>（把一种对象转成另一种，如 String → JsonObject，不会累积累积缓冲）和 MessageToMessageEncoder<I>。判断标准很简单：输入是不是字节流。入站 ByteToMessageDecoder 管字节到对象，MessageToMessageDecoder 管对象到对象。

4.2 粘包半包问题

TCP 是流协议，粘包半包是必然现象，解决思路只有一个：让协议有消息边界。四种经典方案：

方案一：固定长度（FixedLengthFrameDecoder）

简单粗暴，但定长浪费带宽，几乎没人这么设计协议。

方案二：分隔符（LineBasedFrameDecoder / DelimiterBasedFrameDecoder）

问题：数据里不能出现分隔符，需要转义；每条消息还多付一个字节。

方案三：长度字段（LengthFieldBasedFrameDecoder）——生产最常用

参数含义：

参数 含义 示例值
maxFrameLength 帧的最大长度，超过抛异常（防内存攻击） 10MB
lengthFieldOffset 长度字段在帧内的起始偏移 0
lengthFieldLength 长度字段占几个字节 4
lengthAdjustment 长度字段的值 + 调整值 = 帧的总长度或体长度 0（总长）/-4（体长）
initialBytesToStrip 解码后从帧头剥离多少字节（把长度字段剥掉，下游直接拿数据） 4

[4 字节长度][N 字节数据] 这种”长度在前”的格式最常用：maxFrameLength=10MB, lengthFieldOffset=0, lengthFieldLength=4, lengthAdjustment=0, initialBytesToStrip=4——也就是上面那个构造。它输出给下游的 ByteBuf 是”纯数据”，长度信息已被消费。如果下游解码器还需要长度头（比如要校验），initialBytesToStrip 就设为 0。

方案四：自定义协议（魔数 + 长度），见 4.4。

生产经验：maxFrameLength 一定要设，且要比真实最大消息略大。某次线上事故：消息体被恶意/异常数据撑爆，maxFrameLength 设的 10MB 不够，Decoder 抛 TooLongFrameException，由于没有 exceptionCaught 兜底，异常沿 pipeline 传播到 tail 只打了日志，连接半开，客户端重试 → 更多连接打满。修复：maxFrameLength 按业务上限 + 20% 裕量设置，并在 pipeline 尾部统一处理 TooLongFrameException 主动 close。

5.2 高低水位机制（WRITE_BUFFER_WATER_MARK）与 OOM 防护

问题场景：服务端给下游大批量推送数据（如广播、报表导出），如果下游消费慢，数据会堆积在两个地方——Netty 的 ChannelOutboundBuffer（应用层写缓冲）和内核发送缓冲。写缓冲不设上限，数据持续堆积 = 直接内存 OOM。

Netty 的解法是高低水位：出站缓冲的预估字节数超过高水位时，channel.isWritable() 返回 false，并触发 channelWritabilityChanged 事件；降回低水位之下时恢复 true 并再次触发事件。

  • 写缓冲的字节预估包括：未 flush 的消息 + 已提交但未写完的数据，是”大概值”，不精确但足够做流控；
  • isWritable() 判断的是”应用层写缓冲是否超过高水位”，与内核发送缓冲无关；

6. 心跳与断线重连

6.1 IdleStateHandler 原理与使用

IdleStateHandler 是 Netty 内置的空闲检测器，参数：readerIdleTime（读空闲，多久没收到数据）、writerIdleTime（写空闲）、allIdleTime（读写都空闲），任意为 0 表示不检测。

原理：handlerAdded 时在当前 channel 绑定的 EventLoop 上注册一个延迟任务，任务在 EventLoop 线程内周期性执行，对比”上次读写时间”与当前时间，超过阈值就触发一个 IdleStateEvent，通过 userEventTriggered 事件传给下游 handler。关键细节：

  • 在 channelRead/channelReadComplete 中更新”最后读时间”（内部用 reading 状态避免大消息读取中途被误判为空闲）；
  • 空闲任务跑在事件循环线程里，不需要额外的定时器线程，一个 EventLoop 管理它名下所有连接的空闲检测；
  • 事件触发后不会自动关闭连接，只发事件，关不关由你决定。

6.2 心跳机制设计（PING-PONG、心跳超时断连、重连策略）

生产环境的心跳设计参数（经过验证的模板）：

角色 策略 参数依据
客户端 每 30s 发一次 PING（allIdle 触发） 心跳间隔 = 业务容忍的”假死时间”的 1/3 左右
客户端 90s 没收到任何数据（readerIdle）→ 判定服务端故障，进入重连 3 倍心跳间隔，容忍网络抖动和丢包重传
服务端 90s 没收到任何数据 → 关闭连接 与客户端 readerIdle 对齐，防止半开连接堆积
双方 PONG 回复不是必须的 任意一个字节（包括业务响应）都算”有数据”，天然重置空闲计时

为什么是 3 倍：一次 PING 丢失（网络抖动/GC 停顿/中间设备丢弃）不应导致断连，3 次机会基本覆盖瞬态故障；同时必须小于中间设备（NAT、LB、云防火墙）的空闲回收时间。经典线上事故：云厂商 LB 的空闲连接回收时间是 120s，服务端心跳周期是 180s，结果所有长连接在 120s 处被 LB 静默切断，客户端却毫无感知，直到下次发请求才发现连接已死。修复：心跳周期改成 30s。

断线重连（指数退避 + 随机抖动）：

重连的三个纪律：

  1. 重连调度必须挂在 EventLoop 上（ctx.executor().schedule），避免多个线程同时重连导致连接风暴；
  2. 指数退避 + 随机抖动，否则大量客户端同一时刻重连会打爆服务端（惊群）；
  3. 重连期间要主动放弃旧资源：channelInactive 里清理 pending 请求、关闭旧 Channel 防止泄漏。

6.3 心跳检测与业务检测分离

把”心跳”和”业务”耦在一起是生产环境最常见的设计错误，三条原则：

  1. 消息类型分离：心跳是协议的一种消息类型（type 字段区分），而不是在业务消息里塞标志位。心跳消息不经过业务线程池，直接在 IO 线程回复；
  2. 超时配置分离：心跳超时（90s 级）和业务超时（秒级/毫秒级）是两套机制。业务超时用 ReadTimeoutHandler 或 RPC 层 Future 超时，心跳超时用 IdleStateHandler——混用会导致”业务慢一点就被判死连接”；
  3. 心跳 handler 的位置：放在编解码器之后、业务 handler 之前。心跳包解码成 HeartbeatMessage 后直接由 HeartbeatHandler 消费（回复 PONG），不再向下传播，不打扰业务层：

生产经验：如果系统有百万级连接需要大量定时任务，IdleStateHandler 默认用 EventLoop 的调度队列（每连接一个调度条目，量大时可观）。Netty 还提供了 HashedWheelTimer（时间轮）用于统一管理海量超时任务——事件循环 + 时间轮是大型网关的标准组合，面试提到这个细节会加分。

7. ByteBuf 内存管理

7.1 ByteBuf 的读写指针（readerIndex/writerIndex/capacity）

ByteBuf 是替代 ByteBuffer 的缓冲区，核心是读写双指针模型：

  • readerIndex <= writerIndex <= capacity 恒成立；
  • readXxx() 移动 readerIndex（读走可读数据），writeXxx() 移动 writerIndex；
  • readableBytes() = writerIndex - readerIndex，writableBytes() = capacity - writerIndex；
  • markReaderIndex()/resetReaderIndex() 标记与回退（解码器判断半包时回退的利器）；
  • discardReadBytes()：把未读数据搬到头部（有拷贝，频繁调用有性能损耗），用于内存紧张场景；
  • clear()：两个指针都归零，不清理数据，是最廉价的”复位”；
  • 自动扩容：写满了自动扩大 capacity（翻倍增长，有上限），这是 ByteBuffer 没有的能力。

7.2 堆内存 vs 直接内存（HeapByteBuf vs DirectByteBuf）

对比项 HeapByteBuf（堆内） DirectByteBuf（堆外/直接内存）
分配位置 JVM 堆 堆外（Unsafe/malloc 分配）
创建速度 快（对象分配即可） 慢（系统调用），必须池化
回收 GC 自动 引用计数，必须手动 release，泄漏会导致堆外 OOM（OutOfMemoryError: Direct buffer memory）
IO 性能 差：系统调用必须用堆外，需要一次拷贝（堆内 → 临时堆外 → 内核） 好：直接交内核，省一次拷贝
业务处理 好：可拿到 byte[] 数组，读写方便 差：无法拿数组，只能 getBytes() 拷贝出来

结论（Netty 的默认策略）：网络 IO 层（编解码器产出/消费的 buffer）用池化的直接内存——读写 socket 时零拷贝；业务处理层如果需要长时间持有数据（比如塞进队列做异步处理），拷贝成堆内对象再释放原 buffer。这就是 ALLOCATOR 默认是 PooledByteBufAllocator 且 DEFAULT_DIRECT 为直接内存的原因。

生产经验：内存泄漏检测开 paranoid 级别压测环境抓泄漏；线上用 -Dio.netty.leakDetection.level=simple（抽样）。堆外内存不归 JVM 堆管，-Xmx 不够约束它，监控要盯 Direct buffer memory。

7.3 PooledByteBufAllocator 与对象池

Netty 4.1 默认分配器是 PooledByteBufAllocator，核心结构：

分配流程：请求分配 → 按大小分类 → 优先从 ThreadLocal 缓存取 → 没有则从 PoolSubpage/PoolChunk 分配 → 最终分配不到再 Unsafe 向系统申请新内存块。归还（release）流程反过来，用过的 ByteBuf 回到池子。

收益：直接内存的分配/释放是系统调用，池化后高频分配释放不再触碰系统，同时减少 GC 压力和内存碎片。代价是池子本身占内存（可通过 -Dio.netty.allocator.maxOrder、-Dio.netty.allocator.tinyCacheSize 等调优）。

面试官想问什么：为什么 Netty 不用 NIO 的 ByteBuffer.allocateDirect？答：直接内存分配慢 + 回收不可控（依赖 GC），池化后分配变成”从池里取”，快且可控。再追问：池化内存泄漏怎么发现？答：ResourceLeakDetector（引用计数归零前对象被 GC 会打泄漏堆栈）+ 堆外内存监控曲线。

7.4 零拷贝：CompositeByteBuf / slice / FileRegion / wrap

Netty 的”零拷贝”要分两层理解：

第一层：用户态免拷贝（Java 层不搬数据）

典型场景：HTTP 响应 = 响应头 + 响应体，用 CompositeByteBuf 组合直接交给协议层，避免拼接大 byte[] 的拷贝。

第二层：内核态零拷贝（sendfile）

FileRegion.transferTo() 最终调用 Linux sendfile() 系统调用：数据从磁盘 → 内核页缓存 → socket 直接发送，完全不经过用户态和应用内存。几十 GB 的文件传输只占几 KB 内存，这是”文件下载”类接口必须用 FileRegion 的原因。

生产经验：零拷贝不是免费的——slice/wrappedBuffer 是视图，任何一方修改都会互相可见；引用计数要算清楚（retainedSlice、CompositeByteBuf.addComponents(true, ...)）；FileRegion 传输是异步的，文件句柄必须在 write 完成的 listener 里关，提前关文件数据就断了。

10. Netty 在主流框架中的应用

10.1 Dubbo 中的 Netty（NettyServer / NettyClient）

Dubbo 的 RPC 传输层默认就是 Netty（dubbo-remoting-netty4 模块）：

  • NettyServer：服务端，内部是 ServerBootstrap + NettyServerHandler（适配器），配 IdleStateHandler 做心跳；
  • NettyClient：客户端，Bootstrap + NettyClientHandler；
  • NettyChannel：把 Netty 的 Channel 包装成 Dubbo 自己的 Channel 抽象，隔离传输层实现（Netty/MinNet/Http 可切换）；
  • HeaderExchangeHandler：在 Netty pipeline 之上实现 Dubbo 协议——Magic(2) + Flag(1) + Status(1) + RequestId(8) + 数据长度(4)，这就是一个典型的 LengthFieldBasedFrameDecoder 使用场景；
  • 心跳与断开重连：客户端 NettyClient 空闲时发心跳，断开后自动重连（指数退避）；服务端 AllIdleTimeout 关闭死连接；
  • 线程模型：Netty 的 IO 线程负责收发，业务执行在 Dubbo 自己的业务线程池（ThreadPoolExecutor），IO 与业务彻底隔离。

Dubbo 3 的 Triple 协议（HTTP/2 之上）同样构建在 Netty 上，把 RPC 与 HTTP 的能力合二为一。

10.2 RocketMQ 中的 Netty（RemotingServer）

RocketMQ 的通信层（rocketmq-remoting 模块）基于 Netty：

  • NettyRemotingServer / NettyRemotingClient：封装了 ServerBootstrap/Bootstrap，默认 boss 1 线程、worker 默认 CPU + 1；
  • RemotingCommand：统一协议对象，报文结构是 4字节总长 + 4字节头长 + 头(JSON/fastjson) + 体(二进制)；
  • NettyRequestProcessor：请求处理器接口，Broker/NameServer 各自注册处理器，处理器执行在 defaultExecutor 业务线程池；
  • 四种通信模式：oneway（只发不收）、sync（阻塞等待）、async（InvokeCallback 回调）、request-response（服务端主动推）——全部基于 Semaphore + Future + ChannelFutureListener 实现；
  • 心跳：ChannelEventListener 监听连接事件，空闲连接定时清理；网络断开事件触发 disconnect 回调，客户端重建 ChannelFuture 重连。

10.3 gRPC 与 Netty 的关系

gRPC 的 Java 实现（grpc-netty）直接长在 Netty 上：

  • NettyServerBuilder / NettyChannelBuilder：把 gRPC 的 Server/Channel 抽象与 Netty 的 ServerBootstrap/Bootstrap 绑定；
  • gRPC 传输层是 HTTP/2，而 Netty 内置了完整的 HTTP/2 编解码（Http2FrameCodec、Http2MultiplexCodec），gRPC 复用这套能力；
  • 序列化：proto（ProtobufEncoder/ProtobufDecoder 同款生态）+ HPACK 头压缩；
  • 官方同时提供 OkHttp transport 作为备选，但 Netty 是主力（性能、功能最全），生产环境基本都用 Netty。

所以问”gRPC 用的是什么网络框架”，答案是：HTTP/2 由 Netty 实现，gRPC 是跑在 Netty 之上的协议框架。

10.4 Elasticsearch 的 Netty4Transport

ES 的节点间通信（transport 层）和 HTTP REST 层都基于 Netty：

  • Netty4Transport：节点间 RPC，内部 NioGroup（boss 1 线程 + worker 可配）管理连接；每条消息用”长度前缀 + CRC32 校验”的帧格式（SizeHeaderFrameDecoder），破损帧直接抛异常断开；
  • Netty4HttpServerTransport：REST 层，处理 _search 等 HTTP 请求；
  • ES 的请求处理：Netty IO 线程只做协议解析，解析出的 TransportRequest 扔进 ES 自己的线程池（如 search/write/get 分池），各池独立限流——这是大型系统用 Netty 的通用模式：Netty 只当”收发器和解码器”，业务永远在自己可控的线程池里；
  • 内存管理：ES 大量使用直接内存 + 池化（Recycler 对象池），与 Netty 的 ByteBuf 池化一脉相承；
  • ES 还贡献了”压测调参”的经典方法：用 _cat/thread_pool 观察各池队列长度，队列堆积说明要扩容对应池——同样的方法论适用于所有 Netty 服务。

四个框架的共同点：IO 线程只做收发与协议解析，业务全部隔离在各自线程池；都重度依赖 LengthFieldBasedFrameDecoder 系的拆帧；都用 IdleStateHandler 心跳 + 自动重连保证长连接可用性。理解了本文第 2、3、4 节的原理，任何一个基于 Netty 的框架你都能一天上手——这就是”掌握框架底层”的价值。

3. Mapper 动态代理机制【面试核心考点】

面试官在问什么：Mapper 接口明明没有实现类，为什么 session.getMapper(UserMapper.class) 返回的对象能执行 SQL？答案的深度决定了面试评级——背出”JDK 动态代理”是及格分，能讲清 MapperProxy → MapperMethod → SqlSession 三级调用、statementId = 接口全限定名.方法名 的绑定规则、以及”为什么必须用接口而不是类”才是优秀。

3.1 JDK 动态代理回顾

MyBatis 的 Mapper 机制基于 JDK 动态代理：代理对象在运行时由 Proxy.newProxyInstance 生成，对接口的每个方法调用都会被 InvocationHandler.invoke 拦截。

要点：JDK 动态代理只能代理接口（new Class<?>[]{...} 传入的是接口数组），这正是 Mapper 必须是接口的根因；MapperProxy 是 InvocationHandler，但它的 invoke 不转发给”真实实现类”，而是转发给 MyBatis 的执行引擎。

3.4 为什么 Mapper 接口不需要实现类

完整回答分四步：

  1. 绑定阶段：解析 XML 时，XMLMapperBuilder.bindMapperForNamespace() 发现 <mapper namespace="com.example.mapper.UserMapper">，就把 UserMapper.class 注册进 MapperRegistry（knownMappers Map）；纯注解方式由 <mapper class="..."> 或 Configuration.addMapper(Class) 注册。
  2. 获取阶段：session.getMapper(UserMapper.class) 从 MapperRegistry 取 MapperProxyFactory，通过 Proxy.newProxyInstance 生成实现 UserMapper 接口的代理对象。
  3. 调用阶段：方法调用被 MapperProxy.invoke 拦截，MapperMethod 以 接口全限定名.方法名 为 key 从 Configuration.mappedStatements（StrictMap）中取出 MappedStatement，然后走第 2.2 节链路。
  4. 执行阶段：MappedStatement 里的 SqlSource 生成 BoundSql，由 Executor 驱动 JDBC 完成真实查询。

为什么不用 CGLIB 而必须用 JDK 动态代理？

  • Mapper 本来就是接口，JDK 代理零依赖、开销小；
  • JDK 代理只能代理接口，反过来约束了”Mapper 只能是接口”——接口天然与实现解耦，SQL 绑定只依赖方法签名（名字 + 注解），不依赖方法体；
  • 接口没有字段，代理对象的状态（sqlSession、methodCache）放在 MapperProxy 里，干净无污染。

两个容易答错的知识点：

  • 重载：两个同名方法（仅参数不同）共享同一个 statementId，行为不可预期。MyBatis 不支持 Mapper 方法重载，实际项目中不要这样写。
  • XML 与注解冲突：同一个 statementId 在 XML 和注解中都出现时，启动抛 IllegalArgumentException: Mapped Statements collection already contains value for ...（mappedStatements 是 StrictMap，拒绝重复 key）。规则是只能二选一，常见的注解 + XML 混用方式是不同方法分别用，不是同一方法双写。

MyBatis 与 Spring 整合后的一级缓存行为（高频易错点，详见第 7 章）：

  • 非事务环境：mybatis-spring 每次 Mapper 调用都是”拿新 SqlSession → 用完关闭”，一级缓存形同虚设（每次查询新会话）；
  • 事务环境（@Transactional）：整个事务绑定同一个 SqlSession，一级缓存有效且共享，同事务内相同查询只执行一次；
  • 结论：在 Spring 项目中，”一级缓存没有用”的说法只对非事务调用成立，事务内它仍然起着去重查询的作用。

6.2 二级缓存（Mapper 级别）

开启链路：全局 cacheEnabled=true（默认）→ Mapper 配置 <cache/>（或注解 @CacheNamespace）→ Configuration.newExecutor 时用 CachingExecutor 装饰真实 Executor：

二级缓存的特性：

  • 粒度：namespace（一个 Mapper 文件/接口）一个缓存实例，不同 namespace 完全隔离；
  • key 与 value：key 与一级缓存相同（CacheKey）；value 是整个结果 List（序列化后的副本）；
  • 写入延迟：CachingExecutor 通过 TransactionalCacheManager（tcm）管理，查询结果先放进事务缓存，事务 commit 时才真正写入二级缓存，rollback 时丢弃——这是避免”事务内查了脏数据污染缓存”的关键设计；
  • 序列化要求：readOnly=false（默认）时使用 SerializedCache 对结果做深拷贝，**实体类必须实现 Serializable**，否则报 NotSerializableException。

flushInterval 无（不按时间刷新） 毫秒

6.3 缓存穿透与脏读问题

① “缓存穿透”（MyBatis 语境）：MyBatis 缓存不缓存 null 结果——反复查询不存在的记录（如 selectById(99999)）永远穿透缓存直查数据库。生产中的经典组合拳是 MyBatis 一级/二级缓存之上再叠一层 Redis，Redis 层对空结果做 null 缓存（TTL 短），MyBatis 层只服务于高频热数据。

② 脏读（跨 namespace 不一致）：二级缓存按 namespace 隔离，但 SQL 可以跨表。典型事故现场：

t_user 被 UserMapper 更新后，UserMapper 的缓存会被 flushCache 清空，但 OrderMapper 的缓存里还躺着旧 join 结果——查询仍返回脏数据。

解决方案（按推荐度排序）：

  1. 关闭涉及多表 join 的 namespace 缓存（最常用）；
  2. <cache-ref> 把相关联的 namespace 指向同一个缓存实例（粒度粗，命中率互相拖累）；
  3. 报表类查询全部 useCache="false"；
  4. 结合缓存刷新策略（如 TTL + 数据版本号）。

③ 多实例不一致：二级缓存是进程内缓存（PerpetualCache 就是 HashMap），多节点部署时每个 JVM 各存一份，flushCache 只能清本节点的缓存——这是生产环境禁用二级缓存的最硬核理由。

④ 事务相关陷阱：

  • 二级缓存写入延迟到 commit：长事务里别的线程读到的是旧值（属于正常语义，但容易让人困惑）；
  • flushCache 也是走 tcm 的延迟清理：事务提交后才真正清缓存，事务回滚则不清。

6.4 生产环境缓存建议

决策树：

为什么很多团队禁用二级缓存（面试要点）：

  1. 跨节点一致性无解（多实例各自缓存）；
  2. 跨 namespace 脏读防不胜防（join 查询）；
  3. 序列化开销 + 实体必须 Serializable 的侵入性约束；
  4. 排查问题时”为什么数据没变”的困惑成本远高于缓存收益；
  5. 一级缓存已经覆盖了事务内的去重查询，二级缓存的边际收益有限。

③ 懒加载陷阱（性能与心智双重成本）

配置：lazyLoadingEnabled=true + aggressiveLazyLoading=false（3.4.2 起默认 false）。行为：

  • fetchType="lazy" 的 association/collection 第一次被访问时才发子查询；
  • aggressiveLazyLoading=true 时访问任意属性都会把所有懒加载属性全部触发；false 只加载被访问的那个（默认，推荐）；
  • lazyLoadTriggerMethods 默认 equals,clone,hashCode,toString：这些方法被调用也会触发加载。

陷阱清单：

  1. N+1 查询（见 10.2 ①）；
  2. 序列化问题：懒加载代理对象跨 JVM 传输（Dubbo/Redis）后反序列化失效；
  3. 会话关闭后触发：SqlSession 关闭后访问懒加载属性，报 Executor was closed（3.5.x 中 ResultLoader 检测到 Executor 已关闭会新建 Executor 重试，但依赖数据源可用与上下文完整，Spring 事务外极不稳定）；
  4. 调试困惑：看日志时一条 SQL 变成了若干条，排查”为什么这么慢”时先看懒加载。

④ 常规 SQL 性能守则：

  • 不用 SELECT *，显式列（大字段尤其）；
  • 大文本/BLOB 字段拆表或拆查询（列表页不查，详情页才取）；
  • ORDER BY 尽量走索引；深分页（LIMIT 100000, 20）用”上次 id 游标”优化；
  • 统计类查询与业务查询分开 Mapper 方法；
  • 为慢 SQL 配置统一拦截器（第 5.4 节），监控常态化。

Plus 的真实坑（来自生产）：

  1. 与原生插件体系不互通：Plus 用自己的 MybatisPlusInterceptor 管理内建插件（分页/乐观锁/多租户），PageHelper 与 Plus 分页插件二选一，别混用；
  2. 条件构造器写复杂 SQL 很痛苦：join/子查询/union 还是回 XML；

  5. updateById 默认不更新 null 字段（FieldStrategy.NOT_NULL）——期望”把字段置空”的场景会静默失败，需 UpdateWrapper.set(字段, null)。

仓库体系（三级）：

  • 本地仓库：默认 ~/.m2/repository，下载过的构件缓存于此，首次拉取慢、之后秒级。
  • 中央仓库：Maven 官方仓库（repo.maven.apache.org），国内直连慢，一般配阿里云镜像。
  • 私服：公司内部构件仓库，承担「下载代理 + 内部构件发布」双重职责，CI 构建必须依赖它。

SNAPSHOT 与 RELEASE：

  • RELEASE（如 1.0.0）：版本固定，本地缓存后不再重复下载；对外发布、下游依赖用它。
  • SNAPSHOT（如 1.0.0-SNAPSHOT）：开发期版本，Maven 每次构建会检查远程仓库是否有更新（默认 24 小时策略，-U 强制刷新）；多团队联调时依赖方必须用它才能拿到最新代码。
  • 发布正式版本前把 -SNAPSHOT 去掉再 deploy。

依赖范围

scope 元素声明依赖的作用范围，决定依赖在编译、测试、运行哪个阶段可见：

依赖范围 说明
compile scope元素的缺省值。编译、测试、运行阶段都会引入
test 测试阶段引入（JUnit、Mockito、Testcontainers 等）
provided 编译、测试阶段引入，运行期由容器（如 Tomcat 的 servlet-api）提供
runtime 测试、运行阶段引入，编译期不需要（如 JDBC 驱动）
system 用于添加本地 jar，不推荐使用（不参与依赖传递，需配 systemPath，换机器就废）
import 与 dependencyManagement 元素配合使用，其功能是将目标 pom.xml 文件中 dependencyManagement 的配置导入合并到当前 pom.xml 的 dependencyManagement 中

选型口诀：编译要用的写 compile，只有测试用写 test，运行环境自带的写 provided，运行期才加载的写 runtime。

依赖传递

有三个模块A、B、C，A依赖B，B依赖C，C是否能传递到A，取决于B依赖C时使用的依赖范围和配置。

传递规则：

B 依赖 C 时的范围 能否传递到 A 说明
compile 可以传递 C 会被 A 引入，且对 A 编译可见
runtime 可以传递 C 会被 A 引入，但仅在 A 运行时可见
test 不可以传递 test 范围只对声明它的模块（B）的测试生效
provided 不可以传递 由运行环境提供，无需向下游传递
system 不可以传递 本地 jar，不参与传递

optional 为 true 的依赖不能传递：

optional 表示该依赖只是当前模块的可选实现（如 SLF4J 的多个绑定、数据库驱动的多种实现），下游模块需要使用时必须自行显式声明，避免传递出无用的依赖。

依赖冲突

当直接依赖和间接依赖引用了同一个依赖的不同版本时，最终生效的版本由 Maven 的依赖调解决定：

  • 最短路径原则

A 到 jackson-databind 有两条依赖路径：A->B->C->jackson-databind（如 2.14.0）和 A->jackson-databind（如 2.15.0）。路径短的胜出，最终 A 依赖 jackson-databind 的 2.15.0 版本。

  • 声明顺序原则

当 A 到 jackson-databind 的依赖路径长度一样（A->B->jackson-databind 和 A->C->jackson-databind）时，最短路径原则不适用。此时先声明的依赖生效：B 先声明则使用 B 传递的版本，C 先声明则使用 C 传递的版本。

冲突排查实操：

  1. mvn dependency:tree 查看完整依赖树，定位同一依赖的多个版本（重点看 - (conflict) 标记和已被剪枝的版本）。
  2. 运行期报 NoSuchMethodError / ClassNotFoundException：通常是依赖树里同时存在新老版本，低版本抢先被加载。用 mvn dependency:tree -Dverbose 找 class 的来源 jar，在最短路径上 exclusions 掉旧版。

参数 含义
-pl moduleA 只构建 moduleA（projects list）
-pl moduleA -am 构建 moduleA 及其依赖的模块（also make）
-pl moduleA -amd 构建 moduleA 及其依赖它的模块（also make dependents）

多模块项目

多模块工程同时利用 聚合 与 继承 两种机制（父 pom 通常两者兼顾）：

  • 聚合（<modules>）：父 pom 知道有哪些子模块，一条命令构建全部；不要求子模块继承父 pom（独立项目也能聚合）。
  • 继承（<parent>）：子模块获得父 pom 的 properties、dependencyManagement、插件配置；不要求父 pom 聚合子模块。
  • 子模块不写 groupId/version 时自动继承父值；写了 relativePath 说明父 pom 在本地路径（多模块目录结构），packaging 为 pom 的模块不能有其他内容被打包。

提速三板斧：

依赖管理最佳实践清单

  1. **版本全部走 <properties>**，一个版本只在一处定义。
  2. Spring Boot 项目先引 BOM（spring-boot-dependencies），自己只覆盖确有需求的版本。
  3. **内部多模块共享版本用父 pom 的 dependencyManagement**，子模块不写 version。
  4. dependency:tree 是排查依赖问题的第一工具，冲突没闹明白前不要动手改 pom。
  5. exclusions 要带注释说明为什么排除，三个月后没人记得。
  6. 对外发布的公共模块：optional 标注可选依赖、配 maven-source-plugin 出源码、上 enforcer 校验。
  7. 依赖数量克制：每个依赖都是攻击面（CVE 面）和维护成本，dependency:analyze 定期清无用依赖。
  8. 升级依赖前看 release notes，优先升 security 相关；用 versions:display-dependency-updates 定期体检。

附录：脚本编写规范

本文脚本中反复出现以下良好实践，编写新运维脚本时可直接套用。

错误处理：set -euo pipefail

  • set -e：任一命令返回非零立即退出（2.4 deploy-java.sh 已使用，可升级为完整版）
  • set -u：引用未定义变量直接报错，拼写错误无处遁形
  • set -o pipefail：管道中前面命令失败时整体仍算失败——典型场景是 grep 无匹配返回非零（见 2.3 log-analyzer.sh 中 grep -c 的处理注释）
  • 注意：开启 set -e 后，需要捕获退出码的场景要用 cmd; ret=$? 先存后判——$? 只保留上一条命令的退出码，直接连用会丢失前面的结果（见 2.2 服务健康检查 中 process_ok=$? 的写法）

日志规范：时间戳 + 级别

统一 [级别] 时间 消息 格式，方便按级别 grep 检索：

  • 彩色输出可参考 2.4 deploy-java.sh 的 log_info/log_warn/log_error（重定向到文件时退化为纯文本）
  • 持续运行的脚本（如 2.6 monitor-resources.sh）用 tee -a 同时输出到屏幕并落盘

参数校验：dry-run 与必填校验

  • **危险操作提供 --dry-run**：只预览将要执行的动作、不真正执行，确认无误后再去掉该选项（见 1.2 / 2.1 批量重命名）
  • 必填参数显式校验：先判断再退出，附用法提示
  • 环境变量必填校验：用参数扩展直接报错，杜绝空值继续运行（见 2.5 MySQL 备份）
  • 可选参数默认值兜底：LOG_FILE="${1:-application.log}"（见 2.3 日志分析、2.7 批量日志处理）
