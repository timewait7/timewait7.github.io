秒杀系统设计：从方法论到落地

Posted on 2026-08-12 In 系统设计 Word count in article: 5.3k Reading time ≈ 19 mins.

秒杀是系统设计面试里「一题考全」的题目：限流、缓存、消息队列、分布式锁、分库分表、降级兜底，六个知识点在一道题里全部串联。 它考的不是「背方案」，而是「能不能把『瞬间高并发读 + 有限资源并发写』拆成可讨论的设计决策」——这正是 《系统设计方法论》 的解题框架在真实题目上的完整落地。本文按「需求拆解 → 整体架构 → 逐层设计 → 全链路走查 → 面试应答」组织，读完你能把一个秒杀方案从「听过」变成「能讲」。

联动：本文复用 Redis 深度解析（原子操作/Lua/缓存）、MySQL 高可用与分库分表实战（订单表拆分）、RocketMQ 原理与实践（削峰）、设计模式（策略/责任链/外观）的知识点，把它们串成一张系统级方案。

1. 题目拆解：秒杀考的不是高并发，是「并发写」

1.1 需求澄清：面试从「问清数字」开始

面试官抛出「设计一个秒杀系统」后，第一件事不是画架构，是澄清需求——这是方法论篇第 1 节的「问题拆解」，也是区分「背方案」和「会设计」的第一步：

澄清项 示例答案 为什么必须问
规模 100 万用户抢 1 万件商品，峰值 10 万 QPS 决定要不要上 MQ、要不要分库
商品数量 1 个 SKU 还是多个 决定热点是否集中
一致性要求 库存不能超卖，订单不能重复 决定扣减方案
时间窗口 10 分钟还是 1 分钟 决定削峰策略
读多还是写多 查商品 100 万次，下单 10 万次 读可缓存，写是瓶颈

一句话结论：秒杀 = 海量读（可缓存解决）+ 集中写（必须原子化）+ 瞬时高峰（必须削峰）。 读是「工程问题」（缓存扛住即可），写是「正确性问题」（超卖就是 bug），峰是「容量问题」（QPS 超过阈值怎么办）。

1.2 瓶颈分析：先找唯一的并发写热点

秒杀系统的数据流只有两类：

flowchart TD
    U["100 万用户"] -->|"读商品信息<br/>读操作，可缓存"| R["Redis 缓存<br/>扛住 99% 读"]
    U -->|"下单扣库存<br/>写操作，必须准确"| W["库存扣减<br/>唯一热点"]
    W -->|"扣减必须原子"| R2["Redis + Lua"]
    R2 -->|"异步落库"| MQ["消息队列<br/>削峰"]
    MQ --> DB["MySQL<br/>订单表"]

因果链：读请求打到数据库会被缓存拦截（Redis 缓存商品信息，读 QPS 与 DB 无关）；真正的热点只剩一个——库存扣减。设计重点全部集中在这里：扣减要原子（防超卖）、要快（Redis 而不是 DB）、要异步（落库不阻塞用户）。「先找热点，再设计」是系统设计的第一原则——不找热点就画架构图，方案必然泛泛。

2. 整体架构：分层职责图

2.1 五层架构总览

flowchart LR
    A["浏览器/App<br/>倒计时+按钮置灰"] --> B["CDN + 静态页<br/>商品详情静态化"]
    B --> C["接入层网关<br/>令牌桶限流+黑名单"]
    C --> D["秒杀应用<br/>① 查缓存（商品信息）<br/>② Lua 原子扣库存<br/>③ 发下单 MQ"]
    D --> E["Redis<br/>库存+限流+防重"]
    D --> F["RocketMQ<br/>下单队列"]
    F --> G["订单消费者<br/>落库+对账"]
    G --> H["MySQL<br/>订单表（分库分表）"]

每一层只做一件事，任何一层被打爆都不影响其他层：网关限流保证应用不被打爆，Redis 扣减保证库存准确，MQ 排队保证 DB 不被瞬时打爆。这就是方法论篇「高可用设计：用冗余换可靠性」在秒杀场景的实例化——每层都有兜底，任何单点故障只是「少卖」而不是「卖错」。

2.2 与普通下单的区别：读路径与写路径分离

环节 普通下单 秒杀下单
商品信息读取 每次查 DB（或缓存） 缓存 + 静态页，读路径 99% 不到应用层
库存检查 查 DB 行 Redis 原子预扣
下单 同步写 DB MQ 异步写，用户先看到「排队中」
失败处理 直接返回失败 排队后异步通知成功/失败

因果链：普通下单是「一次事务」——检查库存、扣减、下单在一个事务里保证一致性；秒杀把这个事务拆成了「先占坑（Redis 预扣）→ 后处理（异步落库）」两段，用「最终一致性」换「扛住峰值」。面试必被追问：「预扣了库存但后面落库失败怎么办？」——答案是对账：定时任务比对 Redis 预扣数与 DB 订单数，差额回补库存。 这是「两段式设计」的代价，必须主动说出来。

3. 限流：把流量挡在应用之外

3.1 四种限流算法对比

算法 原理 优点 缺点 适用
固定窗口 每秒计数，超限拒绝 实现简单 窗口边界突发（59 秒和 01 秒各 100 次可绕过） 粗略限流
滑动窗口 记录每个请求时间戳，统计窗口内请求数 消除边界问题 内存开销随 QPS 增 网关
漏桶 请求进桶，固定速率流出 流量绝对平滑 突发流量被削平，延迟增大 保护下游
令牌桶 令牌按速率生成，请求取令牌 允许一定突发（桶容量） 桶容量需调 秒杀（允许瞬间放量）

秒杀选令牌桶：秒杀的特点是「开闸瞬间所有用户同时涌来」——固定窗口和漏桶会直接杀掉大部分请求，令牌桶允许桶内突发（比如桶容量 1 万），让「前 1 万个请求快速通过，后续平滑」——既保护系统，又保证有能力的用户进得来。

3.2 网关限流 + 应用限流双层

flowchart LR
    U["100 万请求"] --> G["网关层（Nginx/网关）<br/>令牌桶：总量 10 万 QPS"]
    G -->|"通过 ~10 万"| A["应用层<br/>Redis 分布式限流：每秒 5 万"]
    G -->|"拒绝 90 万<br/>返回"排队失败""| R["快速失败"]
    A -->|"拒绝超额"| R2["提示"手慢了""]
    A -->|"通过"| S["进入扣库存"]
  • 网关限流：无状态、靠内存令牌桶，挡掉 90% 流量——这是性价比最高的一道闸，Nginx 单机可扛百万级连接；
  • 应用限流：多实例部署时内存令牌桶各算各的，必须用 Redis 分布式限流（Lua 脚本保证原子）——单机限流 × N 实例 = 总限流 × N，这是面试必问的「限流在分布式下怎么保证总量」。

3.3 动手验证：手写令牌桶

观察点：容量 10、速率 5 的桶——瞬间来 20 个请求，前 10 个通过，之后按每秒 5 个放行。判定标准：跑出「突发 10 + 匀速 5/s」的通过曲线，即理解令牌桶与漏桶的本质区别（允许突发 vs 强制平滑）。

3.4 深挖：限流与降级的联动

限流是「预先划定的容量」，降级是「故障时的保底」——两者必须联动：当限流指标（拒绝率）超过阈值，说明系统真被打到了，触发降级——关闭非核心功能（购物车、推荐位），把资源全部让给下单链路。因果链：秒杀开场瞬间，任何非核心请求都是对核心链路的伤害，降级是「主动选择服务哪些流量」——方法论篇 §5「熔断与降级：故障下的体验保障」在秒杀里是必选项而不是可选项。

4. 防超卖：库存扣减的原子性

4.1 超卖的本质：检查与扣减不是原子操作

超卖的根因永远是同一个：「先查库存 >0，再扣减」这两步之间，另一个请求插队了。

sequenceDiagram
    participant A as 请求 A
    participant B as 请求 B
    participant S as 库存
    A->>S: 查询库存 = 1
    B->>S: 查询库存 = 1
    A->>S: 扣减 → 0
    B->>S: 扣减 → -1  ← 超卖！

三种方案对比：

方案 做法 问题
DB 悲观锁 SELECT ... FOR UPDATE 锁行导致 QPS 上不去（所有扣减串行化）
DB 乐观锁 UPDATE stock SET n=n-1 WHERE n>0 每次更新一次 DB 往返，10 万 QPS 打不穿
Redis + Lua Lua 脚本内原子检查+扣减 单线程执行天然原子，10 万 QPS 无压力

Redis 单线程执行命令是原子性的核心——Lua 脚本在 Redis 里整段执行，中间不可能被其他命令插队，等于把「检查 + 扣减」变成了一个不可分割的操作。这就是秒杀选 Redis 扣库存的根本原因：不是 Redis 快，是 Redis 单线程给了我们免费的原子性。

4.3 防重：同一用户不能下两单

扣库存之外，还要防「一个用户抢到两件」：

  • Redis SETNX 用户级防重：SETNX order:uid:{userId} 1，抢到锁的用户才能进入下单流程，流程结束 DEL；
  • DB 唯一索引兜底：user_id + goods_id 建唯一索引——即使 Redis 层被绕过，DB 层也能挡掉重复单。两层防重：Redis 挡 99.9%，唯一索引兜 0.1%，这就是「多层防御」的典型用法。

4.4 动手验证：并发扣库存压测

观察点：任何一次并发下出现负数，说明扣减代码不是原子的。判定标准：库存恰好归零 + 成功次数恰好等于初始库存——这就是「不超卖」的可验证定义。

5. 削峰：MQ 排队，把瞬时流量拉平

5.1 为什么要 MQ：DB 的写入能力是硬上限

环节 峰值吞吐 说明
Redis 扣库存 10 万 QPS 内存操作，单线程也扛得住
MQ 写入 数万 TPS 顺序写磁盘，远高于 DB 随机写
MySQL 订单插入 数千 TPS 单库 B+ 树随机写是硬瓶颈

因果链：Redis 扣库存成功后，如果把「生成订单」同步做（写 MySQL），DB 会被瞬时 10 万 QPS 打爆——所以扣完库存只发一条 MQ 消息就返回「排队中」，订单消费者按自己能力（数千 TPS）慢慢落库。用户感知从「下单成功」变成「排队中」，这是秒杀体验设计的核心取舍：把瞬时负载平摊到秒级甚至分钟级。

5.2 消息丢失与重复：削峰方案的必答延伸

面试官必追：「MQ 消息丢了怎么办？重复消费怎么办？」——削峰方案的价值建立在 MQ 可靠性的三条承诺上：

风险 方案 机制出处
生产端丢失 同步发送 + 重试 RocketMQ 同步发送
MQ 端丢失 集群 + 主从同步 + 刷盘策略 RocketMQ 高可用篇
消费端重复 幂等（唯一索引 + 状态机） §4.3 的 DB 唯一索引兜底

因果链：防超卖和防重复是同一件事的两面——扣库存用 Redis 原子保证「卖不多」，落库用唯一索引保证「不重复」。面试答到这里，方案就从「背出来的」变成「能闭环的」：每个环节的失败都有对策，这正是方法论「可讨论的设计决策」的要求。

5.3 排队 vs 拒绝：什么时候削峰，什么时候直接拒

策略 做法 代价 适用
削峰（MQ 排队） 超量请求进队列，异步处理 用户体验变差（等待） 秒杀（1 万件商品值得排队）
直接拒绝 超量请求返回失败 简单直接 限量活动（100 件商品，排队没意义）

判断标准：排队队列的长度要可控——1 万件商品配 10 万请求，排队有意义；100 件商品配 10 万请求，排队只会让 99.99% 的用户等一个注定失败的结果，直接拒绝更合理。设计决策没有标准答案，只有「代价与收益匹配」。

6. 缓存与热点：让 99% 的读请求到不了应用

6.1 缓存层级：静态页 → CDN → Redis

flowchart LR
    U["用户"] --> S["静态页（商品详情纯静态化）<br/>请求不到后端"]
    U --> C["CDN（边缘节点）"]
    C --> R["Redis（商品信息缓存）"]
    R --> A["应用"]
  • 商品详情页秒杀前完全静态化，部署到 CDN——这部分流量和你的后端毫无关系；
  • 秒杀页面的动态数据（库存数字、倒计时）走 Redis；
  • 应用层查询全部命中缓存，DB 只承担「订单落库」。

6.2 热点 key：缓存击穿的防护

秒杀就 1 个 SKU，**所有用户查同一个 key sku:1001**——这就是热点 key 的极端形态：

风险 场景 方案
击穿 缓存过期瞬间，请求全打 DB 互斥锁重建缓存（只让一个线程回源）
打爆 单 key 承载全部读流量 热点 key 复制（sku:1001:0~`sku:1001:9` 十个副本，请求分散）
雪崩 大量 key 同时过期 过期时间加随机值

因果链：秒杀是「单一热点」的最坏情况——所有读流量打同一个 key，这个 key 就是整个系统的单点。热点 key 复制（读副本）把单 key 变 10 个 key，Redis 集群里分散到不同分片，每个分片只扛 1/10 流量——Redis 深度解析里 HotKey 治理在秒杀场景是「开闸瞬间」的生存问题，不是优化问题。

6.3 库存数字的展示与真实扣减分离

展示层库存（Redis 直接读，可 1 秒更新一次）≠ 扣减库存（Lua 原子操作）——用户看到「还有 300 件」只是展示数字，实际扣减永远走 Lua。两个 key 分离，展示挂了不影响扣减，这是「读路径与写路径分离」的第二个实例（第一个是 §2.2）。

7. 全链路走查：一个用户从点击到收货

7.1 时序图：成功路径

sequenceDiagram
    participant U as 用户
    participant G as 网关
    participant A as 秒杀应用
    participant R as Redis
    participant M as RocketMQ
    participant D as 订单消费者
    participant DB as MySQL
    U->>G: 1. 点「立即抢购」
    G->>G: 2. 令牌桶限流（总量）
    G->>A: 3. 通过（或返回「手慢了」）
    A->>R: 4. SETNX 用户防重
    R-->>A: 5. 未抢过 → 放行
    A->>R: 6. Lua 原子扣库存
    R-->>A: 7. 成功
    A->>M: 8. 发下单消息
    A-->>U: 9. 返回「排队中」
    M->>D: 10. 消费订单消息
    D->>DB: 11. 插入订单（唯一索引兜底）
    D->>DB: 12. 成功后回写状态

每一步失败的兜底：3 失败 → 用户看到「手慢了」（快速失败，不占资源）；5 失败 → 「已抢过」；7 失败 → 「已售罄」；11 失败（重复订单被唯一索引拦）→ 静默跳过并回补 Redis 库存。

7.2 对账：预扣与落库的差额回收

这是「先占坑后处理」方案的安全网——§2.2 的承诺在这里兑现：最终一致性不是靠运气，是靠对账任务兜底。

8. 面试应答：从方法论到方案的完整话术

8.1 五段式答题结构（对应用方法论篇框架）

段 内容 方法论对应
1. 澄清 问规模、SKU 数、一致性要求（§1.1） 问题拆解
2. 找热点 读可缓存，扣减是唯一并发写热点（§1.2） 全链路找瓶颈
3. 方案 限流（令牌桶）→ 缓存（静态页/CDN）→ 防超卖（Lua）→ 削峰（MQ）→ 落库（唯一索引） 高性能设计
4. 兜底 降级（关非核心）、对账（差额回收）、熔断（Redis 挂了降级为纯 DB 卖） 高可用设计
5. 权衡 同步 vs 异步的体验代价、排队 vs 拒绝 每个选型的代价

8.2 必被追问的五个深挖题

追问 答案要点
Redis 挂了怎么办？ 降级：Redis 预扣不可用时直接走 DB 乐观锁扣减（UPDATE WHERE n>0），QPS 掉到千级但正确性保住——降级预案必须写在方案里
库存和订单不一致？ 对账任务：Redis 预扣数 vs DB 订单数，差额回补 + 告警（§7.2）
怎么防止重复下单？ 三层：Redis SETNX 防重 → DB 唯一索引 → 消费者幂等
MQ 消息丢了？ 同步发送 + 重试 + 集群，落库失败对账兜底（§5.2）
为什么不用数据库扣？ 锁竞争是硬上限：悲观锁串行化，乐观锁每单一次 DB 往返——Redis 单线程原子性是免费的
秒杀前预加载库存到 Redis？ 活动开始前 1 小时把库存 SET 进 Redis，活动结束清理——Redis 数据与 DB 库存的一致性靠活动编排保证

8.3 和普通购物车系统的区别一句话版

「购物车系统是读多写少、一致性要求一般；秒杀是读多写少但写极度集中且要求严格一致——所以缓存要扛读、Lua 要保写原子、MQ 要削峰、对账要兜底，每一层都是为『1 个 SKU 的库存正确性』服务。」

内存管理：虚拟内存与分页

Posted on 2026-08-12 In 操作系统 Word count in article: 3.9k Reading time ≈ 14 mins.

虚拟内存（virtual memory）是操作系统给每个进程提供的「独立、连续、看似无限」的内存假象：进程以为自己独占整个地址空间，实际数据散落在物理内存各页上，由内核统一映射。它是进程隔离的地基，也是 JVM 内存问题（堆外泄漏、容器被杀、OOM）的总根源。本文讲三件事：地址空间怎么组织、虚拟地址怎么翻译成物理地址、内存不够了会发生什么——并对照 Redis RDB 快照、大页、容器内存限制这些真实技术，看它们怎么建立在本节的机制上。

系列地图（操作系统）：① 进程与线程（执行单元与调度）→ ② 内存管理（本文：地址空间与物理内存） → ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（等待数据的方式）→ ⑤ Linux 资源排查实战（工具收拢）。本文的页缓存是 ③ 的读写地基（页表项指向它），本文的缺页与换页是 ④ 之前「一切等待」的物理背景。

1. 虚拟内存：给每个进程一座孤岛

1.1 为什么需要虚拟内存

没有虚拟内存的时代（实模式），程序直接访问物理地址：两个程序必须约好各占哪段，一个野指针就能改掉别的程序的数据。虚拟内存一次性解决三件事：

问题 虚拟内存的解法
隔离 每个进程有自己的地址空间，A 进程地址 0x1000 和 B 进程地址 0x1000 是两页不同的物理内存
连续性 物理内存碎片化没关系，虚拟地址连续、映射到哪都行
按需加载 程序 100MB，先只映射用到的几页——未访问的代码和数据可以一直留在磁盘上

地址空间是「地址的集合」，不是「内存的集合」——进程里看到的一大片地址，大部分没有对应的物理页，一访问就缺页（第 2 节讲）。

1.2 地址空间布局

x86-64 下用户空间是低位的 128TB（内核占高 128TB）。从低到高：

flowchart TD
    subgraph Low["Low address (0x0)"]
        TEXT["Text (code) segment"]
        DATA["Data / BSS<br/>initialized & uninitialized globals"]
        HEAP["Heap<br/>grows upward (brk / mmap)"]
    end
    subgraph High["High address (0x7fff...)"]

要点：堆向上长、栈向下长，中间是巨大的未映射空洞——new 的对象在堆，局部变量和调用帧在栈，两者相撞叫栈溢出或堆溢出。地址空间底部有随机化（ASLR），每次启动程序布局都变，防攻击者猜地址。

1.3 动手验证：看 JVM 的真实地址空间

看一个 -Xmx2g 的 Java 进程，pmap 输出的规律：

映射 是什么
[heap] 或大块 [anon] JVM 堆（Java 8+ 用匿名 mmap 分配，不叫 heap）
[stack] 主线程栈
[anon] 小块堆叠 每个线程的栈（-Xss，默认 1MB 虚拟）、Metaspace、JIT code cache

对照 ps 的 VSZ 和 RSS：-Xmx2g 的进程 VSZ 常有 4-5GB（预留的地址空间），RSS 才是真占用的物理内存——内存监控看 RSS，别被 VSZ 吓到；反之容器内存限制看的是 RSS，-Xmx 设太大不代表 RSS 一定大，但 RSS 会超过 -Xmx（堆外还有东西，第 4 节展开）。

2. 分页与地址转换

2.1 页表：地址翻译的字典

物理内存按 4KB 一页切成页帧；每个进程维护一张页表，记录「虚拟页号 → 物理页帧号」。进程切换时换页表——这就是第 1 篇说的「进程切换比线程切换贵」的根源。

问题：进程地址空间 128TB，一张扁平页表要 128TB/4KB = 340 亿条记录，装不下。解法是多级页表（x86-64 四级）：只有用到的地址区间才在低层分配表项，未映射区间不占内存。

层级 名称 每项覆盖
L4 PML4（页目录指针的指针） 512GB
L3 PDPT（页目录指针） 1GB
L2 PD（页目录） 2MB
L1 PT（页表） 4KB

一个 4KB 页的转换要查 4 级表（4 次内存访问），所以必须有缓存——TLB（Translation Lookaside Buffer），CPU 内置的页表缓存。命中就免掉 4 次访问，未命中才走完整路径。

深挖：大页（HugePages）就是从页表结构里长出来的优化。页越大，页表条目越少、TLB 命中率越高：2MB 大页把 4KB 页的条目数缩 512 倍。ES、MySQL 这类内存大户在生产上常开内核 vm.nr_hugepages + JVM 的 -XX:+UseLargePages——代价是内存按大页粒度预留、分配更粗放，配置错反而浪费。理解了页表与 TLB，这个参数的来龙去脉就清楚了。

2.2 转换流程与缺页

flowchart TD
    CPU["CPU issues virtual address"] --> TLB{"TLB hit?"}
    TLB -- Yes --> PHYS["Physical address, done"]
    TLB -- No --> WALK["Walk 4-level page table (4 memory accesses)"]
    WALK --> PRESENT{"PTE present?"}
    PRESENT -- Yes --> CACHE["Fill TLB, done"]
    PRESENT -- No --> FAULT["Page fault (trap to kernel)"]
    FAULT --> MINOR{"Page already in RAM?<br/>(page cache / lazy alloc / COW)"}
    MINOR -- Yes --> FIX["Build PTE, return to user<br/>minor fault (~1µs)"]
    MINOR -- No --> IO["Read page from disk (swap / file)<br/>major fault (ms level)"]
    IO --> FIX

缺页分两种，代价差三个数量级：

类型 触发 代价 常见来源
minor fault 页已在物理内存，只是页表项没建 微秒级 JVM 启动、首次 new 对象、fork 写时拷贝
major fault 页要从磁盘读 毫秒级 冷数据首次访问、swap 换回、内存映射文件

JVM 启动慢的本质是海量 minor fault：-Xms 设小、启动后再扩堆，每次扩容都要建页表项；生产建议 -Xms = -Xmx，一次到位，既省 minor fault 也避免堆抖动（老生常谈，根因在这里）。

深挖：写时拷贝（COW）与 Redis RDB 快照。fork() 不复制父进程的内存，而是把页表项标为只读、父子共享；子进程一写才复制那一页（触发 minor fault）。Redis 的 RDB 持久化就是这么拍的：fork 出子进程，子进程把共享内存顺序写进文件，主进程照常服务——写时复制保证子进程看到的是「fork 那一刻」的一致数据。所以 RDB 既不阻塞服务、又能拍到一致快照，靠的全是 COW。

代价与坑（大实例 Redis 的必修课）：

现象 根因 处理
fork 瞬间卡顿几十到几百 ms fork 要复制整个页表（条目数 = 内存/4KB） 观察 INFO persistence 的 last_fork_usec
快照期间内存翻倍风险 写多时 COW 复制页多 内存至少留出数据集 2 倍的余量
频繁 RDB 拖垮服务 每次 fork 的页表复制 + COW 高峰 大实例降 RDB 频率，换主从全量同步

Java 侧同样受 COW 影响：-Xms = -Xmx 的另一层收益是减少启动后的堆扩缩——每次扩堆重建页表、GC 频繁触碰页，都是 minor fault 的代价。

2.3 页面置换：内存不够了踢谁出去

物理页不够时，要把一些页换出（写回磁盘或丢弃）。置换算法：

算法 思路 问题
FIFO 先进来先踢 可能踢掉正热的页（Belady 异常）
LRU 最久没用的先踢 理想但不现实（每页维护访问时间成本太高）
时钟/第二次机会 FIFO + 访问位，被访问过的页放行一轮 工程上的近似 LRU

Linux 用双链表近似 LRU（active/inactive 两条 LRU 链表，页在链表间升降），配合内存水位线（/proc/sys/vm/watermark 相关）决定何时开始回收。Java 视角不用记细节，记住结论：页面置换对应用不可见，但「频繁换页」是性能灾难（见 2.4 的观测方法）。

3. 内存分配与回收

3.1 malloc 的两个来源：brk 与 mmap

进程向内核要内存只有两条路：

途径 机制 适用
brk 移动堆顶指针，扩展/收缩堆 小分配（malloc 默认），快
mmap（匿名） 直接映射一段新地址空间 大分配（>128KB），用完立刻可释放

malloc 的策略：小块走 brk 堆（复用、碎片由 malloc 自己管），大块走 mmap（还给内核干脆）。JVM 的堆就是一次大匿名 mmap 拿下来的，-Xms/-Xmx 控制这段区域。

3.2 内核侧：伙伴系统与 slab

内核把物理页切块管理：伙伴系统按 2 的幂次维护空闲页（要 3 页给 4 页、要 5 页给 8 页），slab 为频繁创建的小对象（task_struct、inode）建专属缓存。这两层对应用透明，但解释了「内存碎片」和「内核内存占用」的来源——容器里 free 的 used 包含了内核 slab，排查内存高时可 cat /proc/meminfo | grep Slab。

3.3 回收与 swap

物理内存吃紧时按顺序回收：页缓存（干净页直接丢，脏页先回写）→ 匿名页换出到 swap。注意 swap 是「匿名页（堆、栈）的磁盘后备」，页缓存不需要 swap——free -h 里 Swap 列全 0 只说明没换出过匿名页。

容器时代（K8s）的共识是节点禁用 swap：换页延迟毫秒级，对服务不可接受，K8s 也默认要求 swapoff。Java 应用在 swap 环境下 GC 停顿会被放大（GC 要访问的页被换出去了）。

3.4 动手验证：free 的正确读法

free -h 输出解读：used 里含 Slab 等内核占用；buff/cache 是页缓存（可随时丢弃，不是泄漏，别因为 cache 高就慌）；看真实可用内存用 available 列（缓存可回收部分算进去）。线上「内存不足」告警，先看 available 而不是 free。

4. OOM：从 JVM 到内核

4.1 JVM 内存全景：堆只是冰山一角

-Xmx 只是 JVM 堆上限，进程的 RSS 由五块组成：

组成 控制参数 典型值
堆 -Xmx 按业务
Metaspace -XX:MaxMetaspaceSize 默认无上限，类太多会涨到几百 MB
线程栈 -Xss（默认 1MB 虚拟） 1000 线程 ≈ 1GB 虚拟内存
直接内存 -XX:MaxDirectMemorySize（默认 = 堆大小） Netty/BufferPool 场景
JIT code cache + GC 结构 -XX:ReservedCodeCacheSize 等 200MB 上下

所以 -Xmx1g 的进程 RSS 到 1.5g 是正常的；容器里只设 -Xmx 不管堆外，就是「被 OOM Killer 杀」的经典剧本——正确姿势是 -XX:MaxRAMPercentage=75 之类按容器内存百分比给堆。

4.2 判定链路：谁杀了我的进程

flowchart TD
    ALLOC["App requests memory (malloc / mmap)"] --> OVER{"overcommit allowed?"}
    OVER -- No --> FAIL["malloc returns NULL<br/>(rare, overcommit_memory=2)"]
    OVER -- Yes --> CG{"cgroup memory limit hit?"}

三层机制：overcommit（内核敢不敢超量承诺虚拟内存，Linux 默认启发式）→ cgroup 限制（容器内存上限，K8s limits.memory）→ OOM Killer（真不够时按 oom_score 选杀，占内存越大、存活越短、oom_score_adj 越高的先死——容器里的进程 oom_score_adj 会被调高，这就是「容器里 JVM 先被杀」的原因之一）。

5. 总结与避坑清单

5.1 面试速答表

面试题 一句话答案
虚拟内存解决了什么问题？ 隔离（进程地址独立）、连续（碎片无所谓）、按需加载（没访问的页不占物理内存）
为什么用多级页表？ 扁平页表 128TB 空间要 340 亿条记录；多级只给用到的区间建表项
TLB 是什么？ 页表项的 CPU 缓存，命中免掉 4 次内存访问
minor/major fault 区别？ minor 页已在内存只差建表项（微秒级）；major 要从磁盘读（毫秒级）
JVM 为什么内存监控要盯 RSS 不是 VSZ？ VSZ 是地址空间承诺，RSS 才是物理驻留；堆外（Metaspace/直接内存/线程栈）都会撑大 RSS
容器里 JVM 为什么老被 OOM 杀？ 只设 -Xmx 不管堆外 + 容器进程 oom_score_adj 高；用 -XX:MaxRAMPercentage 按容器内存给堆

四个收获：地址空间是承诺、RSS 是现实；缺页是「懒」的代价（minor 微秒、major 毫秒）；内存回收的顺序是页缓存 → swap → 杀进程；JVM 的 OOM 从来不只是 -Xmx 的事。

实操建议：

  1. 容器里 JVM 一律 -XX:MaxRAMPercentage=75 + -Xms=-Xmx，先保住别被杀。
  2. 进程被杀先查 dmesg，别猜——是 OOM Killer 还是健康检查，处理方向完全不同。
  3. 用 jcmd <pid> VM.native_memory summary（需 -XX:NativeMemoryTracking=summary）定期对账堆外内存，直接内存泄漏能在 RSS 崩之前发现。

进程与线程：从模型到调度

Posted on 2026-08-12 In 操作系统 Word count in article: 4.9k Reading time ≈ 18 mins.

进程（process）是正在运行的程序实例：程序是磁盘上的静态代码，进程是它被加载进内存后的一套完整运行环境。同一个程序可以同时跑出多个进程——开两个 IDE 窗口就是两个进程。本文回答三个问题：进程/线程/协程到底是什么、CPU 怎么把时间分给它们、切换到底贵在哪——并对照你天天用的技术（线程池大小、虚拟线程、容器 PID 1、Go 的 goroutine），看这些设计怎么从本文的机制里长出来。

系列地图（操作系统）：① 进程与线程（本文：执行单元与调度） → ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（等待数据的方式）→ ⑤ Linux 资源排查实战（工具收拢）。本文的切换成本是 ④ 里「BIO 为什么不行」的根因，本文的栈内存是 ② 里「线程多了为什么 OOM」的依据。

1. 进程模型：正在运行的程序

1.1 程序的四个组成部分

一个进程由四部分构成：

组成 内容 说明
程序代码 指令序列 只读段，可共享（同一程序多进程共享代码段）

内核用进程控制块（PCB，Process Control Block）统一管理进程的一切，Linux 里叫 task_struct：PID、状态、寄存器快照、内存映射、打开的文件表、CPU 使用统计……可以把它理解为进程在操作系统里的「档案袋」。

1.2 生命周期：五个状态

进程一生在几个状态间迁移，ps 输出的 S 列就是当前状态：

僵尸进程是「已退出但还没被父进程 wait() 回收」的进程：不占 CPU 不占内存（PCB 还占着），但 PID 不释放，多了会耗尽 PID 上限。父进程用 wait()/waitpid() 收尸，Java 里对应的就是 Process.waitFor()。父进程先死了怎么办？孤儿进程由 1 号进程（init/systemd）自动收养回收——所以孤儿不可怕，僵尸要防。

Java 里反而不容易造出僵尸——JDK 的 Process 内部有 reaper 线程自动 waitpid 回收子进程。真正常见的坑是「起了子进程但没人读它的输出流」：子进程写满管道缓冲区（64KB）后永久阻塞，表现为整个流程卡死（1.3 有实验）。僵尸进程更多出现在 C/Shell 场景（1.3 给造法）。

2.1 三种线程模型

模型 调度在哪 代表 特点
1:1 内核线程 内核 Linux pthread、Java 平台线程 内核原生支持，但每个线程都占内核资源
M:N 用户线程 用户态库 Java 早期绿色线程（已废弃） 灵活但调度映射复杂，难调优
协程/虚拟线程 用户态 + JVM Go goroutine、Java 虚拟线程 栈上调度，阻塞不占内核线程，百万级并发

Java 平台线程是 1:1 内核线程——每 new 一个 Thread 就创建一个内核线程，所以线程数量上不去；Java 虚拟线程（JDK 21 正式版）是 JVM 用户态调度的协程：线程数可以到几十万，阻塞 I/O 时让出底层载体线程（carrier thread），这就是「百万并发」的来源。

对照 Go 的 goroutine（面试常被连起来问）：Go 的 GMP 模型和虚拟线程同构——G（goroutine）= 虚拟线程，M（machine）= 载体线程，P（processor）= 调度器配额。G 在 channel/syscall 上阻塞时让出 M，M 挂上别的 G 继续跑；Go 不区分「平台线程/虚拟线程」，所有 goroutine 默认都在这个模型里。区别在阻塞边界：Java 虚拟线程遇到 synchronized 会 pin 住载体线程（JDK 21 已基本修复），Go 没有这个历史包袱——所以「Go 天然高并发」的底层原因，就是它从语言诞生起就建在协程模型上。

2.2 为什么线程比进程轻

创建进程要分配/复制地址空间（fork 走写时拷贝），创建线程只是多一个栈和一份调度上下文；切换进程要换页表（TLB 全部失效重载），切换线程共享同一地址空间，只换栈指针和寄存器。一句话：线程省掉了「换地址空间」这个最贵的步骤。

3. 调度：CPU 时间怎么分

调度器（scheduler）负责从就绪任务里选一个上 CPU。单核机器上「同时运行」其实是时间片轮流，调度器决定谁先、谁多、谁被饿死。

3.1 调度算法演进

算法 思路 优点 缺点
FCFS 先来先服务 按到达顺序 简单、公平 长任务堵住短任务（护航效应）
SJF 最短作业优先 先跑最短的 平均等待最小 需预知运行时间，长任务饿死
RR 时间片轮转 固定时间片轮换 响应快 时间片大小难定：太大退化成 FCFS，太小切换开销爆炸

3.2 Linux CFS：把公平量化成 vruntime

Linux 默认调度器 CFS（Completely Fair Scheduler）把「公平」量化成 vruntime（虚拟运行时间）：每个进程按权重累积 vruntime，谁 vruntime 最小谁上 CPU。就绪队列用红黑树按 vruntime 排序，取最左节点 O(log n)。权重由 nice 值决定：nice 越大权重越小、vruntime 涨得越快——nice 0 的进程比 nice 19 的「值钱」得多。

flowchart TD
    A["CPU tick / new task arrives"] --> B["Compute vruntime for each runnable task"]
    B --> C["Pick task with min vruntime<br/>(leftmost in red-black tree)"]
    C --> D["Run for time slice"]
    D --> E{"Preempted or<br/>slice expired?"}
    E -- No --> D
    E -- Yes --> A

一个反直觉但重要的点：CFS 是「按比例分」而不是「轮流分」——睡眠（I/O 等待）期间 vruntime 不涨，所以 IO 密集进程醒来后天然排前面，响应快；CPU 密集进程也不会被饿死，只是分到的比例低。

3.3 上下文切换：切换到底贵在哪

上下文切换（context switch）是把 CPU 从当前任务切到另一个任务的完整过程，发生在时间片耗尽、任务主动让出（I/O、锁等待）或中断时。

切换类型 成本量级 拆解
进程切换 1-10 µs 保存/恢复寄存器 + 切换页表（TLB 全失效）+ 内核态进出
线程切换 0.5-2 µs 同进程：只换寄存器快照和栈，不碰页表
系统调用 0.1-1 µs 只进出内核态，不换任务

所以线程数量远超 CPU 核数时，大量时间花在切换而不是干活上——这就是「线程池核心线程数 ≈ CPU 核数（CPU 密集）或 ×(1+IO 等待/计算比)（IO 密集）」的底层依据。

真实场景：压测 TPS 上不去，vmstat 1 里 cs（context switch）列每秒几十万——线程池 300 线程跑 8 核机器，大半时间在切线程。缩到 40 线程后 TPS 反而翻倍。排查命令：pidstat -w 1 看自愿/非自愿切换，/proc/<pid>/status 里的 voluntary_ctxt_switches 字段。

4. 用户态与内核态：系统调用的代价

用户态（user mode）与内核态（kernel mode）是 CPU 的两种特权级别：内核态能执行特权指令（访问硬件、改页表），用户态不行。用户程序想动硬件，必须通过系统调用（syscall）请内核代劳。分态的目的是安全和隔离：你写的代码不能直接改别人的内存、不能直接写硬盘。

4.1 系统调用链路

Java 里一次文件读取，底层链路是这样的：

sequenceDiagram
    participant Java as Java (user mode)
    participant Libc as glibc (user mode)
    participant Kernel as Kernel (kernel mode)
    participant Disk as Disk / Page Cache
    Java->>Libc: FileInputStream.read()
    Libc->>Kernel: syscall read(fd, buf, len)
    Kernel->>Disk: page cache lookup / device I/O
    Disk-->>Kernel: data
    Kernel-->>Libc: copy to user buffer, return len
    Libc-->>Java: bytes

每发一次 syscall 就有一次用户态↔内核态切换。态切换本身不重（亚微秒级），重的是它打断 CPU 流水线、每次都要校验参数和权限。由此推出两个工程结论：

  • 读 1 字节和读 4KB 都是 1 次 read syscall——缓冲（BufferedInputStream）的意义就在这里：把 N 次小 syscall 合并成一次大的；
  • 高性能框架都在「少 syscall」上做文章：批量读写、mmap、sendfile 零拷贝（一次 syscall 在内核态内完成磁盘→socket 拷贝，详见操作系统系列的 IO 模型篇）。

  2. 用了 Runtime.exec() / ProcessBuilder 一定 waitFor() + 关流，防僵尸进程。
  3. 新项目 IO 密集型并发优先评估虚拟线程（JDK 21+），平台线程留给 CPU 密集和需要可控栈的场景。

设计模式：15 个高频模式的实战内化

Posted on 2026-08-12 In Java Word count in article: 7.6k Reading time ≈ 28 mins.

设计模式面试不考「背定义」，考三件事：一句话说出模式解决什么问题、说出 JDK/框架里的真实落点、说出你项目里怎么用的。 本文按此标准组织：15 个高频模式，每个配「动机 → 结构 → 源码落点 → 动手验证」，最后给出源码落点地图和面试答题框架。读完你能做到：面试官提任意一个高频模式，你 30 秒内答出「是什么、解决什么、哪用到、怎么用」。

联动：本文是 MyBatis 深度解析（动态代理落点）、Spring 深度解析（工厂/模板方法/观察者落点）、Netty 原理与实践（责任链落点）的「模式视角」串联篇。

1. 设计模式全景：面试怎么考

1.1 三个层次：定义、落点、应用

设计模式是在特定上下文中反复出现的问题的解决方案模板——它不是代码规则，是经验的命名。面试考察分三层：

层次 考察方式 区分度
定义层 「单例模式是什么？」 无区分度，背过就会
落点层 「JDK 里哪里用了代理模式？」 区分背书党
应用层 「你项目里哪个地方用了策略模式，为什么？」 区分有经验者

因果链：面试官问设计模式的真实目的是验证「你有没有设计意识」——能不能把变化点隔离出来。凡是回答「我记得 23 种模式的定义」的，都在第一层；能说出落点和自己项目的，才到第三层。 本文的目标是把 15 个高频模式全部推到第三层。

1.3 学习主线：从动机出发，不从结构出发

每个模式背「结构图（UML）+ 角色名」是低效的。正确主线：

动机（解决什么问题）→ 场景（什么信号该用它）→ 落点（JDK/框架哪里在用）→ 动手（自己写一遍）

因果链：设计模式本质是「应对变化」——创建型应对「创建逻辑变化」，结构型应对「职责组合变化」，行为型应对「算法/协作变化」。面试答题说动机不说结构，是区分「懂设计」和「背图」的分水岭——因为结构可以现推，动机不能。

2. 创建型：单例、工厂方法、建造者

2.1 单例：全局唯一 + 延迟创建

动机：某些对象全系统只需要一份（配置中心、连接池、线程池、日志器）——重复创建浪费资源，且状态必须全局共享。单例解决「全局唯一」这个约束本身。

2.2 深挖：DCL 为什么必须 volatile？

new DCLSingleton() 在 JVM 里是三步：分配内存 → 调用构造器 → 把引用赋给变量。指令重排可能让第三步先于第二步——线程 A 拿到半初始化的对象引用（实例非 null 但字段是默认值），线程 B 在第一次检查就返回了这个坏对象。

flowchart LR
    A["线程 A：new 对象<br/>1.分配内存 2.构造 3.赋引用"] --> B["重排：3 先于 2"]
    B --> C["线程 B 看到 instance != null<br/>返回未构造完的对象 → 字段全默认值"]

因果链：volatile 禁止重排（JDK5 起 volatile 语义含 happens-before）→ 三步按序执行 → 线程 B 要么看到 null（继续走锁），要么看到完整对象。这个考点一次考三件事：并发、JVM 内存模型、模式——所以面试官爱问。 生产后果：不加 volatile 的 DCL 在低并发下可能永远不暴露，高并发下偶发字段全为 null/默认值的诡异 bug，极难排查。

生产建议：新代码直接用枚举或静态内部类，DCL 的价值在面试题里大于生产——这本身就是「模式的正确使用」：别用需要你手动保证正确性的写法，当有更简单更安全的等价写法时。

2.3 动手验证：多线程下验证 DCL 与 volatile

观察点：多跑几次，偶发出现 value != 42 即复现了半初始化对象（依赖 JIT 重排概率，也可能跑不出来）。判定标准：跑出问题 → volatile 机制被实证；没跑出 → 理解了「并发 bug 是概率性、压测不 bug 不等于安全」，这正是生产里此类问题的可怕之处。

2.4 工厂方法：把创建逻辑从使用方剥离

动机：当「创建哪个对象」需要运行时决定（按配置、按类型、按环境），把 new 散落在业务代码里会导致创建逻辑到处改。工厂把「选择实现类」收敛到一个地方。

源码落点：Spring 的 BeanFactory 就是工厂模式的放大版——getBean() 不看构造参数，按名字/类型返回，创建细节（单例缓存、循环依赖、AOP 代理）全部藏在内核。你天天在用工厂，只是没意识到：ApplicationContext.getBean()、ExecutorService.newFixedThreadPool()（也是工厂）、Integer.valueOf()（缓存工厂）。

因果链：工厂的核心收益是「变化点隔离」——新增一种 Logger 实现，业务代码零改动，只改工厂。这是所有设计模式共有的底层逻辑：把会变的封装起来，把不变的暴露出去。

2.5 建造者：参数多到构造器放不下

动机：对象有 5 个以上可选参数时，构造器重载爆炸、参数顺序出错难查。建造者用「链式设置 + 最后 build」解决。

落点：StringBuilder（对 String 的建造）、OkHttp/Netty 的各种 Builder、Lombok @Builder。面试对比「建造者 vs 工厂」：工厂管「创建哪类」，建造者管「创建细节多」——一个解决多态，一个解决参数多。

2.6 动手验证：三个创建型模式改造成对照

观察点：对比「改调用点」与「改工厂」的工作量差异。判定标准：能说清「新增一种支付方式，两种写法各要改几个文件」，即掌握了工厂的核心价值——变化点的位置决定维护成本。

3. 结构型：代理、装饰器、适配器、组合、外观

3.1 代理：不改变目标，包一层控制访问

动机：在不改目标类代码的前提下，给目标方法加横切逻辑（日志、鉴权、事务、延迟加载、远程调用）。代理是面试考得最深的结构型模式，因为 Spring AOP 和 MyBatis 都是它的应用。

JDK 动态代理 vs CGLIB：

对比项 JDK Proxy CGLIB
要求 目标必须有接口 无接口可用
原理 生成实现接口的代理类 生成目标类的子类
局限 无接口无法代理 final 类/方法无法代理
性能 反射调用，JDK8+ 优化后差距缩小 方法调用稍快，但生成类慢

源码落点（深度联动）：

  • Spring AOP：默认 JDK 代理，目标类无接口或配置 proxy-target-class=true 时用 CGLIB。生产后果：只对 public 方法生效、自调用（this.method()）不走代理——「@Transactional 自调用不生效」就是代理模式的经典坑；
  • MyBatis Mapper：你写的 UserMapper 接口从没实现类，MyBatis 用 JDK 代理在运行时生成实现——sqlSession.getMapper() 返回的就是代理对象，invoke 里执行 SQL 绑定；
  • 懒加载：MyBatis/ORM 的关联查询懒加载也是代理（访问属性时才查库）。

因果链：代理把「横切逻辑」从业务代码里抽走 → 业务代码只关心业务 → 框架在代理层统一处理事务/日志/权限 → 代价是「你以为调的是自己写的类，实际调的是框架生成的代理」——自调用失效、final 类不生效、内部方法不被拦截，全源于此。面试答「AOP 原理」答到这一层才算懂：不是背「JDK 动态代理 + CGLIB」，而是能说清「代理对象是运行时生成的，业务代码永远在代理之后执行」。

3.2 装饰器：增强功能，保持接口

动机：动态给对象叠加功能，且叠加顺序可变。与继承的区别是关键考点——装饰器是组合式增强，继承是编译期增强。

落点：整个 java.io 包（BufferedInputStream 装饰 FileInputStream）、Collections.synchronizedList(list)（给任意 List 加线程安全）、UnmodifiableCollection。

代理 vs 装饰器（面试高频对比题）：

对比项 代理 装饰器
目的 控制访问（事务/日志/鉴权） 增强功能（缓冲/同步/压缩）
与目标关系 同接口但语义可能变 保持接口，调用方无感
典型 Spring AOP、MyBatis Mapper IO 流、Collections 包装

一句话区分：代理说「我来替你做」，装饰器说「我帮你做得更好」——代理往往可以完全替换目标（AOP 里你只拿到代理），装饰器要求调用方知道它在装饰（IO 流必须自己组装）。

3.3 适配器：接口不匹配，翻译层接上

动机：两套接口语义相同但签名不同，适配器做翻译。经典误区：适配器和装饰器都「包一层」，但适配器改变接口（翻译），装饰器保持接口（增强）。

落点：Slf4j 是全网最伟大的适配器案例——你的代码只依赖 org.slf4j.Logger，底层可以是 logback、log4j2 或 JUL，通过 slf4j-log4j12 这类适配层无缝切换；Arrays.asList()（数组→List）、StringReader（String→Reader）、Spring HandlerAdapter（把不同 Controller 签名统一成 ModelAndView）。

因果链：适配器的价值在于「不破坏双方」——老代码不动、新代码不动，中间加一层。生产里大量「升级依赖、接口变了」的场景，第一反应应该是适配而不是改调用方。面试答「你项目里用过适配器吗」，标准答案不是背例子，而是「我们升级了 XX SDK，新版接口变了，我写了个适配层包住新版，业务侧零改动」。

3.4 组合：树形结构，叶子与容器一视同仁

动机：对象是树形结构（部门树、菜单树、文件目录、组织架构），希望调用方不用区分「叶子」和「分支」——统一操作。

落点：HashMap 的 computeIfAbsent 组合链、Swing/AWT 组件树、JSON 处理（JsonNode 的容器/叶子）、Maven 的 pom 继承聚合。

3.5 外观：给复杂子系统一个简单入口

动机：子系统一堆类（下单要调库存、优惠、支付、物流四个服务），调用方不想知道内部协作。外观提供一个高层接口。

落点：HttpURLConnection（一个类封装整个协议栈）、Facade 是秒杀系统设计的核心工具（后面系统设计篇会复用）。注意区分：外观（Facade）是对外的统一入口，门面模式（Facade）在 GoF 里就是外观；与适配器区分：适配器是「翻译」，外观是「组织」——外观内部可以任意编排子系统，调用方只看到一个方法。

3.6 动手验证：代理 + 装饰器 + 适配器三个「包一层」写在一起对比

观察点：三个都是「包一层」，区别在接口变不变、调用方知不知道。判定标准：能独立判断「同事写的这段包装代码是哪种」，即建立了模式识别能力——识别 > 记忆，是结构型模式的考察核心。

4. 行为型：策略、模板方法、观察者、责任链、迭代器、状态、命令

4.1 策略：算法可变，运行时切换

动机：同一行为有多个实现（排序算法、支付方式、限流算法、优惠计算），且运行时才决定用哪个。策略把「算法族」封装成可替换对象。这是你项目里最可能真正用过的模式。

源码落点：Comparator 就是策略接口（Collections.sort(list, comparator) 传不同策略）；ThreadPoolExecutor 的拒绝策略（AbortPolicy/DiscardPolicy/CallerRunsPolicy）；Spring 里 @Autowired List<Strategy> 按类型注入全部实现再按条件选——策略 + 工厂 + Spring 容器三件套是生产标准写法。

与状态模式的对比（高频易混）：策略模式调用方决定用哪个算法（外部切换）；状态模式对象自身状态决定行为（内部切换，调用方无感）。一句话：策略是「替它选」，状态是「它自己变」。

4.2 模板方法：骨架固定，步骤可替换

动机：流程骨架不变（准备 → 执行 → 收尾），但某些步骤的实现各不相同。父类定义骨架，子类覆写步骤。

源码落点（深度联动）：

  • AQS（AbstractQueuedSynchronizer）：acquire() 骨架固定（尝试获取 → 失败入队 → 阻塞），tryAcquire() 留给子类——ReentrantLock/Semaphore/CountDownLatch 都是实现不同 tryAcquire 的「同一骨架不同步骤」；
  • Spring JdbcTemplate：execute() 骨架（拿连接 → 执行 → 释放），doInStatement 留钩子；
  • HttpServlet：service() 分发骨架，doGet/doPost 留给子类——你写的每个 Controller/ Servlet 都是模板方法的子类。

因果链：模板方法把「不变的流程」上提到父类 → 子类只写变化点 → 生产后果是：流程改动只改骨架一处，所有子类自动生效（比如给所有流程加埋点，改父类 run() 即可）。面试对比「模板方法 vs 策略」：模板方法变的是步骤，策略变的是整个算法。

4.3 观察者：状态变化，通知订阅者

动机：一个对象状态变了，一群对象需要跟着变（价格变了刷新界面、订单创建发通知），又不想让双方互相依赖。观察者解耦「发布者」和「订阅者」。

源码落点：Spring 事件机制（ApplicationEventPublisher + @EventListener）就是观察者——发布方 publishEvent，监听方无感知耦合；Swing/AWT 的事件监听；java.util.Observer（已废弃）；Redis 的订阅发布；MQ 是观察者的分布式版——一个订单事件，多套系统订阅消费。

因果链：观察者的收益是「新增订阅者零侵入」——加一个下单后发短信的组件，只新增一个监听器，OrderPublisher 一行不改。代价是流程不可见：主流程变成「发事件 → 不知道谁在听」→ 排查问题时不能只看调用链，要全搜监听器。面试深挖：「事件驱动架构和观察者模式什么关系？」——观察者是单机版事件驱动，MQ 是跨进程版，同一思想的放大。

4.4 责任链：请求沿链传递，每个节点决定处理或放行

动机：一个请求要被多个处理器按顺序处理（鉴权 → 限流 → 业务），或任一节点可终止（审批流）。责任链把处理器串成链，每个节点「处理 or 传给下一个」。

源码落点（深度联动）：

  • Servlet Filter 链：doFilter 放行即传下一个——你写的每个过滤器都在责任链上；
  • Netty Pipeline：ChannelHandler 串成链，读入站、写出站——Netty 整个架构就是责任链的实现；
  • MyBatis 插件：Interceptor 链包裹四大对象；
  • Spring MVC HandlerInterceptor：preHandle 返回 false 即终止。

因果链：责任链的收益是「加处理器不改链」——新增一个日志节点，只 new 一个类并插进组装处。代价是顺序敏感：链顺序错了，行为就错了（鉴权必须在业务前）→ 生产里责任链的顺序通常写成配置/常量，而不是散落代码里。面试答「Filter vs Interceptor vs AOP 区别」时，责任链是共同底层的组织方式。

4.5 迭代器：遍历与容器解耦

动机：容器内部结构（数组、链表、树）各不相同，调用方希望统一遍历方式。迭代器提供统一接口，容器隐藏结构。

落点：java.util.Iterator（所有 Collection 的遍历）、for-each 语法糖底层就是迭代器、MyBatis 的游标分页（Cursor）。

面试点：for-each 遍历时删除元素为什么抛 ConcurrentModificationException？ —— ArrayList 的迭代器维护 expectedModCount，remove() 直接改 modCount，迭代器 next() 时校验不一致即抛异常。因果链：这是迭代器模式的「契约」——迭代器假定容器在遍历期间不被结构修改，违反契约就用异常提醒。用 iterator.remove() 或 CopyOnWriteArrayList 是正解。

4.6 状态模式：行为随状态切换

动机：对象行为取决于内部状态（订单：待支付 → 已支付 → 已发货 → 已完成），状态多了 if-else 爆炸。状态模式把每个状态的行为封装成独立类。

面试对比：状态 vs 策略（§4.1 已述）；状态 vs if-else（状态模式是 if-else 的面向对象替代，状态多且迁移规则复杂时用）。

4.7 命令：请求封装成对象，可排队可回滚

动机：把「做什么」（命令对象）与「谁来做」（执行者）分离，支持排队、撤销、日志。落点：Runnable/Callable（把任务封装成对象交给线程池）、Spring @Async、数据库事务本身（undo log 就是命令模式的回滚思想）。

4.8 动手验证：用责任链重构一个「入职流程」

观察点：对比「新增一个『背调』环节」时两版的改动范围。判定标准：能说出「if-else 版改主流程方法体，责任链版新增一个类 + 改组装行」，即掌握了责任链的本质——流程变化与流程定义分离。

5.2 面试答题框架：30 秒标准结构

任何高频模式题，按固定框架答，杜绝「背定义」观感：

  1. 一句话动机（解决什么问题）：「单例保证全局唯一，避免重复创建和状态不一致」
  2. 关键机制（怎么实现）：「DCL + volatile 防重排，或静态内部类延迟加载」
  3. 框架落点（哪里见过）：「Spring 的 Bean 默认就是单例的」
  4. 你的应用（自己用过）：「我们项目里配置管理器用了单例，配合 Spring 单例 Bean」
  5. 代价（权衡）：「单例有状态时并发不安全」「单例让测试困难」——主动说代价是加分项，说明你真的用过

核心技巧：第 4、5 步是区分度所在。第 1-3 步所有人都会，第 4 步需要真实经验（没有就说「我看到过 XX 框架里这样用」），第 5 步体现设计判断力。

5.3 反模式警示：什么时候不该用模式

反模式 表现 后果
过度设计 3 个 if 也要套策略 代码量翻倍，可读性崩
为模式而模式 面试官问「用了什么模式」才想起给代码贴标签 模式是结果的命名，不是设计目标
策略类爆炸 每个策略一个类，类数量失控 维护成本高于 if-else
责任链顺序散落 链顺序埋在各处 new 代码里 顺序改了不知道，行为静默变化

判断标准：「这个变化真的会发生吗？」——支付方式未来可能加（策略合理）、会员等级就两种且一年不变（if-else 更务实）。模式的适用前提是「变化可预期且发生频率高」。

6. 总结

6.1 面试速答表

面试题 一句话答案
单例有哪几种写法？ 饿汉/静态内部类/枚举（推荐），DCL 是面试题；DCL 必须 volatile 防指令重排返回半初始化对象
代理和装饰器区别？ 代理控制访问（替你做事），装饰器增强功能（帮你做得更好）；接口变不变、调用方知不知道
JDK 动态代理和 CGLIB？ JDK 基于接口生成代理类；CGLIB 生成子类；无接口用 CGLIB，final 类都不能代理
Spring AOP 为什么自调用失效？ 代理对象是运行时生成的，this 调用不经过代理——自调用（this.method()）直接命中目标方法
MyBatis Mapper 为什么不用写实现类？ SqlSession.getMapper() 返回 JDK 动态代理，invoke 里做 SQL 绑定
策略和状态模式区别？ 策略：调用方选算法（外部切换）；状态：对象自身状态决定行为（内部切换）
模板方法在哪见过？ AQS：acquire 骨架固定，tryAcquire 留钩子；JdbcTemplate、HttpServlet 同理
观察者和 MQ 关系？ 观察者是单机事件通知，MQ 是它的分布式放大版——解耦发布与订阅
for-each 中删除为什么抛异常？ 迭代器校验 modCount，结构修改违反迭代契约
什么时候不该用模式？ 变化不会发生或频率极低时——模式为「可预期的变化」服务

6.2 实战避坑表

症状 原因 处理
DCL 偶发返回「半成品」对象 缺 volatile，指令重排 加 volatile；或换静态内部类/枚举
@Transactional 自调用不生效 走 this 调用，绕过代理 注入自身代理/拆类/用 TransactionTemplate
接口事务不生效 Spring 默认 JDK 代理，目标必须实现接口 配置 proxy-target-class=true 或确保实现接口
策略类爆炸 每个细微差异一个策略 评估变化概率，合并策略或退化回 if-else
责任链顺序错乱 链顺序散落在组装代码 顺序集中管理（配置/常量/文档）
单例保存了可变状态 全局共享状态被并发写 状态只读，或用 ThreadLocal/无状态单例
