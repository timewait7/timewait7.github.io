容量与扩展：什么时候才该分库分表

Posted on 2026-10-25 In 数据存储 Word count in article: 4k Reading time ≈ 15 mins.

「MySQL 撑不住了」这句话里，90% 的情况是索引或慢查询撑不住，不是 MySQL 撑不住。真正的单机上限有三个维度：连接数、单表数据量、写入吞吐。它们触顶的信号完全不同，处理手段也完全不同——用错了手段，就是「分了表之后发现还是慢」。

本文用 1000 万行表的实测数据回答三个问题：单机的天花板在哪、什么时候该往上加一层、真到了分片那一天怎么迁。收官部分给全系列 12 篇的总表。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池与事务 → ⑫ 容量与扩展（本文·收官）

与前后篇的关系：① 的基线、③ 的索引、⑦ 的刷盘共同决定了本文的「天花板」；⑧ 的复制是第一条扩展路径；本文的分片是最后一条。

1. 单机上限：三个维度分别在哪顶住

1.1 维度一：连接数

实测 max_connections = 151（8.0 默认）。每个连接是一个线程，占栈内存与调度时间。

信号 数值 说明
Threads_connected 接近 151 连接耗尽 新请求直接被拒（Too many connections）
Threads_running 持续 > CPU 核数 排队 加连接只会加重排队（⑪ 的实测：池越大 p99 越小，但吞吐受 CPU 限）
连接池 max 总和 > 151 多应用抢连接 要按应用配额分配，别都设成 20

先算一笔账：3 个应用 × 每应用 20 个连接 = 60，加上备份、监控、DBA 连接，离 151 不远。所以「加连接数」的天花板比想象中低得多。

1.2 维度二：单表数据量

这是最容易被误解的维度。实测两张表（同一实例、1GB Buffer Pool）：

指标 100 万行 1000 万行 倍数
数据大小 54 MB 428 MB 8×
数据页数 3,430 27,391 8×
主键点查页请求 4 4 1×
二级索引范围扫（100 行） ~0.2 ms 0.214 ms 1×
全表扫描耗时 61 ms 540 ms ~9×

核心结论：点查几乎不随数据量变慢，全表扫是线性变慢的。 B+ 树的意义就在这里——1000 万行的树高仍然是 3~4 层，所以「按主键查」永远不会因为数据多而变慢。

那为什么大表会「感觉慢」？因为：

变慢的东西 原因 对应篇目
全表扫描 / 无索引查询 线性扫描 27,391 页 ③④
加索引 / 改表结构 要读全表 ⑩
备份与恢复 数据量大 ⑨
冷数据物理读 Buffer Pool 装不下 ⑦
深分页 offset 前全部要读 ④

所以「单表 2000 万行就要分表」是个伪命题。真正该看的是：你的查询有没有全部走索引、Buffer Pool 能不能装下热数据、DDL 与备份的窗口够不够。数据量本身不是红线。

1.3 维度三：写入吞吐与 QPS 拐点

flowchart LR
    A["4 threads<br/>21924 qps"] --> B["8 threads<br/>29088"]
    B --> C["16 threads<br/>37506"]
    C --> D["32 threads<br/>50682"]
    D --> E["64 threads<br/>53676"]
    E -.->|"plateau: adding threads<br/>buys only 6%"| F["Knee of this machine"]

用 Java 压测（64 连接池）对 1000 万行表做主键点查，逐步加线程：

线程数 QPS 相比上一档
4 21,924 —
8 29,088 +33%
16 37,506 +29%
32 50,682 +35%
64 53,676 +6%

拐点在 32~64 线程之间：从 32 加到 64，QPS 只涨 6%，但并发压力翻倍。这就是「加机器/加线程」的收益边界——超过拐点，多出来的并发只会变成排队和上下文切换。

场景 拐点信号 该做什么
点查型 QPS 平台化、CPU 到 80% 加只读副本（读扩展）
写入型 TPS 平台化、innodb_buffer_pool_wait_free > 0 分库（写扩展）
混合型 读写互相拖累 先读写分离，再评估分片

1.4 动手验证：算出你自己的天花板

预期观察点：point_lookup_pages 是 3~4（与表多大无关）；full_scan_pages 约等于表的总页数。

判定标准：

  • 点查页数随数据量增长 → 你的主键设计有问题（比如用了 UUID 或字符主键）；
  • 全表扫页数 ≈ 表页数，且这类查询占慢日志的大头 → 先加索引（③），别急着分表。

2. 扩展路径：先加什么，后加什么

2.1 四条路，代价递增

层级 手段 收益 代价 触发信号
1 索引/查询优化 10~1000× 几乎为零 慢日志里有全表扫
2 缓存（Redis） 10× 读 一致性变复杂 热点读占 80%
3 读写分离 读线性扩展 延迟与一致性（⑧） 读 QPS 到拐点

顺序铁律：1 → 2 → 3 → 4 → 5。跳过任何一步，都会在分片后重新遇到同一个问题。

2.2 什么时候真的该分片

信号 阈值（经验） 说明
单表数据量 > 5000 万行且无法归档 备份、DDL 窗口不可接受
写入 TPS 超过单机拐点 加从库没用，写只有主库扛
单库磁盘 > 2 TB 备份/恢复时间不可控
业务隔离需求 多租户、跨地域 分片是顺带的

注意「且」：单表 5000 万行但查询全走索引、备份窗口 10 分钟、DDL 用 gh-ost——这种情况完全可以不分。分片是「运维成本」与「业务增长」的交易，不是技术炫耀。

3. 分片实操：选键、迁移、校验

3.1 分片键的三个判据

判据 好的分片键 坏的分片键
均匀 用户 ID、订单 ID 的哈希 状态、地区（倾斜严重）
高频查询能定位到单片 WHERE user_id = ? 只有 WHERE create_time > ?
不跨片 订单按 user_id 分，查订单带 user_id 按 order_id 分，却常按 user_id 查

口诀：分片键要选「查询里必带、且分布均匀」的那一列。

3.2 取模 vs 一致性哈希

flowchart LR
    subgraph Mod["mod 4 -> mod 8"]
        M1["key 7: 7%4=3 -> shard3"] --> M2["扩容后 7%8=7 -> shard7<br/>几乎全量搬迁"]
    end
    subgraph Ring["consistent hashing"]
        R1["key 7 -> hash 落在 node C"] --> R2["加节点 D 只迁移<br/>相邻一段"]
    end
方案 扩容影响 实现复杂度 适用
取模（mod N） 换 N 就全量迁移 低 分片数确定不变
取模 + 成倍扩容（4→8） 一半数据迁移 低 早期扩展
一致性哈希 + 虚拟节点 只迁 1/N 中 频繁扩容
预分片（一开始就 1024 片，映射到少量实例） 迁移时只改映射 中 推荐：未来扩容不动数据

推荐做法：逻辑分片数一次给够（如 1024），物理库先少（如 4 个），扩容只是把逻辑分片搬到新库——不需要重算路由，这是大型系统最常见的折中。

3.3 双写迁移流程

sequenceDiagram
    participant App
    participant Old as old table
    participant New as 16 shards
    Note over Old,New: phase 1: full copy (chunked)
    App->>Old: normal read/write
    Old->>New: copy where id <= cutoff
    Note over Old,New: phase 2: dual write

阶段 动作 风险控制
全量拷贝 按主键区间分批（每批 1000~5000 行） 不锁表，可暂停
双写 新老同时写 新写失败要回滚老写，或落补偿队列
增量追平 按 id 水位同步 delta 记录 cutoff，避免漏行
校验 行数 + 金额/数量聚合 + 抽样 必须能发现 1 行的差异
切换 读切新表，观察 N 天 老表保留可回滚
清理 停双写、归档老表 至少保留一个备份周期

3.4 实测：50 万行迁 16 片 + 校验 + 故障注入

本文用 1000 万行的源表做了一次真实迁移（只迁前 50 万行以控制时间）：

阶段 实测
建 16 个分片表 即时
全量拷贝 50 万行（16 条 INSERT ... SELECT，按 user_id % 16 路由） 2.88 s
迁移期间新增 1001 行 —
增量同步（id > 10000000） 0.54 s
校验：源 501,001 行 / 88,130,684.99 —
校验：16 片合计 501,001 行 / 88,130,684.99 ✅ 完全一致
故障注入：删掉分片里 1 行再校验 501,000 行 / 88,130,673.88 → 差 1 行 / 11.11 ✅ 能抓到

这一组数据最有价值的地方不是速度，而是最后一行的「校验能发现 1 行差异」。迁移事故的典型形态不是慢，是「看起来迁完了，其实少了 37 行」——没有校验就没有迁移。

3.5 动手验证：在你自己的表上做一次「小规模迁移」

预期观察点：两条查询的行数与金额完全相同。

判定标准：

  • 行数一致但金额不一致 → 有行被改了没同步（检查双写逻辑）；
  • 差值是整数倍的单行金额 → 漏了某个批次；
  • 校验耗时远大于拷数据 → 校验本身要优化（先按主键区间分片算）。

4. 分片后的一致性代价

能力 单库 分片后 代价
跨片 JOIN 直接写 几乎不可用 冗余字段或内存拼装
全局排序 + 分页 ORDER BY ... LIMIT 各片取 N 条再归并 深分页更难
全局唯一 ID 自增 雪花/号段/UUID ⑫ 的分布式 ID 问题
跨片事务 单机事务 2PC/TCC/Saga 分布式事务（站内另有一篇）
聚合统计 SUM/GROUP BY 各片聚合再合并 实时性下降，常走离线

所以分片的顺序是：先把单库优化到极致（③④⑦），再做读写分离（⑧），最后才分片。反过来说，如果分片后你发现「跨片查询太多」，那不是分片技术不行，是分片键选错了。

Java 侧：连接池打满与 @Transactional 失效的真相

Posted on 2026-10-25 In 数据存储 Word count in article: 3.8k Reading time ≈ 14 mins.

数据库很健康，接口却全量超时——这类故障的根因大多不在 MySQL，而在应用侧的连接池与事务边界。连接池是个排队系统：池里有几个连接，决定了你的系统最多能并发几个「数据库等待」；@Transactional 是个代理：绕过代理的调用，事务根本不存在。

本文用可运行的 Java 代码（JDK 21 + HikariCP 5.0.1 + Spring 6.1.6 + MySQL 8.0.46）把两件事量成数字：池大小 2/8/20 对应的吞吐与 P99，以及六种 @Transactional 写法的真实提交结果——其中四种会「悄悄失效」，数据照样落库。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池与事务（本文） → ⑫ 容量与分库分表

与前后篇的关系：② 测出「一次连接建立是毫秒级、一条语句是微秒级」，本文解释为什么连接必须复用；⑤ 讲的事务机制，在本文变成「代理没生效，事务就没开」；⑩ 的 MDL 雪崩，最终会在这里表现为连接池打满。

1. 连接池是个排队系统

1.1 连接为什么必须复用

② 的实测：新建连接要付 TCP 握手 + 认证，服务端几毫秒；而一条已建立连接上的 SELECT 1 只要 10.8 微秒。差两个数量级。

flowchart LR
    T["32 app threads"] --> Q["HikariCP queue"]
    Q --> P["pool: N connections"]
    P --> DB["MySQL server"]
    DB --> P --> Q --> T
    Q -.->|"no idle connection<br/>and pool full"| W["wait up to<br/>connectionTimeout"]
    W -.->|"exceeded"| E["SQLTransientConnectionException"]

关键认知：池不是缓存，是限流器。它的作用是「限制同时打到 MySQL 的连接数」，而不是「越多越快」。

1.2 HikariCP 关键参数（实测默认值）

用 HikariCP 5.0.1 初始化一个只设了 URL 的池，读出的解析后默认值：

参数 实测默认 含义 实践建议
maximumPoolSize 10 池上限 按 QPS × 平均耗时 估，别拍脑袋
minimumIdle 10（等于 max） 最小空闲 与 max 相等可避免抖动，但要接受启动即建连
connectionTimeout 30000 ms 拿连接的等待上限 业务超时通常 1~3 s，这里要同步调小
idleTimeout 600000 ms 空闲连接回收 默认即可
maxLifetime 1800000 ms 连接最长寿命 要小于 MySQL wait_timeout（默认 8 小时）
keepaliveTime 0（关闭） 保活探测 走 NAT/LB 时可开
validationTimeout 5000 ms 校验连接可用 通常不用改
leakDetectionThreshold 0（关闭） 连接泄漏检测 排查泄漏时临时设为 20~60 s

1.3 池大小怎么算

小学算术：池大小 ≈ 目标 QPS × 单请求在库里的平均耗时（秒）。

场景 目标 QPS 单请求耗时 需要连接数
后台管理 50 10 ms 0.5 → 1~2
普通业务接口 200 20 ms 4
有慢查询（未优化） 200 200 ms 40
秒杀扣减 2000 5 ms 10

这张表最有用的一行是第三行：慢查询会直接放大连接需求。一条 200 ms 的 SQL 在 200 QPS 下需要 40 个连接，而 MySQL 的默认 max_connections 是 151（实测），几个这样的接口就能把实例连接数打满。所以「加连接数」永远是最后手段，先优化 SQL。

1.4 实测：池大小 vs 吞吐 vs P99

32 个线程、240 次请求，每次执行 SELECT SLEEP(0.05)（模拟 50 ms 的慢查询）：

池大小 总耗时 吞吐（rps） p50 p99
2 6,337 ms 37.9 52 ms 6,176 ms
8 1,624 ms 147.8 51 ms 1,622 ms
20 775 ms 309.7 51 ms 757 ms

三个结论：

  1. 吞吐 ≈ 池大小 / 单请求耗时。池 2 → 理论 40 rps，实测 37.9，几乎完全吻合。
  2. p50 一直是 51 ms，与池大小无关；p99 从 6.2 秒降到 0.76 秒。池小不会让单次查询变慢，只会让排队变长。
  3. p99 和 p50 的差距就是排队时间的上界。看到 p50 正常、p99 爆炸，第一反应应该是「池/线程池在排队」，而不是「数据库有问题」。

1.5 动手验证：量出你自己系统的池需求

预期观察点：p50 稳定在你设定的 50 ms 左右，p99 随池变小而成倍增加。

判定标准：

  • rps ≈ poolSize / 平均耗时 → 池就是瓶颈，加池或优化 SQL；
  • rps 不随池增大而上升但仍低于目标 → 瓶颈不在池（CPU、下游、锁）；
  • p99 / p50 > 10 且两者都不是 50 ms → 有 GC 或网络抖动，用 jstack/async-profiler 看。

3. @Transactional 失效：六种写法实测

3.1 原理：你调用的不是原对象

sequenceDiagram
    participant Caller
    participant Proxy as Spring Proxy
    participant Target as YourService
    participant TM as TransactionManager
    Caller->>Proxy: service.doWork()
    Proxy->>TM: begin()
    Proxy->>Target: doWork()
    Target-->>Proxy: return / throw
    Proxy->>TM: commit() / rollback()
    Note over Target: this.other() bypasses proxy<br/>-> no new transaction

@Transactional 靠代理生效。三类情况代理拦不住：① 同类内部自调用；② 方法不是 public（CGLIB 无法覆盖）；③ 对象不是 Spring 管理的 Bean。

3.2 实测：六种写法的提交结果

同一张表、同一个数据库，每条 case 插一行后故意抛异常，然后另开连接查这行还在不在：

# 写法 实测结果 是否符合预期
1 自调用 this.txMethod() rows=1（已提交） ❌ 静默失效
2 private 方法加 @Transactional rows=1（已提交） ❌ 静默失效
3 抛受检异常 Exception rows=1（已提交） ❌ 默认不回滚
4 异常在方法内部被 catch 吞掉 rows=1（已提交） ❌ 事务照常提交
5 抛 RuntimeException（正解） rows=0（已回滚） ✅
6a 外层事务（内层 REQUIRES_NEW 失败） rows=1（已提交） ✅ 外层不受影响
6b 内层 REQUIRES_NEW 抛异常 rows=0（已回滚） ✅ 独立事务回滚

六条里有四条是「看起来有事务、实际没有」。 这就是为什么「我明明加了注解」和「数据还是写进去了」能同时成立。

3.3 逐条解释

① 自调用：this.txMethod() 走的是原始对象，不经过代理，所以那个 @Transactional 完全没执行。修法：拆到另一个 Bean，或注入自身代理（@Lazy 注入自己 / AopContext.currentProxy()）。

② private：CGLIB 通过继承生成子类来拦截，private 方法无法被覆盖。Spring 6 会忽略它，不会报错。

③ 受检异常：@Transactional 的 rollbackFor 默认只有 RuntimeException 和 Error。抛 Exception 时事务照常提交。修法：@Transactional(rollbackFor = Exception.class)。

④ 内部 catch：事务管理器只看到「方法正常返回」，于是提交。要局部失败不影响整体，用 REQUIRES_NEW 把内层独立出去。

⑤ 正解：运行时异常向外抛，代理捕获后 rollback。

**⑥ REQUIRES_NEW**：内层挂起外层事务、独立开一个，失败只回滚自己；外层捕获后继续提交。适合「记录日志/埋点不能拖垮主流程」的场景。

3.4 传播行为速查

传播行为 有外层事务时 典型用途
REQUIRED（默认） 加入外层 绝大多数业务
REQUIRES_NEW 挂起外层，新建 日志、审计、独立补偿
NESTED 保存点 局部失败可回滚到保存点

4. 动态数据源与事务边界

4.1 为什么「事务里切库」会失效

sequenceDiagram
    participant App
    participant DS as RoutingDataSource
    participant Tx as TransactionManager
    participant M as Master
    participant S as Replica
    App->>Tx: @Transactional begin
    Tx->>DS: getConnection()
    DS->>M: connect (write)
    Note over Tx: connection bound to transaction
    App->>DS: switch to replica
    DS-->>App: ignored - connection already bound
    App->>M: SELECT goes to master
现象 原因 处理
事务内切从库不生效 连接在事务开始时已绑定 切库发生在事务外（先查询后开事务）
事务方法里读写都走主库 同上 写后读走主库是有意为之，保证一致性
主从延迟读到旧数据 复制延迟（⑧） 强制走主库，或按 GTID 等待

结论：@Transactional + 动态数据源，路由只在事务开始时决定一次。想「读走从库、写走主库」，必须保证读操作在事务外，且能接受延迟。

4.2 主从路由的一致性代价

方案 一致性 实现成本 适用
全部走主库 强 0 写多、强一致
读写分离（无补偿） 弱 低 读多、能容忍延迟
写后强制读主（时间窗） 中 低 用户刚提交后跳转详情页
按 GTID 等待 强 高 强一致读

在线 DDL：一次加索引如何堵死整张表

Posted on 2026-10-25 In 数据存储 Word count in article: 3.6k Reading time ≈ 13 mins.

DDL 的危险不在「执行慢」，而在「排队等」。一条 ALTER TABLE 本身可能只要 3 秒，但它会先在 MDL 队列里排一个 EXCLUSIVE 请求；后面的所有查询——包括普通 SELECT——都会排在它后面。于是「3 秒的变更」变成「3 分钟的故障」。

本文用 200 万行、106MB 的表把这件事量成数字：7 种 DDL 的耗时、哪些会让写入阻塞、阻塞多久。实测最有说服力的一组对比是：ADD INDEX 期间插入 0.05 秒完成（在线），MODIFY COLUMN 触发的 COPY 重建期间插入等了 3.62 秒（锁表）。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL（本文） → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

与前后篇的关系：⑥ 讲了 MDL 的加锁机制，本文把它落到「变更窗口怎么算」；⑨ 是数据事故，本文是变更事故——两者的预防手法都是「先把检查项写死」。

1.2 实测：七种 DDL 的真实代价

表：200 万行、106MB，Buffer Pool 1GB，本地 SSD。

DDL 实际算法 耗时 期间写入

  2. 加索引要读全表（1.557 s / 2M 行），但在线，不阻塞写入。

1.3 深挖：为什么有些 MODIFY 是 0.002 秒，有些要重建

关键在于存储格式有没有变：

变更 存储格式 结果
VARCHAR(64) → VARCHAR(128)（utf8mb4） 两者都是 2 字节长度前缀 只改元数据，0.002 s
VARCHAR(64) → VARCHAR(200) 同上 同上，元数据级
TINYINT → SMALLINT 1 字节 → 2 字节 必须重建
utf8mb4 → latin1 字符集变了 必须重建
INT → BIGINT 4 字节 → 8 字节 必须重建

判据：字节宽度或编码变了就要重建；只是「上限放宽但宽度不变」可以只改元数据。所以「改字段长度」在线上是相对安全的，「改字段类型」基本等于重建。

1.4 8.0 instant DDL 的边界

能 INSTANT 不能 INSTANT

在中间加列（8.0.29+） 改列类型
删列（8.0.29+） 改字符集
改列默认值 改 ROW_FORMAT
重命名列（8.0 起部分支持） 加主键

一个必须知道的限制：instant 加列有上限（每张表最多 64 次 instant 变更），超过之后需要一次重建来「整理」。所以频繁 instant 加列不是无限的。

  • 报 1846 → 这个变更必须 COPY，按「锁表变更」处理（走 3.2/3.3 的方案）。

2. MDL：一行 ALTER 如何堵住整张表

2.1 队列是 FIFO，不允许插队

flowchart LR
    A["Trx A<br/>SELECT in open transaction<br/>MDL SHARED_READ GRANTED"] --> T["Table big"]
    B["ALTER TABLE<br/>MDL EXCLUSIVE PENDING"] -->|"queued behind A"| T

MDL 队列不允许后来的读绕过前面的写请求，这是为了防饥饿。代价就是：一个 DDL 在排队，后面所有的读一起排队。

2.2 实测：阻塞链长什么样

读法：

  • waiting_pid=22 是 ALTER，它要 EXCLUSIVE，被 blocking_pid=21（那个没提交的事务）的 SHARED_READ 挡住；

2.3 深挖：为什么 innodb_lock_wait_timeout=2 没生效

第一节的 COPY 实验里，我把 innodb_lock_wait_timeout 设成 2，插入却等了 3.62 秒才成功（DDL 结束时放行）。原因：

等待类型 受哪个参数控制 默认值
InnoDB 行锁等待 innodb_lock_wait_timeout 50 秒
MDL 等待 lock_wait_timeout 31536000 秒（一年）

COPY 重建时持有表的 MDL EXCLUSIVE，插入要等的是 MDL，不是行锁。所以 innodb_lock_wait_timeout=2 完全不起作用——这就是为什么很多「我设了超时怎么还在卡」的问题找不到原因。

2.4 DDL 前的 Checklist（照着跑）

检查项 阈值 不通过怎么办
长事务 age_s > 5 等它结束或 KILL（注意大事务回滚耗时）
MDL PENDING 任意 停止发新 DDL，等队列清空
算法 是否 INSTANT/INPLACE COPY 必须走变更窗口或 gh-ost
表大小 CPU 估算时间 2M 行约 1.5 s（加索引），按比例外推

2.5 动手验证：复现 MDL 阻塞

预期观察点：C 在 2 秒后返回 ERROR 1205；期间查 sys.schema_table_lock_waits 能看到 A→B→C 的三层排队。

判定标准：

  • C 立即成功 → A 的事务已提交，或 A 用的是自动提交（autocommit=1 的 SELECT 不持有 MDL）；
  • C 报 1205 且 B 一直 PENDING → 这就是线上雪崩的起点，立刻处理 A。

4. 一次 P0 复盘（用本文实测数据拼合）

时刻 事件 现象
T0 运维发起 ALTER TABLE orders ADD INDEX ... DDL 进入 MDL 队列
T0 队列前面有一个未提交的事务（报表导出） DDL 变成 PENDING
T0+5s 应用查询开始变慢 所有 SELECT 排在 DDL 后面
T0+30s 连接池打满 接口大面积超时（⑪ 的因果）
T0+90s DBA 杀掉报表事务 DDL 执行 1.5 秒后完成

根因：不是 DDL 慢，是「DDL 排在一个长事务后面」，而队列 FIFO 让所有读跟着排队。

处置顺序（可照抄）：

  1. KILL 掉阻塞的事务（先确认不是核心批处理）；
  2. 观察 sys.schema_table_lock_waits 是否清空；
  3. DDL 执行完后确认 metadata_locks 无 PENDING；
  4. 复盘：把 2.4 的 Checklist 写进发布流程，缺一项不许发。

5.4 实操建议

  1. 先问「这个变更能不能 INSTANT」。加列/删列在 8.0 就是毫秒级，别用重工具。
  2. DDL 前跑 2.4 的两条查询，把「长事务为零、MDL 无 PENDING」作为发布门禁。

备份与恢复：删库之后 30 分钟救回来

Posted on 2026-10-25 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

备份的唯一价值是「能不能恢复」，而恢复只有两个数字：RPO（丢多少）和 RTO（要多久）。没演练过的备份等于没有备份——因为你不知道它能不能恢复，也不知道要花几分钟。

本文做了一件很多教程只说不做的事：真的删表，再恢复回来。全备用 mysqldump、恢复用 binlog 重放，全程计时。实测结果：全备 0.09 秒，恢复（全备 + 重放）0.46 秒，120,000 行数据一字不差地回来了。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复（本文） → ⑩ 在线 DDL → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

与前后篇的关系：⑦ 的两阶段提交保证 binlog 与数据一致，这是「重放 binlog 能补回数据」的前提；⑧ 的从库可以当备份源，但复制不是备份（逻辑错误会同步过去），本文解释两者边界。

1. 先定目标，再选工具

1.1 RPO 与 RTO

指标 定义 通俗说法 由什么决定
RPO（Recovery Point Objective） 能容忍丢多少数据 最多丢几分钟 备份频率 + binlog 是否完整
RTO（Recovery Time Objective） 恢复要多久 多久能对外服务 数据量 + 恢复方式 + 演练熟练度 
flowchart LR
    T0["Last backup<br/>03:00"] --> X["Incident<br/>05:00"] --> R["Recovery done<br/>05:20"]
    T0 -.->|"RPO: 2 hours<br/>of binlog replay"| X
    X -.->|"RTO: 20 min"| R

关键认知：RPO 由「备份 + binlog 保留策略」决定，RTO 由「恢复流程 + 演练次数」决定。只买备份工具、不做演练，RPO 达标而 RTO 不可控。

1.2 逻辑备份 vs 物理备份

维度 逻辑备份（mysqldump） 物理备份（xtrabackup / clone）
产出 SQL 文本（CREATE + INSERT） 数据文件拷贝（.ibd 等）
速度 慢（要转成 SQL 再执行） 快（直接拷页）
恢复粒度 可只恢复某张表 整实例，或单表（需 export/import tablespace）
跨版本 兼容性好（8.0 → 8.4 没问题） 大版本间通常不行
空间 小（纯文本，压缩后更小） 大（含索引、碎片）
适合 中小库、单表恢复、跨环境迁移 大库（TB 级）、要求 RTO 极短

1.3 全备、增量、binlog

类型 内容 频率 作用
全备 某时刻的完整数据 每天/每周 恢复的起点
增量 上次备份以来的变化 每小时 缩短重放链
binlog 每个事务的变更流 持续 恢复到任意时间点（PITR）

只有全备 + binlog 才能做 PITR。只有全备，只能回到备份那一刻；只有 binlog，没有起点也恢复不了。

1.4 一致性快照靠什么

mysqldump --single-transaction 的原理是：开一个 REPEATABLE READ 事务，拿到一致快照，然后边读边导，不锁表（InnoDB 表）。

三个前提：

前提 不满足的后果
表必须是 InnoDB MyISAM 表会不一致
备份期间不能有 DDL 会破坏快照一致性（DDL 隐式提交）
需要 --source-data 记录位点 不知道从哪里开始重放 binlog

--master-data 在 8.0.26 之后更名 --source-data（实测 dump 里写入的是 CHANGE MASTER TO MASTER_LOG_FILE=..., MASTER_LOG_POS=... 注释）。

校验必须做，而且要校验「业务含义」而不是只看行数：

2.5 一个意外发现：id 从 131071 开始

恢复后 MAX(id) 是 151070，而不是我预期的 120000。原因不在恢复，而在写入方式：INSERT ... SELECT 属于「批量插入」，InnoDB 在 innodb_autoinc_lock_mode=2（实测默认）下会按 2 的幂预分配自增值，所以第二段插入拿到的 id 从 131071 开始，中间留下大段空洞。

这带来两个结论：

  1. 自增 id 不连续是正常现象，不要拿它当「有没有丢数据」的证据——校验要用 COUNT(*) 与业务聚合值；
  2. 恢复时要确认行事件里的 id 是显式值（ROW 格式天然如此），所以恢复出来的 id 与原文一致，这一点实测验证过（MAX(id) 恢复前后都是 151070）。

2.6 动手验证：自己跑一遍完整 PITR

预期观察点：恢复后应该是 5 行、SUM(amount)=150，与删除前完全一致。

判定标准：

  • 行数对但金额不对 → 重放区间端点选错（包含了不该重放的事务，或多重放了一遍）；
  • 重放报 ERROR 1062 Duplicate entry → 起点位置选在了全备位点之前，导致重复应用；
  • 恢复耗时远超预期 → 全备太大或 binlog 区间太长，考虑增量备份。

说明：官方 mysql:8.0 镜像里**没有 mysqlbinlog**（我实测 command not found），所以要么把 binlog 拷出来用宿主机的 mysqlbinlog，要么单独装客户端工具。这一点很少有文章提到，但真到恢复时会卡住。

3. 误删 2 小时后才发现：为什么不能整库回滚

如果事故发生在 2 小时前，而此时库里已经有 2 小时的新写入，直接「全备 + 重放到 2 小时前」会导致这 2 小时的数据全部回退。

正确做法是「只捞那一张表」：

    B --> C["Restore full backup<br/>+ binlog to T-1s"]
    C --> D["Dump only the lost table<br/>from temp instance"]

步骤 命令要点 注意
1 起临时实例 同版本、同字符集 别在生产实例上折腾

3 只导出目标表 mysqldump shop orders --where="id<=..." 表大就分批导
4 导入生产 导入到新表名，校验后 RENAME TABLE 避免直接覆盖
5 校验 行数 + 关键聚合值 + 抽样对比 三项缺一不可

为什么不能直接覆盖：事故后业务可能已经写入了「补偿数据」或「手工修正」，直接覆盖会把它们冲掉。

binlog 里 --stop-position 怎么定 事故语句之前的位点，用 SHOW MASTER STATUS 或 binlog 里定位 DROP 事件
为什么复制不能当备份 逻辑错误会同步到从库，一条 DROP 两边都没
误删 2 小时后怎么恢复 临时实例恢复到删除前，只导出目标表，校验后切回，不要整库回滚
自增 id 不连续说明丢数据吗 不能说明；INSERT ... SELECT 会按 2 的幂预分配 id，校验要用行数与聚合值
备份怎么验证有效 在临时实例真恢复一次，比对行数与关键聚合
8.0 备份有哪些内置能力 Clone Plugin（8.0.17+）、--source-data、binlog 默认开启

5.2 实战避坑表

症状 原因 处理
恢复后数据少一段 binlog 保留不够，或重放起点错了 检查 --start-position 与 binlog 保留天数
重放报 Duplicate entry 起点早于全备位点，重复应用 用 --source-data 记录的位点作起点
恢复后其他表被回退 整库回滚了 改用「临时实例 + 只捞单表」
备份文件无法恢复 从没验证过 立即做一次恢复演练，别等事故
从库备份点比预期旧 从库延迟 备份前确认 SBM/心跳延迟
恢复很慢（小时级） 全备太大或逻辑备份逐行插入 换物理备份，或按表并行恢复

5.3 工具速查表

工具 看什么 判定标准
mysqldump --source-data=2 备份位点 拿到 binlog.xxx + pos 才能做 PITR
mysqlbinlog --start/stop-position 重放区间 区间必须落在「全备位点 → 事故前」之间
SHOW MASTER STATUS 当前位点 事故前后各记一次
SHOW BINARY LOGS binlog 列表与大小 确认覆盖到目标时间点
information_schema.tables 恢复后行数估算 精确校验用 COUNT(*) 与聚合

5.4 实操建议

  1. 先算 RPO/RTO，再选工具。目标不清就买工具，等于没定需求。
  2. 每次备份都记录位点，--source-data=2 一行注释就够，但必须进备份产物的元数据。
  3. 演练按季度做，并且真删一次表（在测试实例上）。本文这次 0.46 秒的 RTO，是数据量小 + 单表 + 本地盘的结果，生产上要按自己数据量重测。
  4. 只恢复单表时，绝不整库回滚。临时实例 + 导出 + 校验 + RENAME 是标准动作。
  5. 把「备份能不能恢复」写成检查项，和告警、监控一起纳入日常，而不是写在文档里。
