Tomcat 深度解析：连接器、类加载与调优排障

Posted on 2026-08-13 In 框架 Word count in article: 6.2k Reading time ≈ 22 mins.

「你的应用是怎么跑起来的？」——Spring Boot 内嵌的 Tomcat 替你回答了这个问题的全部复杂度，但面试官问的就是这些被藏起来的细节：一个 HTTP 请求从网线到你的 Controller 经历了什么？为什么 Tomcat 要打破双亲委派？maxThreads/maxConnections/acceptCount 三个参数怎么配合？

本文按 「整体架构 → 线程模型 → 请求处理 → 类加载 → 调优排障」 五层讲透 Tomcat：每个概念配可运行验证 + Mermaid 图，读完你能在面试中画出请求旅程图，并在线上「Tomcat 线程打满/连接堆积」时知道先看什么。

1. 定位：Tomcat 在面试里的三个位置

面试问题 本质考点 本文章节
Tomcat 的架构？一个请求怎么走？ 连接器 + 容器两段式，IO 线程与业务线程分离 §2、§4
maxThreads / maxConnections / acceptCount 什么关系？ 连接缓冲深度与线程模型的配合 §3
Tomcat 为什么打破双亲委派？ 类加载器的隔离设计 §5

因果链主线：Tomcat 的全部设计都围绕一个矛盾——「Web 容器要同时服务很多请求（并发），但每个请求的 IO 很慢（网络）」。解法有两条：

  1. IO 线程只做读写不干活，业务线程池干活（连接器两段式）；
  2. 应用之间/应用与容器之间的类要隔离（WebappClassLoader）。

记住这两条，所有参数和机制都能推出来。

2. 整体架构：连接器 + 容器

2.1 两段式架构全景

IO 与业务彻底分离——这是 Tomcat 能扛高并发的架构根基。

2.2 容器分层：Engine → Host → Context → Wrapper

观察点：

3. 连接器：NIO 线程模型与三大参数

3.1 三个线程的职责分工

Tomcat NIO 连接器内部有 三类线程：

线程 职责 数量 阻塞点
Acceptor 只做 accept() 拿新连接 1 个（每端口） accept() 系统调用
Poller NIO Selector 多路复用，检测 socket 可读/可写 1-2 个（每端口） selector.select()
Worker 线程池 解析请求、执行业务 maxThreads（默认 200） 业务代码（用户逻辑）

因果链：

  • NIO 模型下「一个 Poller 线程服务几千个连接」（Selector 多路复用）；
  • 所以 maxThreads 是「同时处理的请求数」，不是「连接数上限」；
  • 连接可以有几万个，同时干活的最多 200 个，其余在队列等待。

3.2 一次请求在连接器中的完整生命周期

把上面的三类线程串起来，一个请求从到达 socket 到进入业务代码，经历的完整步骤：

sequenceDiagram
    participant C as Client
    participant OS as 内核 TCP 队列
    participant A as Acceptor
    participant P as Poller
    participant W as Worker 线程
    participant S as Servlet

    C->>OS: 三次握手，连接建立
    Note over OS: 连接进入 accept 队列<br/>（acceptCount 控制长度）
    A->>OS: accept() 取连接
    A->>P: 注册 SocketChannel 到 Poller
    Note over P: Selector 轮询<br/>等待可读事件
    C->>P: 发送 HTTP 请求数据
    P->>P: select() 返回可读
    P->>W: 提交 SocketProcessor 到线程池
    Note over W: 从队列取任务<br/>若队列满 → 拒绝
    W->>W: 解析 HTTP 协议<br/>生成 Request/Response
    W->>S: 调用 service()
    S->>S: 执行业务逻辑
    S-->>W: 返回响应
    W-->>C: 写回 socket

关键理解：

  1. Acceptor 只负责 accept()，不做任何 IO 读写；
  2. Poller 用 Selector 管理成千上万个连接，只检测「谁就绪了」；
  3. Worker 从线程池取任务，才真正解析协议 + 执行业务。

这就是「IO 与业务分离」的落地方式。

3.3 maxThreads / maxConnections / acceptCount 三参数详解

参数 含义 默认值 超了会怎样
acceptCount TCP accept 队列长度（OS 层 backlog） 100 队列满 → connection refused（直接拒绝新连接）
maxConnections 连接器保持的最大连接数（含等待中的） 10000（NIO） 满了不再 accept，连接在 accept 队列排队
maxThreads 工作线程池上限，同时处理的请求数 200 线程全忙 → 新请求在等待队列（内部队列）排队

更细的补充：

  • acceptCount 是 OS 层参数：本质是 listen(fd, backlog) 的 backlog，Linux 下会被 net.core.somaxconn 截断；
  • maxConnections 是 Tomcat 层参数：达到上限后，Tomcat 不再从 OS 队列里 accept，新连接积压在 OS 队列；
  • maxThreads 是业务层参数：线程全忙时，请求进入 Tomcat 内部的 TaskQueue（默认无界）排队——无界队列意味着不会拒绝，只会越堆越多直到超时。

3.4 三级缓冲的排队模型

这是面试必画图——三个参数构成 三级缓冲，从外到内依次是：

    New[新连接到达] --> Q1{OS accept 队列<br/>长度 = acceptCount<br/>默认 100}
    Q1 -->|队列满| R1[connection refused<br/>客户端收到 RST]
    Q1 -->|有空位| Q2{Tomcat 连接数<br/>< maxConnections?<br/>默认 10000}

因果链：三参数是三级缓冲：

  • maxThreads 管「同时干活的」（最内层）；
  • maxConnections 管「连接能堆多少」（中间层）；
  • acceptCount 管「拒绝前的最后缓冲」（最外层）。

压测时先触达哪个，取决于负载形态：

负载形态 先触达 现象
请求密集但执行快 maxThreads 内部队列堆积，响应变慢
连接数暴涨（慢客户端多） maxConnections 新连接不 accept，OS 队列堆积
洪峰涌入 acceptCount connection refused

3.5 动手验证：压测观察三参数排队

观察点：

  • jstack 里 http-nio-8080-exec-N 线程数变化；

4.2 Servlet 三段生命周期

阶段 时机 说明
init 首次请求或启动时 只执行一次，做初始化

    [*] --> 未初始化
    未初始化 --> 初始化中: 首次请求 / load-on-startup

    就绪 --> 服务中: service() 被调用

    note right of 服务中
        单实例，多线程并发
        service() 被线程池调用
        实例字段 = 共享状态
    end note

因果链（面试高频）：Servlet 是 单实例多线程——一个 Servlet 实例被所有请求共享，实例变量必须线程安全。

面试答「为什么 Controller 不该有实例变量」：

「单实例多线程 + 线程池并发调用，实例字段就是竞态源。」

常见误区：

  • ❌ @Service 里加 int count = 0; → 线程不安全；
  • ✅ 用 ThreadLocal 或者无状态设计；
  • ✅ 需要状态就用外部存储（Redis/DB）。

4.3 动手验证：看 Servlet 实例与线程

观察点：

  • instance= 每次一样 → 单实例；
  • thread= 每次不同 → 线程池并发。

判定标准：亲眼确认「Servlet 实例只有一个、线程是池里随便抽的」，理解实例变量的危险性。

5. 类加载：为什么打破双亲委派

5.1 双亲委派机制回顾

JVM 默认的类加载器层次（自顶向下）：

flowchart TB
    App[Application ClassLoader<br/>AppClassLoader<br/>加载 classpath]
    Ext[Extension ClassLoader<br/>ExtClassLoader<br/>加载 java.ext.dirs]
    Boot[Bootstrap ClassLoader<br/>C++ 实现<br/>加载 rt.jar / java.base]

    App -->|父| Ext
    Ext -->|父| Boot

双亲委派规则：收到类加载请求时，先委托父加载器加载，父加载器加载不了才自己加载。

flowchart TB
    Start[需要加载 com.example.Foo] --> C1[AppClassLoader]
    C1 -->|委托| C2[ExtClassLoader]
    C2 -->|委托| C3[Bootstrap]
    C3 -->|找不到| C2
    C2 -->|找不到| C1
    C1 -->|自己找 classpath| Result[加载成功]

    style Start fill:#e6f0ff
    style Result fill:#e6ffe6

目的：保证核心类不被篡改（java.lang.String 永远由 Bootstrap 加载）。

5.2 Tomcat 的 WebappClassLoader 如何打破

Tomcat 的 WebappClassLoader 对 Web 应用类目录中的类，先自己找，找不到再委派父加载器：

flowchart TB
    Start[需要加载 com.example.Foo] --> Check{是否 JVM 核心类?<br/>java.* / javax.*}
    Check -->|是| Delegate1[委派给父加载器<br/>Bootstrap/Ext]
    Check -->|否| Check2{是否 Tomcat 容器类?<br/>org.apache.catalina.*}
    Check2 -->|是| Delegate2[委派给 Common ClassLoader]
    Check2 -->|否| Local[从 WEB-INF/classes<br/>WEB-INF/lib 自己加载]
    Local -->|找不到| Delegate3[再委派父加载器]
    Delegate1 --> End[加载完成]
    Delegate2 --> End
    Delegate3 --> End

    style Local fill:#e6ffe6
    style Check fill:#ffe6e6
    style Check2 fill:#ffe6e6

为什么这样设计？两个核心原因：

理由 场景 双亲委派的问题
应用类隔离 同一 Tomcat 部署两个应用，各自带不同版本的 Spring 双亲委派会让先加载的版本被所有应用共享，版本冲突
热部署 应用重新部署时旧类加载器整体作废换新的 双亲委派下父加载器会缓存类，无法替换

边界（面试要答全）：

  • 对应用类（WEB-INF/classes、WEB-INF/lib）：先自己加载；
  • 对 javax.servlet.* 等 Servlet 规范类：仍然委派（容器自身规范类不能重载）；
  • 对 java.* 等 JVM 核心类：仍然委派 Bootstrap。

完整答案：『打破双亲委派有两个原因——多应用类隔离 + 热部署；但规范类与核心类仍走委派』，两个原因 + 边界都说全才是完整答案。

5.4 热部署与类加载器泄漏

热部署的原理：应用重新部署时，Tomcat 会丢弃旧的 WebappClassLoader 整个实例，创建新的加载器重新加载类。

sequenceDiagram
    participant Admin as 管理员
    participant Tomcat as Tomcat
    participant Old as 旧 WebappClassLoader
    participant New as 新 WebappClassLoader
    participant App as 应用

    Admin->>Tomcat: 重新部署 /app
    Tomcat->>Old: 停止所有 Servlet
    Tomcat->>Old: destroy() 释放资源
    Tomcat->>Old: 丢弃引用，等待 GC
    Note over Old: 如果无外部引用<br/>GC 会回收整个加载器<br/>连带所有类
    Tomcat->>New: 创建新 WebappClassLoader
    New->>App: 重新加载所有类
    App-->>Admin: 部署完成

类加载器泄漏：如果应用里有线程/ThreadLocal/静态变量持有 WebappClassLoader 的引用，旧加载器无法被 GC，导致 Metaspace OOM。

常见泄漏源：

  • ThreadLocal 未清理，且线程是 Tomcat 线程池的；
  • DriverManager 注册的 JDBC 驱动（Tomcat 会警告）；
  • 定时器线程未停止；
  • 自定义 ClassLoader 未释放。

排查方式：jmap -clstats <pid> 看类加载器数量，或 jcmd <pid> GC.class_stats。

短链系统设计：从方法论到落地

Posted on 2026-08-13 In 系统设计 Word count in article: 3.3k Reading time ≈ 12 mins.

「设计一个短链系统」是系统设计题的常青树——它看着简单（不就是个映射吗），但面试官真正在考的是三件事：长 URL 怎么变成 7 位短码（发号与进制转换）、短码怎么存（分表 + 缓存分层）、跳转用 301 还是 302（状态码背后的业务意图）。 秒杀篇讲的是「写」场景（削峰、防超卖），短链篇讲的是「读」场景（缓存、布隆、热点）——两篇合起来，方法论的两个极端就都有了。读完你能在面试现场把这道题从头推到尾，并且说清每个选择的理由。

联动：本文是 系统设计方法论（需求澄清/容量估算/评估权衡）的第二个完整案例；与 秒杀系统设计（写场景）对照形成读写双案例；缓存分层与布隆过滤器复用 Redis 深度解析；发号器与分表复用 MySQL 高可用与分库分表实战、分布式系统核心理论（分布式 ID）。

1. 定位：这道题考什么

短链系统的需求一句话：输入任意长 URL，输出 7 位短码；访问短链时重定向到原长 URL（如 t.cn/Ab3dE9 → 长链接）。

它为什么高频：短链表面是「字符串映射」，实际覆盖了系统设计的读路径全部考点——容量估算、哈希与冲突、发号器、分库分表、缓存分层、布隆过滤器、热点防护、301/302 语义。一题考完「读场景」所有基本功，这是它和秒杀（写场景）互补的原因。

场景类型 写密集（下单） 读密集（跳转）

3. 核心机制一：短码生成——发号器 + 62 进制

3.1 为什么不用 MD5 截断

方案 问题
MD5 长 URL 截 7 位 哈希冲突概率随数据量上升，冲突要重算（循环）
随机短码 碰撞检测麻烦，每次生成要查重
发号器 + 62 进制 无冲突（号唯一）、可预测、可支持批量

短码 = 发号器拿到的自增 ID，转成 62 进制：ID=1 → "1"，ID=1000000 → "4c92"……7 位最多 62^7≈3.5 万亿个短码，用不完。

3.2 发号器三方案（面试核心）

方案 机制 优缺点
Redis INCR 单 key 自增 简单；Redis 挂影响发号，可持久化兜底
DB 号段（segment） 每次取一批号（如 1 万），内存发完再取 无网络往返、DB 压力小，生产主流
雪花算法 时间戳+机器号+序列号 无序、不可预测；但短码要「短」反而用它少见

因果链：发号器选型的关键是「发号频率 = 写入频率 = 日增 1000 万」——每次取号都打 Redis/DB 会打死存储，号段模式把「1 万次取号」合并成「1 次 DB 查询」（与 MQ 批量消费同一个思想：批量换吞吐）。面试答发号器：「DB 号段 + 内存发号」是标准答案，补一句『发号是写路径唯一瓶颈，所以必须批量』就是完整逻辑。

3.3 动手验证：号段发号的最小实现

观察点：前 1 万次调用只触发 1 次 DB 更新（UPDATE ... + 10000），之后全部内存返回。判定标准：能说出「DB 压力 = 日增 1000 万 ÷ 号段 1 万 = 每天 1000 次写」——发号从「每秒 115 次」降到「每天 1000 次」，这就是号段的威力。

4. 核心机制二：存储与读取——分表 + 缓存分层

4.1 存储设计

层 方案 理由
主表 MySQL，按短码 hash 分 64 表（short_url_0 ~ short_url_63） 10 年 365 亿条，单表 ~5.7 亿超阈值
路由 hash(short_code) % 64（或按 ID 段路由） 短码定表，读路径直查
冗余 主从 + 读写分离 读多写少，从库扛查询
索引 短码唯一索引 跳转按短码精确查

为什么分 64 表而不是 4 表：10 年数据量 × 单表 5.7 亿超红线（MySQL 单表 5000 万经验线）——分表数 = 总量 ÷ 单表容量，先把十年算完再定（细节见 MySQL 高可用与分库分表实战）。

4.2 缓存分层与布隆过滤器

flowchart LR
    C["客户端"] -->|短链访问 2W QPS| NG["网关/本地缓存<br/>(Caffeine, 毫秒级)"]
    NG -->|未命中| R["Redis 缓存<br/>(命中率 ~95%)"]
    R -->|未命中| BF{布隆过滤器<br/>短码存在?}
    BF -->|不存在| E["直接返回 404<br/>(拦掉无效短码)"]
    BF -->|可能存在| DB[("MySQL 分表")]
    DB -->|回填| R
    R -->|回填| NG

因果链（这一层是全题精华）：缓存未命中的请求会打到 DB——但无效短码（用户乱拼的）每次都不存在，会绕开缓存直接打 DB（缓存穿透），2 万 QPS 里若有 10% 无效请求，DB 每秒要扛 2000 次无效查询 → 布隆过滤器在 DB 前拦一层：不存在直接 404，存在才放行。布隆的代价是「可能误判存在」但不误判不存在——宁放行一次空查，不放过一次真查（布隆过滤器原理与实现见 Redis 深度解析）。

4.3 动手验证：布隆拦截无效短码

观察点：无效短码在布隆层即被拦，DB 零压力；写入短链时 BF.ADD 与 DB 同步（失败可容忍——误判只是多查一次）。判定标准：能说出布隆过滤器的取舍——「不存在的必拦，存在的可能漏拦（误判），所以它只防穿透、不防击穿」。

5. 核心机制三：301 vs 302 与热点防护

5.1 301 还是 302（面试高频追问）

状态码 语义 对短链的影响
301 永久重定向 浏览器/客户端缓存跳转结果，下次直接访问长链——后续请求不经过我们，但无法统计点击量、无法修改跳转目标
302 临时重定向 每次访问都先打我们的服务——可以统计、可以改目标，但服务压力大

面试标准答案：选 302——短链是营销/内容运营工具，点击统计和可修改性是产品刚需，牺牲一点服务压力换这两个能力。因果链：301 把控制权交给了客户端缓存，302 把每次访问留在自己手里——「要数据就要 302」。

5.2 热点短链防护

短链符合「二八定律」：20% 的短链扛 80% 的点击（爆款链接）。防护层次：

层 手段
本地缓存 Caffeine 短 TTL（秒级），挡住大部分热点
Redis 热点 key 天然被缓存吸收；单 key 打爆加本地缓存兜底
热点识别 计数器识别 topN 热点 → 加大本地缓存 TTL
限流 网关限流保护后端（见 秒杀篇 的限流章节）

因果链：读场景的雪崩风险是「热点 key 过期瞬间，大量请求同时打到 DB」——本地缓存（Caffeine）是第一层盾：Redis 挂了热点还在本地挡着。面试答「读场景高可用」的标准句式：「多级缓存 + 热点识别 + 网关限流」。

7.1 完整话术

面试题 回答要点

消息队列选型与核心机制对比

Posted on 2026-08-13 In 中间件 Word count in article: 3k Reading time ≈ 11 mins.

「Kafka、RocketMQ、RabbitMQ 到底选哪个？」——这个问题答不好，是因为顺序搞反了：选型不是选名字，是选「机制」与「场景」的匹配。 本文先讲透四个核心机制（消息不丢、幂等、顺序、事务消息），再给一张决策树把选型变成套公式：吞吐要多大、延迟要多低、要不要事务消息、团队熟哪个生态。读完你不仅能答「三选一」，还能说清「为什么 Kafka 扛不住强顺序事务、为什么 RabbitMQ 到不了百万级吞吐」——这两个「为什么」才是面试的区分点。

联动：本文是 Kafka 原理与实践、RocketMQ 原理与实践 的选型总纲；事务消息与 分布式事务：从 2PC 到 Seata 的本地消息表同源；削峰场景见 秒杀系统设计（MQ 是削峰三件套之一）。

1. 定位：MQ 解决什么问题

问题 用 MQ 怎么解 例子
解耦 下游系统随时加/减，上游无感知 订单系统发消息，短信/积分/搜索各自订阅
削峰 请求先进队列，下游按自己的速率消费 秒杀 10 万 QPS 进队列，落库 1 万 QPS
异步 非核心路径不等响应 下单后异步发通知，响应从 500ms → 50ms

因果链：MQ 的本质是「缓冲 + 订阅发布」——缓冲解决削峰（生产者快、消费者慢，中间用队列吸收），订阅发布解决解耦（上游只对 topic 说话，不知道下游是谁）。面试先答这三个价值，再答选型，顺序不能反。

选型的真正前提：先懂「机制」，再谈「选型」——不知道「不丢消息」靠什么机制保证，选型就是背参数。本文 §2-§5 讲机制，§6 给决策。

2. 三巨头画像：存储模型决定一切

三个 MQ 的一切差异，根源是「消息存哪、怎么组织」：

维度 Kafka RocketMQ RabbitMQ
存储模型 分区（Partition）追加日志，顺序写磁盘 CommitLog 顺序写，消费队列是索引 队列内存/磁盘，按交换机路由
吞吐 百万级（顺序写 + 零拷贝） 十万级 万级（单机受队列数限制）
延迟 毫秒~秒级（批量攒批） 毫秒级 微秒~毫秒级（无攒批）
消息顺序 分区内有序（全局需单分区） 队列内有序 单队列有序
事务消息 不支持（2.5+ 有试验版） 原生支持（半消息+回查） 弱（插件）
延迟消息 不支持 原生支持（定时层级） 原生支持
生态 日志/流处理最强（Flink 对接） 阿里系电商场景 AMQP 标准、轻量场景

记忆锚点一句话：

  • Kafka = 日志系统：顺序写盘 + 批量 = 吞吐之王，但「批量」就是「延迟」的代价，且不支持事务消息；
  • RocketMQ = 电商系统：为交易场景设计，事务消息、延迟消息、队列有序是原生能力；
  • RabbitMQ = 消息总线：AMQP 路由灵活、延迟低，但单机吞吐是万级，集群能力弱。

面试话术：先一句话定义「存储模型决定吞吐与能力边界」，再展开三行对比——「Kafka 分区追加日志所以快，RocketMQ commitlog 所以快且能做事务，RabbitMQ 队列路由所以灵活但慢」。

3. 核心机制一：消息不丢——三端各守一段

「不丢消息」是三个环节的接力，任何一端漏守都会丢：

flowchart LR
    P["生产者<br/>ack 机制"] --> B["Broker<br/>持久化"] --> C["消费者<br/>手动 ack"]
环节 丢法 守法 代价
生产者→Broker 发送失败/异步发送丢失 ack 语义：Kafka acks=all、RocketMQ SYNC_MASTER 吞吐下降（等确认）
Broker 存储 机器重启 持久化：Kafka 多副本 ISR 同步、RocketMQ 主从同步刷盘 副本写入开销
Broker→消费者 自动 ack 后消费失败 手动 ack：处理成功才提交 offset 可能重复消费（换来不丢）

因果链核心：不丢与不重是跷跷板——「处理成功才 ack」保证不丢，但处理中崩溃 → 消息会被重新投递 → 重复消费。结论：MQ 的默认语义是 at-least-once（至少一次），「不丢」靠 ack 守，重复靠消费端幂等兜（§4）。面试答「怎么不丢消息」必须说全三端 + 一句「代价是可能重复，所以要有幂等」。

4. 核心机制二：重复消费与幂等三法

重复消费是 at-least-once 的必然产物，消费端必须幂等——三法：

幂等法 原理 适用
唯一键去重 消息带业务唯一 ID，消费时查/写去重表（唯一索引） 通用首选
数据库约束 幂等字段建唯一索引，重复插入直接报错被吞 落库类消费
状态机/版本号 处理前校验状态，已处理则跳过 订单状态流转类

动手验证：用唯一索引做幂等

观察点：同一消息投递两次，第二次 INSERT 主键冲突被捕获后直接 return。判定标准：理解「幂等是消费端职责，不是 MQ 职责」——MQ 只保证 at-least-once，Exactly-once 需要端到端幂等设计。

5. 核心机制三：顺序消息与事务消息

5.1 顺序消息：分区/队列内有序

场景 做法 代价
全局有序 单分区/单队列（吞吐降到单机） 吞吐损失大，极少用
分区有序 同一业务 key 哈希到同一分区（如订单号 → 分区） 按 key 有序，跨 key 无序
有序保证 Kafka：同 key 同分区 + 单消费者线程；RocketMQ：同 key 同队列 消费端也必须单线程

因果链：顺序消息 = 「路由同 key 到同分区」+「消费端串行处理」两步缺一不可——只路由不串行（多线程消费）顺序照样乱。面试陷阱：很多人只答「同 key 同分区」，漏了「消费端单线程」，主动补上这句是加分。

5.2 事务消息：半消息 + 回查

事务消息 = 本地事务 + 消息发送的原子性（与 本地消息表 同思路，但不用业务自己建表）：

sequenceDiagram
    participant P as 生产者
    participant MQ as MQ
    participant DB as 业务库
    P->>MQ: 1. 发送半消息（对消费者不可见）
    P->>DB: 2. 执行本地事务（写订单）
    P->>MQ: 3. 提交/回滚半消息
    MQ-->>P: 4a. 提交 → 消费者可见
    Note over MQ: 4b. 生产者挂了/超时 → MQ 回查本地事务结果
    MQ-->>P: 回查（询问本地事务成功没）

因果链：「先发半消息、后提交」把「发消息」和「业务写」变成可对齐的两步——半消息对消费者不可见，只有本地事务成功后提交才可见；生产者中途挂掉，MQ 通过回查接口（checkLocalTransaction）确认事务结果。这一机制让 RocketMQ 在「有 MQ 的强一致场景」胜出（分布式事务选型 的决策树里「有 MQ 且能最终一致」指向它）。

分布式事务：从 2PC 到 Seata

Posted on 2026-08-13 In 分布式 Word count in article: 3.9k Reading time ≈ 14 mins.

「一个订单要扣库存、减余额、记流水，三个服务各有一个数据库，怎么保证要么全成要么全不成？」 单库事务到此失效——这不是代码问题，是「跨系统无原子性」的架构问题。本文从 2PC 的起源讲到 Seata 的落地：为什么教科书级的 XA 没人敢生产用、TCC 为什么是「业务自己写三阶段」、Saga 为什么是「一条补偿链」、以及 Seata AT 模式怎么用「全局锁 + undo 日志」做到业务零侵入。读完你能在方案评审会上说清「这个场景该用 Seata 的哪种模式、为什么」。

联动：本文是 分布式系统核心理论（CAP/BASE/一致性模型）的落地篇；事务消息方案与 ES 查询优化与实战 的本地消息表、RocketMQ 原理与实践 的事务消息同源；Seata 全局锁与 MySQL 事务原理与实践 的锁语义直接相关。

1. 定位：为什么需要分布式事务

单库事务失效的场景：微服务拆分后，「一次业务操作」跨多个服务、多个数据库，每个库自己的事务管不到别的库——「扣库存成功、减余额失败」就成了可能。

术语 一句话定义
本地事务 单个数据库内的事务（ACID）
分布式事务 跨多个数据库/服务，保证「全成或全不成」的事务
全局事务 分布式事务的总称，与「分支事务」相对
分支事务 各参与者的本地事务
协调者 统筹全局事务提交/回滚的角色

核心矛盾一句话：分布式事务的本质是「在无单点权威的分布式系统里，模拟一个全局的原子性」——但 CAP 定理说可用性、一致性、分区容错只能三选二，任何分布式事务方案都是在「牺牲一部分可用性/性能」换「全局一致」。记住这条，所有方案的取舍都能自己推出来（理论细节见 分布式系统核心理论）。

2. 2PC：两阶段提交的由来与代价

2.1 两阶段：准备 + 提交

sequenceDiagram
    participant C as 协调者
    participant A as 服务A(扣库存)
    participant B as 服务B(减余额)
    C->>A: 1. Prepare：能提交吗？
    C->>B: 1. Prepare：能提交吗？
    A-->>C: 2a. 可以（资源已锁）
    B-->>C: 2b. 可以（资源已锁）
    C->>A: 3. Commit / Rollback
    C->>B: 3. Commit / Rollback

阶段一 Prepare：协调者问每个参与者「能提交吗」，参与者执行本地事务但不提交，资源加锁，回复「可以」或「不行」。阶段二 Commit：全票通过 → 广播 Commit；有人拒绝或超时 → 广播 Rollback。

因果链：2PC 用「先锁定资源、后统一提交」实现原子性——但「锁定」是全部代价的来源：Prepare 阶段开始，所有参与者的资源一直锁着，直到阶段二结束，锁的时长 = 最慢参与者的响应时间，这就是「2PC 阻塞性」的根源。

2.2 三个致命问题（面试核心）

问题 场景 后果
阻塞 某参与者慢/挂 所有参与者资源一直锁着，拖垮全局吞吐
单点 协调者挂了 参与者不知提交还是回滚，永远等（无超时自决）
脑裂风险 阶段二网络分区 部分 Commit、部分回滚不了，数据不一致

面试必答话术：2PC（XA）是教科书方案，但三个问题让它生产上没人敢直接用——「阻塞 + 单点 + 脑裂」，本质是「把单点权威（协调者）引入分布式系统，权威自己却不可靠」。XA 协议（数据库原生支持）是 2PC 的标准实现，但因为上述原因，互联网公司几乎不用 XA，改用下面「业务化的 2PC」。

3. 3PC：多一轮预提交，解决了一半

3.1 三阶段：CanCommit → PreCommit → DoCommit

flowchart LR
    A["CanCommit<br/>先问可行性<br/>（无锁）"] --> B["PreCommit<br/>锁定资源<br/>（有超时）"] --> C["DoCommit<br/>统一提交"]

3PC 把阶段一拆成两步：

阶段 动作 与 2PC 的差异
CanCommit 问「能不能提交」（不动资源） 提前排除不可行者，缩短锁定窗口
PreCommit 锁定资源、写日志 参与者多了超时自决能力
DoCommit 提交 参与者超时后可自行提交（默认提交）

3.2 解决了什么、没解决什么

解决：参与者有超时自决机制（协调者失联超时后默认提交），缓解了协调者单点导致的无限阻塞。

没解决：超时默认提交引入新风险——协调者其实要回滚，但参与者已经提交了（网络分区下的两难：等=永远阻塞，自决=可能错）。因果链：3PC 用「减少等待」换「增加出错概率」，所以实际使用比 2PC 还少。记住结论即可：3PC 是学术改进，工程上几乎无人用，面试提到「知道它存在、知道它为什么没人用」就够了。

4. TCC：业务自己写三阶段

4.1 Try / Confirm / Cancel

TCC 是「业务化的 2PC」：不依赖数据库锁，让业务接口自己实现三个动作：

阶段 接口 业务示例（余额服务）
Try 预留资源 冻结 100 元（frozen=100，可用余额不变）
Confirm 确认提交 扣减：冻结-100，可用余额-100
Cancel 取消回滚 解冻：冻结-100，可用余额不变 
flowchart TD
    S[发起方] --> T[Try 全部成功] --> C[Confirm 全部执行] --> D[事务成功]
    T -->|任一 Try 失败| X[Cancel 全部执行] --> E[事务回滚]

4.2 TCC 的三道坎（面试深水区）

坎 问题 解法
空回滚 网络重试导致 Try 没到、Cancel 先到 Cancel 幂等 + 记录事务状态
悬挂 Try 迟到（Cancel 已完成后又来 Try） 状态机校验：已 Cancel 的事务拒绝再 Try
幂等 Confirm/Cancel 被重试执行多次 接口幂等（状态字段/版本号）

因果链：TCC 把「锁」从数据库换成了「业务预留」，不阻塞数据库、并发能力强——但代价是业务要自己写三个接口、处理空回滚/悬挂/幂等三道坎。适用场景：强一致要求高、并发大的资金类操作（账户冻结/库存预留）。面试加分点：主动说出「TCC 的三个空回滚场景」而不是只说『Try Confirm Cancel 三阶段』。

5. Saga：一条补偿链

5.1 正向执行 + 反向补偿

Saga 的核心思想：不预留、不锁定，只管正向执行；哪一步失败，就把前面所有步骤「反向补偿」一遍：

flowchart LR
    S1[扣库存] --> S2[减余额] --> S3[记流水]
    S3 -->|失败| C2[补偿：余额+100] --> C1[补偿：库存+1]
维度 特点
无锁 每步直接提交本地事务，不锁定资源
补偿 反向执行取消操作（库存加回、余额退回）
编排 两种：编排式（中心化一个 Saga 引擎指挥）/ 协同式（每个服务监听事件自己接下一棒）
一致性 最终一致（中间状态对别的事务可见）

5.2 与 TCC 的分工（面试必考）

对比 TCC Saga
预留 有（Try 冻结） 无（直接提交）
一致性窗口 短（Try→Confirm 之间） 长（全程都可能被看到中间态）
适用 强一致 + 高并发（资金） 弱一致可接受 + 长流程（订单/旅行预订）
补偿方式 Cancel 恢复预留 反向业务操作

一句话分工：TCC 适合「必须强一致但并发又高」的短操作；Saga 适合「可以最终一致」的长流程。资金用 TCC，订单/活动用 Saga——面试被问「TCC 和 Saga 怎么选」，先问一句「业务能接受最终一致吗」，答案自然出来。

6. Seata AT：全局锁 + undo 日志的「无侵入」方案

6.1 AT 模式的两件武器

AT（Auto Transaction）模式 = 自动化的 2PC：业务代码几乎不用改（只加 @GlobalTransactional），Seata 用两个机制替你完成全局原子性：

武器一：undo_log 快照。每个分支事务执行前，Seata 拦截 SQL，把「改动前的数据镜像」写入 undo_log 表；全局回滚时用镜像反向执行 UPDATE/DELETE 把数据改回去——相当于自动生成 Cancel。

武器二：全局锁。事务执行期间，Seata 锁定被改动的主键记录，其他全局事务改到同一记录必须等待，防止两个事务互相覆盖导致回滚错乱。

sequenceDiagram
    participant A as 业务应用
    participant TC as TC(全局事务协调)
    participant RM as RM(分支1: 订单库)
    participant RM2 as RM(分支2: 库存库)
    A->>TC: 1. 开启全局事务（XID）
    A->>RM: 2. 分支注册 + 执行 SQL + 写 undo_log
    A->>RM2: 3. 分支注册 + 执行 SQL + 写 undo_log
    A->>TC: 4. 提交全局事务
    TC->>RM: 5. 删 undo_log，提交
    TC->>RM2: 5. 删 undo_log，提交
    Note over TC: 任一步失败 → 各分支按 undo_log 反向执行回滚

6.2 AT 与 TCC 的对比（生产选型核心）

维度 Seata AT TCC
业务改造 零侵入（注解 + 建 undo_log 表） 手写 Try/Confirm/Cancel 三接口
锁粒度 行级（改哪锁哪） 业务预留（可按资源冻结）
性能 有 undo_log 写入开销 无日志开销，纯业务
场景 通用（大部分业务） 资金强一致 + 高并发
侵入度 全局事务是「两阶段」，冲突时等待 无等待，但代码多

因果链：AT 用「undo_log 自动补偿 + 全局锁防冲突」模拟出 2PC 的效果，把复杂度从业务代码搬进了中间件——这就是它成为生产主流的根本原因。代价是全局锁的等待开销：长事务会拖慢并发，所以 AT 也要求分支事务「短」。

6.3 动手验证：本地跑一个 Seata 最小闭环

观察点：@GlobalTransactional 方法内两个库的写操作，在第二个库抛异常时第一个库的写入被自动回滚（undo_log 反向执行）。判定标准：亲手验证「库存减了但订单插入失败 → 库存被回滚」的完整闭环，理解「业务零侵入」的真实含义。

7. 方案选型：一张决策树

7.1 决策流程

flowchart TD
    Q1{业务能接受最终一致吗？} -->|能| Q2{有现成 MQ 吗？}
    Q2 -->|有| MQ[事务消息/本地消息表<br/>推荐：最简单]
    Q2 -->|无| SAGA[Saga 补偿链]
    Q1 -->|不能，要强一致| Q3{事务短且并发高？}
    Q3 -->|是| TCC[Seata AT / TCC<br/>按侵入度选]
    Q3 -->|否| AT[Seata AT<br/>通用首选]

7.2 决策表

业务特征 首选方案 理由
弱一致可接受 + 有 MQ 事务消息/本地消息表 最简单、无中间件依赖（RocketMQ 事务消息）
弱一致 + 长流程 Saga 无锁、适合订单/旅行
强一致 + 通用业务 Seata AT 零侵入、行级锁
强一致 + 极高并发资金 TCC（或 AT + 短事务） 业务预留不阻塞库
同库多表 本地事务 别引分布式事务（最常见优化）

一句话选型：「能最终一致就消息，必须强一致就 Seata；Seata 里短事务用 AT、资金类用 TCC」。另外记住反模式：能在一个库里解决的（同库多表）绝不上分布式事务——很多「分布式事务」其实是表设计/服务拆分问题。

8. 面试应答：分布式事务六连问

8.1 完整话术

面试题 回答要点
2PC 是什么？ 准备+提交两阶段；先锁资源后统一提交；阻塞、协调者单点、脑裂三个问题，生产不用
XA 为什么没人用？ XA 是 2PC 标准实现，数据库锁资源时长=最慢参与者，互联网高并发场景扛不住
TCC 三阶段？ Try 预留 → Confirm 确认 → Cancel 回滚；注意空回滚/悬挂/幂等三道坎
TCC 和 Saga 区别？ TCC 预留锁、强一致、短操作；Saga 无锁直接提交、最终一致、长流程补偿链
Seata AT 原理？ undo_log 快照反向回滚 + 全局锁防冲突；业务零侵入（注解+建表）
怎么选型？ 能最终一致→消息；必须强一致→Seata（AT/TCC 按并发与侵入度）

8.2 深挖：与本地消息表/事务消息的对照（跨篇联动）

维度 2PC/Seata 本地消息表 事务消息（RocketMQ）
一致性强度 强一致（有锁/快照） 最终一致 最终一致
业务侵入 注解（AT）/ 三接口（TCC） 写一张消息表 一个事务消息接口
消息可靠性 无消息 消息与业务同事务 MQ 半消息+回查
适用 强一致场景 无 MQ 时的替代 有 MQ 时首选

因果链：本地消息表和事务消息的本质是「把『发消息』和『业务写』放进同一个本地事务」，用『消息一定会到』换『跨库强一致』（ES 查询优化与实战 的 Canal 同步用的就是这套思路）。面试答「消息最终一致」，能说出「消息表保证消息不丢 + 消费端幂等保证不重」两层，就是完整答案。

9. 总结

9.1 面试速答表

面试题 一句话答案
分布式事务是什么？ 跨多个库/服务保证「全成或全不成」，本质是无单点权威下模拟全局原子性
2PC 流程？ Prepare 锁定资源 → 全票通过 Commit / 任一拒绝 Rollback
2PC 三个问题？ 阻塞（锁时长=最慢者）、单点（协调者挂）、脑裂（分区后不一致）
3PC 改进了什么？ CanCommit 先问可行性 + 参与者超时自决；但自决可能提交错，工程无人用
TCC 三道坎？ 空回滚（Cancel 先到）、悬挂（Try 迟到）、幂等（重试）
Saga 是什么？ 无锁正向执行，失败逐级反向补偿；编排式/协同式
Seata AT 原理？ undo_log 快照自动反向回滚 + 全局锁防覆盖，业务零侵入
怎么选？ 最终一致→消息；强一致→Seata；资金高并发→TCC；同库→本地事务
