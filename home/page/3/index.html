伪共享与缓存行：一个 @Contended 的 4 倍差距

Posted on 2026-10-26 In Java Word count in article: 3.6k Reading time ≈ 13 mins.

两个线程改的是不同的变量，却因为「这两个变量恰好在同一缓存行」而互相拖慢。实测：相邻的两个 volatile long 字段，两个线程各改一个，耗时 8.60 ns/op；把字段用 @Contended 隔开，降到 1.98 ns/op——4.3 倍。

更有意思的是：类级 @Contended 完全没用（8.28 ns/op），因为它只隔离「对象之间」，不隔离「同一对象的字段之间」。这个坑很多人都踩过。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排 → ④ 伪共享与缓存行（本文） → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：③ 说「volatile 写贵在缓存行弹跳」，本文把这个成本量出来；⑤ 的 LongAdder 正是靠「分散到不同缓存行」打败 AtomicLong 的。

1. 伪共享是什么

缓存以缓存行（cache line）为单位在核之间同步。两个线程写的变量如果落在同一行里，即使逻辑上毫不相干，硬件也会让这一行在核之间来回「弹」——这就是伪共享（false sharing）。

flowchart LR
    subgraph LINE["One cache line (64 or 128 bytes)"]
        X["volatile long x<br/>thread 1 writes"] --- Y["volatile long y<br/>thread 2 writes"]
    end
    C1["Core 1"] -->|"exclusive access"| LINE
    C2["Core 2"] -->|"invalidates line,<br/>then takes it"| LINE
    LINE -.->|"ping-pong"| P["throughput drop"]
概念 含义
真共享 两个线程读写同一个变量，需要同步
伪共享 两个线程读写不同变量，但变量在同一缓存行
缓存行大小 常见 64 字节（x86），Apple Silicon 为 128 字节

2. 实测：五种写法的差距

测试方法：两个线程各做 2000 万次「volatile 读 + 写」，一个改 x、一个改 y，3 轮取最优。

写法 ns/op 相对
相邻字段（同一个对象） 8.60 1.0×
类级 @Contended 8.28 1.0×（没用）
手动 padding（中间塞 15 个 long = 120 字节） 3.20 2.7×
字段级 @Contended 1.98 4.3×
字段级 @Contended 但没加 -XX:-RestrictContended 9.54 1.0×（注解被忽略）

2.1 三个必须知道的结论

结论 证据
字段级 @Contended 有效 8.60 → 1.98（4.3×）
类级 @Contended 对「同对象多字段」无效 8.28，几乎等于相邻
不加 -XX:-RestrictContended 注解会被忽略 9.54，等于相邻

为什么类级无效：类级注解给整个对象前后加 padding，让这个对象不和别的对象共享缓存行；但 x 和 y 在对象内部仍然相邻，还是同一行。要解决「对象内字段争用」，必须给字段加注解。

**为什么必须加 -XX:-RestrictContended**：JDK 8 起 @Contended 默认只对 JDK 内部类生效（防止滥用），普通业务类要用就得显式关掉限制。

2.2 @Contended 不是免费的

代价 数值
每个字段多占 约 128 字节（两侧 padding）
100 万个对象 × 2 个字段 多占 256 MB
开启参数 -XX:-RestrictContended（JVM 启动参数，不能动态改）

判断标准：只有当这个字段确实被多线程高频写、且实测出 3 倍以上差距时，才值得付出这个内存代价。别在 DTO 上乱加。

4. 生产中的伪共享

4.1 四个高发场景

场景 为什么容易伪共享 处理
计数器数组（按线程分槽） 相邻槽在同一行 每个槽补 padding 或 @Contended
线程本地统计汇总 多线程写同一个对象的相邻字段 字段级 @Contended
RingBuffer（Disruptor） 生产/消费序号相邻 序列号各占一行
并发容器内部计数 size、modCount 等相邻 JDK 内部已有 padding（如 LongAdder.Cell）

4.2 Disruptor 的 padding 在防什么

目的：让 value 与 cursor 不在同一缓存行，避免生产者和消费者互相干扰。这和本文「手动 padding 120 字节 → 3.20 ns」是同一手法，只是 Disruptor 做得更彻底（两侧都补）。

4.3 什么时候该管伪共享

    B -- no --> C["ignore: noise"]
    B -- yes --> D{"measured >= 2x gap?"}

条件 判断
多线程高频写不同字段 值得查
写频率低于每秒千次 不用管（噪声）
单线程/只读 不用管
已经实测出 2 倍以上差距 必须处理

经验值：伪共享的代价在「写非常频繁」时才明显。本文 2000 万次写才把差距放大到 4.3 倍；每秒几百次的计数器，缓存行弹跳的成本完全淹没在业务逻辑里。

5. 动手验证：四个可复现实验

5.1 动手验证：相邻字段 vs 字段级 @Contended

预期观察点：加 -XX:-RestrictContended 时，@Contended 那行明显更快（本文 8.60 → 1.98）；不加参数时两行几乎一样。

判定标准：

  • 两行都很快（< 2 ns）→ 两个线程可能跑在同一个核上，或 JIT 把循环优化了；
  • @Contended 没效果 → 检查是否用了字段级注解（类级无效），以及参数是否加上。

5.2 动手验证：扫缓存行边界

预期观察点：存在一个「距离超过它就不再退化」的阈值，那个值就是你这台机器的有效边界。

判定标准：

  • 所有偏移都一样慢 → 你的测量被别的瓶颈主导（比如两个线程在同一核）；
  • 所有偏移都一样快 → 写频率不够，加迭代次数或换 volatile 写。

5.3 动手验证：类级 @Contended 的无效性

预期观察点：两者几乎一样（本文 8.60 vs 8.28），证明类级注解解决不了对象内字段的伪共享。

判定标准：

  • 类级明显更快 → 你的 JDK 版本/实现可能对类级注解做了字段级处理，换版本核对；
  • 两者都慢 → 正常，改用字段级注解再测。

5.4 动手验证：手动 padding 的效果

预期观察点：手动 padding 后明显变快（本文 8.60 → 3.20），但不如字段级 @Contended（1.98）。

判定标准：

  • padding 后没变快 → 缓存行可能更大（比如 128B 需要更多填充），加大到 31 个 long 再试；
  • padding 后比 @Contended 还快 → 你的 JDK 版本 @Contended 实现有额外开销。

6. 总结

6.1 面试速答表

怎么解决伪共享 填充（padding）或 @Contended（字段级）
@Contended 加在类上还是字段上 字段级；类级只隔离对象之间，不隔离对象内字段（本文实测 8.28 vs 1.98）

6.4 实操建议

  1. 先确认真的存在伪共享：两个线程各写各的字段，实测差距 2 倍以上再动手。
  2. @Contended 加在字段上，并确认启动了 -XX:-RestrictContended。
  3. **LongAdder 优先于 AtomicLong**（高并发计数场景），它内部已经处理了伪共享。
  4. 数组按线程分槽时，每槽留 8~16 个 long 的间隔，别用 arr[tid] 裸数组。
  5. 换硬件要重测边界——本文的 aarch64 结果就和「64 字节」的教科书结论不一致。

JMM：把「不可见」和「重排」亲手复现

Posted on 2026-10-25 In Java Word count in article: 3.6k Reading time ≈ 13 mins.

一个 boolean 就能让整个服务挂死，而且日志里什么都看不到。实测：把 stop 声明成普通字段，另一个线程把 stop = true 之后，读线程3 秒都没退出——JIT 把 stop 的读取提到了寄存器里，再也不去内存看。加上 volatile，同样的代码 500 毫秒内正常退出。

这篇逐个复现 JMM 的三个问题：可见性（复现了）、有序性（没复现，但要讲清为什么）、原子性（61.4% 的更新丢失）。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排（本文） → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：① 说「基准会被 JIT 优化」，本文用它复现可见性 bug；④ 会接着讲「volatile 背后的缓存行」；⑤ 用本文的「volatile++ 丢更新」引出 CAS。

1. 三个问题，一张表

问题 一句话定义 本文是否复现 典型后果
可见性 一个线程改了，另一个线程看不到 ✅ 复现（3 秒未退出） 死循环、优雅停机失效
有序性 指令重排导致执行顺序与代码不一致 ❌ 10 万轮未出现 DCL 半初始化、初始化顺序错乱

    B --> C["cache line in Modified state"]
    C --> D["Thread B reads x"]

核心认知：这三个问题都不是「代码写错了」，而是代码没有建立 happens-before 关系。JMM 只承诺：在 happens-before 关系成立的前提下，结果是对的。

2. 可见性：一个 boolean 就能让程序挂死

2.1 实测：普通字段 vs volatile

实测输出（JDK 21.0.12，aarch64，15 核）：

版本 结果 循环次数
普通字段 3 秒未退出（看门狗强制结束） —
volatile 0.5 秒内正常退出 1,998,494,873

为什么：JIT 编译后发现循环体里没有对 stopPlain 的写操作，于是把「读 stopPlain」提升到循环外（循环不变量提升），寄存器里的值永远是初始的 false。

2.2 深挖：这是 JIT 干的，不是 CPU

想确认是 JIT 而不是硬件缓存的问题，用解释模式跑一次：

运行模式 不加 volatile 原因
-Xint（解释） 会退出 每次循环都真的去读字段
默认（JIT） 不退出 读被提升到寄存器

这个对照很重要：它说明「可见性 bug 是编译期优化 + 硬件缓存共同造成的」，所以在测试环境跑不出来，不代表生产不会出。

2.3 正确的写法

写法 适用 说明
volatile 停止标志、状态位 每次读写都过内存，禁止重排
AtomicBoolean 停止标志 + 原子操作 比 volatile 多一层 CAS 封装
interrupt() 线程中断 JVM 内建机制，配合 isInterrupted()
锁 复合状态 顺带保证可见性

生产上更推荐 volatile + interrupt() 组合：标志位负责业务语义，interrupt 负责唤醒阻塞中的线程。

3.3 深挖：没复现 ≠ 不会发生

JMM 是规范，不是实现。规范明确允许 store 与后续 load 重排（这是 DCL 单例必须加 volatile 的根因）。

事实 结论
你在自己机器上跑 10 万轮没看到 只说明你的环境窗口窄
换了 ARM 服务器、换了 JVM 版本 窗口可能变大
依赖「跑一遍没问题」上线 就是在赌

所以正确姿势是「按 happens-before 写」，而不是「跑一遍没出问题就放心」。这一条也解释了为什么有些并发 bug 只在客户现场出现。

4. 原子性：volatile 救不了 i++

4.1 实测：4 线程丢 61.4%

写法 期望 实际 丢失
volatile int 自增 4,000,000 1,545,633 2,454,367（61.4%）
synchronized 自增 4,000,000 4,000,000 0

为什么：volCount++ 是「读 → 加 → 写」三步，volatile 只保证每一步的可见性与顺序，不保证这三步整体原子。两个线程可能同时读到 100，各自加 1 写回 101。

机制 保证什么 不保证什么
volatile 可见性、禁止重排、单个读/写原子 复合操作不原子
synchronized 互斥 + 可见性 性能开销
AtomicInteger 单变量复合操作原子 多变量组合不原子

5. volatile 的成本：1.56 ns/op

5.1 实测

操作 200,000,000 次耗时 折算
plain++ 2 ms 被 JIT 折叠成一次加法
volatile++ 312 ms 1.56 ns/op

读法：在无竞争的本地核上，一次 volatile 写约 1.56 ns；但真正的代价不在这 1.56 ns，而在竞争时——多个核同时写同一个 volatile 变量，缓存行会在核之间来回弹（④ 会量这个成本）。

5.2 happens-before 的六条规则（速查）

规则 内容
程序顺序 同一线程内，前面的操作 hb 后面的操作
volatile 对 volatile 变量的写 hb 后续对它的读
锁 解锁 hb 后续对同一把锁的加锁
线程启动 Thread.start() hb 新线程里的任何操作
线程终止 线程里的所有操作 hb 其他线程从 join() 返回
传递性 A hb B，B hb C ⇒ A hb C

用法：写并发代码时，逐条问「我依赖的读写之间，有哪条 hb 规则支撑？」答不上来就是 bug。

6. 动手验证：四个可复现实验

6.1 动手验证：复现可见性 bug

预期观察点：默认模式下 plain 版本 3 秒不退出；-Xint 模式下会退出；volatile 版本两种模式都正常退出。

判定标准：

  • 两种模式都不退出 → 说明不是 JIT 提升，而是别的问题（比如字段被别处写成 true）；
  • 默认模式也退出 → 你的 JVM 参数（如 -Xint、-XX:-TieredCompilation）影响了编译，换回默认再看。

6.2 动手验证：重排 litmus 测试

预期观察点：多数机器上 reorder=0（本文 aarch64 也是 0）。

判定标准：

  • reorder > 0 → 你的 CPU/JVM 真的重排了，这就是 DCL 必须加 volatile 的实证；
  • reorder = 0 → 正常，不代表安全（见 3.3）。

6.3 动手验证：volatile 的丢更新

预期观察点：volatile++ 丢失几十个百分点（本文 61.4%），synchronized++ 精确等于期望值。

判定标准：

  • volatile++ 没丢 → 线程数太少或临界区太快，加线程到 8/16 再试；
  • synchronized++ 也丢 → 你的 JVM 跑在 -Xint 之外的特殊模式，或代码里其实没加锁。

6.4 动手验证：量 volatile 的写成本

预期观察点：plain 被 JIT 折叠到几毫秒，volatile 是几百毫秒（本文 312 ms，1.56 ns/op）。

判定标准：

  • 两者都接近 0 → 循环被整体消除，把结果写进 volatile 字段再测；
  • volatile 超过 10 ns/op → 有其它线程在竞争这个变量，或 JIT 没编译热路径。

1. 并发的成本只有三个变量

1.1 一句话定义

一个并发问题，永远落在三件事上：共享的可变状态（要不要同步）、线程的调度（切换多少钱）、内存的可见性（写得对不对）。所有优化也都是这三个方向：减少共享、减少切换、减少等待。

成本 一句话定义 由什么决定 怎么观测 详见
创建/销毁 每个线程都要申请栈与内核资源 线程数、平台 Thread.start() 耗时、JFR 线程事件 ②⑧
上下文切换 CPU 换一个线程要保存/恢复现场 线程数 > 核数、锁竞争、阻塞调用 JFR jdk.ThreadPark、perf sched ②⑥
同步/竞争 抢锁、CAS 自旋、缓存行争用 共享粒度、临界区大小 基准对比、jstack 的 BLOCKED ⑤⑥
可见性成本 内存屏障、禁止重排 volatile / CAS / 锁 反汇编、基准对比 ③

先记住一句话：并发的性能问题，本质是「同一份数据被多个核访问」。不共享，就没有成本；一共享，成本由缓存一致性协议决定，而不是由你的代码行数决定。

2.5 动手验证：验证你的基准有没有被 JIT 优化

预期观察点：有 sink = x 时约几百毫秒；注释掉之后耗时接近 0（JIT 判定为死代码，整个循环消失）。

判定标准：

  • 两次耗时差不多 → 你的基准本来就没被优化（或者跑了 -Xint，那是解释执行，慢 10 倍以上）；
  • 第二次也是几百毫秒 → 说明 x 有副作用没被消除，检查是否真注释掉了。

3. 基线四件套

3.1 创建：一个线程 32 µs

指标 实测
单线程创建+回收 32 µs
1 万个顺序创建总耗时 ≈ 320 ms

换算到生产：如果每秒新建 5000 个线程（比如 new Thread 处理请求），就有 160 ms/秒 花在创建上，CPU 有效利用率直接掉一截。这也是线程池存在的第一个理由。

3.2 切换：一次真实切换 2.43 µs

指标 实测
一次 park/unpark 切换 2,426 ns（2.43 µs）
切换次数 100,000
自旋方式的「假切换」 87 ns（第一版，错）

为什么差 28 倍：自旋时线程一直在 RUNNABLE，另一核只是拿到缓存行；park/unpark 是真的把线程挂起、由内核重新调度，涉及 futex/condvar 与调度器。

换算：每秒 10 万次切换 = 0.24 秒纯切换开销。线程数开到核数的 10 倍以上时，这个成本会吃掉大部分 CPU。

3.3 加速比：15 核能拿到 12.68 倍

线程数 耗时 加速比 效率
1 279 ms 1× 100%
2 148 ms 1.89× 94%
4 76 ms 3.67× 92%
8 37 ms 7.54× 94%
15 22 ms 12.68× 85%

读法：纯 CPU 密集任务在 15 核上能拿到 12.68 倍，效率 85%——剩下的 15% 花在任务分发、GC、以及最后几个线程的收尾上。这是「理论上限」的实测值，任何带共享状态的任务都会低于它。

为什么「无共享 0 ns/op」是假的：JIT 发现每个线程只写自己的数组、而数组只被主线程读一次，于是把整个循环消除。修正方法是把结果写进 volatile 静态字段（本文的 SINK），让 JIT 不敢删。

3.4 竞争：同样的加一，差 6 倍

写法 ns/op 说明
synchronized（4 线程） 6 中等竞争，锁大部分时间没被抢
AtomicLong（4 线程） 5 CAS 失败重试，比锁略快
LongAdder（4 线程） 1 分段累加，写扩散到不同缓存行
线程本地 0（被优化） 无共享 = 无同步

注意：这是「4 线程中等竞争」的数字。⑤ 会测 32/64 线程的曲线——竞争加剧时，AtomicLong 会明显退化，而 LongAdder 几乎线性。

3.5 动手验证：跑出你自己的四个基线

预期观察点：jfr summary 里能看到 jdk.ThreadPark、jdk.JavaMonitorEnter、jdk.GCPhasePause 等事件；Thread.print 里 worker 线程状态是 RUNNABLE。

判定标准：

  • JFR 文件为空或没有事件 → 检查 settings=profile 是否生效（jfr summary 会列出事件类型）；
  • Thread.print 报连接失败 → pid 拿错了（jcmd -l 可能列出多个 Java 进程）。

3.6 动手验证：量你自己的线程创建与切换

预期观察点：线程创建在 2050 µs/个，切换在 15 µs/次（取决于机器与内核）。

判定标准：

  • 切换 > 20 µs → 机器有虚拟化层或 CPU 争抢严重（容器配额、其他进程）；
  • 切换 < 200 ns → 你的线程在自旋而不是真的挂起，检查是否用了 park；
  • 两个数字都远大于本文 → 先查宿主机负载，再谈 JVM 参数。

4.1 判断表

症状 大概率是哪类成本 第一件事 别做什么

4.3 动手验证：用 JFR 抓一次锁竞争

预期观察点：jdk.JavaMonitorEnter 事件数量巨大（几十万到上百万），每条带 duration 与 monitorClass，能直接看到「等锁花了多久」。

判定标准：

  • 没有该事件 → 锁没竞争（线程数不够，或临界区外的工作太多）；
  • 事件很多但 duration 都很小（< 1 µs）→ 竞争不激烈，瓶颈不在锁；
  • duration 到毫秒级 → 临界区里有慢操作（IO、日志），要缩小临界区。

5. 总结

5.1 面试速答表

面试题 一句话答案
并发问题的本质是什么 共享可变状态下的原子性、可见性、有序性
创建一个线程要多久 本文实测 32 µs（创建+启动+回收）
一次线程切换要多久 本文实测 2.43 µs（真实 park/unpark）
多线程一定更快吗 纯 CPU 密集 15 核可到 12.68×；共享状态多则会倒退
为什么无共享时开销是 0 JIT 会把无用计算删掉，基准必须消费结果
微基准为什么容易错 JIT 优化、缺少预热、GC 干扰、死代码消除
JMH 解决什么问题 预热、分叉、死代码消除、统计——手写基准的坑它都填了
JFR 能看什么 线程 park、锁进入、GC、IO、异常，是 JDK 自带的生产级工具
jcmd Thread.print 和 jstack 区别 同一个东西，jcmd 是统一入口
该看 CPU 使用率还是线程数 看「线程数 / 核数」与切换成本，CPU 高可能只是自旋

5.4 实操建议

  1. 先在自己的机器上跑一遍四个基线，把数字记下来——后面十一篇都要跟它对照。
  2. 微基准必须做三件事：预热、多轮取最优、消费结果；否则数字不可信。
  3. 记住两个量级：创建 32 µs、切换 2.43 µs。任何「加线程/加池」的方案都要先按这两个数字算账。
  4. **用 JFR 而不是只看 top**：CPU 高可能是自旋，线程多可能是阻塞，只有事件能区分。
  5. **建一份 concurrency-lab.md**，记录「场景 / 线程数 / 数据量 / 环境 / 数字 / 结论」。
