1. Spring 概述：IoC 容器解决了什么问题

本节要解决什么问题：Spring 首先是个 IoC 容器——回答”对象的创建与依赖装配为什么不能靠 new”。

1.1 没有 IoC 的日子

传统写法中，对象之间的依赖由调用方直接 new 出来：

这个写法有四个致命问题：

  1. 强耦合：UserService 直接依赖 UserDao 的构造细节，换实现（如从 JDBC 换成 MyBatis、换成 Mock）必须改代码。
  2. 创建顺序敏感：DataSource 的初始化参数一旦变化，所有依赖它的对象都要跟着改。
  3. 难以单测：无法把 Mock 对象塞进去，测试只能打真实数据库。

1.2 控制反转与依赖注入

IoC（Inversion of Control，控制反转）：把”对象的创建与装配”这一控制权从调用方手里反转给容器。调用方不再 new，而是声明”我需要什么”，容器负责创建并送上门。

DI（Dependency Injection，依赖注入）：IoC 的一种实现方式——容器在创建 Bean 时，把它的依赖通过构造器、Setter 或字段注入进去。面试中两者常被混用，严格说 DI 是 IoC 的具体落地手段（还有 Service Locator 等其他手段，但 Spring 用的是 DI）。

1.3 为什么需要 DI

  • 解耦：面向接口编程，替换实现（Redis 换本地缓存、MySQL 换 PG）只改配置不改业务代码。
  • 可测试性：测试时注入 Mock 依赖，无需起真实服务。
  • 集中管理生命周期：单例、原型、请求作用域等由容器统一管理，连接池等资源有统一的释放时机。
  • 可替换性：同类型多个 Bean 时用 @Primary / @Qualifier 声明优先与选择规则（见 3.2）。

一句话回答面试题”Spring 是什么”：Spring 是一个 IoC 容器（管理对象的创建与依赖）+ AOP 框架（实现横切逻辑复用），并在此基础上构建了 MVC、事务管理、数据访问、消息等一整套生态；Spring Boot 则在框架之上提供了”约定优于配置”的自动装配能力。

3.4 循环依赖与三级缓存

3.4.1 什么是循环依赖

循环依赖指两个及以上 Bean 互相持有对方的引用，形成闭环。例如 A 依赖 B、B 又依赖 A：

创建 A 需要先注入 B，创建 B 又需要注入 A，若容器不做特殊处理，就会陷入”先有鸡还是先有蛋”的死循环。Spring 对单例 Bean 的字段/Setter 注入（属性注入）循环依赖有解，方案就是三级缓存；而构造器注入、Prototype 作用域的循环依赖则无法解决（详见 3.5）。

3.4.2 三级缓存的结构

三级缓存的容器定义在 DefaultSingletonBeanRegistry 中：

级别 字段 存储内容 作用
一级 singletonObjects 走完完整生命周期（实例化→注入→初始化）的 Bean 最终对外提供的”成品”，getBean 的最终来源
二级 earlySingletonObjects 已从三级缓存取出并确定要暴露的早期引用 防止同一 Bean 的 ObjectFactory 被重复执行（重复创建代理）
三级 singletonFactories 惰性执行的 ObjectFactory 延迟决策：真正发生循环依赖时才调用，决定返回原始对象还是 AOP 代理

查询时按 一级 → 二级 → 三级 逐级查找；从三级取到早期引用后，会移入二级缓存并移除三级缓存项，保证同一 Bean 的早期引用只创建一次。

3.4.3 为什么需要三级缓存（核心考点）

常见的追问：二级缓存看起来就够了，为什么一定要三级？关键在于 AOP。

代理对象是在 initializeBean() 的 BeanPostProcessor 后置处理阶段（AbstractAutoProxyCreator.postProcessAfterInitialization）才创建的，而循环依赖发生时，B 在 A 的属性注入阶段就必须要拿到 A 的引用——此时 A 还不知道自己是否会被代理。

  • 若只有一级缓存（实例化后直接暴露裸对象）：B 拿到的是裸 A，而最终对外的是代理 A，注入的引用与最终 Bean 不一致，AOP 全部失效。
  • 若只有二级缓存（实例化后把”早期引用”提前放进二级）：为了拿到代理，就只能无条件地对所有 Bean 提前执行代理逻辑。这不仅让没有循环依赖的 Bean 白白被提前代理，还会与 initializeBean 阶段的正常代理逻辑重复，造成双重代理或触发 doCreateBean 末尾的 “Bean has been injected into other beans in its raw version… but has eventually been wrapped” 异常。

三级缓存用 ObjectFactory 把”是否生成代理”的决策推迟到真正需要时：只有确实发生循环依赖、确实需要提前暴露引用时，才执行 getEarlyBeanReference()，通过 SmartInstantiationAwareBeanPostProcessor 判断该 Bean 是否命中切点——命中则返回代理，未命中返回原始对象：

AbstractAutoProxyCreator（SmartInstantiationAwareBeanPostProcessor 的实现）内部还会通过 earlyProxyReferences 记住”已提前代理”的 Bean，使 postProcessAfterInitialization 阶段不会重复创建代理——无论走早期路径还是正常路径，代理都只创建一次，所有引用拿到的是同一个代理实例。

以 A→B→A 为例的完整时序：

  1. 创建 A：实例化完成，addSingletonFactory 注册三级缓存，进入 populateBean 发现依赖 B，转而 getBean("B")。
  2. 创建 B：同样注册三级缓存，populateBean 发现依赖 A，转而 getBean("A")。
  3. getSingleton("A", true)：一级、二级均未命中，但 A 的三级缓存存在 → 执行 singletonFactory.getObject()（getEarlyBeanReference，若 A 命中切点则直接返回 AOP 代理）→ 早期引用放入二级缓存、移除三级缓存。
  4. B 拿到 A 的早期引用，完成注入与初始化，存入一级缓存。
  5. 回到 A：此时 B 已创建完毕，A 注入 B，完成初始化存入一级缓存。doCreateBean 末尾还会做一次校验：getSingleton(beanName, false) 取到 earlySingletonReference 后，若 exposedObject == bean（未被包装）则直接使用早期引用；若被包装过（如生成代理）且早期引用已被其他 Bean 注入，则抛出 BeanCurrentlyInCreationException，避免”其他 Bean 拿到的是原始对象而最终容器里是代理”的不一致。

3.5.1 构造器注入的循环依赖

4.2 JDK 动态代理 vs CGLIB

维度 JDK 动态代理 CGLIB
原理 运行时生成实现同一接口的代理类（java.lang.reflect.Proxy + InvocationHandler） 运行时生成目标类的子类，覆写非 final 方法（Spring 内部重打包为 org.springframework.cglib，自 Spring 5.0 起基于 CGLIB 3.2 重写）
前提条件 目标类必须实现接口 目标类不能是 final，方法不能是 final/private
代理对象类型 与目标实现同一接口 是目标类的子类，可赋给实现类类型
创建性能 创建快 创建较慢（需生成字节码）
调用性能 JDK 17+ 已基本追平 长期运行下表现稳定

规则一句话：目标是接口或已有代理 → JDK；否则只要 proxyTargetClass=true 或无接口 → CGLIB。

为什么 Spring Boot 2.x 起默认 CGLIB（版本考点）：

  • Spring Boot 1.x：spring.aop.proxy-target-class 默认 false，有接口就用 JDK 代理。
  • Spring Boot 2.0 起：AopAutoConfiguration 中的 CglibAutoProxyConfiguration 通过 @EnableAspectJAutoProxy(proxyTargetClass = true) 把默认改为 CGLIB，官方动机是：
    1. 避免类型转换错误：JDK 代理只能赋给接口引用，@Autowired UserServiceImpl userService（注入实现类类型）在有接口且用 JDK 代理时直接启动失败；
    2. 现代代码普遍不为每个类写接口，CGLIB 无需接口即可代理；
    3. @Configuration 的 CGLIB 增强（full 模式）等场景需要类级代理。
  • 注意：Spring Framework 单独使用（不经过 Boot）默认仍是有接口走 JDK 代理；Spring Boot 3.x 延续 2.x 的 CGLIB 默认。

4.3 代理的创建时机与流程

流程：wrapIfNecessary → findEligibleAdvisors（把切面里的 @Pointcut 与目标方法匹配）→ createProxy（ProxyFactory 按 4.2 的规则选 JDK/CGLIB）。

与循环依赖的联动（呼应 3.4）：正常 Bean 在 postProcessAfterInitialization 创建代理；发生循环依赖的 Bean 则在 getEarlyBeanReference（SmartInstantiationAwareBeanPostProcessor）提前创建，且通过 earlyProxyReferences 保证不重复创建——两次时机只生效一次，这是三级缓存设计的直接动机。

另外要记住：**@Transactional、@Async 走的是同一套代理机制**（只是不同 Advisor），所以它们的失效场景与 AOP 完全一致（见 4.4 和 7.4）。

生效的前提条件

条件 说明

方法需为 public 非 public 方法无法被代理
避免类内部自调用 必须通过代理对象调用方法

失效场景逐个展开

  1. 同类内部自调用（最高频）：

解决方式（三选一）：

  • 拆 Bean：把 updateStock 移到另一个 Service 中，跨 Bean 调用必然走代理；
  • 注入自身代理：@Autowired @Lazy private OrderService self; 然后 self.updateStock(order)（@Lazy 避免启动期循环依赖）；
  • AopContext.currentProxy()：((OrderService) AopContext.currentProxy()).updateStock(order)，需要 @EnableAspectJAutoProxy(exposeProxy = true)。
  1. private 方法：JDK 代理根本拦截不到；CGLIB 生成的子类也无法覆写 private 方法——静默失效。
  2. final 类 / final 方法：CGLIB 无法继承/覆写，启动时抛异常或静默失效。
  3. 切点表达式写错：execution 语法错误或包名不匹配时不会报错，只是不织入——排查时先确认切点能匹配上。
  4. 对象未交给 Spring 管理：new OrderService() 或非 @Component 的类。
  5. 代理机制本身的局限：Spring AOP 只能织入 Spring Bean 的方法调用，不能织入字段访问、静态方法、构造器（那是 AspectJ 的能力范围，需要编译期织入或 load-time weaving）。

③ 各类通知在链中的位置（同一切面的内部顺序固定）：

  • @Around：包裹整条链，pjp.proceed() 之前的代码相当于前置、之后的相当于后置；

  • @After：无论正常还是异常都执行（finally 语义）。

④ @Order 对链顺序的影响：多个切面通过 @Order(n)（或实现 Ordered）排序，数字小的先进入链——体现在执行顺序上：前置逻辑先执行、后置逻辑后执行（看上面的洋葱图：Order=1 的 @Before 在最外层，Order=1 的 @After 也在最外层）。所以”统计耗时的切面”通常用 @Order(0)，让它包在最外层，计时才准确。

5. Spring MVC 请求处理流程

本节要解决什么问题：一个 HTTP 请求从 Tomcat 进来，到 Controller 方法执行、再到响应返回，中间经过哪些组件、每个组件干什么。

5.1 核心组件与职责

ViewResolver 视图解析器：把逻辑视图名解析为物理视图（InternalResourceViewResolver 等）
ModelAndView 模型数据 + 视图信息的载体

完整九步：

  1. 请求进入 Servlet 容器（Tomcat）→ 经过 Filter 链（见第 9 节）→ 到达 DispatcherServlet。
  2. getHandler：按 HandlerMapping 链逐个尝试匹配，RequestMappingHandlerMapping 根据 @RequestMapping 注册的路由表返回 HandlerExecutionChain。

  5. ha.handle：适配器调用 Controller 方法——HandlerMethodArgumentResolver 链解析参数（@RequestBody 由 HttpMessageConverter 把 JSON 反序列化为对象，@PathVariable/@RequestParam 做数据绑定与类型转换），方法执行后由 HandlerMethodReturnValueHandler 处理返回值。
  6. 返回 ModelAndView：有 @ResponseBody（或 @RestController）时返回 null 的 ModelAndView，返回值直接由 HttpMessageConverter（Jackson 的 MappingJackson2HttpMessageConverter）序列化写入响应体。
  7. applyPostHandle：拦截器 postHandle（视图渲染前回调）。
  8. processDispatchResult：若 Handler 抛异常，交给 HandlerExceptionResolver（@ExceptionHandler 在此生效）；否则进入视图解析——ViewResolver 把逻辑视图名解析为 View，渲染后输出。

  • 可覆盖：核心 Bean 一律 @ConditionalOnMissingBean，让用户能替换默认实现。

7.2 事务传播行为

传播行为 行为描述 典型场景
REQUIRED（默认） 有事务则加入，无则新建 绝大多数业务方法
REQUIRES_NEW 挂起当前事务，新建独立事务；内层提交/回滚互不影响 操作日志、审计、消息发送——不能随主事务回滚
NESTED 嵌套事务：基于保存点（Savepoint），内层失败只回滚到保存点，外层可继续 批量处理中跳过单条失败项
SUPPORTS 有事务则加入，无则以非事务方式执行 查询方法
NOT_SUPPORTED 挂起当前事务，以非事务方式执行 耗时的外部调用，不想占事务连接
MANDATORY 必须有事务，否则抛 IllegalTransactionStateException 不允许独立执行的内部方法
NEVER 必须没有事务，否则抛异常 禁止在事务内执行的逻辑

两个高频对比：

  • NESTED vs REQUIRES_NEW：NESTED 内层回滚只回滚到保存点，外层还能继续提交（同一条连接）；REQUIRES_NEW 是完全独立的第二个事务（第二把连接），外层回滚也不影响它。
  • 传播行为只在跨 Bean 的代理调用时生效（同类自调用一律不生效，见 7.4 场景 1）。

7.3 隔离级别与并发问题

隔离级别 脏读 不可重复读 幻读 说明
READ_UNCOMMITTED 可能 可能 可能 读未提交的数据，几乎不用
READ_COMMITTED 不会 可能 可能 Oracle / PostgreSQL 默认
REPEATABLE_READ 不会 不会 可能 MySQL InnoDB 默认；InnoDB 在 RR 下通过 MVCC 快照读 + 间隙锁（Gap Lock）基本消除幻读
SERIALIZABLE 不会 不会 不会 串行化，性能最差
  • 三个并发问题的定义：脏读（读到未提交数据）、不可重复读（同一条记录两次读结果不同，发生在更新）、幻读（同一范围两次查询行数不同，发生在插入/删除）。
  • Spring 的 Isolation.DEFAULT 表示使用数据库默认值，@Transactional(isolation = Isolation.REPEATABLE_READ) 可显式指定。
  • 面试追问：MySQL 默认隔离级别是 REPEATABLE_READ 而不是更严格的 SERIALIZABLE，靠的是 MVCC（多版本并发控制）+ 锁的配合，读不加锁（快照读）、写加行锁/间隙锁，在性能和一致性之间取得平衡。

7.4 @Transactional 失效场景

  1. 同类自调用（最高频，与 4.4 同源）：

解决：拆 Bean；@Autowired @Lazy private OrderService self; 后 self.updateStock(...)；或 AopContext.currentProxy()（需 @EnableAspectJAutoProxy(exposeProxy = true)）。

  1. 非 public 方法：AbstractFallbackTransactionAttributeSource 只解析 public 方法的事务属性，非 public 直接返回 null——静默失效。
  2. 异常被 catch 吞掉：事务提交与否取决于异常是否抛出到代理，自己 catch 掉就不会回滚：
  1. 受检异常默认不回滚：默认只对 RuntimeException 和 Error 回滚，受检异常（如 IOException）不会。需要 @Transactional(rollbackFor = Exception.class)。
  2. **方法/类为 final**：CGLIB 无法继承，事务不生效。
  3. 多线程调用：事务上下文绑定在线程的 ThreadLocal 上，新起的线程（new Thread、线程池）没有事务上下文，各跑各的连接。
  4. 数据库/表不支持事务：MyISAM 引擎、只读连接等。
  5. 对象不是 Spring 管理的：new OrderService() 或手动 getBean 拿原始对象，没有代理。
  6. **传播行为配置引发的”部分提交”**：外层事务方法里 try-catch 包住内层 REQUIRED 调用，异常被外层吞掉后整批回滚（因为 REQUIRED 是同一事务）；想要”内层独立提交”得用 REQUIRES_NEW。

7.5 常见问题

  • 大事务：一个事务里做耗时的外部调用、循环大批量更新，会长时间占用数据库连接与行锁。治理方向：拆分事务、REQUIRES_NEW 抽出独立步骤、或改用编程式事务精准控制边界。
  • **readOnly = true**：语义是”禁止写操作”（误写会抛异常），同时给数据库优化器提示（如 MySQL 8 对只读事务的优化）。适合只读查询接口，但不要指望它带来显著的性能提升。
  • 自增主键/连接释放：由连接池管理，与事务无关；但长事务会”占住”连接不归还，连接池耗尽时表现为”拿不到连接”。

8.6 常见问题与坑

  1. 异常未被捕获：检查 @ControllerAdvice 是否在组件扫描路径内；确认没有其他 Advice 的 @ExceptionHandler(Exception.class) 抢先（@Order 高的先执行）。

10. 常见 Spring 面试题速答

本节用”问题 + 一句话答案 + 定位”的方式速览高频题，详细推导见对应章节。

10.1 IoC / 容器

Q：IoC 和 DI 是什么？
A：IoC 是把对象创建与装配的控制权反转给容器；DI（依赖注入）是它的实现方式——容器把依赖通过构造器/Setter/字段注入进来。详见第 1 节。

Q：BeanFactory 与 ApplicationContext 的区别？
A：ApplicationContext 是 BeanFactory 的子接口。BeanFactory 是底层容器、懒加载；ApplicationContext 预加载单例，自动注册后处理器，并提供事件、国际化、资源加载等能力。详见 2.1。

Q：容器启动时做了什么？
A：解析配置类（ConfigurationClassPostProcessor）→ 注册 BeanDefinition → 注册 BeanPostProcessor → 预实例化单例（finishBeanFactoryInitialization）→ 发布 ContextRefreshedEvent。详见 6.1。

Q：如何发布和监听事件？
A：注入 ApplicationEventPublisher 调 publishEvent；监听用 @EventListener（默认同步、同一线程），@TransactionalEventListener 可在事务提交后触发（Spring 4.2+，观察者模式的典型应用）。

10.2 生命周期 / 作用域

Q：Bean 生命周期关键节点？
A：实例化 → 属性填充（@Autowired 注入）→ Aware 回调 → postProcessBeforeInitialization → @PostConstruct → InitializingBean → init-method → postProcessAfterInitialization（AOP 代理在此创建）→ 就绪；销毁：@PreDestroy → DisposableBean → destroy-method。详见 2.3。

Q：单例与原型区别？
A：单例全容器一个实例、生命周期由容器管理；原型每次 getBean 新实例、容器不管理其销毁。详见 2.4。

Q：Spring Bean 线程安全吗？
A：不是 Spring 保证的。无状态单例天然安全；有状态单例需原子类/同步/ThreadLocal/无状态设计。详见 2.4。

Q：怎么把原型 Bean 注入单例 Bean？
A：@Lookup、ObjectProvider<T>、或 @Scope(proxyMode = TARGET_CLASS)。详见 2.4。

Q：BeanFactory 和 FactoryBean 的区别？
A：BeanFactory 是容器接口；FactoryBean 是生产对象的 Bean，注入拿到的是 getObject() 的结果，& 前缀取 FactoryBean 本身。详见 2.6。

10.3 依赖注入

Q：@Autowired 与 @Resource 的区别？
A：来源（Spring vs JSR-250）、默认策略（按类型 vs 先名称后类型）、@Primary 支持、构造器支持、必填配置。详见 3.1。

Q：同类型多个 Bean 怎么注入？
A：@Qualifier 按名称、@Primary 标默认、@Priority 标顺序，或字段名与 Bean 名一致兜底。详见 3.2。

Q：为什么推荐构造器注入？
A：不可变、必填、可测试；代价是构造器注入的循环依赖无解（会启动报错，反而帮助尽早暴露问题）。详见 3.3。

Q：循环依赖为什么需要三级缓存而不是二级？
A：核心是延迟”是否创建 AOP 代理”的决策——代理在初始化后才创建，循环依赖却在属性填充时就需要引用；三级缓存用 ObjectFactory 把决策推迟到真正需要时。详见 3.4。

Q：构造器注入的循环依赖怎么办？
A：改字段注入，或加 @Lazy；根本上应重构消除循环依赖。Boot 2.6+ 默认禁止循环依赖。详见 3.5。

10.4 AOP

Q：JDK 代理与 CGLIB 的区别？Spring Boot 默认用哪个？
A：JDK 要求实现接口、代理类与目标同接口；CGLIB 生成子类、无接口也能代理但 final 不可。Spring Boot 2.x 起默认 CGLIB（proxy-target-class=true），为的是避免类型转换错误并支持无接口类。详见 4.2。

Q：代理在 Bean 生命周期哪一步创建？
A：正常 Bean 在 postProcessAfterInitialization；循环依赖的 Bean 提前在 getEarlyBeanReference 创建，通过 earlyProxyReferences 保证不重复。详见 4.3。

Q：AOP 哪些情况会失效？
A：同类自调用、private/final 方法、非容器 Bean、切点表达式不匹配。解决自调用：注入自身代理 / AopContext.currentProxy() / 拆 Bean。详见 4.4。

10.5 事务

Q：@Transactional 什么时候失效？
A：同类自调用、非 public、异常被吞、受检异常未配 rollbackFor、final 方法、多线程、MyISAM 表、非容器 Bean。详见 7.4。

Q：7 种传播行为是什么？各自典型场景？
A：REQUIRED（默认）、REQUIRES_NEW（独立事务，日志场景）、NESTED（保存点，跳过失败项）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。详见 7.2。

Q：MySQL 默认隔离级别？三大并发问题？
A：REPEATABLE_READ（InnoDB，MVCC + 间隙锁基本消除幻读）；Oracle/PG 默认 READ_COMMITTED。脏读、不可重复读、幻读。详见 7.3。

Kafka

面试考点范围：Kafka 的定位与选型、核心概念（Topic/Partition/Replica/ISR）、高吞吐设计原理、消息可靠性（acks/ISR/高水位）、幂等与事务、顺序性、消费者组与再平衡、KRaft 架构，以及消息积压、重复消费、Leader 抖动等常见问题的排查思路。RocketMQ/RabbitMQ 仅在选型对比中出现，不混入 Kafka 正文。

1. Kafka 定位：消息队列还是事件流平台

1.1 定位演变

Kafka 诞生于 LinkedIn（2011 年开源），最初是日志聚合场景的消息队列。现在官方定位是分布式事件流平台（Event Streaming Platform），核心差异在于存储模型：

  • 经典消息队列（RabbitMQ 为代表）：消息被消费者拉走后即从队列删除，是”传输通道”。
  • Kafka：消息写入 append-only 日志（Partition），消费不删除消息，按保留策略（log.retention.hours，默认 168 小时）过期删除。因此：
    • 一个 Topic 可以被多个消费者组独立消费（发布订阅 + 组内负载均衡）；
    • 消费者可以回退 offset 重放历史数据（事件回溯、故障恢复、离线计算）；
    • 天然适合事件驱动、数据管道、日志采集、实时数仓等场景。

1.2 消息队列的三大核心价值

  • 异步：把耗时操作（发邮件、初始化画像）从主流程剥离，用户请求链路从”串行等所有步骤”变成”只等核心步骤”，响应时间从几百毫秒降到个位数毫秒。
  • 削峰：秒杀等瞬时洪峰先灌入 MQ，下游按自身处理能力匀速消费，避免数据库被打崩。MQ 本质是一个缓冲区。
  • 解耦：生产者只发消息，不感知下游；新增消费者（如加一个短信系统）无需改动生产者代码，下游故障也不阻塞主流程（消息堆积在 MQ 中）。

1.3 与 RocketMQ、RabbitMQ 的一句话说清选型

维度 Kafka RocketMQ RabbitMQ
定位 分布式事件流平台 分布式消息队列（Java 生态） 轻量消息中间件（AMQP）
吞吐 单机百万级/秒 十万~百万级/秒 万级/秒

选型一句话：吞吐和事件流优先 Kafka；交易场景需要原生事务/延迟消息优先 RocketMQ；轻量灵活、生态简单优先 RabbitMQ。

两个常见的对比追问：

  • RocketMQ 事务消息流程：Producer 先发”半消息”（对消费者不可见）→ 执行本地事务 → 提交 Commit/Rollback 指令 → Broker 收到回查（Check）请求时反向询问 Producer 本地事务最终状态，据此决定消息对消费者可见与否。Kafka 的事务机制不覆盖外部系统，定位不同（见第 6 节）。
  • Broker 选举机制对比：Kafka 由 Controller 从 ISR 中选举新 Leader（一致性优先，宁可分区不可用也不选落后副本）；RocketMQ 主从切换在 DLedger 模式下走 Raft 多数派选举，兼容模式下为异步复制、手动/自动切换。

2. 核心概念：Topic / Partition / Replica / ISR / Controller / Coordinator

一张图讲清它们的关系：

  • Topic：消息的逻辑分类（类比数据库表），一个 Topic 的数据会被切分到多个 Partition 存储。
  • Partition：Topic 的物理切分单元，磁盘上是一个日志目录。它是三个基本单位的集合：
    • 存储单位：消息按 offset 递增追加，写入顺序就是存储顺序；
    • 并行单位：Partition 之间读写互相独立，可以分布在多台 Broker 上并行；
    • 顺序保证单位：Kafka 只保证分区内有序，跨分区无全局顺序。
  • Replica（副本）：每个 Partition 有 replication.factor（生产常用 3）个副本。其中一个为 Leader（负责所有读写），其余为 Follower（只从 Leader 拉取数据同步，不对外服务）。副本分布在不同 Broker 上，提供容错。
  • ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合。Leader 维护 ISR 列表，Follower 在 replica.lag.time.max.ms（默认 30s）内没跟上 Leader，会被移出 ISR。ISR 是 Leader 选举的候选池：只有 ISR 中的副本才有资格当选新 Leader，保证新 Leader 拥有全部已提交数据（详见第 5 节）。
  • Controller：集群中枢。负责 Broker 上下线感知、Partition 的 Leader 选举、Topic 创建/删除等元数据变更，并把变更结果同步给所有 Broker。KRaft 模式下由 Controller Quorum 通过 Raft 选举产生（详见第 9 节）。
  • Coordinator（协调者）：Kafka 有两类协调者，都是”每个组对应一个协调者实例”：
    • Group Coordinator：管理消费者组的成员关系、触发 Rebalance、接收 offset 提交。位置由 hash(groupId) % 50（__consumer_offsets 默认 50 个分区）决定；
    • Transaction Coordinator：管理事务状态（存储在 __transaction_state topic），第 6 节会用到。

3. 高吞吐设计：每个机制为什么快

Kafka 高吞吐的总体思路：把对磁盘的随机访问变成顺序访问（磁盘友好），把热数据留在内存（Page Cache），把网络传输的拷贝次数降到最低（零拷贝），把多次小请求合并成大批量（批量 + 压缩），再把单点瓶颈拆成多路并行（分区）。

3.1 顺序写

  • 为什么快：磁盘顺序写可达 150~200 MB/s（机械盘）甚至更高，而随机写（尤其是小 IO）只有几 MB/s，差距来自机械臂寻道和磁头旋转。SSD 上差距缩小，但顺序 IO 依然显著更快。Kafka 只做追加写（append-only），把”读改写”变成”写尾指针”，磁盘永远是顺序的。
  • 怎么实现：每条消息追加到当前活跃的日志段（Segment）末尾；Segment 按 log.segment.bytes（默认 1GB）滚动切分（段文件结构见第 4 节）。写入路径是 FileChannel.write → OS Page Cache，不逐条 fsync，靠副本冗余保证可靠性（顺序写快并不等于已落盘）。
  • 生产配置：无需特殊配置；注意一个常见误区——不能因为”顺序写快”就认为数据已持久化，可靠性仍要依靠 acks 和副本数（第 5 节）。

3.2 Page Cache

  • 为什么快：磁盘 IO 无论怎么优化都远慢于内存。Kafka 把读写都交给操作系统 Page Cache：写先落到 Page Cache 由内核异步刷盘，读命中 Cache 时就是纯内存操作。
  • 怎么实现：数据不经过 JVM 堆，全部走内核 Page Cache。这让 Kafka 的 JVM 堆可以保持很小（生产建议 4~8GB，其余内存留给 OS），避免大堆 GC 停顿；同时 OS 的 LRU 淘汰、预读、批量回写比 JVM 手动管理更高效，且整个机器的进程共享同一份 Cache。
  • 生产配置：JVM 堆不要盲目调大，防止堆挤占 Page Cache 空间；日志目录建议独立挂盘（多盘可配置 log.dirs 以逗号分隔，数据分散到多块磁盘）。

3.3 零拷贝 sendfile

  • 为什么快：传统”读文件 → 发给 socket”路径要经过 4 次拷贝（DMA 磁盘→内核、内核→用户、用户→内核、内核→网卡）和多次上下文切换，CPU 和内存带宽都被浪费。
  • 怎么实现：sendfile 让内核直接把 Page Cache 中的数据 DMA 到网卡，用户态只传 (offset, length) 两个参数，全程 2 次拷贝（1 次 DMA 进内核 + 1 次 DMA 出网卡），无用户态参与。Kafka 消费时 Broker 用 Java NIO 的 FileChannel.transferTo() 实现，消息体越大收益越明显。另一个细节：Kafka 写日志不用 mmap（写入无法控制刷盘时机），只用 mmap 映射索引文件（offset index / time index，见第 4 节）。
  • 生产配置：无参数；零拷贝依赖 Page Cache 命中，本质是”读的热数据来自内存”。

3.4 批量 + 压缩

  • 为什么快：网络传输的瓶颈在 RTT 和系统调用次数，而不是带宽。把 1 万条 1KB 的消息合并成 10MB 一个批次发送，网络往返和系统调用摊薄了 1 万倍。
  • 怎么实现：
    • Producer 端：batch.size（默认 16KB）和 linger.ms（默认 0）控制攒批。注意 linger.ms=0 表示有数据立刻发，攒批主要靠”批次没满时下一条继续追加”；生产环境给 linger.ms 设 5~20ms 可以显著提升吞吐，代价是引入毫秒级延迟。key 为 null 时 2.4+ 使用 sticky 分区策略，把消息粘在同一个分区攒满再换，避免均匀散开后每个分区都攒不满。
    • Broker 端：按批次（RecordBatch）写入磁盘，落盘单位不是单条消息。
    • Consumer 端：fetch.min.bytes（默认 1）和 fetch.max.wait.ms（默认 500ms）控制攒批拉取，减少拉取次数。
    • 压缩：compression.type（gzip/snappy/lz4/zstd）在 Producer 端压缩，Broker 不解压直接存，Consumer 端解压，压缩成本摊给两端，换来网络和磁盘的大幅节省。zstd 压缩比最高但 CPU 消耗大，lz4 是均衡之选。
  • 生产配置：CPU 不紧张时建议开启压缩（lz4 起步）；对延迟敏感的业务把 linger.ms 调小，对吞吐敏感的业务调大。

3.5 分区并行

  • 为什么快：单分区是单线程顺序写，吞吐上限受单块磁盘 IOPS 和单台机器的网络带宽限制。把 Topic 拆成 N 个 Partition 分布在 M 台 Broker 上，读写多路并行，吞吐理论上可以线性扩展。
  • 怎么实现：Producer 用分区器决定消息进哪个分区（key 哈希 / sticky）；Broker 上多个分区的写入分散到不同磁盘（log.dirs）；Consumer 组内不同实例消费不同分区。
  • 生产配置：分区数是吞吐规划的核心参数——先估单分区吞吐（如 5~10 MB/s），再按总吞吐需求定分区数。分区不是越多越好：分区数过多会放大元数据规模、文件句柄数、Rebalance 时间，以及 Leader 选举开销。经验值：分区数与预期吞吐匹配即可，单 Broker 数千分区以内是常见规模。

4. 物理存储

本节要解决什么问题：一条消息落盘后长什么样——Segment 文件怎么组织、索引怎么定位、日志怎么清理，以及多磁盘怎么分配。

4.1 Segment 文件结构

Kafka 的 Topic 数据按分区存储，一个分区对应磁盘上的一个目录：

日志段（Segment） 是分区的物理存储单位，每个 Segment 由三个文件组成（一组）：

文件 内容
.log 消息本体，二进制追加写
.index offset → 物理位置 的稀疏索引（4.2 详述）
.timeindex 时间戳 → offset 的索引，用于按时间定位（offsetsForTimes）

文件名的 20 位数字 = 段内第一条消息的绝对 offset（例如 00000000000000037281.log 表示该段从 offset 37281 开始）。只有最后一个段是活跃段（active segment），消息只追加到活跃段；写满 log.segment.bytes（默认 1GB）或超过 log.roll.hours（默认 7 天）后滚动生成新段。滚动后的段只读——日志清理（4.3）正是以”段”为单位删除的。

4.2 稀疏索引原理：offset index 怎么用

一个 1GB 的 .log 文件里要定位 offset 37281 之后的第 10 条消息，不可能从文件头逐条扫。.index 就是干这个的，但它不是”每条消息一条索引”（那样索引比数据还大），而是稀疏索引：

  • 每写入 4KB（log.index.interval.bytes 默认 4096 字节）数据，才在 .index 追加一条记录；
  • 每条记录 8 字节：relative offset（4 字节，段内相对偏移）+ position（4 字节，段内物理位置）；
  • 按 offset 查找的路径：① 根据段文件名找到目标 offset 所在的 Segment → ② 在 .index 里二分查找 ≤ 目标 offset 的最大条目 → ③ 拿到物理 position 后从 .log 对应位置顺序扫描到目标 offset。稀疏索引让索引体积缩小上百倍，代价只是最多多扫 4KB 数据——二分 + 顺序扫都是内存/顺序 IO 操作，代价可忽略。

.timeindex 同理：每 4KB 记一条 (timestamp, relative offset)，按时间戳二分定位到段和 offset，支撑”从某时刻开始消费”。

4.3 日志清理策略：delete vs compact

消息消费完不会消失，什么时候真正删除由清理策略决定（Broker 级 log.cleanup.policy，可按 Topic 覆盖）：

delete（默认）：按时间/大小过期删除

  • log.retention.hours（默认 168，即 7 天）或 log.retention.bytes（默认 -1 不限总量）；
  • 清理线程只删非活跃段中过期的段，删除单位是整段；
  • 适合日志、事件类”过了保留期就不需要”的数据。

compact：日志压缩，按 key 保留最新值

  • log.cleanup.policy=compact：不为”过多久删”，而是永远保留每个 key 的最新一条消息，key 的旧值被压缩删除；
  • 后台 cleaner 线程（log.cleaner.enable=true）扫描段 → 用 OffsetMap 记住每个 key 出现的最大 offset → 把每段重新写成”只含各 key 最新值”的紧凑段 → 删除冗余；
  • tombstone：写入 value = null 的消息表示删除该 key，压缩后连 key 一起消失；
  • 适合”最终状态”类数据：用户配置表、股票快照、设备最新状态——历史旧值毫无意义，只有最新值有用。
维度 delete compact
保留语义 保留最近 N 小时/字节 保留每个 key 的最新值
删除单位 整个 Segment（按时间/大小） 段内逐条（按 key）
代价 低 cleaner 线程 CPU 开销
典型应用 日志、指标、事件 配置、快照、状态数据

4.4 磁盘布局：log.dirs 与 Leader 分布

多目录均衡：log.dirs=/data/kafka1,/data/kafka2（逗号分隔）把分区目录分散到多块磁盘。Broker 创建新分区时，选择当前文件数最少的目录——Kafka 不自作聪明搞手动分配，只保证大体均衡，让多盘 IO 并行。

Leader 分区的轮询放置：创建 Topic 时（kafka-topics.sh --create --replication-factor 3 --partitions 6），Controller 会把各分区的 Leader 尽量均匀分配到所有 Broker（优先选副本最少的 Broker），Follower 跟随放置并尽量满足机架感知（rack 配置），保证单个 Broker 宕机不会让某个 Topic 的所有 Leader 同时消失。

工程建议：数据目录按块磁盘规划（一块系统盘 + 两块数据盘分别给日志与数据），log.dirs 指向数据盘；监控磁盘空间——分区目录只增不减，清理策略跟不上时磁盘会写满。

5. 消息可靠性：三个环节怎么保证不丢

先明确三种投递语义，面试常考：

  • at-most-once（最多一次）：可能丢，但不会重复。acks=0 即此语义。
  • at-least-once（至少一次）：不会丢，但可能重复。Kafka 默认就是这种语义。
  • exactly-once（精确一次）：不丢不重。需要幂等 + 事务 + 消费端配合（第 6 节）。

5.1 acks 三种模式

  • **acks=0**：Producer 发完即走，不等任何确认。吞吐最高、延迟最低，但可能丢消息（Broker 宕机、网络故障都感知不到）。只用于日志、指标等可丢数据。
  • **acks=1**：等待 Leader 写入本地日志（Page Cache）后确认。折中方案；若 Leader 写入后、Follower 尚未同步前宕机，消息丢失（因为新 Leader 从 ISR 选出，可能没有这条数据）。
  • acks=all（等价于 acks=-1）：等待 Leader 收到消息且当前 ISR 中所有副本都已写入后才确认。最强可靠性，需要配合 min.insync.replicas 使用才有意义（见下）。

5.2 ISR 最小副本数：acks=all 的正确打开方式

  • 为什么需要：acks=all 的语义是”ISR 全部写入”，但 ISR 是动态收缩的——如果副本都挂得只剩 Leader 自己，ISR 就只剩一个，acks=all 实际退化成 acks=1。所以必须有 min.insync.replicas 卡住底线。
  • 怎么实现：min.insync.replicas 规定”至少 N 个副本在线同步，才接受写入”。当 ISR 收缩到小于该值时，Leader 直接拒绝写入，Producer 收到 NotEnoughReplicasException 并重试——宁可写失败，也不能写成功却只有一份副本。
  • 生产配置：replication.factor=3（Broker 级 default.replication.factor）搭配 min.insync.replicas=2。acks=all + min.insync.replicas=2 的含义是：写入成功的消息必然存在 2 份副本，任意一台 Broker 故障都不丢。

5.3 副本同步与高水位（LEO / HW）

这是 Kafka 一致性的核心考点：

  • 为什么需要：Follower 复制是异步拉取（Follower 主动向 Leader 发 Fetch 请求，Leader 不推）。如果消费者能读到”只有 Leader 有、Follower 还没有”的消息，那么 Leader 一宕机，这些已读数据就凭空消失了。必须定义一条”已提交”的线，消费者只能读线以下的。
  • 怎么实现（两个水位）：
    • LEO（Log End Offset）：每个副本日志下一条要写入的位置；
    • HW（High Watermark）：ISR 中所有副本都同步到的最小 LEO，即”所有 ISR 副本都拥有的位置”。HW 以下的消息视为已提交，消费者只能消费 HW 以下。
    • 更新过程：Follower 拉取时带上自己的 LEO → Leader 取 ISR 中最小 LEO 更新自己的 HW → 响应带回 Leader 的 HW → Follower 把自己的 HW 更新为 min(自身 LEO, Leader HW)。
  • 高水位与 Leader 选举：Leader 从 ISR 中选出，而 ISR 中每个副本的 LEO 都 ≥ HW，所以所有已提交消息必然在新 Leader 上。如果 unclean.leader.election.enable=true 且 ISR 全挂，会从非 ISR（落后副本）选 Leader，新 Leader 会截断（truncate）到自己的 LEO，已确认的消息可能”回滚”丢失。**生产环境必须 unclean.leader.election.enable=false**：宁可分区短暂不可用，也不能丢已确认数据。
  • 补充深度：0.11 引入的 leader epoch（KIP-101）解决了旧 HW 机制在”旧 Leader 复活”场景下可能误截断的问题——每个 Leader 任期记录起始 offset，截断时按 epoch 精确对齐，而不是盲目以新 Leader 的 offset 为准。

5.4 三环节不丢失方案

Producer 环节：

  • 原因：acks=0/1 的确认语义不足；异步发送未处理回调，发送失败无感知。
  • 方案：
    • acks=all + min.insync.replicas=2（前提 RF=3）；
    • 配置 retries（幂等开启后默认很大）和 retry.backoff.ms，让可重试异常（网络抖动、NOT_ENOUGH_REPLICAS）自动重试；
    • **enable.idempotence=true**：开启后强制 acks=all，同时让重试不产生重复数据（详见第 6 节）；
    • send() 的回调必须检查异常并告警，不能只打日志假装没看见。

Broker 环节：

  • 原因：RF=1 单副本，磁盘故障即丢；min.insync.replicas=1 时 acks=all 名存实亡；unclean.leader.election.enable=true 选落后副本当 Leader。
  • 方案：replication.factor=3、min.insync.replicas=2、unclean.leader.election.enable=false。Broker 侧不需要追求逐条 fsync——副本冗余已经保证了”至少两份”，OS 刷盘交给内核即可（追求极致可用性时关注 log.flush.interval.messages，但生产默认配置通常足够）。

Consumer 环节：

  • 原因：默认 enable.auto.commit=true 在 poll 前就提交 offset，消息处理失败（业务异常、进程崩溃）后 offset 已提交，这条消息就”消失”了（还在 Broker 上，但组内无人再消费）。
  • 方案：
    • enable.auto.commit=false，业务处理成功之后手动 commitSync()（或 commitAsync() 并在回调里兜底）；
    • 处理完一批再提交该批最后一条 offset，失败则不提交，重启后自动重新消费；
    • 实现 ConsumerRebalanceListener，在 onPartitionsRevoked 中把已处理的 offset 提交掉，防止分区易主后丢进度（完整代码见第 8 节）。

一句话总结生产配置：RF=3、min.insync.replicas=2、unclean.leader.election.enable=false、acks=all、enable.idempotence=true、消费者手动提交——这套组合把消息丢失概率降到”整个机房故障”级别。

6. 消息不重复：幂等生产者、消费者去重、事务

6.1 为什么会产生重复

在 at-least-once 语义下，重复是结构性的，无法靠”仔细点”消除：

  • 生产者重试：消息已写入 Broker，但 ack 在网络中丢失，Producer 重试导致同一条消息写入两次（两个 offset）；
  • 消费者提交失败：处理成功但 offset 提交失败（网络、崩溃、Rebalance），重平衡后从旧 offset 重新拉取，已处理的消息被再次消费。

6.2 幂等生产者：enable.idempotence=true

  • 为什么需要：重试和去重是矛盾的——不重试会丢，重试会重。幂等机制让”重试”和”不重”同时成立。
  • 怎么实现：Producer 启动时向 Broker 申请一个唯一的 Producer ID；发往每个分区的消息携带单调递增的序列号（从 0 开始）。Broker 记录每个 (PID, 分区) 最近写过的序列号：重复序列号直接忽略，乱序序列号（前一个批次还没到）返回 OutOfOrderSequenceException 并触发重新发送。同时幂等模式自动 acks=all、放大 retries。
  • 局限（面试常问）：去重范围是单个 Producer 会话、单个分区。进程重启后 PID 变化，去重失效；跨分区（同一 PID 不同分区序列号独立）不去重。
  • 生产配置：enable.idempotence=true 是生产必选项，无性能副作用（和顺序性还有协同作用，见第 7 节）。

6.3 消费者端去重：最终的兜底方案

  • 为什么需要：Kafka 的事务只能覆盖 Kafka 内部。消费逻辑一旦牵涉外部系统（数据库、ES、调用下游 API），”不重复”必须由业务侧自己保证。这是最通用、最灵活的方案。
  • 怎么实现：
    • 消息中携带全局唯一业务 ID（订单号、支付流水号）；
    • 处理前查重：SELECT ... WHERE order_id = ? 已存在则跳过；
    • 数据库唯一约束兜底：INSERT 违反唯一键即视为重复（并发场景下查重也挡不住，唯一约束是最后防线）；
    • 需要”只处理一次”的状态机用条件更新：UPDATE t SET status='paid' WHERE order_id=? AND status='unpaid'，影响行数为 0 即重复。

6.4 事务消息 vs 幂等

  • 为什么需要事务：幂等只解决”单分区去重”，解决不了”多个分区的写入要么全成功要么全失败”和”消费与生产原子化”（Kafka Streams 的精确一次、跨 Topic 的一致事件）问题。
  • 怎么实现：事务由 Transaction Coordinator（状态存于 __transaction_state）协调：Producer 开启事务后，写入的分区都在事务内标记；commitTransaction() 时协调者推进事务状态，消费者设置 isolation.level=read_committed 时，只能读到已提交事务内的消息和 LSO（Last Stable Offset）之前的数据，read_uncommitted 则能读到未提交数据。事务要求 enable.idempotence=true。
维度 幂等（enable.idempotence） 事务
解决的问题 重试导致的重复 多分区/多 Topic 原子写入 + 消费提交原子化
覆盖范围 单 Producer 会话、单分区 事务内所有分区、所有 Topic
消费者 无需感知 需 isolation.level=read_committed
对外的保证 不丢不重（分区内） 流处理 exactly-once（Kafka 内部）
局限 跨会话、跨分区不去重 不覆盖外部系统（DB/ES 需业务幂等兜底）

面试回答模板：幂等是”去重”，事务是”原子性”；跨 Kafka 与外部系统的最终一致性，靠业务幂等兜底。

7. 消息顺序性：分区内有序

7.1 分区内有序的原理

Kafka 的顺序保证是”单分区内严格有序“：

  • 写入侧：消息按 offset 追加到分区日志尾部，写入顺序即物理存储顺序；
  • 消费侧：同一个分区的消息只被组内一个消费者实例消费，poll() 按 offset 顺序返回，处理顺序就是消费顺序。

跨分区没有全局顺序（全局有序只能单分区 + 单消费者，等于放弃并行，生产上极少需要）。

7.2 用 key 保证同一实体的消息有序

业务上有序的最小单位是”同一个实体”（同一个订单、同一个用户）。默认分区器（DefaultPartitioner）对 key 做 murmur2 哈希取模选分区，相同 key 必然进同一分区，进而在分区内有序。

  • key 的选择：业务实体 ID（订单号、用户 ID、设备 ID）。例如订单状态流转事件都以 orderId 为 key，则该订单的全部事件按产生顺序落在一个分区。
  • 注意 key 的均匀性：热点 key（如秒杀单品 ID）会把流量压向单个分区，造成分区倾斜——key 的分布要尽量均匀。
  • 需要自定义路由时可实现 Partitioner 接口（如按业务标识 + 一致性哈希），重写 partition() 方法即可。

7.3 乱序场景与处理

  1. 生产者重试导致的乱序：未开幂等时，若 max.in.flight.requests.per.connection > 1（默认 5），第一批发送失败、第二批先成功，乱序产生。处理：开启幂等（Broker 按序列号校验，in-flight 大于 1 也保证有序），或显式设 max.in.flight.requests.per.connection=1（牺牲吞吐）。
  2. 消费者多线程并发处理乱序：单分区被多个线程并发处理时，谁先完成谁先落库，顺序被打乱。处理：分区内单线程处理；或按 key 哈希把消息路由到固定线程（threadIndex = hash(key) % threadCount），保证同一 key 永远由同一线程处理。
  3. 失败重投乱序：消息 A 处理失败，放入重试队列，而它的后继消息 B 已处理完——A 重新入队后反而排在 B 后面。处理：重试消息保持原 key（进同一分区），且重试期间阻塞该 key 的后续消息（同 key 串行重试），或引入延迟重试（先消费到最新再重放）。
  4. Rebalance 不破坏顺序：只要 offset 提交正确，分区易主后新消费者从已提交位置继续，不会跳过也不会回头，顺序不破坏。真正会破坏顺序的是”提交 offset 后继续处理”这种错误写法。

8. 消费者组：Rebalance、分配策略与 Lag 监控

8.1 为什么需要消费者组

单消费者处理能力有限，且单点故障即消费中断。消费者组让 N 个实例协作消费一个 Topic：每个 Partition 同一时刻只被组内一个实例消费，组内实现负载均衡；实例宕机时分区自动转移给其他实例，实现故障转移。

组的基本组成：group.id 标识组；Group Coordinator（位于某个 Broker 上，根据 hash(groupId) % offsets.topic.num.partitions 落在 __consumer_offsets 的某个分区）管理成员关系和 offset 存储；消费者通过 JoinGroup/SyncGroup/Heartbeat 协议与协调者交互。

8.2 Rebalance 的触发条件

  1. 组成员变化：新消费者加入、消费者主动离开（unsubscribe/close）、消费者崩溃（心跳超时被判定下线）；
  2. 订阅的 Topic 分区数变化：kafka-topics.sh --alter --partitions 扩容分区；
  3. 订阅范围变化：正则订阅（如 subscribe("orders.*")）匹配到新 Topic；
  4. 消费速度过慢被踢出：max.poll.interval.ms（默认 5 分钟）内未调用 poll()，协调者认为消费者”卡死”，将其移出组并触发 Rebalance——这是消费端最常见的隐性触发源。

Rebalance 期间组内消费整体暂停，且 Eager 协议下所有消费者先放弃全部分区再重新分配（stop-the-world），因此频繁 Rebalance 是消费抖动和积压的头号元凶。

8.3 三种分区分配策略（partition.assignment.strategy）

  • RangeAssignor（默认）：按 Topic 逐个排序分配。以消费者排序列、分区排序列，平均切块。缺点：每个 Topic 单独计算，分区数不能被消费者数整除时，排在前面的消费者多拿分区；订阅多个 Topic 时倾斜被放大。例：2 个消费者、3 个分区，C0 拿 [0,1]，C1 拿 [2]。
  • RoundRobinAssignor：所有订阅 Topic 的全部分区合并成一个环，轮流分配给消费者。整体最均衡，但每次 Rebalance 全量重新计算，分区迁移多。
  • StickyAssignor：分配结果在”均衡”和”最小化分区迁移”之间取平衡，Rebalance 时尽量保留原分配，减少不必要的分区转移。
  • CooperativeStickyAssignor（推荐生产使用）：Sticky 之上叠加增量式 Rebalance（KIP-429）：先分配好新归属再逐步 revoke 需要移交的分区，全组不需要 stop-the-world，大幅减少 Rebalance 停顿。3.x 默认同时注册了 Range 和 CooperativeSticky，若要享受增量式再平衡需显式配置 partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor。

8.4 静态成员（KIP-345）

group.instance.id 给消费者一个固定身份。普通消费者每次重启都是”新成员”，必然触发 Rebalance；静态成员离线时，Coordinator 会保留其分区所有权直到 session.timeout.ms 超时，短暂的滚动发布、客户端重启不再触发 Rebalance。适合发布频繁或对 Rebalance 敏感的线上服务。

8.5 Consumer Lag 监控

  • 定义：某分区上”消费者已提交的 offset”与”分区当前 LEO”之差，即未消费的消息数量。
  • 查看命令：kafka-consumer-groups.sh --describe --group order-group --members --verbose，或接入 Burrow、Kafka Lag Exporter、Confluent Control Center 等监控工具并配告警。
  • Lag 持续增长的常见原因：
    • 消费者实例数小于分区数（并发上限就是分区数）；
    • 单条消息处理慢：业务逻辑重、下游（数据库/RPC）慢；
    • max.poll.records 太大导致单次 poll 处理超时，被 max.poll.interval.ms 踢出组，陷入”处理超时 → Rebalance → 重复消费 → 更慢”的恶性循环；
    • 分区分配不均（Range 策略倾斜或 key 倾斜导致热点分区）。
  • 处理手段：扩容消费者（数量不超过分区数，超过无用）；提升单消费者吞吐（批处理、异步化、优化下游）；调 fetch.min.bytes / fetch.max.wait.ms 提高拉取效率；排查下游故障；检查 max.poll.interval.ms 是否触发踢组。

9. KRaft 架构：为什么去掉 ZooKeeper

9.1 ZooKeeper 模式的问题

Kafka 2.7 及之前，元数据（Broker 注册、Controller 选举、Topic 配置、ACL、旧版 offset）全部依赖外部 ZooKeeper：

  • 两套系统、两套一致性协议：元数据变更先写 ZK，再同步给 Broker，链路长、延迟高，且 ZK 的 watch 机制在大规模下（数万分区）有通知风暴和写放大问题；
  • 运维复杂：ZK 集群本身要 3/5 节点部署、监控、升级，且 ZK 集群规模不能随意扩展；
  • 扩展性天花板：集群规模（Broker 数、分区数）被 ZK 的元数据能力卡死。

9.2 KRaft 的实现

KRaft 把 ZooKeeper 的职责收编为 Kafka 内部的 Controller Quorum（Raft 组）：

  • Controller 选举：process.roles=controller 的节点组成奇数个（生产建议 3 或 5）的 Raft Quorum，通过 Raft 协议选出唯一的 Active Controller。Active Controller 负责所有元数据写入（创建 Topic、分区 Leader 选举、Broker 上下线登记），其余 Controller 作为 Raft 投票节点参与选举和日志复制。
  • 元数据日志：所有元数据变更作为消息追加到一个单分区的 __cluster_metadata 日志中（和普通数据 Topic 同样的 append-only 结构），由 Active Controller 领导写入、Raft 复制到其他 Controller；Broker 通过元数据 API 订阅增量更新（3.4+ 支持纯 Controller 角色后，Broker 不再参与 Raft，只拉取元数据）。元数据从 ZK 时代的”watch 通知”变成强一致的日志复制 + 增量同步。
  • 部署形态：小集群可合设 process.roles=broker,controller；生产推荐独立 Controller Quorum，通过 controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093 指定。

优势总结：架构简化（自包含，无需单独运维 ZK）；元数据操作单跳、Raft 强一致；可扩展性大幅提升（目标支撑数十万分区）；元数据通信复用 Kafka 的 SSL/SASL 安全机制，安全模型统一。

9.3 版本演进与现状

  • 2.8 引入 KRaft 预览（KIP-500）；3.0 支持新集群使用；3.3 正式 GA；3.5 起 ZooKeeper 模式标记为废弃并支持 ZK 到 KRaft 的在线迁移；Kafka 4.0 已彻底移除 ZooKeeper。
  • 面试结论：新集群一律用 KRaft，ZooKeeper 模式已退出历史舞台；旧集群迁移走官方迁移工具（滚动迁移，KIP-866）。

10. 常见问题排查

10.1 消息积压

排查步骤：

  1. kafka-consumer-groups.sh --describe --group <group> 看各分区 Lag；
  2. 观察 Lag 分布：均匀增长 → 整体消费能力不足；集中在少数分区 → 分配不均或 key 热点导致单分区吞吐瓶颈；
  3. 看消费者日志：是否频繁 Rebalance（max.poll.interval.ms 超时踢组）；看 GC 日志和下游（数据库/RPC）耗时埋点。

处理手段（按优先级）：

  1. 扩容消费者：加到分区数为止（超过分区数的消费者拿不到分区，白加）；
  2. 提升单条处理速度：批量化、异步化、精简逻辑、优化下游（一次查询合并、加索引）；
  3. 调参：适当加大 fetch.min.bytes/fetch.max.wait.ms 攒批拉取，检查 max.poll.records 是否过大导致单次处理超时；
  4. 极端情况临时跳堆：允许丢失的业务直接 seekToEnd() 跳过积压，或临时把消费逻辑换成”只计数不处理”——注意跳堆会破坏顺序，只适用于可丢场景；
  5. 长期方案：拆 Topic（按业务分流）、增加分区（配合生产端 key 设计）、改造消费链路。

10.2 重复消费

定位原因：看 ConsumerRebalanceListener 的 revoke/assign 日志（Rebalance 频率）；看是否 max.poll.interval.ms 超时踢组（处理慢导致分区易主）；看 offset 提交代码是否在异常路径漏提交或提交在业务处理之前。

处理：

  1. 手动提交且处理成功后再提交（commitSync()），保证”提交过的一定处理过”；
  2. 提交频率与处理频率匹配——小批量频繁提交，缩小重复窗口；
  3. 静态成员（group.instance.id）减少非必要 Rebalance；
  4. 业务幂等兜底是最终防线：唯一键、数据库唯一约束、条件更新（第 6.3 节）。重复只能被”容忍并去重”，无法被”消灭”。

10.3 Leader 抖动

现象：kafka-topics.sh --describe 看到 ISR 反复收缩扩大、Broker 日志频繁出现 Leader election；伴随 UnderReplicatedPartitions 指标抖动；ISR 低于 min.insync.replicas 时生产端报 NotEnoughReplicasException。

常见根因：

  1. 网络抖动：Follower 拉取超时（replica.lag.time.max.ms 默认 30s）被移出 ISR，网络恢复后又追平加入，ISR 反复抖动；
  2. Broker 负载过高 / Full GC：Follower 端处理请求变慢，拉取赶不上；
  3. 磁盘慢：慢盘导致写日志、读日志延迟飙升；
  4. 配置过紧：replica.lag.time.max.ms 或 session.timeout.ms 设得太小，把抖动放大成频繁切换。

排查与处理：查 Broker 日志中的 “ISR shrinks/expands”、Leader 切换记录，对应时间点查 GC 日志（Full GC 频率）、网络重传、磁盘 IO 等待（iostat）；对慢盘下线隔离；把 replica.lag.time.max.ms 从默认 30s 适度调大，给抖动留缓冲；跨机房部署时重点排查专线质量。

10.4 消费失败重试与死信队列

先澄清：Kafka Broker 没有原生死信机制（没有 NACK/requeue/TTL 这些 RabbitMQ 概念）。死信是消费者侧的一种通用模式：**重试 N 次仍失败的消息，写入一个专门的”死信 Topic”**，由人工或专用程序处理。这也是”死信队列”类问题在 Kafka 面试中的标准回答。

实现要点：

  1. 把异常分两类：可重试（下游超时、限流，重试有望成功）进重试队列或本地延迟重试；不可重试（数据格式错误、业务规则不满足，重试必然失败）直接进死信；
  2. 死信消息要保留完整上下文：原 Topic、原 Partition、原 offset、消息体、失败原因、失败时间，方便排查与回放；
  3. 死信要有人消费：配告警、建查询页面，死信无限堆积等于没做；
  4. 重试/死信消息保持原 key，保证和原消息在同一分区，顺序可追溯。

面试一句话：Kafka 的可靠性链路是”acks=all + ISR + 手动提交”保证不丢，业务侧”幂等去重”保证不重，处理失败的消息用”重试 Topic + 死信 Topic”隔离兜底，死信必须有告警和人工介入。

11.3 常见性能问题

Producer 发送慢 / 吞吐低：

  1. 检查攒批参数：batch.size 和 linger.ms 是否太小（默认 16KB/0ms 基本不攒批，批量收益没吃到）→ 调大并开启压缩；
  2. 日志报 TimeoutException：看 buffer.memory 是否打满（max.block.ms 超时）→ 调大缓冲或加快消费侧；
  3. 单分区写入是瓶颈：分区数不够时所有消息挤一个分区，单分区吞吐封顶 → 增加分区数（配合 3.5 的估算方法）；
  4. 对照检查网络带宽与压缩率——compression.type 从 none 改 lz4 往往立竿见影。

Consumer 消费慢 / 消息积压：

  1. 实例数 < 分区数：消费并发上限就是分区数，先 kafka-consumer-groups.sh --describe 确认分配是否均匀；
  2. 单条处理慢：批处理、异步化、优化下游（SQL 加索引、合并请求）；
  3. 拉取效率低：fetch.min.bytes 太小导致”一次拉一点点”→ 调大到几 MB；
  4. max.poll.records 与 max.poll.interval.ms 的平衡：调大 records 后必须确认处理时间不超踢组阈值，否则陷入”处理超时 → 踢组 → 重复消费 → 更慢”循环。

排查思路一句话：先看分配（组内是否均匀、实例数 vs 分区数），再看处理（单条耗时埋点），最后调参（攒批/拉取/超时）。

11.4 延时队列在 Kafka 中的实现方案

Kafka 原生没有 RocketMQ 那种”延迟消息”功能（KIP-887 的原生延迟投递在较新版本中才以实验特性出现），生产实现普遍是业务侧方案：

方案一：时间轮 + 延迟 Topic（简单可靠）

  • 专门建一个 delay-topic，消息体里携带”目标执行时间”；一个（或几个）延迟消费者只做一件事：poll 出来后判断是否到期，未到期就不提交并睡眠等待，到期后把消息写入真正的业务 Topic；
  • 优点：实现极简、一条链路；缺点：延迟消费者是单点，且精度受轮询周期限制（睡到到期时间再 poll），积压时到期时间会被推迟。

方案二：分级延迟 Topic（生产常用）

  • 按档位建多个延迟 Topic：delay-5s、delay-30s、delay-1m、delay-10m、delay-1h……每档一个消费者：取到消息后判断”该进入业务 Topic 还是转投下一级延迟 Topic”，类似层级时间轮；
  • 到期即转投，每档消费者各司其职，吞吐高、精度秒级；缺点是档位是离散的（跨档位的时间只能用”下一档 + 重投”逼近）。

与 RocketMQ 对比：

维度 Kafka（自建方案） RocketMQ
原生延迟消息 无（需业务实现） 支持（18 个固定延迟级别，messageDelayLevel）
时间精度 自建分级方案可逼近 只支持预设档位（1s~2h），自定义延迟时间需改造
实现成本 中等（分级 Topic + 定时转投） 零成本，发消息时指定 delayTimeLevel
适用场景 已有 Kafka 生态、高吞吐事件流 交易场景、简单固定档位延迟

选型一句话：消息量小、档位固定选 RocketMQ 原生延迟；消息量大、要任意延迟时间，用 Kafka + 分级延迟 Topic 自建。

1. MySQL 架构概览

回答一个问题：一条 SQL 从客户端发出到返回结果，中间经过哪些组件，它们各自干什么。

1.1 两层架构：Server 层与存储引擎层

MySQL 分为两层：

  • Server 层：负责连接管理、解析、优化、执行以及内置函数（日期、数学、字符串）、存储过程、触发器、视图等通用功能。所有存储引擎共用这一层。
  • 存储引擎层：负责数据的存储与提取。插件式架构是 MySQL 最核心的设计——同样的 SQL，底层可以换成 InnoDB、MyISAM 等不同引擎。

1.2 一条 SELECT 语句的执行流程

一条查询语句依次经过五个组件：

  1. 连接器：建立连接、校验用户名密码、获取权限。连接建立后即使管理员改了权限，也要重连才生效；show processlist 可查看连接状态，空闲连接受 wait_timeout（默认 8 小时）控制。
  2. 解析器：词法分析 + 语法分析，把 SQL 拆成语法树。语法错误在这一步报出。注：MySQL 8.0 已移除查询缓存；8.0 之前会先查查询缓存，命中则直接返回。
  3. 预处理器：检查表和列是否存在、解析别名、校验执行权限（对表的 SELECT 权限在打开表时校验）。
  4. 优化器：基于统计信息选择执行计划——决定用哪个索引、表的连接顺序、是否走索引下推等。
  5. 执行器：按执行计划调用存储引擎接口，逐行判断条件并返回结果。

1.4 一条 UPDATE 语句的执行流程

更新语句比查询多了”修改数据 + 保证持久性”两步，是整个架构的集大成者。一条 UPDATE 的完整流程：

① Server 层：连接、解析、优化

  1. 连接器建立连接，校验身份与权限；
  2. 解析器词法分析 + 语法分析，构建语法树；
  3. 预处理器检查表、列是否存在；
  4. 优化器基于统计信息选择执行计划：决定使用哪个索引定位要更新的行（这是影响更新速度的关键），必要时全表扫描；
  5. 执行引擎按计划调用 InnoDB 接口执行修改。

② InnoDB 层：缓冲池 + 日志先行

  1. 缓冲池查找：InnoDB 先在 Buffer Pool 中查找目标行所在的数据页，不在则从 .ibd 数据文件加载到内存；
  2. 写 Undo Log（关键）：修改前先把旧值写入 undo log（回滚日志）。两个目的：事务回滚时恢复旧值；其他并发事务通过 undo 版本链读到旧版本（MVCC）；
  3. 修改 Buffer Pool：把数据页中的行更新为新值，该页变为脏页（内存与磁盘不一致）；
  4. 写 Redo Log Buffer（关键）：把数据页的物理修改（字节级变化）记入内存中的 redo log buffer。先写日志、后刷脏页，这是 WAL（Write-Ahead Logging）原则——保证崩溃后能重做，也是持久性的来源。

③ 提交阶段：两阶段提交（关键）

  1. Write Redo Log（prepare）：将 redo log buffer 中本事务的记录顺序刷盘，标记为 PREPARE，必要时 fsync()——这是持久性的关键点，也是相对耗时的操作；
  2. Write Binlog：Server 层把逻辑变更写入 binlog（用于主从复制与恢复），同样按 sync_binlog 配置刷盘；
  3. Write Redo Log（commit）：binlog 成功落盘后，在 redo log 中写入 COMMIT 标记，事务在引擎层正式提交；
  4. 释放锁、返回成功。

④ 后台异步刷脏页（非同步操作）

提交成功并不保证脏页立即写回磁盘——redo log 已经保证了持久性。Page Cleaner 线程在以下时机异步刷脏页：

  • 脏页比例过高（innodb_max_dirty_pages_pct 控制）；
  • 系统空闲时；
  • redo log 空间即将用完（回收旧日志前必须先刷对应脏页）；
  • 正常关闭时。

本节小结：Server 层管”怎么执行”，引擎层管”怎么存储”；查询走五件套（连接器→解析器→优化器→执行器→存储引擎），更新在此基础上多了 undo log（可回滚）、redo log（持久化）、binlog（复制与恢复）三个关键环节。细节分别在本文第 5、6 节展开。

2. 索引

回答三个问题：为什么 B+ 树、聚簇索引与二级索引的区别、回表/覆盖索引/最左前缀/索引下推这几个概念怎么串起来。

2.1 B+ 树为什么是 InnoDB 的默认索引结构

B+ 树与 B 树的对比（InnoDB 选择 B+ 树的原因）：

对比维度 B 树 B+ 树 InnoDB 优势体现
数据存储位置 所有节点存储数据 仅叶子节点存储数据 减少磁盘 IO 次数
树高度 较高（数据分散存储） 较低（内部节点纯索引） 3 层 B+ 树可支撑千万级数据
范围查询 需要回溯父节点 通过叶子链表顺序扫描 WHERE id > 100 效率高一个量级
全表扫描 需遍历整棵树 直接顺序遍历叶子节点链表 全表扫描接近顺序读
磁盘利用率 节点含数据，单页存键值少 单页可存更多键值（高分支因子） 相同数据量树高更矮
数据更新代价 可能引起复杂结构调整 插入删除多数情况只需局部调整 支持更高并发写入
缓存命中率 热点数据分散在不同层级 叶子节点集中存储所有数据 Buffer Pool 利用率高

背后的物理原因：磁盘 IO 按页（默认 16 KB）为单位读取，树的层数决定了一次查询的 IO 次数。B+ 树内部节点只存键值 + 指针（不存数据），一页能容纳更多键，树自然更矮；叶子节点用链表串起，范围查询不需要中序遍历。

2.2 聚簇索引 vs 二级索引

维度 聚簇索引（主键索引） 二级索引（辅助索引）
叶子节点内容 完整行数据 索引列的值 + 主键值
每表数量 只能有一个（主键或第一个非空唯一索引） 可以有多个
数据与索引 叶子节点即数据本身，表数据按主键物理排序 与数据物理顺序无关
是否需要回表 不需要 查询字段不在索引中时需要回表

加锁的落点也是索引：InnoDB 的行锁是通过给索引项加锁实现的——没有走索引的 UPDATE/DELETE 会锁住所有行（详见第 4 节）。

2.3 回表、覆盖索引、最左前缀、索引下推

这四个概念是同一件事的四个侧面：二级索引只存”索引列 + 主键”，查询需要的数据不在索引里，就得拿着主键再去聚簇索引查一遍，这就是回表。

回表：查询字段没有全部包含在索引中，需要根据二级索引找到主键，再到主键索引查完整行。

覆盖索引：查询所需的字段全部包含在索引中，无需回表。

覆盖索引是”用空间换回表”：Extra 显示 Using index 即命中覆盖索引。查询只返回索引列、或者只需要主键时，优先考虑覆盖。

最左前缀原则：联合索引 (a, b, c)，查询条件必须从最左列开始、且不能跳过中间列才能命中索引。a=1、a=1 AND b=2 能走索引；b=2、b=2 AND c=3（跳过 a）走不了。

索引下推（ICP，MySQL 5.6+）：把 WHERE 中的过滤条件下推到存储引擎层，在索引遍历时就过滤掉不满足条件的行，减少回表次数。

  • 5.6 之前：引擎层把所有 name LIKE '张%' 的记录全部回表，server 层再过滤 age = 30；
  • 5.6 之后（ICP）：引擎层遍历索引时直接判断 age = 30，只有满足的行才回表。Extra 显示 Using index condition。

2.4 索引失效场景与选错索引

索引失效的常见场景：

场景 示例 原因
对索引列做运算/函数 WHERE DATE(create_time) = '2026-01-01' 索引保存的是列原值，无法按函数结果定位
隐式类型转换 字符串列 WHERE phone = 13012345678 数字被转为字符串比较，索引列发生类型转换
LIKE '%xx' WHERE name LIKE '%张' 前导模糊匹配无法确定扫描起点（张% 可以）
OR 连接非索引列 WHERE name = 'a' OR age > 30（age 无索引） 优化器无法确定只走 name 索引
违反最左前缀 见 2.3 联合索引列序不满足
优化器选错索引 见下 统计信息不准确等

选错索引的原因：优化器基于统计信息（采样）估算扫描行数，可能误判。手动干预：

2.5 面试题：WHERE b=1 AND c=2 ORDER BY a 能否用上组合索引 (a, b, c)

可以，但效率不高——需要扫描全索引，无法索引查找：

  1. 缺少最左列 a，无法用索引做等值查找，只能对 (a, b, c) 索引做索引全扫描；
  2. 扫描过程中对每条索引记录检查 b=1 AND c=2；
  3. 好处是 ORDER BY a 天然满足（索引本身就按 a 排序），不需要 filesort。

结论：能用但低效，实际设计时应让联合索引的最左列与查询条件对齐。

2.6 索引设计原则

  • 区分度优先：优先为区分度高（基数大）的列建索引；区分度低的列（如性别）收益很小；
  • 遵循最左前缀：联合索引的列按查询条件的使用频率排列，高频等值列放最前面；
  • 尽量覆盖：让查询所需的列尽量包含在索引中，避免回表；
  • 控制索引数量：索引不是越多越好，写入时同步维护索引，占用空间和开销；
  • 长字符串用前缀索引：如 URL 可用 ALTER TABLE t ADD INDEX idx_url(url(20))（注意区分度损失）；
  • 避免冗余索引：(a, b) 联合索引已覆盖 (a) 单列索引，后者应删除；
  • 主键要短：二级索引叶子存的是主键值，主键越长，所有二级索引越大。

本节小结：B+ 树用”矮树 + 叶子链表”换磁盘 IO 次数；聚簇索引即数据，二级索引即”列值 + 主键”，两者之间的差价是回表；覆盖索引、最左前缀、索引下推分别从字段、列序、过滤时机三个角度压回表成本。

3.3 count(*)、count(1)、count(id)、count(字段) 的区别

语法 统计逻辑 是否包含 NULL
COUNT(*) 统计所有行（对 InnoDB 而言就是数行数） 包含
COUNT(1) 统计所有行（1 是常量表达式，与列无关） 包含
COUNT(id) 统计 id 列非 NULL 的行数 不包含
COUNT(字段) 统计该字段非 NULL 的行数 不包含

性能：count(字段) < count(id) < count(1) ≈ count(*)

count(字段) 最慢是因为需要解析该列并判断是否为空、拷贝字段值；count(*) 在 InnoDB 中被特殊优化为”数行”而不取列值，因此并不慢。注意 InnoDB 不能像 MyISAM 那样直接返回总数（MVCC 下不同事务看到的行数不同），必须实时扫描；大表 count 的优化思路是缓存计数（Redis 维护计数或独立计数表）。

3.4 分页优化：OFFSET 很大时为什么慢

LIMIT 100000, 10 慢的原因：MySQL 需要先扫描并跳过 offset + limit 行，再返回结果——越到后面的页越慢。

方案一：记录上一页最后一条数据的 ID（推荐）

方案二：子查询先定位边界，再取出该页

分页必须搭配 ORDER BY：缺少 ORDER BY 时，MySQL 返回结果的顺序不确定（引擎层顺序），会导致分页结果混乱或重复。

3.5 IN 和 EXISTS 的区别

  • **IN**：先执行子查询，把结果集加载到内存，再对外部查询做匹配。子查询结果集很大时，内存占用和临时表会成为瓶颈；
  • **EXISTS**：对外部查询的每一行执行一次子查询，只判断子查询是否返回行（不关心具体值），不加载完整结果集。子查询能走索引时性能更好。

现代版本说明：MySQL 5.7+ 对 IN 子查询会做物化（materialization）并自动添加半连接（semi-join）优化，IN 与 EXISTS 经常被优化为同一执行计划，性能差异大幅缩小。面试回答的要点是小表驱动大表：外层表小、子查询结果大用 IN；外层表大、子查询结果小且能走索引用 EXISTS。

本节小结：EXPLAIN 四件套（type/key/rows/Extra）是分析入口；慢日志解决”找出哪条慢”；count 与分页解决”大表计数与深分页”两个高频痛点；IN/EXISTS 的本质差异已经被优化器部分抹平，理解驱动表关系比背结论重要。

4. 锁

回答一个问题：并发写数据时，MySQL 靠什么锁保证正确性，死锁怎么查。

4.1 全局锁、表锁、行锁

全局锁：锁住整个实例。

典型场景：全库逻辑备份（保证备份的一致性快照）。注意 InnoDB 备份更推荐 mysqldump --single-transaction——利用 MVCC 快照，不加全局锁。

表锁：锁粒度是整张表，开销小、冲突大。

此外还有 MDL（元数据锁）：执行 DML 时自动加 MDL 读锁、执行 DDL 时自动加 MDL 写锁，防止”查着表结构被改了”；MDL 写锁排队时可能阻塞后续所有查询，DDL 要错峰执行。

行锁：锁粒度是行（InnoDB 专有），冲突最小、并发最高。加锁对象是索引项——如果 UPDATE/DELETE 没走索引，会退化为锁住所有行（相当于表锁）。

4.2 行锁的三种形态：记录锁、间隙锁、临键锁

InnoDB 的索引分为”记录 + 记录之间的间隙”，行锁由此有三种形态：

  • 记录锁（Record Lock）：锁单行记录；
  • 间隙锁（Gap Lock）：锁记录之间的间隙，不锁记录本身，防止其他事务在间隙中插入数据（防幻读的关键）；
  • 临键锁（Next-Key Lock）：记录锁 + 它前面的间隙锁，即左开右闭区间 (prev, cur]，是 InnoDB RR 级别下的默认行锁。

注意：临键锁的上界是记录本身（15），而不是条件中的上界 20。若表中存在 id=20 的记录，扫描会停在第一个不满足 id < 20 的记录 20 上，对其加临键锁 (15,20]，此时间隙锁范围为 (10,15)、(15,20)。

4.3 意向锁（IS/IX）

行锁与表锁的兼容性检查需要知道”表里有没有行锁”。意向锁就是为了让这个判断变成 O(1)：事务加行锁前，先给表加一个意向锁（IS：意向共享；IX：意向排他），它只是标记，不锁数据。

  • 表级锁与意向锁的冲突矩阵：X 表锁与任何 IS/IX 冲突；S 表锁与 IX 冲突、与 IS 兼容。
  • 意向锁之间互相兼容（它们只表示”表内将要有行锁”），真正的互斥发生在行级别。

4.4 死锁与排查

死锁：两个事务各自持有一把锁，又都在等待对方持有的锁，形成环路，永远无法推进。

  4. 降低并发冲突：合理设计索引、避免热点行集中更新。

本节小结：全局锁管备份、表锁管 DDL/MyISAM、行锁管并发；行锁三形态里临键锁是”记录 + 间隙”的组合，是 RR 级别防幻读的当前读手段；死锁不可完全避免，靠检测 + 重试 + 固定顺序访问控制风险。

4.5 插入意向锁（Insert Intention Lock）

什么是插入意向锁：事务执行 INSERT 时，在插入记录之前，会先对”插入位置所在的间隙”加一把插入意向锁（Insert Intention Lock）——它是间隙锁（Gap Lock）的一种变体，表示”我准备往这个间隙里插数据”。注意命名容易混淆：它属于意向锁家族（与 4.3 的 IS/IX 并列），而不是记录锁/间隙锁那一族。

与间隙锁的区别（核心考点）：

锁 A \ 锁 B 间隙锁（Gap） 插入意向锁（Insert Intention）
间隙锁 同一间隙上互斥（都会阻塞） 冲突：间隙锁阻塞插入意向锁（这就是”间隙锁阻止插入”的锁层面实现）
插入意向锁 冲突（要插必须等间隙锁释放） 互相兼容：多个事务可以同时对同一间隙持有插入意向锁（各自插各自的位置）

5. 事务与 MVCC

回答一个问题：事务的隔离性靠什么实现——undo log 版本链 + ReadView 组成的 MVCC。

5.1 ACID

事务保证一组操作要么全执行、要么全不执行。事务支持在引擎层实现（InnoDB 支持，MyISAM 不支持）。

持久性（Durability） 提交后修改永久保存 redo log（WAL）

5.4 MVCC 实现原理

MVCC（Multi-Version Concurrency Control）靠两样东西：undo log 版本链 + ReadView。

① 版本链

InnoDB 为每行数据生成两个隐藏列：

  • DB_TRX_ID：最后修改该行的事务 ID；
  • DB_ROLL_PTR：指向 undo log 中旧版本的回滚指针。

每次修改都会在 undo log 中留下旧版本，通过回滚指针串成一条版本链：最新的版本在前，旧版本依次指向后。多个版本并行存在，这就是”多版本”。

② ReadView（读视图）

事务做快照读时生成一个 ReadView，用于判断版本链上哪个版本对当前事务可见：

可见性判断规则（对版本链上的每个版本，用其 trx_id 判断）：

  1. trx_id < min_trx_id → 该版本由已提交事务产生，可见；
  2. trx_id 在 m_ids 中（活跃）→ 未提交，不可见；
  3. trx_id >= max_trx_id → 由 ReadView 生成之后的事务产生，不可见；
  4. 不可见时沿 DB_ROLL_PTR 找到上一个版本继续判断，直到可见版本或版本链尽头（尽头为空则记录不存在）。

③ ReadView 的生成时机决定隔离级别：

  • READ COMMITTED：每次 SELECT 都创建新的 ReadView——能看到最近已提交的版本（解决了脏读，但两次 SELECT 之间别的提交会让结果变化，即不可重复读）；
  • REPEATABLE READ：事务中第一次 SELECT 时创建 ReadView，之后整个事务复用——后续 SELECT 看到的永远是同一份快照（解决了不可重复读）。

5.5 隔离级别与幻读的真相

标准 SQL 定义里 RR 会幻读，但 InnoDB 的 RR 下：

  • 快照读（普通 SELECT）：MVCC 保证整个事务看到一致的快照——新增的行不在快照里，不会幻读；
  • 当前读（FOR UPDATE / UPDATE / DELETE）：临键锁（记录锁 + 间隙锁）锁住记录和间隙，其他事务插不进新行，不会幻读。

所以 InnoDB 的 RR 实际上消除了幻读（这也是为什么 MySQL 默认用 RR 且很少提到幻读问题）。如果要把幻读问题讲得更完整：唯一残留的幻读场景是”先快照读、后当前读”的混合边界情况；SERIALIZABLE 级别把所有快照读也升级为当前读，代价是并发度骤降。

本节小结：undo log 提供多版本（可回滚、可读旧值），ReadView 提供”哪些版本对我可见”的判断，锁（临键锁）兜住当前读的间隙；RC 与 RR 的差别只是 ReadView 的生成时机不同，这一句话就能串起整个 MVCC。

6. 日志

回答一个问题：崩溃后数据凭什么不丢——redo log 的 WAL 机制，以及它和 binlog 如何通过两阶段提交保持一致。

6.1 redo log 与 WAL

redo log（重做日志，物理日志）：记录”在哪个数据页的哪个偏移量做了什么修改”，例如”表空间 X、页号 Y、偏移量 Z 起 4 字节被改为 0x12345678”。它不关心 SQL 是什么，只记录物理变化。

WAL（Write-Ahead Logging，先写日志、后刷数据） 的核心：改数据页是随机 IO，慢；写日志是顺序 IO，快。所以先落日志、再异步刷脏页。只要 redo log 落盘，事务就算持久化了——崩溃后从 redo log 重放即可恢复。

redo log 的刷盘策略由 innodb_flush_log_at_trx_commit 控制：

取值 行为 安全性
0 每秒写入并刷盘 最差：崩溃最多丢 1 秒事务
1 每次事务提交时写入并刷盘（默认） 最好：崩溃不丢已提交事务
2 每次提交写入 OS 缓存，每秒刷盘 中：MySQL 崩溃不丢，OS 崩溃最多丢 1 秒

redo log 是循环写入的（ib_logfile0、ib_logfile1 一组），日志文件写满后会触发检查点（checkpoint）：把 checkpoint 之前的脏页刷盘后，日志空间才能复用。redo log 只服务于崩溃恢复，用完即覆盖，不做历史归档。

6.2 binlog 三种格式

binlog（二进制日志，逻辑日志）：由 Server 层记录，用于主从复制、时间点恢复、数据审计。根据格式记录内容不同：

格式 记录内容 优点 缺点
STATEMENT 原始 SQL 语句 日志小、易读 非确定性函数（UUID()、NOW()）可能导致主从不一致
ROW（8.0 默认） 被修改行的前后值（before/after 镜像） 最安全，与执行环境无关；还支持闪回 批量操作日志量巨大
MIXED 默认 STATEMENT，遇到非确定性语句自动切 ROW 两者兼顾 行为不完全可预期

binlog 刷盘由 sync_binlog 控制：0 依赖 OS 刷新（性能最好、风险最高）；1（默认）每次提交后刷盘；N 每 N 个事务刷一次（折中）。

6.3 redo log vs binlog 对比

特性 redo log binlog
所属层级 InnoDB 存储引擎层 MySQL Server 层
主要作用 崩溃恢复，保证持久性 主从复制、时间点恢复、审计
日志类型 物理日志（页面修改） 逻辑日志（SQL 或行变化）
写入时机 事务执行过程中持续写 事务提交时一次性写
写入方式 顺序写，循环文件（用完覆盖） 追加写，可长期保存
刷盘策略 innodb_flush_log_at_trx_commit sync_binlog
内容格式 InnoDB 私有格式 STATEMENT / ROW / MIXED
生命周期 检查点后即可覆盖 按策略清理或归档

6.4 两阶段提交

redo log 在引擎层、binlog 在 Server 层，两套独立的日志、两个独立的刷盘时机。如果各写各的，崩溃时会不一致：例如引擎层已提交、binlog 还没写，主从复制就会丢事务（从库数据缺失）；或者 binlog 已写、引擎层没提交，从库多执行一个事务（数据不一致）。两阶段提交把这两个日志的写入绑成一个原子动作：

  1. Prepare 阶段（InnoDB）：事务的 redo log 写入并刷盘，标记为 PREPARE——此刻磁盘上已有”该事务改了什么”；
  2. Write & Sync Binlog（Server）：binlog 事件写入并刷盘（sync_binlog=1）——此刻磁盘上已有”该事务执行了什么”；
  3. Commit 阶段（InnoDB）：在 redo log 写入 COMMIT 标记，事务正式提交。

关键顺序：先 redo prepare，再写 binlog，最后 redo commit。

6.5 崩溃恢复

崩溃后 InnoDB 从最近的 checkpoint 处扫描 redo log 重放，逐个事务按状态恢复：

崩溃发生时机 事务状态 恢复动作
redo prepare 之前 未写入 redo 直接丢弃（事务本身未提交，undo log 负责回滚已改的脏页）
redo prepare 之后、binlog 写之前 PREPARE，binlog 中无该事务 回滚——binlog 没有它，主从要一致就不能提交
binlog 写完之后、redo commit 之前 PREPARE，binlog 中有该事务 重做（提交）——binlog 已有该事务，从库会执行，主库必须也提交

也就是说：恢复时以 binlog 为准判断一个 PREPARE 状态的事务是提交还是回滚，这保证主库与从库、与 binlog 恢复出来的库永远一致。

本节小结：redo log 用 WAL 换持久性（引擎层、循环写），binlog 换复制与恢复（Server 层、追加写）；两阶段提交让”引擎层状态”与”Server 层日志”在崩溃时保持一致，崩溃恢复时以 binlog 有无为准决定 PREPARE 事务的生死。

7.2 Buffer Pool（缓冲池）

本质：数据库的内存缓存区域，缓存从磁盘读取的数据页和索引页。所有数据读写都发生在内存，这是 InnoDB 性能的核心。

  • 读：优先从 Buffer Pool 读取，未命中则读磁盘并加载（预读机制：一次读入相邻的多个页）；
  • 写：修改发生在 Buffer Pool 的脏页上，同时写 redo log 保证持久性；脏页由后台线程按 LRU 淘汰、检查点、空闲等时机异步刷盘（innodb_buffer_pool_size 建议设为物理内存的 60%~75%）。

LRU 的细节：InnoDB 的 LRU 分为 young/old 两段（5/8 处划分），全表扫描等大查询只污染 old 区，不会把真正的热点数据挤出——这是对朴素 LRU 的重要修正。

7.3 Change Buffer（变更缓冲）

解决什么问题：非唯一二级索引的页不在 Buffer Pool 时，传统做法要先把索引页从磁盘读进来才能改——这是随机 IO，很贵。Change Buffer 把这次修改”缓冲”下来，延迟合并，减少随机磁盘 IO。

  • 作用对象：仅限非唯一二级索引的 INSERT/UPDATE/DELETE。主键/聚簇索引（数据就在内存页上）不适用；唯一索引必须立即加载索引页校验唯一性，也不适用；
  • 工作方式：索引页不在内存 → 把修改记录到 Change Buffer（修改本身照常写 redo log）；合并（Merge）时机：该索引页被读入内存时、后台 Purge 线程、检查点、Server 空闲、Change Buffer 满、关闭数据库时——读页时把缓冲的修改应用上去，页变脏后再走正常刷盘；
  • 适用场景：写多读少、修改后不立即读的二级索引收益最大；写密集且读频繁的热点索引反而可能”延迟写入变成本地读”。

7.4 自适应哈希索引（AHI）

本质：InnoDB 根据运行时的访问模式自动为频繁访问的索引页构建哈希索引，等值查询命中时直接 O(1) 定位，跳过 B+ 树逐层查找。

要点：由 InnoDB 自动维护、不能人为创建；只对等值查询有效（范围查询走不上）；缓存的是”索引页内的匹配位置”，随页面淘汰而重建；可通过 innodb_adaptive_hash_index 关闭（并发极高、AHI 成为瓶颈时）。

7.5 Doublewrite（双写缓冲）

解决什么问题：磁盘写页不是原子的——断电或系统崩溃时，一个 16 KB 的页可能只写了一半（部分页写入 / torn page）。此时页损坏，redo log 也无法恢复：redo 记录的是”在页上的修改”，前提是页本身完好。

机制：脏页刷盘前，先顺序写入 doublewrite buffer（共享表空间中两块连续的 1 MB 区域），fsync 后再写入实际数据文件。恢复时先检查 doublewrite 中的页副本，页损坏则用副本修复，再应用 redo log。

代价与权衡：每次刷盘多写一份（写放大），但它是顺序写，代价可控；换来的是一旦崩溃，页损坏问题有副本兜底（redo log 才能正常重放）。这也是 InnoDB 相比 MyISAM 崩溃恢复可靠的原因之一。8.0.20+ 对 doublewrite 的页合并与加载做了进一步优化，默认开启即可。

本节小结：Buffer Pool 让所有读写发生在内存；Change Buffer 推迟二级索引的随机 IO；AHI 用哈希加速等值查询；Doublewrite 用”先写副本”解决部分页写入——四个机制分别回答”快、更省、更快、更稳”。

8. 连接池优化

本节要解决什么问题：连接池为什么必须存在、HikariCP 参数怎么配、池多大才合适，以及”连接打满”怎么排查。

8.1 为什么需要连接池

MySQL 连接的建立成本很高：TCP 三次握手 + MySQL 认证（密码校验、权限加载）+ 会话初始化，一次完整建连要几毫秒到几十毫秒；高并发下”每个请求都建连”会把时间全耗在握手和认证上。连接池做的两件事：

  1. 复用：建好的连接放池子里循环使用，避免反复握手认证；
  2. 限流：池大小就是数据库的”并发上限”，防止应用把数据库的连接数打爆。

MySQL 单机的连接上限是硬约束：max_connections 默认 151，每个连接占用一个线程 + 内存（数百 KB 起步），连接数上去后线程切换和锁竞争反而让吞吐下降。连接池是”应用侧保护数据库”的第一道闸门。

Java 生态三选一：HikariCP（Spring Boot 默认，性能最好）、Druid（阿里，监控最强）、c3p0/DBCP（老项目遗留）。

8.2 HikariCP 核心参数

参数 默认值 说明
maximumPoolSize 10 池中最大连接数（含闲置），也是数据库并发上限
minimumIdle 与 maximumPoolSize 相同 池中保底的空闲连接数（恒为最大值时连接不退）
connectionTimeout 30000ms 从池中取连接的最大等待时间，超时抛 SQLTransientConnectionException（见 8.4）
idleTimeout 600000ms 空闲连接被回收的阈值（仅当 minimumIdle < maximumPoolSize 时生效）
maxLifetime 1800000ms 连接最大存活时间，**必须小于数据库 wait_timeout**（默认 8 小时），防止用上已被 MySQL 侧断开的死连接
keepaliveTime 0（不探测） 周期性向空闲连接发探活，提前踢掉坏连接
validationTimeout 5000ms 校验连接可用性的超时

三个高频坑：**maxLifetime 配得比数据库 wait_timeout 大（拿到被 MySQL 断掉的连接，报 Communications link failure）；connectionTimeout 太小（业务高峰期正常排队也超时）；minimumIdle = maximumPoolSize 时连接池永不回收空闲连接**（闲置期也占着数据库连接）。

8.3 连接池大小公式

HikariCP 官方建议：

  • core_count：CPU 核心数；effective_spindle_count：磁盘数（机械盘按盘片数算，SSD 视为 0）。
  • 8 核 + SSD 机器 → 8 × 2 + 0 = 16 条连接；8 核 + 4 块机械盘 → 20 条。

为什么这么小：公式面向”CPU 密集 + 短查询”的典型 OLTP 场景。连接本质是线程，超过 CPU 核心数后，线程切换和数据库侧锁竞争会让吞吐不升反降——连接不是越多越好。

工程修正方向：

  1. 查询以 IO 等待为主时（慢查询、远程调用、大事务），按 Little’s law 估算：连接数 ≈ 峰值 QPS × 单查询平均耗时（秒）。例：QPS 200、平均查询 50ms → 200 × 0.05 = 10 条，与公式同数量级；如果单查询 500ms，就奔着 100 条去了；
  2. 按数据源分层：订单主库（短事务、高频）用小池，报表库（长查询）单独调大，日志库干脆开小池限流；
  3. 压测验证：调完池大小用压测数据说话，盯”取连接等待时间”这个指标（打满前它会先涨）。

误区：**”池越大吞吐越高” ✗**——池大 = 数据库线程多、内存多、锁竞争大，超过拐点后吞吐反降，唯一变好的是”排队取连接”的假象。

9. 数据库设计

回答一个问题：表怎么建才不生异常——范式是底线，反范式是性能妥协，两者如何权衡。

9.1 候选码与函数依赖

候选码：关系模式中能够唯一标识每一行数据的最小属性集。多个候选码中选一个作为主键，一个关系只能有一个主键。

函数依赖：属性集 X 的值确定属性集 Y 的值，记作 X → Y。

  • 完全函数依赖：X → Y，且不存在 X 的真子集能推出 Y（如 {Sno, Cname} → Grade）；
  • 部分函数依赖：存在 X 的真子集 X' 使得 X' → Y（如 {Sno, Cname} → Sname，其实 Sno → Sname）；
  • 传递函数依赖：X → Y，Y → Z，则 X → Z（如 Sno → Sdept，Sdept → Mname）。

9.2 不规范设计带来的异常

假设有一个学生课程关系模式（候选码 {Sno, Cname}）：

Sno Sname Sdept Mname Cname Grade
1 学生-1 学院-1 院长-1 课程-1 90
2 学生-2 学院-2 院长-2 课程-2 80
2 学生-2 学院-2 院长-2 课程-1 100
3 学生-3 学院-2 院长-2 课程-2 95

这个模式不符合范式，存在四类异常：

异常 表现 根因
数据冗余 学生-2、学院-2 等数据重复出现 属性依赖了部分主键
插入异常 学生尚未选课就无法插入（Cname 不能为空时） 主键部分为空
修改异常 只修改其中一条的学院信息，导致数据不一致 冗余导致一处改动多处
删除异常 删除课程-1 的记录会连带丢失学生-1 的信息 多语义混在一张表

9.3 范式：1NF / 2NF / 3NF

范式 要求 解决
1NF 每个属性都是不可分割的原子项（列不可再拆） 建表底线
2NF 满足 1NF，且不存在部分函数依赖（所有非主属性完全依赖主键） 冗余、插入/删除异常

9.4 反范式化

完全遵循范式的代价是大量连表查询（每个查询都要 join）。反范式是牺牲部分规范性换取性能：

手段 做法 收益
增加冗余列 在多个表中保存相同列 避免连表
增加派生列 存可由其他数据计算出的列（如订单表存”商品快照价格”） 减少查询时的计算量
重新组表 把高频连表的结果合成一张表 减少 join
分割表 垂直分割（按列拆）、水平分割（按行拆/分表） 降低单表压力

反范式的代价与之对称：数据冗余（存储浪费）、数据不一致（一处改动多处失效）、增删改效率降低、可能重新引入异常。工程上的常规做法：

  • 核心交易表守范式：订单、账户等强一致数据按 3NF 设计；
  • 查询/报表场景放开：冗余”商品名称、价格快照”到订单表——订单创建后商品可能改名，反而需要快照；
  • 一致性兜底：冗余字段由应用层或定时任务维护，接受最终一致。

本节小结：范式按”完全依赖、直接依赖”逐级消除异常，是数据一致性的设计底线；反范式在读多写少、连表昂贵的场景用空间换时间，但必须清楚它重新引入了不一致风险，需要用快照语义或异步同步兜底。

1.0 面试官为什么问版本

版本问题考察的不是”记住了哪些新特性”，而是三件事：

1.1 Java 8（2014，LTS）：函数式编程进入 Java 生态

为什么需要：Java 8 发布时语言已 18 岁，上一轮语言级大改是 JDK 5 的泛型。此时多核 CPU 已经普及，但 Java 处理集合的方式仍是”for 循环 + 临时变量”，并发手段仍是原生线程 + synchronized。函数式编程（Lambda、流式处理）正是为解决两件事：

  • 样板代码：匿名内部类写一个 Runnable、Comparator 要十几行；
  • 集合处理声明式化：过滤、映射、归约这类操作，用流水线表达比命令式循环更清晰、更易并行。

怎么实现的：Lambda 不是语法糖展开成匿名类，而是由编译器生成 invokedynamic 调用点，由 LambdaMetafactory 在运行期生成函数式接口的实现类——性能接近手写匿名类。

Lambda 表达式

函数式接口

只有一个抽象方法的接口，可用 @FunctionalInterface 注解标记——它同时约束了接口不能有第二个抽象方法，避免误用。

方法引用

简化 Lambda 表达式，直接引用已有方法。四种形式：类::静态方法、对象::实例方法、类::实例方法、类::new（构造器引用）。

默认方法

Stream 要加在 Collection 接口上，但 Collection 有成千上万个实现类。如果直接给接口加抽象方法，所有实现类都会编译失败。默认方法的引入让接口可以在不破坏现有实现的前提下演化 API——这是 Java 8 能新增 Collection.stream() 的前提。

Stream API

惰性求值是 Stream 的灵魂：中间操作（filter/map）不立即执行，只是登记流水线，直到遇到终端操作（collect/reduce/forEach）才一次性执行。这允许只遍历一次完成整个流水线。

陷阱：parallelStream() 默认使用共享的 ForkJoinPool.commonPool()，CPU 密集任务并行度 = 核心数，且与其它并行流互相抢占；对 IO 任务不如专用线程池；对有序、有状态的中间操作（limit、collect 到有序集合）并行反而更慢。

Optional 类

Optional 的本质不是消除 NPE，而是把”可能为 null”变成类型签名的一部分，强迫调用方显式处理。注意它本身不推荐用作字段或方法参数，只用于返回值。

新的日期时间 API（JSR 310）

为什么需要：java.util.Date 是可变对象（线程不安全），且 API 混乱——年份从 1900 起算、月份从 0 起算，SimpleDateFormat 也不是线程安全的。新 API 全部不可变 + 线程安全，并且纳入 ISO 8601 标准体系。

1.2 Java 11（2018，LTS）：模块化成熟、var、HTTP Client、ZGC

为什么需要：JDK 9~11 解决了两个积累已久的问题——巨型单体 JDK（rt.jar 约 66MB，无法按需裁剪，内部实现类缺乏封装）和网络编程 API 的老化（HttpURLConnection 只支持 HTTP/1.1、阻塞式、API 难用）。同时 GC 领域首次出现”停顿时间与堆大小无关”的收集器。

模块化（JPMS，JDK 9，JEP 261）

rt.jar 被拆分为 90+ 个模块，每个模块在 module-info.java 里声明导出和依赖，实现强封装；新增 jlink 工具可按模块裁剪出最小运行时。

升级影响：JDK 8 → 9 是历次升级中最痛的一步——sun.misc.* 等内部 API 被封装后直接编译失败（--add-exports 可临时绕过），大量老框架在 9 上不兼容。这也是很多团队直接 8 → 17 的原因。

var 局部变量类型推断（JDK 10，JEP 286；JDK 11 JEP 323 扩展到 Lambda 参数）

var 是编译期推断、运行期仍是静态类型——它不是 JavaScript 的 var，类型在编译后已经确定，只是不用手写。JDK 11 允许在 Lambda 参数上用 var（通常与注解配合才有意义，因为注解不能标在隐式类型参数上）。

新的字符串方法

新增 isBlank()、lines()、strip()、repeat() 等方法。注意 strip() 比 trim() 更正确——trim() 只去掉码点 <= 0x20 的字符（按 char 处理），strip() 按 Unicode 空白规则处理（支持全角空格等）。

标准 HTTP 客户端（JDK 11 转正，JEP 321）

在 JDK 9 以孵化器模块（incubator）引入，JDK 11 正式转正，替代老朽的 HttpURLConnection，支持 HTTP/2 多路复用和 WebSocket，且提供同步（send）和异步（sendAsync 返回 CompletableFuture）两种调用方式。

文件读写与集合转数组的简化

Files.readString() / writeString() 让文件读写一行搞定；Collection.toArray(IntFunction) 让”集合转数组”不再需要先 new 一个空数组。

ZGC（JDK 11 引入，JEP 333 实验性）

为什么需要：传统收集器的停顿时间随堆大小增长——堆到 1TB 时，G1 的一次 Full GC 停顿可能达到秒级，大内存服务无法接受。

怎么实现的：ZGC 采用染色指针（Colored Pointer）+ 读屏障（Read Barrier），绝大多数 GC 工作与业务线程并发执行，停顿时间 < 10ms 且与堆大小无关。

成熟路径：JDK 11 实验性（需 -XX:+UnlockExperimentalVMOptions -XX:+UseZGC）→ JDK 15 转正（JEP 377，生产可用）→ JDK 17 完善并发类卸载等，成为大堆低延迟场景的标准答案。

1.3 Java 17（2021，LTS）：sealed class、模式匹配推进、ZGC 成熟

为什么需要：JDK 8 的免费维护已停止，17 是承接 8 项目升级的最重要 LTS。语言层面，模式匹配（pattern matching）作为 JDK 14 以来的主线工程在 17 完成第一块拼图，同时 sealed class 解决了”类层次失控”的问题。

模式匹配 instanceof（JDK 16 转正，JEP 394）

为什么需要：instanceof 检查 + 强转是两个重复的步骤，”检查后必然转换”是样板代码。模式匹配把两者合成一步。

sealed class（JDK 17 转正，JEP 409）

为什么需要：没有修饰符时任何类都能继承一个类，大型项目里类层次失控（”不知道谁继承了我”），审计困难。sealed class 让继承关系显式可控——只能列出白名单子类。它也是模式匹配穷举性检查的前提（编译器能确认 switch 覆盖了所有子类）。

文本块（JDK 15 转正，JEP 378）

为什么需要：多行字符串（SQL、HTML、JSON）在旧语法里要手动 \n + 转义，可读性极差，还容易写错缩进。

伪随机数生成器 API（JDK 17，JEP 356）

统一了 20 多种随机数算法的接口：RandomGenerator 接口 + RandomGeneratorFactory 工厂，可在运行期按名称选择算法（如高性能的 L32X64MixRandom），不再被 Random 的默认算法绑死。

switch 模式匹配（JDK 17 preview，JEP 406；JDK 21 转正）

JDK 17 中以 preview 提供：switch 的 case 可以是类型模式、null、守卫条件（when），配合 sealed class 可以实现穷举。**preview 意味着”语法定了但可能改，需要 --enable-preview 编译”**，生产项目在它转正前不要用。

版本升级注意点

  • 偏向锁：JDK 15（JEP 374）弃用并默认禁用，JDK 18 完全移除——不要在新代码里依赖”偏向锁性能”的旧结论；
  • 内部 API 强封装（JEP 403）：sun.misc 等默认不可访问，老项目依赖需 --add-opens/--add-exports 或升级依赖。

1.4 Java 21（2023，LTS）：虚拟线程，并发编程的范式转变

为什么虚拟线程是革命性的：这是自 JDK 5 引入 java.util.concurrent 以来并发模型最大的一次改变，直接回答了”一请求一线程模型在高并发下不可行”这个困扰 Java 服务十几年的问题。

背景：平台线程（Platform Thread）1:1 映射操作系统内核线程，每个线程默认约 1MB 栈 + 内核资源，一台机器撑死几千到几万线程。于是高并发只能两条路：线程池复用（请求排队、吞吐受限）或异步回调（CompletableFuture / Reactor，代码心智负担极重、调试困难）。

虚拟线程的答案：虚拟线程由 JVM 调度，挂载在少量”载体线程”（Carrier，默认 ForkJoinPool，线程数 = CPU 核数）上执行。虚拟线程阻塞（IO、sleep、锁等待）时，JVM 自动把它从载体上卸载（涉及 Continuation 机制），载体去执行其它虚拟线程。于是：

  • 成本：一个虚拟线程约几 KB，百万级并发成为可能；
  • 写法：可以回到”一请求一线程”的同步阻塞写法——简单、可读、可调试，却拥有异步的吞吐；
  • 不用再：为每个 IO 资源设计专用线程池、纠结 CompletableFuture 的链式错误处理。

注意事项（面试加分点）：

  • 虚拟线程不适合 CPU 密集型任务（没有阻塞点，挂载卸载没有意义，并行度受限于载体线程数）；
  • 不要池化虚拟线程（newVirtualThreadPerTaskExecutor 本身就是廉价创建/销毁的，池化反而违背设计）；
  • JDK 21 中 synchronized 块会固定（pin）载体线程，使阻塞无法卸载——已知限制，后续版本已改进（使用 ReentrantLock 可绕开，JDK 24 起已解除 pinning）；
  • 线程切换成本从”内核级”降到”用户态”，但共享资源的竞争成本不变，锁的滥用仍是瓶颈。

结构化并发（JDK 21 preview，JEP 453）

为什么需要：Future.get() 逐个等待、某个子任务失败时其它子任务不知情继续空跑、无法统一取消——并发任务的生命周期管理是散的。结构化并发把一组子任务放进一个 StructuredTaskScope，要么全部成功、要么一起失败并统一取消（”并发领域的 try-with-resources”）。

Record Pattern 与模式匹配完善（JDK 21 转正，JEP 440 / JEP 441）

为什么需要：Record 定义的是”纯数据载体”，解构时逐字段调用访问器是样板代码；Record Pattern 让解构一步完成，与 switch 模式匹配组合后，**”按类型 + 结构 + 条件”的解构式编程**成为可能。

1.5 版本选择建议：生产环境什么时候升级

要点：

  1. 非 LTS 版本（9/10/1216/1820）不要作为生产基线：每半年一个版本，Oracle 只提供下一个版本发布前的更新，维护期极短；
  2. LTS 的免费更新窗口：Oracle 对 LTS 提供至下一个 LTS 发布后 6 个月（17 → 2029-09，21 → 2031-09）；想长期免费打补丁就用 OpenJDK 发行版（Temurin、Corretto、Liberica 等）；

2.1 equals 与 hashCode

面试官为什么问：这是把对象放进 HashMap/HashSet 的最基本前提。违反契约的后果是隐性的——“存得进去、取不出来”或”重复存储”，比编译错误难排查得多。

契约（Object 规范）

  1. 自反、对称、传递，且与 null 比较返回 false；
  2. 必要条件：a.equals(b) == true ⇒ a.hashCode() == b.hashCode()（反过来不成立，哈希碰撞是允许的）；
  3. hashCode() 在对象参与比较的字段未变化时，多次调用必须返回相同值。

为什么”必须”重写，而不是”应该”

HashMap 的查找分两步：先 hash(key) 定位桶（tab[(n-1) & hash]），再在桶内用 equals() 比对。默认的 hashCode() 由 Object 实现，返回与内存地址相关的值——两个逻辑相等（equals 为 true）的对象哈希不同，就会落到不同桶：

  • 存：a、b 都能放进 HashSet，集合出现两个逻辑相同的对象；
  • 取：用 a 存、用 b 查，b 的哈希定位到另一个桶，永远查不到。

  • **getClass() vs instanceof**：instanceof 写法允许子类与父类相等（对称性有风险），getClass() 写法要求严格同类。一般业务对象用 instanceof（Java 16+ 配合 pattern matching 的 o instanceof Person p 写法），枚举/值类型用 getClass()；

2.2 String

面试官为什么问：String 是使用频率最高的对象，它的内存模型（常量池）与 intern() 是”版本差异”类问题的经典题材，同时其不可变性设计贯穿安全、线程安全、哈希缓存多个考点。

为什么 String 设计成不可变

  1. 安全性：类加载器、网络地址、反射参数、HashMap 的 key 都依赖 String 的稳定内容。可变字符串意味着”拿到引用就能篡改”——常量池共享后，一个引用改内容会污染所有共享者；
  2. 字符串常量池复用：池化依赖”内容相同即同一个对象”的假设，内容可变则无法共享；
  3. 线程安全：不可变对象天然线程安全，无需同步；
  4. 哈希缓存：JDK 的 String 在首次调用 hashCode() 后把结果缓存到字段里——只有不可变才允许缓存；
  5. 作为 HashMap 的 key：key 的 hashCode 必须稳定，String 是理想的 key 类型。

2.3 异常体系

面试官为什么问：异常体系考察你对”错误处理设计”的理解——checked vs unchecked 的争论是 Java 语言设计史上最经典的话题之一，你的选择直接体现 API 设计能力。

层次结构

checked 与 unchecked 的设计哲学

  • checked 的动机（源自 JDK 1.0，借鉴 C++ 惯例）：”可恢复的失败”必须显式暴露在方法签名上，编译器强制调用方处理——IOException（文件不存在、网络中断）这类外部环境问题，调用方有机会重试、降级、换源，值得被强制感知；
  • unchecked 的动机：编程错误（传了 null、索引越界、状态非法）是代码 bug，强制处理没有意义——调用方不该为 bug 写 try-catch，应该让异常快速上抛、快速失败；
  • 实际项目中的现实：
    • 过度使用 checked 导致签名污染：throws Exception 满天飞、catch (Exception e) {} 空吞异常，反而掩盖错误；
    • 现代 Java 生态整体向 unchecked 倾斜：Spring 把 SQLException 等 checked 异常翻译成 unchecked 的 DataAccessException（DAO 层不再被迫 throws），MyBatis、JPA 类似；JDK 自身新 API（如 CompletableFuture 的 CompletionException）也大量使用 unchecked 包装；
    • 主流的共识：外部资源/IO 类的”可恢复”异常可以是 checked，其余一律 unchecked；跨层传递时用自定义 RuntimeException + 统一异常处理（如 Spring 的 @RestControllerAdvice）。

2.4 泛型

面试官为什么问：泛型是集合与框架设计的地基；理解类型擦除，才能理解”为什么 List<String>.class 不存在””Spring 是怎么拿到泛型参数做依赖注入的”这类进阶问题。

为什么需要泛型

泛型（JDK 5 引入）解决两大问题：

  1. 类型安全：没有泛型时，List 可以放任何类型，取出时必须强转，ClassCastException 推迟到运行期才暴露。泛型把错误检查提前到编译期——list.add(1) 到 List<String> 直接编译失败；
  2. 代码复用：排序、比较、搜索等算法无需为每种类型重写一遍，<T> 让算法作用于类型参数。

什么是类型擦除

Java 泛型是编译期特性：编译器在编译时移除所有泛型类型信息，替换为原始类型或边界类型，并在必要处插入强制转换。设计目的是兼容 JDK 5 之前的非泛型遗留代码（二进制兼容）。这与 C# 的”真泛型”（运行期保留类型，值类型可免装箱）有本质区别——这也是面试常对比的点。

2.5 反射与动态代理

面试官为什么问：反射是 Spring IOC/AOP、MyBatis、Jackson 等几乎所有框架的底层机制，”框架原理”类问题最终都会下沉到这里。

什么是反射

在程序运行期间动态获取类或对象信息以及动态调用对象方法的功能称为 Java 的反射机制。

  • 优点：动态、灵活——IOC（运行期根据配置创建对象）、AOP（运行期拦截方法）设计的基石；
  • 缺点：性能开销大于直接调用（现代 JVM 已做优化：方法句柄、内联缓存，但热路径仍应避免）、破坏封装（能访问私有成员）、代码可读性差。

实际应用场景：框架开发（Spring 通过反射读取配置动态创建 Bean、AOP 动态代理；Hibernate/MyBatis 反射映射结果集）、注解处理（JUnit 找 @Test）、动态代理、通用工具库（Jackson/Gson 序列化）、IDE 的代码提示与调试器。

动态代理

动态代理在不改变原代码的情况下，通过运行期生成的代理对象对目标对象做增强。两种实现：JDK 动态代理（基于接口）与 CGLIB/ByteBuddy（基于子类）。

JDK 动态代理（基于接口）：要求目标实现接口。Proxy.newProxyInstance 在运行期生成一个实现了目标接口的代理类，所有方法调用经 InvocationHandler.invoke 转发——Spring AOP 在目标有接口时默认用这种方式。

CGLIB 动态代理（基于子类）：不要求接口，通过生成目标类的子类并重写方法实现增强（目标类不能是 final）。回调接口是 MethodInterceptor。

考点补充：

  • 为什么 JDK 代理要求接口：生成的代理类只能 extends Proxy（Java 单继承），无法再继承目标类，只能通过实现接口转发；CGLIB 生成子类绕开了这个限制，代价是 final 类/方法不可代理、生成子类有额外字节码成本；
  • Spring AOP 的选择：有接口 → JDK 代理，无接口 → CGLIB；Spring Boot 2.x 起默认使用 CGLIB（proxyTargetClass=true）——因为 CGLIB 不要求接口，且规避了”只代理接口、丢失实现类特有方法”的坑；
  • JDK 16（JEP 396） 重写了 ProxyGenerator（用 Java 实现替代 sun.misc.ProxyGenerator），动态代理现在支持 Proxy 类默认方法代理、性能更好；
  • 用动态代理必须注意：通过代理调用走 invoke，同类内自调用（this.method()）不会触发增强——Spring 的 @Transactional 自调用失效就是这个原因。

如何防止反射破坏单例

使用枚举实现单例（推荐）：JVM 从底层保证枚举构造器只被调用一次，且 Constructor.newInstance() 内部会检查并拒绝创建枚举实例——反射无法破坏。这是《Effective Java》作者 Josh Bloch 强烈推荐的方式。

（普通懒加载单例还需注意：getDeclaredConstructor().setAccessible(true) 可绕过私有构造器；序列化也会破坏单例，需 readResolve() 防御——枚举则天然免疫这两种攻击。）

2.6 序列化

面试官为什么问：Java 原生序列化（Serializable）是公认的失败设计，面试官想看你是否理解跨进程数据格式的选择逻辑——安全、性能、版本演进是核心维度。

Java 原生序列化的原理

实现 Serializable 后，ObjectOutputStream 通过反射遍历对象图，把类元数据（类名、字段名/类型/继承结构）+ 字段值写入二进制流；ObjectInputStream 反序列化时再重建对象。特点：反射开销大、体积大（一个对象带全套类描述）、Java 专属、二进制不可读。

为什么 Java 原生序列化被淘汰

3.1 集合框架概览

Java 集合框架分两大体系：Collection（List/Set/Queue）与 Map。决策从”我需要什么语义”出发：

并发场景补充决策：需要线程安全的 Map/Set/List，首选 ConcurrentHashMap/ConcurrentSkipListSet/CopyOnWriteArrayList；Collections.synchronizedXXX 是全局锁，只在低并发时考虑；**Hashtable、Vector、Stack 是 JDK 1.0 遗留物**（所有方法 synchronized 全局锁），JDK 1.2 保留它们仅出于兼容，新代码不要用。

fail-fast 与 fail-safe

  • fail-fast（快速失败）：在原集合上遍历，迭代器创建时记录 expectedModCount，每次 next()/remove() 前检查 modCount == expectedModCount，不相等立即抛 ConcurrentModificationException。本质是单线程环境下的错误检测机制——它不能保证检测到所有并发修改（比如修改后又改回去就检测不到），也不是并发安全方案。代表：ArrayList、HashMap 的迭代器；
  • fail-safe（安全失败）：不在原集合上迭代，基于快照（snapshot）或弱一致性视图。迭代过程中原集合被修改不影响本次迭代，不抛异常。代价是弱一致性（可能读不到最新数据）和额外内存（快照）。代表：ConcurrentHashMap、CopyOnWriteArrayList 的迭代器。

3.2 ArrayList vs LinkedList

面试官为什么问：教科书说”数组 vs 链表”，但真实性能与直觉相反——面试官考察你是否做过实测、是否理解现代 CPU 缓存对性能的影响。

结构

  • ArrayList：Object[] elementData 动态数组，size 记录实际元素数；扩容是数组拷贝；
  • LinkedList：双向链表，每个节点 Node<E> 含 item/next/prev 三个引用。

ArrayList 扩容机制

为什么 1.5 倍而不是 2 倍：扩容是”空间 vs 拷贝次数”的权衡。2 倍扩容次数更少但每次浪费更多空间；1.5 倍（old + old >> 1）扩容均摊后插入仍为 O(1)，且减少内存浪费。预分配：能估算大小时直接 new ArrayList<>(expectedSize)（如 new ArrayList<>(map.size())），避免多次扩容拷贝。

性能对比

操作 ArrayList LinkedList 结论
随机访问 get(i) **O(1)**（下标直接定位） O(n)（从头部/尾部双向遍历） ArrayList 完胜
尾部 add O(1) 均摊（偶尔扩容拷贝） O(1)（追加节点） 打平
头部 add/remove O(n)（System.arraycopy 整体平移） **O(1)**（改指针） 理论 LinkedList 胜
内存 数组 + 对象引用，紧凑 每个节点额外 24~32 字节（3 个引用 + 对象头），通常更大 ArrayList 胜
缓存友好性 连续内存，CPU 缓存命中率高 节点分散，缓存命中率低 ArrayList 胜

反直觉的点：头部插入理论上 LinkedList O(1)，但小规模数据（万级以下）下 System.arraycopy 的批量内存拷贝速度极快，配合 CPU 缓存预取，实测往往比 LinkedList 的逐节点指针操作更快；LinkedList 的 O(1) 优势只在数据量很大、且操作点位于头部/尾部时才明显。

结论：90% 以上的场景选 ArrayList。LinkedList 的合理用途几乎没有——需要”双端队列”语义时用 ArrayDeque（也是更优解），真正需要链表的是 LRU 自定义实现等场景。面试答”我实测过，LinkedList 的 O(1) 是理论值，实际受缓存影响，选 ArrayList”是加分回答。

3.3 HashMap

面试官为什么问：HashMap 是使用率最高的容器，实现细节（树化阈值、扩容策略、哈希算法）是区分”背面试题”与”真懂”的分水岭。

基本结构

  • JDK 7：数组 + 链表（头插法）；
  • JDK 8：数组 + 链表 + 红黑树（尾插法）。

JDK 7 → 8 的变化

变化点 JDK 7 JDK 8 为什么改
插入方式 头插法 尾插法 头插法在扩容时链表元素顺序反转，多线程扩容可能形成环形链表 → get 死循环（JDK 7 经典事故）；尾插法杜绝成环
哈希函数 四次扰动（^、移位多轮） 一次扰动：(h = key.hashCode()) ^ (h >>> 16) 高位参与低位计算，减少冲突；一次运算更高效
冲突解决 纯链表 链表长度 ≥ 8 且容量 ≥ 64 → 红黑树 长链表查找 O(n) 恶化到不可接受，树化后 O(log n)
扩容策略 全量 rehash（每个元素重算位置） 按 (e.hash & oldCap) == 0 拆分成高低位两条链表，原位不动 / 移到 i+oldCap 避免全量重算哈希，扩容效率大幅提升
线程安全 否（死循环 + 丢数据） 否（死循环已修复，但仍丢数据：并发 put 互相覆盖） 并发场景必须用 ConcurrentHashMap

为什么链表 ≥ 8 才转红黑树、≤ 6 就退化

  1. 8 的统计依据（泊松分布）：负载因子 0.75、随机哈希下，桶内链表长度达到 8 的概率约为 0.00000006（六千万分之一）——这个数字出自 JDK 源码注释。也就是说正常情况下链表根本不会长到 8，树化是针对”哈希函数被恶意/异常破坏”（如 hash 冲突攻击、糟糕的 hashCode）的兜底，而不是常态；
  2. 为什么是 8 而不是更早：红黑树节点 TreeNode 比普通链表节点多 parent/left/right/red 等字段（占用约 2 倍内存），树化的”查找 O(log n) vs 链表 O(n)”性能优势要与节点内存开销权衡，8 是两者交叉点附近的经验值；
  3. 为什么退化阈值是 6 而不是 7/8：预留缓冲。如果退化阈值也是 8，一个桶在 7/8 之间反复增删，会频繁”树化→解树化→树化”，而树化是重操作（调整指针、变色、旋转），抖动代价高。6 与 8 之间留 2 的间隔就是为了防止抖动；
  4. 树化还有前置条件：数组容量 ≥ 64（MIN_TREEIFY_CAPACITY）。容量小时（如 16/32）哈希分布本来很差，此时扩容比树化更优（扩容后元素分散、链表自然变短），所以容量 < 64 时先扩容而不是树化。

为什么容量是 2 的幂

  1. 定位公式用位运算代替取模：桶下标 = (n - 1) & hash（n 为容量）。当 n 是 2 的幂时，n - 1 的二进制是全 1（如 16 → 1111），(n-1) & hash 等价于 hash % n 但只做一次位运算，更快；且低位全 1 让 hash 低 4 位均匀分布，冲突更少。如果 n 不是 2 的幂，n-1 会有 0 位，对应位恒为 0，部分桶永远空置；
  2. 扩容时位置推导：扩容 2 倍后，n-1 多了一个最高位 1。元素的新位置只可能是原位置 i 或 i + oldCap——取决于 hash 在新增位的值是 0 还是 1，即 (e.hash & oldCap) == 0。这就是 JDK 8 扩容”免全量 rehash”的原理；
  3. 容量始终向上取 2 的幂：tableSizeFor() 把任意指定容量转成最近的 2 的幂（如指定 13 → 实际 16）；
  4. 负载因子为什么是 0.75：空间利用率与冲突概率的权衡。0.5 冲突更少但空间浪费一半；1.0 空间足但冲突剧增（桶装满才扩容，链表变长）。0.75 是经验最优（泊松分布分析的基础）。

JDK 8 resize() 源码分析

分析要点：

  • 扩容倍数：oldCap << 1（2 倍），新阈值 oldThr << 1；
  • (e.hash & oldCap) == 0 是 JDK 8 的灵魂：oldCap 是 2 的幂（如 16 = 10000b），hash & 16 只考察 hash 在”新增位”的值——0 则新下标不变（i），1 则新下标 i + oldCap。链表整体按这条规则拆成两条子链表，顺序保持（尾插法的副产品），且每个节点只处理一次；
  • 相比 JDK 7”每个节点重新 hash & (newCap-1)“，省去了每个节点的重新取模，且因为顺序不变，不会像 JDK 7 头插法那样反转链表；
  • 红黑树桶走 TreeNode.split()，内部同样的高低位拆分逻辑（按低位链长度决定保持树形还是退化成链表）。

线程安全与 null key

  • JDK 7 多线程 put 扩容成环：头插法 + 扩容时链表反转，两个线程同时扩容可能把链表转成环形，get 无限循环（Java 7 时代经典生产事故，Java 8 用尾插法修复）；
  • JDK 8 多线程 put 丢数据：两个线程同时 put 到空桶，后写覆盖先写（oldVal 丢失），且 size 计数不准确。HashMap 任何版本都不是线程安全的，并发必须用 ConcurrentHashMap；
  • null key：HashMap 允许一个 null key（散列到 0 号桶，hash == 0）。而 ConcurrentHashMap 不允许 null key/value——并发场景下 get 返回 null 无法区分”key 不存在”还是”value 是 null”（这个歧义在非并发 HashMap 里可以用 containsKey 消解，但在并发下两次调用之间数据已经变了，无解）。

3.4 ConcurrentHashMap

面试官为什么问：ConcurrentHashMap 是并发容器选型的核心，JDK 7→8 的重构浓缩了现代无锁并发技术的精髓（CAS、细粒度锁、协同扩容、分片计数）。

为什么不用 Hashtable / Collections.synchronizedMap：两者都是全局锁——读也要拿锁，所有操作串行，并发度为零。CHM 的核心目标：读完全无锁，写只锁必要的桶。

JDK 7 实现（分段锁 Segment）

  1. 核心结构：固定大小的 Segment 数组（默认 16），每个 Segment 继承 ReentrantLock，内部维护自己的 HashEntry[] 桶数组。锁粒度是段——不同段上的写操作可并发，最多 16 个线程同时写；
  2. **put**：按 hash 定位 Segment → 加该段锁 → 段内找桶、插入/更新 → 释放锁；
  3. get：完全无锁——HashEntry.value 声明为 volatile，读依赖 volatile 保证可见性；
  4. size()：先无锁累加两次各段 count 与 modCount，若两次 modCount 一致则返回；否则锁住所有 Segment 再统计（高并发下开销大）；
  5. 扩容：发生在 Segment 内部，只扩触发扩容的那个段。

JDK 8 实现（CAS + synchronized + 红黑树）—— 为什么改

特性 Java 7 Java 8 优化点
锁机制 分段锁（Segment，继承 ReentrantLock） 桶级别锁（synchronized 锁桶头节点） + CAS 锁粒度更细（桶 vs 段）；空桶插入用 CAS 完全无锁；synchronized 受 JVM 持续优化（锁消除、轻量级锁），低竞争场景性能接近 CAS
数据结构 数组 + 链表（仅 HashEntry） 数组 + 链表 + 红黑树（Node/TreeNode） 高冲突桶查询 O(n) → O(log n)（与 HashMap 同策略：≥8 且容量 ≥64 树化）
size() 可能锁全表，低效 无锁：baseCount + CounterCell[] 分片计数（LongAdder 思想） 单一计数器在并发下是热点，分片把竞争摊到多个计数单元（配合 @Contended 避免伪共享）
扩容 段内独立扩容 多线程协同扩容（helpTransfer） 触发扩容后，后续写线程遇到 ForwardingNode 会领取一段迁移任务帮忙搬桶——利用并发加速扩容，缩短停顿
读操作 无锁（volatile value） 完全无锁（volatile + 特殊节点 find 转发） 读性能极高且稳定
内存开销 较高（Segment 结构 + 每段锁） 更低（单 Node 数组，树节点按需创建） 结构精简
ForwardingNode 无 有：迁移完成的桶放置 ForwardingNode 指向新表 无锁读 + 协同扩容的关键：get 遇到它转发到新表，写线程遇到它帮忙迁移

为什么 JDK 8 放弃 Segment 改用 synchronized + CAS：

  1. 锁粒度：从”段”细化为”桶头节点”——并发写碰撞概率从 1/16 降到 1/桶数，并发度提升一个数量级；
  2. 无锁化：桶为空时 put 直接 CAS 写入（casTabAt），初始化 table 也用 CAS + sizeCtl 控制——大量路径根本没有锁；
  3. **synchronized 不再”重”**：JDK 6 之后 synchronized 有偏向锁→轻量级锁→重量级锁的升级路径（注意：偏向锁 JDK 15 起默认禁用、JDK 18 移除，但轻量级锁/自旋让低竞争场景的 synchronized 依然很轻），锁桶头节点在低冲突场景开销极小；
  4. 读永远无锁：Node.value、Node.next 都是 volatile；扩容期间 get 通过 ForwardingNode.find() 转发到新表——get 与扩容并发执行也不会错。

JDK 8 put 流程（背熟这个）：

  1. 算 hash（扰动函数同 HashMap）；table 未初始化则 CAS 初始化；
  2. 定位桶 i；桶为空 → CAS 直接放入新节点，无锁完成；
  3. 桶头是 ForwardingNode → 正在扩容，协助扩容（helpTransfer）后再 put；
  4. 桶非空 → synchronized 锁桶头节点：链表则遍历更新/尾插；树节点则走红黑树插入；
  5. 检查是否树化（≥8 且容量 ≥64）→ 检查是否需要扩容。

与 Hashtable 效率对比

  • 锁粒度：Hashtable 全局锁（一次只允许一个线程操作）→ CHM7 段锁（16 段并发）→ CHM8 桶锁（几乎无限并发写）；
  • 读：Hashtable 读也要锁；CHM 两个版本的读都完全无锁（volatile 保证可见性）。

完整示例：并发计数/写入

3.5 TreeSet / TreeMap

面试官为什么问：有序集合的选型与比较器契约（Comparable vs Comparator），以及”有序”与”唯一性”的关系——TreeSet 的去重依据是 compareTo()==0 而非 equals()，这是最常见的坑。

底层结构：红黑树

TreeMap 基于红黑树（自平衡二叉搜索树），TreeSet 基于 TreeMap（元素作 key，value 为固定 PRESENT）。红黑树的平衡性质保证：

  • 每个节点红或黑；根为黑；红节点的子节点必为黑；任意节点到其每个叶子路径上的黑节点数相同；
  • 由此保证最长路径不超过最短路径的 2 倍 → 增删改查全部 **O(log n)**，且不会退化成链表（AVL 树平衡更严格但旋转更频繁，红黑树是”足够平衡”的工程选择）。

什么时候用 TreeMap/TreeSet

需求 选择 原因
键有序迭代 / 范围查询（排行榜、区间统计） TreeMap 有序 + subMap/tailMap/headMap
元素去重且有序 TreeSet 底层 TreeMap
无排序需求 HashMap/HashSet **O(1) vs O(log n)**，别为不需要的顺序付代价
键按访问/插入顺序（LRU 缓存） LinkedHashMap 注意和 TreeMap 区分：它是”按顺序迭代”，不是”按键排序”

与哈希系对比：

实现 底层结构 add/remove/contains 迭代顺序 去重依据
HashSet HashMap（数组 + 链表/红黑树） **O(1)**（极端 O(n)） 无序 equals() + hashCode()

注意点：

  • 去重依据是 compareTo()==0，与 equals() 无关：两个 equals() 为 false 的对象，只要比较器认为相等（compareTo()==0），在 TreeSet 里就只能存一个——反之亦然。规则是”与 equals 一致”（compareTo()==0 ⇔ equals()），违反会导致集合行为诡异；
  • key 不可变：可变 key 会导致树结构错乱（和 HashMap 同样的教训）；
  • null key：TreeMap 默认不允许 null key（插入时 compare(null, x) 抛 NPE）；JDK 7 起若自定义 Comparator 支持 null（如 Comparator.nullsFirst(...)）则允许；
  • 常用 API：firstKey/lastKey、floorKey/ceilingKey/lowerKey/higherKey（小于等于/大于等于/严格小于/严格大于）、subMap(from, to)/tailMap(from)/headMap(to)。

4. Java IO

IO 面试的核心逻辑只有一条：如何用更少的线程服务更多的连接。从 BIO 到 NIO 到 AIO 再到虚拟线程，都是为了回答这个问题。

4.1 从 BIO 到 NIO 的演进

BIO 的问题：一连接一线程

传统阻塞 IO（BIO）的调用点（accept、read、write）都是阻塞的——线程发起 IO 后挂起，直到数据到达。于是高并发服务只能”一连接一线程”：

  • 线程数 = 连接数：10000 连接 = 10000 线程。每个平台线程默认约 1MB 栈 + 内核资源，加上上下文切换开销，C10K 问题（万级连接）就是天花板；
  • 资源浪费：大多数连接处于空闲等待（等数据、等响应），线程却一直占着——“线程在等，不是在做”；
  • 线程池方案是缓解不是解决：池大小受限，连接数超过池容量就排队，吞吐受限。

NIO 的答案：一个线程管多个连接

JDK 1.4 引入 NIO（New IO），核心思想是非阻塞 + 事件驱动：线程不再”等某个连接”，而是问内核”哪些连接就绪了”（Selector），只处理就绪的连接，一个线程可管理数万连接。

AIO 的尴尬：JDK 7 的 AIO 在 Windows 上基于 IOCP（真异步），在 Linux 上网络部分实际是 epoll 模拟（Linux 内核的 POSIX AIO 只支持文件 IO），加上回调模型编程复杂，实际网络编程主流始终是 NIO + Reactor（Netty），AIO 几乎没被采用。io_uring（Linux 5.1+）出现后，真正的内核异步才有可行方案，Netty 5.x 已提供 io_uring 支持——但这是后话。

字节流与字符流

  • 字节流：InputStream/OutputStream，处理二进制数据（图片、视频、网络包），核心类 FileInputStream；
  • 字符流：Reader/Writer，处理文本数据（自动处理编码），核心类 FileReader、InputStreamReader；
  • 关键点：字符流底层依赖字节流 + 编码转换——InputStreamReader 是字节到字符的桥梁（指定 Charset，否则用平台默认编码，跨平台会乱码）。

为什么要有字符流：直接操作字符避免手动转码（UTF-8/GBK 互转），一次性解决乱码问题；按字符（而非字节）处理文本逻辑更自然。

BIO 与 NIO 对比

特性 BIO（传统 IO） NIO
模型 阻塞式（Blocking） 非阻塞式（Non-blocking）
数据单位 流（Stream），单向 缓冲区（Buffer） + 通道（Channel），双向
多路复用 不支持 Selector 轮询机制
线程模型 一连接一线程 一线程多连接

NIO 三大核心组件

  • Buffer：数据容器（ByteBuffer 等），核心操作 flip()（写转读）、clear()（读转写）、compact()。三个关键属性：position（读写位置）、limit（读写边界）、capacity（容量）；
  • Channel：双向数据传输通道（FileChannel、SocketChannel、ServerSocketChannel），对比流的单向性——一个 Channel 既能读又能写；
  • Selector：单线程监听多个 Channel 的事件（OP_ACCEPT、OP_READ、OP_WRITE、OP_CONNECT），select() 返回就绪事件集合——多路复用的核心。

4.2 五大 IO 模型

理解五个模型前先记住：一次 IO 分两个阶段——① 等待数据就绪（数据从网卡/磁盘到内核缓冲区）；② 数据从内核缓冲区拷贝到用户态。五个模型的本质区别就是”阻塞发生在哪个阶段、由谁通知”。

1. 阻塞 I/O 模型（Blocking I/O）—— 用户态、内核态两个阶段都阻塞

特点：线程发起 IO 后被挂起，直到数据就绪并拷贝完成才返回。最简单直接，但线程全程被占着。

2. 非阻塞 I/O 模型（Non-blocking I/O）—— 等待阶段不阻塞，靠轮询

特点：accept/read 立即返回（没数据返回 -1 或 0），线程通过轮询检查就绪状态。不阻塞了，但轮询本身消耗 CPU——单线程轮询 N 个连接 = N 次系统调用，高并发下不可用。这个模型的定位是”教学意义上的中间态”，实际工程用的是模型 3。

3. I/O 多路复用模型（I/O Multiplexing）—— 单线程 + 内核通知就绪事件

特点：一个线程把大量连接注册到 Selector，调用 select() 阻塞等待，内核负责检测哪些连接就绪并通知。对比模型 2，就绪检测从”用户态轮询”下放到”内核事件通知”，系统调用次数从 O(n) 降到 O(1)（有事件才返回）。这是 Netty 的基石。

4. 信号驱动 I/O 模型（Signal-driven I/O）—— 内核发信号通知就绪，Java 不直接支持

特点：进程注册 SIGIO 信号处理器，内核在数据就绪时发信号通知，进程在信号处理器里发起读取（读取仍是阻塞的——只解决了”等待阶段”）。实现复杂、信号队列可能溢出，实际很少使用。Java 没有直接对应 API（NIO 的 Selector 更接近多路复用而非信号驱动）。

5. 异步 I/O 模型（Asynchronous I/O）—— 两个阶段都不阻塞，完成回调

特点：发起 IO 后立即返回，数据从内核拷贝到用户态完成之后才回调 CompletionHandler——连”拷贝阶段”都不阻塞（对比：多路复用模型在拷贝时仍需线程）。Java 对应 NIO.2（JDK 7）的 AsynchronousServerSocketChannel / AsynchronousSocketChannel。

各模型对比总结：

模型 阻塞阶段 Java 实现 优点 缺点
阻塞 I/O 等待数据到达和复制 Socket, ServerSocket 编程简单 线程资源浪费，一连接一线程
非阻塞 I/O 无（但需轮询） NIO configureBlocking(false) 单线程管理多连接 轮询消耗 CPU，系统调用频繁
I/O 多路复用 等待事件通知 NIO Selector 高效管理大量连接（内核通知） 编程较复杂；拷贝阶段仍阻塞
信号驱动 I/O 无（但需处理信号） Java 不支持 减少轮询开销 编程复杂，信号队列溢出

一句话记忆：阻塞与非阻塞看”调用是否立即返回”；多路复用与异步看”就绪/完成的检测与通知方”——多路复用还需要线程去拷贝，异步连拷贝都不用管。

4.3 select / poll / epoll 对比

三者都是 IO 多路复用的实现，让一个线程同时监听大量文件描述符（fd），由内核通知哪些 fd 就绪。区别在于内核的实现方式、fd 上限与性能。

select

  • 把监听的 fd 放入一个 fd_set 位图（bitmap）。每次调用都要把整个位图从用户态拷贝到内核态，内核遍历位图判断哪些 fd 就绪，再把结果拷贝回用户态；
  • fd 数量受限：受 FD_SETSIZE 限制，通常为 1024；
  • 复杂度 O(n)：内核需线性遍历全部 fd 才能知道谁就绪；返回后用户程序还要再遍历一遍才能确定哪些 fd 可读写。fd 越多，性能越差；
  • 内核会**修改传入的 fd_set**（就绪的 fd 被标记），因此每次调用前都要重新填充；
  • 只支持水平触发（LT），且属于主动轮询，没有事件通知机制。

poll

  • 思路与 select 相同，但把位图换成了 pollfd 结构体数组（fd + events + revents）：用户只填充 events，内核就绪后回填 revents，无需像 select 那样每次重新构造；
  • 没有连接数上限（受系统允许进程打开的 fd 数限制，如 ulimit -n）；
  • 遍历仍是 **O(n)**：每次调用都要把整个数组拷贝进内核并线性扫描，连接数多时性能依然线性下降。

**epoll**（Linux 2.6+ 专属）

  • 事件驱动：通过 epoll_create 创建句柄、epoll_ctl 注册/修改/删除 fd、epoll_wait 等待事件。内核只把就绪的 fd 挂入就绪链表返回，无需扫描全部 fd；
  • O(1) 复杂度：就绪 fd 通过回调直接入链，epoll_wait 直接取走就绪链表，耗时与连接总数无关。已注册的 fd 由内核中的红黑树组织，增删改查为 O(log n)；
  • 用户态与内核态通过 mmap 共享内存共用事件表，避免数据拷贝，近乎零拷贝；
  • 支持 LT（水平触发） 与 ET（边缘触发） 两种模式：
    • LT：fd 只要可读写就反复通知（数据没读完就持续上报），与 select/poll 行为一致，不易丢事件，编程简单；
    • ET：仅在状态变化时通知一次，必须配合非阻塞 IO + 循环 read 一次性读完，否则可能漏数据。通知次数少、效率更高，但编程复杂（Netty 默认采用 ET 风格）。

对比总结：

特性 select poll epoll
底层数据结构 fd_set 位图 pollfd 数组 红黑树 + 就绪链表
最大连接数 1024（FD_SETSIZE） 无上限（受系统限制） 无上限
遍历方式 线性扫描全部 fd，O(n) 线性扫描全部 fd，O(n) 事件回调，只返回就绪 fd，O(1)
用户态↔内核态拷贝 每次调用全量拷贝 每次调用全量拷贝 mmap 共享内存，近乎零拷贝
触发模式 仅 LT 仅 LT LT + ET
平台支持 几乎所有平台 几乎所有平台 仅 Linux

场景选择：连接数少、追求跨平台用 select/poll；高并发、海量连接用 epoll（Netty 在 Linux 上的 EpollEventLoop 就是对 epoll 的封装）。为什么 epoll 快：select/poll 是”我扫一遍所有 fd 看谁就绪”（O(n) 每次都扫），epoll 是”fd 就绪时内核回调把我挂进就绪链表”（只有就绪的才处理）——从”扫描”变成”通知”，这是本质区别。

4.4 Reactor 模式

为什么需要 Reactor：4.2 的模型 3 代码里，selector.select() 返回后，事件分发、业务处理、读写都揉在一个循环里。连接多了之后这个循环会变成瓶颈。Reactor 模式把职责拆开：IO 事件分发（Reactor）与业务处理（Handler）解耦，事件循环只做分发，业务可以放到线程池。

三种形态：

形态 结构 特点 代表
单 Reactor 单线程 一个线程：select + 分发 + IO + 业务 最简单；业务阻塞会拖垮整个事件循环 Redis 6.0 之前（事件驱动单线程）
单 Reactor 多线程 一个线程 select + 分发 + IO；业务处理进线程池 业务慢不影响事件循环；但 select 与 IO 仍在一个线程 下面的完整示例即此形态
主从 Reactor 多线程 主 Reactor 只负责 accept；从 Reactor（可多个）负责连接建立后的 IO 事件；业务进线程池 并发连接建立也是瓶颈时，把 accept 单独拆出来；扩展性最强 Netty（BossGroup / WorkerGroup）

Netty 的对应关系：BossGroup = 主 Reactor（accept 分发），WorkerGroup = 从 Reactor 组（每个 EventLoop 一个 select 循环，负责读写与业务调度）；NioEventLoop 封装了 epoll/select，DefaultEventExecutorGroup 承载业务线程池。

Reactor 与 Proactor 的一句话对比：Reactor 是”IO 就绪了通知你，你自己读写”（同步、多路复用）；Proactor 是”读写完成了我通知你”（异步）。Netty 是 Reactor 的忠实实现。

完整可运行示例：先运行 SimpleReactor（端口 8083），再运行 ReactorClient 压测

代码解析（面试要能讲出）：

  • Reactor 线程：selector.select() 阻塞等待事件 → 通过 SelectionKey.attachment() 找到事件处理器（Acceptor/Handler）分发执行——“事件分发”与”业务处理”解耦；
  • Acceptor：处理 OP_ACCEPT，接受连接后创建 Handler（注册 OP_READ）；
  • Handler：OP_READ 时在 Reactor 线程读数据，业务处理（Processor）提交给 workerPool——业务慢不会阻塞事件循环，这是”单 Reactor 多线程”的要点；
  • 跨线程注意点：业务线程向共享 output 缓冲区写入、修改 interestOps 都必须 synchronized，并 selector.wakeup() 唤醒 select（否则 select 阻塞着不会立刻感知新事件）——这也是为什么更彻底的主从多线程模型把事件循环分组，避免跨线程触碰 selector 状态；
  • 为什么生产不用这段代码：业务线程直接操作 Reactor 的共享 Buffer 与 interestOps，同步负担重且易错；Netty 通过 EventLoop 线程模型保证”同一 Channel 的所有操作都在同一线程”，从根上消除跨线程共享。

5. 网络基础（TCP/IP 与 HTTP）

网络是 Java 后端的”地基”——你写的每一个 HTTP 接口、每一条数据库连接、每一次消息推送都跑在 TCP/IP 之上。面试官问网络，考察的不是背报文格式，而是三件事：数据到底是怎么走的（分层与封装）、TCP 的可靠性是怎么做到的（握手、窗口、拥塞），以及 HTTP/HTTPS 的机制细节（报文、状态码、跨域、TLS）。

5.1 TCP/IP 协议栈

OSI 七层 vs TCP/IP 四层

为什么需要分层：一次网络传输要解决无数问题——信号怎么变成比特、比特怎么变成帧、帧怎么路由到对方、怎么保证不丢不乱。分层把这些问题拆成互相独立的模块，每层只干一件事、只跟相邻层打交道——任何一层换实现（比如链路层从以太网换成 WiFi）不影响其它层。

面试常问”为什么 OSI 是七层、实际用的却是四层”：OSI 是理论模型（学术价值在于”分层思想”），它的会话层/表示层在互联网实践中没形成独立的协议（功能被应用层协议自己承担），所以 TCP/IP 模型把它俩合并进了应用层。记 OSI 是为了背层次顺序，实际抓包分析永远以 TCP/IP 四层为准。

记忆锚点：端口负责”这台机器上的哪个进程”，IP 负责”哪台机器”，MAC 负责”同一局域网内谁收”——一次传输三层寻址全要用到。

数据封装与解封装

封装（发送方，从上往下逐层加头）：应用层产出 HTTP 数据 → 传输层加 TCP 头（源/目的端口）→ 网际层加 IP 头（源/目的 IP）→ 链路层加以太网头（源/目的 MAC）→ 物理层把比特发到线缆。

解封装（接收方，从下往上逐层剥头）：链路层看 MAC 确认是给自己的 → 网际层看 IP 确认目的 → 传输层看端口交给对应进程 → 应用层拿到原始数据。

关联考点：MTU 与 MSS。以太网帧最大 1500 字节（MTU），IP 头 20 字节 + TCP 头 20 字节，所以 TCP 单次最多携带 MSS = 1500 − 40 = 1460 字节数据——这就是”大消息必须分片、应用层必须自己处理半包”的物理根源。

5.2 TCP 协议

TCP 是最重要的传输层协议，面试围绕四个机制展开：连接管理（三次握手/四次挥手）、可靠性（确认与重传）、流量控制（滑动窗口）、拥塞控制。

三次握手（SYN → SYN+ACK → ACK）

建立连接时双方交换三个报文，确认”我能发、你能收；你能发、我能收”：

步骤 报文 方向 内容 目的
① SYN 客户端 → 服务器 seq = x（初始序列号） 客户端请求建立连接，告知自己的序列号起点
② SYN+ACK 服务器 → 客户端 seq = y, ack = x+1 服务器确认收到，同时告知自己的序列号起点
③ ACK 客户端 → 服务器 ack = y+1 客户端确认收到——至此双方双向就绪，进入 ESTABLISHED

为什么是三次不是两次（必背）：

  • 两次握手只能保证”服务器确认了客户端能发”，无法保证”客户端确认了服务器能发”——但核心问题还不是这个；
  • 经典反例——失效的旧连接请求：客户端发的第一个 SYN 在网络中滞留，客户端超时重发 SYN 并成功完成连接、传输、关闭。此时旧 SYN 才到达服务器。若只有两次握手，服务器收到旧 SYN 后回 SYN+ACK 并直接进入 ESTABLISHED、分配资源——但客户端根本不会理会这个连接，服务器的资源被白白占用（SYN Flood 攻击就是利用这个原理耗尽服务器资源）；
  • 三次握手时，客户端收到服务器对旧请求的回应后会回一个 RST，服务器收到 RST 就知道对方无意连接，释放资源。**三次握手让服务器在分配资源之前，先确认”这个连接是客户端真心想建立的”**。

四次挥手（FIN → ACK → FIN → ACK）与 TIME_WAIT

连接是双向的，每一方要关闭自己那一半就得发一次 FIN，所以完整关闭需要四个报文：

步骤 报文 方向 状态变化 说明
① FIN 主动方 → 被动方 主动方 FIN_WAIT_1 主动方说”我的数据发完了，我要关我这半边”
② ACK 被动方 → 主动方 被动方 CLOSE_WAIT；主动方 FIN_WAIT_2 被动方确认，但自己还有数据要发（半关闭）
③ FIN 被动方 → 主动方 被动方 LAST_ACK 被动方数据发完，关闭自己半边
④ ACK 主动方 → 被动方 主动方 TIME_WAIT；被动方 CLOSED 主动方确认，等 2MSL 后才真正 CLOSED

为什么 TIME_WAIT 要等 2MSL（必背，两点）：

  1. 保证最后一次 ACK 到达：第④步的 ACK 可能丢失。若丢失，被动方（LAST_ACK）超时会重发 FIN，主动方需要还在（TIME_WAIT 中）才能回 ACK 完成关闭。最后一次 ACK 传输耗时 1 个 MSL，重发的 FIN 耗时 1 个 MSL，等 2MSL 保证”即使 ACK 丢了，重发循环也能走完”；
  2. 让旧连接的报文在网络中消亡：同一对 (源IP, 源端口, 目的IP, 目的端口) 的新连接可能复用原端口。若旧连接的迟到报文未消失就建立了新连接，新连接会收到脏数据。等 2MSL 让旧报文在网络中全部死亡，保证新连接干净。

MSL（报文最大生存时间）Linux 默认 30s，2MSL 即 60s——这就是服务器上大量 TIME_WAIT 连接要挂 60 秒的原因。高并发短连接场景（如连接池频繁重建）TIME_WAIT 大量堆积是常见生产问题，优化方向是连接复用（keep-alive/连接池），而不是暴力调小 tcp_fin_timeout。

TCP 状态迁移

状态 含义 进入方式
CLOSED 无连接 初始/关闭完成
LISTEN 监听中 服务端 bind + listen
SYN_SENT 已发 SYN 客户端主动 connect
SYN_RCVD 已收 SYN 并回 SYN+ACK 服务端收到 SYN
ESTABLISHED 连接建立 握手完成
FIN_WAIT_1 已发 FIN 主动方发起关闭
FIN_WAIT_2 已收对方 ACK 主动方收到 ACK
CLOSE_WAIT 对方已关、自己未关 被动方收到 FIN
LAST_ACK 已发 FIN 等最后 ACK 被动方发 FIN 后
TIME_WAIT 等 2MSL 主动方发出最后 ACK
CLOSING 双方同时关闭 双方同时发 FIN（罕见）

生产排查两个高危状态：

  • 大量 TIME_WAIT：主动关闭方多——通常是服务器主动 close（短连接场景），资源开销不大，但端口耗尽时新连接失败；
  • 大量 CLOSE_WAIT（重点）：被动关闭方收到了 FIN 但应用层没有调用 close()——典型原因是连接泄漏、未关闭的流（try-with-resources 没用好）、线程池任务排队迟迟不处理响应。CLOSE_WAIT 只增不减基本等于代码 bug，lsof -i + 线程栈定位是标准排查姿势。

滑动窗口与流量控制

为什么需要：发送方不能无脑发——发太快，接收方缓冲区溢出丢包，触发重传反而更慢；发太慢，浪费带宽。所以需要”接收方告诉发送方自己能收多少”。

  • 每个 TCP 头都带 16 位 window 字段：接收方通告自己当前可接收的字节数（接收窗口 rwnd）；
  • 发送方维护**发送窗口 = min(rwnd, 拥塞窗口 cwnd)**，窗口内的数据可以连续发出（不必等逐个 ACK）；
  • 接收方处理完数据后通过 ACK 携带窗口更新值——这就是”滑动”：窗口左边是已确认、中间是已发未确认、右边是待发送。

与拥塞控制的区别（面试必分清）：流量控制是端到端的——防止”发送方淹没接收方”（接收方缓冲区不够）；拥塞控制是端到网络的——防止”发送方淹没网络”（路由器缓冲区溢出）。一个管接收端，一个管网络。

拥塞控制

算法 触发时机 cwnd 变化 目的
慢启动 连接建立 / 超时重传后 指数增长（每 RTT 翻倍） 快速探测网络可用带宽
拥塞避免 cwnd ≥ ssthresh（慢启动阈值） 线性增长（每 RTT +1） 接近带宽上限后谨慎试探
快速重传 收到 3 个重复 ACK 立即重传丢失报文 不等超时（RTO 通常 ≥ 200ms），减少等待
快速恢复 快速重传触发后 ssthresh = cwnd/2，cwnd = ssthresh，转拥塞避免 网络只是轻微丢包，不必回到慢启动重头探测

面试完整链路：连接建立 → 慢启动指数增长 → 撞到 ssthresh 转拥塞避免线性增长 → 某包丢失 → 收到 3 个重复 ACK 触发快速重传 + 快速恢复（cwnd 减半继续拥塞避免）→ 若超时（RTO）则视为严重拥塞，回到慢启动且 ssthresh 减半。TCP 的公平性正是靠”拥塞就减半”的加性增/乘性减实现的。

TCP 粘包 / 半包

为什么会有这个问题：TCP 是字节流协议，没有”消息边界”——发送方写两次 write，接收方可能一次 read 全拿到（粘包）；发送方写一次大消息，接收方可能分多次 read 才拿完（半包）。粘包/半包不是 TCP 的 bug，而是”多条应用消息塞进一个字节流”的必然结果：

  • 粘包原因：发送方连续小包被 Nagle 算法合并、或被内核缓冲区一次性发送；接收方一次 read 读到多条消息；
  • 半包原因：单条消息超过 MSS（1460 字节）被分片；接收方 read 的缓冲区小于消息长度。

三种解决方案：

方案 做法 优点 缺点 代表
固定长度 每条消息定长，不足补位 实现最简单 浪费带宽、长度必须预先知道 一些老旧协议
分隔符 消息以 \n 等特殊字符结尾 实现简单、可读 内容里不能出现该字符（需转义） Redis RESP、行协议
长度字段 头部 4 字节长度 + 消息体 通用、高效、无内容限制 实现稍复杂 Netty LengthFieldBasedFrameDecoder、Kafka 协议

5.3 UDP 协议

UDP 的特点

特点 说明
无连接 无需握手，直接发数据报，省去建立连接的时间
不可靠 不保证到达、不保证顺序、不保证不重复，丢了就丢了
有边界 每个数据报独立（不粘包/半包），单包最大约 64KB
无拥塞控制 不会因网络拥塞主动降速——牺牲公平保时延
低开销 头只有 8 字节（TCP 20 字节），无状态、无连接队列

TCP vs UDP 选型表

维度 TCP UDP
连接 面向连接（三次握手、四次挥手） 无连接（即发即走）
可靠性 可靠：确认、重传、排序、去重 不可靠：尽力而为
数据边界 字节流（无边界，粘包/半包） 数据报（有边界）
拥塞控制 有（慢启动/拥塞避免） 无（延迟稳定）
传输效率 握手 + 重传 + 滑动窗口开销 低延迟、低开销（头 8 字节）
适用场景 HTTP/HTTPS、数据库、文件传输、消息队列 音视频、DNS、游戏、NTP、日志上报

什么场景用 UDP：

  • 音视频通话/直播（WebRTC）：丢几帧画面可以接受，卡顿 200ms 不可接受——TCP 的”丢包重传 + 拥塞降速”在实时场景是灾难；
  • DNS：一次查询一次响应，响应丢了客户端重查一次即可（DNS 默认走 UDP 53，区域传输才用 TCP）；
  • 游戏实时对战：位置同步丢一包用下一包覆盖（要的是”最新状态”而不是”完整历史”）；
  • NTP 时间同步 / 物联网传感器上报：单包即语义完整，重传无意义。

判断口诀：数据丢了”无所谓或有最新覆盖” → UDP；数据丢了”必须补上” → TCP。

如何基于 UDP 实现可靠传输（RUDP）

为什么需要 RUDP：TCP 可靠但慢（握手 RTT、队头阻塞、拥塞控制不可控），UDP 快但不可靠。某些场景要”TCP 的可靠性 + 自定义的控制权”——于是把可靠机制搬到应用层自己实现。

RUDP 的基本思想（照搬 TCP 的零件）：

  1. 序列号：每个数据报编号，接收方用序号检测丢失、乱序、重复；
  2. ACK / NACK：接收方回确认；丢包时用 NACK（或 ACK 缺口）快速告知发送方，比等超时更快；
  3. 超时重传：发送方对未确认的包超时重发；
  4. 滑动窗口：控制”在途未确认”的数据量，防止把自己和网络打爆；
  5. 可选拥塞控制：可借鉴慢启动/拥塞避免，也可以故意不做拥塞控制（游戏优先低延迟，宁可丢包不降速）。

成熟案例：QUIC（HTTP/3 的传输层）本质就是 RFC 标准化的 RUDP——UDP 之上实现可靠传输、多路复用、0-RTT、连接迁移。游戏行业的 RUDP 私有协议（如 KCP）思路一致。

RUDP 的代价：所有机制自己实现（序列号管理、重传队列、拥塞状态机），复杂度高、容易出 bug、协议互不兼容。选型判断：有现成标准（TCP/QUIC）能满足就别自己造。

GET vs POST

维度 GET POST
语义 获取资源（查询） 提交数据 / 创建资源

幂等性（RFC 7231）：同一请求重复执行，资源状态不变。GET/HEAD/PUT/DELETE 语义上幂等；POST 不幂等。幂等性 = 重试安全——网络超时后客户端可以放心重放 GET，但重放 POST 可能导致”重复下单”。所以订单/支付接口要么保证幂等（幂等键 + 唯一索引），要么禁止自动重试。

URL 长度限制的实际原因：HTTP 协议本身不限制 URL 长度——限制来自各环节的实现：

环节 典型限制
浏览器 老 IE 约 2KB；现代浏览器约 8KB~64KB
Web 服务器 Tomcat maxHttpHeaderSize 默认 8KB；Nginx large_client_header_buffers 默认 8KB
代理/CDN 各家不同，通常 8KB~16KB

URL 超过限制会返回 **414 URI Too Long**。所以”GET 参数多放几个没事”是误区——大数据（复杂查询条件、文件上传）必须走 POST。

Cookie 与 Session

Cookie：服务端通过 Set-Cookie 下发、客户端存下来、后续请求通过 Cookie 头带回的小型键值数据。关键属性：HttpOnly（禁止 JS 读取，防 XSS 窃取）、Secure（仅 HTTPS 传输）、SameSite（防 CSRF 跨站携带）、Domain/Path（作用范围）、Max-Age/Expires（过期时间）。单条约 4KB、单域名约 50 条。

Session：服务端为会话分配唯一 id，把用户状态存服务端（内存/Redis），客户端只需持有 session id（通常放 Cookie）。**Cookie 存数据，Session 存”身份 + 服务端数据”**。

维度 Cookie Session

安全性 明文存储、可被篡改（须 HttpOnly + Secure + 签名） 客户端只持有随机 id，更安全

  1. Session 粘滞（sticky）：负载均衡把同一用户固定到同一台机器——机器宕机就丢会话，不推荐；
  2. 集中存储：Session 放 Redis，任意节点可查——Spring Session 的标准方案，推荐；
  3. 无状态化（JWT）：服务端不存会话，把用户身份放进客户端持有的签名 Token（JWT），每次请求验签——天然水平扩展，代价是无法主动注销（只能等过期/黑名单），敏感操作慎用。

跨域：同源策略与 CORS

同源策略：浏览器的安全机制——协议 + 域名 + 端口三者全相同才算同源。跨源时，浏览器允许”发请求”，但阻止 JS 读取响应（除非服务端明确允许）。注意：同源策略是浏览器的行为，服务端到服务端（Java 调 Java）不受限制——所以跨域问题只在”浏览器 → 后端”场景出现。

CORS（跨域资源共享）：服务端通过响应头声明”允许哪些源访问我”：

简单请求 vs 预检请求（必背）：

简单请求 预检请求
触发条件 方法为 GET/HEAD/POST 且 Content-Type 为 application/x-www-form-urlencoded / multipart/form-data / text/plain 且 无自定义请求头 其它一切：PUT/DELETE、application/json、自定义头（Authorization、X-Token）
流程 直接发真实请求，响应回来后浏览器校验 CORS 头，不通过则拦截 浏览器先发 OPTIONS 预检，服务端返回允许列表后，才发真实请求
开销 无额外往返 多一次 OPTIONS 往返

实践要点：现在后端接口几乎全是 application/json → 几乎都会触发预检，所以跨域接口常看到”先 OPTIONS 200、再真实请求”两个包——这是正常现象。配置层面 Spring 用 CorsFilter / @CrossOrigin，网关/Nginx 用 add_header Access-Control-*。生产环境不要配 * + credentials（浏览器禁止组合），也不要全局放行（正确做法：白名单源）。

HTTP/1.1 → HTTP/2 → HTTP/3

特性 HTTP/1.1 HTTP/2 HTTP/3
底层传输 TCP TCP UDP + QUIC
连接模型 持久连接，但同连接请求串行 一个 TCP 连接上多路复用（多流并发） 多路复用 + 流间互不阻塞
头部传输 明文逐请求重发 HPACK 压缩（静态表/动态表/Huffman） QPACK（面向乱序的改进）
队头阻塞 有（响应必须按序，队头慢包堵全队） TCP 层仍有（一个包丢失，重传期间阻塞整条连接所有流） 基本消除（丢包只影响所属流）
握手 TCP 握手 + TLS 握手（多次 RTT） 同左 0-RTT 可带数据
其他 管线化（理论可行，实践被浏览器禁用） 二进制分帧、服务器推送（已被 Chrome 废弃） 连接迁移（换网络不断连）

HTTP/1.1：keep-alive 持久连接解决了”每次请求都重新握手”的问题；管线化（pipelining）理论上允许一次发出多个请求，但要求响应按序返回——队头第一个响应慢，后面全堵着，浏览器实际禁用，这也是 HTTP/2 出现的直接动机。

HTTP/2 的关键机制：

  • 二进制分帧：报文拆成帧（HEADERS 帧 / DATA 帧），每个帧带 stream id——一个 TCP 连接上多个流交错传输，接收端按流 id 重组，实现多路复用（一个连接并发几十个请求）；
  • 头部压缩（HPACK）：Header 不再逐请求明文重发——静态表预置常见头（:method、:path），动态表缓存重复值，配合 Huffman 编码，头部体积可减小 80% 以上；
  • 服务器推送（Server Push）：服务器预测客户端将请求的资源（如 HTML 里引用的 CSS）主动推给客户端。注意：Chrome 已在 2022 年移除对 Server Push 的支持（实际收益低、与客户端缓存冲突），面试讲到要说”已废弃”；
  • 缺点：TCP 层队头阻塞依然存在——一条流丢一个包，TCP 要等重传，而重传期间该连接上的所有流都被阻塞。

HTTP/3：QUIC 把可靠传输搬进用户态：QUIC 基于 UDP，在用户态实现”类 TCP 的可靠传输”（正是 5.3 的 RUDP 思路）——每个流独立编号、独立确认，一个流丢包只重传这个流，不阻塞其它流，彻底解决队头阻塞；同时把 TLS 1.3 集成进握手（首次连接 1-RTT，复用 0-RTT 可带数据），连接通过 Connection ID 标识（换 WiFi/4G 不断连）。代价是 QUIC 实现复杂度高，且依赖 UDP 端口穿透（部分老防火墙/NAT 对 UDP 不友好）。

5.5 HTTPS

为什么需要 HTTPS：HTTP 明文传输——中间人可以窃听（看到密码）、篡改（改响应内容）、伪装（冒充服务器）。HTTPS = HTTP + TLS，解决三件事：机密性（加密防窃听）、完整性（防篡改）、身份认证（防伪装）。

对称加密 vs 非对称加密

维度 对称加密 非对称加密
密钥 加解密同一把密钥 公钥加密、私钥解密（反之：私钥签名、公钥验签）
速度 快（AES 有硬件指令加速） 慢（RSA 比 AES 慢几个数量级；ECC 系更优）
密钥分发 困难：怎么安全地把密钥交给对方？ 公钥可公开分发
算法 AES、DES、3DES RSA、ECC（ECDHE/ECDSA）
用途 传输数据加密 密钥协商、数字签名、证书

HTTPS 的组合思路：性能差的非对称加密只用来协商对称密钥（密钥交换），拿到密钥后全部数据走对称加密（AES）——既安全（密钥不落地传输，由双方临时算出）又高效。密钥交换优先用 ECDHE（椭圆曲线 DH）：双方的 pre-master 由各自私钥 + 对方公钥算出，即使服务器私钥泄露也无法解密历史流量（前向保密）；RSA 密钥交换无前向保密，已被淘汰。

TLS 握手过程

步骤 内容 目的
① ClientHello 客户端支持的 TLS 版本、密码套件列表、随机数 发起协商
② ServerHello 选定版本与套件、随机数 定下协议参数
③ Certificate 服务器证书（含公钥 + CA 签名） 证明”我是 example.com”
④ 证书校验 客户端验证证书链、有效期、域名（SAN） 防伪装
⑤ 密钥交换 双方算出同一个 pre-master 生成会话密钥的种子
⑥ Finished 各自发 Finished 确认，切换对称加密 握手完成

TLS 1.3 的简化：只保留 1 次握手往返（1-RTT），移除 RSA 密钥交换等弱套件，强制 ECDHE + 前向保密；会话复用场景下 0-RTT——客户端直接带着上次会话的凭证发第一个请求，快一个往返。

证书链与 CA 信任体系

为什么需要 CA：服务器自己生成公钥没问题，但怎么让客户端相信”这把公钥真的是 example.com 的”？——证书（公钥 + 域名 + CA 的数字签名）。CA（证书颁发机构）是受信任第三方：它验证域名所有权后，用自己的私钥给证书签名；客户端用系统/浏览器内置信任库里的 CA 公钥验签——签名通过，就信这个证书。

证书链（三级）：

校验方向正好相反：从下往上——用中间 CA 的公钥验证 leaf 签名 → 用根 CA 的公钥验证中间 CA 签名 → 根 CA 在信任库里，验证链闭合。

为什么需要中间 CA：根 CA 私钥一旦泄露等于信任体系崩溃，所以根私钥离线保存、极少使用；签发权限下放给中间 CA，根只给中间 CA 签名。常见运维坑：

  • 中间证书没下发：服务器只配了 leaf 证书，客户端手里没有中间 CA 导致验证链断裂（chain incomplete）——排查用上面的 openssl s_client，修法是拼接”leaf + 中间CA”下发；
  • 证书与域名不匹配：证书 SAN 里没有当前域名（内网 IP、泛域名配置错）；
  • 证书过期：Let’s Encrypt 90 天短证书自动续期失败是高频事故；
  • 自签名证书：没经过 CA，浏览器不信任——只适合开发环境（用 mkcert 可以生成本地信任的证书），生产一律用正式 CA。

HTTPS 的性能优化

优化手段 原理
会话复用（Session ID / Session Ticket） 首次握手后缓存会话密钥，后续连接跳过完整握手（TLS 1.3 更是 0-RTT 直接带数据）——建连成本从”多次往返”降到”一次往返”
OCSP Stapling 证书吊销状态（OCSP 查询）由服务器代为查询并随握手响应下发，浏览器省去额外的吊销状态查询往返
HSTS 响应头 Strict-Transport-Security: max-age=31536000; includeSubDomains——浏览器记住”本域必须 HTTPS”，杜绝降级到 HTTP（防 SSL Strip 攻击）
TLS 1.3 握手 1-RTT、0-RTT 复用，密码套件简化（CPU 开销更小）
HTTP/2 + HTTPS 多路复用减少连接数，握手只发生一次
密钥轮换 / 证书自动续期 前向保密 + 避免过期事故（Let’s Encrypt 自动续期 + 监控）
