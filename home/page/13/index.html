向量数据库原理与实践

Posted on 2026-08-04 In AI大模型 Word count in article: 3.6k Reading time ≈ 13 mins.

向量数据库原理与实践

本文是《AI学习体系导航》阶段三的向量库专题深文，也是本站 ES 深文在 AI 方向的姊妹篇：从 ANN 索引原理（IVF/HNSW/PQ）到 Milvus/Pinecone/Elasticsearch 的选型与实战，覆盖生产级向量检索的完整知识。RAG 主链路见 RAG原理与实践，本文解决其中的”存储与检索”底座。

撰写时快照：本文基于 2026 年 8 月向量数据库生态撰写；各产品版本迭代快，部署参数以官方文档为准。

一、为什么需要向量数据库

1.1 向量检索场景

向量检索（语义相似度检索）在 AI 应用里无处不在：

场景 检索什么 典型规模
RAG 知识库 文档分块的 Embedding 万~亿级
语义搜索 商品/文档/代码向量 十万~十亿级
推荐召回 用户与物品向量 亿级
去重/查重 文本/图片相似度 千万级

1.2 与关系型数据库、全文检索的区别

维度 关系型 (MySQL) 全文检索 (ES) 向量数据库
查询方式 精确匹配/范围 关键词/分词 相似度 Top-K
索引结构 B+Tree 倒排索引 ANN 图/倒排+量化
返回 精确结果集 相关度排序 按相似度排序
典型查询 WHERE user_id=? match('退款') knn(query_vec, k=5)

关键差异是语义：向量数据库回答”和这句话最像的内容是什么“，而 SQL/全文检索回答”包含什么“。”退款流程”和”怎么退钱”在 SQL 里毫无关系，在向量空间里是邻居。

Java 对照：把向量库理解为”语义索引 + 相似度排序”的新存储引擎。你熟悉的 MySQL/Redis/ES 选型思维（数据量、QPS、一致性、运维成本）直接套用。

1.3 为什么不用 MySQL/ES 硬算

  • MySQL 存向量可以（BLOB + 余弦计算），但全表扫描——百万级数据单次查询秒级起，不可扩展；
  • ES 8.x 内置向量检索（dense_vector 字段自 7.10 引入，kNN 检索 8.x 完善，见第六章），小规模可用；
  • 专门的向量库在索引结构上做了优化（HNSW/IVF），亿级数据毫秒级返回。

选型铁律：数据量 × QPS 超过”硬算能扛”的阈值（约十万级×低QPS），就上专门的向量库。

二、索引原理：从暴力检索到 ANN

2.1 暴力检索

逐条计算查询向量与库中所有向量的相似度，取 Top-K。结果最准（精确 Top-K），但复杂度 O(N)——百万向量 × 1024 维，单次查询需要数十亿次浮点运算，不可接受。

所有向量索引都是近似（ANN, Approximate Nearest Neighbor）：牺牲一点点召回率，换来数量级的性能提升。

2.2 IVF（倒排文件索引）

思想：分桶 + 只搜附近的桶。

  • 聚类（K-means）把空间分成 N 个桶（如 1000 个），每个向量归入最近的桶；
  • 查询时只在与 query 最近的 n 个桶（nprobe）内暴力搜索；
  • 复杂度从 O(N) 降到 O(N/nprobe)。
参数 含义 权衡
nlist 桶数量 越多分得越细，建库越慢
nprobe 查询桶数 越大召回越高、越慢

类比：图书分类上架（按类分桶），查书先找对书架。IVF 是”分区”思路，实现简单，适合数据规模稳定、并发高的场景。

2.3 HNSW（层级可导航小世界图）

思想：多层图，从上往下逐层逼近。

参数 含义 权衡
M 每节点连接数 越大图越密、召回越高、内存越大
efConstruction 建图搜索宽度 越大图质量越高、建库越慢
efSearch 查询搜索宽度 越大召回越高、越慢

HNSW 是当前 RAG 场景的事实标准：召回率高、查询快，代价是内存占用大（图结构常驻内存）。类比：城市的道路导航——先走高速（稀疏层），再转县道（密集层），最终到达目的地。

2.4 PQ（乘积量化）与压缩

思想：降精度换内存。

  • 把 1024 维向量切成 M 段（如 64 段 × 16 维），每段用 K 个码字（如 256 个）量化；
  • 一个向量从”1024 个 float”（4KB）压缩为”M 个码字编号”（64 字节），内存降约 60 倍；
  • 相似度计算用查表（码本）代替浮点运算，更快。

代价：精度损失。生产实践：IVF+PQ 组合（大库标配）召回率可保持 95%+（配合足够 nprobe），内存却省一个数量级。

2.5 三种索引对比

索引 查询性能 召回率 内存 建库成本 适用
Brute Force 差 100% 高 无 小数据量、精度敏感
IVF 中 中 中 低 大库、可接受近似
HNSW 优 高 高 中 RAG 默认首选
IVF+PQ 优 中高 低 中 超大库、内存受限

Java 对照：IVF ≈ 分库分表的分区思路；HNSW ≈ 多级索引（B+Tree 从上到下的逼近）；PQ ≈ 压缩/降精度换空间。全是存量知识的换皮。

三、度量与评估

3.1 距离度量

度量 语义 典型场景
余弦相似度 方向相似（不看长度） 文本 Embedding 默认
内积 方向 + 幅度 已归一化向量的推荐
L2 距离 绝对距离 图像/几何

选型要点：文本 Embedding 首选余弦；库内度量必须与训练/向量化时一致（混用 = 检索失真）。注意：很多向量库把余弦预归一化为内积，声明要看清。

3.2 评估指标：Recall@k 与延迟

指标 定义 意义
Recall@k 暴力检索 Top-k 中，被 ANN 召回的比例 ANN 的”近似损失”
P95 查询延迟 95% 查询耗时 线上体验
索引内存 常驻内存占用 成本

验收流程：同一批查询，先跑暴力检索得到”真值 Top-k”，再对比 ANN 索引的召回率。目标：Recall@10 ≥ 95%，P95 < 20ms（百万级）。

四、Milvus 实战

4.1 架构概览

Milvus（开源向量数据库，Zilliz 主导）由松耦合组件构成：

组件 职责

Coordinator 元数据管理、集群调度
Datanode/Indexnode 数据存储与索引构建
Querynode 查询执行（CPU/GPU）
Meta Store（etcd）+ 对象存储 元数据与数据持久化

部署形态：单机 docker compose 起步（学习/原型），生产走 Kubernetes 集群（需要对象存储如 MinIO/S3）。

五、Pinecone 与托管服务

5.1 托管服务的定位

不想运维向量库时，托管服务（Pinecone、云厂商向量检索等）是省心之选：

维度 自建 Milvus 托管（Pinecone 等）
运维 自己管集群/备份/扩容 全托管，Serverless 按量计费
起步 快（docker compose） 最快（API Key 即用）
成本 固定服务器成本 按存储+查询计费，量大后更高
数据主权 完全自主 数据出网（合规需评估）
能力边界 灵活可控 受平台限制（过滤语法等）

决策建议：原型/验证期用托管（省时），进入规模化生产且数据敏感时迁自建。协议层面两者都能通过 Python SDK / REST 接入，迁移成本主要在建库流程。

八、生产优化

8.1 数据量预估

估算项 公式/经验
分块数 文档总 token ÷ 块大小（500）
向量存储 分块数 × 维度 × 4 字节（float32）
HNSW 内存 向量存储 × 2~3 倍（图结构开销）
示例 100 万块 × 1024 维 ≈ 4GB 向量 + 8~12GB 图内存

先算账再选型：内存超单机 → Milvus 集群 or IVF+PQ 压缩。

8.2 Filtered ANN

元数据过滤分两种实现：

  • 先过滤后检索：候选集小 → 慢且召回可能被过滤打断；
  • 先检索后过滤：候选集大 → 快但可能返回过滤后不足 k 条。

各库实现不同（Milvus 支持过滤索引加速；ES 的 knn+filter 同理）。生产必须测：过滤字段加索引，压测”带过滤的查询”延迟，防止过滤把毫秒级查询拖到秒级。

8.3 缓存与降级

  • 热点 query 缓存（Redis，与业务缓存同构）；
  • 索引构建/加载失败 → 降级到暴力扫描或直接报错（检索是强依赖，需有兜底）；
  • 监控：查询延迟、召回率抽样、索引内存、写入积压。

8.4 监控指标体系

指标 阈值参考
P95 查询延迟 < 20ms
Recall@10（抽样对暴力检索） ≥ 95%
写入延迟/积压 不积压
索引内存 < 节点内存 70%

九、实战：RAG 场景的向量库选型决策

以”企业私有知识库（100 万文档分块）”为例走一遍决策：

决策点 选择 理由
数据规模 ~100 万块 × 1024 维 内存 ~12GB，单机 Milvus 或 ES 均可
是否已有 ES 是 → ES 起步 复用集群与运维
过滤需求 按 doc_id/部门过滤 两种方案都支持，需加过滤索引压测
混合检索 是（编号/专有名词多） ES 内建 RRF，Milvus 配 BM25 外部融合
数据敏感 不出网 排除 Pinecone
最终 ES（复用存量）→ 数据过亿再评估 Milvus 摩擦最小

决策心法：向量库选型不是”哪个最强”，而是”哪个摩擦最小”——运维一致性、团队熟悉度、过滤能力往往比峰值性能更关键。

RAG原理与实践

Posted on 2026-08-04 In AI大模型 Word count in article: 4.5k Reading time ≈ 16 mins.

RAG 原理与实践

本文是《AI学习体系导航》阶段三的核心深文，也是本站 RAG 的唯一专题：从”为什么需要 RAG”到文档解析、分块、Embedding、检索、重排、上下文组装、评测迭代与工程化，覆盖生产级 RAG 系统的完整链路。Python 生态为主（unstructured / bge-embedding / LangChain / LlamaIndex / RAGAS），Java 侧以 Spring AI VectorStore 对照收尾。

撰写时快照：本文基于 2026 年 8 月主流 RAG 技术栈撰写；Embedding 模型与向量库版本演进较快，选型数据以文中标注为准。

一、为什么需要 RAG

1.1 大模型的三个固有缺陷

缺陷 表现 根因
知识过期 训练截止后的事实不知道 参数记忆有截止时间
私有知识缺失 公司内部文档、业务数据一概不知 训练数据不含私有语料
幻觉 一本正经编造不存在的事实 生成式模型本质是”合理续写”

RAG（Retrieval-Augmented Generation，检索增强生成）的解法朴素而有效：先检索、再生成——把相关文档检索出来塞进上下文，让模型”照着资料回答”。

1.2 RAG vs 微调 vs Prompt 调优：先决策再动手

方案 解决什么 成本 生效时机 适用场景
Prompt 调优 输出风格、格式 极低 即时 不涉及新知识
RAG 知识注入、防幻觉 低（向量库+调用费） 即时可更新 私有知识、动态知识、需要引用溯源
微调 学习行为模式、领域语言 高（训练+评测） 需训练周期 风格对齐、特殊格式、难以用资料表达的隐含知识

决策原则：知识问题用 RAG，行为问题才考虑微调。 大多数业务需求（FAQ、文档问答、业务助手）都是知识问题——这也是 LLM微调入门 的核心论点”微调是最后手段”的由来。

1.3 RAG 的适用边界

  • 适合：知识库问答、私域文档检索、动态资讯（产品文档、客服手册、法律法规）；
  • 不适合：纯推理题（检索帮不上）、创意生成（知识不是瓶颈）、实时性要求苛刻的超长文档（窗口装得下就别检索）。

二、文档解析与清洗

2.1 解析：从”文件”到”文本”

知识库的源文件千奇百怪：PDF、Word、Markdown、HTML、PPT、扫描件。解析的目标是无损地还原文档的逻辑结构（标题层级、表格、段落）。

格式 工具 要点
PDF pypdf / PyMuPDF / unstructured 区分文本型与扫描型（后者需 OCR）
Word python-docx 保留段落与表格结构
Markdown/HTML langchain-text-splitters / BeautifulSoup 保留标题层级（对分块至关重要）
表格 结构化解析为 Markdown 表格 表格转文字行会丢结构

黄金准则：解析要保结构。 标题层级是后续分块的锚点，表格转纯文本会严重损害检索质量。

2.2 清洗：脏数据是检索质量的隐形杀手

脏数据 影响 清洗手段
页眉页脚/页码 污染语义 正则/位置过滤
重复段落 检索冗余、涨分块数 相似度去重（Embedding 余弦 > 0.98 视为重复）
乱码/控制字符 解析异常 字符级清洗
无效文本（”第N页共M页”） 检索噪声 规则过滤 + 人工抽检

清洗阶段做得好，能省下游 80% 的调优时间。

三、Chunking 策略

3.1 为什么必须分块

  • 检索单元：Embedding 对整本书的向量会”平均化”，什么都像、什么都不像；
  • 上下文预算：窗口有限，检索结果只能塞进部分文本；
  • 引用精度：回答要能溯源到具体段落。

分块是 RAG 系统里性价比最高的调优点——同样的文档，分块好坏可差 10-20 个百分点的检索命中率。

3.2 四种主流策略

策略 做法 优点 缺点 适用
固定窗口 按 token/字符数硬切 简单、快 切断语义 兜底/海量文档
递归字符 按 \n\n → \n → 句子逐级切 保留段落边界 需调分隔符 通用首选
语义分块 按嵌入相似度找语义边界 块内语义内聚 计算成本高 语义跳跃大的文档
父子分块 小块检索 + 大块喂上下文 精度与信息量兼得 实现复杂 生产系统推荐

3.3 块大小与重叠

  • 块大小：200-800 token 是主流区间。块越小检索越精确但上下文越碎；块越大上下文越完整但噪声越多；
  • 重叠（overlap）：相邻块重叠 10-20%，防止关键句被切断；
  • 元数据：每个块携带来源（文档、章节、页码、更新时间）——这是引用溯源的基础。

Java 对照：分块 ≈ 日志/消息的分片策略。chunk 大小 ≈ 分片大小，overlap ≈ 分片重叠保护边界——你在 Kafka 分区设计里的直觉同样适用。

3.4 分块效果的实验方法

不要拍脑袋：对同文档跑 2-3 种分块配置，用 20 个典型问题 + 人工判断”检索到的块是否包含答案”，记录命中率。分块参数要在检索层面评测，而不是在生成层面凭感觉。

四、Embedding

4.1 Embedding 是什么

Embedding 把文本映射为固定维度（如 1024 维）的稠密向量，语义相近的文本在向量空间中距离更近：

相似度度量：余弦相似度（最常用）、内积、L2 距离。

4.2 模型选型

模型 特点 适用
text-embedding-3-small/large 云 API、无需自部署 快速起步
bge / BAAI 系列 中文效果好、可自部署 中文知识库、数据安全要求高
Qwen 系 Embedding 中文生态 中文 + 本地化
多模态 Embedding 文本+图片统一向量 图文知识库

关键决策：自部署 vs 云 API。 决定因素：数据敏感性（私有文档能否出网）、调用量成本、中文效果要求。自部署 Embedding 模型成本低（几 GB 显存），是私有知识库的常见选择（部署见 LLM推理与部署实战）。

4.3 批量与缓存

  • 批量：Embedding API 支持一次传多段文本（batch），显著降低成本与延迟；
  • 缓存：文档没变就不要重复向量化——按内容哈希缓存向量，增量更新场景必备（见第九章）；
  • 维度选择：同源 Embedding 维度必须一致，切换模型 = 全库重新向量化（这是重要的架构约束，选型前想清楚）。

五、检索原理

5.1 相似度检索与 Top-K

检索器的工作：把用户问题向量化 → 在向量库中找 Top-K 最相似的分块。K 的典型值 3-10：太小漏信息，太大噪声多、token 成本高。

5.2 元数据过滤

只靠语义相似度不够——业务上”只要近 30 天的文档””只检索某部门资料”是常态。过滤（filter）与检索（search）要分开做：先按元数据缩小候选集，再在候选集内做向量检索。

Java 对照：元数据过滤 ≈ SQL 的 WHERE 前置 + 召回排序。检索本质是”索引筛选 + 评分排序”，与 ES 查询心智完全一致。

5.3 混合检索（BM25 + 稠密向量）

稠密向量检索擅长语义匹配，但对精确词、编号、专有名词（”XJ-2024-0012”）常常失灵——这种场景传统的关键词检索（BM25）反而稳。混合检索 = 两条腿走路：

混合检索是生产级 RAG 的标配——纯向量检索在真实企业知识库（充满编号、术语、表格）上通常比混合检索低 5-15 个百分点。

5.4 多路召回

复杂的知识库可以同时走多路：向量检索（语义）、BM25（关键词）、SQL 精确查（结构化数据）、图检索（关系查询），最后融合。多路召回增加覆盖，代价是工程复杂度——先单路 + 混合检索跑通，再按评测数据决定是否加路。

六、Rerank

6.1 为什么需要重排

向量相似度是”近似语义匹配”，而相关性判断（”这段到底回答得了这个问题吗”）是更精细的任务。重排：先粗召回 Top-50，再用更强的模型精排成 Top-5。

阶段 模型 候选量 目标
召回 Bi-Encoder（快） 50-100 不遗漏
精排 Cross-Encoder（慢但准） 5-10 高精度

Bi-Encoder：query 和文档分别编码后算相似度（可离线建索引）；Cross-Encoder：query 与文档拼在一起过一遍模型（计算昂贵，只能在线小批量）。Cross-Encoder 的相关性判断显著更准。

6.2 Rerank 部署与延迟

  • Rerank 模型（如 bge-reranker）很小（百 MB 级），本地部署成本低；
  • 精排 50 个候选约几十毫秒到几百毫秒——只对粗召回结果做，延迟可控；
  • Rerank 后必须重新设置 Top-K 与置信度阈值，过滤低相关结果。

收益量化：业界实践普遍显示，加 Rerank 后检索命中率提升 5-15 个百分点，是 RAG 优化中投入产出比最高的单项。

七、上下文组装与生成

7.1 Prompt 模板：检索结果如何”喂”给模型

检索结果不是简单拼接——需要明确的指令边界：

关键设计：

  • 来源标注：每段资料带编号与出处，回答要求引用编号（溯源）；
  • 防幻觉指令：”仅基于资料回答 + 无答案明说”是 RAG 防幻觉的第一道防线；
  • 角色分离：资料与问题用明确分隔符区分，防止资料内容与指令混淆（安全边界，见 Agent安全与防护）。

7.2 引用溯源（citation）

回答带引用是 RAG 区别于”裸模型”的核心能力：

输出示例：退款通常 3-5 个工作日到账 [2]。

Java 对照：引用编号 ≈ 日志里的 traceId——回答可回溯到证据，是排查”答错了为什么”的关键基础设施。

7.3 长上下文的取舍

  • 检索结果塞得越多，上下文越长、成本越高、模型越容易”迷路”；
  • 原则：宁缺毋滥——Top-5 高质量块优于 Top-20 的噪声堆；
  • 超长上下文场景考虑：先摘要再生成，或分层检索（先检索章节，再在章节内检索段落——即父子分块的自然延伸）。

八、评测与迭代

8.1 评测的两个层面

层面 问题 指标
检索质量 该召回的是否召回 命中率、Recall@k、MRR
生成质量 回答是否忠实于检索结果 忠实度、答案相关性、上下文相关性

两个层面分开评：检索不好先修检索（分块/重排/混合检索），生成不好再修 Prompt——混在一起没法定位问题。

8.2 RAGAS 指标

RAGAS 是开源 RAG 评测框架，核心四个指标：

指标 衡量 直觉理解
忠实度（Faithfulness） 回答是否忠于检索资料 有没有编造
答案相关性（Answer Relevancy） 回答是否切题 有没有答非所问
上下文相关性（Context Relevancy） 检索结果与问题相关度 检索得准不准
上下文召回（Context Recall） 该有的资料是否都被检索到 有没有漏

8.3 评测集构建

  • 规模：起步 30-50 条，覆盖常见问题、边界问题、易混问题；
  • 真值：每条标注 ground_truth 答案 + 期望检索到的资料；
  • 迭代：评测集进 Git 管理，RAG 任何改动（分块参数、检索策略、Prompt）跑一遍回归，分数不降才上线（与 Prompt工程实战 的回归流程同构，完整体系见 LLM评测与可观测性）。

8.4 常见失败模式与优化清单

症状 排查方向 优化手段
该答的没答上 检索召回不足 混合检索、加大召回、分块优化
答非所问 检索结果与问题错位 Rerank、过滤规则、query 改写
回答编造 生成层没守住 防幻觉指令、引用溯源、降温度
答得泛 上下文太碎 父子分块、加大块大小

一、OpenAI 兼容协议

1.1 为什么先讲协议而不是 SDK

所有大模型平台（云端与本地）的 HTTP 接口都收敛到 OpenAI 兼容协议——POST /v1/chat/completions 返回结构几乎一致。掌握了协议，SDK 只是协议的一层封装，换任何平台、任何语言都不再需要重学。

max_tokens 输出上限（含输出 token 计费） 按任务给，宁小勿大

二、流式输出 SSE

2.1 为什么必须流式

大模型生成速度约 2060 token/s，一段 500 token 的回答完整返回需要 1025 秒。用户无法等待”转圈结束”——首 token 时间（TTFT）是对话产品体验的第一指标。流式让首 token 在几百毫秒内到达，后续内容边生成边渲染。

场景 非流式 流式
对话产品 用户干等 10s+ 首 token < 1s
长文档生成 20s+ 无反馈 边写边看
服务端整合 简单 需转发流（见 2.5）

2.2 SSE 协议原理

SSE（Server-Sent Events）是基于 HTTP 的服务器单向推送协议，与 WebSocket 的区别：单向、纯文本、HTTP 原生。每个事件格式：

  • 每行 data: 前缀 + JSON，空行分隔事件；
  • 内容逐 token 出现在 choices[0].delta.content；
  • 结束标记 data: [DONE]。

Java 对照：SSE 就是”长连接 + 分块推送”，与 Netty 的 Chunked Write/异步读思路同构。你已经掌握的异步与背压思维直接适用。

2.4 Java 原生流式

WebFlux 的响应式流天然对应 SSE 的推送模型——这是 Java 工程师进入 AI 领域最平滑的技术迁移点。

2.5 服务端转发流

真实系统中，LLM 调用在后端服务里，需要把流转发给前端：

  • 后端：StreamingChatService 接收上游 SSE，逐块转发到下游；
  • 前端：EventSource（GET 限定）或 fetch + ReadableStream（POST 可用，推荐）逐段渲染；
  • 关键点：转发层必须处理客户端断开（取消上游）、超时、错误吞掉（不能让一个中断的流污染业务）。

三、结构化输出

3.1 为什么需要结构化输出

LLM 输出是自由文本，而业务需要的是 JSON。"只输出 JSON" 在 prompt 里说一百遍，也不如协议层约束可靠。结构化输出是 RAG 管道、Agent 工具调用、数据抽取 的前提（后续文章全部依赖它）。

3.2 JSON Mode 与强约束

JSON Mode（response_format={"type":"json_object"}）：保证输出是合法 JSON，但不保证字段结构。

强约束（response_format + JSON Schema，或工具约束）：字段结构也由 Schema 保证——生产环境优先用它，JSON Mode 只作为兜底。

Java 对照：JSON Schema 约束 ≈ 强类型 DTO 的序列化约束。Schema 直接由 Java DTO 的 Jackson 注解生成（jackson-jsonschema），双端一致。

3.3 Python 校验与修复循环

协议约束仍可能被模型绕过（字段缺失、类型错误），工程上必须加解析 + 校验 + 修复闭环：

修复循环是结构化输出的核心工程模式：解析失败不是直接报错，而是把错误信息作为新消息回喂模型修正。成功率可从 90% 提升到 99%+。

四、Function Calling

4.1 原理：一次”模型不会执行、只会申请”的握手

Function Calling 是 Agent 能力的基石。模型本身不执行任何代码，它只负责：识别”这个任务需要调用工具”→ 输出一个结构化的工具调用申请（函数名 + 参数 JSON）→ 由你的代码执行 → 把结果回填给模型继续生成。

Java 对照：这本质是 RPC + 回调：模型是调用方（只发请求不执行），你的服务是提供方。工具注册表 ≈ 服务注册中心，工具 Schema ≈ 接口契约。

4.2 工具 Schema 设计准则

Schema 的质量决定模型选工具的准确率：

准则 说明
描述要具体 查询天气 远不如 查询指定城市指定日期的天气，返回温度、降水、风力
参数越少越好 3 个以内的必选参数；多余参数模型容易填错
枚举约束 城市、单位等用 enum 限定取值空间
数量克制 单个模型暴露 5~15 个工具最佳；工具太多选择准确率断崖下降（业界案例：Copilot 工具数从 40 收敛到 13）

4.3 完整调用流程（Python）

必须遵守的三条协议规则（踩坑高发区）：

  1. 工具结果必须以 role: "tool" + tool_call_id 回填；
  2. 模型的 tool_calls 消息必须先追加进 messages 再追加工具结果；
  3. max_steps 循环上限必须存在——否则模型可能无限调用工具。

4.4 并行工具调用

支持 parallel_tool_calls 的模型一次可申请多个工具调用（同一消息里多个 tool_calls 条目）。适合相互独立的查询：

  • 收益：一次往返完成 N 个查询，延迟降为约 1/N；
  • 风险：工具必须有副作用安全（幂等）——并行执行顺序不可控。

Java 对照：并行工具调用 ≈ CompletableFuture 批量查询；每个工具执行封装成独立任务，结果按 tool_call_id 合并回填。

4.5 工具调用的常见坑

坑 表现 对策
参数幻觉 传了 Schema 外的字段 服务端白名单校验，丢弃未知字段
重复调用 同一查询反复申请 会话内工具结果缓存
工具异常 工具抛错 把错误转成”工具返回错误信息”，让模型换方案（不要直接中断）
死循环 模型反复调用失败工具 max_steps 上限 + 熔断

五、多轮对话与上下文

5.1 messages 结构与角色

LLM 本身无状态——“记忆”就是把历史原样塞进 messages。四个角色：

角色 语义 说明
system 系统指令 设定行为，一般只放一条且放最前（优先级最高）
user 用户输入 多轮中的每个问题
assistant 模型回复 历史回答（含历史 tool_calls）
tool 工具结果 必须携带 tool_call_id 回填（见第四章）

Java 对照：messages ≈ 一个有界队列的消息记录。角色约束（assistant 不得伪造 user 消息）≈ 消息类型校验。

5.2 Token 计数与上下文预算

每次请求的输入 token = 系统指令 + 全部历史 + 本次输入。三件事必须心里有数：

  1. 窗口上限：如 128K 上下文窗口，超限会报错或被截断；
  2. 成本随轮次线性增长：第 10 轮的输入 token 可能比第 1 轮多 10 倍；
  3. **长上下文的”稀释效应”**：窗口内信息越多，模型越容易遗漏早期指令（指令遗忘）。

5.3 历史裁剪三策略

策略 做法 适用场景
滑动窗口 只保留最近 N 轮，最早的直接丢弃 闲聊、客服（简单可靠）
摘要压缩 把早期历史交给模型生成摘要，替换原文 长文档分析、深度对话
关键信息抽取 提取早期对话中的事实（偏好、参数）存结构化记忆 个性化场景（搭配向量记忆见 Agent原理与实践）

六、错误处理与重试

6.1 错误分类

错误 含义 处理策略
429 限流（QPM/token 超限） 指数退避重试 + 排队
408/超时 网关或读取超时 短超时重试 1-2 次
401/403 鉴权失败 不重试，告警查 key
400 参数错误（多为 messages 非法） 不重试，记日志修代码
5xx 服务端故障 退避重试，最大次数有限
网络中断 连接断开 重试前判断请求是否可能已生效

原则：只对可重试的错误重试；永远不要让重试放大副作用。

6.2 指数退避 + 抖动

重试是概率系统下的必需品——模型服务高负载时会限流，退避重试是行业标准做法：

Java 对照：这就是 Spring Retry / Resilience4j 的 Retry + ExponentialBackoff，加上 Sentinel 的限流熔断——你已经写过无数次。唯一新意是重试单位变成”秒级”而非”毫秒级”。

6.3 熔断与降级

高频调用场景需要熔断（连续失败快速失败，避免雪崩）：

降级策略示例（按代价从小到大）：

  1. 换小模型（如 gpt-4o → gpt-4o-mini）继续服务；
  2. 换供应商（OpenAI ↔ 通义 ↔ 本地 vLLM——协议统一让切换零成本）；
  3. 返回缓存命中 / 兜底话术。

6.4 幂等与重放保护

重试的最大隐患：请求已被执行但响应丢失。工具调用场景（第四章）必须做到：

  • 工具本身幂等（查询天然幂等；写操作带幂等键）；
  • 请求级幂等键：同一请求重试复用同一 ID，服务端去重；
  • 记请求日志，重放时先查日志确认是否已处理。

七、成本与延迟优化

7.1 Token 计价模型

模型档位 输入单价（元/百万 token，约） 输出单价 场景
旗舰 高 更高 复杂推理、Agent 决策
中级 中 中 通用问答、RAG 生成
小模型 低（可低 10-20 倍） 低 分类、抽取、路由、摘要

成本公式：单次成本 = 输入token × 输入单价 + 输出token × 输出单价。

一个真实账本（日 100 万次调用）：

场景 输入 token 输出 token 单价档位 日成本
全用旗舰 800 200 高 ≈ 数千元
路由后 80% 走小模型 800 200 混合 ≈ 数百元

成本控制的第一杠杆不是压 token，是路由到合适的模型。

7.2 Prompt 缓存

系统指令、Few-shot 示例是固定前缀，主流平台提供自动/显式前缀缓存：命中缓存的输入 token 费用降为约 1/10，首 token 延迟也显著下降。

工程要点：

  • 系统指令放在 messages 最前，且保持字节级稳定（改动一个字符 = 缓存全部失效）；
  • 模板变量放在固定前缀之后、靠近用户消息；
  • 用缓存命中率指标监控 Prompt 稳定性（这是”Prompt 当代码管”的直接收益）。

7.3 模型路由与降级

统一协议让路由成为纯配置：

更工程化的做法是让一个小模型做意图分类（分类器成本极低），再由路由表决定用哪个模型。降级链：旗舰 → 中级 → 小模型 → 缓存 → 兜底话术（见 6.3）。

7.4 延迟优化清单

手段 收益 代价
流式输出 TTFT 从秒级到毫秒级 前端/转发层改造
并行工具调用 多查询延迟 ~1/N 工具需幂等
Prompt 缓存 首 token 延迟下降 + 成本下降 前缀需稳定

输出上限控制 防长输出拖慢 P99 需处理 finish_reason=length

8.1 统一 LLM Client 层

所有调用收敛到一个抽象层，业务不直接碰 SDK：

  • 记录：请求 ID、模型、输入/输出 token、耗时、是否重试、是否命中缓存；
  • 脱敏：用户消息与工具结果中的 PII 字段必须脱敏后才落日志；
  • 审计：工具调用（谁、何时、用了什么工具、参数）全量留痕——安全与合规的基础（见 Agent安全与防护）；
  • 结构化：日志进统一的 trace 体系（LLM评测与可观测性）。

8.3 并发与限流

LLM API 是高延迟外部依赖（非流式 1-10s+），并发治理与数据库连接池同理：

  • 客户端侧限流（令牌桶）：防止单服务打爆供应商配额；
  • 连接复用：HTTP 连接池（Python httpx.AsyncClient / Java OkHttp 连接池）；
  • 队列化：突发流量进队列削峰（消息队列思维直接复用）；
  • 超时分层：连接超时 < 读超时 < 全请求超时，逐层降级。

Prompt 工程实战

本文是《AI学习体系导航》阶段一的实践篇，也是全站 AI 系列的第一篇”方法论”文章：给出 Prompt 从设计、调优到评估的完整工程方法。概念定义见 AI大模型核心概念综述，API 调用细节见 LLM API与工具调用实战。

撰写时快照：本文基于 2026 年 8 月主流大模型 API 的通用行为撰写；各家模型在指令遵循、格式稳定性上存在差异，示例 Prompt 需结合具体模型微调。

一、Prompt 的本质与评判标准

1. 本质：与概率系统对话的接口

写 Java 时，代码是确定性的：同样的输入必然得到同样的输出。而 LLM 是概率系统——同样的 Prompt 每次输出可能不同。这意味着：

  • 你无法”调试” Prompt，只能”评估”它；
  • 效果问题不能靠读代码定位，只能靠样本统计定位；
  • Prompt 不是文档，是代码：它会变化、有 bug、需要版本管理和回归测试。

把这个思维转换建立起来，是 Prompt 工程的第一课。

2. 四个评判维度

维度 衡量什么 典型观测手段
正确率 任务完成的对错 回归测试集上的通过率
格式稳定性 输出是否符合约定结构 JSON 解析成功率、字段缺失率
成本 每请求 token 消耗 输入/输出 token 统计
延迟 首 token / 总耗时 请求日志

Java 对照：正确率 ≈ 单元测试通过率，格式稳定性 ≈ 反序列化失败率，成本 ≈ 每接口调用的资源开销。用工程指标管 Prompt，不要用”感觉”。

3. 一个典型的”坏 Prompt”

问题：任务含糊（格式不明）、无输出约束（自由发挥）、无边界（时区？null？）。改成结构化后：

同一模型，前者的格式乱、边界未处理；后者一次到位。差距不在模型，在输入设计。

二、结构化 Prompt 设计

1. 五要素模板

成熟的业务 Prompt 通常包含五个要素：

要素 作用 缺失后果
角色 限定知识范围与语气 回答泛化、不聚焦
任务 明确要做什么 答非所问
输入 声明输入结构 遗漏字段、处理错位
输出格式 约束结构 解析困难、字段缺失
约束 边界与禁忌 越界、幻觉、过度发挥

组合成模板：

2. 系统指令设计原则

  • **写”要什么”，也写”不要什么”**：仅靠正面描述，模型可能输出多余的客套话或越界内容。
  • 约束必须可验证：让”输出 JSON”变成”只输出 JSON，无任何其他文字”——后者可被程序直接验证。
  • 信息密度优先：每个词都有信息量，避免客套开场（”我将尽力帮助您”之类是纯 token 浪费）。
  • 把示例当规范：输出格式部分给一个完整示例，比十句描述都有效。

3. 输出格式：JSON 与结构化输出

配合 API 的 JSON Mode / 结构化输出约束（见 LLM API与工具调用实战）可进一步保证解析成功。

三、Few-shot 示例

1. 为什么示例有效

Few-shot 让模型从”按描述理解”变为”按示例模仿”，对格式类、分类类、风格类任务效果显著。示例本质上是在给模型划定输入分布。

2. 示例设计要点

要点 说明
多样性 覆盖不同输入形态，避免只给”典型”样本
边界样本 放 1-2 个易混淆的负例（这是最常见被忽略的）
数量权衡 2-5 个通常足够；每个示例都有 token 成本
示例即规范 示例中的任何意外细节都会被模型模仿（如多余空格）

3. 静态 vs 动态示例

  • 静态：固定 2-3 个示例，适合格式稳定、分布简单的任务。
  • 动态：从示例库中按相似度检索 top-k（本质是一个迷你 RAG），适合输入分布宽的任务——示例的选择可以随用户输入变化。

Java 对照：示例选择 ≈ 缓存键设计——选对”命中”的样本，效果立竿见影。

1. 零样本 CoT

在任务末尾追加一句”让我们一步步思考”，能显著提升推理类任务的正确率。零样本、零成本，先试它：

2. CoT 提示

对复杂推理，给出完整推理过程示例比只给结论有效得多：

3. Self-consistency

同一问题采样 N 次，取答案投票最多的——把概率系统的随机性变成统计优势。成本 N 倍，正确率可再提升 10-20 个百分点（推理任务）。适合离线/可等待场景，不适合实时对话。

4. 适用边界

任务类型 CoT 效果 建议
数学/逻辑推理 显著提升 必用
分类/抽取 提升有限 可跳过，结构化 Prompt 足够
创意写作 无帮助 不要用
短任务 反而引入废话 关闭

不要对简单任务无脑加 CoT——它浪费 token 且降低响应速度。

五、失败模式与调试

1. 常见失败模式

失败模式 表现 常见原因 应对
幻觉 编造事实、引用不存在 知识缺失、Prompt 诱导 加”仅基于给定信息回答”；接 RAG
格式错误 JSON 解析失败、多输出文字 约束不严、示例缺失 结构化输出约束 + 完整示例

关键习惯：temperature 固定为 0 再调试，否则你无法区分”Prompt 的问题”和”随机性的问题”。

八、与工程结合

1. 模板化管理

  • Prompt 与代码分离：存模板文件（如 prompts/ 目录），按环境（dev/prod）配置；
  • 版本化：Prompt 变更走代码评审与回归流程；
  • 变量化：角色、示例、约束做成参数，避免复制粘贴出多份漂移副本。

2. 成本与缓存

  • 系统指令 + 示例部分是固定前缀，可用 API 的 prompt caching 机制显著降本；
  • 长 Prompt 的 token 成本按量计费（见 LLM推理与部署实战 成本章节）；
  • 精简 Prompt 每省 1 个 token，乘以百万级调用都是真实成本。

3. 安全的基线

  • 系统指令不能信任：用户输入可能覆盖它（提示注入），必须结合 Agent安全与防护 的输入边界设计；
  • 用户输入与指令拼接时做角色分离，不要简单字符串拼接。
