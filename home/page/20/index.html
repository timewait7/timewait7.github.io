1. MySQL 架构概览

回答一个问题：一条 SQL 从客户端发出到返回结果，中间经过哪些组件，它们各自干什么。

1.1 两层架构：Server 层与存储引擎层

MySQL 分为两层：

  • Server 层：负责连接管理、解析、优化、执行以及内置函数（日期、数学、字符串）、存储过程、触发器、视图等通用功能。所有存储引擎共用这一层。
  • 存储引擎层：负责数据的存储与提取。插件式架构是 MySQL 最核心的设计——同样的 SQL，底层可以换成 InnoDB、MyISAM 等不同引擎。

1.2 一条 SELECT 语句的执行流程

一条查询语句依次经过五个组件：

  1. 连接器：建立连接、校验用户名密码、获取权限。连接建立后即使管理员改了权限，也要重连才生效；show processlist 可查看连接状态，空闲连接受 wait_timeout（默认 8 小时）控制。
  2. 解析器：词法分析 + 语法分析，把 SQL 拆成语法树。语法错误在这一步报出。注：MySQL 8.0 已移除查询缓存；8.0 之前会先查查询缓存，命中则直接返回。
  3. 预处理器：检查表和列是否存在、解析别名、校验执行权限（对表的 SELECT 权限在打开表时校验）。
  4. 优化器：基于统计信息选择执行计划——决定用哪个索引、表的连接顺序、是否走索引下推等。
  5. 执行器：按执行计划调用存储引擎接口，逐行判断条件并返回结果。

1.4 一条 UPDATE 语句的执行流程

更新语句比查询多了”修改数据 + 保证持久性”两步，是整个架构的集大成者。一条 UPDATE 的完整流程：

① Server 层：连接、解析、优化

  1. 连接器建立连接，校验身份与权限；
  2. 解析器词法分析 + 语法分析，构建语法树；
  3. 预处理器检查表、列是否存在；
  4. 优化器基于统计信息选择执行计划：决定使用哪个索引定位要更新的行（这是影响更新速度的关键），必要时全表扫描；
  5. 执行引擎按计划调用 InnoDB 接口执行修改。

② InnoDB 层：缓冲池 + 日志先行

  1. 缓冲池查找：InnoDB 先在 Buffer Pool 中查找目标行所在的数据页，不在则从 .ibd 数据文件加载到内存；
  2. 写 Undo Log（关键）：修改前先把旧值写入 undo log（回滚日志）。两个目的：事务回滚时恢复旧值；其他并发事务通过 undo 版本链读到旧版本（MVCC）；
  3. 修改 Buffer Pool：把数据页中的行更新为新值，该页变为脏页（内存与磁盘不一致）；
  4. 写 Redo Log Buffer（关键）：把数据页的物理修改（字节级变化）记入内存中的 redo log buffer。先写日志、后刷脏页，这是 WAL（Write-Ahead Logging）原则——保证崩溃后能重做，也是持久性的来源。

③ 提交阶段：两阶段提交（关键）

  1. Write Redo Log（prepare）：将 redo log buffer 中本事务的记录顺序刷盘，标记为 PREPARE，必要时 fsync()——这是持久性的关键点，也是相对耗时的操作；
  2. Write Binlog：Server 层把逻辑变更写入 binlog（用于主从复制与恢复），同样按 sync_binlog 配置刷盘；
  3. Write Redo Log（commit）：binlog 成功落盘后，在 redo log 中写入 COMMIT 标记，事务在引擎层正式提交；
  4. 释放锁、返回成功。

④ 后台异步刷脏页（非同步操作）

提交成功并不保证脏页立即写回磁盘——redo log 已经保证了持久性。Page Cleaner 线程在以下时机异步刷脏页：

  • 脏页比例过高（innodb_max_dirty_pages_pct 控制）；
  • 系统空闲时；
  • redo log 空间即将用完（回收旧日志前必须先刷对应脏页）；
  • 正常关闭时。

本节小结：Server 层管”怎么执行”，引擎层管”怎么存储”；查询走五件套（连接器→解析器→优化器→执行器→存储引擎），更新在此基础上多了 undo log（可回滚）、redo log（持久化）、binlog（复制与恢复）三个关键环节。细节分别在本文第 5、6 节展开。

2. 索引

回答三个问题：为什么 B+ 树、聚簇索引与二级索引的区别、回表/覆盖索引/最左前缀/索引下推这几个概念怎么串起来。

2.1 B+ 树为什么是 InnoDB 的默认索引结构

B+ 树与 B 树的对比（InnoDB 选择 B+ 树的原因）：

对比维度 B 树 B+ 树 InnoDB 优势体现
数据存储位置 所有节点存储数据 仅叶子节点存储数据 减少磁盘 IO 次数
树高度 较高（数据分散存储） 较低（内部节点纯索引） 3 层 B+ 树可支撑千万级数据
范围查询 需要回溯父节点 通过叶子链表顺序扫描 WHERE id > 100 效率高一个量级
全表扫描 需遍历整棵树 直接顺序遍历叶子节点链表 全表扫描接近顺序读
磁盘利用率 节点含数据，单页存键值少 单页可存更多键值（高分支因子） 相同数据量树高更矮
数据更新代价 可能引起复杂结构调整 插入删除多数情况只需局部调整 支持更高并发写入
缓存命中率 热点数据分散在不同层级 叶子节点集中存储所有数据 Buffer Pool 利用率高

背后的物理原因：磁盘 IO 按页（默认 16 KB）为单位读取，树的层数决定了一次查询的 IO 次数。B+ 树内部节点只存键值 + 指针（不存数据），一页能容纳更多键，树自然更矮；叶子节点用链表串起，范围查询不需要中序遍历。

2.2 聚簇索引 vs 二级索引

维度 聚簇索引（主键索引） 二级索引（辅助索引）
叶子节点内容 完整行数据 索引列的值 + 主键值
每表数量 只能有一个（主键或第一个非空唯一索引） 可以有多个
数据与索引 叶子节点即数据本身，表数据按主键物理排序 与数据物理顺序无关
是否需要回表 不需要 查询字段不在索引中时需要回表

加锁的落点也是索引：InnoDB 的行锁是通过给索引项加锁实现的——没有走索引的 UPDATE/DELETE 会锁住所有行（详见第 4 节）。

2.3 回表、覆盖索引、最左前缀、索引下推

这四个概念是同一件事的四个侧面：二级索引只存”索引列 + 主键”，查询需要的数据不在索引里，就得拿着主键再去聚簇索引查一遍，这就是回表。

回表：查询字段没有全部包含在索引中，需要根据二级索引找到主键，再到主键索引查完整行。

覆盖索引：查询所需的字段全部包含在索引中，无需回表。

覆盖索引是”用空间换回表”：Extra 显示 Using index 即命中覆盖索引。查询只返回索引列、或者只需要主键时，优先考虑覆盖。

最左前缀原则：联合索引 (a, b, c)，查询条件必须从最左列开始、且不能跳过中间列才能命中索引。a=1、a=1 AND b=2 能走索引；b=2、b=2 AND c=3（跳过 a）走不了。

索引下推（ICP，MySQL 5.6+）：把 WHERE 中的过滤条件下推到存储引擎层，在索引遍历时就过滤掉不满足条件的行，减少回表次数。

  • 5.6 之前：引擎层把所有 name LIKE '张%' 的记录全部回表，server 层再过滤 age = 30；
  • 5.6 之后（ICP）：引擎层遍历索引时直接判断 age = 30，只有满足的行才回表。Extra 显示 Using index condition。

2.4 索引失效场景与选错索引

索引失效的常见场景：

场景 示例 原因
对索引列做运算/函数 WHERE DATE(create_time) = '2026-01-01' 索引保存的是列原值，无法按函数结果定位
隐式类型转换 字符串列 WHERE phone = 13012345678 数字被转为字符串比较，索引列发生类型转换
LIKE '%xx' WHERE name LIKE '%张' 前导模糊匹配无法确定扫描起点（张% 可以）
OR 连接非索引列 WHERE name = 'a' OR age > 30（age 无索引） 优化器无法确定只走 name 索引
违反最左前缀 见 2.3 联合索引列序不满足
优化器选错索引 见下 统计信息不准确等

2.5 面试题：WHERE b=1 AND c=2 ORDER BY a 能否用上组合索引 (a, b, c)

可以，但效率不高——需要扫描全索引，无法索引查找：

  1. 缺少最左列 a，无法用索引做等值查找，只能对 (a, b, c) 索引做索引全扫描；
  2. 扫描过程中对每条索引记录检查 b=1 AND c=2；
  3. 好处是 ORDER BY a 天然满足（索引本身就按 a 排序），不需要 filesort。

结论：能用但低效，实际设计时应让联合索引的最左列与查询条件对齐。

2.6 索引设计原则

  • 区分度优先：优先为区分度高（基数大）的列建索引；区分度低的列（如性别）收益很小；
  • 遵循最左前缀：联合索引的列按查询条件的使用频率排列，高频等值列放最前面；
  • 尽量覆盖：让查询所需的列尽量包含在索引中，避免回表；
  • 控制索引数量：索引不是越多越好，写入时同步维护索引，占用空间和开销；
  • 长字符串用前缀索引：如 URL 可用 ALTER TABLE t ADD INDEX idx_url(url(20))（注意区分度损失）；
  • 避免冗余索引：(a, b) 联合索引已覆盖 (a) 单列索引，后者应删除；
  • 主键要短：二级索引叶子存的是主键值，主键越长，所有二级索引越大。

本节小结：B+ 树用”矮树 + 叶子链表”换磁盘 IO 次数；聚簇索引即数据，二级索引即”列值 + 主键”，两者之间的差价是回表；覆盖索引、最左前缀、索引下推分别从字段、列序、过滤时机三个角度压回表成本。

3.3 count(*)、count(1)、count(id)、count(字段) 的区别

语法 统计逻辑 是否包含 NULL
COUNT(*) 统计所有行（对 InnoDB 而言就是数行数） 包含
COUNT(1) 统计所有行（1 是常量表达式，与列无关） 包含
COUNT(id) 统计 id 列非 NULL 的行数 不包含
COUNT(字段) 统计该字段非 NULL 的行数 不包含

性能：count(字段) < count(id) < count(1) ≈ count(*)

count(字段) 最慢是因为需要解析该列并判断是否为空、拷贝字段值；count(*) 在 InnoDB 中被特殊优化为”数行”而不取列值，因此并不慢。注意 InnoDB 不能像 MyISAM 那样直接返回总数（MVCC 下不同事务看到的行数不同），必须实时扫描；大表 count 的优化思路是缓存计数（Redis 维护计数或独立计数表）。

3.4 分页优化：OFFSET 很大时为什么慢

LIMIT 100000, 10 慢的原因：MySQL 需要先扫描并跳过 offset + limit 行，再返回结果——越到后面的页越慢。

方案一：记录上一页最后一条数据的 ID（推荐）

方案二：子查询先定位边界，再取出该页

分页必须搭配 ORDER BY：缺少 ORDER BY 时，MySQL 返回结果的顺序不确定（引擎层顺序），会导致分页结果混乱或重复。

3.5 IN 和 EXISTS 的区别

  • **IN**：先执行子查询，把结果集加载到内存，再对外部查询做匹配。子查询结果集很大时，内存占用和临时表会成为瓶颈；
  • **EXISTS**：对外部查询的每一行执行一次子查询，只判断子查询是否返回行（不关心具体值），不加载完整结果集。子查询能走索引时性能更好。

现代版本说明：MySQL 5.7+ 对 IN 子查询会做物化（materialization）并自动添加半连接（semi-join）优化，IN 与 EXISTS 经常被优化为同一执行计划，性能差异大幅缩小。面试回答的要点是小表驱动大表：外层表小、子查询结果大用 IN；外层表大、子查询结果小且能走索引用 EXISTS。

本节小结：EXPLAIN 四件套（type/key/rows/Extra）是分析入口；慢日志解决”找出哪条慢”；count 与分页解决”大表计数与深分页”两个高频痛点；IN/EXISTS 的本质差异已经被优化器部分抹平，理解驱动表关系比背结论重要。

4. 锁

回答一个问题：并发写数据时，MySQL 靠什么锁保证正确性，死锁怎么查。

4.1 全局锁、表锁、行锁

全局锁：锁住整个实例。

典型场景：全库逻辑备份（保证备份的一致性快照）。注意 InnoDB 备份更推荐 mysqldump --single-transaction——利用 MVCC 快照，不加全局锁。

表锁：锁粒度是整张表，开销小、冲突大。

此外还有 MDL（元数据锁）：执行 DML 时自动加 MDL 读锁、执行 DDL 时自动加 MDL 写锁，防止”查着表结构被改了”；MDL 写锁排队时可能阻塞后续所有查询，DDL 要错峰执行。

行锁：锁粒度是行（InnoDB 专有），冲突最小、并发最高。加锁对象是索引项——如果 UPDATE/DELETE 没走索引，会退化为锁住所有行（相当于表锁）。

4.2 行锁的三种形态：记录锁、间隙锁、临键锁

InnoDB 的索引分为”记录 + 记录之间的间隙”，行锁由此有三种形态：

  • 记录锁（Record Lock）：锁单行记录；
  • 间隙锁（Gap Lock）：锁记录之间的间隙，不锁记录本身，防止其他事务在间隙中插入数据（防幻读的关键）；
  • 临键锁（Next-Key Lock）：记录锁 + 它前面的间隙锁，即左开右闭区间 (prev, cur]，是 InnoDB RR 级别下的默认行锁。

注意：临键锁的上界是记录本身（15），而不是条件中的上界 20。若表中存在 id=20 的记录，扫描会停在第一个不满足 id < 20 的记录 20 上，对其加临键锁 (15,20]，此时间隙锁范围为 (10,15)、(15,20)。

4.3 意向锁（IS/IX）

行锁与表锁的兼容性检查需要知道”表里有没有行锁”。意向锁就是为了让这个判断变成 O(1)：事务加行锁前，先给表加一个意向锁（IS：意向共享；IX：意向排他），它只是标记，不锁数据。

  • 表级锁与意向锁的冲突矩阵：X 表锁与任何 IS/IX 冲突；S 表锁与 IX 冲突、与 IS 兼容。
  • 意向锁之间互相兼容（它们只表示”表内将要有行锁”），真正的互斥发生在行级别。

避免死锁的工程手段：

  1. 多个事务按固定顺序访问资源（如总是先更新订单表再更新库存表）；
  2. 事务尽量短小（少持锁、快释放），拆分大事务；
  3. 让行锁精确命中索引——没走索引会锁全表，死锁概率暴涨；
  4. 降低并发冲突：合理设计索引、避免热点行集中更新。

本节小结：全局锁管备份、表锁管 DDL/MyISAM、行锁管并发；行锁三形态里临键锁是”记录 + 间隙”的组合，是 RR 级别防幻读的当前读手段；死锁不可完全避免，靠检测 + 重试 + 固定顺序访问控制风险。

4.5 插入意向锁（Insert Intention Lock）

什么是插入意向锁：事务执行 INSERT 时，在插入记录之前，会先对”插入位置所在的间隙”加一把插入意向锁（Insert Intention Lock）——它是间隙锁（Gap Lock）的一种变体，表示”我准备往这个间隙里插数据”。注意命名容易混淆：它属于意向锁家族（与 4.3 的 IS/IX 并列），而不是记录锁/间隙锁那一族。

与间隙锁的区别（核心考点）：

锁 A \ 锁 B 间隙锁（Gap） 插入意向锁（Insert Intention）
间隙锁 同一间隙上互斥（都会阻塞） 冲突：间隙锁阻塞插入意向锁（这就是”间隙锁阻止插入”的锁层面实现）
插入意向锁 冲突（要插必须等间隙锁释放） 互相兼容：多个事务可以同时对同一间隙持有插入意向锁（各自插各自的位置）

语义解读：

  • 间隙锁”阻止插入”的实现：事务 B 想往 (5,10) 间隙插入，必须先拿插入意向锁；而事务 A 已持有 (5,10) 的间隙锁，两者冲突 → B 阻塞，直到 A 提交释放间隙锁；
  • 插入意向锁之间不冲突的意义：两个事务可以同时往同一个间隙的不同位置插入（如 B 插 7、C 插 8），只要不撞上”间隙锁”或”相同记录”，就能并发插入——这是 InnoDB 在 RR 下仍然保持并发插入能力的关键。

死锁案例：两个事务先同时给同一范围加了间隙锁，再各自往间隙里插入——互相等待对方的间隙锁释放：

SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段落会显示两个事务各自的等待链，其中能看到：

lock_mode X locks gap ... insert intention waiting 就是”插入意向锁在等间隙锁”。规避手段：并发插入同一范围的业务统一串行化插入（如插入前先 SELECT ... FOR UPDATE 锁行/锁范围）；事务保持短小；避免”先大范围加锁、后插入”的写法。

5. 事务与 MVCC

回答一个问题：事务的隔离性靠什么实现——undo log 版本链 + ReadView 组成的 MVCC。

5.1 ACID

事务保证一组操作要么全执行、要么全不执行。事务支持在引擎层实现（InnoDB 支持，MyISAM 不支持）。

特性 说明 依赖的机制

持久性（Durability） 提交后修改永久保存 redo log（WAL）

5.4 MVCC 实现原理

MVCC（Multi-Version Concurrency Control）靠两样东西：undo log 版本链 + ReadView。

① 版本链

InnoDB 为每行数据生成两个隐藏列：

  • DB_TRX_ID：最后修改该行的事务 ID；
  • DB_ROLL_PTR：指向 undo log 中旧版本的回滚指针。

每次修改都会在 undo log 中留下旧版本，通过回滚指针串成一条版本链：最新的版本在前，旧版本依次指向后。多个版本并行存在，这就是”多版本”。

② ReadView（读视图）

事务做快照读时生成一个 ReadView，用于判断版本链上哪个版本对当前事务可见：

可见性判断规则（对版本链上的每个版本，用其 trx_id 判断）：

  1. trx_id < min_trx_id → 该版本由已提交事务产生，可见；
  2. trx_id 在 m_ids 中（活跃）→ 未提交，不可见；
  3. trx_id >= max_trx_id → 由 ReadView 生成之后的事务产生，不可见；
  4. 不可见时沿 DB_ROLL_PTR 找到上一个版本继续判断，直到可见版本或版本链尽头（尽头为空则记录不存在）。

③ ReadView 的生成时机决定隔离级别：

  • READ COMMITTED：每次 SELECT 都创建新的 ReadView——能看到最近已提交的版本（解决了脏读，但两次 SELECT 之间别的提交会让结果变化，即不可重复读）；
  • REPEATABLE READ：事务中第一次 SELECT 时创建 ReadView，之后整个事务复用——后续 SELECT 看到的永远是同一份快照（解决了不可重复读）。

5.5 隔离级别与幻读的真相

标准 SQL 定义里 RR 会幻读，但 InnoDB 的 RR 下：

  • 快照读（普通 SELECT）：MVCC 保证整个事务看到一致的快照——新增的行不在快照里，不会幻读；
  • 当前读（FOR UPDATE / UPDATE / DELETE）：临键锁（记录锁 + 间隙锁）锁住记录和间隙，其他事务插不进新行，不会幻读。

所以 InnoDB 的 RR 实际上消除了幻读（这也是为什么 MySQL 默认用 RR 且很少提到幻读问题）。如果要把幻读问题讲得更完整：唯一残留的幻读场景是”先快照读、后当前读”的混合边界情况；SERIALIZABLE 级别把所有快照读也升级为当前读，代价是并发度骤降。

本节小结：undo log 提供多版本（可回滚、可读旧值），ReadView 提供”哪些版本对我可见”的判断，锁（临键锁）兜住当前读的间隙；RC 与 RR 的差别只是 ReadView 的生成时机不同，这一句话就能串起整个 MVCC。

6. 日志

回答一个问题：崩溃后数据凭什么不丢——redo log 的 WAL 机制，以及它和 binlog 如何通过两阶段提交保持一致。

6.1 redo log 与 WAL

redo log（重做日志，物理日志）：记录”在哪个数据页的哪个偏移量做了什么修改”，例如”表空间 X、页号 Y、偏移量 Z 起 4 字节被改为 0x12345678”。它不关心 SQL 是什么，只记录物理变化。

WAL（Write-Ahead Logging，先写日志、后刷数据） 的核心：改数据页是随机 IO，慢；写日志是顺序 IO，快。所以先落日志、再异步刷脏页。只要 redo log 落盘，事务就算持久化了——崩溃后从 redo log 重放即可恢复。

redo log 的刷盘策略由 innodb_flush_log_at_trx_commit 控制：

取值 行为 安全性
0 每秒写入并刷盘 最差：崩溃最多丢 1 秒事务
1 每次事务提交时写入并刷盘（默认） 最好：崩溃不丢已提交事务
2 每次提交写入 OS 缓存，每秒刷盘 中：MySQL 崩溃不丢，OS 崩溃最多丢 1 秒

redo log 是循环写入的（ib_logfile0、ib_logfile1 一组），日志文件写满后会触发检查点（checkpoint）：把 checkpoint 之前的脏页刷盘后，日志空间才能复用。redo log 只服务于崩溃恢复，用完即覆盖，不做历史归档。

6.2 binlog 三种格式

binlog（二进制日志，逻辑日志）：由 Server 层记录，用于主从复制、时间点恢复、数据审计。根据格式记录内容不同：

格式 记录内容 优点 缺点
STATEMENT 原始 SQL 语句 日志小、易读 非确定性函数（UUID()、NOW()）可能导致主从不一致
ROW（8.0 默认） 被修改行的前后值（before/after 镜像） 最安全，与执行环境无关；还支持闪回 批量操作日志量巨大
MIXED 默认 STATEMENT，遇到非确定性语句自动切 ROW 两者兼顾 行为不完全可预期

binlog 刷盘由 sync_binlog 控制：0 依赖 OS 刷新（性能最好、风险最高）；1（默认）每次提交后刷盘；N 每 N 个事务刷一次（折中）。

6.3 redo log vs binlog 对比

特性 redo log binlog
所属层级 InnoDB 存储引擎层 MySQL Server 层
主要作用 崩溃恢复，保证持久性 主从复制、时间点恢复、审计
日志类型 物理日志（页面修改） 逻辑日志（SQL 或行变化）
写入时机 事务执行过程中持续写 事务提交时一次性写
写入方式 顺序写，循环文件（用完覆盖） 追加写，可长期保存
刷盘策略 innodb_flush_log_at_trx_commit sync_binlog
内容格式 InnoDB 私有格式 STATEMENT / ROW / MIXED
生命周期 检查点后即可覆盖 按策略清理或归档

6.4 两阶段提交

redo log 在引擎层、binlog 在 Server 层，两套独立的日志、两个独立的刷盘时机。如果各写各的，崩溃时会不一致：例如引擎层已提交、binlog 还没写，主从复制就会丢事务（从库数据缺失）；或者 binlog 已写、引擎层没提交，从库多执行一个事务（数据不一致）。两阶段提交把这两个日志的写入绑成一个原子动作：

  1. Prepare 阶段（InnoDB）：事务的 redo log 写入并刷盘，标记为 PREPARE——此刻磁盘上已有”该事务改了什么”；
  2. Write & Sync Binlog（Server）：binlog 事件写入并刷盘（sync_binlog=1）——此刻磁盘上已有”该事务执行了什么”；
  3. Commit 阶段（InnoDB）：在 redo log 写入 COMMIT 标记，事务正式提交。

关键顺序：先 redo prepare，再写 binlog，最后 redo commit。

6.5 崩溃恢复

崩溃后 InnoDB 从最近的 checkpoint 处扫描 redo log 重放，逐个事务按状态恢复：

崩溃发生时机 事务状态 恢复动作
redo prepare 之前 未写入 redo 直接丢弃（事务本身未提交，undo log 负责回滚已改的脏页）
redo prepare 之后、binlog 写之前 PREPARE，binlog 中无该事务 回滚——binlog 没有它，主从要一致就不能提交
binlog 写完之后、redo commit 之前 PREPARE，binlog 中有该事务 重做（提交）——binlog 已有该事务，从库会执行，主库必须也提交

也就是说：恢复时以 binlog 为准判断一个 PREPARE 状态的事务是提交还是回滚，这保证主库与从库、与 binlog 恢复出来的库永远一致。

本节小结：redo log 用 WAL 换持久性（引擎层、循环写），binlog 换复制与恢复（Server 层、追加写）；两阶段提交让”引擎层状态”与”Server 层日志”在崩溃时保持一致，崩溃恢复时以 binlog 有无为准决定 PREPARE 事务的生死。

7. InnoDB 核心

回答一个问题：InnoDB 在内存与磁盘层面做了哪些工程优化——buffer pool、change buffer、自适应哈希索引、doublewrite。

7.1 InnoDB vs MyISAM

维度 MyISAM InnoDB
锁 表级锁 行级锁 + 表级锁（意向锁）
事务 不支持 支持（MVCC + undo log）
索引结构 B 树 B+ 树
外键 不支持 支持
崩溃恢复 无（易损坏） redo log 自动恢复

适用场景 只读、极简场景（几乎不用） 默认选择，绝大多数业务

需要事务、外键、高并发写，选 InnoDB；MySQL 5.5 之后 InnoDB 成为默认引擎，MyISAM 实际已边缘化。

7.2 Buffer Pool（缓冲池）

本质：数据库的内存缓存区域，缓存从磁盘读取的数据页和索引页。所有数据读写都发生在内存，这是 InnoDB 性能的核心。

  • 读：优先从 Buffer Pool 读取，未命中则读磁盘并加载（预读机制：一次读入相邻的多个页）；
  • 写：修改发生在 Buffer Pool 的脏页上，同时写 redo log 保证持久性；脏页由后台线程按 LRU 淘汰、检查点、空闲等时机异步刷盘（innodb_buffer_pool_size 建议设为物理内存的 60%~75%）。

LRU 的细节：InnoDB 的 LRU 分为 young/old 两段（5/8 处划分），全表扫描等大查询只污染 old 区，不会把真正的热点数据挤出——这是对朴素 LRU 的重要修正。

7.3 Change Buffer（变更缓冲）

解决什么问题：非唯一二级索引的页不在 Buffer Pool 时，传统做法要先把索引页从磁盘读进来才能改——这是随机 IO，很贵。Change Buffer 把这次修改”缓冲”下来，延迟合并，减少随机磁盘 IO。

  • 作用对象：仅限非唯一二级索引的 INSERT/UPDATE/DELETE。主键/聚簇索引（数据就在内存页上）不适用；唯一索引必须立即加载索引页校验唯一性，也不适用；
  • 工作方式：索引页不在内存 → 把修改记录到 Change Buffer（修改本身照常写 redo log）；合并（Merge）时机：该索引页被读入内存时、后台 Purge 线程、检查点、Server 空闲、Change Buffer 满、关闭数据库时——读页时把缓冲的修改应用上去，页变脏后再走正常刷盘；
  • 适用场景：写多读少、修改后不立即读的二级索引收益最大；写密集且读频繁的热点索引反而可能”延迟写入变成本地读”。

7.4 自适应哈希索引（AHI）

本质：InnoDB 根据运行时的访问模式自动为频繁访问的索引页构建哈希索引，等值查询命中时直接 O(1) 定位，跳过 B+ 树逐层查找。

要点：由 InnoDB 自动维护、不能人为创建；只对等值查询有效（范围查询走不上）；缓存的是”索引页内的匹配位置”，随页面淘汰而重建；可通过 innodb_adaptive_hash_index 关闭（并发极高、AHI 成为瓶颈时）。

7.5 Doublewrite（双写缓冲）

解决什么问题：磁盘写页不是原子的——断电或系统崩溃时，一个 16 KB 的页可能只写了一半（部分页写入 / torn page）。此时页损坏，redo log 也无法恢复：redo 记录的是”在页上的修改”，前提是页本身完好。

机制：脏页刷盘前，先顺序写入 doublewrite buffer（共享表空间中两块连续的 1 MB 区域），fsync 后再写入实际数据文件。恢复时先检查 doublewrite 中的页副本，页损坏则用副本修复，再应用 redo log。

代价与权衡：每次刷盘多写一份（写放大），但它是顺序写，代价可控；换来的是一旦崩溃，页损坏问题有副本兜底（redo log 才能正常重放）。这也是 InnoDB 相比 MyISAM 崩溃恢复可靠的原因之一。8.0.20+ 对 doublewrite 的页合并与加载做了进一步优化，默认开启即可。

本节小结：Buffer Pool 让所有读写发生在内存；Change Buffer 推迟二级索引的随机 IO；AHI 用哈希加速等值查询；Doublewrite 用”先写副本”解决部分页写入——四个机制分别回答”快、更省、更快、更稳”。

8. 连接池优化

本节要解决什么问题：连接池为什么必须存在、HikariCP 参数怎么配、池多大才合适，以及”连接打满”怎么排查。

8.1 为什么需要连接池

MySQL 连接的建立成本很高：TCP 三次握手 + MySQL 认证（密码校验、权限加载）+ 会话初始化，一次完整建连要几毫秒到几十毫秒；高并发下”每个请求都建连”会把时间全耗在握手和认证上。连接池做的两件事：

  1. 复用：建好的连接放池子里循环使用，避免反复握手认证；
  2. 限流：池大小就是数据库的”并发上限”，防止应用把数据库的连接数打爆。

MySQL 单机的连接上限是硬约束：max_connections 默认 151，每个连接占用一个线程 + 内存（数百 KB 起步），连接数上去后线程切换和锁竞争反而让吞吐下降。连接池是”应用侧保护数据库”的第一道闸门。

Java 生态三选一：HikariCP（Spring Boot 默认，性能最好）、Druid（阿里，监控最强）、c3p0/DBCP（老项目遗留）。

8.2 HikariCP 核心参数

参数 默认值 说明
maximumPoolSize 10 池中最大连接数（含闲置），也是数据库并发上限
minimumIdle 与 maximumPoolSize 相同 池中保底的空闲连接数（恒为最大值时连接不退）
connectionTimeout 30000ms 从池中取连接的最大等待时间，超时抛 SQLTransientConnectionException（见 8.4）
idleTimeout 600000ms 空闲连接被回收的阈值（仅当 minimumIdle < maximumPoolSize 时生效）
maxLifetime 1800000ms 连接最大存活时间，**必须小于数据库 wait_timeout**（默认 8 小时），防止用上已被 MySQL 侧断开的死连接
keepaliveTime 0（不探测） 周期性向空闲连接发探活，提前踢掉坏连接
validationTimeout 5000ms 校验连接可用性的超时

三个高频坑：**maxLifetime 配得比数据库 wait_timeout 大（拿到被 MySQL 断掉的连接，报 Communications link failure）；connectionTimeout 太小（业务高峰期正常排队也超时）；minimumIdle = maximumPoolSize 时连接池永不回收空闲连接**（闲置期也占着数据库连接）。

8.3 连接池大小公式

HikariCP 官方建议：

  • core_count：CPU 核心数；effective_spindle_count：磁盘数（机械盘按盘片数算，SSD 视为 0）。
  • 8 核 + SSD 机器 → 8 × 2 + 0 = 16 条连接；8 核 + 4 块机械盘 → 20 条。

为什么这么小：公式面向”CPU 密集 + 短查询”的典型 OLTP 场景。连接本质是线程，超过 CPU 核心数后，线程切换和数据库侧锁竞争会让吞吐不升反降——连接不是越多越好。

工程修正方向：

  1. 查询以 IO 等待为主时（慢查询、远程调用、大事务），按 Little’s law 估算：连接数 ≈ 峰值 QPS × 单查询平均耗时（秒）。例：QPS 200、平均查询 50ms → 200 × 0.05 = 10 条，与公式同数量级；如果单查询 500ms，就奔着 100 条去了；
  2. 按数据源分层：订单主库（短事务、高频）用小池，报表库（长查询）单独调大，日志库干脆开小池限流；
  3. 压测验证：调完池大小用压测数据说话，盯”取连接等待时间”这个指标（打满前它会先涨）。

误区：**”池越大吞吐越高” ✗**——池大 = 数据库线程多、内存多、锁竞争大，超过拐点后吞吐反降，唯一变好的是”排队取连接”的假象。

9. 数据库设计

回答一个问题：表怎么建才不生异常——范式是底线，反范式是性能妥协，两者如何权衡。

9.1 候选码与函数依赖

候选码：关系模式中能够唯一标识每一行数据的最小属性集。多个候选码中选一个作为主键，一个关系只能有一个主键。

函数依赖：属性集 X 的值确定属性集 Y 的值，记作 X → Y。

  • 完全函数依赖：X → Y，且不存在 X 的真子集能推出 Y（如 {Sno, Cname} → Grade）；
  • 部分函数依赖：存在 X 的真子集 X' 使得 X' → Y（如 {Sno, Cname} → Sname，其实 Sno → Sname）；
  • 传递函数依赖：X → Y，Y → Z，则 X → Z（如 Sno → Sdept，Sdept → Mname）。

9.2 不规范设计带来的异常

假设有一个学生课程关系模式（候选码 {Sno, Cname}）：

Sno Sname Sdept Mname Cname Grade
1 学生-1 学院-1 院长-1 课程-1 90
2 学生-2 学院-2 院长-2 课程-2 80
2 学生-2 学院-2 院长-2 课程-1 100
3 学生-3 学院-2 院长-2 课程-2 95

这个模式不符合范式，存在四类异常：

异常 表现 根因
数据冗余 学生-2、学院-2 等数据重复出现 属性依赖了部分主键
插入异常 学生尚未选课就无法插入（Cname 不能为空时） 主键部分为空
修改异常 只修改其中一条的学院信息，导致数据不一致 冗余导致一处改动多处
删除异常 删除课程-1 的记录会连带丢失学生-1 的信息 多语义混在一张表

9.3 范式：1NF / 2NF / 3NF

范式 要求 解决
1NF 每个属性都是不可分割的原子项（列不可再拆） 建表底线
2NF 满足 1NF，且不存在部分函数依赖（所有非主属性完全依赖主键） 冗余、插入/删除异常

9.4 反范式化

完全遵循范式的代价是大量连表查询（每个查询都要 join）。反范式是牺牲部分规范性换取性能：

手段 做法 收益
增加冗余列 在多个表中保存相同列 避免连表
增加派生列 存可由其他数据计算出的列（如订单表存”商品快照价格”） 减少查询时的计算量
重新组表 把高频连表的结果合成一张表 减少 join
分割表 垂直分割（按列拆）、水平分割（按行拆/分表） 降低单表压力

反范式的代价与之对称：数据冗余（存储浪费）、数据不一致（一处改动多处失效）、增删改效率降低、可能重新引入异常。工程上的常规做法：

  • 核心交易表守范式：订单、账户等强一致数据按 3NF 设计；
  • 查询/报表场景放开：冗余”商品名称、价格快照”到订单表——订单创建后商品可能改名，反而需要快照；
  • 一致性兜底：冗余字段由应用层或定时任务维护，接受最终一致。

本节小结：范式按”完全依赖、直接依赖”逐级消除异常，是数据一致性的设计底线；反范式在读多写少、连表昂贵的场景用空间换时间，但必须清楚它重新引入了不一致风险，需要用快照语义或异步同步兜底。

1. JVM 内存模型

为什么需要了解：几乎所有 JVM 问题——OOM、GC 停顿、调优——最后都会落到”某块内存区域的数据太多或回收太慢“上。背出五个区域的名字没有价值，面试官真正想听的是：你写的每一个变量、每一个 new 出来的对象，在 JVM 里到底待在哪、由谁负责回收、什么时候会出问题。

1.1 运行时数据区全景

JVM 规范把运行时内存划分为 6 个区域（HotSpot 是其中最常见的实现）：

内存区域 存什么 线程私有/共享 抛出的异常 一句话本质
程序计数器（PC Register） 当前线程正在执行的字节码指令地址 私有 无（唯一不会 OOM 的区域） 线程切换后能”接上”执行到哪了
虚拟机栈（VM Stack） 每个方法调用对应一个栈帧（局部变量表、操作数栈、动态链接、方法出口） 私有 StackOverflowError（深度超限）/ OutOfMemoryError（申请不到栈） 方法的调用与返回
本地方法栈（Native Method Stack） native 方法（如 C 实现的 Object.hashCode 底层）的栈 私有 同虚拟机栈 给 native 方法用的栈
堆（Heap） 所有对象实例和数组 共享 OutOfMemoryError: Java heap space GC 的主战场
方法区（Method Area） 类元数据、运行时常量池、方法字节码、静态变量 共享 OutOfMemoryError: Metaspace 类的”档案室”
运行时常量池（在方法区内） 编译期生成的字面量和符号引用 + 运行期新放入的常量 共享 OutOfMemoryError 常量与引用

三个容易搞混的点：

  1. 方法区是规范，永久代/元空间是实现。JVM 规范只规定了”方法区该存什么”，没规定怎么存。HotSpot 在 JDK 7 及以前用永久代（PermGen）实现（占据堆空间），JDK 8 起用元空间（Metaspace）实现（使用本地内存）。其他 JVM（如 JRockit）从来没有永久代。

  2. 程序计数器是唯一不会 OOM 的区域，因为它是所有区域中唯一规定不依赖内存大小、只存一个地址的地方。注意：执行 native 方法时，PC 值是”未定义”（undefined），因为 native 方法不是字节码，不靠 PC 记录执行位置。

  3. 栈帧里存的是什么：局部变量表（基本类型、引用类型，以 slot 为单位，long/double 占两个 slot）、操作数栈（字节码指令计算的临时区，iadd 就是把栈顶两个数弹出去相加再压回）、动态链接（指向运行时常量池中该方法的引用，实现多态）、方法出口（返回时知道回哪去）。栈默认大小约 1MB（-Xss 调整），这也是递归默认只能到几千层的原因。

面试怎么答：先给出”线程私有三个：程序计数器、虚拟机栈、本地方法栈；线程共享三个：堆、方法区、运行时常量池”的骨架，再补一句”私有区域的异常要么是深度溢出要么是申请不到空间，共享区域的异常都是内存不足”，最后点出”方法区是规范，元空间是 HotSpot 的实现”——这三点讲全，区域问题基本满分。

1.2 堆内存细分

为什么需要了解：堆是 99% 的 OOM 发生地，也是 GC 的主战场。不弄清堆的内部结构，就解释不了”为什么 Minor GC 这么快””对象什么时候进老年代””大对象有什么坑”。

新生代（Young Gen）：绝大多数对象”朝生夕死”，在这里诞生和死亡。

  • Eden 区：几乎所有新对象都在这里分配。
  • S0 / S1（两个 Survivor 区）：Minor GC 时把存活对象复制进其中一个，两个区交替充当 From/To，保证任意时刻有一个 Survivor 是空的，供复制算法使用。
  • 默认比例 Eden : S0 : S1 = 8 : 1 : 1（-XX:SurvivorRatio=8），新生代实际可用空间是 90%——复制算法”浪费”的那 10% 就是那个永远空着的 To Survivor。

为什么是两个 Survivor 而不是一个：复制算法需要一个完全空闲的目标区来承接存活对象。如果只有一个 S，上一轮存活下来的对象和这一轮 Eden 里的存活对象会撞在一起——S 既是源又是目标，没法操作。两个 S 轮转，还能顺便给对象”记年龄”：每熬过一轮 Minor GC 年龄 +1，年龄够了就晋升老年代，避免对象过早晋升。

TLAB（Thread Local Allocation Buffer，线程本地分配缓冲）：

  • 堆是线程共享的，如果所有线程都去竞争同一个”堆顶指针”，分配对象会变成高并发热点。
  • 解决：每个线程在 Eden 里预申请一块私有缓冲区（TLAB），对象分配优先在自己的 TLAB 里做——只移动自己这块缓冲区的 top 指针，无需加锁。默认开启（-XX:+UseTLAB）。
  • 放不下 TLAB 的大对象退回堆上直接分配；再大（超过 -XX:PretenureSizeThreshold，默认 0 即不启用）则直接进老年代，避免它在 Eden 和 Survivor 之间反复搬运（此参数只对 Serial / ParNew 生效，G1 用的是 Humongous Region 机制）。

老年代（Old Gen）：存放多次 Minor GC 后仍存活的对象、大对象。回收频率低。默认 新生代 : 老年代 = 1 : 2（-XX:NewRatio=2）。

字符串常量池的位置变迁（重点考点）：

版本 字符串常量池位置 运行时常量池位置 关键事件
JDK 6 及以前 方法区（永久代） 方法区（永久代） 池在永久代，Full GC 才回收，intern() 大量使用时易 PermGen OOM
JDK 7 堆（JEP 223） 方法区（永久代） 移到堆后，Minor GC 就能回收无用字符串，OOM 风险大降
JDK 8 起 堆 方法区（元空间） 永久代整体移除

String.intern() 的跨版本行为对比（面试高频，原文精华保留）：

一句话总结：JDK 7 前 intern() 是”复制”（池里存副本），JDK 7 起是”存引用”（池里放堆对象地址）。

进阶题：String s = new String("a") + new String("a") 一共创建几个对象（JDK 8 下经典答案是 6 个，不计 StringBuilder 内部 char[] 则为 5 个）：

创建的对象 数量 说明
常量池中的 "a" 1 两处字面量指向同一个常量池项
堆上的 new String("a") 2 每次 new 都是新实例
StringBuilder 1 编译器自动生成的拼接容器

面试怎么答：先说三件套”Eden 8 + S0/S1 各 1”，解释两个 Survivor 是复制算法运转的前提；再讲 TLAB 解决的是”并发分配的无锁化”；最后主动抛出 intern() 的 JDK6/7/8 对比，并补一句”JDK 7 把字符串常量池移进堆，就是为了让 Minor GC 也能回收它”——这一问就答成了体系。

1.3 元空间 vs 永久代

为什么需要了解：-XX:MaxPermSize 和 -XX:MaxMetaspaceSize 是两道非常常见的面试/实战题，而且”元空间默认无限”这句话一半对一半错——它确实无限，但有个触发阈值会悄悄引起 Full GC。

为什么从永久代迁移到元空间（JEP 122）：

  1. 永久代大小难以预估：类元数据（尤其 CGLIB 动态代理、JSP 编译、反射生成类）的数量运行期不可预测。-XX:MaxPermSize 设小了频繁 Full GC 甚至 OOM，设大了浪费内存。
  2. 字符串常量池放永久代易 OOM：大量 intern() 会撑爆固定大小的永久代，JDK 7 先把字符串池移进堆，JDK 8 干脆把整个永久代移除。
  3. 回收负担重：永久代与堆混在一起，永久代不足会触发 Full GC，且需要带整理的回收才能调整大小，代价高。
  4. 融合 JRockit：Oracle 合并 HotSpot 与 JRockit（JRockit 没有永久代），统一用元空间实现更平滑。

对比表：

对比项 永久代（PermGen） 元空间（Metaspace）
存在版本 JDK 7 及以前，JDK 8 被彻底移除 JDK 8 起
物理位置 堆的一部分（HotSpot 实现） 本地内存（native memory），不占用堆
默认大小 固定上限，需 -XX:MaxPermSize 指定（默认约 64~82M） 无上限，自动扩容，仅受物理内存约束
存放内容 类元数据 + 字符串常量池 + 静态变量 仅类元数据；字符串池已在堆（JDK 7 起），静态变量对象也在堆
回收与调优 大小难预估、回收效率低，容易 OOM 类元数据回收更彻底，可按需扩容
调优参数 -XX:PermSize / -XX:MaxPermSize -XX:MetaspaceSize（GC 触发阈值）/ -XX:MaxMetaspaceSize（上限）

参数陷阱（必考）：-XX:MetaspaceSize（默认约 21M）不是上限，而是触发阈值——类元数据使用量达到它时，会触发一次 Full GC 去回收类元数据；真正的上限是 -XX:MaxMetaspaceSize，默认不设置（即”无限”，只受进程可寻址内存约束）。配套参数：-XX:MinMetaspaceFreeRatio / -XX:MaxMetaspaceFreeRatio 控制 Full GC 后元空间的扩容/收缩比例；-XX:CompressedClassSpaceSize（默认 1GB）限制压缩类指针空间。

元空间的 OOM 场景：动态生成类不受控——CGLIB/ByteBuddy 代理、JSP 首次访问编译、Groovy 脚本热加载、应用热部署且不卸载旧类加载器。症状是 java.lang.OutOfMemoryError: Metaspace，排查重点是”谁在不停造新类”，而不是堆。

面试怎么答：答案四段式——① 永久代是方法区在 HotSpot 的实现，元空间是它的替代；② 迁移原因：大小难预估、字符串池拖累、回收代价高、融合 JRockit；③ 关键差异：本地内存、默认无上限；④ 参数考点：MetaspaceSize 是触发阈值不是上限。再主动补一句”实际中元空间 OOM 常见于动态代理和热部署”。

2. 对象的生命周期

为什么需要了解：new 一个对象背后发生的事、对象在内存里长什么样、JVM 怎么找到它、它什么时候进老年代——这四件事串起来就是”一个 Java 对象的一生”。面试官问对象相关问题时，八成在问这条流水线的某个环节。

2.1 对象创建过程

以 new 指令为例（HotSpot 视角，五步）：

  1. 类加载检查：new 指令在常量池中定位类的符号引用，检查该类是否已加载、解析、初始化。未加载则先执行类加载流程（见第 3 章），并判断类是否可被实例化（接口、抽象类会抛 InstantiationError）。
  2. 分配内存：在堆上为对象划分空间。分配方式取决于堆是否规整：
    • 指针碰撞（Bump the Pointer）：堆规整（复制/整理算法回收后），空闲内存是连续的一块，只需把指针往空闲方向挪动对象大小。Serial、ParNew 等带整理能力的收集器用它。
    • 空闲列表（Free List）：堆不规整（标记-清除回收后），JVM 维护一张空闲块列表，从中找一块足够大的分给对象。CMS 用它。
    • 并发安全：要么 CAS + 失败重试，要么用 TLAB（每个线程在 Eden 预分配私有缓冲，分配时不竞争堆顶指针）。
  3. 初始化零值：将分配到的内存（实例字段区）全部置零（0、null、false），保证对象字段在不赋初值时可直接使用（int 为 0 而不是垃圾值）。
  4. 设置对象头：写入对象所属类的元数据指针（Klass Pointer）、对象的 GC 分代年龄（0）、锁状态等（见 2.2）。
  5. 执行 <init> 构造方法：按程序员写的构造逻辑初始化实例字段，new 完成，返回引用。

面试怎么答：按五步背，但重点讲第二步——主动说出”指针碰撞 vs 空闲列表取决于堆是否规整，而堆是否规整取决于收集器算法；并发分配靠 CAS 和 TLAB 解决”——这比背流程更能体现理解深度。

2.2 对象的内存布局（Mark Word + Klass Pointer + 实例数据 + 对齐填充）

一个对象在堆里占三块（HotSpot 64 位 JVM）：

组成部分 大小 内容
对象头：Mark Word 8 字节 对象自身的运行时数据：哈希码（延迟计算）、GC 分代年龄（4 bit）、锁状态标志位（无锁 01 / 偏向锁 101 / 轻量级锁 00 / 重量级锁 10 / GC 标记 11）、偏向锁线程 ID、epoch 等
对象头：Klass Pointer 4 字节（开启压缩）或 8 字节 指向方法区中类元数据的指针，JVM 靠它知道对象是哪个类的实例
实例数据（Instance Data） 不定 对象的实例字段值，按类型分配（long/double 8 字节、int 4 字节、引用类型按压缩指针 4 字节等）
对齐填充（Padding） 0~7 字节 对象大小必须是 8 字节的整数倍，不足则补齐（64 位 HotSpot 默认对象对齐）

关键细节：

  • 压缩指针：-XX:+UseCompressedOops 默认开启（64 位且堆 ≤ 32GB），对象引用由 8 字节压到 4 字节，堆 32G 的机器实际能装的引用量翻倍。开启后对象头固定 12 字节（8 + 4），加填充后正好 16 字节对齐。
  • Mark Word 是锁状态的总开关：synchronized 锁升级（偏向 → 轻量 → 重量）的所有信息都写在 Mark Word 的比特位里（详见并发篇）。这也是为什么 Mark Word 里同时要塞哈希码、年龄和锁标志——一个字节能表达的东西都挤在一起。
  • GC 年龄只有 4 bit：最大只能记到 15，所以 -XX:MaxTenuringThreshold 的合法上限是 15（CMS 下默认 6）。

面试怎么答：画一遍三块结构图，然后强调两点——① Mark Word 是一把锁 + GC 信息复用的小仓库（哈希码延迟计算、年龄 4 bit、锁标志位）；② 压缩指针让引用 8 字节变 4 字节，前提是堆 ≤ 32G。

2.3 对象的访问定位（句柄 vs 直接指针）

对象创建出来，栈上的引用（reference）怎么找到堆里的对象？两种设计：

对比项 句柄访问（Handle） 直接指针访问（Direct Pointer）
结构 reference → 句柄池 →（对象实例指针 + 类型指针） reference 直接指向对象地址，对象头里带 Klass Pointer
寻址次数 两次（先找句柄，再找对象） 一次
GC 移动对象时 只改句柄池里的指针，reference 不用动 必须更新所有引用该对象的 reference
优点 GC 效率高（对象移动无感） 速度快（少一次指针定位）、实现简单
缺点 慢（多一次寻址） GC 移动对象时要额外修正引用
谁在用 早期一些 JVM（如 JVM 规范示例） HotSpot 采用直接指针

HotSpot 选择直接指针的原因：访问对象是最高频的操作，少一次指针跳转意味着整体访问速度更快；配合压缩指针（UseCompressedOops）还能弥补直接指针内存占用高的劣势。代价是 GC 移动对象（复制、整理）时必须同时修正栈/堆里的引用——HotSpot 通过”遍历 GC Roots 时更新引用”来承接这个成本。

面试怎么答：两句搞定——“句柄访问两次寻址但 GC 移动对象无感；直接指针一次寻址但 GC 要修引用。HotSpot 选直接指针，因为对象访问是最高频操作，速度优先，压缩指针解决了内存占用问题。”

对象晋升路径全景图：

三个容易答不全的点：

  1. 动态年龄判断：不是只有”年龄到 15 才晋升”。如果 S 区里同一年龄的对象加起来已经占了 Survivor 一半空间，说明这些对象大概率会长期存活，就直接把 ≥ 这个年龄的对象全部晋升，避免它们在 S 区里挤占复制算法的目标空间。
  2. 空间分配担保（HandlePromotionFailure）：Minor GC 前，JVM 要确认老年代是否装得下”这次可能晋升的所有对象”。历史上有 -XX:HandlePromotionFailure 参数，JDK 6 Update 24 之后该参数已失效，规则变为：只要老年代连续空间大于新生代对象总大小或历次晋升的平均大小，就允许 Minor GC；否则改为 Full GC。
  3. 大对象直接进老年代：-XX:PretenureSizeThreshold（如 -XX:PretenureSizeThreshold=3m）让超过 3MB 的对象直接进老年代，避免大对象在 Eden 与 Survivor 间反复复制、以及大对象晋升时触发过早的 Full GC。注意它只对 Serial / ParNew 生效，G1 用 Humongous Region 承担同样职责。

面试怎么答：顺着路径图讲：Minor GC 存活 → S 区轮转 + 年龄累加 → 两条晋升通道（年龄达标、动态年龄判定）→ 一条直达通道（大对象）→ 最后补一句担保机制——“老年代空间不够时 Minor GC 会升级为 Full GC”，这条流水线就完整了。

3. 类加载机制

为什么需要了解：类加载器决定了”你的代码如何被找到和执行”，是 JVM 与外部世界的第一道边界。框架（Spring、Tomcat、MyBatis）底层大量依赖类加载器，SPI 机制、热部署、JDBC 驱动加载都建立在这套机制上。

3.1 类的生命周期

一个类从字节码变成可执行代码，经历 7 个阶段（前 5 个合称”类加载过程”）：

① 加载（Loading）：通过全限定名获取类的二进制字节流（.class 文件、JAR、网络、运行时动态生成——CGLIB 就是这样造类的）；把字节流转化为方法区（元空间）的运行时数据结构；在堆中生成 java.lang.Class 对象作为访问入口。

② 验证（Verification）：字节码安全校验：文件格式（魔数 0xCAFEBABE）、元数据（父类、接口合法性）、字节码（操作数栈类型是否匹配）、符号引用（能否找到对应类/方法）。防止加载恶意字节码破坏 JVM。

③ 准备（Preparation）：为静态变量分配内存并设零值（0、null、false）。注意两个坑：

  • 此刻还没有执行任何 Java 代码，public static int x = 100; 在准备阶段 x 是 0，真正的 100 要等初始化阶段执行 <clinit> 才写入；
  • 特例：static final 常量（编译期可确定的）会直接赋真实值。

④ 解析（Resolution）：把常量池中的符号引用（如 java/lang/System 的名字）替换为直接引用（内存地址/偏移量）。HotSpot 默认把解析推迟到第一次真正使用时（惰性解析），invokedynamic（Lambda、字符串拼接）更是要到运行期才解析。

⑤ 初始化（Initialization）：执行 <clinit>()——静态变量赋值 + 静态代码块。触发条件（主动使用，6 种）：

  1. new、getstatic、putstatic、invokestatic（创建实例、读写静态字段、调用静态方法）；
  2. 反射调用（Class.forName("...") 默认 initialize=true 会初始化；ClassLoader.loadClass() 不会）；
  3. 初始化子类时，先初始化其父类；
  4. 程序主类（main 方法所在类）；
  5. JDK 7 起，invokedynamic 指令解析出的目标方法句柄对应的类；
  6. JDK 8 起，实现类初始化前，若接口定义了 default 方法，接口会先被初始化。

⑥ 使用（Using）：正常执行。

⑦ 卸载（Unloading）：类要被卸载，需同时满足三个条件：该类的所有实例都被回收、该类的 Class 对象不可达、加载它的类加载器不可达（第三条是热部署能释放旧代码的关键——Tomcat 每部署一次就新建一个 WebAppClassLoader，停止应用后旧加载器连同它加载的类一起被回收）。

Class.forName() 和 ClassLoader.loadClass() 的区别（高频题）：

对比项 Class.forName() ClassLoader.loadClass()
触发阶段 加载 + 链接 + 初始化（默认执行 <clinit> 静态块） 只加载 + 链接（不初始化，首次主动使用才初始化）
典型用途 JDBC 老驱动 Class.forName("com.mysql.jdbc.Driver") 注册驱动 框架按需加载类（Spring、反射场景）
是否可控 重载 forName(name, initialize, loader) 可关掉初始化 本身不初始化

面试怎么答：七阶段（或五阶段）流程 + 一个区分题。重点：准备阶段给静态变量的是零值不是初值；static final 常量例外；主动使用 6 种情形能列举 3 种以上即可，最好带出”初始化子类先初始化父类”。

3.2 类加载器（Bootstrap → Platform → Application，JDK 9+ 的模块化类加载器）

JDK 9+ 的结构（JEP 220 / JEP 261，模块化后）：

类加载器 加载内容 父加载器
Bootstrap ClassLoader java.base、java.lang 等基础模块（JVM 自带，C++ 实现，null 表示） 无
Platform ClassLoader（平台类加载器） java.sql、java.xml 等 SE 平台模块（由 Extension 改名而来） Bootstrap
Application ClassLoader（应用类加载器） classpath / module-path 上的应用类 Platform
自定义 ClassLoader 用户指定路径 Application（或自定义）

JDK 8 及以前的结构（面试常考对照）：

类加载器 加载路径 父加载器
Bootstrap ClassLoader JRE/lib/rt.jar 等核心库 无（顶级）
Extension ClassLoader JRE/lib/ext 扩展库 Bootstrap
Application ClassLoader 应用类路径（ClassPath） Extension
自定义 ClassLoader 用户自定义路径 Application

版本差异必考点：从 JDK 9（JEP 220） 起，扩展机制被模块系统（JPMS）取代：Extension ClassLoader 改名为 Platform ClassLoader，rt.jar 被拆分为 jmods 模块——**rt.jar 文件已不存在**。老资料里”JRE/lib/rt.jar“的说法在 JDK 9+ 已失效。

面试怎么答：JDK 8 说”Bootstrap → Extension → Application”，JDK 9+ 说”Bootstrap → Platform → Application”，并主动点出”rt.jar 没了、Extension 改名叫 Platform”，一句话体现版本意识。

3.3 双亲委派模型

双亲委派：一个类加载器收到加载请求，先把请求委派给父加载器，父加载器再往上委派，直到 Bootstrap；只有父加载器返回”找不到”，才轮到子加载器自己尝试加载（findClass）。

ClassLoader.loadClass() 的核心逻辑（流程控制）：

为什么需要双亲委派（三个理由）：

  1. 安全性：java.lang.String 必须由 Bootstrap 加载。如果没有委派，应用可以自定义一个恶意 java.lang.String 顶替核心类；有了委派，所有 java.* 类最终都回到 Bootstrap，杜绝篡改。
  2. 避免重复加载：同一个类在 JVM 中”类全名 + 加载它的类加载器”共同决定唯一性。委派保证应用里的类都落到同一个加载链上，不会出现”两个一模一样的类”互相 instanceof 失败的诡异问题。
  3. 模块化/隔离的基础：虽然委派是”由上而下统一”，但它同时为”由下而上隔离”（容器、OSGi）提供了扩展点。

双亲委派的缺点/局限：父加载器加载不了”只对子加载器可见”的类——这正是 SPI 和 Web 容器场景需要打破它的原因。

如何打破双亲委派（四种方式）：

  1. **重写 loadClass()**：直接改流程控制，先自己加载、失败再委派（或反之）。
  2. 线程上下文类加载器（TCCL）：用于 SPI（JDBC、JNDI 等），见 3.4。
  3. 容器类加载器：Tomcat 的 WebAppClassLoader 就是典型——为了”每个 Web 应用能加载自己 WEB-INF/classes 和 WEB-INF/lib 里不同版本的类”，它把顺序颠倒过来：先看自己是否已加载，再尝试自己加载（应用类），找不到才委派父加载器；但 java.* 等 JVM 核心类仍然强制先委派父类，避免破坏基础库。
  4. OSGi / 模块化框架：每个 bundle 一个类加载器，完全自定义加载顺序（类可以依赖声明关系加载）。

loadClass() 和 findClass() 的区别（高频题）：

特性 loadClass() findClass()
职责 控制加载流程（委派机制） 实现具体加载逻辑（读字节流、defineClass）
重写必要性 通常不重写（保持委派模型） 自定义类加载器时必须重写
双亲委派角色 实现委派逻辑 被委派机制调用（父加载失败后才调用）
典型用途 类加载入口 自定义类加载器扩展资源获取方式

面试怎么答：先讲流程（findLoadedClass → 父加载器递归 → 自己 findClass），再答”为什么”（安全 + 不重复加载），最后主动给”打破”的两种标准答案——重写 loadClass 和线程上下文类加载器，并举 Tomcat 的例子说明”为什么需要打破”（应用隔离）。

3.4 线程上下文类加载器

问题背景：双亲委派是”父优先”，但存在一类场景反过来——由高层（父加载器加载的）代码去加载低层（子加载器才可见）的实现类。典型是 JDBC：

  • DriverManager 在 java.base 模块里，由 Bootstrap 加载；
  • MySQL 驱动 com.mysql.cj.jdbc.Driver 在应用的 classpath 里，只有 Application 类加载器（App ClassLoader）能找到；
  • Bootstrap 按双亲委派永远委派不到 App ClassLoader（委派方向是向下的，找不到就放弃）。

解决方案：线程上下文类加载器（Thread Context ClassLoader）

  • 每个线程有一个 contextClassLoader（默认继承父线程的，初始默认是 App ClassLoader）；
  • 高层代码拿不到低层实现时，通过 Thread.currentThread().getContextClassLoader() **反过来借用”当前线程的类加载器”**去加载实现类；
  • 这就是 SPI（Service Provider Interface） 机制的基石：JDBC、JNDI、JAXP、JMS 等所有”核心 API 在 JDK、实现由厂商提供”的标准接口，都靠它工作。
  • 调用链：DriverManager.getConnection() → Class.forName(driverClass, true, Thread.currentThread().getContextClassLoader())。JDBC 4.0 之后靠 META-INF/services/java.sql.Driver 自动发现驱动，ServiceLoader 同样借助上下文加载器完成加载。

面试怎么答：一句话点破本质——“双亲委派是向下委派，SPI 需要向上借用，所以引入了线程上下文类加载器”；再举 JDBC 的例子（Bootstrap 加载的 DriverManager 要用 App 加载器加载 MySQL 驱动），最后提一句 Tomcat 和 JDK 9+ 模块化后该机制依旧存在（java.sql 模块在 Platform 层，驱动仍在 classpath）。

4. 性能指标与调优方法论

为什么需要了解：调优不是”把参数调得好看”，而是”让系统达到业务要求的性能”。不理解 RT/TPS 这些指标，就没有量化目标；不会压测，就不知道系统真实容量。这一章先把”指标 → 目标 → 压测验证”的闭环补齐，第 7 章的实战案例全部建立在这套方法论上。

4.1 RT、TPS、QPS、并发数——四个核心指标

RT（Response Time，响应时间）：一个请求从发出到收到完整响应的时间。两个要点：

  • 看分位值而不是平均值：平均 RT 会被长尾请求严重污染——1% 的请求耗时 5s，其余 99% 只要 10ms，平均值也会被拉到 60ms 左右，完全反映不了真实体验。业界看 p95 / p99 / p999（95%/99%/99.9% 的请求分别在多少毫秒内完成），压测报告里”avg=45ms, p99=180ms”比”avg=45ms”信息量大得多。
  • RT 要分段定位：全链路 RT = 网络 + 网关 + 应用 + DB/缓存 + 下游。调优前先用 traceId/日志把耗时拆开，90% 的”接口慢”慢在 DB 或下游，而不是 JVM——别一上来就调 GC。

TPS（Transactions Per Second，每秒事务数）：每秒完成多少笔业务事务。强调”事务”是有业务语义的完整操作（一次下单 = 校验 + 扣库存 + 建订单），不是单条 SQL，也不是单个 HTTP 请求。

QPS（Queries Per Second，每秒查询数）：每秒完成的读请求数。实践中 QPS 常被泛化为”每秒请求数”（含读含写），与 TPS 混用也没关系——面试讲清楚”TPS 强调事务完整性，QPS 强调请求吞吐“即可。

并发数（Concurrency）：同一时刻在途（已发出、未返回）的请求数，也就是系统同时处理的请求总数。注意它不等于”线程数”——同步模型下一个线程处理一个在途请求，异步模型下（NIO、协程）一个线程可以同时驱动多个在途请求。

四个指标之间的关系（Little 定律）：

并发数 = TPS × RT

这是排队论 Little 定律的直接应用：系统每秒完成 1000 个事务、每个事务耗时 100ms，则在途请求数 = 1000 × 0.1 = 100。反过来可反推容量：

RT 目标 TPS 需要的并发数
50ms 10,000 500
100ms 5,000 500
100ms 10,000 1,000
200ms 10,000 2,000

两个经典用法：

  1. 估算容量：目标 QPS 10000、压测测得 RT 100ms → 至少需要 1000 个并发槽位（线程池/连接池的配置参考）。
  2. 判断瓶颈：RT 不变、TPS 不再随并发上升 → 已到系统极限；TPS 下降、RT 暴涨 → 某个环节开始排队（线程池打满、连接池耗尽、GC 停顿），要找瓶颈而不是盲目加线程。

面试怎么答：先报四个定义，再主动给出 Little 定律公式和一个换算例子（”目标 QPS 1 万、RT 100ms，并发就是 1000”），最后补一句”平均 RT 没有意义，看 p99”——公式 + 分位数意识都拿出来，这题就完整了。

4.2 3S 定理（Speed、Scalability、Stability）

性能测试的三个维度，简称 3S：

维度 含义 怎么验证
Speed（性能） 单机/单实例的处理能力：RT 与吞吐（TPS） 单机压测，确认 RT 分位值与最大 TPS
Scalability（可扩展性） 加机器，吞吐能否近似线性增长 1 台 → 2 台 → 4 台压测，画吞吐增长曲线
Stability（稳定性） 长时间运行（72h+）后性能不退化、资源水位稳定 长稳压测：观察 GC、内存、线程、连接池水位

三个维度有优先级：先单机性能（Speed）打底，再验证水平扩展（Scalability），最后长稳（Stability）兜底。每个维度都有一个经典翻车案例：

  • 扩展性失败：1 台机器 TPS 1000，4 台只有 2000 而不是 4000——瓶颈在共享资源（DB 连接数、Redis 带宽、分布式锁、热点数据），这就是”加了机器没效果”的真相；
  • 稳定性失败：压测 12 小时后 TPS 逐步下滑——典型是泄漏：内存泄漏（老年代持续增长）、线程池泄漏（活跃线程只增不降）、连接池泄漏（连接数涨满）。

面试怎么答：3S 三个词 + 一句话”先单机性能、再扩展性、后稳定性”，并各举一个翻车案例（加机器吞吐不翻倍 → 查共享资源；长时间压测吞吐下降 → 查泄漏），比单纯背缩写打动人。

4.3 梯度压测（200 → 500 → 1000 → 2000 → 5000）

为什么用梯度：一上来直接上高并发，系统直接雪崩，什么信息都拿不到。梯度压测的意义是**找到”拐点”**——吞吐不再随并发上升、甚至开始下降的那个点，它定义了系统的真实容量。

标准流程：

  1. 冒烟压测：小并发（如 200）跑通链路，确认功能与监控正常；
  2. 梯度加压：200 → 500 → 1000 → 2000 → 5000 线程逐档施压，每档持续 3~5 分钟（让系统进入稳态），逐档记录 TPS、RT 分位、错误率；
  3. 找拐点：TPS 曲线从”线性上升”转为”走平或下降”的那一档就是容量上限——继续加压只会让 RT 恶化、错误率飙升；
  4. 资源画像：每档同步观察 CPU、内存、GC、线程池活跃线程、DB 连接池、MQ 积压，定位瓶颈环节；
  5. 结论输出：给出”最大支撑 TPS、对应 RT p99、瓶颈在 X”，并预留 30%~50% 余量作为生产容量目标——压测极限值直接当线上水位，一个抖动就挂了。

典型拐点场景：

现象 瓶颈
TPS 走平但 RT 缓慢上升，CPU 已打满 计算密集：应用线程/GC 是瓶颈
TPS 走平，活跃线程数打满，RT 陡增 同步阻塞：下游（DB/接口）慢，线程在等
TPS 下降，GC 停顿变长，老年代持续上升 内存问题：晋升过快、泄漏
错误率突然升高，大量超时 达到某资源上限（连接池耗尽、限流阈值）

面试怎么答：讲”梯度 + 拐点 + 余量”三件事——“从 200 逐档加到 5000，每档记录 TPS 和 RT 分位，找到吞吐拐点，按拐点值预留 30~50% 作为容量目标”，再补一句”拐点通常对应一个具体瓶颈（线程池/连接池/GC），压测的目的就是把它找出来”。

4.4 压测工具简介（JMeter / wrk / ab）

工具 特点 适用场景
JMeter GUI 配置测试计划，线程组/定时器/断言/聚合报告插件丰富，支持分布式压测（主控 + 多台施压机） 完整链路压测、接口回归、需要断言与报表的正式压测

5. 垃圾回收

为什么需要了解：GC 是 JVM 面试的重灾区——从”对象怎么算死”到”谁负责收”再到”怎么调”，层层递进。面试官问 GC 的潜台词是：你能不能定位线上停顿/OOM 问题，而不只是背名词。

5.1 如何判断对象已死

引用计数法

每个对象维护一个计数器，被引用 +1，引用失效 -1，计数为 0 即回收。简单高效，但无法解决循环引用：

这就像两个已经没人要的东西互相”抱着取暖”，谁都不敢收。因此主流 JVM（HotSpot）都不用它，改用可达性分析。

可达性分析

从一组称为 GC Roots 的根对象出发，沿引用链向下搜索，不可达的对象即为垃圾。GC Roots 包括：

GC Roots 来源 说明
虚拟机栈中引用的对象 栈帧局部变量表、操作数栈里的引用（正在执行的方法局部变量）
本地方法栈中引用的对象 JNI 引用的对象
元空间/方法区中静态属性引用的对象 static 变量（如 static Map 缓存——这就是静态缓存泄漏时它”永垂不朽”的原因）
元空间/方法区中常量引用的对象 常量池里的引用（如被 intern() 驻留的字符串）
被 synchronized 持有锁的对象 monitor 关联的对象
活跃线程（Thread）对象 所有未被 stop 的线程
JVM 内部引用 基本类型包装类缓存（IntegerCache）、常驻异常对象（NullPointerException 等）、系统类加载器加载的类等

两次标记与 finalize() 的废弃

宣告一个对象真正死亡，在历史上要经过两次标记：

  1. 第一次标记：从 GC Roots 出发，不可达的对象被标记，若其重写且未执行过 finalize()，被放入 F-Queue 队列；
  2. 第二次标记：JVM 用低优先级 Finalizer 线程执行 F-Queue 中的 finalize()，如果对象在方法中把自己重新赋值给某个引用（”自救”），就会被移出队列存活下来；否则彻底死亡。每个对象的 finalize() 只会执行一次。

为什么要废弃 finalize()（JDK 9 起弃用，JDK 18 经 JEP 421 进一步标记移除）：

  • 执行时机不确定：对象”死亡”到 finalize() 执行之间可能隔很久，资源迟迟不释放；
  • 性能差：Finalizer 线程 + F-Queue 队列带来额外开销，重写 finalize 的对象回收变慢；
  • “自救”反模式：能复活对象听起来酷，但会导致对象被反复回收、行为不可预测；
  • 替代方案：try-with-resources（确定性释放）和 **java.lang.ref.Cleaner**（JDK 9 引入，基于虚引用实现，DirectByteBuffer 清理堆外内存就是用它）。

四种引用类型

引用类型 回收时机 用途 实现类
强引用 永不回收（OOM 也不收） 日常 new 的对象；静态集合缓存不清理就会泄漏 Object
软引用（SoftReference） 内存不足、OOM 之前回收 内存敏感缓存：能利用内存就留着，内存紧张自动释放 SoftReference
弱引用（WeakReference） 下一次 GC 即回收（不管内存够不够） WeakHashMap（键是弱引用）、ThreadLocalMap 的 key WeakReference
虚引用（PhantomReference） 回收后通知（get() 恒为 null，无法用它取对象） 跟踪对象回收时机：堆外内存清理（DirectByteBuffer + Cleaner） PhantomReference

三个必答细节：

  1. 软引用的版本差异：JDK 8 及以前按”最近一次 GC 后存活时间”判定（-XX:SoftRefLRUPolicyMSPerMB，默认 1000ms/MB）；JDK 9 起改为基于堆使用率——堆使用率低于 50% 时软引用对象不回收，该参数不再生效。
  2. **虚引用必须配合 ReferenceQueue**：对象被回收后，虚引用会被放入队列，清理线程从队列取出引用，知道”对象死了”，再去释放关联的堆外资源。DirectByteBuffer 本身只有几十字节，但它关联的堆外内存可能很大——JVM 靠 Cleaner（内部是 PhantomReference）在 DirectByteBuffer 回收时调用 unsafe.freeMemory 释放堆外内存。
  3. ThreadLocal 泄漏的引用层面解释：ThreadLocalMap 的 key（ThreadLocal 本身）是弱引用，但 value 是强引用——所以线程池中长期存活的线程里，ThreadLocal 用完不 remove()，value 就永远被强引用着（key 变 null 也没用），这就是经典泄漏点。

面试怎么答：引用计数法一句话带过（”有循环引用问题，所以不用”）；可达性分析讲清 GC Roots 的 6~7 类来源；四种引用按”回收时机 + 用途”讲，务必带出虚引用的实际案例（DirectByteBuffer 堆外内存）；最后主动说”finalize 已废弃，JDK 9 弃用、JEP 421 标记移除，现在用 Cleaner 和 try-with-resources”。

5.2 垃圾收集算法

漫画式理解三种基本算法（讲给面试官听，比背定义生动得多）：

🗑️ 标记-清除（Mark-Sweep）：像整理旧书架——先把要留下的书一本本贴上标签（标记），然后把没贴标签的统统扔进垃圾桶（清除）。问题在于：扔完书之后，书架上空出来的位置东一块西一块（内存碎片），下次想放一套大百科（大对象）时，可能找不到连续的空间——单个空位加起来够大，但拼不成一整块。

📦 标记-复制（Copying）：干脆把房间一分为二，平时只用一半。要打扫时，把幸存的东西全部搬到另一半，然后把这一半直接清空（顺便全屋无碎片，因为搬过来的时候是紧挨着摆的）。缺点很明显：一半房间常年空着（空间利用率 50%）。新生代把它改良成 8:1:1，只浪费 10%，而且幸存对象本来就少，搬起来快——完美契合”朝生夕死”。

🚚 标记-整理（Mark-Compact）：把幸存的书一本一本往墙根推，全部挤得整整齐齐，腾出一整块连续空间。解决了碎片问题，代价是搬运很慢（所有存活对象都要移动）。适合”幸存者多”的区域——老年代。

对比表：

算法 步骤 优点 缺点 适用场景
标记-清除 标记存活 → 清除垃圾 实现简单、不移动对象 内存碎片；标记/清除两次扫描 CMS 的老年代（配合”碎片整理”兜底）
标记-复制 存活对象复制到空闲区 → 整区清空 无碎片、分配只动指针、回收快 浪费空间（需要一块空区） 新生代（8:1:1 只浪费 10%）
标记-整理 标记存活 → 向一端移动 → 清边界外 无碎片、适合存活率高的区域 移动对象成本高、停顿长 老年代（Serial Old、Parallel Old）

分代收集（为什么这样设计）：基于两个经验假说——弱分代假说（绝大多数对象朝生夕死）和强分代假说（熬过多次 GC 的对象更可能继续存活）。于是：新生代存活率低 → 复制算法，快、无碎片；老年代存活率高 → 标记-清除/标记-整理，避免反复搬运。不同区域用不同算法，整体效率最高——这就是分代收集的全部理由。G1 之后的收集器在物理上不再连续分代，但”把存活率不同的对象分开处理”的思想没变（Region 逻辑分代）。

面试怎么答：先画漫画（三个比喻），再落到对比表，最后一句升华：”分代收集不是一种算法，而是’把对象按存活概率分组，各组用最合适的算法’的工程策略。”把”复制算法只浪费 10% 而不是 50%”讲出来，就能体现你看过源码而非背过八股。

新生代三剑客：Serial / ParNew / Parallel Scavenge

收集器 特点 目标 何时用 配套参数
Serial 新生代单线程收集，STW 全程停顿，Client 模式默认 简单可靠 单核 CPU / 小内存桌面应用；JDK 8 里 CMS 老年代的后备 -XX:+UseSerialGC

注意：Parallel Scavenge 与其他收集器不同，它关注”吞吐量”（吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC 时间)），而不是停顿时间——这是它和 CMS/G1 的定位分野。

CMS：四个阶段详解、优缺点、为什么被废弃

CMS（Concurrent Mark Sweep）是 JDK 5 引入的第一款真正并发的老年代收集器，目标：最短停顿时间（互联网应用优先响应速度）。基于标记-清除算法，回收分 4 个阶段：

  1. 初始标记（Initial Mark，STW）：只标记 GC Roots 直接关联的对象。速度极快，停顿很短。
  2. 并发标记（Concurrent Mark）：从初始标记的对象出发，与用户线程并发做可达性分析，标记所有存活对象。不 STW，但会抢占 CPU。
  3. 重新标记（Remark，STW）：修正并发标记期间用户线程运行导致的引用变化（用增量更新 Incremental Update 记录新引用）。停顿比初始标记长。
  4. 并发清除（Concurrent Sweep）：与用户线程并发清理垃圾、回收内存。

优点：只有初始标记和重新标记两个短暂 STW，整体停顿低。

缺点（为什么最终被 G1 取代）：

  • 内存碎片：标记-清除不整理内存，长时间运行产生大量碎片，大对象无法分配时提前触发 Full GC；
  • 占用 CPU：并发阶段抢占 CPU（默认并发线程数 = (CPU核数+3)/4），CPU 核数少时吞吐量明显下降；
  • 浮动垃圾：并发标记/清除期间新产生的垃圾只能等下次回收，必须预留空间（默认老年代用到 -XX:CMSInitiatingOccupancyFraction=92% 就触发 CMS，留 8% 给浮动垃圾）；
  • Concurrent Mode Failure：并发清除期间老年代空间不足，CMS 退化为 Serial Old 单线程 Full GC（标记-整理），停顿时间极长——CMS 最怕的灾难场景；
  • 版本路线：JDK 9（JEP 291）标记弃用，JDK 14（JEP 363）正式移除。经典参数 -XX:+UseConcMarkSweepGC 已不存在。

G1：Region 布局、Young GC / Mixed GC / Full GC、RSet 和 SATB

G1（Garbage First）是 JDK 7u4 正式提供、JDK 9（JEP 248）起成为默认收集器，目标：在可预测的停顿时间内完成回收，是 CMS 的官方继任者。

Region 化堆布局：把整个堆划分为约 2048 个大小相等、逻辑连续的 Region（默认 1MB~32MB，-XX:G1HeapRegionSize 指定）。每个 Region 运行期动态扮演 Eden / Survivor / Old 角色——物理上不再连续分代，逻辑上仍分代。超过 Region 一半大小的对象放入 Humongous Region（大对象区），避免大对象在 Region 间复制。

回收过程：

  1. Young GC（STW）：回收所有 Eden + Survivor Region，存活对象复制到新的 Survivor Region，熬过阈值的晋升到 Old Region。Eden Region 越多，耗时越长。
  2. 并发标记（Concurrent Marking）：与用户线程并发标记全堆存活对象，为 Mixed GC 做准备。
  3. Mixed GC（STW）：只回收”垃圾占比最高、回收收益最大”的老年代 Region——这就是 “Garbage First” 的含义——而不是回收整个老年代，从而把停顿控制在目标内。回收对象按”收益/成本”排序，取性价比最高的集合。
  4. Full GC（兜底）：并发标记失败或 Humongous 分配失败时，退化为单线程 Full GC（标记-整理），停顿极长，应尽量避免（大堆上 G1 的 Full GC 通常意味着 OOM 前的信号）。

两个关键数据结构（G1 的精华考点）：

  • RSet（Remembered Set，记忆集）：记录”其他 Region 对当前 Region 的引用“。回收某个 Region 时只需扫描它的 RSet，就能知道”谁引用了我”，避免回收时全堆扫描（尤其是”收集新生代时要扫整个老年代”这个代价）。由写屏障（Write Barrier）在引用写入时维护，代价是额外的写操作开销（Card Table 精化）。
  • SATB（Snapshot-At-The-Beginning，起始快照）：并发标记基于”GC 开始时的堆快照“工作，通过 pre-write 屏障记录并发期间”被覆盖的旧引用值”——这样即使并发期间对象被重新引用，也不会被误判为垃圾。相比 CMS 的增量更新（记录新值、重新标记时要重新扫描根），SATB 更保守，停顿更可预测。

停顿模型：-XX:MaxGCPauseMillis（默认 200ms）给出停顿目标，G1 后台统计每个 Region 的回收耗时与收益，每次 Mixed GC 按性价比挑选 Region 集合，使总停顿贴近目标（软实时）。

为什么 G1 取代 CMS：停顿可预测（Region 增量回收 vs CMS 无法控制停顿）；无碎片（复制/整理回收）；支持超大堆（TB 级，RSet 避免全堆扫描）；SATB + RSet 的正确性机制比 CMS 增量更新更完善。

简要：ZGC 和 Shenandoah

收集器 版本路线 核心机制 解决什么问题
ZGC JDK 11 实验（JEP 333），JDK 15 生产可用（JEP 377） 着色指针（Colored Pointers）：64 位指针的高位存 4 位元数据（标记位、重映射位等）+ 读屏障；并发移动对象（并发整理） 停顿时间与堆大小无关：无论 4G 还是 16TB 堆，停顿都小于 1ms，且支持超大堆
Shenandoah JDK 12 实验（JEP 189），JDK 15 生产可用（JEP 379） Brooks 转发指针 + 读屏障：对象移动时在原位置留一个”指向新家的路标” 同样实现低停顿 + 并发整理；Red Hat 主导，被阿里云等大规模落地

两者与 G1 的本质区别：回收（甚至整理、移动对象）全程与用户线程并发，几乎不需要 STW，把停顿从”几十毫秒”压到”亚毫秒”。它们共同的代价是读屏障带来的访问开销（每次访问对象都要多一次判断）。

收集器总览表：

如何解读一行 GC 日志（以 Parallel 收集器为例）：

片段 含义
GC (Allocation Failure) 本次是 Minor GC（年轻代），原因是 Eden 分配失败；Full GC 则为老年代回收

快速判断健康度的口诀：Minor GC 频繁但堆用量回收后回不到低位 → 对象分配太快或新生代太小；Full GC 频繁且回收量小 → 老年代有存活对象堆积（内存泄漏的特征：FGCT 只涨不降）；GC 停顿超预期 → 看是堆太大、晋升太多还是收集器选择问题。

调优思路（不是调参数本身，而是”先确认目标，再选收集器，最后微调参数”）：

  1. 确认目标：要延迟（响应时间敏感，如在线交易）还是要吞吐（后台批处理）？堆内存在多大范围（64 位服务器上大堆常见）？
  2. 选收集器：JDK 8 默认 Parallel（吞吐）；延迟敏感换 G1（-XX:+UseG1GC）；大堆 + 亚毫秒停顿上 ZGC（-XX:+UseZGC）；小堆小机器 Serial 反而更好。
  3. 微调参数（一次只改一个，用日志 A/B 对比）：先定 -Xms=-Xmx（消除扩容抖动）→ 再定新生代（-Xmn 或 -XX:SurvivorRatio，观察 Minor GC 频率与晋升量）→ 最后调 GC 细节（停顿目标 -XX:MaxGCPauseMillis、晋升阈值 -XX:MaxTenuringThreshold、G1 的 -XX:InitiatingHeapOccupancyPercent）。先看日志再动参数，没有日志依据的调优都是玄学。

面试怎么答：参数能精确说出”-XX:+UseG1GC、-XX:MaxGCPauseMillis=200、-XX:InitiatingHeapOccupancyPercent=45“；日志能当场拆解一行（前 → 后 → 总容量 → 耗时）；调优背出”目标 → 选收集器 → 微调”的顺序，并强调”-Xms 与 -Xmx 相等、一次只改一个参数”的工程纪律。

6.3 实战：一个完整的 OOM 排查流程

故事背景：某电商订单服务的 JVM 内存告警 “Heap usage > 90%”，每 3 天左右 OOM 重启一次，重启后能撑几天再复发。这是典型的内存泄漏（而不是一次性分配过大）——真 OOM 往往几小时内就挂，能”撑几天”说明垃圾回收节节败退。

第一步：识别症状，确认是泄漏而非压力过大

观察要点：Full GC 后老年代占用（O 列）几乎不回落，FGC 次数和 FGCT 持续上升——回收不掉的东西在持续堆积，这就是泄漏特征。如果是”压力大”，Full GC 后 O 列会明显回落。

第二步：为 OOM 现场预埋 dump 开关（下次 OOM 自动留证据）

生产上正是靠 -XX:+HeapDumpOnOutOfMemoryError 在 OOM 瞬间保存现场，否则进程一挂，什么都查不了。

第四步：用 MAT 分析 dump（Leak Suspects → Dominator Tree → Path to GC Roots）

7. 调优实战案例

为什么需要了解：前面讲的是”是什么、怎么看”，这一章讲”怎么调”。三个案例覆盖三大典型诉求——吞吐量优先（后台批处理）、响应时间优先（在线接口）、稳定性优先（死锁排查），每个案例都遵循第 4 章的方法论：先定目标 → 选收集器 → 参数微调 → 用日志和监控验证。

7.1 吞吐量优先案例（Parallel Scavenge + Parallel Old）

场景描述：后台批处理服务，每天凌晨跑全量报表生成与积分批量计算，运行窗口 2 小时。业务要求：在窗口期内跑完所有任务，单位时间处理量（吞吐）越高越好；单次 GC 停顿允许达到秒级（没有人等着它）。堆内存 8G（-Xms8g -Xmx8g），JDK 8。

选型：Parallel Scavenge + Parallel Old（-XX:+UseParallelGC）。JDK 8 默认组合，多线程并行回收、不追求低停顿，正是”高吞吐 + 容忍停顿”场景的标准答案。依据是吞吐量公式：

吞吐量 = 用户代码运行时间 /（用户代码运行时间 + GC 时间）
Parallel 的目标是让 GC 时间占比尽量小，而不是让单次停顿尽量短——这是它与 CMS/G1 的分野（呼应 5.3 节）。

关键参数：

参数 作用 本案例取值
-XX:+UseParallelGC 选用 Parallel Scavenge + Parallel Old 必选
-Xmn4g 新生代 4G（案例关键：批处理产生大量”朝生夕死”对象） 4g
-XX:MaxGCPauseMillis=500 停顿目标（配合自适应策略调整堆布局） 500ms
-XX:GCTimeRatio=19 吞吐目标：GC 时间占比 ≤ 1/(1+19) = 5% 19

调优过程（GC 日志前后对比）：

优化前（默认配置，新生代被自适应策略压缩到约 260M，老年代被撑到 96%+）：

问题解读：Full GC 每 5 分钟一次、每次 3 秒以上，回收量却极小（老年代回收后几乎不降）——不是”垃圾多”，而是老年代里全是还活着的批处理对象。大量本应在新生代就死掉的对象因为新生代太小被过早晋升，把老年代撑满，Full GC 变成”定时打卡”，吞吐损失惨重。

优化后（-Xmn4g 扩大新生代，GCTimeRatio=19）：

解读：新生代扩到 4G 后，绝大多数临时对象死在新生代（回收后堆从 4.4G 降到 700M，老年代仅约 250M），只剩 0.18 秒的 Minor GC，Full GC 归零。总 GC 时间从”每小时约 36 秒 + 每 5 分钟一次 3 秒的 Full GC”降到”每小时约 20 秒纯 Minor GC”，报表窗口期提前 25 分钟跑完。

jstat 监控输出与分析：

分析要点：优化后 FGC 列恒为 0、FGCT 不再增长，O 列稳定在 40% 上下——晋升速度与处理速度匹配，系统进入良性循环。FGCT 只涨不降 + O 列居高不下，永远是 Full GC 问题的第一诊断信号（呼应第 6 章的泄漏排查）。

小结：吞吐优先场景三板斧——① 选 Parallel 系；② 把新生代调大，让”朝生夕死”的对象死在新生代；③ 用 GCTimeRatio 明确吞吐目标。判断吞吐调优是否成功，看 FGCT 增速和窗口期总时长，而不是看单次停顿。

7.2 响应时间优先案例（G1）

场景描述：交易查询接口服务，对外 SLA 是 p99 < 500ms。流量 24 小时持续，峰值 3000 QPS，堆 8G。业务要求：任何请求都不能被长 GC 停顿”惩罚”——接口超时的直接损失是上游重试和用户流失。

选型：G1（-XX:+UseG1GC）。理由：可预测停顿模型（Region 增量回收 + 停顿目标），用”吞吐略降”换”停顿可控”，正对响应时间敏感的在线服务。JDK 9+ 默认即 G1，JDK 8 需显式开启。

关键参数：

参数 作用 本案例取值
-XX:+UseG1GC 启用 G1 必选
-XX:MaxGCPauseMillis=200 停顿目标：单次 GC 尽量 ≤ 200ms 200
-XX:InitiatingHeapOccupancyPercent=45 堆使用率达 45% 即启动并发标记（为 Mixed GC 备料） 45
-XX:G1HeapRegionSize Region 大小（默认自动；大对象多时可显式设 8m/16m） 自动

调优过程（Parallel → G1 的 GC 暂停时间对比）：

指标 优化前（Parallel + Parallel Old） 优化后（G1）

偶发 Full GC 每 23 天一次，**25 秒**，期间接口集体超时 无（Mixed GC 兜底，峰值 ~180ms）
p99 RT 峰值时段 800ms~1.2s（被 Full GC 污染） 稳定 < 300ms
接口超时率 峰值时段 0.5%~1% < 0.01%

为什么 G1 能把停顿压住：Full GC 是 G1 的灾难（单线程标记-整理），正常的 GC 压力被拆成 Young GC + Mixed GC 两路消化——Young GC 只回收 Eden/Survivor Region（快）；Mixed GC 每次只挑”垃圾占比最高的一批老年代 Region”（-XX:G1MixedGCLiveThresholdPercent 控制），把一次大停顿拆成多次小停顿。InitiatingHeapOccupancyPercent=45 意味着堆用到 45% 就开始并发标记、提前为 Mixed GC 备好料，避免堆被撑满后被迫 Full GC。

G1 调优的两个观察点：

  1. 看停顿分布（GC 日志 -Xlog:gc*）：停顿是否逼近 MaxGCPauseMillis；Young GC 停顿超标，说明 Eden Region 太多（调小 -XX:G1NewSizePercent）或晋升量大、复制耗时大；
  2. 看 Mixed GC 周期：GC 日志出现频繁的 to-space exhausted（复制目标空间不足）或 Evacuation Failure，说明回收速度赶不上分配速度——调高 InitiatingHeapOccupancyPercent 提前启动标记，或调大堆。

小结：响应时间优先场景三板斧——① 选 G1；② MaxGCPauseMillis 定停顿目标；③ InitiatingHeapOccupancyPercent 提前备料，让 GC 压力”日常消化”，不给 Full GC 登场的机会。切换收集器后必须用日志验证停顿分布，不是切了就完事。

7.3 死锁排查完整案例（jstack + Arthas）

场景描述：订单服务线上偶发”部分请求永久卡死”——不超时、不报错，每个卡死的请求占用一个线程且不释放，线程数只涨不降，最终打满线程池导致服务不可用。重启恢复，几小时后复发。经典死锁特征：请求不是变慢，而是永远等不到。

第一步：构造死锁 demo（复现现场）

第二步：第一次 jstack 采样

解读 “Found one Java-level deadlock”：jstack 会遍历所有线程的 monitor 持有/等待关系，自动发现锁等待环（A 等的锁被 B 持有、B 等的锁被 A 持有）并直接打印死锁链。看到这段输出就是死锁实锤。两个关键信息：

  • waiting to lock <对象地址> 与 locked <对象地址>：每个线程在等哪把锁、持有哪把锁，环一眼画出来；
  • 栈顶方法（DeadlockDemo.java:11 / :22）：死锁发生在哪两行代码，直接定位到业务代码。

第三步：第二次 jstack 采样（对比确认）

为什么必须采两次：单次采样只能说明”此刻有两个线程在互相等待”——也许是瞬时竞争，下一秒就结束了。死锁是持久的：30 秒后再次采样，同一对线程还阻塞在同一对锁上、栈顶方法完全一样，才能确认是死锁而不是偶发阻塞。对比两份 dump 重点看三点：① 线程名一致；② 锁对象地址一致；③ 栈顶方法一致。

第四步：Arthas thread -b 确认

thread -b（blocked thread）直接找出阻塞其他线程的锁与持有者，一条命令定位死锁环；配合 dashboard 能看到两个线程 BLOCKED 状态卡死不动。

局限提醒：jstack 的自动死锁检测只覆盖 synchronized monitor。用 ReentrantLock 等 AQS 锁导致的死锁，线程状态是 WAITING (parking) 而不是 BLOCKED，jstack 通常不会打印 “Found one Java-level deadlock”——这时靠两次采样对比（同一批线程长期 WAITING）+ Arthas thread -b（它会分析 java.util.concurrent 的锁等待关系）来定位。

第五步：修复方案

死锁的根治方向是消除锁等待环，三个方案按推荐度排序：

方案一：统一锁获取顺序（最推荐，根因修复）——所有线程按同一顺序加锁，环不存在：

方案二：tryLock 超时放弃（无法统一顺序时的兜底）——用 ReentrantLock 替换 synchronized，拿不到锁就放弃而不是无限等待：

方案三：消除嵌套锁（结构性修复）——检查两个锁保护的临界区是否真的需要嵌套：能合并成一把锁就合并，能用 CAS/原子类就无锁化，别让加锁顺序成为业务代码的隐性契约。

1.1 Java 8（2014，LTS）：函数式编程进入 Java 生态

为什么需要：Java 8 发布时语言已 18 岁，上一轮语言级大改是 JDK 5 的泛型。此时多核 CPU 已经普及，但 Java 处理集合的方式仍是”for 循环 + 临时变量”，并发手段仍是原生线程 + synchronized。函数式编程（Lambda、流式处理）正是为解决两件事：

  • 样板代码：匿名内部类写一个 Runnable、Comparator 要十几行；
  • 集合处理声明式化：过滤、映射、归约这类操作，用流水线表达比命令式循环更清晰、更易并行。

怎么实现的：Lambda 不是语法糖展开成匿名类，而是由编译器生成 invokedynamic 调用点，由 LambdaMetafactory 在运行期生成函数式接口的实现类——性能接近手写匿名类。

Lambda 表达式

函数式接口

只有一个抽象方法的接口，可用 @FunctionalInterface 注解标记——它同时约束了接口不能有第二个抽象方法，避免误用。

方法引用

简化 Lambda 表达式，直接引用已有方法。四种形式：类::静态方法、对象::实例方法、类::实例方法、类::new（构造器引用）。

默认方法

Stream 要加在 Collection 接口上，但 Collection 有成千上万个实现类。如果直接给接口加抽象方法，所有实现类都会编译失败。默认方法的引入让接口可以在不破坏现有实现的前提下演化 API——这是 Java 8 能新增 Collection.stream() 的前提。

Stream API

惰性求值是 Stream 的灵魂：中间操作（filter/map）不立即执行，只是登记流水线，直到遇到终端操作（collect/reduce/forEach）才一次性执行。这允许只遍历一次完成整个流水线。

陷阱：parallelStream() 默认使用共享的 ForkJoinPool.commonPool()，CPU 密集任务并行度 = 核心数，且与其它并行流互相抢占；对 IO 任务不如专用线程池；对有序、有状态的中间操作（limit、collect 到有序集合）并行反而更慢。

Optional 类

Optional 的本质不是消除 NPE，而是把”可能为 null”变成类型签名的一部分，强迫调用方显式处理。注意它本身不推荐用作字段或方法参数，只用于返回值。

新的日期时间 API（JSR 310）

为什么需要：java.util.Date 是可变对象（线程不安全），且 API 混乱——年份从 1900 起算、月份从 0 起算，SimpleDateFormat 也不是线程安全的。新 API 全部不可变 + 线程安全，并且纳入 ISO 8601 标准体系。

1.2 Java 11（2018，LTS）：模块化成熟、var、HTTP Client、ZGC

为什么需要：JDK 9~11 解决了两个积累已久的问题——巨型单体 JDK（rt.jar 约 66MB，无法按需裁剪，内部实现类缺乏封装）和网络编程 API 的老化（HttpURLConnection 只支持 HTTP/1.1、阻塞式、API 难用）。同时 GC 领域首次出现”停顿时间与堆大小无关”的收集器。

模块化（JPMS，JDK 9，JEP 261）

rt.jar 被拆分为 90+ 个模块，每个模块在 module-info.java 里声明导出和依赖，实现强封装；新增 jlink 工具可按模块裁剪出最小运行时。

升级影响：JDK 8 → 9 是历次升级中最痛的一步——sun.misc.* 等内部 API 被封装后直接编译失败（--add-exports 可临时绕过），大量老框架在 9 上不兼容。这也是很多团队直接 8 → 17 的原因。

var 局部变量类型推断（JDK 10，JEP 286；JDK 11 JEP 323 扩展到 Lambda 参数）

var 是编译期推断、运行期仍是静态类型——它不是 JavaScript 的 var，类型在编译后已经确定，只是不用手写。JDK 11 允许在 Lambda 参数上用 var（通常与注解配合才有意义，因为注解不能标在隐式类型参数上）。

新的字符串方法

新增 isBlank()、lines()、strip()、repeat() 等方法。注意 strip() 比 trim() 更正确——trim() 只去掉码点 <= 0x20 的字符（按 char 处理），strip() 按 Unicode 空白规则处理（支持全角空格等）。

标准 HTTP 客户端（JDK 11 转正，JEP 321）

在 JDK 9 以孵化器模块（incubator）引入，JDK 11 正式转正，替代老朽的 HttpURLConnection，支持 HTTP/2 多路复用和 WebSocket，且提供同步（send）和异步（sendAsync 返回 CompletableFuture）两种调用方式。

文件读写与集合转数组的简化

Files.readString() / writeString() 让文件读写一行搞定；Collection.toArray(IntFunction) 让”集合转数组”不再需要先 new 一个空数组。

ZGC（JDK 11 引入，JEP 333 实验性）

为什么需要：传统收集器的停顿时间随堆大小增长——堆到 1TB 时，G1 的一次 Full GC 停顿可能达到秒级，大内存服务无法接受。

怎么实现的：ZGC 采用染色指针（Colored Pointer）+ 读屏障（Read Barrier），绝大多数 GC 工作与业务线程并发执行，停顿时间 < 10ms 且与堆大小无关。

成熟路径：JDK 11 实验性（需 -XX:+UnlockExperimentalVMOptions -XX:+UseZGC）→ JDK 15 转正（JEP 377，生产可用）→ JDK 17 完善并发类卸载等，成为大堆低延迟场景的标准答案。

1.3 Java 17（2021，LTS）：sealed class、模式匹配推进、ZGC 成熟

为什么需要：JDK 8 的免费维护已停止，17 是承接 8 项目升级的最重要 LTS。语言层面，模式匹配（pattern matching）作为 JDK 14 以来的主线工程在 17 完成第一块拼图，同时 sealed class 解决了”类层次失控”的问题。

模式匹配 instanceof（JDK 16 转正，JEP 394）

为什么需要：instanceof 检查 + 强转是两个重复的步骤，”检查后必然转换”是样板代码。模式匹配把两者合成一步。

sealed class（JDK 17 转正，JEP 409）

为什么需要：没有修饰符时任何类都能继承一个类，大型项目里类层次失控（”不知道谁继承了我”），审计困难。sealed class 让继承关系显式可控——只能列出白名单子类。它也是模式匹配穷举性检查的前提（编译器能确认 switch 覆盖了所有子类）。

文本块（JDK 15 转正，JEP 378）

为什么需要：多行字符串（SQL、HTML、JSON）在旧语法里要手动 \n + 转义，可读性极差，还容易写错缩进。

伪随机数生成器 API（JDK 17，JEP 356）

统一了 20 多种随机数算法的接口：RandomGenerator 接口 + RandomGeneratorFactory 工厂，可在运行期按名称选择算法（如高性能的 L32X64MixRandom），不再被 Random 的默认算法绑死。

switch 模式匹配（JDK 17 preview，JEP 406；JDK 21 转正）

JDK 17 中以 preview 提供：switch 的 case 可以是类型模式、null、守卫条件（when），配合 sealed class 可以实现穷举。**preview 意味着”语法定了但可能改，需要 --enable-preview 编译”**，生产项目在它转正前不要用。

版本升级注意点

  • 偏向锁：JDK 15（JEP 374）弃用并默认禁用，JDK 18 完全移除——不要在新代码里依赖”偏向锁性能”的旧结论；
  • 内部 API 强封装（JEP 403）：sun.misc 等默认不可访问，老项目依赖需 --add-opens/--add-exports 或升级依赖。

1.4 Java 21（2023，LTS）：虚拟线程，并发编程的范式转变

为什么虚拟线程是革命性的：这是自 JDK 5 引入 java.util.concurrent 以来并发模型最大的一次改变，直接回答了”一请求一线程模型在高并发下不可行”这个困扰 Java 服务十几年的问题。

背景：平台线程（Platform Thread）1:1 映射操作系统内核线程，每个线程默认约 1MB 栈 + 内核资源，一台机器撑死几千到几万线程。于是高并发只能两条路：线程池复用（请求排队、吞吐受限）或异步回调（CompletableFuture / Reactor，代码心智负担极重、调试困难）。

虚拟线程的答案：虚拟线程由 JVM 调度，挂载在少量”载体线程”（Carrier，默认 ForkJoinPool，线程数 = CPU 核数）上执行。虚拟线程阻塞（IO、sleep、锁等待）时，JVM 自动把它从载体上卸载（涉及 Continuation 机制），载体去执行其它虚拟线程。于是：

  • 成本：一个虚拟线程约几 KB，百万级并发成为可能；
  • 写法：可以回到”一请求一线程”的同步阻塞写法——简单、可读、可调试，却拥有异步的吞吐；
  • 不用再：为每个 IO 资源设计专用线程池、纠结 CompletableFuture 的链式错误处理。

注意事项（面试加分点）：

  • 虚拟线程不适合 CPU 密集型任务（没有阻塞点，挂载卸载没有意义，并行度受限于载体线程数）；
  • 不要池化虚拟线程（newVirtualThreadPerTaskExecutor 本身就是廉价创建/销毁的，池化反而违背设计）；
  • JDK 21 中 synchronized 块会固定（pin）载体线程，使阻塞无法卸载——已知限制，后续版本已改进（使用 ReentrantLock 可绕开，JDK 24 起已解除 pinning）；
  • 线程切换成本从”内核级”降到”用户态”，但共享资源的竞争成本不变，锁的滥用仍是瓶颈。

结构化并发（JDK 21 preview，JEP 453）

为什么需要：Future.get() 逐个等待、某个子任务失败时其它子任务不知情继续空跑、无法统一取消——并发任务的生命周期管理是散的。结构化并发把一组子任务放进一个 StructuredTaskScope，要么全部成功、要么一起失败并统一取消（”并发领域的 try-with-resources”）。

Record Pattern 与模式匹配完善（JDK 21 转正，JEP 440 / JEP 441）

为什么需要：Record 定义的是”纯数据载体”，解构时逐字段调用访问器是样板代码；Record Pattern 让解构一步完成，与 switch 模式匹配组合后，**”按类型 + 结构 + 条件”的解构式编程**成为可能。

1.5 版本选择建议：生产环境什么时候升级

要点：

  1. 非 LTS 版本（9/10/1216/1820）不要作为生产基线：每半年一个版本，Oracle 只提供下一个版本发布前的更新，维护期极短；
  2. LTS 的免费更新窗口：Oracle 对 LTS 提供至下一个 LTS 发布后 6 个月（17 → 2029-09，21 → 2031-09）；想长期免费打补丁就用 OpenJDK 发行版（Temurin、Corretto、Liberica 等）；
  3. 8 → 17 比 8 → 11 更划算：升级的固定成本（依赖扫描、字节码库、测试）是一样的，11 很快又会被迫升，一步到位 17 更省；
  4. 升级前必查清单：sun.misc/sun.reflect 等内部 API 使用、-XX: 参数兼容性（CMS 在 14 被移除）、偏向锁相关调优参数、SecurityManager（17 弃用，24 移除）、字节码增强库（CGLIB/ASM 版本）。

1.6 动手验证：javap 看 Lambda 真相，实测虚拟线程成本

实验 1：验证 Lambda 不是匿名类语法糖（对照实验）

预期观察点：字节码中出现 invokedynamic #xx 调用点，目录里没有按数字编号的匿名类文件（Demo$1.class）。

判定标准：invokedynamic 出现 + 无匿名类文件——证明 Lambda 由 LambdaMetafactory 在运行期生成实现类，不是「匿名内部类的语法糖」。

实验 2：虚拟线程 vs 平台线程的成本账（JDK 21）

预期观察点：同样「万线程 sleep」用平台线程写，默认栈 1MB 起步就是 10GB 虚拟内存 + 上万次内核级切换；虚拟线程（每线程几 KB）1 秒跑完。

判定标准：运行中 ps -M <pid> | wc -l 看到的载体线程数 ≈ CPU 核数（而非 1 万）；jcmd <pid> Thread.dump_to_file -format=json vthreads.json 能导出 1 万条虚拟线程记录。

2. Java 基础

2.1 equals 与 hashCode

面试官为什么问：这是把对象放进 HashMap/HashSet 的最基本前提。违反契约的后果是隐性的——“存得进去、取不出来”或”重复存储”，比编译错误难排查得多。

契约（Object 规范）

  1. 自反、对称、传递，且与 null 比较返回 false；
  2. 必要条件：a.equals(b) == true ⇒ a.hashCode() == b.hashCode()（反过来不成立，哈希碰撞是允许的）；
  3. hashCode() 在对象参与比较的字段未变化时，多次调用必须返回相同值。

为什么”必须”重写，而不是”应该”

HashMap 的查找分两步：先 hash(key) 定位桶（tab[(n-1) & hash]），再在桶内用 equals() 比对。默认的 hashCode() 由 Object 实现，返回与内存地址相关的值——两个逻辑相等（equals 为 true）的对象哈希不同，就会落到不同桶：

  • 存：a、b 都能放进 HashSet，集合出现两个逻辑相同的对象；
  • 取：用 a 存、用 b 查，b 的哈希定位到另一个桶，永远查不到。

  • **getClass() vs instanceof**：instanceof 写法允许子类与父类相等（对称性有风险），getClass() 写法要求严格同类。一般业务对象用 instanceof（Java 16+ 配合 pattern matching 的 o instanceof Person p 写法），枚举/值类型用 getClass()；

2.2 String

面试官为什么问：String 是使用频率最高的对象，它的内存模型（常量池）与 intern() 是”版本差异”类问题的经典题材，同时其不可变性设计贯穿安全、线程安全、哈希缓存多个考点。

为什么 String 设计成不可变

  1. 安全性：类加载器、网络地址、反射参数、HashMap 的 key 都依赖 String 的稳定内容。可变字符串意味着”拿到引用就能篡改”——常量池共享后，一个引用改内容会污染所有共享者；
  2. 字符串常量池复用：池化依赖”内容相同即同一个对象”的假设，内容可变则无法共享；
  3. 线程安全：不可变对象天然线程安全，无需同步；
  4. 哈希缓存：JDK 的 String 在首次调用 hashCode() 后把结果缓存到字段里——只有不可变才允许缓存；
  5. 作为 HashMap 的 key：key 的 hashCode 必须稳定，String 是理想的 key 类型。

2.3 异常体系

面试官为什么问：异常体系考察你对”错误处理设计”的理解——checked vs unchecked 的争论是 Java 语言设计史上最经典的话题之一，你的选择直接体现 API 设计能力。

层次结构

checked 与 unchecked 的设计哲学

  • checked 的动机（源自 JDK 1.0，借鉴 C++ 惯例）：”可恢复的失败”必须显式暴露在方法签名上，编译器强制调用方处理——IOException（文件不存在、网络中断）这类外部环境问题，调用方有机会重试、降级、换源，值得被强制感知；
  • unchecked 的动机：编程错误（传了 null、索引越界、状态非法）是代码 bug，强制处理没有意义——调用方不该为 bug 写 try-catch，应该让异常快速上抛、快速失败；
  • 实际项目中的现实：
    • 过度使用 checked 导致签名污染：throws Exception 满天飞、catch (Exception e) {} 空吞异常，反而掩盖错误；
    • 现代 Java 生态整体向 unchecked 倾斜：Spring 把 SQLException 等 checked 异常翻译成 unchecked 的 DataAccessException（DAO 层不再被迫 throws），MyBatis、JPA 类似；JDK 自身新 API（如 CompletableFuture 的 CompletionException）也大量使用 unchecked 包装；
    • 主流的共识：外部资源/IO 类的”可恢复”异常可以是 checked，其余一律 unchecked；跨层传递时用自定义 RuntimeException + 统一异常处理（如 Spring 的 @RestControllerAdvice）。

  • 多异常合并（JDK 7）：catch (IOException | SQLException e)；

  • **finally 里不要 return**：会吞掉 try 块抛出的异常。

2.4 泛型

面试官为什么问：泛型是集合与框架设计的地基；理解类型擦除，才能理解”为什么 List<String>.class 不存在””Spring 是怎么拿到泛型参数做依赖注入的”这类进阶问题。

为什么需要泛型

泛型（JDK 5 引入）解决两大问题：

  1. 类型安全：没有泛型时，List 可以放任何类型，取出时必须强转，ClassCastException 推迟到运行期才暴露。泛型把错误检查提前到编译期——list.add(1) 到 List<String> 直接编译失败；
  2. 代码复用：排序、比较、搜索等算法无需为每种类型重写一遍，<T> 让算法作用于类型参数。

什么是类型擦除

Java 泛型是编译期特性：编译器在编译时移除所有泛型类型信息，替换为原始类型或边界类型，并在必要处插入强制转换。设计目的是兼容 JDK 5 之前的非泛型遗留代码（二进制兼容）。这与 C# 的”真泛型”（运行期保留类型，值类型可免装箱）有本质区别——这也是面试常对比的点。

2.5 反射与动态代理

面试官为什么问：反射是 Spring IOC/AOP、MyBatis、Jackson 等几乎所有框架的底层机制，”框架原理”类问题最终都会下沉到这里。

什么是反射

在程序运行期间动态获取类或对象信息以及动态调用对象方法的功能称为 Java 的反射机制。

  • 优点：动态、灵活——IOC（运行期根据配置创建对象）、AOP（运行期拦截方法）设计的基石；
  • 缺点：性能开销大于直接调用（现代 JVM 已做优化：方法句柄、内联缓存，但热路径仍应避免）、破坏封装（能访问私有成员）、代码可读性差。

实际应用场景：框架开发（Spring 通过反射读取配置动态创建 Bean、AOP 动态代理；Hibernate/MyBatis 反射映射结果集）、注解处理（JUnit 找 @Test）、动态代理、通用工具库（Jackson/Gson 序列化）、IDE 的代码提示与调试器。

动态代理

动态代理在不改变原代码的情况下，通过运行期生成的代理对象对目标对象做增强。两种实现：JDK 动态代理（基于接口）与 CGLIB/ByteBuddy（基于子类）。

JDK 动态代理（基于接口）：要求目标实现接口。Proxy.newProxyInstance 在运行期生成一个实现了目标接口的代理类，所有方法调用经 InvocationHandler.invoke 转发——Spring AOP 在目标有接口时默认用这种方式。

CGLIB 动态代理（基于子类）：不要求接口，通过生成目标类的子类并重写方法实现增强（目标类不能是 final）。回调接口是 MethodInterceptor。

考点补充：

  • 为什么 JDK 代理要求接口：生成的代理类只能 extends Proxy（Java 单继承），无法再继承目标类，只能通过实现接口转发；CGLIB 生成子类绕开了这个限制，代价是 final 类/方法不可代理、生成子类有额外字节码成本；
  • Spring AOP 的选择：有接口 → JDK 代理，无接口 → CGLIB；Spring Boot 2.x 起默认使用 CGLIB（proxyTargetClass=true）——因为 CGLIB 不要求接口，且规避了”只代理接口、丢失实现类特有方法”的坑；
  • JDK 16（JEP 396） 重写了 ProxyGenerator（用 Java 实现替代 sun.misc.ProxyGenerator），动态代理现在支持 Proxy 类默认方法代理、性能更好；
  • 用动态代理必须注意：通过代理调用走 invoke，同类内自调用（this.method()）不会触发增强——Spring 的 @Transactional 自调用失效就是这个原因。

如何防止反射破坏单例

使用枚举实现单例（推荐）：JVM 从底层保证枚举构造器只被调用一次，且 Constructor.newInstance() 内部会检查并拒绝创建枚举实例——反射无法破坏。这是《Effective Java》作者 Josh Bloch 强烈推荐的方式。

（普通懒加载单例还需注意：getDeclaredConstructor().setAccessible(true) 可绕过私有构造器；序列化也会破坏单例，需 readResolve() 防御——枚举则天然免疫这两种攻击。）

2.6 序列化

面试官为什么问：Java 原生序列化（Serializable）是公认的失败设计，面试官想看你是否理解跨进程数据格式的选择逻辑——安全、性能、版本演进是核心维度。

Java 原生序列化的原理

实现 Serializable 后，ObjectOutputStream 通过反射遍历对象图，把类元数据（类名、字段名/类型/继承结构）+ 字段值写入二进制流；ObjectInputStream 反序列化时再重建对象。特点：反射开销大、体积大（一个对象带全套类描述）、Java 专属、二进制不可读。

为什么 Java 原生序列化被淘汰

问题 具体表现
安全 反序列化是远程代码执行（RCE）重灾区：恶意字节流可构造任意对象图触发 gadget 链（ysoserial 等工具；Fastjson、Commons-Collections 反序列化漏洞都属此类）。修复靠黑名单补丁，疲于奔命
性能 反射遍历对象图 + 写入完整类元数据，体积比 JSON 大数倍、比 protobuf 大一个数量级；速度慢 10~100 倍
版本兼容脆弱 类结构变化（新增字段、改类型）与 serialVersionUID 不匹配 → InvalidClassException；字段增删的演进流程非常痛苦
跨语言 二进制格式是 Java 专属，无法与 Go/Python/Rust 服务通信
可读性 二进制不可读，无法 curl 查看、无法调试

替代方案

方案 体积/速度 跨语言 特点与适用场景
JSON（Jackson/Gson） 中 ✅ 可读性好，REST API、日志、配置的标准；性能瓶颈可换 Jackson + Afterburner 或 JSON-B
protobuf 极小/极快 ✅ 二进制紧凑 + schema 演进机制（字段编号、required/optional），RPC 内部通信首选（gRPC 默认）

Kryo 小/快 ❌ Java 专属 高吞吐 Java 内部传输（缓存、分布式计算框架），比原生序列化快 10 倍+

总结：现代 Java 项目几乎不用原生序列化——对外用 JSON，对内 RPC 用 protobuf。如果你还在写 implements Serializable，通常是：远程方法调用（已过时的 RMI）、Java 缓存框架的堆外存储、或者历史遗留代码。

3.1 集合框架概览

Java 集合框架分两大体系：Collection（List/Set/Queue）与 Map。决策从”我需要什么语义”出发：

并发场景补充决策：需要线程安全的 Map/Set/List，首选 ConcurrentHashMap/ConcurrentSkipListSet/CopyOnWriteArrayList；Collections.synchronizedXXX 是全局锁，只在低并发时考虑；**Hashtable、Vector、Stack 是 JDK 1.0 遗留物**（所有方法 synchronized 全局锁），JDK 1.2 保留它们仅出于兼容，新代码不要用。

fail-fast 与 fail-safe

  • fail-fast（快速失败）：在原集合上遍历，迭代器创建时记录 expectedModCount，每次 next()/remove() 前检查 modCount == expectedModCount，不相等立即抛 ConcurrentModificationException。本质是单线程环境下的错误检测机制——它不能保证检测到所有并发修改（比如修改后又改回去就检测不到），也不是并发安全方案。代表：ArrayList、HashMap 的迭代器；
  • fail-safe（安全失败）：不在原集合上迭代，基于快照（snapshot）或弱一致性视图。迭代过程中原集合被修改不影响本次迭代，不抛异常。代价是弱一致性（可能读不到最新数据）和额外内存（快照）。代表：ConcurrentHashMap、CopyOnWriteArrayList 的迭代器。

3.2 ArrayList vs LinkedList

面试官为什么问：教科书说”数组 vs 链表”，但真实性能与直觉相反——面试官考察你是否做过实测、是否理解现代 CPU 缓存对性能的影响。

结构

  • ArrayList：Object[] elementData 动态数组，size 记录实际元素数；扩容是数组拷贝；
  • LinkedList：双向链表，每个节点 Node<E> 含 item/next/prev 三个引用。

ArrayList 扩容机制

为什么 1.5 倍而不是 2 倍：扩容是”空间 vs 拷贝次数”的权衡。2 倍扩容次数更少但每次浪费更多空间；1.5 倍（old + old >> 1）扩容均摊后插入仍为 O(1)，且减少内存浪费。预分配：能估算大小时直接 new ArrayList<>(expectedSize)（如 new ArrayList<>(map.size())），避免多次扩容拷贝。

面试官为什么问：HashMap 是使用率最高的容器，实现细节（树化阈值、扩容策略、哈希算法）是区分”背面试题”与”真懂”的分水岭。

基本结构

  • JDK 7：数组 + 链表（头插法）；
  • JDK 8：数组 + 链表 + 红黑树（尾插法）。

为什么链表 ≥ 8 才转红黑树、≤ 6 就退化

  1. 8 的统计依据（泊松分布）：负载因子 0.75、随机哈希下，桶内链表长度达到 8 的概率约为 0.00000006（六千万分之一）——这个数字出自 JDK 源码注释。也就是说正常情况下链表根本不会长到 8，树化是针对”哈希函数被恶意/异常破坏”（如 hash 冲突攻击、糟糕的 hashCode）的兜底，而不是常态；
  2. 为什么是 8 而不是更早：红黑树节点 TreeNode 比普通链表节点多 parent/left/right/red 等字段（占用约 2 倍内存），树化的”查找 O(log n) vs 链表 O(n)”性能优势要与节点内存开销权衡，8 是两者交叉点附近的经验值；
  3. 为什么退化阈值是 6 而不是 7/8：预留缓冲。如果退化阈值也是 8，一个桶在 7/8 之间反复增删，会频繁”树化→解树化→树化”，而树化是重操作（调整指针、变色、旋转），抖动代价高。6 与 8 之间留 2 的间隔就是为了防止抖动；
  4. 树化还有前置条件：数组容量 ≥ 64（MIN_TREEIFY_CAPACITY）。容量小时（如 16/32）哈希分布本来很差，此时扩容比树化更优（扩容后元素分散、链表自然变短），所以容量 < 64 时先扩容而不是树化。

为什么容量是 2 的幂

  1. 定位公式用位运算代替取模：桶下标 = (n - 1) & hash（n 为容量）。当 n 是 2 的幂时，n - 1 的二进制是全 1（如 16 → 1111），(n-1) & hash 等价于 hash % n 但只做一次位运算，更快；且低位全 1 让 hash 低 4 位均匀分布，冲突更少。如果 n 不是 2 的幂，n-1 会有 0 位，对应位恒为 0，部分桶永远空置；
  2. 扩容时位置推导：扩容 2 倍后，n-1 多了一个最高位 1。元素的新位置只可能是原位置 i 或 i + oldCap——取决于 hash 在新增位的值是 0 还是 1，即 (e.hash & oldCap) == 0。这就是 JDK 8 扩容”免全量 rehash”的原理；
  3. 容量始终向上取 2 的幂：tableSizeFor() 把任意指定容量转成最近的 2 的幂（如指定 13 → 实际 16）；
  4. 负载因子为什么是 0.75：空间利用率与冲突概率的权衡。0.5 冲突更少但空间浪费一半；1.0 空间足但冲突剧增（桶装满才扩容，链表变长）。0.75 是经验最优（泊松分布分析的基础）。

JDK 8 resize() 源码分析

分析要点：

  • 扩容倍数：oldCap << 1（2 倍），新阈值 oldThr << 1；
  • (e.hash & oldCap) == 0 是 JDK 8 的灵魂：oldCap 是 2 的幂（如 16 = 10000b），hash & 16 只考察 hash 在”新增位”的值——0 则新下标不变（i），1 则新下标 i + oldCap。链表整体按这条规则拆成两条子链表，顺序保持（尾插法的副产品），且每个节点只处理一次；
  • 相比 JDK 7”每个节点重新 hash & (newCap-1)“，省去了每个节点的重新取模，且因为顺序不变，不会像 JDK 7 头插法那样反转链表；
  • 红黑树桶走 TreeNode.split()，内部同样的高低位拆分逻辑（按低位链长度决定保持树形还是退化成链表）。

线程安全与 null key

  • JDK 7 多线程 put 扩容成环：头插法 + 扩容时链表反转，两个线程同时扩容可能把链表转成环形，get 无限循环（Java 7 时代经典生产事故，Java 8 用尾插法修复）；
  • JDK 8 多线程 put 丢数据：两个线程同时 put 到空桶，后写覆盖先写（oldVal 丢失），且 size 计数不准确。HashMap 任何版本都不是线程安全的，并发必须用 ConcurrentHashMap；
  • null key：HashMap 允许一个 null key（散列到 0 号桶，hash == 0）。而 ConcurrentHashMap 不允许 null key/value——并发场景下 get 返回 null 无法区分”key 不存在”还是”value 是 null”（这个歧义在非并发 HashMap 里可以用 containsKey 消解，但在并发下两次调用之间数据已经变了，无解）。

3.4 ConcurrentHashMap

面试官为什么问：ConcurrentHashMap 是并发容器选型的核心，JDK 7→8 的重构浓缩了现代无锁并发技术的精髓（CAS、细粒度锁、协同扩容、分片计数）。

为什么不用 Hashtable / Collections.synchronizedMap：两者都是全局锁——读也要拿锁，所有操作串行，并发度为零。CHM 的核心目标：读完全无锁，写只锁必要的桶。

JDK 7 实现（分段锁 Segment）

  1. 核心结构：固定大小的 Segment 数组（默认 16），每个 Segment 继承 ReentrantLock，内部维护自己的 HashEntry[] 桶数组。锁粒度是段——不同段上的写操作可并发，最多 16 个线程同时写；
  2. **put**：按 hash 定位 Segment → 加该段锁 → 段内找桶、插入/更新 → 释放锁；
  3. get：完全无锁——HashEntry.value 声明为 volatile，读依赖 volatile 保证可见性；
  4. size()：先无锁累加两次各段 count 与 modCount，若两次 modCount 一致则返回；否则锁住所有 Segment 再统计（高并发下开销大）；
  5. 扩容：发生在 Segment 内部，只扩触发扩容的那个段。

JDK 8 实现（CAS + synchronized + 红黑树）—— 为什么改

特性 Java 7 Java 8 优化点
锁机制 分段锁（Segment，继承 ReentrantLock） 桶级别锁（synchronized 锁桶头节点） + CAS 锁粒度更细（桶 vs 段）；空桶插入用 CAS 完全无锁；synchronized 受 JVM 持续优化（锁消除、轻量级锁），低竞争场景性能接近 CAS
数据结构 数组 + 链表（仅 HashEntry） 数组 + 链表 + 红黑树（Node/TreeNode） 高冲突桶查询 O(n) → O(log n)（与 HashMap 同策略：≥8 且容量 ≥64 树化）
size() 可能锁全表，低效 无锁：baseCount + CounterCell[] 分片计数（LongAdder 思想） 单一计数器在并发下是热点，分片把竞争摊到多个计数单元（配合 @Contended 避免伪共享）
扩容 段内独立扩容 多线程协同扩容（helpTransfer） 触发扩容后，后续写线程遇到 ForwardingNode 会领取一段迁移任务帮忙搬桶——利用并发加速扩容，缩短停顿
读操作 无锁（volatile value） 完全无锁（volatile + 特殊节点 find 转发） 读性能极高且稳定
内存开销 较高（Segment 结构 + 每段锁） 更低（单 Node 数组，树节点按需创建） 结构精简
ForwardingNode 无 有：迁移完成的桶放置 ForwardingNode 指向新表 无锁读 + 协同扩容的关键：get 遇到它转发到新表，写线程遇到它帮忙迁移

为什么 JDK 8 放弃 Segment 改用 synchronized + CAS：

  1. 锁粒度：从”段”细化为”桶头节点”——并发写碰撞概率从 1/16 降到 1/桶数，并发度提升一个数量级；
  2. 无锁化：桶为空时 put 直接 CAS 写入（casTabAt），初始化 table 也用 CAS + sizeCtl 控制——大量路径根本没有锁；
  3. **synchronized 不再”重”**：JDK 6 之后 synchronized 有偏向锁→轻量级锁→重量级锁的升级路径（注意：偏向锁 JDK 15 起默认禁用、JDK 18 移除，但轻量级锁/自旋让低竞争场景的 synchronized 依然很轻），锁桶头节点在低冲突场景开销极小；
  4. 读永远无锁：Node.value、Node.next 都是 volatile；扩容期间 get 通过 ForwardingNode.find() 转发到新表——get 与扩容并发执行也不会错。

JDK 8 put 流程（背熟这个）：

  1. 算 hash（扰动函数同 HashMap）；table 未初始化则 CAS 初始化；
  2. 定位桶 i；桶为空 → CAS 直接放入新节点，无锁完成；
  3. 桶头是 ForwardingNode → 正在扩容，协助扩容（helpTransfer）后再 put；
  4. 桶非空 → synchronized 锁桶头节点：链表则遍历更新/尾插；树节点则走红黑树插入；
  5. 检查是否树化（≥8 且容量 ≥64）→ 检查是否需要扩容。

与 Hashtable 效率对比

  • 锁粒度：Hashtable 全局锁（一次只允许一个线程操作）→ CHM7 段锁（16 段并发）→ CHM8 桶锁（几乎无限并发写）；
  • 读：Hashtable 读也要锁；CHM 两个版本的读都完全无锁（volatile 保证可见性）。

3.5 TreeSet / TreeMap

面试官为什么问：有序集合的选型与比较器契约（Comparable vs Comparator），以及”有序”与”唯一性”的关系——TreeSet 的去重依据是 compareTo()==0 而非 equals()，这是最常见的坑。

底层结构：红黑树

TreeMap 基于红黑树（自平衡二叉搜索树），TreeSet 基于 TreeMap（元素作 key，value 为固定 PRESENT）。红黑树的平衡性质保证：

  • 每个节点红或黑；根为黑；红节点的子节点必为黑；任意节点到其每个叶子路径上的黑节点数相同；
  • 由此保证最长路径不超过最短路径的 2 倍 → 增删改查全部 **O(log n)**，且不会退化成链表（AVL 树平衡更严格但旋转更频繁，红黑树是”足够平衡”的工程选择）。

  • 去重依据是 compareTo()==0，与 equals() 无关：两个 equals() 为 false 的对象，只要比较器认为相等（compareTo()==0），在 TreeSet 里就只能存一个——反之亦然。规则是”与 equals 一致”（compareTo()==0 ⇔ equals()），违反会导致集合行为诡异；

4. Java IO

IO 面试的核心逻辑只有一条：如何用更少的线程服务更多的连接。从 BIO 到 NIO 到 AIO 再到虚拟线程，都是为了回答这个问题。

4.1 从 BIO 到 NIO 的演进

BIO 的问题：一连接一线程

传统阻塞 IO（BIO）的调用点（accept、read、write）都是阻塞的——线程发起 IO 后挂起，直到数据到达。于是高并发服务只能”一连接一线程”：

  • 线程数 = 连接数：10000 连接 = 10000 线程。每个平台线程默认约 1MB 栈 + 内核资源，加上上下文切换开销，C10K 问题（万级连接）就是天花板；
  • 资源浪费：大多数连接处于空闲等待（等数据、等响应），线程却一直占着——“线程在等，不是在做”；
  • 线程池方案是缓解不是解决：池大小受限，连接数超过池容量就排队，吞吐受限。

NIO 的答案：一个线程管多个连接

JDK 1.4 引入 NIO（New IO），核心思想是非阻塞 + 事件驱动：线程不再”等某个连接”，而是问内核”哪些连接就绪了”（Selector），只处理就绪的连接，一个线程可管理数万连接。

AIO 的尴尬：JDK 7 的 AIO 在 Windows 上基于 IOCP（真异步），在 Linux 上网络部分实际是 epoll 模拟（Linux 内核的 POSIX AIO 只支持文件 IO），加上回调模型编程复杂，实际网络编程主流始终是 NIO + Reactor（Netty），AIO 几乎没被采用。io_uring（Linux 5.1+）出现后，真正的内核异步才有可行方案，Netty 5.x 已提供 io_uring 支持——但这是后话。

字节流与字符流

  • 字节流：InputStream/OutputStream，处理二进制数据（图片、视频、网络包），核心类 FileInputStream；
  • 字符流：Reader/Writer，处理文本数据（自动处理编码），核心类 FileReader、InputStreamReader；
  • 关键点：字符流底层依赖字节流 + 编码转换——InputStreamReader 是字节到字符的桥梁（指定 Charset，否则用平台默认编码，跨平台会乱码）。

为什么要有字符流：直接操作字符避免手动转码（UTF-8/GBK 互转），一次性解决乱码问题；按字符（而非字节）处理文本逻辑更自然。

NIO 三大核心组件

  • Buffer：数据容器（ByteBuffer 等），核心操作 flip()（写转读）、clear()（读转写）、compact()。三个关键属性：position（读写位置）、limit（读写边界）、capacity（容量）；
  • Channel：双向数据传输通道（FileChannel、SocketChannel、ServerSocketChannel），对比流的单向性——一个 Channel 既能读又能写；
  • Selector：单线程监听多个 Channel 的事件（OP_ACCEPT、OP_READ、OP_WRITE、OP_CONNECT），select() 返回就绪事件集合——多路复用的核心。

4.2 五大 IO 模型

理解五个模型前先记住：一次 IO 分两个阶段——① 等待数据就绪（数据从网卡/磁盘到内核缓冲区）；② 数据从内核缓冲区拷贝到用户态。五个模型的本质区别就是”阻塞发生在哪个阶段、由谁通知”。

1. 阻塞 I/O 模型（Blocking I/O）—— 用户态、内核态两个阶段都阻塞

特点：线程发起 IO 后被挂起，直到数据就绪并拷贝完成才返回。最简单直接，但线程全程被占着。

2. 非阻塞 I/O 模型（Non-blocking I/O）—— 等待阶段不阻塞，靠轮询

特点：accept/read 立即返回（没数据返回 -1 或 0），线程通过轮询检查就绪状态。不阻塞了，但轮询本身消耗 CPU——单线程轮询 N 个连接 = N 次系统调用，高并发下不可用。这个模型的定位是”教学意义上的中间态”，实际工程用的是模型 3。

3. I/O 多路复用模型（I/O Multiplexing）—— 单线程 + 内核通知就绪事件

特点：一个线程把大量连接注册到 Selector，调用 select() 阻塞等待，内核负责检测哪些连接就绪并通知。对比模型 2，就绪检测从”用户态轮询”下放到”内核事件通知”，系统调用次数从 O(n) 降到 O(1)（有事件才返回）。这是 Netty 的基石。

4. 信号驱动 I/O 模型（Signal-driven I/O）—— 内核发信号通知就绪，Java 不直接支持

特点：进程注册 SIGIO 信号处理器，内核在数据就绪时发信号通知，进程在信号处理器里发起读取（读取仍是阻塞的——只解决了”等待阶段”）。实现复杂、信号队列可能溢出，实际很少使用。Java 没有直接对应 API（NIO 的 Selector 更接近多路复用而非信号驱动）。

5. 异步 I/O 模型（Asynchronous I/O）—— 两个阶段都不阻塞，完成回调

特点：发起 IO 后立即返回，数据从内核拷贝到用户态完成之后才回调 CompletionHandler——连”拷贝阶段”都不阻塞（对比：多路复用模型在拷贝时仍需线程）。Java 对应 NIO.2（JDK 7）的 AsynchronousServerSocketChannel / AsynchronousSocketChannel。

各模型对比总结：

模型 阻塞阶段 Java 实现 优点 缺点
阻塞 I/O 等待数据到达和复制 Socket, ServerSocket 编程简单 线程资源浪费，一连接一线程
非阻塞 I/O 无（但需轮询） NIO configureBlocking(false) 单线程管理多连接 轮询消耗 CPU，系统调用频繁
I/O 多路复用 等待事件通知 NIO Selector 高效管理大量连接（内核通知） 编程较复杂；拷贝阶段仍阻塞
信号驱动 I/O 无（但需处理信号） Java 不支持 减少轮询开销 编程复杂，信号队列溢出

一句话记忆：阻塞与非阻塞看”调用是否立即返回”；多路复用与异步看”就绪/完成的检测与通知方”——多路复用还需要线程去拷贝，异步连拷贝都不用管。

4.3 select / poll / epoll 对比

三者都是 IO 多路复用的实现，让一个线程同时监听大量文件描述符（fd），由内核通知哪些 fd 就绪。区别在于内核的实现方式、fd 上限与性能。

select

  • 把监听的 fd 放入一个 fd_set 位图（bitmap）。每次调用都要把整个位图从用户态拷贝到内核态，内核遍历位图判断哪些 fd 就绪，再把结果拷贝回用户态；
  • fd 数量受限：受 FD_SETSIZE 限制，通常为 1024；
  • 复杂度 O(n)：内核需线性遍历全部 fd 才能知道谁就绪；返回后用户程序还要再遍历一遍才能确定哪些 fd 可读写。fd 越多，性能越差；
  • 内核会**修改传入的 fd_set**（就绪的 fd 被标记），因此每次调用前都要重新填充；
  • 只支持水平触发（LT），且属于主动轮询，没有事件通知机制。

poll

  • 思路与 select 相同，但把位图换成了 pollfd 结构体数组（fd + events + revents）：用户只填充 events，内核就绪后回填 revents，无需像 select 那样每次重新构造；
  • 没有连接数上限（受系统允许进程打开的 fd 数限制，如 ulimit -n）；
  • 遍历仍是 **O(n)**：每次调用都要把整个数组拷贝进内核并线性扫描，连接数多时性能依然线性下降。

**epoll**（Linux 2.6+ 专属）

  • 事件驱动：通过 epoll_create 创建句柄、epoll_ctl 注册/修改/删除 fd、epoll_wait 等待事件。内核只把就绪的 fd 挂入就绪链表返回，无需扫描全部 fd；
  • O(1) 复杂度：就绪 fd 通过回调直接入链，epoll_wait 直接取走就绪链表，耗时与连接总数无关。已注册的 fd 由内核中的红黑树组织，增删改查为 O(log n)；
  • 用户态与内核态通过 mmap 共享内存共用事件表，避免数据拷贝，近乎零拷贝；
  • 支持 LT（水平触发） 与 ET（边缘触发） 两种模式：
    • LT：fd 只要可读写就反复通知（数据没读完就持续上报），与 select/poll 行为一致，不易丢事件，编程简单；
    • ET：仅在状态变化时通知一次，必须配合非阻塞 IO + 循环 read 一次性读完，否则可能漏数据。通知次数少、效率更高，但编程复杂。

对比总结：

特性 select poll epoll
底层数据结构 fd_set 位图 pollfd 数组 红黑树 + 就绪链表
最大连接数 1024（FD_SETSIZE） 无上限（受系统限制） 无上限
遍历方式 线性扫描全部 fd，O(n) 线性扫描全部 fd，O(n) 事件回调，只返回就绪 fd，O(1)

平台支持 几乎所有平台 几乎所有平台 仅 Linux

场景选择：连接数少、追求跨平台用 select/poll；高并发、海量连接用 epoll（Netty 在 Linux 上的 EpollEventLoop 就是对 epoll 的封装）。为什么 epoll 快：select/poll 是”我扫一遍所有 fd 看谁就绪”（O(n) 每次都扫），epoll 是”fd 就绪时内核回调把我挂进就绪链表”（只有就绪的才处理）——从”扫描”变成”通知”，这是本质区别。

深挖：Redis 用 ET、Netty 用 LT——同一个机制的两份答案

LT/ET 不是「谁更先进」，而是两种完全不同的契约：LT 保证「事件不丢失」（数据没读完就反复通知），ET 保证「一次就绪只通知一次」（读不完是你自己的事）。两大框架各选一头，机制原因各不相同：

框架 选择 机制原因 生产后果
Redis（事件循环单线程） ET 单线程串行处理，一个 fd 就绪后由同一线程连续读到 EAGAIN，不存在「别的线程抢读」；ET 让通知次数与事件数严格 1:1，省掉 LT 反复确认的开销 读循环少判一次 EAGAIN 就丢数据，所以 Redis 的读回调必须是 while 循环读完整批
Netty（EventLoop） LT（epoll 默认） 多个 Channel 的事件由同一 EventLoop 串行分发，LT 保证「事件没处理完就持续通知」，配合 16MB 自动读配额，事件永不丢失；若默认 ET，Netty 无法替用户保证「一定循环读完了」 用 ET 自研服务器的团队，最常见的线上事故是「偶发丢数据」——read 循环在某个边界少读了一次，下次通知永远不会再来

记住一句话：LT 是「有数据就反复叫你，直到你读完」；ET 是「变一次叫一次，没读完算你丢」。生产自研 NIO 服务器入门一律 LT；只有像 Redis 那样单线程串行处理、且读逻辑保证循环读完的场景才上 ET。

4.4 Reactor 模式

为什么需要 Reactor：4.2 的模型 3 代码里，selector.select() 返回后，事件分发、业务处理、读写都揉在一个循环里。连接多了之后这个循环会变成瓶颈。Reactor 模式把职责拆开：IO 事件分发（Reactor）与业务处理（Handler）解耦，事件循环只做分发，业务可以放到线程池。

三种形态：

形态 结构 特点 代表
单 Reactor 单线程 一个线程：select + 分发 + IO + 业务 最简单；业务阻塞会拖垮整个事件循环 Redis 6.0 之前（事件驱动单线程）
单 Reactor 多线程 一个线程 select + 分发 + IO；业务处理进线程池 业务慢不影响事件循环；但 select 与 IO 仍在一个线程 下面的完整示例即此形态
主从 Reactor 多线程 主 Reactor 只负责 accept；从 Reactor（可多个）负责连接建立后的 IO 事件；业务进线程池 并发连接建立也是瓶颈时，把 accept 单独拆出来；扩展性最强 Netty（BossGroup / WorkerGroup）

Netty 的对应关系：BossGroup = 主 Reactor（accept 分发），WorkerGroup = 从 Reactor 组（每个 EventLoop 一个 select 循环，负责读写与业务调度）；NioEventLoop 封装了 epoll/select，DefaultEventExecutorGroup 承载业务线程池。

Reactor 与 Proactor 的一句话对比：Reactor 是”IO 就绪了通知你，你自己读写”（同步、多路复用）；Proactor 是”读写完成了我通知你”（异步）。Netty 是 Reactor 的忠实实现。

完整可运行示例：先运行 SimpleReactor（端口 8083），再运行 ReactorClient 压测

代码解析（面试要能讲出）：

  • Reactor 线程：selector.select() 阻塞等待事件 → 通过 SelectionKey.attachment() 找到事件处理器（Acceptor/Handler）分发执行——“事件分发”与”业务处理”解耦；
  • Acceptor：处理 OP_ACCEPT，接受连接后创建 Handler（注册 OP_READ）；
  • Handler：OP_READ 时在 Reactor 线程读数据，业务处理（Processor）提交给 workerPool——业务慢不会阻塞事件循环，这是”单 Reactor 多线程”的要点；
  • 跨线程注意点：业务线程向共享 output 缓冲区写入、修改 interestOps 都必须 synchronized，并 selector.wakeup() 唤醒 select（否则 select 阻塞着不会立刻感知新事件）——这也是为什么更彻底的主从多线程模型把事件循环分组，避免跨线程触碰 selector 状态；
  • 为什么生产不用这段代码：业务线程直接操作 Reactor 的共享 Buffer 与 interestOps，同步负担重且易错；Netty 通过 EventLoop 线程模型保证”同一 Channel 的所有操作都在同一线程”，从根上消除跨线程共享。

5. 网络基础（TCP/IP 与 HTTP）

网络是 Java 后端的”地基”——你写的每一个 HTTP 接口、每一条数据库连接、每一次消息推送都跑在 TCP/IP 之上。面试官问网络，考察的不是背报文格式，而是三件事：数据到底是怎么走的（分层与封装）、TCP 的可靠性是怎么做到的（握手、窗口、拥塞），以及 HTTP/HTTPS 的机制细节（报文、状态码、跨域、TLS）。

5.1 TCP/IP 协议栈

OSI 七层 vs TCP/IP 四层

为什么需要分层：一次网络传输要解决无数问题——信号怎么变成比特、比特怎么变成帧、帧怎么路由到对方、怎么保证不丢不乱。分层把这些问题拆成互相独立的模块，每层只干一件事、只跟相邻层打交道——任何一层换实现（比如链路层从以太网换成 WiFi）不影响其它层。

OSI 七层 TCP/IP 四层 核心协议 数据单位 典型设备/组件
应用层（7） 应用层 HTTP/HTTPS、DNS、FTP、SMTP、SSH 报文（Message） 浏览器、Nginx、Tomcat
表示层（6） 应用层（合并） SSL/TLS、字符编码、数据压缩 — —
会话层（5） 应用层（合并） 会话管理、认证（JDBC Session、RPC 连接） — —
传输层（4） 传输层 TCP、UDP 报文段（Segment）/ 数据报（Datagram） 四层负载均衡（LVS）
网络层（3） 网际层 IP、ICMP（ping）、IGMP 数据包（Packet） 路由器
数据链路层（2） 网络接口层 以太网（Ethernet）、ARP、VLAN 帧（Frame） 交换机

面试常问”为什么 OSI 是七层、实际用的却是四层”：OSI 是理论模型（学术价值在于”分层思想”），它的会话层/表示层在互联网实践中没形成独立的协议（功能被应用层协议自己承担），所以 TCP/IP 模型把它俩合并进了应用层。记 OSI 是为了背层次顺序，实际抓包分析永远以 TCP/IP 四层为准。

各层核心协议速览

层 核心协议 端口/标识 一句话职责
应用层 HTTP/HTTPS、DNS、FTP、SMTP、SSH 80/443、53、21、25/465、22 定义业务语义与数据格式
传输层 TCP、UDP 源/目的端口（16 位） 端到端传输：可靠（TCP）或尽力（UDP）
网际层 IP、ICMP 源/目的 IP 地址（32/128 位） 跨网络寻址与路由
网络接口层 以太网、ARP MAC 地址（48 位） 局域网内点对点传输

记忆锚点：端口负责”这台机器上的哪个进程”，IP 负责”哪台机器”，MAC 负责”同一局域网内谁收”——一次传输三层寻址全要用到。

数据封装与解封装

封装（发送方，从上往下逐层加头）：应用层产出 HTTP 数据 → 传输层加 TCP 头（源/目的端口）→ 网际层加 IP 头（源/目的 IP）→ 链路层加以太网头（源/目的 MAC）→ 物理层把比特发到线缆。

解封装（接收方，从下往上逐层剥头）：链路层看 MAC 确认是给自己的 → 网际层看 IP 确认目的 → 传输层看端口交给对应进程 → 应用层拿到原始数据。

关联考点：MTU 与 MSS。以太网帧最大 1500 字节（MTU），IP 头 20 字节 + TCP 头 20 字节，所以 TCP 单次最多携带 MSS = 1500 − 40 = 1460 字节数据——这就是”大消息必须分片、应用层必须自己处理半包”的物理根源。

5.2 TCP 协议

TCP 是最重要的传输层协议，面试围绕四个机制展开：连接管理（三次握手/四次挥手）、可靠性（确认与重传）、流量控制（滑动窗口）、拥塞控制。

三次握手（SYN → SYN+ACK → ACK）

建立连接时双方交换三个报文，确认”我能发、你能收；你能发、我能收”：

步骤 报文 方向 内容 目的
① SYN 客户端 → 服务器 seq = x（初始序列号） 客户端请求建立连接，告知自己的序列号起点
② SYN+ACK 服务器 → 客户端 seq = y, ack = x+1 服务器确认收到，同时告知自己的序列号起点
③ ACK 客户端 → 服务器 ack = y+1 客户端确认收到——至此双方双向就绪，进入 ESTABLISHED

一次连接的完整生命周期（握手 → 传输 → 挥手）：

sequenceDiagram

为什么是三次不是两次（必背）：

  • 两次握手只能保证”服务器确认了客户端能发”，无法保证”客户端确认了服务器能发”——但核心问题还不是这个；
  • 经典反例——失效的旧连接请求：客户端发的第一个 SYN 在网络中滞留，客户端超时重发 SYN 并成功完成连接、传输、关闭。此时旧 SYN 才到达服务器。若只有两次握手，服务器收到旧 SYN 后回 SYN+ACK 并直接进入 ESTABLISHED、分配资源——但客户端根本不会理会这个连接，服务器的资源被白白占用（SYN Flood 攻击就是利用这个原理耗尽服务器资源）；
  • 三次握手时，客户端收到服务器对旧请求的回应后会回一个 RST，服务器收到 RST 就知道对方无意连接，释放资源。**三次握手让服务器在分配资源之前，先确认”这个连接是客户端真心想建立的”**。

四次挥手（FIN → ACK → FIN → ACK）与 TIME_WAIT

连接是双向的，每一方要关闭自己那一半就得发一次 FIN，所以完整关闭需要四个报文：

步骤 报文 方向 状态变化 说明
① FIN 主动方 → 被动方 主动方 FIN_WAIT_1 主动方说”我的数据发完了，我要关我这半边”
② ACK 被动方 → 主动方 被动方 CLOSE_WAIT；主动方 FIN_WAIT_2 被动方确认，但自己还有数据要发（半关闭）
③ FIN 被动方 → 主动方 被动方 LAST_ACK 被动方数据发完，关闭自己半边
④ ACK 主动方 → 被动方 主动方 TIME_WAIT；被动方 CLOSED 主动方确认，等 2MSL 后才真正 CLOSED

为什么 TIME_WAIT 要等 2MSL（必背，两点）：

  1. 保证最后一次 ACK 到达：第④步的 ACK 可能丢失。若丢失，被动方（LAST_ACK）超时会重发 FIN，主动方需要还在（TIME_WAIT 中）才能回 ACK 完成关闭。最后一次 ACK 传输耗时 1 个 MSL，重发的 FIN 耗时 1 个 MSL，等 2MSL 保证”即使 ACK 丢了，重发循环也能走完”；
  2. 让旧连接的报文在网络中消亡：同一对 (源IP, 源端口, 目的IP, 目的端口) 的新连接可能复用原端口。若旧连接的迟到报文未消失就建立了新连接，新连接会收到脏数据。等 2MSL 让旧报文在网络中全部死亡，保证新连接干净。

MSL（报文最大生存时间）Linux 默认 30s，2MSL 即 60s——这就是服务器上大量 TIME_WAIT 连接要挂 60 秒的原因。高并发短连接场景（如连接池频繁重建）TIME_WAIT 大量堆积是常见生产问题，优化方向是连接复用（keep-alive/连接池），而不是暴力调小 tcp_fin_timeout。

生产排查两个高危状态：

  • 大量 TIME_WAIT：主动关闭方多——通常是服务器主动 close（短连接场景），资源开销不大，但端口耗尽时新连接失败；
  • 大量 CLOSE_WAIT（重点）：被动关闭方收到了 FIN 但应用层没有调用 close()——典型原因是连接泄漏、未关闭的流（try-with-resources 没用好）、线程池任务排队迟迟不处理响应。CLOSE_WAIT 只增不减基本等于代码 bug，lsof -i + 线程栈定位是标准排查姿势。

滑动窗口与流量控制

为什么需要：发送方不能无脑发——发太快，接收方缓冲区溢出丢包，触发重传反而更慢；发太慢，浪费带宽。所以需要”接收方告诉发送方自己能收多少”。

  • 每个 TCP 头都带 16 位 window 字段：接收方通告自己当前可接收的字节数（接收窗口 rwnd）；
  • 发送方维护**发送窗口 = min(rwnd, 拥塞窗口 cwnd)**，窗口内的数据可以连续发出（不必等逐个 ACK）；
  • 接收方处理完数据后通过 ACK 携带窗口更新值——这就是”滑动”：窗口左边是已确认、中间是已发未确认、右边是待发送。

与拥塞控制的区别（面试必分清）：流量控制是端到端的——防止”发送方淹没接收方”（接收方缓冲区不够）；拥塞控制是端到网络的——防止”发送方淹没网络”（路由器缓冲区溢出）。一个管接收端，一个管网络。

拥塞控制

算法 触发时机 cwnd 变化 目的
慢启动 连接建立 / 超时重传后 指数增长（每 RTT 翻倍） 快速探测网络可用带宽
拥塞避免 cwnd ≥ ssthresh（慢启动阈值） 线性增长（每 RTT +1） 接近带宽上限后谨慎试探
快速重传 收到 3 个重复 ACK 立即重传丢失报文 不等超时（RTO 通常 ≥ 200ms），减少等待
快速恢复 快速重传触发后 ssthresh = cwnd/2，cwnd = ssthresh，转拥塞避免 网络只是轻微丢包，不必回到慢启动重头探测

面试完整链路：连接建立 → 慢启动指数增长 → 撞到 ssthresh 转拥塞避免线性增长 → 某包丢失 → 收到 3 个重复 ACK 触发快速重传 + 快速恢复（cwnd 减半继续拥塞避免）→ 若超时（RTO）则视为严重拥塞，回到慢启动且 ssthresh 减半。TCP 的公平性正是靠”拥塞就减半”的加性增/乘性减实现的。

TCP 粘包 / 半包

为什么会有这个问题：TCP 是字节流协议，没有”消息边界”——发送方写两次 write，接收方可能一次 read 全拿到（粘包）；发送方写一次大消息，接收方可能分多次 read 才拿完（半包）。粘包/半包不是 TCP 的 bug，而是”多条应用消息塞进一个字节流”的必然结果：

  • 粘包原因：发送方连续小包被 Nagle 算法合并、或被内核缓冲区一次性发送；接收方一次 read 读到多条消息；
  • 半包原因：单条消息超过 MSS（1460 字节）被分片；接收方 read 的缓冲区小于消息长度。

三种解决方案：

固定长度 每条消息定长，不足补位 实现最简单 浪费带宽、长度必须预先知道 一些老旧协议
分隔符 消息以 \n 等特殊字符结尾 实现简单、可读 内容里不能出现该字符（需转义） Redis RESP、行协议
长度字段 头部 4 字节长度 + 消息体 通用、高效、无内容限制 实现稍复杂 Netty LengthFieldBasedFrameDecoder、Kafka 协议

UDP 的特点

特点 说明
无连接 无需握手，直接发数据报，省去建立连接的时间

TCP vs UDP 选型表

维度 TCP UDP
连接 面向连接（三次握手、四次挥手） 无连接（即发即走）
可靠性 可靠：确认、重传、排序、去重 不可靠：尽力而为
数据边界 字节流（无边界，粘包/半包） 数据报（有边界）
拥塞控制 有（慢启动/拥塞避免） 无（延迟稳定）

什么场景用 UDP：

  • 音视频通话/直播（WebRTC）：丢几帧画面可以接受，卡顿 200ms 不可接受——TCP 的”丢包重传 + 拥塞降速”在实时场景是灾难；
  • DNS：一次查询一次响应，响应丢了客户端重查一次即可（DNS 默认走 UDP 53，区域传输才用 TCP）；
  • 游戏实时对战：位置同步丢一包用下一包覆盖（要的是”最新状态”而不是”完整历史”）；
  • NTP 时间同步 / 物联网传感器上报：单包即语义完整，重传无意义。

判断口诀：数据丢了”无所谓或有最新覆盖” → UDP；数据丢了”必须补上” → TCP。

如何基于 UDP 实现可靠传输（RUDP）

为什么需要 RUDP：TCP 可靠但慢（握手 RTT、队头阻塞、拥塞控制不可控），UDP 快但不可靠。某些场景要”TCP 的可靠性 + 自定义的控制权”——于是把可靠机制搬到应用层自己实现。

RUDP 的基本思想（照搬 TCP 的零件）：

  1. 序列号：每个数据报编号，接收方用序号检测丢失、乱序、重复；
  2. ACK / NACK：接收方回确认；丢包时用 NACK（或 ACK 缺口）快速告知发送方，比等超时更快；
  3. 超时重传：发送方对未确认的包超时重发；
  4. 滑动窗口：控制”在途未确认”的数据量，防止把自己和网络打爆；
  5. 可选拥塞控制：可借鉴慢启动/拥塞避免，也可以故意不做拥塞控制（游戏优先低延迟，宁可丢包不降速）。

成熟案例：QUIC（HTTP/3 的传输层）本质就是 RFC 标准化的 RUDP——UDP 之上实现可靠传输、多路复用、0-RTT、连接迁移。游戏行业的 RUDP 私有协议（如 KCP）思路一致。

RUDP 的代价：所有机制自己实现（序列号管理、重传队列、拥塞状态机），复杂度高、容易出 bug、协议互不兼容。选型判断：有现成标准（TCP/QUIC）能满足就别自己造。

幂等性（RFC 7231）：同一请求重复执行，资源状态不变。GET/HEAD/PUT/DELETE 语义上幂等；POST 不幂等。幂等性 = 重试安全——网络超时后客户端可以放心重放 GET，但重放 POST 可能导致”重复下单”。所以订单/支付接口要么保证幂等（幂等键 + 唯一索引），要么禁止自动重试。

环节 典型限制

代理/CDN 各家不同，通常 8KB~16KB

URL 超过限制会返回 **414 URI Too Long**。所以”GET 参数多放几个没事”是误区——大数据（复杂查询条件、文件上传）必须走 POST。

Cookie 与 Session

Cookie：服务端通过 Set-Cookie 下发、客户端存下来、后续请求通过 Cookie 头带回的小型键值数据。关键属性：HttpOnly（禁止 JS 读取，防 XSS 窃取）、Secure（仅 HTTPS 传输）、SameSite（防 CSRF 跨站携带）、Domain/Path（作用范围）、Max-Age/Expires（过期时间）。单条约 4KB、单域名约 50 条。

Session：服务端为会话分配唯一 id，把用户状态存服务端（内存/Redis），客户端只需持有 session id（通常放 Cookie）。**Cookie 存数据，Session 存”身份 + 服务端数据”**。

维度 Cookie Session
存储位置 客户端浏览器 服务端
大小限制 约 4KB / 每域 50 条 取决于存储（内存/Redis）
安全性 明文存储、可被篡改（须 HttpOnly + Secure + 签名） 客户端只持有随机 id，更安全
分布式扩展 天然无状态 单机内存 Session 在多实例部署下直接失效

分布式会话三方案（面试高频）：

  1. Session 粘滞（sticky）：负载均衡把同一用户固定到同一台机器——机器宕机就丢会话，不推荐；
  2. 集中存储：Session 放 Redis，任意节点可查——Spring Session 的标准方案，推荐；
  3. 无状态化（JWT）：服务端不存会话，把用户身份放进客户端持有的签名 Token（JWT），每次请求验签——天然水平扩展，代价是无法主动注销（只能等过期/黑名单），敏感操作慎用。

流程 直接发真实请求，响应回来后浏览器校验 CORS 头，不通过则拦截 浏览器先发 OPTIONS 预检，服务端返回允许列表后，才发真实请求
开销 无额外往返 多一次 OPTIONS 往返

实践要点：现在后端接口几乎全是 application/json → 几乎都会触发预检，所以跨域接口常看到”先 OPTIONS 200、再真实请求”两个包——这是正常现象。配置层面 Spring 用 CorsFilter / @CrossOrigin，网关/Nginx 用 add_header Access-Control-*。生产环境不要配 * + credentials（浏览器禁止组合），也不要全局放行（正确做法：白名单源）。

HTTP/1.1 → HTTP/2 → HTTP/3

特性 HTTP/1.1 HTTP/2 HTTP/3
底层传输 TCP TCP UDP + QUIC
连接模型 持久连接，但同连接请求串行 一个 TCP 连接上多路复用（多流并发） 多路复用 + 流间互不阻塞
头部传输 明文逐请求重发 HPACK 压缩（静态表/动态表/Huffman） QPACK（面向乱序的改进）
队头阻塞 有（响应必须按序，队头慢包堵全队） TCP 层仍有（一个包丢失，重传期间阻塞整条连接所有流） 基本消除（丢包只影响所属流）
握手 TCP 握手 + TLS 握手（多次 RTT） 同左 0-RTT 可带数据
其他 管线化（理论可行，实践被浏览器禁用） 二进制分帧、服务器推送（已被 Chrome 废弃） 连接迁移（换网络不断连）

HTTP/1.1：keep-alive 持久连接解决了”每次请求都重新握手”的问题；管线化（pipelining）理论上允许一次发出多个请求，但要求响应按序返回——队头第一个响应慢，后面全堵着，浏览器实际禁用，这也是 HTTP/2 出现的直接动机。

HTTP/2 的关键机制：

  • 二进制分帧：报文拆成帧（HEADERS 帧 / DATA 帧），每个帧带 stream id——一个 TCP 连接上多个流交错传输，接收端按流 id 重组，实现多路复用（一个连接并发几十个请求）；
  • 头部压缩（HPACK）：Header 不再逐请求明文重发——静态表预置常见头（:method、:path），动态表缓存重复值，配合 Huffman 编码，头部体积可减小 80% 以上；
  • 服务器推送（Server Push）：服务器预测客户端将请求的资源（如 HTML 里引用的 CSS）主动推给客户端。注意：Chrome 已在 2022 年移除对 Server Push 的支持（实际收益低、与客户端缓存冲突），面试讲到要说”已废弃”；
  • 缺点：TCP 层队头阻塞依然存在——一条流丢一个包，TCP 要等重传，而重传期间该连接上的所有流都被阻塞。

HTTP/3：QUIC 把可靠传输搬进用户态：QUIC 基于 UDP，在用户态实现”类 TCP 的可靠传输”（正是 5.3 的 RUDP 思路）——每个流独立编号、独立确认，一个流丢包只重传这个流，不阻塞其它流，彻底解决队头阻塞；同时把 TLS 1.3 集成进握手（首次连接 1-RTT，复用 0-RTT 可带数据），连接通过 Connection ID 标识（换 WiFi/4G 不断连）。代价是 QUIC 实现复杂度高，且依赖 UDP 端口穿透（部分老防火墙/NAT 对 UDP 不友好）。

5.5 HTTPS

为什么需要 HTTPS：HTTP 明文传输——中间人可以窃听（看到密码）、篡改（改响应内容）、伪装（冒充服务器）。HTTPS = HTTP + TLS，解决三件事：机密性（加密防窃听）、完整性（防篡改）、身份认证（防伪装）。

对称加密 vs 非对称加密

维度 对称加密 非对称加密
密钥 加解密同一把密钥 公钥加密、私钥解密（反之：私钥签名、公钥验签）
速度 快（AES 有硬件指令加速） 慢（RSA 比 AES 慢几个数量级；ECC 系更优）
密钥分发 困难：怎么安全地把密钥交给对方？ 公钥可公开分发
算法 AES、DES、3DES RSA、ECC（ECDHE/ECDSA）
用途 传输数据加密 密钥协商、数字签名、证书

HTTPS 的组合思路：性能差的非对称加密只用来协商对称密钥（密钥交换），拿到密钥后全部数据走对称加密（AES）——既安全（密钥不落地传输，由双方临时算出）又高效。密钥交换优先用 ECDHE（椭圆曲线 DH）：双方的 pre-master 由各自私钥 + 对方公钥算出，即使服务器私钥泄露也无法解密历史流量（前向保密）；RSA 密钥交换无前向保密，已被淘汰。

TLS 握手过程

步骤 内容 目的
① ClientHello 客户端支持的 TLS 版本、密码套件列表、随机数 发起协商
② ServerHello 选定版本与套件、随机数 定下协议参数
③ Certificate 服务器证书（含公钥 + CA 签名） 证明”我是 example.com”
④ 证书校验 客户端验证证书链、有效期、域名（SAN） 防伪装
⑤ 密钥交换 双方算出同一个 pre-master 生成会话密钥的种子

TLS 1.3 的简化：只保留 1 次握手往返（1-RTT），移除 RSA 密钥交换等弱套件，强制 ECDHE + 前向保密；会话复用场景下 0-RTT——客户端直接带着上次会话的凭证发第一个请求，快一个往返。

证书链与 CA 信任体系

为什么需要 CA：服务器自己生成公钥没问题，但怎么让客户端相信”这把公钥真的是 example.com 的”？——证书（公钥 + 域名 + CA 的数字签名）。CA（证书颁发机构）是受信任第三方：它验证域名所有权后，用自己的私钥给证书签名；客户端用系统/浏览器内置信任库里的 CA 公钥验签——签名通过，就信这个证书。

证书链（三级）：

校验方向正好相反：从下往上——用中间 CA 的公钥验证 leaf 签名 → 用根 CA 的公钥验证中间 CA 签名 → 根 CA 在信任库里，验证链闭合。

为什么需要中间 CA：根 CA 私钥一旦泄露等于信任体系崩溃，所以根私钥离线保存、极少使用；签发权限下放给中间 CA，根只给中间 CA 签名。常见运维坑：

  • 中间证书没下发：服务器只配了 leaf 证书，客户端手里没有中间 CA 导致验证链断裂（chain incomplete）——排查用上面的 openssl s_client，修法是拼接”leaf + 中间CA”下发；
  • 证书与域名不匹配：证书 SAN 里没有当前域名（内网 IP、泛域名配置错）；
  • 证书过期：Let’s Encrypt 90 天短证书自动续期失败是高频事故；
  • 自签名证书：没经过 CA，浏览器不信任——只适合开发环境（用 mkcert 可以生成本地信任的证书），生产一律用正式 CA。

Netty 原理与实践

Posted on 2025-07-22 In 中间件 Word count in article: 15k Reading time ≈ 53 mins.

Netty 是 Java 网络编程绕不开的高性能基石，也是高级 Java 工程师面试的必考环节。本文从 BIO 的阻塞困境讲起，逐层剖析 Netty 的线程模型（Reactor 演进）、ChannelPipeline 责任链、编解码器、TCP 参数调优、心跳与断线重连、ByteBuf 内存管理，再到启动/连接/读数据三大源码链路，最后用 15 个类的完整代码手写一个可运行的 RPC 框架，并盘点 Dubbo、RocketMQ、gRPC、Elasticsearch 中 Netty 的真实应用。

1. 从 BIO 到 NIO 到 Netty

1.1 BIO 的阻塞困境

这个”一连接一线程”模型的三个致命问题：

  1. 线程数 = 连接数。每个连接占一个线程，线程栈默认 1MB，1 万个连接就是 10GB 虚拟内存，还要加上线程上下文切换的 CPU 开销。连接数达到 C10K（1 万台客户端同时在线）时系统直接崩溃。
  2. 线程大量阻塞空转。大多数连接处于”等待数据”状态，线程阻塞在 read() 上不干活，却占着栈内存和调度资源。
  3. 连接数不可控。高并发下创建线程本身就会触发 OOM，且无法优雅降级。

1.2 NIO 的复杂性

Java 1.4 引入 NIO，核心思想是用少量线程通过 Selector 多路复用管理大量连接：Selector 上注册感兴趣的连接，内核帮你监听，有事件了才通知。

模型对了，但直接用 NIO 写生产代码，坑多到让人想辞职：

  • Selector 空轮询 bug（JDK 6462197 / Linux epoll bug）：select() 在没有事件时也可能立即返回 0，导致 CPU 空转 100%。这个 bug 在部分 JDK + Linux 内核组合下依然存在，必须自己加”空轮询计数 + 重建 Selector”的兜底逻辑。
  • 粘包/半包：TCP 是字节流协议，没有消息边界。你 send 了两次 "hello"，对端可能一次收到 "hellohello"（粘包），也可能先收到 "hel"（半包）。每条消息的边界全靠自己解析。
  • ByteBuffer 难用：flip()、compact()、rewind()、clear() 四个方法转换位置状态，写错一次指针，数据就错乱；Buffer 还没有自动扩容能力。
  • 缺乏高层次抽象：没有”处理器链”、没有编解码器、没有心跳、没有优雅停机，所有东西都得从零手写，还容易写错。

1.3 Netty 的设计目标

Netty 的设计目标一句话：把 NIO 的复杂度全部封装掉，给你一个事件驱动的高性能网络编程框架。它做到了：

痛点 Netty 的解法

Selector 空轮询 rebuildSelector() 自动重建 Selector，无感
粘包半包 ByteToMessageDecoder + 各种现成 FrameDecoder
ByteBuffer 难用 ByteBuf 读写双指针、自动扩容、池化、引用计数
无处理器抽象 ChannelPipeline 责任链 + 丰富的 ChannelHandler

还有一个隐性价值：Netty 屏蔽了底层 IO 模型的差异。同样的代码可以跑在 NIO（多路复用）、Epoll（Linux 原生）、OIO（阻塞，已废弃）、KQueue（Mac）、甚至 io_uring 上，换一个 EventLoopGroup 和 Channel 类型即可。

2.1 Reactor 模式回顾

Reactor（反应堆）模式的核心：一个线程（或者几个线程）负责监听和分发所有 IO 事件，事件到了再调用对应的处理器，而不是为每个连接开一个线程。分三个演进阶段：

单 Reactor 单线程：一个线程既负责 accept 新连接，又负责读写和业务处理。问题：一个业务阻塞，所有连接都卡死。只适合 Demo。

单 Reactor 多线程：Reactor 线程只负责 IO 事件的监听和分发，业务处理丢给工作线程池。问题：高并发下 Reactor 单线程依然是瓶颈（accept、read、write 都在它身上），且可能出现并发操作同一连接的问题。

主从 Reactor 多线程（最成熟）：主 Reactor 只负责 accept 新连接，把连接交给从 Reactor；从 Reactor 负责该连接的读写，业务仍交给业务线程池。Netty 就是这种模型。

一个经典的坑：

引用计数的核心规则：ByteBuf 实现 ReferenceCounted 接口。release() 一次计数减一，减到 0 就归还池子。规则很简单——谁最后消费了消息，谁负责 release：

  • 用 SimpleChannelInboundHandler 业务处理，框架自动释放；
  • 用 ChannelInboundHandlerAdapter，处理完调 ReferenceCountUtil.release(msg)；
  • 消息继续往下游传播（调了 fireChannelRead(msg)）时，不要 release，让下游处理；
  • 把消息引用存到成员变量长期使用（非引用计数对象包装）时，必须 retain() 一次，防止被其他 handler 释放；
  • 分发给多个消费者时，每个消费者 retain()，最后每个都 release()。

排查内存泄漏：启动参数加 -Dio.netty.leakDetection.level=paranoid（默认是 simple 抽样检测），Netty 会在泄漏的 ByteBuf 被 GC 时打印创建它的堆栈（LEAK: ByteBuf.release() was not called before it's garbage-collected）。

面试官追问：pipeline 中一个 handler 抛异常会怎样？异常沿入站方向传播，exceptionCaught 事件从抛错点向后传播，直到有 handler 处理它；如果没有任何 handler 处理，最后会到 tail，Netty 只打一条 warn 日志（不会自动关连接）。所以一定要在 pipeline 尾部加一个兜底 exceptionCaught handler，统一打日志 + 关闭连接，防止半开连接堆积。

TCP 是流协议，粘包半包是必然现象，解决思路只有一个：让协议有消息边界。四种经典方案：

方案一：固定长度（FixedLengthFrameDecoder）

简单粗暴，但定长浪费带宽，几乎没人这么设计协议。

方案二：分隔符（LineBasedFrameDecoder / DelimiterBasedFrameDecoder）

5.2 高低水位机制（WRITE_BUFFER_WATER_MARK）与 OOM 防护

问题场景：服务端给下游大批量推送数据（如广播、报表导出），如果下游消费慢，数据会堆积在两个地方——Netty 的 ChannelOutboundBuffer（应用层写缓冲）和内核发送缓冲。写缓冲不设上限，数据持续堆积 = 直接内存 OOM。

Netty 的解法是高低水位：出站缓冲的预估字节数超过高水位时，channel.isWritable() 返回 false，并触发 channelWritabilityChanged 事件；降回低水位之下时恢复 true 并再次触发事件。

业务侧的正确姿势：

要点：

  • 写缓冲的字节预估包括：未 flush 的消息 + 已提交但未写完的数据，是”大概值”，不精确但足够做流控；
  • isWritable() 判断的是”应用层写缓冲是否超过高水位”，与内核发送缓冲无关；
  • 大文件/大数据响应，别一次 writeAndFlush 一个几十 MB 的大对象，用 FileRegion（见 7.4）或分块写；
  • 判断”写成功”用 writeAndFlush(msg).addListener(ChannelFutureListener.FAIL_ON_EXCEPTION)，而不是盲目相信 flush 完成。

5.3 连接超时与读写超时配置

连接超时（CONNECT_TIMEOUT_MILLIS）：客户端专用，默认 30s，生产建议 3~5s。超过后 connect 任务失败，future.cause() 是 ConnectTimeoutException。

读超时：Netty 提供 ReadTimeoutHandler，基于 EventLoop 的调度实现，不是操作系统超时：

写超时：WriteTimeoutHandler，在指定时间内写操作没完成（数据没刷完）就抛 WriteTimeoutException。注意它监控的是”写操作是否完成”，不是缓冲区里数据滞留时间。

生产经验：读超时的时间设置要与业务场景匹配。某次事故：推送大文件接口走了普通读超时链路，下载 3s 没读完就被 ReadTimeoutHandler 掐断，而文件传输本来就要几十秒。修复：大文件通道单独建 pipeline 或放大超时，心跳/短请求通道保持短超时。超时配置永远按通道的流量特征分而治之。

6. 心跳与断线重连

6.1 IdleStateHandler 原理与使用

IdleStateHandler 是 Netty 内置的空闲检测器，参数：readerIdleTime（读空闲，多久没收到数据）、writerIdleTime（写空闲）、allIdleTime（读写都空闲），任意为 0 表示不检测。

原理：handlerAdded 时在当前 channel 绑定的 EventLoop 上注册一个延迟任务，任务在 EventLoop 线程内周期性执行，对比”上次读写时间”与当前时间，超过阈值就触发一个 IdleStateEvent，通过 userEventTriggered 事件传给下游 handler。关键细节：

  • 在 channelRead/channelReadComplete 中更新”最后读时间”（内部用 reading 状态避免大消息读取中途被误判为空闲）；
  • 空闲任务跑在事件循环线程里，不需要额外的定时器线程，一个 EventLoop 管理它名下所有连接的空闲检测；
  • 事件触发后不会自动关闭连接，只发事件，关不关由你决定。

6.2 心跳机制设计（PING-PONG、心跳超时断连、重连策略）

生产环境的心跳设计参数（经过验证的模板）：

角色 策略 参数依据
客户端 每 30s 发一次 PING（allIdle 触发） 心跳间隔 = 业务容忍的”假死时间”的 1/3 左右
客户端 90s 没收到任何数据（readerIdle）→ 判定服务端故障，进入重连 3 倍心跳间隔，容忍网络抖动和丢包重传
服务端 90s 没收到任何数据 → 关闭连接 与客户端 readerIdle 对齐，防止半开连接堆积
双方 PONG 回复不是必须的 任意一个字节（包括业务响应）都算”有数据”，天然重置空闲计时

为什么是 3 倍：一次 PING 丢失（网络抖动/GC 停顿/中间设备丢弃）不应导致断连，3 次机会基本覆盖瞬态故障；同时必须小于中间设备（NAT、LB、云防火墙）的空闲回收时间。经典线上事故：云厂商 LB 的空闲连接回收时间是 120s，服务端心跳周期是 180s，结果所有长连接在 120s 处被 LB 静默切断，客户端却毫无感知，直到下次发请求才发现连接已死。修复：心跳周期改成 30s。

断线重连（指数退避 + 随机抖动）：

重连的三个纪律：

  1. 重连调度必须挂在 EventLoop 上（ctx.executor().schedule），避免多个线程同时重连导致连接风暴；
  2. 指数退避 + 随机抖动，否则大量客户端同一时刻重连会打爆服务端（惊群）；
  3. 重连期间要主动放弃旧资源：channelInactive 里清理 pending 请求、关闭旧 Channel 防止泄漏。

6.3 心跳检测与业务检测分离

把”心跳”和”业务”耦在一起是生产环境最常见的设计错误，三条原则：

  1. 消息类型分离：心跳是协议的一种消息类型（type 字段区分），而不是在业务消息里塞标志位。心跳消息不经过业务线程池，直接在 IO 线程回复；
  2. 超时配置分离：心跳超时（90s 级）和业务超时（秒级/毫秒级）是两套机制。业务超时用 ReadTimeoutHandler 或 RPC 层 Future 超时，心跳超时用 IdleStateHandler——混用会导致”业务慢一点就被判死连接”；
  3. 心跳 handler 的位置：放在编解码器之后、业务 handler 之前。心跳包解码成 HeartbeatMessage 后直接由 HeartbeatHandler 消费（回复 PONG），不再向下传播，不打扰业务层：

生产经验：如果系统有百万级连接需要大量定时任务，IdleStateHandler 默认用 EventLoop 的调度队列（每连接一个调度条目，量大时可观）。Netty 还提供了 HashedWheelTimer（时间轮）用于统一管理海量超时任务——事件循环 + 时间轮是大型网关的标准组合，面试提到这个细节会加分。

7. ByteBuf 内存管理

7.1 ByteBuf 的读写指针（readerIndex/writerIndex/capacity）

ByteBuf 是替代 ByteBuffer 的缓冲区，核心是读写双指针模型：

  • readerIndex <= writerIndex <= capacity 恒成立；
  • readXxx() 移动 readerIndex（读走可读数据），writeXxx() 移动 writerIndex；
  • readableBytes() = writerIndex - readerIndex，writableBytes() = capacity - writerIndex；
  • markReaderIndex()/resetReaderIndex() 标记与回退（解码器判断半包时回退的利器）；
  • discardReadBytes()：把未读数据搬到头部（有拷贝，频繁调用有性能损耗），用于内存紧张场景；
  • clear()：两个指针都归零，不清理数据，是最廉价的”复位”；
  • 自动扩容：写满了自动扩大 capacity（翻倍增长，有上限），这是 ByteBuffer 没有的能力。

7.2 堆内存 vs 直接内存（HeapByteBuf vs DirectByteBuf）

对比项 HeapByteBuf（堆内） DirectByteBuf（堆外/直接内存）
分配位置 JVM 堆 堆外（Unsafe/malloc 分配）
创建速度 快（对象分配即可） 慢（系统调用），必须池化
回收 GC 自动 引用计数，必须手动 release，泄漏会导致堆外 OOM（OutOfMemoryError: Direct buffer memory）
IO 性能 差：系统调用必须用堆外，需要一次拷贝（堆内 → 临时堆外 → 内核） 好：直接交内核，省一次拷贝
业务处理 好：可拿到 byte[] 数组，读写方便 差：无法拿数组，只能 getBytes() 拷贝出来

结论（Netty 的默认策略）：网络 IO 层（编解码器产出/消费的 buffer）用池化的直接内存——读写 socket 时零拷贝；业务处理层如果需要长时间持有数据（比如塞进队列做异步处理），拷贝成堆内对象再释放原 buffer。这就是 ALLOCATOR 默认是 PooledByteBufAllocator 且 DEFAULT_DIRECT 为直接内存的原因。

生产经验：内存泄漏检测开 paranoid 级别压测环境抓泄漏；线上用 -Dio.netty.leakDetection.level=simple（抽样）。堆外内存不归 JVM 堆管，-Xmx 不够约束它，监控要盯 Direct buffer memory。

7.3 PooledByteBufAllocator 与对象池

Netty 4.1 默认分配器是 PooledByteBufAllocator，核心结构：

分配流程：请求分配 → 按大小分类 → 优先从 ThreadLocal 缓存取 → 没有则从 PoolSubpage/PoolChunk 分配 → 最终分配不到再 Unsafe 向系统申请新内存块。归还（release）流程反过来，用过的 ByteBuf 回到池子。

收益：直接内存的分配/释放是系统调用，池化后高频分配释放不再触碰系统，同时减少 GC 压力和内存碎片。代价是池子本身占内存（可通过 -Dio.netty.allocator.maxOrder、-Dio.netty.allocator.tinyCacheSize 等调优）。

面试官想问什么：为什么 Netty 不用 NIO 的 ByteBuffer.allocateDirect？答：直接内存分配慢 + 回收不可控（依赖 GC），池化后分配变成”从池里取”，快且可控。再追问：池化内存泄漏怎么发现？答：ResourceLeakDetector（引用计数归零前对象被 GC 会打泄漏堆栈）+ 堆外内存监控曲线。

7.4 零拷贝：CompositeByteBuf / slice / FileRegion / wrap

Netty 的”零拷贝”要分两层理解：

第一层：用户态免拷贝（Java 层不搬数据）

典型场景：HTTP 响应 = 响应头 + 响应体，用 CompositeByteBuf 组合直接交给协议层，避免拼接大 byte[] 的拷贝。

第二层：内核态零拷贝（sendfile）

FileRegion.transferTo() 最终调用 Linux sendfile() 系统调用：数据从磁盘 → 内核页缓存 → socket 直接发送，完全不经过用户态和应用内存。几十 GB 的文件传输只占几 KB 内存，这是”文件下载”类接口必须用 FileRegion 的原因。

生产经验：零拷贝不是免费的——slice/wrappedBuffer 是视图，任何一方修改都会互相可见；引用计数要算清楚（retainedSlice、CompositeByteBuf.addComponents(true, ...)）；FileRegion 传输是异步的，文件句柄必须在 write 完成的 listener 里关，提前关文件数据就断了。

10. Netty 在主流框架中的应用

10.1 Dubbo 中的 Netty（NettyServer / NettyClient）

Dubbo 的 RPC 传输层默认就是 Netty（dubbo-remoting-netty4 模块）：

  • NettyServer：服务端，内部是 ServerBootstrap + NettyServerHandler（适配器），配 IdleStateHandler 做心跳；
  • NettyClient：客户端，Bootstrap + NettyClientHandler；
  • NettyChannel：把 Netty 的 Channel 包装成 Dubbo 自己的 Channel 抽象，隔离传输层实现（Netty/MinNet/Http 可切换）；
  • HeaderExchangeHandler：在 Netty pipeline 之上实现 Dubbo 协议——Magic(2) + Flag(1) + Status(1) + RequestId(8) + 数据长度(4)，这就是一个典型的 LengthFieldBasedFrameDecoder 使用场景；
  • 心跳与断开重连：客户端 NettyClient 空闲时发心跳，断开后自动重连（指数退避）；服务端 AllIdleTimeout 关闭死连接；
  • 线程模型：Netty 的 IO 线程负责收发，业务执行在 Dubbo 自己的业务线程池（ThreadPoolExecutor），IO 与业务彻底隔离。

Dubbo 3 的 Triple 协议（HTTP/2 之上）同样构建在 Netty 上，把 RPC 与 HTTP 的能力合二为一。

10.2 RocketMQ 中的 Netty（RemotingServer）

RocketMQ 的通信层（rocketmq-remoting 模块）基于 Netty：

  • NettyRemotingServer / NettyRemotingClient：封装了 ServerBootstrap/Bootstrap，默认 boss 1 线程、worker 默认 CPU + 1；
  • RemotingCommand：统一协议对象，报文结构是 4字节总长 + 4字节头长 + 头(JSON/fastjson) + 体(二进制)；
  • NettyRequestProcessor：请求处理器接口，Broker/NameServer 各自注册处理器，处理器执行在 defaultExecutor 业务线程池；
  • 四种通信模式：oneway（只发不收）、sync（阻塞等待）、async（InvokeCallback 回调）、request-response（服务端主动推）——全部基于 Semaphore + Future + ChannelFutureListener 实现；
  • 心跳：ChannelEventListener 监听连接事件，空闲连接定时清理；网络断开事件触发 disconnect 回调，客户端重建 ChannelFuture 重连。

10.3 gRPC 与 Netty 的关系

gRPC 的 Java 实现（grpc-netty）直接长在 Netty 上：

  • NettyServerBuilder / NettyChannelBuilder：把 gRPC 的 Server/Channel 抽象与 Netty 的 ServerBootstrap/Bootstrap 绑定；
  • gRPC 传输层是 HTTP/2，而 Netty 内置了完整的 HTTP/2 编解码（Http2FrameCodec、Http2MultiplexCodec），gRPC 复用这套能力；
  • 序列化：proto（ProtobufEncoder/ProtobufDecoder 同款生态）+ HPACK 头压缩；
  • 官方同时提供 OkHttp transport 作为备选，但 Netty 是主力（性能、功能最全），生产环境基本都用 Netty。

所以问”gRPC 用的是什么网络框架”，答案是：HTTP/2 由 Netty 实现，gRPC 是跑在 Netty 之上的协议框架。

10.4 Elasticsearch 的 Netty4Transport

ES 的节点间通信（transport 层）和 HTTP REST 层都基于 Netty：

  • Netty4Transport：节点间 RPC，内部 NioGroup（boss 1 线程 + worker 可配）管理连接；每条消息用”长度前缀 + CRC32 校验”的帧格式（SizeHeaderFrameDecoder），破损帧直接抛异常断开；
  • Netty4HttpServerTransport：REST 层，处理 _search 等 HTTP 请求；
  • ES 的请求处理：Netty IO 线程只做协议解析，解析出的 TransportRequest 扔进 ES 自己的线程池（如 search/write/get 分池），各池独立限流——这是大型系统用 Netty 的通用模式：Netty 只当”收发器和解码器”，业务永远在自己可控的线程池里；
  • 内存管理：ES 大量使用直接内存 + 池化（Recycler 对象池），与 Netty 的 ByteBuf 池化一脉相承；
  • ES 还贡献了”压测调参”的经典方法：用 _cat/thread_pool 观察各池队列长度，队列堆积说明要扩容对应池——同样的方法论适用于所有 Netty 服务。

四个框架的共同点：IO 线程只做收发与协议解析，业务全部隔离在各自线程池；都重度依赖 LengthFieldBasedFrameDecoder 系的拆帧；都用 IdleStateHandler 心跳 + 自动重连保证长连接可用性。理解了本文第 2、3、4 节的原理，任何一个基于 Netty 的框架你都能一天上手——这就是”掌握框架底层”的价值。
