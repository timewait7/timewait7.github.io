设计模式：15 个高频模式的实战内化

Posted on 2026-08-12 In Java Word count in article: 7.6k Reading time ≈ 28 mins.

设计模式面试不考「背定义」，考三件事：一句话说出模式解决什么问题、说出 JDK/框架里的真实落点、说出你项目里怎么用的。 本文按此标准组织：15 个高频模式，每个配「动机 → 结构 → 源码落点 → 动手验证」，最后给出源码落点地图和面试答题框架。读完你能做到：面试官提任意一个高频模式，你 30 秒内答出「是什么、解决什么、哪用到、怎么用」。

联动：本文是 MyBatis 深度解析（动态代理落点）、Spring 深度解析（工厂/模板方法/观察者落点）、Netty 原理与实践（责任链落点）的「模式视角」串联篇。

1. 设计模式全景：面试怎么考

1.1 三个层次：定义、落点、应用

设计模式是在特定上下文中反复出现的问题的解决方案模板——它不是代码规则，是经验的命名。面试考察分三层：

层次 考察方式 区分度
定义层 「单例模式是什么？」 无区分度，背过就会
落点层 「JDK 里哪里用了代理模式？」 区分背书党
应用层 「你项目里哪个地方用了策略模式，为什么？」 区分有经验者

因果链：面试官问设计模式的真实目的是验证「你有没有设计意识」——能不能把变化点隔离出来。凡是回答「我记得 23 种模式的定义」的，都在第一层；能说出落点和自己项目的，才到第三层。 本文的目标是把 15 个高频模式全部推到第三层。

判断标准：不是记住 23 个名字，而是看到一段代码能认出用了什么模式，看到一个需求能选对模式——识别能力 > 记忆能力。面试官更常考的是后者（给你场景问你会怎么设计）。

1.3 学习主线：从动机出发，不从结构出发

每个模式背「结构图（UML）+ 角色名」是低效的。正确主线：

动机（解决什么问题）→ 场景（什么信号该用它）→ 落点（JDK/框架哪里在用）→ 动手（自己写一遍）

因果链：设计模式本质是「应对变化」——创建型应对「创建逻辑变化」，结构型应对「职责组合变化」，行为型应对「算法/协作变化」。面试答题说动机不说结构，是区分「懂设计」和「背图」的分水岭——因为结构可以现推，动机不能。

2. 创建型：单例、工厂方法、建造者

2.1 单例：全局唯一 + 延迟创建

动机：某些对象全系统只需要一份（配置中心、连接池、线程池、日志器）——重复创建浪费资源，且状态必须全局共享。单例解决「全局唯一」这个约束本身。

2.2 深挖：DCL 为什么必须 volatile？

new DCLSingleton() 在 JVM 里是三步：分配内存 → 调用构造器 → 把引用赋给变量。指令重排可能让第三步先于第二步——线程 A 拿到半初始化的对象引用（实例非 null 但字段是默认值），线程 B 在第一次检查就返回了这个坏对象。

flowchart LR
    A["线程 A：new 对象<br/>1.分配内存 2.构造 3.赋引用"] --> B["重排：3 先于 2"]
    B --> C["线程 B 看到 instance != null<br/>返回未构造完的对象 → 字段全默认值"]

因果链：volatile 禁止重排（JDK5 起 volatile 语义含 happens-before）→ 三步按序执行 → 线程 B 要么看到 null（继续走锁），要么看到完整对象。这个考点一次考三件事：并发、JVM 内存模型、模式——所以面试官爱问。 生产后果：不加 volatile 的 DCL 在低并发下可能永远不暴露，高并发下偶发字段全为 null/默认值的诡异 bug，极难排查。

生产建议：新代码直接用枚举或静态内部类，DCL 的价值在面试题里大于生产——这本身就是「模式的正确使用」：别用需要你手动保证正确性的写法，当有更简单更安全的等价写法时。

2.3 动手验证：多线程下验证 DCL 与 volatile

观察点：多跑几次，偶发出现 value != 42 即复现了半初始化对象（依赖 JIT 重排概率，也可能跑不出来）。判定标准：跑出问题 → volatile 机制被实证；没跑出 → 理解了「并发 bug 是概率性、压测不 bug 不等于安全」，这正是生产里此类问题的可怕之处。

2.4 工厂方法：把创建逻辑从使用方剥离

动机：当「创建哪个对象」需要运行时决定（按配置、按类型、按环境），把 new 散落在业务代码里会导致创建逻辑到处改。工厂把「选择实现类」收敛到一个地方。

源码落点：Spring 的 BeanFactory 就是工厂模式的放大版——getBean() 不看构造参数，按名字/类型返回，创建细节（单例缓存、循环依赖、AOP 代理）全部藏在内核。你天天在用工厂，只是没意识到：ApplicationContext.getBean()、ExecutorService.newFixedThreadPool()（也是工厂）、Integer.valueOf()（缓存工厂）。

因果链：工厂的核心收益是「变化点隔离」——新增一种 Logger 实现，业务代码零改动，只改工厂。这是所有设计模式共有的底层逻辑：把会变的封装起来，把不变的暴露出去。

2.5 建造者：参数多到构造器放不下

动机：对象有 5 个以上可选参数时，构造器重载爆炸、参数顺序出错难查。建造者用「链式设置 + 最后 build」解决。

落点：StringBuilder（对 String 的建造）、OkHttp/Netty 的各种 Builder、Lombok @Builder。面试对比「建造者 vs 工厂」：工厂管「创建哪类」，建造者管「创建细节多」——一个解决多态，一个解决参数多。

2.6 动手验证：三个创建型模式改造成对照

观察点：对比「改调用点」与「改工厂」的工作量差异。判定标准：能说清「新增一种支付方式，两种写法各要改几个文件」，即掌握了工厂的核心价值——变化点的位置决定维护成本。

3. 结构型：代理、装饰器、适配器、组合、外观

3.1 代理：不改变目标，包一层控制访问

动机：在不改目标类代码的前提下，给目标方法加横切逻辑（日志、鉴权、事务、延迟加载、远程调用）。代理是面试考得最深的结构型模式，因为 Spring AOP 和 MyBatis 都是它的应用。

JDK 动态代理 vs CGLIB：

对比项 JDK Proxy CGLIB
要求 目标必须有接口 无接口可用
原理 生成实现接口的代理类 生成目标类的子类
局限 无接口无法代理 final 类/方法无法代理
性能 反射调用，JDK8+ 优化后差距缩小 方法调用稍快，但生成类慢

源码落点（深度联动）：

  • Spring AOP：默认 JDK 代理，目标类无接口或配置 proxy-target-class=true 时用 CGLIB。生产后果：只对 public 方法生效、自调用（this.method()）不走代理——「@Transactional 自调用不生效」就是代理模式的经典坑；
  • MyBatis Mapper：你写的 UserMapper 接口从没实现类，MyBatis 用 JDK 代理在运行时生成实现——sqlSession.getMapper() 返回的就是代理对象，invoke 里执行 SQL 绑定；
  • 懒加载：MyBatis/ORM 的关联查询懒加载也是代理（访问属性时才查库）。

因果链：代理把「横切逻辑」从业务代码里抽走 → 业务代码只关心业务 → 框架在代理层统一处理事务/日志/权限 → 代价是「你以为调的是自己写的类，实际调的是框架生成的代理」——自调用失效、final 类不生效、内部方法不被拦截，全源于此。面试答「AOP 原理」答到这一层才算懂：不是背「JDK 动态代理 + CGLIB」，而是能说清「代理对象是运行时生成的，业务代码永远在代理之后执行」。

3.2 装饰器：增强功能，保持接口

动机：动态给对象叠加功能，且叠加顺序可变。与继承的区别是关键考点——装饰器是组合式增强，继承是编译期增强。

落点：整个 java.io 包（BufferedInputStream 装饰 FileInputStream）、Collections.synchronizedList(list)（给任意 List 加线程安全）、UnmodifiableCollection。

代理 vs 装饰器（面试高频对比题）：

对比项 代理 装饰器
目的 控制访问（事务/日志/鉴权） 增强功能（缓冲/同步/压缩）
与目标关系 同接口但语义可能变 保持接口，调用方无感
典型 Spring AOP、MyBatis Mapper IO 流、Collections 包装

一句话区分：代理说「我来替你做」，装饰器说「我帮你做得更好」——代理往往可以完全替换目标（AOP 里你只拿到代理），装饰器要求调用方知道它在装饰（IO 流必须自己组装）。

3.3 适配器：接口不匹配，翻译层接上

动机：两套接口语义相同但签名不同，适配器做翻译。经典误区：适配器和装饰器都「包一层」，但适配器改变接口（翻译），装饰器保持接口（增强）。

落点：Slf4j 是全网最伟大的适配器案例——你的代码只依赖 org.slf4j.Logger，底层可以是 logback、log4j2 或 JUL，通过 slf4j-log4j12 这类适配层无缝切换；Arrays.asList()（数组→List）、StringReader（String→Reader）、Spring HandlerAdapter（把不同 Controller 签名统一成 ModelAndView）。

因果链：适配器的价值在于「不破坏双方」——老代码不动、新代码不动，中间加一层。生产里大量「升级依赖、接口变了」的场景，第一反应应该是适配而不是改调用方。面试答「你项目里用过适配器吗」，标准答案不是背例子，而是「我们升级了 XX SDK，新版接口变了，我写了个适配层包住新版，业务侧零改动」。

3.4 组合：树形结构，叶子与容器一视同仁

动机：对象是树形结构（部门树、菜单树、文件目录、组织架构），希望调用方不用区分「叶子」和「分支」——统一操作。

落点：HashMap 的 computeIfAbsent 组合链、Swing/AWT 组件树、JSON 处理（JsonNode 的容器/叶子）、Maven 的 pom 继承聚合。

3.5 外观：给复杂子系统一个简单入口

动机：子系统一堆类（下单要调库存、优惠、支付、物流四个服务），调用方不想知道内部协作。外观提供一个高层接口。

落点：HttpURLConnection（一个类封装整个协议栈）、Facade 是秒杀系统设计的核心工具（后面系统设计篇会复用）。注意区分：外观（Facade）是对外的统一入口，门面模式（Facade）在 GoF 里就是外观；与适配器区分：适配器是「翻译」，外观是「组织」——外观内部可以任意编排子系统，调用方只看到一个方法。

3.6 动手验证：代理 + 装饰器 + 适配器三个「包一层」写在一起对比

观察点：三个都是「包一层」，区别在接口变不变、调用方知不知道。判定标准：能独立判断「同事写的这段包装代码是哪种」，即建立了模式识别能力——识别 > 记忆，是结构型模式的考察核心。

4. 行为型：策略、模板方法、观察者、责任链、迭代器、状态、命令

4.1 策略：算法可变，运行时切换

动机：同一行为有多个实现（排序算法、支付方式、限流算法、优惠计算），且运行时才决定用哪个。策略把「算法族」封装成可替换对象。这是你项目里最可能真正用过的模式。

源码落点：Comparator 就是策略接口（Collections.sort(list, comparator) 传不同策略）；ThreadPoolExecutor 的拒绝策略（AbortPolicy/DiscardPolicy/CallerRunsPolicy）；Spring 里 @Autowired List<Strategy> 按类型注入全部实现再按条件选——策略 + 工厂 + Spring 容器三件套是生产标准写法。

与状态模式的对比（高频易混）：策略模式调用方决定用哪个算法（外部切换）；状态模式对象自身状态决定行为（内部切换，调用方无感）。一句话：策略是「替它选」，状态是「它自己变」。

4.2 模板方法：骨架固定，步骤可替换

动机：流程骨架不变（准备 → 执行 → 收尾），但某些步骤的实现各不相同。父类定义骨架，子类覆写步骤。

源码落点（深度联动）：

  • AQS（AbstractQueuedSynchronizer）：acquire() 骨架固定（尝试获取 → 失败入队 → 阻塞），tryAcquire() 留给子类——ReentrantLock/Semaphore/CountDownLatch 都是实现不同 tryAcquire 的「同一骨架不同步骤」；
  • Spring JdbcTemplate：execute() 骨架（拿连接 → 执行 → 释放），doInStatement 留钩子；
  • HttpServlet：service() 分发骨架，doGet/doPost 留给子类——你写的每个 Controller/ Servlet 都是模板方法的子类。

因果链：模板方法把「不变的流程」上提到父类 → 子类只写变化点 → 生产后果是：流程改动只改骨架一处，所有子类自动生效（比如给所有流程加埋点，改父类 run() 即可）。面试对比「模板方法 vs 策略」：模板方法变的是步骤，策略变的是整个算法。

4.3 观察者：状态变化，通知订阅者

动机：一个对象状态变了，一群对象需要跟着变（价格变了刷新界面、订单创建发通知），又不想让双方互相依赖。观察者解耦「发布者」和「订阅者」。

源码落点：Spring 事件机制（ApplicationEventPublisher + @EventListener）就是观察者——发布方 publishEvent，监听方无感知耦合；Swing/AWT 的事件监听；java.util.Observer（已废弃）；Redis 的订阅发布；MQ 是观察者的分布式版——一个订单事件，多套系统订阅消费。

因果链：观察者的收益是「新增订阅者零侵入」——加一个下单后发短信的组件，只新增一个监听器，OrderPublisher 一行不改。代价是流程不可见：主流程变成「发事件 → 不知道谁在听」→ 排查问题时不能只看调用链，要全搜监听器。面试深挖：「事件驱动架构和观察者模式什么关系？」——观察者是单机版事件驱动，MQ 是跨进程版，同一思想的放大。

4.4 责任链：请求沿链传递，每个节点决定处理或放行

动机：一个请求要被多个处理器按顺序处理（鉴权 → 限流 → 业务），或任一节点可终止（审批流）。责任链把处理器串成链，每个节点「处理 or 传给下一个」。

源码落点（深度联动）：

  • Servlet Filter 链：doFilter 放行即传下一个——你写的每个过滤器都在责任链上；
  • Netty Pipeline：ChannelHandler 串成链，读入站、写出站——Netty 整个架构就是责任链的实现；
  • MyBatis 插件：Interceptor 链包裹四大对象；
  • Spring MVC HandlerInterceptor：preHandle 返回 false 即终止。

因果链：责任链的收益是「加处理器不改链」——新增一个日志节点，只 new 一个类并插进组装处。代价是顺序敏感：链顺序错了，行为就错了（鉴权必须在业务前）→ 生产里责任链的顺序通常写成配置/常量，而不是散落代码里。面试答「Filter vs Interceptor vs AOP 区别」时，责任链是共同底层的组织方式。

4.5 迭代器：遍历与容器解耦

动机：容器内部结构（数组、链表、树）各不相同，调用方希望统一遍历方式。迭代器提供统一接口，容器隐藏结构。

落点：java.util.Iterator（所有 Collection 的遍历）、for-each 语法糖底层就是迭代器、MyBatis 的游标分页（Cursor）。

面试点：for-each 遍历时删除元素为什么抛 ConcurrentModificationException？ —— ArrayList 的迭代器维护 expectedModCount，remove() 直接改 modCount，迭代器 next() 时校验不一致即抛异常。因果链：这是迭代器模式的「契约」——迭代器假定容器在遍历期间不被结构修改，违反契约就用异常提醒。用 iterator.remove() 或 CopyOnWriteArrayList 是正解。

4.6 状态模式：行为随状态切换

动机：对象行为取决于内部状态（订单：待支付 → 已支付 → 已发货 → 已完成），状态多了 if-else 爆炸。状态模式把每个状态的行为封装成独立类。

面试对比：状态 vs 策略（§4.1 已述）；状态 vs if-else（状态模式是 if-else 的面向对象替代，状态多且迁移规则复杂时用）。

4.7 命令：请求封装成对象，可排队可回滚

动机：把「做什么」（命令对象）与「谁来做」（执行者）分离，支持排队、撤销、日志。落点：Runnable/Callable（把任务封装成对象交给线程池）、Spring @Async、数据库事务本身（undo log 就是命令模式的回滚思想）。

4.8 动手验证：用责任链重构一个「入职流程」

观察点：对比「新增一个『背调』环节」时两版的改动范围。判定标准：能说出「if-else 版改主流程方法体，责任链版新增一个类 + 改组装行」，即掌握了责任链的本质——流程变化与流程定义分离。

MySQL 事务原理与实践

Posted on 2026-08-12 In 数据存储 Word count in article: 5.5k Reading time ≈ 20 mins.

事务（Transaction）是一组数据库操作的最小执行单元：要么全部提交生效，要么全部回滚，不允许只执行一半。它解决的是「多步操作的一致性」问题——转账时扣钱成功、加钱失败，账就对不上了。

本文把事务拆成三层讲：目标（ACID）、机制（隔离级别、MVCC、行锁）、实战（事务边界控制、死锁排查、Spring 事务的坑）。基础概念在《MySQL 原理与优化》第 5 章有概览，本篇每个概念都展开到「可复现的实验」和「真实项目里的坑」。读完你应能自己复现三种并发问题、看懂死锁报告、修掉 Spring 事务失效。

1. 事务是什么：ACID 与它的实现机制

1.1 ACID 四特性：目标与实现机制（面试核心考点）

特性 一句话定义 靠什么实现 损坏的后果
原子性（Atomicity） 一组操作要么全成功、要么全回滚 undo log 转账只扣了钱，账目错乱
一致性（Consistency） 事务前后数据满足完整性约束 应用代码 + 数据库约束 余额为负、外键断裂
隔离性（Isolation） 事务之间互不可见、互不干扰 锁 + MVCC 并发读写出错
持久性（Durability） 提交后修改永久保存，崩溃不丢 redo log（WAL） 提交了的数据丢失

一致性是目标，其余三个是实现手段——原子性、隔离性、持久性都是为了最终保证「数据始终一致」。面试答到这一层比背定义得分高。

1.2 只有 InnoDB 支持事务

事务是存储引擎层的能力，不是 Server 层的。

引擎 事务 行锁 崩溃恢复
InnoDB 支持 支持 redo log 重放
MyISAM 不支持 仅表锁 无，重启可能丢数据

业务表必须用 InnoDB。MyISAM 下 START TRANSACTION 照写不报错，但两条 UPDATE 之间插电重启，第一条照样生效——回滚根本不存在。

2. 事务的控制方式：autocommit 与隐式提交陷阱

2.1 autocommit 与显式事务

MySQL 默认 autocommit = 1：每条 DML 语句自动开启并提交一个事务。所以「MySQL 怎么开事务」的答案分两种：

方式 写法 适用场景
自动提交 什么都不写，每条 DML 独立成事务 单条 INSERT/UPDATE
显式事务 START TRANSACTION / BEGIN，最后 COMMIT / ROLLBACK 多步操作必须原子

START TRANSACTION 本身有个隐藏行为：执行它会先隐式提交当前事务（见 2.3），所以显式事务前别带着上一个未提交的事务。

2.2 JDBC 手写一个转账事务

对照 Java 的思维：commit/rollback 就像方法返回值和异常——commit 是正常返回，rollback 是异常兜底。事务边界必须包住所有需要原子的步骤，多包一个远程调用就是多锁一秒。

2.3 隐式提交陷阱：哪些语句会偷偷提交事务（实战重点）

以下语句执行前，MySQL 会先隐式提交当前事务，然后才执行语句本身：

语句类别 具体例子
DDL CREATE / ALTER / DROP / TRUNCATE / RENAME
权限与账号 GRANT / REVOKE / SET PASSWORD
表与数据管理 LOCK TABLES / UNLOCK TABLES / LOAD DATA
其他 START TRANSACTION 本身、FLUSH、ANALYZE TABLE

实际踩过的坑：事务里先 UPDATE 了一批数据，中途执行 CREATE INDEX（DDL），前面的 UPDATE 已经被悄悄提交。后续逻辑抛异常回滚，只回滚了索引之后的变更，数据只改了一半。

口诀：事务里只放 DML 和 SELECT，DDL 是隐式提交的雷。

2.4 回滚也是有成本的

回滚靠 undo log 实现，不是「把数据原样恢复」这么便宜：

  • insert undo log：插入产生的，事务提交后立刻删除；
  • update undo log：更新/删除产生的，还要给其他事务做快照读，事务提交后不能马上删，由后台 purge 线程在确认没有事务再用时才清理。

所以「回滚一个 100 万行的 UPDATE」实际要反向执行 100 万次补偿，还要让出 purge 空间——大事务的回滚和提交一样慢。这也是长事务危害的根源之一（见 8.1）。

3. 隔离级别：从定义到亲手复现

3.1 三个并发问题（面试核心考点）

并发问题 英文 现象 一句话记忆
脏读 Dirty Read 读到其他事务尚未提交的修改 读到了不存在的未来
不可重复读 Non-Repeatable Read 同一查询两次结果，同一行内容变了 同行被改，两次读不一致
幻读 Phantom Read 同一查询两次结果，行数变了 多了或少了行

注意区分不可重复读和幻读的考察点：前者是同一条记录被改，后者是结果集增删行。面试常考这个区分。

3.2 四级隔离级别

隔离级别 脏读 不可重复读 幻读 特点
read uncommitted 可能 可能 可能 不隔离，几乎不用
read committed 不可能 可能 可能 每个 SQL 一个快照
repeatable read 不可能 不可能 基本杜绝 MySQL 默认
serializable 不可能 不可能 不可能 所有读变当前读，并发最低

口诀：隔离级别从低到高，防的问题从少到多，并发度从高到低。

延伸考点：为什么 MySQL 默认 RR，而 Oracle 默认 RC？历史原因是主从复制基于 binlog 的 statement 格式，RC 下并发写顺序可能与 binlog 记录不一致，导致主从不一致；RR 靠间隙锁保证写顺序稳定。现在 binlog 默认 row 格式，理论上可切 RC（不少大厂为并发切到 RC）——面试答出「历史原因 + row 格式下可切」就是满分。

4. MVCC 原理：版本链 + ReadView

4.1 MVCC 定义

MVCC（Multi-Version Concurrency Control，多版本并发控制）让「读」不阻塞「写」、「写」不阻塞「读」——读写互不等待。做法：修改数据时不覆盖旧值，而是写入新版本，读事务从版本链里挑一个对自己可见的版本。

对照 Java 思维：类似 CopyOnWriteArrayList——写线程改到新副本，读线程永远拿到一份稳定快照。快照读（普通 SELECT）因此不加锁，这是 MySQL 高并发读的根基。

4.2 隐藏列与 undo log 版本链

InnoDB 给每行记录额外维护三个隐藏列：

隐藏列 作用
DB_ROW_ID 表没有主键时生成的自增 id（有主键则用主键定位）
DB_TRX_ID 最近一次修改该行的事务 id
DB_ROLL_PTR 指向 undo log 中上一版本的回滚指针

每次 UPDATE 不直接覆盖：旧值写进 undo log，行的 DB_TRX_ID 更新为当前事务，DB_ROLL_PTR 指向旧版本，于是同一行存在多个历史版本，串成一条链：

flowchart LR
    V3["V3: trx=60, balance=800"] --> V2["V2: trx=40, balance=900"]
    V2 --> V1["V1: trx=30, balance=1000"]
    V1 --> N1["NULL"]

版本链头部（V3）是最新版本。任何事务做快照读，都从头部开始沿链找「对自己可见」的版本——判断标准就是 ReadView。

4.3 ReadView：谁能看到哪个版本（面试核心考点）

事务做快照读时生成一个 ReadView（读视图），记录生成时刻的并发状态：

字段 含义
creator_trx_id 创建 ReadView 的事务 id
m_ids 生成时刻所有活跃（未提交）事务 id 列表
min_trx_id 活跃事务中的最小 id
max_trx_id 下一个要分配的事务 id（即当前最大 id + 1）

可见性判断对版本链上的每个版本依次进行：

flowchart TD
    A["Snapshot read creates ReadView"] --> B["Check version chain head's trx_id"]
    B --> C{"trx_id < min_trx_id ?"}
    C -- "Yes" --> V1["Visible: committed before this view"]
    C -- "No" --> D{"trx_id >= max_trx_id ?"}
    D -- "Yes" --> I1["Invisible: created after this view"]
    D -- "No" --> E{"trx_id in m_ids (still active) ?"}
    E -- "Yes" --> I2["Invisible: uncommitted"]
    E -- "No" --> V2["Visible: committed between min and max"]
    I1 --> F{"Previous version exists ?"}
    I2 --> F
    F -- "Yes" --> B
    F -- "No" --> N1["Not visible / record not exists"]

一句话概括规则：事务开始时还没提交的版本不可见，已经提交的版本可见。找不到可见版本就沿 DB_ROLL_PTR 往旧版本走，走到链尾都没有则这条记录对该事务「不存在」。

4.4 RC 与 RR 的差别只有一句话

隔离级别 ReadView 生成时机 效果
read committed 每次 SELECT 都新建 能看到两次 SELECT 之间新提交的版本 → 不可重复读
repeatable read 事务中第一次 SELECT 时创建，之后复用 整个事务看同一份快照 → 不可重复读被解决

一句话串起 MVCC：undo log 提供多版本，ReadView 决定哪些版本可见，锁兜底当前读（下一章）。RC 与 RR 的差别只是 ReadView 的生成时机——这一句话就够答大部分 MVCC 面试题。

5. 当前读与行锁：幻读为什么被消除

5.1 快照读 vs 当前读

MVCC 只管快照读；要改数据、要拿最新值，就得走当前读。

特性 快照读（一致性非锁定读） 当前读
读的数据 历史快照版本 最新已提交版本
加锁 不加锁 加锁（共享锁 / 排他锁）
并发性 高，读写互不阻塞 低，可能阻塞
触发语句 普通 SELECT SELECT ... FOR UPDATE、UPDATE、DELETE、INSERT

5.2 三种行锁：记录锁、间隙锁、临键锁

锁 锁定的范围 说明
记录锁（Record Lock） 单条索引记录 最基础的行锁
间隙锁（Gap Lock） 开区间 (a, b) 锁住「记录之间的空隙」，防插入
临键锁（Next-Key Lock） 左开右闭 (a, b] 记录锁 + 间隙锁的组合，RR 级别当前读的默认锁

两个前提必须记住：行锁是加在索引记录上的，WHERE 条件没走索引时锁会退化成表级（所有记录都锁）；间隙锁只在 RR 级别下生效，RC 级别没有间隙锁。

5.3 临键锁如何挡住幻读

回到 3.5 的场景：如果 A 先做当前读（FOR UPDATE），InnoDB 会锁住命中的记录和两侧的间隙，B 的新行根本插不进来：

sequenceDiagram
    participant A as Transaction A (RR)
    participant B as Transaction B
    participant I as InnoDB
    A->>I: SELECT * FROM t WHERE id >= 20 FOR UPDATE
    I-->>A: Locks rows 20,30 + gaps (20,30) (30,+inf)
    B->>I: INSERT INTO t VALUES (25)
    I-->>B: Blocked: waiting for gap lock
    Note over A: COMMIT
    I-->>B: Gap lock released, INSERT continues

所以 InnoDB 的 RR 下：快照读靠 MVCC 看不到新行，当前读靠临键锁插不进新行——两个方向都堵死了，标准意义上的幻读被消除。这也是为什么 MySQL 敢把 RR 设为默认级别。

5.4 残留幻读：什么时候还能发生

3.5 的实验就是残留场景，成因梳理：

场景 走什么路径 结果
先快照读，再快照读 复用同一个 ReadView 一致，不幻读
先当前读，再插入 间隙锁把口堵死 不幻读
先快照读，后当前读 当前读不看 ReadView，读最新已提交 幻读残留

残留幻读一句话：只有「先快照读、后当前读」的混合边界才看得到新行。生产代码里同一事务内先 SELECT 再 FOR UPDATE 的场景（典型的「查询-再更新」逻辑）要留意这一点。

6. 死锁：成因、复现与排查（实战重点）

6.1 死锁的产生条件

死锁（Deadlock）指两个以上事务互相持有对方需要的锁，谁也不放手。产生需要同时满足四个条件：

条件 含义
互斥 同一资源同时只能被一个事务持有
持有并等待 拿着自己的锁，还等别人的锁
不可剥夺 锁只能由持有者主动释放
循环等待 A 等 B、B 等 A，形成环

InnoDB 默认开启死锁检测（innodb_deadlock_detect = ON），检测到环后主动回滚一个事务（通常回滚 undo log 量小的一方），报错 ERROR 1213 (40001)；没开检测则等 innodb_lock_wait_timeout（默认 50 秒）超时。

7.1 长事务的危害

危害 机制
阻塞并发 行锁/间隙锁持有过久，其他事务排队等锁，甚至等满 innodb_lock_wait_timeout

7.5 事务与连接池

一个事务从开启到提交始终独占一个连接，理解这一点能解释很多现象：

  • @Transactional 方法进入时从池里拿连接，方法返回才归还——方法里调外部 RPC，等于把连接锁住等网络；
  • REQUIRES_NEW 需要第二个连接，池子只剩一个空闲时会发生「自己等自己」的连接饥饿；
  • 只读方法别挂事务，挂事务白占一个连接和一份锁。

事务编程口诀：边界最小化、传播要匹配、异常要抛出、连接要短占。

8. 总结与避坑清单

8.1 本文收获

  • 目标：ACID 四个特性中一致性是目标，原子性/隔离性/持久性是实现手段，分别依赖 undo log、锁 + MVCC、redo log；
  • 机制：隔离级别决定 ReadView 的生成时机（RC 每次 SELECT 新建、RR 事务首次 SELECT 创建后复用）；undo log 版本链 + ReadView 构成 MVCC；快照读不加锁，当前读靠临键锁，两者配合让 RR 基本杜绝幻读，但「先快照读后当前读」的混合场景有残留；
  • 实战：隐式提交语句、长事务、死锁、@Transactional 失效——每一条都对应真实生产事故，建议对照 8.2 清单自查。

8.2 避坑清单

场景 建议做法 理由
转账等多步写 显式事务，提交/回滚放在 try-catch 两端 原子性
事务内查询 能快照读就普通 SELECT，需要最新才 FOR UPDATE 少拿锁
大批量更新 分批提交（每批几百到几千条） 避免长事务

DDL 永远不要在业务事务中间执行 隐式提交

最后一句：事务不是「加个注解就行」的黑盒——隔离级别决定你看到什么，锁决定别人能不能改，边界决定你占资源多久。把这三层想清楚，事务相关的面试题和线上事故都能少一半。

Redis 缓存淘汰策略解析

Posted on 2026-08-12 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

内存淘汰（memory eviction） 是 Redis 在内存写满时，按配置的策略删除一部分 key 来腾出空间的机制。它是缓存场景的最后一层保险：不配置，Redis 会被系统 OOM Killer 直接杀进程。本文讲透三件事：maxmemory 怎么配、8 种策略怎么选、近似 LRU 和 LFU 的实现差异在哪。

1. 为什么内存必须设上限

1.1 maxmemory：Redis 的内存天花板

Redis 是一个基于内存的键值数据库，数据主要放在内存里，读写是微秒到亚毫秒级。内存是稀缺资源，所以必须给 Redis 划一条内存上限（maxmemory），超过上限后的写入会触发内存淘汰（memory eviction）——按策略删除一部分 key，腾出空间继续写入。

不设 maxmemory 的后果：Redis 吃满机器内存后，OS 的 OOM Killer 会直接 kill 掉 redis-server 进程（类比 Java 应用 -Xmx 设太大、堆外内存失控被容器 OOM kill），主从全部挂掉，未落盘数据全部丢失。生产环境这是第一优先级配置。

类比 Java 应用 Redis
内存上限 -Xmx / 容器 limit maxmemory
超限行为 抛 OOM 异常（可捕获） 按策略淘汰 key，或拒绝写入
失控后果 被容器 OOM kill 被系统 OOM Killer 杀进程

3. 八种淘汰策略全景

3.1 速查表（面试核心考点）

策略 作用范围 淘汰依据 引入版本 典型场景
noeviction 全部 key 不淘汰，写满报错 一直 队列、计数器等写失败可重试
allkeys-lru 全部 key 最近最少使用 一直 通用缓存，最常用
volatile-lru 带 TTL 的 key 最近最少使用 一直 缓存带过期 + 少量长驻 key
allkeys-random 全部 key 随机 一直 key 可重建、淘汰成本均等

volatile-ttl 带 TTL 的 key 剩余 TTL 最短 一直 数据有明确时效
allkeys-lfu 全部 key 访问频次最低 4.0 长尾热点
volatile-lfu 带 TTL 的 key 访问频次最低 4.0 带 TTL 的长尾热点

命名规律：前缀 allkeys- 管全部 key，volatile- 只管带过期时间的 key；后缀 -lru 看最近访问、-lfu 看访问频次、-random 随机、-ttl 看剩余寿命。

3.2 volatile-* 的隐藏降级

volatile-* 系列有个大坑：如果带 TTL 的 key 一个都没有（或没有可淘汰的），行为退化成 noeviction——写满直接报错。

真实场景：某天排查发现缓存全部写不进去，配置明明是 volatile-lru，查下来是业务方刚把 key 的 TTL 全去掉了。结果整个 Redis 变只读，线上炸了才反应过来。

口诀：volatile 系列依赖 TTL，TTL 没设，策略就失效。

3.3 allkeys 与 volatile 怎么选

核心区别一句话：allkeys- 保护的是”内存不超限”，volatile- 保护的是”带 TTL 的 key 优先存活”**。如果缓存数据和不过期数据混用同一个实例（比如有人把配置、统计也塞 Redis），必须用 volatile-*，否则淘汰可能把不该删的业务数据删掉。

4. 近似 LRU：用采样换精度

4.1 为什么不做严格 LRU

严格 LRU 需要维护双向链表，每次访问把节点移到队首，每个 key 额外占两个指针的开销。Redis 的 key 数量以百万计，这个成本不可接受；链表在 RDB 持久化、主从复制时也会引入额外复杂度。所以 Redis 选择近似 LRU（approximate LRU）：只记录”上次访问时间”，淘汰时抽样比较。

4.2 数据结构：RedisObject 的 24bit 时钟

每个 value 对象（RedisObject）里有一个 24bit 的 lru 字段：

  • LRU 模式：存上次访问时间（秒级时钟 LRU_CLOCK，约 194 天轮回一次）。
  • LFU 模式：拆成 16bit 时间 + 8bit 频次计数器（第 5 节讲）。

每次 key 被访问（GET/SET 等），lru 字段刷新为当前时钟。

4.3 淘汰算法：采样取最老

  1. 从键空间随机取 N 个 key（N = maxmemory-samples，默认 5）。

采样数越大越接近严格 LRU，但每次淘汰的 CPU 成本越高。Redis 5.0 起引入淘汰池（eviction pool）：上一轮采样过的候选 key 保留在池中，下一轮优先从池里挑，跨轮次累积样本，近似精度进一步提升（6.0 对池大小做了动态调整）。

5. LFU：频次才是真相

5.1 LRU 的致命场景

LRU 只看”最近访问”，不看”访问了多少次”。一次突发热点（秒杀、新闻爆点）就能让一批 key 变成”最近访问”，随后把真正长期高热的 key 挤掉——等热点过去，缓存里全是没人再看的 key。

这个痛点 Java 开发者也不陌生：Caffeine 的 W-TinyLFU 淘汰算法就是针对 LRU 对”长尾热点”命中率差才诞生的，思路同源。

5.2 同一个字段，两种读法

Redis 4.0 起，LFU 模式下 24bit 的 lru 字段被拆成两部分：

位段 名称 含义
高 16bit ldt（last decrement time） 上次衰减时间的分钟级时钟
低 8bit logc（logistic counter） 对数计数器，0~255

8bit 只能记 255 次访问，不够用，所以用对数计数器（logistic counter）：访问次数越多，计数器增长越慢——用概率递增代替每次访问 +1。

6.1 决策表

选型口诀：没把握就 allkeys-lru；有长尾热点换 allkeys-lfu；混用持久数据必须 volatile。

6.2 三个真实场景

  • 登录 token（TTL 短、无差别）：volatile-random 即可，谁被淘汰无所谓，反正过期快。
  • 电商秒杀（短时突发热点）：用 allkeys-lru。LFU 会把秒杀 key 的计数器顶到高位，热点过后长期霸占缓存，反而有害。
  • 用户画像/推荐位（长期频次差异大）：allkeys-lfu，避免一波流量把常驻热 key 挤掉。

6.3 验证：用数据说话

上线后观察两天：evicted_keys 平稳且被淘汰的都是冷 key，说明策略选对了；如果出现热 key 被淘汰（业务告警）或 evicted_keys 陡增，先扩 maxmemory，再考虑换策略。

6.4 避坑清单（面试也常问）

症状 原因 处理
缓存写满后大量写入报 OOM 策略是 noeviction，或 volatile-* 但 key 没带 TTL 换成 allkeys-lru，或给 key 补 TTL
突发流量后热 key 命中率骤降 LRU 被”一波流”污染 评估换 allkeys-lfu
写入延迟毛刺明显 每次写前都要先淘汰，可能多轮采样删除 提高 maxmemory 余量，或写操作错峰
主从行为不一致 淘汰只在主节点触发 正常现象，从库同步主库数据；不要只在从库配不同策略
内存碎片率长期偏高 频繁淘汰 + 大 key 释放 开启 activedefrag，或检查内存分配策略

7. 总结与实操建议

三个收获：淘汰只发生在写路径、volatile-* 依赖 TTL 且可能静默降级、LRU 看”最近” LFU 看”频次”，两者的实现都是近似方案（采样 + 概率计数）。

实操建议按优先级：

  1. **先设 maxmemory**，这是 Redis 生产环境的第一道保险，没有上限，策略都是空谈。
  2. 默认 allkeys-lru 起步，出问题再换，不要一上来就 LFU——LFU 有 lfu-log-factor 和 lfu-decay-time 两个参数要调。
  3. **缓存与存储数据混用的实例必须用 volatile-***。
  4. 上线后盯 evicted_keys 和命中率，策略选对的标准是”被淘汰的都是冷 key”。

MySQL 索引原理与实践

Posted on 2026-08-11 In 后端开发 , 数据存储 , MySQL Word count in article: 7.5k Reading time ≈ 27 mins.

本文是《MySQL 原理与优化》的索引专题深挖篇，把该文第 2 章”索引”展开成完整知识体系：B+ 树的底层结构为什么长这样、聚簇索引与非聚簇索引的本质区别、以及日常建索引时真正管用的实践要点。索引是 MySQL 面试的必考区，也是 1-3 年 Java 后端从”会写 SQL”到”会优化 SQL”的分水岭——多表 join 能写出来是基本功，慢 SQL 能自己建索引治好才是进阶。

本文按”为什么需要索引 → B+ 树底层结构 → 聚簇与非聚簇 → 联合索引与最左前缀 → EXPLAIN 与索引失效 → 建索引实践”六章组织，每章末尾给结论，第 7 章是高频面试速答。全文默认讨论 InnoDB 引擎 + MySQL 5.7/8.0。

1. 为什么需要索引

1.1 没有索引的查询：全表扫描

MySQL 的数据以页为单位存在磁盘上（默认 16 KB/页，innodb_page_size）。一张 1000 万行的表，数据占几千个页。没有索引时，查询只能从第一页扫到最后一页，逐行判断条件——这就是全表扫描，复杂度 O(n)，一次查询就是几千次磁盘 IO。

几个关键数字，记住它们才能理解索引的价值：

存储/操作 延迟量级
内存访问 约 100 ns
SSD 随机读 约 0.1 ms
HDD 随机读 约 10 ms
一次磁盘 IO（读一页） 机械盘毫秒级，SSD 亚毫秒级

一次全表扫描 = 数千次这样的随机 IO。而索引的目标，是把”扫几千页”变成”读 2~3 个页”。

1.2 索引的本质：一张有序的”目录”

索引本质上是一份独立于表数据、按键排序的目录结构，类似新华字典的拼音检字表：

  • 没有检字表：从第 1 页翻到第 900 页找”栈”字；
  • 有检字表：先定位”zhan”在拼音表的哪个区间，再翻到对应正文页。

数据库索引同理：先在索引里用二分查找定位到目标键，再顺着指针拿到数据所在页。查找次数从 O(n) 降到 O(log n)，而且是页级的 log n——这正是 B+ 树多叉设计的用武之地（见第 2 章）。

当然索引不是免费的午餐，它有两个代价：

  • 空间：每个索引都是一份额外的有序结构，占用磁盘与 Buffer Pool 内存；
  • 写放大：每次 INSERT/UPDATE/DELETE 都要同步维护索引，索引越多，写入越慢（详见 6.3）。

1.3 为什么偏偏是 B+ 树

工程师拿到”有序目录”的需求，天然会想到几类候选结构。逐一排除：

候选结构 等值查找 范围查询 磁盘友好度 结论
哈希表 O(1)，最快 不支持（无序） 一般 InnoDB 仅在内存中用自适应哈希索引加速热点页，不做持久化索引
二叉查找树/AVL/红黑树 O(log n) 需要中序遍历 差 树高 log₂n，10 亿数据约 30 层 = 30 次磁盘 IO；且平衡调整频繁
B 树 O(log n) 需要回溯父节点 中 所有节点都存数据，单页装下的键少，树偏高（对比见 2.5）
跳表 O(log n) 好（内存中） 差 链式结构对磁盘页对齐不友好，Redis 的 ZSet 用在内存场景
B+ 树 O(log n) 好（叶子链表顺序扫） 最好 InnoDB 的选择

结论：等值、范围、磁盘 IO、写入稳定性四者权衡下来，B+ 树是磁盘数据库索引的最优解。为什么这么说，第 2 章把它的底层结构拆开看。

2. B+ 树索引的底层结构

2.1 先理解磁盘 IO 模型：页、树高、IO 次数

InnoDB 的索引和数据都以页为单位读写，一次磁盘 IO 至少读一个页。所以一次索引查找的磁盘 IO 次数 ≈ 树的层数。层数就是 B+ 树的设计核心：把树做得越矮，查询就越快。

B+ 树的层数由”每个页能装多少键”决定，这个数字叫分支因子。以 8 字节的 BIGINT 主键 + 6 字节页指针为例，一条索引记录约 14 字节：

也就是说，一个非叶子页能带 1170 个孩子。树的容量是几何级数增长的：

层数 可支撑数据量（按叶子页 15 行/页估算） 实际 IO 次数
2 层 1170 × 15 ≈ 1.7 万行 1 次
3 层 1170 × 1170 × 15 ≈ 2000 万行 2 次
4 层 百亿行 3 次

注意 IO 次数比层数少 1：根页常驻 Buffer Pool 内存，不需要读磁盘。所以 1000 万行的表按主键查，真实磁盘 IO 只要 2 次。这就是”3 层 B+ 树支撑千万级数据”这句话的来历。

2.2 B+ 树长什么样

两个核心设计：

  • 内部节点只存键 + 指针。一个页能装下 1170 个键，整棵树被压得很矮——这是 B+ 树 vs B 树最大的区别（2.5 详述）；
  • 所有数据都在叶子节点，叶子之间用链表串联。范围查询找到起点后，沿链表顺序往下读即可，天然支持顺序扫描。

2.3 页内二分查找

B+ 树的查找分两个阶段：沿树逐层下探（每次读一页），在页内二分查找（内存操作）。

2.4 插入与页分裂

B+ 树的插入规则很简单：找到应插入的叶子页，放进去；页满了就分裂成两页，并把新的最小键上提到父节点（父节点可能继续分裂，向上递归）。

页分裂的代价很大——要写两个新页、改父节点，可能连锁向上分裂。所以插入顺序直接决定索引的健康度：

  • 顺序插入（自增主键）：永远追加在最右叶子页，只有这一个页反复分裂，代价最小，叶子页空间利用率接近 100%；
  • 乱序插入（UUID 主键）：随机落在任意页，页频繁分裂，分裂后两页都只装一半数据——空间利用率跌到约 50%，索引膨胀一倍，还会产生大量碎片。

这一条直接导出了第 3 章的结论：主键不要用 UUID。

2.5 B+ 树 vs B 树：好在哪里

对比维度 B 树 B+ 树 对磁盘数据库意味着什么
数据存储位置 所有节点都存数据 只有叶子节点存数据 B+ 树单页能装更多键，树更矮，IO 更少
单页键容量 少（每条记录 14B+行数据） 多（纯键 + 指针） 同样 2000 万行，B 树要多 1~2 层
范围查询 要回溯父节点、中序遍历 叶子链表顺序扫描 id > 100 的效率高一个量级
全表扫描 需要遍历整棵树 直接扫叶子链表，近似顺序读 顺序 IO 比随机 IO 快几个数量级
写放大 中间节点存数据，更新频繁 内部节点纯指针，结构稳定 支持更高并发写入

本节小结：B+ 树用”非叶子纯索引 → 高分支因子 → 矮树”换来更少的磁盘 IO；用”叶子链表”换来高效的范围查询和顺序读。这两个特性叠加，就是 InnoDB 把它选为默认索引结构的全部理由。

3. 聚簇索引与非聚簇索引

3.1 聚簇索引：数据就是索引

聚簇索引（Clustered Index，InnoDB 中即主键索引）的叶子节点直接存完整行数据。也就是说，InnoDB 的表数据本身就是一棵 B+ 树——数据物理上按键有序组织，这叫索引组织表（Index-Organized Table）。

每个表只能有一个聚簇索引，由 InnoDB 按以下优先级自动决定：

  1. 显式定义的主键；
  2. 如果没有主键，取第一个非空 UNIQUE 索引；
  3. 都没有，InnoDB 自动生成一个隐藏的 6 字节 ROWID 作为聚簇索引（表结构设计缺陷，见 3.5）。

聚簇索引叶子页里除了业务列，还藏着 InnoDB 的隐藏列（trx_id 事务 ID、roll_pointer 回滚指针），MVCC 的版本链就挂在它们上面——这是《MySQL 原理与优化》事务章节的内容，此处不展开。

3.2 非聚簇索引（二级索引）：列值 + 主键

二级索引（Secondary Index，又称非聚簇索引/辅助索引）的叶子节点只存两样东西：索引列的值 + 主键值。

一个关键细节（面试常考）：InnoDB 二级索引叶子存的是主键值，而不是行指针（MyISAM 的索引叶子存的是行指针/文件偏移）。为什么？因为聚簇索引里数据页分裂、移动是常态，如果二级索引存指针，每次数据挪动都要回写所有二级索引；而主键值永远不变。代价是：主键越长，每个二级索引越大——这是 3.5 主键要短的核心原因。

一张表可以建多个二级索引，它们与数据的物理顺序无关，各自独立。

3.3 两种索引对比

维度 聚簇索引（主键索引） 二级索引（非聚簇索引）
叶子节点内容 完整行数据 索引列值 + 主键值
每表数量 只能有 1 个 可以有多个
与数据关系 数据即索引，物理顺序 = 主键序 独立结构，与物理顺序无关
查找路径 命中叶子即拿到整行 命中叶子只拿到主键，可能需要回表
创建方式 主键自动生成 CREATE INDEX 显式创建
主键值变化 — 所有二级索引需要跟着改

3.4 回表与覆盖索引

回表是这两个概念之间的”差价”，一句话定义：二级索引只存”列值 + 主键”，当查询需要的字段不在索引里时，只能拿主键再到聚簇索引查一遍完整行，这次”回头”就是回表。

每次回表都是一次聚簇索引查找（约 1~2 次磁盘 IO）。如果命中了 100 行，就是 100 次回表——这就是大范围查询慢的真相。

3.5 主键怎么选：自增 vs UUID vs 业务主键

结合 2.4 的页分裂和 3.2 的”叶子存主键”，主键选择可以一次性推出来：

候选 插入顺序性 索引膨胀 结论
BIGINT 自增 顺序插入，无页分裂 8 字节，二级索引最小 首选
雪花 ID（BIGINT） 基本有序，可接受 8 字节 分布式场景首选
UUID（36 字符串/16B binary） 完全乱序，页分裂频繁，碎片多 大，且乱序会加剧膨胀 避免
业务主键（如 18 位身份证号） 视业务而定 长字符串，所有二级索引跟着变大 避免，用唯一索引约束替代

实践结论：

  • 主键用无业务含义的 BIGINT 自增（单机）或雪花 ID（分布式），一列定生死：乱序、过长都是慢性病，上线后很难改；
  • 业务上的唯一性（身份证号、手机号、订单号）用 UNIQUE 索引约束，而不是塞进主键；
  • 主键与唯一索引的语义区别：主键不能为 NULL，唯一索引允许 NULL（且多个 NULL 不冲突）。

本节小结：聚簇索引 = 整张表的数据本体；二级索引 = “索引列 + 主键”的副本。两者之间的差价是回表，覆盖索引是抹平差价的手段；而主键的选择（顺序、长度）决定所有二级索引的生死。

4. 联合索引与最左前缀

4.1 联合索引的内部排序

联合索引 (a, b, c) 底层就是一棵 B+ 树，只是排序规则变成了先按 a 排，a 相同再按 b 排，b 相同再按 c 排：

这个”字典序”就是最左前缀原则的全部来源：索引能用来定位的条件，必须是从最左列开始的一段连续前缀。因为索引里的顺序是”先 a 后 b 后 c”，只给 b 的值，索引无法知道去哪一区间找。

4.2 最左前缀：哪些查询能用上 (a, b, c)

查询条件 能用到的索引部分 说明
a = 1 a 完整使用
a = 1 AND b = 2 a + b 完整使用
a = 1 AND b = 2 AND c = 3 a + b + c 完整使用
b = 2 无 缺最左列 a，索引失效（全表扫描或索引全扫）
a = 1 AND c = 3 只用 a 跳过 b，c 无法用于索引定位（5.6+ 可被索引下推部分挽回，见 4.3）
b = 2 AND a = 1 a + b 优化器会重排等值条件，等价于 a=1 AND b=2

两个补充规则：

  • 等值条件顺序无关：优化器会自动把等值条件按索引列序重排，所以 b=2 AND a=1 和 a=1 AND b=2 效果一样；
  • 范围条件后面的列”断链”：a > 1 AND b = 2 中，a 用于索引定位，但 b 无法用于定位——索引定位只能在第一个范围条件上停止（b=2 只能退化为索引层过滤，8.0 前回表后过滤，8.0 中可被 ICP 拦截，见 4.3）。所以等值列放前面、范围列放后面是联合索引设计的铁律（见 6.2）。

4.3 索引下推（ICP）：把过滤提前到索引层

MySQL 5.6 引入的索引下推（Index Condition Pushdown），解决的是”联合索引部分失效”场景下的回表浪费：

  • 5.6 之前：引擎层把 name LIKE '张%' 命中的所有记录（含 age != 30 的）全部回表，由 Server 层过滤 age = 30——假设命中 1 万条，就回表 1 万次；
  • 5.6 之后（ICP）：引擎层在**遍历二级索引时直接判断 age = 30**，只把满足条件的行回表——假设只剩 50 条，就回表 50 次。

执行计划里看到 Extra: Using index condition 即命中 ICP。注意前提：过滤条件里的列（这里的 age）必须是索引列。

4.4 索引与排序：ORDER BY 免排序

B+ 树的叶子天然有序，所以只要排序字段是联合索引的一个连续前缀，ORDER BY 就能直接按索引顺序取数据，省掉 filesort（内存/磁盘排序，代价很高）：

看到 Extra: Using filesort 就要警惕——它通常意味着一次额外的排序开销，优先考虑把排序列放进索引（或调整索引列序）。

本节小结：联合索引 = 一棵按”字典序”排序的树；最左前缀是它的使用规则，等值前置、范围后置是它的设计规则；ICP 在索引层提前过滤，覆盖索引/索引序消灭回表与 filesort——这四个机制全部围绕”减少聚簇索引访问”服务。

key_len 计算示例（面试手算题）：utf8mb4 字符集下 VARCHAR(32) 可空列，32 × 4 + 2（变长长度字节）+ 1（NULL 标记）= 131 字节。联合索引 (a, b) 的 key_len 只等于 a 的长度，说明 b 没用上。

5.2 索引失效场景清单

场景 示例 原因与正解
对索引列做函数/运算 WHERE DATE(create_time) = '2026-08-01' 索引存的是列原值，无法按函数结果定位。正解：create_time >= '2026-08-01' AND create_time < '2026-08-02'，或 8.0 函数索引
隐式类型转换 字符串列 WHERE phone = 13800000000（数值） 列上发生类型转换，见 5.3
LIKE '%xx' 前导模糊 WHERE name LIKE '%张' 无法确定扫描起点。张% 可以走 range
OR 连接非索引列 WHERE name = 'a' OR age > 30（age 无索引） 优化器无法保证只走 name 索引。正解：拆两条 SQL 或给 age 建索引
违反最左前缀 联合索引 (a,b,c) 查 WHERE b = 2 见 4.2
范围条件断链 WHERE a > 1 AND b = 2 b 无法用于定位，只能过滤（等值列放前，见 4.2）
NOT IN / != / NOT LIKE WHERE status != 1 非绝对失效：返回比例高时优化器主动选全表扫描，比例低时可能走 range，取决于统计信息
数据量过小 几千行的表 优化器认为全表扫描更快（扫描几个页 vs 走索引还要回表），是合理决策，不是 bug

两个常见误解要澄清：

  • IS NULL 走不走索引？ 走。InnoDB 二级索引允许存 NULL，IS NULL 是 ref 级别的索引查找；
  • != 一定失效？ 不一定。它是优化器基于成本的选择，与数据分布有关——用 EXPLAIN 验证而不是背结论。

5.3 隐式类型转换：最容易踩的坑

MySQL 的规则：字符串列与数值比较时，字符串被转换为数值——转换发生在列上，索引失效；数值列与字符串比较时，字符串被转成数值，列不受影响，索引可用。

实践规则：Java 里用 MyBatis/JPA 传参时，phone 这类字符串字段传参类型必须和列类型一致（DTO 里是 String），否则会掉进这个坑且线上很难发现。排查技巧：EXPLAIN 里 key 为 NULL 但条件明明有索引，先检查类型。

6. 日常建索引的实践要点

6.1 建索引的决策流程

不要”凭感觉建索引”，按下面的流程走：

  1. 定位慢 SQL：开启慢查询日志（long_query_time = 1，或阈值按业务调），或用 performance_schema/监控平台捞 Top SQL；
  2. EXPLAIN 分析：确认是不是全表扫描（type = ALL）、有没有 filesort、rows 是否过大；
  3. 设计索引：把 SQL 的 WHERE 等值列、JOIN 关联列、ORDER BY 排序列、GROUP BY 列列出来，按 6.2 的规则排成联合索引；
  4. 验证：EXPLAIN 对比建索引前后的 type、rows、Extra，确认覆盖到查询；
  5. 上线观察：索引对写放大有代价，上线后观察慢日志和写入延迟，确认收益 > 成本。

6.2 选列与排序的四个原则

① 区分度优先：索引的价值在于”过滤”，区分度低的列（性别、状态位）单独建索引收益极低——过滤完还是半张表。用 SHOW INDEX FROM t 看 Cardinality（估算基数），基数/总行数越大越好。区分度低的列适合放在联合索引靠后的位置做等值过滤（见③）。

② 等值列在前，范围/排序列在后：等值条件（=）能精确确定扫描区间，范围条件（>、BETWEEN、LIKE 'x%'）会让后面的列断链。排序/分组列放在最后，顺便免掉 filesort（4.4）。

③ 尽量让查询覆盖：查询只返回索引列的列时，把高频 SELECT 的列塞进索引尾部队列，用空间换回表。典型：列表页查 (id, name, status)，就建 (name, status) 或让联合索引带上它们。

④ 先查后建，宁缺毋滥：没有慢 SQL 就没有索引需求；小表（万行以内）全表扫描只有几个页的 IO，索引的收益可以忽略，别为”仪式感”建索引。

6.3 索引的成本：为什么不能建太多

每个索引都是一份独立的排序副本，代价具体到数字：

  • 写放大：一条 INSERT 要写 1 份聚簇索引 + N 份二级索引；UPDATE 修改了索引列，对应索引也要改；DELETE 同理。索引从 3 个加到 8 个，写入开销接近翻倍；
  • 空间：每加一个索引，就是表数据的 20%~100% 的额外存储（取决于列宽），同时挤占 Buffer Pool 内存，降低缓存命中率；
  • 唯一索引更贵：插入前要立即判断唯一性，无法利用 change buffer 的延迟合并（普通二级索引可以）。

量化建议：单表索引控制在 5~6 个以内，能用联合索引覆盖的查询就不要拆成多个单列索引。

6.4 冗余索引与维护

  • 联合索引吞并单列索引：有 (a, b) 就没必要保留单列 (a)——前者完全覆盖后者的能力。但 (b, a) 与 (a, b) 是两种不同结构，别删错；
  • 8.0 的 INVISIBLE 索引：拿不准要不要删的索引，先 ALTER TABLE ... ALTER INDEX idx INVISIBLE 无痛隐藏，观察一段时间没有报错再 DROP，比直接删安全得多；
  • 索引碎片：页分裂会留下碎片。SHOW TABLE STATUS LIKE 't_order' 看 Data_free，碎片明显时 OPTIMIZE TABLE t_order 重建表（注意锁表时间，选业务低峰）；
  • 前缀索引：超长字符串（URL、邮箱）建 url(20) 前缀索引，但会损失区分度，且无法用于覆盖索引和 ORDER BY——权衡后使用；
  • 8.0 函数索引：CREATE INDEX idx_date ON t ( (DATE(create_time)) )，专门兜底”函数查询”场景，但优先还是改写 SQL。

7. 面试高频题速答（1-3 年档）

问题 速答
为什么 InnoDB 用 B+ 树而不是 B 树？ 内部节点不存数据 → 单页键多 → 树矮 IO 少；叶子链表 → 范围查询和顺序扫描高效；写放大更小
聚簇索引和非聚簇索引的区别？ 聚簇叶子存整行、每表一个、决定物理顺序；二级索引叶子存”列值 + 主键”、可多个、与物理顺序无关
为什么二级索引存主键而不是行指针？ 数据页移动/分裂时主键不变，避免级联更新所有二级索引；代价是主键越长索引越大
什么是回表和覆盖索引？ 二级索引缺字段时拿主键回头查聚簇索引叫回表；查询列全在索引里则无需回表（Extra: Using index）
联合索引 (a,b,c)，WHERE b=1 AND c=2 能用吗？ 不能定位，最左列缺失；只能全索引扫描，8.0 下可被 ICP 在索引层过滤
索引下推解决什么问题？ 让二级索引遍历时直接过滤部分失效的索引列，减少回表次数（Extra: Using index condition）
什么场景索引会失效？ 函数/运算、隐式类型转换、LIKE '%x'、OR 非索引列、违反最左前缀、范围后断链
自增主键 vs UUID？ 自增顺序插入无页分裂、索引小；UUID 乱序导致页分裂、碎片、空间利用率掉到 50% 附近
索引是不是越多越好？ 不是。每个索引都是写放大 + 空间成本，单表 5~6 个为常见上限，用联合索引替代多个单列索引
唯一索引和普通索引怎么选？ 需要业务防重/唯一约束用唯一索引；否则用普通索引（可走 change buffer，写入更便宜）

8. 总结

一条主线串起全文：B+ 树用”矮树 + 叶子链表”把磁盘 IO 次数从 O(n) 压到 O(层数)；聚簇索引就是表数据本体，二级索引是”列 + 主键”的副本，回表是两者之间的差价；联合索引按字典序组织，最左前缀决定能用不能用，等值前置决定用得好不好；EXPLAIN 的 type/key/Extra 三件套 + 隐式转换、函数、LIKE 这些失效清单，是排查慢 SQL 的标准动作；最后落到实践：先慢日志，后 EXPLAIN，再按”区分度、列序、覆盖、成本”四原则建索引。

索引优化是 MySQL 学习中性价比最高的投入——它不需要改代码，不需要扩机器，一条 CREATE INDEX 常常把慢 SQL 从秒级降到毫秒级。但这张”免费的优化券”也有规则：建错了（冗余、过度）会拖垮写入，建歪了（列序、类型）等于没建。
