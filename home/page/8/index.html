复制与高可用：延迟的量化与判定

Posted on 2026-10-25 In 数据存储 Word count in article: 4.2k Reading time ≈ 15 mins.

Seconds_Behind_Source 不可信，但绝大多数监控只看它。它的计算方式决定了两个盲区：从库应用线程停住时它显示 NULL（不是持续增长的数字），从库追平后它又恒为 0——两种情况都会让「延迟 > 阈值」的告警失效。

本文搭了一套真实的 GTID 主从（两个容器），用实测把这件事钉死：在应用线程停住的 10 秒里，SBM 一直是 NULL，而心跳表测出的真实延迟从 11.38 秒线性涨到 21.71 秒。最后再做一次主从切换演练，看 GTID 怎么把「找位点」变成「对集合」。

1. 复制链路：三个线程、两份日志

1.1 三线程模型

    end
    subgraph R["Replica"]
        IO["IO thread"] -->|"pull binlog"| RL["relay log"]

        SQL --> ENG2["InnoDB"]

    BL -->|"SOURCE"| IO
组件 在哪 干什么 出问题时的表现
binlog dump 线程 主库 把 binlog 推给从库 从库 IO thread 报连接错误
IO thread 从库 拉 binlog 写 relay log Replica_IO_Running: No，Last_IO_Error 有内容
SQL thread（可多个 worker） 从库 回放 relay log Replica_SQL_Running: No，Last_SQL_Error 有内容，延迟增长

一个必须分清的点：IO 线程停了，从库连不上主库（网络问题）；SQL 线程停了，从库拿到了日志但没执行（应用冲突或人为停下）。两者的排查方向完全不同。

1.2 binlog 三种格式

格式 写什么 大小 一致性风险 适用
STATEMENT SQL 原文 小 NOW()、UUID()、LIMIT 无排序等不确定语句会让主从不一致 不推荐
ROW（默认，实测） 每行变更前后值 大（一条 UPDATE 影响 100 万行 = 100 万条事件） 最安全，主从必然一致 生产默认
MIXED 自动切换 中 由优化器判断，仍有不确定性 历史遗留

实测默认 binlog_format=ROW。这解释了一个常见疑惑：为什么主库一条 UPDATE ... WHERE 改了 100 万行，binlog 会暴涨——ROW 格式记录的是每一行的变化，不是那条 SQL。

1.3 GTID：把「找位点」变成「对集合」

传统位点复制要维护 MASTER_LOG_FILE + MASTER_LOG_POS，切换时容易错。GTID 给每个事务一个全局唯一编号 uuid:seq，从库只需声明「我执行过哪些」，主从自动对账。

    CaughtUp --> Replicating: new transactions arrive
    Replicating --> Promoted: STOP REPLICA<br/>RESET REPLICA ALL
    Promoted --> Writing: read_only=OFF
    Writing --> [*]

主从一致性校验 靠位点推算 比较 gtid_executed 两个集合

2. 并行复制：为什么默认还是慢

2.1 实测默认值

参数 值 含义
replica_parallel_workers 4（实测） 回放线程数
replica_parallel_type LOGICAL_CLOCK（实测） 按事务的提交顺序分组并行
binlog_format ROW（实测） 行级事件
replica_preserve_commit_order ON（8.0 文档默认） 并行回放但提交顺序与主库一致

LOGICAL_CLOCK 的并行依据是「在主库上是否同一时刻提交」：同一组内的事务可以在从库并行回放，不同组之间必须有序。

2.2 大事务是并行的天敌

一个事务只能由一个 worker 回放。所以：

主库操作 从库能并行吗 后果
1000 个独立小事务 能（按组） 几乎无延迟
1 个改 100 万行的事务 不能 单线程回放，延迟 = 回放耗时
100 个大事务串行提交 不能（组间有序） 延迟线性累加

2.3 实测：100 万行单事务的回放

本地两容器、ROW 格式，100 万行的单条 INSERT ... SELECT：

指标 实测
主库写入耗时 数十秒（本机，未精确计时）
从库追平耗时 2~4 秒（本地 SSD + 空表）
期间 SBM 峰值 2 秒
期间心跳延迟峰值 0.49 秒

本机太快，复现不了生产的分钟级延迟——但这张表本身说明了一个重要事实：延迟不是「事务多大」决定的，而是「回放速度 vs 产生速度」的差。生产上从库延迟 40 分钟，通常不是单条 SQL 慢，而是：主库持续高速写入 + 从库单线程回放 + 大事务把 worker 堵死。

3. 延迟：两个指标，两套盲区

3.1 Seconds_Behind_Source 到底怎么算

它等于「当前正在回放的事件的时间戳」与「从库当前时间」的差。三个后果：

  1. 只在有事件正在回放时有意义；
  2. 事件时间戳来自主库，主从时钟不同步会直接污染这个值；
  3. 没有事件时它没有「年龄」概念，于是返回 0 或 NULL。

3.2 实测：两个指标的背离

人为停住从库的应用线程（模拟「回放跟不上」），主库持续写入，每秒采样：

时刻 SBM 心跳延迟 说明
停住后 1s NULL 11.38 s SBM 直接没有值
停住后 5s NULL 15.97 s 心跳在老实增长
停住后 10s NULL 21.71 s 差 21 秒，SBM 依然空
恢复后 1s 12 1.21 s SBM 跳了一下
恢复后 2s 0 2.35 s SBM 归零，心跳继续涨
恢复后 5s 0 5.76 s 追平后 SBM 恒为 0

两件事被这组数据钉死：

盲区一：应用线程停住时 SBM 是 NULL，不是增长的数字。 如果你的告警是 SBM > 60，这段时间永远不会触发。这是最危险的漏报——延迟 21 秒、业务已经在读旧数据，监控一片绿。

盲区二：追平后 SBM 恒为 0。 上表恢复后的 2~5 秒里，从库确实追平了，SBM=0 是对的；但心跳延迟还在涨，因为主库此时已经停止写心跳。所以 SBM=0 只能说明「没有积压」，不能说明「数据新鲜」。

3.3 心跳表：怎么测真延迟

原理很简单：主库每秒往一张表写一次时间戳（这个写入本身也会被复制），从库读这行，用当前时间减它就是真实延迟。

方案 优点 盲区
SBM 内置、零成本 停住时 NULL、空闲时恒 0、受时钟影响
心跳表 真实反映数据新鲜度 主库不写心跳时也会「假涨」；需要额外表与定时任务
performance_schema.replication_applier_status 能看到 worker 级状态 不直接给秒数
对比 gtid_executed 集合 精确知道差多少事务 需要额外查询，不知时间

判定准则：SBM 为 NULL 或 0 且心跳延迟 > 5 秒时，以心跳为准；两者都健康才叫健康。监控上要同时采这两个值，并对 NULL 单独告警——NULL 往往意味着线程停了，比延迟更严重。

3.4 延迟的四类根因

flowchart TD
    L["Replica lag detected"] --> Q1{"SQL thread<br/>running?"}
    Q1 -- no --> A["Apply stopped<br/>SBM = NULL<br/>check Last_SQL_Error"]
    Q1 -- yes --> Q2{"big transactions<br/>in binlog?"}
    Q2 -- yes --> B["Single transaction<br/>cannot parallelize"]
    Q2 -- no --> Q3{"primary write rate<br/>higher than apply rate?"}
    Q3 -- yes --> C["Capacity: add workers<br/>or reduce write burst"]
    Q3 -- no --> D["Network / IO thread<br/>relay log write slow"]
根因 特征 处理
大事务 binlog 里单个事务事件量巨大，SBM 阶梯式跳变 拆批提交（每批 1000~5000 行）
单线程瓶颈 worker 数少、CPU 用不满、SBM 缓慢增长 加 replica_parallel_workers，确认 LOGICAL_CLOCK
主库写入过载 主库 TPS 高，从库回放跟不上 削峰、分库、读写分离降级
网络/relay log IO SBM 波动大，Retrieved 增长慢 查带宽、sync_relay_log 配置
从库资源争抢 从库还在跑备份/大查询 隔离备份窗口，innodb_buffer_pool_size 给足

3.5 动手验证：制造并观测延迟

预期观察点：停住期间 SBM 是 NULL（SHOW REPLICA STATUS 里显示 NULL），心跳延迟每秒 +1 左右；恢复后 SBM 先跳一个值再归 0。

判定标准：

  • SBM = NULL 且 Replica_SQL_Running: Yes → 线程刚启动或正在等事件，结合心跳判断；
  • SBM = NULL 且 Replica_SQL_Running: No → 应用线程挂了，看 Last_SQL_Error；
  • 心跳延迟持续增长但 SBM=0 → 主库没写入，不是复制问题。

4. 高可用：切换演练

4.1 实测：把从库提升为主库

实测结果：

检查项 实测值
命令耗时 0 秒（不含路由切换与应用重连）
read_only / super_read_only 0 / 0
数据行数 1,500,011（与主库一致）
gtid_executed 两个 UUID（原主库 1-193 + 自身 1-6）

最后一行值得单独说：切换后 gtid_executed 会包含两个 UUID 的集合——原主库贡献的历史，加自己的新写入。这正是 GTID 的价值：谁都能算清「我有哪些事务」，不需要再去比对文件名和偏移量。

4.2 三种高可用方案

方案 一致性 自动化 适用
主从 + MHA/Orchestrator 异步/半同步，可能丢少量事务 脚本化切换 传统自建机房
半同步复制 至少一个副本确认 需配合外部切换 对丢失敏感但可接受延迟
MGR / InnoDB Cluster 多数派提交（Paxos 类） 内置选主 + Router 要求自动故障转移

半同步在 8.0.26 之后参数改了名，实测镜像里插件文件确实存在（semisync_source.so / semisync_replica.so），参数是 rpl_semi_sync_source_enabled 与 rpl_semi_sync_replica_enabled；装法：

sequenceDiagram
    participant C as Client
    participant P as Primary
    participant R as Replica
    C->>P: COMMIT
    P->>P: commit in InnoDB

注意：半同步只保证「至少一个副本收到了 relay log」，不保证副本已经执行。所以半同步切换后仍可能读到旧数据（读到的是 relay log 里的事务尚未 apply 完成）。

4.3 脑裂与 fencing

切换最怕的不是慢，是「两个主库同时可写」。三个必要动作：

动作 目的
提升前 SET GLOBAL super_read_only = ON 原主库（若还活着） 强制原主只读
用 VIP / 代理层做统一入口 应用只认一个地址
切换后校验 gtid_executed 是否包含原主全部事务 防丢数据

4.4 动手验证：写一个可重复的切换演练

预期观察点：第 2 步等待期间 SBM 可能一直是 0（主库已停写），此时要用 gtid_executed 是否相等来判断追平，而不是信 SBM——这正是 3.2 那个盲区的实际影响。

判定标准：

  • 提升后写入成功、gtid_executed 含原主库全部事务 → 切换成功；
  • 提升后 read_only 仍为 1 → 漏了 super_read_only（它优先级更高，必须先关）。

5.4 实操建议

  1. 监控必须同时采 SBM 和心跳延迟，并对 SBM IS NULL 单独告警——这是最容易被忽略的漏报。
  2. 切换的判定条件是 gtid_executed 相等，不是 SBM=0。前者是事实，后者是推测。
  3. 批处理一律拆小（每批 1000~5000 行），既降延迟又降回滚代价。
  4. 半同步不是「不丢数据」的保证，它只保证「至少一个副本收到」；要读到自己刚写的数据，还是得走主库。
  5. 切换演练每季度做一次，并且用真实的业务写入验证，而不是只看 read_only=0。

InnoDB 内存与刷盘：物理 IO 的钱花在哪

Posted on 2026-10-25 In 数据存储 Word count in article: 4.4k Reading time ≈ 16 mins.

前面六篇都在省「读」，这一篇看「写」。一次 COMMIT 背后至少两次落盘：redo 一次、binlog 一次。这两次 fsync 值多少钱？实测下来，把 innodb_flush_log_at_trx_commit 从 1 改成 0，单行插入 TPS 从 734 涨到 151,035——206 倍。而代价是：kill -9 之后，刚提交的 2000 行一行都不剩。

这就是本文要算的账：性能与持久性的兑换率。文中所有数字都在 MySQL 8.0.46 容器里实测，kill -9 是真杀进程后重启验证的。

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘（本文） → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

1. 写路径：一次 commit 写了几次盘

1.1 WAL：先写日志，再慢慢写数据

InnoDB 改数据时不直接改磁盘上的页，而是：

  1. 把页读进 Buffer Pool（内存），在内存里改；
  2. 把「改了什么」写进 redo log（顺序写、小）；
  3. 提交时确保 redo 落盘 → 事务就算持久了；
  4. 脏页由后台线程慢慢刷回磁盘（随机写、慢）。
flowchart LR
    C["COMMIT"] --> RB["redo log buffer<br/>memory"]
    RB -->|"write()"| OS["OS page cache"]
    OS -->|"fsync()"| RD["redo file<br/>#innodb_redo"]
    C --> BB["binlog buffer"]
    BB -->|"write()"| BOS["OS page cache"]
    BOS -->|"fsync()"| BF["binlog file"]
    BP["Buffer Pool dirty pages"] -->|"background flush"| DF["data files .ibd"]

WAL 的价值：把「随机写数据页」变成「顺序写日志」。一次事务改 3 个页，日志可能只有 200 字节；如果不写日志直接刷脏页，就要 3 次随机 IO。

代价是：同一份数据写了两遍（redo + 数据页），而且 redo 也要落盘。所以「写放大」在数据库里是常态，不是 bug。

1.2 两阶段提交：redo 与 binlog 必须一致

redo 是 InnoDB 的，binlog 是 Server 层的，两者独立。为了让「主库数据和从库/备份的 binlog」一致，提交要走两阶段：

sequenceDiagram
    participant C as Client
    participant S as Server
    participant I as InnoDB
    C->>S: COMMIT
    S->>I: prepare (写 redo, 标记 prepare)
    I-->>S: ok
    S->>S: 写 binlog + fsync
    S->>I: commit (redo 标记 commit)
    I-->>C: ok

崩溃恢复时的判定很简单：

崩溃时机 redo 状态 binlog 状态 恢复动作
prepare 之前 无 无 回滚
prepare 之后、binlog 之前 prepare 无 回滚
binlog 之后、commit 之前 prepare 有 提交（redo 补 commit）
commit 之后 commit 有 无需动作

这就是「binlog 写成功但没 commit」也能恢复的原因。理解了这张表，⑧ 的主从一致性、⑨ 的 PITR 都不会再有疑问。

1.3 一次 commit 的 fsync 次数

配置 redo fsync binlog fsync 一次 commit 的 fsync 次数 丢失风险
flush=1, sync_binlog=1 每次提交 每次提交 2 不丢
flush=2, sync_binlog=1 每秒（后台） 每次提交 1 掉电丢 ~1s
flush=1, sync_binlog=0 每次提交 由 OS 决定 1 掉电丢 binlog

实测默认值（8.0.46）：innodb_flush_log_at_trx_commit=1、sync_binlog=1、innodb_flush_method=fsync、innodb_redo_log_capacity=100MB、binlog_group_commit_sync_delay=0。

2.1 实测 TPS 阶梯

  1. sync_binlog 比 flush_log 更贵。第 2 行到第 3 行只改了 sync_binlog，TPS 从 1,962 跳到 23,443（12 倍）；而第 1 行到第 2 行改 flush_log 只有 2.7 倍。原因：binlog 的 fsync 是每次提交都做（sync_binlog=1），而 redo 在 flush=2 时交给后台每秒一次。
  2. flush=0 和 flush=2 完全不是一个量级。flush=2 至少把 redo write() 到了操作系统，进程崩溃不丢；flush=0 连 write 都不做，数据还在 MySQL 自己的内存里。

2.3 深挖：为什么 flush=2 在 kill -9 下没丢数据

这是本文最容易被误解的一点。flush=2 的语义是：**提交时 write() 到操作系统，但不 fsync()**。

崩溃类型 flush=2 会丢吗 原因
mysqld 进程崩溃（kill -9、段错误） 不会 数据已 write() 进 OS page cache，进程死了 OS 还在

3. Buffer Pool：命中率是怎么算的

3.1 结构：一个被改造过的 LRU

Buffer Pool 按页管理（默认 16KB/页），内部是「young / old」两段式 LRU：

flowchart LR
    subgraph LRU["Buffer Pool LRU list"]
        Y["young sublist<br/>hot pages, 5/8"] --> O["old sublist<br/>cold pages, 3/8"]
    end
    NEW["new page read in"] --> O
    O -->|"accessed again<br/>after innodb_old_blocks_time"| Y
    O -->|"evicted when full"| OUT["evicted"]

为什么分成两段：全表扫描会一次性读入大量「只用一次」的页。如果纯 LRU，这些页会把热数据挤出去。分两段之后，新页先落在 old 区，只有被再次访问（且间隔超过 innodb_old_blocks_time，默认 1000ms）才会晋升 young 区。这就是「一次大查询不会把热数据全冲掉」的机制。

参数 实测默认值 作用
innodb_buffer_pool_size 128MB 池大小，生产建议内存的 50%~70%
innodb_buffer_pool_instances 8（≥1GB 时） 分段减少锁竞争
innodb_buffer_pool_chunk_size 128MB 扩容/缩容的最小单位
innodb_old_blocks_time 1000ms 新页晋升 young 的等待时间

3.2 命中率的算法与陷阱

两个陷阱：

  1. 它是「页级」指标，不是「SQL 级」。一条慢 SQL 可能命中率 100% 但读了 30 万个页（③ 的回表），所以命中率不能替代 EXPLAIN。
  2. 它的分母是请求次数，不是数据量。循环访问同一个页 100 万次，命中率也是 100%。

① 的实测正好能对照：100 万行表（3430 页）在 128MB 池里能整表装下，冷启动扫一次物理读 1046，热缓存后再扫 物理读 0，但逻辑读一次都没少。命中率只说明「要不要去磁盘」，不说明「读得多不多」。

机制 解决什么问题 边界

4. 崩溃恢复：redo 怎么把数据救回来

4.1 恢复流程

flowchart TD
    S["mysqld starts"] --> A["read checkpoint from redo"]
    A --> B["replay redo from checkpoint<br/>redo apply"]
    B --> C{"page corrupt?<br/>(torn page)"}
    C -- yes --> D["restore page from doublewrite"]
    C -- no --> E["continue"]
    D --> E
    E --> F["rollback uncommitted trx<br/>using undo"]
    F --> G["purge starts,<br/>history list drains"]
    G --> H["ready for connections"]

三个关键点：

  1. redo 重放是幂等的：同一个变更重放多次结果一样，所以崩溃恢复可以放心重做。
  2. doublewrite 只在「页损坏」时登场：它的作用不是加速，是保险。
  3. 未提交事务靠 undo 回滚：这就是 ⑤ 里 undo 的第二个用途（第一个是 MVCC）。

4.2 实测：kill -9 之后看恢复

预期观察点：启动日志/状态里能看到 Database was not shut down normally 之类的提示，随后是 redo apply 的进度；恢复时间与「上次检查点之后写了多少 redo」成正比。

判定标准：

  • 恢复时间突然变长 → 检查点推进不及时（大事务、刷脏跟不上），看 innodb_buffer_pool_wait_free；
  • 启动报 page corruption → doublewrite 可能被关了，或者磁盘真坏了。

5.4 实操建议

  1. **别碰 flush=0**。它省下的不是性能，是数据；要在压测里用它，先想清楚压出来的数字能证明什么。

1. 三种行锁：锁的是索引，不是行

WHERE c = 5（非唯一索引） idx_c X on 5,5 + idx_c X,GAP（5,10）+ PRIMARY X,REC_NOT_GAP on 5 插入 c=6 被阻塞 插入 c=11 成功
范围 WHERE id > 5 逐条 next-key（本文没测，原理同第三行） 区间内插入 区间外插入

第一行是最反直觉的：唯一索引等值命中时，InnoDB 会退化成纯记录锁（REC_NOT_GAP），不锁间隙。所以 SELECT * FROM tl WHERE id = 5 FOR UPDATE 不影响别人插入 id = 7。

第三行的三个锁要连起来看：

  • idx_c X on 5,5：非唯一索引上的 next-key，锁住记录 5 前后
  • idx_c X,GAP on 10,10：锁住 (5,10) 这段空隙
  • PRIMARY X,REC_NOT_GAP on 5：回表锁住真实行

这就是「WHERE c = 5 会把 (5,10) 之间的插入全堵住」的机制——间隙锁锁的是空隙，不是记录，所以 INSERT c = 6 会卡住，而 INSERT c = 11 不受影响。

1.3 加锁范围的推导规则

flowchart TD
    S["Current read with condition"] --> Q1{"unique index,<br/>equality?"}
    Q1 -- "hit" --> A["Record lock only<br/>REC_NOT_GAP"]
    Q1 -- "miss" --> B["Gap lock<br/>X,GAP"]
    Q1 -- "no" --> Q2{"non-unique index?"}
    Q2 -- yes --> C["Next-Key locks<br/>record + gap"]
    Q2 -- "no index at all" --> D["Scan + lock every row<br/>effectively table-wide"]
    C --> E["also lock clustered index<br/>for the matched rows"]

记住一条：间隙锁只在 REPEATABLE READ 及以上级别生效，READ COMMITTED 下基本没有间隙锁（除了外键/唯一性检查）。所以「把隔离级别降到 RC 能减少锁冲突」这句话是对的，代价是放弃可重复读（⑤ 讲过代价）。

1.4 为什么「没走索引」等于锁全表

UPDATE tl SET c = 1 WHERE k = 'no-such-value' 如果 k 上没有索引：InnoDB 只能全表扫描，扫过的每一行都会加锁（RR 下是 next-key），等于锁住整张表。此时任何插入都可能被阻塞。

生产上的典型症状：「一个按非索引字段跑批的 UPDATE，把整张表锁了 30 秒」。诊断方法就是看 data_locks 里 LOCK_DATA 有多少条记录——几百条基本可以确定是全表扫。

3. MDL：为什么一条 ALTER 能堵死整张表

3.1 两种锁，两套规则

行锁保护「数据」，MDL（Metadata Lock）保护「表结构」。两者完全独立：

维度 行锁 MDL
保护对象 行数据 表结构（列、索引）
加锁时机 当前读 / 写 任何访问表的语句，包括普通 SELECT
持有到何时 事务结束 语句结束（普通查询）或事务结束
等待变量 innodb_lock_wait_timeout（默认 50s） lock_wait_timeout（默认 31536000s，等于「永远等」）

关键差异：普通 SELECT 不加行锁，但要加 MDL 共享锁。这就是为什么「我只查了一下」也会参与 MDL 排队。

4.2 一个真实的因果链（本文实测的拼合）

T0 会话 A 开了事务查了一次表 持有 MDL SHARED_READ

5.4 实操建议

  1. 写完 FOR UPDATE 就问一句：这个条件走的是唯一索引等值吗？是 → 只锁一行；不是 → 先看 data_locks 再上线。
  2. 批量更新按主键排序。这一条能消掉大部分 ABBA 死锁，成本几乎为零。
  3. 业务侧把锁等待超时调到 3~5 秒，别用默认 50 秒——长等待会连带打满连接池。
  4. DDL 前必跑两条检查（长事务 + MDL PENDING），并把 lock_wait_timeout 显式设小。
  5. 间隙锁不是 bug。它是 RR 保证可重复读的代价；要消掉它，改隔离级别或改索引设计，不要指望调参数。

事务与 MVCC：把「不可重复读」亲手复现出来

隔离级别不是背四个名字，而是回答「同一个事务里两次读，凭什么看到同一个值」。答案是 MVCC：每行数据挂一条 undo 版本链，事务开始时拍一张 ReadView 快照，之后所有普通查询都按这张快照判断「哪个版本我能看」。理解了这条链，脏读、不可重复读、幻读的差别就不再是术语，而是三个可以手工复现的现象。

本文用两个会话把三种异常逐个演出来（全部实测），再解释 ReadView 的判定规则、快照读与当前读的分界线，最后用数据说明长事务为什么是「三重危害」。这一篇也是下一篇锁机制的地基：快照读不加锁、当前读加锁，是理解间隙锁的前提。

1. ACID 不是四个词，是四套机制

1.1 每个字母背后都有一个组件

特性 一句话定义 靠什么实现 失效后果
原子性（A） 要么全做，要么全不做 undo log（回滚日志） 扣了钱没加钱
一致性（C） 约束始终成立 由 A、I、D 与应用共同保证 余额为负、外键悬空

持久性（D） 提交了就不丢 redo log + 刷盘 宕机丢订单

“一致性”是唯一没有专属组件的：它是前三个加上业务约束的结果。所以面试问「MySQL 怎么保证一致性」时，答「靠 undo、redo、锁一起」比背定义有效。

2. MVCC：一条版本链 + 一张快照

2.1 隐藏列与版本链

InnoDB 每行都有两个隐藏列：DB_TRX_ID（最后修改它的事务 ID）和 DB_ROLL_PTR（指向 undo 里的上一个版本）。每次更新都把「旧值」写进 undo，并用指针串起来：

flowchart LR
    R["Current row<br/>balance=1000<br/>DB_TRX_ID=100"] --> U1["undo v1<br/>balance=900<br/>trx_id=80"]
    U1 --> U2["undo v2<br/>balance=800<br/>trx_id=60"]
    U2 --> U3["...older versions"]

一条链上的每个版本都带着「是哪个事务写的」。读的时候从当前行沿链往回走，找到第一个「对我可见」的版本——这就是 MVCC 的全部。

概念 存在哪 作用
DB_TRX_ID 行记录 标记最后修改者
DB_ROLL_PTR 行记录 指向 undo 里的旧版本
undo log undo 表空间 存旧版本 + 支撑回滚
ReadView 内存（事务私有） 判断「谁能看见谁」

2.2 ReadView 的四个字段与判定规则

ReadView 是一个「活跃事务名单」的快照，只有四个关键值：

字段 含义
m_ids 创建快照时，所有活跃（未提交）事务的 ID 列表
min_trx_id m_ids 里的最小值
max_trx_id 创建快照时系统下一个要分配的事务 ID
creator_trx_id 创建这个 ReadView 的事务自己

判定一个版本 trx_id = V 是否可见：

flowchart TD
    V["version trx_id = V"] --> Q1{"V == creator_trx_id?"}
    Q1 -- yes --> VIS["Visible: my own change"]
    Q1 -- no --> Q2{"V < min_trx_id?"}
    Q2 -- yes --> VIS2["Visible: committed before snapshot"]
    Q2 -- no --> Q3{"V >= max_trx_id?"}
    Q3 -- yes --> INV["Invisible: born after snapshot"]
    Q3 -- no --> Q4{"V in m_ids?"}
    Q4 -- yes --> INV2["Invisible: still uncommitted at snapshot"]
    Q4 -- no --> VIS3["Visible: committed before snapshot"]

按这个顺序判断，直到找到一个可见版本；找不到就说明这行在快照时刻还不存在（这也是幻读的机制）。

2.3 RC 与 RR 的差别，只有一句话

ReadView 的创建时机不同：

级别 ReadView 何时创建 效果
READ COMMITTED 每条语句都新建 每次都能看到别人已提交的新数据 → 不可重复读
REPEATABLE READ 事务内第一次快照读时创建，之后复用 整个事务看同一个快照 → 可重复读

这就是 1.3 实验的全部解释：同样的两条 SELECT，差别只在「第二次读有没有重新拍快照」。

注意一个反直觉点：RR 下「可重复读」是快照读的特权。如果你在事务里用 UPDATE 或 SELECT ... FOR UPDATE，读的是最新已提交版本（当前读），不是快照。这也是「RR 也挡不住丢失更新」的原因。

2.4 动手验证：看一眼正在运行的事务

预期观察点：trx_state 是 RUNNING，age_s 就是它开了多久，trx_rows_modified 是它改了多少行。

判定标准：

  • age_s > 10 且 trx_rows_modified > 0 → 长写事务，第 4 节处理；
  • age_s > 60 但 trx_rows_modified = 0 → 长只读事务，同样会拖住 purge；
  • 同一张表上有多条 RUNNING 事务互相等 → 去 ⑥ 看锁。

3. 快照读与当前读：一条分界线

3.1 哪些语句走哪个读

语句 读类型 加锁 看哪个版本
SELECT ...（普通） 快照读 不加锁 ReadView 快照
SELECT ... FOR UPDATE 当前读 排他锁 最新已提交
SELECT ... FOR SHARE（8.0，旧名 LOCK IN SHARE MODE） 当前读 共享锁 最新已提交
UPDATE / DELETE 当前读 排他锁 最新已提交
INSERT 当前读 插入意向锁 + 唯一性检查 最新已提交 
flowchart LR
    Q["A statement arrives"] --> T{"which kind?"}
    T -- "plain SELECT" --> SN["Snapshot read<br/>ReadView, no lock<br/>reads undo versions"]
    T -- "FOR UPDATE / FOR SHARE<br/>UPDATE / DELETE" --> CU["Current read<br/>latest committed<br/>takes locks"]
    SN --> OK["never blocks writers"]
    CU --> BLK["blocks conflicting writers"]

这条分界线决定了后面几篇的所有并发问题：快照读之所以能「读不加锁」，是因为它读的是 undo 里的历史版本；当前读必须看最新值，所以必须加锁把别人挡在外面。

3.2 实测：幻读只出现在当前读

会话 A（RR）：

会话 B（A 睡眠期间）：INSERT INTO acct VALUES (4,'dave',1800.00,0);

实测结果：

步骤 结果 说明
#1 快照读 2 bob 2000 + carol 3000
#2 快照读（B 已提交后） 2 快照没变，幻读被挡住
#3 当前读 FOR UPDATE 3 看到 dave，幻读出现

同一张表、同一个事务，仅仅把 SELECT 换成 SELECT ... FOR UPDATE，结果就变了。这就是「RR 解决了幻读」这句话的准确边界：它解决的是快照读下的幻读。

3.3 实测：快照读不加锁，当前读加锁

会话 A 执行的语句 会话 B 的 UPDATE 结果 耗时
普通 SELECT（快照读） 立即成功 0.061 s
SELECT ... FOR UPDATE（当前读） ERROR 1205 锁等待超时 2.07 s（innodb_lock_wait_timeout=2）

同样是「读一行」，一个完全不影响写入，一个把写入挡到超时。线上「我只查了一下，为什么把别人堵住了」的疑问，答案就在这里：你查的方式不对。

3.4 动手验证：脏读只在 RU 出现

会话 A：

会话 B（不提交就回滚）：START TRANSACTION; UPDATE acct SET balance=9999 WHERE id=2; DO SLEEP(3); ROLLBACK;

实测结果：A 第一次读到 9999.00（B 未提交的脏数据），B 回滚后 A 读到 2000.00。

判定标准：RU 下读到未提交值 = 脏读确认；把 A 的级别换成 RC 重跑，就应该仍是 2000.00。生产上永远不要用 RU，它唯一的用途是「不在乎一致性的统计快照」。

4.1 危害一：锁一直不放，把写入排队

4.2 危害二：undo 膨胀，而且不会自己缩回去

实测同一实例里 undo 表空间的 allocated size 变化：

阶段 undo 总占用
初始（2 个 undo 表空间 × 16MB） 32 MB
长事务 + 并发更新后 48 MB
再一轮更新后 64 MB
长事务结束、purge 追平后 仍是 64 MB 
flowchart TD
    LT["Long-running transaction"] --> L1["row locks held<br/>writers queue"]
    LT --> L2["old read view or<br/>big undo footprint"]
    L2 --> U1["undo records cannot be purged"]
    U1 --> U2["undo tablespace grows"]
    U2 --> D1["disk pressure +<br/>longer crash recovery"]
    LT --> L3["binlog/relay log backlog"]
    L3 --> R1["replica lag"]

为什么不会自己缩回去：innodb_undo_log_truncate 默认 ON，但只有 undo 表空间超过 innodb_max_undo_log_size（实测默认 1024MB）才会触发截断。64MB 这种量级，它会一直留着——平时看不出来，等到磁盘告警时才发现。

4.3 危害三：拖住 purge，间接拖垮从库

长事务持有一个很旧的 ReadView，purge 线程（实测默认 4 个）就不敢清理它可能需要的旧版本。清理跟不上，undo 持续增长，同时：

  • Buffer Pool 里堆积着大量「只对历史快照有用」的页；
  • 主库写压力不变但有效吞吐下降；
  • 大事务写 binlog 时是一次性巨量写入，从库单线程回放时会形成长延迟（⑧ 展开）。

一个诚实的说明：本篇实测里 trx_rseg_history_len（history list length）一直是个位数（5~7），因为 20 万行这个量级 purge 完全跟得上。生产上看到 10 万+ 的前提是「高 TPS × 事务持续数分钟」，不是单次大 UPDATE。所以别把这个指标当唯一信号，innodb_trx 里的 age_s 更直接。

4.4 排查与判定

信号 阈值 含义
age_s（最老事务） > 10s 需关注，> 60s 处理 长事务
trx_rows_modified > 1 万 大事务，回滚代价高
history_list_length > 10 万（经验值） purge 跟不上
undo 占用 接近 innodb_max_undo_log_size 磁盘风险
data_lock_waits 有记录 任意 已经有事务在等锁

4.5 动手验证：亲手造一个长事务再抓它

预期观察点：会话 2 看到 age_s 与 trx_rows_modified = 50000；会话 3 大约 3 秒后返回 ERROR 1205。

判定标准：

  • 会话 3 立即成功 → 说明它更新的行不在被锁范围内（id = 100 应该在里面）；
  • 报 1205 而不是 1213（死锁） → 只是等待超时，没有循环等待（死锁见 ⑥）。

5. Java 侧：事务是怎么被拉长的

@Transactional 只是「在方法前后加 begin/commit」，它不会让你的方法变快。三个最常见的拉长方式：

写法 为什么变长 改法
事务里调 RPC / HTTP 网络耗时全在事务内，锁一直持有 把远程调用挪到事务外，先算后写
事务里循环查库 / 循环 insert 每条语句都要走一遍 Server 层 批量操作、一次性查出来内存处理
大文件 / 大批量处理放在事务里 事务持有时长与数据量成正比 分批提交，每批独立事务

6.1 面试速答表

面试题 一句话答案
ACID 分别靠什么实现 原子性靠 undo，持久性靠 redo，隔离性靠 MVCC + 锁，一致性靠前三者加业务约束
MVCC 是什么 每行挂 undo 版本链 + 事务持 ReadView 快照，读时沿链找第一个可见版本
RC 和 RR 的差别 只差 ReadView 的创建时机：RC 每语句新建，RR 事务内首个快照读建一次后复用
RR 能防幻读吗 快照读能，当前读（FOR UPDATE/UPDATE）不能；实测同一事务里快照读 2 行、当前读 3 行
快照读和当前读的区别 快照读读 undo 历史版本、不加锁；当前读读最新已提交、必须加锁
为什么普通 SELECT 不阻塞 UPDATE 它不加锁，只读快照
长事务有什么危害 锁持有（阻塞写入）、undo 无法 purge（膨胀且不回落）、binlog 累积（从库延迟）
undo 表空间会自动缩小吗 只有超过 innodb_max_undo_log_size（默认 1GB）才触发 truncate，否则一直占着

RR 下会丢更新吗 会。两个事务都「快照读 + 计算 + 写」，后写的覆盖先写的；要用当前读或原子更新
为什么 RU 不能用 会读到未提交数据，回滚后你的逻辑已经基于幽灵数据跑了

6.4 实操建议

  1. 先记住那条分界线：快照读不加锁、当前读加锁。遇到任何并发问题，先判断这条语句是哪一类。
  2. 事务里禁止出现 RPC、文件 IO、循环查询。这三件事是把 10ms 事务变成 2s 事务的标准配方。
  3. 给每个事务设上限：业务上定一个「事务最长 1 秒」的约定，超过就拆分，比事后排查便宜。
  4. 监控 age_s 而不是只看 TPS。一个有长事务的库，TPS 可能很好看，但锁等待在堆积。
  5. 别用 RU 换性能。脏读带来的问题，修复成本远高于那点收益。
