日常运维高频命令实战手册

Posted on 2026-08-22 In 部署运维 Word count in article: 16k Reading time ≈ 57 mins.

1. 系统信息与性能排查

1.1 排查顺序：先看全局，再钻进程

服务器变慢时，顺序永远是「负载 → CPU → 内存 → IO → 进程 → 线程」，从粗到细逐层收敛。四类资源的快捷判定：

graph TD
    S[Server Slow] --> L[uptime: load average]
    L --> C[top / vmstat: us sy wa]
    L --> M[free: mem and swap]
    L --> I[iostat: await and util]
    C --> P[top -Hp: hot thread]
    P --> J[jstack: match hex TID]
    I --> D[du / lsof: who writes the disk]
    M --> O[dmesg: OOMKiller]

1.2 常用选项清单

uptime / free / lscpu / nproc：系统概览

命令 核心选项 说明 使用场景
uptime — 负载、运行时长、登录用户数 第一眼看负载
-p 人性化显示运行时长 确认机器是否刚重启过
free -h 人类可读单位 看内存/Swap 占用
-m 以 MB 为单位 老脚本里常见
-s 2 每 2 秒刷新一次 实时观察内存变化
-w 把 buffers 和 cache 分列显示（默认合并） 判断 page cache 占用（内核 3.14+）
lscpu — CPU 架构、核数、NUMA 信息 确认物理核/超线程
nproc — 可用 CPU 核数 算负载基线、设线程池
uname -a 内核版本与架构 确认内核版本
ulimit -a 所有资源限制 排查 “Too many open files”
-n 最大打开文件数（nofile） 高并发服务必查

一句口诀：load average 要和 nproc 对比着看——4 核机器 load 8 说明平均有 4 个任务在排队。

top / htop：实时进程视角

命令/按键 说明 使用场景
top -c 显示完整命令行 区分同名 java 进程
top -Hp <pid> 展开该进程的所有线程 定位打满 CPU 的线程
top -u <user> 只看某用户的进程 多租户机器
top -p <pid1>,<pid2> 只看指定进程 盯住目标进程
top -b -n 1 批处理模式输出一次 写脚本采集，不能交互时用
top -d 2 刷新间隔 2 秒 降低刷新频率
top -o %MEM 按内存排序启动 内存排查
交互键 P / M / T 按 CPU / 内存 / 运行时间排序 现场切换排序
交互键 1 展开每个 CPU 核心 发现单核打满
交互键 H 线程视图开关 等价于 -H
交互键 c 完整命令行开关 等价于 -c
交互键 k 直接杀进程 应急操作
htop 彩色交互版，支持鼠标、树状视图 日常首选（需安装）

top 头部关键列：us（用户态）、sy（内核态）、wa（IO 等待）、si/so（Swap 换入换出，非零即为事故）、st（被虚拟化偷走的 CPU）。

vmstat / iostat / mpstat / sar / pidstat：采样统计视角

命令 核心选项 说明 使用场景
vmstat 1 5 每秒采样一次，共 5 次 看 r 队列、上下文切换、Swap
-s 汇总统计 开机以来的总量
-d 磁盘统计 各磁盘读写块数
-w 宽格式（列不挤在一起） 大数字时更易读
iostat -x 扩展统计（await、%util 等） 排查磁盘瓶颈必用
-z 不显示无活动的设备 输出更干净
-m 以 MB/s 显示吞吐 看带宽是否打满
-d 只看磁盘（默认含 CPU） 专注 IO
1 只写数字 = 采样间隔秒数 iostat -xz 1
mpstat -P ALL 1 每个核心的使用率 确认是否单核打满
sar -n DEV 1 网卡流量、错误包 网络吞吐排查
-u 1 CPU 使用率历史采样 复盘「昨晚 10 点为什么卡」
-r 1 内存历史采样 同上
pidstat -u -p <pid> 1 指定进程的 CPU 使用（含用户态/内核态拆分） 进程级细分
-d -p <pid> 1 指定进程的磁盘 IO 找「谁在写盘」
-w -p <pid> 1 上下文切换 线程切换风暴
-t -p <pid> 1 按线程拆分 等价于 top -Hp 的采样版

dmesg：内核日志

命令 核心选项 说明 使用场景
dmesg -T 人类可读时间戳 对照故障时间点
-w 持续输出（follow） 实时盯内核日志
-l err,warn 只看指定级别 过滤噪音
| tail -20 看最后 20 行 快速判断硬件/OOM

案例入口：dmesg -T | grep -i "out of memory" 是确认 OOM Killer 是否出手的第一条命令。

1.3 生产实践案例：服务器卡顿，页面打开缓慢

场景：业务反馈服务器卡顿，页面打开缓慢。

处理结果：发现是某个定时任务与业务高峰叠加，临时降低任务频率，并优化了代码中的死循环。

复盘结论：r 队列、us/sy、单核打满这三条线索都指向 CPU 竞争；如果 wa 高而 us 低，方向就要换到磁盘。

1.4 动手验证：亲手复现一次「CPU 打满」

预期观察点与判定标准：

观察点 正常 异常判定
uptime 的 load 1 分钟值 ≈ 任务数 持续 > 核数 × 1.5 视为过载
us（用户态） 与业务量匹配 yes 这类纯计算会顶到接近 100%
wa（IO 等待） 个位数 持续 > 20% 说明磁盘是瓶颈
si/so（Swap） 0 只要非零，立即查内存
r 列（vmstat） ≤ 核数 持续 > 核数 = 有任务排队

更贴近生产的做法是用 stress-ng --cpu 4 --timeout 60s 造多核负载，观察 mpstat -P ALL 的均衡性。

2. 文件与权限基础

2.1 常用选项清单

ls / cd / pwd：目录浏览

命令 核心选项 说明 使用场景
ls -l 长格式（权限、大小、时间） 查看文件详情
-a 含 . 开头的隐藏文件 查看隐藏配置
-h 人类可读大小（K/M/G） 看文件大小必加
-t / -r 按修改时间排序 / 反向 找最新/最旧文件
-S 按大小排序 找大文件
-d 显示目录本身而非内容 ls -ld /data/www 查目录权限
常用组合 ls -lah 全部文件 + 人类可读 + 详情 每天必用
ls -lht 按时间排序 日志目录找最新
ls -ltr 按时间倒序（最旧在最上） 找最旧文件
cd ~ / - / .. 主目录 / 上次目录 / 上级目录 cd - 在两目录间跳
pwd -P 物理路径（不显示软链） 确认软链背后的真实路径

cp / mv / rm：复制、移动与删除

命令 核心选项 说明 使用场景
cp -i 覆盖前询问 防止覆盖重要配置，建议设别名
-u 只复制更新的文件 增量部署：只覆盖改动过的静态资源
-r / -a 递归（-a 保留权限、时间戳、软链） 备份整个项目目录
-b 覆盖前自动备份（~ 后缀） 改配置前的保险
-p 保留属主/权限/时间戳 跨机器拷文件
mv -i 覆盖前询问 防止误覆盖
-u 只移动更新的文件 合并两个目录
-b 覆盖前备份 同上
rm -i 逐个询问 救命选项
-r 递归删除目录 极度危险，执行前先 ls 一遍
-f 强制，不提示 与 -i 相反，脚本里慎用
-- 结束选项标志 删除 -file.txt 这类怪文件名

rm 安全习惯：rm -rf 前先把命令里的 rm -rf 换成 ls -ld 跑一遍确认路径，再改回来。删除大量文件用 find ... -delete 更有审查痕迹。

chmod / chown：文件权限

命令 核心用法 说明 生产场景
chmod chmod 755 file 数字模式 脚本加执行权限
chmod u+x file 符号模式 精确控制
chmod -R 755 dir/ 递归 批量修复
chmod --reference=模板 目标 参考复制权限 快速对齐
chown chown user:group file 改属主属组 部署后修正归属
chown -R user:group dir/ 递归 批量
chown --reference=模板 目标 参考复制 —

权限数字速查：4=r、2=w、1=x；755 = 用户 rwx、组 r-x、其他 r-x；644 = 用户 rw-、组 r–、其他 r–；600 = 仅属主读写（密钥文件必须 600）。

find：按条件查找

用法 说明 生产场景
find /path -name "*.log" 按文件名 查找日志文件
find /path -iname "*.log" 忽略大小写 同上
find /path -type f / -type d 按类型 只找文件/目录
find /path -size +100M 按大小 找出大文件清理磁盘
find /path -mtime -7 / +7 修改时间 7 天内 / 超过 7 天 清理旧日志
find /path -mmin -30 按分钟 定位「刚刚被改的文件」
find /path -maxdepth 2 限制递归深度 避免扫全盘
find /path -delete 直接删除匹配项 比 -exec rm 快且安全
find /path -exec {} \; 对每个结果执行命令 逐个处理，慢但安全
find /path -exec {} + 批量传给命令一次执行 批量操作，效率高
find /path -print0 | xargs -0 处理含空格/换行的文件名 生产必用，防文件名炸裂

对照：-exec {} \; 每个文件 fork 一次，1 万个文件就是 1 万次进程创建；-exec {} + 和 xargs 会攒批，数量级更快。

tar：打包压缩（基础用法）

格式 打包（创建） 解包 查看内容 生产场景
.tar.gz tar -czvf 包.tar.gz 源目录/ tar -xzvf 包.tar.gz tar -tzvf 包.tar.gz 最常用，发布 Java/Go/Node 应用
.tar.bz2 tar -cjvf 包.tar.bz2 源目录/ tar -xjvf 包.tar.bz2 tar -tjvf 包.tar.bz2 压缩率更高，适合归档
.zip zip -r 包.zip 源目录/ unzip 包.zip -d 目标目录/ unzip -l 包.zip 跨平台（Windows/Linux 通用）

补充选项：

选项 说明
tar -C /target 解压到指定目录：tar -xzvf 包.tar.gz -C /target/
tar --exclude='*.log' 打包时排除
tar --strip-components=1 解压时去掉一层目录（解 jar 包/发布包常用）

tar -czvf = Create Zip Verbose File；tar -xzvf = eXtract。口诀：c 创建、x 解压、t 查看、f 指定文件名必须放最后。

ln：软链接（版本切换必备）

命令 说明 生产场景
ln -s 源文件 链接名 创建软链接（存路径） JDK/应用版本切换、统一日志路径
ln -sfn 新目标 链接名 覆盖已有软链（-n 防止跟进目录） 版本切换标准写法：ln -sfn /opt/jdk-17 /opt/java

一句话区别：软链接存的是路径，原文件删了就失效（ls -l 显示 ->）。目录不能建硬链接。

2.2 动手验证：文件名带空格时，两种写法差在哪

判定标准：写法 A 输出 4 行（app、log、1.log……被空格切开），写法 B/C 输出 2 行完整文件名。**只要管道下游是 rm/mv/chmod，就必须用 -print0 | xargs -0 或 -exec**。

3. 文本处理与日志分析

命令组装成管道才是战斗力：grep 过滤 → awk 取列 → sort | uniq -c 统计 → sort -rn | head 取 TOP N。本章先给每个命令的选项清单，再给一套「日志分析管道」实战。

3.1 常用选项清单

grep：按行搜索

核心选项 说明 使用场景
-i 忽略大小写 搜索不区分大小写
-r / -R 递归搜索目录（-R 跟进软链） 全项目找调用
-v 反向匹配 过滤注释行、空行
-c 统计匹配行数 统计错误条数
-n 显示行号 定位代码行
-l / -L 只显示匹配/不匹配的文件名 快速定位哪些文件包含关键字
-q 静默（只看退出码） 脚本判断存在性
-A 5 / -B 5 / -C 5 匹配行的后 5 行 / 前 5 行 / 前后各 5 行 看错误上下文
-o 只打印匹配部分 提取 IP、时间等片段
-E 扩展正则（ERE） 用 |、+、?、{}
-F 固定字符串（faster） 关键字里有正则元字符
-P PCRE 正则 用 \d、\s、环视
-w / -x 整词 / 整行匹配 防止 user 命中 username
-m 10 最多匹配 10 行就停 大文件里只要前几条
--include='*.log' 只搜某类文件 配合 -r
--exclude-dir=.git 排除目录 配合 -r
--color=auto 高亮匹配 交互查阅

组合口诀：grep -rn --include='*.java' "关键字" . 是最常用的「全项目找代码」；日志分析里 grep -c 计数、grep -A/-B 看上下文。

awk：字段提取与统计

核心模型：逐行读取 → 按分隔符切分 → 用 $1、$2…… 访问每一列。

概念 说明 示例
$0 整行 {print $0}
$1…$N 第 N 列 {print $1}
$NF 最后一列 {print $NF}
NF / NR / FNR 列数 / 行号 / 当前文件行号 {print NR, $1}
FS / OFS 输入/输出分隔符 -F: 或 BEGIN{FS=":"}
BEGIN{} / END{} 读文件前 / 后执行一次 打印表头 / 输出统计
条件过滤 $3=="ERROR"、$4>300、&&、||、! '$9==500'
数组 关联数组（类似 Java 的 Map） count[$1]++
遍历 for (k in arr) END{for(k in c) print k, c[k]}
常用函数 length()、substr()、split()、gsub()、printf 格式化输出

常用参数：-F ':' 指定分隔符、-v x=1 传入变量、-f script.awk 脚本文件。

黄金管道：awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -10 —— 统计访问量 TOP10 接口。整个日志分析章节都是这条管道的变体。

sort / uniq / wc：排序、去重与统计

命令 核心选项 说明 生产场景
sort -n 按数字排序 排序响应时间、状态码
-r 反向（大到小） 找最大/最频繁
-k 2 按第 2 列排序 按日志某一列
-t ':' 指定分隔符 处理 CSV、passwd
-u 排序去重 快速去重
-h 人类可读数字（K/M/G） 配合 du -h 排序
uniq -c 统计出现次数 最常用
-d / -u 只看重复行 / 只看唯一行 找重复数据
-i 忽略大小写 同上
wc -l / -w / -c 行数 / 单词数 / 字节数 统计日志条数

必知前提：uniq 只合并相邻的重复行，直接 uniq -c 统计频率会出错；必须先 sort。黄金组合：sort | uniq -c | sort -rn。

cut / tr / head / tail / less

命令 核心选项 说明 使用场景
cut -d ':' -f 1,3 指定分隔符取列 取 passwd 的用户名和 UID
-d ':' -f 2- 取第 2 列到末尾 字段数不固定时
-c 1-10 取第 1–10 个字符 固定宽度字段
--complement 取反（排除指定列） 排除敏感列
tr 'a-z' 'A-Z' 字符替换（大小写） 归一化
-d '\r' 删除字符 Windows 文件去 \r
-s ' ' 压缩连续重复字符 合并多个空格
head -n 50 / -c 100 前 50 行 / 前 100 字节 看文件头、样例数据
tail -n 100 后 100 行 看最新日志
-f 持续跟踪 实时盯日志
-F 跟踪 + 文件轮转后重新打开 比 -f 更适合生产（logrotate 后不断）
-n +100 从第 100 行到结尾 跳过头部
less +F 进入实时跟踪模式 分页 + 实时跟踪
-N 显示行号；/ 搜索、G 到末尾、q 退出 大文件浏览
zcat / zgrep / zless — 不解压直接看/搜 .gz 查历史归档日志

journalctl：systemd 日志

命令 核心选项 说明 使用场景
journalctl -u nginx 指定服务 看某服务日志
-f / -n 100 跟踪 / 最后 100 行 实时 vs 快照
--since "10 min ago" / --until 时间范围 复盘故障时间窗
-p err 按级别过滤（emerg/alert/crit/err/warning/notice/info/debug） 只看错误
-b / -b -1 本次 / 上次启动 机器重启后查上一次
-k 只看内核消息 等价于 dmesg 持久化版
-o short-iso / -o json 输出格式 时间戳精确 / 给程序解析
--no-pager 不分页 脚本里必加
--disk-usage 日志占用 journal 占满磁盘时
-xe 显示上下文 + 跳转到末尾 systemctl status 的提示命令

3.2 生产实践案例：接口大量 5xx，定位问题接口

场景：API 接口出现大量 5xx 错误，需要快速定位问题接口。

处理结果：定位到 /api/v1/orders 接口因数据库慢查询导致超时，优化索引后 5xx 下降为 0。

3.3 动手验证：自造日志跑一遍完整管道

判定标准：第 2 步输出 /api/vX/itemY 的次数降序；第 3 步两行数字相加 = 1000（统计口径自洽）。管道里的每一段都可以单独 Ctrl-C 后重跑，这是日志分析和写代码最大的区别——先看中间结果，再决定下一步。

4. 在线诊断：JVM 与 Arthas

线上 Java 服务出问题，排查链路是固定的：先系统（top/vmstat）→ 再进程（top -Hp）→ 再 JVM（jstack/jstat）→ 再方法（Arthas）→ 最后代码。

graph TD
    A[Service Slow or CPU High] --> B[top -c: locate java pid]
    B --> C[top -Hp pid: hot thread TID]
    C --> D[jstack: match hex TID]
    D --> E[Arthas watch/trace: confirm method and params]
    E --> F[Fix code or config]
    B --> G[jstat -gcutil: GC pressure]
    G --> H[jmap / jcmd: heap dump]

4.1 JDK 自带工具

命令 核心选项 说明 使用场景
jps -l / -m / -v 列出 Java 进程（主类/参数/JVM 参数） 找 PID 第一步
jstack <pid> 线程栈（含锁信息） 死锁、卡顿、CPU 高
-l 附锁的附加信息（ownable synchronizers） 死锁排查必加
-F 进程无响应时强制 dump 卡死时
| grep -A 20 <hex_tid> 按线程 id 过滤（十六进制） 对接 top -Hp
jmap -heap 堆配置与使用概览 快速看堆
-histo:live 存活对象直方图 看什么对象最多（会触发一次 Full GC）
-dump:live,format=b,file=heap.hprof 导出堆快照 给 MAT 分析
jstat -gcutil <pid> 1000 10 GC 各区使用率，每秒 1 次共 10 次 看 GC 健康度

5.4 深挖：ExitCode 137 与容器 OOM

容器进程退出码不是随便编的：137 = 128 + 9，即被 SIGKILL 杀死。在容器里，能发出 SIGKILL 的通常就是内核 OOM Killer——因为 cgroup 的内存上限触发了内核的强制回收。串起来的因果链：

cgroup 限制了容器可用内存 → 进程超限时内核在 cgroup 内选「最胖」的进程杀 → 容器主进程（PID 1）被杀 → docker ps 显示 Exited (137) / K8s 显示 OOMKilled。

证据 来源 含义
docker inspect -f '{{.State.ExitCode}}' = 137 Docker 被 SIGKILL
kubectl describe pod 里 Reason: OOMKilled K8s 明确是内存超限
dmesg -T | grep -i oom 内核 宿主层面 OOM（可能是整机，不一定是容器）
docker stats 的 MEM USAGE / LIMIT Docker 实时逼近上限
JVM 场景：-XX:MaxRAMPercentage JVM 容器内默认只按 25% 限额用堆，堆外（元空间/线程栈/直接内存）超了照样 137

与 Docker 容器实战 里 cgroup 章节的呼应：--memory 限制的是整个 cgroup（堆 + 堆外 + 页缓存），不是 JVM 堆。Java 应用在 K8s 里 OOMKilled，一半的锅要分给「堆外内存没算进 limit」。

9.3 深挖：TIME_WAIT 与 CLOSE_WAIT 是两回事

ss -s 里两个高频「异常」，机制完全不同：

状态 谁产生的 机制 正确处理
TIME_WAIT 主动关闭方 等 2MSL（约 60 秒）确保最后的 ACK 到达、旧包在网络中消散 大量短连接客户端角色（网关、爬虫）会攒；用连接池/长连接减少，内核调优是运维的活
CLOSE_WAIT 被动关闭方 对端已 FIN，本端应用没有调用 close() 这是应用 bug：连接池没归还、异常分支没关流；ss -tnp state close-wait 找到进程去查代码

TIME_WAIT 不是故障，是协议在保证可靠性。作为后端，你该关注的是 CLOSE_WAIT 高 → 自己的代码漏关了连接，这是真正的 BUG。TIME_WAIT 高 → 说明你的服务短连接过多，方向是上连接池/长连接，而不是去改内核参数（那是运维的活）。

10.4 深挖：cron 的环境为什么和登录时不一样

cron 不经过登录流程，**不会读 /etc/profile、~/.bashrc**，拿到的是一份极简环境（PATH 通常只有 /usr/bin:/bin）。这是「手动执行成功、cron 执行失败」的第一大原因。四类差异与对策：

差异 表现 对策
PATH 不同 command not found 脚本开头 source /etc/profile，或全用绝对路径
工作目录不同 相对路径文件找不到 开头 cd /data/scripts
没有终端 tput、read、交互命令失败 脚本里禁用交互
环境变量缺失 JAVA_HOME 等未定义 在 crontab 顶部或脚本里显式定义

调试口诀：cron 任务就是「无 TTY、无 profile、无工作目录」的三无进程。写定时脚本时把自己当成一个刚登录的陌生用户来考虑。

10.5 动手验证：亲眼看到 cron 的环境差异

判定标准：cron 的 PATH 明显短于登录 shell（通常缺 /usr/local/bin 等）。这个实验做一次，以后所有「cron 不执行」的排查都会先想到环境。

4.2 一次请求在连接器中的完整生命周期

把上面的三类线程串起来，一个请求从到达 socket 到进入业务代码，经历的完整步骤：

sequenceDiagram
    participant C as Client
    participant OS as 内核 TCP 队列
    participant A as Acceptor
    participant P as Poller
    participant W as Worker 线程
    participant S as Servlet

    C->>OS: 三次握手，连接建立
    Note over OS: 连接进入 accept 队列<br/>（acceptCount 控制长度）
    A->>OS: accept() 取连接
    A->>P: 注册 SocketChannel 到 Poller
    Note over P: Selector 轮询<br/>等待可读事件
    C->>P: 发送 HTTP 请求数据
    P->>P: select() 返回可读
    P->>W: 提交 SocketProcessor 到线程池
    Note over W: 从队列取任务<br/>若队列满 → 拒绝
    W->>W: 解析 HTTP 协议<br/>生成 Request/Response
    W->>S: 调用 service()
    S->>S: 执行业务逻辑
    S-->>W: 返回响应
    W-->>C: 写回 socket

关键理解：

  1. Acceptor 只负责 accept()，不做任何 IO 读写；
  2. Poller 用 Selector 管理成千上万个连接，只检测「谁就绪了」；
  3. Worker 从线程池取任务，才真正解析协议 + 执行业务。

这就是「IO 与业务分离」的落地方式。

4.3 NIO 连接器内部组件

Tomcat NIO 连接器的核心内部类：

组件 职责
NioEndpoint NIO 连接器实现，管理 Acceptor / Poller / Worker
Acceptor 独立线程，循环调用 serverSocket.accept()
Poller 独立线程，持有 Selector，轮询就绪的 SocketChannel
PollerEvent Acceptor 注册连接的事件，放入 Poller 的队列
SocketProcessor 可运行任务，提交到 Worker 线程池执行协议解析
Http11Processor HTTP/1.1 协议解析器，生成 Request / Response
NioChannel 封装 SocketChannel + SocketBufferHandler
NioSelectorPool Selector 池，用于阻塞写（大响应时）

为什么 Poller 只有 1-2 个线程却能管几千连接？

因为 NIO 的 Selector.select() 是多路复用——一个线程就能监听成千上万个 Channel 的可读/可写事件。这是 NIO 相对 BIO 的核心优势。

4.4 三大参数详解

参数 含义 默认值 超了会怎样
acceptCount TCP accept 队列长度（OS 层 backlog） 100 队列满 → connection refused（直接拒绝新连接）
maxConnections 连接器保持的最大连接数（含等待中的） 10000（NIO） 满了不再 accept，连接在 accept 队列排队
maxThreads 工作线程池上限，同时处理的请求数 200 线程全忙 → 新请求在等待队列（内部队列）排队

更细的补充：

  • acceptCount 是 OS 层参数：本质是 listen(fd, backlog) 的 backlog，Linux 下会被 net.core.somaxconn 截断；
  • maxConnections 是 Tomcat 层参数：达到上限后，Tomcat 不再从 OS 队列里 accept，新连接积压在 OS 队列；
  • maxThreads 是业务层参数：线程全忙时，请求进入 Tomcat 内部的 TaskQueue（默认无界）排队——无界队列意味着不会拒绝，只会越堆越多直到超时。

相关参数补充：

参数 默认值 说明
minSpareThreads 10 最小空闲线程数，低于此值会创建新线程
threadPriority 5 线程优先级
connectionTimeout 20000ms 连接超时，超过后关闭连接
keepAliveTimeout 同 connectionTimeout keep-alive 超时
maxKeepAliveRequests 100 单连接最多复用多少次
maxHttpHeaderSize 8192 HTTP 头最大字节数
maxPostSize 2MB POST 表单最大字节数
maxSwallowSize 2MB 失败请求最多吞掉多少字节

为什么这样设计？两个核心原因：

理由 场景 双亲委派的问题
应用类隔离 同一 Tomcat 部署两个应用，各自带不同版本的 Spring 双亲委派会让先加载的版本被所有应用共享，版本冲突
热部署 应用重新部署时旧类加载器整体作废换新的 双亲委派下父加载器会缓存类，无法替换

边界（面试要答全）：

  • 对应用类（WEB-INF/classes、WEB-INF/lib）：先自己加载；
  • 对 javax.servlet.* 等 Servlet 规范类：仍然委派（容器自身规范类不能重载）；
  • 对 java.* 等 JVM 核心类：仍然委派 Bootstrap。

完整答案：『打破双亲委派有两个原因——多应用类隔离 + 热部署；但规范类与核心类仍走委派』，两个原因 + 边界都说全才是完整答案。

6.4 热部署与类加载器泄漏

热部署的原理：应用重新部署时，Tomcat 会丢弃旧的 WebappClassLoader 整个实例，创建新的加载器重新加载类。

sequenceDiagram
    participant Admin as 管理员
    participant Tomcat as Tomcat
    participant Old as 旧 WebappClassLoader
    participant New as 新 WebappClassLoader
    participant App as 应用

    Admin->>Tomcat: 重新部署 /app
    Tomcat->>Old: 停止所有 Servlet
    Tomcat->>Old: destroy() 释放资源
    Tomcat->>Old: 丢弃引用，等待 GC
    Note over Old: 如果无外部引用<br/>GC 会回收整个加载器<br/>连带所有类
    Tomcat->>New: 创建新 WebappClassLoader
    New->>App: 重新加载所有类
    App-->>Admin: 部署完成

类加载器泄漏：如果应用里有线程 / ThreadLocal / 静态变量持有 WebappClassLoader 的引用，旧加载器无法被 GC，导致 Metaspace OOM。

常见泄漏源：

  • ThreadLocal 未清理，且线程是 Tomcat 线程池的；
  • DriverManager 注册的 JDBC 驱动（Tomcat 会警告）；
  • 定时器线程未停止；
  • 自定义 ClassLoader 未释放；
  • 第三方库缓存了类加载器引用（如日志框架、Fastjson 的 ASM 缓存）。

排查方式：

Tomcat 自带的泄漏检测：context.xml 中配置 <Context clearReferencesStopThreads="true"> 可在应用停止时强制停止泄漏线程（有风险，生产慎用）。

Servlet 为什么单实例多线程？ 容器设计如此；实例变量是共享状态，必须线程安全
内嵌 Tomcat 与独立部署区别？ 架构相同；内嵌单 Context、生命周期由 Spring Boot 管理
Tomcat 启动流程？ Bootstrap → Catalina → Server → Service → Connector/Engine → Host → Context → Wrapper，逐层 init 后逐层 start
Tomcat 怎么优雅停机？ 停止接收新请求 → 等待处理中请求完成 → 销毁 Servlet → 关闭上下文
Tomcat 类加载器泄漏怎么排查？ jmap -clstats 看加载器数量；查 ThreadLocal、JDBC Driver、定时器
Tomcat 和 Jetty/Undertow 区别？ Tomcat 稳、生态好；Jetty 轻量；Undertow 高并发低内存

11.4 深挖：常见追问

Q1：Tomcat 的 maxThreads 设置多少合适？

没有固定值。IO 密集型可以 CPU × 2 以上（甚至 500+），CPU 密集型不超过 CPU 核数。关键看业务耗时：如果单请求 10ms，200 线程理论 QPS = 20000；如果单请求 1s，200 线程 QPS 只有 200。先压测，再定参。

Q2：Tomcat 为什么默认 maxThreads=200？

历史经验值。200 线程对多数 Web 应用足够，且不会因为线程过多导致上下文切换开销。但现代高并发场景常调到 400~800。

Q3：Tomcat 的 Connector 可以配多个吗？

可以。一个 Service 可以有多个 Connector（如 HTTP 8080 + HTTPS 8443 + AJP 8009），共享同一个 Engine。但生产建议只开必要的。

Q4：Tomcat 的 Session 和 Cookie 关系？

Session 存在服务端，通过 JSESSIONID Cookie 关联客户端。Cookie 被禁用时可用 URL 重写（;jsessionid=xxx），但不安全，生产建议只用 Cookie。

Q5：Tomcat 支持 HTTP/2 吗？

支持（Tomcat 8.5+）。配置 server.http2.enabled=true 或 <Connector><UpgradeProtocol className="org.apache.coyote.http2.Http2Protocol"/></Connector>。但 HTTP/2 需要 HTTPS 才生效（浏览器限制）。

Q6：Tomcat 的 WAR 和 JAR 部署区别？

WAR 是传统 Java Web 应用打包方式，丢进 webapps 自动解压部署；JAR 是 Spring Boot 内嵌方式，java -jar 启动。WAR 适合多应用共用 Tomcat，JAR 适合微服务独立部署。

Posted on 2026-08-13 In 系统设计 Word count in article: 3.3k Reading time ≈ 12 mins.

「设计一个短链系统」是系统设计题的常青树——它看着简单（不就是个映射吗），但面试官真正在考的是三件事：长 URL 怎么变成 7 位短码（发号与进制转换）、短码怎么存（分表 + 缓存分层）、跳转用 301 还是 302（状态码背后的业务意图）。 秒杀篇讲的是「写」场景（削峰、防超卖），短链篇讲的是「读」场景（缓存、布隆、热点）——两篇合起来，方法论的两个极端就都有了。读完你能在面试现场把这道题从头推到尾，并且说清每个选择的理由。

联动：本文是 系统设计方法论（需求澄清/容量估算/评估权衡）的第二个完整案例；与 秒杀系统设计（写场景）对照形成读写双案例；缓存分层与布隆过滤器复用 Redis 深度解析；发号器与分表复用 MySQL 高可用与分库分表实战、分布式系统核心理论（分布式 ID）。

1. 定位：这道题考什么

短链系统的需求一句话：输入任意长 URL，输出 7 位短码；访问短链时重定向到原长 URL（如 t.cn/Ab3dE9 → 长链接）。

它为什么高频：短链表面是「字符串映射」，实际覆盖了系统设计的读路径全部考点——容量估算、哈希与冲突、发号器、分库分表、缓存分层、布隆过滤器、热点防护、301/302 语义。一题考完「读场景」所有基本功，这是它和秒杀（写场景）互补的原因。

与秒杀的核心对照（面试立论用）：

维度 秒杀（上一案例） 短链
场景类型 写密集（下单） 读密集（跳转）
核心矛盾 瞬时流量洪峰 热点 key 与缓存击穿
关键中间件 Redis 预扣 + MQ 削峰 Redis 缓存 + 布隆过滤器

3. 核心机制一：短码生成——发号器 + 62 进制

3.1 为什么不用 MD5 截断

方案 问题
MD5 长 URL 截 7 位 哈希冲突概率随数据量上升，冲突要重算（循环）
随机短码 碰撞检测麻烦，每次生成要查重
发号器 + 62 进制 无冲突（号唯一）、可预测、可支持批量

短码 = 发号器拿到的自增 ID，转成 62 进制：ID=1 → "1"，ID=1000000 → "4c92"……7 位最多 62^7≈3.5 万亿个短码，用不完。

3.2 发号器三方案（面试核心）

方案 机制 优缺点
Redis INCR 单 key 自增 简单；Redis 挂影响发号，可持久化兜底
DB 号段（segment） 每次取一批号（如 1 万），内存发完再取 无网络往返、DB 压力小，生产主流
雪花算法 时间戳+机器号+序列号 无序、不可预测；但短码要「短」反而用它少见

因果链：发号器选型的关键是「发号频率 = 写入频率 = 日增 1000 万」——每次取号都打 Redis/DB 会打死存储，号段模式把「1 万次取号」合并成「1 次 DB 查询」（与 MQ 批量消费同一个思想：批量换吞吐）。面试答发号器：「DB 号段 + 内存发号」是标准答案，补一句『发号是写路径唯一瓶颈，所以必须批量』就是完整逻辑。

3.3 动手验证：号段发号的最小实现

观察点：前 1 万次调用只触发 1 次 DB 更新（UPDATE ... + 10000），之后全部内存返回。判定标准：能说出「DB 压力 = 日增 1000 万 ÷ 号段 1 万 = 每天 1000 次写」——发号从「每秒 115 次」降到「每天 1000 次」，这就是号段的威力。

4. 核心机制二：存储与读取——分表 + 缓存分层

4.1 存储设计

层 方案 理由
主表 MySQL，按短码 hash 分 64 表（short_url_0 ~ short_url_63） 10 年 365 亿条，单表 ~5.7 亿超阈值
路由 hash(short_code) % 64（或按 ID 段路由） 短码定表，读路径直查
冗余 主从 + 读写分离 读多写少，从库扛查询
索引 短码唯一索引 跳转按短码精确查

为什么分 64 表而不是 4 表：10 年数据量 × 单表 5.7 亿超红线（MySQL 单表 5000 万经验线）——分表数 = 总量 ÷ 单表容量，先把十年算完再定（细节见 MySQL 高可用与分库分表实战）。

4.2 缓存分层与布隆过滤器

flowchart LR
    C["客户端"] -->|短链访问 2W QPS| NG["网关/本地缓存<br/>(Caffeine, 毫秒级)"]
    NG -->|未命中| R["Redis 缓存<br/>(命中率 ~95%)"]
    R -->|未命中| BF{布隆过滤器<br/>短码存在?}
    BF -->|不存在| E["直接返回 404<br/>(拦掉无效短码)"]
    BF -->|可能存在| DB[("MySQL 分表")]
    DB -->|回填| R
    R -->|回填| NG

因果链（这一层是全题精华）：缓存未命中的请求会打到 DB——但无效短码（用户乱拼的）每次都不存在，会绕开缓存直接打 DB（缓存穿透），2 万 QPS 里若有 10% 无效请求，DB 每秒要扛 2000 次无效查询 → 布隆过滤器在 DB 前拦一层：不存在直接 404，存在才放行。布隆的代价是「可能误判存在」但不误判不存在——宁放行一次空查，不放过一次真查（布隆过滤器原理与实现见 Redis 深度解析）。

4.3 动手验证：布隆拦截无效短码

观察点：无效短码在布隆层即被拦，DB 零压力；写入短链时 BF.ADD 与 DB 同步（失败可容忍——误判只是多查一次）。判定标准：能说出布隆过滤器的取舍——「不存在的必拦，存在的可能漏拦（误判），所以它只防穿透、不防击穿」。

5. 核心机制三：301 vs 302 与热点防护

5.1 301 还是 302（面试高频追问）

状态码 语义 对短链的影响
301 永久重定向 浏览器/客户端缓存跳转结果，下次直接访问长链——后续请求不经过我们，但无法统计点击量、无法修改跳转目标
302 临时重定向 每次访问都先打我们的服务——可以统计、可以改目标，但服务压力大

面试标准答案：选 302——短链是营销/内容运营工具，点击统计和可修改性是产品刚需，牺牲一点服务压力换这两个能力。因果链：301 把控制权交给了客户端缓存，302 把每次访问留在自己手里——「要数据就要 302」。

5.2 热点短链防护

短链符合「二八定律」：20% 的短链扛 80% 的点击（爆款链接）。防护层次：

层 手段
本地缓存 Caffeine 短 TTL（秒级），挡住大部分热点
Redis 热点 key 天然被缓存吸收；单 key 打爆加本地缓存兜底
热点识别 计数器识别 topN 热点 → 加大本地缓存 TTL
限流 网关限流保护后端（见 秒杀篇 的限流章节）

因果链：读场景的雪崩风险是「热点 key 过期瞬间，大量请求同时打到 DB」——本地缓存（Caffeine）是第一层盾：Redis 挂了热点还在本地挡着。面试答「读场景高可用」的标准句式：「多级缓存 + 热点识别 + 网关限流」。

完整链路：写入（长链 → 发号取号 → 62 进制转短码 → 落 64 表 → 布隆 ADD → 缓存回填）；读取（短码 → 本地缓存 → Redis → 布隆 → DB → 逐级回填 → 302 跳转）。

7. 面试应答：短链六连问

7.1 完整话术

面试题 回答要点
短码怎么生成？ 发号器（DB 号段）取自增 ID → 62 进制转 7 位短码，无冲突
为什么不用 MD5？ 截断有冲突率，冲突处理复杂；发号器确定性无冲突
数据怎么存？ 按总量算分表（10 年 365 亿 → 64 表），短码唯一索引，主从读写分离
缓存穿透怎么防？ 布隆过滤器拦无效短码：不存在必拦，存在可能误判放行
301 还是 302？ 302：要点击统计与可修改性，每次访问留在自己手里
热点怎么防？ 多级缓存（Caffeine + Redis）+ 热点识别 + 网关限流
发号器挂了怎么办？ 号段模式 DB 压力极小；DB 用主从，主挂从顶上（号段不丢）

7.2 深挖：与秒杀的双案例对照（跨篇联动）

维度 秒杀（写场景） 短链（读场景）
核心矛盾 瞬时洪峰（写放大） 热点 + 穿透（读放大）
第一防线 限流（令牌桶/双层） 多级缓存（Caffeine→Redis）
中间件 MQ 削峰 + Redis 预扣 布隆过滤器 + Redis
容量重点 峰值 QPS 与库存原子性 总量 × 生命周期与命中率
最终兜底 对账 + 降级 302 语义 + 限流

一句话：秒杀教你怎么扛「一分钟的十万并发」，短链教你怎么扛「十年的每天两万」——一个是打（洪峰），一个是磨（长尾）。面试把两篇的对照讲出来，等于证明「方法论不是背的，是用的」。

8. 总结

8.1 面试速答表

面试题 一句话答案
短码生成方案？ 发号器（DB 号段）→ 62 进制，无冲突、可批量
号段发号原理？ 一次取 1 万号内存发放，DB 压力从每秒降到每天
为什么 64 张表？ 10 年 365 亿条 ÷ 单表 5.7 亿超线，分表数由总量反推
缓存穿透怎么防？ 布隆过滤器：不存在的必拦，存在的可能放行
301 vs 302？ 302：要统计与可改目标；301 把控制权交给客户端
热点怎么护？ 本地缓存 + 热点识别 + 限流，Redis 挂热点仍挡得住
缓存击穿怎么防？ 热点 key 永不过期 + 重建互斥锁（Redis 深度解析的经典方案）

症状 原因 处理
短码偶尔跳错 62 进制实现有歧义字符 去掉 0/O、1/l/I 等易混字符
