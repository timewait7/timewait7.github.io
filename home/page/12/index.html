Spring AI 与 LangChain4j 实战

本文是《AI学习体系导航》阶段二的核心实践篇，也是本站唯一的 Java AI 框架代码文：用 Java 生态把前几篇文章讲的能力（对话、流式、工具调用、RAG）实现一遍。协议原理见 LLM API与工具调用实战，RAG 全链路见 RAG原理与实践。

撰写时快照：本文基于 2026 年 8 月的 Spring AI / LangChain4j 版本撰写；两个框架迭代极快，依赖版本与 API 以官方文档为准。

一、为什么需要 Java AI 框架

1.1 现状：AI 生态主战场在 Python

LangChain、LlamaIndex、vLLM 等主流生态都是 Python 优先，Java 开发者直接照抄示例会遇到两个问题：示例跑不通、出了问题没有本地社区可问。Spring AI（Spring 官方）与 LangChain4j（社区）就是 Java 生态对这两个问题的回答——把”调用模型、组装 Prompt、管理对话、接入向量库、工具调用”抽象成 Java 惯用的形式。

1.2 框架解决什么

关注点 裸写（OkHttp 手拼） Spring AI / LangChain4j
模型调用 手写 HTTP + JSON 解析 ChatClient，一个接口
流式响应 WebFlux 手拼 SSE 流式 API 一行开启
工具调用 手写 schema + 循环回填 @Tool 注解即 schema
RAG 手写分块/向量化/检索链路 文档加载器 + VectorStore 开箱
多模型切换 改代码 配置切换，模型路由

1.3 与 Python 生态的关系

维度 Spring AI / LangChain4j LangChain / LlamaIndex
语言 Java/Kotlin Python
生态广度 覆盖主流场景 最全、新特性最快
工程集成 Spring Boot 原生（监控/配置/事务） 需自己接入
适合 Java 存量团队、企业系统集成 算法/原型团队

结论：不是二选一。团队里 Python 做实验与数据，Java 做生产服务（见第六章分工）。

二、Spring AI 核心

2.1 最小对话应用

ChatClient 是 Spring AI 的核心抽象：prompt() 组装输入、call() 同步调用、content() 取文本。一个接口屏蔽了协议细节——这就是 LLM API与工具调用实战 讲的”统一 Client 层”由框架代劳了。

2.2 流式响应

Controller 直接返回 Flux<String>（WebFlux 自动 SSE）——流式转发到前端零胶水代码。

2.3 系统指令与模板

system() / user() / variables() 对应 messages 的角色与模板变量——与 Prompt工程实战 的五要素模板完全对应。

2.4 工具调用：@Tool 注解

对比 LLM API与工具调用实战 第四章手写的 schema + 回填循环——框架把协议细节全部消化，方法签名即契约。

2.5 多模型路由

多个 ChatModel Bean + 配置化选择（对应成本章节的模型路由）：

简单任务走小模型、复杂任务走大模型——路由逻辑与 LLM API与工具调用实战 第七章同构，只是配置化。

三、Spring AI Alibaba

3.1 是什么

Spring AI Alibaba（阿里开源，spring-ai-alibaba）是 Spring AI 的阿里云生态实现：对接百炼平台（DashScope）的模型与服务，并提供企业级能力（Starter 自动装配、可观测性集成等）。

3.2 选择建议

场景 选择
国内合规 / 通义模型 Spring AI Alibaba（百炼）
国际模型 / 开源模型兼容 Spring AI OpenAI starter（base-url 指向任何兼容端点）
都要 两个 starter 共存，按模型路由

协议统一的好处再次体现：切换 = 换 starter + 换 api-key，业务代码不动。

四、LangChain4j

4.1 定位：Java 版的 LangChain

LangChain4j 提供与 LangChain 对应的抽象（LLM、Embedding、Document、EmbeddingStore、Retriever、Agent），但以 Java 类型安全方式实现——AI Services 是其招牌特性。

4.2 AI Services：接口即 AI

用接口定义 AI 能力——比直接调 SDK 更符合 Java 工程习惯：接口即契约，mock/测试/替换都容易。

4.3 工具绑定

4.4 RAG 全链路

对比 RAG原理与实践 的 Python 链路：概念完全对应（分块参数、检索器、上下文注入），只是换成了 Java 类型安全 API——这正是”原理不变、语言无关”的实证。

五、实战：两个交付物

5.1 交付物一：Spring AI 对话应用

  • Spring Boot 3.x + spring-ai-openai starter；
  • REST 接口：POST /api/chat（同步）+ GET /api/chat/stream（SSE 流式）；
  • 注册 2-3 个 @Tool（天气、计算器）；
  • 验证：curl 调用 + 流式前端页面。

5.2 交付物二：LangChain4j 知识库问答

  • 导入 10 篇真实文档（Markdown/PDF）；
  • 分块 → 向量化 → 入库（InMemory 起步，验证后换 Milvus）；
  • Assistant 接口 + contentRetriever 组装；
  • 验收（对齐 RAG原理与实践 标准）：20 个问题检索命中率 ≥ 90%、回答带引用。

5.3 常见坑

坑 表现 对策
依赖版本不一致 启动报 NoSuchMethodError starter 版本与 Spring Boot 版本对齐（看官方 BOM）
工具方法未注册 模型总说”没有可用工具” @Tool 类必须是 Spring Bean 且调用时 .tools() 传入

六、Java 与 Python 混合团队分工

环节 建议归属 理由

Prompt 调优 两侧协作 模板可共享（Prompt 与语言无关）

多智能体协作实战

Posted on 2026-08-04 In AI大模型 Word count in article: 2.3k Reading time ≈ 8 mins.

多智能体协作实战（LangGraph）

本文是《AI学习体系导航》阶段四/五的多智能体落地篇：Agent原理与实践 讲了单 Agent 的完整原理，本文讲多个 Agent 怎么协作——以 LangGraph（Python 生态最主流的 Agent 编排框架）为主线，覆盖核心概念、三种编排模式与一个完整项目。

撰写时快照：本文基于 2026 年 8 月 LangGraph 生态撰写；API 以官方文档为准，文中版本为撰写时主流版本。

一、为什么需要多智能体

1.1 单 Agent 的三个天花板

天花板 表现
上下文容量 一个 Agent 装不下”产品文档 + 用户画像 + 工具手册 + 历史”
职责混杂 一个 Agent 既当客服又当代码评审又当数据分析，指令互相干扰
单点决策 所有判断一个模型做，出错即全错

多智能体的思路：拆成多个”专才”，各管一摊，协作完成——和微服务拆分是同一种架构直觉。

1.2 适用场景判断

场景 单 Agent 多 Agent
步骤 < 5 的单工具任务 ✅ ❌ 过度设计
单一职责、上下文可控 ✅ ❌
多领域知识混合（文档+代码+数据） ⚠️ 勉强 ✅
需要并行调研多个方向 ❌ 串行慢 ✅ 并行
需要评审/对抗机制 ❌ ✅

铁律：单 Agent 能做的，不要上多智能体——多智能体的成本（N 倍 token、协调复杂度、失败放大）是实打实的。

1.3 主流框架对比

框架 定位 特点
LangGraph 图编排 显式状态图、可控性强、生产友好
AutoGen 对话式多 Agent 天然多 Agent 对话、研究友好
CrewAI 角色化团队 上手快、抽象高、定制受限

本文选 LangGraph：把 Agent 流程画成图（节点=步骤，边=流转），比”自由对话”更容易工程化——与 Java 的 BPM/状态机心智最接近。

二、LangGraph 核心概念

2.1 StateGraph：流程即图

LangGraph 的三个基本元素：

元素 类比 说明
State（状态） 共享变量 所有节点共享的结构化状态（如消息列表、中间结果）
Node（节点） 处理器 一个步骤（Agent、工具、普通函数）
Edge（边） 流转 连接节点；条件边按状态决定下一步

2.2 条件边：让图会”思考”

条件边是 LangGraph 的灵魂——按状态决定走哪条路（对应 ReAct 中”模型决定下一步”）：

2.3 与 Workflow 的区别

  • LangGraph 的图节点里可以放 LLM 调用——图是”动态路由”的，节点可反复执行（循环边）；
  • 支持循环（Agent 本质是循环）与并行（多个节点同时执行）；
  • 显式的状态与边 = 可观测、可暂停恢复、可测试——这正是生产系统需要的。

Java 对照：StateGraph ≈ 状态机 + 流程引擎（如 Spring StateMachine）；节点 ≈ 处理器 Bean，条件边 ≈ 路由规则。

三、三种编排模式

3.1 Supervisor

  • 主管 Agent 负责：理解任务 → 分派给对应专家 → 汇总结果；
  • 专家 Agent 各管一摊（客服、代码、数据），上下文互不污染；
  • 适用：职责清晰、可拆分的业务。

3.2 分层

  • 层层分解，顶层只管分派，底层只管执行；
  • 适用：大型任务（如企业级运营流程），副作用是深度增加、协调链路长。

3.3 对等

  • 平级协作：A 产出 → B 评审 → A 修改（对抗机制）；
  • 适用：方案评审、内容创作、代码 review——质量敏感场景。

3.4 选型表

模式 复杂度 成本 典型场景
Supervisor 中 中 客服分流、多领域助手
分层 高 高 大型流程编排
对等 低 中 评审、对抗、头脑风暴

起步建议：从 Supervisor 开始——结构清晰、收益直接；对等模式可作为质量兜底叠加。

四、团队分工设计

4.1 角色划分准则

准则 说明
按知识域划分 每个 Agent 一个领域（文档/代码/数据），上下文纯净
按工具集划分 工具随 Agent 走，避免全量工具暴露（安全）
接口明确 每个 Agent 的输入输出格式固定（结构化协议）
职责最小化 一个 Agent 只做一件事，可独立测试

4.2 结构化通信

Agent 之间不要传散文——用结构化消息：

结构化消息的好处：可校验、可追溯、可存档（全量消息日志 = 审计线索）。

4.3 冲突处理

多 Agent 结果矛盾时（评审不通过、数据不一致）：

策略 做法
主管裁决 主管 Agent 做最终决策
版本迭代 打回修改，最多 N 轮（防死循环）
人类介入 高代价决策升级人工（含权限场景，见 Agent安全与防护）

5.1 需求

一个”竞品调研助手”：用户给个产品方向，三个 Agent 协作产出调研报告。

5.3 验收标准

项 标准
流程正确性 三节点按预期流转，报告含”对比表 + 结论”

六、可靠性

6.1 与 Agent 主循环共用护栏

多智能体的每个节点 Agent 都有 Agent原理与实践 第六章的五道护栏（循环上限、超时、幂等、停止条件、补偿）；图层面再加两道：

图级护栏 说明
全局步数上限 整个图执行的总步数上限（防多 Agent 级联死循环）
节点级熔断 某 Agent 连续失败 N 次 → 跳过/降级到模板结果

6.2 成本控制

  • 多 Agent = 多份上下文 = 多份 token，预算先算后写：每个 Agent 的上下文预估 × 轮次 × 调用次数；
  • 简单步骤用小模型（路由/分类），复杂步骤才上大模型；
  • 共享状态里只传必要信息（结构化消息，不传全量历史）。

6.3 测试与观测

  • 图级测试：固定输入跑全流程，断言状态流转与最终输出（LangGraph 支持断点与状态快照，测试友好）；
  • 观测：每个节点记 trace（模型调用、工具调用、耗时、token），全流程一条 traceId（见 LLM评测与可观测性）。

Agent原理与实践

Posted on 2026-08-04 In AI大模型 Word count in article: 4.2k Reading time ≈ 15 mins.

Agent 原理与实践

本文是《AI学习体系导航》阶段四的核心深文，本站 Agent 的唯一原理专题：首次系统引入 ReAct 命名，把学习指南阶段四的四个模块（任务规划、上下文管理、记忆系统、工具调用）逐一展开，并覆盖 Agent 主循环的工程化（状态机、幂等重试）、可观测与安全。多智能体部分见 多智能体协作实战，安全纵深见 Agent安全与防护。

撰写时快照：本文基于 2026 年 8 月主流 Agent 技术栈撰写；模式（ReAct/Reflexion 等）有稳定论文出处，框架 API 以各框架文档为准。

一、Agent 是什么

1.1 定义：从”对话”到”做事”

LLM 应用的两个层级：

层级 形态 特征
Workflow（工作流） 预编排的固定链路 每个步骤做什么、顺序如何，全部提前写死
Agent（智能体） 模型自主决策的循环 模型决定下一步做什么、调什么工具、何时结束

区分一句话：控制权在谁手里。 Workflow 的控制权在代码，Agent 的控制权在模型。

1.2 Agent 循环的四个要素

一个 Agent 系统 = 模型（大脑）+ 工具（手脚）+ 记忆（经历）+ 循环（执行逻辑）：

要素 作用 对应本文章节
模型 决策：下一步做什么 二、任务规划
上下文 决策依据的”眼前状态” 三、上下文管理
记忆 跨会话的”长期经历” 四、记忆系统
工具 执行动作的接口 五、工具调用
循环 把上面串起来的控制流 六、Agent 主循环工程

Java 对照：Agent ≈ 一个”模型做决策”的状态机，工具 ≈ 注入的 Bean，记忆 ≈ 持久化存储，循环 ≈ 主流程编排。你已有的系统思维全部适用，唯一”黑盒”是决策函数（模型）。

1.3 Agent 适合做什么

任务类型 适合 Agent？ 理由
多步、多工具任务 ✅ 首选 中间步骤不可预测，需动态决策
步骤固定的流水线 ❌ 用 Workflow 固定链路更便宜、更快、更可控
单轮问答 ❌ 直接用 LLM Agent 是过度设计
高代价操作链 ⚠️ 谨慎 模型误判代价高，需安全护栏（第八章）

原则：能用 Workflow 解决的，不要上 Agent——Agent 的灵活性是用可控性换来的。

二、任务规划：ReAct 与它的继承者们

2.1 ReAct：推理与行动的交织

ReAct（Reasoning + Acting，Yao et al., 2022，论文《ReAct: Synergizing Reasoning and Acting in Language Models》）是最有影响力的 Agent 模式：把”思考”和”行动”交替输出，形成闭环。

三个关键输出类型：

输出类型 含义 示例
Thought 推理：分析现状、决定下一步 “用户要查北京天气，我需要先调用天气工具”
Action 行动：申请调用工具 get_weather(city="北京", date="明天")
Observation 观察：工具返回结果 “晴，22°C”

循环过程（这就是 LLM API与工具调用实战 第四章的 Function Calling 在 Agent 层面的展开）：

ReAct 的本质：让模型在”推理”与”行动”间交替，每一步都基于真实的工具反馈继续——这比让模型一次性”想完再答”可靠得多（错误可以在中途被观察结果纠正）。

2.2 从 ReAct 到 Plan-and-Execute

ReAct 的短板：局部决策——每步只想着下一步，复杂任务容易”走一步看一步”，缺乏全局计划。

Plan-and-Execute（Wang et al., 2023）拆成两阶段：

模式 优点 缺点 适用
ReAct 灵活、可中途纠错 复杂任务易迷失 步骤 < 10、反馈驱动
Plan-and-Execute 全局视野、可并行执行独立计划项 计划可能过时 多步骤、可预规划
两者混合 计划 + 每步 ReAct 验证 工程复杂度 生产级 Agent 常见形态

2.3 任务分解

无论哪种模式，分解能力是 Agent 质量的核心。实用的分解准则：

  • 原子性：每个子任务能用一步工具调用或一次推理完成；
  • 可验证性：每个子任务有明确的完成判定（不依赖”感觉”）；
  • 顺序标注：明确依赖关系（B 依赖 A 的输出）与可并行项（并行项可批量工具调用）。

Java 对照：任务分解 ≈ 把大接口拆成小方法的思维，加上依赖图（DAG）——你的拓扑排序直觉直接复用。

2.4 Reflexion：让 Agent 会反思

Reflexion（Shinn et al., 2023）：任务失败后，让模型写下失败原因，存进记忆，下次同类任务先读反思。

Reflexion 是把”试错成本”变成”系统资产”的机制——尤其适合重复性强的业务任务（客服、运维处置）。

三、上下文管理

3.1 上下文是 Agent 的”工作内存”

Agent 每轮循环都要把全部历史（用户问题、Thought、Action、Observation）塞进上下文，模型才能”记得”进行到哪。这是 Agent 区别于普通对话的关键工程点：循环 N 轮，上下文按 N 增长。

3.2 三个管理手段

手段 做法 适用
窗口裁剪 只保留最近 K 轮（Thought/Action/Observation 成组裁剪） 循环轮次少的场景
摘要压缩 早期过程让模型压成摘要，替换原文 长任务（10 轮+）
关键信息抽取 把过程中的事实（用户偏好、已完成步骤）抽成结构化状态 生产 Agent 推荐

3.3 关键设计：Observation 的”瘦身”

Observation 是上下文膨胀的最大源头——工具返回几 KB 原始数据，循环 10 轮就几十 KB。两条铁律：

  1. 工具返回前先精简：工具层过滤字段、截断、摘要（”只返回温度，不返回原始 JSON”）；
  2. Observation 必须结构化：固定 schema 的结果让模型更好理解，也便于窗口裁剪时丢弃。

Java 对照：上下文预算 ≈ 内存预算，Observation 瘦身 ≈ 接口返回 DTO 裁剪（只返所需字段）。你优化接口返回体积的习惯直接平移。

四、记忆系统

4.1 短期记忆与长期记忆

类型 存储 生命周期 典型内容
短期（会话内） 上下文窗口 一次会话 当前任务的过程与中间结果
长期（跨会话） 向量库 / 数据库 持久 用户偏好、历史事实、反思记录

短期记忆就是上下文（第三章），长期记忆是”模型之外的第二大脑”。

五、工具调用

5.1 工具是 Agent 的行动能力

没有工具的 Agent 只会”说”，有工具的 Agent 才能”做”：查数据库、调 API、发消息、操作文件。工具调用的协议细节（Schema 设计、并行调用、结果回填）见 LLM API与工具调用实战 第四章，本文聚焦 Agent 层面的工具治理。

5.2 工具治理三原则

原则 说明
数量克制 单个 Agent 暴露 5~15 个工具；工具太多，模型选择准确率断崖下降
描述即契约 工具描述决定模型能否正确选择——“什么场景用这个工具、参数含义”写清楚
错误可回填 工具异常转成结构化错误结果回填给模型，让它换方案，而不是中断循环

5.3 工具的分层：Agent 不该直接摸数据库

生产 Agent 的工具设计有个常见错误：直接暴露 SQL 执行工具。正确的分层：

Agent 只接触语义化工具——“create_ticket”而不是”execute_sql”。这既是安全边界（见 Agent安全与防护），也是质量边界（语义化工具的输入空间小，模型误用率低）。

5.4 MCP：工具的标准化接入

手写工具接入（Function Calling）每对接一个客户端就要实现一遍协议。MCP（Model Context Protocol）把工具接入标准化：一个 MCP Server 暴露的工具，任何支持 MCP 的客户端（Claude Code、IDE、自研 Agent）开箱即用。

Agent 侧集成 MCP 后，新增能力 = 注册一个新 MCP Server，不改 Agent 代码（类似微服务的服务注册）。完整实现见 MCP开发指南（修订版），概念辨析见 MCP与Agent Skill双轮驱动，本站三个真实 MCP 服务见 file-server-mcp、weathermate-mcp、ticket-agent-mcp。

6.2 循环的五道护栏

护栏 说明 Java 对照
循环上限 max_steps（如 15 轮）强制终止 防死循环 ≈ 防无限递归

七、多智能体概览

7.1 为什么要多智能体

单个 Agent 的局限：上下文容量有限、职责混杂、单点决策。多智能体把复杂任务拆给多个”专才”Agent 协作：

模式 结构 适用
Supervisor（主管-下属） 一个主管分派任务给多个专家 Agent 职责清晰、任务可拆
分层（Hierarchical） 多级上下级，层层分解 大型复杂任务
对等（Peer） 平级 Agent 互相讨论/评审 头脑风暴、评审

7.2 多智能体的代价

  • 成本翻倍：N 个 Agent 各自有上下文与模型调用；
  • 协调复杂度：消息格式、结果合并、冲突处理；
  • 失败放大：一个 Agent 的失误会顺着协作链传播。

决策原则：单 Agent 能做的，不要上多智能体。 多智能体的完整工程实践见 多智能体协作实战（LangGraph 三种编排模式 + 完整项目）。

八、可观测与安全

8.1 Agent 可观测性：过程比结果重要

Agent 的每一步（Thought/Action/Observation）都是审计线索——“为什么做这个决定”必须可回放：

观测项 记录内容
决策轨迹 每一步 Thought 原文（不可省！）
工具调用 工具名、参数、结果摘要、耗时
成本 每轮 token 消耗（Agent 成本 = 轮次 × 每轮成本）
状态流转 RUNNING → FINISHED/FAILED 及原因

Java 对照：这就是全链路 trace（traceId + span）——Agent 的 Thought/Action/Observation 就是天然 span 结构。完整体系见 LLM评测与可观测性。

8.2 Agent 安全基线

风险 对策（详见 Agent安全与防护）
提示注入（工具结果伪装指令） 工具输出与指令角色分离
工具滥用 语义化工具 + 权限校验 + 敏感操作二次确认
数据泄露 工具结果脱敏、最小化返回
失控循环 循环上限 + 熔断 + 人工介入通道

铁律：Agent 能调的工具 = 你信任它能犯错的工具。 把”模型可能误用工具”当成默认假设来设计权限。

Posted on 2026-08-04 In AI大模型 Word count in article: 4.5k Reading time ≈ 16 mins.

RAG 原理与实践

本文是《AI学习体系导航》阶段三的核心深文，也是本站 RAG 的唯一专题：从”为什么需要 RAG”到文档解析、分块、Embedding、检索、重排、上下文组装、评测迭代与工程化，覆盖生产级 RAG 系统的完整链路。Python 生态为主（unstructured / bge-embedding / LangChain / LlamaIndex / RAGAS），Java 侧以 Spring AI VectorStore 对照收尾。

撰写时快照：本文基于 2026 年 8 月主流 RAG 技术栈撰写；Embedding 模型与向量库版本演进较快，选型数据以文中标注为准。

一、为什么需要 RAG

1.1 大模型的三个固有缺陷

缺陷 表现 根因
知识过期 训练截止后的事实不知道 参数记忆有截止时间
私有知识缺失 公司内部文档、业务数据一概不知 训练数据不含私有语料
幻觉 一本正经编造不存在的事实 生成式模型本质是”合理续写”

RAG（Retrieval-Augmented Generation，检索增强生成）的解法朴素而有效：先检索、再生成——把相关文档检索出来塞进上下文，让模型”照着资料回答”。

1.2 RAG vs 微调 vs Prompt 调优：先决策再动手

方案 解决什么 成本 生效时机 适用场景
Prompt 调优 输出风格、格式 极低 即时 不涉及新知识
RAG 知识注入、防幻觉 低（向量库+调用费） 即时可更新 私有知识、动态知识、需要引用溯源
微调 学习行为模式、领域语言 高（训练+评测） 需训练周期 风格对齐、特殊格式、难以用资料表达的隐含知识

决策原则：知识问题用 RAG，行为问题才考虑微调。 大多数业务需求（FAQ、文档问答、业务助手）都是知识问题——这也是 LLM微调入门 的核心论点”微调是最后手段”的由来。

1.3 RAG 的适用边界

  • 适合：知识库问答、私域文档检索、动态资讯（产品文档、客服手册、法律法规）；
  • 不适合：纯推理题（检索帮不上）、创意生成（知识不是瓶颈）、实时性要求苛刻的超长文档（窗口装得下就别检索）。

二、文档解析与清洗

2.1 解析：从”文件”到”文本”

知识库的源文件千奇百怪：PDF、Word、Markdown、HTML、PPT、扫描件。解析的目标是无损地还原文档的逻辑结构（标题层级、表格、段落）。

格式 工具 要点
PDF pypdf / PyMuPDF / unstructured 区分文本型与扫描型（后者需 OCR）
Word python-docx 保留段落与表格结构
Markdown/HTML langchain-text-splitters / BeautifulSoup 保留标题层级（对分块至关重要）
表格 结构化解析为 Markdown 表格 表格转文字行会丢结构

黄金准则：解析要保结构。 标题层级是后续分块的锚点，表格转纯文本会严重损害检索质量。

2.2 清洗：脏数据是检索质量的隐形杀手

脏数据 影响 清洗手段
页眉页脚/页码 污染语义 正则/位置过滤
重复段落 检索冗余、涨分块数 相似度去重（Embedding 余弦 > 0.98 视为重复）
乱码/控制字符 解析异常 字符级清洗
无效文本（”第N页共M页”） 检索噪声 规则过滤 + 人工抽检

清洗阶段做得好，能省下游 80% 的调优时间。

三、Chunking 策略

3.1 为什么必须分块

  • 检索单元：Embedding 对整本书的向量会”平均化”，什么都像、什么都不像；
  • 上下文预算：窗口有限，检索结果只能塞进部分文本；
  • 引用精度：回答要能溯源到具体段落。

分块是 RAG 系统里性价比最高的调优点——同样的文档，分块好坏可差 10-20 个百分点的检索命中率。

3.2 四种主流策略

策略 做法 优点 缺点 适用
固定窗口 按 token/字符数硬切 简单、快 切断语义 兜底/海量文档
递归字符 按 \n\n → \n → 句子逐级切 保留段落边界 需调分隔符 通用首选
语义分块 按嵌入相似度找语义边界 块内语义内聚 计算成本高 语义跳跃大的文档
父子分块 小块检索 + 大块喂上下文 精度与信息量兼得 实现复杂 生产系统推荐

3.3 块大小与重叠

  • 块大小：200-800 token 是主流区间。块越小检索越精确但上下文越碎；块越大上下文越完整但噪声越多；
  • 重叠（overlap）：相邻块重叠 10-20%，防止关键句被切断；
  • 元数据：每个块携带来源（文档、章节、页码、更新时间）——这是引用溯源的基础。

Java 对照：分块 ≈ 日志/消息的分片策略。chunk 大小 ≈ 分片大小，overlap ≈ 分片重叠保护边界——你在 Kafka 分区设计里的直觉同样适用。

3.4 分块效果的实验方法

不要拍脑袋：对同文档跑 2-3 种分块配置，用 20 个典型问题 + 人工判断”检索到的块是否包含答案”，记录命中率。分块参数要在检索层面评测，而不是在生成层面凭感觉。

四、Embedding

4.1 Embedding 是什么

Embedding 把文本映射为固定维度（如 1024 维）的稠密向量，语义相近的文本在向量空间中距离更近：

相似度度量：余弦相似度（最常用）、内积、L2 距离。

4.2 模型选型

模型 特点 适用
text-embedding-3-small/large 云 API、无需自部署 快速起步
bge / BAAI 系列 中文效果好、可自部署 中文知识库、数据安全要求高
Qwen 系 Embedding 中文生态 中文 + 本地化
多模态 Embedding 文本+图片统一向量 图文知识库

关键决策：自部署 vs 云 API。 决定因素：数据敏感性（私有文档能否出网）、调用量成本、中文效果要求。自部署 Embedding 模型成本低（几 GB 显存），是私有知识库的常见选择（部署见 LLM推理与部署实战）。

4.3 批量与缓存

  • 批量：Embedding API 支持一次传多段文本（batch），显著降低成本与延迟；
  • 缓存：文档没变就不要重复向量化——按内容哈希缓存向量，增量更新场景必备（见第九章）；
  • 维度选择：同源 Embedding 维度必须一致，切换模型 = 全库重新向量化（这是重要的架构约束，选型前想清楚）。

五、检索原理

5.1 相似度检索与 Top-K

检索器的工作：把用户问题向量化 → 在向量库中找 Top-K 最相似的分块。K 的典型值 3-10：太小漏信息，太大噪声多、token 成本高。

5.2 元数据过滤

只靠语义相似度不够——业务上”只要近 30 天的文档””只检索某部门资料”是常态。过滤（filter）与检索（search）要分开做：先按元数据缩小候选集，再在候选集内做向量检索。

Java 对照：元数据过滤 ≈ SQL 的 WHERE 前置 + 召回排序。检索本质是”索引筛选 + 评分排序”，与 ES 查询心智完全一致。

5.3 混合检索（BM25 + 稠密向量）

稠密向量检索擅长语义匹配，但对精确词、编号、专有名词（”XJ-2024-0012”）常常失灵——这种场景传统的关键词检索（BM25）反而稳。混合检索 = 两条腿走路：

混合检索是生产级 RAG 的标配——纯向量检索在真实企业知识库（充满编号、术语、表格）上通常比混合检索低 5-15 个百分点。

5.4 多路召回

复杂的知识库可以同时走多路：向量检索（语义）、BM25（关键词）、SQL 精确查（结构化数据）、图检索（关系查询），最后融合。多路召回增加覆盖，代价是工程复杂度——先单路 + 混合检索跑通，再按评测数据决定是否加路。

六、Rerank

6.1 为什么需要重排

向量相似度是”近似语义匹配”，而相关性判断（”这段到底回答得了这个问题吗”）是更精细的任务。重排：先粗召回 Top-50，再用更强的模型精排成 Top-5。

阶段 模型 候选量 目标
召回 Bi-Encoder（快） 50-100 不遗漏
精排 Cross-Encoder（慢但准） 5-10 高精度

Bi-Encoder：query 和文档分别编码后算相似度（可离线建索引）；Cross-Encoder：query 与文档拼在一起过一遍模型（计算昂贵，只能在线小批量）。Cross-Encoder 的相关性判断显著更准。

6.2 Rerank 部署与延迟

  • Rerank 模型（如 bge-reranker）很小（百 MB 级），本地部署成本低；
  • 精排 50 个候选约几十毫秒到几百毫秒——只对粗召回结果做，延迟可控；
  • Rerank 后必须重新设置 Top-K 与置信度阈值，过滤低相关结果。

收益量化：业界实践普遍显示，加 Rerank 后检索命中率提升 5-15 个百分点，是 RAG 优化中投入产出比最高的单项。

七、上下文组装与生成

7.1 Prompt 模板：检索结果如何”喂”给模型

检索结果不是简单拼接——需要明确的指令边界：

关键设计：

  • 来源标注：每段资料带编号与出处，回答要求引用编号（溯源）；
  • 防幻觉指令：”仅基于资料回答 + 无答案明说”是 RAG 防幻觉的第一道防线；
  • 角色分离：资料与问题用明确分隔符区分，防止资料内容与指令混淆（安全边界，见 Agent安全与防护）。

7.2 引用溯源（citation）

回答带引用是 RAG 区别于”裸模型”的核心能力：

输出示例：退款通常 3-5 个工作日到账 [2]。

Java 对照：引用编号 ≈ 日志里的 traceId——回答可回溯到证据，是排查”答错了为什么”的关键基础设施。

7.3 长上下文的取舍

  • 检索结果塞得越多，上下文越长、成本越高、模型越容易”迷路”；
  • 原则：宁缺毋滥——Top-5 高质量块优于 Top-20 的噪声堆；
  • 超长上下文场景考虑：先摘要再生成，或分层检索（先检索章节，再在章节内检索段落——即父子分块的自然延伸）。

八、评测与迭代

8.1 评测的两个层面

层面 问题 指标
检索质量 该召回的是否召回 命中率、Recall@k、MRR
生成质量 回答是否忠实于检索结果 忠实度、答案相关性、上下文相关性

两个层面分开评：检索不好先修检索（分块/重排/混合检索），生成不好再修 Prompt——混在一起没法定位问题。

8.2 RAGAS 指标

RAGAS 是开源 RAG 评测框架，核心四个指标：

指标 衡量 直觉理解
忠实度（Faithfulness） 回答是否忠于检索资料 有没有编造
答案相关性（Answer Relevancy） 回答是否切题 有没有答非所问
上下文相关性（Context Relevancy） 检索结果与问题相关度 检索得准不准
上下文召回（Context Recall） 该有的资料是否都被检索到 有没有漏

8.3 评测集构建

  • 规模：起步 30-50 条，覆盖常见问题、边界问题、易混问题；
  • 真值：每条标注 ground_truth 答案 + 期望检索到的资料；
  • 迭代：评测集进 Git 管理，RAG 任何改动（分块参数、检索策略、Prompt）跑一遍回归，分数不降才上线（与 Prompt工程实战 的回归流程同构，完整体系见 LLM评测与可观测性）。

8.4 常见失败模式与优化清单

症状 排查方向 优化手段
该答的没答上 检索召回不足 混合检索、加大召回、分块优化
答非所问 检索结果与问题错位 Rerank、过滤规则、query 改写
回答编造 生成层没守住 防幻觉指令、引用溯源、降温度
答得泛 上下文太碎 父子分块、加大块大小

九、工程化

9.1 增量更新与去重

知识库是动态的（文档改版、新文档上线），工程上必须支持增量：

能力 实现
内容哈希去重 文档内容哈希 → 未变化跳过向量化
文档级版本 同一文档多版本 → 只检索最新版（元数据过滤）
删除传播 文档下线 → 删除其所有分块（向量库按 doc_id 批量删）

9.2 缓存

  • Query 缓存：完全相同的问法（精确或近似）命中缓存，直接返回——客服场景命中率可观；
  • 向量缓存：分块未变不重复 Embedding（见 4.3）。

9.3 延迟与成本

手段 收益
向量检索毫秒级（HNSW） 检索不是瓶颈（见 向量数据库原理与实践）
Rerank 只精排粗召回 延迟 +100~300ms 可控
Prompt 缓存（模板固定） 输入 token 成本降约 90%
检索结果大小控制 每少 100 token × 万次调用 = 真金白银
