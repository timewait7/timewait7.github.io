Java 后端面试导航

Posted on 2026-08-06 In Java Word count in article: 8.7k Reading time ≈ 31 mins.

本文是 Java 后端面试知识体系的导航枢纽 + 高频题速查。知识内容已按专题拆分为多篇文章深度重写（每篇按”为什么 → 怎么实现 → 代码/案例”组织），本文只做三件事：

  1. 路线图（第 1 节）：按经验年限给出准备重点与时间分配。
  2. 导航（第 2~8 节）：按专题链接到各文章，标注覆盖范围、重点章节与版本要点。
  3. 速查（附录）：50 道高频面试题，按”问题 → 答案要点 → 详见某专题”整理，其中 HashMap 底层对比、Redis 数据类型应用、分布式锁完整实现链等原文内容完整保留。

原文件中的外部链接索引（javaguide.cn、微信公众号、知识星球推广等）已全部移除，答案要点以自研为准，展开阅读见各专题文章。

1. 面试准备路线图

按经验年限划分准备重心。总体周期建议 6~8 周：前 3-4 周按专题过知识点，中间 2 周刷题 + 手写 SQL/算法，最后 1-2 周做模拟面试与查漏补缺。

阶段 面试考察重点 准备重心 时间分配建议
应届生 / 校招 基础广度 + 算法 + 项目（课设/实习） Java 基础与集合、网络/OS 基础、手写 SQL、LeetCode 常考题、实习项目深挖 基础 30% / 算法 30% / 项目 20% / MySQL+Redis 15% / 模拟面试 5%
1-3 年 基础深度 + 框架 + 真实业务项目 并发/JVM、Spring 全家桶、MySQL 索引与事务、Redis、项目中的性能与排查细节 Java 30% / 数据库 25% / 框架 20% / 项目 15% / 算法+网络 10%
3-5 年 中间件 + 分布式 + 系统设计 Kafka/ES/Dubbo、分布式理论（CAP/一致性/事务/锁/ID）、系统设计题、线上问题排查案例 分布式与中间件 35% / 系统设计 25% / 项目深挖 25% / 八股查漏 15%
5 年+ 架构决策 + 团队/业务视角 系统设计与 DDD、技术选型对比（每个选型说得出代价）、故障复盘、团队协作案例 系统设计 40% / 项目复盘 40% / 新趋势与查漏 20%

备考通用要点（踩坑总结）：

  1. 尽早准备。技术面试不同于编程，会写代码不代表面试能过，每个知识点要能讲出为什么，并尽量结合项目里的一次真实使用。
  2. 多面试、多复盘：每场面试后把被问倒的题目记进薄弱清单，针对性补。
  3. 熟悉简历里的每个细节：数据量、并发量、表结构、接口设计、瓶颈与优化，都要经得起追问。
  4. 目标差异：国企/小厂重项目与基础广度，大厂重深度、场景题与系统设计。
  5. 学历一般时，把重心放到项目经历上，项目是证明工程能力最有力的部分。
  6. 电话/视频面试提前调试环境；面试后及时复盘，失败是常态，保持节奏。

Spring Boot 3.x 关键变化（面试常被追问”你用的什么版本”，老项目升级必考）：

  • 基线 **JDK 17+**（Boot 2.7 仍支持 JDK 8）。
  • javax.* → **jakarta.***：基于 Servlet 5.0 / 内嵌 Tomcat 10，第三方库需同步升级（@PostConstruct 等注解 import 需改）。
  • 自动配置注册从 META-INF/spring.factories 迁移到 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports + @AutoConfiguration 注解：2.7 起推荐，3.x 已完全移除旧方式。
  • 默认使用 CGLIB 代理（2.0 起即默认，接口代理需显式配置）。

共 50 题，按主题分组。”答案要点”是速查记忆锚点，完整推导与代码见对应专题文章（括号内为章节）。

A. Java 基础

1. String、StringBuffer、StringBuilder 的区别？String 为什么不可变？

  • 要点：String 不可变且线程安全（每次修改产生新对象）；StringBuffer 可变、方法加 synchronized 安全但慢；StringBuilder 可变、非安全但最快（单线程首选）。不可变原因：字符串常量池复用、hashCode 可缓存、安全（不会被子类/并发修改）、可作常量。
  • 详见：Java 核心基础 第 2 节

2. String s1 = new String("abc"); 创建了几个对象？

  • 要点：常量池中没有 "abc" 时创建 2 个（常量池 1 个 + 堆 1 个），已有则只创建 1 个（堆）。intern() 可把堆字符串放入常量池。
  • 详见：Java 核心基础 第 2 节

3. == 与 equals 的区别？hashCode 与 equals 的关系？

  • 要点：== 比引用地址；equals 默认同 ==，重写后比内容（String 重写过）。重写 equals 必须重写 hashCode：两个对象 equals 相等则 hashCode 必相等（反之不成立），否则基于哈希的集合（HashMap/HashSet）会错乱。
  • 详见：Java 核心基础 第 2 节

4. 包装类型的缓存机制？自动装箱/拆箱原理？

  • 要点：Integer 缓存 -128127（valueOf 命中缓存返回同一对象，new Integer 不缓存），Character 缓存 0127，Boolean 缓存 true/false，Long/Short/Byte 缓存全部范围（-128~127）。装箱调 valueOf，拆箱调 xxxValue()。缓存范围外的值用 == 比较会踩坑。
  • 详见：Java 核心基础 第 2 节

5. Java 反射？有什么缺点？为什么框架需要反射？

  • 要点：反射在运行时获取类的结构（Class 对象 → 构造器/字段/方法）并动态调用。优点：动态性、解耦（框架不需要在编译期知道具体类）；缺点：性能开销（调用绕过 JIT 优化）、破坏封装、安全问题。Spring 通过反射实例化 Bean、注入依赖、代理拦截。
  • 详见：Java 核心基础 第 2 节

6. Java 泛型？什么是类型擦除？常用通配符？

  • 要点：泛型是编译期检查，运行时擦除为 Object + 强制转换（桥方法保持多态）。? extends T 上界限定，只读；? super T 下界限定，可写（PECS：生产者 extends，消费者 super）。
  • 详见：Java 核心基础 第 2 节

7. 哪些集合是线程不安全的？怎么解决？

  • 要点：ArrayList/HashMap/HashSet 均不安全（HashMap 并发 put 可能丢数据甚至死循环，1.8 修复了扩容死循环）。解决：Collections.synchronizedXxx（整对象加锁）、CopyOnWriteArrayList（读多写少）、ConcurrentHashMap（分段/桶级锁）、Vector/Hashtable（全锁，不推荐）。
  • 详见：Java 核心基础 第 3 节

8. HashMap 的底层实现（1.7 vs 1.8）？

JDK 版本 底层数据结构 冲突解决
JDK 1.7 数组 + 链表 拉链法（头插法，扩容 rehash 在并发下可能成环）
JDK 1.8 数组 + 链表 + 红黑树 链表长度 > 8 时：数组长度 < 64 先扩容，否则链表转红黑树；尾插法
  • 要点：默认容量 16、负载因子 0.75；key 可为 null（HashMap 允许，Hashtable 不允许）；hash = h ^ (h >>> 16) 扰动后 (n-1) & hash 定位。
  • 详见：Java 核心基础 第 3 节

9. HashMap 长度为什么是 2 的幂？ConcurrentHashMap 线程安全实现？

  • 要点：容量 2 的幂使 (n-1) & hash 等价于取模且更快，扩容时元素要么留在原位、要么移到 原位置 + 旧容量，重排开销小。ConcurrentHashMap：1.7 分段锁（Segment 继承 ReentrantLock，默认 16 段）；1.8 放弃分段锁，CAS + synchronized 锁链表/红黑树首节点，支持并发扩容，并发度更高。
  • 详见：Java 核心基础 第 3 节

B. Java 并发

10. sleep() 和 wait() 的区别？

  • 要点：sleep 来自 Thread，不释放锁，必须处理中断；wait 来自 Object，释放锁并进入等待队列，必须在 synchronized 块中调用，由 notify/notifyAll 唤醒。
  • 详见：Java 并发编程 第 1 节

11. volatile 解决了什么问题？与 synchronized 的区别？

  • 要点：volatile 保证可见性 + 禁止指令重排，不保证原子性（i++ 仍不安全），适用状态标志/单写场景。synchronized 保证可见性 + 原子性 + 有序性。JMM 下通过 happens-before 原则判断可见性。
  • 详见：Java 并发编程 第 2 节

12. synchronized 的锁升级过程？与 ReentrantLock 的区别？

  • 要点：无锁 → 偏向锁 → 轻量级锁（自旋）→ 重量级锁（monitor，阻塞）；JDK 15 起默认禁用偏向锁。ReentrantLock：可中断/可超时、公平锁可选、Condition 分组唤醒，基于 AQS。
  • 详见：Java 并发编程 第 3、4 节

13. ThreadLocal 的作用？内存泄漏问题？

  • 要点：每个线程持有一个 ThreadLocalMap，key 为 ThreadLocal 的弱引用，value 为强引用。key 被 GC 回收后 value 无法访问即泄漏（线程池复用线程时更严重）。解决：用完后显式 remove()；set/get 时会顺带清理过期 entry。
  • 详见：Java 并发编程 第 6 节

14. 线程池的参数、处理流程、拒绝策略？为什么不推荐内置线程池？

  • 要点：7 参数（corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler）；流程：核心线程 → 阻塞队列 → 最大线程 → 拒绝。4 种拒绝策略：AbortPolicy（抛异常）/ CallerRunsPolicy（调用者执行）/ DiscardPolicy / DiscardOldestPolicy。Executors 的问题：FixedThreadPool 无界队列（OOM）、CachedThreadPool 最大线程数 Integer.MAX（线程爆炸）。生产用 ThreadPoolExecutor 自定义参数并命名线程。
  • 详见：Java 并发编程 第 5 节

15. AQS 原理了解吗？基于它的组件有哪些？

  • 要点：AQS 维护 volatile state + CLH 双向等待队列，提供独占/共享两种模式与模板方法。基于它：ReentrantLock（独占）、Semaphore（共享计数）、CountDownLatch（共享，计数减到 0 放行）、ReentrantReadWriteLock（读写分离）。
  • 详见：Java 并发编程 第 4 节

16. 多个任务的编排怎么做？CompletableFuture 怎么用？

  • 要点：串行 thenApply/thenCompose、并行 allOf/anyOf、异常恢复 exceptionally/handle、回调线程池 thenApplyAsync。相比 Future.get 阻塞与 CountDownLatch 手写编排，CompletableFuture 声明式组合，项目里可用来并行查询多个接口后合并。
  • 详见：Java 并发编程 第 7 节

C. JVM

17. 运行时数据区有哪些区域？哪些共享？哪些会出现 OOM？

  • 要点：线程共享：堆、方法区（元空间）；线程独享：虚拟机栈、本地方法栈、程序计数器。OOM 可能出现在堆、元空间、直接内存（栈溢出是 StackOverflowError，程序计数器唯一不会 OOM）。
  • 详见：JVM 原理与调优 第 1 节

18. 如何判断对象是否死亡？可达性分析中哪些对象是 GC Roots？

  • 要点：引用计数法无法解决循环引用，JVM 用可达性分析：从 GC Roots 出发不可达即死亡。GC Roots：虚拟机栈中的引用、静态属性引用、常量引用、JNI 引用、同步锁（monitor）持有的对象等。
  • 详见：JVM 原理与调优 第 2 节

19. 垃圾收集有哪些算法？CMS 与 G1、ZGC 各自特点？

  • 要点：标记-清除（碎片）、复制（存活少时高效，浪费空间）、标记-整理（老年代）。CMS 四步：初始标记 → 并发标记 → 重新标记 → 并发清除，缺点：浮动垃圾、内存碎片、并发失败退化 Serial Old。G1：Region 化、可预测停顿、RSet + 写屏障。ZGC：染色指针 + 读屏障，停顿毫秒级。
  • 详见：JVM 原理与调优 第 4 节

20. 双亲委派是什么？为什么需要？如何打破？

  • 要点：类加载请求自底向上委派，Bootstrap → Platform → Application，只有父加载器加载不了才向下。好处：避免重复加载、防止核心类被篡改。打破：Tomcat 每个 Webapp 独立类加载器（先加载自己的类）；JDBC SPI 通过线程上下文类加载器加载实现类。
  • 详见：JVM 原理与调优 第 3 节

21. 如何降低 Full GC 的频率？

  • 要点：避免大对象直接进老年代（大对象频繁触发并发失败）；合理设置新生代/老年代比例，让对象在新生代被回收；减少 System.gc()（RMI 等会触发）；检查内存泄漏（静态集合、ThreadLocal 未 remove）；堆大小与 GC 器参数配合（G1 下控制 Region 大小与停顿目标）。
  • 详见：JVM 原理与调优 第 5 节

D. Spring

22. 谈谈对 Spring IoC 和 AOP 的理解？

  • 要点：IoC 把对象创建与依赖装配的控制权反转给容器（DI 是落地手段），解耦 + 统一生命周期管理。AOP 把日志/事务/安全等横切逻辑织入业务代码之外，基于动态代理（接口优先 JDK 代理，否则 CGLIB）。
  • 详见：Spring 深度解析 第 1、4 节

23. Spring Bean 的生命周期？

  • 要点：实例化 → 属性填充 → Aware 回调（BeanName/ApplicationContext）→ BeanPostProcessor#postProcessBeforeInitialization → 初始化（InitializingBean/init-method）→ BeanPostProcessor#postProcessAfterInitialization（代理在此生成）→ 使用 → 销毁。
  • 详见：Spring 深度解析 第 2 节

24. Spring 如何解决循环依赖？

  • 要点：三级缓存——singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（工厂，提前暴露对象）。A 创建时把 A 的工厂放第三级，B 依赖 A 时经工厂拿到 A 的早期引用。构造器注入无法解决循环依赖；Boot 2.6+ 默认禁止循环依赖；AOP 场景依赖第三级缓存提前代理。
  • 详见：Spring 深度解析 第 3 节

25. Spring Boot 的自动配置是如何实现的？

  • 要点：@SpringBootApplication 含 @EnableAutoConfiguration，通过 META-INF/spring/...AutoConfiguration.imports（3.x）加载自动配置类，结合 @ConditionalOnClass/@ConditionalOnMissingBean 等条件注解按需装配；用户自定义 Bean 优先于自动配置（@ConditionalOnMissingBean 兜底）。
  • 详见：Spring 深度解析 第 6 节

26. @Transactional 失效的场景有哪些？

  • 要点：方法非 public；同类内部调用（this 调用走不到代理）；异常被 catch 吞掉；抛出 checked 异常且未指定 rollbackFor（默认只回滚 RuntimeException）；final/static 方法；传播行为设置不当（如 REQUIRES_NEW 处理不当）。
  • 详见：Spring 深度解析 第 7 节

E. MySQL

27. 事务的四大特性？MySQL 的隔离级别？

  • 要点：ACID（原子性、一致性、隔离性、持久性）。4 种隔离级别：读未提交（脏读）/读已提交（不可重复读）/可重复读（幻读）/串行化。InnoDB 默认 RR，用 MVCC（快照读）+ Next-Key Lock（当前读）解决幻读。
  • 详见：MySQL 原理与优化 事务节

28. InnoDB 对 MVCC 的具体实现？

  • 要点：每行隐藏列 trx_id（最近修改事务）、roll_pointer（指向 undo 版本链）；快照读按 ReadView（m_ids/up_limit_id/low_limit_id/creator_trx_id）沿版本链找可见版本；RR 下第一次查询生成 ReadView 并复用（当前读除外，当前读走当前最新版本 + 锁）。
  • 详见：MySQL 原理与优化 事务节

29. 最左前缀匹配原则？什么是覆盖索引？索引失效场景？

  • 要点：组合索引按最左顺序匹配，跳过中间列会部分失效（可用索引下推优化）；覆盖索引指查询列全部在索引中，不回表；失效：违背最左前缀、对索引列做函数/运算/隐式类型转换、LIKE '%xx'、OR 连接非索引列、优化器评估全表扫描更优。
  • 详见：MySQL 原理与优化 索引节

30. B+ 树做索引比红黑树、Hash 好在哪里？

  • 要点：B+ 树矮胖、层高 3~4，磁盘 IO 少；非叶子节点只存键，单页容纳更多记录；叶子节点链表有序，支持范围查询与排序；对比 Hash 索引：单点 O(1) 但不支持范围、无法排序。红黑树/二叉查找树高度高、随机 IO 多，不适合磁盘场景。
  • 详见：MySQL 原理与优化 索引节

31. redo log、binlog、undo log 的区别？为什么需要两阶段提交？

  • 要点：redo log 是 InnoDB 物理日志（页修改，循环写），崩溃恢复保证持久性（WAL：先写日志再刷盘）；binlog 是 Server 层逻辑日志（归档/主从复制）；undo log 记录回滚版本，保证原子性并支撑 MVCC。两阶段提交保证 redo 与 binlog 一致，避免主从数据与恢复结果不一致。
  • 详见：MySQL 原理与优化 日志节

32. InnoDB 有哪几类行锁？Next-Key Lock 的加锁范围？

  • 要点：记录锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock = 记录锁 + 间隙锁）；意向锁是表级。RR 下范围条件默认加 Next-Key Lock（含间隙），唯一索引等值命中退化为记录锁；RC 只加记录锁。
  • 详见：MySQL 原理与优化 锁节

F. Redis

33. Redis 为什么这么快？6.0 为什么引入多线程？

  • 要点：内存存储；单线程命令执行避免锁竞争与上下文切换；IO 多路复用（epoll）监听大量连接；高效数据结构（SDS/quicklist/listpack/跳表）；渐进式 rehash。6.0 的多线程只处理网络 IO 读写，命令执行仍单线程——因为瓶颈是网络 IO 而非 CPU，且要保证命令原子性。
  • 详见：Redis 深度解析 第 3 节

34. String 的底层实现？为什么用 SDS？为什么用跳表而不用红黑树/B+ 树？

  • 要点：SDS 保存 len，O(1) 获取长度、避免缓冲区溢出、二进制安全、预分配减少扩容次数。跳表 vs 红黑树：实现简单、范围查询天然有序；vs B+ 树：内存中不需要页级 IO 优化，跳表足够且分层可调。
  • 详见：Redis 深度解析 第 2 节

35. 宕机了，Redis 如何避免数据丢失？RDB 和 AOF 如何选择？

  • 要点：RDB 全量快照（fork 子进程写临时文件后原子替换，恢复快、可能丢最近数据）；AOF 追加写（everysec 默认，最多丢 1 秒，文件大需重写）；4.0+ 混合持久化（RDB 头 + AOF 增量）。选型：允许丢数据、重启快用 RDB；高可靠用 AOF/混合。
  • 详见：Redis 深度解析 第 4 节

36. 缓存穿透、击穿、雪崩分别是什么？怎么解决？

  • 要点：穿透（查不存在的数据打穿到 DB）：布隆过滤器 / 缓存空值（带短过期）/ 参数校验；击穿（热点 key 过期瞬间被并发打爆）：互斥锁重建缓存 / 逻辑过期；雪崩（大量 key 同时过期或 Redis 宕机）：过期时间加随机值 / 集群高可用 / 限流降级 / 缓存预热。
  • 详见：Redis 深度解析 第 6 节

37. 有缓存的情况下如何保证数据一致性？

  • 要点：主流 Cache Aside——读：先查缓存，miss 读库回填；写：先更新 DB 再删除缓存（删除而非更新，避免并发写脏）。可加延迟双删、删除失败走消息队列/订阅 binlog 重试。强一致场景需引入分布式锁或旁路对账。

G. 网络

41. TCP 为什么三次握手、四次挥手？

  • 要点：三次握手能确认双方收发能力都正常，且能阻止历史重复连接（比两次握手多一个”确认旧 SYN 已被丢弃”的校验，四次则多余）。四次挥手因为断开是半关闭：收到 FIN 后可能还有数据要发，ACK 与 FIN 分开，主动方最后等 2MSL（保证对方收到 FIN-ACK、让旧报文消亡）。
  • 详见：无专题文章，答案要点供自检，需展开请自行整理笔记

42. TCP 如何保证传输可靠性？

  • 要点：序号 + 确认应答；超时重传与快速重传（收到 3 个重复 ACK）；滑动窗口流量控制（防接收方被打爆）；慢启动/拥塞避免/快恢复拥塞控制（防网络被打爆）；校验和；数据分段与有序重组。
  • 详见：无专题文章，答案要点供自检

43. HTTPS 的加密过程？常见状态码？

  • 要点：对称加密快、非对称慢，HTTPS 用非对称交换密钥、对称加密数据：客户端验证 CA 证书 → 通过 ECDHE（前向安全）或 RSA 交换出会话密钥 → 之后全部对称加密。状态码：200 OK / 301 永久重定向 / 302 临时 / 304 缓存 / 400 参数错误 / 401 未认证 / 403 无权限 / 404 / 429 限流 / 500 / 502 / 503。
  • 详见：无专题文章，答案要点供自检

44. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

  • 要点：1.1 长连接 + 管线化（存在队头阻塞）；2.0 二进制分帧 + 多路复用（单连接并发请求，仍受 TCP 层队头阻塞）、HPACK 头部压缩、Server Push；3.0 基于 UDP 的 QUIC：0-RTT、连接迁移、彻底解决队头阻塞。

  • 要点：饿汉（类加载即初始化）；懒汉 DCL + volatile（双检锁，防指令重排）；静态内部类（推荐，懒加载 + 无线程同步开销）；枚举（最推荐：天然线程安全、防反射与序列化破坏）。Spring 的 Bean 默认是单例（容器级）。

47. CAP 定理与 BASE 理论？Raft 是怎么工作的？

七、实战：五步拆解法

遇到任何人生难题，按此流程走一遍（30-60分钟，用笔记写下每一步）：

一、为什么需要多智能体

1.1 单 Agent 的三个天花板

天花板 表现
上下文容量 一个 Agent 装不下”产品文档 + 用户画像 + 工具手册 + 历史”

多智能体的思路：拆成多个”专才”，各管一摊，协作完成——和微服务拆分是同一种架构直觉。

1.2 适用场景判断

铁律：单 Agent 能做的，不要上多智能体——多智能体的成本（N 倍 token、协调复杂度、失败放大）是实打实的。

2.1 StateGraph：流程即图

2.3 与 Workflow 的区别

  • LangGraph 的图节点里可以放 LLM 调用——图是”动态路由”的，节点可反复执行（循环边）；
  • 支持循环（Agent 本质是循环）与并行（多个节点同时执行）；

三、三种编排模式

3.1 Supervisor

  • 主管 Agent 负责：理解任务 → 分派给对应专家 → 汇总结果；
  • 专家 Agent 各管一摊（客服、代码、数据），上下文互不污染；
  • 适用：职责清晰、可拆分的业务。

3.2 分层

  • 层层分解，顶层只管分派，底层只管执行；
  • 适用：大型任务（如企业级运营流程），副作用是深度增加、协调链路长。

3.3 对等

  • 平级协作：A 产出 → B 评审 → A 修改（对抗机制）；
  • 适用：方案评审、内容创作、代码 review——质量敏感场景。

6.2 成本控制

  • 多 Agent = 多份上下文 = 多份 token，预算先算后写：每个 Agent 的上下文预估 × 轮次 × 调用次数；
  • 简单步骤用小模型（路由/分类），复杂步骤才上大模型；
  • 共享状态里只传必要信息（结构化消息，不传全量历史）。
