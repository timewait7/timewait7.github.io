Zeus-Doc 架构设计与技术选型

Posted on 2026-08-06 In 项目实战 Word count in article: 5.5k Reading time ≈ 20 mins.

一、项目概述

Zeus-Doc 是面向多租户企业的知识库文档中台，提供文档创作、协同编辑、全文检索、文件存储、审计追溯等完整能力。系统采用 Spring Cloud 微服务架构，按业务边界拆分为 6 大核心服务 + 1 个网关，背后由 MySQL、Redis、Elasticsearch、MinIO、RocketMQ 等中间件支撑。

核心业务能力：

  • 文档 CRUD + 版本管理（全量快照 + Diff-Match-Patch 增量补丁）
  • 三级缓存（Caffeine → Redis → MySQL）+ 布隆过滤器 + 互斥锁重建
  • 实时协同编辑（Netty WebSocket + OT 算法合并）
  • ES 全文检索（高亮 + 聚合 + Sentinel 熔断降级）
  • 大文件分片上传 + 零拷贝合并（MinIO）
  • 审计日志分库分表（ShardingSphere）+ Seata TCC 分布式事务

二、需求分析与系统边界

2.1 业务背景

Zeus-Doc 是面向中大型企业的「知识库文档中台」，提供文档全生命周期管理：创建、富文本/Markdown 编辑、多人协同编辑、版本回溯、全文检索、文件附件、细粒度权限审计与回收站。系统采用 SaaS 多租户模型，需要支撑单租户日均 50 万次文档读、峰值 3000 QPS、千人同时在线协同编辑。

2.2 核心功能需求

模块 关键需求 性能指标
文档管理 CRUD、版本历史、回收站、分享链接 读 RT < 50ms（命中缓存）
协同编辑 实时多人协同、OT 冲突合并 WebSocket 5000 连接/节点
全文检索 ES 倒排、高亮、聚合 搜索 RT < 200ms
文件存储 大文件分片上传、断点续传 单文件最大 2GB
审计日志 全量行为留痕、租户隔离 异步落库不阻塞主流程
用户权限 RBAC + 租户隔离 JWT 鉴权 < 5ms

2.3 系统边界（做什么 / 不做什么）

  • 做：文档中台业务能力、多租户隔离、跨服务最终一致事务、协同编辑冲突合并。
  • 不做：即时通讯（IM）、视频会议、OA 审批流；这些由上游系统通过 OpenAPI 接入。

2.4 非功能性约束

  • 可用性 ≥ 99.9%，核心读链路支持同城双活；
  • 数据一致性：金融级强一致非目标，业务最终一致 + 审计可追溯即可；
  • 可扩展性：水平扩容无状态化，分库分表承载亿级 doc_history。

五、微服务拆分说明（6 大服务职责边界）

5.1 拆分原则

  1. 领域驱动（DDD）：按业务领域而非技术分层拆分；
  2. 生命周期独立：每个服务可独立部署、扩容、故障隔离；
  3. 数据 ownership：每个服务独占自己的数据库，跨服务仅通过 RPC/MQ 通信。

5.2 职责边界矩阵

服务 核心领域 数据所有权 对外能力
user 用户/租户 zeus_user 库 登录、RBAC、租户管理
doc 文档聚合根 zeus_doc / zeus_doc_history_0..3 分片 文档 CRUD、版本、缓存、TCC 分支
collab 协同会话 Redis（会话态） WebSocket、OT 合并、在线广播
search 检索索引 Elasticsearch 全文检索、聚合统计
file 对象存储 MinIO 上传/下载/秒传/分片
audit 审计/回收站 zeus_audit 分片库 审计查询、回收站恢复、TCC 编排

5.3 服务间依赖（避免循环）

依赖方向严格单向：gateway → 各业务服务；doc → audit（Feign，TCC 分支）；doc → collab（协同触发）；doc → search（MQ 异步解耦）。审计侧 DocDeleteTccFacade 作为 TCC 编排方开启 @GlobalTransactional，doc 侧 DocDeleteTccActionImpl 作为分支参与同一 XID，XID 经 Feign 拦截器透传，不存在反向同步依赖。

六、技术选型决策理由

6.1 为什么选 MySQL 而非 MongoDB

维度 MySQL 8.0 MongoDB
事务能力 InnoDB 强 ACID、行锁，原生 XA 4.0+ 多文档事务性能差、限制多
业务匹配 元数据强关系（doc↔user↔share↔audit）需多表 Join 与外键约束 适合 schema-free 场景；正文 JSON 字段用 MySQL JSON 类型即可承载
分库分表 ShardingSphere-JDBC 在 JDBC 层透明路由 内置分片，但跨片事务与 Join 弱
一致性 文档元数据强一致要求高 最终一致为主
团队熟悉度 DBA 成熟，主从/备份/监控/慢查询工具链完善 内存控制、分片平衡需额外投入

结论： 文档元数据、审计、回收站需强事务保证（删除走 TCC 跨库），且核心数据有强关系约束（多表 Join），ShardingSphere 在 JDBC 层做分片对应用透明（application-sharding.yml 配置即可路由），团队掌握度高，因此选 MySQL。文档正文（Quill Delta JSON）以 TEXT 列存储，必要时可下沉到对象存储，DB 只存元数据 + 摘要，MySQL 完全胜任。MongoDB 在 schema 多变场景更优，本项目 schema 稳定，故不选。

6.2 为什么选 MinIO 而非 FastDFS

维度 MinIO FastDFS
协议标准 原生 S3 兼容，SDK 生态丰富，可无缝迁移 OSS/S3 私有协议，SDK 封闭
部署运维 单二进制、轻量、K8s 友好 Tracker/Storage 双角色，部署复杂
签名 URL S3 Presigned URL 开箱即用，前端直传 需自实现 token 机制
高可用 纠删码 Erasure Coding，50% 冗余即可 主备复制，组间同步机制较弱
活跃度 持续更新（8.5.11） 社区萎缩、维护停滞

结论： 文件服务需要「前端直传 + 签名 URL + 分片上传」能力，MinIO 的 S3 兼容性让这些能力开箱即用，未来可无缝迁移 OSS/S3。ZeroCopyStorage（zeus-doc-service-file/.../minio/ZeroCopyStorage.java）通过 FileChannel.transferFrom 调用 Linux sendfile 实现分片零拷贝合并，与 MinIO 配合良好。纠删码以 50% 冗余实现高可用，性价比优于三副本。

6.3 为什么选 Tomcat（而非 Undertow/Netty HTTP）

维度 Tomcat Undertow Netty（裸 HTTP）
Spring Boot 默认 是，零配置即可用 需替换 starter 需自行实现 HTTP 协议栈
调优模型 max-threads/max-connections/accept-count 三参数清晰（application.yml:3-11） 参数少但调参黑盒、经验稀缺 完全自定义，开发成本高
监控诊断 Processor 等 JMX 指标完善，jstack/arthas 经验沉淀多 指标偏少 需自建监控
业务匹配 请求-响应短连接业务完全胜任；压测 max-threads=200 出现 TPS 拐点，调到 500 边际收益递减 性能略优但收益有限 适合长连接（协同服务已用）

结论： 文档/搜索/审计等 HTTP 服务用 Tomcat（Spring Boot 默认，配置见 application.yml:3-11），协同服务用 Netty 处理 WebSocket 长连接，各取所长、避免技术栈分裂。Tomcat 调优模型清晰、压测拐点可控（见《03-性能压测报告》）；Undertow 内存更省但调参黑盒，Netty 自建 HTTP 栈开发成本高，权衡后选 Tomcat。

6.4 关键中间件版本对齐（pom.xml 第 36-61 行）

Spring Cloud Alibaba 2023.0.1.0 与 Spring Boot 3.2.5 / Spring Cloud 2023.0.1 严格对齐（2023.x 线），JDK 17。Seata 2.0.0 支持 TCC 增强，ShardingSphere 5.4.1 支持 INTERVAL 分表算法。

关键点说明：

  1. 拦截位置：@RateLimit 在 applyPreHandle 阶段执行（RateLimitInterceptor.java:53），早于 Controller 方法。限流 key = 接口 + userId/IP（RateLimitInterceptor.java:69），避免单用户刷爆全局限流。
  2. 限流算法：Redis Lua 脚本原子执行 incr + expire（固定窗口），DefaultRedisScript 注入保证原子性。
  3. @CurrentUserId 解析器：在 getHandlerAdapter 后、handle 前由 HandlerMethodArgumentResolver 解析参数，从 UserContext.currentUserId() 取值注入。
  4. ThreadLocal 清理：START_TS 必须在 afterCompletion remove（RateLimitInterceptor.java:97），否则线程池线程复用导致内存泄漏（详见《05-JVM 调优报告》ThreadLocal 泄漏章节）。
  5. 中断语义：preHandle 返回 false 时 postHandle 不执行，但 afterCompletion 仍对已通过 preHandle 的拦截器执行（清理资源）。

11.1 TCC 三大坑与防御（DocDeleteTccActionImpl.java:14-20 注释）

坑 场景 防御方案

一、线程池设计总览

线程池配置位于 zeus-doc-service-doc/src/main/java/com/zeus/doc/threadpool/ThreadPoolConfig.java。该类声明 4 个隔离线程池（第 49-52 行）：

线程池 core max queue 拒绝策略 用途
doc-executor CPU×2 (8) CPU×4 (16) 2000 AbortPolicy 文档保存、版本生成（核心写）
audit-executor 2 4 500 CallerRunsPolicy 审计日志异步写入（不丢日志）
search-sync-executor 4 8 1000 DiscardOldestPolicy MQ 消费后同步 ES
export-executor 2 4 200 AbortPolicy PDF 导出重型 IO

CPU 核数动态获取：Runtime.getRuntime().availableProcessors()（ThreadPoolConfig.java:46），本报告以 4C 容器为基准（core=8, max=16）。

1.1 隔离设计原则（ThreadPoolConfig.java:22-28 注释）

  1. 故障隔离：A 业务慢请求堆积不会拖垮 B 业务（避免雪崩传染）；
  2. 资源隔离：核心写（doc-executor）不会被日志（audit-executor）抢占线程；
  3. 监控隔离：每个池独立监控队列长度、拒绝次数，便于定位问题；
  4. 调优隔离：不同业务 CPU/IO 特性不同，参数独立调整。

1.2 拒绝策略选择（ThreadPoolConfig.java:29-32 注释）

  • AbortPolicy（doc/export）：核心业务用，抛异常让调用方感知并降级，避免任务丢失却无感知；
  • CallerRunsPolicy（audit）：日志不能丢，退化为调用线程同步执行也不丢；
  • DiscardOldestPolicy（search-sync）：ES 索引同步丢弃最旧任务，保留最新（旧索引可由全量补偿任务修复）。

1.3 TTL 上下文传递（ThreadPoolConfig.java:88-90 注释）

所有线程池经 TtlExecutorUtil.wrap(executor) 包装（第 103 行），主线程的 UserContext（userId/tenantId/traceId）通过 TransmittableThreadLocal 正确传递到 worker 线程，避免跨线程上下文丢失。

1.4 优雅关闭（ThreadPoolConfig.java:99-101）

应用关闭时等待队列任务执行完（最多 30s），避免任务半途丢失。@PreDestroy（第 121 行）触发清理。

4.3 LongAdder 原理分析

LongAdder 在高并发下 TPS 是 synchronized 的 8.3 倍，原理：

  • 内部维护 base + Cell[] 数组（默认 2 倍 CPU 核数）；
  • 写：线程 hash 到不同 Cell 做 CAS，减少单点竞争；
  • 读：sum() = base + 所有 Cell 累加（非强一致，适合统计场景）；
  • Cell 用 @Contended 注解填充缓存行，避免伪共享。

4.4 适用场景

场景 推荐
在线人数、QPS 统计 LongAdder（非精确一致，高频写）
精确计数（如余额） AtomicLong / synchronized
复杂临界区（多步操作） ReentrantLock（可超时可中断）

6.1 问题现象

7.2 锁升级死锁验证（DocCacheManager.tryUpgradeToWriteLock）

DocCacheManager.java:125-155 注释说明：持有读锁时调用 writeLock.lock() 会永久阻塞（死锁）。第 132-133 行的错误示范已注释，正确做法是先 readLock.unlock() 再 writeLock.lock() + 双重检查（第 136-149 行）。

死锁原因：若允许读锁升级写锁，多个读线程同时持有读锁并都想升级时，写锁需等所有读锁释放，而读锁因等待写锁不释放，形成循环等待死锁。Java 显式禁止此操作。

九、结论与最佳实践

  1. 线程池隔离是必要的：共用池在慢调用注入下 TPS 暴跌 60%，隔离方案故障不传染；
  2. 读写锁适合读多写少：但生产建议直接用 Caffeine 分段无锁，避免写锁竞争（jstack 定位到 writeLock 阻塞 TOP1）；
  3. LongAdder 是计数器首选：cells 分段 CAS 比 synchronized 快 8 倍，配合 @Contended 解决伪共享再提升 63%；
  4. 拒绝策略因业务而异：核心写用 Abort 暴露问题，日志用 CallerRuns 不丢，ES 同步用 DiscardOldest 保最新；
  5. 动态调优：core/max 可 Nacos 热更新，队列容量需重建，设计时预留容量上限。

线程模型设计需结合压测数据持续迭代，锁竞争排查依赖 jstack + JOL 工具链。详见《05-JVM 调优报告》与《06-面试手册第7/9问》。

4.5 分析

  1. synchronized vs ReentrantLock：低中并发下性能接近（JDK 17 偏向锁优化后 synchronized 甚至更快）；ReentrantLock 优势在可中断、超时、公平、多 Condition。本项目 DocCacheManager 用 ReentrantReadWriteLock（读多写少场景读锁并行）。
  2. AtomicInteger 退步：200 并发下 CAS 自旋失败率升高（ABA + 自旋空耗），不如 LongAdder。
  3. LongAdder 最优：Cell[] 分段累加，不同线程命中不同 Cell，无竞争；最终 sum() 合并。TPS 是 synchronized 的 4.6 倍，cs 仅为 1/4。

场景 推荐
计数统计（QPS、在线人数） LongAdder（HotStats 应改用）
读多写少缓存 ReentrantReadWriteLock（DocCacheManager）
简单互斥 synchronized（语法简单，JVM 优化充分）
需要超时/中断/公平 ReentrantLock

附5、伪共享（False Sharing）分析（补充章节）

5.1 问题原理

CPU 缓存行（Cache Line）通常 64 字节。多个线程修改同一缓存行内的不同变量时，虽无逻辑竞争，但缓存一致性协议（MESI）会反复失效对方缓存行，导致性能骤降。

5.2 测试场景

两个线程分别对 HotStats 中相邻的 long hitCount 和 long missCount 累加 1 亿次。

  3. 从库服务 mysql-slave（3307）：server-id=2 + GTID + –skip-log-bin；
  4. 从库 initdb 挂 deploy/sql/slave-init/01_slave_setup.sh：等待主库 → 等全部业务库存在（防竞态） → dump 快照导入 → CHANGE MASTER → START SLAVE；

  • 验证：deploy/verify/verify-master-slave.sh

⚠️ 常见坑点（全部实测踩过）

  1. docker 同一容器路径挂两个 bind mount 会互相遮蔽：mysql8 曾同时挂 master-init 和 ../sql 到 /docker-entrypoint-initdb.d，后者被遮蔽 → schema 脚本静默不执行，从库 dump 时报 Unknown database 'zeus_doc' 才发现。规则：一个容器路径只挂一个卷。
  2. mysqladmin ping 通过 ≠ schema 就绪：从库脚本在主子初始化完成前 dump → Unknown database。必须显式等待”全部业务库存在”。
  3. docker-entrypoint 执行 initdb 时默认 USE MYSQL_DATABASE（zeus_user）→ 存储过程建到了 zeus_user，CALL 时找不到（1305）。跨库调用必须全限定：CALL zeus_audit_0.create_audit_monthly_tables(...)。
  4. 存储过程内未限定表名解析到过程定义库：CALL 时的 USE 不影响过程内部 → 月表全建到 _0 库。库名/表名分别反引号：`zeus_audit_0`.`doc_audit_202601`。
  5. MySQL 8.0.22+ 列名变更：SHOW REPLICA STATUS 输出 Replica_IO_Running / Seconds_Behind_Source（旧版 Slave_*），验证脚本需兼容两种。
  6. bash 变量名后紧跟全角括号（$VAR（）会被解析进变量名 → set -u 报 unbound。脚本内 $VAR 后接全角标点前加空格。

验收标准

Phase 14: MQ 死信 / 延迟 / 顺序消息

学习目标

  • 掌握 RocketMQ 延迟消息的 18 级限制与映射
  • 理解”分区顺序”的实现前提（发送端 hashKey 路由 + 消费端 ORDERLY）
  • 理解死信队列的产生路径与告警消费

核心知识点

  1. 延迟消息：RocketMQ 只支持固定 18 级（1s/5s/10s/30s/1m…/2h），Broker 定时线程检查延时队列；
  2. 顺序消息 = 分区顺序：syncSendOrderly(topic, msg, hashKey) 按 hashKey 哈希选队列，同一业务键永远进同一队列；消费端 ConsumeMode.ORDERLY 单线程串行消费；队列内 FIFO、跨队列不保证；
  3. 死信：消费失败抛异常 → Broker 指数退避重试（默认 16 次）→ 投递 %DLQ%<topic> → 死信消费者告警。

实现步骤

  1. mq/ScenarioMessage：通用消息体（msgId/type/docId/userId/version）；
  2. mq/MqScenarioProducer：
    • resolveDelayLevel(Duration)：业务时长 → 18 级映射（向上取最近，超 2h 封顶，0/负不延迟）；
    • sendDelayedRemind：syncSend 带 delayLevel（演示 10s 级）；
    • sendVersionOrderly：syncSendOrderly 以 docId 为 hashKey；
  3. mq/DelayedRemindConsumer：延迟提醒消费；zeus.mq.demo-fail=true 开关演示失败重试（教学性反例，默认关闭）；
  4. mq/VersionOrderlyConsumer：ConsumeMode.ORDERLY + 记录每个 docId 已消费最大版本号（顺序性监控）；
  5. mq/ScenarioDlqConsumer：监听 %DLQ%zeus-doc-scenario 死信告警（MessageExt 原始消息）。

参考文件

  • zeus-doc-service-doc/src/main/java/com/zeus/doc/mq/MqScenarioProducer.java 等 6 个类

A.1 ShardingSphere 依赖 artifact 错误

错误：Could not find artifact org.apache.shardingsphere:shardingsphere-jdbc:jar:5.4.1

根因：ShardingSphere 5.4.x 中 shardingsphere-jdbc 的 <packaging>pom</packaging>，是 POM 聚合器，没有 JAR。Maven Central 返回 404。

解决：改用 shardingsphere-jdbc-core（实际 JAR 包含所有 JDBC 功能）。

影响文件：pom.xml（父）、zeus-doc-service-doc/pom.xml、zeus-doc-service-audit/pom.xml

A.2 diff_match_patch API 版本不匹配

错误：程序包 name.fraser.neil.plaintext 不存在

根因：代码引用 Google 原版 name.fraser.neil.plaintext.diff_match_patch（snake_case），但 Maven 依赖 org.bitbucket.cowwoc:diff-match-patch:1.2 使用不同的包名和 camelCase API。

解决：重构为 cowwoc API：

  • diff_match_patch → DiffMatchPatch
  • patch_make() → patchMake()
  • patch_apply() → patchApply()
  • patch_toText() → patchToText()
  • patch_fromText() → patchFromText()（返回 List 而非 LinkedList，需 new LinkedList<>() 转换）
  • diff_main() → diffMain()

影响文件：OtService.java（doc）、OtMergeEngine.java（collab）

A.3 JacksonConfig 缺少静态 MAPPER

错误：RateLimitInterceptor.java:7 找不到符号 JacksonConfig

根因：JacksonConfig 在 com.zeus.common.config 包，但 RateLimitInterceptor 从 com.zeus.common.utils 导入。且 JacksonConfig 没有静态 MAPPER 字段。

解决：

  1. 修正 import 路径
  2. 在 JacksonConfig 中添加 public static final ObjectMapper MAPPER = buildMapper()

A.4 HotStats 内部 API 不可见

错误：程序包 jdk.internal.vm.annotation 不可见

根因：@jdk.internal.vm.annotation.Contended 是 JDK 内部 API，默认不可见，需 --add-exports 编译参数。

解决：移除 @Contended，改用手动 long 填充字段（7 个 long = 56 字节 + 对象头 8 字节 = 64 字节缓存行），无需 JVM 参数。

A.5 RejectedExecutionHandler 不是嵌套类

错误：ThreadPoolConfig.java:91 找不到符号

根因：代码写 ThreadPoolExecutor.RejectedExecutionHandler，但 RejectedExecutionHandler 是 java.util.concurrent 的顶层接口，不是 ThreadPoolExecutor 的嵌套类。

解决：添加 import java.util.concurrent.RejectedExecutionHandler 并直接使用。

A.6 RocketMQ 注解属性不存在

错误：DocSyncMQConsumer.java:31,33 找不到符号

根因：rocketmq-spring 2.3.0 的 @RocketMQMessageListener 不支持 consumeThreadMin 和 pullBatchSize 属性。

解决：移除这两个属性，仅保留 consumeThreadMax。

A.7 Seata getActionContext 类型转换

错误：java.lang.Object 无法转换为 java.lang.Long

根因：BusinessActionContext.getActionContext(String key) 返回 Object，不能直接赋给 Long。

解决：使用泛型版本 getActionContext("key", Long.class)。

影响文件：AuditTccActionImpl.java、RecycleBinTccActionImpl.java

A.11 Sentinel 熔断常量名

共 50 题，按主题分组。”答案要点”是速查记忆锚点，完整推导与代码见对应专题文章（括号内为章节）。

A. Java 基础

1. String、StringBuffer、StringBuilder 的区别？String 为什么不可变？

  • 要点：String 不可变且线程安全（每次修改产生新对象）；StringBuffer 可变、方法加 synchronized 安全但慢；StringBuilder 可变、非安全但最快（单线程首选）。不可变原因：字符串常量池复用、hashCode 可缓存、安全（不会被子类/并发修改）、可作常量。
  • 详见：Java 核心基础 第 2 节

2. String s1 = new String("abc"); 创建了几个对象？

  • 要点：常量池中没有 "abc" 时创建 2 个（常量池 1 个 + 堆 1 个），已有则只创建 1 个（堆）。intern() 可把堆字符串放入常量池。
  • 详见：Java 核心基础 第 2 节

3. == 与 equals 的区别？hashCode 与 equals 的关系？

  • 要点：== 比引用地址；equals 默认同 ==，重写后比内容（String 重写过）。重写 equals 必须重写 hashCode：两个对象 equals 相等则 hashCode 必相等（反之不成立），否则基于哈希的集合（HashMap/HashSet）会错乱。
  • 详见：Java 核心基础 第 2 节

4. 包装类型的缓存机制？自动装箱/拆箱原理？

  • 要点：Integer 缓存 -128127（valueOf 命中缓存返回同一对象，new Integer 不缓存），Character 缓存 0127，Boolean 缓存 true/false，Long/Short/Byte 缓存全部范围（-128~127）。装箱调 valueOf，拆箱调 xxxValue()。缓存范围外的值用 == 比较会踩坑。
  • 详见：Java 核心基础 第 2 节

5. Java 反射？有什么缺点？为什么框架需要反射？

  • 要点：反射在运行时获取类的结构（Class 对象 → 构造器/字段/方法）并动态调用。优点：动态性、解耦（框架不需要在编译期知道具体类）；缺点：性能开销（调用绕过 JIT 优化）、破坏封装、安全问题。Spring 通过反射实例化 Bean、注入依赖、代理拦截。
  • 详见：Java 核心基础 第 2 节

6. Java 泛型？什么是类型擦除？常用通配符？

  • 要点：泛型是编译期检查，运行时擦除为 Object + 强制转换（桥方法保持多态）。? extends T 上界限定，只读；? super T 下界限定，可写（PECS：生产者 extends，消费者 super）。
  • 详见：Java 核心基础 第 2 节

7. 哪些集合是线程不安全的？怎么解决？

  • 要点：ArrayList/HashMap/HashSet 均不安全（HashMap 并发 put 可能丢数据甚至死循环，1.8 修复了扩容死循环）。解决：Collections.synchronizedXxx（整对象加锁）、CopyOnWriteArrayList（读多写少）、ConcurrentHashMap（分段/桶级锁）、Vector/Hashtable（全锁，不推荐）。
  • 详见：Java 核心基础 第 3 节

8. HashMap 的底层实现（1.7 vs 1.8）？

JDK 版本 底层数据结构 冲突解决
JDK 1.7 数组 + 链表 拉链法（头插法，扩容 rehash 在并发下可能成环）
JDK 1.8 数组 + 链表 + 红黑树 链表长度 > 8 时：数组长度 < 64 先扩容，否则链表转红黑树；尾插法
  • 要点：默认容量 16、负载因子 0.75；key 可为 null（HashMap 允许，Hashtable 不允许）；hash = h ^ (h >>> 16) 扰动后 (n-1) & hash 定位。
  • 详见：Java 核心基础 第 3 节

9. HashMap 长度为什么是 2 的幂？ConcurrentHashMap 线程安全实现？

  • 要点：容量 2 的幂使 (n-1) & hash 等价于取模且更快，扩容时元素要么留在原位、要么移到 原位置 + 旧容量，重排开销小。ConcurrentHashMap：1.7 分段锁（Segment 继承 ReentrantLock，默认 16 段）；1.8 放弃分段锁，CAS + synchronized 锁链表/红黑树首节点，支持并发扩容，并发度更高。
  • 详见：Java 核心基础 第 3 节

B. Java 并发

10. sleep() 和 wait() 的区别？

  • 要点：sleep 来自 Thread，不释放锁，必须处理中断；wait 来自 Object，释放锁并进入等待队列，必须在 synchronized 块中调用，由 notify/notifyAll 唤醒。
  • 详见：Java 并发编程 第 1 节

11. volatile 解决了什么问题？与 synchronized 的区别？

  • 要点：volatile 保证可见性 + 禁止指令重排，不保证原子性（i++ 仍不安全），适用状态标志/单写场景。synchronized 保证可见性 + 原子性 + 有序性。JMM 下通过 happens-before 原则判断可见性。
  • 详见：Java 并发编程 第 2 节

12. synchronized 的锁升级过程？与 ReentrantLock 的区别？

  • 要点：无锁 → 偏向锁 → 轻量级锁（自旋）→ 重量级锁（monitor，阻塞）；JDK 15 起默认禁用偏向锁。ReentrantLock：可中断/可超时、公平锁可选、Condition 分组唤醒，基于 AQS。
  • 详见：Java 并发编程 第 3、4 节

13. ThreadLocal 的作用？内存泄漏问题？

  • 要点：每个线程持有一个 ThreadLocalMap，key 为 ThreadLocal 的弱引用，value 为强引用。key 被 GC 回收后 value 无法访问即泄漏（线程池复用线程时更严重）。解决：用完后显式 remove()；set/get 时会顺带清理过期 entry。
  • 详见：Java 并发编程 第 6 节

14. 线程池的参数、处理流程、拒绝策略？为什么不推荐内置线程池？

  • 要点：7 参数（corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler）；流程：核心线程 → 阻塞队列 → 最大线程 → 拒绝。4 种拒绝策略：AbortPolicy（抛异常）/ CallerRunsPolicy（调用者执行）/ DiscardPolicy / DiscardOldestPolicy。Executors 的问题：FixedThreadPool 无界队列（OOM）、CachedThreadPool 最大线程数 Integer.MAX（线程爆炸）。生产用 ThreadPoolExecutor 自定义参数并命名线程。
  • 详见：Java 并发编程 第 5 节

15. AQS 原理了解吗？基于它的组件有哪些？

  • 要点：AQS 维护 volatile state + CLH 双向等待队列，提供独占/共享两种模式与模板方法。基于它：ReentrantLock（独占）、Semaphore（共享计数）、CountDownLatch（共享，计数减到 0 放行）、ReentrantReadWriteLock（读写分离）。
  • 详见：Java 并发编程 第 4 节

16. 多个任务的编排怎么做？CompletableFuture 怎么用？

  • 要点：串行 thenApply/thenCompose、并行 allOf/anyOf、异常恢复 exceptionally/handle、回调线程池 thenApplyAsync。相比 Future.get 阻塞与 CountDownLatch 手写编排，CompletableFuture 声明式组合，项目里可用来并行查询多个接口后合并。
  • 详见：Java 并发编程 第 7 节

C. JVM

17. 运行时数据区有哪些区域？哪些共享？哪些会出现 OOM？

  • 要点：线程共享：堆、方法区（元空间）；线程独享：虚拟机栈、本地方法栈、程序计数器。OOM 可能出现在堆、元空间、直接内存（栈溢出是 StackOverflowError，程序计数器唯一不会 OOM）。
  • 详见：JVM 原理与调优 第 1 节

18. 如何判断对象是否死亡？可达性分析中哪些对象是 GC Roots？

  • 要点：引用计数法无法解决循环引用，JVM 用可达性分析：从 GC Roots 出发不可达即死亡。GC Roots：虚拟机栈中的引用、静态属性引用、常量引用、JNI 引用、同步锁（monitor）持有的对象等。
  • 详见：JVM 原理与调优 第 2 节

19. 垃圾收集有哪些算法？CMS 与 G1、ZGC 各自特点？

  • 要点：标记-清除（碎片）、复制（存活少时高效，浪费空间）、标记-整理（老年代）。CMS 四步：初始标记 → 并发标记 → 重新标记 → 并发清除，缺点：浮动垃圾、内存碎片、并发失败退化 Serial Old。G1：Region 化、可预测停顿、RSet + 写屏障。ZGC：染色指针 + 读屏障，停顿毫秒级。
  • 详见：JVM 原理与调优 第 4 节

20. 双亲委派是什么？为什么需要？如何打破？

  • 要点：类加载请求自底向上委派，Bootstrap → Platform → Application，只有父加载器加载不了才向下。好处：避免重复加载、防止核心类被篡改。打破：Tomcat 每个 Webapp 独立类加载器（先加载自己的类）；JDBC SPI 通过线程上下文类加载器加载实现类。
  • 详见：JVM 原理与调优 第 3 节

21. 如何降低 Full GC 的频率？

  • 要点：避免大对象直接进老年代（大对象频繁触发并发失败）；合理设置新生代/老年代比例，让对象在新生代被回收；减少 System.gc()（RMI 等会触发）；检查内存泄漏（静态集合、ThreadLocal 未 remove）；堆大小与 GC 器参数配合（G1 下控制 Region 大小与停顿目标）。
  • 详见：JVM 原理与调优 第 5 节

  • 详见：Spring 深度解析 第 2 节

24. Spring 如何解决循环依赖？

  • 要点：三级缓存——singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（工厂，提前暴露对象）。A 创建时把 A 的工厂放第三级，B 依赖 A 时经工厂拿到 A 的早期引用。构造器注入无法解决循环依赖；Boot 2.6+ 默认禁止循环依赖；AOP 场景依赖第三级缓存提前代理。
  • 详见：Spring 深度解析 第 3 节

25. Spring Boot 的自动配置是如何实现的？

  • 要点：@SpringBootApplication 含 @EnableAutoConfiguration，通过 META-INF/spring/...AutoConfiguration.imports（3.x）加载自动配置类，结合 @ConditionalOnClass/@ConditionalOnMissingBean 等条件注解按需装配；用户自定义 Bean 优先于自动配置（@ConditionalOnMissingBean 兜底）。
  • 详见：Spring 深度解析 第 6 节

26. @Transactional 失效的场景有哪些？

  • 要点：方法非 public；同类内部调用（this 调用走不到代理）；异常被 catch 吞掉；抛出 checked 异常且未指定 rollbackFor（默认只回滚 RuntimeException）；final/static 方法；传播行为设置不当（如 REQUIRES_NEW 处理不当）。
  • 详见：Spring 深度解析 第 7 节

E. MySQL

27. 事务的四大特性？MySQL 的隔离级别？

  • 要点：ACID（原子性、一致性、隔离性、持久性）。4 种隔离级别：读未提交（脏读）/读已提交（不可重复读）/可重复读（幻读）/串行化。InnoDB 默认 RR，用 MVCC（快照读）+ Next-Key Lock（当前读）解决幻读。
  • 详见：MySQL 原理与优化 事务节

28. InnoDB 对 MVCC 的具体实现？

  • 要点：每行隐藏列 trx_id（最近修改事务）、roll_pointer（指向 undo 版本链）；快照读按 ReadView（m_ids/up_limit_id/low_limit_id/creator_trx_id）沿版本链找可见版本；RR 下第一次查询生成 ReadView 并复用（当前读除外，当前读走当前最新版本 + 锁）。
  • 详见：MySQL 原理与优化 事务节

29. 最左前缀匹配原则？什么是覆盖索引？索引失效场景？

  • 要点：组合索引按最左顺序匹配，跳过中间列会部分失效（可用索引下推优化）；覆盖索引指查询列全部在索引中，不回表；失效：违背最左前缀、对索引列做函数/运算/隐式类型转换、LIKE '%xx'、OR 连接非索引列、优化器评估全表扫描更优。
  • 详见：MySQL 原理与优化 索引节

30. B+ 树做索引比红黑树、Hash 好在哪里？

  • 要点：B+ 树矮胖、层高 3~4，磁盘 IO 少；非叶子节点只存键，单页容纳更多记录；叶子节点链表有序，支持范围查询与排序；对比 Hash 索引：单点 O(1) 但不支持范围、无法排序。红黑树/二叉查找树高度高、随机 IO 多，不适合磁盘场景。
  • 详见：MySQL 原理与优化 索引节

31. redo log、binlog、undo log 的区别？为什么需要两阶段提交？

  • 要点：redo log 是 InnoDB 物理日志（页修改，循环写），崩溃恢复保证持久性（WAL：先写日志再刷盘）；binlog 是 Server 层逻辑日志（归档/主从复制）；undo log 记录回滚版本，保证原子性并支撑 MVCC。两阶段提交保证 redo 与 binlog 一致，避免主从数据与恢复结果不一致。
  • 详见：MySQL 原理与优化 日志节

32. InnoDB 有哪几类行锁？Next-Key Lock 的加锁范围？

  • 要点：记录锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock = 记录锁 + 间隙锁）；意向锁是表级。RR 下范围条件默认加 Next-Key Lock（含间隙），唯一索引等值命中退化为记录锁；RC 只加记录锁。
  • 详见：MySQL 原理与优化 锁节

F. Redis

33. Redis 为什么这么快？6.0 为什么引入多线程？

  • 要点：内存存储；单线程命令执行避免锁竞争与上下文切换；IO 多路复用（epoll）监听大量连接；高效数据结构（SDS/quicklist/listpack/跳表）；渐进式 rehash。6.0 的多线程只处理网络 IO 读写，命令执行仍单线程——因为瓶颈是网络 IO 而非 CPU，且要保证命令原子性。
  • 详见：Redis 深度解析 第 3 节

34. String 的底层实现？为什么用 SDS？为什么用跳表而不用红黑树/B+ 树？

  • 要点：SDS 保存 len，O(1) 获取长度、避免缓冲区溢出、二进制安全、预分配减少扩容次数。跳表 vs 红黑树：实现简单、范围查询天然有序；vs B+ 树：内存中不需要页级 IO 优化，跳表足够且分层可调。
  • 详见：Redis 深度解析 第 2 节

35. 宕机了，Redis 如何避免数据丢失？RDB 和 AOF 如何选择？

  • 要点：RDB 全量快照（fork 子进程写临时文件后原子替换，恢复快、可能丢最近数据）；AOF 追加写（everysec 默认，最多丢 1 秒，文件大需重写）；4.0+ 混合持久化（RDB 头 + AOF 增量）。选型：允许丢数据、重启快用 RDB；高可靠用 AOF/混合。
  • 详见：Redis 深度解析 第 4 节

36. 缓存穿透、击穿、雪崩分别是什么？怎么解决？

  • 要点：穿透（查不存在的数据打穿到 DB）：布隆过滤器 / 缓存空值（带短过期）/ 参数校验；击穿（热点 key 过期瞬间被并发打爆）：互斥锁重建缓存 / 逻辑过期；雪崩（大量 key 同时过期或 Redis 宕机）：过期时间加随机值 / 集群高可用 / 限流降级 / 缓存预热。
  • 详见：Redis 深度解析 第 6 节

37. 有缓存的情况下如何保证数据一致性？

  • 要点：主流 Cache Aside——读：先查缓存，miss 读库回填；写：先更新 DB 再删除缓存（删除而非更新，避免并发写脏）。可加延迟双删、删除失败走消息队列/订阅 binlog 重试。强一致场景需引入分布式锁或旁路对账。
  • 详见：Redis 深度解析 第 7 节

G. 网络

41. TCP 为什么三次握手、四次挥手？

  • 要点：三次握手能确认双方收发能力都正常，且能阻止历史重复连接（比两次握手多一个”确认旧 SYN 已被丢弃”的校验，四次则多余）。四次挥手因为断开是半关闭：收到 FIN 后可能还有数据要发，ACK 与 FIN 分开，主动方最后等 2MSL（保证对方收到 FIN-ACK、让旧报文消亡）。
  • 详见：无专题文章，答案要点供自检，需展开请自行整理笔记

42. TCP 如何保证传输可靠性？

  • 要点：序号 + 确认应答；超时重传与快速重传（收到 3 个重复 ACK）；滑动窗口流量控制（防接收方被打爆）；慢启动/拥塞避免/快恢复拥塞控制（防网络被打爆）；校验和；数据分段与有序重组。
  • 详见：无专题文章，答案要点供自检

43. HTTPS 的加密过程？常见状态码？

  • 要点：对称加密快、非对称慢，HTTPS 用非对称交换密钥、对称加密数据：客户端验证 CA 证书 → 通过 ECDHE（前向安全）或 RSA 交换出会话密钥 → 之后全部对称加密。状态码：200 OK / 301 永久重定向 / 302 临时 / 304 缓存 / 400 参数错误 / 401 未认证 / 403 无权限 / 404 / 429 限流 / 500 / 502 / 503。
  • 详见：无专题文章，答案要点供自检

44. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

  • 要点：1.1 长连接 + 管线化（存在队头阻塞）；2.0 二进制分帧 + 多路复用（单连接并发请求，仍受 TCP 层队头阻塞）、HPACK 头部压缩、Server Push；3.0 基于 UDP 的 QUIC：0-RTT、连接迁移、彻底解决队头阻塞。

H. 算法、分布式与场景题

45. 写出三种单例模式实现？推荐哪一种？

  • 要点：饿汉（类加载即初始化）；懒汉 DCL + volatile（双检锁，防指令重排）；静态内部类（推荐，懒加载 + 无线程同步开销）；枚举（最推荐：天然线程安全、防反射与序列化破坏）。Spring 的 Bean 默认是单例（容器级）。

46. 手写题：LRU、快排/堆排、数组栈队列、链表反转、生产者消费者

  • 要点：LRU 用 HashMap + 双向链表 O(1) 命中与淘汰；快排分治、堆排 O(nlogn)；数组栈用指针、数组队列用环形数组；生产者消费者用 synchronized/wait/notify 或 BlockingQueue（速查-代码片段里有现成实现）。

47. CAP 定理与 BASE 理论？Raft 是怎么工作的？

  • 要点：分区（P）不可避免，分区时一致性（C）与可用性（A）只能二选一：CP（ZooKeeper/etcd）牺牲短暂可用，AP（Eureka/多数缓存场景）牺牲强一致。BASE：基本可用 + 软状态 + 最终一致。Raft：Leader 选举 + 日志复制 + 多数派提交，日志只从 Leader 流向 Follower。

48. 一个合格的分布式 ID 需要满足什么要求？常见生成方案？

  • 要点：全局唯一、趋势递增（利于索引）、高性能、高可用。方案：数据库自增（简单，单点压力大）/ 号段模式（Leaf-segment，批量取号）/ UUID（唯一但无序、过长）/ 雪花算法（时间戳 + 机器 + 序列，需处理时钟回拨）/ 美团 Leaf 混合方案。

49. 如何保证消息不被重复消费？消息堆积如何解决？

  • 要点：MQ 保证 at-least-once，消费端必须幂等：唯一业务键 + 数据库唯一索引 / Redis SETNX / 状态机判断。堆积：先查堆积原因（消费者挂掉/消费过慢/分区不均），临时扩容消费者、批量拉取、把堆积消息转存临时队列慢慢消费。
