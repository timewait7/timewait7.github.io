ZooKeeper 原理与实践

Posted on 2025-11-01 In 中间件 Word count in article: 8.4k Reading time ≈ 30 mins.

本文基于 ZooKeeper 3.8.x（2022 年发布的 3.x 系列最终主线，后续 4.x 由 3.8 分支演进而来）。3.8.x 默认使用 Netty 传输层，支持 TLS、动态重配置（reconfig）与持久递归 Watcher，兼容 Java 8 至 17。

1. ZooKeeper 是什么

1.1 分布式协调服务的定位

分布式系统的核心难点之一是”多台机器如何就一件事达成一致”。ZooKeeper 的定位不是数据库，也不是消息队列，而是分布式协调服务，专门解决以下问题：

  • 配置管理：集群共享配置集中存放，变更实时通知到所有节点；
  • 命名服务：统一的名字 -> 地址映射，如服务注册中心；
  • 分布式锁：跨进程互斥，保证同一时刻只有一个节点执行临界区；
  • 集群管理：感知节点上下线（临时节点的天然能力）；
  • Master 选举：保证同一时刻只有一个 Master 在干活，避免双主。

ZooKeeper 之所以适合做这些事，是因为它提供三个基础能力：

  1. 一个类似文件系统的树形数据模型，操作简单；
  2. 高可用：数据多副本（3~5 台），多数派存活即可对外服务；
  3. 强一致（写方向）：所有写操作通过 ZAB 协议在集群内达成一致，不会出现”两个 Leader 各写各的”。

1.2 数据模型（ZNode）

ZooKeeper 以树形结构组织数据，每个节点称为 ZNode，路径形如 /app1/p_1。每个 ZNode 可存一份数据（字节数组）并挂多个子节点，同时附带一个 Stat 状态：

ZNode 按类型分为四种，这是理解 ZooKeeper 一切应用的前提：

类型 创建命令 特点 典型用途
持久节点 PERSISTENT create /app data 显式删除才消失 配置、元数据
持久顺序节点 PERSISTENT_SEQUENTIAL create -s /app/q_ data 自动追加 10 位序号 分布式队列、公平锁
临时节点 EPHEMERAL create -e /app/tmp data 会话结束自动删除 锁、Master 选举、服务注册
临时顺序节点 EPHEMERAL_SEQUENTIAL create -e -s /lock/l_ data 临时 + 序号 分布式锁

临时节点是 ZooKeeper 的灵魂：客户端崩溃或会话过期时，临时节点会被服务端自动清理，天然实现”故障自愈”，无需人工兜底。

一个 ZNode 的完整路径是原子创建的（create 要么成功要么失败），且子节点列表整体有序，这两个性质分别是分布式锁和顺序保证的基础。

1.3 会话机制（Session）

客户端连接 ZooKeeper 集群即建立会话，所有操作都挂在会话上：

  • 会话标识：服务端分配 64 位 sessionId（高 8 位是该服务器的 myid），以及一个客户端可感知的 sessionPassword；
  • 超时协商：客户端声明期望的 sessionTimeout，服务端取客户端值与自身配置 minSessionTimeout/maxSessionTimeout 的交集（默认 2tickTime=4s 至 20tickTime=40s，tickTime 默认 2000ms）；
  • 心跳保活：客户端后台线程每 sessionTimeout/3 发一次 Ping，服务端 SessionTracker 跟踪最后心跳时间，超过 sessionTimeout 未收到心跳即判定会话过期，删除该会话名下所有临时节点并关闭连接；
  • 断线迁移：连接断开并不等于会话过期。客户端会从连接串中的服务器里重新选一台连上（会话在集群内是共享状态），只要在超时前重连成功，临时节点与操作句柄都还在；
  • 状态机：客户端连接状态经历 CONNECTING -> CONNECTED -> DISCONNECTED -> EXPIRED（或 AUTH_FAILED）。

会话过期是线上最常见的事故来源（详见第 8 章）：GC 停顿几秒、网络抖动超过超时时间，都会导致”锁突然没了””注册的节点被删了”。

2. ZAB 协议

2.1 为什么需要共识协议

单节点没有共识问题：一个服务挂了系统就不可用，于是做多副本。但多副本引来了新问题——副本之间如何保持一致：

  • 客户端写请求到哪台？副本之间谁先谁后？
  • Leader 挂了，剩下的节点谁能上位？以谁的日志为准？
  • 怎么避免网络分区时出现”两个 Leader 都认为自己是老大”（脑裂）？

答案就是共识协议。ZooKeeper 没有直接使用 Paxos/Raft，而是实现了自己的 ZAB（ZooKeeper Atomic Broadcast） 协议——一个面向”主备模式（primary-backup）”的原子广播协议，保证：

  1. 全序性（Total Order）：所有已提交的事务，在所有服务器上按同一个顺序执行；
  2. 原子性：要么所有服务器都提交，要么都不提交；
  3. 写线性一致：客户端成功收到写响应，意味着该写已提交到多数派，之后的读不会看到更旧的状态（顺序一致性保证）。

2.2 ZAB 的四个阶段

ZAB 协议完整地描述为两种模式的循环切换：

即经典的四个阶段：

阶段 干什么 关键点
1. Leader 选举 选出唯一的 Leader，且数据必须最新 比较 ZXID，见 2.4
2. 发现（Discovery） 新 Leader 收集各 Follower 的事务历史，确定同步方案 计算各自缺了哪些事务
3. 同步（Synchronization） Leader 把差异数据同步给 Follower：增量事务用 DIFF，差异过大用 SNAP（快照），多提交的未提交事务用 TRUNC（截断回滚） 保证提交过的事务不丢，未提交的不保留
4. 广播（Broadcast） 稳态下的正常写入流程 见 2.3

其中关键设计是 ZXID（ZooKeeper Transaction ID）：64 位整数，高 32 位是 epoch（纪元），低 32 位是事务计数器。

  • 每产生一个新 Leader，epoch 加 1，计数器清零；
  • 每次广播新事务，计数器加 1；
  • 所以 ZXID 越大，说明数据越新，这是选举和同步的统一标尺。

2.3 广播阶段

ZAB 的广播本质是简化版的二阶段提交（不用回滚、不用协调者外部交互）：

要点：

  • 写请求只走 Leader：客户端无论连到哪台服务器，写请求都会被转发到 Leader（follower 收到写请求会返回 NOT_READONLY 重定向信息，或直接内部转发），这是”全局有序”的保证；
  • 提交条件是多数派 ACK 而非全部 ACK：只要超过一半的投票节点（Leader+Follower，Observer 不投票）确认即可提交，所以 3 节点集群容忍 1 台故障，5 节点容忍 2 台；
  • ACK 前必须落盘（写事务日志），这样即使集群全部崩溃，重启后也能从日志恢复；
  • 读不走广播：读请求由每台服务器独立处理自己内存中的数据树（这是 ZooKeeper 读扩展性的来源，代价是读可能滞后，见 5.3）。

2.4 崩溃恢复

Leader 挂掉或与多数派失联时，进入选举。ZooKeeper 3.x 使用 Fast Leader Election（FLE），规则只有一条：

比较候选者的 （epoch，counter，myid），数值大的赢。因为 epoch 相同说明是同一代 Leader，此时事务计数器大的数据新；epoch 不同说明前者已换代，换代后计数器清零重来，所以先比 epoch。

选举过程（以 5 节点、node1 挂掉为例）：

  1. 每个节点初始投自己（(zxid, myid)）；
  2. 节点间互相广播投票（NOTIFICATION），发现别人的 (zxid, myid) 更大就改票投它；
  3. 某节点收集到多数派对自己的投票，即为 Leader，通知全集群进入发现阶段。

选举规则保证”选出来的 Leader 一定是数据最新的”——因为投票阶段比较了 zxid，拥有最新数据的节点会被多数节点投票选中。

随后进入发现与同步（2.2 的第 2、3 阶段），核心语义是：

  • 已提交的事务绝不丢失：新 Leader 必须补全所有已提交事务（DIFF/SNAP），Follower 与 Leader 不一致的尾部未提交事务一律 TRUNC 截断；
  • 新 Leader 确立 epoch（epoch+1），此后的写入使用新纪元，旧 Leader 的写请求即使在网络分区期间”成功”了，也会因 epoch 落后被新 Leader 拒绝。

面试高频追问：为什么 ZAB 能防脑裂？因为写提交需要多数派确认，而网络分区下最多只有一个分区拥有多数派；旧 Leader 若失联于多数派，它自己写的数据不会被提交，即使它”自以为还是 Leader”，客户端读不到它未提交的东西。

一句话总结：三者核心等价（都是”多数派 + 单调递增编号 + 日志对齐”），Raft 是 Paxos 的易实现工程版，ZAB 是面向 ZooKeeper 数据模型优化的广播协议。

3. 典型应用场景

3.1 分布式锁

思路：利用临时顺序节点 + 只监听前驱节点。

算法（业内标准做法，Curator 的 InterProcessMutex 即此实现）：

为什么要”只监听前驱”而不是监听整个目录？ 若所有等待者都监听同一个父节点，锁释放时父节点子节点变化事件会同时推给所有等待者——这就是惊群效应（Thundering Herd）：N 个客户端同时醒来重新抢锁，服务端瞬间产生 N 条通知、N 次请求。只监听前驱后，一次释放恰好唤醒一个等待者，通知量从 O(N) 降为 O(1)，且天然公平（FIFO）。

释放锁：删除自己的节点。客户端崩溃或会话过期时，临时节点被服务端自动清理，锁自动释放——无需”锁超时自动续期”这类额外机制，这是 ZK 锁相比 Redis 锁（SETNX + 过期时间）的语义优势；但代价是持有锁期间进程 GC 停顿超过 sessionTimeout 会导致锁被强抢（见 8.1）。

3.2 配置中心

核心模式：客户端读配置时注册 Watcher，收到变更通知后重新拉取配置并重新注册。

与 Nacos 配置中心的对比：

对比项 ZooKeeper Nacos（长轮询）
通知方式 服务端主动推送（Watcher） 客户端 HTTP 长轮询（默认挂起约 30s）
通知内容 仅事件类型 + 路径，不含数据，需再拉一次 返回变更的配置内容（dataId/group）
一次性 是，每次触发后必须重注册 天然可持续
连接形态 TCP 长连接 无状态 HTTP
断线影响 断线期间事件丢失（需重注册/重拉） 重发请求即可
承载量 Watch 多时服务端内存与推送压力大 轮询对服务端压力更大但实现简单

ZK 通知不含数据（轻量），客户端收到通知要再走一次 getData，多一次 RTT；但推送延迟低（毫秒级）。实践中 ZK 做配置中心完全可行（很多老项目就是这么干的），但若配置量大、变更频繁，建议用 Nacos/etcd（etcd 的 Watch 可带变更数据且非一次性）。

3.3 服务注册与发现

最经典的应用：Provider 启动时注册，下线时自动摘除。

  • Provider 启动：创建临时节点 /dubbo/com.example.DemoService/providers/dubbo%3A%2F%2F192.168.1.10%3A20880（URL 编码后的地址，临时节点）；
  • Consumer 启动：注册自己（/consumers/...），同时 getChildren + watch 订阅 /dubbo/.../providers；
  • Provider 变更（上线/下线）：Watch 触发，Consumer 刷新本地可用列表；
  • Provider 崩溃：会话过期 -> 临时节点被删 -> 自动从列表摘除，无需人工介入。

注意：ZK 在这里只扮演注册中心，Dubbo 本身不依赖 ZK 的锁/配置能力。Dubbo 3.x 推荐基于 Nacos 或应用级服务发现（/services/<app>/<ip:port>），ZK 仅作为可插拔的注册中心实现之一。

3.4 Master 选举

思路：临时节点的创建是原子的——同一路径只有一个客户端能创建成功，成功者即 Master。

这个方案简单但有两个问题：

  1. 惊群：Master 宕机时所有候选者同时被唤醒。改进：候选者先创建临时顺序节点，排序最小的当 Master，其余只监听前驱（同 3.1）；
  2. 旧 Master 假死：Master 因网络分区与集群失联（会话还在、临时节点没删），此时新 Master 已上任，可能出现”双主”——这不是 ZK 能解决的，需要业务侧做 fencing（如带版本号的租约、幂等操作、旧主发现无法再连接集群时自杀）。

生产环境直接用 Curator 的 LeaderLatch / LeaderSelector（见 6.3），别自己造轮子。

3.5 分布式队列与屏障

  • FIFO 队列：入队 create -s /queue/q_ 空数据，出队 getChildren 取序号最小的并删除。实现简单，但”取最小 + 删除”不是原子的，并发出队需要加锁或用事务，性能也差——实践中几乎没人用 ZK 做队列，直接上 Kafka/RabbitMQ；
  • 分布式屏障（Barrier）：所有参与方在 /barrier/join 下创建临时节点，某节点 getChildren 数达到阈值后创建 /barrier/ready，其余节点 exists("/barrier/ready", watcher) 等待放行。

场景价值不大，主要是考察对”顺序节点 + Watch”组合的掌握程度。

4. Watcher 机制

4.1 Watch 的原理与特性

客户端在 getData / getChildren / exists 时传入 Watcher，即可对节点注册监听。核心特性：

  1. 一次性触发：事件触发后 Watcher 即失效，客户端必须重新注册，否则后续变更收不到；
  2. 轻量通知：服务端只推送事件类型和节点路径，不包含变更后的数据，客户端需要再发一次读请求；
  3. 服务端存储：Watcher 保存在服务端内存（按连接管理），事件触发时由处理该事务的服务器发送给客户端；
  4. 顺序保证：同一客户端的 Watcher 回调按触发顺序串行执行（客户端单线程事件处理，见 4.2）。
事件类型 触发条件 哪些 API 可注册
NodeCreated 节点被创建 exists
NodeDeleted 节点被删除 exists / getData
NodeDataChanged 节点数据或 Stat 变更 exists / getData
NodeChildrenChanged 子节点列表变化 getChildren

注意细节：getData 注册的 Watcher 不会因子节点变化触发，getChildren 注册的 Watcher 不会因数据变化触发，exists 注册的能覆盖创建/删除/数据变化。

3.6+ 的增强：addWatch(path, watcher, AddWatchMode) 支持持久 Watcher（触发后不失效）和持久递归 Watcher（对子节点也生效），缓解了”一次性”带来的重注册烦恼。

4.2 客户端 Watch 管理（ZKWatchManager、事件处理）

原生客户端的 Watcher 管理分三层：

  1. ZKWatchManager：每个客户端连接持有一个，内部维护三张表——dataWatches、existWatches、childWatches，均为 Map<String, Set<Watcher>>（路径 -> Watcher 集合），表间独立分发；
  2. SendThread：IO 线程，负责网络收发与心跳，收到服务端的 WatcherEvent 后放入事件队列；
  3. EventThread：事件处理线程，从阻塞队列中取出事件回调 Watcher.process()。所有 Watcher 回调都在 EventThread 上串行执行，保证同一客户端内回调不并发、顺序与事件产生顺序一致——这也意味着回调里不能做耗时操作，否则会阻塞后续事件（包括连接状态事件）。

事件分发的核心逻辑（materialize）：按事件类型（NodeDataChanged 等）匹配路径到对应的 watch 表，取出 Watcher 集合后从表中移除（一次性），并过滤掉连接断开期间的无效状态。

Watch 丢失的根源：连接断开期间产生的事件不会补发（触发即失效），恢复连接后已注册的 Watcher 也不再有效。因此正确的客户端模式是”事件回调里重新注册 + 重连成功后全量刷新“。Curator 的 NodeCache 内部封装了这套逻辑（Watch 回调里自动重注册），线上应优先使用，避免手写踩坑。

5. 集群与高可用

5.1 集群角色（Leader / Follower / Observer）

角色 参与投票 处理写请求 处理读请求 数量建议
Leader 是 是（唯一写入口，其他节点转发给它） 是 1
Follower 是 转发给 Leader 是 2~4（与 Leader 组成奇数，如 3 或 5）
Observer 否 转发给 Leader 是 按需扩展读
  • 法定人数（Quorum）：> n/2，3 节点集群需 2 票，5 节点需 3 票。投票只算 Leader + Follower；
  • Observer：不参与选举和投票，只同步数据并提供读服务，用于扩展读吞吐或跨机房就近读（只读节点不会拖慢写提交）。配置方式：server.4=host:2888:3888:observer 或节点内 peerType=observer；
  • 为什么集群通常 3 或 5 台：需要奇数的投票节点来避免”平票”：3 台容忍 1 台故障，5 台容忍 2 台，7 台以上边际收益递减（每次写要等多数派，投票成员越多写延迟越高）。

每台节点在 dataDir 下写 myid 文件（内容为 1/2/3）。启动后 zkServer.sh start，用 zkServer.sh status 查看角色。

部署要点：

  • 事务日志与数据快照分开磁盘（dataLogDir 指向独立磁盘/SSD），写事务日志是提交路径上的 fsync，磁盘性能直接决定写 QPS；
  • 三节点跨机房部署时应避免”2+1”式分区（多数派恰好落在同一机房时可容忍，但极端情况下可能整体不可用），一般同机房双机房 + 奇数投票；
  • 客户端连接串用逗号分隔全部节点（zk1:2181,zk2:2181,zk3:2181），客户端会自动择一连接并支持故障切换，也可用 chroot（zk1:2181/app）将命名空间隔离给不同业务。

5.3 线性一致读（sync 调用）

ZooKeeper 的写是线性一致的，但读不是：读请求被各自服务器独立处理，命中落后于 Leader 的 Follower 时会读到旧数据（顺序一致性允许）。需要严格线性一致读（例如读取后马上要用于业务决策）时，标准做法是 sync + read：

Curator 封装为 client.sync().forPath(path)。注意 sync 是异步的，必须等回调后再读。

也可以直接命中 Leader 读（Leader 的数据必然最新），但客户端不知道谁是 Leader，且读 Leader 也会增加 Leader 负载。工程上的取舍：绝大多数读场景容忍最终一致（几毫秒~几十毫秒），个别强读场景用 sync，不要把读都压到 Leader 上。

6. Curator 客户端实战

6.1 Curator 对原生客户端的改进

原生客户端（ZooKeeper 类）的问题：API 原始、Watcher 一次性易丢、没有重试、线程要自己管、没有分布式锁/选举等高层组件。Curator（Apache 顶级项目，社区事实上标准）提供：

  • CuratorFramework：fluent API 的框架封装，带连接状态管理与会话重建；
  • RetryPolicy：可配置重试（ExponentialBackoffRetry 等），自动处理临时失败；
  • 连接状态监听：ConnectionStateListener 区分 RECONNECTED / SUSPENDED / LOST，解决”会话过期了业务还不知道”的经典问题；
  • Recipes：分布式锁、Leader 选举、屏障、计数器、NodeCache（自动重注册的 Watch 缓存）等开箱即用。

6.2 分布式锁（InterProcessMutex 源码级分析）

InterProcessMutex 是 Curator 最常用的锁，源码要点：

  1. 加锁（acquire -> internalLock -> attemptLock）：
    • StandardLockInternalsDriver.createsTheLock：在锁路径下创建临时顺序节点，路径形如 /locks/my-lock/_c_<uuid>-0000000001（_c_ 是 Curator 约定前缀）；
    • 获取锁路径下所有子节点并排序（getSortedChildren），找到自己的位置；
    • 自己排第一 -> 加锁成功，返回；
    • 否则监听前驱节点（getChildren 排序后 index-1），阻塞在内部锁上；前驱被删除触发 Watch 后重新检查（循环），兼顾了前驱被删后自己前面还有别的节点的竞态；
  2. 可重入：InterProcessMutex 用 ThreadLocal 记录持有次数与锁节点路径，同一线程可重复 acquire，重入次数归零才真正删除节点；
  3. 释放（release）：删除自己的临时节点。前驱删除会唤醒恰好排在后面的那个等待者——一次释放只唤醒一个，天然防惊群；
  4. 会话过期：临时节点被服务端删除，锁”丢失”，但本地认为还持有——正确姿势是注册 ConnectionStateListener，收到 LOST 事件时终止业务（抛异常/降级），绝不能继续操作临界区。

配套组件：InterProcessSemaphoreMutex（不可重入）、InterProcessReadWriteLock（读写锁，写锁排他）。

6.3 Leader 选举（LeaderLatch / LeaderSelector）

LeaderLatch：简单”抢一把锁，抢到就是 Leader”。

实现原理：每个实例在 /election/master 下创建自己的临时节点，排序最小的实例是 Leader（与锁同款逻辑：监听前驱），其余实例等待；Leader 掉线（会话过期/主动 close）后自动顶替。latch.hasLeadership() 可查询当前状态。

LeaderSelector：带”任期”的选举——当选后回调 takeLeadership()，方法返回即让出领导权，配合 autoRequeue() 自动重新参与竞选，适合”周期性换人干活”的定时任务场景。

选择建议：只要求”同刻唯一主”用 LeaderLatch；要求”轮换执行任务”用 LeaderSelector。

6.4 完整 Spring Boot 集成示例

依赖管理注意：项目里若同时引入 Kafka/Hadoop 等其他 ZK 依赖，务必统一 org.apache.zookeeper:zookeeper 版本，否则极易出现 NoSuchMethodError。

7. ZooKeeper 在主流框架中的应用

7.1 Dubbo 中的 ZK

Dubbo 使用 ZK 作为默认注册中心之一（dubbo:// 协议下）。数据节点结构：

工作流程：Provider 注册临时节点 -> Consumer 订阅 providers 目录（Watch）-> 列表变化实时刷新 -> Provider 崩溃临时节点消失自动摘除。Dubbo 3.x 的应用级服务发现则注册到 /services/<application>/<ip:port>，配一份服务元数据，节点数从”接口数”降为”实例数”，对 ZK 的压力大幅降低。

7.2 Kafka 旧版中的 ZK

Kafka 3.x 之前的版本把 ZK 当”大脑”：

  • Controller 选举：/controller 临时节点，谁创建成功谁是 Controller（负责分区 leader 选举、副本分配）；
  • Broker 注册：/brokers/ids/{id} 临时节点，保存监听地址；
  • 元数据：/brokers/topics/{topic} 存储分区与副本分配、ISR 列表、版本信息；
  • 旧版消费者组：/consumers/{group}/offsets（0.9 之前的消费者；0.9 之后偏移量已迁到 Kafka 自身的 __consumer_offsets topic）；
  • 配置与集群 ID：/config、/cluster/id。

为什么 Kafka 要脱离 ZK（KRaft 演进）：

  1. 伸缩瓶颈：分区数达到百万级时，ISR 变更、分区元数据变更让 ZK 的写入成为瓶颈——ZK 是”全部写走单 Leader + 多数派落盘”，吞吐有限；
  2. 双系统运维：Kafka 集群之外还得单独部署、监控、升级一套 ZK 集群，版本兼容问题频发；
  3. 故障域耦合：ZK 抖动会拖垮整个 Kafka 集群（Controller 失联即触发重选，期间不可服务）；
  4. 一致性模型限制：Kafka 需要”分区内有序 + 高吞吐”的元数据日志，自研 KRaft（基于 Raft 的控制器集群，元数据以日志方式复制）更贴合业务。

时间线：Kafka 2.8 引入 KRaft（early access），3.3 起生产可用，4.0 彻底移除 ZK 支持。新项目直接用 KRaft 模式即可。

7.3 Hadoop / HBase 中的 ZK

  • Hadoop HA（HDFS）：ActiveStandbyElector 在 /hadoop-ha/{nameservice}/ActiveStandbyElection/ActiveBreadCrumb 创建临时节点，创建成功的 NameNode 为 Active，Standby 监听并监控 Active 的会话；Active 故障时触发自动故障转移（failover），并对旧 Active 执行 fencing（强制杀进程/关端口），防止双主写；
  • HBase：根路径 /hbase 下——/hbase/master（Active HMaster 的临时节点，多 HMaster 竞争创建，失败者注册到 /hbase/backup-masters 待命）、/hbase/rs/{hostname,port}（RegionServer 临时节点，上下线实时可见）、/hbase/hbaseid（集群 ID）、/hbase/replication（复制协调）。HBase 2.x 之后 region 分配已改为 HMaster 内的 Procedure V2，ZK 的职责收窄为主要承担 HMaster 选举、RegionServer 注册与复制协调。

8. 运维与避坑

8.1 常见问题

1. Session 过期（最频发的事故）

表象：锁突然失效、服务注册节点被删、客户端收到 Expired 状态。根因一般是心跳超时：网络分区、JVM 长 GC（CMS/老年代收集停顿超过 sessionTimeout）、CPU 飙高或线程饥饿。

应对：

  • 合理设置 sessionTimeout（默认协商上限 40s，可调大 maxSessionTimeout；对锁场景建议 30~60s 与业务容忍度匹配——太短容易被 GC 误杀，太长故障感知慢）；
  • 服务端 JVM 使用低停顿 GC（3.8 默认 G1 也可），避免秒级 Full GC；监控 jstat；
  • 客户端捕获 Expired 后必须重建客户端实例（旧实例不可复用），临时节点会按新会话重新注册；
  • 用 Curator 时在 ConnectionStateListener 的 LOST 回调里做业务兜底（终止持有锁的任务）。

2. Watch 丢失

原因：Watch 一次性 + 连接断开期间事件不补发。表现：配置更新没生效、服务列表没刷新。

应对：

  • 回调里”重新注册 + 拉取最新数据”，两步同时做，杜绝”先查后注册”之间变更的竞态；
  • 重连成功后（RECONNECTED）全量刷新本地缓存，而不是依赖增量事件；
  • 直接用 Curator 的 NodeCache / PathChildrenCache（内部自动重注册）。

3. 脑裂与”双 Leader”

ZooKeeper 集群自身不会脑裂（提交需多数派），但客户端侧要防两类问题：

  • 分区期间连上少数派的 Follower：能读到旧数据，写会被拒绝（没有 Leader），业务要能容忍；
  • 自研选举/锁的”假死双主”：旧主还活着但已与集群失联。ZK 只管”节点存在”，不管”业务进程存活”，需要业务侧 fencing（版本号、租约、任务幂等）。

4. 集群抖动

慢盘导致 fsync 超时 -> Follower 被 syncLimit 剔除 -> 触发重选，雪崩式切换。排查顺序：磁盘 IO（iostat）-> 磁盘剩余空间（快照/txn 日志占满 dataDir）-> 时钟偏移 -> GC。另外注意：syncLimit 默认 5*tickTime=10s，太激进可放宽到 10~15s。

5. 大节点与多 Watch

  • 单 ZNode 数据默认上限 1MB（jute.maxbuffer，调大需全部节点一致且谨慎）；业务数据永远不要放 ZK；
  • Watch 数量级在万级以上会显著增加服务端内存与网络压力，监控 zk_watch_count；
  • 临时节点大量短生命周期时，会话过期清理会瞬时打高 Leader 负载。

8.2 监控指标

开启 4 字命令白名单（3.5+ 默认关闭，zoo.cfg 配置）：

mntr 关键指标与建议：

指标 含义 建议
zk_server_state 本机角色（leader/follower/observer） 记录切换次数，频切即告警
zk_znode_count 节点总数 趋势监控，突增可能是临时节点泄漏

8.3 ZooKeeper 的局限性

面试与选型都常被问到，明确这些边界比堆优点更重要：

  1. 不是数据库：无表、无索引、无 SQL，数据全量驻留内存，单节点数据默认限 1MB，只适合小体积协调数据；
  2. 写吞吐有限：所有写走单 Leader + 多数派落盘，3~5 节点集群常规磁盘下写 QPS 通常在数千到两三万量级，不适合高写入；读吞吐可通过加 Observer 线性扩展；
  3. 一致性有取舍：读不是线性一致（需 sync），Watch 一次性且通知不含数据，使用起来比 etcd/Nacos 笨重；
  4. 扩缩容不友好：投票成员变化影响法定人数，扩容通常需要滚动重启（3.5+ 有 reconfig 动态变更，但运维复杂度仍在），集群规模一般 3~7 台；
  5. 运营成本：需要独立部署、监控、升级，这也是 Kafka 等框架选择脱离 ZK 的根本原因之一；
  6. 故障窗口：fsync 批量窗口（fsync.windowMs，默认 1000ms）内确认的事务可能在崩溃时丢失，且会话过期机制会误杀慢 GC 的持锁进程。

选型建议：配置管理、分布式锁、服务注册用 etcd/Nacos 体验更现代；若团队已有 ZK 基建、或需要临时节点的”故障自愈”语义，ZK 3.8 依然可靠。理解 ZK 的价值不在”用它”，而在于它把共识、选举、Watch、临时节点这些分布式原语讲得最清楚——吃透 ZAB 和本文的场景，分布式系统面试的核心内容就覆盖了大半。

MySQL 高可用与分库分表实战

Posted on 2025-10-10 In 数据存储 Word count in article: 13k Reading time ≈ 46 mins.

本文是《MySQL 原理与优化》的进阶篇，索引/SQL 优化/锁/MVCC 等基础概念见该文（abbrlink：32511a71）。本篇聚焦”单机 MySQL 撑不住之后怎么办”：先解决高可用（主从复制、读写分离、故障自动转移），再解决扩展性（分库分表、ShardingSphere 实战、平滑扩容）。

1. 为什么需要高可用与分库分表

1.1 单机 MySQL 的三个瓶颈

瓶颈 具体表现 对应解法
容量瓶颈 单表数据过亿，B+ 树高度增加，索引页缓存命中率下降，备份/DDL 时间不可接受 分库分表
并发瓶颈 单机连接数（默认 151）打满、锁竞争加剧、IOPS/CPU 成为天花板 读写分离 + 多实例 + 分库
单点故障 机器宕机/磁盘损坏/机房故障，服务直接不可用，数据可能丢失 主从复制 + 高可用切换

这三个瓶颈不是”选一个解决”，而是层层递进的关系：

1.2 CAP 视角下的 MySQL 扩展路径

CAP 定理：一个分布式系统最多同时满足一致性（C）、可用性（A）、分区容错性（P）中的两个。MySQL 生态的所有扩展手段，本质都是在 C 与 A 之间做权衡：

  • 主从异步复制：追求 A（主库写完立即返回，从库可能滞后），牺牲 C（短暂读到旧数据）。
  • 半同步复制/组复制：把 C 拉回来，代价是写延迟上升、吞吐下降。
  • 分库分表：数据被切到多个实例，C 从”单实例内强一致”退化为”跨实例需要分布式事务”，这也是 5.4 分库分表问题的根源。

选型心法：先问”要解决什么问题”。读多写少 → 读写分离；数据量大 → 分库分表；既想高可用又想低延迟 → 半同步 + 自动切换工具。不要一上来就分库分表——它带来的复杂度（见 5.4）远超单机加配置。

2. 主从复制

2.1 复制原理：三线程 + binlog

主从复制的核心是 binlog（二进制日志，记录数据变更事件）。它的流转依赖三个线程：

线程 所在节点 职责
Binlog Dump Thread 主库 监听 binlog 变更，把事件推送给已注册的从库（show master status 记录 File/Position，dump 从这个位点开始）
I/O Thread 从库 向主库发起 dump 请求，接收 binlog 事件，顺序追加写入本地 relay log（中继日志）
SQL Thread 从库 从 relay log 读取事件，顺序执行重放，把变更应用到从库数据

binlog 有三种记录格式，直接影响复制行为：

格式 记录内容 优点 缺点
STATEMENT 原始 SQL 日志量小 依赖上下文（NOW()、LIMIT 无 order、存储过程等）导致主从不一致
ROW 变更前后的整行数据 最准确，与上下文无关 日志量大，大事务日志放大
MIXED 引擎自动选择 折中 仍有不可控分支

生产环境 5.7+ 建议 binlog_format=ROW，配合 binlog_row_image=FULL（默认），这是半同步、组复制、CDC（Canal）的基石。

位点复制 vs GTID 复制

位点复制（5.6 及之前）：靠 binlog 文件名 + 偏移量 定位同步起点。

问题：主库 binlog 滚动或人为清理后，File/Position 就失效了；多级复制（主→从→从）场景位点定位极难。

GTID 复制（5.6 引入，5.7/8.0 主流）：GTID = server_uuid:transaction_id，全局唯一。每个提交的事务都有独立 GTID，从库记录 gtid_executed，靠 GTID 集合自动对齐位点。

对比项 位点复制 GTID 复制
定位方式 文件名 + 偏移量 全局事务 ID 集合自动对齐
建从库 需 mysqldump --master-data 记录位点，手工填 AUTO_POSITION=1 自动同步起点
binlog 滚动 位点可能失效，需重置 不受影响
主从切换 切换后手工找位点，易错 新主从关系自动协商，无需手工
限制 无 事务内不支持混合使用临时表与 DDL 等少量场景

结论：新环境一律 GTID。8.0 中位点复制仅用于极特殊场景。

2.2 复制模式：异步 / 半同步 / 组复制

异步复制

主库写完 binlog 就返回成功，dump 线程异步推送。从库永远可能落后，主库宕机时未推送的 binlog 会丢失（丢数据），且从库可能选成新主导致数据不一致。

半同步复制（semi-sync）

主库在提交前等待至少一个从库 ACK（收到并写入 relay log），才向客户端返回成功。5.7 后有两个等待点：

  • rpl_semi_sync_master_wait_point=AFTER_SYNC（默认，推荐）：binlog 刷盘后、引擎提交前等待 ACK。从库 ACK 后主库才提交，主从零丢失（主库宕机时至少一个从库有全部数据）。
  • AFTER_COMMIT：引擎提交后等待 ACK。主库已提交才等，宕机瞬间有丢数据窗口，且从库重复执行（幂等性）问题更复杂。

半同步是”退让式”的：ACK 超时（rpl_semi_sync_master_timeout，默认 10s）自动降级为异步，保证主库可用性，同时产生数据丢失风险——这正是 MHA 等切换工具要处理的问题。

组复制（Group Replication，MGR）

把写事务广播给组内所有成员，通过 Paxos 一致性协议对”事务提交顺序”达成共识，再执行 certification（认证） 冲突检测：新事务与组内未提交事务读写冲突（AUTO_INCREMENT、外键、未提交读、写冲突）则回滚重试。MGR 保证：组内任一成员提交成功，数据在组内一致——这是 C 与 A 之间最靠 C 的一档。

对比项 异步 半同步 组复制
数据一致性 可能丢数据 至少一从库不丢 组内强一致
写延迟影响 无 +1 次 RTT（等 ACK） +2~3 次 RTT（Paxos 协商）
故障切换 手动/工具 手动/工具 组内自动选举
可用性 最高 高（超时降级） 依赖多数派（n/2+1 存活）
复杂度 最低 低 高（插件、网络、主键要求）
适用场景 兜底备份、可容忍丢失 生产主从标配 要求自动容灾 + 一致性

2.3 主从延迟的原因

延迟 = SQL Thread 回放速度跟不上主库生成 binlog 的速度。常见根因：

  1. 大事务：一条 DELETE FROM t WHERE create_time < '2020-01-01' 删千万行，binlog 事件量大，从库要连续回放很久，期间只差会指数增长。
  2. 从库单线程回放：主库并发写入（10 个线程各写各的），从库 SQL Thread 只能一条条顺序执行——天然吞吐减半以上。
  3. 主库并发写入量高：主库 10 万 TPS，从库回放能力（与执行能力相当）只有几万，永远追不平。
  4. 从库配置弱：CPU/磁盘（机械盘 vs SSD）/刷盘参数（sync_binlog、innodb_flush_log_at_trx_commit）与主库不对等。
  5. 无主键的表：ROW 格式回放时要全表扫描定位行，回放速度断崖下跌。
  6. 行锁/外键：回放事务之间互相阻塞。
  7. 误判断延迟：Seconds_Behind_Master 本身有缺陷——当 I/O 线程落后（网络慢）时它显示 0，实际已经落后很多。

2.4 并行复制（MTS，Multi-Threaded Slave）

从 5.6 到 8.0，并行复制的演进史就是”允许哪些事务并行回放”的放宽史：

版本 并行策略 原理 缺点
5.6 按库并行（slave_parallel_type=DATABASE） 不同库的事务并行回放 单库写多无效果；库之间锁依赖仍串行
5.7 按组提交并行（LOGICAL_CLOCK） 主库同一组 commit 的事务（组提交窗口内），从库并行回放 依赖主库 binlog_group_commit_sync_delay 加大组；窗口小并行度低
8.0 writeset 并行（WRITESET） 用行哈希（writeset）判断事务写集是否相交，不相交即可并行，不依赖提交窗口 内存开销；自增/外键/唯一索引仍强制串行

要点：writeset 是最接近理论最优的方案——主库两个事务只要更新的是不相交的行，从库就能并行重放，把”主从吞吐差异”这一延迟主因几乎抹平。生产 8.0 直接开 writeset。

2.5 主从切换与故障恢复

切换目标：主库故障时，把从库提升为新主、其余从库指向新主、业务流量切过去，且不丢数据、不双主脑裂。

手工切换的四个动作（理解了这个，才能理解 MHA/Orchestrator 在自动化什么）：

  1. 定位差距：选一个 binlog 位置最靠前的从库（show slave status 的 Read_Master_Log_Pos），它是新主候选。
  2. 补齐中继日志：候选从库先用其他从库的 relay log（apply_diff_relay_logs）或主库 binlog 把自己补到”全组最新”。
  3. 提升：STOP SLAVE; RESET SLAVE ALL; 让候选库变成可写主库。
  4. 重定向：其余从库 CHANGE MASTER TO 指向新主，业务数据源指向新主。

手工切换的致命风险：脑裂。主库其实没死（网络分区），切换后旧主恢复写入，两个主同时接收写请求，数据分裂。所以切换工具必须配合”旧主下线/只读”（read_only=ON）或 VIP 摘除来防脑裂。

3. 读写分离

3.1 实现方案

方案 代表 实现位置 优点 缺点
客户端路由 AbstractRoutingDataSource、ShardingSphere-JDBC 应用内 无额外网络跳数、延迟最低、可编程性强 侵入应用、每语言一套实现
中间件代理 ShardingSphere-Proxy、MyCat、ProxySQL 应用与 MySQL 之间 应用无感知、跨语言、便于集中管控 多一跳网络、单点风险（需中间件自身高可用）

无论哪种方案，核心都是：读 SQL 路由到从库，写 SQL（含事务）路由到主库。判断”读还是写”的规则：SELECT 走从库；INSERT/UPDATE/DELETE/DDL 以及任何事务内的 SQL 走主库（事务内读从库可能读到事务本身未提交的数据）。

3.2 主从延迟下的数据一致性处理

读写分离引入的经典问题：写完主库立刻读从库，读到旧值。处理手段按可靠性排序：

方案 原理 可靠性 代价
强制走主库 写操作后紧接着的读（或整个请求/用户会话）路由到主库 高（无脑正确） 主库读压力上升，读分离收益打折
等待位点/GTID 读前执行 SELECT MASTER_POS_WAIT(...) 或 WAIT_FOR_EXECUTED_GTID_SET(...)，等从库追到指定位置 高（有明确语义） 等待耗时 = 剩余延迟，最坏到超时
半同步复制 从库 ACK 后再返回写成功 较高 写延迟 +1 RTT，且超时降级
sleep 固定时间 Thread.sleep(100) 再读从库 低（靠猜，延迟超界就出错） 白等 100ms，不推荐

工程落地组合拳（业界通用做法）：

  1. 刚写完立即读 → 走主库。Spring 中实现：路由键记录”本线程/本请求最近是否有写”，有写则该请求内后续读强制走主库数据源。
  2. 事务内一律走主库（事务隔离性要求）。
  3. 对账类、统计类弱一致读 → 走从库 + 可容忍延迟。
  4. 底层把半同步 + MTS 开起来，把延迟基数压到毫秒级，前面 1 的窗口就很小。

4. 高可用架构

高可用 = 主从复制 + 故障自动检测 + 自动切换 + 防脑裂。下面四种方案在”自动化程度”和”一致性”两个维度上递进。

4.1 MHA（Master High Availability）

架构：Manager 节点（可做主备）+ 每台 MySQL 节点上的 Node 组件。

故障切换流程：

  1. Manager 通过心跳检测主库（SSH + 3306 端口探活），判定主库不可用（连续失败 N 次）。
  2. 从候选从库中选中继日志最新的（再考虑配置、优先规则）。
  3. 候选从库执行 apply_diff_relay_logs：从其他从库补齐缺失的中继日志，把自己追到全组最新（如果半同步没兜住主库已丢的 binlog，这里补不回来——这就是 MHA 的”丢数据窗口”）。
  4. 候选从库 STOP SLAVE 并提升为可写主库。
  5. 其余从库自动 CHANGE MASTER TO 指向新主。
  6. 通过回调脚本把 VIP（虚拟 IP）或代理配置切到新主，业务恢复。

优点：成熟（10+ 年生产验证）、切换速度快（通常 30s 内）、不依赖复制协议（位点/GTID 都行）。
缺点：官方已停止更新（社区维护）、切换依赖 SSH、一致性靠”半同步 + 补齐 relay log”尽力而为，极端场景仍可能丢数据。

4.2 MGR（MySQL Group Replication，组复制）

第 2.2 节的组复制协议，配成高可用架构时选单主模式：

  • 组内只有 Primary 可写，其余 Secondary 只读（super_read_only）。
  • Primary 故障后，组内通过一致性协议自动选举新 Primary（优先级最高、数据最新的节点），其他成员自动把 GTID 对齐到新 Primary。
  • 业务侧需要感知”谁是 Primary”——要么通过 MySQL Router（见 4.3），要么应用层 SELECT * FROM performance_schema.replication_group_members 探测。

限制（必须背）：只支持 InnoDB；所有表必须有主键（否则认证冲突检测失效）；外键/SAVEPOINT/LOAD DATA 受限；成员间网络抖动会反复触发 re-election，延迟敏感业务要关注。

4.3 InnoDB Cluster（MySQL Shell + MySQL Router）

把 MGR 工程化的全家桶方案：

  • MySQL Shell：一行命令建集群 dba.createCluster('mycluster')、加实例、在线变更配置。
  • MySQL Router：应用连 Router 的固定端口，Router 探测组内 primary/secondary 变化，故障切换后自动把读写流量引到新主，应用零感知。
  • 8.0.20+ 还支持 InnoDB ClusterSet（跨机房主备）和 Read Replicas（只读扩展）。

优点：官方全家桶、运维命令友好、Router 免应用改造。
缺点：必须 MGR（继承其限制）；Router 本身是单点（需多 Router + VIP 或负载均衡）；切换时间受 MGR 选举影响，比 MHA 慢（秒级~十秒级）。

4.4 Orchestrator + VIP 自动故障转移

Orchestrator 是独立于 MySQL 的拓扑管理/故障切换工具：

  • 多个 Orchestrator 节点用 Raft 选主，保证切换决策本身不脑裂。
  • 持续采集 MySQL 复制拓扑（show slave status、binlog 位点），可视化任意拓扑结构（级联、双主、任意树）。
  • 故障时按策略自动选择新主（is_master、replication_depth、preferred 列表），执行切换并通过 Hook 脚本把 VIP 飘移/通知 DNS 或代理（如 LVS、Keepalived）。

优点：拓扑管理能力最强（任意结构、在线演练 orchestrator-client recover 模拟切换）、支持多机房、社区活跃（GitHub Vitess 生态）。
缺点：部署运维复杂度高（Orchestrator 自身 + VIP/脚本都要管）、默认不做数据补齐（需半同步兜底）、切换动作依赖 Hook 脚本质量。

5. 分库分表理论

5.1 垂直拆分 vs 水平拆分

维度 垂直拆分 水平拆分
拆分对象 按列（字段）拆 按行（数据）拆
拆分粒度 表拆列：大文本/热列分离；库拆业务：订单库/用户库/库存库 同结构多表：t_order_0..N，每个只存部分行
解决 单表字段过多、IO 放大、业务耦合 单表数据量过大、写入吞吐不够
副作用 表要 join 回来；跨库 join 全局查询、聚合、事务都要跨分片
难度 较低 较高（所有复杂度都在这里）

工程事实：垂直拆库是最先做、收益最大的——把订单、用户、库存拆到独立实例，各自扩容互不干扰；水平分表是最后的手段，只在垂直拆分 + 读写分离之后仍撑不住时上。

5.2 分片键选择

分片键（Sharding Key）决定一行数据落在哪个分片。选错分片键，分库分表就废了。原则：

  1. 等值查询频率最高的列。订单表按 user_id 分片，则”查某用户的订单”完美命中单个分片；如果用户端访问是主流，order_id 就不如 user_id。
  2. 写入均匀性：分片键取值分布要均匀（用户 ID 天然均匀；按商家分片则大商家容易打爆单库）。
  3. 无法命中分片键的查询要提前想好兜底：
    • 映射表/索引表：user_id ↔ order_id 双向映射表，先查映射再路由（MySQL 还是 ES 自选）。
    • 数据冗余/宽表：把查询热点维度冗余到独立分片表（业界最常用：ES 存检索数据，MySQL 只做 ID 回源）。
    • 广播查询：小表场景直接全分片广播 + 合并（ShardingSphere 的”全库路由”）。

5.3 分片算法

算法 原理 优点 缺点 适用
取模 mod shard = key % N 实现简单、分布均匀 扩容 N 变化后几乎所有数据都要迁移；范围查询无法裁剪 数据量长期稳定、不常扩容
范围 range shard = key / 单表容量 或按日期/ID 段 扩容友好（加表不迁移旧数据）、天然支持范围裁剪 热点集中（新数据都写最后一片）；分布不均 日志、时序数据（按天/月分表）
哈希 hash shard = hash(key) % N 分布均匀、无顺序关联 同取模，扩容迁移大 同取模，可加盐避免规律冲突
一致性哈希 key 哈希到环上，顺时针找最近节点 加节点只迁移相邻 1/N 数据 路由计算复杂、数据分布天然不均（靠虚拟节点缓解）、范围查询难 需要频繁扩缩容的 KV 类场景

口诀：均匀性要取模（或 hash 取模），扩展性要 range，两者都想要 → 一致性哈希或”range + 末尾预留”（如 09 表，扩到 20 表时只迁移 1019 的部分数据）。绝大多数业务最终选择 取模 + 规划好 2 的幂次倍扩容（8 表→16 表→32 表，每次全量迁移一次，代价可预估）。

5.4 分库分表带来的问题

问题 具体表现 解法
跨库 JOIN 订单与订单明细拆到不同分片，JOIN 失效 ①绑定表（同分片规则的表可 JOIN，见 6.2）②应用层组装（两次查询在内存 JOIN）③宽表冗余④禁止 JOIN 用 ES 兜底
分布式事务 一笔订单扣库存（库存库）+ 记订单（订单库），不能同时成功 ①事务内禁止跨库（把需要强一致的拆到同库）②Seata AT/TCC/2PC（见 6.5）③消息最终一致（对账兜底）
分布式 ID 多分片自增主键会重复 雪花算法（见 6.4）、号段模式（Leaf）、UUID（仅非索引场景）
扩容 取模分片加节点要迁移数据 停机迁移、双写迁移、一致性哈希（见第 8 章）
全局查询 COUNT(*)、不分片键的 WHERE 只能全分片聚合 汇总表/ES 预聚合、禁止此类查询、控制范围（时间兜底）

6. ShardingSphere 实战

ShardingSphere 有两个形态：JDBC（客户端模式，轻量，融入应用）与 Proxy（中间件模式，独立进程）。本章以 ShardingSphere-JDBC 5.4.x 为例，先啃内核，再上配置。

6.1 ShardingSphere-JDBC 架构：五阶段内核源码级分析

一句话总览：一条 SQL 进来，经过”解析 → 路由 → 改写 → 执行 → 归并”五个阶段，变成 N 条物理 SQL 发到 N 个数据源，再把 N 个结果集归并成一个返回。

阶段一：Parse（SQL 解析）

入口 SQLParserEngine（org.apache.shardingsphere.sql.parser.api）。用 ANTLR4 生成的语法解析器（每种方言一个 grammar，如 MySQLStatementLexer/Parser）把 SQL 变成 ParseTree（解析树），再经 SQLStatementVisitor（如 MySQLDMLStatementVisitor）遍历转换为抽象语法树 AST——SQLStatement 对象（SelectStatement、InsertStatement、UpdateStatement、DeleteStatement）。

SQLStatement 里装了什么？表（TableSegment）、条件（WhereSegment / PredicateSegment）、列（ColumnSegment）、聚合（AggregationSegment）、分页（LimitSegment）、分组排序（GroupBySegment/OrderBySegment） 等元数据。后续四个阶段全部基于这份 AST 工作，不再碰原始 SQL 字符串。解析结果按 SQL 文本缓存（ParseTreeCache），命中缓存省掉词法语法分析。

阶段二：Route（路由）

入口 SQLRouteExecutor → 根据 SQLStatement 类型交给对应 RouteEngine。路由的产物是 RouteContext，核心是 RouteUnit 列表——每个 RouteUnit = (dataSourceName, SQLUnit(逻辑 SQL + 参数))，即”这条逻辑 SQL 要拆成哪些物理片”。

路由的根本依据是分片键的值（来自 WHERE 条件、或参数绑定、或 Hint）。关键代码走向：StandardRoutingEngine.route() 内 calculateRouteContext() → getShardingConditions() 从 AST 提取 ShardingCondition（含 ShardingValue）→ 调用 ShardingRule.route() 交给 ShardingAlgorithm.sharding() 算出目标库/表。

三种典型路由行为：

  • 分片键等值条件 → 精确路由到 1 个数据源 1 张表（最好的情况）。
  • 分片键范围条件（BETWEEN/IN/>）→ 有 range 算法则范围裁剪，只路由命中的分片；没有则退化为全路由。
  • WHERE 里没有分片键 → 广播路由，全库全表都执行，结果在归并层合并——这是性能杀手，也是 5.2 强调分片键的原因。

阶段三：Rewrite（SQL 改写）

入口 SQLRewriteEngine。把逻辑 SQL 里的逻辑表名、逻辑列名替换为物理表名/列名，并处理分页、聚合、生成键等，产出可执行的物理 SQL。

改写的核心机制是 Token 流：SQLRewriteEngine 遍历 AST，把每个需要改写的位置（SQLToken）与原文片段交错拼接成新的 SQL 字符串。常见 Token：

Token 改写的例子
TableToken t_order → t_order_0（表名加分片后缀）
ColumnsToken 分片键/生成键列不在 INSERT 列中时补列名
InsertValuesToken INSERT 值改写（补分片键值、生成键值）
LimitToken（PaginationToken） LIMIT 10 → LIMIT 10 原样下发，归并层再整体截断（见归并阶段）
AggregationDistinctToken COUNT(DISTINCT id) 改写为子查询，归并层恢复
OrderByToken / GroupByToken 保序下发（有时改写排序字段）

参数也在这里改写（ParameterRewriteEngine）：分片键来自 ? 占位符时，把参数值路由层解析后用新的参数序号重建 ParameterList，保证改写后的物理 SQL 与参数一一对应。

阶段四：Execute（执行）

入口 JDBCExecutor + ExecutorEngine（内核线程池）。多个 RouteUnit 对应的物理 SQL 被分组并发执行：相同数据源的 SQL 聚成 ExecutionGroup，一个物理连接按顺序执行组内 SQL（减少连接数）；不同组在不同连接上并发跑。最终每个数据源返回各自的 ResultSet，放进一个 List<ResultSet> 交给归并阶段。

这里有两个决定性能的关键概念：

  • 连接模式（ConnectionMode）：
    • MEMORY_STRICTLY：结果一次性全量拉进内存（适合后续要全量归并的场景，如 GROUP BY/内存归并），占内存但连接占用少。
    • CONNECTION_STRICTLY：流式逐条读取（一个连接只服务一个结果集，适合 ORDER BY 流式归并），省内存但吃连接。
  • 执行引擎（ExecutorEngine.execute()）内部做负载均衡与并发控制，可按数据源/实例配置 max-connections-size-per-query 限制单查询连接数。

阶段五：Merge（结果归并）

入口 MergeEngine。把 N 个分片返回的 ResultSet 合并成逻辑上完整的一份结果。核心是 ResultSetMerger 接口与装饰器（Decorator）模式：根据 SQLStatement 类型把”核心 merger”层层包装。

归并的两大流派：

  • 流式归并（StreamMerger）：各分片结果本身有序（物理 SQL 已带 ORDER BY），用 PriorityQueue（堆）做多路归并，边读边出，内存 O(N)（N=分片数）。OrderByStreamMerger 是典型。
  • 内存归并（MemoryMerger）：分片结果无序或需要全量去重/分组时，全部载入内存再处理。GroupByMemoryMerger、DistinctDecoratorMerger 属于此类。

聚合函数在归并层重算而非简单相加：AVG = 各分片 SUM 之和 / 各分片 COUNT 之和（AvgAggregationUnit）；SUM/COUNT/MAX/MIN 对应各自 AggregationUnit；COUNT(DISTINCT) 需要在每个分片取 distinct 集合再合并。

归并层的精髓：LIMIT 不是简单把各分片拼起来，而是各分片取够 offset+limit 行，归并层用 LimitDecoratorMerger 边归并边丢弃，最终只返回 limit 行——内存与传输都最小化。

8. 扩容方案

分库分表最痛的时刻就是”表不够用了”——取模 8 表变 16 表，意味着数据要搬家。三种方案按”停机时长”递增排列。

8.1 停机扩容 vs 平滑扩容

方案 流程 停机时间 数据一致性 适用
停机扩容 停服 → 备份 → 按新规则全量迁移（INSERT ... SELECT 或工具）→ 校验 → 切新数据源 → 重启 数小时~数天 完全一致（无并发写入） 可接受停服的内部系统、凌晨窗口
双写迁移 双写 → 对账 → 灰度切读 → 停老库 接近 0 靠对账兜底 核心在线业务
一致性哈希 环上扩节点，仅相邻 1/N 数据搬家 可在线迁移 迁移期间新旧并存需标记位 KV 场景、持续扩容型业务

8.2 双写迁移方案

工程要点：

  • 双写原子性：A、B 双写不要放在业务事务里（拖慢主链路），用 MQ 异步双写 + 消息可重试，A 失败重试补写。
  • 对账是灵魂：比对范围字段（如 updated_at + 行哈希），发现差异用 B 为准回补 A；对账发现率极低但必须有，这是双写敢上线的底气。
  • 切读灰度：按 user_id 分段放量（1% → 10% → 50% → 100%），每段监控读延迟与错误率。
  • binlog 兜底：用 Canal 订阅 B 的 binlog 回放进 A，双写 + binlog 回放可以互为兜底（双写为主，binlog 保证最终一致）。

8.3 一致性哈希 + 虚拟节点的最小数据迁移

原理（见 5.3）：把节点哈希到一个 0~2^32-1 的环上，数据 key 哈希后顺时针找最近节点。加一个节点，只有该节点逆时针方向上一个节点的数据需要迁移（约 1/N）——对比取模的”几乎全量迁移”，这是数量级的差别。

虚拟节点的作用是解决两个痛点：

  1. 数据倾斜：节点少时哈希分布不均（环上某段数据密集），每个物理节点复制成 K 个虚拟节点（如 160 个）均匀铺在环上，数据分布趋近均匀。
  2. 迁移粒度：虚拟节点让”一段环”变小，迁移单位从”整节点”变成”虚拟节点片段”，迁移更精细。

迁移执行：新增节点后，把需要迁移的 key 范围标记为”迁移中”（读写双查、双写新节点），迁移完成后摘除标记——这个过程可在线、可灰度，比双写全量迁移方案轻得多。

代价：路由要维护哈希环（环结构 + 虚拟节点映射），范围查询基本不可用，适合 KV 型数据（缓存、Session、短 ID 查询）。MySQL 业务数据用一致性哈希的少，更多是作为”分片键再哈希”的辅助手段。

9. 最佳实践与避坑指南

9.1 分库分表不是银弹

什么时候该用：

  • 单表数据量 > 千万级且仍在增长，按分片键的查询仍是访问主流（说明值得拆）。
  • 写入吞吐超过单机上限（分库后写并发乘 N）。
  • 单库连接数、备份恢复时间、DDL 时间不可接受。

什么时候不该用（绕开）:

  • 数据量可控（百万级内）、未来 3 年可预估——单机 + 索引优化 + 读写分离足够，别为了架构而架构。
  • 查询面太广：大量查询不带分片键、需要频繁 JOIN/跨维度聚合——拆了之后这些查询全部退化，成本远超收益。
  • 团队无中间件运维能力——中间件本身要监控、升级、排障，比多买一台 MySQL 贵得多。

9.2 分片键设计原则

  1. 选”主查询路径”的等值列：订单库用户端高频查询是 WHERE user_id=?，分片键选 user_id；后台管理端高频按 order_id 查，那就做 order_id → user_id 映射表。
  2. 避免选”值可被更新”的列：分片键一旦修改 = 数据跨片搬家，业务上禁止 UPDATE 分片键（数据库层都不允许）。
  3. 分布要均匀：先 SELECT user_id % 8, COUNT(*) FROM t GROUP BY 1 验证历史数据分布再定。
  4. 范围算法考虑尾部热点：按时间分表时”今天”永远是最后一张表，写入热点单表——要么提前预建表，要么接受。
  5. 多维度访问提前设计：主键分片 + 索引表 + ES 检索的三层结构是订单类系统的标准答案。

  1. **只监控 Seconds_Behind_Master**：I/O 线程与 SQL 线程差距大时该值失真，漏报延迟——必须上 pt-heartbeat。

1. Dubbo 是什么

Dubbo 是 Apache 基金会下的高性能 Java RPC 框架，核心定位是：远程方法调用 + 服务治理。

它的定位不是全家桶式的微服务解决方案（那属于 Spring Cloud），而是一个把”服务之间如何高效、可靠、可控地互相调用”这件事做到极致的框架。

核心能力一张图：

能力分类 具体能力 Dubbo 中的实现载体
远程调用 透明 RPC（像调本地方法一样调远程） 动态代理 + 协议层（dubbo / tri / rest）
服务发现 服务注册、订阅、变更推送 Registry SPI（ZooKeeper / Nacos / Consul / Redis / K8s）
负载均衡 五种均衡策略 LoadBalance SPI（Random / RoundRobin / LeastActive / ConsistentHash / ShortestResponse）
集群容错 失败重试、快速失败、容错降级等 Cluster SPI（Failover / Failfast / Failsafe / Failback / Forking / Broadcast）
服务治理 路由、权重、灰度、降级、限流、优雅停机 Router SPI + Filter SPI + 配置中心
可观测性 调用统计、Metrics、链路追踪、QoS 控制台 Monitor + Metrics + QoS（默认端口 22222）
扩展机制 一切核心组件均可替换 SPI 机制（第 8 节重点）

与主流方案一句话对比：

  • vs gRPC：gRPC 是语言无关的高性能 RPC（HTTP/2 + Protobuf），强在跨语言互操作与性能，但服务发现、负载均衡、治理能力需要自行搭配；Dubbo 强在开箱即用的服务治理，3.x 通过 Triple 协议与 gRPC 生态打通。
  • vs Spring Cloud：Spring Cloud 以 HTTP REST 为中心，强在生态广度（网关、配置、消息等全家桶）；Dubbo 以二进制私有协议为中心，性能更高、治理能力内建（负载均衡/容错/路由/限流在框架内部完成，不依赖外部组件）。
  • 选型共识：Java 内部服务间调用、对延迟敏感 → Dubbo；跨语言、与 K8s/Envoy 生态深度整合 → gRPC；业务微服务全家桶、追求生态统一 → Spring Cloud。三者并非互斥，实践中常共存。

Dubbo 不是网关（对外 HTTP 接入需走 Triple REST 能力或独立网关）、不是配置中心（3.x 的配置中心只管理 Dubbo 自身配置）。

2. 核心架构

Dubbo 的经典架构由五大角色组成：

角色 职责
Container 服务运行容器（Spring 容器等），负责加载、启动、管理服务实例
Provider 服务提供方，暴露服务接口，向注册中心注册自己提供的服务
Consumer 服务消费方，向注册中心订阅服务，发起远程调用
Registry 注册中心，服务地址的注册与发现，地址变更时主动通知
Monitor 监控中心，异步收集调用次数、调用耗时等统计数据

一次完整调用的 6 步链路：

  1. 启动：Container 加载并启动 Provider，Provider 初始化连接、端口等资源。
  2. 注册：Provider 启动完成后，向 Registry 注册自己提供的服务 URL（协议、IP、端口、参数）。
  3. 订阅：Consumer 启动时向 Registry 订阅自己需要的服务。
  4. 通知：Registry 返回 Provider 地址列表给 Consumer；Provider 增减、下线、权重变化时，Registry 主动推送变更。
  5. 调用：Consumer 根据软负载均衡算法从地址列表中选择一个 Provider 发起调用；失败时按集群容错策略处理（重试/快速失败等）。
  6. 监控：Consumer 与 Provider 异步上报调用次数、耗时、成功失败等统计信息给 Monitor。

两个补充场景：

  • 直连模式：绕过注册中心，通过 URL 直连指定 Provider，常用于联调：@DubboReference(url = "dubbo://192.168.1.10:20880")。
  • 本地调用（injvm）：Consumer 与 Provider 同进程时，默认走 injvm 协议本地调用，不占用网络端口，也避免序列化开销。

3.2 服务暴露全流程

以 dubbo.registry.address=zookeeper://127.0.0.1:2181 为例：

  1. 配置解析：ServiceConfig（@DubboService 注解）读取 dubbo.application.name、dubbo.protocol.name、dubbo.registry.address 等配置。
  2. 组装 URL：生成 dubbo://192.168.1.10:20880/com.example.DemoService?anyhost=true&application=demo-provider&interface=com.example.DemoService&...，URL 是 Dubbo 的统一配置模型，后续注册、路由、负载均衡都基于它。
  3. 生成 Invoker：ProxyFactory.getInvoker(serviceImpl, DemoService.class, url) 把服务实现包装为 AbstractProxyInvoker（Invoker 是”可执行远程调用的实体”的统一抽象）。
  4. 暴露服务：Protocol.export(invoker) 交给 DubboProtocol，创建 Netty Server 绑定 20880 端口，返回 Exporter。
  5. 注册地址：RegistryFactory.getRegistry(url).register(url)，在 ZK 创建临时节点：dubbo/com.example.DemoService/providers/dubbo%3A%2F%2F192.168.1.10%3A20880%2F...。
  6. 本地副本：同时做本地暴露（injvm），供同进程 Consumer 直接调用；启动 QoS 管理端口 22222。

3.3 服务引用全流程

  1. 配置解析：ReferenceConfig（@DubboReference 注解）解析配置，构建引用 URL 与注册中心 URL。
  2. 创建引用 Invoker：Protocol.refer(DemoService.class, url)，RegistryProtocol 接管。
  3. 订阅（Subscribe）：registry.subscribe(consumerUrl)，在 ZK 持久监听 dubbo/com.example.DemoService/providers、routers、configurators 等节点。
  4. 通知（Notify）：注册中心返回 Provider URL 列表（首次订阅立即返回，之后变更增量推送）；RegistryDirectory 将 URL 列表转换为 Invoker 列表并动态维护。
  5. 集群包装：Cluster 按容错策略（如 failover）把 Invoker 列表包装成一个 ClusterInvoker——调用时先过 Router（路由过滤，如 tag 路由、条件路由），再经 LoadBalance 选一台。
  6. 生成代理：ProxyFactory.getProxy(clusterInvoker) 用 Javassist/JDK 生成接口动态代理，业务代码拿到的是代理对象，调用时经 InvokerInvocationHandler → ClusterInvoker → Filter 链 → 网络层发送。

Invoke 链路一句话： 业务方法 → 动态代理 → ClusterInvoker → Router 过滤 → LoadBalance 选点 → 出/入站 Filter 链 → 编解码 → 传输层。

4.2 Dubbo 协议：高性能但”封闭”

  • 单一长连接：Consumer 对每个 Provider 默认只建一条 TCP 连接（配置 dubbo.consumer.connections=1），所有请求在这条连接上复用，靠 requestId 关联请求与响应（16 字节固定报文头：magic 0xdabb(2B) + flag(1B) + status(1B) + requestId(8B) + bodyLength(4B)）。单连接避免了大量连接的资源开销，是 Dubbo 高性能的关键之一。
  • 局限：单连接 + 串行 IO 在大数据包、高并发大消息场景会成为瓶颈（官方建议消息体控制在 1M 内）；私有二进制协议导致跨语言、云原生场景举步维艰。

4.3 Triple 协议：为什么 Dubbo3 主推它

  1. 跨语言互操作：基于 HTTP/2 + Protobuf，与 gRPC 完全兼容，gRPC 客户端（Go/Python/Node 等）可直接调用 Dubbo 服务；Dubbo 也可以反哺 gRPC 生态。
  2. 云原生友好：HTTP/2 是网关、Ingress、Envoy、Istio、K8s 基础设施的天然标准，流量可被统一治理、观测；自定义 TCP 二进制协议对基础设施是”黑盒”。
  3. 多路复用：HTTP/2 一个连接上并发多路复用，解决大规模场景下连接数爆炸问题，也解除了 Dubbo 协议单连接的吞吐上限。
  4. 流式通信：原生支持四种调用模式，满足大文件传输、实时推送等场景。
  5. 新项目官方建议直接选 Triple；老项目可平滑升级（ext-protocol: tri + preferred-protocol: tri）。

注意：Dubbo 3.x 默认协议仍是 dubbo（兼容老用户），但官方强烈建议新项目显式配置 dubbo.protocol.name: tri。

4.4 序列化选型

序列化 性能 体积 跨语言 特点与场景

5. 负载均衡

配置方式：@DubboReference(loadbalance = "leastactive")、@DubboService(loadbalance = "...")，或全局 dubbo.consumer.loadbalance=random（默认）。优先级：方法级 > 服务级 > Consumer 全局 > Provider 端。

策略 原理 什么时候用
Random（默认） 加权随机：权重越大被选中概率越高，按权重分配随机数区间 通用默认场景：集群节点性能相近、没有特殊诉求时直接用
RoundRobin 平滑加权轮询（借鉴 Nginx，3.x 重写实现，避免权重不均时请求扎堆） 请求量稳定、希望流量严格均匀分布：如无状态计算服务，按权重精确分配
LeastActive 最少活跃调用数优先，活跃数相同再按权重随机 机器性能参差不齐：性能好的机器处理快、活跃数低，自动获得更多流量，天然按能力分流
ConsistentHash 一致性哈希（默认 160 个虚拟节点），相同参数请求总是落在同一台机器 有状态服务：本地缓存热点场景（如用户数据缓存），相同入参命中同一节点提高缓存命中率
ShortestResponse 按最近滑动窗口的平均响应时间选节点（叠加权重），响应时间接近时按权重随机 请求耗时差异大、对延迟敏感：自动把流量倾斜到”当前最快”的节点，动态适应机器负载波动

面试补充：ConsistentHash 的虚拟节点是为了解决节点数少时数据倾斜；LeastActive 和 ShortestResponse 都是”自适应”策略，但前者依据并发度（活跃数），后者依据延迟。

6. 集群容错

配置方式：@DubboReference(cluster = "failover") 或 dubbo.consumer.cluster=failover（默认）。作用在 Consumer 侧，控制”一个调用在多台 Provider 之间如何处理”。

策略 行为 典型参数 什么时候用
Failover（默认） 调用失败后自动切换其他 Provider 重试 retries=2（默认，加首次共 3 次） 幂等操作（查询、幂等写）；非幂等写必须 retries=0，否则可能重复执行
Failfast 只发起一次调用，失败立即抛异常 无需配置 非幂等写操作（新增、扣款），宁可直接报错也不重复执行
Failsafe 失败直接吞掉异常，返回空结果，只记日志 无需配置 可容忍丢失的辅助操作：日志上报、审计埋点、通知统计
Failback 失败先返回空结果，失败请求进入内存队列，后台每 5 秒重试，直到成功（进程内记录，不持久化） 无需配置 最终一致性的异步通知类：如订单状态变更通知，允许延迟送达
Forking 并行调用多个 Provider，任一成功即返回 forks=2（默认并行 2 个） 对实时性要求极高且消费方资源充足：如首页聚合、秒杀查价；代价是放大请求量，有状态操作禁用
Broadcast 逐个（可配置并行）调用所有 Provider，全部成功才算成功 broadcast.fail.percent=100（3.x，允许容忍失败百分比） 需要通知所有机器同步状态：如通知所有 Provider 更新本地缓存、清理本地资源

面试补充：

  • Failover 与幂等：retries 影响的是超时/异常后的重试次数，重试会放大对 Provider 的压力，也要与超时配合设置（总耗时 ≈ 单次超时 × 重试次数）。
  • Forking 与并发：forks 超过 Provider 数时退化为全量并行。
  • 容错策略可以和方法级配置叠加：写方法 retries=0，读方法保持默认重试。

7. 服务治理

7.1 动态路由

Dubbo 3 支持条件路由、标签路由、脚本路由（不推荐）。规则通过注册中心/配置中心下发，热生效，无需重启。

  • 条件路由：=> 前匹配 Consumer，后匹配 Provider。 常用于：机房隔离、A/B 测试、故障节点摘除。
  • 标签路由（tag）：给 Provider 打标签，Consumer 按标签选组。
    • Provider 侧：dubbo.provider.tag=gray
    • Consumer 侧：dubbo.consumer.tag=gray
    • Consumer 未打 tag 时默认不匹配带 tag 的 Provider（或配置 force=false 时 fallback 到无标签节点）。

7.2 权重调整

dubbo.provider.weight=100（默认 100），调整权重影响所有加权负载均衡策略的选点概率。配合注册中心下发（configurator 规则）可动态调整，无需重启——常用于上线初期的”先小流量、后放量”。

7.3 灰度发布

  1. 新版本 Provider 打标 dubbo.provider.tag=gray 并上线（只注册、可被灰度流量命中）。
  2. 灰度 Consumer 组配置 dubbo.consumer.tag=gray，流量被标签路由导到新版本；未打标的正常流量仍走老版本。
  3. 验证通过后，逐步调低老版本权重、调高新版本权重（或逐步扩大 tag 范围）。
  4. 全量后移除 tag 配置，下线老版本。

7.4 降级

@DubboReference(mock = "...") 或 dubbo.consumer.mock，分两种前缀：

写法 语义 场景
force:return+null 强制降级：不发起任何远程调用，直接返回 大促时主动屏蔽非核心服务（如积分、营销）
fail:return+null 容错降级：调用失败后返回 null（或 mock 类逻辑），而非抛异常 核心链路依赖的旁路服务故障时，不影响主流程

也支持 mock 实现类（如 MockDemoService implements DemoService，在 RpcException 时执行兜底逻辑返回本地数据）。

7.5 限流

  • TPS 限流（内置 TpsLimitFilter，Provider 侧）：Provider URL 携带 tps.limit.rate 即自动激活；令牌桶算法，超过速率直接抛 RpcException 拒绝。
  • 复杂限流（推荐 Sentinel 接入）：按调用方限流、动态阈值、熔断等场景，使用 Sentinel 的 Dubbo Adapter，在 Provider 侧配置 QPS 阈值。
  • 自适应限流（3.x）：dubbo.provider.flowcontrol=autoConcurrencyLimiter（或 heuristicSmoothingFlowControl），基于 CPU 使用率、并发度自动调整阈值，无需人工设置。

7.6 优雅停机

通过 JVM ShutdownHook 实现（kill PID 触发，kill -9 不触发）：

  • Provider：先标记不接收新请求（新请求直接失败，让 Consumer 重试其他节点）→ 等待线程池中存量请求执行完成 → 再释放连接、注销注册。
  • Consumer：不再发起新调用 → 等待未返回的响应 → 关闭。
  • 超时兜底：dubbo.service.shutdown.wait=30000（默认 10000ms，超过则强制关闭）。

8. Dubbo SPI

8.1 Java SPI 回顾

SPI 是 Java 提供的一种服务发现机制，通过接口与实现解耦实现动态扩展。核心流程如下：

  1. 定义服务接口（如 PaymentService）
  2. 提供实现类（如 AlipayService, WechatPayService）
  3. 注册实现：在 META-INF/services/ 下创建以接口全限定名命名的文件，写入实现类全限定名
  4. 动态加载：通过 ServiceLoader 加载所有注册的实现

优势：

  • 开闭原则：新增实现无需修改核心代码
  • 解耦：接口与实现分离
  • 可插拔：通过配置文件动态替换实现

实际应用场景：

  • JDBC 驱动加载（DriverManager）
  • 日志门面（SLF4J）
  • 序列化框架（Jackson）
  • Spring Boot 自动配置

通过 SPI 机制，Java 实现了真正的面向接口编程，使系统具备高度可扩展性，符合「开闭原则」。

8.2 Java SPI 的 6 个问题

  1. 效率低下（全量加载）：
    • ServiceLoader 在加载一个接口的实现时，会遍历并实例化 META-INF/services/ 目录下对应配置文件中的所有实现类。
    • 问题： 如果某个扩展点有很多实现（或者某些实现类初始化成本很高），但实际运行时只需要用到其中一个或几个，这种全量加载会造成不必要的资源消耗（内存、CPU）和启动延迟。
  2. 缺乏按需获取能力（不灵活）：
    • Java SPI 只能获取所有实现，然后由调用者遍历查找需要的那个。没有内置的机制根据名称、参数或其他条件直接获取特定的实现实例。
    • 问题： 使用起来不够方便和直观，需要额外的筛选逻辑。
  3. 不支持依赖注入：
    • 通过 SPI 加载的实现类实例，其构造函数或成员变量如果依赖其他对象，需要调用者手动设置。
    • 问题： 在复杂的框架中，扩展点实现类可能需要依赖框架内部的核心组件（如配置中心、注册中心、序列化器等），手动管理这些依赖非常繁琐且容易出错，破坏了扩展点的封装性。
  4. 不支持扩展点自适应/IoC/AOP：
    • Java SPI 是静态的，加载哪个实现在配置文件中是写死的。它无法根据运行时的参数（如方法参数、URL 参数、配置项）动态选择不同的实现。
    • 问题： 缺乏动态性，难以实现更高级的功能如适配器、包装器（AOP）、条件选择等。
  5. 配置不友好（无名称标识）：
    • 配置文件里直接写实现类的全限定名。没有为每个实现定义一个易于理解和使用的名称（Key）。
    • 问题： 配置和引用不够直观，容易出错，不利于通过配置中心动态修改。
  6. 缺乏生命周期管理：
    • Java SPI 没有提供标准的初始化和销毁回调机制。

8.3 Dubbo SPI 八大特性

Dubbo 设计了一套功能更强大、更灵活的 SPI 机制（核心在 org.apache.dubbo.common.extension 包），完美解决了上述问题：

  1. 按需加载（核心改进）：
    • Dubbo SPI 不会一次性加载和实例化所有实现类。
    • 它维护了一个映射关系：扩展点名称 (Key) -> 实现类全限定名。
    • 只有当通过名称 (key) 明确请求某个扩展点时，才会加载并实例化对应的实现类。大大提高了效率和资源利用率，加快了启动速度。
  2. 支持扩展点命名与配置化：
    • 配置文件路径：META-INF/dubbo/ 或 META-INF/dubbo/internal/ 或 META-INF/services/（兼容 Java SPI），文件名为接口全限定名。
    • 文件内容格式：key=implementation.class.name (例如：dubbo=org.apache.dubbo.rpc.protocol.dubbo.DubboProtocol)。这为每个实现赋予了明确的标识符 (key)。
  3. **强大的依赖注入 (IoC)**：
    • Dubbo SPI 在实例化扩展点实现时，会自动扫描其 setter 方法。
    • 如果 setter 方法的参数类型是另一个已知的扩展点类型，Dubbo 会自动注入该扩展点的适配实例（通常是自适应扩展点实例，见下一点）。
    • 也支持注入框架内部的核心组件（如 ApplicationModel, ModuleModel, ScopeModel 等）。
    • 优势： 解耦扩展点实现与框架内部依赖，开发者只需关注业务逻辑，依赖由框架自动注入。
  4. **自适应扩展点 (Adaptive Extension - 核心特性)**：
    • 概念： 一种特殊的扩展点，它本身通常不包含具体逻辑，而是一个动态生成的代理（编译时生成或运行时生成）。
    • 作用： 在方法被调用时，根据传入的运行时参数（通常是包含配置信息的 URL 对象或 @Adaptive 注解指定的参数），动态决定将调用委托给哪个真正的扩展点实现 (key 对应的实现)。
    • 实现方式：
      • 编译时生成： Dubbo 编译器会为标记了 @Adaptive 注解的接口方法生成代理类代码（如 Protocol$Adaptive）。
      • 运行时生成： 如果接口没有任何方法标记 @Adaptive，Dubbo 会查找该接口的默认实现（通过 @SPI 的 value 指定）。如果需要在运行时根据方法参数选择，也可以在具体实现类的方法上使用 @Adaptive（较少见）。
    • 优势： 实现了真正的运行时动态扩展选择。例如，Protocol 接口的自适应扩展点，根据 URL 中的 protocol 参数值 (dubbo, hessian, http, injvm 等）决定使用哪个具体的协议实现。这是 Dubbo 高度可扩展性的基石。
  5. **自动包装 (Wrapper - AOP)**：
    • 如果扩展点实现类的构造函数接受单个参数且是该扩展点接口类型，Dubbo 会识别它为 Wrapper 类。
    • 在加载真正的扩展点实现（称为 instance）时，Dubbo 会像”洋葱”一样，用所有找到的 Wrapper 类层层包裹这个 instance：new Wrapper1(new Wrapper2(new Wrapper3(instance)))。
    • 作用： 在不修改原始实现类代码的前提下，实现 AOP 功能。Wrapper 可以在调用真正实现的前后添加逻辑，如日志记录、监控统计、权限校验、失败重试、负载均衡（部分策略）等。Dubbo 自身的很多功能（如 Filter Chain）都是通过 Wrapper 机制实现的。
  6. **自动激活扩展点 (Activate)**：
    • 通过 @Activate 注解标记扩展点实现。
    • 可以根据给定的条件（如 URL 中的特定参数值、消费者/提供者端角色）自动激活并组合一组符合条件的扩展点实现。
    • 典型应用： Dubbo 的 Filter 链。开发者可以方便地添加自定义 Filter，并通过 @Activate 注解控制它在哪些条件下自动生效（如所有调用、特定分组、特定服务等）。
  7. 支持默认扩展点和覆盖：
    • 在 @SPI 注解中可以指定默认扩展点的 key (如 @SPI("dubbo"))。
    • Dubbo 支持通过配置（系统属性、外部配置）覆盖默认实现或已加载的实现。
  8. 缓存优化：
    • Dubbo 对加载的扩展点定义、实例（单例或原型）、自适应扩展点实例等进行了细致的缓存管理，避免重复加载和创建，提升性能。

11. 常见面试题速答

Q1：Dubbo 和 Spring Cloud 怎么选？
Dubbo 是高性能 RPC + 服务治理框架，二进制协议性能好、负载均衡/容错/限流内建；Spring Cloud 是 REST 为主的微服务全家桶，生态广但性能弱于二进制 RPC。Java 内部高并发链路用 Dubbo，跨语言/云原生用 gRPC，业务生态整合用 Spring Cloud，实际常混用（详细对比见第 10 章）。

Q2：注册中心挂了，服务还能调用吗？
能。Consumer 本地缓存了已拉取的 Provider 地址列表，已发现的服务可继续调用；只是无法感知地址变更（新节点、下线节点），且新启动的实例无法完成初始订阅。注册中心不处于调用链路上，是它高可用的设计关键。

Q3：Failover 重试会有什么风险？
重试会重复执行请求。非幂等操作（新增、扣款）必须 retries=0；幂等读可以放心重试。同时重试放大 Provider 压力，总耗时 ≈ 单次超时 × 重试次数。

Q4：Dubbo 协议为什么是单一长连接？
减少连接建立/维护开销，靠 requestId 复用一条连接多路复用请求；但大消息会阻塞同连接其他请求，官方建议消息体 1M 内，大包走 Triple 的流式能力。

Q5：为什么 Dubbo3 主推 Triple？
跨语言（gRPC 兼容）、云原生友好（HTTP/2 可被网关/Envoy/K8s 统一治理）、多路复用解决连接爆炸、原生流式通信。

Q6：负载均衡怎么选？
节点性能均衡用 Random/RoundRobin；性能参差用 LeastActive；本地缓存有状态用 ConsistentHash；延迟敏感用 ShortestResponse。

Q7：如何实现一个自定义 Filter（如统计耗时）？
实现 org.apache.dubbo.rpc.Filter，@Activate(group = "provider") 标记生效侧，在 META-INF/dubbo/org.apache.dubbo.rpc.Filter 里注册 key=实现类全限定名，SPI 自动加载进 Filter 链，无需改框架代码。

Q8：超时配置在谁那边设置？优先级？
dubbo.consumer.timeout（Consumer 侧）/ dubbo.provider.timeout（Provider 侧，作为 Consumer 缺省）。优先级：方法级 > 服务级 > Consumer > Provider > 全局默认（1000ms）。注意 Consumer 超时要大于 Provider 端实际处理时间，否则 Provider 还在执行、Consumer 已超时。

Q9：如何做灰度发布？
tag 路由：新版本 Provider 打 dubbo.provider.tag=gray，灰度 Consumer 配 dubbo.consumer.tag=gray，验证通过后逐步调权重放量，最后摘除 tag 全量。

Q10：Dubbo 接口级和服务级服务发现有什么区别？
接口级每个接口×实例都注册 URL，数据量大；应用级只注册实例、元数据放元数据中心，数据量 = 接口数 + 实例数，支撑更大规模，是 Dubbo3 的核心升级点。

Q11：什么是 Dubbo SPI 的 Adaptive 扩展点？
动态生成的代理：调用时根据运行时参数（URL 中的 key）选择真实实现。比如 Protocol 的自适应代理根据 URL 中 protocol=dubbo 委托给 DubboProtocol。它是”配置即代码、运行时多态”的关键。

Q12：zk 临时节点 + Watcher 如何支撑服务发现？
Provider 注册临时节点（会话断开自动删除，天然感知宕机）；Consumer 订阅节点并注册 Watcher，节点增删改触发回调重新拉取 + 重新注册 Watcher；Watcher 一次性是”重新注册”的原因，也是服务多时通知风暴的来源。

1. Elasticsearch 是什么

1.1 定位：Lucene 之上的分布式搜索引擎

Elasticsearch（下文简称 ES）是 2010 年由 Shay Banon 开源的分布式、近实时（NRT）的全文搜索引擎，基于 Java 实现。它的底层是 Apache Lucene——Doug Cutting 开发的高性能全文检索库。Lucene 本身只是一个嵌入式的 JAR 包，只解决”单机上的索引与搜索”问题；ES 在 Lucene 之上封装了分布式能力（分片、副本、集群）和 RESTful API，让全文搜索变成可以直接部署、调用的服务。

一句话：Lucene 是引擎，ES 是装了引擎的分布式整车。

1.2 全文搜索 vs 数据库搜索

面试常问”为什么不用 MySQL 的 LIKE 做搜索”，核心差异如下：

维度 MySQL（LIKE） Elasticsearch
查询方式 %关键词% 无法利用 B+ 树索引，退化为全表扫描 倒排索引直接定位词项，不扫描全表
相关性排序 不支持打分，只能按自定义字段排序 BM25 相关性打分，可控制权重
数据量级 千万级开始吃力 亿级以上，分片横向扩展
模糊能力 通配符（前导通配符同样全表扫描） 分词 + 短语/模糊/同义词，天然适合中文分词
写入一致性 强一致，写入即查得到 近实时，默认 1 秒后才可搜到（见第 3 节）

注意一个前提：ES 是搜索和聚合引擎，不是数据源。它没有跨文档事务、没有强一致保证，业务数据的主存仍然是 MySQL，ES 只是副本/索引（见第 9 节数据同步）。

1.3 适用场景

  • 站内搜索：电商商品、文档、知识库的全文检索，是 ES 的第一场景。
  • 日志与指标分析：ELK 技术栈（Elasticsearch + Logstash + Kibana），日志检索、监控大盘。
  • 聚合分析：基于海量数据的统计报表（点击、订单、访问量）。
  • 地理检索：geo_point 附近的人、门店搜索。
  • 向量检索：8.x 起支持 dense_vector 字段和 kNN 搜索，可做语义搜索、RAG 召回。
  • 不适合：强事务/多文档原子操作（无 ACID）、复杂多表关联查询（ES 的 join 能力很弱且不推荐）、低频小数据量的简单查询（杀鸡用牛刀）。

2. 核心概念

  • 文档（Document）： 数据的基本单位，通常是 JSON 格式，对应数据库中的一行记录。
  • 索引（Index）： 具有相似特征的文档集合，对应数据库中的一张表。一个索引由一个或多个分片组成。
  • 类型（Type）： 索引内部的逻辑分区，曾允许在同一索引中存储不同类型的文档（如 user、product）。版本演变：6.x 起被标记废弃（deprecated，一个索引只允许一个 type）；7.x 中正式废弃，API 默认使用 _doc 类型；8.x 中类型概念被完全移除，现在一个索引只包含一种文档类型。
  • 映射（Mapping）： 定义索引中每个字段的类型、分词器、是否索引等元数据，相当于数据库的表结构（DDL），详见第 7 节。
  • 分片（Shard）： 索引被水平分割成的子集，每个分片本身就是一个功能完整且独立的”索引”（一个 Lucene 索引）。
    • 主分片（Primary Shard）： 存储文档数据并处理索引/更新操作。索引创建时指定数量，后续不可更改（除非 Reindex）。
    • 副本分片（Replica Shard）： 主分片的拷贝，提供高可用性（主分片故障时副本可提升为主）和读取吞吐量（查询可负载均衡到所有副本）。
  • 节点（Node）： 运行中的 Elasticsearch 实例。
  • 集群（Cluster）： 一个或多个节点协同工作的集合，共同持有整个数据并提供联合索引和搜索能力。
  • 倒排索引（Inverted Index）： ES 实现快速全文搜索的核心数据结构，存储了词项（Token）到包含该词项的文档 ID 列表的映射。相比传统数据库的正排索引（文档 ID 到字段值），倒排索引天然适配”哪些文档包含某个词？”这一类查询。

2.1 倒排索引详解

  • 定义： 倒排索引是一种将文档中的词项（Token）映射到包含该词项的文档列表的数据结构，由两个核心部分组成：
    • 词项字典（Term Dictionary）： 包含所有不重复的词项，通常按字典序排序，并配合 FST（有限状态转换器） 压缩存储、常驻内存，实现 O(1) 级别的词项查找。
    • 倒排列表（Postings List）： 对于每个词项，记录包含该词项的所有文档 ID 列表，以及词项在文档中出现的位置（Position）、词频（Term Frequency）等信息，用于相关性评分和短语查询。
  • 重要性：
    • 快速定位： 直接通过词项找到包含它的文档，避免扫描全部文档。
    • 高效布尔查询： AND/OR/NOT 操作可以通过对倒排列表进行交、并、差集运算高效完成。
    • 相关性评分基础： TF-IDF、BM25 等经典评分模型严重依赖倒排索引中存储的词频（TF）、文档频率（DF/IDF）信息。
    • 支持短语查询： 利用存储的位置信息，可以精确查找相邻出现的词组（match_phrase）。

3. 写入与刷新

3.1 完整写入链路

  1. 路由： 请求到达任意节点（该节点即协调节点），根据 routing = hash(文档ID) % 主分片数 定位到主分片。
  2. 写内存 + Translog： 主分片将文档写入内存缓冲区（Indexing Buffer），同时立即追加写入事务日志（Translog）。Translog 是持久化的。
  3. Refresh： 定期（默认 1 秒）将内存缓冲区中的内容生成一个新的、可搜索的 Lucene 段（Segment），并清空缓冲区。这个过程使新写入的数据对搜索可见。 注意：此时数据还在操作系统的文件系统缓存（Page Cache）中，并未物理刷盘（fsync）。
  4. 段合并： 小段在后台按 Tiered Merge Policy 合并成大段，控制段数量（见 8.2）。
  5. Flush： 定期（默认 30 分钟，或 Translog 大小达到阈值）将段数据 fsync 落盘并截断 Translog。

这就是 ES”近实时”的原因：数据可搜索需要等一次 Refresh（1 秒级），而 Translog 只保证数据不丢，不保证立刻可见。如果需要写入后立刻可搜，可在写请求带 ?refresh=true（或 refresh=wait_for），代价是性能下降。

3.2 写入可靠性

  • 事务日志（Translog）： 所有写入操作在写入内存缓冲区的同时，会立即追加写入到事务日志中。Translog 的刷盘时机由 index.translog.durability 控制：默认 request（每个写请求都 fsync，性能换可靠性），可改为 async（默认每 5 秒批量刷盘，性能更好但断电最多丢几秒数据）。
  • 副本确认： 写入操作在主分片执行成功后，必须等待所有配置的副本分片也写入成功才返回客户端确认（除非使用 wait_for_active_shards 降低要求），确保数据冗余。
  • 故障恢复： 节点重启时，会重放 Translog 中尚未刷盘的操作来恢复数据；副本分片的存在保证了主分片丢失时数据不丢（副本提升为主分片）。
  • 兜底： 跨机房的灾难恢复靠定期快照（_snapshot API，备份到 HDFS/S3 等）。ES 不是数据库，关键数据的主存必须在 MySQL，极端情况可从源库重建索引（见第 9 节）。

3.3 refresh vs flush 区别

维度 refresh flush
目的 使新写入的数据对搜索可见 将数据安全持久化到磁盘，并清理 Translog
操作 Buffer 中的文档生成新 Segment，写入文件系统缓存（Page Cache），不立即 fsync ① 先执行一次 Refresh；② fsync 将段数据强制写入磁盘；③ 清空（截断）当前 Translog
频率 默认每秒一次（index.refresh_interval，设为 -1 可关闭） 每 30 分钟（index.translog.flush_threshold_period）、Translog 超 512MB（index.translog.flush_threshold_size）、或显式调用 _flush API
开销 较低，只写入 Page Cache；但频繁 Refresh 会产生大量小段，增加合并压力 较高，涉及磁盘 I/O（fsync）

4. 查询原理

4.1 一次搜索的流程

  1. 协调节点接收请求，解析 DSL，按 routing 找到目标分片，将查询广播到所有主/副本分片（默认 query_then_fetch 模式）。
  2. 各分片在自己的 Lucene 索引上本地执行查询并打分，返回 Top N 的文档 ID 和分数（默认每个分片取 from + size 条）。
  3. 协调节点合并排序所有分片的结果，取全局 Top N，进入 Fetch 阶段。
  4. 协调节点向各分片取回完整的 _source，组装后返回。

加分项：query_then_fetch 是”本地 IDF 打分”，每个分片只能基于自己的词频统计，结果与全局 IDF 有轻微偏差；dfs_query_then_fetch 会先收集全局词频再打分，更精确但多一轮通信，生产环境很少使用。

4.2 Query 上下文 vs Filter 上下文

bool 查询中的 filter 子句、constant_score、term/range 直接放在 query 里都是 Query 上下文；放在 bool.filter / bool.must_not / constant_score.filter 里则是 Filter 上下文。

维度 Query 上下文 Filter 上下文
相关性 参与 _score 计算，影响排序 不参与算分（_score 恒为 0）
缓存 不缓存 结果可缓存（节点级 Query Cache 中的位图 Bitset），同条件复用
性能 有算分开销，相对慢 更快，适合高频过滤条件
场景 全文检索、相关性排序 状态、范围、布尔标记等刚性过滤条件

最佳实践：需要算分的放 Query（如 match），不需要算分的过滤条件尽量放 Filter（如 status、price 范围、is_deleted），既省算分开销又能命中缓存。

4.3 相关性评分：TF-IDF vs BM25

  • TF-IDF：词频 × 逆文档频率 × 长度归一化。问题是词频是线性增长的，高频词（”的””手机”）在长文档中会过度主导得分。
  • BM25：在 TF-IDF 基础上引入 TF 饱和函数和 IDF 平滑，并增加可调参数 k1（默认 1.2，词频饱和速度）和 b（默认 0.75，文档长度归一化程度）。
维度 TF-IDF BM25
TF 处理 线性增长，高频词得分过高 饱和函数，达到阈值后增长放缓
IDF 处理 经典公式，罕见词得分可能过高 平滑处理
可调参数 无 k1、b，可按字段配置权重
默认状态 ES 5.0 之前默认（Lucene 4/5） ES 5.0 起默认（Lucene 6+）

4.5 深分页

from + size 是普通分页，但 max_result_window 默认上限 10000（超出报错）。深分页的问题在于协调节点要把每个分片的 from + size 条结果都收上来排序，from 越大，内存和耗时越大。

方案 适用场景 特点
from + size 前 10000 条内的浅分页 实现最简单，深翻页内存爆炸

5.2 聚合与查询的区别

  • 查询（Query）：选出符合条件的文档，返回文档本身；聚合（Aggregation）：对结果集做分组和统计，返回统计结果。类比 SQL：查询是 WHERE，聚合是 GROUP BY + 聚合函数。
  • 聚合默认作用于查询筛选后的结果集（无 query 则默认 match_all 全部文档）；聚合可以嵌套（桶内再分桶、桶内再算指标），Pipeline 聚合还能跨桶计算。
  • 聚合结果中的桶是 Top-N 近似值（先在各分片取 top，再合并），与精确分组有偏差。

5.3 聚合优化

  • text 字段不能直接聚合：聚合依赖 doc_values，text 默认没有（详见 8.3）。给字段配 keyword 子字段后用 field.keyword 聚合。
  • terms 聚合的 size 默认 10，要更多桶需显式设置；分片返回桶数由 shard_size 控制（默认约 size * 1.5 + 10），桶数很大时适当调大 shard_size 保证准确性。
  • cardinality 是近似去重：precision_threshold 默认 3000，值不超过阈值时精确，超过后基于 HyperLogLog 近似，可适当调大换取精确性。
  • 大桶数分页用 composite 聚合：terms 聚合超过 size 的桶拿不到，composite 支持 after 游标分页取全部桶。
  • 不需要聚合/排序的字段可以关闭 doc_values 省磁盘（默认开启）。
  • 聚合结果可用 Shard Request Cache 缓存（?request_cache=true，仅缓存 size: 0 的请求），适合报表类固定查询。

6. 分片与集群

6.1 分片策略

  • 主分片数量：7.x 默认 1（6.x 及更早默认 5）。合理规则：单个分片数据量控制在 10~50GB，总分片数按数据总量估算（如 300GB 数据 ≈ 10 个主分片）。
    • 分片过少：单分片查询/恢复慢，无法利用多节点并行。
    • 分片过多：每个分片都是独立的 Lucene 索引，元数据和文件句柄开销大，GC 压力大。
  • 主分片数创建后不可变：路由公式 hash(id) % 分片数 决定了它无法动态增减。要改只能 Reindex（POST /_reindex 把数据搬到新索引），或者用索引别名平滑切换。
  • 副本数量可以动态调整：PUT /index/_settings 修改 number_of_replicas，随时增减。
  • 副本上限：副本数最多为 节点数 - 1（同一份数据不能在同一个节点上有主副本两份），单节点集群配 1 个副本必然 Yellow。

6.2 副本的作用

  • 高可用：主分片故障时，副本可被提升为主分片，数据不丢、服务不中断。
  • 读扩展：查询可以负载均衡到所有主/副本分片执行，副本越多，读取吞吐越高。
  • 不承担写：索引/更新/删除请求只发主分片（副本写入由主分片转发），副本对写没有扩展作用——写瓶颈只能靠增加主分片数解决。

6.3 集群状态 Yellow 或 Red 意味着什么？如何排查？

  • Yellow：
    • 含义： 所有主分片都已分配，但至少有一个副本分片没有分配。
    • 常见原因：
      • 节点数量不足（例如，索引配置了 number_of_replicas=1，但集群只有一个节点）。
      • 新创建的索引副本分片正在初始化（短暂状态）。
      • 有节点故障，导致部分副本分片丢失（但主分片还在）。
    • 影响： 高可用性降低（丢失一个节点可能导致数据不可用），查询吞吐量可能下降（副本少）。
    • 排查： 使用 GET _cluster/allocation/explain API 查看未分配分片的具体原因；检查节点数、节点状态、磁盘空间、分片分配设置。
  • Red：
    • 含义： 至少有一个主分片没有分配（可能连带其副本也缺失）。
    • 常见原因：
      • 持有主分片的节点永久丢失，且没有可用的副本分片可以提升为主分片。
      • 磁盘空间不足导致分片无法分配。
      • 配置错误（如分片分配规则 exclude 了所有节点）。
    • 影响： 数据部分丢失或完全不可用！ 涉及该主分片的索引和搜索操作都会失败。
    • 排查： 紧急处理！立即检查 _cluster/health 和 _cat/shards?v 确认哪些索引/分片是 red。使用 GET _cluster/allocation/explain 分析未分配原因。检查节点状态、磁盘空间、日志。必要时从备份恢复或手动分配分片（风险操作）。
  • 目标： 始终追求 Green 状态。

6.4 脑裂问题

  • 定义： 在分布式系统中，当网络分区（Network Partition）发生时，集群的不同部分（节点组）可能无法互相通信。如果每个部分都认为自己是唯一可用的部分并选举出新的主节点，就会导致集群分裂成两个或多个独立运作的”脑”，各自接受写入操作，造成数据不一致和冲突。
  • ES 防止机制： 核心思想是多数派（Quorum）原则——只有包含超过半数（> N/2）主节点资格节点的节点组才能选举或维持主节点。假设有 N 个主节点资格节点：
    • 6.x 及以前（Zen Discovery）： 显式配置 discovery.zen.minimum_master_nodes = N/2 + 1（例如，3 节点集群设为 2）。
    • 7.x 起： 基于 Raft 协议的投票选举机制，discovery.zen.minimum_master_nodes 已被废弃，集群自动要求多数投票；集群首次启动时用 cluster.initial_master_nodes 列出候选主节点。
    • 8.x： 彻底移除 Zen Discovery 相关配置。
  • 效果： 网络分区时，任何节点组如果包含的主节点资格节点数不足多数（<= N/2），就无法选举新主节点或维持现有主节点状态（无法获得多数确认），从而无法提供服务或接受写操作，避免了”双主”导致的脑裂。只有拥有多数节点的分区才能正常运作。
  • 实践建议： 主节点资格节点配奇数个（生产通常 3 个专用 master 节点），并做好角色分离（7.x 起节点可配置 node.roles，把 master/data/ingest 角色分开），避免大节点既做 master 又扛数据。

7. 索引优化

7.1 显式映射与动态映射

ES 支持动态映射：写入文档时自动推断字段类型（字符串推断为 text + keyword 子字段、数字推断为 long、日期按格式推断）。生产环境应优先使用显式映射，动态映射只保留给开发期：

dynamic 三种模式的取舍：

值 行为 适用
true（默认） 自动创建字段映射 开发期、字段完全可控
false 忽略未知字段（不索引、搜索不到） 字段不可控但不想写失败
strict 未知字段直接报错拒绝写入 生产环境、强 schema

7.2 映射爆炸

  • 定义： 当索引中包含大量唯一字段（通常是动态映射产生的）时，导致集群状态（Cluster State）变得极其庞大（可能超过数百 MB 甚至 GB），主节点在广播和维持集群状态时压力巨大，严重影响集群稳定性和性能。
  • 原因： 常见于索引日志类数据，其中每个文档都有大量不同的、不可预测的字段（如包含用户 ID 或请求 ID 的字段名）。
  • 避免：
    • 严格控制动态映射： 设置 "dynamic": "strict"（禁止未知字段）或 "dynamic": "false"（忽略未知字段，但不索引）。优先使用显式映射。
    • 限制字段总数： index.mapping.total_fields.limit 默认 1000，超限直接拒绝写入，可据此报警。
    • 使用 flattened 类型（7.2+）： 将整个 JSON 对象映射为单个 flattened 字段，避免为每个内部键创建独立字段。适用于不需要独立查询/聚合的元数据。
    • 使用 object/nested 但限制深度： 使用 index.mapping.depth.limit 控制嵌套深度（默认 20）。
    • 字段别名： 如果不同来源的字段语义相同，用别名统一映射到一个字段。
    • 合理的索引设计： 避免将差异巨大的文档类型塞进同一个索引（日志按天滚动索引也是这个道理）。

7.3 keyword vs text

  • 使用 keyword 类型当：
    • 需要精确匹配（如状态码、标签、ID、枚举值）。
    • 需要聚合（如 Terms、Significant Terms 聚合）。
    • 需要排序。
    • 不需要全文分词搜索。
  • 使用 text 类型当：
    • 字段内容是需要被全文搜索的自然语言文本（如邮件正文、产品描述）。
    • 需要被分词器处理（分词、归一化）。

索引方式 分词器拆成多个词项后索引 整体作为一个词项索引
匹配方式 match 全文检索 term 精确匹配
聚合/排序 默认不支持（需 fielddata，见 8.3） 支持（基于 doc_values）
场景 自然语言内容 ID、枚举、状态码、标签
其他 — 单个词项最长 32766 字节，可用 ignore_above 丢弃超长值

7.4 force merge、routing、index sorting

  • force merge（强制合并段）： POST /index/_forcemerge?max_num_segments=1。适合只读索引（历史归档）、删除大量文档后（真正释放磁盘空间）、以及批量导入完成后。合并是 I/O 密集型操作，不要在在线高峰对热索引执行。
  • 自定义 routing： 默认按 _id 哈希路由到分片；可通过 ?routing=user_88 指定路由键（如按用户/租户），让同一业务实体的文档落在同一分片，查询时指定 routing 只扫一个分片。代价是可能数据倾斜、routing 变化时需要 Reindex，适合租户隔离类场景。
  • index sorting（索引预排序，7.x+）： 创建索引时指定 index.sort.field（如 timestamp），写入时即按该字段排序，能显著加速时间范围查询和大范围排序（排序字段自动进入 doc_values），代价是写入性能略有下降。

8. 性能优化

8.1 Bulk API

单个请求写入性能远低于批量写入，因为每条请求都有一次网络往返和一次完整处理。Bulk API 是写入优化的第一手段：

  • 批次大小： 经验值每批 5~15MB 或 1000~5000 条（按单条大小调整），需要压测确定最优值。批次过大：占用协调节点/分片内存，单条失败整批重试代价高；批次过小：网络往返占比高，吞吐上不去。
  • 关注响应：检查响应中的 errors 字段，对失败项重试；客户端用多线程并发打满吞吐，重试用指数退避避免雪崩。
  • 配合优化：批量导入场景可临时 index.refresh_interval: -1（导入完恢复并 force merge），减少频繁 refresh 产生的小段。

8.2 段合并

  • 为什么需要： 频繁的 refresh 会产生大量小的 Lucene 段。小段过多会降低查询性能（需要打开更多文件句柄）且占用更多资源（文件描述符、内存）。删除操作只是标记文档为删除，空间不会立即释放。
  • 优点：
    • 减少段数量，提升查询速度（减少文件打开和搜索范围）。
    • 真正删除被标记删除的文档，回收磁盘空间。
    • 合并过程中优化索引结构（如压缩）。
  • 缺点：
    • 是 I/O 和 CPU 密集型操作，在合并期间可能显著影响集群性能（写入延迟、查询延迟增加）。
    • 需要额外的临时磁盘空间。
  • 调优： 默认 Tiered Merge Policy 会自动按层级合并；index.merge.scheduler.max_thread_count 默认 min(4, CPU核数/2)，机械盘环境建议调为 1；大写入任务前可临时关闭 refresh（见 8.1），完成后 _forcemerge 收尾。

8.3 doc_values vs fielddata

聚合、排序需要读取整列数据，ES 提供两种机制：

维度 doc_values fielddata
存储 列式存储，在磁盘（常驻 OS Page Cache） 内存（JVM 堆），懒加载
默认 keyword/数值/日期默认开启 默认关闭（2.0 起）
用途 聚合、排序、脚本访问 仅用于让 text 字段也能聚合（不推荐）
风险 占磁盘，可对不需要聚合的字段关闭 堆内存 OOM 的重灾区（1.x 时代默认开启，曾引发大量线上事故）

结论：聚合排序一律依赖 doc_values（配合 keyword），不要让 text 开 fielddata。确实需要对 text 做统计时，用 keyword 子字段代替。

8.4 堆内存配置

  • -Xms 与 -Xmx 设为相同值，避免运行时动态扩容触发 Full GC。
  • **不超过物理内存的 50%**（ES_JAVA_OPTS 或 jvm.options 配置），其余内存留给 OS Page Cache——段文件和 doc_values 都靠页缓存加速，这是 ES 的命根子。
  • 不要超过 32GB：超过后 HotSpot 的压缩指针（Compressed Oops）失效，指针占用翻倍，堆内存反而”缩水”。
  • 关闭 swap：bootstrap.memory_lock: true（锁内存防止被换出）。
  • 7.x 起默认使用 G1GC；indices.fielddata.cache.size 建议设置上限（默认无上限），熔断器 indices.breaker.fielddata.limit 默认保护堆的 40%。

8.6 其他常用调优

  • 磁盘水位： 磁盘使用率触发分片迁移/拒绝写入的三档阈值默认 **85% / 90% / 95%**（cluster.routing.allocation.disk.watermark.low/high/flood_stage），生产建议监控提前预警，避免集群进入只读。
  • 查询缓存： Filter 命中的结果缓存在节点级 Query Cache（默认占堆 10%，indices.queries.cache.size）；size: 0 的聚合可配 Shard Request Cache（?request_cache=true）。
  • 查询写法： 过滤条件优先进 Filter 上下文；避免 *keyword 前导通配符、宽泛正则、脚本中做重计算；深分页用 search_after（见 4.5）；multi_match 指定字段避免默认 _all 全字段检索（7.x 已移除 _all）。
  • 索引生命周期（ILM，6.6+）： 日志类数据按时间滚动索引（daily index + index.lifecycle 策略），自动完成 hot → warm → cold → delete 的分层与清理，从机制上解决索引无限增长。

9. 数据同步

业务数据的主源在 MySQL，ES 需要一份副本用于搜索，这就产生了同步问题。三种主流方案对比：

维度 Logstash（JDBC 插件） Canal（binlog 订阅） 应用双写
原理 定时轮询执行增量 SQL（sql_last_value 记录游标） 伪装 MySQL 从库解析 binlog，解析成事件后重放给 ES 业务代码写 MySQL 的同时写 ES（或发消息异步写）
实时性 秒级~分钟级（取决于轮询间隔） 准实时（binlog 推送，毫秒级） 实时
对源库侵入 无侵入（只读查询） 需开启 binlog_format=ROW，连接占用 侵入业务代码
删除同步 无法感知 DELETE（只能同步存在的数据） 天然携带 delete 事件，可同步删除 需业务显式处理删除
实现成本 最低（配置即用） 中（Canal + 自研/现成消费者） 低（代码内实现）
适用 读多写少、实时性要求不高的搜索索引 中大型系统、需要严格实时同步 小项目、团队可控的快速方案

9.1 推荐架构

  • 方案 A（首选，通用场景）： MySQL（binlog，ROW 格式）→ Canal → Kafka → 消费端（Logstash 或自研消费者）→ ES。先做一次全量初始化（快照 + Reindex），再切增量。优点是实时、不侵入业务、削峰（写入峰值被 Kafka 缓冲）、解耦。
  • 方案 B（双写 + MQ）： 业务代码先写 MySQL，成功后发消息到 MQ，消费者异步写 ES。注意不能在”一个事务里同时写 MySQL 和 ES”（跨库事务不可行），ES 写入失败绝不能回滚数据库。
  • 方案 C（快速起步）： 小项目直接用 Logstash JDBC 轮询，接受分钟级延迟和”不支持删除同步”的局限（删除用软删字段兜底）。

9.2 一致性兜底

双写/异步同步的本质是最终一致性，必须配套兜底：

  • 重试：写 ES 失败的消息进重试队列（指数退避），超过次数进死信队列人工处理。
  • 幂等：写 ES 用业务主键作为 _id，重复投递时 upsert 覆盖，天然幂等。
  • 对账：定时任务按更新时间段扫描 MySQL，与 ES 对比，发现缺失/不一致就补同步——这是最后防线，不能省。

10. 常见面试题速答

Q1：ES 为什么查询快？
倒排索引直接定位词项（O(1) 级查找），不用全表扫描；数据分片后可跨节点并行查询，协调节点合并；段文件和 doc_values 常驻 OS Page Cache，读基本不落盘；近实时架构避免了实时索引带来的写入阻塞。

Q2：为什么 ES 是”近实时”而不是实时？
写入先进内存 Buffer + Translog，要等默认 1 秒一次的 Refresh 生成新 Segment 才对搜索可见。Translog 只保证不丢数据，不保证可见性。refresh=true 可强刷但牺牲性能。

Q3：match 和 term 有什么区别？
match 会把查询串分词后做全文检索，用于 text 字段；term 不分词，按词项整体精确匹配，用于 keyword/数值字段。对 text 字段用 term 常常查不到（text 已按词项索引，term 拿完整字符串去匹配必然落空）。

Q4：深分页为什么慢？怎么解决？
from+size 需要协调节点收集每个分片的 from+size 条结果再排序，from 越大开销越大，且 max_result_window 默认上限 10000。实时翻页用 search_after（需唯一排序键），导出数据用 scroll（快照语义、非实时）。

Q5：text 字段能直接聚合/排序吗？
不能。聚合/排序依赖列式存储 doc_values，text 默认没有（fielddata 默认也关闭，且堆内存开销巨大）。做法是给字段配 keyword 子字段，用 field.keyword 聚合。

Q6：索引建好后主分片数还能改吗？
不能。分片数参与路由公式 hash(id) % 分片数，改了路由就失效。要调整只能 Reindex 到新索引（新索引别名平滑切换，注意建别名防止写入断流）。所以分片数要在创建前按数据量估算好（单分片 10~50GB）。

Q7：中文搜索怎么分词？
ES 自带 standard 分词器对中文是按单字切分，效果差。生产中常用 IK 分词器：ik_max_word 做最细粒度切分（召回高，用于索引），ik_smart 做最粗粒度切分（精确，用于搜索），再配合扩展词典维护行业词库。

Q8：写入 ES 的数据丢了怎么办？
分情况：节点重启丢数据 → 重放 Translog 恢复；节点永久宕机 → 副本提升为主分片，不丢；若主分片和副本同时丢失则数据真丢，只能从快照（_snapshot）或源库 MySQL 重建（所以业务主存永远在 MySQL，这也是第 9 节同步架构存在的原因）；写入端对失败的 Bulk 批量重试。ES 的可靠性设计是”防丢失 + 可重建”，不是数据库级的强一致。
