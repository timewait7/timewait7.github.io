Java 并发编程

Posted on 2025-07-28 In Java Word count in article: 19k Reading time ≈ 1:08

Java 并发的全部知识可以从一条主线串起来：并发编程有三个核心问题（可见性、原子性、有序性）→ JMM 定义规则（happens-before、volatile、内存屏障）→ 语言级与类库级的解决方案（synchronized、CAS/Atomic、AQS/ReentrantLock、线程池、ThreadLocal、CompletableFuture、并发容器与工具）。所有考点都挂在这条主线上，学完本文你应该能回答”为什么要设计这个东西”而不仅仅是”它是什么”。

1. 并发编程的核心问题

1.1 问题一：可见性

问题是什么：现代 CPU 为了加速，每个核心有自己的 L1/L2 高速缓存，多核共享 L3/主内存。一个线程修改了变量，修改可能还停留在它所在核心的缓存里，其他核心上的线程读到的还是旧值。这就是”写了一个变量，别的线程看不见”。

最小复现：

JMM 的抽象：Java 内存模型（JMM）不讨论具体硬件缓存，而是抽象出”主内存 + 每线程的工作内存”模型：线程对变量的所有操作都在自己的工作内存中进行，不能直接读写主内存。可见性问题 = 工作内存与主内存之间的同步问题。

Java 怎么解决：volatile（读写直接操作主内存语义）、synchronized（进入/退出同步块时刷新工作内存）、final（构造完成后发布安全）。

1.2 问题二：原子性

问题是什么：一条高级语言语句在字节码/机器指令层面是多条指令。比如 count++ 是”读 → 加 1 → 写回”三步，两个线程同时执行就会丢更新。

Java 怎么解决：加锁（synchronized/ReentrantLock）把”读-改-写”包成原子临界区；或者用无锁的原子类（AtomicInteger 等，底层 CAS）。注意：**volatile 不解决原子性**，volatile int count 的 count++ 照样丢更新。

1.3 问题三：有序性

问题是什么：编译器和 CPU 为了流水线效率会重排指令（只要不改变单线程语义，即 as-if-serial 原则）。但重排在多线程下会破坏正确性。经典案例是双重检查锁（DCL）：

Java 怎么解决：把 instance 声明为 volatile——volatile 写会插入内存屏障，禁止这个重排（JDK 5 JSR-133 之后才保证这一点）。或者用 static final 懒加载（内部类方式），或枚举单例。

1.4 三个问题与 Java 并发机制的总对应

并发问题 解决机制 机制原理
可见性 volatile、synchronized、final volatile 读写直接走主内存；synchronized 进出块时刷工作内存；final 有特殊发布语义
原子性 synchronized、ReentrantLock、CAS 原子类 锁保证临界区互斥；CAS 保证单条读-改-写原子
有序性 volatile、synchronized、final volatile 禁重排；synchronized 块内/块外临界区有天然的顺序约束；final 防引用逃逸

生产启示：写并发代码前先自问——我面对的是哪个问题？count++ 用原子类或锁（原子性问题）；发布状态标志用 volatile（可见性问题）；共享复杂对象用锁（三个问题一起解决）。锁能同时解决三个问题，但代价是性能；按需选择最便宜的机制才是高手。

2. Java 内存模型（JMM）

2.1 JMM 是什么

JMM 是 Java 语言的内存模型规范（JSR-133，JDK 5 落地），它规定了：线程如何以及何时能看到其他线程修改过的共享变量的值，以及如何同步地访问共享变量。它不是真实内存布局，而是一套抽象规则，兼容不同 CPU 架构的强弱内存模型。

核心抽象：

  • 主内存：所有线程共享，对应物理主内存。
  • 工作内存：每线程私有，对应 CPU 缓存 + 寄存器。线程对变量的读写不能绕过工作内存（抽象上的”拷贝”），这解释了可见性问题从何而来。

2.2 happens-before 规则

happens-before（HB）是 JMM 判断”一个写对另一个读可见”的判定标准：如果 A happens-before B，那么 A 的操作结果对 B 可见，且 A 的指令排在 B 之前（不被重排破坏）。8 条规则不要背诵，理解每一条的”合理性”即可：

1. 程序次序规则：同一线程内，按程序书写顺序，前面的操作 HB 后面的操作。

为什么合理：如果连单线程程序自己的顺序语义都保证不了，所有代码都不可信。它约束的是 JIT/CPU 不能重排到破坏单线程语义的程度（as-if-serial）。注意它只说”同一线程内”。

2. 监视器锁规则：对一个锁的解锁 HB 后续对这个锁的加锁。

为什么合理：这是 synchronized 能保护共享数据的前提——线程 A 在锁内写了 10 个变量，释放锁；线程 B 获取同一把锁后，必须能看到 A 写的全部 10 个变量（而不是只有部分）。**”解锁”和”加锁”是内存同步的分界点**。这也解释了为什么 synchronized 块里所有变量都是安全的，而不仅仅是块内加锁的变量。

3. volatile 变量规则：对一个 volatile 变量的写 HB 后续对该变量的读。

为什么合理：读线程只要看到 volatile 的新值，就保证写 volatile 之前的所有写都已可见。volatile 是个”传令兵”：命令本身不重要，重要的是它传递了之前所有状态。DCL 单例正是依赖这条规则。

4. 传递性：A HB B，B HB C，则 A HB C。

为什么合理：它是把多条规则连接成链的工具。经典用法：普通变量 a 写 → volatile 变量 flag 写 → 另一线程读 flag → 读 a，由规则 1、3、4 推导出 a 的写对读可见。

5. 线程启动规则：Thread.start() HB 该线程内的任何操作。

为什么合理：你在启动线程之前准备好的初始数据（如传入的构造参数、先写的共享字段），子线程应该一开始就能看到，否则”传参数”这个基本操作都不可靠。实现上，start() 内部有隐式同步点（JVM 通过屏障保证）。

6. 线程终止规则：线程内所有操作 HB 对其他线程检测到该线程终止（join() 返回、isAlive() 为 false）。

为什么合理：主线程 join() 子线程后要读取子线程算出的结果，必须保证能看到子线程的全部写。join() 内部也是靠隐式同步（线程结束时有内存屏障）。

7. 中断规则：对线程的 interrupt() 调用 HB 被中断线程检测到中断（抛出 InterruptedException 或被 isInterrupted 检测到）。

为什么合理：中断本质是”通知+共享状态”，通知必须携带通知者之前的状态。

8. 终结器规则：对象构造完成 HB 其 finalize() 开始。（JDK 18 起 finalize 被废弃，这条规则了解即可。）

面试提示：能随手画出”锁规则/volatile 规则/传递性”三条推导链（比如 DCL 的可见性证明），比背全 8 条更分。

2.3 volatile 的用途和局限

用途：

  1. 状态标志：volatile boolean shutdown，工作线程轮询它决定是否退出（最常见、最合适）。
  2. DCL 单例：禁止构造器与引用赋值的重排（见 1.3）。
  3. 发布不可变对象：把”所有字段 final + 引用 volatile”组合，实现无锁的安全发布（safe publication）。

局限（面试必考”volatile 不保证什么”）：

  1. 不保证原子性：volatile int i; i++ 依然线程不安全。复合操作（read-modify-write）需要锁或 AtomicInteger。
  2. 不能替代锁做复合操作：check-then-act（如 if (map.isEmpty()) map.put(...)）即使变量都 volatile 也竞态。
  3. volatile 数组元素不 volatile：volatile int[] arr 只保证数组引用本身可见，arr[i] 的读写没有 volatile 语义——要用 AtomicIntegerArray。
  4. volatile 修饰的是字段级：对象内部状态的修改仍需要对象自己的同步手段。

补充一个加分点：JSR-133 还保证了 64 位（long/double）读写的原子性——规范要求 volatile long/double 的读写必须是原子的，非 volatile 的 long/double 读写在不同 JVM/平台上可能被拆成两次 32 位操作（实际上主流 64 位 JVM 上基本都是原子的，但规范只保证 volatile 情形）。

2.4 指令重排与内存屏障

重排的三种来源：编译器优化重排、CPU 指令级并行重排（乱序执行）、内存系统重排（缓存一致性协议）。JMM 通过内存屏障（Memory Barrier）指令来禁止特定重排。

四类屏障：

屏障 语义（X 类型操作不能重排到 Y 类型操作之前/之后） 作用
LoadLoad Load1; LoadLoad; Load2 禁止 Load1 与 Load2 重排
StoreStore Store1; StoreStore; Store2 禁止 Store1 与 Store2 重排（保证 Store1 先刷入内存）
LoadStore Load1; LoadStore; Store2 禁止 Load1 与 Store2 重排
StoreLoad Store1; StoreLoad; Load2 禁止 Store1 与 Load2 重排（最强，防止”写后读”重排，x86 上唯一真正需要的屏障）

JMM 对 volatile 插入的屏障（保守策略）：

  • volatile 写：写前插 StoreStore（禁止与前面普通写重排），写后插 StoreLoad（禁止与后面 volatile 读/写重排，同时保证写刷入主内存后才允许后续读——这是 volatile 写”立即可见”的关键）。
  • volatile 读：读后插 LoadLoad + LoadStore（禁止与后面普通读、普通写重排，保证读到的值是主内存最新值，且后面的操作不早于这次读）。
  • final 字段：构造器内 final 字段写之后插 StoreStore，防止 final 引用在构造器完成前逃逸（这也是”final 安全发布”的实现基础）。

硬件差异：x86 是 TSO（Total Store Order，强内存模型）架构，硬件天然满足 LoadLoad/LoadStore/StoreStore，唯一需要显式插入的是 StoreLoad（mfence 或带 lock 前缀的指令）。所以 volatile 在 x86 上的成本相对低，在 ARM/PowerPC（弱内存模型）上成本高——这也是并发程序在 x86 上跑得好、上 ARM 服务器就出 bug 的常见原因，面试能说出这一点是亮点。

3. synchronized 锁升级

3.1 对象头布局与 Mark Word 的 5 种状态

每个 Java 对象在内存里由三部分组成：对象头（Header）、实例数据（Instance Data）、对齐填充（Padding）。对象头包含：

  • Mark Word：64 位机器上占 8 字节，存锁状态、哈希码、GC 分代年龄。
  • 类型指针（Klass Pointer）：指向类的元数据（开启指针压缩后 4 字节）。
  • 数组长度（仅数组对象）。

Mark Word 的 64 位布局按锁状态复用这些比特位：

锁状态 锁标志位（低 2 位） 偏向位 Mark Word 内容（64 位）
无锁 01 0 对象 hashCode(31) + 分代年龄(4) + 偏向位(1) + 标志位(2) + 剩余未用位
偏向锁 101 1 线程 ID(54) + epoch(2) + 未用位(1) + 分代年龄(4) + 偏向位(1) + 标志位(2)
轻量级锁 00 - 指向当前线程栈中锁记录（Lock Record）的指针(62) + 标志位(2)
重量级锁 10 - 指向 ObjectMonitor 的指针(62) + 标志位(2)
GC 标记 11 - 空（GC 回收时使用，与锁无关）

记住两个关键点：锁标志位 01 表示”无锁或偏向锁”，由偏向位区分；锁升级本质就是改写 Mark Word 中的比特位。GC 年龄（4 位，最大 15）也藏在 Mark Word 里。

3.3 升级路径：偏向锁 → 轻量级锁 → 重量级锁

锁只能升级、不能降级（重偏向例外），这是 HotSpot 的取舍：让锁适配”竞争从无到有”的动态过程，避免一上来就付出高成本。

第一阶段：偏向锁

解决什么问题：无竞争场景（同一个线程反复进入同一把锁）下，连 CAS 都是浪费。

流程：

  1. 第一次加锁：CAS 把 Mark Word 的偏向位改为 1，并写入当前线程 ID。成功则此后该线程每次进出同步块只需检查”线程 ID 是否匹配 + 偏向位是否为 1”，两个判断位运算搞定，零开销。
  2. 其他线程来竞争：撤销偏向锁。此时 JVM 必须等安全点（Safe Point）执行撤销（Stop-The-World 操作），把偏向位改回 0，对象回到无锁态，再走轻量级锁流程。
  3. 撤销优化：批量重偏向（阈值 20）——若某类的锁被反复撤销，说明首个线程不再需要它，JVM 批量把该类锁重偏向到新线程；批量撤销（阈值 40）——若撤销更频繁，说明竞争已是常态，JVM 直接对该类所有锁禁用偏向。

第二阶段：轻量级锁

解决什么问题：多个线程交替（而非同时）访问同一锁时，用 CAS + 自旋避免内核态阻塞。

流程：

  1. 线程在自己的栈帧中创建锁记录（Lock Record），把 Mark Word 复制进去（Displaced Mark Word）。
  2. CAS 尝试把对象 Mark Word 替换为指向自己锁记录的指针：
    • 成功 → 持锁，Mark Word 锁标志位变为 00。
    • 失败 → 先检查 Mark Word 是否已经指向自己的锁记录（重入，锁记录计数 +1）；否则说明有竞争，自旋等待（JDK 6 之前的固定自旋次数，JDK 6 起是自适应自旋：JVM 根据同一把锁上一次自旋的成功率、锁持有者线程的状态动态决定自旋次数，能显著减少无效自旋）。
  3. 自旋仍失败（或两个线程同时 CAS 失败）→ 锁膨胀：升级为重量级锁，Mark Word 改为指向 ObjectMonitor。

注意：轻量级锁的加锁失败不代表一定有重量级竞争，也可能是”锁被持有时间稍长”，所以才有自旋这个中间态。

第三阶段：重量级锁

竞争激烈时：未抢到锁的线程 park() 阻塞，进入 ObjectMonitor 的 EntryList/cxq 排队，由 JVM 在线程间做上下文切换唤醒。这是唯一的”真阻塞”，也是 synchronized 最慢的形态。

3.4 锁消除与锁粗化

锁消除（Lock Elimination）：JIT 的逃逸分析发现某个对象只被当前线程使用（不逃逸），则其上的 synchronized 会被直接消除。例子：方法内部 new 一个 StringBuffer（其 append 方法带 synchronized）做局部字符串拼接——对象不逃逸，锁被消除，性能与 StringBuilder 相当。

3.5 为什么 JDK 15（JEP 374）废弃、JDK 18 移除偏向锁

时间线：JDK 15（JEP 374）把偏向锁标记为废弃且默认禁用（-XX:+UseBiasedLocking 不再生效）；JDK 18 彻底移除了偏向锁相关代码（JDK-8233151）。

原因（这是”为什么”考点，比”是什么”更值钱）：

  1. 撤销成本太高且不可控：偏向锁的撤销必须在安全点（STW）执行，撤销线程数多时 STW 时间被拉长。它省的是”每次加锁的两个位运算”，代价是”撤销时的全局停顿”——这笔账在现代大堆多核服务器上经常是亏的。
  2. 应用场景变了：JDK 6 时代的应用大量”同一个对象被同一个线程反复加锁”（如老的 Hashtable 内部同步）。现代应用恰恰相反——ConcurrentHashMap 用桶头节点做锁、锁竞争模式碎片化，每个锁被使用的频次低，偏向锁收益接近于零，甚至为负。
  3. 实现复杂度高：epoch 机制、批量重偏向/批量撤销、与类卸载交互（撤销时还要维护 klass 的偏向状态）让实现和维护成本居高不下。
  4. 轻量级锁已足够快：现代 JVM 的轻量级锁（CAS + 自适应自旋）在低竞争场景开销已经极低，偏向锁省的那么一点在整体上可忽略。

面试延伸：这同时解释了一个更本质的转变——JDK 6 之后 synchronized 的性能已经不输 ReentrantLock（两者在无竞争时都是几条原子指令），synchronized 的”慢”早已是历史印象。

3.6 补充考点

  • synchronized 的三种用法：同步方法（锁当前实例/Class 对象）、同步代码块（锁指定对象）、静态同步方法（锁 Class 对象）。锁对象不同则互不阻塞。
  • 可重入性：Monitor 的 _count 记录重入次数，同一线程可嵌套进入同一把锁（synchronized 和 ReentrantLock 都支持）。实现依赖”持有者线程身份”判断（ObjectMonitor._owner 或 AQS 的 exclusiveOwnerThread）。
  • wait/notify 的前提：必须在 synchronized 块内（持锁）调用，否则抛 IllegalMonitorStateException。调用 wait() 会释放锁并进入 WaitSet，notify() 只把线程从 WaitSet 移到 EntryList（不是直接唤醒执行，还要抢锁）。
  • 锁竞争对性能的真正损耗顺序：锁竞争（重量级阻塞唤醒/上下文切换）>> 自旋 > CAS > 无竞争检查。优化方向永远是”减少临界区大小、降低锁竞争”。

4. CAS 与 Atomic 类家族

问题背景：第 1 章讲过原子性问题的两种解法——锁与无锁。synchronized/ReentrantLock 是锁（悲观：先假设会冲突，直接互斥）；CAS 是无锁（乐观：先假设不冲突，改了再验证，冲突就重试）。锁适合临界区长的场景，CAS 适合临界区极短（一个变量的读-改-写）的场景——高并发下 CAS 没有线程阻塞、没有上下文切换，是 Java 并发性能的基石（ConcurrentHashMap、AQS 内部全是它）。

4.1 CAS 原理

是什么：CAS（Compare-And-Swap）是一条原子指令级的操作：比较内存中的值 V 与预期值 A，相等则把 V 更新为新值 B（返回 true），不相等则什么都不做（返回 false）。**”比较 + 更新”作为一个整体不可分割**。

Java 侧最典型的入口是 sun.misc.Unsafe.compareAndSwapInt：

底层实现（CPU 指令）：compareAndSwapInt 在 x86 上最终编译为 **lock cmpxchg**（Compare and Exchange）指令：

  • cmpxchg：一条指令完成”比较 + 条件交换”，由 CPU 硬件保证原子；
  • lock 前缀：锁定总线/缓存行，保证多核之间比较与交换的原子性（单核上 cmpxchg 本身就原子，多核必须加 lock）。

也就是说，CAS 的原子性来自硬件（一条指令），而不是软件加锁——这就是它比锁快一个数量级的根本原因。ARM 平台对应 LDXR/STXR（加载-预留/存储-条件）指令对。

自旋与代价：

  • 自旋的代价：高竞争下大量线程同时 CAS，只有少数成功，其余空转重试——CPU 空耗、缓存行颠簸（同一缓存行被多个核反复失效）；
  • 适用场景：临界区只有一个变量、操作极快（几纳秒），自旋重试的成本远低于线程阻塞唤醒（微秒级）；
  • 不适用：临界区长的操作（CAS 无法原子化多条语句）、超高竞争（自旋风暴），这时锁反而更好；
  • 局限：只能保证一个变量的原子性，多个变量的原子更新必须用锁（或把多个变量打包进一个对象/一个 long）。

ABA 问题与 AtomicStampedReference

CAS 判断”值没变”的前提是”值等于预期值”，但值经历 A→B→A 后，CAS 依然认为没变——这就是 ABA 问题。复现场景：

语义危害：T1 的”余额还是 100”判断被欺骗——数据被中间人动过（比如透支过）却无从察觉。经典受害场景：无锁栈/队列（top 指针）、账户余额、缓存 key 交换。

解决：给”值”加上版本号，CAS 时连版本号一起比较：

  • AtomicStampedReference：compareAndSet(期望引用, 新引用, 期望版本, 新版本)，版本号每次递增——解决 ABA 的标准答案；
  • AtomicMarkableReference：版本退化为 boolean（只标记”是否被改过”），适合”只要知道动没动过”的场景（如链表节点的 marked 标记）。

生产启示：CAS 是 JUC 的基石——ConcurrentHashMap 的桶插入、AQS 的 state 获取、Atomic 全家桶全部建立在它之上。面试答”为什么并发容器这么快”，第一句话永远是”读无锁 + CAS”，而不是”用了分段锁”。

基本类型：AtomicInteger / AtomicLong / AtomicBoolean

LongAdder 与 Striped64 分片计数

问题：高并发下所有线程 CAS 同一个 AtomicLong——成功率暴跌、自旋风暴，吞吐断崖式下降（高竞争时可能掉一个数量级）。

LongAdder 的思路（分片）：Striped64 基类维护 base + Cell[] 数组：

  • 初始：所有累加走 base（无竞争时的零开销路径，等同 AtomicLong）；
  • 竞争升级：CAS base 失败 → 分配 Cell[]（初始 2 个 Cell），每个线程用线程探针（ThreadLocalRandom 的 probe）hash 定位一个 Cell，只在自己的 Cell 上 CAS；
  • 碰撞迁移：自己的 Cell 竞争失败 → 尝试扩容（cells 翻倍）或换一个 Cell——把单点热点摊成 N 个桶；
  • Cell 用 @sun.misc.Contended 注解按 128 字节对齐，避免伪共享（相邻 Cell 落在同一缓存行会被多个核互相失效）；
  • sum()：无锁累加 base + 所有 Cell（近似值，累加期间可能又有更新）。

5. AQS 与 ReentrantLock

5.1 AQS 是什么

AbstractQueuedSynchronizer（java.util.concurrent 包的基石）是一个框架：用一个 volatile int state + 一个 FIFO 阻塞队列实现同步器。JUC 里一半工具建立在它之上：ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock、ThreadPoolExecutor（Worker 本身就是一个 AQS 子类）。

核心三要素：

  • **state**（volatile int）：同步状态。语义由子类定义——ReentrantLock 里是”重入次数”，Semaphore 里是”剩余许可数”，CountDownLatch 里是”剩余计数”。
  • **exclusiveOwnerThread**（继承自 AbstractOwnableSynchronizer）：当前持有独占锁的线程（可重入判断的基础）。
  • CLH 队列变体：等待线程的队列。

模板方法模式：AQS 定义骨架流程（acquire/release），把”如何判断获取成功”留给子类实现（tryAcquire/tryRelease/tryAcquireShared/tryReleaseShared/isHeldExclusively）。ReentrantLock 的 Sync（公平 FairSync / 非公平 NonfairSync）就是实现这些钩子的子类。

5.2 CLH 队列变体：为什么不用原版 CLH

AQS 的队列灵感来自 CLH 锁（Craig-Landin-Hagersten），但做了关键改造，理解差异就是理解”为什么这样设计”：

维度 原版 CLH 锁 AQS 变体
等待机制 自旋（前驱释放后轮询前驱状态） 阻塞唤醒（LockSupport.park/unpark，不烧 CPU）
队列结构 单向链表、隐式前驱（只保存前驱的 Node） 双向链表（显式 prev/next 指针 + 头哨兵）
能否唤醒后继 不能（不知道后继是谁） 能（释放时直接 unpark 下一个节点）
取消/超时 不支持（队中线程无法退出） 支持（CANCELLED 状态节点出队）
适用场景 临界区极短的硬件/自旋锁 系统级阻塞锁（可能被阻塞任意长时间）

为什么必须用变体：Java 的锁目标是”让等待的线程睡过去”而不是”转圈等”，阻塞型锁必须满足三点：① 释放者要能精确唤醒一个后继（单向 CLH 做不到）；② 线程可取消（如 tryLock(timeout)、中断，自旋锁队列里取消是灾难）；③ 避免所有等待线程同时被唤醒去抢（thundering herd）。所以 AQS 选择了”双向链表 + 显式前驱/后继 + park/unpark”的变体。

Node 的 waitStatus 状态（面试常问）：

  • CANCELLED(1)：线程取消（超时/中断），节点将被清理。
  • SIGNAL(-1)：后继节点需要被唤醒（当前节点释放时要 unpark 后继）。
  • CONDITION(-2)：节点在 Condition 条件队列里。
  • PROPAGATE(-3)：共享模式下传播唤醒（如 Semaphore、CountDownLatch 释放时连续唤醒）。
  • 0：初始状态。

5.3 获取与释放锁的完整流程

**非公平获取 lock()**（以 ReentrantLock 为例）：

  1. 快速通道：直接 CAS(state, 0, 1)——成功即持锁（这就是”插队”，见 4.4），失败进入 acquire。
  2. acquire(1)：
    • tryAcquire(1)（NonfairSync.nonfairTryAcquire）：state == 0 时再 CAS 一次；若 current == exclusiveOwnerThread（重入），state + 1。
    • 失败 → addWaiter(Node.EXCLUSIVE)：创建 Node，CAS 把它挂到队尾（compareAndSetTail）。
    • acquireQueued()：死循环——如果前驱是 head，再 tryAcquire 一次（成功则把自己设为 head，出队）；否则 shouldParkAfterFailedAcquire 把前驱状态置为 SIGNAL，然后 LockSupport.park(this) 阻塞。被 unpark 唤醒后回到循环重试。
  3. 中断处理：acquire 模式不响应中断（中断只设置标志位）；lockInterruptibly() 会直接抛 InterruptedException。

**释放 unlock()**：

  1. tryRelease(1)：state - 1；只有 state 减到 0（可重入锁要释放全部重入层）才真正释放——置 exclusiveOwnerThread = null，返回 true。
  2. 释放成功 → unparkSuccessor()：找到 head 的 next（跳过 CANCELLED 节点），LockSupport.unpark 唤醒它。

重入的关键：state 是重入计数，加锁 +1、释放 -1，减到 0 才算释放——这就是 synchronized 与 ReentrantLock 可重入的共同实现思路（synchronized 靠 Monitor 的 _count）。

5.4 公平锁 vs 非公平锁

非公平锁（默认）：lock() 的第一步就是直接 CAS 抢锁——新线程可以插到等待队列前面。失败才入队排队。

公平锁：lock() 直接走 acquire，tryAcquire 里先调 hasQueuedPredecessors()：检查队列中是否有（除头哨兵外的）等待节点——有则主动入队让行，没有才尝试 CAS。

为什么非公平锁吞吐更高（核心考点）：

  1. 减少唤醒成本：刚释放锁的线程有”时间局部性”——它可能马上又要锁，直接再抢一次成功的话，就省掉了一次”唤醒队头线程 + 上下文切换”。等待线程从 park 到真正运行有可观的延迟，插队线程利用了这段空档。
  2. 队头线程被唤醒后仍要重新抢锁：唤醒不是”直接授予”，而是”叫醒去抢”。非公平下队头线程失败的概率低，但总体等待时间方差大。
  3. 代价：等待队列中的线程可能饥饿（理论上）。实践中插队窗口很小，饥饿几乎不会发生，但公平性语义确实被破坏。

怎么选：默认用非公平（吞吐优先）；只有对”等待时间上限”有严格要求的场景（如金融撮合、需要顺序执行）才用公平锁。

5.5 Condition 的实现原理

Condition 是 Object.wait/notify 的增强版，ReentrantLock.newCondition() 创建。核心类 ConditionObject 内部维护独立的单向条件队列（firstWaiter/lastWaiter，复用一个带 CONDITION 状态的 AQS Node，通过 nextWaiter 字段串联）。

**await()**：

  1. 当前线程必须已持有锁（否则 IllegalMonitorStateException，与 wait 相同）。
  2. 创建 Node(CONDITION) 加入条件队列尾。
  3. 完全释放锁：saveState = state; release(state)——注意要释放全部重入层（这是与 wait() 释放锁一致的设计，让其他线程能进临界区）。
  4. LockSupport.park 阻塞。
  5. 被 signal 后：acquire(saveState) 重新竞争锁（恢复重入计数），成功才从 await 返回。

**signal()**：

  1. 把条件队列头节点通过 transferForSignal 移到 AQS 等待队列尾部（改状态为 0，LockSupport.unpark 唤醒它，让它参与正常的锁竞争）。
  2. signalAll()：把整个条件队列全部转移。

与 wait/notify 的对比：

维度 wait/notify Condition
等待队列数 每个对象 1 个 一个锁可多个 Condition（生产者/消费者分离）
超时 wait(timeout) await(timeout, unit) 可精确到纳秒
中断 不支持（等待时无法响应中断） awaitUninterruptibly/中断可配置

经典场景：生产者-消费者用 full 和 empty 两个 Condition——生产者等 full，消费者等 empty，signal 只唤醒对方队列的线程，比 notifyAll 扫全场效率高得多。

选择建议：

  • 默认用 synchronized：语法简单不会漏解锁、可读性好、JVM 持续优化（锁升级 + 锁消除 + 锁粗化）、与 wait/notify 配套。

  • StampedLock（JDK 8，了解即可）：读写锁之上的”乐观读”——读不加锁，先乐观读，写完用 CAS 校验版本（validate），失败才升级悲观读。读多写少的场景性能极致，但不可重入、条件变量支持弱、乐观读里不能有写操作，用错极易出 bug，生产优先 ReentrantReadWriteLock。

5.7 ReentrantReadWriteLock 读写锁

解决什么问题：ReentrantLock 是排他锁——读和读之间也互斥。读多写少的场景（缓存、配置、路由表）里大量读线程互相排队，白白损失并发度。读写锁把访问权限拆成读（共享）与写（独占）：读读可并发，读写/写写互斥，是”读多写少”场景的官方答案。

一个 state，两种计数

ReentrantReadWriteLock 内部是一个 AQS 同步器（Sync），把唯一的 state 32 位拆成两半：

  • 写锁：独占。tryAcquire：已有读锁、或写锁被其他线程持有 → 失败；否则 CAS state + 1（低 16 位）。重入：当前线程已持写锁 → state + 1；
  • 读锁：共享。tryAcquireShared：写锁被持有且持有者不是当前线程 → 失败；否则 CAS state + (1 << 16)（高 16 位 +1）。读锁的重入计数不占 state 的高 16 位（否则 65535 次就溢出了），而是放在线程自己的 ThreadLocal（cachedHoldCounter）里；
  • 读锁的 tryAcquireShared 失败后走 AQS 共享模式排队（5.2 节 waitStatus 的 PROPAGATE(-3) 状态就是为它准备的）；写锁走独占模式。

锁降级（写 → 读）

定义：持有写锁期间获取读锁，再释放写锁——锁从”独占”降级为”共享”，当前线程仍然持有锁（现在是读锁）。

为什么允许、且推荐：缓存更新场景——线程 A 拿写锁写完数据，如果直接释放写锁，另一个线程 B 可能立刻抢到写锁改数据，A 接着读时就读到了 B 的新数据，前后不连贯。降级方案：A 在写锁内完成更新 → 立即拿读锁（写锁保护下读锁必然拿到）→ 释放写锁 → 用读锁读完再释放——**”写”与”紧接着的读”之间不可能插入别的写者**。JDK 官方文档明确推荐该模式（write-to-read downgrading）。

为什么不能锁升级（读 → 写）

定义：持有读锁期间尝试获取写锁。被 JDK 明确禁止（ReentrantReadWriteLock 文档：直接升级会抛异常或死锁），原因是必然死锁：线程 A、B 都持有读锁，都想升级成写锁——A 等 B 释放读锁、B 等 A 释放读锁，互相等待对方的共享锁释放，谁也放不了。正确做法：读完先释放读锁，再重新获取写锁（中间会插入其他操作，业务要接受这个间隙）。

非公平模式的写饥饿：默认非公平模式下，新来的读线程可以插队——读多写少的系统里写锁可能长期拿不到（写饥饿）。可选 new ReentrantReadWriteLock(true) 公平模式：写线程请求时排队（先到先得），后续读线程不能再插队。注意读锁不支持 Condition（Condition 依赖独占语义），写锁支持。

适用场景与选型：

场景 用法
缓存（配置、路由表、黑白名单） 读锁 get / 写锁 update（低频全量替换 + 锁降级）
读多写少的共享状态 读写锁替代 synchronized 提升读并发
读多写少但要求写不被饿死 公平模式（ReentrantReadWriteLock(true)）
写多读少 / 读写都频繁 读写锁无优势，直接用 ConcurrentHashMap / synchronized
要求读性能极致 StampedLock 乐观读（见 5.6，注意它的坑）

面试怎么答：先答 state 布局（高 16 位读、低 16 位写），再答”读锁走共享模式、写锁走独占模式”；主动抛出两个考点——锁降级是官方推荐、锁升级是死锁禁区（各给一句原因）；最后补一句”读多写少才用它，写多读少没收益”。

6. 线程池

6.1 ThreadPoolExecutor 的 7 个参数与执行流程

参数含义（面试先报全 7 个）：

参数 含义 要点
corePoolSize 核心线程数 即使空闲也保留（除非 allowCoreThreadTimeOut(true)），任务提交时先创建核心线程
maximumPoolSize 最大线程数 核心线程数 + 队列满时临时扩容的上限
keepAliveTime 非核心线程空闲存活时间 超过 corePoolSize 的线程空闲这么久被回收；对核心线程默认不生效
unit keepAliveTime 的时间单位 -
workQueue 任务阻塞队列 LinkedBlockingQueue/ArrayBlockingQueue/SynchronousQueue 等
threadFactory 线程工厂 生产环境必配：命名（order-pool-1）、daemon、异常处理器
handler 拒绝策略 线程数到 maximum 且队列满时触发

任务提交的完整流程（execute() 源码级，与直觉不同：先线程后队列，先队列后扩线程）：

  1. workerCount < corePoolSize → 创建核心线程执行（即使有空闲核心线程也会先建新线程）。
  2. 否则 workQueue.offer(task) 入队成功 → 二次检查（double-check）：若线程池已停止则出队并拒绝；若 worker 数为 0 则补一个线程（防止”任务在队列里没人执行”）。
  3. 队列满 → addWorker(task, false) 创建非核心线程（不超过 maximumPoolSize）。
  4. 线程数已达 maximum → 触发 handler 拒绝策略。

6.2 参数调优原则

线程数（业界经验公式，最终以压测为准）：

  • CPU 密集型：CPU 核数 + 1（多一个线程抵销缺页中断等暂停）。
  • IO 密集型：2 × CPU 核数，或更严谨的 CPU 核数 × (1 + 等待时间 / 计算时间)——等待占比越高，线程数可以越多，因为大部分线程在阻塞。

队列：生产必须有界。无界队列（new LinkedBlockingQueue()）会让 maximumPoolSize 和拒绝策略形同虚设——任务无限排队、内存无限增长，最终 OOM。容量按”业务可容忍的积压量”评估。

线程池类型与任务形态匹配：

任务形态 推荐配置
短任务、高频、对延迟敏感 SynchronousQueue + 较大 maximumPoolSize（SynchronousQueue 不缓存任务，直接转给线程）
任务量大、执行时间均匀 LinkedBlockingQueue(有界)
需要排序/延迟执行 DelayedWorkQueue（ScheduledThreadPoolExecutor 用）

其他原则：线程名可排查（threadFactory）、拒绝策略与业务重要性匹配、核心线程数应能覆盖平均负载而非峰值（峰值靠临时扩容 + 队列吸收）。

6.3 4 种拒绝策略的适用场景

策略 行为 适用场景
AbortPolicy（默认） 抛 RejectedExecutionException 任务绝不能丢，调用方必须感知并处理（如重试、降级）。注意要在提交处 try-catch
CallerRunsPolicy 由提交任务的线程（调用 execute 的线程）直接执行该任务 天然背压：提交线程自己干活时没法再提交，自然限速；适合能接受”提交线程被占用”的批处理
DiscardPolicy 静默丢弃 任务丢了无所谓的场景（如日志、埋点、可重算的统计）
DiscardOldestPolicy 丢弃队列中最老的任务，重新提交当前任务 缓存型/快照型任务：新数据比旧数据有价值（如价格快照、实时状态）
自定义（实现 RejectedExecutionHandler） 记录日志、写入 MQ/数据库、放入重试队列 生产标配：拒绝必留痕，通常”记录 + 告警 + 落盘/重试”

6.4 Executors 快捷方法的陷阱

方法 隐藏的问题
newFixedThreadPool(n) LinkedBlockingQueue 无界 → 任务积压导致 OOM
newCachedThreadPool() SynchronousQueue + maximumPoolSize = Integer.MAX_VALUE → 突发流量创建海量线程，线程栈 OOM（每线程默认约 1MB 栈内存）
newSingleThreadExecutor() 同 fixed，无界队列
newScheduledThreadPool(n) DelayedWorkQueue 无界 → 积压 OOM

《阿里巴巴 Java 开发手册》明确禁止使用 Executors 快捷方法创建线程池。**生产一律手动 new ThreadPoolExecutor**，配上有界队列 + 命名 threadFactory + 明确拒绝策略。

6.5 线程池参数动态调整：为什么”不能随便调”

ThreadPoolExecutor 提供了 setCorePoolSize、setMaximumPoolSize、setKeepAliveTime、allowCoreThreadTimeOut 等动态调整 API——可以调，但”随便调”是事故现场：

  1. 只影响未来，不影响存量：调参只作用于新任务的调度路径。已在队列中的任务、正在运行的任务、已创建的线程都不会被新参数”纠正”——比如发现堆积把 core 调大，队列里已积压的任务不会因此被多线程加速处理（线程是从队列取任务的，会有作用，但注意调大 core 是立即创建新线程，如果此刻刚好无任务，就白创建了线程）。
  2. 调大线程数不线性提升吞吐：IO 阻塞线程增多只是多耗资源；CPU 密集线程增多反而因上下文切换、缓存失效而变慢。线程数的合理值依赖任务性质，动态调大解决不了”任务本身就是瓶颈”。
  3. 高峰期调整引入抖动：新线程创建需要时间（栈内存分配 + 首次唤醒），瞬间创建大量线程会带来短暂的 CPU 峰值和 GC 压力；调小 maximumPoolSize 不会杀死正在运行的线程，它们要等 keepAliveTime 才回收，期间表现不可预期。
  4. 缺少整体性：线程数、队列容量、拒绝策略必须作为一个整体设计。单独调某个数，比如”队列放大了但没改拒绝策略”或”core 调大了但队列还是满的”，参数之间互相抵消，等于没调。
  5. 正确姿势：基于监控（队列积压、活跃线程、拒绝次数）评估 → 压测验证 → 低峰期分步调整 → 调整后持续观察。真正优雅的方案是开箱即用的动态线程池框架（如美团的动态线程池中间件思路：配置中心下发 core/max/queue，同时支持任务队列容量动态调整）。

6.6 如何正确关闭线程池

三个 API 的区别（保留原文考点）：

  • shutdown()：温和关闭——不再接受新任务，但把已提交任务（含队列中）执行完。
  • shutdownNow()：强停——中断所有正在执行的任务（Thread.interrupt()），返回队列中未执行的任务列表 List<Runnable>。任务若不响应中断则无法停止。
  • awaitTermination(timeout, unit)：阻塞等待线程池终止，返回 boolean。

生产关闭模板（必须配合使用）：

要点：任务的正确性依赖任务自己响应中断（检查 Thread.interrupted()、捕获 InterruptedException 后恢复中断标志），否则 shutdownNow 形同虚设。

补充：**JDK 19 起 ExecutorService 继承了 AutoCloseable**，可以配合 try-with-resources 自动调用 shutdown（ExecutorService 的 close 等价 shutdown + awaitTermination），JDK 21 后 newVirtualThreadPerTaskExecutor() 也用它。

6.7 常见错误

错误一：异常被”吞掉”

场景 A（最隐蔽，生产事故高发）：用 submit() 提交任务，却**从不调用 get()**——任务抛出的异常被封装在 Future 里，没人读取就永远沉默。代码不报错、不打印、只有业务数据悄悄缺失。

场景 B：execute() 提交的任务抛异常，worker 线程退出（异常默认打印到 stderr，也常被忽略），线程池会默默补一个新线程继续跑——业务上表现为”任务莫名中断，日志里看不到”。

正确姿势（三选一或组合）：

  1. 任务内统一 try-catch 记录日志（最简单，但每处都要写）。
  2. **重写 afterExecute(Runnable, Throwable)**（ThreadPoolExecutor 钩子，任务结束后调用，包括异常后）：注意 afterExecute 拿不到异常时，要主动从 Future 里取：
  1. **自定义 UncaughtExceptionHandler**：通过 threadFactory 给每个线程设置（对 execute() 抛出的、且未被捕获的异常生效；对 submit 的 Future 异常不生效）。

错误二：ThreadLocal 未清理

线程池线程被复用，ThreadLocal 值会残留并串到下一个任务：任务 A 设置了 userId，没清理，任务 B 在同一个线程上执行时 get() 到的是 A 的用户——数据串线的经典 bug，且伴随内存泄漏。解决：每个任务结束时 remove()，或用统一的任务包装器。

错误三：execute vs submit 语义混淆

execute(Runnable)：无返回值，异常走 UncaughtExceptionHandler 路径；submit(Callable)：有返回值，异常封装进 Future。**”想拿结果用 submit，只想触发用 execute”**，但两者都要有异常兜底。

7. ThreadLocal

7.1 实现原理

三个关键事实：

  1. 数据存在线程里，不在 ThreadLocal 对象里：Thread 类内部有两个字段 threadLocals 和 inheritableThreadLocals（类型 ThreadLocal.ThreadLocalMap）。ThreadLocal 只是一个”键 + 操作工具”，每个线程的副本各自存放。
  2. ThreadLocalMap 是定制哈希表：用 Entry 数组 + 开放寻址（线性探测）解决冲突——不是 HashMap 的链表/红黑树。ThreadLocal 自带自增的 threadLocalHashCode（增量 0x61c88647，斐波那契散列，保证散列均匀）。初始容量 16，扩容阈值 2/3。
  3. Entry 的弱引用设计：

set/get/remove 流程（面试讲清三句话）：

  • set(value)：getMap(Thread.currentThread()) → 无则 createMap → 有则按 hash 定位，线性探测放入；遇到 key 为 null 的过期条目（stale entry）则 replaceStaleEntry 就地替换并触发 expungeStaleEntry（清理连续段）。
  • get()：map.getEntry(this)；miss 时 getEntryAfterMiss 继续探测，沿途清理 stale entry。找不到则 setInitialValue（initialValue 或 null）。
  • remove()：定位 Entry 并删除（唯一保证清理 value 的路径）。

为什么 key 用弱引用：如果 key 是强引用，只要线程还活着（线程池线程可以活很久），ThreadLocalMap 的 Entry 就一直强引用着 ThreadLocal 对象——即使业务代码早就用不到它了，ThreadLocal 对象及其（可达的）值都无法被回收，key 泄漏。弱引用让 key 在无外部强引用时自动失效（变 null），把”泄漏”收敛为”可被清理的 stale entry”。

7.2 内存泄漏：根本原因与解决方案

泄漏链条：

两个叠加条件：① value 是强引用；② 线程池线程不销毁（普通线程死了 threadLocals 随之回收，不会泄漏；线程池复用线程才是重灾区）。

为什么 get/set 的自动清理救不了你：expungeStaleEntry/cleanSomeSlots 只清理哈希桶连续段内的 stale entry——如果你的 key 所在桶不再被任何 set/get/remove 触及，那个 Entry（连同强引用的 value）就永久驻留。清理是”顺手为之”，不是”兜底保证”。

解决方案（按重要性排序）：

  1. finally 中 remove()（必须）——唯一确定性清理路径：
  1. 统一任务包装器（线程池场景一次解决所有任务）：
  1. 用封装好的上下文工具类（如 UserContextHolder，自带 clear 方法，拦截器 afterCompletion 里调用——原文示例即是此模式）。
  2. 值尽量放小对象；泄漏兜底可给 value 套 WeakReference（不推荐，语义不符）。
  3. 静态分析工具（如 IDEA 的 “ThreadLocal leaks” 检查）配合 review。

面试追问：”为什么 ThreadLocal 还会泄漏，弱引用不是解决了吗？”——弱引用只解决了 key 的泄漏；value 是强引用，stale entry 的清理是惰性的，线程池复用 + 桶不再被访问时泄漏仍会发生，所以 remove() 是唯一可靠手段。

7.3 InheritableThreadLocal 与线程池的冲突

InheritableThreadLocal 的语义：创建子线程时，把父线程的副本拷贝到子线程（new Thread() 内部调用 createInheritedMap）。用途：主线程的上下文（traceId、租户 id）自动带进异步任务。

与线程池的冲突（高频面试题）：

  • 线程池里的线程是复用的：createInheritedMap 只在线程创建那一刻执行一次。
  • 结果是：第一个任务能拿到”提交它的父线程”的值；后续任务拿到的还是第一次拷贝的旧值（如果第一个任务没清理）——不同请求的值互相串线，且新请求的值根本传不进去。
  • 对比：普通 ThreadLocal 在线程池的问题是”上一个任务残留值串到下一个任务”；InheritableThreadLocal 的问题是”只在首次创建时继承，后续请求的值传不进去，且旧值残留”。

解决方案：

  1. 显式传参：提交任务时把上下文作为参数传入（无状态、最干净）。
  2. 阿里开源的 TransmittableThreadLocal（TTL）：任务提交时快照、执行时恢复、完成后清理——专门解决”线程池场景下上下文跨线程传递”。
  3. 自研任务包装器：submit 前手动 set、执行后 remove（同 6.2 的包装器思路）。

7.4 实际场景

场景 用法 关键点
链路追踪（traceId） 请求进入时生成 traceId 存 ThreadLocal，日志、RPC、DB 全链路打印 子线程任务用 TTL；请求结束 finally remove；Logback 的 MDC 就是 ThreadLocal
数据库读写分离 路由键（如”是否主库”）存 ThreadLocal，AbstractRoutingDataSource 按它选数据源 事务结束后必须清理，否则下一个请求路由错误（生产事故高发）
用户上下文 拦截器解析 token → 存 userId → 业务层直接用 与”接口传参”相比少侵入，但要防”上下文跨请求串线”
事务管理 Connection 绑到线程，保证同一事务内复用同一连接（Spring 的 TransactionSynchronizationManager 就是这个模式） 连接是重量级资源，必须归还 + 清理
线程安全工具替换 每线程一个 SimpleDateFormat（不推荐，用 DateTimeFormatter 即可）、每线程一个 Random（即 ThreadLocalRandom 的设计） 这类场景一般无泄漏风险（值小且线程结束即回收）

8. CompletableFuture

8.1 从 Future 的局限到 CompletableFuture 的设计

Future（JDK 5）只能做两件事：get() 阻塞等待、isDone() 轮询。它的局限直接引出 CompletableFuture 的设计动机：

能力 Future CompletableFuture（JDK 8）
获取结果 get() 阻塞 回调（thenXxx），非阻塞
完成状态检测 isDone() 轮询（浪费 CPU） 事件驱动：完成时自动触发后续
任务组合 无 thenCompose/thenCombine/allOf/anyOf 链式编排
手动完成 无 complete(v)/completeExceptionally(e)（任意线程可完成，超时/外部事件的基础）
异常处理 ExecutionException 包装，处理笨拙 exceptionally/handle/whenComplete 声明式处理
超时 只能 get(timeout) 阻塞等 orTimeout/completeOnTimeout（JDK 9）
中断 cancel(true) 只中断直接任务，无传播 同样需手动设计，但配合超时方法更易用

设计本质：CompletableFuture 是一个可手动完成的结果容器 + 状态机（NEW → COMPLETING → NORMAL/EXCEPTIONAL/CANCELLED），内部用依赖栈/链表挂接后续回调；前驱完成时遍历依赖，把后续阶段提交执行。它实现了 CompletionStage 接口，所有 thenXxx 返回新的 stage，构成异步流水线。

8.2 核心方法串讲

创建任务：

  • supplyAsync(Supplier<T>)：异步执行有返回值。
  • runAsync(Runnable)：异步执行无返回值。
  • 两个方法都有带 Executor 的重载（见 7.4）。

转换与消费：

方法 语义 对比要点
thenApply(Function<T,U>) 结果转换 T→U 同步回调（见 7.4 执行线程）
thenApplyAsync(...) 异步转换，提交到（指定）线程池 用 thenCompose（扁平化）而非嵌套
thenAccept(Consumer<T>) 消费结果，不返回新值 链末常见
thenRun(Runnable) 前驱完成后执行动作，不关心结果 如清理、通知
thenCompose(Function<T, CompletionStage<U>>) 扁平化组合：前驱结果作为入参启动新异步任务，避免 CompletableFuture<CompletableFuture<U>> 嵌套 对比 thenApply 返回的是 Future 还是值
thenCombine(other, BiFunction) 两个并行任务都完成后合并结果 与 thenCompose 的区别：thenCombine 两任务无依赖、并行；thenCompose 有依赖、串行
allOf(cf...) / anyOf(cf...) 全部 / 任一完成 allOf 返回 Void，结果要自己 join() 各 Future；anyOf 返回最先完成的 Object

异常处理（面试必考三者区别）：

方法 触发时机 返回值 典型用途
exceptionally(Function<Throwable,T>) 仅异常时 恢复值（正常完成时结果透传） 失败降级为默认值
handle(BiFunction<T,Throwable,U>) 无论成功失败都执行 新结果（可重新抛异常） 统一收口”结果或异常”
whenComplete(BiConsumer<T,Throwable>) 无论成功失败都执行 不改变结果（异常继续传播） 旁路：日志、指标、资源清理

异常传播规则：链上任一阶段抛异常，后续 thenApply/thenAccept 不会执行，异常沿链传递到 exceptionally/handle 或最终 get()/join() 时抛出。中间没人处理就一直沉到最后。

结果获取：get()（受检异常，抛 ExecutionException 包装原始异常）vs join()（非受检，抛 CompletionException）。生产建议链末用回调，避免阻塞。

8.3 线程池：默认 ForkJoinPool vs 自定义线程池

默认执行器：不带 Executor 参数的 supplyAsync/thenApplyAsync 等使用 ForkJoinPool.commonPool()——全局共享池，并行度 = CPU 核数 - 1（可通过 java.util.concurrent.ForkJoinPool.common.parallelism 系统属性调整），整个 JVM 只有一个。

致命坑：commonPool 同时服务于 parallelStream()、其他 CompletableFuture。在回调里做阻塞操作（DB、HTTP、MQ）会占住公共池线程——公共池线程数量等于 CPU 核数，一旦被 N 个阻塞任务占满，全 JVM 所有依赖 commonPool 的并行计算全部卡死（这是生产事故经典场景：一个接口的 CF 阻塞操作拖垮了整个应用的 parallelStream）。

执行线程的语义（高频考点）：

  • thenApply（非 Async）：在前驱完成的那条线程上同步执行（若前驱是同步完成的，则在调用 thenApply 的当前线程上执行）——执行线程不可控。
  • thenApplyAsync（Async）：保证提交到执行器（默认 commonPool 或指定 Executor）的线程上执行。

生产实践：

  1. IO 任务全部显式指定专用线程池（独立于 commonPool），按资源隔离：DB 池、HTTP 池分开，避免互相拖累。
  2. CPU 密集的转换用 commonPool 没问题。
  3. 回调内部不要放阻塞代码；非放不可就用 thenApplyAsync(..., pool)。

8.5 JDK 21：虚拟线程 + CompletableFuture 的简化

问题回顾：CompletableFuture 的复杂编排（thenCompose 扁平化、异常传播、回调地狱的变种）本质是在”用回调模拟阻塞”。为什么非要这样？因为 JDK 8 时代线程是稀缺昂贵资源，阻塞一个平台线程（约 1MB 栈）代价高，才用事件回调让线程”不阻塞”。

虚拟线程（JDK 21 正式版，JEP 444）改变假设：虚拟线程由 JVM 调度，栈可以随时释放、挂载到任何载体线程，数量可达十万级——阻塞一个虚拟线程的成本趋近于零。

  • 非阻塞事件链（外部回调 complete、超时组合 orTimeout、多事件任意完成）→ CompletableFuture 依然是正确工具，虚拟线程也解决不了”事件驱动”。

9.1 CountDownLatch vs CyclicBarrier vs Semaphore

三者都是 JUC 的同步工具（都基于 AQS），但语义完全不同——先记一句话区分：**CountDownLatch 是”一个/多个线程等 N 个事件”；CyclicBarrier 是”N 个线程互相等齐再出发”；Semaphore 是”资源只有 N 个许可”**。

维度 CountDownLatch CyclicBarrier Semaphore

谁等谁 一个（或多个）线程 await() 等其他线程 countDown() 所有线程互相等（每个都 await） 线程等资源许可，不是等线程
可复用 不可（用一次作废，需新建） 可循环（reset() 后再次使用） 一直可用（许可循环）
回调 无 barrierAction：全部到达后执行一次动作 无
公平性 无 无 可配公平/非公平（Semaphore(permits, fair)）
典型场景 压测同时起跑、等待多个接口全部返回 多线程分片计算后合并、批次处理 限流（连接池、接口并发上限）

9.2 ConcurrentHashMap：从分段锁到 CAS + synchronized

JDK 7：分段锁（Segment Locking）

  • 结构：一个固定 Segment[]（默认 16，创建后不可变）+ 每个 Segment 内一个 HashEntry[] 哈希表。Segment 继承 ReentrantLock——每个段一把锁。
  • 写：按 hash 定位段 → 锁该段 → 段内操作（头插法）。不同段的写可并发，并发度上限 = 段数 16。
  • 读：无锁——HashEntry.value 声明为 volatile，读依赖 volatile 语义拿最新值。
  • size()：先无锁累加两次，modCount 不变则返回；否则锁所有段再统计（昂贵）。
  • 扩容：段内独立扩容（段锁内进行）。
  • 缺陷：锁粒度仍粗（同段内竞争互斥）、段数固定无法扩展并发度、size 需要锁全表、HashEntry 链表过长时读变慢。

JDK 8：CAS + synchronized + 红黑树

  • 结构：抛弃 Segment，一个 volatile Node[] table。Node 的 hash/key 为 final，val/next 为 volatile（读无锁的安全基础）。链表长度 ≥ 8 且 table 长度 ≥ 64 时树化为红黑树（TreeBin 包装，hash 为 -2），树节点 ≤ 6 时解树。
  • 锁粒度：细到单个桶的头节点（synchronized 锁桶头）。
  • put 流程：
    1. 桶为空 → CAS 直接插入（无锁路径，casTabAt）。
    2. 桶头是 ForwardingNode（hash 为 -1，正在扩容）→ 协助扩容（helpTransfer）。
    3. 否则 synchronized 锁桶头 → 链表尾插（JDK 7 的头插在并发扩容下有死循环隐患，JDK 8 改尾插）或树插入。
  • 读（完全无锁）：tabAt（Unsafe getObjectVolatile 保证数组元素的 volatile 语义——注意 volatile Node[] 只保证引用本身可见，数组元素访问必须靠 Unsafe 原子读）；桶头 hash < 0 时按特殊节点处理（ForwardingNode 去新表找 / TreeBin 树查找）；Node.val 的 volatile 保证看到最新值。
  • size()（O(1) 估计）：baseCount + 竞争时拆分的 CounterCell[] 分片计数（@sun.misc.Contended 防伪共享），结果是近似值（累加瞬间可能有更新）；mappingCount() 返回 long 更准确。
  • 扩容（多线程协同）：新表 nextTable（2 倍），触发扩容的线程把迁移任务按 stride 分段，transferIndex 分配任务，其他写线程遇到 ForwardingNode 主动帮忙迁桶——扩容被多个线程摊平，极大缩短停顿。

JDK 7 vs JDK 8 对比表：

维度 JDK 7 JDK 8
锁机制 分段锁（Segment 继承 ReentrantLock） 桶头节点 synchronized + CAS 无锁路径
并发度 上限 = 段数（默认 16） 上限 = 桶数（随扩容增长）
数据结构 数组 + 链表（HashEntry） 数组 + 链表 + 红黑树（高冲突桶 O(log n)）
插入方式 头插（并发扩容有死循环隐患） 尾插
size() 可能锁全表 无锁分片计数（baseCount + CounterCell），近似值
扩容 段内独立 多线程协同扩容（helpTransfer）
读 无锁（volatile value） 完全无锁（Unsafe 原子读 + volatile val/next）
内存 Segment 结构开销大 更精简（单个 Node 数组 + 树节点按需建）
哈希 多次扰动 一次 (h ^ (h >>> 16))

为什么 JDK 8 敢用 synchronized 而不用 ReentrantLock：桶锁的临界区极小（几次比较 + 指针操作），而 synchronized 经锁升级/锁消除优化后，低竞争场景开销与 CAS 相当——JVM 层面的持续优化让”内置锁”重回性价比巅峰（与 3.5 节的结论呼应）。

生产要点：

  1. 读多写少、计数场景选 LongAdder 而非 CHM：CHM 的 size 是”无锁但需累加全部 CounterCell”，高频 size() 仍有开销；单纯计数用 LongAdder 更优。
  2. computeIfAbsent/compute 系列：这些方法在持锁期间执行函数，函数里千万别做耗时/阻塞/再进锁的操作（否则该桶锁被长期占用甚至死锁）。
  3. 弱一致性：迭代器/get 不保证看到操作瞬间的全局一致快照（size、get 都可能稍旧），对一致性要求极高的场景要谨慎。
  4. 不要存放 null key/value（与 HashMap 不同，CHM 从 JDK 7 起就禁止 null，原因：无法区分”值为 null”和”不存在”）。

9.3 CopyOnWriteArrayList：适用场景和代价

原理：底层 volatile Object[] array + ReentrantLock。

  • 写（add/remove/set）：加锁 → Arrays.copyOf 复制整个数组 → 在新数组上修改 → 替换 volatile 数组引用 → 解锁。写一次复制全量。
  • 读（get/iterator）：无锁，直接读 volatile 数组引用指向的数组。
  • 迭代器：持有的是创建时的数组快照——迭代期间原集合的修改完全不可见，也永不抛 ConcurrentModificationException（fail-safe）。

适用场景：读多写极少，且集合本身较小：

  • 监听器/观察者列表（注册多、触发多、变更少——事件总线常用）。
  • 配置/规则/白名单的低频全量替换（更新时直接 set 整个副本）。
  • 缓存 key 列表等”读频率 >> 写频率”的场景。

代价（面试必答三点）：

  1. 写代价 O(n)：每次写复制整个数组，元素多时开销极大，不适合频繁写。
  2. 内存瞬时翻倍：复制期间新旧数组并存，大集合 + 大对象会推高峰值内存（GC 压力）。
  3. 弱一致性：迭代器/读可能拿到旧数据；addIfAbsent 等在并发下也只是”尽力”去重。它解决的是”并发修改抛异常”问题，不是”读到最新值”问题。

选型对比：

场景 选型
读多写极少、集合小 CopyOnWriteArrayList
读多写多、需要互斥保证 Collections.synchronizedList（整表锁，简单可靠）
读多写多、想细粒度控制 ReentrantReadWriteLock 自封装
高并发、无顺序要求 换 ConcurrentLinkedQueue/ConcurrentHashMap 思路重新建模

考点速查

  • 三个问题：可见性（volatile 失效场景）→ 原子性（count++）→ 有序性（DCL）。
  • happens-before：程序次序、锁规则、volatile 规则、传递性，用例子推导 DCL 的安全性。
  • 锁升级：Mark Word 5 态 → 偏向（JDK 15 弃 / JDK 18 删）→ 轻量（CAS+自旋）→ 重量（monitor）；锁消除/粗化是 JIT 行为。
  • CAS 与 Atomic：lock cmpxchg 一条指令 → 自旋只适合短临界区 → ABA 用 StampedReference（版本号）→ 字段更新器省内存（Netty）→ 写多读少的统计用 LongAdder 分片计数。
  • AQS：state + CLH 变体（为什么双向 + park/unpark）→ 非公平先插队 CAS → 重入靠 state；Condition 是独立条件队列 + 释放锁；读写锁：state 高 16 位读 / 低 16 位写，可降级不可升级。
  • 线程池：execute 四步（先 core 后队列再 max 后拒绝）→ 无界队列的坑 → 拒绝策略背压原理 → shutdownNow 需任务配合中断 → submit 不 get 吞异常。
  • ThreadLocal：值在线程的 ThreadLocalMap（开放寻址）→ Entry key 弱引用 value 强引用 → 线程池不 remove 必泄漏/串线 → TTL 解决跨线程传递。
  • CompletableFuture：Future 局限 → thenCompose（扁平）vs thenCombine（并行合并）→ 默认 commonPool 会被阻塞任务占满 → Async 与非 Async 执行线程差异 → JDK 21 虚拟线程替代复杂编排。
  • 工具三兄弟：Latch 等事件、Barrier 线程互等可复用、Semaphore 资源许可。
  • CHM：JDK7 段锁（并发度=16）→ JDK8 桶锁 + CAS + 树化 + 协同扩容；读无锁靠 volatile + Unsafe 数组原子读。
  • COW：读无锁写复制，读多写极少才用，内存翻倍 + 弱一致。

系统设计面试：从问题拆解到方案落地

系统设计面试考的不是”你背过多少系统”，而是三件事：能不能把模糊需求拆成可讨论的设计决策、能不能说出每个选型的代价、能不能在追问下深入一层。本文按面试的能力维度组织：先讲解题思路（第 1 节），再讲三条设计主线——高性能、高可用、限流熔断降级（第 2~5 节），然后用 8 道真题演示框架（第 6 节），最后是 DDD 精华（第 7 节）与真题附录。

1. 系统设计面试的思路：不是背答案，而是学会拆解问题

系统设计面试和八股文面试最大的区别：没有标准答案。面试官想看的不是”你见过这道题”，而是面对一个没见过的系统时，你的思考路径和取舍能力。

1.1 解题五步法

第一步：需求澄清（5 分钟）

不要拿到题目就画架构图。先确认：

  • 功能需求：核心用例是什么？（如短链系统的核心是”长转短”和”重定向”，而不是”统计”）
  • 非功能需求（用数字对齐期望）：
    • QPS：读多还是写多？峰值多少？
    • 延迟：P99 要求多少？重定向链路 200ms 内是合理的，交易链路要求更高；
    • 数据量：总量多少、每天新增多少、保留多久；
    • 一致性：强一致还是最终一致？能否容忍短暂不一致；
    • 可用性：几个 9？成本随 9 的数量指数上升（见第 3 节）。
  • 明确边界：这个系统”不需要”做什么，同样加分。

第二步：容量估算（10 分钟）

面试不要求精确，但要会”数量级”估算，并给出依据：

  • 峰值 QPS ≈ 日请求量 / 86400 × 峰值系数（通常 3~10）；
  • 存储 = 单条数据大小 × 条数 × 副本数 × 保留时间，再考虑分库分表；
  • 带宽 = QPS × 单响应大小。

记住几个参照数，能帮你快速判断方案是否可行：

参照 量级
单台 MySQL 实例写 QPS ~1k
单台 MySQL 读 QPS（加缓存后） ~1 万+
单台 Redis QPS ~10 万
单台无状态应用服务器 QPS ~1 万（视业务）
100 万 QPS 大厂级，需要多级缓存 + 分片 + 异步化

决策依据：当估算出的 QPS 超过单机能力一个数量级时，就必须引入缓存、异步、分片——容量估算决定了架构选型，这是面试官判断你有没有经验的分水岭。

1.3 三条原则

  • 先说结论，再讲理由：每个选型都要能说出”为什么不用另一个方案”。
  • 大胆做假设：需求没给数字，就自己假设并明说（”假设 DAU 1000 万，峰值 QPS 约 5 万”），面试官要听的就是假设 + 推导过程。
  • 承认 trade-off：没有完美的方案，说出代价（如”用缓存换了强一致，但业务可接受最终一致”）是加分项。

面试官想要的回答：不是”我设计过一个短链系统”，而是”拿到任何题目，我都能先澄清需求、估算容量，再带着权衡理由做架构选型”——把面试题当成一次真实设计，而不是背诵。

2. 高性能设计：全链路找瓶颈，而不是堆缓存

高性能优化的本质：在有限的硬件成本下，让系统在单位时间内处理更多请求、并降低响应时间。原则是先定位瓶颈、再针对性优化、最后压测验证——从用户请求到数据落地的全链路分析，而不是盲目堆缓存。

2.1 各层优化概览：一条请求走过的每一层都有优化空间

层 手段 收益
客户端 CDN 就近分发、静态化（商品详情页）、压缩（gzip/br）、长连接、HTTP/2 把大部分流量挡在业务系统之外
网关 限流、缓存、参数校验、协议转换 保护后端，前置拦截
服务层 异步化、连接池、批量读写、合理的并发模型、无状态化 提升单机吞吐，便于水平扩展
存储层 索引、读写分离、分库分表、冷热分离、慢查询治理 降低延迟与负载，绝大多数系统的瓶颈所在

决策依据：优化顺序应该是 先缓存 → 再异步 → 再批量 → 再扩展 → 最后才是数据库与 JVM 调优，每一步都要有数据支撑，避免”优化了个寂寞”。

2.2 缓存：性价比最高的优化

多级缓存架构：数据按访问频率分层，越靠上越快、越贵、越小：

级别 代表 延迟 容量 说明
L1 本地缓存 Caffeine/Guava 纳秒级 单机 MB~GB 无网络开销，但有数据一致性问题
L2 分布式缓存 Redis 毫秒级 TB 级 多实例共享，命中率更高
L3 数据库 MySQL 10ms 级 无限 最后兜底

读请求先查 L1，miss 查 L2，再 miss 查 DB 并逐级回填——这就是”多级缓存”。

缓存更新模式对比：

模式 做法 优缺点
Cache Aside 读 miss 查库回填；写：先更新 DB，再删除缓存 主流方案，实现简单；DB 与缓存间有短暂不一致窗口
Read Through 缓存组件（旁路代理）负责回填 对业务无感，依赖中间件支持
Write Through 写 DB 的同时同步写缓存 强一致，但写放大、吞吐受限
Write Behind 先写缓存，异步批量落库 吞吐最高，但断电可能丢数据

决策依据：绝大多数业务选 Cache Aside + 先更新 DB 再删缓存。为什么”先删缓存再更新 DB”不行？——并发下旧数据可能被读回填，脏数据持续更久。为什么先更 DB 再删缓存仍有问题？——更新 DB 成功、删缓存失败时缓存里就是旧值，因此生产上常用延迟双删（删缓存 → 更新 DB → 延迟几百 ms 再删一次）或 Canal 订阅 binlog 异步删缓存兜底。

缓存三大经典问题：

  1. 穿透：查询一个不存在的 key，缓存不命中直接打到 DB，恶意请求可打垮 DB。
    • 方案：参数合法性校验；缓存空值（短 TTL，如 5 分钟）；布隆过滤器前置拦截（见第 6 节）。
  2. 击穿：某个热点 key 恰好过期，瞬间大量并发打到 DB。
    • 方案：互斥锁（重建缓存只允许一个请求回源，其余等待）；逻辑过期（key 永不过期，value 带过期时间，异步线程重建）；热点 key 永不过期 + 后台刷新。
  3. 雪崩：大量 key 在同一时间过期，DB 瞬间被压垮。
    • 方案：过期时间加随机数（打散过期时间）；多级缓存兜底（L1 兜 L2）；加熔断限流保护 DB（见第 4、5 节）。

2.3 服务层与存储层的其他手段

  • 异步化：发短信、写日志、积分、报表等非核心操作通过 MQ 削峰填谷，主链路只做”必要的事”——吞吐提升最立竿见影；
  • 批量与连接复用：连接池（Druid/HikariCP）、HTTP Keep-Alive、批量读写（multiGet、batch insert）——减少网络往返（RTT）是提升性能最直接的手段；
  • 索引优化：最左前缀、覆盖索引避免回表、避免函数与隐式类型转换导致索引失效；EXPLAIN 看 type/rows/Extra；
  • 读写分离：主写从读，注意主从延迟——一致性敏感场景强制走主库；
  • 分库分表：单表千万级以上按业务垂直拆分、按分片键水平拆分；同时要解决分布式 ID、跨分片分页聚合问题；
  • 网络与运行时：零拷贝（Kafka/Netty 的 sendfile）、protobuf 优于 JSON、线程池参数（CPU 密集 ≈ 核数 + 1，IO 密集 ≈ 核数 × 2）、避免频繁 Full GC；
  • 可观测与压测：APM（SkyWalking / Prometheus + Grafana）定位耗时分布，JMeter 压测找到系统水位线，再针对热点路径优化。

面试官想要的回答：把”高性能”拆成”缓存、异步、批量、扩展”四条主线，每条能讲清原理、适用场景和代价；遇到缓存必答三大问题（穿透/击穿/雪崩）与更新模式的选择依据——而不是背出一堆名词。

3. 高可用设计：用冗余换可靠性

高可用的核心思想只有一句话：用冗余换可靠性——任何单点都可能故障，那就让每个组件都有多个副本，并通过故障转移让系统在部分组件故障时依然对外提供服务。

3.1 冗余设计

  • 数据多副本：MySQL 主从/双主、Redis 主从 + Sentinel/Cluster、Kafka 多副本（副本因子默认 3），保证单节点故障不丢数据；
  • 多可用区（Multi-AZ）：同一地域内不同可用区间网络延迟低（毫秒级）但故障域隔离（机房断电、光缆中断不会同时影响两个 AZ）。数据库跨 AZ 部署可将可用性从 99.9% 提升到 99.99% 量级；
  • 多地域（Multi-Region）：异地多活（单元化部署），多个 Region 同时提供服务，故障时由 DNS/全局负载均衡把流量切到健康地域——最高级别的高可用，代价是数据双向同步与冲突解决的架构复杂度极高。

决策依据：从单机到多 AZ 到多 Region，可用性每升一个台阶，成本与复杂度都上一个数量级。先问”业务值不值得”，再谈架构。

3.2 故障转移

模式 做法 适用 代价
主备（Active-Passive） 备机不对外服务，主故障后由监控/仲裁切换：VIP 漂移（Keepalived）、DNS 切换、注册中心/etcd 选主 有状态的数据节点（MySQL、Redis） 备机闲置、切换有秒级到分钟级延迟
双活（Active-Active） 多个副本同时服务，负载均衡 + 注册中心自动摘除故障节点，对用户无感知 无状态服务（API 层标准做法） 需要处理状态共享与数据一致
集群选举 通过 Raft/Paxos 一致性协议选主（etcd、ZooKeeper、Kafka 控制器、Redis Cluster） 强一致的数据组件 实现复杂，依赖多数派（5 节点容忍 2 个故障）

决策依据：无状态用双活 + 自动摘除，有状态用主备/选主——不要给无状态服务设计 VIP 主备，那是把简单问题做复杂。

3.3 健康检查与优雅上下线

  • 注册中心（Nacos/Eureka）通过心跳续约感知实例存活；消费者本地缓存可用实例列表，调用失败时快速重试下一个实例；
  • 网关/Nginx 对后端做主动探活（/actuator/health、HTTP 状态码判断），连续失败自动摘除，恢复后自动加回；
  • 优雅上下线：服务下线前先通知注册中心、再摘流量（等待正在处理的请求完成），避免发布期间的 5xx。

3.4 服务治理：限流 / 熔断 / 降级 / 隔离

高可用不只是”多副本”，还包括故障下的体验保障：

  • 超时与重试：连接超时 < 读超时；重试要幂等、要限次数（配合指数退避）；
  • 限流：保护系统不被突发流量打垮（见第 4 节）；
  • 熔断：下游故障时快速失败，防止级联雪崩（见第 5 节）；
  • 降级：非核心功能返回兜底，保证核心链路可用（见第 5 节）；
  • 隔离：线程池隔离/信号量隔离（如 Hystrix 按服务划分线程池），把故障限制在局部。

3.5 可用性指标：N 个 9

可用性 = 正常运行时间 / 总时间，”几个 9”是业界量化的方式：

可用性 全年不可用时间 参考评价
99%（2 个 9） 87.6 小时 允许定期维护，内部系统常见
99.9%（3 个 9） 8.76 小时 大多数互联网业务的最低要求
99.99%（4 个 9） 52.6 分钟 核心交易系统水准，需要多副本 + 自动化运维
99.999%（5 个 9） 5.26 分钟 电信级，需要异地多活 + 极致的自动化

注意：每提高一个 9，成本可能增加一个数量级。高可用设计要结合业务价值确定目标，避免过度设计——能用 3 个 9 解决的，不必硬上 4 个 9。

面试官想要的回答：开口就是”冗余 + 故障转移 + 服务治理”三层框架；给每个方案配上”为什么”（如”有状态用选主，因为脑裂只能靠多数派解决”），并主动说明成本边界。

4. 限流：保护系统不被突发流量打垮

核心思想：在单位时间内，只允许特定数量的请求通过，超过阈值的请求将被拒绝、排队等待或降级处理。限流有三个层次的目的：保护自己（不被打垮）、保护下游（不把慢服务打到雪崩）、保证公平（不让大客户饿死小客户）。

4.1 四种经典算法

固定窗口

问题（临界问题）：窗口切换的瞬间，上一个窗口的最后一批请求和下一个窗口的第一批请求可以同时通过，实际流量达到 2 倍阈值。比如限制 1 分钟内 100 次，59.9s 时来了 100 次，60.0s 时又能进 100 次，同一秒内 200 次穿过限流。

滑动窗口计数

把窗口切成若干小格子（如 1 分钟切成 6 个 10 秒格），统计窗口内所有格子计数之和。实现简单、内存固定，精度取决于格子数，是网关限流的常见做法：

滑动日志算法

取舍：精确记录每个请求的时间，判定最准确（无临界问题）；但每个请求都要存时间戳，内存 O(窗口内请求数)，高 QPS 下不可接受——适合低 QPS、对精度要求高的场景。

漏桶算法

特点：不管请求来得多猛，出去的速率恒定为 1/leakRateMillis，完全平滑；代价是不能应对突发流量——即使桶空着，请求也只能匀速通过。适合保护下游（如慢的第三方接口、写入数据库的批处理）。

令牌桶算法

特点：匀速补充令牌 + 容量上限，既保证平均速率，又允许短时突发（桶里攒下的令牌一次花光）——突发是业务喜欢的（秒杀瞬间、首屏加载），所以 Guava RateLimiter、Sentinel、Spring Cloud Gateway 都基于令牌桶。对”突发上限”敏感的场景，把 capacity 调小即可。

算法对比总结

算法 流量平滑 允许突发 内存/复杂度 典型缺陷 适用
固定窗口 否 是（且有临界翻倍问题） O(1) 窗口边界 2 倍流量 简单场景、低精度
滑动窗口计数 否 是（上限精确） O(格子数) 精度取决于格子数 网关/Redis 主流
滑动日志 是（精确） 否 O(窗口内请求数) 高 QPS 内存爆炸 低 QPS 高精度
漏桶 是（恒定速率） 否 O(1) 无法应对突发 保护下游、削峰
令牌桶 是（匀速+突发上限） 是（受容量限制） O(1) 实现稍复杂 业界主流、通用

5. 熔断与降级：故障下的体验保障

降级与熔断的区别（高频题）：

  • 降级是主动的、有预案的：系统根据自身状态或业务策略，主动放弃部分非核心功能，保证核心链路可用。例如大促时临时关闭”商品评价””个性化推荐”等非核心接口。
  • 熔断是被动的、故障触发的：下游服务持续报错或超时时，自动切断对该服务的调用（快速失败），避免调用方线程被拖死，防止级联故障（雪崩）。

一句话总结：**降级是”我主动砍掉不重要的”，熔断是”它坏了，我先不调它了”**。两者通常配合使用——熔断触发后，调用方同时执行降级逻辑返回兜底数据。

5.1 降级策略分级

级别 策略 举例
功能降级 关闭/弱化非核心功能 大促关推荐、关评论、关报表；按用户等级/流量比例灰度降级（如 10% 用户降级、VIP 不降级）
读降级 保读弃写，写转异步 关闭下单/评论接口，只保留读能力；写请求进 MQ 异步处理（削峰降级）
页面降级 静态化兜底 详情页、列表页切换为服务端渲染的静态 HTML，页面可用但无个性化
数据降级 返回兜底数据 接口异常时返回预设值（推荐列表返回空、价格显示上次缓存值），客户端可容忍

降级的重要前提是预案与开关：通过配置中心（Apollo/Nacos）动态下发降级开关，秒级生效、无需发版——降级预案平时就要演练好，大促前必须过一遍。

5.2 断路器状态机

  • Closed（关闭/正常）：请求正常放行，在滑动窗口内统计失败率/失败次数；
  • Open（打开/熔断）：后续请求直接快速失败（不再发起真实调用），给下游恢复的时间；
  • Half-Open（半开）：熔断超时后放行少量探测请求（如 10% 流量）试探下游，成功率达到阈值则恢复 Closed，否则重新进入 Open——半开是”试探性恢复”，防止下游刚恢复就被流量打挂。

熔断参数怎么定（决策依据）：失败率阈值（默认 50%）、统计窗口（最近 N 个请求，如 100）、Open 等待时长（按下游恢复时间量级取，通常 10~30s）、最小调用数（如 10——样本太少时统计无意义）。参数没有标准答案，以压测和线上数据为准，核心原则是：宁可误熔断快速失败，不可让故障无限传播。

6.1 短链系统

需求：长 URL → 短 URL，访问短链 302 跳转到长链；可追加点击统计、自定义别名。非功能：读多写少（约 100:1），可用性 99.9%+。

容量估算：假设每天新增 1 亿条、每天 100 亿次访问 → 峰值读 QPS ≈ 100 亿/86400 × 3 ≈ 35 万，写 QPS ≈ 1 亿/86400 × 3 ≈ 3500。7 位 Base62 短码可表示 62⁷ ≈ 3.5 万亿，够用几十年；按每条 100B 计，日增约 10GB，需分库分表。

6.2 秒杀系统

需求：极短时间内大量用户抢购有限库存（如 10 万件、瞬间 50 万 QPS），不能超卖，活动可随时关闭——这是一个”平时闲置、瞬时爆炸”的系统。

容量估算：10 万人同时抢 → 峰值 QPS 数十万到百万级；订单总量受库存上限约束（最多 10 万单），读写比极度失衡。

核心架构：

关键技术决策：

  • 动静分离：商品页、秒杀页静态化上 CDN，业务系统只处理”点击秒杀”这一下；
  • 独立部署：秒杀单独一套系统/域名/容量规划，避免拖垮主站；
  • 限流：按用户维度限流（每人一次），网关层先挡一层（见第 4 节）；
  • 库存扣减：Redis + Lua 原子扣减（防超卖、QPS 十万级），绝不能靠 DB 行锁扣减（单库行锁只有千级 QPS）；
  • 异步下单：扣减成功的请求进 MQ，消费端批量落库——削峰的关键；
  • 幂等：用户重复提交只算一单（token + 订单号唯一键）。

6.3 实时排行榜

需求：统计话题/条目的实时热度并展示 Top N（如 Top 50），可查询指定条目排名，热度随时间衰减。非功能：秒级~分钟级更新，读多写少。

容量估算：100 万条目、10 万读 QPS；每次互动（点击/转发/评论）都是一次写。

核心架构：

关键技术决策：

  • 数据结构：Redis ZSET（有序集合）天生适合排行榜——更新 O(logN)，取 Top N 一步到位；
  • 实时 vs 准实时：每条事件实时改 score 会放大写压力，每 10 秒批量聚合一次；热度按”点击×1 + 转发×2 + 评论×3”加权并随时间衰减（半衰期公式）；
  • 多级缓存：Top 50 结果可在本地缓存 30 秒，进一步降读压力；
  • 条目过万级时：可按条目 hash 拆多个 ZSET，各自取 Top N 后归并（百万级内一般不需要）。

6.4 千万级消息推送系统

需求：向千万级用户推送通知（全量 + 定向），送达率高、可离线补推。

容量估算：1000 万用户、在线率 10% → 100 万长连接；每天推送 1 亿条，峰值推送 QPS 上万。

核心架构：

关键技术决策：

  • 长连接保活：心跳 + 自动重连，网关按连接数水平扩展（单机撑 10 万长连接是常见设计目标）；
  • 推拉结合：先推”有新消息”的通知，客户端再拉取——推保证即时性、拉保证可靠性（消息不丢）；
  • 全量推送：推送服务把任务投递到 MQ，各网关广播给本机连接——避免单个服务挨个发；
  • 幂等去重：消息带全局唯一 ID，客户端按 ID 去重；
  • 离线消息：存 Redis（短 TTL）或 DB，用户上线时补拉。

6.5 文件存储

需求：海量图片/视频的上传、下载、浏览，秒级加载。非功能：容量近乎无限、读写分离、多规格缩略图。

容量估算：1 亿用户，人均每天 1 张图（500KB）→ 日增约 50TB，年增 PB 级——自建文件服务器不可行，必须对象存储。

核心架构：

关键技术决策：

  • 对象存储 vs 自建：对象存储按量付费、内置多副本与跨地域容灾、容量无限；自建要自己解决扩容与多副本——PB 级数据没理由自建；
  • 直传 vs 转发：客户端拿签名 URL 直传对象存储，业务系统不经过流量，否则单台服务器的带宽就是瓶颈；
  • CDN 加速：图片读取全部走 CDN，源站只承受首次回源；
  • 多规格缩略图：上传后异步生成多规格图（小图/中图/WebP），列表页只拉小图——“朋友圈秒开”的关键。

6.6 电商库存防超卖

需求：有限库存（如 1000 件）面对大量并发下单，任何情况下都不能卖出超过库存的数量，下单成功即锁定库存。

容量估算：抢购瞬间 QPS 数万到数十万，但库存量小——热点集中在单条库存记录上，这是问题本质。

核心架构：

关键技术决策（方案演进三选一）：

  1. DB 乐观锁：UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock > 0——正确但行锁串行，单条记录只能扛千级 QPS；
  2. Redis + Lua 原子扣减：十万级 QPS、天然防超卖——抢购场景的标准答案；
  3. 预扣 vs 直接扣：预扣（下单即锁定）防止”下单成功却无货可发”，超时未支付再回补库存；
  4. 幂等与回滚：同一用户重复下单只扣一次；支付超时/取消自动释放库存。

6.7 分布式唯一 ID

需求：全局唯一、趋势递增（对数据库索引友好）、高性能（每毫秒大量生成）、高可用（不能依赖单点）。

容量估算：Snowflake 64 位 = 1 位符号 + 41 位时间戳（69 年）+ 10 位机器 ID（1024 台）+ 12 位序列（单机每毫秒 4096 个）——单机 400 万/秒，足够。

核心架构：无中心化依赖，各节点本地生成，不依赖网络——高可用天然满足。

关键技术决策（方案对比）：

方案 优点 缺点
DB 自增 简单、绝对有序 单点瓶颈，QPS 低
UUID 本地生成、无中心 无序、太长（36 字符），主键索引性能差
Redis INCR 高性能 依赖 Redis 可用性，跨集群不连续
Snowflake 趋势递增、无中心、高性能 时钟回拨问题
号段模式（Leaf） 批量取号，DB 压力极小 实现略复杂
  • 时钟回拨：Snowflake 最大的坑。处理策略：回拨幅度小时等待时间追平（预留 buffer）、记录上次生成时间戳拒绝回拨，必要时改用号段模式；
  • 机器 ID 分配：通过配置中心或 ZK 预分配，避免冲突；
  • Java 的 long 有符号，符号位必须固定为 0，否则生成的 ID 可能为负。

6.8 海量数据判重

需求：在集合中快速判断”是否存在”（URL 判重、缓存穿透拦截、推荐去重），允许极小的误判率（宁可误判为存在，不可漏判为不存在）。

容量估算：10 亿个元素、误判率 1% 时，每个元素约 9.6 bit → 约 1.2GB 内存；而把原始数据放进 Set 需要 10GB+。空间优势一个数量级，这是它的存在意义。

核心架构：

关键技术决策：

  • 原理：k 个哈希函数映射到位数组，查重时任一 bit 为 0 即确定不存在——**只可能误判”存在”，不可能误判”不存在”**；
  • 不支持删除：常规布隆过滤器删元素会把其他元素的 bit 清掉，需要计数布隆过滤器（每个 bit 升级为计数器）；
  • 与 DB 双检：误判的代价往往可接受——命中后回源 DB 确认一次，把”误判”变成”多一次查询”；
  • 分布式：Redis Bitmap 或分片内存实现，key 按业务维度区分。

面试官想要的回答：不是复述题目，而是展示框架——每条线都能说出”为什么这么设计、代价是什么”，并且能主动给系统找出瓶颈与扩展方向。

7. DDD 精华：面试中怎么讲 DDD

DDD（领域驱动设计）是系统设计面试里偏”软实力”的考点，考察你面对复杂业务时如何组织模型与边界。一分钟讲法：DDD 通过”战略设计”划分领域边界、通过”战术设计”在边界内构建模型，用统一语言消除歧义，用模型驱动对抗代码腐化——它解决的是业务复杂度，而不是技术复杂度。

7.1 战略设计：划分领域边界，明确核心问题

  • 领域（Domain）：业务问题的范围（如电商领域的”订单””支付”）。
  • 子域（Subdomain）：领域的细分，分为：
    • 核心子域（核心竞争力，如电商的”交易系统”）；
    • 支撑子域（辅助业务，如”物流跟踪”）；
    • 通用子域（通用功能，如”用户认证”）。
  • 限界上下文（Bounded Context）：
    • 领域模型的明确边界，每个上下文有独立的统一语言和模型；
    • 例如：电商中”订单上下文”和”库存上下文”的”商品”模型可能不同。
  • 上下文映射（Context Mapping）：描述限界上下文间的交互方式，如：
    • 合作关系（Partnership）：两个上下文协同完成目标；
    • 防腐层（Anti-Corruption Layer, ACL）：隔离外部上下文的不合理模型；
    • 开放主机服务（Open Host Service）：通过标准化协议（如 API）暴露功能。

7.2 战术设计：在限界上下文内构建领域模型

  • 实体（Entity）：具有唯一标识的对象（如 Order 通过 orderId 区分），标识不变、属性可变；
  • 值对象（Value Object）：通过属性值定义的无标识对象（如 Money 包含金额和货币类型），通常不可变（Immutable）；
  • 聚合（Aggregate）：一组关联对象的集合，聚合根（Aggregate Root）是唯一访问入口。例如 Order（聚合根）包含 OrderItem 和 Address，外部只能通过 Order 修改其内部对象——保证业务一致性（事务边界）；
  • 领域服务（Domain Service）：处理跨聚合或与外部交互的逻辑（如 PaymentService 处理支付），通常无状态；
  • 领域事件（Domain Event）：表示领域中发生的重要事件（如 OrderPaidEvent），用于解耦系统（事件驱动架构）；
  • 仓储（Repository）：封装聚合的持久化逻辑（如 OrderRepository），隔离领域模型与基础设施；
  • 工厂（Factory）：负责复杂对象的创建逻辑（如 OrderFactory 处理订单初始化）。

7.3 其他关键概念

  • 统一语言（Ubiquitous Language）：开发人员与业务专家共同定义的术语，贯穿代码、文档、对话——代码里、会议上、PR 描述里都用同一个词；
  • 分层架构（Layered Architecture）：用户界面层（Presentation）→ 应用层（Application，协调领域对象、处理用例流程）→ 领域层（Domain，核心业务逻辑）→ 基础设施层（Infrastructure，数据库、消息队列等技术实现）。依赖方向只能向内，领域层不依赖任何技术。

7.4 技术实现模式

  • CQRS（Command Query Responsibility Segregation）：分离读写模型，命令和查询可用不同数据源（如读走 ES、写走 MySQL）；
  • 事件溯源（Event Sourcing）：不存状态、只存事件，用事件流重建聚合状态——审计友好，但查询复杂、事件版本演进难；
  • 六边形架构（Hexagonal Architecture）：领域模型位于核心，通过端口/适配器与外部交互（”依赖倒置”的体现）。

7.5 核心思想与适用场景

核心思想总结：

  1. 聚焦核心领域，通过限界上下文划分边界；
  2. 模型驱动设计，统一语言消除歧义；
  3. 战术模式（实体/值对象/聚合等）实现高内聚、低耦合。

适用场景：

  • 业务逻辑复杂、需长期演化的系统（如金融、电商、SaaS 平台）；
  • 团队需与业务专家紧密协作的场景。

什么时候不该用（加分项）：简单 CRUD 系统、以技术复杂度为主的系统（如日志、监控）、团队不具备领域协作能力时，用 DDD 是过度设计——它引入的建模成本可能比它节省的复杂度还多。

面试官想要的回答：能用 1 分钟把”战略设计 vs 战术设计”讲清楚（战略划边界、战术建模型），能把 DDD 落到一个具体案例上（如订单聚合根 + 防腐层保护库存上下文），并主动说出”什么时候不该用 DDD”——最后一点是区分”会背”与”会选型”的关键。

分布式系统核心理论

Posted on 2025-07-26 In 分布式 Word count in article: 11k Reading time ≈ 41 mins.

本文围绕一条主线展开：分布式系统到底难在哪里，业界又是如何一步步解决这些难题的。内容覆盖核心理论（CAP、BASE、一致性协议、ZAB）与高频工程实践（分布式事务、分布式锁、分布式 ID）。服务治理（Nacos、Sentinel、Gateway 等）与 RPC 框架（Dubbo、gRPC）另有 Spring 面试专文，此处不展开。

1. 分布式系统的核心挑战

定义： 分布式系统是一组通过网络相连、相互协作完成任务的节点集合，对外呈现为单一系统。

单机系统中，内存与磁盘的状态是一致的、可靠的；分布式系统的麻烦在于，节点之间只能通过消息传递通信，而消息和节点本身都不可靠。具体来说有三个绕不开的挑战：

  1. 网络不可靠。 消息可能丢失、延迟任意时长、重复或乱序到达。更棘手的是，你无法精确区分”对方宕机了”和”网络延迟/分区了”——两者的外在表现完全相同。
  2. 节点故障。 进程可能崩溃、挂起（例如 JVM GC 停顿数十秒）、被网络隔离成孤岛。
  3. 时钟不可靠。 机器本地时钟会漂移，可能被 NTP 校准回拨，不能当作全局可信的时间源。这直接影响分布式 ID 生成、日志排序、超时判定。

这三个挑战决定了分布式系统必须回答一个根本问题：当部分节点失联时，系统怎么办？ 是继续响应请求（哪怕返回旧数据），还是宁可拒绝请求也要保证不返回错误数据？CAP 定理正是把这个权衡形式化的起点——理解 CAP，是理解后面所有内容（BASE、一致性协议、分布式事务、分布式锁）的前提。

2. CAP 定理

定义： CAP 定理由 Eric Brewer 于 2000 年提出、2002 年被证明：在存在网络分区（P）的情况下，分布式系统无法同时满足一致性（C）和可用性（A）。

  • 一致性（Consistency）： 所有节点在同一时刻看到的数据完全相同。一次写入完成后，任何节点上的任何读取都立即返回最新值（学术上对应线性一致性）。
  • 可用性（Availability）： 每个请求都能在合理时间内获得非错误响应，即使部分节点故障，系统仍能正常响应。
  • 分区容忍性（Partition Tolerance）： 网络分区（节点间通信中断、形成孤岛）发生时，系统仍能继续运行。

为什么不能同时满足：

网络分区是客观现实、无法消除，因此 P 是分布式系统的必选项，问题只在于分区发生时 C 和 A 怎么选。假设两个节点被分区隔离：

  • 向某一侧的节点发起写请求：如果该节点正常响应（满足 A），那么它无法与其他节点同步数据，读取时可能出现不一致（违反 C）；
  • 如果拒绝请求（满足 C），该侧的节点在分区期间不可用（违反 A）。

所以 CAP 的核心结论是：分区发生时，必须在 C 和 A 之间二选一。

两个常见误解：

  • CAP 不是”三个特性里随便选两个”。系统正常运行时 C 和 A 可以同时满足，只有分区发生时才需要取舍。
  • CAP 中的 C 是强一致（线性一致），不要与”最终一致””因果一致”等弱一致概念混为一谈。

实际系统中的取舍：

取向 代表系统 分区时的行为
CP ZooKeeper、etcd、HBase 牺牲可用性，拒绝请求以保证一致性
AP Eureka、Cassandra、CouchDB 继续响应，返回可能过期的数据
折中 MySQL / Redis 主从复制 “尽力而为”，从库可能读到旧数据，谈不上严格的分区容忍

选 CP 还是 AP，取决于业务：订单、账户、元数据（注册中心、配置中心）通常需要强一致；商品浏览、社交动态等场景可以容忍短暂的不一致，换取更高的可用性。

3. BASE 理论（Basically Available / Soft state / Eventually consistent）

定义： BASE 是基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent）的缩写，由 eBay 的 Dan Pritchett 提出。它是对 CAP 中 C 与 A 权衡的工程化回答：放弃强一致性，通过保证”最终一致”换取可用性和性能。

  • 基本可用（Basically Available）： 系统故障时保证核心功能可用，允许损失部分可用性。例如电商大促时，为保证购物流程稳定，部分用户被引导到降级页面或排队页面。
  • 软状态（Soft State）： 允许系统存在中间状态，即不同节点的数据副本之间存在同步延迟，该中间状态不影响系统整体可用性。
  • 最终一致性（Eventually Consistent）： 所有数据副本经过一段时间的同步后，最终能达到一致的状态。最终一致性还可细分为读己之写、单调读、因果一致等强度不同的变体，工程上按需选择。

ACID 与 BASE 的关系： ACID 强调强一致性，用于单库事务；BASE 强调最终一致性，用于跨节点的分布式场景。两者不是替代关系，而是结合使用——核心资金操作用 ACID，非核心链路（积分、通知、统计）用 BASE，这正是绝大多数互联网系统的真实形态。

4. 一致性协议

CAP 回答的是”分布式系统做不到什么”，接下来要回答”怎么做”：如何在存在故障的网络环境中，让一组节点就某个值达成一致？ 这就是共识（Consensus）问题，它的两个代表性解法是 Paxos 与 Raft。

Paxos

定义： Paxos 是 Leslie Lamport 于 1990 年提出（论文 1998 年发表）的共识算法，解决”在存在故障的网络环境中，多个节点如何就某个值达成一致”，是 Raft、ZAB 等后续共识算法的思想源头。

三种角色：

  • Proposer（提议者）： 提出提案，提案由提案编号 N 和提案值 V 组成；
  • Acceptor（接受者）： 对提案投票，只有被多数派（N/2 + 1）接受的提案才会被选定；
  • Learner（学习者）： 不参与投票，只学习已被选定的值，保证所有节点最终一致。

两阶段流程（Basic Paxos）：

  1. Prepare 阶段： Proposer 生成递增的提案编号 N，向所有 Acceptor 广播 Prepare(N)。Acceptor 收到后做出承诺：不再接受编号小于 N 的提案；若自己已接受过编号小于 N 的提案，则把其中编号最大的那条（编号 + 值）返回给 Proposer。
  2. Accept 阶段： Proposer 收到超过半数的 Promise 后，发出 Accept(N, V)。V 的取值规则：若 Promise 中带有已接受的提案，则 V 必须取其中编号最大的那个值（不能自选）；否则可自由指定。Acceptor 在不违反承诺的前提下接受提案，并把结果同步给 Learner。

为什么多数派能保证一致： 任意两个多数派集合必然有交集（两个 N/2 + 1 的集合交集至少为 1），Acceptor 通过”只认最大编号”的承诺保证：一旦某个值被选定，后续任何新的提议只能选定同一个值。这就是 Paxos 一致性的核心数学保证。

为什么说 Paxos 难懂： 工程化需要完整的 Multi-Paxos（多实例、日志复制、Leader 选举）和日志压缩；多个 Proposer 并发竞争时还会出现活锁（需要随机退避重试），实现极易出错。面试中讲清 Basic Paxos 的两阶段流程即可；若被追问”工程上为什么用 Raft 而不用 Paxos”——Raft 通过强领导者模型把共识问题分解为选举、复制、安全三个子问题，大幅降低了理解和实现难度。

Raft

定义： Raft 由 Diego Ongaro 于 2014 年提出，设计目标是”易理解“。它把共识问题拆解为三个相对独立的子问题：领导者选举（Leader Election）、日志复制（Log Replication）、安全性（Safety）。

领导者选举：

  • 节点有三种状态：Leader、Follower、Candidate，任何时刻系统最多只有一个 Leader；
  • 引入单调递增的任期（Term）概念：每次选举任期 +1，任期内 Leader 必须周期性发送心跳（Heartbeat）维持权威；
  • Follower 在随机化的选举超时（通常 150~300ms，随机化是为了避免多个节点同时发起选举、票数分散）内收不到心跳，就转为 Candidate 并发起选举：任期 +1、投自己一票、请求其他节点投票；获得多数派投票即成为新 Leader，其他节点收到新 Leader 的心跳后自动转为 Follower。

日志复制：

  • 客户端所有写请求统一交给 Leader，Leader 将操作追加为一条日志条目，并行广播 AppendEntries 给所有 Follower；
  • Follower 收到并落盘后返回 ACK；Leader 收到多数派确认后，将该条目标记为已提交（Committed）、应用到状态机，并通知 Follower 应用。

安全性（Safety）：

  • 选举限制： 只有日志”足够新”（任期号更大，或任期相同但日志更长）的 Candidate 才有资格当选，防止已提交的日志被新 Leader 覆盖；
  • 提交限制： Leader 只提交自己任期内的日志条目，上一任期的条目必须通过当前任期条目的间接提交来确认，从而保证”已提交的日志永不被覆盖”。

与 Paxos 的关系： Paxos 允许多个 Proposer 并发提议，协议更通用但更难实现；Raft 采用强领导者模型（Strong Leader）——所有写入都经 Leader、日志只能由 Leader 单向追加，用”问题分解 + 强领导”换来了可理解性，代价是写请求需要先转发给 Leader。两者本质相同：多数派确认 + 编号/任期单调递增。

为什么需要了解这些

共识算法不是纯理论，而是现代基础设施的地基：

  • etcd（Kubernetes 的存储后端）、TiKV（TiDB 的存储引擎）、Consul 均基于 Raft；
  • ZooKeeper 使用 ZAB（与 Paxos/Raft 同源的选主共识，详见第 5 章）；
  • MongoDB 复制集、MySQL 组复制（Group Replication）的选主也借鉴了 Raft 思想。

因此，”etcd 如何保证强一致”这类面试问题，本质上就是 Raft 日志复制 + 多数派确认机制。需要注意：共识算法保证的是”节点间的日志一致”，不等于业务层面的分布式事务——日志一致只是地基，跨业务资源的一致性仍需下一节的分布式事务机制来解决。

5. ZAB 协议（ZooKeeper Atomic Broadcast）

定义： ZAB（ZooKeeper Atomic Broadcast，ZooKeeper 原子广播）是 ZooKeeper 实现分布式一致性所用的协议，由 Yahoo! 团队在 ZooKeeper 的实现中提出（2008 年公开）。它与 Paxos 同源（作者之一正是 Paxos 提出者 Leslie Lamport 的学生），但目标不同：Paxos 解决”就某个值达成一致”，ZAB 解决”就一系列日志条目的顺序达成一致”——它面向主备复制（Primary-Backup）模型：集群中只有一个 Leader 接收写请求，把每个写操作包装成事务提案，按全局唯一的顺序（ZXID）广播给所有 Follower 并提交。正是 ZAB 让 ZooKeeper 对外表现为”全局有序的写入 + 单调递增的 ZXID”。

两种模式： 崩溃恢复模式（选举 / 发现 / 同步）与消息广播模式（广播）循环交替：Leader 正常任期走广播模式；Leader 崩溃 → 进入崩溃恢复（选新 Leader + 同步日志）→ 恢复完成后再次进入广播模式。ZAB 的核心保证是：广播模式下的事务不会丢、顺序不变；崩溃恢复后，新 Leader 一定持有所有已提交事务。

5.1 ZAB 的四个阶段

① Leader 选举（Election）

ZooKeeper 使用 Fast Leader Election（FLE）（快速选主，基于 Fast Paxos 思想，避免多轮往返）。每个参与选举的节点投出自己心中的”最优候选者”，获得多数派（N/2 + 1）选票的节点当选。

投票比较规则（ZXID 比较）：每张选票形如 (epoch, zxid, sid)（epoch 为投票轮次、zxid 为节点已知的最大事务 ID、sid 为节点编号），两票相比：

  1. 先比 epoch：大者优先（epoch 是逻辑时钟，越大代表越”新鲜”的轮次）；
  2. epoch 相等再比 zxid：大者优先（zxid 大 = 数据更新）；
  3. epoch、zxid 都相等再比 sid：大者优先（打破平局的兜底）。

ZXID 的结构：64 位，高 32 位是 epoch（任期编号），低 32 位是 counter（该任期内的顺序号）。每次选主后 epoch +1、counter 清零重新累加。所以面试答案”epoch 大者优先，相等则比较 counter“就是”数据更新的节点优先当选”的量化表达。

当选条件：节点收到多数派选票即当选；其余节点确认新 Leader 的 epoch 更新后放弃竞选、转为 Follower。选举期间集群不可用——ZooKeeper 是 CP 系统，选主窗口内拒绝读写，这正是”牺牲可用性保证一致性”的具体体现。

② 发现阶段（Discovery）

新 Leader 当选后，收敛所有 Follower 的日志进度：

  1. 新 Leader 向所有 Follower 广播自己的 epoch（newEpoch）；
  2. Follower 收到后返回自己记录的最大 ZXID，并把 Leader 的历史提案同步给它；
  3. 新 Leader 汇集反馈后，取多数集合内最新的 ZXID 作为恢复日志的起点，并确认该 epoch 已被多数节点接受。

发现阶段结束时：新 Leader 知道集群中日志最全的节点在哪、自己缺哪些事务。

③ 同步阶段（Synchronization）

新 Leader 把缺失的事务补发给所有 Follower：

  • 日志落后不多的 Follower：Leader 只发送差额部分（Leader 有、Follower 没有的提案），Follower 逐条追加到本地事务日志；
  • 差距过大/日志太旧的 Follower：Leader 直接做全量快照同步（把当前状态快照发给它），快照后再走差额同步；
  • 同步完成、收到多数节点确认后，Leader 才广播 COMMIT 提交已同步的事务，正式进入广播模式。

同步阶段是”崩溃恢复后不丢已提交事务”的关键：只要某个多数集合的节点持有某条事务，它就能在同步阶段被补全——与 Paxos/Raft 的”多数派决定已提交”一脉相承。

④ 广播阶段（Broadcast，两阶段提交的简化版）

Leader 正常任期内处理写请求的流程。相比 2PC 有两处简化：没有 Abort 指令（Leader 端校验通过就广播），且提交由 Leader 单方决定（收到多数派 Ack 即提交，无需询问每个节点”能否提交”）：

  1. Propose：写请求只能发给 Leader（客户端读写统一走 Leader——ZooKeeper 的线性一致严格保证在写路径上）；Leader 为它生成全局递增的事务 ID（ZXID），把提案 Propose(ZXID, data) 广播给所有 Follower；
  2. Ack：Follower 把提案写入本地事务日志（落盘）后返回 Ack(ZXID)——落盘才 Ack，这是崩溃恢复的前提；
  3. Commit：Leader 收到多数派 Ack 后广播 Commit(ZXID)（先提交自己），Follower 收到后把事务应用到内存数据树，并回复客户端成功。

两者同为”选主 + 日志复制”的共识协议，但设计取向不同：

6. 分布式事务

定义： 分布式事务是涉及多个独立资源（数据库、服务）的一个操作单元，这些资源分布在不同节点上。其目标与单机事务一致——要么全部成功提交，要么全部回滚（ACID 特性），但难点在于：单库事务由数据库引擎保证原子性，跨资源时没有全局协调者，且网络不可靠。

为什么需要： 微服务拆分、分库分表之后，一个业务操作必然横跨多个数据源。例如下单 = 订单库写订单 + 库存库扣库存 + 账户库扣余额，任何一个环节失败，都不能留下”订单已创建但库存没扣”的脏状态。

没有一种方案适用于所有场景，选择取决于对强一致性和性能的权衡。下面按”从强一致到最终一致”的顺序介绍主流方案。

6.1 两阶段提交（2PC）/ 三阶段提交（3PC）/ XA

2PC 流程： 引入一个独立的协调者，分两个阶段：

  1. 准备阶段： 协调者询问所有参与者”是否可以提交”。参与者执行事务操作（锁资源、写 Redo/Undo 日志），但不实际提交，向协调者投票（同意 / 中止）。
  2. 提交/回滚阶段： 若全部同意，协调者广播提交指令，参与者正式提交并释放资源；若任何一个中止或等待超时，协调者广播回滚指令，参与者利用 Undo 日志回滚并释放资源。

优点： 理论上提供强一致性，有标准实现（XA 协议）。

缺点：

  • 同步阻塞： 准备阶段参与者一直持有资源锁，直到收到第二阶段的指令，吞吐量低；
  • 协调者单点故障： 协调者崩溃时参与者可能永远持有锁，阻塞其他操作；
  • 脑裂风险： 提交阶段协调者广播提交后若部分参与者崩溃或失联，会出现部分提交、部分未提交的不一致，且一旦进入提交阶段就无法回滚，只能人工干预。

3PC 的改进： 针对 2PC”协调者故障导致参与者无限阻塞”和”提交阶段盲目执行”两个问题，3PC 增加了一个 CanCommit 询问阶段（先确认参与者是否都能提交，提前中止不可行的事务），并把提交阶段细分为 PreCommit（预提交）与 DoCommit（正式提交），且参与者引入超时机制：收不到协调者指令时不再无限等待，超时后自行决策（经典 3PC 中通常默认提交）。3PC 降低了”全员阻塞”的概率，但网络分区时参与者可能做出不同决定（一侧收到回滚、另一侧超时提交），仍然不能严格保证一致，因此工程上极少使用——实际选择通常是 2PC/XA，或干脆放弃强一致。

XA： X/Open 组织定义的分布式事务规范，由数据库厂商实现（MySQL、Oracle 等），流程与 2PC 对应，Java 侧由 JTA（如 Atomikos）支持。问题在于资源锁时间过长、性能差，互联网公司很少直接使用，仅在参与方少、强一致要求极高且性能不敏感的场景（如传统银行核心系统）使用。

6.2 TCC（Try / Confirm / Cancel）

定义： TCC 把”提交/回滚”从资源层提升到业务层：每个参与者实现三个业务接口，用预留资源 + 确认/取消代替数据库锁。

  • Try： 完成业务检查并预留资源（冻结库存、冻结余额），为最终操作做准备；
  • Confirm： 真正提交业务（扣减库存、扣款）。仅在 Try 全部成功后才执行，通常要求必然成功；
  • Cancel： 释放预留资源（解冻库存、恢复余额）。Try 成功后整体事务需要回滚时执行。

与 2PC 的对比：

维度 2PC / XA TCC
协调对象 资源层（数据库） 业务层（预留 + 确认/取消）
锁资源 锁数据库资源，阻塞 业务冻结，不锁资源
一致性 强一致 最终一致
性能 低 高
实现成本 低（数据库原生支持） 高（三个接口 + 幂等处理）

TCC 的三个经典坑：

  • 幂等： Confirm/Cancel 可能因网络重试被重复执行，必须幂等；
  • 空回滚： Try 因网络超时未到达，但 Cancel 已执行，需要识别并跳过（通常用事务控制表记录 Try 状态）；
  • 悬挂： Try 超时后 Cancel 先执行、Try 之后才到达，需要拒绝迟到的 Try。

TCC 适合对隔离性要求较高、需要防超卖的高并发场景（电商库存、金融账户）。

6.3 Saga

定义： Saga 把一个大事务拆成一串本地事务（T1, T2, …, Tn），每个本地事务对应一个补偿事务（C1, …, Cn）。执行到第 n 步失败时，反向执行 C(n-1), …, C1 回滚已完成的操作。

两种协调方式（中文资料里两者常混译为”编排”，面试时用”中心化 / 去中心化”区分即可）：

  • 编排（Orchestration）： 有一个中心协调器（Saga 状态机）按顺序调用各服务，失败时反向触发补偿。优点：流程集中、可跟踪；缺点：引入中心节点。
  • 事件编排（Choreography）： 没有中心协调者，每个服务执行完后发布事件，下一个服务监听事件并执行自己的操作或补偿操作。优点：松耦合；缺点：流程散落在事件中，难以追踪和排障。

两种恢复模式：

  • 向前恢复： 某步失败就重试该步（适用于可重试的临时错误）；
  • 向后恢复： 某步失败就触发反向补偿（适用于不可重试的业务错误）。

Saga 的短板： 无隔离性——中间状态对其他事务可见（例如订单已创建但支付未完成，其他事务能看到”未支付订单”）。解决思路是业务上容忍，或对关键资源做预留（与 TCC 思想结合）。

6.4 本地消息表 + 最大努力通知

本地消息表（事务发件箱）：

  • 原理： 发起方在同一个本地事务里写业务数据 + 写消息表。本地事务保证”业务成功 = 消息一定入库”，两者原子。之后由独立的消息转发器（定时任务扫描消息表）把消息投递到 MQ，消费者收到后执行并幂等消费。
  • 为什么可靠： 本地事务保证业务操作与消息入库存取的原子性；MQ 投递失败可重试（至少投递一次）；消费者幂等应对重复投递。这是”基于可靠消息的最终一致性”的标准实现，业界大量使用（也有 RocketMQ 事务消息等中间件原生方案）。

最大努力通知：

  • 原理： 不引入 MQ，发起方在本地事务记录”待通知”状态，通过定时任务 + 指数退避重试反复调用接收方接口（同步接口），直到成功；达到最大重试次数仍失败，则记录失败明细，进入人工/对账兜底。
  • 与本地消息表的区别： 本地消息表依赖 MQ 解耦、异步投递；最大努力通知是直接调用 + 尽力重试，实现更简单，但通知成功与否”尽力而为”——必须配套对账与人工补偿。
  • 适用场景： 支付结果通知、短信/邮件发送这类”错过可接受、但绝不能重复出错”的低频通知场景。

6.5 选型决策树

按两个问题决策：对一致性的要求有多强？对性能的要求有多高？

补充一句 Seata：国产开源分布式事务框架，提供 AT（自动生成回滚镜像、业务无感的 2PC 改良）、TCC、Saga 三种模式，面试中常被作为”2PC 的工程化实现”提及（详见 6.6 节）。

6.6 Seata 实战

定义： Seata（Simple Extensible Autonomous Transaction Architecture）是阿里开源的分布式事务框架，提供 AT、TCC、Saga 三种模式，覆盖”强一致 → 最终一致”的选型谱系（6.5 决策树里”事务内大量 DB 读写、已有框架 → Seata AT 模式”说的就是它）。

Seata 架构：TC / TM / RM 三角色

角色 全称 职责 部署位置
TC Transaction Coordinator，事务协调器 独立部署的 Server：维护全局事务与分支事务的状态，驱动全局提交/回滚，管理全局锁 独立服务（seata-server）
TM Transaction Manager，事务管理器 业务侧发起方：开启全局事务、提交/回滚全局事务 业务应用（SDK）
RM Resource Manager，资源管理器 业务侧参与方：管理分支事务（本地事务 + undo_log）、向 TC 注册分支、汇报状态 业务应用（SDK）

XID 传播（全局事务的唯一标识）：TM 开启全局事务时生成全局唯一 XID（如 10.1.1.1:8091:123456789），必须沿调用链传到所有参与方——通过 RPC 上下文透传（Dubbo 的 attachment / Spring Cloud 的 header，Seata 的 RootContext 保存，集成层自动注入）。XID 传不到，后续分支事务就无法关联到全局事务，这是 Seata 集成排障的第一排查点。

整体流程：TM 开启全局事务（生成 XID）→ 各 RM 执行本地事务并注册分支（branchId）→ 全部成功后 TM 向 TC 提交 → TC 驱动所有分支提交；任一分支失败 → TM 向 TC 回滚 → TC 通知各 RM 回滚。

AT 模式原理

AT（Auto Transaction）模式的魔法：业务代码无侵入（一个 @GlobalTransactional 注解），回滚镜像由框架自动生成。核心是 undo_log 前后镜像 + 全局锁：

一阶段（业务本地事务内）：

  1. 执行业务 SQL（框架通过拦截器拿到执行计划，自动生成回滚 SQL）；
  2. 写 undo_log：执行前拍 beforeImage（受影响行的完整数据），执行后拍 afterImage，与分支事务一起写在同一本地事务里（undo_log 与业务数据同库同事务，保证镜像与数据一致）；
  3. 本地事务提交（RM 无需持锁等待二阶段——这是 AT 相比 XA 吞吐高的根本：锁只存在于本地事务内，事务提交就释放本地锁，不需要全局资源锁）。

二阶段提交（全局成功）：TC 通知 RM 提交，RM 异步删除 undo_log——全局事务已成功，镜像不再需要，业务数据就是最终状态。

二阶段回滚（全局失败）：

  1. RM 根据 undo_log 的 beforeImage 生成反向 SQL（UPDATE 改回原值 / DELETE 插回原行 / INSERT 删除原行）；
  2. 执行回滚前做脏写校验：比较当前数据库数据与 afterImage，一致（期间没人改过）→ 执行反向 SQL，回滚成功，删除 undo_log；
  3. 脏写校验失败（当前数据 ≠ afterImage，说明回滚窗口内其他事务改过该行）→ 不能盲目回滚（会覆盖别人的修改），抛异常上报 TC，走人工/提示处理。

全局锁与死锁检测：两个全局事务并发改同一行时，若各自都提交了本地事务，回滚时就会互相覆盖——所以 AT 在写之前要先获取全局锁（Seata Server 侧维护的”行级锁”，key 为 资源ID + 表名 + 主键）：事务 A 写行 X 前向 TC 申请全局锁 X，事务 B 再写 X 时拿不到全局锁 → 等待（默认重试 30 次、间隔 10ms）→ 超时抛异常回滚。本地锁与全局锁的协同：先拿本地锁，再等全局锁，等不到就释放本地锁回滚——避免两个事务互相持本地锁等全局锁的全局死锁。

前提要求：业务表必须有主键（回滚 SQL 按主键定位）；undo_log 表（undo_log）需建在每个参与的数据源；全局事务内的方法不能跨异步线程（XID 默认只在调用链传播，异步任务要手动传递）。

TCC 模式（业务实现 Try / Confirm / Cancel）

TCC 把”提交/回滚”从资源层提升到业务层：Try 预留资源 → Confirm 真正提交 → Cancel 释放预留。相比 AT 的自动镜像，TCC 的补偿逻辑由业务自己写，控制力更强、不依赖 undo_log，适合业务校验复杂、资源类型不支持镜像的场景。

TCC 的两个经典问题（框架如何解决）：

  1. 空回滚（Cancel 比 Try 先到达）：Try 请求因网络超时/丢失没执行成功，但 TC 已判定全局失败，Cancel 被调用——此时没有可回滚的预留资源。Seata 的处理：branchId 的注册即”Try 已执行”的凭证——Cancel 执行前检查 TC 侧分支事务注册记录：分支未注册（Try 没执行成功）→ 直接返回成功（空回滚，什么都不做），不执行任何补偿逻辑。
  2. 悬挂（Try 在 Cancel 之后到达）：Try 超时后 Cancel 先执行完（空回滚），迟到的 Try 又执行了冻结——资源被永久挂起。Seata 的处理：Try 执行前先检查该分支是否已经 Cancel 过（TC 侧保存了 Cancel 记录）——已 Cancel 则拒绝执行 Try（直接返回失败），保证”Cancel 之后绝不会有 Try 生效”。

一句话：**空回滚防的是”没 Try 却 Cancel”，悬挂防的是”已 Cancel 还 Try”**——两者都靠 TC 侧的分支状态记录做检查，所以分支状态记录是框架的职责，业务只管保证 Confirm/Cancel 幂等。

AT vs TCC vs Saga 选型表

维度 AT TCC Saga
侵入性 低（注解 + 自动镜像，业务 SQL 不动） 高（三个接口全业务实现） 中（拆本地事务 + 补偿，协调模式自选）
隔离性 较强（全局写锁防脏写；默认读未提交，可开启全局读锁升级） 中（预留资源提供一定隔离） 弱（中间状态对外可见）

性能 高（本地事务即提交，无长锁） 高（业务冻结，无长锁） 高（纯本地事务串行）
适用场景 大量 DB 读写、业务无侵入诉求、数据一致性敏感（有全局锁） 高并发、资源可预留（库存冻结、余额冻结）、隔离性要求高 长流程、跨系统异步补偿（订单/配送/对账）

面试怎么答：先讲三角色与 XID 传播（架构题必答）；AT 模式讲透”一阶段本地事务 + undo_log 镜像、二阶段回滚反向 SQL + 脏写校验、全局锁防并发回滚错乱”四件事；TCC 讲”预留/确认/释放 + 空回滚与悬挂怎么被框架解决”；最后落到选型——**”业务无侵入、一致性敏感选 AT；资源可冻结、隔离要求高选 TCC；长流程异步补偿选 Saga”**。

7. 分布式锁

定义： 分布式锁是跨进程（跨 JVM、跨机器）的互斥机制，保证多个实例对同一共享资源的访问互斥。

为什么需要： 单机时代 synchronized、ReentrantLock 基于 JVM 内存即可互斥；微服务多实例部署后，锁对象分散在不同 JVM 中，必须借助外部共享存储（Redis、ZooKeeper、数据库）实现跨进程互斥。典型场景：分布式定时任务”同一时刻只有一个实例执行”、库存扣减防超卖、缓存重建防击穿。

一个合格的分布式锁需要满足：

  1. 互斥性： 任何时刻只有一个客户端持有锁（核心要求）；
  2. 防死锁： 持锁客户端崩溃后锁必须自动释放（加锁时设置过期时间 / 使用临时节点）；
  3. 防误删： 只能释放自己持有的锁（value 用唯一标识 + Lua 校验）；
  4. 可重入（可选）： 同一线程可重复获取（Redisson 用 Hash 结构实现）；
  5. 容错性： 锁服务本身高可用，锁失效窗口尽量小。

第三步，Redlock 及其争议。 Redis 主从架构下，主节点宕机时未同步的锁会丢失，可能出现两个客户端同时持锁。Redlock 的思路：向 5 个独立 Redis 节点依次加锁，超过 3 个成功且总耗时小于锁过期时间才算成功，释放时向所有节点释放。但 Martin Kleppmann（《数据密集型应用系统设计》作者）在 2016 年发文反驳（《How to do distributed locking》）：GC 停顿导致锁过期后线程仍继续执行、系统时钟跳跃都会破坏互斥性，Redlock 只是”尽力而为”而非严格安全。业界主流结论：绝大多数业务场景用单 Redis + 看门狗续期即可，Redlock 复杂度高、收益低，无需过度设计。

7.2 基于 ZooKeeper（临时顺序节点）

利用 临时顺序节点（EPHEMERAL_SEQUENTIAL）+ Watch 监听：

  1. 客户端在锁目录下创建临时顺序节点 /lock/lock_0001；
  2. 判断自己是否是最小序号节点——是则获得锁；
  3. 否则 Watch 监听前一个节点（如 lock_0000）的删除事件，前一个节点删除后唤醒再次检查；
  4. 释放锁即删除自己的节点；客户端异常断开时临时节点自动消失，天然防死锁，无需过期时间。

优点： 无锁丢失问题（ZK 本身由 ZAB 多数派保证强一致）、只监听前一个节点不会惊群。缺点： 性能不如 Redis，且依赖 ZK 集群本身。

8. 分布式 ID

需求： 分库分表、微服务场景下，单库自增 ID 无法保证多实例全局唯一。一个合格的分布式 ID 方案需要满足：全局唯一、趋势递增（对 B+ 树索引友好，避免随机插入造成页分裂）、高性能低延迟、高可用（生成服务不可用会拖垮整个写入链路），且 ID 尽量短（减少存储和索引开销）。

8.1 方案对比

1. UUID——最简单但最不推荐

  • 优点：本地生成、无网络开销、性能极高、绝对唯一。
  • 缺点：无序（B+ 树随机插入导致页分裂，索引性能差）；36 字符过长（存储翻倍）；无业务含义、无法排序。
  • 适用：对索引不敏感的场景（日志 ID、消息 ID、链路追踪 ID）。

2. 数据库自增 ID——单点瓶颈

依赖 AUTO_INCREMENT，简单可靠，但单库写性能有上限，主从切换、数据迁移时容易冲突。优化手段：双主互相错开步长（一台 auto_increment_increment=2, offset=1，另一台 offset=2）可支撑两倍写量，但扩展性有限——每增加一台机器都要重配步长。

3. 号段模式（Segment）——批量取号，内存发放

核心思想：数据库表 id_alloc(biz_tag, max_id, step) 维护各业务的最大 ID，每次从库中取一段号段（如 1000 个）缓存在本地内存逐号发放，用尽后再取下一段，数据库只承担低频的”取段”请求：

  • 优点：大幅降低数据库压力（1000 个 ID 只访问一次 DB），性能高，ID 趋势递增，实现简单可靠；
  • 缺点：号段未用完时重启会浪费一段；多实例同时取段可能产生跨实例乱序（整体仍趋势递增）；
  • 工程化：美团 Leaf-segment 即此模式，并增加了双 buffer（当前段 + 预取段）消除取段间隙的停顿。

4. 雪花算法（Snowflake）——最主流方案

64 位 Long：1 位符号位（0）+ 41 位毫秒时间戳（可用约 69 年）+ 10 位机器 ID（5 位机房 + 5 位机器，支持 1024 台）+ 12 位序列号（单机每毫秒 4096 个）。单机 QPS 可达 409 万/秒，趋势递增，本地生成无网络开销：

时钟回拨问题（最大坑）： 生成依赖服务器本地时钟，若 NTP 校准导致时钟回拨，可能生成重复 ID。常见解法：

  • 短回拨（小于阈值）： 线程自旋等待，直到时钟追平（百度 UidGenerator 的做法）；
  • 回拨较大： 拒绝服务或直接报错，等待人工处理；
  • 彻底规避： 用 ZK/Redis 集中分配 workerId（Leaf-snowflake 的做法），或改用号段模式兜底。

5. 业界方案

  • 美团 Leaf： 同时实现号段模式（Leaf-segment）和雪花模式（Leaf-snowflake），支持双模式动态切换，用 ZK 管理 workerId；
  • 百度 UidGenerator： 雪花 + 自定义位分配 + RingBuffer 缓存预生成；
  • 滴滴 Tinyid： 号段模式改进。

担心时钟回拨、求稳 号段模式更稳妥

9. 总结：分布式系统的设计范式

把全文串起来看，分布式系统的解法有一条清晰的脉络：

  1. 起点是物理现实： 网络不可靠、节点会故障、时钟不可信，这是所有问题的根源。
  2. CAP 划定边界： 分区不可避免，必须在一致性和可用性之间取舍；BASE 给出工程取向——大多数业务用最终一致性换取可用性和性能。
  3. 一致性协议解决”单值共识”： Paxos、Raft 与 ZAB 用”多数派 + 单调编号/任期/ZXID”让节点就日志达成一致，这是 etcd、ZooKeeper、TiKV 等地基。
  4. 分布式事务解决”跨业务资源的一致”： 从 2PC（强一致、代价高）到 Seata AT/TCC/Saga/消息（最终一致、轻量），本质是把”全局原子性”拆成”本地原子 + 异步补偿”。
  5. 分布式锁是”小号的共识”： 本质是在共享存储上实现互斥——Redis 快但弱，ZK 强但慢。
  6. 分布式 ID 是”单点问题的分布式化”： 从数据库自增（单点）到号段（低频访问数据库）到雪花（本地生成），层层去除单点依赖。

贯穿其中的设计范式可以归纳为四条：

  • 先问业务要什么，再选方案： 强一致不是默认选项，而是有代价的选项；对一致性和延迟的真实要求决定一切选型。
  • 能用异步就不用同步，能用最终一致就不用强一致： 尽量把全局协调拆成”本地事务 + 消息/补偿”，这是 BASE 思想的工程化。
  • 幂等是一切的基石： 消息重投、补偿重试、通知重发，都依赖接收方的幂等；不解决幂等，任何最终一致性方案都会出问题。
  • 工程上规避理论难题： 理论给出安全边界（多数派、单调编号），工程上则尽量把难题挡在门外——预分配 workerId 规避时钟回拨、看门狗续期规避锁过期，复杂度能不上就不上。

回答相关面试题时，按”定义 → 为什么 → 怎么做 → 代价“的结构组织，最后落到”根据业务要求取舍“的结论上，就能把这条脉络完整地呈现出来。

3.4 循环依赖与三级缓存

3.4.1 什么是循环依赖

循环依赖指两个及以上 Bean 互相持有对方的引用，形成闭环。例如 A 依赖 B、B 又依赖 A：

创建 A 需要先注入 B，创建 B 又需要注入 A，若容器不做特殊处理，就会陷入”先有鸡还是先有蛋”的死循环。Spring 对单例 Bean 的字段/Setter 注入（属性注入）循环依赖有解，方案就是三级缓存；而构造器注入、Prototype 作用域的循环依赖则无法解决（详见 3.5）。

3.4.2 三级缓存的结构

三级缓存的容器定义在 DefaultSingletonBeanRegistry 中：

级别 字段 存储内容 作用
一级 singletonObjects 走完完整生命周期（实例化→注入→初始化）的 Bean 最终对外提供的”成品”，getBean 的最终来源
二级 earlySingletonObjects 已从三级缓存取出并确定要暴露的早期引用 防止同一 Bean 的 ObjectFactory 被重复执行（重复创建代理）
三级 singletonFactories 惰性执行的 ObjectFactory 延迟决策：真正发生循环依赖时才调用，决定返回原始对象还是 AOP 代理

查询时按 一级 → 二级 → 三级 逐级查找；从三级取到早期引用后，会移入二级缓存并移除三级缓存项，保证同一 Bean 的早期引用只创建一次。

3.4.3 为什么需要三级缓存（核心考点）

常见的追问：二级缓存看起来就够了，为什么一定要三级？关键在于 AOP。

代理对象是在 initializeBean() 的 BeanPostProcessor 后置处理阶段（AbstractAutoProxyCreator.postProcessAfterInitialization）才创建的，而循环依赖发生时，B 在 A 的属性注入阶段就必须要拿到 A 的引用——此时 A 还不知道自己是否会被代理。

  • 若只有一级缓存（实例化后直接暴露裸对象）：B 拿到的是裸 A，而最终对外的是代理 A，注入的引用与最终 Bean 不一致，AOP 全部失效。
  • 若只有二级缓存（实例化后把”早期引用”提前放进二级）：为了拿到代理，就只能无条件地对所有 Bean 提前执行代理逻辑。这不仅让没有循环依赖的 Bean 白白被提前代理，还会与 initializeBean 阶段的正常代理逻辑重复，造成双重代理或触发 doCreateBean 末尾的 “Bean has been injected into other beans in its raw version… but has eventually been wrapped” 异常。

三级缓存用 ObjectFactory 把”是否生成代理”的决策推迟到真正需要时：只有确实发生循环依赖、确实需要提前暴露引用时，才执行 getEarlyBeanReference()，通过 SmartInstantiationAwareBeanPostProcessor 判断该 Bean 是否命中切点——命中则返回代理，未命中返回原始对象：

AbstractAutoProxyCreator（SmartInstantiationAwareBeanPostProcessor 的实现）内部还会通过 earlyProxyReferences 记住”已提前代理”的 Bean，使 postProcessAfterInitialization 阶段不会重复创建代理——无论走早期路径还是正常路径，代理都只创建一次，所有引用拿到的是同一个代理实例。

维度 JDK 动态代理 CGLIB

创建性能 创建快 创建较慢（需生成字节码）
调用性能 JDK 17+ 已基本追平 长期运行下表现稳定

Spring 的选择逻辑（DefaultAopProxyFactory）：

规则一句话：目标是接口或已有代理 → JDK；否则只要 proxyTargetClass=true 或无接口 → CGLIB。

为什么 Spring Boot 2.x 起默认 CGLIB（版本考点）：

  • Spring Boot 1.x：spring.aop.proxy-target-class 默认 false，有接口就用 JDK 代理。
  • Spring Boot 2.0 起：AopAutoConfiguration 中的 CglibAutoProxyConfiguration 通过 @EnableAspectJAutoProxy(proxyTargetClass = true) 把默认改为 CGLIB，官方动机是：
    1. 避免类型转换错误：JDK 代理只能赋给接口引用，@Autowired UserServiceImpl userService（注入实现类类型）在有接口且用 JDK 代理时直接启动失败；
    2. 现代代码普遍不为每个类写接口，CGLIB 无需接口即可代理；
    3. @Configuration 的 CGLIB 增强（full 模式）等场景需要类级代理。
  • 注意：Spring Framework 单独使用（不经过 Boot）默认仍是有接口走 JDK 代理；Spring Boot 3.x 延续 2.x 的 CGLIB 默认。

4.3 代理的创建时机与流程

流程：wrapIfNecessary → findEligibleAdvisors（把切面里的 @Pointcut 与目标方法匹配）→ createProxy（ProxyFactory 按 4.2 的规则选 JDK/CGLIB）。

与循环依赖的联动（呼应 3.4）：正常 Bean 在 postProcessAfterInitialization 创建代理；发生循环依赖的 Bean 则在 getEarlyBeanReference（SmartInstantiationAwareBeanPostProcessor）提前创建，且通过 earlyProxyReferences 保证不重复创建——两次时机只生效一次，这是三级缓存设计的直接动机。

另外要记住：**@Transactional、@Async 走的是同一套代理机制**（只是不同 Advisor），所以它们的失效场景与 AOP 完全一致（见 4.4 和 7.4）。

失效场景逐个展开

  1. 同类内部自调用（最高频）：

解决方式（三选一）：

  • 拆 Bean：把 updateStock 移到另一个 Service 中，跨 Bean 调用必然走代理；
  • 注入自身代理：@Autowired @Lazy private OrderService self; 然后 self.updateStock(order)（@Lazy 避免启动期循环依赖）；
  • AopContext.currentProxy()：((OrderService) AopContext.currentProxy()).updateStock(order)，需要 @EnableAspectJAutoProxy(exposeProxy = true)。
  1. private 方法：JDK 代理根本拦截不到；CGLIB 生成的子类也无法覆写 private 方法——静默失效。

  3. 切点表达式写错：execution 语法错误或包名不匹配时不会报错，只是不织入——排查时先确认切点能匹配上。

代理对象拦截到方法调用后，不是”一个通知”直接执行，而是把命中的通知组装成一条责任链，逐个放行。三个关键类：DefaultAdvisorChainFactory（组装链）、ReflectiveMethodInvocation（链的执行器）、各 MethodInterceptor（链上的节点）。

③ 各类通知在链中的位置（同一切面的内部顺序固定）：

  • @Before：目标方法执行前，执行完立即放行到链尾；
  • @Around：包裹整条链，pjp.proceed() 之前的代码相当于前置、之后的相当于后置；
  • @AfterReturning：目标方法正常返回后执行（拿得到返回值）；
  • @AfterThrowing：目标方法抛异常时执行（拿得到异常）；
  • @After：无论正常还是异常都执行（finally 语义）。

④ @Order 对链顺序的影响：多个切面通过 @Order(n)（或实现 Ordered）排序，数字小的先进入链——体现在执行顺序上：前置逻辑先执行、后置逻辑后执行（看上面的洋葱图：Order=1 的 @Before 在最外层，Order=1 的 @After 也在最外层）。所以”统计耗时的切面”通常用 @Order(0)，让它包在最外层，计时才准确。

本节要解决什么问题：一个 HTTP 请求从 Tomcat 进来，到 Controller 方法执行、再到响应返回，中间经过哪些组件、每个组件干什么。

5.1 核心组件与职责

5.2 一次请求的完整旅程

核心调度代码在 DispatcherServlet.doDispatch()：

完整九步：

  1. 请求进入 Servlet 容器（Tomcat）→ 经过 Filter 链（见第 9 节）→ 到达 DispatcherServlet。
  2. getHandler：按 HandlerMapping 链逐个尝试匹配，RequestMappingHandlerMapping 根据 @RequestMapping 注册的路由表返回 HandlerExecutionChain。
  3. getHandlerAdapter：为 Handler 找到适配器（RequestMappingHandlerAdapter）。
  4. applyPreHandle：执行拦截器链的 preHandle，任一返回 false 则请求在此中断。
  5. ha.handle：适配器调用 Controller 方法——HandlerMethodArgumentResolver 链解析参数（@RequestBody 由 HttpMessageConverter 把 JSON 反序列化为对象，@PathVariable/@RequestParam 做数据绑定与类型转换），方法执行后由 HandlerMethodReturnValueHandler 处理返回值。
  6. 返回 ModelAndView：有 @ResponseBody（或 @RestController）时返回 null 的 ModelAndView，返回值直接由 HttpMessageConverter（Jackson 的 MappingJackson2HttpMessageConverter）序列化写入响应体。
  7. applyPostHandle：拦截器 postHandle（视图渲染前回调）。
  8. processDispatchResult：若 Handler 抛异常，交给 HandlerExceptionResolver（@ExceptionHandler 在此生效）；否则进入视图解析——ViewResolver 把逻辑视图名解析为 View，渲染后输出。
  9. afterCompletion（拦截器）：请求处理完成后的清理回调，随后响应返回客户端。

  1. 启动 main 方法，加载标注 @SpringBootApplication 的主类。
  2. @EnableAutoConfiguration 激活自动装配。
  3. 通过 @Import 引入 AutoConfigurationImportSelector（DeferredImportSelector，延迟到用户配置之后执行）。
  4. 读取 .imports 文件（3.x）/ spring.factories（2.6 及以前）获取所有候选自动配置类。
  5. 用 spring-autoconfigure-metadata.properties 快速过滤，再逐类评估 @Conditional。
  6. 满足条件的配置类中定义的 Bean 被注册到容器，应用开箱即用。

7.2 事务传播行为

传播行为 行为描述 典型场景
REQUIRED（默认） 有事务则加入，无则新建 绝大多数业务方法
REQUIRES_NEW 挂起当前事务，新建独立事务；内层提交/回滚互不影响 操作日志、审计、消息发送——不能随主事务回滚
NESTED 嵌套事务：基于保存点（Savepoint），内层失败只回滚到保存点，外层可继续 批量处理中跳过单条失败项
SUPPORTS 有事务则加入，无则以非事务方式执行 查询方法
NOT_SUPPORTED 挂起当前事务，以非事务方式执行 耗时的外部调用，不想占事务连接
MANDATORY 必须有事务，否则抛 IllegalTransactionStateException 不允许独立执行的内部方法
NEVER 必须没有事务，否则抛异常 禁止在事务内执行的逻辑

两个高频对比：

  • NESTED vs REQUIRES_NEW：NESTED 内层回滚只回滚到保存点，外层还能继续提交（同一条连接）；REQUIRES_NEW 是完全独立的第二个事务（第二把连接），外层回滚也不影响它。
  • 传播行为只在跨 Bean 的代理调用时生效（同类自调用一律不生效，见 7.4 场景 1）。

7.3 隔离级别与并发问题

隔离级别 脏读 不可重复读 幻读 说明
READ_UNCOMMITTED 可能 可能 可能 读未提交的数据，几乎不用
READ_COMMITTED 不会 可能 可能 Oracle / PostgreSQL 默认
REPEATABLE_READ 不会 不会 可能 MySQL InnoDB 默认；InnoDB 在 RR 下通过 MVCC 快照读 + 间隙锁（Gap Lock）基本消除幻读
SERIALIZABLE 不会 不会 不会 串行化，性能最差
  • 三个并发问题的定义：脏读（读到未提交数据）、不可重复读（同一条记录两次读结果不同，发生在更新）、幻读（同一范围两次查询行数不同，发生在插入/删除）。
  • Spring 的 Isolation.DEFAULT 表示使用数据库默认值，@Transactional(isolation = Isolation.REPEATABLE_READ) 可显式指定。
  • 面试追问：MySQL 默认隔离级别是 REPEATABLE_READ 而不是更严格的 SERIALIZABLE，靠的是 MVCC（多版本并发控制）+ 锁的配合，读不加锁（快照读）、写加行锁/间隙锁，在性能和一致性之间取得平衡。

7.4 @Transactional 失效场景

  1. 同类自调用（最高频，与 4.4 同源）：

解决：拆 Bean；@Autowired @Lazy private OrderService self; 后 self.updateStock(...)；或 AopContext.currentProxy()（需 @EnableAspectJAutoProxy(exposeProxy = true)）。

  1. 非 public 方法：AbstractFallbackTransactionAttributeSource 只解析 public 方法的事务属性，非 public 直接返回 null——静默失效。
  2. 异常被 catch 吞掉：事务提交与否取决于异常是否抛出到代理，自己 catch 掉就不会回滚：
  1. 受检异常默认不回滚：默认只对 RuntimeException 和 Error 回滚，受检异常（如 IOException）不会。需要 @Transactional(rollbackFor = Exception.class)。
  2. **方法/类为 final**：CGLIB 无法继承，事务不生效。
  3. 多线程调用：事务上下文绑定在线程的 ThreadLocal 上，新起的线程（new Thread、线程池）没有事务上下文，各跑各的连接。
  4. 数据库/表不支持事务：MyISAM 引擎、只读连接等。
  5. 对象不是 Spring 管理的：new OrderService() 或手动 getBean 拿原始对象，没有代理。
  6. **传播行为配置引发的”部分提交”**：外层事务方法里 try-catch 包住内层 REQUIRED 调用，异常被外层吞掉后整批回滚（因为 REQUIRED 是同一事务）；想要”内层独立提交”得用 REQUIRES_NEW。

7.5 常见问题

  • 大事务：一个事务里做耗时的外部调用、循环大批量更新，会长时间占用数据库连接与行锁。治理方向：拆分事务、REQUIRES_NEW 抽出独立步骤、或改用编程式事务精准控制边界。
  • **readOnly = true**：语义是”禁止写操作”（误写会抛异常），同时给数据库优化器提示（如 MySQL 8 对只读事务的优化）。适合只读查询接口，但不要指望它带来显著的性能提升。
  • 自增主键/连接释放：由连接池管理，与事务无关；但长事务会”占住”连接不归还，连接池耗尽时表现为”拿不到连接”。

8.6 常见问题与坑

  1. 异常未被捕获：检查 @ControllerAdvice 是否在组件扫描路径内；确认没有其他 Advice 的 @ExceptionHandler(Exception.class) 抢先（@Order 高的先执行）。

10. 常见 Spring 面试题速答

本节用”问题 + 一句话答案 + 定位”的方式速览高频题，详细推导见对应章节。

10.1 IoC / 容器

Q：IoC 和 DI 是什么？
A：IoC 是把对象创建与装配的控制权反转给容器；DI（依赖注入）是它的实现方式——容器把依赖通过构造器/Setter/字段注入进来。详见第 1 节。

Q：BeanFactory 与 ApplicationContext 的区别？
A：ApplicationContext 是 BeanFactory 的子接口。BeanFactory 是底层容器、懒加载；ApplicationContext 预加载单例，自动注册后处理器，并提供事件、国际化、资源加载等能力。详见 2.1。

Q：容器启动时做了什么？
A：解析配置类（ConfigurationClassPostProcessor）→ 注册 BeanDefinition → 注册 BeanPostProcessor → 预实例化单例（finishBeanFactoryInitialization）→ 发布 ContextRefreshedEvent。详见 6.1。

Q：如何发布和监听事件？
A：注入 ApplicationEventPublisher 调 publishEvent；监听用 @EventListener（默认同步、同一线程），@TransactionalEventListener 可在事务提交后触发（Spring 4.2+，观察者模式的典型应用）。

10.2 生命周期 / 作用域

Q：Bean 生命周期关键节点？
A：实例化 → 属性填充（@Autowired 注入）→ Aware 回调 → postProcessBeforeInitialization → @PostConstruct → InitializingBean → init-method → postProcessAfterInitialization（AOP 代理在此创建）→ 就绪；销毁：@PreDestroy → DisposableBean → destroy-method。详见 2.3。

Q：单例与原型区别？
A：单例全容器一个实例、生命周期由容器管理；原型每次 getBean 新实例、容器不管理其销毁。详见 2.4。

Q：Spring Bean 线程安全吗？
A：不是 Spring 保证的。无状态单例天然安全；有状态单例需原子类/同步/ThreadLocal/无状态设计。详见 2.4。

Q：怎么把原型 Bean 注入单例 Bean？
A：@Lookup、ObjectProvider<T>、或 @Scope(proxyMode = TARGET_CLASS)。详见 2.4。

Q：BeanFactory 和 FactoryBean 的区别？
A：BeanFactory 是容器接口；FactoryBean 是生产对象的 Bean，注入拿到的是 getObject() 的结果，& 前缀取 FactoryBean 本身。详见 2.6。

10.3 依赖注入

Q：@Autowired 与 @Resource 的区别？
A：来源（Spring vs JSR-250）、默认策略（按类型 vs 先名称后类型）、@Primary 支持、构造器支持、必填配置。详见 3.1。

Q：同类型多个 Bean 怎么注入？
A：@Qualifier 按名称、@Primary 标默认、@Priority 标顺序，或字段名与 Bean 名一致兜底。详见 3.2。

Q：为什么推荐构造器注入？
A：不可变、必填、可测试；代价是构造器注入的循环依赖无解（会启动报错，反而帮助尽早暴露问题）。详见 3.3。

Q：循环依赖为什么需要三级缓存而不是二级？
A：核心是延迟”是否创建 AOP 代理”的决策——代理在初始化后才创建，循环依赖却在属性填充时就需要引用；三级缓存用 ObjectFactory 把决策推迟到真正需要时。详见 3.4。

Q：构造器注入的循环依赖怎么办？
A：改字段注入，或加 @Lazy；根本上应重构消除循环依赖。Boot 2.6+ 默认禁止循环依赖。详见 3.5。

10.4 AOP

Q：JDK 代理与 CGLIB 的区别？Spring Boot 默认用哪个？
A：JDK 要求实现接口、代理类与目标同接口；CGLIB 生成子类、无接口也能代理但 final 不可。Spring Boot 2.x 起默认 CGLIB（proxy-target-class=true），为的是避免类型转换错误并支持无接口类。详见 4.2。

Q：代理在 Bean 生命周期哪一步创建？
A：正常 Bean 在 postProcessAfterInitialization；循环依赖的 Bean 提前在 getEarlyBeanReference 创建，通过 earlyProxyReferences 保证不重复。详见 4.3。

Q：AOP 哪些情况会失效？
A：同类自调用、private/final 方法、非容器 Bean、切点表达式不匹配。解决自调用：注入自身代理 / AopContext.currentProxy() / 拆 Bean。详见 4.4。

10.5 事务

Q：@Transactional 什么时候失效？
A：同类自调用、非 public、异常被吞、受检异常未配 rollbackFor、final 方法、多线程、MyISAM 表、非容器 Bean。详见 7.4。

Q：7 种传播行为是什么？各自典型场景？
A：REQUIRED（默认）、REQUIRES_NEW（独立事务，日志场景）、NESTED（保存点，跳过失败项）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。详见 7.2。

Q：MySQL 默认隔离级别？三大并发问题？
A：REPEATABLE_READ（InnoDB，MVCC + 间隙锁基本消除幻读）；Oracle/PG 默认 READ_COMMITTED。脏读、不可重复读、幻读。详见 7.3。
