ES 原理深挖：写入链路、分片与集群健康

Posted on 2026-08-13 In 数据存储 Word count in article: 3.6k Reading time ≈ 13 mins.

ES 面试的深水区只有三个问题：为什么说 ES 是「近实时」而不是实时？数据是怎么分布到分片上的？集群黄了红了到底意味着什么？ 入门篇回答了「ES 是什么、为什么搜得快」（倒排索引、分词），本文下潜到写入链路、分片路由、副本一致性、脑裂与集群健康——面试问「ES 写入流程」「分片数怎么定」「脑裂怎么防」的答案全在这。读完你能画出一次写入的完整旅程，并能在集群变黄/变红时说出先查什么。

联动：本文是 Elasticsearch 原理与实践（倒排索引/分词/基本查询）的深挖续篇；写入链路与 MySQL 原理与优化 的 redo log/WAL 是同一思想的两种实现（先记日志再落盘）；集群选举与 ZooKeeper 原理与实践 的 Zab 协议呼应。

1. 定位：这篇深挖什么

入门篇讲了「ES 为什么快」（倒排索引 + 分片并行），本文回答三个「为什么」：

现象 表层答案 本文深挖
写入后 1 秒内搜不到 「refresh 间隔 1 秒」 §2：写入的三段式旅程，为什么必须这样设计
主分片数建索引后不能改 「路由固定」 §3：hash 路由机制，改了就找不到数据
集群 yellow 还能用 「有副本没起来」 §4：三色健康状态的真实含义与处理

因果链主线：ES 的所有「奇怪现象」（近实时、分片不可变、yellow 可用）都不是 bug，是同一组设计权衡——「内存快、磁盘慢、网络不可靠」三个约束下，用批量 + 缓冲 + 冗余换性能与可用性。面试答 ES 能答到「每个现象背后的权衡」，就从背结论升级到了懂设计。

2. 写入链路：一次写入的三段式旅程

2.1 全景：refresh / translog / flush

sequenceDiagram
    participant C as 客户端
    participant P as 主分片
    participant M as 内存 buffer
    participant T as translog(磁盘)
    participant S as segment(磁盘)
    C->>P: 1. 写入请求（POST doc）
    P->>M: 2. 写入内存 buffer（未可搜）
    P->>T: 3. 同步写 translog（先记日志！）
    Note over P: 每 1 秒：buffer → 内存 segment → 刷成可搜（refresh）
    Note over P: 每 30 秒或 translog 满：flush 落盘 + translog 清空
    P-->>C: 4. 返回成功（此时数据还没落盘）

一次写入的完整旅程：

步骤 动作 数据在哪 可搜？
① 写入内存 buffer 内存 ❌
② 同步写 translog（事务日志） 磁盘（日志） ❌
③ refresh（默认 1s）：buffer → 内存 segment，清空 buffer 内存 segment ✅
④ flush（默认 30s 或 translog 满）：segment 落盘，清空 translog 磁盘 ✅

三个设计要点的因果链：

  1. 为什么返回成功时数据还没落盘？ —— 批量写入内存是毫秒级，逐条刷磁盘是毫秒级的几十倍。ES 选择「先回成功、后落盘」，用 translog 兜底崩溃：机器挂了，重启后从 translog 重放未落盘的数据——这与 MySQL 的 WAL（先写 redo log 再改数据页）是同一个思想，先记日志、后落盘，日志是崩溃恢复的承诺。
  2. 为什么 refresh 1 秒才可搜？ —— 磁盘 segment 是不可变的（只能新建不能改），每秒把内存 buffer 攒成一个新 segment 批量落内存。「近实时」不是缺陷，是「批量化换取吞吐」的必然代价：要实时可搜就得每请求刷一次盘，吞吐直接崩。1 秒的 refresh 是吞吐与实时性的平衡点。
  3. translog 为什么要 fsync？ —— 默认每次写入 fsync（index.translog.durability: request）保证 translog 真正落盘，此时才返回成功——「返回成功」的语义 = 「translog 已落盘」，不是「数据已落盘」。

2.2 动手验证：亲眼看到「近实时」

观察点：紧接写入的搜索 hits.total 可能为 0，1.2 秒后变 1——refresh 间隔的现场。判定标准：亲自复现「写入后短暂搜不到、1 秒后能搜到」，理解「近实时」的字面含义。生产意义：刚写入就要立刻搜到的场景（订单即时查询）必须调 refresh=true（性能换实时）或用「可搜索快照」技术，不能指望默认 1 秒。

2.3 深挖：为什么 Lucene 段不可变是好事

segment 不可变（只能整体新建）看似低效，实际是三个收益的源头：

收益 机制
免锁 不可变 = 无需并发控制，读路径无锁
缓存友好 段的词典/倒排表可整体缓存，不会失效
崩溃恢复简单 已落盘的段永远有效，恢复只重放 translog

因果链：不可变 → 免锁 + 可缓存 → 单机查询吞吐高 → 但更新/删除是「标记删除」+「新段覆盖」→ 产生段膨胀 → 后台 merge（段合并）压缩段数 → 合并是 CPU/IO 大户，大段合并是 ES 性能问题的常见来源（集群慢先查 merge 指标）。面试答「ES 的删除是逻辑删除」时，补一句「靠 merge 物理清理」是加分项。

3. 分片与副本：数据怎么分布

3.1 路由：为什么主分片数不可变

文档写入哪个分片由 routing = hash(_id) % number_of_shards 决定：

flowchart LR
    A["文档 _id"] --> B["hash(_id)"] --> C["% 主分片数 (3)"] --> D["分片 0 / 1 / 2"]

因果链：主分片数一旦确定就不能改，因为改了取模的分母，同一文档会被路由到不同分片，旧数据全找不到了。改分片数只能 _reindex 到新索引（重新 hash 全量重建）。面试必问「分片数怎么定」的完整答案：

维度 建议 依据
分片大小 每分片 20-50GB 过大 merge 慢、恢复慢；过小分片数爆炸
分片数量 总数据量 ÷ 30GB 左右 平衡并行度与开销
上限参考 单节点 ≤3-5 分片 每个分片有独立文件句柄/内存开销
副本数 ≥1（生产必配） 无副本 = 单点，节点挂了数据就 red

工程经验：分片数定少了后期只能 reindex（全量重建，灾难）；定多了浪费资源。「按数据规模反推分片数」是设计时的核心决策，不是部署后能改的。

3.2 副本：读扩展 + 故障转移

能力 机制 说明
读扩展 副本分担读请求 搜索默认在主+副本间负载均衡
故障转移 主挂了副本自动升主 不需要人工干预
写入一致性 主写成功 → 同步副本 wait_for_active_shards 可等副本确认（牺牲延迟换一致）

副本不是备份，是「可用的读副本」：副本与主分片数据实时同步，搜索请求可打到任意副本——副本数 = 读吞吐的扩展维度。生产配置原则：副本数 ≥1 是底线（否则单节点故障即 red），读多写少的搜索场景副本数可 = 2。

3.3 动手验证：看分片分布与路由

观察点：_cat/shards 里主分片 P 与副本 R 的节点分布；单节点时副本显示 UNASSIGNED、集群变 yellow。判定标准：理解「副本必须分布在不同节点才有意义」——单节点集群配副本是浪费（副本和主在同节点，挂了一起挂），这也是「集群为什么 yellow」的第一个答案。

4. 集群健康：三色状态与脑裂

4.1 三色健康的真实含义

颜色 含义 还能用吗 处理
green 主分片+副本全部就绪 完全正常 无需处理
yellow 主分片都在，副本缺失（unassigned） 能读能写，但无故障转移能力 查为什么副本没起来（节点数不足/磁盘满/网络隔离）
red 有主分片缺失 该分片数据不可用（部分索引不可搜） 立即处理：恢复节点或 reroute

因果链：yellow 不是「小问题」——它意味着「副本没就位，任何主分片所在节点挂掉，数据就永久丢失（除非还有别的副本）」。生产铁律：集群 yellow 必须当天处理，不能挂着过夜——常见的黄色原因（单节点配了副本、新节点加入后副本未分配、磁盘水位线导致不分配）排查路径全部在 _cat/allocation 里。

4.2 脑裂：集群最大的安全风险

脑裂 = 一个集群分裂成两个「各自认为自己是主」的子集群，两边同时接受写入，数据分裂，集群永久损坏。

产生条件（老版本 discovery.zen.minimum_master_nodes 配置不当）：5 节点集群配 minimum_master_nodes=2——网络分区把集群切成 3+2 两半，两边都能选出主节点，各自接受写入 → 恢复后数据冲突，不可修复。

防护三板斧：

手段 机制
discovery.zen.minimum_master_nodes = (节点数/2) + 1 选举需要过半数投票，少数派无法选主
master 节点独立角色 master-eligible 节点与 data 节点分离，master 不扛数据压力
8.x 新机制（cluster.auto_shrink_voting_configuration） 动态调整投票配置，自动规避多数派问题

因果链：脑裂的根源是「少数派认为自己合法」——过半数投票规则让少数派选不出主（3 节点集群配 2 票，2+1 分区时 1 票的少数派选不出主）。面试答「怎么防脑裂」：一句话「minimum_master_nodes 设为过半」+ 一句解释「让少数派选不出主」，就到位了。

4.3 动手验证：复现 yellow 与理解 unassigned

观察点：单节点 + 副本 → yellow 且 unassigned 列表齐全；节点全停 → 集群失联。判定标准：能解释「为什么单节点集群配副本是 yellow 而不是 green」——副本需要另一台节点才就位，这个「节点不足 → 副本不分配 → yellow」链条是集群健康的第一课。

维度 MySQL ES

一句话：ES 的 translog 就是搜索引擎界的 WAL——「先记日志、后落盘、日志兜底崩溃」是数据库与搜索引擎共同的设计底座（MySQL 原理与优化 的 redo log 章节在此复用）。面试被问「ES 和 MySQL 的写入设计有什么共同点」，答出这一层是明显加分。

6.1 面试速答表

从零实现智能工单 Agent：MCP+RAG 全流程实战

Posted on 2026-08-13 In AI大模型 Word count in article: 5.7k Reading time ≈ 21 mins.

智能工单 Agent（ITPA）是一个「把 LLM 接进业务系统」的最小完整样板：接收入口（MCP Server）→ 分类判断（LLM）→ 知识检索（RAG）→ 回复生成（LLM）→ 数据落库（MySQL），一条链覆盖 AI 应用的全部核心模式。 本项目用 TypeScript 从零实现，读者是懂 Java 后端的开发者——每个技术选型都对照你熟悉的 Java 生态（TypeORM≈JPA、Fastify≈Spring Boot、Pino≈Logback）。读完你能复刻一个可运行的 Agent 服务，并理解 MCP 协议、向量检索、结构化输出的完整工程细节。

联动：本文是 MCP 开发指南 的完整落地案例（协议从概念到代码）、RAG 原理与实践 的工程实现（Embedding/检索/阈值）、LLM API 与工具调用实战 的实战演练（Function Calling/JSON 输出）。姊妹篇：Python 版实现见 ticket-agent-mcp(py)，两版结构约 80% 重叠，按熟悉的技术栈选一篇精读。

1. 项目定位：解决什么问题

1.1 真实业务痛点

典型中大型企业客服场景：每天 500+ 用户工单，涵盖技术问题、账单疑问、账户申诉、产品咨询、投诉反馈五大类。纯人工处理带来三个核心痛点：

痛点 表现 成本
响应速度慢 平均响应 >2 小时 用户流失
人力成本高 客服团队随工单量线性扩张 工资 × N
知识资产难沉淀 老客服的经验无法复制 培训周期长

本项目构建的智能工单 Agent 接入企业现有工单系统，自动完成四件事：

  1. 自动分类：识别工单属于哪一类问题（LLM + 结构化输出）；
  2. 相似检索：基于向量相似度检索历史已解决工单与 FAQ（RAG）；
  3. 生成回复：结合检索结果生成可供人工审批的回复草稿（LLM）；
  4. 落库流转：写入 MySQL，自动分配优先级与状态（工程化）。

设计定位：不是「全自动客服」，而是「人审 AI 草稿」——回复生成后必须人工审批才发出。这是 AI 应用上生产的第一原则：LLM 输出不可直接面对用户，置信度低时降级给人。

1.2 为什么用这个项目练手

  • 全链路覆盖：HTTP/MCP 接入 → 分类 → 向量检索 → LLM 生成 → 数据库落库，一条完整的「请求-处理-响应」链路；
  • AI 原生：真实调用 OpenAI API，理解 embedding/chat 两类核心接口；
  • 生产级复杂度：JSON Schema 验证（Zod）、结构化日志（Pino）、连接池、健康检查、容器化——不是玩具项目；
  • 可演进：从本地 stdio 模式起步，一行配置切到 HTTP 模式的分布式部署。

关键决策一：为什么用 Bun 而不是 Node.js？ Bun 把包管理（bun install≈Maven 依赖）、TS 运行（bun run≈直接运行 Java）、测试（bun test≈JUnit）、打包（bun build≈Maven Shade）整合进一个工具链——Java 开发者最习惯的「一个工具链搞定一切」体验。启动 10ms（Node 约 100ms），运行时快 2-4 倍。

关键决策二：为什么 MySQL 存向量而不是上向量数据库？ 数据量小时（万级工单），MySQL JSON 列 + 应用层余弦相似度完全够用——少一个基础设施，少一类运维问题。数据量大或需要 ANN 索引时再迁移 HeatWave/单独向量库（向量数据库原理与实践 已讲选型）。这是「架构演进而非一步到位」的典型。

3. 架构设计：MCP 协议 + 分层

3.1 MCP 协议核心原语

6. 核心服务层：Agent 的四个大脑

6.1 Embedding 服务：把文本变成向量，带缓存

设计要点（因果链）：embedding 是确定性的（同一文本永远同一向量）——确定性 = 可缓存。缓存命中省一次 API 调用（省钱 + 省延迟），这是 RAG 工程化第一个性能优化点。批量接口 + 限速：Embedding API 按 token 计费且速率受限，分批 + 间隔是生产必需。

6.2 检索服务：RAG 的核心——余弦相似度 + 阈值过滤

为什么要有相似度阈值（关键工程决策）：检索的目的是「给 LLM 喂有效上下文」——喂了不相关的上下文，LLM 会被带偏（幻觉/答非所问）。阈值 0.7 意味着「没有足够相似的参考就空着」，让 LLM 老实承认不知道，而不是编造。这是 RAG 质量的核心控制点：检索质量 > 生成能力（RAG 原理与实践 的 Chunking/检索章节在此落地）。

性能坦白：应用层全量算相似度是 O(n) 扫描——万级数据够用，十万级要上向量索引（ANN/HNSW），百万级必须换向量数据库。设计文档里写清楚「当前规模下这个选择成立」是工程成熟的标志。

6.3 分类服务：LLM + 结构化输出（JSON mode）

三个关键工程决策：

  1. response_format: json_object 强制结构化——LLM 自由文本输出没法直接进下游（枚举校验/数据库）。结构化输出是 LLM 上生产的前提（LLM API 与工具调用实战 §三）；
  2. temperature: 0.3 低温——分类任务要确定性，高温会让同一工单每次分类不同；
  3. JSON.parse 后要校验——LLM 偶发返回非法 JSON 或缺失字段，生产代码必须有兜底（try-catch + 默认值），别让一个坏输出打挂整条链路。

因果链：分类结果里带 confidence（置信度）不是装饰——它是下游「是否人工介入」的判据：置信度 < 0.8 的工单直接转人工，只有高置信度才自动流转。AI 应用的可靠性不是「让 AI 永远对」，而是「AI 不确定时知道说不并降级」。

6.4 生成服务：RAG 上下文注入的回复草稿

温度策略对比（两处设计的呼应）：

服务 温度 原因
分类 0.3 低 确定性优先：同一工单必须同分类
生成 0.7 高 自然度优先：回复要像人写的

同一套 API、同一个模型，温度一个参数就改变任务的本质——这是 LLM 工程里最便宜的调参杠杆。sourcesUsed 字段记录引用来源——AI 回复要可追溯：用户追问「你凭什么这么答」时，能指出引用的工单/FAQ，这是生产合规的底线。

算法篇三：哈希表、二叉树与递归

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.5k Reading time ≈ 13 mins.

二叉树 + 递归 + 哈希表，是面试 80% 题型的主战场：树的遍历、验证 BST、最近公共祖先、两数之和、TopK——全部在这三个话题里。 本篇先讲哈希表的原理与工程对照（你天天用 HashMap，算法题里把它当武器），再讲二叉树遍历三法（递归/迭代/层序）与五道必会模板题，最后讲递归思维与复杂度。读完你能做到：树类手撕题 10 分钟内 AC，并能说出每步的复杂度。

系列地图（数据结构与算法）：① 复杂度分析与高频结构速查（度量衡）→ ② 数组/链表/栈/队列与双指针（线性结构手撕）→ ③ 本文：哈希表、二叉树与递归（系列收官）。

1. 哈希表：工程里天天用，算法里是武器

1.1 原理回顾：数组 + 哈希函数 + 冲突处理

HashMap 的本质：hash(key) % 数组长度 定位桶 → 冲突链（链表/红黑树）→ 装载因子超阈值扩容。你每天用的这个结构，在算法题里的用法是「空间换时间的查询加速」：

算法题用法 做法 典型题
去重 Set 判存在 环形链表、判断重复元素
计数 Map<key, count> 多数元素、字谜分组
位置记录 Map<key, index> 两数之和、最长无重复子串
缓存子问题 Map<key, 结果> 记忆化递归（DP）

因果链：算法题里哈希表的任务永远是「把 O(n) 的查找变成 O(1)」——两数之和暴力是 O(n²)（两两枚举），哈希表一次遍历 O(n)（每个数查「补数」是否存在）。

1.2 模板：两数之和（哈希版）

模板要点：边遍历边记录——「先查补数，再记自己」。与第二篇的左右指针版对比：哈希版不要求有序（通杀），左右指针版 O(1) 空间但要求有序（更省）。面试两版都要会，答「有序数组用双指针 O(1) 空间，无序用哈希 O(n) 空间」是完整答案。

1.3 动手验证：哈希 vs 暴力的时间差

观察点：n=100 万时暴力完全不可行、哈希瞬时返回。判定标准：能独立说出「数据规模决定算法选择」——100 个元素的题暴力无所谓，10 万个元素的题暴力必挂，这就是复杂度分析在题目里的直接应用。

2. 二叉树：先建立遍历三法

2.1 二叉树的结构与递归定义

二叉树是天然递归的结构：每个节点 = 值 + 左子树 + 右子树，而左右子树也是二叉树。结构递归 → 解法递归，这是「树题 90% 用递归」的根本原因——不是树题恰好适合递归，是树的定义本身就是递归的。

3. 五道必会树模板题

3.1 最大深度（后序思维入门）

后序思维：先要子树的答案，再算自己的。复杂度 O(n) 时间、O(高度) 栈空间。变体「直径」「平衡二叉树」全是同一骨架（平衡二叉树 = 每层检查左右深度差 ≤1）。

3.2 验证二叉搜索树（中序升序的威力）

常见错误：只比较 root > left && root < right——子树内部的所有节点都必须满足，不仅仅是直接孩子（例：{5, 4, 6, null, null, 3, 7} 左根右都满足但 3 小于 5 不是 BST）。中序升序检查天然规避了这个坑。变体「BST 的第 K 小」：中序遍历计数到 K 即答案。

3.3 翻转二叉树（递归 + 交换）

三行递归 + 三行交换，5 行代码——这是「递归题之美」的典型。复杂度 O(n)。面试官用这题考察的是「你能不能别背，理解递归在树上的执行流」——后序的顺序是这题的灵魂。

3.4 最近公共祖先（LCA，后序思维巅峰）

解读这段代码就是在读后序：先看左右子树各找没找到，再决定自己是不是答案——「两边都有 → 我是 LCA；只有一边 → 结果在那边」。复杂度 O(n)。变体「BST 的 LCA」：利用有序性，p.val < root.val && q.val < root.val 就只往左找——O(log n)。面试答 LCA 必须主动提 BST 变体，说明你理解「结构性质 → 算法加速」。

3.5 动手验证：层序打印 + 翻转后对比

观察点：翻转后层序每层是原层的镜像。判定标准：程序输出与「镜像」直觉一致——把「抽象的后序递归」和「看得见的层序输出」对照起来，是理解递归执行的最后一公里。

4. 递归与回溯：树的延伸

4.1 从「树的结构」到「决策树」

递归的通用形态是决策树：每层递归是一个决策点，每个分支是一个选择——树的遍历是决策树的最简单实例。「回溯」= 决策树的 DFS + 撤销选择：

回溯模板四步：终止条件 → 遍历选择 → 做选择 → 撤销选择。变体：全排列（交换写法/used 数组）、组合、括号生成——全是同一个骨架。复杂度：子集 2ⁿ 个结果，复杂度 O(n·2ⁿ)（输出量本身就是指数级，无法优化——先看输出规模再定复杂度期望）。

4.2 动手验证：子集数量是 2 的幂

观察点：n=20 时输出已近 100 万行。判定标准：理解「指数复杂度不是代码问题，是输出量本身」——面试题给 n 的上限，就是给你「该不该用回溯」的信号（n≤20 回溯可行，n≤10⁵ 必是贪心/DP）。

TreeMap/TreeSet 红黑树 有序集合 = BST 变体
MySQL B+ 树索引 多路搜索树 树高=磁盘 IO 次数（深度概念）
堆（PriorityQueue） 完全二叉树 树形结构存储（数组下标 = 树位置）
JVM 类加载器 树 双亲委派是树的遍历

因果链：面试考树，是因为工程里树无处不在——HashMap 优化到红黑树、MySQL 索引是 B+ 树、JVM 类加载是树。你答「树的深度影响什么」时，能举例 MySQL B+ 树树高 3 层 = 3 次磁盘 IO（万级数据），比纯背定义高一个层次——这是《MySQL 原理与优化》里 B+ 树的直接复用。

5.2 复杂度对照：树的常用操作

结构/操作 平均 最坏 说明
二叉树查找（非 BST） O(n) O(n) 无序树要全遍历
BST 查找 O(log n) O(n) 有序插入退化成链
平衡树（红黑树） O(log n) O(log n) 自平衡，工程默认
堆 插入/取顶 O(log n) O(log n) 完全二叉树保证
HashMap 查询 O(1) O(n) 冲突退化，红黑树兜底

面试高频题「BST 退化的后果」：有序插入 1,2,3,…,n → BST 变成一条链 → 查找 O(n) → 这就是为什么工程里用红黑树而不是裸 BST（TreeMap 的自平衡来源）。

AI 在 Java 后端的落地实践：RAG 服务化与向量检索上生产

Posted on 2026-08-13 In AI大模型 Word count in article: 4.8k Reading time ≈ 18 mins.

本篇回答一个问题：RAG 从「能跑的脚本」到「生产可用的服务」，中间差了什么？ RAG原理与实践 讲「检索怎么做好」，本篇讲「检索怎么作为一个服务跑在生产上」——接口设计、索引流水线、权限隔离、降级链路、容量评估，全部以 Java 后端视角展开。

1. 从实验到服务：RAG 落地的完整闭环

1.1 脚本 RAG 的四个问题

实验阶段的 RAG 通常长这样：一个 Python 脚本，启动时解析文档 → 分块 → 调 embedding 接口 → 灌进本地向量库 → 收到问题直接查库拼接 prompt。它能回答「效果好不好」，但上不了生产：

问题 实验脚本表现 生产要求
不可用 向量库挂在脚本进程里，重启全丢 服务独立部署，库高可用
不可扩展 一个进程既管入库又管检索 读写分离，各自独立扩展
不可治理 谁都能查所有知识，无权限概念 知识按租户/部门隔离，审计可追
不可观测 报错就是 print，效果好坏靠感觉 延迟、召回、成本全部可度量

因果链：实验脚本的「简单」来自把所有环节耦合在一个进程里——一旦拆成「对外接口、索引流水线、检索链路、模型网关」四件事，就不得不回答服务化的一系列设计问题，这正是本篇的主线。

1.2 服务化的四个目标

目标 具体含义 对应章节
功能闭环 入库、检索、问答有稳定接口 第 2、3 章
安全可控 知识隔离、权限过滤、审计 第 4 章
可用性 依赖故障（向量库/模型）有降级路径 第 5、6 章
可度量 延迟/召回/成本有指标有预算 第 7、8 章

2. 检索服务的接口设计

2.1 三个核心接口

接口 场景 同步/异步 说明
POST /search 纯检索（RAG 之外也可用） 同步 输入 query + 过滤条件，返回 chunks
POST /chat 问答（检索 + 生成） 同步（SSE 流式） 一次调用包含完整 RAG 链路
POST /ingest 文档入库/更新/删除 异步 返回任务 ID，轮询/回调查状态

因果链：/ingest 必须异步——文档解析、分块、embedding 是大模型调用（慢、贵、可能失败），同步接口要么拖垮调用方，要么超时后状态不明；异步 + 任务表才能支持「失败重试、进度可见、结果审计」。

2.2 接口参数设计

动手验证：最小检索服务

观察点：接口的前两行就是权限校验——检索服务的正确性不只是「结果对不对」，更是「不该看到的结果一条都不能出」。判定标准：权限校验必须发生在检索之前（否则过滤器被绕过时数据已出库）。

2.3 流式问答：chat 接口的 SSE

/chat 用 SSE（text/event-stream）返回，而不是等全部生成完再返回：

方式 首字延迟 用户体感 服务端资源
一次性返回 数秒 转圈，像死机 连接占用时间相同
SSE 流式 数百 ms 看到字在出 连接占用时间相同

动手验证：Spring WebFlux + SseEmitter，或直接用 Spring AI 的 StreamingChatClient（见 Spring AI与LangChain4j实战）——前端 fetch 读流即可。判定标准：首字延迟是问答服务的第一体验指标，流式是标配不是加分项。

3. 索引更新流水线：知识怎么进系统

3.1 全量重建 vs 增量更新

方式 场景 代价
全量重建 首次上线、文档批量导入、分块策略升级 慢（全量 embedding），但实现简单、结果一致
增量更新 日常单文档增删改 快，但要处理「文档变更了，旧 chunk 怎么办」

核心问题：增量更新的「文档 → chunk」映射——向量库只认 chunk，不认文档；文档更新时必须按 documentId 把旧 chunk 全部删掉再插新的，否则旧片段残留、新片段重复。

动手验证：双缓冲版本切换（全量重建不打折）

观察点：重建期间用户查的是旧版本（active 不变），切版本是原子操作，全程服务不中断。判定标准：任何「重建期间检索结果不一致/报错」都是双缓冲没做好的信号。

3.2 流水线的四步与失败处理

flowchart LR
    A["1 解析<br/>(pdf/word → 文本)"] --> B["2 分块<br/>(chunk + 元数据)"]
    B --> C["3 Embedding<br/>(批量调模型)"]
    C --> D["4 入库<br/>(写向量库)"]
    C -.失败.-> E["重试队列<br/>(指数退避)"]

因果链：流水线每步都可能失败（文件损坏、embedding 限流、向量库抖动），没有重试队列的流水线，失败就静默丢文档——用户问「为什么新文档答不出来」，排查半天才发现入库任务失败了没人知道。

动手验证：任务状态表

重试策略：失败任务重试 3 次（指数退避 1s/5s/30s），仍失败进失败队列人工处理；状态表 + 定时扫描替代「丢线程里自生自灭」。判定标准：任意时刻能回答「这份文档入库到哪一步了」。

4. 多知识库与权限控制

4.1 为什么必须隔离

知识库问答最大的风险不是「答不对」，是越权出数据：销售部门的同事能问到财务文档。生产环境必须有明确的知识边界。

4.2 三种隔离方案对比

方案 隔离粒度 优点 缺点
独立向量库/实例 租户级 物理隔离最彻底，互不影响性能 运维成本 ×N，不能跨库检索
独立集合/表 知识库级 逻辑隔离，管理简单 单个库容量受限，查询跨集合麻烦
元数据过滤 任意粒度（文档级） 最灵活，一次部署全租户共享 过滤条件漏配 = 越权，必须服务端强制

推荐组合：元数据过滤为主 + 权限上下文服务端强制。knowledgeBase 和 userId 不来自前端请求，而是来自服务端从登录态解析的上下文——前端传什么都不可信。

4.3 文档级权限过滤的泄漏风险

元数据过滤在检索时只返回匹配 chunk，但过滤条件必须与文档权限同源：

因果链（泄漏路径）：文档 A 属于部门 X → 检索请求只带了 department=X → 系统相信了请求参数 → 部门 Y 的用户伪造参数 → 检索到文档 A 的 chunk → 数据泄漏。防御：权限不是「检索条件」，是「服务端强制注入的约束」，来源只能是登录态/Token 解析出的身份。

观察点：enforcedFilter 里服务端追加的键，前端无法覆盖（合并时后者胜出，或直接拒绝请求体里的同名键）。判定标准：去掉前端 filter 参数，权限过滤依然生效。

5. Embedding 网关与模型调用治理

5.1 为什么 embedding 调用需要独立网关

Embedding 是 RAG 里调用量最大、最容易被打爆的环节：一个 1000 页的文档集，分块后可能产生数万个 chunk，每个 chunk 一次 embedding 调用。直接散在各处调：

  • 并发不可控 → 触发模型服务限流 → 入库失败
  • 重复计算 → 相同 chunk 反复 embedding（浪费钱）
  • 依赖不可观测 → 模型服务慢/挂了没有任何反馈

Embedding 网关职责：批量合并、结果缓存、限流重试、降级。

5.2 批量与合并

因果链：单条调用模型 API（网络往返 × N）→ 高并发下模型服务限流 + 高延迟；合并成 batch（网络往返 × 1）→ 吞吐 ↑、限流 ↓、成本 ↓（很多厂商按 batch 计价更便宜）。

5.3 降级策略：embedding 挂了怎么办

故障 降级动作 服务表现
embedding 服务超时 重试 2 次（退避）→ 放弃该批，任务标 failed 可重跑 入库暂停，检索不受影响
embedding 服务长时间不可用 检索降级为纯 BM25/关键词检索（见 6.2） 问答变差但不宕机
向量库不可用 同上：BM25 兜底（需保留纯文本索引） 不宕机

动手验证：手动停掉 embedding 服务进程，观察系统行为——正确实现下，已入库的检索应该照常工作（检索链路的 embedding 只用于「查询向量化」，查询侧 embedding 缓存了热点 query 或降级关键词）。判定标准：任何单点依赖故障都不应该让整个问答服务 502。

6. 检索链路的可用性设计

6.1 延迟预算拆解

一次 /chat 调用的 2 秒预算怎么分配（示例）：

环节 预算 说明
查询 embedding 200ms 缓存命中则 0ms
向量检索 100ms 百万级向量 HNSW 索引下是毫秒级
Rerank 200ms 只对 top-50 重排，不是全量
LLM 生成 1.5s（首字） 最大头，SSE 流式下用户感知快
链路开销 0ms 检索与生成并行不了（生成依赖检索结果），但检索内部可并行

因果链：延迟大头永远在 LLM 生成，检索侧优化到 300ms 以下后，再优化对用户体验无感——预算应该花在「缓存命中率」和「rerank 是否必要」上，而不是死磕向量检索的 20ms。

6.2 降级链路：向量库 → BM25 兜底

生产环境的必答题：向量库（Milvus/ES 向量索引，选型对比见 向量数据库原理与实践）故障时，检索服务还能不能回答？

方案：检索时向量 + 关键词双路召回，向量路失败自动切关键词路：

flowchart LR
    Q["query"] --> V["向量检索"]
    Q --> K["关键词检索<br/>(ES/BM25，纯文本索引)"]
    V -->|"成功(≥2s/报错)"| R["Rerank 合并"]
    K -->|"兜底"| R

代价：需要额外维护一份纯文本索引（解析后的 chunk 文本同步进 ES）——这份索引在检索质量上也有价值（混合检索本身更好，见 RAG原理与实践 5.3），一举两得。

动手验证：停掉向量库容器，直接查 /search——正确实现下返回 BM25 结果（质量略降，服务不挂）。判定标准：故障演练表里必须有一项「向量库宕机」，没有做过的系统不算有降级链路。

6.3 多级缓存

缓存层级 缓存什么 命中收益 失效策略
Embedding 级 query → 向量 省 1 次模型调用（最贵的一层） query 完全相同时命中，热点问答命中率高
检索级 query → 检索结果 省检索链路 TTL 短（分钟级），知识更新时按 kb 失效
问答级 query → 完整回答 省全链路（最省） TTL 长（小时级），知识更新时必须主动失效

因果链（问答级缓存的陷阱）：问答级缓存命中率最高、最省钱 → 但知识库更新后缓存不失效 → 用户问新知识得到旧回答 → 缓存一致性比缓存命中率更重要。实现：每份缓存带 kb_version 键（见 3.1 双缓冲），知识版本切换时按前缀批量失效。

6.4 限流与成本控制

维度 策略
用户级限流 每用户每分钟 N 次 chat（LLM 调用最贵，必须按用户限制）
服务级限流 向量库/模型网关 QPS 上限，防止上游被打爆
成本告警 按知识库/按部门统计 token 消耗，超预算告警（见第 7 章）

8. 性能压测与容量评估

8.1 从业务量倒推容量

峰值系数 5×（上班高峰） 峰值 QPS ≈ 10万/(8×3600)×5 ≈ 17 QPS
每次 chat 的 LLM 耗时 3s 需要的并发 ≈ 17 × 3 = 51 路并发

结论：多数内部知识库问答系统是「低 QPS、高并发占用」——瓶颈在 LLM 并发数，不在向量检索。压测时用真实 LLM 调用（mock 掉生成环节会高估吞吐 10 倍以上）。

9.1 身份体系与权限对接

检索服务不维护自己的用户体系——从现有 SSO/网关解析登录态（JWT/Session），拿到 userId + 部门 + 角色，权限上下文从这来（呼应 4.3 的「服务端强制注入」）。

9.2 数据源对接

知识来源 对接方式 注意
MySQL 业务数据 定时任务/CDC（Canal）拉取 → 流水线 与 ES 双写一致性 同款问题：更新失败要能对账重跑
文件系统/对象存储 上传接口 + 监听触发 ingest 文档版本管理（同 documentId 覆盖）
现有 ES 索引 同步文本 → chunk 纯文本索引就是 6.2 的 BM25 兜底，一份数据两个用途

9.3 部署形态

组件 部署 说明
检索服务 K8s Deployment（多副本） 无状态，水平扩展只加副本（K8s 部署）
索引流水线 K8s CronJob / 消息队列消费 与检索服务资源隔离：重活不挤占在线链路
向量库 独立部署（StatefulSet） 有状态，滚动升级注意兼容（K8s StatefulSet）

因果链（部署陷阱）：入库流水线（重 CPU、重 IO）和在线检索跑在同一份资源池 → 大文档导入时在线问答变慢。离线/在线资源隔离是检索服务 SLA 的基本保障。

9.4 与 Spring AI 的关系

Spring AI与LangChain4j实战 解决了「Java 里怎么调模型、怎么接向量库」——本篇解决的是「接好之后，怎么组织成服务」：Spring AI 的 VectorStore 是组件，本篇的检索服务是把组件编排进接口/权限/降级/观测体系。两者是组件与架构的关系。

10. 落地检查清单

# 检查项 不做的后果
1 /ingest 是异步任务 + 状态表 文档入库失败无人知，问答缺知识
2 权限上下文来自服务端，不由前端传 越权检索，数据泄漏

5 问答级缓存带知识版本号，更新即失效 知识更新后答旧话
6 chat 全链路有 trace + token 成本记录 慢在哪、贵在哪全靠猜
7 用真实 LLM 压过测，P95 首字 < 3s 上线即体验崩
