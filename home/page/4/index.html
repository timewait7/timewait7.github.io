算法篇二：数组、链表、栈、队列与双指针

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.6k Reading time ≈ 13 mins.

线性结构手撕是笔试的第一道门槛：链表反转、环检测、括号匹配、滑动窗口，四类题覆盖笔试的 30% 且全部有固定模板。 本篇给每类题「模板代码 + 变体 + 复杂度 + 易错点」，按面试真实节奏组织：看到信号词 → 套模板 → 写变体。读完你能做到：这四类题 15 分钟内写出通过全部用例的代码。

系列地图（数据结构与算法）：① 复杂度分析与高频结构速查（度量衡）→ ② 本文：数组、链表、栈、队列与双指针（线性结构手撕） → ③ 哈希表/二叉树与递归（面试 80% 题型的落点）。

1. 数组：连续内存的 O(1) 访问

1.1 数组的本质：下标即地址

arr[i] 的寻址是 起始地址 + i × 元素大小——一步乘法一个加法，这就是 O(1) 访问的来源。而插入/删除要挪动后续所有元素，O(n)。

面试问「数组和链表本质区别」的底层答案：数组的 O(1) 访问来自「内存连续 + 下标寻址」，链表的 O(1) 插入来自「指针修改 + 无需移动」——两者都是物理结构决定的，不是实现细节。

1.2 模板一：原地操作（双指针同向）

「原地删除重复元素」「移除指定值」这类题，核心是用新指针覆盖写，原地完成：

模板要点：快指针扫描（读），慢指针标注结果区（写）——读快写慢，覆盖推进。变体：「移除元素」（保留等于 val 之外的）、「移动零」（把零移到末尾）全是同一个骨架。

1.3 模板二：左右指针（有序数组的两数之和）

为什么左右指针能行：数组有序 → nums[l]+nums[r] < target 时，nums[l] 与任何更右的元素和都太小（右指针是当前最大），只能 l++；对称地，>target 只能 r–。每一步排除一行/一列搜索空间，总步数 ≤ n——这就是 O(n) 的证明，面试官追问「为什么不是 O(n²)」就答这个。

1.4 动手验证：手写数组二分并测复杂度

观察点：三个易错点——<= vs <（决定死循环）、mid+1/mid-1 vs mid（决定收敛）、l + (r-l)/2 vs (l+r)/2（防溢出）。判定标准：把 target 换成「不存在」的值跑一遍（比如数组 [1,3,5,7] 查 4）——不死的循环 + 返回 -1 即模板正确。用一万个元素实测：任何查找最多 14 次比较（2¹⁴ ≈ 16384）——log₂ 的体感。

2. 链表：指针操作是手撕的主战场

2.1 模板一：反转链表（最高频链表题）

模板要点：三指针 prev/cur/next，四步走「存下 → 反转 → 前移 → 前移」。易错点：第①步不存 next 直接改指针，链表就断了。变体：「反转前 N 个」「K 个一组反转」都是这个模板的递归/循环扩展。

2.2 模板二：环检测（快慢指针）

为什么快慢必相遇：有环时快指针每次相对慢指针靠近 1 步，环长 k 则最多 k 次追上——O(n) 时间、O(1) 空间。面试变体「找环入口」：相遇后让一个指针从头出发，另一个从相遇点，都走一步，再次相遇点即入口（数学推导：头到入口距离 = 相遇点到入口的「回头距离」）。记住结论即可，推导一句话带过：「快慢指针第一次相遇时，慢指针没走完一整圈」——这句话值一个加分项。

2.3 模板三：合并两个有序链表

模板要点：终止条件（空）→ 选小者 → 递归合并剩余 → 返回头。复杂度 O(n+m) 时间、O(n+m) 递归栈。变体「合并 K 个有序链表」：两两合并（O(k·n)）或堆优化（O(n log k)）——第三篇堆会用到。

2.4 动手验证：反转 + 环检测组合拳

观察点：反转后逐节点打印验证顺序；环的构造是「把尾节点的 next 指回中间的节点」。判定标准：反转打印输出 5,4,3,2,1 且环检测返回 true——两个模板都能独立手写，是链表关的过关标准。面试 5 分钟里能默写出这两个模板，说明指针操作真的熟了。

3. 栈：后进先出的场景识别

3.1 模板一：括号匹配（栈的教科书题）

信号词识别：成对出现、嵌套结构、需要「最近匹配」——都是栈。「最近匹配」是栈的灵魂：后进先出天然对应「最内层的先闭合」这个语义。

3.2 模板二：单调栈（下一个更大元素）

单调栈的核心：维护「还没找到答案的候选」序列，且保持单调（这里递减）——新元素来临时，把所有「比它小的栈顶」一次性弹出并结算答案。每个元素入栈出栈各一次 → O(n)，暴力是 O(n²)。变体「接雨水」是单调栈的最难变体，掌握这个模板后接雨水只是「结算逻辑变化」。

3.3 动手验证：手写一个最小栈

观察点：push 3,5,2 后 getMin()=2，pop 后 getMin() 恢复为 3——辅助栈记录的是「每个历史时刻的最小值」。判定标准：任意操作序列下 getMin 都正确且 O(1)——「用空间换时间的思路」在这里具象化：辅助栈 O(n) 空间换 O(1) 查询。

4. 队列：先进先出与滑动窗口

4.1 模板一：用队列做层序（树的层序遍历）

模板要点：int size = queue.size() 是本层与下一层的分界线——漏掉这句，层就混了。BFS（最短路径）和层序遍历是同一套代码的两种用法。

4.2 模板二：滑动窗口（最长无重复子串）

滑动窗口的本质：窗口右边界负责「扩展」，左边界负责「收缩」，两指针只前进不后退 → O(n)。信号词：「最长/最短连续子数组/子串」+「满足某条件」→ 滑动窗口。变体：「最小覆盖子串」（窗口收缩时记录）、「长度最小的子数组」（和 ≥ target）。

4.3 动手验证：滑动窗口 vs 暴力对比

观察点：n=10 万时暴力版直接卡死，窗口版瞬间出结果。判定标准：亲眼看到「O(n²) 跑不动、O(n) 秒回」的对比——这就是为什么笔试必须会滑动窗口：暴力在 LeetCode 中等题几乎全超时。

5. 双指针三件套：面试最省代码的技巧

5.1 三指针套路总览

套路 信号词 复杂度 典型题
快慢指针 链表环/中点/倒数第 K O(n)/O(1) 环检测、链表中点
左右指针 有序数组、两数之和 O(n)/O(1) 两数之和、反转数组
滑动窗口 连续子数组/子串 O(n)/O(1)~O(n) 最长无重复、最小覆盖

双指针的共同原理：让指针只前进不后退，把 O(n²) 的枚举压缩成 O(n) 的扫描——每步排除一个不可行的候选区间。面试答「为什么双指针 O(n)」就答这一句，比背代码有说服力。

5.2 快慢指针变体：找链表中点

用途：归并排序的链表版找中点、回文链表判断（先中点再反转后半）。「找中点」是快慢指针的第二高频用法，和环检测并列为链表题的两个必背模板。

5.3 动手验证：双指针 vs 暴力枚举两数之和

观察点：100 万元素的数组，暴力枚举直接等不到结果，双指针瞬间返回。判定标准：跑通且时间差肉眼可见——笔试现场你能靠体感判断「这题该用双指针」而不是「先暴力再说」。

6. 总结

6.1 面试速答表

面试题 一句话答案
数组和链表本质区别？ 数组连续内存下标寻址 O(1) 访问、O(n) 插入；链表指针修改 O(1) 插入、O(n) 访问
反转链表怎么写？ 三指针 prev/cur/next：存下 → 反转 → 前移 → 前移
链表有没有环？ 快慢指针，fast 两步 slow 一步，相遇即有环，O(n)/O(1)

算法篇一：复杂度分析与高频结构速查

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.3k Reading time ≈ 12 mins.

算法面试的第一题永远不是算法题，是「复杂度分析」——它能答题你不会，问你为什么 O(n) 你却答不出，面试直接结束。 本篇建立算法题的度量衡：大 O 直觉、常见复杂度对照表、数据结构操作复杂度速查、递归思维基本功。读完你能做到：看到任何一段代码/任何一道题，10 秒内说出复杂度，并解释为什么——这是后面所有手撕题的前提。

系列地图（数据结构与算法）：① 本文：复杂度分析与高频结构速查（度量衡） → ② 数组/链表/栈/队列与双指针（线性结构手撕） → ③ 哈希表/二叉树与递归（面试 80% 题型的落点）。

1. 复杂度是什么：算法题的统一度量衡

1.1 为什么不是「快 1 倍」而是「大 O」

两个程序谁快，不取决于运行时间（不同机器差别 100 倍），取决于数据量增长时，运行时间怎么增长。大 O 描述的是这个增长趋势，不是绝对时间：

记号 含义 直觉
O(1) 常数时间 数据翻倍，时间不变
O(log n) 对数时间 数据翻 1000 倍，时间加 10
O(n) 线性时间 数据翻倍，时间翻倍
O(n log n) 线性对数 排序的典型水平
O(n²) 平方时间 数据翻倍，时间×4
O(2ⁿ) 指数时间 数据加 1，时间翻倍

判断标准：把 n 从 1000 变 100 万，想一下时间怎么变。 1000 到 100 万是 1000 倍——O(n) 慢 1000 倍（1ms→1s 还能忍），O(n²) 慢 100 万倍（1ms→16 分钟，崩了），O(2ⁿ) 直接不可想象。复杂度分析的本质是问「数据大了之后我还活不活得下来」。

1.2 动手验证：亲手测出 O(n) 和 O(n²) 的差别

观察点：n 从 1000 到 10 万（×100），O(n) 慢了 100 倍，O(n²) 慢了 10000 倍——O(n²) 增长是 O(n) 的平方关系。判定标准：实际测出的增长比例接近「n 增长 10 倍，O(n²) 时间增长 100 倍」，即建立了大 O 的体感——体感比公式重要，面试手撕时你能靠体感判断「这解法是不是太暴力了」。

1.3 常见代码模式 → 复杂度速查

代码模式 复杂度 识别信号
单层循环 O(n) for (i = 0; i < n; i++)
双层循环各走 n O(n²) 两层嵌套，每层到 n
循环减半 O(log n) while (l <= r) { mid = l + (r - l) / 2; ... }
循环+减半 O(n log n) 排序、归并、外层线性内层二分
递归两个分支 O(2ⁿ) 斐波那契朴素递归
HashMap/Set 操作 O(1) 摊还 get/put/contains
数组按下标访问 O(1) arr[i]
链表按下标访问 O(n) list.get(i) 从头走

因果链：大 O 不是数学题，是「代码结构 → 资源消耗」的映射——循环层数决定 n 的次数，减半决定 log n，哈希访问摊还 O(1)。面试手撕时先想「我的解法什么复杂度」再说代码，是区分「会写」和「懂写」的分界线——因为面试官下一句永远跟「能不能优化」。

2. 复杂度进阶：常见的分析陷阱

2.1 只保留增长最快项

  • O(n² + n) → O(n²)：n 足够大时 n 项可以忽略；
  • O(2n + 100) → O(n)：常数系数忽略；
  • O(n log n + n²) → O(n²)：只留最高阶。

面试陷阱题：for i in 0..n: for j in 0..i: 内层随 i 变化，总次数 = 0+1+…+n-1 = n(n-1)/2 → O(n²)（不是 O(n)）。识别信号：双层循环内层上限是外层变量，总和还是 n² 级别——这个坑面试官最爱埋。

2.2 空间复杂度：面试总被忽略的另一半

做法 空间复杂度 信号
只用几个变量 O(1) 双指针、原地交换
用了一个与 n 等大的数组 O(n) 额外哈希表、栈
递归深度 n O(n) 递归栈（二分 O(log n)，链表递归 O(n)）

经典权衡题：「O(1) 空间的反转链表 vs 递归版」——迭代版原地改指针 O(1) 空间，递归版压栈 O(n) 空间。面试问「空间换时间」就是问这个权衡：哈希表 O(n) 空间换 O(1) 查询，是算法题最高频的优化手段（第二篇、第三篇会反复用到）。

2.3 摊还分析：为什么 ArrayList 的 add 是 O(1)

ArrayList.add() 满了要扩容（复制整个数组 O(n)），但均摊下来每个元素只被复制约 1 次（扩容翻倍），所以摊还 O(1)。因果链：扩容翻倍策略让「偶尔 O(n)、平均 O(1)」——这是工程里「用摊还思维设计数据结构」的经典，HashMap 的扩容同理。 面试答「ArrayList 和 LinkedList 区别」时，说出「add 均摊 O(1)」比「ArrayList 基于数组」高一个层次。

3. 数据结构复杂度总表：面试的「查表能力」

3.1 线性结构

操作 数组 链表 栈 队列
按下标访问 O(1) O(n) — —
头部插入/删除 O(n)（移动） O(1) — —
尾部插入/删除 O(1) 摊还 O(1)（有尾指针） O(1) O(1)
中间插入 O(n) O(n)（找位置） — —
查找 O(n) O(n) O(n) O(n)

选型判断：数组「下标访问快、插入慢」，链表「插入快、访问慢」——双指针题喜欢链表，滑动窗口题喜欢数组，这是第三篇的伏笔。

3.2 哈希与树

操作 HashMap TreeMap（红黑树） 数组二分
查找 O(1) 平均 O(log n) O(log n)
插入 O(1) 平均 O(log n) O(n)（移动）
有序遍历 ❌ 无序 ✅ O(n) ✅ O(n)
排序后 — — ✅

面试决策链：需要「按键查值」→ HashMap；需要「范围查询/有序输出」→ TreeMap；数据已有序 → 二分。「什么时候用哪个」是数据结构面试的一半题目——另一半是手撕。

4. 递归思维：算法题的基本功

4.1 递归的三要素：终止条件、子问题、返回值

90% 的树题和一半的链表题用递归解。递归不是「函数调自己」这个语法，而是把大问题拆成同构的小问题：

因果链：写递归的正确顺序是「先写终止条件，再写子问题调用，最后写返回值怎么组合」——三个要素缺一个就死循环（无终止）或结果错（组合错）。面试手撕递归题，先说出三要素再写代码，是稳拿分的节奏——面试官看的是你的思考过程。

4.2 递归的代价：栈溢出与重复计算

问题 表现 解法
栈溢出 深度 > 万级 StackOverflowError 改迭代；尾递归（Java 不优化）
重复计算 朴素斐波那契 O(2ⁿ) 记忆化（memo 缓存子问题结果）→ O(n)

面试高频追问：「递归怎么优化？」——标准答案三连：记忆化去重（O(2ⁿ)→O(n)）→ 空间优化（滚动数组 O(n)→O(1)）→ 改迭代。 每层追问都答出「少做了什么」，面试官知道你懂复杂度。

4.3 动手验证：递归与迭代的栈深度对比

观察点：递归深度受 JVM 栈大小限制（默认约 1 万层左右），迭代不受。判定标准：亲眼看到 StackOverflowError——记住这个画面：树的高度就是递归深度，退化成链的树（比如有序插入的 BST）递归会爆栈，所以面试里「树退化」要主动提到（第三篇详述）。

从输入 URL 到页面展示全链路

Posted on 2026-08-13 In 计算机网络 Word count in article: 3.5k Reading time ≈ 13 mins.

从输入 URL 到页面展示，是一次横跨五层模型、四个网络环节、两个进程域的完整旅程：DNS 解析、TCP 握手、TLS 协商、HTTP 请求、服务端处理、响应渲染——每一站都在前四篇讲过机制，本文把这条链完整走一遍：每一步消耗多少个 RTT、卡在哪个队列、优化的杠杆在哪。读完你会获得一张「全链路地图」：任何页面慢的问题，都能钉在图上某一站，说出它背后的机制和改法。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（可靠传输与代价）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 本文：全链路串讲，系列收官。

1. 全链路总览：一次请求的完整旅程

1.1 全景图：十二个环节

sequenceDiagram
    participant B as Browser
    participant D as DNS resolver
    participant S as Server
    B->>D: 1. resolve example.com (T1: DNS)
    D-->>B: IP + TTL (T1 done, cached)
    B->>S: 2. SYN (T2: TCP handshake, 1 RTT)
    S->>B: SYN+ACK
    B->>S: ACK
    B->>S: 3. TLS ClientHello (T3: TLS, 1-2 RTT)
    S->>B: ServerHello + cert
    B->>S: keys (T3 done)
    B->>S: 4. GET / HTTP/1.1 (T4: request/response, 1+ RTT)
    S-->>B: 200 + body (T4 done)
    Note over B: 5. parse & render (T5: local)
  • T1 DNS：可缓存（第 4 篇的 TTL 机制），首访耗 1 个查询 RTT；
  • T2 TCP：三次握手 = 1 个 RTT（第 2 篇）；
  • T3 TLS：1.3 版 1 个 RTT、1.2 版 2 个 RTT（第 3 篇 §4.1）；
  • T4 HTTP：请求-响应至少 1 个 RTT（第 3 篇）；
  • T5 渲染：本地计算，不耗网络 RTT。

性能总账 = RTT 数量 × RTT 大小：跨洋场景单个 RTT 约 100-200ms，一次完整首访 = 4-6 个 RTT ≈ 0.5-1.2 秒，这还没算服务端处理时间。所有网络优化手段（第 2 篇的连接复用、第 3 篇的 TLS 1.3/HTTP/2、第 4 篇的 DNS 缓存）都在做同一件事：削减 RTT 数量。

1.2 动手验证：curl 把时间拆开

观察点：第二次运行时 dns 明显变小（系统 DNS 缓存命中，第 4 篇 §1.3 的缓存层级）、tcp 变小（连接复用，第 3 篇 §2.1 的 keep-alive）——同一台机器两次访问，机制在悄悄给你省钱。判定标准：两次 dns/tcp 出现可观察差异即验证了缓存与复用机制；tls 与 ttfb 的差值就是「TLS 握手 + 服务端处理」两个 RTT 段。

2. 请求出发：从域名到加密通道

2.1 DNS 与连接建立：三个待机环节

  1. 输入 URL → IP：先查浏览器缓存，再查系统缓存，最后问递归服务器（第 4 篇 §1.3 四级缓存）——TTL 决定这次查询是否真实发生；
  2. TCP 握手：SYN/SYN+ACK/ACK 一个 RTT，顺带完成 MSS 协商（第 2 篇 §1.1/§2.2 的 1460 边界）；
  3. TLS 协商：证书链验证 + 密钥交换（第 3 篇 §4.1），TLS 1.3 压缩到 1 个 RTT。

2.2 深挖：「少一个 RTT」的三代努力

手段 省掉的 RTT 机制
HTTP keep-alive 后续请求 2 个 RTT 连接复用（第 3 篇 §2.1）
TLS 1.3 会话恢复（0-RTT） 重访 1-2 个 RTT 缓存会话密钥，ClientHello 直接带数据
TCP Fast Open / HTTP/3 QUIC 新连接 1 个 RTT 握手与首包数据合并发出（第 3 篇 §2.3）

因果链：三代优化是「第 2 篇 BDP 视角」的连续应用——RTT 是网络物理上限（光速 × 距离），协议层只能「少往返、多利用往返」；keep-alive 是复用已付出的握手，0-RTT 是提前预支握手结果。面试答「怎么优化首屏」先答 RTT 账，再答具体手段，是区分「背方案」和「懂机制」的分水岭。

2.3 动手验证：把首次访问和二次访问的握手差拍下来

观察点：二次访问的 tcp/tls 耗时断崖式下降——连接复用的现场。判定标准：第二次 total 明显小于第一次即通过；若 tcp 仍是完整 RTT，说明服务器没开 keep-alive（老版本配置的典型坑）。

3. 请求到达服务端：链路上的每个队列

3.1 网关链路：请求先过几道「分流器」

URL 解析出的 IP 大概率不是业务服务器，而是 LB：四层 LB 按五元组转发（第 1 篇 §5.1），七层 LB 按 URL 路由，CDN 在前面按地域拦截静态请求（第 3 篇 §3.2）。一次请求的网络旅程 = 客户端 → CDN/LB → 业务网关 → 应用服务器，每一跳都是一次 TCP 连接（或复用）。

3.2 深挖：一次请求在服务端过五道队列

请求进入服务器后，要穿过五道队列才能被业务代码处理：

flowchart LR
    SYNQ["1. half-open queue<br/>(SYN, kernel, Ch.2)"] --> ACCQ["2. accept queue<br/>(backlog, Ch.2)"]
    ACCQ --> THREAD["3. thread pool queue<br/>(OS series Ch.1)"]
    THREAD --> APP["4. app business logic"]
    APP --> DB["5. DB/MQ queue<br/>(if any)"]
队列 归属 溢出的表现 机制出处
半连接队列 内核 connect 超时、SYN_RECV 堆积 第 2 篇 §4.2
全连接队列（backlog） 内核+应用 accept 延迟、连接被丢 第 2 篇 §1.2
线程池队列 应用 排队等待、RT 上升 操作系统系列第 1 篇
中间件队列 应用/中间件 背压、丢弃 操作系统系列第 3 篇

因果链：服务端延迟 = 五道队列的排队时间之和——排查「接口慢」先问「慢在哪个队列」：ss -tan 看 SYN_RECV/ESTABLISHED 堆积（前两道，内核视角），jstack 看线程池排队（第三道，JVM 视角），DB 慢查询日志看第五道——每道队列对应一套工具和一种机制，这就是第 4 篇「分层定位」在服务端的镜像。

3.3 动手验证：看一个请求在服务端留下的时间戳

观察点：ttfb（首字节）≈ 200ms + RTT——服务端处理时间直接进了 TTFB。判定标准：ttfb ≈ 0.2s 即验证了「响应时间 = 网络 RTT + 服务端排队/处理」；再把 sleep 改成 0 对比，TTFB 骤降——这就解释了为什么「接口慢」先查服务端而不是网络。

4. 响应与渲染：最后一公里的两个世界

4.1 响应路径：缓存决定「走网络还是走本地」

响应回来先过浏览器缓存判断：强缓存命中（Cache-Control 有效期内）根本不发请求；协商缓存命中回 304 只传头（第 3 篇 §3.1）——缓存是页面里唯一「不花钱的环节」，优先级永远最高。

4.2 深挖：渲染是另一条「流水线」

拿到 HTML 后，浏览器本地执行：解析 HTML 建 DOM、解析 CSS 建 CSSOM → 合并成 Render Tree → Layout 计算几何 → Paint 绘制。关键资源（CSS 阻塞渲染、JS 阻塞解析）会卡住流水线——渲染阶段的性能问题和网络无关，但优化目标和网络一致：减少环节、减少体积：

手段 省什么 机制
合并/压缩 CSS JS 请求数与体积 少 RTT、少解析
CDN 分发静态资源 网络距离 DNS 就近（第 4 篇）+ HTTP 缓存（第 3 篇）
字体/图片懒加载 首屏资源数 渲染树更快完整
HTTP/2 并发上限 单连接多路复用（第 3 篇 §2.2）

4.3 动手验证：用浏览器瀑布图验证「排队与复用」

打开 DevTools → Network → 勾选「Disable cache」刷新两次：第一次全部资源耗时高（无缓存 + 串行握手），第二次明显降低（缓存 + 连接复用）。观察点：瀑布图里每个资源的时间条由 Queued/Stalled/DNS/Connect/Request/Response 组成——这就是 §1.1 的 RTT 账在浏览器里的可视化。判定标准：能读出「二次访问 DNS 段消失、Connect 段只剩一个」即掌握读图能力。

5. 全链路优化：每个环节的杠杆

5.1 优化杠杆表：把「慢」钉在图上

环节 慢的症状 杠杆 机制出处
DNS dns 时间长 预解析（dns-prefetch）、TTL 合理设置 第 4 篇
TCP connect 长 keep-alive、连接池、QUIC 第 2/3 篇
TLS appconnect 长 TLS 1.3、会话恢复 第 3 篇
网络 RTT 各段都长 CDN 就近、回源优化 第 1/4 篇

5.2 深挖：延迟预算——从感受倒推预算

性能优化的第一步不是优化，是定预算：首屏目标 2 秒 → 拆给各环节（DNS 0.2s + 握手 0.2s + 首包 0.5s + 渲染 0.8s + 余量）→ 各环节对照预算找超标项。因果链：预算制把「页面慢」变成「某环节超预算」——这与第 4 篇分层定位法（第 3 篇 §3.1）是同一方法论的两副面孔：一个是排障定位，一个是目标管理。线上实践常配合 Web Vitals（LCP/FID/CLS）监控，把「用户感受到的慢」翻译成「哪个环节的预算被击穿」。

5.3 动手验证：本地完整复现一次「优化前 → 优化后」

观察点：每次请求 tcp 都完整计一次——HTTP/1.0 短连接模式 = 每次请求付一次握手；对比 §2.3 的 baidu 二次访问，同一台机器两种世界观。判定标准：tcp 每次都非零即复现了「无 keep-alive 的代价」，而 2.3 的对比数据就是 keep-alive 的价值证明——本节实验给「为什么 HTTP/1.1 默认 keep-alive」提供了亲手数据。

DNS 与网络排查实战

Posted on 2026-08-13 In 计算机网络 Word count in article: 3.2k Reading time ≈ 12 mins.

DNS（Domain Name System）是把域名翻译成 IP 的分层数据库：浏览器访问任何网站的第一件事，都是问 DNS「这个域名在哪个 IP」。 它本身是一次「应用层查询」，却发生在 TCP 连接之前——解析快慢直接进首屏时间，解析错误直接断网。本文回答四个问题：解析链路怎么走、缓存为什么关键、DNS 在生产里扮演什么角色（LB/CDN/HTTPDNS）、网络故障怎么按分层定位——并把系列工具链收拢成「症状 → 层 → 工具 → 根因」的完整排查法。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（可靠传输与代价）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（本文：工具收拢） → ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. DNS 解析：从域名到 IP 的分层接力

1.1 为什么需要 DNS：名字与地址的分离

IP 是「地址」，域名是「名字」——名字的意义是：可以改地址、可以有多个地址、可以全球唯一。这带来两个直接能力：

  1. 负载均衡：一个域名配多个 A 记录（www.baidu.com → 10.0.0.1/10.0.0.2/10.0.0.3），解析时随机返回——DNS 是最原始的负载均衡，比四层/七层 LB（第 1 篇 §5.1）更靠前：它直接决定「请求发给哪台机器」；
  2. CDN 接入：域名用 CNAME 指向 CDN 厂商的域名，CDN 的权威服务器按用户地理位置返回就近节点 IP——第 3 篇讲的「CDN 缓存」能生效，前提是 DNS 把用户导到了离他最近的节点。

1.2 递归与迭代：一次解析的完整接力

递归查询：客户端只问「帮我查 www.baidu.com」，本地递归服务器负责搞定；迭代查询：递归服务器逐级问根服务器「.com 找谁」、问 .com 顶级服务器「baidu.com 找谁」、最后问 baidu.com 的权威服务器「www 的 IP 是」：

flowchart TD
    C["Browser"] -->|"recursive: www.baidu.com?"| R["Local recursive resolver<br/>(ISP / 8.8.8.8 / 114.114.114.114)"]
    R -->|"iterative: who is .com?"| ROOT["Root servers (13 groups)"]
    ROOT -->|".com TLD server ->"| R
    R -->|"iterative: who is baidu.com?"| TLD[".com TLD servers"]
    TLD -->|"baidu.com authoritative ->"| R
    R -->|"iterative: A record of www?"| AUTH["baidu.com authoritative servers"]
    AUTH -->|"IP 1.1.1.1 + TTL"| R
    R -->|"IP 1.1.1.1"| C

因果链：这个接力是「第 1 篇分层的递归应用」——每层只回答「下一层去哪问」的问题，与路由器「只认下一跳」完全同构（第 1 篇 §4.1）；区别是路由器转包、DNS 转「问题」。面试速记：客户端问递归（一次问完），递归服务器逐级迭代（分级追问）。

1.3 缓存层级：TTL 是唯一的失效开关

解析结果会被四级缓存：浏览器 → 操作系统 → 本地递归服务器 → 各级 DNS 服务器，每级缓存按 TTL（记录生存时间，A 记录常见 60-600 秒） 过期：

缓存层 谁持有 特点
浏览器缓存 浏览器进程 最快，几十秒级
操作系统缓存 /etc/hosts + 系统解析器 hosts 优先于一切，可手动覆盖
本地递归服务器 ISP/公共 DNS 秒级 TTL，服务所有用户
权威服务器 域名所有者 无缓存，TTL 由它下发

TTL 是 DNS 的命门：域名切换 IP 后，「生效时间 = 最高 TTL 的缓存层过期时间」——TTL 设 600 秒的域名切 IP，最坏 10 分钟才全部生效。生产「切了 IP 用户还在访问老机器」的根因九成在这。

1.4 动手验证：dig 把解析拆开看

观察点：+trace 输出从根服务器的提示开始逐级展开——递归与迭代的现场；多个 A 记录说明该域名在做 DNS 负载均衡。判定标准：+trace 里能看到「根 → .com → 权威」三级且最后给出 IP，就亲眼看到了 §1.2 的接力。

2. DNS 的生产形态：LB、CDN 与 HTTPDNS

2.1 深挖：CDN 与 HTTPDNS——DNS 的两个生产难题

问题 1：就近调度不精准。 系统 DNS 由 ISP 分配，递归服务器所在位置不等于用户位置——CDN 拿递归服务器的 IP 判断用户地域，可能把北京用户导到上海节点。问题 2：DNS 可被劫持。 公共网络/运营商可能篡改 UDP 53 的响应（污染），把域名指到广告/钓鱼 IP。

两个问题的解法汇聚到移动端 HTTPDNS：App 不走系统 DNS，而是直接 HTTP 请求厂商的解析 API（如 http://119.29.29.29/d?dn=www.xxx.com）拿到 IP——用 HTTP（第 3 篇的协议）替代 UDP 53（DNS 原生的脆弱通道），既绕开劫持（HTTPS 加密 + 厂商鉴权），又能拿到基于用户真实出口 IP 的精确调度。

因果链：DNS 用 UDP 53 是因为「单次请求-响应、无状态」（第 2 篇 UDP 对比表）——这个轻量设计是性能优势，也是被劫持的漏洞来源；HTTPDNS 是「用应用层更重的通道换可靠性」的典型交易，与 HTTP/3 换掉 TCP（第 3 篇 §2.3）是同一个决策模式：下层通道给不了的保证，换个通道实现。

2.2 深挖：容器里的 DNS——K8s 的 CoreDNS

K8s 集群里 Pod 间通信靠 Service 名，解析由集群内 DNS（CoreDNS）完成：Pod 的 /etc/resolv.conf 指向 CoreDNS，且带 search 域（default.svc.cluster.local）——短域名自动补全域名后缀：

因果链：Pod 访问 my-service 会依次试 my-service.default.svc.cluster.local → my-service.svc.cluster.local → my-service.cluster.local——search 域让「短名可用」是牺牲查询次数换来的；排查 K8s 里「跨 namespace 访问用短名失败」就是忘了加全限定名。这是 DNS 机制在容器时代的直接变形。

2.3 常见 DNS 故障速查

症状 原因 处理
切了 IP 用户还在访问旧的 各级缓存未过期（TTL 太长） 切换前先调低 TTL（如 60s），等生效再切

2.4 动手验证：复现一次「TTL 缓存」观察

观察点：两次查询 ANSWER 区IP 相同、TTL 递减——你在看一个活着的缓存条目在倒数计时。判定标准：TTL 从 600 → 590 左右即验证了「缓存按 TTL 倒计时」的机制；这也预告了 2.3 表第一行的生产教训（TTL 设多长，切换就等多长）。

3. 网络排查实战：症状 → 层 → 工具

3.1 分层定位法：四问定层

网络故障排查的核心是先定层、再用该层的工具（第 1 篇 §1.3 的雏形，现在收拢成完整流程）：

flowchart TD
    FAIL["App error / timeout"] --> Q1{"DNS resolves?"}
    Q1 -- No --> T1["dig / nslookup<br/>-> DNS layer problem"]
    Q1 -- Yes --> Q2{"TCP connects?"}
    Q2 -- No --> T2["nc / ss / telnet<br/>-> network / firewall / LB"]
    Q2 -- Yes --> Q3{"TLS handshake?"}
    Q3 -- No --> T3["openssl s_client<br/>-> cert / TLS config"]
    Q3 -- Yes --> Q4{"HTTP status?"}
    Q4 -- "4xx" --> T4A["request problem (client)"]
    Q4 -- "5xx" --> T4B["server / upstream problem"]

每一层的工具与判定标准：

层 工具 通过标准
DNS dig 能返回 A 记录
TCP nc -vz host port succeeded 字样
TLS openssl s_client -brief 能输出证书与协议
HTTP curl -i 拿到状态码
应用 服务日志 有对应请求日志

3.2 案例复盘：三个真实排障

案例一：解析到老 IP

环节 内容
症状 域名切换新机器后，部分用户仍访问旧机器，旧机器已关，用户报「打不开」
工具 dig +short 在本机解析出新 IP；dig @8.8.8.8 +short 也是新 IP；但 nslookup 走运营商 DNS 仍是旧 IP
根因 运营商递归服务器缓存未过期（切换前 TTL 设的 600s）——§2.3 第一行的标准场景
处理 等 TTL 过期自然收敛；此后切换流程固定为「先降 TTL 至 60s，等 24h 再切」

案例二：客户端偶发连接被重置

环节 内容
症状 移动端间歇性 RST（连接被重置），PC 正常
工具 抓包看到 RST 直接回；nc -vz 偶发失败；对比不同网络（WiFi/4G）
根因 运营商/中间设备对 UDP 53 与长连接做干扰；或四层 LB 连接数限制触发重置
处理 移动端换 HTTPDNS（§2.1）；服务端确认四层 LB 连接复用配置

案例三：502 与 504 的判别

环节 内容
症状 网关报 502 或 504，业务侧「看起来没挂」
工具 curl -i 确认状态码；nc -vz 上游IP 端口 测 TCP；看上游响应时间
根因 502 = 连不上上游（端口/防火墙/上游没起）；504 = 连上了但超时（上游慢、队列满）——第 3 篇 §1.2 的判别落地
处理 502 查网络与进程；504 查上游性能与超时配置（网关 proxy_read_timeout）

三个案例的共同模式：先 dig 排除 DNS、再 nc 排除 TCP、最后才是应用层——按分层顺序排查，每层一个工具一次判定，永远不跳层。

3.3 动手验证：完整跑一遍分层定位

观察点：四条命令依次通过/失败的位置，就是故障所在的层——把「不知道哪坏了」变成「明确坏在第几层」。判定标准：任一步失败后，该层对应的工具（dig/nc/openssl/curl）就是下一步排查的起点；这个流程值得存成 netcheck.sh，任何网络问题先跑一遍（与操作系统系列第 5 篇的 sos.sh 同款习惯）。

4. 总结

4.1 面试速答表

面试题 一句话答案
DNS 为什么是分层结构？ 根 → 顶级 → 权威逐级授权，每层只回答「下一层去哪问」——与路由器逐跳转发同构
递归和迭代查询的区别？ 客户端问递归服务器（一次问完）；递归服务器逐级迭代追问（分级接力）
域名切换 IP 为什么生效慢？ 各级缓存按 TTL 倒计时，生效时间 = 最高 TTL 的缓存层过期时间
DNS 怎么做负载均衡？ 一个域名多个 A 记录轮询返回；CNAME 到 CDN 后按地域返回就近 IP
为什么移动端用 HTTPDNS？ 系统 DNS 用 UDP 53，可被劫持且就近调度不精准；HTTPDNS 走加密 HTTP 绕开
网络故障排查第一步？ 定层：dig 排除 DNS → nc 排除 TCP → openssl 排除 TLS → curl 看 HTTP
502 和 504 怎么分？ 502 连不上上游，504 连上了但超时——排查方向不同

4.3 工具速查表

工具 看什么 对应环节
dig +trace 完整解析链路 1. 递归/迭代
dig +short A 记录与 TTL 1. 缓存/LB

实操建议：

  1. 任何「网站打不开」先跑 dig → nc -vz → openssl → curl 四条命令，把故障钉在某一层再动手——不跳层。
  2. 域名切换的流程固定成「先降 TTL → 等 24h → 切换 → 观察」，这条流程的每一步都在为缓存的 TTL 买单。
  3. 移动端网络请求一律接入 HTTPDNS；服务端对外域名用公共 DNS 做双保险探测，发现解析异常立即告警。
