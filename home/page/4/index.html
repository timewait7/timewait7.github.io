容量规划与分片：什么时候才该上 Cluster

Posted on 2026-10-25 In 数据存储 Word count in article: 3.9k Reading time ≈ 14 mins.

「Redis 扛不住了」这句话，八成是「key 太多」或「value 太大」，而不是「QPS 太高」。实测单实例 GET 在 8 个并发连接时就到了 27.5 万 rps，加到 128 连接也只到 32.9 万（+19%），而 p50 从 0.023 ms 涨到 0.199 ms（8.6 倍）——加并发不会让单实例更快，只会让延迟变高。

这一篇是收官篇，回答三个问题：单实例的上限在哪、什么时候该分片、分片之后要多付什么代价。最后附全系列 12 篇的总表。

1.1 QPS：8 个连接就到顶了

单实例、10 万 key 已预热、GET 压测：

并发连接 QPS p50
1 32,916 0.031 ms
8 275,103 0.023 ms
32 310,078 0.055 ms
64 322,581 0.103 ms
128 328,947 0.199 ms

读法：

  1. 8 个连接就把单核吃满了（27.5 万 rps）；
  2. 从 8 加到 128，QPS 只涨 19%，p50 涨了 8.6 倍；
  3. 所以「加连接数」在单实例上不是扩容，是用延迟换一点点吞吐。

这是 loopback 的数字，生产环境受网络与客户端影响会更低；但「拐点在个位数到几十个连接」这个结论是普适的——因为 Redis 执行命令只有一个线程。

1.2 内存：按 key 数算，不是按 value 大小算

实测（MEMORY USAGE 抽样）：

value 大小 单 key 实际占用 额外开销 1 亿 key 估算
64 B 128 B 64 B 11.9 GB
1 KB 1,328 B 304 B 123.7 GB
10 KB 12,336 B 2,096 B 1,148.9 GB

三个必须知道的点：

  1. 小 value 的开销占比最高（64B 的 value 实际占 128B，开销 100%）；
  2. 大 value 有 jemalloc size class 效应（10 KB → 12 KB 桶，多 20%）；
  3. 1 亿个 10 KB 的 key 要 1.1 TB 内存——这时候必须分片，不是为了 QPS。

2. 分片：什么时候该上 Cluster

2.1 决策路径

flowchart TD
    A["Capacity alert"] --> B{"CPU-bound?<br/>QPS at knee"}
    B -- yes --> C["Read scaling:<br/>replicas + client routing"]
    C --> D{" writes also hot?"}
    D -- yes --> E["Sharding"]
    B -- no --> F{"memory-bound?"}
    F -- yes --> G{"can we shrink keys?<br/>TTL / big key split"}
    G -- yes --> H["Fix data model first"]
    G -- no --> E
    E --> I["Choose shard key,<br/>then reshard plan"]

判断顺序：先确认是 CPU 还是内存瓶颈 → 能靠读扩展/数据治理解决就不分片 → 都不行才分片。

2.2 三种分片方式

方式 扩容影响 客户端复杂度 适用
客户端分片（取模） 换 N 就全量迁移 高（业务自己算路由） 早期、分片数固定
代理分片（Codis/Twemproxy） 中 低（客户端无感） 已有代理层
Redis Cluster 槽迁移，可在线 中（要处理 MOVED/ASK） 主流选择

2.3 分片键：三个判据

判据 好 坏
均匀 用户 ID 哈希 状态、地区
查询能定位单片 user:{id}:profile 只有 SCAN 类需求
允许跨片？ 单 key 操作 跨片 MGET/Lua（⑥ 实测 CROSSSLOT）

hash tag 是分片设计的一部分：{user:1}:name 与 {user:1}:age 会落到同一个槽（⑧ 实测：都是 10778），这是「同一实体的多字段需要原子操作」的前提。

2.4 分片的真实代价

代价 具体表现 缓解

6. 动手验证：四个可复现实验

6.1 动手验证：测出你自己实例的 QPS 拐点

预期观察点：QPS 在 8~32 连接后平台化，p50 随连接数上升（本文 27.5 万 → 32.9 万，p50 0.023 → 0.199 ms）。

判定标准：QPS 随连接数持续增长 → 你的实例还有余量；QPS 下降 → 有 CPU 争抢或客户端瓶颈。

6.2 动手验证：按 key 数估算内存

预期观察点：64B→128B、1KB→1328B、10KB→12336B（本文）。

判定标准：实测值远大于 value → 有 jemalloc size class 取整，评估容量时要按实测乘 key 数。

6.3 动手验证：验证 hash tag 同槽

预期观察点：两个 {user:1}:* 槽号相同（本文 10778），user:2:name 不同（15992）。

判定标准：两个 hash tag key 槽号不同 → 花括号位置写错了（必须包住要哈希的部分）。

6.4 动手验证：算一次容量

预期观察点：输出应给出「QPS 需求」与「内存需求」两行，取较大者作为分片数。

判定标准：两者数量级差异很大 → 说明瓶颈单一，先按瓶颈那一侧扩容，别盲目分片。

5. 总结

5.1 面试速答表

面试题 一句话答案

加连接能提升 QPS 吗 几乎不能：8→128 连接 QPS +19%，p50 +8.6 倍

1 亿个 key 要多少内存 64B value 约 11.9 GB；10KB value 约 1.1 TB（本文实测）
什么时候该分片 QPS 到拐点且读扩展无效，或内存超过单机
Redis Cluster 有什么代价 跨槽操作受限、MOVED 多一次 RTT、运维复杂

maxclients 默认多少 10000（本文实测）

5.4 实操建议

  1. 先算容量再谈分片：QPS、内存、连接数三个维度分别算，缺哪个补哪个。
  2. 单实例的 QPS 拐点比你想象的早（本文 8 个连接），别用「加连接」当扩容。
  3. 内存按 key 数 × 单 key 实际占用估，别用 value 大小乘（会差 2 倍以上）。
  4. 分片键必须在查询里出现，否则跨片查询会让分片失去意义。
  5. 分片前先做大 key 清理与 TTL 治理，否则分片只会把问题放大。

系列完结。十二篇的因果链是一条：先量（①）→ 算账（②）→ 数据与内存（③④）→ 单线程与原子性（⑤⑥）→ 持久化与高可用（⑦⑧）→ 应用模式（⑨⑩⑪）→ 最后才谈容量（⑫）。

分布式锁与限流：从 SET NX 到 Redisson

Posted on 2026-10-25 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

SET NX 只能保证「同一时刻只有一个客户端能写进去」，它不保证「这把锁一直属于你」。本文实测了三种锁失效：用 DEL 释放会把别人的锁删掉；任务执行时间超过 TTL 会出现两个持有者；主库宕机 + 旧主未隔离（脑裂）时，两个节点上会各有一把同名锁，两个客户端同时认为自己独占。

后半篇换到限流：固定窗口在边界上能放行 2 倍的请求（实测 100/s 的限制放行了 200 个），滑动窗口与令牌桶分别是 100 和 117。

2.3 主从切换：两个节点各有一把同名锁（实测）

先说我没复现出来的那个实验：在 loopback 上，SET 之后立刻断链、立刻杀主，从库已经同步了这把锁（复制延迟 <1ms），所以哨兵提升后 B 拿不到锁。

4. RedLock 的争议在争什么

观点 主张 核心论据
antirez（RedLock） 向 N 个独立 Redis 加锁，多数成功即视为持有 单点故障下仍能互斥
Kleppmann RedLock 不能保证「锁的持有者一定是执行者」 依赖时钟假设；GC 停顿会让持有者失去锁而不自知

争论的本质不是「RedLock 实现得好不好」，而是「你到底需不需要一把绝对安全的锁」：

你的需求 建议
防止重复执行（可幂等） 单实例 SET NX + 幂等 + 唯一索引兜底
互斥访问共享资源（不可幂等） 需要 fencing token（每次加锁递增的版本号，下游校验）
强一致（金融扣减） 别用 Redis 锁，用数据库行锁/事务（MySQL 系列 ⑤⑥）

一句话：Redis 锁适合「防重复」，不适合「防并发写」。后者要靠数据库约束或 fencing。

缓存与数据库一致性：更新顺序与不一致窗口

Posted on 2026-10-25 In 数据存储 Word count in article: 3.4k Reading time ≈ 13 mins.

「先删缓存再更库」是四种常见写法里唯一 100% 出错的。实测 60 轮并发读写：先更库再删缓存 0 轮不一致，延迟双删 0 轮，只更库不动缓存 60 轮不一致，而「先删缓存再更库」60 轮全部不一致——因为读线程在删缓存之后、更库之前回源，把旧值又写回了缓存。

本文用真实的 MySQL + Redis + 8 个读线程，把四种写策略的「不一致率」和「不一致窗口」都量出来。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性（本文） → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：⑨ 讲「读不到怎么办」，本文讲「写的时候怎么保证读到的不是旧值」；⑧ 的主从延迟会让「更库成功但读到旧库」也变成一种不一致来源。

1. 四种写策略

A 先更库，再删缓存 最常见，Cache-Aside 标准做法 0/60 不一致
B 先删缓存，再更库 「让缓存先失效更保险」 60/60 不一致
C 先删缓存，更库，延迟再删一次 延迟双删 0/60 不一致
D 只更库，不动缓存 靠 TTL 自然过期 60/60 不一致

2. 实测：谁会真的不一致

方法：60 轮，每轮 8 个读线程持续读（读不到就回源并写回缓存），写线程执行一次更新，立刻对比缓存与数据库。

策略 不一致轮数 不一致率 结束时 cache / db
A 先更库再删缓存 0 / 60 0% B / B ✅
B 先删缓存再更库 60 / 60 100% A / B ❌
C 先删-更库-延迟再删 0 / 60 0% B / B ✅
D 只更库不动缓存 60 / 60 100% A / B ❌

为什么 B 全错：读线程在「缓存已删、数据库还没更新」的窗口里回源，读到旧值 A 并写回缓存。写线程随后把数据库改成 B，但缓存里已经是 A——而且没有任何机制会再删它，直到 TTL 到期。

2.1 B 的危险在于「持续」而不是「短暂」

策略 不一致持续时间 影响
A 等于「更库到删缓存」的间隔（本文 20ms → 实测窗口 23ms） 短暂，可接受
B 直到 TTL 到期（TTL 1 小时就是 1 小时） 持续，不可接受
C 同 A（多一次删除兜底） 短暂
D 直到 TTL 到期 持续，但 TTL 短时可接受

这就是「先删缓存再更库」被很多人认为「更安全」的误区：它看起来让旧数据更快失效，实际上制造了一个「读回源把旧值写回」的机会窗口，而且窗口之后无人修复。

3. 不一致窗口有多宽

策略 配置 实测最长不一致窗口

C 异步删除（模拟 binlog 订阅，50ms 轮询） 轮询间隔 50ms 58 ms
B 先删缓存再更库 间隔 20ms 持续到 TTL（本文不设上限）

5. 更强的方案：读主库 + 版本号

方案 一致性 性能 适用
A 先更库再删缓存 最终一致（窗口 ~ms） 高 绝大多数场景
延迟双删 最终一致（窗口更小） 高 删缓存可能失败时兜底
binlog 订阅 最终一致（窗口 = 消费延迟） 高 需要覆盖非应用写入
读写都走主库 强一致 低（主库压力翻倍） 金额、库存等关键字段
缓存带版本号 + 校验 可检测 中 对一致性要求高的读

「读主库」的代价很实在：⑧ 说过主从是异步复制，读写分离时读从库可能读到旧值。所以「强一致 = 读写都走主库」，这是容量与一致性的直接兑换。

5.1 一个容易被忽略的不一致来源：主从延迟

即使你用了 A 策略，如果读请求走了从库：

时序 结果
写主库（成功） 主库 = B
删缓存（成功） 缓存空
读请求 → 从库（还没同步到 B） 读到 A，写回缓存 = A
从库追平 数据库 = B，缓存还是 A

这是「A 策略 + 读写分离」组合下的隐藏 bug：删缓存的窗口虽然只有毫秒，但读从库可能读到回滚前的值。处理办法：

手段 说明
写后一段时间内强制读主库 比如 500ms 内该 key 走主库
用 GTID/位点等待 从库等到指定位置再返回（MySQL 系列 ⑧）
缓存删除加「延时双删」 覆盖主从延迟窗口

5.2 动手验证：复现 B 的 100% 不一致

预期观察点：并发跑 60 轮，几乎每轮结束时 redis.get(key) 都是旧值 A，而数据库是 B。

判定标准：

  • 不一致率接近 100% → 你用了「先删缓存再更库」，立刻改成先更库；
  • 不一致率 0% 但偶发 → 检查是不是读写分离读到了从库（5.1）；
  • 延迟双删后仍然不一致 → 延迟时间太短，或第二次删除失败没重试。

5.3 为什么是「删缓存」而不是「更新缓存」

做法 并发写两次的结果 问题
更新缓存 请求 1 写 DB=A、缓存=A；请求 2 写 DB=B、缓存=B 如果顺序错乱（缓存 B 先写、A 后写），缓存停在 A，DB 是 B
删除缓存 两次都只是 DEL 幂等，谁先谁后结果一样，下一次读会回源到最新值

本质：删除是幂等操作，更新不是。并发场景下「谁最后写缓存」无法保证，而删除没有这个问题——代价只是下一次读多一次回源（几十微秒到几毫秒）。

什么时候可以更新缓存：写少读多、且能保证串行（比如单线程消费 binlog），此时更新缓存可以省掉一次回源。

7. 动手验证：四个可复现实验

7.1 动手验证：复现「先删缓存再更库」的 100% 不一致

预期观察点：60 轮里 60 轮结束时缓存是旧值、数据库是新值（本文 B 策略 60/60）。

判定标准：不一致率很低 → 你的窗口太窄（更库太快）或读并发太低，把间隔调到 50ms 再试。

7.2 动手验证：测量不一致窗口

预期观察点：A 策略窗口 23 ms、异步删除 58 ms（本文）；B 策略会持续到 TTL。

判定标准：窗口远大于预期 → 删缓存这一步被阻塞（连接池/网络），或主从延迟导致读到了旧库。

7.3 动手验证：验证延迟双删

预期观察点：60 轮 0 不一致（本文）。

判定标准：仍有不一致 → 延迟时间不够（小于一次回源+写回耗时），或第二次删除失败没重试。

7.4 动手验证：验证读写分离导致的不一致

预期观察点：从库返回旧值并被写回缓存，从库追平后缓存仍是旧值。

判定标准：没有复现 → 复制太快（loopback）或读请求没有路由到从库。

6.4 实操建议

  1. 默认用「先更库、再删缓存」，别用「先删缓存再更库」——实测 100% 出错。
  2. 删缓存要重试（消息队列或重试表），一次失败就可能长期不一致。
  3. 核心字段读主库，用容量换确定性；非核心接受毫秒级窗口。
  4. 读写分离时，写后 500ms 内强制读主，避免「读到从库旧值又写回缓存」。

缓存三大问题：穿透、击穿、雪崩的量化与解法

Posted on 2026-10-25 In 数据存储 Word count in article: 3.6k Reading time ≈ 13 mins.

缓存不是「读不到就查库」这么简单。实测一组数字：全命中时数据库压力是 0 QPS；一旦换成「查不存在的数据」，同样的并发把 9,241 QPS 全打到 MySQL 上——而 MySQL 单机点查的拐点大约 5 万（MySQL 系列 ⑫ 实测），也就是说这一个接口就能吃掉近五分之一的总容量。

这篇用真实的 Redis + MySQL 环境，把穿透、击穿、雪崩三种问题各跑一遍，并量化四种解法的效果。

系列地图（Redis 实战路线，12 篇）

2. 穿透：查不存在的数据

2.1 实测：全命中 vs 全穿透

环境：Redis 7.4.11 + MySQL 8.0，users 表 10 万行，50 线程、每场景 5 秒，客户端复用连接。

场景 总请求 QPS 未命中 DB 查询 DB QPS
A 全命中（1000 个热 key） 78,374 15,669 0 0 0
B 穿透（1 万个不存在的 id，不缓存空值） 46,446 9,241 46,446 46,446 9,241

两条结论：

  1. 缓存正常工作时，数据库压力是 0——这就是缓存的价值；
  2. 穿透时，每一个请求都变成一次数据库查询，且 QPS 从 15,669 掉到 9,241（-41%），因为数据库比 Redis 慢一个数量级。

2.2 解法一：缓存空值

把「查不到」也缓存起来（值为空字符串，短 TTL）：

场景 总请求 QPS DB 查询 DB QPS 相对穿透
B 无保护 46,446 9,241 46,446 9,241 —
C 空值缓存（TTL 5s） 63,443 12,634 10,011 1,994 DB -78%

代价：如果攻击者每次用不同的随机 ID，空值缓存也挡不住（缓存会被垃圾 key 填满）。这时需要布隆过滤器或参数校验。

2.3 解法二：布隆过滤器

用 Redis 的 bitmap 实现一个 100 万位、3 个哈希函数的布隆过滤器，预先把 10 万个存在的 id 写进去：

场景 总请求 QPS DB 查询 DB QPS 误判
D 布隆过滤器 36,446 12,053 554 183 1.5%

    BF -- "不存在（确定）" --> N["直接返回空<br/>不查库"]
    BF -- "可能存在（概率）" --> DB["查 MySQL"]
    DB --> W["回写缓存"]

2.4 动手验证：在你自己的库上复现穿透

预期观察点：用一个不存在的 ID 循环压测，INFO stats 的 keyspace_misses 与 MySQL 的 Questions 同步增长。

判定标准：

  • MySQL Questions 增速 ≈ 应用 QPS → 完全穿透，必须加保护；
  • 加了空值缓存后 MySQL 增速降到 1/5 以下 → 生效；
  • 空值缓存也挡不住 → 请求的 ID 是随机的，上布隆过滤器。

3. 击穿：热 key 失效的瞬间

3.1 实测：50 并发同时重建

把数据库查询人为加 50ms 延迟（模拟慢 SQL），然后让热点 key 失效，50 个线程同时来：

方案 请求 未命中 DB 查询
无互斥（各自回源） 48,264 50 50
互斥重建（SET NX） 49,097 442 2

50 → 2，25 倍差距。关键在于：如果没有互斥，50 个线程会同时发起 50 条相同的慢查询，数据库瞬间多出 50 个 50ms 的查询；并发再高一点，连接池就被打满（MySQL 系列 ⑪ 的因果）。

3.2 互斥重建的实现

sequenceDiagram
    participant A as Thread A
    participant B as Thread B
    participant R as Redis
    participant D as MySQL
    A->>R: GET hot:1 -> nil
    B->>R: GET hot:1 -> nil
    A->>R: SET lock:hot:1 1 NX EX 3 -> OK
    B->>R: SET lock:hot:1 1 NX EX 3 -> nil
    A->>D: SELECT ...（50ms）
    B->>B: sleep 5ms，回头再读缓存
    A->>R: SET hot:1 value EX 60
    A->>R: DEL lock:hot:1
    B->>R: GET hot:1 -> value

两个必须注意的点：

问题 后果 对策
锁没有超时 回源线程崩了，锁永久占住，所有请求都拿不到 EX 必须设，且大于最长回源时间
没抢到锁的线程直接返回 null 用户看到「数据不存在」 短暂自旋 + 重试读缓存，或返回降级数据

3.3 另一种解法：逻辑过期

不删 key，而是把「过期时间」放在 value 里；读到过期数据时，先返回旧值，再异步触发重建。

方案 一致性 延迟 实现复杂度
互斥重建 强（等新值） 一个回源周期 低
逻辑过期 弱（短暂返回旧值） 无等待 中（要异步线程池）

选型：能接受「短暂旧数据」用逻辑过期（比如商品详情）；必须读到最新值的用互斥重建。

3.4 动手验证：量一次击穿

预期观察点：无互斥时，MySQL 的 Questions 会在 key 失效的瞬间跳一下（等于并发数）；有互斥时只跳 1~2。

判定标准：

  • 跳变量 ≈ 并发线程数 → 没有互斥，必须修；
  • 跳变量 ≈ 1 → 互斥生效；
  • 跳变量远大于并发数 → 有别的原因（比如缓存写回失败、内存淘汰）。

4. 雪崩：大规模同时失效

4.1 实测：1 万个 key 同时失效

场景 请求 未命中 DB 查询 DB QPS
1 万个 key 同时失效 30,324 9,581 9,581 3,194
只有 20% 失效（模拟抖动） 45,026 2,003 2,003 668

同时失效让数据库压力涨到 4.8 倍，而且这不是瞬时尖刺——9,581 次查询分布在 3 秒里，持续压着数据库。

4.2 解法一：TTL 抖动

做法 失效分布 峰值压力
固定 TTL 同一秒集中失效 高
TTL ± 10% 抖动 摊到 10 分钟内 低

4.3 解法二：多级缓存 + 限流兜底

flowchart LR
    C["Client"] --> L1["本地缓存<br/>(Caffeine)"]
    L1 -- miss --> L2["Redis"]
    L2 -- miss --> DB["MySQL"]
    L2 -.->|"Redis 整体不可用"| FUSE["熔断/限流"]
    FUSE --> FALLBACK["返回降级数据或排队"]
手段 作用 代价
本地缓存（Caffeine） Redis 挂了还有一层 一致性问题（多实例）
限流（Sentinel/令牌桶） 保护数据库不被打穿 部分请求被拒
熔断 数据库撑不住时快速失败 用户看到降级页
预热 发布/重启后先灌热点 需要知道热点是什么

4.4 动手验证：制造一次雪崩

预期观察点：删除后的一段时间内，MySQL 的 Questions 增速是正常时的数倍，且 SHOW PROCESSLIST 里出现大量相同的查询。

判定标准：

  • MySQL QPS 涨到平时的 3 倍以上 → 雪崩成立，需要 TTL 抖动；
  • MySQL QPS 没变 → 你的 key 没有集中失效，或者根本没缓存。

  4. 监控 keyspace_misses 的突增，它是穿透和雪崩最早的症状。
  5. 永远假设 Redis 会挂：本地缓存 + 限流 + 降级，三件套至少有两件。
