算法篇三：哈希表、二叉树与递归

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.5k Reading time ≈ 13 mins.

二叉树 + 递归 + 哈希表，是面试 80% 题型的主战场：树的遍历、验证 BST、最近公共祖先、两数之和、TopK——全部在这三个话题里。 本篇先讲哈希表的原理与工程对照（你天天用 HashMap，算法题里把它当武器），再讲二叉树遍历三法（递归/迭代/层序）与五道必会模板题，最后讲递归思维与复杂度。读完你能做到：树类手撕题 10 分钟内 AC，并能说出每步的复杂度。

系列地图（数据结构与算法）：① 复杂度分析与高频结构速查（度量衡）→ ② 数组/链表/栈/队列与双指针（线性结构手撕）→ ③ 本文：哈希表、二叉树与递归（系列收官）。

1. 哈希表：工程里天天用，算法里是武器

1.1 原理回顾：数组 + 哈希函数 + 冲突处理

HashMap 的本质：hash(key) % 数组长度 定位桶 → 冲突链（链表/红黑树）→ 装载因子超阈值扩容。你每天用的这个结构，在算法题里的用法是「空间换时间的查询加速」：

算法题用法 做法 典型题
去重 Set 判存在 环形链表、判断重复元素
计数 Map<key, count> 多数元素、字谜分组
位置记录 Map<key, index> 两数之和、最长无重复子串
缓存子问题 Map<key, 结果> 记忆化递归（DP）

因果链：算法题里哈希表的任务永远是「把 O(n) 的查找变成 O(1)」——两数之和暴力是 O(n²)（两两枚举），哈希表一次遍历 O(n)（每个数查「补数」是否存在）。

1.2 模板：两数之和（哈希版）

模板要点：边遍历边记录——「先查补数，再记自己」。与第二篇的左右指针版对比：哈希版不要求有序（通杀），左右指针版 O(1) 空间但要求有序（更省）。面试两版都要会，答「有序数组用双指针 O(1) 空间，无序用哈希 O(n) 空间」是完整答案。

1.3 动手验证：哈希 vs 暴力的时间差

观察点：n=100 万时暴力完全不可行、哈希瞬时返回。判定标准：能独立说出「数据规模决定算法选择」——100 个元素的题暴力无所谓，10 万个元素的题暴力必挂，这就是复杂度分析在题目里的直接应用。

2. 二叉树：先建立遍历三法

2.1 二叉树的结构与递归定义

二叉树是天然递归的结构：每个节点 = 值 + 左子树 + 右子树，而左右子树也是二叉树。结构递归 → 解法递归，这是「树题 90% 用递归」的根本原因——不是树题恰好适合递归，是树的定义本身就是递归的。

3. 五道必会树模板题

3.1 最大深度（后序思维入门）

后序思维：先要子树的答案，再算自己的。复杂度 O(n) 时间、O(高度) 栈空间。变体「直径」「平衡二叉树」全是同一骨架（平衡二叉树 = 每层检查左右深度差 ≤1）。

3.2 验证二叉搜索树（中序升序的威力）

常见错误：只比较 root > left && root < right——子树内部的所有节点都必须满足，不仅仅是直接孩子（例：{5, 4, 6, null, null, 3, 7} 左根右都满足但 3 小于 5 不是 BST）。中序升序检查天然规避了这个坑。变体「BST 的第 K 小」：中序遍历计数到 K 即答案。

3.3 翻转二叉树（递归 + 交换）

三行递归 + 三行交换，5 行代码——这是「递归题之美」的典型。复杂度 O(n)。面试官用这题考察的是「你能不能别背，理解递归在树上的执行流」——后序的顺序是这题的灵魂。

3.4 最近公共祖先（LCA，后序思维巅峰）

解读这段代码就是在读后序：先看左右子树各找没找到，再决定自己是不是答案——「两边都有 → 我是 LCA；只有一边 → 结果在那边」。复杂度 O(n)。变体「BST 的 LCA」：利用有序性，p.val < root.val && q.val < root.val 就只往左找——O(log n)。面试答 LCA 必须主动提 BST 变体，说明你理解「结构性质 → 算法加速」。

3.5 动手验证：层序打印 + 翻转后对比

观察点：翻转后层序每层是原层的镜像。判定标准：程序输出与「镜像」直觉一致——把「抽象的后序递归」和「看得见的层序输出」对照起来，是理解递归执行的最后一公里。

4. 递归与回溯：树的延伸

4.1 从「树的结构」到「决策树」

递归的通用形态是决策树：每层递归是一个决策点，每个分支是一个选择——树的遍历是决策树的最简单实例。「回溯」= 决策树的 DFS + 撤销选择：

回溯模板四步：终止条件 → 遍历选择 → 做选择 → 撤销选择。变体：全排列（交换写法/used 数组）、组合、括号生成——全是同一个骨架。复杂度：子集 2ⁿ 个结果，复杂度 O(n·2ⁿ)（输出量本身就是指数级，无法优化——先看输出规模再定复杂度期望）。

4.2 动手验证：子集数量是 2 的幂

观察点：n=20 时输出已近 100 万行。判定标准：理解「指数复杂度不是代码问题，是输出量本身」——面试题给 n 的上限，就是给你「该不该用回溯」的信号（n≤20 回溯可行，n≤10⁵ 必是贪心/DP）。

5. 二叉树的工程对照：为什么面试考树

5.1 树在工程里的真实位置

工程结构 本质 与面试树题的关系
HashMap 的冲突链 链表 退化分析（O(1)→O(n)）
HashMap ≥8 转红黑树 红黑树 「平衡」保证 O(log n)
TreeMap/TreeSet 红黑树 有序集合 = BST 变体
MySQL B+ 树索引 多路搜索树 树高=磁盘 IO 次数（深度概念）
堆（PriorityQueue） 完全二叉树 树形结构存储（数组下标 = 树位置）
JVM 类加载器 树 双亲委派是树的遍历

因果链：面试考树，是因为工程里树无处不在——HashMap 优化到红黑树、MySQL 索引是 B+ 树、JVM 类加载是树。你答「树的深度影响什么」时，能举例 MySQL B+ 树树高 3 层 = 3 次磁盘 IO（万级数据），比纯背定义高一个层次——这是《MySQL 原理与优化》里 B+ 树的直接复用。

5.2 复杂度对照：树的常用操作

结构/操作 平均 最坏 说明
二叉树查找（非 BST） O(n) O(n) 无序树要全遍历
BST 查找 O(log n) O(n) 有序插入退化成链
平衡树（红黑树） O(log n) O(log n) 自平衡，工程默认
堆 插入/取顶 O(log n) O(log n) 完全二叉树保证
HashMap 查询 O(1) O(n) 冲突退化，红黑树兜底

面试高频题「BST 退化的后果」：有序插入 1,2,3,…,n → BST 变成一条链 → 查找 O(n) → 这就是为什么工程里用红黑树而不是裸 BST（TreeMap 的自平衡来源）。

6. 总结

6.1 面试速答表

面试题 一句话答案
HashMap 为什么快？ 数组 + 哈希定位 O(1)，冲突链/红黑树处理碰撞，扩容翻倍摊还
两数之和有几种写法？ 哈希 O(n) 空间换时间（无序通用）；有序数组双指针 O(1) 空间
树为什么用递归？ 树的定义本身递归（节点=值+左右子树），结构递归决定解法递归
遍历三法什么时候用哪个？ 中序 = BST 升序；后序 = 先子树后自己（高度/LCA/镜像）
验证 BST 怎么写？ 中序遍历严格升序，别只比直接孩子
最近公共祖先？ 后序：左右各找到 → 当前是 LCA；都在一边 → 沿那边返回；BST 版 O(log n)
回溯模板？ 终止条件 → 遍历选择 → 做选择 → 撤销选择，四步一个不落
为什么工程用红黑树不用 BST？ 有序插入退化成链 O(n)，红黑树自平衡保证 O(log n)

算法篇二：数组、链表、栈、队列与双指针

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.6k Reading time ≈ 13 mins.

线性结构手撕是笔试的第一道门槛：链表反转、环检测、括号匹配、滑动窗口，四类题覆盖笔试的 30% 且全部有固定模板。 本篇给每类题「模板代码 + 变体 + 复杂度 + 易错点」，按面试真实节奏组织：看到信号词 → 套模板 → 写变体。读完你能做到：这四类题 15 分钟内写出通过全部用例的代码。

系列地图（数据结构与算法）：① 复杂度分析与高频结构速查（度量衡）→ ② 本文：数组、链表、栈、队列与双指针（线性结构手撕） → ③ 哈希表/二叉树与递归（面试 80% 题型的落点）。

1. 数组：连续内存的 O(1) 访问

1.1 数组的本质：下标即地址

arr[i] 的寻址是 起始地址 + i × 元素大小——一步乘法一个加法，这就是 O(1) 访问的来源。而插入/删除要挪动后续所有元素，O(n)。

面试问「数组和链表本质区别」的底层答案：数组的 O(1) 访问来自「内存连续 + 下标寻址」，链表的 O(1) 插入来自「指针修改 + 无需移动」——两者都是物理结构决定的，不是实现细节。

1.2 模板一：原地操作（双指针同向）

「原地删除重复元素」「移除指定值」这类题，核心是用新指针覆盖写，原地完成：

模板要点：快指针扫描（读），慢指针标注结果区（写）——读快写慢，覆盖推进。变体：「移除元素」（保留等于 val 之外的）、「移动零」（把零移到末尾）全是同一个骨架。

1.3 模板二：左右指针（有序数组的两数之和）

为什么左右指针能行：数组有序 → nums[l]+nums[r] < target 时，nums[l] 与任何更右的元素和都太小（右指针是当前最大），只能 l++；对称地，>target 只能 r–。每一步排除一行/一列搜索空间，总步数 ≤ n——这就是 O(n) 的证明，面试官追问「为什么不是 O(n²)」就答这个。

1.4 动手验证：手写数组二分并测复杂度

观察点：三个易错点——<= vs <（决定死循环）、mid+1/mid-1 vs mid（决定收敛）、l + (r-l)/2 vs (l+r)/2（防溢出）。判定标准：把 target 换成「不存在」的值跑一遍（比如数组 [1,3,5,7] 查 4）——不死的循环 + 返回 -1 即模板正确。用一万个元素实测：任何查找最多 14 次比较（2¹⁴ ≈ 16384）——log₂ 的体感。

2. 链表：指针操作是手撕的主战场

2.1 模板一：反转链表（最高频链表题）

模板要点：三指针 prev/cur/next，四步走「存下 → 反转 → 前移 → 前移」。易错点：第①步不存 next 直接改指针，链表就断了。变体：「反转前 N 个」「K 个一组反转」都是这个模板的递归/循环扩展。

2.2 模板二：环检测（快慢指针）

为什么快慢必相遇：有环时快指针每次相对慢指针靠近 1 步，环长 k 则最多 k 次追上——O(n) 时间、O(1) 空间。面试变体「找环入口」：相遇后让一个指针从头出发，另一个从相遇点，都走一步，再次相遇点即入口（数学推导：头到入口距离 = 相遇点到入口的「回头距离」）。记住结论即可，推导一句话带过：「快慢指针第一次相遇时，慢指针没走完一整圈」——这句话值一个加分项。

2.3 模板三：合并两个有序链表

模板要点：终止条件（空）→ 选小者 → 递归合并剩余 → 返回头。复杂度 O(n+m) 时间、O(n+m) 递归栈。变体「合并 K 个有序链表」：两两合并（O(k·n)）或堆优化（O(n log k)）——第三篇堆会用到。

2.4 动手验证：反转 + 环检测组合拳

观察点：反转后逐节点打印验证顺序；环的构造是「把尾节点的 next 指回中间的节点」。判定标准：反转打印输出 5,4,3,2,1 且环检测返回 true——两个模板都能独立手写，是链表关的过关标准。面试 5 分钟里能默写出这两个模板，说明指针操作真的熟了。

3. 栈：后进先出的场景识别

3.1 模板一：括号匹配（栈的教科书题）

信号词识别：成对出现、嵌套结构、需要「最近匹配」——都是栈。「最近匹配」是栈的灵魂：后进先出天然对应「最内层的先闭合」这个语义。

3.2 模板二：单调栈（下一个更大元素）

单调栈的核心：维护「还没找到答案的候选」序列，且保持单调（这里递减）——新元素来临时，把所有「比它小的栈顶」一次性弹出并结算答案。每个元素入栈出栈各一次 → O(n)，暴力是 O(n²)。变体「接雨水」是单调栈的最难变体，掌握这个模板后接雨水只是「结算逻辑变化」。

3.3 动手验证：手写一个最小栈

观察点：push 3,5,2 后 getMin()=2，pop 后 getMin() 恢复为 3——辅助栈记录的是「每个历史时刻的最小值」。判定标准：任意操作序列下 getMin 都正确且 O(1)——「用空间换时间的思路」在这里具象化：辅助栈 O(n) 空间换 O(1) 查询。

4. 队列：先进先出与滑动窗口

4.1 模板一：用队列做层序（树的层序遍历）

模板要点：int size = queue.size() 是本层与下一层的分界线——漏掉这句，层就混了。BFS（最短路径）和层序遍历是同一套代码的两种用法。

4.2 模板二：滑动窗口（最长无重复子串）

滑动窗口的本质：窗口右边界负责「扩展」，左边界负责「收缩」，两指针只前进不后退 → O(n)。信号词：「最长/最短连续子数组/子串」+「满足某条件」→ 滑动窗口。变体：「最小覆盖子串」（窗口收缩时记录）、「长度最小的子数组」（和 ≥ target）。

4.3 动手验证：滑动窗口 vs 暴力对比

观察点：n=10 万时暴力版直接卡死，窗口版瞬间出结果。判定标准：亲眼看到「O(n²) 跑不动、O(n) 秒回」的对比——这就是为什么笔试必须会滑动窗口：暴力在 LeetCode 中等题几乎全超时。

5. 双指针三件套：面试最省代码的技巧

5.1 三指针套路总览

套路 信号词 复杂度 典型题
快慢指针 链表环/中点/倒数第 K O(n)/O(1) 环检测、链表中点
左右指针 有序数组、两数之和 O(n)/O(1) 两数之和、反转数组
滑动窗口 连续子数组/子串 O(n)/O(1)~O(n) 最长无重复、最小覆盖

双指针的共同原理：让指针只前进不后退，把 O(n²) 的枚举压缩成 O(n) 的扫描——每步排除一个不可行的候选区间。面试答「为什么双指针 O(n)」就答这一句，比背代码有说服力。

5.2 快慢指针变体：找链表中点

用途：归并排序的链表版找中点、回文链表判断（先中点再反转后半）。「找中点」是快慢指针的第二高频用法，和环检测并列为链表题的两个必背模板。

5.3 动手验证：双指针 vs 暴力枚举两数之和

观察点：100 万元素的数组，暴力枚举直接等不到结果，双指针瞬间返回。判定标准：跑通且时间差肉眼可见——笔试现场你能靠体感判断「这题该用双指针」而不是「先暴力再说」。

6. 总结

6.1 面试速答表

面试题 一句话答案
数组和链表本质区别？ 数组连续内存下标寻址 O(1) 访问、O(n) 插入；链表指针修改 O(1) 插入、O(n) 访问
反转链表怎么写？ 三指针 prev/cur/next：存下 → 反转 → 前移 → 前移
链表有没有环？ 快慢指针，fast 两步 slow 一步，相遇即有环，O(n)/O(1)
怎么找环入口？ 相遇后一个指针从头走、一个从相遇点走，再相遇即入口
括号匹配？ 栈：左入栈右出栈，栈空/不配对即 false，结束栈必须空
下一个更大元素？ 单调栈：维护未结算候选，新元素结算所有小于它的栈顶，O(n)
最长无重复子串？ 滑动窗口：右扩左缩，哈希记录位置，O(n)
为什么双指针 O(n)？ 指针只前进不后退，每步排除一个不可行区间

AI 在 Java 后端的落地实践：RAG 服务化与向量检索上生产

Posted on 2026-08-13 In AI大模型 Word count in article: 4.8k Reading time ≈ 18 mins.

本篇回答一个问题：RAG 从「能跑的脚本」到「生产可用的服务」，中间差了什么？ RAG原理与实践 讲「检索怎么做好」，本篇讲「检索怎么作为一个服务跑在生产上」——接口设计、索引流水线、权限隔离、降级链路、容量评估，全部以 Java 后端视角展开。

1. 从实验到服务：RAG 落地的完整闭环

1.1 脚本 RAG 的四个问题

实验阶段的 RAG 通常长这样：一个 Python 脚本，启动时解析文档 → 分块 → 调 embedding 接口 → 灌进本地向量库 → 收到问题直接查库拼接 prompt。它能回答「效果好不好」，但上不了生产：

问题 实验脚本表现 生产要求
不可用 向量库挂在脚本进程里，重启全丢 服务独立部署，库高可用
不可扩展 一个进程既管入库又管检索 读写分离，各自独立扩展
不可治理 谁都能查所有知识，无权限概念 知识按租户/部门隔离，审计可追
不可观测 报错就是 print，效果好坏靠感觉 延迟、召回、成本全部可度量

因果链：实验脚本的「简单」来自把所有环节耦合在一个进程里——一旦拆成「对外接口、索引流水线、检索链路、模型网关」四件事，就不得不回答服务化的一系列设计问题，这正是本篇的主线。

1.2 服务化的四个目标

目标 具体含义 对应章节
功能闭环 入库、检索、问答有稳定接口 第 2、3 章
安全可控 知识隔离、权限过滤、审计 第 4 章
可用性 依赖故障（向量库/模型）有降级路径 第 5、6 章
可度量 延迟/召回/成本有指标有预算 第 7、8 章

1.3 整体架构

flowchart TB
    U["业务系统 / 前端"] --> G["检索服务 API 网关<br/>/search /chat /ingest"]
    G --> S["检索服务（Java/Spring Boot）"]
    S --> |"chat"| R["RAG 链路<br/>检索→重排→拼装"]
    S --> |"ingest"| P["索引流水线<br/>解析→分块→embedding→入库"]
    R --> V[("向量库")]
    P --> V
    R --> E["Embedding 网关<br/>批量/缓存/降级"]
    P --> E
    R --> L[("LLM（自部署/API）")]
    V --> B["BM25/ES 兜底"]
    S --> M["指标/日志/追踪"]

架构决策一句话：检索服务只做编排，向量库、模型、embedding 全部是独立依赖——每个依赖都要回答「它挂了怎么办」，这就是第 5、6 章的内容。

2. 检索服务的接口设计

2.1 三个核心接口

接口 场景 同步/异步 说明
POST /search 纯检索（RAG 之外也可用） 同步 输入 query + 过滤条件，返回 chunks
POST /chat 问答（检索 + 生成） 同步（SSE 流式） 一次调用包含完整 RAG 链路
POST /ingest 文档入库/更新/删除 异步 返回任务 ID，轮询/回调查状态

因果链：/ingest 必须异步——文档解析、分块、embedding 是大模型调用（慢、贵、可能失败），同步接口要么拖垮调用方，要么超时后状态不明；异步 + 任务表才能支持「失败重试、进度可见、结果审计」。

2.2 接口参数设计

动手验证：最小检索服务

观察点：接口的前两行就是权限校验——检索服务的正确性不只是「结果对不对」，更是「不该看到的结果一条都不能出」。判定标准：权限校验必须发生在检索之前（否则过滤器被绕过时数据已出库）。

2.3 流式问答：chat 接口的 SSE

/chat 用 SSE（text/event-stream）返回，而不是等全部生成完再返回：

方式 首字延迟 用户体感 服务端资源
一次性返回 数秒 转圈，像死机 连接占用时间相同
SSE 流式 数百 ms 看到字在出 连接占用时间相同

动手验证：Spring WebFlux + SseEmitter，或直接用 Spring AI 的 StreamingChatClient（见 Spring AI与LangChain4j实战）——前端 fetch 读流即可。判定标准：首字延迟是问答服务的第一体验指标，流式是标配不是加分项。

3. 索引更新流水线：知识怎么进系统

3.1 全量重建 vs 增量更新

方式 场景 代价
全量重建 首次上线、文档批量导入、分块策略升级 慢（全量 embedding），但实现简单、结果一致
增量更新 日常单文档增删改 快，但要处理「文档变更了，旧 chunk 怎么办」

核心问题：增量更新的「文档 → chunk」映射——向量库只认 chunk，不认文档；文档更新时必须按 documentId 把旧 chunk 全部删掉再插新的，否则旧片段残留、新片段重复。

动手验证：双缓冲版本切换（全量重建不打折）

观察点：重建期间用户查的是旧版本（active 不变），切版本是原子操作，全程服务不中断。判定标准：任何「重建期间检索结果不一致/报错」都是双缓冲没做好的信号。

3.2 流水线的四步与失败处理

flowchart LR
    A["1 解析<br/>(pdf/word → 文本)"] --> B["2 分块<br/>(chunk + 元数据)"]
    B --> C["3 Embedding<br/>(批量调模型)"]
    C --> D["4 入库<br/>(写向量库)"]
    C -.失败.-> E["重试队列<br/>(指数退避)"]

因果链：流水线每步都可能失败（文件损坏、embedding 限流、向量库抖动），没有重试队列的流水线，失败就静默丢文档——用户问「为什么新文档答不出来」，排查半天才发现入库任务失败了没人知道。

动手验证：任务状态表

重试策略：失败任务重试 3 次（指数退避 1s/5s/30s），仍失败进失败队列人工处理；状态表 + 定时扫描替代「丢线程里自生自灭」。判定标准：任意时刻能回答「这份文档入库到哪一步了」。

4. 多知识库与权限控制

4.1 为什么必须隔离

知识库问答最大的风险不是「答不对」，是越权出数据：销售部门的同事能问到财务文档。生产环境必须有明确的知识边界。

4.2 三种隔离方案对比

方案 隔离粒度 优点 缺点
独立向量库/实例 租户级 物理隔离最彻底，互不影响性能 运维成本 ×N，不能跨库检索
独立集合/表 知识库级 逻辑隔离，管理简单 单个库容量受限，查询跨集合麻烦
元数据过滤 任意粒度（文档级） 最灵活，一次部署全租户共享 过滤条件漏配 = 越权，必须服务端强制

推荐组合：元数据过滤为主 + 权限上下文服务端强制。knowledgeBase 和 userId 不来自前端请求，而是来自服务端从登录态解析的上下文——前端传什么都不可信。

4.3 文档级权限过滤的泄漏风险

元数据过滤在检索时只返回匹配 chunk，但过滤条件必须与文档权限同源：

因果链（泄漏路径）：文档 A 属于部门 X → 检索请求只带了 department=X → 系统相信了请求参数 → 部门 Y 的用户伪造参数 → 检索到文档 A 的 chunk → 数据泄漏。防御：权限不是「检索条件」，是「服务端强制注入的约束」，来源只能是登录态/Token 解析出的身份。

动手验证：

观察点：enforcedFilter 里服务端追加的键，前端无法覆盖（合并时后者胜出，或直接拒绝请求体里的同名键）。判定标准：去掉前端 filter 参数，权限过滤依然生效。

5. Embedding 网关与模型调用治理

5.1 为什么 embedding 调用需要独立网关

Embedding 是 RAG 里调用量最大、最容易被打爆的环节：一个 1000 页的文档集，分块后可能产生数万个 chunk，每个 chunk 一次 embedding 调用。直接散在各处调：

  • 并发不可控 → 触发模型服务限流 → 入库失败
  • 重复计算 → 相同 chunk 反复 embedding（浪费钱）
  • 依赖不可观测 → 模型服务慢/挂了没有任何反馈

Embedding 网关职责：批量合并、结果缓存、限流重试、降级。

5.2 批量与合并

因果链：单条调用模型 API（网络往返 × N）→ 高并发下模型服务限流 + 高延迟；合并成 batch（网络往返 × 1）→ 吞吐 ↑、限流 ↓、成本 ↓（很多厂商按 batch 计价更便宜）。

5.3 降级策略：embedding 挂了怎么办

故障 降级动作 服务表现
embedding 服务超时 重试 2 次（退避）→ 放弃该批，任务标 failed 可重跑 入库暂停，检索不受影响
embedding 服务长时间不可用 检索降级为纯 BM25/关键词检索（见 6.2） 问答变差但不宕机
向量库不可用 同上：BM25 兜底（需保留纯文本索引） 不宕机

动手验证：手动停掉 embedding 服务进程，观察系统行为——正确实现下，已入库的检索应该照常工作（检索链路的 embedding 只用于「查询向量化」，查询侧 embedding 缓存了热点 query 或降级关键词）。判定标准：任何单点依赖故障都不应该让整个问答服务 502。

6. 检索链路的可用性设计

6.1 延迟预算拆解

一次 /chat 调用的 2 秒预算怎么分配（示例）：

环节 预算 说明
查询 embedding 200ms 缓存命中则 0ms
向量检索 100ms 百万级向量 HNSW 索引下是毫秒级
Rerank 200ms 只对 top-50 重排，不是全量
LLM 生成 1.5s（首字） 最大头，SSE 流式下用户感知快
链路开销 0ms 检索与生成并行不了（生成依赖检索结果），但检索内部可并行

因果链：延迟大头永远在 LLM 生成，检索侧优化到 300ms 以下后，再优化对用户体验无感——预算应该花在「缓存命中率」和「rerank 是否必要」上，而不是死磕向量检索的 20ms。

6.2 降级链路：向量库 → BM25 兜底

生产环境的必答题：向量库（Milvus/ES 向量索引，选型对比见 向量数据库原理与实践）故障时，检索服务还能不能回答？

方案：检索时向量 + 关键词双路召回，向量路失败自动切关键词路：

flowchart LR
    Q["query"] --> V["向量检索"]
    Q --> K["关键词检索<br/>(ES/BM25，纯文本索引)"]
    V -->|"成功(≥2s/报错)"| R["Rerank 合并"]
    K -->|"兜底"| R

代价：需要额外维护一份纯文本索引（解析后的 chunk 文本同步进 ES）——这份索引在检索质量上也有价值（混合检索本身更好，见 RAG原理与实践 5.3），一举两得。

动手验证：停掉向量库容器，直接查 /search——正确实现下返回 BM25 结果（质量略降，服务不挂）。判定标准：故障演练表里必须有一项「向量库宕机」，没有做过的系统不算有降级链路。

6.3 多级缓存

缓存层级 缓存什么 命中收益 失效策略
Embedding 级 query → 向量 省 1 次模型调用（最贵的一层） query 完全相同时命中，热点问答命中率高
检索级 query → 检索结果 省检索链路 TTL 短（分钟级），知识更新时按 kb 失效
问答级 query → 完整回答 省全链路（最省） TTL 长（小时级），知识更新时必须主动失效

因果链（问答级缓存的陷阱）：问答级缓存命中率最高、最省钱 → 但知识库更新后缓存不失效 → 用户问新知识得到旧回答 → 缓存一致性比缓存命中率更重要。实现：每份缓存带 kb_version 键（见 3.1 双缓冲），知识版本切换时按前缀批量失效。

6.4 限流与成本控制

维度 策略
用户级限流 每用户每分钟 N 次 chat（LLM 调用最贵，必须按用户限制）
服务级限流 向量库/模型网关 QPS 上限，防止上游被打爆
成本告警 按知识库/按部门统计 token 消耗，超预算告警（见第 7 章）

7. 可观测性与成本

7.1 三个必看的指标

指标 定义 怎么用
P95 首字延迟 用户看到第一个字的时间 问答体验的核心 SLA；SSE 下 LLM 生成占大头
检索召回率（抽检） 抽样人工判断「相关文档有没有被检索出来」 指标退化 = 分块/embedding/rerank 该调了（见 RAG原理与实践 第 8 章评测）
成本/每问答 一次 chat 的 token 费用 按知识库、按部门分账，异常暴涨告警

7.2 日志与链路追踪

一次 /chat 调用跨 5 个环节（权限 → 检索 → rerank → 拼装 → 生成），没有 trace 就没法回答「慢在哪」：

评测与线上质量监控的完整方案见 LLM评测与可观测性——本篇只讲「服务怎么观测」，评测体系看那篇。

7.3 成本核算模板

项目 计算 示例
Embedding 成本 chunk 数 × 每千 token 单价 10 万 chunk × 0.001 元 = 100 元（一次性）
问答成本 chat 次数 × 平均 prompt+completion tokens × 单价 1 万次/日 × 0.03 元 = 300 元/日
向量库存储 维度 × chunk 数 × 4 字节 1536 维 × 100 万 chunk ≈ 6GB

动手验证：给每个 chat 请求记录 token 用量，按周聚合出「top10 贵知识库」——通常会发现文档冗余（同一内容重复入库）是最大的浪费源，比调模型便宜得多。

8. 性能压测与容量评估

8.1 从业务量倒推容量

业务参数 数值 推算
日活跃用户 1 万 —
人均每日问答 10 次 日 chat 量 10 万
峰值系数 5×（上班高峰） 峰值 QPS ≈ 10万/(8×3600)×5 ≈ 17 QPS
每次 chat 的 LLM 耗时 3s 需要的并发 ≈ 17 × 3 = 51 路并发

结论：多数内部知识库问答系统是「低 QPS、高并发占用」——瓶颈在 LLM 并发数，不在向量检索。压测时用真实 LLM 调用（mock 掉生成环节会高估吞吐 10 倍以上）。

8.2 压测方法与瓶颈定位

算法篇一：复杂度分析与高频结构速查

Posted on 2026-08-13 In 数据结构与算法 Word count in article: 3.3k Reading time ≈ 12 mins.

算法面试的第一题永远不是算法题，是「复杂度分析」——它能答题你不会，问你为什么 O(n) 你却答不出，面试直接结束。 本篇建立算法题的度量衡：大 O 直觉、常见复杂度对照表、数据结构操作复杂度速查、递归思维基本功。读完你能做到：看到任何一段代码/任何一道题，10 秒内说出复杂度，并解释为什么——这是后面所有手撕题的前提。

系列地图（数据结构与算法）：① 本文：复杂度分析与高频结构速查（度量衡） → ② 数组/链表/栈/队列与双指针（线性结构手撕） → ③ 哈希表/二叉树与递归（面试 80% 题型的落点）。

1. 复杂度是什么：算法题的统一度量衡

1.1 为什么不是「快 1 倍」而是「大 O」

两个程序谁快，不取决于运行时间（不同机器差别 100 倍），取决于数据量增长时，运行时间怎么增长。大 O 描述的是这个增长趋势，不是绝对时间：

记号 含义 直觉
O(1) 常数时间 数据翻倍，时间不变
O(log n) 对数时间 数据翻 1000 倍，时间加 10
O(n) 线性时间 数据翻倍，时间翻倍
O(n log n) 线性对数 排序的典型水平
O(n²) 平方时间 数据翻倍，时间×4
O(2ⁿ) 指数时间 数据加 1，时间翻倍

判断标准：把 n 从 1000 变 100 万，想一下时间怎么变。 1000 到 100 万是 1000 倍——O(n) 慢 1000 倍（1ms→1s 还能忍），O(n²) 慢 100 万倍（1ms→16 分钟，崩了），O(2ⁿ) 直接不可想象。复杂度分析的本质是问「数据大了之后我还活不活得下来」。

1.2 动手验证：亲手测出 O(n) 和 O(n²) 的差别

观察点：n 从 1000 到 10 万（×100），O(n) 慢了 100 倍，O(n²) 慢了 10000 倍——O(n²) 增长是 O(n) 的平方关系。判定标准：实际测出的增长比例接近「n 增长 10 倍，O(n²) 时间增长 100 倍」，即建立了大 O 的体感——体感比公式重要，面试手撕时你能靠体感判断「这解法是不是太暴力了」。

1.3 常见代码模式 → 复杂度速查

代码模式 复杂度 识别信号
单层循环 O(n) for (i = 0; i < n; i++)
双层循环各走 n O(n²) 两层嵌套，每层到 n
循环减半 O(log n) while (l <= r) { mid = l + (r - l) / 2; ... }
循环+减半 O(n log n) 排序、归并、外层线性内层二分
递归两个分支 O(2ⁿ) 斐波那契朴素递归
HashMap/Set 操作 O(1) 摊还 get/put/contains
数组按下标访问 O(1) arr[i]
链表按下标访问 O(n) list.get(i) 从头走

因果链：大 O 不是数学题，是「代码结构 → 资源消耗」的映射——循环层数决定 n 的次数，减半决定 log n，哈希访问摊还 O(1)。面试手撕时先想「我的解法什么复杂度」再说代码，是区分「会写」和「懂写」的分界线——因为面试官下一句永远跟「能不能优化」。

2. 复杂度进阶：常见的分析陷阱

2.1 只保留增长最快项

  • O(n² + n) → O(n²)：n 足够大时 n 项可以忽略；
  • O(2n + 100) → O(n)：常数系数忽略；
  • O(n log n + n²) → O(n²)：只留最高阶。

面试陷阱题：for i in 0..n: for j in 0..i: 内层随 i 变化，总次数 = 0+1+…+n-1 = n(n-1)/2 → O(n²)（不是 O(n)）。识别信号：双层循环内层上限是外层变量，总和还是 n² 级别——这个坑面试官最爱埋。

2.2 空间复杂度：面试总被忽略的另一半

做法 空间复杂度 信号
只用几个变量 O(1) 双指针、原地交换
用了一个与 n 等大的数组 O(n) 额外哈希表、栈
递归深度 n O(n) 递归栈（二分 O(log n)，链表递归 O(n)）

经典权衡题：「O(1) 空间的反转链表 vs 递归版」——迭代版原地改指针 O(1) 空间，递归版压栈 O(n) 空间。面试问「空间换时间」就是问这个权衡：哈希表 O(n) 空间换 O(1) 查询，是算法题最高频的优化手段（第二篇、第三篇会反复用到）。

2.3 摊还分析：为什么 ArrayList 的 add 是 O(1)

ArrayList.add() 满了要扩容（复制整个数组 O(n)），但均摊下来每个元素只被复制约 1 次（扩容翻倍），所以摊还 O(1)。因果链：扩容翻倍策略让「偶尔 O(n)、平均 O(1)」——这是工程里「用摊还思维设计数据结构」的经典，HashMap 的扩容同理。 面试答「ArrayList 和 LinkedList 区别」时，说出「add 均摊 O(1)」比「ArrayList 基于数组」高一个层次。

3. 数据结构复杂度总表：面试的「查表能力」

3.1 线性结构

操作 数组 链表 栈 队列
按下标访问 O(1) O(n) — —
头部插入/删除 O(n)（移动） O(1) — —
尾部插入/删除 O(1) 摊还 O(1)（有尾指针） O(1) O(1)
中间插入 O(n) O(n)（找位置） — —
查找 O(n) O(n) O(n) O(n)

选型判断：数组「下标访问快、插入慢」，链表「插入快、访问慢」——双指针题喜欢链表，滑动窗口题喜欢数组，这是第三篇的伏笔。

3.2 哈希与树

操作 HashMap TreeMap（红黑树） 数组二分
查找 O(1) 平均 O(log n) O(log n)
插入 O(1) 平均 O(log n) O(n)（移动）
有序遍历 ❌ 无序 ✅ O(n) ✅ O(n)
排序后 — — ✅

面试决策链：需要「按键查值」→ HashMap；需要「范围查询/有序输出」→ TreeMap；数据已有序 → 二分。「什么时候用哪个」是数据结构面试的一半题目——另一半是手撕。

4. 递归思维：算法题的基本功

4.1 递归的三要素：终止条件、子问题、返回值

90% 的树题和一半的链表题用递归解。递归不是「函数调自己」这个语法，而是把大问题拆成同构的小问题：

因果链：写递归的正确顺序是「先写终止条件，再写子问题调用，最后写返回值怎么组合」——三个要素缺一个就死循环（无终止）或结果错（组合错）。面试手撕递归题，先说出三要素再写代码，是稳拿分的节奏——面试官看的是你的思考过程。

4.2 递归的代价：栈溢出与重复计算

问题 表现 解法
栈溢出 深度 > 万级 StackOverflowError 改迭代；尾递归（Java 不优化）
重复计算 朴素斐波那契 O(2ⁿ) 记忆化（memo 缓存子问题结果）→ O(n)

面试高频追问：「递归怎么优化？」——标准答案三连：记忆化去重（O(2ⁿ)→O(n)）→ 空间优化（滚动数组 O(n)→O(1)）→ 改迭代。 每层追问都答出「少做了什么」，面试官知道你懂复杂度。

4.3 动手验证：递归与迭代的栈深度对比

观察点：递归深度受 JVM 栈大小限制（默认约 1 万层左右），迭代不受。判定标准：亲眼看到 StackOverflowError——记住这个画面：树的高度就是递归深度，退化成链的树（比如有序插入的 BST）递归会爆栈，所以面试里「树退化」要主动提到（第三篇详述）。

6. 总结

6.1 面试速答表

面试题 一句话答案
什么是大 O？ 数据量增长时运行时间的增长趋势，不看绝对时间
O(log n) 是什么感觉？ 数据×1000，时间+10——二分、平衡树查找
ArrayList add 为什么 O(1)？ 扩容翻倍，元素平均复制次数 ≈ 1（摊还）
HashMap 为什么 O(1)？ 数组+哈希定位，冲突链摊还常数；退化时 O(n)
递归怎么优化？ 记忆化（去重 O(2ⁿ)→O(n)）→ 滚动数组 → 迭代
递归为什么爆栈？ JVM 栈深度有限，树退化成链时深度 = n
空间换时间什么意思？ 哈希表 O(n) 空间换 O(1) 查询，最常用优化手段
