复制、哨兵与 Cluster：切一次主要多久

Posted on 2026-10-25 In 数据存储 Word count in article: 3.3k Reading time ≈ 12 mins.

Redis 的主从切换没有「秒级」这么模糊的说法，实测是 3.33 秒（哨兵）和 6.9 秒（Cluster）。这两个数字都由同一个参数决定：多久判定一个节点「死了」。

本文搭了三套真实环境：一主一从、三哨兵、六节点 Cluster（3 主 3 从），把全量同步、部分重同步、故障转移、槽路由全部跑了一遍。

1. 复制：全量同步与部分重同步

1.1 PSYNC 的流程

sequenceDiagram
    participant S as Replica
    participant M as Master
    S->>M: PSYNC ? -1（首次连接）
    M-->>S: FULLRESYNC replid offset
    M->>M: BGSAVE 生成 RDB
    M-->>S: RDB 文件
    M-->>S: 期间的写命令（repl buffer）
    S->>S: 加载 RDB + 重放缓冲
    S->>M: PSYNC replid offset（断线重连）
    M-->>S: CONTINUE（增量，不传 RDB）
场景 结果 代价
首次连接 FULLRESYNC：传整个 RDB 与数据量成正比
短暂断线后重连 CONTINUE：只补 offset 之后的命令 极小
断线太久（超出 backlog） 又变成全量 大

1.2 实测：全量同步与部分重同步

搭一主一从（--replicaof r-master 6379），写入 10000 个 key：

指标 主库 从库
role master slave
connected_slaves 1 —
master_link_status — up
dbsize 10,000 10,000
master_repl_offset 535,669 535,669（slave_repl_offset）
sync_full / sync_partial_ok 1 / 0 —

offset 相等就代表追平——这是比 lag 更硬的判据（lag 是秒级粒度，offset 是字节级）。

然后重启从库，观察重连行为：

指标 重启前 重启后
sync_full 1 1（没增加）
sync_partial_ok 0 1
链路恢复耗时 — 0.31 s
从库数据 10,000 10,000（无损）

结论：短时间断线走的是部分重同步，没有重新传 RDB。这依赖 repl-backlog-size（默认 1 MB）能覆盖断线期间的写入量——如果你的写入很猛、断线又久，backlog 撑不住就会退化成全量同步。

1.3 复制延迟的三种来源

来源 表现 处理
网络 master_link_status 抖动、offset 差距波动 同机房部署
从库负载 从库在跑 BGSAVE/大查询 持久化放到专用从库（⑦）
主库写入过猛 offset 持续落后 分批写、限流

2. 哨兵：把「主从」变成「高可用」

2.2 实测：3 哨兵，3.33 秒完成切换

配置：quorum 2、down-after-milliseconds 2000、failover-timeout 10000，3 个哨兵 + 1 主 1 从。

实测流程：

步骤 结果
3 个哨兵都认到 master SENTINEL get-master-addr-by-name mymaster → 172.19.0.2
已知副本数 1
kill -9 主库 —
哨兵确认新主 3.33 s，新主 172.19.0.3

3.33 秒是怎么来的：down-after = 2000ms 判定主观下线 + quorum 内互相确认 + 选举 leader + 提升从库 + 通知其余节点。想更快就把 down-after 调小，但误判风险上升（网络抖动 1 秒就被判死，代价是一次不必要的切换）。

4. 一致性代价

4.1 异步复制的丢失窗口

Redis 复制是异步的：主库写完就回客户端，不等从库确认。所以：

场景 会丢什么
主库宕机，从库未收到最后 N 条 丢掉这 N 条（N 由网络与负载决定）
主库磁盘坏 + AOF 也没了 丢到上次 RDB/AOF
切换后旧主恢复 旧主上的数据可能被丢弃（新主成为权威）

代价很直接：从库全挂时主库会拒绝写入。这是「可用性 vs 一致性」的显式选择，不是免费的。

4.2 切换瞬间会丢锁（⑪ 的伏笔）

一个具体的连锁反应：

  1. 客户端 A 用 SET lock:order 1 NX PX 30000 拿到了锁（写在主库）；
  2. 主库在把这条命令同步给从库前宕机；
  3. 哨兵把从库提升为新主——这把锁不存在了；
  4. 客户端 B 用同样的 key 加锁，成功。

于是 A 和 B 同时认为自己持有锁。这就是 ⑪ 要讲的「RedLock 争议」的现实版。

6. 动手验证：四个可复现实验

6.1 动手验证：搭一主一从并验证追平

预期观察点：master_link_status:up，两边 offset 相等。

判定标准：offset 持续不相等 → 有复制阻塞；link_status:down 查网络与 Last_IO_Error。

6.2 动手验证：验证部分重同步

预期观察点：sync_full 不变（仍为 1），sync_partial_ok 变成 1，说明走的是增量同步。

判定标准：sync_full 变成 2 → 退化成全量同步，检查 repl-backlog-size 是否太小。

6.3 动手验证：哨兵切换计时

预期观察点：本文 3.33 s 完成切换；新主 role:master 且可写。

判定标准：超过 10 s → 检查 quorum 是否满足、哨兵数量是否够、down-after 是否过大。

6.4 动手验证：验证 Cluster 重定向

预期观察点：错误节点返回 MOVED <slot> <ip:port>；-c 自动跟随成功；跨槽 MGET 报 CROSSSLOT。

判定标准：集群刚创建时 cluster_state 可能是 fail，等几秒收敛；长时间 fail 查 CLUSTER NODES 是否有节点没握手。

5. 总结

5.1 面试速答表

面试题 一句话答案
Redis 复制的流程 PSYNC → 首次 FULLRESYNC 传 RDB + 缓冲命令；断线重连 CONTINUE 增量同步
全量同步什么时候发生 首次连接，或断线超出 repl-backlog-size（默认 1 MB）
怎么判断从库追平了 master_repl_offset 与 slave_repl_offset 相等（比 lag 精确）
哨兵怎么判定主库挂了 超时 down-after → 主观下线；达到 quorum → 客观下线 → 选 leader 切换
哨兵切换要多久 本文 3.33 s（down-after 2 s、quorum 2）
哨兵配置的坑 启动时要能解析主机名，否则 FATAL；用 IP 或稳定域名
Cluster 有多少槽 16384，3 主各分 ~5461 个
客户端请求错节点会怎样 返回 MOVED <slot> <ip:port>，客户端需重定向
跨槽多 key 操作 报 CROSSSLOT，用 {} hash tag 让 key 同槽
Cluster failover 多久 本文 6.9 s（node-timeout 5 s）
为什么 Cluster 比哨兵慢 判定依赖 cluster-node-timeout + gossip + 选举
什么时候该上 Cluster 数据量超过单机内存时；只是为了高可用用哨兵就够
Redis 复制是同步的吗 异步，主库不等从库确认；可用 min-replicas-to-write 换一致性

5.2 实战避坑表

症状 原因 处理
从库频繁全量同步 backlog 太小 / 断线太久 调大 repl-backlog-size
哨兵不切换 quorum 不满足 / 只部署了 1 个哨兵 至少 3 个哨兵，奇数
哨兵启动失败 主机名解析不了 用 IP 或稳定域名
客户端切换后连不上 客户端缓存了旧主地址 用支持哨兵/集群的客户端（Jedis/Lettuce 的 sentinel 模式）
Cluster 里 MGET 报错 跨槽 hash tag 或拆分
切换后数据少了 异步复制丢失窗口 min-replicas-to-write 或接受
切换后出现双写 旧主未彻底下线 旧主降级为从库，REPLICAOF 新主

5.3 工具速查表

工具 看什么 判定标准
INFO replication role、link_status、offset offset 相等 = 追平
SENTINEL get-master-addr-by-name 当前主地址 切换后应返回新主
SENTINEL replicas 已知副本 数量要与部署一致
CLUSTER INFO cluster_state、slots_ok ok 且 16384 全覆盖
CLUSTER SLOTS 槽与节点映射 用于排查重定向

5.4 实操建议

  1. 先算清你是否真的需要 Cluster。数据装得下就哨兵，装不下才 Cluster。
  2. 哨兵部署 3 个以上且奇数，quorum 取多数；配置里用 IP。
  3. 监控 offset 差而不是只看 lag，前者能提前发现复制阻塞。
  4. min-replicas-to-write 是显式取舍，开了就别抱怨「从库挂了主库不能写」。
  5. 切换演练每季度一次，并验证客户端能自动发现新主（很多故障卡在客户端缓存）。

持久化：RDB、AOF 与丢失窗口

appendfsync always 让每次写入从 103 微秒变成 487 微秒——慢了 4.7 倍，换来的却是「kill -9 三档都不丢数据」的同一个结果。持久化的代价与收益，只有把「每秒能写多少」和「会丢多少」放在同一张表里才看得清。

本文做了三组实验：三档 appendfsync 的写入开销、真 kill -9 后的存活条数、以及 AOF 从 18.6 MB 重写成 4.3 MB 的全过程。

1. 三种持久化，三种保护范围

1.1 RDB / AOF / 混合

1.2 默认值（实测）

参数 实测默认 含义

2. appendfsync 三档：性能与丢失窗口

2.1 实测写入开销（3000 次顺序 SET）

always 与 everysec 差 4.7 倍——差的正是每次写一个 fsync。这个数字和 MySQL 的「flush_log_at_trx_commit=1 vs 2」是同一类账（MySQL 系列 ⑦）。

2.2 实测：kill -9 之后三档都没丢

每次：写入 3000 条 → 立刻 docker kill -s KILL → 重启 → 数 DBSIZE：

模式 写入 恢复耗时 存活 丢失
always 3000 0.11 s 3000 0
everysec 3000 0.11 s 3000 0
no 3000 0.11 s 3000 0

为什么三档都不丢：Redis 在每一轮事件循环结束时都会把 AOF 缓冲 write() 到操作系统。kill -9 只杀进程，操作系统的 page cache 还在，数据不会消失。fsync 保证的是「写到磁盘介质」，而不是「写进 OS」。

2.3 深挖：kill -9 ≠ 掉电

这是本文最重要的一条，也是很多文章写错的地方：

崩溃类型 always everysec no
进程崩溃（kill -9、段错误） 0 丢失 ≈0 丢失（本文实测 0） ≈0 丢失
OS 崩溃 / 掉电 0 丢失 ≤1 秒 最多约 30 秒（OS 脏页回写周期）
磁盘损坏 可能全丢 可能全丢 可能全丢

所以「everysec 会丢 1 秒」这句话的前提是掉电，不是进程崩溃。 要验证它，只能拔电源或做 OS 级故障注入——容器里 kill -9 测不出来。

2.4 一次「看起来丢了」的实验：流水线中途 kill

我用流水线发 100,000 条 SET（不等回复），0.35 秒时 kill -9，恢复后：

指标 值
客户端已发送 100,000
恢复后存活 32,420

这个 32,420 不能解读成「持久化丢了 67,580 条」。里面混着两类：

类别 是否算持久化丢失
服务端还没执行（还在 socket 缓冲里） ❌ 不算，客户端本来就没收到确认
已执行、但 AOF 缓冲还没写到 OS ✅ 算（但窗口是「一个事件循环」级别）

要在实验里精确区分这两类，必须在每次写入后读回复（everysec 下会让窗口缩小到一个循环周期，几乎测不到）。这正是「丢失窗口」的真实含义：它不是一个固定的秒数，而是「多久没落盘」的概率分布。

2.5 动手验证：量你自己的写入开销

预期观察点：always 的耗时是 everysec 的 3~5 倍（本文 4.7 倍）。

判定标准：

  • always 与 everysec 差距 < 2 倍 → 你的磁盘很快（NVMe/内存盘），或者 fsync 被文件系统吞了；
  • no 比 everysec 还慢 → 测量噪声，或 AOF 重写正在跑（INFO persistence 看 aof_rewrite_in_progress）。

3. AOF 重写：18.6 MB 变成 4.3 MB

3.1 实测：20 万 key（35 MB 内存）

指标 实测

RDB 快照 4.3 MB

为什么 AOF 会大：它记录的是「每条写命令」，同一个 key 被改 10 次就有 10 条记录；重写是「按当前状态重新生成最小命令集」，所以能压缩到接近 RDB 的大小。

  1. 先确认你的实例到底开没开 AOF，appendonly no 是默认值，很多人以为开了。
  2. 缓存用 RDB 就够，别为了「保险」给纯缓存加 AOF，白白付出写入开销。
  3. **要确定性就用 always**，但先测你的磁盘能不能承受 4~5 倍的写入成本。
  4. **定期观察 aof_current_size**，重写阈值（64 MB / 100%）对高写入实例可能太宽松。

Pipeline、事务与 Lua：原子性和 RTT 怎么兼得

Posted on 2026-10-25 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

Redis 的事务没有回滚。 这不是 bug，是设计取舍：MULTI 里 SET 成功、INCR 失败，EXEC 之后 SET 的值照样在库里——本文实测，GET 回来的是 hello，而 EXEC 的返回里躺着一条 ERR value is not an integer。

这一篇把三种「批量 + 原子」手段量清楚：MULTI/EXEC、WATCH 乐观锁、Lua 脚本。1000 次 INCR 的实测是 105 ms（逐条）→ 2.2 ms（pipeline）→ 2.9 ms（MULTI + pipeline），而 Cluster 下 Lua 还有一个硬约束：所有 key 必须落在同一个槽。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua（本文） → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：② 测出 pipeline 能提升 18 倍，本文把它和事务组合起来量；⑤ 说「Lua 不可打断」，本文给出边界与 Cluster 限制；⑪ 的分布式锁用到的 SET NX + Lua 释放，就是本文机制的工程化。

1. 三个需求，三种手段

需求 手段 是否原子 省 RTT
批量发命令，少等几次 pipeline ❌ 不保证 ✅ 最强
多条命令当一组执行 MULTI/EXEC ⚠️ 部分（不回滚） ✅ 配合 pipeline
「先判断再修改」不被打断 Lua 或 WATCH ✅ Lua 真原子 ✅ 一次往返

先记住这张表：pipeline 解决「网络」，MULTI 解决「打包」，Lua 解决「判断+修改」的原子性。三者不是替代关系。

1.1 实测：1000 次 INCR 的三种写法

同一个实例、同一个客户端（loopback）：

写法 总耗时 每次操作 相对逐条
逐条 INCR 104.9 ms 105 µs 1×
pipeline（一次发 1000 条） 2.2 ms 2.2 µs 48×
MULTI + pipeline + EXEC 2.9 ms 2.9 µs 36×

三个可以直接拿走的数字：

  1. 逐条 105 µs/次，其中 Redis 执行 INCR 只要 0.1 µs 左右（② 实测），99.9% 是往返；
  2. pipeline 把 105 µs 摊到 2.2 µs；
  3. **MULTI 的代价是 32%**（2.2 → 2.9 ms）——事务不是免费的，它要在服务端维护队列与状态。

2. MULTI/EXEC：不是事务，是「排队后一起执行」

2.1 机制：先入队，EXEC 才执行

sequenceDiagram
    participant C as Client
    participant R as Redis
    C->>R: MULTI
    R-->>C: OK
    C->>R: SET mykey hello
    R-->>C: QUEUED
    C->>R: INCR mykey
    R-->>C: QUEUED
    C->>R: EXEC
    R-->>C: [OK, ERR value is not an integer]
    Note over R: both commands run,<br/>no rollback on the failed one

MULTI 之后命令只是入队，EXEC 时才按顺序一次性执行。执行期间不会插入其他客户端的命令——这一点保证了「不被别人打断」，但不保证「失败就撤销」。

2.2 实测：运行期错误不回滚

实测输出：

INCR 失败了，但 SET mykey hello 已经落库。 这就是「Redis 事务不支持回滚」的具体表现。

2.3 实测：入队期错误会让整个事务作废

实测输出：

错误类型 发生时机 结果
命令不存在、参数个数不对 入队时 EXECABORT，全部不执行

这一对差异要背下来：入队期错误是「事务级失败」，执行期错误是「单命令失败」。

2.4 深挖：为什么 Redis 不回滚

回滚需要 undo 日志或 MVCC（MySQL 的那套，见 MySQL 系列 ⑤）。Redis 的定位是「极简 + 极快」，加回滚意味着：

代价 说明
内存 每条命令都要保留旧值
复杂度 回滚逻辑要处理所有数据结构
性能 写路径变重，失去「单线程无锁」的优势

所以官方的态度很明确：要么在应用层保证命令不会失败（先检查类型），要么用 Lua 做「检查 + 执行」的原子组合。

2.5 隔离性：EXEC 期间不会被插队，但 MULTI 到 EXEC 之间会

阶段 其他客户端能否插入
MULTI → EXEC 之间（还在入队） 能（你的命令还没执行，别人的命令照常执行）
EXEC 执行期间 不能（单线程连续执行）
Lua 执行期间 不能

这意味着：如果你在 MULTI 和 EXEC 之间读取外部状态，读到的可能已经过期——这正是 WATCH 要解决的问题。

4. Lua：把多步变成一步

4.1 实测：Lua 的错误同样不回滚

实测输出：

6.4 实操建议

  1. 别把 MULTI 当事务用。它只保证「不被打断」，不保证「失败回滚」。
  2. 批量优先 pipeline，需要原子再叠加 MULTI，两者用同一个连接。
  3. 「判断 + 修改」一律 Lua（扣库存、限额、锁释放），并保证 key 同槽。
  4. 集群下先设计 key 的 hash tag，否则上线后改 key 名就是数据迁移。
  5. **脚本里禁止 O(N)**，并给脚本加「最多操作 N 个 key」的自我保护。

单线程：为什么快，什么时候会卡

Posted on 2026-10-25 In 数据存储 Word count in article: 4k Reading time ≈ 15 mins.

一条 KEYS * 让 Redis 卡了 117 毫秒，而这段时间里所有客户端的 PING 最大延迟正好也是 117 毫秒。这不是巧合，是单线程的物理事实：Redis 执行一条命令时，其他所有请求排队。

本文把「阻塞」从形容词变成数字：用探针客户端每 100 微秒发一次 PING，另一边执行 KEYS *、DEL 大 key、重 Lua、BGSAVE，测出每种操作的阻塞时长——从 156 毫秒到 7 微秒，差四个数量级。

1. 单线程的本质

1.1 一个循环，一次一条命令

flowchart LR
    E["epoll_wait<br/>等待就绪 fd"] --> R["read 请求"]
    R --> P["解析协议"]
    P --> X["执行命令<br/>（单线程，不可打断）"]
    X --> W["写回复"]
    W --> E
    X -.->|"执行期间<br/>其他请求全部排队"| Q["其他客户端"]
阶段 谁在做 能否并行
等待连接就绪 epoll（主线程） 是（内核）
读 socket / 解析协议 主线程（可用 io-threads 分担） 是（可选）
执行命令 主线程 否
写回复 主线程（可用 io-threads） 是（可选）

关键：io-threads 能分担读写，但命令执行永远只有一个线程（② 的实测也证明了小 value 场景开 io-threads 没有收益）。

1.2 为什么这样还能快

原因 数字
纯内存 GET 服务端执行 0.07 µs（② 实测）
无锁无切换 单线程，没有上下文切换与锁竞争
命令短 一条命令几十纳秒到几十微秒

代价也很明确：没有「抢占」，谁在执行谁就独占。你的 KEYS 跑了 117 ms，其他 1000 个客户端就等 117 ms。

2.4 重 Lua：4 毫秒，但会叠加

300 万次空循环的 Lua 脚本：服务端 4,032 µs，探针 max 4,260 µs。

单看 4 ms 不吓人，但要知道两件事：

  1. 脚本内不能被打断，脚本里做 1 万次 GET 就是 1 万次串行操作；
  2. 脚本会随访问量叠加：每秒 100 次这样的脚本 = 每秒 400 ms 被占用（40% 的 CPU 时间），P99 必然劣化。

⑥ 会专门讲「Lua 什么时候安全、什么时候危险」。

5.4 实操建议

  1. **线上禁用 KEYS**，用 SCAN；能用 rename-command 禁掉最好。
  2. **删除一律用 UNLINK**，这是零成本的 2 万倍提升。
  3. 慢日志阈值调到 1~2 ms，并开 latency-monitor-threshold（10~50 ms）。
  4. **定期 --bigkeys**，大 key 是阻塞、倾斜、带宽三个问题的共同源头。
  5. 把重活挪到副本或离线：RDB 备份、大范围扫描、批量清理。
