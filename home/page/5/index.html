Posted on 2026-08-05 In AI大模型 Word count in article: 2.1k Reading time ≈ 8 mins.

LLM 微调入门（LoRA / QLoRA）

本文是《AI学习体系导航》阶段五的微调入门篇，定位收敛为决策 + LoRA/QLoRA 实操入门（不做全参训练）：先讲清”什么情况该微调、什么情况不该”的决策框架，再落地 LoRA/QLoRA 的最小实践与评估上线。RAG 与 Prompt 的对比决策见 RAG原理与实践 第一章，部署承接见 LLM推理与部署实战。

撰写时快照：本文基于 2026 年 8 月的开源微调生态撰写（LLaMA-Factory / unsloth 等）；框架版本迭代快，命令以官方文档为准。

一、微调全景

1.1 微调在做什么

微调（Fine-tuning）是在预训练模型基础上，用任务数据继续训练，让模型适配特定任务/风格/领域。与预训练（训练基础能力）的区别：

阶段 数据规模 成本 目的
预训练 万亿 token 级 千万级成本 语言能力
微调（SFT） 万~百万条指令 数百元~数万元 任务适配
对齐（RLHF/DPO） 千~万条偏好数据 更高 价值观对齐

本文范围是 SFT（监督微调）——绝大多数业务需求够用的就是它。

1.2 微调能解决/不能解决什么

能解决 不能解决
输出风格/格式（客服口吻、固定模板） 知识缺失（知识问题归 RAG）
领域语言（医疗/法律术语表达） 推理能力不足（换更大模型）
特殊指令遵循（按固定 schema 输出） 实时信息（数据是训练时的快照）

**微调的本质是”行为塑形”，不是”知识注入”**——这是决策的第一条铁律。

二、决策框架：微调是最后手段

2.1 代价顺序

按这个顺序排查，90% 的需求停在①②。这也是学习指南”误区 6：遇到效果问题就微调模型”的正解（AI学习体系导航）。

2.2 微调的真实风险

风险 说明
灾难性遗忘 新数据学过头，通用能力下降（客服模型忘了写代码）
数据成本 高质量标注数据稀缺且贵
评估成本 微调效果必须评测，否则是黑盒赌博
维护成本 模型迭代、重新训练、部署管线

2.3 决策检查表

  • 问题属于”行为/风格/格式”而非”知识”？
  • Prompt 调优已经尽力（用了 Prompt工程实战 的模式库与回归）？
  • RAG 不适用或已试过（知识类问题 RAG 优先，见 RAG原理与实践）？
  • 有足够的标注数据（起步万级指令）？
  • 有评测集能验证微调效果（LLM评测与可观测性）？

全部通过，才进入微调。

三、LoRA 原理

3.1 问题：全参微调太贵

7B 模型全参微调：需要更新 70 亿参数，显存要模型权重的 4-6 倍（优化器状态 + 梯度），一张 24GB 卡跑不了。

3.2 LoRA 的核心思想：冻结 + 低秩增量

LoRA（Low-Rank Adaptation）：冻结原模型全部权重，只训练一个低秩增量：

  • 可训练参数占比通常 **< 1%**（7B 模型只训几千万参数）；
  • 显存需求从”4-6 倍权重”降到”权重 + 少量增量”；
  • 效果对标全参微调（在大多数任务上差距很小）——LoRA 是 2026 年事实上的微调默认方案。

Java 对照：LoRA ≈ 不改基座代码，只加一个轻量”适配层”（装饰器/Filter）——与 Spring 的 AOP 增强是同一个架构直觉。

3.3 关键超参数

参数 含义 常用值
r（秩） 增量矩阵的秩 8~64，任务复杂取大
alpha 缩放系数 常为 r 的 1-2 倍
学习率 微调用学习率 1e-4 ~ 2e-4（远小于预训练）
轮数 训练轮次 2~3 轮（数据少时防过拟合）

四、QLoRA 实践

4.1 QLoRA：量化 + LoRA

QLoRA = 权重 4bit 量化加载 + LoRA 训练：一张 24GB 卡能微调 7B~13B 模型（普通 LoRA 需 48GB+）。

方案 7B 显存需求 效果
全参微调 60GB+ 基准
LoRA 30~48GB ≈ 全参
QLoRA ~12GB ≈ LoRA（可微差）

4.4 常见坑

坑 表现 对策

五、评估与上线

5.1 微调前必须建评测集

微调是”黑盒改造”，没有评测就是赌博。流程：

  1. 微调前：跑一组基线任务（目标任务 + 通用任务各一组）记录分数；
  2. 微调后：同一组评测集再跑一遍；
  3. 对比决策：目标任务升、通用任务不降 → 可上线；通用任务大跌 → 灾难性遗忘，回滚或调整。

5.2 部署

微调产物合并后（5.4 的 export），部署与普通模型零差别：

  • 本地：ollama create 导入 GGUF 或直接 vLLM 加载合并目录；
  • 服务化：vLLM 启动命令只改 --model 路径（见 LLM推理与部署实战）；
  • 需要时再量化压缩（合并 → 量化 → 部署的流水线）。

5.3 上线后的维护

  • 效果漂移检测：线上抽样评测（LLM评测与可观测性）；
  • 数据版本管理：训练数据进版本库，可复现；
  • 多版本并存：微调版本与基座并存，路由切换灰度（模型路由见 LLM推理与部署实战 第六章）。

六、微调 vs RAG：一个对比案例

场景 诉求 推荐 理由
客服要知道最新退款政策 知识 + 时效 RAG 政策月月变，RAG 即时更新
客服要按固定话术模板回复 行为 + 风格 微调 模板在 Prompt 里写不清，微调最稳
医疗报告要输出专业术语风格 风格 + 知识混合 RAG（知识）+ 微调（风格） 组合拳
只是想减少 Prompt 长度 成本 都不要 先优化 Prompt 与缓存

决策心法：知识归 RAG、行为归微调、成本归工程——三者不是竞争，是分工。

LLM推理与部署实战

Posted on 2026-08-05 In AI大模型 Word count in article: 3.5k Reading time ≈ 13 mins.

LLM 推理与部署实战

本文是《AI学习体系导航》阶段五的核心深文，主线一句话：**”模型服务 = RPC 服务”**——vLLM/Ollama 起的推理服务，本质就是你已经很熟的 RPC 服务（协议、并发、负载均衡、监控、成本），只是协议换成了 OpenAI 兼容、资源换成了 GPU 显存。覆盖 Ollama 起手、推理原理（Prefill/Decode、KV Cache、batching）、vLLM 生产部署、量化、模型路由、成本控制与运维。API 侧的对接见 LLM API与工具调用实战，微调产物部署见 LLM微调入门。

撰写时快照：本文基于 2026 年 8 月的推理生态撰写；vLLM/Ollama 版本迭代快，文中版本号与参数以官方文档为准。

一、推理服务全景

1.1 云 API vs 自部署：先决策

维度 云 API（OpenAI/通义等） 自部署（Ollama/vLLM）
起步成本 极低，Key 即用 GPU 硬件 + 运维
能力上限 旗舰模型（开源达不到） 受限于开源模型与显存
数据合规 数据出网 完全本地
成本曲线 按量计费，量大线性涨 固定成本，量大摊薄
延迟/定制 不可控 可控、可量化、可微调模型

决策点：数据敏感 → 自部署；需要旗舰模型能力 → 云 API；量大且模型可开源替代 → 自部署。实际生产多是混合：云 API 走旗舰，自部署走量大/敏感场景，中间用路由网关切换（第六章）。

1.2 主线：模型服务就是 RPC 服务

对照表（本文的骨架）：

你熟悉的 Java 概念 推理服务对应
服务框架 vLLM / Ollama / TensorRT-LLM
RPC 协议 OpenAI 兼容 HTTP（LLM API与工具调用实战）
资源（CPU/内存） GPU 显存（KV Cache）
高并发手段 continuous batching、动态批处理
性能优化 量化（压缩）、投机解码（预测）
监控告警 吞吐/延迟/排队指标
成本治理 token 计价、模型路由、降级

**把推理服务当 RPC 服务治理，你就已经会了 80%**——剩下 20% 是 GPU 与推理引擎的特有知识，本文覆盖。

二、本地起手：Ollama

2.1 为什么先学 Ollama

Ollama 是本地模型管理的”最简单路径”：一条命令拉起模型、自带 OpenAI 兼容 API、跨平台（macOS/Linux/Windows）。学习推理、验证模型效果、本地开发调试用它最快。

2.2 OpenAI 兼容 API

Ollama 提供 /v1/chat/completions 兼容端点——你的业务代码一行不改，把 base_url 指过来即可：

Java 对照：这就是把上游服务地址换了个 base_url——RPC 服务切换提供方的日常操作。协议统一（第一章的结论）在这里直接兑现。

2.3 GGUF 格式

Ollama 的模型是 GGUF 格式（llama.cpp 系），本质是”模型权重 + 量化 + 元数据”打包。GGUF 的好处：

  • 支持 4bit/5bit/6bit/8bit 量化（省显存，见第五章）；
  • CPU 也能跑（慢但可用）——没有 GPU 也能开始学习；
  • 生态兼容（Ollama、llama.cpp、LM Studio 通用）。

三、推理原理

3.1 Prefill 与 Decode

LLM 生成分两个阶段：

关键认知：总耗时 ≈ Prefill 一次 + Decode 逐 token。长输出的瓶颈在 Decode，长输入的瓶颈在 Prefill。

3.2 KV Cache：为什么显存是关键资源

生成第 N 个 token 时，模型需要”看到”之前的 N-1 个 token——如果每次都重算，计算量爆炸。KV Cache 把历史 token 的中间结果缓存下来，代价是显存：

这就是”上下文窗口”的真实物理代价：窗口越大，显存需求线性涨。显存不够 → 缩短窗口、用量化、或用 GQA 等减少 KV 的模型架构。

3.3 显存估算公式

先算显存再买卡/选模型——这是推理部署最常踩的坑（OOM 的根因全是预算没算对）。

3.4 批处理：static vs continuous batching

GPU 是”吞吐机器”——一次喂 32 个请求并行算，比串行算 32 次快得多。批处理策略：

策略 做法 问题
Static batching 攒够一批（如 32 个）一起算 长请求拖累全批（等最慢的）；短请求浪费算力
Continuous batching 批内随时插入新请求、剔除完成的 利用率高 10 倍级；现代引擎标配

Continuous batching 是 vLLM 的核心卖点（配合 PagedAttention 管理 KV Cache）——高吞吐的秘诀不在模型，在调度。这与 Java 线程池的”动态调整、避免排队等待”是同一个思想。

四、vLLM 生产部署

4.1 vLLM 是什么

vLLM 是高吞吐推理引擎（PagedAttention 显存管理 + continuous batching + 量化支持），生产自部署的事实标准。Ollama 负责”简单”，vLLM 负责”吞吐”。

4.2 启动与参数

关键参数 作用 调优要点
--max-model-len 窗口上限 过大显存爆，过小拒长输入
--gpu-memory-utilization 显存利用率 0.8-0.95；给 KV 留空间
--tensor-parallel-size 多卡并行 模型太大时开
--quantization 量化类型 见第五章

4.3 服务形态与性能指标

vLLM 起的是 OpenAI 兼容服务（/v1/chat/completions），业务接入同第二章。衡量推理服务的四个指标：

指标 含义 优化方向
TTFT 首 token 时间 降低批大小、量化、Prefill 优化
TPOT 每 token 生成时间 模型/精度选择
吞吐 tokens/s（全并发） 加大批处理、continuous batching 生效
P99 延迟 体验红线 排队控制、容量规划

关键权衡：吞吐 vs 延迟——批越大吞吐越高但单请求延迟越大。生产按 SLA 定批上限（如单请求等待 < 2s）。

4.4 Java 接入与负载均衡

多推理实例（多卡/多机）时，业务层用负载均衡 + 健康检查（Nginx/K8s Service 即可）——多实例推理集群的管理与 Java 服务集群零差别（扩缩容见第八章）。

五、量化

5.1 量化的本质

把权重从 FP16（2 字节）压到 INT8（1 字节）/INT4（0.5 字节）：用精度换显存与速度。三大类：

方案 精度 代表 特点
训练后量化（PTQ） INT8 bitsandbytes 最省事，小模型可无损
低比特量化 INT4 GPTQ / AWQ 大模型主流（70B 压到 35GB）
动态量化打包 混合 GGUF k-quant Ollama/llama.cpp 生态

5.2 权衡表

维度 FP16 INT8 INT4
显存（7B） 14GB 7GB 4GB
效果损失 基准 可忽略 轻微（复杂任务可见）
速度 基准 略快 快（显存瓶颈场景显著）
适用 显存充足 通用默认 大模型/显存受限

实践建议：先跑 FP16 定基准，再试 INT8（通常无损）；显存不够再上 INT4（GPTQ/AWQ），并用评测（LLM评测与可观测性）确认效果损失可接受——量化不是免费的，是有价的，要评测验收。

5.3 量化与微调的关系

  • 微调后的模型（LoRA 合并）可以再量化部署——流程：微调 → 合并 → 量化 → 部署（见 LLM微调入门）；
  • QLoRA 本身就是在量化权重上微调（训练侧量化）。

六、模型路由与降级

6.1 为什么需要路由

真实系统同时有”旗舰需求”与”量大廉价需求”：全走旗舰，成本失控；全走小模型，复杂任务质量不达标。路由 = 按任务难度把请求分到合适的模型：

6.2 路由策略

策略 做法 适用
规则路由 按任务类型/长度关键词匹配 任务形态固定
意图分类路由 小模型先分类，再路由 任务多样
打分路由 按输入复杂度评分阈值 需要精细控制

6.3 降级链

环节 触发 说明
熔断 连续错误率超阈值 快速失败，避免雪崩（LLM API与工具调用实战 6.3）
降级 熔断/超时 依次降档，本地模型是”最后一层保障”
兜底 全部失败 固定话术 + 记录待人工处理

自部署模型在降级链里价值巨大：云 API 不可用时，本地模型保证服务不中断——这就是 1.1 说”混合架构”的工程理由。

七、成本控制

7.1 自部署的成本模型

自部署的成本不是 0——是固定成本：GPU 折旧/租赁 + 电力 + 运维。何时划算：

一个粗略决策示例：日均 100 万 token 全走云 API（中级模型），月成本数万元；一张 24GB GPU（月租数千元）跑 7B INT4 可支撑相近量级。量大才自部署。

7.2 token 视角的成本治理

手段 效果
Prompt 缓存 固定前缀命中，输入 token 消耗与耗时双降（LLM API与工具调用实战 7.2）
输出上限控制 max_tokens 收紧，防长输出烧钱
模型路由 简单任务走小模型（第六章）
批处理监控 单 token 成本 = 硬件成本 ÷ 总产出 token，吞吐即成本

7.3 成本观测

每请求记录：模型、输入/输出 token、延迟、是否缓存命中——按模型/业务线/小时聚合，成本必须可归因（详见 LLM评测与可观测性 成本章节）。

八、可观测与运维

8.1 推理服务指标

指标 含义 健康参考
吞吐（tokens/s） 集群产能 基线对比
平均批大小 批处理效率 越高越省
排队请求数 积压程度 持续 > 0 需扩容
显存利用率 资源紧张度 > 90% 需规划
P99 延迟 / TTFT 体验 SLA 内

8.2 扩容与缩容

推理集群的扩缩容和 Java 服务完全一样：

  • 水平扩展：多实例 + 负载均衡（4.4）；
  • 垂直扩展：单实例加显存（换卡/多卡）；
  • 自动扩缩：K8s HPA 按”排队请求数”或”吞吐”指标伸缩；
  • 关键差异：模型加载耗时（分钟级）→ 预热策略：提前拉起实例、避免流量高峰时现场加载。

8.3 常见故障与排查

故障 排查方向
OOM 显存预算（3.3 公式）→ 缩窗口/量化/减批
吞吐骤降 批大小/排队 → 是否被长请求占满
首 token 慢 Prefill 瓶颈 → 批太大/输入太长

LLM评测与可观测性

Posted on 2026-08-05 In AI大模型 Word count in article: 2.3k Reading time ≈ 8 mins.

LLM 评测与可观测性

本文是《AI学习体系导航》阶段五的评测+可观测专题：AI 系统上线后，”效果到底怎么样、哪里在变差、钱花到哪了”必须有数据回答。覆盖离线评测（RAGAS 等）与线上观测（Langfuse、指标告警）两条线，以及把两者串起来的优化闭环。RAG 场景的评测落地见 RAG原理与实践 第八章，本文是其体系化展开。

撰写时快照：本文基于 2026 年 8 月主流评测与观测工具撰写；指标定义与工具 API 以官方文档为准。

一、为什么要评测

1.1 LLM 系统是”概率系统”，必须用样本说话

传统软件的测试（单测、集成测试）对确定性逻辑有效；LLM 系统的输出每次不同，”这次跑对了”不能说明”下次也对”。评测 = 用固定样本集 + 统计指标，把概率系统变成可度量的工程对象。

Java 对照：评测体系 ≈ 测试体系 + 监控体系的 AI 版。RAGAS 指标 ≈ 单测断言，评测集 ≈ 回归测试集，线上指标 ≈ Prometheus 告警。

1.2 两条线缺一不可

线 时间 回答的问题 工具
离线评测 上线前/迭代中 这次改动变好还是变差？ 评测集 + RAGAS/LLM Judge
线上观测 运行中 生产上效果如何、哪里异常？ Langfuse/自研埋点 + 指标告警

**离线评测管”改版门禁”，线上观测管”运行健康”**——只做任何一条都会出事：只做离线会漏掉线上分布偏移；只做线上则无法定位具体版本问题。

二、RAGAS 评测

2.1 四个核心指标

RAGAS 是开源 RAG 评测框架，指标可分两层（检索层 + 生成层）：

指标 层面 衡量 直觉理解
上下文相关性（Context Precision/Relevancy） 检索 检索结果与问题相关度 检索得准不准
上下文召回（Context Recall） 检索 该有的资料是否都被召回 有没有漏
忠实度（Faithfulness） 生成 回答是否忠于检索资料 有没有编造
答案相关性（Answer Relevancy） 生成 回答是否切题 有没有答非所问

两个层面分开看：检索指标差 → 修检索（分块/重排/混合检索）；生成指标差 → 修 Prompt 与上下文组装。混在一起无法定位。

2.2 评测集格式与运行

2.3 指标解读的注意事项

现象 说明
忠实度低 模型没”照着资料答”——查防幻觉指令、引用溯源
上下文召回低 检索漏了——查分块大小、混合检索、top_k
上下文相关低 + 召回高 召回太宽——查 Rerank、过滤规则
答案相关低 模型跑题——查系统指令与任务定义

指标只是信号，不是结论：每个指标异常都对应一个可排查的方向清单（RAG 场景的排查表见 RAG原理与实践 8.4）。

三、评测集构建

3.1 来源与规模

方式 做法 适用
真实日志采样 线上用户问题抽样 最有代表性，首选
人工标注 专家写标准答案与边界问题 冷启动、质量基准
LLM 合成 让模型生成变体/边界问题 补充覆盖（需人工抽检防幻觉标注）

规模建议：起步 30-50 条（典型 70% + 边界 30%），迭代期逐步扩容；每条带 category 标签（退款/物流/账户…），改版时按类别看升降。

3.2 评测集的工程治理

  • 进 Git：评测集是”测试用例”，随代码版本管理；
  • 版本化：评测集改版与系统改版分开记录，防止”指标涨了是因为评测集换了”；
  • 真值审查：定期抽检 ground_truth 本身的质量（AI 合成标注尤其要查）。

四、Agent 评测

4.1 为什么 Agent 评测不一样

Agent 是”过程 + 结果”的系统（见 Agent原理与实践）：结果对了但过程错（绕路、调用不该用的工具）也是问题。所以 Agent 评测必须评轨迹：

维度 指标 采集方式
任务成功率 端到端完成率 人工/规则判定最终结果
工具调用正确性 每一步是否用了正确的工具/参数 轨迹标注或规则校验
步骤效率 平均轮数 vs 最优轮数 轨迹统计
安全合规 是否触犯禁区（误用高权限工具） 规则 + 人工抽检

4.2 轨迹评测实操

**Agent 上线前必须有一组”轨迹用例”**（给定任务 → 期望工具链 → 判定通过/失败），否则多步 Agent 的行为退化解耦无感。

五、LLM 可观测

5.1 观测什么

观测项 内容 对应问题
调用追踪（Trace） 一次请求全链路：模型调用、工具调用、RAG 检索 慢在哪、错在哪
Token 用量 输入/输出/缓存命中 钱花哪了
延迟 TTFT、总耗时、P50/P95 体验如何
错误 429/超时/解析失败率 稳不稳
成本 token × 单价汇总 预算是否超支

5.2 Langfuse：开源的 LLM 观测平台

Langfuse 提供 trace、token 统计、成本估算、评测集管理与打分面板，SDK 接入极轻：

埋点位置必须是统一 LLMClient 层——业务代码无感，观测随框架自动生效。

5.3 自研 vs 工具

方案 优点 缺点
Langfuse 等现成平台 零维护、带评测面板 数据出网（合规需评估）
自研埋点（日志 + Prometheus + Grafana） 数据主权、与现有监控体系统一 开发成本、无现成 Agent 轨迹视图

Java 团队建议：起步用自研（复用现有 Prometheus/Grafana 体系，指标口径一致），Agent 轨迹视图按需自建；敏感场景必须自研。

六、线上指标与告警

6.1 指标体系

层级 指标 告警阈值（参考）
可用性 请求成功率 < 99% 告警
性能 P95 总延迟 / TTFT 超业务 SLA 告警
质量 抽检满意度 / 人工标注跑分 连续下降 2 个周期告警
成本 单日成本 / 单请求平均成本 超预算 120% 告警
稳定性 429 率、超时率 > 1% 告警

6.2 质量指标怎么上告警

LLM 质量无法实时自动判定（成本高），工程化做法是抽样 + 人工/LLM 判定：

  • 按比例抽样（如 1%）存样本 → LLM Judge 初筛 → 人工复核疑点样本；
  • 判定结果回流成线上指标（满意度分）；
  • 连续下降触发告警 → 拉出变差样本 → 复现定位（Prompt 改了吗？模型换了吗？检索数据更新了吗？）。

抽样判定 ≈ Java 侧的”线上拨测 + 日志采样分析”——把不确定的 LLM 质量变成可告警的数字。

七、评测 → 定位 → 优化闭环

核心原则：一次只改一个变量。 同时改 Prompt + 分块 + 重排，指标涨了也不知道是谁的功劳——这和 Java 性能优化的控制变量法完全一致。

四、Agent 轨迹 集成测试/链路测试 轨迹用例 ≈ 场景级集成测试

Spring AI 与 LangChain4j 实战

本文是《AI学习体系导航》阶段二的核心实践篇，也是本站唯一的 Java AI 框架代码文：用 Java 生态把前几篇文章讲的能力（对话、流式、工具调用、RAG）实现一遍。协议原理见 LLM API与工具调用实战，RAG 全链路见 RAG原理与实践。

撰写时快照：本文基于 2026 年 8 月的 Spring AI / LangChain4j 版本撰写；两个框架迭代极快，依赖版本与 API 以官方文档为准。

一、为什么需要 Java AI 框架

1.1 现状：AI 生态主战场在 Python

LangChain、LlamaIndex、vLLM 等主流生态都是 Python 优先，Java 开发者直接照抄示例会遇到两个问题：示例跑不通、出了问题没有本地社区可问。Spring AI（Spring 官方）与 LangChain4j（社区）就是 Java 生态对这两个问题的回答——把”调用模型、组装 Prompt、管理对话、接入向量库、工具调用”抽象成 Java 惯用的形式。

1.2 框架解决什么

关注点 裸写（OkHttp 手拼） Spring AI / LangChain4j
模型调用 手写 HTTP + JSON 解析 ChatClient，一个接口
流式响应 WebFlux 手拼 SSE 流式 API 一行开启
工具调用 手写 schema + 循环回填 @Tool 注解即 schema
RAG 手写分块/向量化/检索链路 文档加载器 + VectorStore 开箱
多模型切换 改代码 配置切换，模型路由

1.3 与 Python 生态的关系

维度 Spring AI / LangChain4j LangChain / LlamaIndex
语言 Java/Kotlin Python
生态广度 覆盖主流场景 最全、新特性最快
工程集成 Spring Boot 原生（监控/配置/事务） 需自己接入
适合 Java 存量团队、企业系统集成 算法/原型团队

结论：不是二选一。团队里 Python 做实验与数据，Java 做生产服务（见第六章分工）。

二、Spring AI 核心

2.1 最小对话应用

ChatClient 是 Spring AI 的核心抽象：prompt() 组装输入、call() 同步调用、content() 取文本。一个接口屏蔽了协议细节——这就是 LLM API与工具调用实战 讲的”统一 Client 层”由框架代劳了。

2.2 流式响应

Controller 直接返回 Flux<String>（WebFlux 自动 SSE）——流式转发到前端零胶水代码。

2.3 系统指令与模板

system() / user() / variables() 对应 messages 的角色与模板变量——与 Prompt工程实战 的五要素模板完全对应。

2.4 工具调用：@Tool 注解

对比 LLM API与工具调用实战 第四章手写的 schema + 回填循环——框架把协议细节全部消化，方法签名即契约。

2.5 多模型路由

多个 ChatModel Bean + 配置化选择（对应成本章节的模型路由）：

简单任务走小模型、复杂任务走大模型——路由逻辑与 LLM API与工具调用实战 第七章同构，只是配置化。

三、Spring AI Alibaba

3.1 是什么

Spring AI Alibaba（阿里开源，spring-ai-alibaba）是 Spring AI 的阿里云生态实现：对接百炼平台（DashScope）的模型与服务，并提供企业级能力（Starter 自动装配、可观测性集成等）。

3.2 选择建议

场景 选择
国内合规 / 通义模型 Spring AI Alibaba（百炼）
国际模型 / 开源模型兼容 Spring AI OpenAI starter（base-url 指向任何兼容端点）
都要 两个 starter 共存，按模型路由

协议统一的好处再次体现：切换 = 换 starter + 换 api-key，业务代码不动。

四、LangChain4j

4.1 定位：Java 版的 LangChain

LangChain4j 提供与 LangChain 对应的抽象（LLM、Embedding、Document、EmbeddingStore、Retriever、Agent），但以 Java 类型安全方式实现——AI Services 是其招牌特性。

4.2 AI Services：接口即 AI

用接口定义 AI 能力——比直接调 SDK 更符合 Java 工程习惯：接口即契约，mock/测试/替换都容易。

4.3 工具绑定

4.4 RAG 全链路

对比 RAG原理与实践 的 Python 链路：概念完全对应（分块参数、检索器、上下文注入），只是换成了 Java 类型安全 API——这正是”原理不变、语言无关”的实证。

五、实战：两个交付物

5.1 交付物一：Spring AI 对话应用

  • Spring Boot 3.x + spring-ai-openai starter；
  • REST 接口：POST /api/chat（同步）+ GET /api/chat/stream（SSE 流式）；
  • 注册 2-3 个 @Tool（天气、计算器）；
  • 验证：curl 调用 + 流式前端页面。

5.2 交付物二：LangChain4j 知识库问答

  • 导入 10 篇真实文档（Markdown/PDF）；
  • 分块 → 向量化 → 入库（InMemory 起步，验证后换 Milvus）；
  • Assistant 接口 + contentRetriever 组装；
  • 验收（对齐 RAG原理与实践 标准）：20 个问题检索命中率 ≥ 90%、回答带引用。

5.3 常见坑
