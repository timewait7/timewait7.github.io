DNS 与网络排查实战

Posted on 2026-08-13 In 计算机网络 Word count in article: 3.2k Reading time ≈ 12 mins.

DNS（Domain Name System）是把域名翻译成 IP 的分层数据库：浏览器访问任何网站的第一件事，都是问 DNS「这个域名在哪个 IP」。 它本身是一次「应用层查询」，却发生在 TCP 连接之前——解析快慢直接进首屏时间，解析错误直接断网。本文回答四个问题：解析链路怎么走、缓存为什么关键、DNS 在生产里扮演什么角色（LB/CDN/HTTPDNS）、网络故障怎么按分层定位——并把系列工具链收拢成「症状 → 层 → 工具 → 根因」的完整排查法。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（可靠传输与代价）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（本文：工具收拢） → ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. DNS 解析：从域名到 IP 的分层接力

1.1 为什么需要 DNS：名字与地址的分离

IP 是「地址」，域名是「名字」——名字的意义是：可以改地址、可以有多个地址、可以全球唯一。这带来两个直接能力：

  1. 负载均衡：一个域名配多个 A 记录（www.baidu.com → 10.0.0.1/10.0.0.2/10.0.0.3），解析时随机返回——DNS 是最原始的负载均衡，比四层/七层 LB（第 1 篇 §5.1）更靠前：它直接决定「请求发给哪台机器」；
  2. CDN 接入：域名用 CNAME 指向 CDN 厂商的域名，CDN 的权威服务器按用户地理位置返回就近节点 IP——第 3 篇讲的「CDN 缓存」能生效，前提是 DNS 把用户导到了离他最近的节点。

1.2 递归与迭代：一次解析的完整接力

递归查询：客户端只问「帮我查 www.baidu.com」，本地递归服务器负责搞定；迭代查询：递归服务器逐级问根服务器「.com 找谁」、问 .com 顶级服务器「baidu.com 找谁」、最后问 baidu.com 的权威服务器「www 的 IP 是」：

flowchart TD
    C["Browser"] -->|"recursive: www.baidu.com?"| R["Local recursive resolver<br/>(ISP / 8.8.8.8 / 114.114.114.114)"]
    R -->|"iterative: who is .com?"| ROOT["Root servers (13 groups)"]
    ROOT -->|".com TLD server ->"| R
    R -->|"iterative: who is baidu.com?"| TLD[".com TLD servers"]
    TLD -->|"baidu.com authoritative ->"| R
    R -->|"iterative: A record of www?"| AUTH["baidu.com authoritative servers"]
    AUTH -->|"IP 1.1.1.1 + TTL"| R
    R -->|"IP 1.1.1.1"| C

因果链：这个接力是「第 1 篇分层的递归应用」——每层只回答「下一层去哪问」的问题，与路由器「只认下一跳」完全同构（第 1 篇 §4.1）；区别是路由器转包、DNS 转「问题」。面试速记：客户端问递归（一次问完），递归服务器逐级迭代（分级追问）。

1.3 缓存层级：TTL 是唯一的失效开关

解析结果会被四级缓存：浏览器 → 操作系统 → 本地递归服务器 → 各级 DNS 服务器，每级缓存按 TTL（记录生存时间，A 记录常见 60-600 秒） 过期：

缓存层 谁持有 特点
浏览器缓存 浏览器进程 最快，几十秒级
操作系统缓存 /etc/hosts + 系统解析器 hosts 优先于一切，可手动覆盖
本地递归服务器 ISP/公共 DNS 秒级 TTL，服务所有用户
权威服务器 域名所有者 无缓存，TTL 由它下发

TTL 是 DNS 的命门：域名切换 IP 后，「生效时间 = 最高 TTL 的缓存层过期时间」——TTL 设 600 秒的域名切 IP，最坏 10 分钟才全部生效。生产「切了 IP 用户还在访问老机器」的根因九成在这。

1.4 动手验证：dig 把解析拆开看

观察点：+trace 输出从根服务器的提示开始逐级展开——递归与迭代的现场；多个 A 记录说明该域名在做 DNS 负载均衡。判定标准：+trace 里能看到「根 → .com → 权威」三级且最后给出 IP，就亲眼看到了 §1.2 的接力。

2. DNS 的生产形态：LB、CDN 与 HTTPDNS

2.1 深挖：CDN 与 HTTPDNS——DNS 的两个生产难题

问题 1：就近调度不精准。 系统 DNS 由 ISP 分配，递归服务器所在位置不等于用户位置——CDN 拿递归服务器的 IP 判断用户地域，可能把北京用户导到上海节点。问题 2：DNS 可被劫持。 公共网络/运营商可能篡改 UDP 53 的响应（污染），把域名指到广告/钓鱼 IP。

两个问题的解法汇聚到移动端 HTTPDNS：App 不走系统 DNS，而是直接 HTTP 请求厂商的解析 API（如 http://119.29.29.29/d?dn=www.xxx.com）拿到 IP——用 HTTP（第 3 篇的协议）替代 UDP 53（DNS 原生的脆弱通道），既绕开劫持（HTTPS 加密 + 厂商鉴权），又能拿到基于用户真实出口 IP 的精确调度。

因果链：DNS 用 UDP 53 是因为「单次请求-响应、无状态」（第 2 篇 UDP 对比表）——这个轻量设计是性能优势，也是被劫持的漏洞来源；HTTPDNS 是「用应用层更重的通道换可靠性」的典型交易，与 HTTP/3 换掉 TCP（第 3 篇 §2.3）是同一个决策模式：下层通道给不了的保证，换个通道实现。

2.2 深挖：容器里的 DNS——K8s 的 CoreDNS

K8s 集群里 Pod 间通信靠 Service 名，解析由集群内 DNS（CoreDNS）完成：Pod 的 /etc/resolv.conf 指向 CoreDNS，且带 search 域（default.svc.cluster.local）——短域名自动补全域名后缀：

因果链：Pod 访问 my-service 会依次试 my-service.default.svc.cluster.local → my-service.svc.cluster.local → my-service.cluster.local——search 域让「短名可用」是牺牲查询次数换来的；排查 K8s 里「跨 namespace 访问用短名失败」就是忘了加全限定名。这是 DNS 机制在容器时代的直接变形。

2.4 动手验证：复现一次「TTL 缓存」观察

观察点：两次查询 ANSWER 区IP 相同、TTL 递减——你在看一个活着的缓存条目在倒数计时。判定标准：TTL 从 600 → 590 左右即验证了「缓存按 TTL 倒计时」的机制；这也预告了 2.3 表第一行的生产教训（TTL 设多长，切换就等多长）。

3. 网络排查实战：症状 → 层 → 工具

3.1 分层定位法：四问定层

网络故障排查的核心是先定层、再用该层的工具（第 1 篇 §1.3 的雏形，现在收拢成完整流程）：

flowchart TD
    FAIL["App error / timeout"] --> Q1{"DNS resolves?"}
    Q1 -- No --> T1["dig / nslookup<br/>-> DNS layer problem"]
    Q1 -- Yes --> Q2{"TCP connects?"}
    Q2 -- No --> T2["nc / ss / telnet<br/>-> network / firewall / LB"]
    Q2 -- Yes --> Q3{"TLS handshake?"}
    Q3 -- No --> T3["openssl s_client<br/>-> cert / TLS config"]
    Q3 -- Yes --> Q4{"HTTP status?"}
    Q4 -- "4xx" --> T4A["request problem (client)"]
    Q4 -- "5xx" --> T4B["server / upstream problem"]

每一层的工具与判定标准：

层 工具 通过标准
DNS dig 能返回 A 记录
TCP nc -vz host port succeeded 字样
TLS openssl s_client -brief 能输出证书与协议
HTTP curl -i 拿到状态码
应用 服务日志 有对应请求日志

3.2 案例复盘：三个真实排障

案例一：解析到老 IP

环节 内容
症状 域名切换新机器后，部分用户仍访问旧机器，旧机器已关，用户报「打不开」
工具 dig +short 在本机解析出新 IP；dig @8.8.8.8 +short 也是新 IP；但 nslookup 走运营商 DNS 仍是旧 IP
根因 运营商递归服务器缓存未过期（切换前 TTL 设的 600s）——§2.3 第一行的标准场景
处理 等 TTL 过期自然收敛；此后切换流程固定为「先降 TTL 至 60s，等 24h 再切」

案例二：客户端偶发连接被重置

环节 内容
症状 移动端间歇性 RST（连接被重置），PC 正常
工具 抓包看到 RST 直接回；nc -vz 偶发失败；对比不同网络（WiFi/4G）
根因 运营商/中间设备对 UDP 53 与长连接做干扰；或四层 LB 连接数限制触发重置
处理 移动端换 HTTPDNS（§2.1）；服务端确认四层 LB 连接复用配置

案例三：502 与 504 的判别

环节 内容
症状 网关报 502 或 504，业务侧「看起来没挂」
工具 curl -i 确认状态码；nc -vz 上游IP 端口 测 TCP；看上游响应时间
根因 502 = 连不上上游（端口/防火墙/上游没起）；504 = 连上了但超时（上游慢、队列满）——第 3 篇 §1.2 的判别落地
处理 502 查网络与进程；504 查上游性能与超时配置（网关 proxy_read_timeout）

三个案例的共同模式：先 dig 排除 DNS、再 nc 排除 TCP、最后才是应用层——按分层顺序排查，每层一个工具一次判定，永远不跳层。

3.3 动手验证：完整跑一遍分层定位

观察点：四条命令依次通过/失败的位置，就是故障所在的层——把「不知道哪坏了」变成「明确坏在第几层」。判定标准：任一步失败后，该层对应的工具（dig/nc/openssl/curl）就是下一步排查的起点；这个流程值得存成 netcheck.sh，任何网络问题先跑一遍（与操作系统系列第 5 篇的 sos.sh 同款习惯）。

实操建议：

HTTP 协议：应用层之王

Posted on 2026-08-13 In 计算机网络 Word count in article: 3.7k Reading time ≈ 14 mins.

HTTP（HyperText Transfer Protocol）是应用层的请求-响应协议：浏览器和服务端用「方法 + URL + 状态码 + 头 + 体」这套固定骨架，交换业务语义。 它是你每天接触最多的协议——网关、CDN、负载均衡、浏览器缓存、前后端联调全在说它的语言。本文回答四个问题：HTTP 报文长什么样、无状态怎么补状态、连接与性能怎么演进（1.0 → 1.1 → 2 → 3）、缓存和 HTTPS 在生产里怎么用——并对照 keep-alive 与端口耗尽、304 命中、HTTPS 握手开销这些场景，看协议演进如何被「下层机制」一路推着走。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（可靠传输与代价）→ ③ HTTP 协议（本文：应用层之王） → ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. HTTP 的骨架：请求-响应模型

1.1 报文结构：固定四段

请求：请求行（方法 路径 版本）→ 请求头 → 空行 → 请求体。响应：状态行（版本 状态码 短语）→ 响应头 → 空行 → 响应体。

flowchart LR
    subgraph REQ["Request"]
        R1["GET /index.html HTTP/1.1<br/>Host: blog.example.com<br/>Cookie: sid=abc<br/><br/>(body)"]
    end
    subgraph RESP["Response"]
        S1["HTTP/1.1 200 OK<br/>Content-Type: text/html<br/>Cache-Control: max-age=60<br/><br/>&lt;html&gt;..."]
    end
    REQ -->|"over TCP (keep-alive)"| RESP

头部是「元数据」的载体：Host（虚拟主机路由）、Content-Type（体格式）、Cookie（会话状态）、Cache-Control（缓存策略）。空行是头和体的分界——解析器先读到空行，才知道「头结束了、体从哪开始」（第 1 篇 §5.2 的长度边界问题在这里有个简单的解：空行本身就是一个边界标记）。

1.2 状态码：生产只看这几档

档位 含义 生产常见
2xx 成功 200 正常、204 无内容（DELETE 等）
3xx 重定向/协商 301 永久、302 临时、304 缓存未变（§3.2）
4xx 客户端错误 400 参数错、401 未认证、403 无权限、404 不存在、413 体过大、429 限流
5xx 服务端错误 500 程序异常、502 网关拿不到上游、503 过载/停机、504 上游超时

面试速记：4xx 是「请求本身的问题」，5xx 是「服务的问题」——排查第一问就是「状态码第几位」。502 与 504 的分界是「连接被拒/断开 vs 等不到响应」，两者排查方向不同（网关配置 vs 上游超时）。

1.3 无状态与 Cookie：协议的无记忆 vs 业务的需要

HTTP 本身无状态：每个请求都是独立的，服务端不记得你是谁。但业务需要会话——于是 Cookie 在应用层补了状态：服务端在响应头 Set-Cookie 里下发一个会话 ID，浏览器之后每次请求自动带上。因果链：无状态是 HTTP 的可扩展性根源（任何一台服务器都能服务任何请求，负载均衡随便转发——回看第 1 篇 §5.1 七层 LB 的会话保持），Cookie 是「协议无状态 × 业务要状态」的补丁；而补丁带来的安全问题（Cookie 被偷、被伪造）催生了 SameSite、Secure、HttpOnly 这些属性。

1.4 动手验证：把一次请求的报文完整看一遍

观察点：第一行状态行 HTTP/1.1 200 OK、Content-Type、Set-Cookie（如果有）逐行可读；-w 的计时把「DNS → TCP 连接 → 总时间」拆开——每个阶段对应分层模型的一层（DNS 在第 4 篇展开）。判定标准：能说出「计时三段的每一段是哪一层干的」即通过。

2. 连接与性能：从 keep-alive 到 HTTP/3

2.1 keep-alive：连接复用的价值

HTTP/1.0 时代每个请求都新建 TCP 连接——三次握手 + 四次挥手每请求一次。HTTP/1.1 默认 keep-alive：一个 TCP 连接串行复用多个请求。

因果链（跨两篇闭环）：短连接时代，「服务端主动关闭」产生大量 TIME_WAIT（第 2 篇 §1.4 的机制）→ 高并发下端口耗尽（操作系统系列第 5 篇 §5.1 的事故现场）→ keep-alive 让连接复用、让 TIME_WAIT 不再产生。HTTP/1.1 的默认连接策略，就是 TCP 机制这笔账算出来的——这也是为什么面试问「TIME_WAIT 怎么治」时答「连接复用」会追溯到 HTTP 连接管理。

2.2 队头阻塞：HTTP/1.1 的原罪

keep-alive 下请求仍然串行：一个请求没响应完，下一个就得等——队头阻塞（HOL blocking）。浏览器的应对是并发连接（Chrome 同源约 6 条），但也到顶了。于是 HTTP/2 换思路：一个 TCP 连接里塞多个并行的「流（stream）」，字节流被切成帧交错发送，接收方按流重组：

flowchart TD
    subgraph H11["HTTP/1.1: serial requests on one connection"]
        A1["Req1 ... wait ... Resp1 -> Req2 -> Resp2"]
    end
    subgraph H2["HTTP/2: multiplexed streams over one connection"]
        B1["stream1: Req/Resp 1 -------"]
        B2["stream2: Req/Resp 2 ---"]
        B3["stream3: Req/Resp 3 -------"]
    end

加上二进制分帧（帧 = 头 + 类型 + 所属流 ID）和 HPACK 头部压缩，HTTP/2 把「并发」从「多条连接」变成了「一条连接内的多路复用」。

2.3 深挖：队头阻塞没消失，只是搬家了

HTTP/2 的多路复用治好了「应用层」队头阻塞，但 TCP 的队头阻塞还在：一条 TCP 连接丢一个包，TCP 要等重传，阻塞的是整条连接上的所有流。于是 HTTP/3 干脆换掉传输层——QUIC 协议跑在 UDP 上，自己实现可靠传输、多路复用、0-RTT 连接恢复：

版本 传输层 并发方式 队头阻塞 握手
HTTP/1.1 TCP 多条连接（浏览器 ~6 条） 应用层串行 1 RTT
HTTP/2 TCP 单连接多流 应用层解决，TCP 层仍有 1 RTT
HTTP/3 QUIC (UDP) 单连接多流 传输层也解决 0-1 RTT

因果链：这条演进链是「上层协议被下层机制约束」的完整教材——HTTP/2 的每个设计点都是对 HTTP/1.1 缺陷的回答，HTTP/3 的回答是「既然 TCP 的可靠性模型跟不上，就把可靠传输拿回应用层自己做」（和第 1 篇 §5.2 粘包拆包同构：传输层给不了的语义，应用层自己补）。

2.4 动手验证：看协议协商（ALPN）与连接复用

观察点：ALPN, server accepted ... h2 说明协商到 HTTP/2；Re-using existing connection 说明 curl 复用了同一 TCP 连接——keep-alive 的现场。判定标准：能同时看到「HTTP/2 协商」和「连接复用」两条日志，本节机制就算看到了；curl --http1.1 重跑对比，HTTP/2 握手少一个往返（time_connect 更快）。

3. 缓存：让数据少走网络

3.1 两级缓存决策：先问本地，再问服务器

浏览器拿到响应先看强缓存（Cache-Control: max-age=60）：60 秒内直接用本地副本，不发请求；过期后再发请求做协商缓存：带 If-None-Match（ETag 值），服务端比对后若没变回 304 Not Modified（只传头、不传体）：

flowchart TD
    REQ["Request"] --> CC{"Cache-Control valid?"}
    CC -- Yes --> LOCAL["Use local copy (no request)"]
    CC -- No --> ETAG{"Send If-None-Match /<br/>If-Modified-Since"}
    ETAG -- "Unchanged" --> N304["304: headers only, no body"]
    ETAG -- "Changed" --> N200["200: full response"]

易错点（面试高频）：no-cache 不是「不缓存」，是「每次都要协商」；no-store 才是「真的不存」。max-age 的优先级高于 Expires。

3.2 深挖：缓存一致性——为什么前端文件都带 hash

缓存提高性能的前提是内容不变；内容变了要能让用户拿到新版本。生产标准做法：内容寻址——文件名带内容 hash（app.a1b2c3.js），hash 变 = 文件名变 = 新的缓存条目；发布时静态资源 max-age 设一年，靠文件名变化让浏览器「被迫」重新拉取。因果链：静态资源长缓存 + hash 文件名 = 用「文件名即版本」绕开「缓存无法主动失效」的协议局限——CDN 的分发逻辑同样是这个模型（CDN 节点缓存到源站的 HTTP 响应，回源策略就是缓存策略）。

3.3 动手验证：起一个带缓存头的服务，看 200 → 304

观察点：第一次 200 带回缓存头；带 If-None-Match 的第二次只回 HTTP/1.1 304 Not Modified（无体）——协商缓存的完整流程。判定标准：304 出现即验证通过；再体会「304 省的是体、不是请求」——RTT 还在，这就是强缓存比协商缓存更贵的道理。

4. 安全：HTTPS 与常见攻击

4.1 HTTPS：在应用层和传输层之间加一层安全

HTTPS = HTTP + TLS。TLS 干两件事：身份认证（证书链）+ 加密传输（对称密钥 + 非对称交换）。简化握手：

sequenceDiagram
    participant Client
    participant Server
    Client->>Server: ClientHello (support TLS 1.3, key share)
    Server->>Client: ServerHello with certificate and signature
    Client->>Server: Verify chain and send encrypted keys (1-RTT done)
    Note over Client,Server: TLS 1.3: 1 RTT, session resume: 0 RTT

因果链：为什么 HTTPS 慢、为什么 TLS 1.3 快——TLS 1.2 完整握手要 2 个 RTT（协商 + 密钥交换），TLS 1.3 砍到 1 个 RTT（密钥共享提前到 ClientHello），会话恢复 0 RTT。每少一个 RTT，都是对「第 2 篇 BDP 视角」的呼应：跨洋请求的每个 RTT 都是 100ms 级，握手 RTT 数量直接进用户体验。生产上「全站 HTTPS 变慢」的优化手段（OCSP stapling、会话复用、TLS 1.3）全是「减少 RTT」的努力。

4.2 深挖：中间人攻击为什么会被证书拦住

TLS 防的是中间人（MITM）：攻击者伪装成服务器截获流量。原理：服务端必须出示可验证的证书（域名 + 公钥，由证书颁发机构 CA 签名），客户端验证签名链——攻击者的证书没有被受信任的 CA 签过名，验证失败。因果链：证书信任链是「分层模型之外的信任层」——它不在任何一层传输数据，而是给「传输的双方身份」背书；生产里「自签证书」「内网 https 绕过验证」都是在削弱这一层换取便利，代价是中间人风险重新打开。

4.3 常见攻击与 HTTP 层的防御

攻击 机制 HTTP 层防御
CSRF 攻击者诱导浏览器带 Cookie 发请求（Cookie 自动携带） SameSite=Lax/Strict、CSRF Token、校验 Referer

深挖：CSRF 的根源是「HTTP 无状态 × Cookie 自动携带」的补丁副作用——无状态（§1.3）让服务端认 Cookie，Cookie 自动携带让攻击者可以「借」受害者的身份发请求；SameSite 是浏览器层对「跨站请求不该带 Cookie」的补丁。每一次攻击与防御，都是对协议设计权衡的再修补。

4.4 动手验证：看 TLS 握手的实际协商结果

观察点：SSL connection using TLSv1.3 说明协商到 TLS 1.3（1-RTT）；openssl s_client -brief 能看到证书签发者（CA）和协议版本。判定标准：能读出「协议版本 + 证书签发者 + 加密套件」三项即通过——这就是 4.1/4.2 的机制在真实连接上的落点。

TCP 协议：可靠传输的代价

Posted on 2026-08-13 In 计算机网络 Word count in article: 4k Reading time ≈ 14 mins.

TCP（Transmission Control Protocol）是传输层的可靠字节流协议：用序号、确认、重传、窗口四套机制，把不可靠的网络变成「有序、不丢、不重」的字节流。 可靠是有代价的——握手延迟、确认往返、拥塞退避，每一个都是「性能 vs 可靠性」的显式权衡。本文回答四个问题：连接怎么建立和拆除、可靠性靠什么保证、为什么 TCP 有时快不起来、状态机怎么变成线上事故——并对照 TIME_WAIT/CLOSE_WAIT 堆积、SYN 洪泛、TCP_NODELAY 这些生产场景，看机制如何长成排查手段。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（本文：可靠传输与代价） → ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. 三次握手与四次挥手：连接的建立与拆除

1.1 三次握手：互相确认序号

连接建立的本质是双方同步序号——后续所有可靠性都建立在序号上。三次握手每次交换的都是「我的初始序号 + 我确认收到你的」：

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: SYN seq=100 (SYN_SENT)
    S->>C: SYN+ACK seq=300 ack=101 (SYN_RECV)
    C->>S: ACK seq=101 ack=301 (ESTABLISHED)
    Note over C,S: ESTABLISHED: 双方都确认了对方序号
  • 第 1 次（SYN）：客户端说「我想连，我的起始序号是 100」
  • 第 2 次（SYN+ACK）：服务端说「收到，我的起始序号是 300，请确认 101」
  • 第 3 次（ACK）：客户端说「确认 301」——只有第 3 次到达，服务端才确认「客户端确实活着」

1.2 为什么是三次而不是两次

两次握手无法防御「迟到的旧 SYN」：若客户端某次连接的超时 SYN 在网络里游荡，1 秒后才到服务端，服务端回 SYN+ACK 并建立连接、占用资源——而客户端根本不知道这回事（它早已放弃）。三次握手中客户端第 3 次的 ACK 携带了「我确实在发起这次连接」的确认，服务端收到它才分配连接资源，旧 SYN 永远等不到第 3 次 ACK，自然超时释放。

深挖：这直接决定了半连接与全连接队列的设计——服务端收到 SYN 只进半连接队列（内核管理，还没分配完整连接），收到第 3 次 ACK 才移入全连接队列（应用层 backlog 参数），accept() 从全连接队列取。两个队列的容量就是两个不同的攻击面（§4.2 展开）。

1.3 四次挥手：半关闭的两段告别

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: FIN (FIN_WAIT_1)
    S->>C: ACK (CLOSE_WAIT / FIN_WAIT_2)
    S->>C: FIN (LAST_ACK)
    C->>S: ACK (TIME_WAIT 2MSL / CLOSED)

挥手是四次而不是三次，因为 TCP 支持半关闭：收到 FIN 只代表对方「不再发」，本端可能还有数据要发。于是「FIN → ACK」（对方发完）和「FIN → ACK」（本端发完）是两对独立的过程。生产上的时间点：先收到 FIN 的一方进入 CLOSE_WAIT，最后发送 FIN 的一方进入 TIME_WAIT。

1.4 深挖：TIME_WAIT 为什么必须等 2MSL

主动关闭方最后发 ACK 后进入 TIME_WAIT，等待 2 倍 MSL（报文最大生存时间，Linux 默认 60 秒），两个原因：

  1. 保证最后的 ACK 到达：ACK 可能丢失，对方会重发 FIN——TIME_WAIT 期间内核能重发 ACK；
  2. 防止旧报文污染新连接：网络中可能还游荡着这条连接的迟到报文（序号可能撞上新连接的序号），等 2MSL 让它们自然消亡。

因果链：TIME_WAIT 是「防迟到报文」的安全收尾，所以它不能通过调小端口或缩短等待来根治——高并发短连接服务的 TIME_WAIT 堆积（操作系统系列第 5 篇 §5.1 的端口耗尽事故）正解是连接复用：HTTP keep-alive、连接池把短连接变长连接，让 TIME_WAIT 根本不产生。机制决定解法，这是最典型的一例。

1.5 动手验证：亲眼看到握手与挥手

观察点：抓包里依次出现 S（SYN）→ S.（SYN+ACK）→ .（ACK）→ 数据 → 挥手时 F/F./F.P. 序列。判定标准：每 4 个包一组对应一次连接，三次握手 3 个包 + 挥手 4 个包清晰可见即验证通过。顺手看 ss -tan | grep 45681，客户端断开后服务端进入 CLOSE_WAIT——状态机不是背的，是观察出来的。

2. 可靠传输：序号、确认与重传

2.1 序号与累计确认

发送方给每个字节编号（seq），接收方回「下一个期望的字节号」（ack）。累计确认：ack=501 表示「500 之前都收到了，请从 501 开始发」——接收方不需要逐字节确认，一个 ack 覆盖之前全部。这是 TCP 高效的根本：确认开销与数据量无关，与「空洞」次数有关。

2.2 三种重传：从傻等到智能

重传机制 触发条件 代价
超时重传 发出去没等到 ACK，RTO 到期 慢（RTO 通常 200ms 起，指数退避）
快速重传 收到 3 个重复 ACK 快（不用等超时，立刻知道丢了）
SACK 收到带 SACK 选项的 ACK（报告空洞范围） 最快（只重传丢失的段，不重传全部）

深挖：快速重传是怎么「不超时就知道丢了」的——接收方收到乱序数据会立刻回「期望序号」的重复 ACK，发送方连收 3 个重复 ACK 就断定丢包（而不是等 RTO）。SACK 更进一步，接收方用选项字段报告「我收了 1-500 和 800-1000，缺 501-799」——发送方精确补缺。这就是为什么生产内核都默认开 SACK（tcp_sack=1），跨洋传输尤其依赖它——重传粒度从「整条」降到「一段」，吞吐差距能到数倍。

2.3 滑动窗口：流量控制

接收方在 ACK 里携带自己的接收窗口（rwnd），宣告「你最多再发这么多，我缓存放得下」——发送方的发送窗口 = min(自己的拥塞窗口 cwnd, 对方的 rwnd)。这就是流量控制：保护接收方不被撑爆。

因果链：窗口是「字节流没有消息边界」的机制源头——内核按窗口大小打包发送，应用层 write 的数据被切成段、段又可能被合并（回看第 1 篇 §5.2 的粘包拆包）。流量控制管「发多少」，拥塞控制管「发多快」，一个是接收方视角，一个是网络视角——两个窗口，两种保护对象。

2.4 动手验证：把确认和重传抓出来看

观察点：tcp_sack 为 1 说明 SACK 生效——之后所有重传都是「选择性补缺」而非整段重传。判定标准：内核参数为 1 + 抓包能看到 ACK 里带 SACK 选项，即验证了第 2.2 节的机制在当前系统是活的。

3. 拥塞控制：为什么 TCP 快不起来

3.1 慢启动与拥塞避免

拥塞窗口（cwnd）决定发送速率，算法分两段：

flowchart LR
    subgraph SS["Slow start (cwnd doubles each RTT)"]
        A1["cwnd=10 -> 20 -> 40 -> ..."]
    end
    subgraph CA["Congestion avoidance (cwnd +1 each RTT)"]
        B1["linear growth until packet loss"]
    end
    A1 -->|"hit ssthresh"| B1
    B1 -->|"packet loss: ssthresh = cwnd/2, cwnd reset"| A1
  • 慢启动：cwnd 从 10 段（RFC 6928）开始，每个 RTT 翻倍——指数增长，快速探测带宽；
  • 拥塞避免：涨到 ssthresh 后每个 RTT 只 +1——线性试探，逼近丢包边缘；
  • 丢包即信号：超时或 3 个重复 ACK 都判定网络拥塞，ssthresh 减半、cwnd 重置——这就是「TCP 快不起来」的机制根源：它靠丢包探测带宽，一旦探测到就退避，天然保守。

3.2 深挖：BDP——为什么「加了带宽还是慢」

BDP（带宽延迟积）= 带宽 × RTT：一秒钟「在路上」的数据量。要让链路打满，发送窗口必须 ≥ BDP，否则无论带宽多大，每个 RTT 只发得出一窗数据：

RTT 100Mbps 链路的 BDP 需要的窗口
10ms（同城） 125KB 默认窗口可能够用
100ms（跨洋） 1.25MB 必须调大 socket 缓冲区
500ms（卫星/跨洲） 6.25MB 远超默认，不调就永远跑不满

因果链：跨洋传输慢的根因往往不是带宽，是「窗口 < BDP」——Linux 的 tcp_rmem/tcp_wmem 上限（默认最大 4-6MB）在百兆跨洋链路下刚好不够。生产调优方向：确认 rmem/wmem 上限 ≥ BDP、开 tcp_window_scaling（默认已开）、或接受「长肥管道」的物理上限。面试答「为什么加了带宽没用」的正确姿势就是背出 BDP 公式并算出窗口需求。

3.3 深挖：Nagle 与延迟 ACK——小包的隐形敌人

  • Nagle 算法：小包（< MSS）要等「前面数据的 ACK 全部回来」或「缓冲凑满 MSS」才发——避免一堆小包占满带宽；
  • 延迟 ACK：接收方攒最多 40ms 再回 ACK——减少 ACK 数量。

两者叠加产生40ms 级的额外延迟（小请求被 Nagle 摁住、ACK 被延迟等），对 RPC/Redis 这类低延迟交互是灾难。解法：**TCP_NODELAY 关掉 Nagle（socket 选项 SO_TCP_NODELAY）——Netty 默认开启、Redis 服务端默认开启，这就是为什么它们响应快。因果链**：Nagle 是为「带宽利用率」设计的历史包袱，低延迟场景要显式关掉——「优化带宽的机制在延迟敏感场景变成负担」，这是 TCP 设计权衡的又一例。

3.4 动手验证：测量「窗口 < BDP」的直觉

观察点：算出 RTT 后立刻估算「这条链路要打满需要多大窗口」，再对比本机默认缓冲上限。判定标准：当「BDP 需求 > 默认上限」时你就预见到了「加带宽不加窗口没用」的生产结论——这就是公式变判断力。

4. 状态机排查：从状态堆积到生产事故

4.1 深挖：CLOSE_WAIT 堆积——代码泄漏的信号

CLOSE_WAIT = 对方发了 FIN，本端没调用 close()——连接「半死不活」地挂在那里。这是应用代码问题（不是内核问题）：读流没读完就放弃、异常路径忘了关闭、连接池里的连接没有 close。症状特征：ss -tan 里 CLOSE_WAIT 数量只增不减，lsof 看每个 fd 都对应同一个业务线程——排查方向是代码的关闭路径，不是调内核参数。

因果链：CLOSE_WAIT 是「TCP 半关闭机制 × 应用忘记关闭」的交叉产物——机制本身是正确的（等本端把数据发完），代价是泄漏必须由应用显式管理；Java 侧 try-with-resources、finally 关闭、连接池 testOnReturn 都是对「close 是义务」的工程化。

4.2 深挖：SYN_RECV 堆积——半连接队列溢出

ss -tan 大量 SYN_RECV = 服务端发了 SYN+ACK 但等不到第 3 次 ACK——半连接队列被占满。两个原因：

原因 特征 处理
SYN Flood 攻击 源 IP 随机、半连接数突增 内核 SYN cookies（tcp_syncookies=1）自动防；前置四层 LB 抗流量
backlog 太小 正常流量也堆半连接 调大 tcp_max_syn_backlog + 应用 backlog（Tomcat acceptCount、Netty SO_BACKLOG）

因果链：半连接队列是「三次握手分两阶段设计」的直接产物（§1.2）——攻击者只发 SYN 不发 ACK，就能占满队列让正常连接进不来；SYN cookies 的解法是「服务端不存半连接状态，把状态编码进 SYN+ACK 的序号里」——用机制绕过机制。

4.3 动手验证：复现 CLOSE_WAIT 堆积

观察点：20 个客户端断开后，ss -tan 里 45680 端口挂着 20 个 CLOSE_WAIT——服务端「没关」连接的现场。判定标准：CLOSE_WAIT 数量与客户端数一致即复现成功；修法就是把 // 不读不关 换成 finally 里 close——一次复现胜过十行背默。

网络分层：七层模型与数据包旅程

Posted on 2026-08-13 In 计算机网络 Word count in article: 4k Reading time ≈ 15 mins.

网络分层（network layering）是协议栈的组织方式：把「一次网络通信」拆成五道工序，每一层只解决一类问题，对上提供接口，对下不关心实现。 你写的每一行 socket 代码、遇到的每个连接超时、选型的每个负载均衡方案，都对应到某一层的职责。本文回答四个问题：网络为什么要分层、数据包从你的进程到对方进程走了什么路、TCP/IP 与 OSI 模型差在哪、分层的边界怎么决定你日常的技术选型——并对照四层/七层负载均衡、TCP 粘包拆包这些真实场景，看「分层的边界」如何从模型长成生产决策。

系列地图（计算机网络）：① 网络分层（本文：网络长什么样、数据怎么走） → ② TCP 协议（可靠传输）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. 为什么要分层：把「一次通信」拆成五道工序

1.1 网络为什么难：四个天然困难

困难 说明 例子
异构 中间设备来自不同厂商，协议必须统一 家用路由器 / 交换机 / 光猫混搭
不可靠 线路有噪声，报文会丢、会乱序、会重复 无线信号抖动
无全局视角 每台设备只知道自己的邻居，不知道全貌 路由器只认「下一跳」
距离远 一次访问要穿过几十台设备、几千公里 北京访问美西服务器

如果把这些困难揉进一个协议里，任何一端升级都要全世界配合。分层的本质是「关注点分离」：链路层只管把帧送到同网段的邻居，网络层只管把包送到目标网络，传输层只管端到端的可靠性——每层都假定「下面的层已经帮我搞定」而不用关心怎么搞定的。

1.2 七层 vs 四层：教科书与事实标准

OSI 七层模型是教科书（ISO 制定），TCP/IP 四层是事实标准（互联网实际运行）。两者差别只在最上面三层：OSI 把应用层拆成应用/表示/会话（分别管协议格式、数据编码、连接会话），TCP/IP 认为这些都是应用自己的事，合为一层。日常说的「五层模型」是折中：把 TCP/IP 的链路层拆成数据链路层和物理层。

五层模型 核心职责 代表协议 PDU 名称 寻址单位
应用层 定义业务数据格式 HTTP / DNS / TLS 报文 无（进程内）
传输层 端到端可靠/不可靠传输 TCP / UDP 段（segment） 端口
网络层 跨网段寻址与路由 IP / ICMP 包（packet） IP 地址
数据链路层 同网段帧传输 Ethernet 帧（frame） MAC 地址
物理层 比特传输 双绞线 / 光纤 比特 无

面试速记：端口在传输层、IP 在网络层、MAC 在链路层——三者不是一回事，这是后续一切排查的基础。

1.3 动手验证：curl -v 是一次可见的分层

输出里从上到下依次是：TCP_NODELAY（socket 选项）→ Connected to ... port 443（传输层：TCP 三次握手完成）→ SSL connection using TLSv1.3（应用层内的安全子层）→ GET / HTTP/1.1（应用层：HTTP 报文）。观察点：先有传输层连接，才有应用层请求——这是分层的执行顺序，不是巧合。判定标准：看到三行分层日志即验证通过，再看 curl -v 失败时停在哪一层（连不上 = 传输层，返回 4xx = 应用层逻辑），这就是「分层定位」的雏形。

2. 数据包的旅程：封装与解封装

2.1 封装：每层加一个头

数据从应用出发，每一层给数据加一个自己的头（header），就像寄快递逐层套箱：

flowchart TD
    APP["App data (HTTP request)"] --> L4["+ TCP header (src/dst port, seq)<br/>-> segment"]
    L4 --> L3["+ IP header (src/dst IP)<br/>-> packet"]
    L3 --> L2["+ Ethernet header (src/dst MAC)<br/>-> frame"]
    L2 --> WIRE["Bits on the wire"]
    WIRE --> R2["Receiving side: strip headers in reverse order"]
    R2 --> APP2["Original HTTP data"]

封装过程就是一次请求的实际形态：curl 发出的 HTTP 报文，先被 TCP 加头（含端口号、序号），再被 IP 加头（含源/目的 IP），最后被网卡封装成以太网帧（含 MAC）。对端按相反顺序逐层剥头。每一层只认识自己的头——路由器剥到 IP 层就够了，不认识也不关心 HTTP 里写的是什么。

2.2 MTU 与 MSS：链路层给传输层划的边界

MTU（Maximum Transmission Unit，最大传输单元） 是链路层一帧能装的最大数据量，以太网默认 1500 字节。IP 包超过 MTU 就要分片（拆成多个包）。MSS（最大分段大小） 是传输层据此主动设的边界：MSS = MTU − IP 头(20) − TCP 头(20) = 1460 字节。

flowchart LR
    MTU["Ethernet MTU = 1500"] --> IPH["IP header 20B"]
    IPH --> TCPH["TCP header 20B"]
    TCPH --> MSS["MSS = 1460B payload"]

深挖：MSS 是「链路层边界向上传导」的活例子——TCP 协商 MSS（三次握手时各自声明）的目的就是避免 IP 分片：分片包在中间路由器上任意一片丢失就要重传整包（传输层重传基于序号，不知道分片的存在），性能灾难。生产上「TCP 大包传输慢」「UDP 大数据报被悄悄丢弃」的根因常在这里。

2.3 动手验证：实测 MTU 边界

观察点：-D 禁止分片，超过 MTU 的包会收到「分片需要但被禁止」的 ICMP 错误。判定标准：找到「能通的最大包 = MTU − 28」这个边界，就理解了 MTU 的真实含义。应用侧推断：TCP 里调大缓冲区不会超过 MSS 单段上限，数据是按 1460 字节一段段排着走的。

3. 传输层：端口与连接的承上启下

3.1 端口：进程的地址

IP 地址定位机器，端口定位机器上的进程。一条连接用五元组唯一标识：源 IP + 源端口 + 目的 IP + 目的端口 + 协议。这就是为什么一台机器上可以同时跑 MySQL（3306）、Redis（6379）、Tomcat（8080）而不冲突——监听端口互不相同。

3.2 TCP vs UDP：可靠性与实时性的取舍

维度 TCP UDP
连接 有（三次握手） 无
可靠性 确认重传、序号去重、按序交付 不保证，丢了就丢
流量控制 滑动窗口 无
典型场景 HTTP、MySQL、Redis 主从 DNS、视频流、游戏帧同步

深挖：分层模型直接解释了「为什么 MySQL 用 TCP 而 DNS 用 UDP」——TCP 的可靠性机制（确认重传）在传输层完成，应用层不用重复造；UDP 把可靠性留给应用自己（游戏自研重传、视频容忍丢帧）。选型不是「TCP 好还是 UDP 好」，而是你的应用在哪一层承担可靠性。

3.3 动手验证：一次连接的两端视角

观察点：连接建立后，ss 里出现一对「源端口 → 45678」的 established 记录——五元组里的每个字段都是分层模型的一层地址。判定标准：能看到 established 状态即验证了「传输层提供连接」；再加 lsof -iTCP:45678 -P 能看到监听进程是 nc——端口 ↔ 进程的映射实锤。

4. 网络层与链路层：寻址的两级接力

4.1 IP 管跨网段，MAC 管同网段

数据包从北京到美西，逐跳转发：每个路由器只负责把包交给「更接近目标的那一个邻居」。IP 地址是逻辑地址（跨网段都认识），MAC 地址是物理地址（只在同网段有意义）——于是每跳都是「路由表查 IP → ARP 查 MAC → 交给邻居」的接力：

flowchart LR
    A["Host A: send to 1.2.3.4"] --> RT["Router: look up routing table<br/>(which next hop is closer?)"]
    RT --> ARP["ARP: find next-hop MAC<br/>(IP -> MAC in same LAN)"]
    ARP --> L2["Ethernet frame to next hop"]
    L2 --> RT2["Next router: repeat until destination"]

ARP（Address Resolution Protocol）是「同网段内 IP → MAC」的翻译：发送方先广播「谁是 1.2.3.4？」，目标回自己的 MAC，之后直接单播。所以 arp -a 看到的是最近打过交道的邻居，不是全网的机器——这解释了为什么 ARP 表是「最近使用」式的缓存。

4.2 动手验证：看路由表与逐跳路径

观察点：netstat -rn 里 default 那行就是「所有不认识的目标都交给它」的网关；traceroute 输出第 1 跳通常是网关，后面每跳的延迟代表跨过一个路由器。判定标准：traceroute 能列出 ≥3 跳且延迟逐跳累加，你就看到了「逐跳转发」的真实样子；某跳 * 表示该路由器不响应探测——不是断网，是不响应（排查时最容易误判的点）。

5. 分层视角下的开发日常：选型由分层边界决定

5.1 深挖：四层负载均衡 vs 七层负载均衡

负载均衡器是「站在分层模型的某个高度转发流量」的设备，它的能力边界 = 它认识哪几层：

维度 四层 LB 七层 LB
看到的内容 只剥到传输层（IP+端口） 剥到应用层（HTTP 报文）
代表 LVS、nginx stream、云 LB（SLB/NLB） nginx http、HAProxy、云 ALB
路由依据 五元组 URL、Host、Header、Cookie
性能 高（不解析报文，纯转发） 低（每包要解析 HTTP）
能力 转发 + 端口级健康检查 URL 路由、会话保持、请求改写
穿透性 支持任意 TCP/UDP 协议（MySQL、Redis、gRPC 都能转发） 只适合 HTTP 系协议

因果链：四层 LB 只认识传输层，所以它能转发任何 TCP 流量（MySQL、Redis、自定义协议）——这是它性能高又通用的原因，但也因此做不到「按 URL 分流」（应用层信息它看不见）；七层 LB 认识应用层，所以能按 URL/会话做精细化路由——代价是每包解析、协议限定 HTTP。生产选型一句话：需要按 URL/会话分流选七层，需要转发任意 TCP 协议或极致性能选四层。这也是「分层的边界决定技术边界」的最直接案例。

5.2 深挖：TCP 粘包拆包——传输层边界与消息边界的错位

TCP 是字节流，不保证「一次 write 对应一次 read」：应用层没有消息边界，内核只按 MSS 分包、按滑动窗口发送。于是多个小消息可能被合在一个段里（粘包），一个大消息可能被拆成多段（拆包）——这是用 TCP 做自定义协议（RPC、游戏、IM）必须自己解决的问题。

解法是在应用层重新定义边界，三种方案：

方案 做法 场景 Netty 对应解码器
定长 每条消息固定 N 字节 极少用（浪费） FixedLengthFrameDecoder
分隔符 消息以 \n 等结束 文本协议、行协议 LineBasedFrameDecoder
长度前缀 头 4 字节声明体长 主流 RPC（Dubbo/Thrift） LengthFieldBasedFrameDecoder

因果链：粘包问题的根源在分层模型——传输层只承诺「字节流可靠有序」，消息边界是应用层（第 5 层）的责任；Netty 的解码器就是在应用层把「无边界的字节流」重新切回「有边界的消息」，等价于应用层内的再分层。面试答「粘包拆包」的正确姿势是：先讲字节流机制（传输层为什么不管边界），再讲三种方案（应用层怎么补边界），最后落到你项目的解码器选型。

5.3 动手验证：看一次粘包

观察点：本地回环上大概率输出 server received 10 bytes——两条消息合在一次 read 里到达，这就是粘包。判定标准：received 10 而非 5，即复现成功；把两个 write 之间加 Thread.sleep(100) 再跑，可能变成两次 5 字节——说明边界本来就不存在，一切取决于网络时序。这就是为什么应用层必须自己定义边界。

6. 总结

6.1 面试速答表

面试题 一句话答案
为什么网络要分层？ 关注点分离：每层只解决一类问题（寻址/可靠/格式），换实现不影响其他层
OSI 七层和 TCP/IP 四层差在哪？ 最上三层合一（表示/会话归应用层），链路层拆两层
端口、IP、MAC 各自定位什么？ 进程、机器（跨网段逻辑地址）、网卡（同网段物理地址）
什么是封装/解封装？ 每层加自己的头，对端按逆序剥头；每层只认识自己的头
MTU 和 MSS 什么关系？ MSS = MTU − 40，TCP 主动限流避免 IP 分片（分片丢一片重传整包）
四层和七层负载均衡怎么选？ 按 URL/会话分流选七层；任意 TCP 协议或极致性能选四层
TCP 粘包拆包怎么办？ 传输层是字节流无边界，应用层自己定义：定长/分隔符/长度前缀

实操建议：

  1. 排网络问题先问「故障停在哪一层」：连不上是传输层，超时返回是应用层，抓包看帧能区分链路层与网络层。
  2. 自定义 TCP 协议一律长度前缀方案（对齐 Dubbo/Thrift 的主流做法），不要赌网络时序不会粘包。
  3. 选负载均衡先写清楚「我需要看哪几层的信息」，能力边界由分层模型决定，不是由厂商宣传决定。
