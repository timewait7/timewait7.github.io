TCP 协议：可靠传输的代价

Posted on 2026-08-13 In 计算机网络 Word count in article: 4k Reading time ≈ 14 mins.

TCP（Transmission Control Protocol）是传输层的可靠字节流协议：用序号、确认、重传、窗口四套机制，把不可靠的网络变成「有序、不丢、不重」的字节流。 可靠是有代价的——握手延迟、确认往返、拥塞退避，每一个都是「性能 vs 可靠性」的显式权衡。本文回答四个问题：连接怎么建立和拆除、可靠性靠什么保证、为什么 TCP 有时快不起来、状态机怎么变成线上事故——并对照 TIME_WAIT/CLOSE_WAIT 堆积、SYN 洪泛、TCP_NODELAY 这些生产场景，看机制如何长成排查手段。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（本文：可靠传输与代价） → ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. 三次握手与四次挥手：连接的建立与拆除

1.1 三次握手：互相确认序号

连接建立的本质是双方同步序号——后续所有可靠性都建立在序号上。三次握手每次交换的都是「我的初始序号 + 我确认收到你的」：

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: SYN seq=100 (SYN_SENT)
    S->>C: SYN+ACK seq=300 ack=101 (SYN_RECV)
    C->>S: ACK seq=101 ack=301 (ESTABLISHED)
    Note over C,S: ESTABLISHED: 双方都确认了对方序号
  • 第 1 次（SYN）：客户端说「我想连，我的起始序号是 100」
  • 第 2 次（SYN+ACK）：服务端说「收到，我的起始序号是 300，请确认 101」
  • 第 3 次（ACK）：客户端说「确认 301」——只有第 3 次到达，服务端才确认「客户端确实活着」

1.2 为什么是三次而不是两次

两次握手无法防御「迟到的旧 SYN」：若客户端某次连接的超时 SYN 在网络里游荡，1 秒后才到服务端，服务端回 SYN+ACK 并建立连接、占用资源——而客户端根本不知道这回事（它早已放弃）。三次握手中客户端第 3 次的 ACK 携带了「我确实在发起这次连接」的确认，服务端收到它才分配连接资源，旧 SYN 永远等不到第 3 次 ACK，自然超时释放。

深挖：这直接决定了半连接与全连接队列的设计——服务端收到 SYN 只进半连接队列（内核管理，还没分配完整连接），收到第 3 次 ACK 才移入全连接队列（应用层 backlog 参数），accept() 从全连接队列取。两个队列的容量就是两个不同的攻击面（§4.2 展开）。

1.3 四次挥手：半关闭的两段告别

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: FIN (FIN_WAIT_1)
    S->>C: ACK (CLOSE_WAIT / FIN_WAIT_2)
    S->>C: FIN (LAST_ACK)
    C->>S: ACK (TIME_WAIT 2MSL / CLOSED)

挥手是四次而不是三次，因为 TCP 支持半关闭：收到 FIN 只代表对方「不再发」，本端可能还有数据要发。于是「FIN → ACK」（对方发完）和「FIN → ACK」（本端发完）是两对独立的过程。生产上的时间点：先收到 FIN 的一方进入 CLOSE_WAIT，最后发送 FIN 的一方进入 TIME_WAIT。

1.4 深挖：TIME_WAIT 为什么必须等 2MSL

主动关闭方最后发 ACK 后进入 TIME_WAIT，等待 2 倍 MSL（报文最大生存时间，Linux 默认 60 秒），两个原因：

  1. 保证最后的 ACK 到达：ACK 可能丢失，对方会重发 FIN——TIME_WAIT 期间内核能重发 ACK；
  2. 防止旧报文污染新连接：网络中可能还游荡着这条连接的迟到报文（序号可能撞上新连接的序号），等 2MSL 让它们自然消亡。

因果链：TIME_WAIT 是「防迟到报文」的安全收尾，所以它不能通过调小端口或缩短等待来根治——高并发短连接服务的 TIME_WAIT 堆积（操作系统系列第 5 篇 §5.1 的端口耗尽事故）正解是连接复用：HTTP keep-alive、连接池把短连接变长连接，让 TIME_WAIT 根本不产生。机制决定解法，这是最典型的一例。

1.5 动手验证：亲眼看到握手与挥手

观察点：抓包里依次出现 S（SYN）→ S.（SYN+ACK）→ .（ACK）→ 数据 → 挥手时 F/F./F.P. 序列。判定标准：每 4 个包一组对应一次连接，三次握手 3 个包 + 挥手 4 个包清晰可见即验证通过。顺手看 ss -tan | grep 45681，客户端断开后服务端进入 CLOSE_WAIT——状态机不是背的，是观察出来的。

2. 可靠传输：序号、确认与重传

2.1 序号与累计确认

发送方给每个字节编号（seq），接收方回「下一个期望的字节号」（ack）。累计确认：ack=501 表示「500 之前都收到了，请从 501 开始发」——接收方不需要逐字节确认，一个 ack 覆盖之前全部。这是 TCP 高效的根本：确认开销与数据量无关，与「空洞」次数有关。

2.2 三种重传：从傻等到智能

重传机制 触发条件 代价
超时重传 发出去没等到 ACK，RTO 到期 慢（RTO 通常 200ms 起，指数退避）
快速重传 收到 3 个重复 ACK 快（不用等超时，立刻知道丢了）
SACK 收到带 SACK 选项的 ACK（报告空洞范围） 最快（只重传丢失的段，不重传全部）

深挖：快速重传是怎么「不超时就知道丢了」的——接收方收到乱序数据会立刻回「期望序号」的重复 ACK，发送方连收 3 个重复 ACK 就断定丢包（而不是等 RTO）。SACK 更进一步，接收方用选项字段报告「我收了 1-500 和 800-1000，缺 501-799」——发送方精确补缺。这就是为什么生产内核都默认开 SACK（tcp_sack=1），跨洋传输尤其依赖它——重传粒度从「整条」降到「一段」，吞吐差距能到数倍。

2.3 滑动窗口：流量控制

接收方在 ACK 里携带自己的接收窗口（rwnd），宣告「你最多再发这么多，我缓存放得下」——发送方的发送窗口 = min(自己的拥塞窗口 cwnd, 对方的 rwnd)。这就是流量控制：保护接收方不被撑爆。

因果链：窗口是「字节流没有消息边界」的机制源头——内核按窗口大小打包发送，应用层 write 的数据被切成段、段又可能被合并（回看第 1 篇 §5.2 的粘包拆包）。流量控制管「发多少」，拥塞控制管「发多快」，一个是接收方视角，一个是网络视角——两个窗口，两种保护对象。

2.4 动手验证：把确认和重传抓出来看

观察点：tcp_sack 为 1 说明 SACK 生效——之后所有重传都是「选择性补缺」而非整段重传。判定标准：内核参数为 1 + 抓包能看到 ACK 里带 SACK 选项，即验证了第 2.2 节的机制在当前系统是活的。

3. 拥塞控制：为什么 TCP 快不起来

3.1 慢启动与拥塞避免

拥塞窗口（cwnd）决定发送速率，算法分两段：

flowchart LR
    subgraph SS["Slow start (cwnd doubles each RTT)"]
        A1["cwnd=10 -> 20 -> 40 -> ..."]
    end
    subgraph CA["Congestion avoidance (cwnd +1 each RTT)"]
        B1["linear growth until packet loss"]
    end
    A1 -->|"hit ssthresh"| B1
    B1 -->|"packet loss: ssthresh = cwnd/2, cwnd reset"| A1
  • 慢启动：cwnd 从 10 段（RFC 6928）开始，每个 RTT 翻倍——指数增长，快速探测带宽；
  • 拥塞避免：涨到 ssthresh 后每个 RTT 只 +1——线性试探，逼近丢包边缘；
  • 丢包即信号：超时或 3 个重复 ACK 都判定网络拥塞，ssthresh 减半、cwnd 重置——这就是「TCP 快不起来」的机制根源：它靠丢包探测带宽，一旦探测到就退避，天然保守。

3.2 深挖：BDP——为什么「加了带宽还是慢」

BDP（带宽延迟积）= 带宽 × RTT：一秒钟「在路上」的数据量。要让链路打满，发送窗口必须 ≥ BDP，否则无论带宽多大，每个 RTT 只发得出一窗数据：

RTT 100Mbps 链路的 BDP 需要的窗口
10ms（同城） 125KB 默认窗口可能够用
100ms（跨洋） 1.25MB 必须调大 socket 缓冲区
500ms（卫星/跨洲） 6.25MB 远超默认，不调就永远跑不满

因果链：跨洋传输慢的根因往往不是带宽，是「窗口 < BDP」——Linux 的 tcp_rmem/tcp_wmem 上限（默认最大 4-6MB）在百兆跨洋链路下刚好不够。生产调优方向：确认 rmem/wmem 上限 ≥ BDP、开 tcp_window_scaling（默认已开）、或接受「长肥管道」的物理上限。面试答「为什么加了带宽没用」的正确姿势就是背出 BDP 公式并算出窗口需求。

3.3 深挖：Nagle 与延迟 ACK——小包的隐形敌人

  • Nagle 算法：小包（< MSS）要等「前面数据的 ACK 全部回来」或「缓冲凑满 MSS」才发——避免一堆小包占满带宽；
  • 延迟 ACK：接收方攒最多 40ms 再回 ACK——减少 ACK 数量。

两者叠加产生40ms 级的额外延迟（小请求被 Nagle 摁住、ACK 被延迟等），对 RPC/Redis 这类低延迟交互是灾难。解法：**TCP_NODELAY 关掉 Nagle（socket 选项 SO_TCP_NODELAY）——Netty 默认开启、Redis 服务端默认开启，这就是为什么它们响应快。因果链**：Nagle 是为「带宽利用率」设计的历史包袱，低延迟场景要显式关掉——「优化带宽的机制在延迟敏感场景变成负担」，这是 TCP 设计权衡的又一例。

3.4 动手验证：测量「窗口 < BDP」的直觉

观察点：算出 RTT 后立刻估算「这条链路要打满需要多大窗口」，再对比本机默认缓冲上限。判定标准：当「BDP 需求 > 默认上限」时你就预见到了「加带宽不加窗口没用」的生产结论——这就是公式变判断力。

4. 状态机排查：从状态堆积到生产事故

4.1 深挖：CLOSE_WAIT 堆积——代码泄漏的信号

CLOSE_WAIT = 对方发了 FIN，本端没调用 close()——连接「半死不活」地挂在那里。这是应用代码问题（不是内核问题）：读流没读完就放弃、异常路径忘了关闭、连接池里的连接没有 close。症状特征：ss -tan 里 CLOSE_WAIT 数量只增不减，lsof 看每个 fd 都对应同一个业务线程——排查方向是代码的关闭路径，不是调内核参数。

因果链：CLOSE_WAIT 是「TCP 半关闭机制 × 应用忘记关闭」的交叉产物——机制本身是正确的（等本端把数据发完），代价是泄漏必须由应用显式管理；Java 侧 try-with-resources、finally 关闭、连接池 testOnReturn 都是对「close 是义务」的工程化。

4.2 深挖：SYN_RECV 堆积——半连接队列溢出

ss -tan 大量 SYN_RECV = 服务端发了 SYN+ACK 但等不到第 3 次 ACK——半连接队列被占满。两个原因：

原因 特征 处理
SYN Flood 攻击 源 IP 随机、半连接数突增 内核 SYN cookies（tcp_syncookies=1）自动防；前置四层 LB 抗流量
backlog 太小 正常流量也堆半连接 调大 tcp_max_syn_backlog + 应用 backlog（Tomcat acceptCount、Netty SO_BACKLOG）

因果链：半连接队列是「三次握手分两阶段设计」的直接产物（§1.2）——攻击者只发 SYN 不发 ACK，就能占满队列让正常连接进不来；SYN cookies 的解法是「服务端不存半连接状态，把状态编码进 SYN+ACK 的序号里」——用机制绕过机制。

4.3 动手验证：复现 CLOSE_WAIT 堆积

观察点：20 个客户端断开后，ss -tan 里 45680 端口挂着 20 个 CLOSE_WAIT——服务端「没关」连接的现场。判定标准：CLOSE_WAIT 数量与客户端数一致即复现成功；修法就是把 // 不读不关 换成 finally 里 close——一次复现胜过十行背默。

网络分层：七层模型与数据包旅程

Posted on 2026-08-13 In 计算机网络 Word count in article: 4k Reading time ≈ 15 mins.

网络分层（network layering）是协议栈的组织方式：把「一次网络通信」拆成五道工序，每一层只解决一类问题，对上提供接口，对下不关心实现。 你写的每一行 socket 代码、遇到的每个连接超时、选型的每个负载均衡方案，都对应到某一层的职责。本文回答四个问题：网络为什么要分层、数据包从你的进程到对方进程走了什么路、TCP/IP 与 OSI 模型差在哪、分层的边界怎么决定你日常的技术选型——并对照四层/七层负载均衡、TCP 粘包拆包这些真实场景，看「分层的边界」如何从模型长成生产决策。

系列地图（计算机网络）：① 网络分层（本文：网络长什么样、数据怎么走） → ② TCP 协议（可靠传输）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. 为什么要分层：把「一次通信」拆成五道工序

1.1 网络为什么难：四个天然困难

困难 说明 例子
异构 中间设备来自不同厂商，协议必须统一 家用路由器 / 交换机 / 光猫混搭
不可靠 线路有噪声，报文会丢、会乱序、会重复 无线信号抖动
无全局视角 每台设备只知道自己的邻居，不知道全貌 路由器只认「下一跳」
距离远 一次访问要穿过几十台设备、几千公里 北京访问美西服务器

如果把这些困难揉进一个协议里，任何一端升级都要全世界配合。分层的本质是「关注点分离」：链路层只管把帧送到同网段的邻居，网络层只管把包送到目标网络，传输层只管端到端的可靠性——每层都假定「下面的层已经帮我搞定」而不用关心怎么搞定的。

1.2 七层 vs 四层：教科书与事实标准

OSI 七层模型是教科书（ISO 制定），TCP/IP 四层是事实标准（互联网实际运行）。两者差别只在最上面三层：OSI 把应用层拆成应用/表示/会话（分别管协议格式、数据编码、连接会话），TCP/IP 认为这些都是应用自己的事，合为一层。日常说的「五层模型」是折中：把 TCP/IP 的链路层拆成数据链路层和物理层。

五层模型 核心职责 代表协议 PDU 名称 寻址单位
应用层 定义业务数据格式 HTTP / DNS / TLS 报文 无（进程内）
传输层 端到端可靠/不可靠传输 TCP / UDP 段（segment） 端口
网络层 跨网段寻址与路由 IP / ICMP 包（packet） IP 地址
数据链路层 同网段帧传输 Ethernet 帧（frame） MAC 地址
物理层 比特传输 双绞线 / 光纤 比特 无

面试速记：端口在传输层、IP 在网络层、MAC 在链路层——三者不是一回事，这是后续一切排查的基础。

1.3 动手验证：curl -v 是一次可见的分层

输出里从上到下依次是：TCP_NODELAY（socket 选项）→ Connected to ... port 443（传输层：TCP 三次握手完成）→ SSL connection using TLSv1.3（应用层内的安全子层）→ GET / HTTP/1.1（应用层：HTTP 报文）。观察点：先有传输层连接，才有应用层请求——这是分层的执行顺序，不是巧合。判定标准：看到三行分层日志即验证通过，再看 curl -v 失败时停在哪一层（连不上 = 传输层，返回 4xx = 应用层逻辑），这就是「分层定位」的雏形。

2. 数据包的旅程：封装与解封装

2.1 封装：每层加一个头

数据从应用出发，每一层给数据加一个自己的头（header），就像寄快递逐层套箱：

flowchart TD
    APP["App data (HTTP request)"] --> L4["+ TCP header (src/dst port, seq)<br/>-> segment"]
    L4 --> L3["+ IP header (src/dst IP)<br/>-> packet"]
    L3 --> L2["+ Ethernet header (src/dst MAC)<br/>-> frame"]
    L2 --> WIRE["Bits on the wire"]
    WIRE --> R2["Receiving side: strip headers in reverse order"]
    R2 --> APP2["Original HTTP data"]

封装过程就是一次请求的实际形态：curl 发出的 HTTP 报文，先被 TCP 加头（含端口号、序号），再被 IP 加头（含源/目的 IP），最后被网卡封装成以太网帧（含 MAC）。对端按相反顺序逐层剥头。每一层只认识自己的头——路由器剥到 IP 层就够了，不认识也不关心 HTTP 里写的是什么。

2.2 MTU 与 MSS：链路层给传输层划的边界

MTU（Maximum Transmission Unit，最大传输单元） 是链路层一帧能装的最大数据量，以太网默认 1500 字节。IP 包超过 MTU 就要分片（拆成多个包）。MSS（最大分段大小） 是传输层据此主动设的边界：MSS = MTU − IP 头(20) − TCP 头(20) = 1460 字节。

flowchart LR
    MTU["Ethernet MTU = 1500"] --> IPH["IP header 20B"]
    IPH --> TCPH["TCP header 20B"]
    TCPH --> MSS["MSS = 1460B payload"]

深挖：MSS 是「链路层边界向上传导」的活例子——TCP 协商 MSS（三次握手时各自声明）的目的就是避免 IP 分片：分片包在中间路由器上任意一片丢失就要重传整包（传输层重传基于序号，不知道分片的存在），性能灾难。生产上「TCP 大包传输慢」「UDP 大数据报被悄悄丢弃」的根因常在这里。

2.3 动手验证：实测 MTU 边界

观察点：-D 禁止分片，超过 MTU 的包会收到「分片需要但被禁止」的 ICMP 错误。判定标准：找到「能通的最大包 = MTU − 28」这个边界，就理解了 MTU 的真实含义。应用侧推断：TCP 里调大缓冲区不会超过 MSS 单段上限，数据是按 1460 字节一段段排着走的。

3. 传输层：端口与连接的承上启下

3.1 端口：进程的地址

IP 地址定位机器，端口定位机器上的进程。一条连接用五元组唯一标识：源 IP + 源端口 + 目的 IP + 目的端口 + 协议。这就是为什么一台机器上可以同时跑 MySQL（3306）、Redis（6379）、Tomcat（8080）而不冲突——监听端口互不相同。

3.2 TCP vs UDP：可靠性与实时性的取舍

维度 TCP UDP
连接 有（三次握手） 无
可靠性 确认重传、序号去重、按序交付 不保证，丢了就丢
流量控制 滑动窗口 无
典型场景 HTTP、MySQL、Redis 主从 DNS、视频流、游戏帧同步

深挖：分层模型直接解释了「为什么 MySQL 用 TCP 而 DNS 用 UDP」——TCP 的可靠性机制（确认重传）在传输层完成，应用层不用重复造；UDP 把可靠性留给应用自己（游戏自研重传、视频容忍丢帧）。选型不是「TCP 好还是 UDP 好」，而是你的应用在哪一层承担可靠性。

3.3 动手验证：一次连接的两端视角

观察点：连接建立后，ss 里出现一对「源端口 → 45678」的 established 记录——五元组里的每个字段都是分层模型的一层地址。判定标准：能看到 established 状态即验证了「传输层提供连接」；再加 lsof -iTCP:45678 -P 能看到监听进程是 nc——端口 ↔ 进程的映射实锤。

4. 网络层与链路层：寻址的两级接力

4.1 IP 管跨网段，MAC 管同网段

数据包从北京到美西，逐跳转发：每个路由器只负责把包交给「更接近目标的那一个邻居」。IP 地址是逻辑地址（跨网段都认识），MAC 地址是物理地址（只在同网段有意义）——于是每跳都是「路由表查 IP → ARP 查 MAC → 交给邻居」的接力：

flowchart LR
    A["Host A: send to 1.2.3.4"] --> RT["Router: look up routing table<br/>(which next hop is closer?)"]
    RT --> ARP["ARP: find next-hop MAC<br/>(IP -> MAC in same LAN)"]
    ARP --> L2["Ethernet frame to next hop"]
    L2 --> RT2["Next router: repeat until destination"]

ARP（Address Resolution Protocol）是「同网段内 IP → MAC」的翻译：发送方先广播「谁是 1.2.3.4？」，目标回自己的 MAC，之后直接单播。所以 arp -a 看到的是最近打过交道的邻居，不是全网的机器——这解释了为什么 ARP 表是「最近使用」式的缓存。

4.2 动手验证：看路由表与逐跳路径

观察点：netstat -rn 里 default 那行就是「所有不认识的目标都交给它」的网关；traceroute 输出第 1 跳通常是网关，后面每跳的延迟代表跨过一个路由器。判定标准：traceroute 能列出 ≥3 跳且延迟逐跳累加，你就看到了「逐跳转发」的真实样子；某跳 * 表示该路由器不响应探测——不是断网，是不响应（排查时最容易误判的点）。

5. 分层视角下的开发日常：选型由分层边界决定

5.1 深挖：四层负载均衡 vs 七层负载均衡

负载均衡器是「站在分层模型的某个高度转发流量」的设备，它的能力边界 = 它认识哪几层：

维度 四层 LB 七层 LB
看到的内容 只剥到传输层（IP+端口） 剥到应用层（HTTP 报文）
代表 LVS、nginx stream、云 LB（SLB/NLB） nginx http、HAProxy、云 ALB
路由依据 五元组 URL、Host、Header、Cookie
性能 高（不解析报文，纯转发） 低（每包要解析 HTTP）
能力 转发 + 端口级健康检查 URL 路由、会话保持、请求改写
穿透性 支持任意 TCP/UDP 协议（MySQL、Redis、gRPC 都能转发） 只适合 HTTP 系协议

因果链：四层 LB 只认识传输层，所以它能转发任何 TCP 流量（MySQL、Redis、自定义协议）——这是它性能高又通用的原因，但也因此做不到「按 URL 分流」（应用层信息它看不见）；七层 LB 认识应用层，所以能按 URL/会话做精细化路由——代价是每包解析、协议限定 HTTP。生产选型一句话：需要按 URL/会话分流选七层，需要转发任意 TCP 协议或极致性能选四层。这也是「分层的边界决定技术边界」的最直接案例。

5.2 深挖：TCP 粘包拆包——传输层边界与消息边界的错位

TCP 是字节流，不保证「一次 write 对应一次 read」：应用层没有消息边界，内核只按 MSS 分包、按滑动窗口发送。于是多个小消息可能被合在一个段里（粘包），一个大消息可能被拆成多段（拆包）——这是用 TCP 做自定义协议（RPC、游戏、IM）必须自己解决的问题。

解法是在应用层重新定义边界，三种方案：

方案 做法 场景 Netty 对应解码器
定长 每条消息固定 N 字节 极少用（浪费） FixedLengthFrameDecoder
分隔符 消息以 \n 等结束 文本协议、行协议 LineBasedFrameDecoder
长度前缀 头 4 字节声明体长 主流 RPC（Dubbo/Thrift） LengthFieldBasedFrameDecoder

因果链：粘包问题的根源在分层模型——传输层只承诺「字节流可靠有序」，消息边界是应用层（第 5 层）的责任；Netty 的解码器就是在应用层把「无边界的字节流」重新切回「有边界的消息」，等价于应用层内的再分层。面试答「粘包拆包」的正确姿势是：先讲字节流机制（传输层为什么不管边界），再讲三种方案（应用层怎么补边界），最后落到你项目的解码器选型。

5.3 动手验证：看一次粘包

观察点：本地回环上大概率输出 server received 10 bytes——两条消息合在一次 read 里到达，这就是粘包。判定标准：received 10 而非 5，即复现成功；把两个 write 之间加 Thread.sleep(100) 再跑，可能变成两次 5 字节——说明边界本来就不存在，一切取决于网络时序。这就是为什么应用层必须自己定义边界。

5. 连接类故障：TIME_WAIT 与端口耗尽

5.1 高并发短连接的经典事故

TIME_WAIT 是主动关闭方的收尾状态（持续 2MSL ≈ 60 秒）：短连接服务（每请求一个连接，连接由服务端主动关闭）高并发时，TIME_WAIT 连接堆积，占满本地端口范围（/proc/sys/net/ipv4/ip_local_port_range，默认约 2.8 万个）——新连接没有可用本地端口，ss -s 里 timewait 数量暴涨 + 业务报连接失败。

5.2 深挖：为什么连接要复用

TIME_WAIT 设计的本意是防「迟到旧报文污染新连接」（第 4 篇 TCP 状态机的安全收尾）。生产解法不是调小端口而是连接复用：HTTP keep-alive / 连接池把「短连接」变「长连接」——这正好呼应第 4 篇：连接数是 fd 数、是线程数的直接消耗者，复用连接等于同时省掉 TIME_WAIT、fd 和握手开销（三次握手也是一次 RTT）。连接池参数（maxTotal/minIdle）背后的机制，就是 TIME_WAIT 与端口范围。

IO 模型：阻塞、多路复用与零拷贝

Posted on 2026-08-12 In 操作系统 Word count in article: 6.2k Reading time ≈ 23 mins.

IO 模型决定「数据没就绪时，你的线程在干什么」：阻塞模型让线程干等，非阻塞模型让线程反复问，多路复用让内核一次告诉你「谁好了」，异步模型让内核干完再叫你。本文串起三件事：五种模型的取舍、epoll 为什么是标准答案、以及 Java 侧（BIO/NIO/Netty/虚拟线程）分别落在哪个模型上——并全程对照 Redis、nginx、Netty、Tomcat 这些你天天用的技术，看它们各自的线程模型怎么从本文的机制里长出来。

系列地图（操作系统）：① 进程与线程（执行单元与调度）→ ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（本文：等待数据的方式） → ⑤ Linux 资源排查实战（前四篇工具收拢）。本文是前四篇的汇合点：阻塞线程的成本来自 ① 的切换开销与 ② 的栈内存，零拷贝数据路径来自 ③ 的页缓存。

1.2 阻塞与非阻塞：read 的两种等待

阻塞 IO：read() 发出后线程挂起，数据就绪才返回——等待期间线程不占 CPU 但占「线程配额」，每个连接一个线程。

这套「线程 = 连接」的模型在 1999 年的 C10K 问题（万级并发连接）上撞了墙：1 万连接 = 1 万线程。1 万线程意味着什么？用前两篇的知识算账：每线程默认 1MB 栈（第 2 篇），虚拟内存承诺 10GB；1 万线程轮流上 CPU，上下文切换每秒几十万次（第 1 篇），光调度就吃掉大半 CPU。所以 C10K 的解法不是「更多线程」，而是「更少线程」——epoll 让一个线程等 1 万 fd（§2），Reactor 让几个线程服务 1 万连接（§3）。

回头看今天的技术，全是这套解法的后代：Redis 单线程事件循环扛 10 万 QPS、nginx 的 worker 数 = CPU 核数、Netty 默认两组 EventLoop 线程池。它们的线程数差异（Redis=1、nginx/Netty=核数级、BIO=连接数）就是「切换成本 vs 并发需求」的三档答案——这也是为什么面试问「Redis 为什么单线程还快」，标准答案的第一句永远是「它不做阻塞 IO，一个线程足以喂饱 CPU」。

非阻塞 IO：read() 立即返回——没数据时返回 EAGAIN，应用必须自己重试。避免了线程浪费，但把「等」的责任推给了应用，纯轮询是 CPU 灾难，实战中只作为多路复用的补充（数据没就绪时转去等 epoll）。

1.3 多路复用：一次等一堆

多路复用（I/O multiplexing）让一个线程把「等待」交给内核：注册一堆 fd，内核在任何一个就绪时唤醒线程。select/poll 是第一代实现，epoll 是 Linux 的工程答案（第 2 节展开）。Java NIO 的 Selector 就是对它的封装，Netty 底层就是它。

1.4 异步 IO：内核干完再叫你

异步 IO 是「提交请求就走，内核完成后再通知」：应用线程完全不参与等待。Linux 上的 io_uring（及早期 aio）是代表。注意区分：多路复用是「内核替你等」，异步是「内核替你干」——Netty 常被叫异步框架，其实是多路复用 + 回调，不是真异步。

1.5 动手验证：strace 看一次阻塞读

strace 输出里能看到 recvfrom(3, ... 阻塞住——poll/recvfrom 返回前的等待就是「阻塞」。把同样的观测换成 NIO 程序，会看到 epoll_wait 在循环——这就是两种模型在系统调用层的全部区别。

2. epoll：多路复用的工程答案

2.1 select/poll 的两个问题

维度 select poll epoll
fd 上限 1024（FD_SETSIZE） 无上限 无上限
每次调用 全量拷贝 fd 数组进内核 同左 只增删改（epoll_ctl）
查找就绪 O(n) 扫描全部 O(n) O(1) 取就绪链表
内核实现 线性扫描 线性扫描 红黑树 + 就绪链表

select 每次调用都要把几千个 fd 拷进内核、扫描一遍——连接多了以后，等待本身变成了性能瓶颈。epoll 把「注册」和「等待」拆开：注册一次，之后只等结果。

2.2 epoll 的三板斧

flowchart LR
    APP["App"] --> C1["epoll_create()<br/>create red-black tree"]
    C1 --> C2["epoll_ctl()<br/>register / modify / delete fd"]
    C2 --> C3["epoll_wait()<br/>sleep; wake on ready"]
    C3 --> READY["Ready list (linked list)"]
    KERN["Kernel: fd becomes readable"] --> READY
    READY --> C3

机制拆解：内核里一棵红黑树存所有注册的 fd（增删改 O(log n)），一个就绪链表存已经可读可写的 fd（由中断/唤醒路径挂入）；epoll_wait 只把就绪链表拷给用户——等待与规模无关，这就是 O(1) 的真相。

2.3 LT 与 ET：就绪事件报几次

模式 行为 适用
LT（水平触发，默认） fd 一直可读就反复报，不处理下次还报 简单，不容易漏事件
ET（边缘触发） 只报一次，必须一次读完，否则丢事件 高性能（配合非阻塞 + 读到 EAGAIN）

LT 与 ET 的取舍不是风格之争，是两套技术场景逼出来的设计——直接看两个最著名的使用者：

  • Redis 用 ET：单线程事件循环，所有连接的处理在一条线程里串行完成。LT 会反复上报同一个就绪事件、每次都唤醒循环白耗一次；而单线程意味着没有并发读竞争，「一次读到 EAGAIN」安全且必然——ET「必须读尽」的代价在单线程模型下不存在。这是 Redis 单线程 10 万 QPS 的细节之一。
  • Netty 默认 LT：EventLoop 池是多线程，且每次循环有读配额（默认 16MB）防止一个连接吃光 CPU——读不完的剩余数据回到队列、下次循环再读，此时 LT 的「反复上报」恰好保证事件不漏。所以 Netty 默认 LT 不是偷懒，是用重复唤醒换「不漏事件」的确定性。

生产后果：Netty 若手动改 ET，业务必须自己保证读尽——线上「偶发丢数据」事故的一大来源就是 ET 读循环少判了一次 EAGAIN；Redis 反而没有这个问题（单线程 + 读尽是写死的）。入门用 LT，性能临界再上 ET，前提是读循环写到 EAGAIN 为止。

多路复用解决了「一个线程等一堆」，但业务处理也挤在这一个线程上：一个连接读数据慢，其他连接全被拖住。于是演进出 Reactor 系列：

3.2 Netty 的 boss/worker 与 epoll

Netty 的 EventLoopGroup 就是 Reactor 的实现：bossGroup 只负责 accept（epoll_wait 在监听 fd 上），workerGroup 负责已连接 socket 的读写。三个关键设计细节，每个都能对应上本节讲的机制：

  1. EventLoop = 线程 + epoll_wait 循环：默认 worker 线程数 = CPU 核数 × 2。为什么不是越多越好？每个 EventLoop 是串行循环，线程数超过核数后，多出来的只是排队抢 CPU（第 1 篇的切换成本）——并发不涨，切换变多。
  2. 一个 channel 绑定一个 EventLoop，不轮询：同一连接的所有事件永远由同一个线程处理——天然免锁。这是「单线程串行」理念在 Netty 里的落地：Netty 内部几乎无锁，靠的就是这个绑定关系。
  3. IO 线程红线：业务代码绝不能在 IO 线程里做阻塞操作（数据库查询、Thread.sleep、锁等待）——那会让这个 EventLoop 的几百个连接一起等，等于把「一线程管 N 连接」退化成「N 个连接共用一根喉咙」。这是 Netty 面试第一题，也是线上 Netty 服务卡顿的第一大原因。

对照 Redis：Redis 是单 Reactor 单线程（纯内存操作，无阻塞 IO，一个线程够喂饱 CPU），Netty 是主从 Reactor 多线程（网络 IO + 业务混合，必须分线程）。Redis=1、Netty=核数×2、BIO=连接数——三档线程数就是切换成本与并发需求的三档答案，与 C10K 一节的结论完全一致。

3.3 虚拟线程：把阻塞写法映射回多路复用

JDK 21 虚拟线程的妙处：业务代码写回阻塞风格，JVM 底层自动把「阻塞」变成「让出载体线程去服务别人」——本质是 JVM 内部实现了一个多路复用 + 线程调度器：

sequenceDiagram

3.4 Tomcat 的线程模型：又一个 Reactor 变体（实战重点）

Tomcat 的 Connector（连接器）是独立于 Servlet 引擎的 IO 层，负责 socket 的建立与读写——从 8.5 起它默认跑在 NIO 上，是 Reactor 家族的第三个成员。但它的线程模型和 Netty 有本质区别，先看连接器演进：

Tomcat 版本 默认连接器 底层 说明
8.0 及以前 BIO（Java IO） 阻塞 IO，每连接一线程 8.5.0 起移除（官方迁移指南）
8.5 / 9 / 10 NIO 多路复用（Selector） 默认协议 HTTP/1.1
8.0+（可选） NIO2 JDK AIO 一直非默认，Linux 上无收益（§4.2）
8.5+（可选） APR/native 本地库 OpenSSL Tomcat 9 起并入 NIO 的 OpenSSL 形态
10.1.10+ / 11 虚拟线程执行器 JDK 21 虚拟线程 10.1 需显式配置，11 起默认

为什么 BIO 在 8.5 被移除：连接数一上来，「每连接一线程」的账就崩了（§1.2 的 C10K 算账），而 NIO 只需两个专职线程就能服务全部连接。Tomcat 的 NIO 线程模型是三段式：

flowchart TD
    CLIENT["Clients"] -->|"new connection"| ACC["Acceptor (x1)<br/>blocking accept() loop"]
    ACC -->|"register fd"| POLLER["Poller (Linux x1)<br/>epoll_wait loop, pollTime 2ms"]
    POLLER -->|"ready event as task"| POOL["Worker thread pool<br/>maxThreads=200 (default)"]
    POOL -->|"executes servlet request"| APP["Business logic"]

三个角色各干一件事（默认值均出自官方文档）：

  1. acceptor（默认 1 个线程）：死循环 accept()，收到新连接注册给 poller——对应 Netty 的 boss。
  2. poller（Linux 默认 1 个线程）：epoll_wait 循环（pollTime 默认 2000 微秒），就绪事件封装成任务丢进线程池——对应 Netty 的 worker 职责。
  3. worker 线程池（maxThreads 默认 200，minSpareThreads 默认 10）：真正执行 Servlet 业务。

poller 与 Netty worker 的分工差异，是两者线程模型的分水岭：

维度 Netty Tomcat
连接分配 连接绑定单个 EventLoop，同一连接永远同一线程 每次请求从池里临时抓线程，无绑定
线程数 boss 1 + worker 核数×2 acceptor 1 + poller 1 + 线程池 200
免锁依据 绑定 → 单线程串行 → 天然无锁 请求间无共享状态 → 无锁
适配场景 长连接、协议帧（RPC / 网关 / IM） 短请求、HTTP 语义（Servlet 每请求一线程模型）
线程打满后果 一个 EventLoop 卡住，几百连接一起等 池满，新请求排队或拒连

深挖：为什么 Tomcat 用「池」而 Netty 用「绑定」？ 机制差异是连接有没有状态——HTTP 请求之间无关联，Servlet 规范要求「一个请求在一个线程里从头执行到尾」，Tomcat 只需临时分配，用池；Netty 面向长连接协议开发，连接上挂着编解码器、半包缓冲等状态，必须钉死在一个线程上才能免锁，用绑定。生产后果：压测 1 万连接打进 Tomcat，真正干活的始终 ≤200 个线程，其余连接在排队——先等 worker 线程（池满），再等操作系统队列（acceptCount 默认 100，官方文档），队列也满就被内核直接拒连。所以压测里大量 Connection reset，第一嫌疑是 maxConnections（默认 8192，官方文档）和 acceptCount 这两个数，不是应用崩了。这正是一开始 C10K 结论的镜像：BIO 是线程=连接，Tomcat 是线程=并发请求（上限 200），连接再多也不长线程——收益是线程数可控，代价是请求排队。

另外，§3.3 的虚拟线程在 Tomcat 有官方落点：10.1.10+ 提供 StandardVirtualThreadExecutor（JDK 21+），把 worker 换成虚拟线程后「一请求一虚拟线程」，maxThreads 不再是硬天花板；Tomcat 11 起默认启用（发布公告）。「阻塞写法 + 容器帮你多路复用」在 web 容器里落了地。细节上，Tomcat poller 的 Selector 默认 LT 语义（事件没处理完下次继续报），和 Netty 的取向一致——防漏事件优先（§2.3）。

3.5 动手验证：连接数与线程数的对照

对照实验：BIO 服务器 1000 连接 = 1000+ 线程（pstree -p <pid> 数）；NIO/Netty 服务器 1000 连接 = 几个线程。线程数、连接数、fd 数三者的数量关系，就是 IO 模型在进程里的实锤。

再对 Tomcat（任意本地 Spring Boot 应用，内置就是 Tomcat）做一次线程解剖：

  • 预期观察点：Acceptor 1 个、Poller 1 个（Linux 默认）、exec-N 线程随并发增减且 ≤ maxThreads（默认 200）。
  • 判定标准：默认配置压测 Failed=0；把 server.tomcat.threads.max=50（Spring Boot 配置）改小重压，Failed 显著上升、exec 线程封顶在 50——线程池上限就是 Tomcat 吞吐的天花板，而连接数可以远大于 50。

4. Java 侧实践：BIO/NIO/AIO 怎么选

4.1 三种形态对照

形态 底层模型 典型类 连接并发 代码风格
BIO 阻塞 IO Socket / ServerSocket 线程 = 连接 最简单
NIO 多路复用（Selector + epoll） Selector / Channel / Buffer 线程 << 连接 回调/状态机
AIO 真异步（Windows IOCP；Linux 上退化） AsynchronousSocketChannel 线程 ≈ 0 回调
虚拟线程 + BIO 阻塞写法 + JVM 多路复用 普通 Socket + 虚拟线程池 线程 = 逻辑任务 阻塞风格，最简单

AIO 的坑在 4.2 深挖：Linux 上 JDK 的 AIO 底层还是多路复用模拟，没有真异步 IO 的收益，Netty 直接不用 AIO。

4.2 深挖：AIO 的真相——IOCP 与 Linux 的尴尬

AIO（异步 IO，JDK 7 的 NIO.2 异步通道）是「提交请求立即返回，内核完成后再回调」——回到 §1.4 的定义：多路复用是「内核替你等」，异步是「内核替你干」。这一节看「替你干」在三个平台上的三种真相：

实现 真异步？ 机制 现状
Windows IOCP 是 完成端口：内核完成 IO 后投递完成包，线程池取出回调 JDK AIO 在 Windows 的底层实现
Linux JDK AIO 否 epoll 多路复用 + JDK 内部线程池模拟 Netty 官方 wiki 明说不用 AIO
Linux io_uring 是 内核完成队列（SQ/CQ 环形队列，5.1+） Netty 有 incubator 移植，生产未普及

深挖：JDK 在 Linux 上的 AIO 是「多路复用 + 线程池」披了一层回调的壳（源码 UnixAsynchronousChannelProvider 走事件循环）。等于你自己写 NIO 再包回调，性能不比 NIO 好，还把线程的控制权交了出去——这正是 Netty 不用 AIO 的理由：Linux 上无性能收益（官方 wiki），且 AIO 回调跑在 JDK 内部线程池上，和 Netty「回调必须绑定 EventLoop」的线程模型冲突。IOCP 是真异步，因为 Windows 内核为此设计了完整的完成端口机制；Linux 内核直到 5.1 才有 io_uring 提供真异步，但它和 JDK AIO 的 API 不兼容，Java 生态还在追赶（netty-incubator-transport-native-io_uring）。

生产结论：Linux 上的 Java 高并发网络服务，多路复用（NIO / Netty）仍是主线；AIO 的价值在 Windows 场景和文件 IO（AsynchronousFileChannel），不在 Linux 网络 IO——这也是 Tomcat 的 NIO2 连接器始终非默认（§3.4 表）的底层原因。

动手验证：strace 拆穿 Linux 上的 AIO

写一个最小的 AIO echo 服务器，用 strace 看它到底调了什么系统调用：

  • 预期观察点：输出里是 epoll_create / epoll_ctl / epoll_wait 循环，没有任何 io_submit / io_uring_enter。
  • 判定标准：看到 epoll_wait 即证明 Linux 上 JDK AIO 是多路复用模拟——「异步」名不副实，性能天花板和自写 NIO 相同。

4.3 选型结论

场景 选择
内部服务、连接数少（<200） BIO + 线程池就够，别过度设计
高并发网关/RPC/消息 Netty（NIO + 主从 Reactor）
高吞吐 IO 密集业务 虚拟线程（JDK 21+）或 Netty
需要精确控制每个连接 NIO 裸写（极少）

4.4 动手验证：复现 Too many open files

这个报错的完整链路：连接数 × 每连接 fd（socket + 管道）> nofile → accept 失败 → 服务半残。**生产上所有高并发进程的启动脚本里都要有 ulimit -n 65535 或 systemd 的 LimitNOFILE**——漏了它，压测第一波流量就能干崩服务。

5. 总结与避坑清单

5.1 面试速答表

面试题 一句话答案
BIO/NIO/AIO 区别？ BIO 阻塞、一线程一连接；NIO 多路复用、一线程多连接；AIO 提交后回调（Linux JDK 上是模拟）
epoll 为什么比 select 快？ select 每次全量拷贝 + O(n) 扫描；epoll 注册一次、红黑树管理、只返回就绪链表（O(1)）
LT 和 ET 区别？ LT 反复报就绪（防漏）；ET 只报一次，必须读到 EAGAIN（高性能，写错丢事件）
Netty 为什么快？ 主从 Reactor + epoll + 零拷贝 + 池化 ByteBuf，全是内核与 JVM 机制的叠加
虚拟线程和 Netty 怎么选？ 都是「线程数低于连接数」；虚拟线程换阻塞写法，Netty 保留显式控制
10 万连接怎么实现？ 多路复用（1 线程管 N 连接）+ 调大 nofile + 调大端口范围（ip_local_port_range）
Tomcat 的连接器默认是什么？ 8.5 起默认 NIO（BIO 已移除）；acceptor 1 + poller 1（Linux）+ worker 线程池 200
Tomcat 压测大量 Connection reset？ 连接数超 maxConnections（默认 8192）或操作系统队列超 acceptCount（默认 100），内核拒连
Tomcat 和 Netty 线程模型差别？ Tomcat 池化（每次请求临时抓线程，无状态免锁）；Netty 绑定（连接钉死一个 EventLoop，串行免锁）
AIO 和 NIO 的区别？ NIO 内核替你等（就绪后你读）；AIO 内核替你干（完成再回调）；Linux 上 JDK AIO 是 epoll 模拟
Netty 为什么不用 AIO？ Linux 上 JDK AIO = 多路复用 + 线程池模拟，无性能收益，且回调线程不可控（官方 wiki）

5.2 实战避坑清单

症状 原因 处理
压测报 Too many open files nofile 配额默认 1024，连接数轻松超 启动脚本 ulimit -n / systemd LimitNOFILE
Netty 服务偶发卡顿 业务线程把阻塞操作（DB 查询）写进了 IO 线程 业务逻辑丢业务线程池；IO 线程只做编解码
连接数高但线程数也高 还在用 BIO 或线程池开太大 换 NIO/Netty；或虚拟线程
NIO 数据偶尔丢/错乱 ET 模式没读到 EAGAIN 就放弃 读循环直到返回 0 或 EAGAIN；入门用 LT
select 服务器连接>1024 异常 select 的 FD_SETSIZE 硬上限 换 poll/epoll（或 Netty）
Tomcat 高并发大量 Connection reset / 超时 maxConnections（8192）、acceptCount（100）、maxThreads（200）默认值被压穿 ss -lnt 对照连接数；调大三参数，或 10.1+/JDK 21 换虚拟线程执行器
Tomcat exec 线程数堆到上限且请求排队 maxThreads 设得太大，切线程成本吃掉 CPU（第 1 篇） 调回合理值；优化业务耗时；换虚拟线程让池上限失去意义

工具 看什么 对应本节概念

五个收获：IO 模型本质是「谁在等数据」的分配问题；epoll 的快是「注册与等待分离」的快；线程模型解决「等到了之后谁来处理」（Netty 绑定、Tomcat 池化、Redis 单线程是三份答案）；AIO 的「内核替你干」在 Linux 上名不副实；Java 的 BIO/NIO/虚拟线程是同一套内核机制的三副面孔。

实操建议：

  1. 高并发服务上线前检查三件事：ulimit -n、ip_local_port_range、监听端口 backlog（ss -lnt 看 Send-Q 溢出）。
  2. 用了 Netty/自研 NIO，先立规矩：IO 线程零阻塞操作，所有耗时逻辑必须出线程池。
  3. 新项目 IO 密集业务直接评估虚拟线程，连接管理交给框架（Netty/RPC 框架），两套并存不冲突。
  4. Tomcat 上线前核对三参数：maxThreads、maxConnections、acceptCount（压测 Connection reset 先查它们）；JDK 21 + Tomcat 10.1 直接评估 StandardVirtualThreadExecutor。
