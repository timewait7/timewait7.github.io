查询优化：优化器为什么会选错索引

Posted on 2026-10-24 In 数据存储 Word count in article: 5.5k Reading time ≈ 20 mins.

优化器不是”笨”，它是在信息不全的情况下做了一道成本算术题。它只知道三件事：表有多少行、索引的基数（cardinality）、以及一套写死的成本常数。你对数据分布的所有直觉——“这个状态只有 0.1%”——它都看不见，除非你给它统计信息。

本文要纠正一个流传很广的说法：优化器并不是动不动就选错。实测下来，绝大多数情况下它的选择是对的；真正的偏差集中在五种可识别的模式里。掌握这五种模式，你不需要背「十条优化铁律」，也能在 EXPLAIN 输出的第一眼判断它是否在犯错。

1. 优化器的账本：三个数字

1.1 它只算三件事

flowchart LR
    P["Parse<br/>conditions known"] --> R["Estimate rows<br/>stats + dives + histograms"]
    R --> C["Estimate cost<br/>read_cost + eval_cost"]
    C --> J["Compare candidate plans"]
    J --> W["Pick lowest cost"]
    R -.->|"no stats"| D["Default 10%<br/>guess"]
    D --> C

任何一份 EXPLAIN FORMAT=JSON 里，你只需要先看三个字段：

字段 含义 为什么重要
rows_examined_per_scan 这个访问方式预计要扫多少行 成本的主要来源
filtered 扫描后还剩百分之几（附加条件的选择性） 决定「扫了很多但没几条」的严重程度
rows_produced_per_join rows_examined × filtered% 估算的最终产出行数，JOIN 顺序靠它

1.2 统计信息从哪来

优化器不是瞎猜，它有四个信息来源，精度依次递减：

来源 适用 精度 怎么刷新
索引基数（index dive） 有索引的列做等值/范围 高：直接读索引页数行 ANALYZE TABLE，或自动（innodb_stats_auto_recalc）
索引统计（采样） IN 列表很长时替代 dive 中 同上
直方图（histogram） 没有索引的列 高：等高分桶 手动 ANALYZE TABLE ... UPDATE HISTOGRAM，不会自动更新
默认先验 什么都没有 低：等值 10%、范围 50% 无

一个容易踩的边界：eq_range_index_dive_limit 默认 200。当 IN (…) 里的值超过 200 个，优化器会放弃逐个值做 index dive，改用索引统计——同一个查询在 IN 列表第 200 个和第 201 个值之间，可能换一个执行计划。这不是玄学，是这个参数。

1.3 动手验证：读出一份账本

预期观察点：filtered 如果是 10.00、50.00 这类整数，多半说明这一列没有可用统计信息，走的是默认先验（等值 10%、范围 50%）；cardinality 会明显小于真实的不同值个数。

判定标准：

  • rows_examined_per_scan 与真实扫描行数差 10 倍以上 → 统计信息问题（本文第 2 节）；
  • filtered 与实际选择性差 10 倍以上 → 需要直方图或索引；
  • query_cost 只能用于同一实例内比较计划，不要拿它当毫秒。

2. 直方图：能修什么，不能修什么

2.1 实测 A/B：一个 0.1% 的状态列

造一张 100 万行的表，status = 1 只占 **0.1%**（1000 行），其余 99.9% 是 0。查询：

status 上没有索引，只有 create_time 上有。三种状态下优化器的估算：

状态 filtered 估算产出行 真实匹配行 选了哪个索引
无直方图 10.00 49,844 ~500 idx_ct 范围扫
有直方图（100 桶） 0.10 498 ~500 idx_ct 范围扫（没变）
status 上有索引 —（rows = 1000） 1,000 1,000 idx_status 等值

估算从 49,844 修到 498，误差从 100 倍降到 1 倍以内——直方图确实把「估算」修准了。但注意第三列：计划没变。

flowchart TD
    C["ANALYZE TABLE t UPDATE HISTOGRAM<br/>ON status WITH 100 BUCKETS"] --> B["equi-height buckets:<br/>each bucket ~ same row count"]
    B --> E["optimizer reads bucket for value 1<br/>-> 0.1% selectivity"]
    E --> F["filtered: 10.00 -> 0.10"]
    F --> G{"any alternative plan<br/>to switch to?"}
    G -- no --> H["estimate better,<br/>plan unchanged"]
    G -- yes --> I["join order / index choice<br/>may flip"]

2.2 为什么计划没变：估算准 ≠ 有别的计划可选

这条 SQL 只有 idx_ct 一个索引能用，其他候选是「全表扫描 + filesort」。优化器把 idx_ct 的成本算得更准了，但另一个候选本来就贵得多，次序不变。

这是一个必须说清的边界：直方图修的是「估算」，不是「决策」。 估算准了但计划没变，不代表白做——它让优化器在有多个候选计划时能选对（主要是 JOIN 顺序、子查询物化、IN 与 EXISTS 的取舍），也让你的 EXPLAIN 读数更可信。

2.3 有索引时，直方图没那么重要

同一个查询，给 status 建索引之后再跑，rows_examined_per_scan 直接就是 1000——和真值一致。因为索引上有基数统计，等值查询可以走 index dive 精确数一遍，比直方图更准。

所以加直方图的优先级是：

场景 该做什么
列没有索引，但经常作为过滤条件 加直方图（这是它的主战场）
列有索引 先 ANALYZE TABLE 刷新基数，直方图收益有限
列有索引且分布极倾斜（99% / 1%） 直方图可能帮不上，考虑改写 SQL 或建针对性索引（见 3.1）

2.4 直方图的两个硬坑

  1. 不会自动更新。innodb_stats_auto_recalc 只负责索引统计，直方图要手动 ANALYZE TABLE ... UPDATE HISTOGRAM。数据分布变了而你没刷新，估算就一直是旧的。
  2. 最多 1000 个桶，桶是等高的。100 个不同值的列用 100 个桶正好；100 万不同值的列用 1000 个桶，每个桶代表 1000 行，边界值附近还是估不准。它不是万能的。

2.5 动手验证：自己造一次估算修正

预期观察点：第 2 步 filtered 是 10.00，第 3 步变成 0.10（或接近真实值的数字），rows_produced_per_join 从五位数掉到三位数。

判定标准：

  • filtered 没变 → 检查列上是不是有索引（有索引时优先用索引统计），或者直方图没建成功；
  • filtered 变了但计划没变 → 正常，说明没有更优候选（2.2）；
  • 真实选择性与估算差 10 倍以上，且这列没索引 → 直方图值得加。

3. 五类真实的选择偏差

优化器大多是对的。真正值得记住的是下面五种模式——每一种都能用一条 SQL 复现。

# 模式 机制 实测
1 为了省排序，选了一个扫描面极大的索引 成本模型里排序很贵，LIMIT 的「提前停」收益估不准 扫 33 万个索引项，102 ms
2 隐式类型转换 字符串列与数字比较 → 列被 CAST 成数字，索引失效 0.012 ms → 127 ms
3 函数包裹列 列上做运算，索引无法定位 0.18 ms → 92 ms
4 深分页 offset offset 之前的行必须真读真丢 62.9 ms → 236 ms
5 统计信息过期 大批量写入后基数没刷新 cardinality 偏小，选错索引

3.1 模式一：为了省排序，扫了 33 万个索引项

上一篇那张订单表上，(status, create_time) 这个索引对「用户订单列表」本不该被用——但优化器选了它，因为能省掉 filesort：

方案 首行时间 全量时间 逻辑读
(status, create_time)（优化器选的） 7.21 ms 102 ms 333,178
(user_id, status, create_time)（人脑选的） 0.05 ms 0.052 ms 108

机制：优化器只算「总量成本」，不知道用户体感的是「首行时间」。它认为「顺着 create_time 排好序扫，找到 20 行就停」比「扫 200 行再排序」便宜，但它把「要扫多少行才能凑够 20 行」估成了乐观值。

处理：这不靠调参数解决，靠索引设计（③ 的列序）或 FORCE INDEX 兜底。更重要的是识别信号：EXPLAIN 里出现「key 是一个低选择性列打头的索引」+「rows_examined_per_scan 远大于返回行数」，就是它。

3.2 模式二：隐式类型转换让索引失效

code 是 VARCHAR(16) 且有索引：

写法 计划 实测
WHERE code = '12345' Index lookup on tord using idx_code 0.0116 ms
WHERE code = 12345 Table scan on tord + Filter: (code = 12345) 127 ms 
flowchart LR
    A["WHERE code = 12345"] --> B{"column type"}
    B -- "VARCHAR" --> C["CAST(code AS DOUBLE) = 12345<br/>expression on the column"]
    C --> D["index unusable<br/>full table scan"]
    B -- "BIGINT" --> E["direct key compare<br/>index lookup"]

差 一万倍。原因：MySQL 比较字符串列与数字时，把列转成数字再比（CAST(code AS DOUBLE)），列上做运算 → 索引无法定位。

这个坑在 Java 侧极其常见：MyBatis 里 #{id} 传的是 Long，而库里那一列是 VARCHAR。类型对不上的后果，就是一条本该 10 微秒的查询变成 127 毫秒，QPS 一上来直接打满 CPU。

处理：让 Java 类型、JDBC 参数类型、列类型三者一致；EXPLAIN 的 attached_condition 里出现 cast(...) 就是证据。

3.3 模式三：函数包裹列

写法 计划 实测
DATE(create_time) = ? Covering index scan（全索引扫 100 万行） + cast(...) 92.3 ms
范围改写 Covering index range scan（1440 行） 0.179 ms

注意一个精度细节：函数包裹版并不是「完全不用索引」，它退化成全索引扫描（覆盖索引，只读索引不读数据），所以比全表扫快一点，但仍然是 100 万行的成本。很多人看到 key 有值就以为索引生效了，其实扫的是整棵树。

同类问题：WHERE YEAR(create_time) = 2026、WHERE amount + 0 > 100、WHERE LEFT(name, 2) = '张'。处理方式只有两种：改写成范围，或者建函数索引（8.0.13+）。

3.4 模式四：深分页，offset 之前全是白读

写法 计划 实测
SELECT * FROM tord ORDER BY create_time LIMIT 900000, 20 全表扫 + filesort 100 万行 236 ms
延迟关联（先取 20 个主键再回表） 覆盖索引扫 90 万项 + 20 次回表 62.9 ms
SELECT * FROM tord ORDER BY id LIMIT 900000, 20 主键索引扫 90 万行 98.9 ms
主键 + 延迟关联 覆盖扫 + 20 次回表 61.4 ms 
flowchart LR
    subgraph Bad["LIMIT 900000, 20"]
        R["read rows 1..900000"] --> X["discard all of them"] --> K["keep 20 rows"]
    end
    subgraph Good["cursor pagination"]
        C1["WHERE create_time < last_seen"] --> C2["read 20 rows and stop"]
    end

延迟关联的写法：

机制：LIMIT 900000, 20 必须先把前 90 万行读出来再丢掉，这一步无法跳过。延迟关联省掉的是「前 90 万行每行都要回表取全字段」，只保留索引扫描。所以收益取决于「每行回表成本」，实测 3.75 倍。

根治：翻页深到十万级，本身就说明接口设计有问题。用「上一页最后一条的排序键」做游标（seek method）才能做到 O(1)：

3.5 模式五：统计信息过期

innodb_stats_auto_recalc 只在大约 10% 的行发生变化后才重新统计，突发大批量写入后，基数可能明显偏离。表现是：昨天还正常的查询，今天突然走了另一个索引。

判定标准：last_update 早于最近一次大批量写入 → 优先怀疑统计过期，再怀疑别的。

3.6 动手验证：五类各跑一条

预期观察点：① 的 Index range scan 扫描行数会是返回行数的上千倍；② 会出现 Table scan + cast；③ 是 Covering index scan 而不是 range scan；④ 有 Limit/Offset: 20/900000；⑤ 的 last_update 可能是几天前。

判定标准：五条里有任意一条命中，就按对应模式处理；全都没命中，问题多半不在优化器（去 ⑥⑦）。

4. 慢查询治理闭环

4.1 五步闭环

flowchart LR
    A["Alert: P99 spike"] --> B["Find top SQL<br/>digest by SUM_TIMER_WAIT"]
    B --> C["EXPLAIN ANALYZE<br/>estimate vs actual"]
    C --> D{"Which pattern?<br/>1-5"}
    D --> E["Fix: index / rewrite /<br/>histogram / ANALYZE"]
    E --> F["Verify on baseline<br/>logical reads + P99"]
    F --> G["Gray release<br/>watch error rate"]
    G --> A
步骤 动作 工具 产出
1 定位 按总耗时排序找 Top SQL events_statements_summary_by_digest 1~3 条待查 SQL
2 归因 估算 vs 实际行数、是否回表、是否排序 EXPLAIN ANALYZE 落在哪个模式
3 修复 加索引 / 改写 / 直方图 / ANALYZE DDL 与 SQL 改写 一条候选改动
4 验证 逻辑读、P99 前后对比 基线档案（① 那张表） 收益量化
5 灰度 小流量观察，保留回滚手段 应用灰度 + 索引 INVISIBLE 上线或回滚

4.2 慢日志聚合：pt-query-digest

EXPLAIN 只能看一条 SQL，而慢日志是批量看的入口：

报告里最该看的三列：Response time 总占比、Rows examine（扫多少行）、Rows sent（返回多少行）。两者的比值就是「白读倍数」，比值大的基本都是索引问题。

不装 Percona Toolkit 时，用 performance_schema 的 digest 表也能得到同样的视图（上一篇给过查询），差别只是拿不到完整 SQL 文本。

4.3 贯穿案例：订单列表 P99 收到这一层

回到那条贯穿线索：订单列表 P99 从 200ms 涨到 3.2s。走到本篇，能确定的是：

  • 如果 EXPLAIN 显示走了「低选择性列打头的索引 + 大范围扫描」→ 模式一，回 ③ 改列序；
  • 如果出现 cast → 模式二，改类型；
  • 如果 filtered 与实际差 10 倍且列无索引 → 模式五 + 直方图；
  • 如果 Limit/Offset 很深 → 模式四，改游标翻页。

都排除了，说明慢不在「选计划」这一层——接着去 ⑤（长事务、undo 膨胀）、⑦（刷脏、物理读）、⑧（从库延迟）找。这就是六层成本账的正确用法：一层层排除，而不是一次改十个参数。

4.4 FORCE INDEX 什么时候该用

场景 该用吗 理由
已用前后对比证明优化器选错，且统计无法修正 可以用 人脑补足模型的先验
只是「感觉」另一个索引更快 不要 没有量化的直觉通常是错的
表数据量会大幅变化 谨慎 数据分布一变，强制索引可能变成灾难
临时救火 可以，但留 TODO 必须记：为什么、复查时间、失效条件

用法与留痕：

更温和的替代是 USE INDEX（给建议而非强制）和 8.0 的 INVISIBLE 索引（把错误选项直接藏起来，观察是否还选错）。

4.5 动手验证：走完一次闭环

预期观察点：改写后逻辑读从六位数掉到四位数以下，actual time 从几十毫秒掉到亚毫秒。

判定标准：

  • 逻辑读降了一个数量级 → 修复有效，进灰度；
  • 逻辑读没变但耗时降了 → 省的是 CPU（函数调用），也算收益；
  • 两者都没变 → 你的瓶颈不在这条 SQL，回到第 1 步重新排序。

5. 总结

5.1 面试速答表

面试题 一句话答案
优化器怎么选索引 枚举候选访问路径，按 rows_examined × 读成本 + rows_produced × 评估成本 估总成本，取最低
filtered 是什么意思 该访问方式扫描后，附加条件能筛出多少百分比；10.00 通常是没统计信息时的默认先验
EXPLAIN 的 rows 准吗 是估算；有索引时靠 index dive 较准，无统计时用默认 10%，可能偏差百倍
直方图解决什么问题 修无索引列的选择性估算；有索引时优先用索引统计，收益有限
直方图会自动更新吗 不会，必须手动 ANALYZE TABLE ... UPDATE HISTOGRAM
为什么隐式类型转换会让索引失效 比较时把列转成数字（CAST(col AS DOUBLE)），列上有运算就无法按索引定位
为什么函数包裹列会让索引失效 同上；注意它通常退化成「全索引扫描」而不是完全不用索引
深分页为什么慢 offset 之前的所有行必须真读真丢；延迟关联能省回表，根治要用游标翻页
什么时候该 FORCE INDEX 有前后对比证据、统计无法修正、且愿意定期复查时才用；靠感觉用等于赌博
eq_range_index_dive_limit 是干什么的 IN 列表超过它（默认 200）就不逐个 index dive，改用索引统计，可能导致计划跳变

症状 原因 处理

5.4 实操建议

  1. **先看 filtered 是不是 10.00 或 50.00**。这是判断「有没有统计信息」最快的一眼，但它是嫌疑而非定罪，最终要用真实选择性对一下。
  2. 不要迷信直方图。它只修「无索引列的估算」，且不会自动更新；有索引时先 ANALYZE。
  3. 五种模式做成排查卡：排序诱惑、隐式转换、函数包裹、深分页、统计过期。命中一个就处理一个，不要同时改三处。
  4. FORCE INDEX 必须留注释：为什么、什么时候复查、什么条件下失效。没有注释的强制索引，半年后就是一颗地雷。
  5. 每次修复回到基线档案记一行：逻辑读、P99、扫描行数。这是你和「凭感觉优化」之间唯一的区别。

Schema 与索引：把逻辑读降下来

Posted on 2026-10-24 In 数据存储 Word count in article: 5.7k Reading time ≈ 21 mins.

索引不是「加一个就快」，而是用「写代价 + 磁盘空间」买「读路径」。它唯一能改变的东西是上一篇那把尺子：一次查询碰了多少个 16KB 页。所以索引设计的本质不是记口诀，而是把查询的访问形态——等值、范围、排序——翻译成 B+ 树的物理顺序，让引擎沿着顺序读，而不是满地找。

本文用一张 100 万行的订单表回答四个问题：B+ 树到底怎么排、为什么二级索引要回表、复合索引的列序为什么不能拍脑袋、以及每个索引要向写入收多少费。所有数字都在 MySQL 8.0.46 容器里实测。

1. B+ 树：物理顺序决定一切

1.1 三层结构，一个公式

InnoDB 的索引是一棵 B+ 树，页大小默认 16KB（innodb_page_size，实测 16384，建库时定死）。

flowchart TD
    ROOT["Root page<br/>~1170 entries"]
    ROOT --> B1["Branch page<br/>~1170 entries"]
    ROOT --> B2["Branch page"]
    ROOT --> B3["Branch page"]
    B1 --> L1["Leaf pages<br/>rows = 16384 / row_size"]
    B1 --> L2["Leaf pages"]
    B2 --> L3["Leaf pages"]
    B3 --> L4["Leaf pages"]
    L1 -.->|"leaf chained by<br/>doubly linked list"| L2

非叶子节点只存「键 + 页指针」，所以一页能装很多项：

  • 主键 BIGINT 8 字节 + 页指针 6 字节 = 14 字节 → 每页约 1170 个分支项
  • 叶子节点存整行（聚簇索引）或「索引列 + 主键」（二级索引）→ 每页行数 = 16384 / 行大小

于是容量公式是：

行大小 每页行数 三层容量 1000 万行需要几层
50 字节（窄表） ~327 ~4.4 亿 3 层
100 字节 ~163 ~2.2 亿 3 层
1KB（宽表） ~16 ~2190 万 3~4 层
4KB（含大字段） ~4 ~547 万 4 层

这张表就是「三层 2000 万行」这个说法的出处：它只在行大小 1KB 时成立。窄表三层能装 4 亿行，宽表可能四层都不够。面试时先问行大小，再给数字，比背结论有效。

本文的 orders 表 100 万行、56.6MB → 每行约 59 字节 → 每页约 275 行 → 叶子页约 3636 个 → 分支页 4 个 → 树高 3 层。所以主键等值查询要碰 3~4 个页（根 + 分支 + 叶子，加上定位记录那次）。

回表的成本不是「多一次查找」，而是「第二次树遍历 + 随机页访问」。上一篇测过：同一批 1 万行，覆盖索引 53 次逻辑读，回表 31223 次。差出来的 3 万次，全是聚簇索引上的随机页。

1.3 深挖：二级索引为什么存主键，而不是行地址

如果二级索引的叶子存「数据文件的物理地址」，一次回表就不用再走 B+ 树，看起来更快。InnoDB 没这么做，原因在页分裂：插入一行导致叶子页分裂时，页内所有行的物理位置都会变，所有指向它的二级索引条目都要跟着改——写放大直接变成灾难。

存主键则只需要主键稳定，行的物理位置怎么搬都不影响索引。代价是回表必须重新走一次聚簇索引，多一层树遍历。

这个取舍在生产上的后果很具体：

  • 主键越短越好。主键是 BIGINT（8 字节）时，二级索引每条结束都要多 8 字节；换成 CHAR(32) 的 UUID，二级索引体积直接膨胀几十个百分点，Buffer Pool 能装的页变少（⑦ 会算这笔账）。
  • 主键别用「业务上会变」的列。改主键 = 搬整行 + 重建所有二级索引条目。
  • 自增主键的顺序插入让叶子页基本只在右侧追加，页分裂少；随机主键（UUID）会把分裂摊到整棵树，这是「UUID 做 PK 写入慢」的真实机制。

1.4 动手验证：数清一次主键查询碰了几页

预期观察点：bytes_per_row 落在几十到几百字节；page_requests 是 3~4（树高 3 层 + 定位记录）。如果结果是几十，说明你查的不是主键，或者表上还有别的开销。

判定标准：

  • 页请求数 ≈ log1170(叶子页数) + 1 → 结构正常；
  • 页请求数异常大 → 检查是否用了 WHERE id + 0 = ?（表达式让优化器放弃等值定位）。

2. 复合索引：列序是由物理顺序决定的，不是习惯

2.1 最左前缀不是规则，是字典序

idx(user_id, status, create_time) 的叶子按 (user_id, status, create_time) 三级排序，等价于一本先按姓氏、再按名字、最后按生日的电话簿：

  • 你能直接翻到「姓张」的区段 → 只给 user_id 能用
  • 你能翻到「姓张、名三」的区段 → 给 user_id + status 也能用
  • 你没法直接翻到「所有叫三的人」→ 只给 status 用不上

2.2 七种索引方案，两条真实查询

场景是一张 100 万行的订单表：5000 个用户，每人约 200 单，状态分布 90% / 9% / 1%（已完成 / 处理中 / 异常）。

两条真实查询：

  • Q1 用户订单列表：WHERE user_id = 123 AND status = 0 ORDER BY create_time DESC LIMIT 20
  • Q2 运营后台筛选：WHERE status = 2 ORDER BY create_time DESC LIMIT 20

A 无二级索引 128 ms 5723 filesort 113 ms 5723
B (user_id) 0.317 ms 820 filesort 114 ms 5724
C (user_id, status) 0.304 ms 821 filesort 114 ms 5724
D (user_id, status, create_time) 0.052 ms 108 无 119 ms 5724

G (status, create_time) 7.21 ms（首行 102 ms 全量） 333178 无 0.346 ms 1469

2.3 这张矩阵读出的三件事

第一，没有万能索引。 D 让 Q1 快了 2400 倍，但对 Q2 毫无作用（119ms，等于全表扫）；G 让 Q2 快了 300 倍，但对 Q1 是灾难。原因是同一件事：索引只在「最左列被等值约束」时才定位得动。Q1 限制 user_id，Q2 限制 status，两个条件互为「非最左列」，各自都需要一棵按自己打头的树。

第二，能用 ≠ 该用。 G 在 Q1 上被优化器选中了（因为能省掉 filesort），结果是扫了 333,178 个索引项才凑够 20 行——7.21ms 才吐出第一行，全部 20 行用了 102ms，比 A 的全表扫还接近。这就是「优化器为了省排序，愿意付出三千倍的扫描」：它按成本估算，而估算里没有「你要等 7 秒才看到第一行」这件事。

第三，排序被索引吃掉时，收益最大。 C → D 只多了一个列，耗时从 0.304ms 掉到 0.052ms，逻辑读从 821 掉到 108。区别不在「过滤更多行」，而在逻辑读从 820 页降到 108 页：C 需要把该用户的 200 行全部回表、再排序取 20 行；D 顺着索引直接取前 20 行就停。

反过来看 B → C 几乎没变化（820 → 821）。这是因为只有 200 行的内存排序本来就很便宜。这解释了为什么「把 WHERE 里的列都塞进索引」多半没用：索引的价值在「少读页」和「省排序」，不在「条件看起来都覆盖了」。

一个需要标明的推理（非实测）：E (user_id, create_time) 在 Q1 上与 D 打平，依赖的是 status = 0 占 90% 这个分布——它顺着 create_time 扫，碰到非 0 状态就跳过。如果把条件换成 status = 2（占 1%），E 就要扫完该用户全部 200 行、回表 200 次才能凑够 20 条，而 D 依然直接定位。索引方案的选择不能脱离数据分布。

2.4 三星索引：把「等值、排序、覆盖」一次吃下

Lahdenmäki 的三星评价体系，是复合索引列序的实用口诀：

星级 条件 收益
★ 一星 WHERE 里的等值列放在索引最左 能定位，减少扫描
★★ 二星 ORDER BY 的列紧跟等值列 消除 filesort，LIMIT 能提前停
★★★ 三星 SELECT 需要的列全在索引里 不回表

对应到 Q1：(user_id, status, create_time) 拿到 ★★（等值 user_id, status + 排序 create_time），但因为 SELECT * 需要 amount、remark，拿不到第三星——所以它是「两星索引 + 20 次回表」。如果接口只要 user_id / status / create_time / amount 这 4 个字段，把 amount 追加进索引就能拿满三星，回表次数从 20 降到 0。

口诀：等值在前，排序在中，覆盖在后；范围一旦出现，后面的列只能当过滤器。

2.5 深挖：范围条件为什么截断后面的列

因为 B+ 树在范围内是有序的，但范围之间不保证全局序。create_time > '2026-01-01' 命中很多叶子页，每页内部按 create_time 有序，而 status 在这些页之间是完全乱序的。引擎只能逐页扫、逐行过滤，无法「跳到 status = 0 的位置」。

生产上的三个直接后果：

  1. 范围列别放中间。(a, b_range, c) 里 c 基本废了，应改成 (a, c, b_range)（如果 c 是等值）。
  2. IN 是多个等值区间，不是范围。status IN (1,2) 会让索引变成两段 seek，通常比 status > 0 这种真范围好得多。
  3. !=、NOT IN、IS NOT NULL 都是范围，后面的列同样失效。

2.6 动手验证：在自己的表上跑这张矩阵

预期观察点：方案的差异会集中在两个地方——actual time 的首行时间，以及计划里有没有 Sort 节点。有 Sort 的说明排序没被吃掉。

判定标准：

  • 逻辑读 > 1000 → 索引没定位住，检查最左列是不是等值；
  • 有 Sort 且行数 > 1 万 → 排序是主要成本，把 ORDER BY 列挪到等值列之后；
  • 逻辑读个位数但耗时几十毫秒 → 你在等锁或等 IO，去 ⑥⑦。

3. 写放大与空间：索引是收费的

3.1 实测：0 到 5 个索引的插入耗时

同一张表结构、插入 30 万行，只改二级索引数量（单线程、同容器、innodb_flush_log_at_trx_commit=1）：

二级索引数 插入耗时 相对倍数 索引占用
0 0.451 s 1.00× 0
1 0.610 s 1.35× 7.5 MB

4 1.299 s 2.88× 28.1 MB
5 1.882 s 4.17× —（统计未刷新）

五个索引让写入慢了 4.2 倍。 每插入一行，InnoDB 要做：1 次聚簇索引插入 + N 次二级索引插入 + undo/redo 记录。每个二级索引都是一棵独立的 B+ 树，都要找位置、可能分裂页。

3.2 空间账

orders 表本体 56.6MB，一个 (status, create_time) 索引就占 21.5MB——**索引是数据的 38%**。300 万行的表如果有 5 个索引，索引体积很容易超过数据本体。

更要紧的是这些页要一起进 Buffer Pool。池的大小固定（⑦ 会算），索引越多，能缓存的数据页越少，物理读越多。所以「加索引」在内存上是一笔真实的支出，不是免费的。

3.3 深挖：change buffer 只救非唯一二级索引

写放大有一个缓冲机制：change buffer。当二级索引页不在内存时，InnoDB 先把变更记在 change buffer 里，等页被读进来时再合并，省掉一次随机读。

但它有边界：

索引类型 change buffer 是否生效 原因
非唯一二级索引 是 不需要检查唯一性，先记下来
唯一二级索引 否 必须读页确认没有重复值，读都读了，直接改
聚簇索引（主键） 否 聚簇索引的变更本身就是数据变更

这就是一条常被忽略的工程结论：「唯一索引」不是免费的约束，它把随机写放大了一倍。业务上真需要唯一性（防重复下单、幂等键）当然要用，但「顺手加个唯一」的代价要算清楚。

顺带解释一个常见疑问：为什么批量导入时先把唯一索引去掉、导完再加回去会快？因为省掉的是「每行一次唯一性检查的随机读」。

3.4 动手验证：测你自己的写放大曲线

预期观察点：耗时随索引数单调上升，5 个索引时约为 0 索引的 4 倍；同时 information_schema.tables 的 index_length 也在涨。

判定标准：

  • 每加一个索引，写入劣化超过 40% → 先算清这个索引带来的读收益是否值得；
  • 写入劣化明显但读没有改善 → 索引列序错了（回到 2.2 的矩阵）；
  • 索引体积超过数据体积 → 该做冗余索引清理了（4.3）。

4.2 回到订单表：最终方案

结合 2.2 的矩阵，两条查询的结论很清晰：

保留 理由 放弃 理由
(user_id, status, create_time) 覆盖 Q1，等值 + 排序都吃到 (user_id) 是上面前缀，冗余

— — (user_id, create_time) 与 D 打平但对低占比状态会退化

最终两个索引，各服务一种访问形态。这不是「索引越多越好」，也不是「越少越好」，而是每个索引都要有一个明确的、被量化的查询在用它。

4.3 冗余索引的三种形态

形态 例子 处理
前缀冗余 (a) 与 (a, b) 同时存在 删掉短的（长的能替代它）

一个实测的细节：SHOW INDEX 里 status 列的 Cardinality 显示 2，而它实际有 10 个不同值。因为统计信息是采样估算，不是精确值——基数也会骗人。这件事在 ④ 会展开：优化器就是拿着这种估算去做决策的。

4.4 动手验证：给你的库做一次索引体检

预期观察点：schema_redundant_indexes 会直接把「短的被长的覆盖」列出来；index_pct 超过 50% 说明索引比数据还重。

判定标准：

  • index_pct > 100% → 索引体积已超过数据，先清冗余再谈加索引；
  • 冗余索引存在但你不敢删 → 先设 ALTER TABLE ... ALTER INDEX ... INVISIBLE（8.0 特性），观察一周无异常再删。

5.1 面试速答表

面试题 一句话答案
为什么用 B+ 树而不用 B 树 / 红黑树 B+ 树非叶子只存键，一页装更多分支 → 树更矮；叶子有链表 → 范围扫描快；磁盘读写以页为单位，矮树意味着更少 IO

为什么二级索引存主键不存行地址 页分裂会让行地址变化，存主键只需主键稳定；代价是回表要再走一次聚簇索引

5.4 实操建议

  1. 先列查询形态，再想索引。等值、范围、排序各是哪几列，写在一张纸上，比直接 ADD INDEX 有效。
  2. 每加一个索引，就记录三件事：它服务哪条 SQL、逻辑读降了多少、写入慢了多少。记不住的索引，就是该删的索引。
  3. 优先做覆盖索引，它同时省逻辑读和回表；做不到时再退一步做「等值 + 排序」的两星索引。
  4. 范围条件一律放到最后，status IN (...) 比 status > 0 友好得多。
  5. **删索引之前先 INVISIBLE**，观察一个完整业务周期（含月结）再物理删除。

一条 SQL 的六层成本账：架构不是画流程图

Posted on 2026-10-24 In 数据存储 Word count in article: 5.7k Reading time ≈ 21 mins.

架构图的价值不在于「分了几层」，而在于每层各花多少时间。一条看起来朴素的 SELECT，从建立连接到把字节吐回客户端要过六道关，这六道的量级差着三个数量级：连接是毫秒级，解析是微秒级，页访问是百纳秒级，落盘是几十微秒级。搞不清钱花在哪一层，所有优化都是蒙。

本文用一条线索把六层串起来：先看清每层的成本量级，再判断你的慢查询卡在第几层，最后只改那一层。文中所有数字都在 MySQL 8.0.46 容器里实测，表是上一篇那张 100 万行的 t1。

这张表的用法很直接：你的慢查询卡在哪一行，就只优化那一行。一个 40ms 的查询，如果 35ms 花在磁盘上，你加索引是没用的；如果 35ms 花在 Buffer Pool 上（逻辑读太多），你加内存也没用。

1.2 实测：把六层的数字钉在墙上

同一个容器、同一张表（100 万行、3430 页、默认 128MB 池），把不同「深度」的语句各跑 200 次，取服务端 performance_schema 的平均耗时：

语句 经过哪几层 实测平均耗时 备注
SELECT 1 连接（已复用）+ 解析 + 优化 + 执行 10.8 µs 不碰任何表的纯开销
SELECT id FROM t1 WHERE id = ? 上面全部 + Buffer Pool 3~4 页 21.3 µs 主键等值
SELECT SUM(user_id) … user_id BETWEEN 1 AND 1000 + 索引范围扫 1 万行（覆盖） 1.17 ms 53 次逻辑读

把这张表竖着看，能读出三个结论：

  1. 固定开销约 11 微秒。这是 MySQL 处理任何一条语句的地板价（解析 + 优化 + 派发），它跟你查什么无关。所以「一条 SQL 发一次」的循环写法天生亏，批量接口省的不是索引，是这 11 微秒 × N。
  2. 从 21 µs 到 61 ms，差 2900 倍，而这一段的差别全部是「逻辑读多少个页」。索引能做的，就是把 3430 页压到 4 页。
  3. 同一份数据、同一批结果，SUM(user_id) 和 SUM(LENGTH(c)) 差 2.8 倍，只因为后者需要回表。这一条是第 3 节的主角。

1.3 深挖：为什么连接层贵得不成比例

在一个已复用的连接上执行 SELECT 1 是 10.8 微秒，而新建一个连接要付：三次 TCP 握手、认证往返（caching_sha2_password 要额外一轮）、会话变量初始化、权限表装载、线程创建。这一串在服务端是几毫秒，而它换来的是 11 微秒的执行——连接成本比执行成本高两个数量级。

实测对比（macOS + Docker Desktop，注意这个数字包含容器与客户端进程启动）：

单次 30.7 ms 里绝大部分是 docker exec 与 mysql 客户端进程启动，服务端只占几毫秒——这个比例本身才是重点：真正的业务代码里没有 docker exec，但同样要付客户端到服务端的网络 RTT × 2~3 次。所以「短连接」在任何网络有延迟的环境里都是灾难。

这也是连接池存在的原因，而且能解释一个常见误判：连接池打满时，接口耗时会突然从毫秒跳到秒级，因为请求在等一个「贵两个数量级」的资源。⑪ 会专门算这笔账，这里只需记住：连接是六层里唯一「用不起就别用」的一层。

再往下一层，是站内《进程与线程：从模型到调度》里算过的账：在 MySQL 里每个连接对应一个服务端线程，线程一多，上下文切换的成本就开始吃掉 CPU。线程数不是越多越好，连接池不是越大越好，两个结论来自同一个机制。

判定标准：

  • 两者差值在微秒级 → 你的瓶颈不在这层，往 ③ 走；
  • SELECT 1 就超过 1 ms → 先查网络 RTT 和连接池（⑪），不要碰 SQL；
  • 平均值与 P99 差 10 倍以上 → 有排队或锁等待，去 ⑥。

2. Server 层：解析、优化、执行

2.1 解析器：只做「这句话合法吗」

阶段 做什么 典型的失败
词法分析 把字符串切成 token（关键字、标识符、常量） 引号 / 反引号混用
语法分析 按语法规则建出语法树 GROUP BY 少列、ON 写错位置
预处理 检查表、列、别名是否存在，检查权限 Unknown column、权限不足

这三步是纯 CPU 操作，成本在微秒级，没有优化空间——除非你减少语句数量。一个常见的反例是在循环里拼 SQL 逐条执行，等于把 11 微秒的地板价乘以 N。

顺带说一个 8.0 的变化：查询缓存在 8.0 已被整体移除（上一篇实测 query_cache% 变量为空集），所以「同样的 SQL 第二次会变快」这句话在 8.0 上只可能来自 Buffer Pool 或操作系统缓存，不可能是 SQL 文本缓存。

2.2 优化器：六层里唯一「做决策」的地方

优化器不执行查询，它只做一件事：在若干候选执行计划里挑成本最低的那个。成本由三部分构成——读页的 IO 成本、评估条件的 CPU 成本、以及行数估算。

  • filtered = 10.00：优化器认为这个等值条件能筛掉 90% 的行——因为它对 c 列没有任何统计信息（没索引、没直方图），只能用内置先验：等值条件的选择性按 10% 估。

优化器还有几个固定的成本常数（读一页的成本、评估一行的成本、比对一次的成本），这套常数源自早期硬件假设（随机 IO 昂贵、CPU 单核），而不是你机器上的真实延迟。你的 NVMe 盘随机读比 HDD 快一到两个数量级，但在优化器眼里两者一视同仁——这是成本模型落后于硬件的经典案例，也是为什么生产上偶尔要 FORCE INDEX，那是在用人的判断纠正模型的先验。

2.3 执行器：按计划走，不动脑

执行器拿到执行计划后，逐行调用存储引擎的 handler 接口（index_read、rnd_next、index_next 等），每调用一次至少涉及一次页访问。

维度 优化器 执行器
职责 决定「怎么查」 负责「照着查」

出错表现 走错索引、JOIN 顺序差 回表太多、函数调用过多

一个实用的判据：EXPLAIN 里的 rows 是优化器的估算，EXPLAIN ANALYZE 里的 actual rows 是执行器的实际。两者差 10 倍以上，问题在优化器（统计信息）；两者接近但都很大，问题在执行路径（索引没覆盖住）。

3.2 回表：逻辑读的放大器

二级索引只存索引列 + 主键值。当查询需要索引里没有的列时，必须拿主键回聚簇索引再查一次——这就是回表。它的代价不是「多一次查找」，而是把一次顺序的索引扫描变成一万次分散的页访问。

同一批 1 万行，逻辑读差 589 倍，耗时却只差 2.8 倍。这个不对称是本文最值得记住的一课。

3.3 深挖：为什么逻辑读涨 589 倍，时间只涨 2.8 倍

因为这张表整表都在内存里（3430 页 vs 8192 页的池）。回表增加的 3 万次页访问全部命中 Buffer Pool，每次约 100 纳秒（3.33 ms ÷ 31223 ≈ 0.107 µs，其中还含排序等其他开销），所以放大了 589 倍只换来 2.8 倍耗时。

换算一下两者的单价：

操作 单价（量级） 换算
逻辑读（命中 Buffer Pool） ~100 ns 1 倍
物理读（NVMe SSD 随机） 50~100 µs 500~1000 倍

这就是「回表很慢」这句话的真实含义：只有在页不在内存时，回表的逻辑读放大才会等比例变成时间。生产库几百万行、Buffer Pool 装不下时，那 3 万次访问里有相当一部分要落盘，3.33 ms 会变成几十毫秒——同一份 SQL，本地测 3 ms，线上 80 ms，差的就是这一层。

所以「加索引 / 改覆盖索引」的收益是条件性的：数据全在内存时，它省的是 CPU 和锁竞争；数据装不下时，它省的是磁盘 IO。判断属于哪种，看 Innodb_buffer_pool_reads 有没有涨——这是上一篇那把尺子的第二次使用。

站内《文件系统与磁盘 IO》讲过 page cache 与 fsync 的成本结构，放在这里就是第 6 层的账：物理读的钱一次几十微秒，而每次 fsync 还要再付一遍。一次事务提交至少一次日志落盘，2 万 TPS 就是每秒 2 万次 fsync——⑦ 会算这笔账，并解释为什么 innodb_flush_log_at_trx_commit=1 换来的性能损失是「必需的成本」而不是「可以调的参数」。

3.4 动手验证：把回表的账算在自己机器上

预期观察点：A 的逻辑读在两位数到三位数，B 跳到四位数甚至五位数（本篇 53 → 31223），而 B 的 actual time 只涨两三倍。

判定标准：

  • B/A 的逻辑读比 > 10 → 这张表上回表很贵，优先考虑覆盖索引（③）；
  • 若 B 的 actual time 涨幅接近逻辑读的涨幅 → 说明有物理读参与，池不够（⑦）；
  • 若两者耗时都很大但逻辑读很小 → 你在等锁，去 ⑥。

4. 成本账的实战用法

4.1 同一 SQL，数据量不同，钱花在不同层

5.4 实操建议

  1. **先量 SELECT 1**。这个数字代表你这套环境的地板价，任何低于它的优化目标都是幻想。
  2. 把「六层」当成排查清单，每次慢查询按顺序排除：连接 → 解析 → 优化 → 执行 → 池 → 磁盘，一次只排除一层。
  3. 记住三个单价：逻辑读 100 ns、物理读 ~50100 µs、连接 ~几毫秒。三者差两个数量级，你的优化收益上限由它们决定。
  4. 遇到「估算与实际差 10 倍」，先怀疑统计信息，再怀疑索引——filtered 是整数就是证据。
  5. 每次改完，回到上一篇的基线表加一行：逻辑读、物理读、耗时。没有这三列，你无法证明自己改对了。

1. 性能只有三个钱包：逻辑读、物理读、等待

1.1 一句话定义

MySQL 的慢，永远落在三件事之一：读得太多（逻辑读）、读得太远（物理读）、在等（锁 / IO / 调度）。优化手段再多，也只是在这三个钱包里省钱。

这三层的省钱难度是递增的：改索引能直接把逻辑读砍掉一个数量级；加内存只能让物理读变少，逻辑读一次都不会少；而等待往往要动事务边界和业务逻辑，最贵。

先记住这句话：逻辑读是可以被设计掉的，物理读只能被缓存掉。

1.2 逻辑读：唯一能靠设计降下来的成本

实测一张 100 万行的表（表结构见 2.3 节），三种访问方式的页访问次数差异极大：

查询 访问路径 扫了多少行 页请求 实测耗时
WHERE id = 500000 主键等值 1 行 4 次 0.083 ms
WHERE user_id = 12345（无索引） 全表扫描 100 万行 3430 页 85.2 ms
WHERE user_id = 12345（建索引后） 覆盖索引 10 行 个位数 0.0066 ms

同一张表、同一份数据，只加了一个索引，耗时差了四个数量级——而这四次差距全部发生在逻辑读这一层，物理读没有参与（表早就全在内存里了）。

主键等值只用了 4 次页请求，这正好对上 B+ 树的层数：这张表 3430 页，根节点 1 页 → 内部节点 3 页 → 叶子 3430 页，树高 3 层，加一次记录定位就是 3~4 次。

顺带把「B+ 树三层能存多少行」这个面试题的算法说清：每页能存的行数 = 16384 / 行大小。行大小 54 字节时每页约 300 行，三层就是 1170 × 1170 × 300 ≈ 4 亿行；行大小 1KB 时每页 16 行，三层约 2000 万行。所以「三层 2000 万」只在宽行场景成立，背结论不如记公式。

1.3 物理读：Buffer Pool 决定的那部分

同一张 100 万行的表（3430 页 ≈ 54MB），在默认 128MB 的 Buffer Pool（8192 页）里能整表装下。这就是为什么本地测试经常出现下面这种「完美」结果：

场景 逻辑读 物理读 说明
重启后第一次全表扫描 数千 1046 冷启动，含 InnoDB 的预读
紧接着再扫一次 数千 0 全命中，物理读归零
主键等值查询 4 0 页常驻内存

注意这里的关键事实：命中之后物理读变成 0，但逻辑读一次都没少。 所以「Buffer Pool 命中率 99.9%」从来不等于「查询很快」——它只说明你不用去磁盘，不说明你没读多余的数据。这两件事在监控面板上是两个指标，在优化时是两条完全不同的路。

1.4 深挖：为什么你在本地永远测不出 IO 瓶颈

MySQL 8.0 的 innodb_buffer_pool_size 默认是 128MB（本篇实测 134217728 字节），而且它不感知容器的 cgroup 内存限制——你给容器 8G 内存，它也只肯用 128MB 做缓冲池，除非你显式设。

把这件事换算成数据量：

表行数 页数（估算） 数据量 与 128MB 池的关系 你会看到的现象
10 万 ~340 ~5MB 池的 4% 全是逻辑读，物理读恒为 0
100 万 3430（实测） 54MB 池的 42% 依然全内存，本地「测不出 IO 问题」
1000 万 ~3.4 万 ~540MB 池的 4 倍 物理读出现，命中率明显下降
5000 万 ~17 万 ~2.7GB 池的 21 倍 IO 主导，P99 开始抖

这就是「本地跑得好好的，上线就慢」的技术原因之一。生产库动辄几百 GB，Buffer Pool 再大也只能装下一部分，冷数据必然走磁盘；而你在本地用 100 万行测出来的 43ms，测的是内存速度。

这背后的机制值得多说一句：InnoDB 的 Buffer Pool 和操作系统的 page cache 是两层独立缓存。一次物理读的路径是「磁盘 → page cache → Buffer Pool」，读进来的页在两边各存一份，内存被用了两次。

flowchart LR
    Q["Query needs page #42"] --> BP{"Buffer Pool<br/>128MB default"}
    BP -- hit --> R1["Return row<br/>no disk IO"]
    BP -- miss --> PC{"OS page cache"}
    PC -- hit --> R2["Copy into Buffer Pool<br/>memory-to-memory"]
    PC -- miss --> D["Disk read<br/>real physical IO"]
    D --> PC
    R2 --> R1

一个页在两级缓存里各占一份，等于同一条数据买了两次内存。命中路径上的三种情况（Buffer Pool 命中、page cache 命中、真落盘）在你的监控里都只表现为「一次逻辑读」——这也是为什么只看命中率会误判。所以生产环境常见的取舍是 innodb_flush_method=O_DIRECT（绕开 page cache），代价是失去预读增益——这条取舍线在 ⑦ 讲刷盘时会展开，这里先记住「两层缓存，一份数据」。

站内《文件系统与磁盘 IO》里算过 page cache 与 fsync 的成本，同一个物理事实在数据库层的表现就是：每次 fsync 都是一次真实的等待，而 MySQL 一秒钟可能要做几千次。

3. 建立基线：把「快慢」变成数字

3.1 三个必测指标，外加一个分位数

指标 怎么算 为什么必须测
TPS / QPS Questions 增量 / 时间 吞吐上限，压测拐点的横轴
延迟 客户端视角（sysbench）+ 服务端视角（digest 平均耗时） 两者差距大 → 网络或排队，不是 SQL 本身
Buffer Pool 命中率 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests 决定物理读是不是瓶颈
P99 sysbench --percentile=99，或 events_statements_histogram_by_digest 均值会骗人，P99 才是用户体感

只报平均值是最常见的自欺：一条 ORDER BY 走错索引的查询，均值可能只涨 3ms，P99 已经翻了 20 倍，而用户投诉的永远是那 1%。

指标 健康线 超线说明什么
Buffer Pool 命中率 ≥ 99%（OLTP 读多场景） < 95% 时物理读主导，先加内存再谈索引
P99 / 均值 < 3~5 倍 超过说明有毛刺：锁等待、刷脏抖动、从库延迟
Threads_running 持续 < CPU 核数 高于核数说明在排队，CPU 不是瓶颈，等待才是

Threads_running 这条线值得单独解释：线程被唤醒就要做一次上下文切换，站内《进程与线程：从模型到调度》算过这笔账——切换一次是微秒级，但每秒几十万次就是几十毫秒的纯开销，而且缓存会失效。所以「线程数超过核数」不只是排队，还是在付费买切换。压测时把线程数一路加上去，直到 QPS 不再涨，那个点就是这台机器用切换成本换来的上限。
| 慢查询条数 / 分钟 | 与你的 SLA 对齐 | 与 SLA 对不上说明 long_query_time 设错了 |

3.3 深挖：基准测试和真实负载为什么永远对不上

sysbench 的 oltp_read_write 是均匀随机访问，而真实业务是幂律分布：1% 的热点商品扛着 80% 的流量。两者的差别会在三个地方暴露：

  1. Buffer Pool 命中率被高估：均匀访问会把整个表都焐热，真实访问只热那 1%，冷数据每次都要落盘；
  2. 锁冲突被低估：均匀访问几乎不撞同一行，热点行会撞成一串锁等待（⑥ 的主角）；
  3. P99 被美化：真实流量的毛刺来自大促、定时任务、批量导入，基准测试里没有这些。

所以基准测试的定位是测上限和做对照，不是预测生产。想靠近真实负载，至少要补三件事：按业务比例构造热点数据、把批量任务混进去、按真实读写比调 --oltp-read-only 之类的开关。这条线在 ⑫ 做容量规划时会正式展开——那里要用拐点数据回答「单机还能撑多久」，而拐点只能靠你自己的压测曲线给。

5. 总结

5.1 面试速答表

面试题 一句话答案
逻辑读和物理读的区别 逻辑读是访问了多少个 16KB 页（不管在不在内存），物理读是其中有多少页真去了磁盘；命中率只影响后者
Buffer Pool 命中率 99.9% 说明什么 只说明不用去磁盘，不说明没读多余数据；慢查询照样可以在全命中时发生
B+ 树三层能存多少行 每页行数 = 16384 / 行大小；三层约 1170 × 1170 × 每页行数，宽行 1KB 时约 2000 万
为什么本地测不出 IO 瓶颈 默认 Buffer Pool 128MB，百万行表全装得下，物理读恒为 0
MySQL 8.0 为什么没有查询缓存 8.0 已整体移除，query_cache% 变量不存在，SQL_NO_CACHE 是空操作
一次主键等值查询读几个页 等于 B+ 树高度：百万行小表 3 层左右，实测 4 次页请求
慢查询怎么定位 慢日志找 SQL → digest 排总耗时 → EXPLAIN ANALYZE 看实际行数 → 对照基线判断是读多了还是在等
为什么压测 QPS 和线上差很多 基准测试是均匀分布，生产是幂律热点；命中率、锁冲突、P99 三条都会被美化

5.4 实操建议

  1. 今天就起一台容器，把 --innodb-buffer-pool-size=1G 和 --long-query-time=0.5 带上，别用默认值做实验。
  2. 造两张表：一张 100 万行（递归 CTE），一张 1000 万行（sysbench），前者做快速验证，后者做 IO 相关实验。
  3. **建一个 mysql-lab.md**，把每次实验的「场景 / 数据量 / 参数 / SQL / 逻辑读 / 物理读 / 耗时 / 结论」记八列。三个月后这份文件比任何教程都值钱。
  4. 每次只改一个变量，并且前后都用同一条 SQL、同一份数据量；两个变量一起改，结论一定是错的。
  5. 把「是读多了还是在等」当成条件反射，遇到任何慢查询先问这一句，再决定去查索引还是查锁。
