IO 模型：阻塞、多路复用与零拷贝

Posted on 2026-08-12 In 操作系统 Word count in article: 6.2k Reading time ≈ 23 mins.

IO 模型决定「数据没就绪时，你的线程在干什么」：阻塞模型让线程干等，非阻塞模型让线程反复问，多路复用让内核一次告诉你「谁好了」，异步模型让内核干完再叫你。本文串起三件事：五种模型的取舍、epoll 为什么是标准答案、以及 Java 侧（BIO/NIO/Netty/虚拟线程）分别落在哪个模型上——并全程对照 Redis、nginx、Netty、Tomcat 这些你天天用的技术，看它们各自的线程模型怎么从本文的机制里长出来。

系列地图（操作系统）：① 进程与线程（执行单元与调度）→ ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（本文：等待数据的方式） → ⑤ Linux 资源排查实战（前四篇工具收拢）。本文是前四篇的汇合点：阻塞线程的成本来自 ① 的切换开销与 ② 的栈内存，零拷贝数据路径来自 ③ 的页缓存。

1.2 阻塞与非阻塞：read 的两种等待

阻塞 IO：read() 发出后线程挂起，数据就绪才返回——等待期间线程不占 CPU 但占「线程配额」，每个连接一个线程。

这套「线程 = 连接」的模型在 1999 年的 C10K 问题（万级并发连接）上撞了墙：1 万连接 = 1 万线程。1 万线程意味着什么？用前两篇的知识算账：每线程默认 1MB 栈（第 2 篇），虚拟内存承诺 10GB；1 万线程轮流上 CPU，上下文切换每秒几十万次（第 1 篇），光调度就吃掉大半 CPU。所以 C10K 的解法不是「更多线程」，而是「更少线程」——epoll 让一个线程等 1 万 fd（§2），Reactor 让几个线程服务 1 万连接（§3）。

回头看今天的技术，全是这套解法的后代：Redis 单线程事件循环扛 10 万 QPS、nginx 的 worker 数 = CPU 核数、Netty 默认两组 EventLoop 线程池。它们的线程数差异（Redis=1、nginx/Netty=核数级、BIO=连接数）就是「切换成本 vs 并发需求」的三档答案——这也是为什么面试问「Redis 为什么单线程还快」，标准答案的第一句永远是「它不做阻塞 IO，一个线程足以喂饱 CPU」。

非阻塞 IO：read() 立即返回——没数据时返回 EAGAIN，应用必须自己重试。避免了线程浪费，但把「等」的责任推给了应用，纯轮询是 CPU 灾难，实战中只作为多路复用的补充（数据没就绪时转去等 epoll）。

1.3 多路复用：一次等一堆

多路复用（I/O multiplexing）让一个线程把「等待」交给内核：注册一堆 fd，内核在任何一个就绪时唤醒线程。select/poll 是第一代实现，epoll 是 Linux 的工程答案（第 2 节展开）。Java NIO 的 Selector 就是对它的封装，Netty 底层就是它。

1.4 异步 IO：内核干完再叫你

异步 IO 是「提交请求就走，内核完成后再通知」：应用线程完全不参与等待。Linux 上的 io_uring（及早期 aio）是代表。注意区分：多路复用是「内核替你等」，异步是「内核替你干」——Netty 常被叫异步框架，其实是多路复用 + 回调，不是真异步。

1.5 动手验证：strace 看一次阻塞读

strace 输出里能看到 recvfrom(3, ... 阻塞住——poll/recvfrom 返回前的等待就是「阻塞」。把同样的观测换成 NIO 程序，会看到 epoll_wait 在循环——这就是两种模型在系统调用层的全部区别。

2. epoll：多路复用的工程答案

2.1 select/poll 的两个问题

维度 select poll epoll
fd 上限 1024（FD_SETSIZE） 无上限 无上限
每次调用 全量拷贝 fd 数组进内核 同左 只增删改（epoll_ctl）
查找就绪 O(n) 扫描全部 O(n) O(1) 取就绪链表
内核实现 线性扫描 线性扫描 红黑树 + 就绪链表

select 每次调用都要把几千个 fd 拷进内核、扫描一遍——连接多了以后，等待本身变成了性能瓶颈。epoll 把「注册」和「等待」拆开：注册一次，之后只等结果。

2.2 epoll 的三板斧

flowchart LR
    APP["App"] --> C1["epoll_create()<br/>create red-black tree"]
    C1 --> C2["epoll_ctl()<br/>register / modify / delete fd"]
    C2 --> C3["epoll_wait()<br/>sleep; wake on ready"]
    C3 --> READY["Ready list (linked list)"]
    KERN["Kernel: fd becomes readable"] --> READY
    READY --> C3

机制拆解：内核里一棵红黑树存所有注册的 fd（增删改 O(log n)），一个就绪链表存已经可读可写的 fd（由中断/唤醒路径挂入）；epoll_wait 只把就绪链表拷给用户——等待与规模无关，这就是 O(1) 的真相。

2.3 LT 与 ET：就绪事件报几次

模式 行为 适用
LT（水平触发，默认） fd 一直可读就反复报，不处理下次还报 简单，不容易漏事件
ET（边缘触发） 只报一次，必须一次读完，否则丢事件 高性能（配合非阻塞 + 读到 EAGAIN）

LT 与 ET 的取舍不是风格之争，是两套技术场景逼出来的设计——直接看两个最著名的使用者：

  • Redis 用 ET：单线程事件循环，所有连接的处理在一条线程里串行完成。LT 会反复上报同一个就绪事件、每次都唤醒循环白耗一次；而单线程意味着没有并发读竞争，「一次读到 EAGAIN」安全且必然——ET「必须读尽」的代价在单线程模型下不存在。这是 Redis 单线程 10 万 QPS 的细节之一。
  • Netty 默认 LT：EventLoop 池是多线程，且每次循环有读配额（默认 16MB）防止一个连接吃光 CPU——读不完的剩余数据回到队列、下次循环再读，此时 LT 的「反复上报」恰好保证事件不漏。所以 Netty 默认 LT 不是偷懒，是用重复唤醒换「不漏事件」的确定性。

生产后果：Netty 若手动改 ET，业务必须自己保证读尽——线上「偶发丢数据」事故的一大来源就是 ET 读循环少判了一次 EAGAIN；Redis 反而没有这个问题（单线程 + 读尽是写死的）。入门用 LT，性能临界再上 ET，前提是读循环写到 EAGAIN 为止。

3. Reactor：多路复用的线程模型

3.1 单线程不够，上主从

多路复用解决了「一个线程等一堆」，但业务处理也挤在这一个线程上：一个连接读数据慢，其他连接全被拖住。于是演进出 Reactor 系列：

    subgraph Workers["Worker reactors (IO + business)"]
        W1["Thread pool: epoll_wait<br/>on accepted fd set"]
        W2["Thread pool: epoll_wait<br/>on accepted fd set"]
    end
    B -->|"hand off accepted socket"| W1
    B -->|"hand off accepted socket"| W2
模型 线程数 适用
单 Reactor 单线程 1 线程全包 Redis（纯内存、CPU 密集单线程够用）
单 Reactor 多线程 1 个 accept + 业务线程池 入门架构
主从 Reactor 多线程 accept 线程 + IO 线程池 Netty 默认（boss + worker）

3.2 Netty 的 boss/worker 与 epoll

Netty 的 EventLoopGroup 就是 Reactor 的实现：bossGroup 只负责 accept（epoll_wait 在监听 fd 上），workerGroup 负责已连接 socket 的读写。三个关键设计细节，每个都能对应上本节讲的机制：

  1. EventLoop = 线程 + epoll_wait 循环：默认 worker 线程数 = CPU 核数 × 2。为什么不是越多越好？每个 EventLoop 是串行循环，线程数超过核数后，多出来的只是排队抢 CPU（第 1 篇的切换成本）——并发不涨，切换变多。
  2. 一个 channel 绑定一个 EventLoop，不轮询：同一连接的所有事件永远由同一个线程处理——天然免锁。这是「单线程串行」理念在 Netty 里的落地：Netty 内部几乎无锁，靠的就是这个绑定关系。
  3. IO 线程红线：业务代码绝不能在 IO 线程里做阻塞操作（数据库查询、Thread.sleep、锁等待）——那会让这个 EventLoop 的几百个连接一起等，等于把「一线程管 N 连接」退化成「N 个连接共用一根喉咙」。这是 Netty 面试第一题，也是线上 Netty 服务卡顿的第一大原因。

对照 Redis：Redis 是单 Reactor 单线程（纯内存操作，无阻塞 IO，一个线程够喂饱 CPU），Netty 是主从 Reactor 多线程（网络 IO + 业务混合，必须分线程）。Redis=1、Netty=核数×2、BIO=连接数——三档线程数就是切换成本与并发需求的三档答案，与 C10K 一节的结论完全一致。

3.3 虚拟线程：把阻塞写法映射回多路复用

JDK 21 虚拟线程的妙处：业务代码写回阻塞风格，JVM 底层自动把「阻塞」变成「让出载体线程去服务别人」——本质是 JVM 内部实现了一个多路复用 + 线程调度器：

sequenceDiagram
    participant VT as Virtual thread
    participant Sched as JVM scheduler
    participant Carrier as Carrier thread (OS thread)
    participant Kernel as Kernel (epoll)
    VT->>Sched: socket read (blocking syntax)
    Sched->>Carrier: park, free the carrier
    Kernel->>Sched: data ready (epoll wakes)
    Sched->>Carrier: unpark, resume VT

对比：Netty 是「异步写法 + 多路复用」，虚拟线程是「阻塞写法 + JVM 替你多路复用」。都能扛高并发，选型取决于团队更熟哪种风格——虚拟线程省掉了回调状态机，但线程调度与锁竞争的可控性不如显式 Reactor。

3.4 Tomcat 的线程模型：又一个 Reactor 变体（实战重点）

Tomcat 的 Connector（连接器）是独立于 Servlet 引擎的 IO 层，负责 socket 的建立与读写——从 8.5 起它默认跑在 NIO 上，是 Reactor 家族的第三个成员。但它的线程模型和 Netty 有本质区别，先看连接器演进：

Tomcat 版本 默认连接器 底层 说明
8.0 及以前 BIO（Java IO） 阻塞 IO，每连接一线程 8.5.0 起移除（官方迁移指南）
8.5 / 9 / 10 NIO 多路复用（Selector） 默认协议 HTTP/1.1
8.0+（可选） NIO2 JDK AIO 一直非默认，Linux 上无收益（§4.2）
8.5+（可选） APR/native 本地库 OpenSSL Tomcat 9 起并入 NIO 的 OpenSSL 形态
10.1.10+ / 11 虚拟线程执行器 JDK 21 虚拟线程 10.1 需显式配置，11 起默认

为什么 BIO 在 8.5 被移除：连接数一上来，「每连接一线程」的账就崩了（§1.2 的 C10K 算账），而 NIO 只需两个专职线程就能服务全部连接。Tomcat 的 NIO 线程模型是三段式：

flowchart TD
    CLIENT["Clients"] -->|"new connection"| ACC["Acceptor (x1)<br/>blocking accept() loop"]
    ACC -->|"register fd"| POLLER["Poller (Linux x1)<br/>epoll_wait loop, pollTime 2ms"]
    POLLER -->|"ready event as task"| POOL["Worker thread pool<br/>maxThreads=200 (default)"]
    POOL -->|"executes servlet request"| APP["Business logic"]

三个角色各干一件事（默认值均出自官方文档）：

  1. acceptor（默认 1 个线程）：死循环 accept()，收到新连接注册给 poller——对应 Netty 的 boss。
  2. poller（Linux 默认 1 个线程）：epoll_wait 循环（pollTime 默认 2000 微秒），就绪事件封装成任务丢进线程池——对应 Netty 的 worker 职责。
  3. worker 线程池（maxThreads 默认 200，minSpareThreads 默认 10）：真正执行 Servlet 业务。

poller 与 Netty worker 的分工差异，是两者线程模型的分水岭：

维度 Netty Tomcat
连接分配 连接绑定单个 EventLoop，同一连接永远同一线程 每次请求从池里临时抓线程，无绑定
线程数 boss 1 + worker 核数×2 acceptor 1 + poller 1 + 线程池 200
免锁依据 绑定 → 单线程串行 → 天然无锁 请求间无共享状态 → 无锁
适配场景 长连接、协议帧（RPC / 网关 / IM） 短请求、HTTP 语义（Servlet 每请求一线程模型）
线程打满后果 一个 EventLoop 卡住，几百连接一起等 池满，新请求排队或拒连

深挖：为什么 Tomcat 用「池」而 Netty 用「绑定」？ 机制差异是连接有没有状态——HTTP 请求之间无关联，Servlet 规范要求「一个请求在一个线程里从头执行到尾」，Tomcat 只需临时分配，用池；Netty 面向长连接协议开发，连接上挂着编解码器、半包缓冲等状态，必须钉死在一个线程上才能免锁，用绑定。生产后果：压测 1 万连接打进 Tomcat，真正干活的始终 ≤200 个线程，其余连接在排队——先等 worker 线程（池满），再等操作系统队列（acceptCount 默认 100，官方文档），队列也满就被内核直接拒连。所以压测里大量 Connection reset，第一嫌疑是 maxConnections（默认 8192，官方文档）和 acceptCount 这两个数，不是应用崩了。这正是一开始 C10K 结论的镜像：BIO 是线程=连接，Tomcat 是线程=并发请求（上限 200），连接再多也不长线程——收益是线程数可控，代价是请求排队。

另外，§3.3 的虚拟线程在 Tomcat 有官方落点：10.1.10+ 提供 StandardVirtualThreadExecutor（JDK 21+），把 worker 换成虚拟线程后「一请求一虚拟线程」，maxThreads 不再是硬天花板；Tomcat 11 起默认启用（发布公告）。「阻塞写法 + 容器帮你多路复用」在 web 容器里落了地。细节上，Tomcat poller 的 Selector 默认 LT 语义（事件没处理完下次继续报），和 Netty 的取向一致——防漏事件优先（§2.3）。

3.5 动手验证：连接数与线程数的对照

对照实验：BIO 服务器 1000 连接 = 1000+ 线程（pstree -p <pid> 数）；NIO/Netty 服务器 1000 连接 = 几个线程。线程数、连接数、fd 数三者的数量关系，就是 IO 模型在进程里的实锤。

再对 Tomcat（任意本地 Spring Boot 应用，内置就是 Tomcat）做一次线程解剖：

  • 预期观察点：Acceptor 1 个、Poller 1 个（Linux 默认）、exec-N 线程随并发增减且 ≤ maxThreads（默认 200）。
  • 判定标准：默认配置压测 Failed=0；把 server.tomcat.threads.max=50（Spring Boot 配置）改小重压，Failed 显著上升、exec 线程封顶在 50——线程池上限就是 Tomcat 吞吐的天花板，而连接数可以远大于 50。

4. Java 侧实践：BIO/NIO/AIO 怎么选

4.1 三种形态对照

形态 底层模型 典型类 连接并发 代码风格
BIO 阻塞 IO Socket / ServerSocket 线程 = 连接 最简单
NIO 多路复用（Selector + epoll） Selector / Channel / Buffer 线程 << 连接 回调/状态机
AIO 真异步（Windows IOCP；Linux 上退化） AsynchronousSocketChannel 线程 ≈ 0 回调
虚拟线程 + BIO 阻塞写法 + JVM 多路复用 普通 Socket + 虚拟线程池 线程 = 逻辑任务 阻塞风格，最简单

AIO 的坑在 4.2 深挖：Linux 上 JDK 的 AIO 底层还是多路复用模拟，没有真异步 IO 的收益，Netty 直接不用 AIO。

4.2 深挖：AIO 的真相——IOCP 与 Linux 的尴尬

AIO（异步 IO，JDK 7 的 NIO.2 异步通道）是「提交请求立即返回，内核完成后再回调」——回到 §1.4 的定义：多路复用是「内核替你等」，异步是「内核替你干」。这一节看「替你干」在三个平台上的三种真相：

实现 真异步？ 机制 现状
Windows IOCP 是 完成端口：内核完成 IO 后投递完成包，线程池取出回调 JDK AIO 在 Windows 的底层实现
Linux JDK AIO 否 epoll 多路复用 + JDK 内部线程池模拟 Netty 官方 wiki 明说不用 AIO
Linux io_uring 是 内核完成队列（SQ/CQ 环形队列，5.1+） Netty 有 incubator 移植，生产未普及

深挖：JDK 在 Linux 上的 AIO 是「多路复用 + 线程池」披了一层回调的壳（源码 UnixAsynchronousChannelProvider 走事件循环）。等于你自己写 NIO 再包回调，性能不比 NIO 好，还把线程的控制权交了出去——这正是 Netty 不用 AIO 的理由：Linux 上无性能收益（官方 wiki），且 AIO 回调跑在 JDK 内部线程池上，和 Netty「回调必须绑定 EventLoop」的线程模型冲突。IOCP 是真异步，因为 Windows 内核为此设计了完整的完成端口机制；Linux 内核直到 5.1 才有 io_uring 提供真异步，但它和 JDK AIO 的 API 不兼容，Java 生态还在追赶（netty-incubator-transport-native-io_uring）。

生产结论：Linux 上的 Java 高并发网络服务，多路复用（NIO / Netty）仍是主线；AIO 的价值在 Windows 场景和文件 IO（AsynchronousFileChannel），不在 Linux 网络 IO——这也是 Tomcat 的 NIO2 连接器始终非默认（§3.4 表）的底层原因。

4.4 动手验证：复现 Too many open files

这个报错的完整链路：连接数 × 每连接 fd（socket + 管道）> nofile → accept 失败 → 服务半残。**生产上所有高并发进程的启动脚本里都要有 ulimit -n 65535 或 systemd 的 LimitNOFILE**——漏了它，压测第一波流量就能干崩服务。

5.1 面试速答表

面试题 一句话答案
BIO/NIO/AIO 区别？ BIO 阻塞、一线程一连接；NIO 多路复用、一线程多连接；AIO 提交后回调（Linux JDK 上是模拟）

文件系统与磁盘 IO

Posted on 2026-08-12 In 操作系统 Word count in article: 3.7k Reading time ≈ 13 mins.

文件系统（file system）是内核在磁盘上建立的「文件名 → 字节数据」组织层：你写的代码只认路径和读写接口，实际数据以块为单位躺在磁盘上，由文件系统负责映射、缓存和落盘。本文回答四个问题：文件在磁盘上怎么组织、读写为什么先过内存缓存、磁盘 IO 的延迟从哪来、Java 怎么和这几层正确打交道——并对照 MySQL/ES/Kafka/RocketMQ 的落盘策略，看「fsync 频率」「顺序写」「零拷贝」这些参数和架构决策怎么从本节机制里长出来。

系列地图（操作系统）：① 进程与线程（执行单元与调度）→ ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（本文：数据落盘） → ④ IO 模型（等待数据的方式）→ ⑤ Linux 资源排查实战（工具收拢）。本文的页缓存是 ② 的页表指向的内存区，本文的 syscall/fsync 成本来自 ① 的用户态与内核态切换。

1. 文件系统：从文件名到字节

1.1 inode：文件的「户口本」

inode（index node）是文件的元数据记录，存权限、大小、时间戳、数据块位置，但不存文件名。文件名存在目录项（dentry）里——目录是一个「文件名 → inode 编号」的映射表。

概念 是什么 存在哪
inode 文件的元数据（大小/权限/块位置） 磁盘 inode 区 + 内存
dentry 文件名 → inode 的映射项 内存（缓存）
数据块 文件实际内容（ext4 默认 4KB 一块） 磁盘数据区
硬链接 两个文件名指向同一 inode 目录表
软链接 存目标路径的文件（inode 内容是路径） 目录表 + 数据块

由此推出两个冷知识：硬链接不能跨文件系统（inode 编号只在同一文件系统内有效）；移动文件在同一文件系统内只是改目录项（所以 mv 秒完成，跨盘才是复制+删除）。

1.2 路径解析：一次 ls 的完整旅程

flowchart TD
    CMD["ls /data/logs/app.log"] --> ROOT["Look up / (root dentry)"]
    ROOT --> D1["Resolve data -> dentry<br/>(hash lookup in dir cache)"]
    D1 --> D2["Resolve logs -> dentry"]
    D2 --> D3["Resolve app.log -> dentry"]
    D3 --> INODE["Get inode: perms / size / block list"]
    INODE --> DATA{"Blocks cached in page cache?"}
    DATA -- Yes --> SHOW["Read from RAM, done"]
    DATA -- No --> DISK["Read blocks from disk into page cache"]
    DISK --> SHOW

/data/logs/app.log 要逐级解析：根 → data → logs → app.log，每级都是「查目录项 → 找 inode」。所以路径越深、目录项缓存越冷，一次访问越慢——应用侧经验：热点文件放浅路径，冷启动时 find/遍历大目录会打爆目录缓存。

2. 页缓存：文件读写的加速层

2.1 读路径：一切先过页缓存

磁盘读不会直接进用户程序——内核先把数据读进页缓存（page cache），再从页缓存拷给用户。第二次读同一文件就是纯内存操作（第 2 篇的 dd 实验已经验证过）。

2.2 写路径：先缓存，异步落盘

写也不直接落盘：写操作先进页缓存标为脏页（dirty），由内核回写线程异步刷盘。这是「write 返回了但数据还没到磁盘」的根本原因——也是 MySQL/ES 这类要保数据的系统必须自己调 fsync 的原因。

flowchart LR
    APP["App write()"] --> PC["Mark page dirty in page cache<br/>(write returns fast)"]
    PC --> WB{"writeback timer<br/>or dirty ratio exceeded?"}
    WB -- No --> PC
    WB -- Yes --> FLUSH["Flush dirty pages to disk"]
    FLUSH --> PC
    APP -. "fsync() forces now" .-> FLUSH

脏页刷盘由两个条件触发：定时（dirty_expire_centisecs，默认 30 秒）和比例（脏页占内存 dirty_ratio，默认 20%）。于是有个经典故障模式：写入量大时脏页积压到阈值，一次性大批量回写，磁盘瞬时打满、应用瞬间卡顿（回写风暴）。

2.3 三种 IO 路径：缓冲、直接、mmap

方式 机制 特点 适用
缓冲 IO（默认） 读写过页缓存 快（缓存命中免磁盘），写不保证落盘 通用场景
直接 IO（O_DIRECT） 绕过页缓存直达磁盘 可控，每次都要真实 IO 数据库自己管理缓存时
mmap 页缓存映射进用户空间 免 read/write syscall，直接当内存用 大文件随机读、共享内存

MySQL 的 innodb_flush_method=O_DIRECT、ES 的 mmapfs，都是在告诉内核「缓存我自己管，别给我套一层」。

2.4 动手验证：看到脏页与回写

判定标准：Dirty 长期接近 dirty_ratio 阈值 = 写入速率超过刷盘能力，回写风暴随时触发；生产上给日志/数据盘调小 vm.dirty_ratio（如 5%），把大回写拆成小批，换平滑性。

3. 磁盘 IO：延迟从哪来

3.1 延迟量级记忆法

介质 访问延迟 记忆点
内存 100ns 基线
SSD（NVMe） 0.1ms 比内存慢 1000 倍
HDD（机械盘） 10ms 寻道 + 旋转，比 SSD 慢 100 倍
跨机房网络 10-100ms 比磁盘还慢

机械盘慢在寻道（磁头移动到目标磁道，物理动作），所以「随机 IO」对 HDD 是灾难、对 SSD 只是小事（SSD 没有寻道，但随机写会放大写放大，见 3.3）。IO 优化第一原则：把随机 IO 变成顺序 IO——Kafka/MySQL redo log 全部是顺序追加写，就是这个原因。

3.2 IO 调度器：磁盘前的最后一道队列

内核把应用的 IO 请求排序后再交给磁盘：SSD/NVMe 时代基本用 none（直通，乱序无所谓）；机械盘时代用 mq-deadline/bfq（合并相邻请求、保证延迟上限）。

3.3 顺序 vs 随机：为什么顺序写快

场景 HDD SSD
顺序写 无寻道，接近带宽上限 快，且无写放大
随机写 每次寻道 10ms，TPS 个位数 每次覆盖要「读-改-写」整块（写放大），寿命受损

所以日志、消息队列、数据库 redo log 全部顺序追加；而随机读多的场景靠缓存（页缓存、Redis）而不是靠盘。Kafka 号称「快」，本质是顺序写 + 页缓存 + 零拷贝三件套。

4.1 文件写盘的可靠性层次

A 和 B 耗时差两个数量级，这就是为什么 MySQL/ES 不会每条日志都 fsync：MySQL 用 innodb_flush_log_at_trx_commit 权衡（=1 每次提交刷盘、=2 只刷 OS 缓存），ES 的 translog 同理——性能与可靠性的取舍点，就是 fsync 频率。

深挖：WAL——把随机写变成顺序写。MySQL（redo log + binlog）、ES（translog）、RocketMQ（commitlog）的落盘模式是同一条：先顺序追加日志并 fsync，再异步刷数据页。为什么？数据页是随机 IO（散在磁盘各处），日志是顺序追加（尾部写）——先保证「日志在盘上」再用它兜底重建数据，于是随机写被拆成「高频小顺序写 + 低频异步随机写」，这是「顺序优于随机」（§3.3）在存储架构上的直接应用：

inode 和文件名的关系？ 文件名在目录项里，inode 存元数据；硬链接是多个名字指向同一 inode
write 返回就落盘了吗？ 没有——先进页缓存标脏页，异步回写；fsync 才强制落盘
缓冲 IO 和直接 IO 的区别？ 缓冲 IO 过页缓存（快、断电有风险）；O_DIRECT 绕过缓存直达磁盘，适合自己管缓存的应用
为什么数据库要 fsync？ 数据可靠性要求断电不丢；fsync 频率是性能与可靠性的取舍点
什么是零拷贝？ sendfile 在内核态把文件直接发到 socket，用户空间不参与拷贝；Java 用 FileChannel.transferTo
为什么 Kafka 这么快？ 顺序写 + 页缓存 + 零拷贝三件套，全是内核机制的直接受益者
磁盘满但建不了文件？ 大概率 inode 耗尽（df -i 100%），清小文件而不是扩盘

秒杀系统设计：从方法论到落地

Posted on 2026-08-12 In 系统设计 Word count in article: 5.3k Reading time ≈ 19 mins.

秒杀是系统设计面试里「一题考全」的题目：限流、缓存、消息队列、分布式锁、分库分表、降级兜底，六个知识点在一道题里全部串联。 它考的不是「背方案」，而是「能不能把『瞬间高并发读 + 有限资源并发写』拆成可讨论的设计决策」——这正是 《系统设计方法论》 的解题框架在真实题目上的完整落地。本文按「需求拆解 → 整体架构 → 逐层设计 → 全链路走查 → 面试应答」组织，读完你能把一个秒杀方案从「听过」变成「能讲」。

联动：本文复用 Redis 深度解析（原子操作/Lua/缓存）、MySQL 高可用与分库分表实战（订单表拆分）、RocketMQ 原理与实践（削峰）、设计模式（策略/责任链/外观）的知识点，把它们串成一张系统级方案。

1. 题目拆解：秒杀考的不是高并发，是「并发写」

1.1 需求澄清：面试从「问清数字」开始

面试官抛出「设计一个秒杀系统」后，第一件事不是画架构，是澄清需求——这是方法论篇第 1 节的「问题拆解」，也是区分「背方案」和「会设计」的第一步：

澄清项 示例答案 为什么必须问
规模 100 万用户抢 1 万件商品，峰值 10 万 QPS 决定要不要上 MQ、要不要分库
商品数量 1 个 SKU 还是多个 决定热点是否集中
一致性要求 库存不能超卖，订单不能重复 决定扣减方案
时间窗口 10 分钟还是 1 分钟 决定削峰策略
读多还是写多 查商品 100 万次，下单 10 万次 读可缓存，写是瓶颈

一句话结论：秒杀 = 海量读（可缓存解决）+ 集中写（必须原子化）+ 瞬时高峰（必须削峰）。 读是「工程问题」（缓存扛住即可），写是「正确性问题」（超卖就是 bug），峰是「容量问题」（QPS 超过阈值怎么办）。

1.2 瓶颈分析：先找唯一的并发写热点

秒杀系统的数据流只有两类：

2.1 五层架构总览

每一层只做一件事，任何一层被打爆都不影响其他层：网关限流保证应用不被打爆，Redis 扣减保证库存准确，MQ 排队保证 DB 不被瞬时打爆。这就是方法论篇「高可用设计：用冗余换可靠性」在秒杀场景的实例化——每层都有兜底，任何单点故障只是「少卖」而不是「卖错」。

2.2 与普通下单的区别：读路径与写路径分离

环节 普通下单 秒杀下单
商品信息读取 每次查 DB（或缓存） 缓存 + 静态页，读路径 99% 不到应用层
库存检查 查 DB 行 Redis 原子预扣
下单 同步写 DB MQ 异步写，用户先看到「排队中」
失败处理 直接返回失败 排队后异步通知成功/失败

因果链：普通下单是「一次事务」——检查库存、扣减、下单在一个事务里保证一致性；秒杀把这个事务拆成了「先占坑（Redis 预扣）→ 后处理（异步落库）」两段，用「最终一致性」换「扛住峰值」。面试必被追问：「预扣了库存但后面落库失败怎么办？」——答案是对账：定时任务比对 Redis 预扣数与 DB 订单数，差额回补库存。 这是「两段式设计」的代价，必须主动说出来。

3. 限流：把流量挡在应用之外

3.1 四种限流算法对比

算法 原理 优点 缺点 适用
固定窗口 每秒计数，超限拒绝 实现简单 窗口边界突发（59 秒和 01 秒各 100 次可绕过） 粗略限流
滑动窗口 记录每个请求时间戳，统计窗口内请求数 消除边界问题 内存开销随 QPS 增 网关
漏桶 请求进桶，固定速率流出 流量绝对平滑 突发流量被削平，延迟增大 保护下游
令牌桶 令牌按速率生成，请求取令牌 允许一定突发（桶容量） 桶容量需调 秒杀（允许瞬间放量）

秒杀选令牌桶：秒杀的特点是「开闸瞬间所有用户同时涌来」——固定窗口和漏桶会直接杀掉大部分请求，令牌桶允许桶内突发（比如桶容量 1 万），让「前 1 万个请求快速通过，后续平滑」——既保护系统，又保证有能力的用户进得来。

3.2 网关限流 + 应用限流双层

3.3 动手验证：手写令牌桶

观察点：容量 10、速率 5 的桶——瞬间来 20 个请求，前 10 个通过，之后按每秒 5 个放行。判定标准：跑出「突发 10 + 匀速 5/s」的通过曲线，即理解令牌桶与漏桶的本质区别（允许突发 vs 强制平滑）。

3.4 深挖：限流与降级的联动

限流是「预先划定的容量」，降级是「故障时的保底」——两者必须联动：当限流指标（拒绝率）超过阈值，说明系统真被打到了，触发降级——关闭非核心功能（购物车、推荐位），把资源全部让给下单链路。因果链：秒杀开场瞬间，任何非核心请求都是对核心链路的伤害，降级是「主动选择服务哪些流量」——方法论篇 §5「熔断与降级：故障下的体验保障」在秒杀里是必选项而不是可选项。

4. 防超卖：库存扣减的原子性

4.1 超卖的本质：检查与扣减不是原子操作

超卖的根因永远是同一个：「先查库存 >0，再扣减」这两步之间，另一个请求插队了。

sequenceDiagram
    participant A as 请求 A
    participant B as 请求 B
    participant S as 库存
    A->>S: 查询库存 = 1
    B->>S: 查询库存 = 1
    A->>S: 扣减 → 0
    B->>S: 扣减 → -1  ← 超卖！

三种方案对比：

方案 做法 问题
DB 悲观锁 SELECT ... FOR UPDATE 锁行导致 QPS 上不去（所有扣减串行化）
DB 乐观锁 UPDATE stock SET n=n-1 WHERE n>0 每次更新一次 DB 往返，10 万 QPS 打不穿
Redis + Lua Lua 脚本内原子检查+扣减 单线程执行天然原子，10 万 QPS 无压力

Redis 单线程执行命令是原子性的核心——Lua 脚本在 Redis 里整段执行，中间不可能被其他命令插队，等于把「检查 + 扣减」变成了一个不可分割的操作。这就是秒杀选 Redis 扣库存的根本原因：不是 Redis 快，是 Redis 单线程给了我们免费的原子性。

4.3 防重：同一用户不能下两单

扣库存之外，还要防「一个用户抢到两件」：

  • Redis SETNX 用户级防重：SETNX order:uid:{userId} 1，抢到锁的用户才能进入下单流程，流程结束 DEL；
  • DB 唯一索引兜底：user_id + goods_id 建唯一索引——即使 Redis 层被绕过，DB 层也能挡掉重复单。两层防重：Redis 挡 99.9%，唯一索引兜 0.1%，这就是「多层防御」的典型用法。

4.4 动手验证：并发扣库存压测

观察点：任何一次并发下出现负数，说明扣减代码不是原子的。判定标准：库存恰好归零 + 成功次数恰好等于初始库存——这就是「不超卖」的可验证定义。

5. 削峰：MQ 排队，把瞬时流量拉平

5.1 为什么要 MQ：DB 的写入能力是硬上限

环节 峰值吞吐 说明
Redis 扣库存 10 万 QPS 内存操作，单线程也扛得住
MQ 写入 数万 TPS 顺序写磁盘，远高于 DB 随机写
MySQL 订单插入 数千 TPS 单库 B+ 树随机写是硬瓶颈

因果链：Redis 扣库存成功后，如果把「生成订单」同步做（写 MySQL），DB 会被瞬时 10 万 QPS 打爆——所以扣完库存只发一条 MQ 消息就返回「排队中」，订单消费者按自己能力（数千 TPS）慢慢落库。用户感知从「下单成功」变成「排队中」，这是秒杀体验设计的核心取舍：把瞬时负载平摊到秒级甚至分钟级。

5.2 消息丢失与重复：削峰方案的必答延伸

面试官必追：「MQ 消息丢了怎么办？重复消费怎么办？」——削峰方案的价值建立在 MQ 可靠性的三条承诺上：

风险 方案 机制出处
生产端丢失 同步发送 + 重试 RocketMQ 同步发送
MQ 端丢失 集群 + 主从同步 + 刷盘策略 RocketMQ 高可用篇
消费端重复 幂等（唯一索引 + 状态机） §4.3 的 DB 唯一索引兜底

因果链：防超卖和防重复是同一件事的两面——扣库存用 Redis 原子保证「卖不多」，落库用唯一索引保证「不重复」。面试答到这里，方案就从「背出来的」变成「能闭环的」：每个环节的失败都有对策，这正是方法论「可讨论的设计决策」的要求。

5.3 排队 vs 拒绝：什么时候削峰，什么时候直接拒

策略 做法 代价 适用
削峰（MQ 排队） 超量请求进队列，异步处理 用户体验变差（等待） 秒杀（1 万件商品值得排队）
直接拒绝 超量请求返回失败 简单直接 限量活动（100 件商品，排队没意义）

判断标准：排队队列的长度要可控——1 万件商品配 10 万请求，排队有意义；100 件商品配 10 万请求，排队只会让 99.99% 的用户等一个注定失败的结果，直接拒绝更合理。设计决策没有标准答案，只有「代价与收益匹配」。

6. 缓存与热点：让 99% 的读请求到不了应用

6.1 缓存层级：静态页 → CDN → Redis

flowchart LR
    U["用户"] --> S["静态页（商品详情纯静态化）<br/>请求不到后端"]
    U --> C["CDN（边缘节点）"]
    C --> R["Redis（商品信息缓存）"]
    R --> A["应用"]
  • 商品详情页秒杀前完全静态化，部署到 CDN——这部分流量和你的后端毫无关系；
  • 秒杀页面的动态数据（库存数字、倒计时）走 Redis；
  • 应用层查询全部命中缓存，DB 只承担「订单落库」。

6.2 热点 key：缓存击穿的防护

秒杀就 1 个 SKU，**所有用户查同一个 key sku:1001**——这就是热点 key 的极端形态：

风险 场景 方案
击穿 缓存过期瞬间，请求全打 DB 互斥锁重建缓存（只让一个线程回源）
打爆 单 key 承载全部读流量 热点 key 复制（sku:1001:0~`sku:1001:9` 十个副本，请求分散）
雪崩 大量 key 同时过期 过期时间加随机值

因果链：秒杀是「单一热点」的最坏情况——所有读流量打同一个 key，这个 key 就是整个系统的单点。热点 key 复制（读副本）把单 key 变 10 个 key，Redis 集群里分散到不同分片，每个分片只扛 1/10 流量——Redis 深度解析里 HotKey 治理在秒杀场景是「开闸瞬间」的生存问题，不是优化问题。

6.3 库存数字的展示与真实扣减分离

展示层库存（Redis 直接读，可 1 秒更新一次）≠ 扣减库存（Lua 原子操作）——用户看到「还有 300 件」只是展示数字，实际扣减永远走 Lua。两个 key 分离，展示挂了不影响扣减，这是「读路径与写路径分离」的第二个实例（第一个是 §2.2）。

    A->>R: 6. Lua 原子扣库存
    R-->>A: 7. 成功
    A->>M: 8. 发下单消息
    A-->>U: 9. 返回「排队中」
    M->>D: 10. 消费订单消息
    D->>DB: 11. 插入订单（唯一索引兜底）
    D->>DB: 12. 成功后回写状态

每一步失败的兜底：3 失败 → 用户看到「手慢了」（快速失败，不占资源）；5 失败 → 「已抢过」；7 失败 → 「已售罄」；11 失败（重复订单被唯一索引拦）→ 静默跳过并回补 Redis 库存。

7.2 对账：预扣与落库的差额回收

这是「先占坑后处理」方案的安全网——§2.2 的承诺在这里兑现：最终一致性不是靠运气，是靠对账任务兜底。

内存管理：虚拟内存与分页

Posted on 2026-08-12 In 操作系统 Word count in article: 3.9k Reading time ≈ 14 mins.

虚拟内存（virtual memory）是操作系统给每个进程提供的「独立、连续、看似无限」的内存假象：进程以为自己独占整个地址空间，实际数据散落在物理内存各页上，由内核统一映射。它是进程隔离的地基，也是 JVM 内存问题（堆外泄漏、容器被杀、OOM）的总根源。本文讲三件事：地址空间怎么组织、虚拟地址怎么翻译成物理地址、内存不够了会发生什么——并对照 Redis RDB 快照、大页、容器内存限制这些真实技术，看它们怎么建立在本节的机制上。

系列地图（操作系统）：① 进程与线程（执行单元与调度）→ ② 内存管理（本文：地址空间与物理内存） → ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（等待数据的方式）→ ⑤ Linux 资源排查实战（工具收拢）。本文的页缓存是 ③ 的读写地基（页表项指向它），本文的缺页与换页是 ④ 之前「一切等待」的物理背景。

1. 虚拟内存：给每个进程一座孤岛

1.1 为什么需要虚拟内存

没有虚拟内存的时代（实模式），程序直接访问物理地址：两个程序必须约好各占哪段，一个野指针就能改掉别的程序的数据。虚拟内存一次性解决三件事：

问题 虚拟内存的解法
隔离 每个进程有自己的地址空间，A 进程地址 0x1000 和 B 进程地址 0x1000 是两页不同的物理内存
连续性 物理内存碎片化没关系，虚拟地址连续、映射到哪都行
按需加载 程序 100MB，先只映射用到的几页——未访问的代码和数据可以一直留在磁盘上

地址空间是「地址的集合」，不是「内存的集合」——进程里看到的一大片地址，大部分没有对应的物理页，一访问就缺页（第 2 节讲）。

1.2 地址空间布局

x86-64 下用户空间是低位的 128TB（内核占高 128TB）。从低到高：

flowchart TD
    subgraph Low["Low address (0x0)"]
        TEXT["Text (code) segment"]
        DATA["Data / BSS<br/>initialized & uninitialized globals"]
        HEAP["Heap<br/>grows upward (brk / mmap)"]
    end
    subgraph High["High address (0x7fff...)"]
        STACK["Stack<br/>grows downward"]
        ENV["Environment & argv<br/>+ vdso"]
    end
    HEAP --- GAP["Huge unmapped gap<br/>(accessed = segfault)"]

要点：堆向上长、栈向下长，中间是巨大的未映射空洞——new 的对象在堆，局部变量和调用帧在栈，两者相撞叫栈溢出或堆溢出。地址空间底部有随机化（ASLR），每次启动程序布局都变，防攻击者猜地址。

看一个 -Xmx2g 的 Java 进程，pmap 输出的规律：

对照 ps 的 VSZ 和 RSS：-Xmx2g 的进程 VSZ 常有 4-5GB（预留的地址空间），RSS 才是真占用的物理内存——内存监控看 RSS，别被 VSZ 吓到；反之容器内存限制看的是 RSS，-Xmx 设太大不代表 RSS 一定大，但 RSS 会超过 -Xmx（堆外还有东西，第 4 节展开）。

2. 分页与地址转换

2.1 页表：地址翻译的字典

物理内存按 4KB 一页切成页帧；每个进程维护一张页表，记录「虚拟页号 → 物理页帧号」。进程切换时换页表——这就是第 1 篇说的「进程切换比线程切换贵」的根源。

问题：进程地址空间 128TB，一张扁平页表要 128TB/4KB = 340 亿条记录，装不下。解法是多级页表（x86-64 四级）：只有用到的地址区间才在低层分配表项，未映射区间不占内存。

层级 名称 每项覆盖
L4 PML4（页目录指针的指针） 512GB
L3 PDPT（页目录指针） 1GB
L2 PD（页目录） 2MB
L1 PT（页表） 4KB

一个 4KB 页的转换要查 4 级表（4 次内存访问），所以必须有缓存——TLB（Translation Lookaside Buffer），CPU 内置的页表缓存。命中就免掉 4 次访问，未命中才走完整路径。

深挖：大页（HugePages）就是从页表结构里长出来的优化。页越大，页表条目越少、TLB 命中率越高：2MB 大页把 4KB 页的条目数缩 512 倍。ES、MySQL 这类内存大户在生产上常开内核 vm.nr_hugepages + JVM 的 -XX:+UseLargePages——代价是内存按大页粒度预留、分配更粗放，配置错反而浪费。理解了页表与 TLB，这个参数的来龙去脉就清楚了。

2.2 转换流程与缺页

flowchart TD
    CPU["CPU issues virtual address"] --> TLB{"TLB hit?"}
    TLB -- Yes --> PHYS["Physical address, done"]
    TLB -- No --> WALK["Walk 4-level page table (4 memory accesses)"]
    WALK --> PRESENT{"PTE present?"}
    PRESENT -- Yes --> CACHE["Fill TLB, done"]
    PRESENT -- No --> FAULT["Page fault (trap to kernel)"]
    FAULT --> MINOR{"Page already in RAM?<br/>(page cache / lazy alloc / COW)"}
    MINOR -- Yes --> FIX["Build PTE, return to user<br/>minor fault (~1µs)"]
    MINOR -- No --> IO["Read page from disk (swap / file)<br/>major fault (ms level)"]
    IO --> FIX

缺页分两种，代价差三个数量级：

类型 触发 代价 常见来源
minor fault 页已在物理内存，只是页表项没建 微秒级 JVM 启动、首次 new 对象、fork 写时拷贝
major fault 页要从磁盘读 毫秒级 冷数据首次访问、swap 换回、内存映射文件

JVM 启动慢的本质是海量 minor fault：-Xms 设小、启动后再扩堆，每次扩容都要建页表项；生产建议 -Xms = -Xmx，一次到位，既省 minor fault 也避免堆抖动（老生常谈，根因在这里）。

深挖：写时拷贝（COW）与 Redis RDB 快照。fork() 不复制父进程的内存，而是把页表项标为只读、父子共享；子进程一写才复制那一页（触发 minor fault）。Redis 的 RDB 持久化就是这么拍的：fork 出子进程，子进程把共享内存顺序写进文件，主进程照常服务——写时复制保证子进程看到的是「fork 那一刻」的一致数据。所以 RDB 既不阻塞服务、又能拍到一致快照，靠的全是 COW。

代价与坑（大实例 Redis 的必修课）：

现象 根因 处理
fork 瞬间卡顿几十到几百 ms fork 要复制整个页表（条目数 = 内存/4KB） 观察 INFO persistence 的 last_fork_usec
快照期间内存翻倍风险 写多时 COW 复制页多 内存至少留出数据集 2 倍的余量
频繁 RDB 拖垮服务 每次 fork 的页表复制 + COW 高峰 大实例降 RDB 频率，换主从全量同步

Java 侧同样受 COW 影响：-Xms = -Xmx 的另一层收益是减少启动后的堆扩缩——每次扩堆重建页表、GC 频繁触碰页，都是 minor fault 的代价。

2.3 页面置换：内存不够了踢谁出去

物理页不够时，要把一些页换出（写回磁盘或丢弃）。置换算法：

算法 思路 问题
FIFO 先进来先踢 可能踢掉正热的页（Belady 异常）
LRU 最久没用的先踢 理想但不现实（每页维护访问时间成本太高）
时钟/第二次机会 FIFO + 访问位，被访问过的页放行一轮 工程上的近似 LRU

Linux 用双链表近似 LRU（active/inactive 两条 LRU 链表，页在链表间升降），配合内存水位线（/proc/sys/vm/watermark 相关）决定何时开始回收。Java 视角不用记细节，记住结论：页面置换对应用不可见，但「频繁换页」是性能灾难（见 2.4 的观测方法）。

3. 内存分配与回收

3.1 malloc 的两个来源：brk 与 mmap

进程向内核要内存只有两条路：

途径 机制 适用
brk 移动堆顶指针，扩展/收缩堆 小分配（malloc 默认），快
mmap（匿名） 直接映射一段新地址空间 大分配（>128KB），用完立刻可释放

malloc 的策略：小块走 brk 堆（复用、碎片由 malloc 自己管），大块走 mmap（还给内核干脆）。JVM 的堆就是一次大匿名 mmap 拿下来的，-Xms/-Xmx 控制这段区域。

3.2 内核侧：伙伴系统与 slab

内核把物理页切块管理：伙伴系统按 2 的幂次维护空闲页（要 3 页给 4 页、要 5 页给 8 页），slab 为频繁创建的小对象（task_struct、inode）建专属缓存。这两层对应用透明，但解释了「内存碎片」和「内核内存占用」的来源——容器里 free 的 used 包含了内核 slab，排查内存高时可 cat /proc/meminfo | grep Slab。

3.3 回收与 swap

物理内存吃紧时按顺序回收：页缓存（干净页直接丢，脏页先回写）→ 匿名页换出到 swap。注意 swap 是「匿名页（堆、栈）的磁盘后备」，页缓存不需要 swap——free -h 里 Swap 列全 0 只说明没换出过匿名页。

容器时代（K8s）的共识是节点禁用 swap：换页延迟毫秒级，对服务不可接受，K8s 也默认要求 swapoff。Java 应用在 swap 环境下 GC 停顿会被放大（GC 要访问的页被换出去了）。

3.4 动手验证：free 的正确读法

free -h 输出解读：used 里含 Slab 等内核占用；buff/cache 是页缓存（可随时丢弃，不是泄漏，别因为 cache 高就慌）；看真实可用内存用 available 列（缓存可回收部分算进去）。线上「内存不足」告警，先看 available 而不是 free。

4. OOM：从 JVM 到内核

4.1 JVM 内存全景：堆只是冰山一角

-Xmx 只是 JVM 堆上限，进程的 RSS 由五块组成：

组成 控制参数 典型值
堆 -Xmx 按业务
Metaspace -XX:MaxMetaspaceSize 默认无上限，类太多会涨到几百 MB
线程栈 -Xss（默认 1MB 虚拟） 1000 线程 ≈ 1GB 虚拟内存
直接内存 -XX:MaxDirectMemorySize（默认 = 堆大小） Netty/BufferPool 场景
JIT code cache + GC 结构 -XX:ReservedCodeCacheSize 等 200MB 上下

所以 -Xmx1g 的进程 RSS 到 1.5g 是正常的；容器里只设 -Xmx 不管堆外，就是「被 OOM Killer 杀」的经典剧本——正确姿势是 -XX:MaxRAMPercentage=75 之类按容器内存百分比给堆。

4.2 判定链路：谁杀了我的进程

flowchart TD
    ALLOC["App requests memory (malloc / mmap)"] --> OVER{"overcommit allowed?"}
    OVER -- No --> FAIL["malloc returns NULL<br/>(rare, overcommit_memory=2)"]
    OVER -- Yes --> CG{"cgroup memory limit hit?"}
    CG -- Yes --> RECLAIM{"Reclaim succeeded?<br/>(cache drop / swap)"}
    RECLAIM -- No --> KILL["OOM Killer picks victim by oom_score<br/>and SIGKILLs it"]

三层机制：overcommit（内核敢不敢超量承诺虚拟内存，Linux 默认启发式）→ cgroup 限制（容器内存上限，K8s limits.memory）→ OOM Killer（真不够时按 oom_score 选杀，占内存越大、存活越短、oom_score_adj 越高的先死——容器里的进程 oom_score_adj 会被调高，这就是「容器里 JVM 先被杀」的原因之一）。

为什么用多级页表？ 扁平页表 128TB 空间要 340 亿条记录；多级只给用到的区间建表项
TLB 是什么？ 页表项的 CPU 缓存，命中免掉 4 次内存访问
minor/major fault 区别？ minor 页已在内存只差建表项（微秒级）；major 要从磁盘读（毫秒级）
JVM 为什么内存监控要盯 RSS 不是 VSZ？ VSZ 是地址空间承诺，RSS 才是物理驻留；堆外（Metaspace/直接内存/线程栈）都会撑大 RSS
容器里 JVM 为什么老被 OOM 杀？ 只设 -Xmx 不管堆外 + 容器进程 oom_score_adj 高；用 -XX:MaxRAMPercentage 按容器内存给堆

工具 看什么 对应本节概念

四个收获：地址空间是承诺、RSS 是现实；缺页是「懒」的代价（minor 微秒、major 毫秒）；内存回收的顺序是页缓存 → swap → 杀进程；JVM 的 OOM 从来不只是 -Xmx 的事。

实操建议：

  1. 容器里 JVM 一律 -XX:MaxRAMPercentage=75 + -Xms=-Xmx，先保住别被杀。
  2. 进程被杀先查 dmesg，别猜——是 OOM Killer 还是健康检查，处理方向完全不同。
  3. 用 jcmd <pid> VM.native_memory summary（需 -XX:NativeMemoryTracking=summary）定期对账堆外内存，直接内存泄漏能在 RSS 崩之前发现。
