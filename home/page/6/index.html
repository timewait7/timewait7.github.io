内存、淘汰与碎片：maxmemory 设了为什么还会 OOM

Posted on 2026-10-25 In 数据存储 Word count in article: 4.4k Reading time ≈ 16 mins.

设了 maxmemory 不等于安全。本文实测了三种「照样出问题」的情况：noeviction 下写满就报 OOM command not allowed；一段 Lua 脚本能在 maxmemory=2MB 的实例里写出 34MB；以及删掉一半数据后 RSS 不降、碎片率从 1.09 飙到 4.96——直到开 activedefrag 才把 128MB 还给操作系统。

这一篇把「容量」这件事拆成三层：装不装得下（淘汰）→ 还回不还回（过期与惰性释放）→ 碎不碎（碎片整理）。

1. 淘汰：装不下的时候怎么办

1.1 八种策略，先分清两类

策略 从哪选淘汰对象 适用
noeviction（默认） 不淘汰，写满报错 当数据库用、绝不允许丢数据
allkeys-lru 所有 key，按最近最少使用 缓存场景首选
allkeys-lfu 所有 key，按访问频次 热点长期稳定
allkeys-random 所有 key，随机 几乎不用，除非访问完全均匀
volatile-lru 只从设置了 TTL 的 key 里选 缓存与持久数据混布
volatile-lfu 同上，按频次 同上
volatile-random 同上，随机 同上
volatile-ttl 同上，优先淘汰快过期的 同上 
flowchart TD
    M["Memory full"] --> P{"maxmemory-policy"}
    P -- "noeviction" --> E["Reject writes<br/>OOM error"]
    P -- "allkeys-*" --> A["Evict from all keys"]
    P -- "volatile-*" --> V{"key has TTL?"}
    V -- yes --> VE["Evict among volatile keys"]
    V -- "no TTL keys at all" --> E

关键区别：volatile-* 只在「有过期时间的 key」里淘汰。如果你忘了给缓存设 TTL，volatile-lru 在内存满时会退化成 noeviction——这是生产上最常见的「淘汰不生效」原因。

1.2 实测：同一个写满过程，两种结局

固定 maxmemory=2mb，写入 40,000 条 100 字节的 key：

策略 成功写入 被淘汰 最终 dbsize 报错
noeviction 766 条后停止 0 766 OOM command not allowed when used memory > 'maxmemory'.
allkeys-lru 40,000 条全成功 38,730 1,577 无

noeviction 那条记录的 total_error_replies 是 11,014——也就是说这轮写入了 1 万多次失败，而应用侧如果没把这类错误单独处理，用户看到的就是「偶发写入失败」。

指标 实测值

原因：maxmemory 的检查发生在命令入口（执行每条命令前判断是否需要淘汰/拒绝），而一段脚本在执行过程中不会再走这个入口。所以脚本里的写入不受限制，RDB/AOF 也拦不住它。

生产含义很直接：

场景 风险
用 Lua 做批量写入/迁移 能瞬间把内存打爆，触发 OOM Killer
用 Lua 做大 key 遍历 长时间阻塞（⑥ 会算）
用 EVAL 做「安全」的限流 与 maxmemory 无关，但会阻塞

结论：脚本要么限制迭代次数，要么在应用侧分批调用；指望 maxmemory 兜底是错的。

1.4 动手验证：验证你的实例在写满时是「报错」还是「淘汰」

预期观察点：noeviction 下出现 OOM command not allowed...；allkeys-lru 下所有 SET 都返回 OK，且 INFO stats 的 evicted_keys 增长。

判定标准：

  • 线上是 noeviction 且当缓存用 → 迟早写满报错，改成 allkeys-lru；
  • 是 volatile-lru 但 key 都没 TTL → 等同于 noeviction，检查 TTL 覆盖率；
  • evicted_keys 持续增长 → 容量不足，先算真实内存（⑫）再扩。

2. 命中率：LRU、LFU 与随机差多少

2.1 实验设计（这一步比结论重要）

  • 缓存上限 4MB，先灌 5 万个 key（必然触发淘汰）
  • 预热 1000 个热 key（模拟应用访问过）
  • 工作负载 10 万次：80% 访问热 key（1000 个）、15% 访问冷 key、5% 写入新 key

2.2 实测结果

策略 命中 未命中 命中率 淘汰数
allkeys-lru 83,479 11,523 87.9% 4,410
allkeys-lfu 81,334 13,668 85.6% 4,426
allkeys-random 73,022 21,980 76.9% 4,436 
flowchart LR
    R["allkeys-random<br/>76.9%"] --> L["allkeys-lfu<br/>85.6%"]
    L --> U["allkeys-lru<br/>87.9%"]

结论与流行说法不一样：在这个 80/20 场景里，LRU 与 LFU 只差 2.3 个百分点，LRU 甚至略好，而随机策略明显差一档（-11 个百分点）。

2.3 深挖：为什么 LFU 没有想象中那么好

LFU 的优势要在「热点长期稳定 + 访问频次差异大」时才显现。本文的工作负载里，热 key 刚被预热过、又持续被访问——「最近」和「最频繁」几乎是同一批 key，两种策略自然接近。

LFU 真正的坑在另一头：

问题 机制 对策
历史热点赖着不走 频次计数器长期不衰减，新热点挤不进来 lfu-decay-time（实测默认 1 分钟）
新 key 冷启动 新 key 频次从 0 开始，容易被淘汰 lfu-log-factor（实测默认 10，控制增长曲线）
计数器占空间 每 key 多几个 bit 可忽略

所以选型建议：默认 allkeys-lru；只有当你能观察到「热点稳定、LRU 频繁误淘汰」时再上 LFU，并配合调 lfu-decay-time。

2.4 一个被忽略的细节：淘汰是「近似」的

maxmemory-samples（实测默认 5）决定每次淘汰时采样多少 key 来「近似」找最久未用的。采样越少越省 CPU、越不准。

参数 实测默认 调大的代价 调大的收益
maxmemory-samples 5 每次淘汰多采样，CPU 上升 淘汰更准，命中率略升

这也是为什么「理论上的 LRU」和「Redis 的 LRU」不完全一样——后者是采样近似。

2.5 动手验证：给你的业务负载测一次命中率

预期观察点：命中率 = keyspace_hits / (hits + misses)，本文在 87% 左右。

判定标准：

  • 命中率 < 60% → 容量不足或访问分布太散，加内存比换策略有效；
  • 命中率 > 95% 且 evicted_keys 很低 → 容量富余，可考虑缩容；
  • 命中率忽高忽低 → 有定时任务在批量写（把热数据冲掉了）。

实验设计的一个坑：我第一次测出 LRU 只有 5.1% 命中率——因为热 key 在灌数据阶段就被淘汰了，工作负载又只有 GET（未命中不会回填）。命中率实验必须包含「预热」或「回填」，否则测出来的不是策略效果。

3. 过期与惰性释放：内存为什么没还回去

3.1 实测：10 万个 TTL 5 秒的 key

时刻 dbsize used_memory rss expired_keys
写入后 100,000 26.06 MB 42.28 MB 0
6 秒后 0 1.25 MB 42.28 MB 100,000

暴露了两件事：

  1. 过期删除是有效的：10 万个 key 在 6 秒内全部清掉，used_memory 从 26MB 掉到 1.25MB；
  2. RSS 没降：43MB 一直占着，因为 jemalloc 把释放的内存留在自己的 arena 里，不还给 OS。此时 mem_fragmentation_ratio 显示 34.85——这个数字毫无意义，因为分母（used）太小了。

3.2 深挖：碎片率什么时候才有意义

used_memory ratio 是否要处理
1 MB 34.85 不用，分母太小，纯噪声
37 MB 4.96 要，说明有真实碎片
170 MB 1.09 不用，健康
任意 > 1.5 且 used > 几百 MB 要，考虑 activedefrag 或迁移

判据：先看 used_memory 是否够大（比如 > 100MB），再看 ratio。空实例 ratio 13.94（① 的实测）也是同一个道理。

3.3 实测：碎片是怎么产生的，怎么收回去

阶段 used rss ratio
灌 10 万条（64B~4KB 混合） 169.62 MB 184.75 MB 1.09
删掉一半（5 万条） 37.30 MB 184.75 MB 4.96
开 activedefrag +8s 37.30 MB 105.11 MB 2.82
+13s 37.30 MB 56.24 MB 1.51
+18s / +23s 37.30 MB 56.24 MB 1.51（收敛） 
flowchart LR
    A["fill 100k keys<br/>used 169MB rss 185MB<br/>ratio 1.09"] --> B["delete half<br/>used 37MB rss 185MB<br/>ratio 4.96"]
    B --> C["activedefrag 8s<br/>rss 105MB ratio 2.82"]
    C --> D["+13s<br/>rss 56MB ratio 1.51"]

activedefrag 把 128 MB 还给了操作系统（184.75 → 56.24 MB），碎片率从 4.96 降到 1.51。整个过程没有重启、没有迁移数据。

3.4 碎片整理的三个参数

参数 实测默认 含义
activedefrag no 总开关，默认关闭
active-defrag-ignore-bytes 100 MB 碎片小于这个量不整理
active-defrag-threshold-lower 10% 碎片率超过它才开始整理
active-defrag-threshold-upper 100% 超过它全力整理
active-defrag-cycle-min / -max 5 / 75 每轮占用的 CPU 百分比上下限
lazyfree-lazy-eviction no 淘汰时是否异步释放（默认同步）
lazyfree-lazy-expire no 过期时是否异步释放
lazyfree-lazy-user-flush no FLUSHALL 是否异步

代价：activedefrag 会消耗 CPU（单线程！），在高峰期开要小心；lazyfree-* 打开会把释放操作放到后台线程，降低主线程阻塞，但也让内存回收更「慢半拍」。

3.5 动手验证：制造碎片再收回去

预期观察点：删一半后 ratio 会跳到 4 以上；开整理后 RSS 逐步下降，ratio 收敛到 1.5 附近。

判定标准：

  • ratio 长期 > 1.5 且 used > 100MB → 开 activedefrag；
  • 开了之后 ratio 不降 → 检查 active-defrag-ignore-bytes（碎片量不到 100MB 不会动）；
  • 生产高峰期不要开（会抢单线程 CPU）。

6. 动手验证：四个可复现实验

6.1 动手验证：验证写满时是报错还是淘汰

预期观察点：noeviction 下出现大量 OOM，evicted_keys 为 0；换成 allkeys-lru 重跑，grep -c OOM 为 0、evicted_keys 持续增长。

判定标准：报错条数 ≈ 超出容量的写入数；如果一条 OOM 都没有，说明 maxmemory 没生效或 key 太小没打满。

6.2 动手验证：命中率实验必须带预热

预期观察点：命中率 = hits/(hits+misses)，本文在 87% 左右；evicted_keys 应为正数。

判定标准：命中率 < 60% 说明容量不足或访问太散；如果命中率异常低（如 5%），检查是否漏了「预热」这一步。

6.3 动手验证：验证 TTL 过期与内存回收

预期观察点：6 秒后 DBSIZE 为 0、expired_keys ≈ 100000、used_memory 大幅下降，但 used_memory_rss 基本不动。

判定标准：used 降而 rss 不降是正常现象（jemalloc 不归还）；如果 used 也没降，说明过期删除被阻塞（查 lazyfree 与大 key）。

6.4 动手验证：制造碎片再收回去

预期观察点：删一半后 ratio 会跳到 4 以上；开 activedefrag 后 RSS 逐步下降、ratio 收敛到 1.5 附近。

判定标准：ratio 不降 → 检查 active-defrag-ignore-bytes（默认 100MB）是否把这次整理挡在门外。

5.4 实操建议

  1. maxmemory 与策略一起设，只设前者不设后者等于留了个 noeviction 的雷。
  2. 缓存 key 必须有 TTL，否则 volatile-* 策略失效——这条比选哪个策略更重要。
  3. 别在 Lua 里做无界写入，maxmemory 拦不住它（本文实测）。
  4. 碎片率要结合 used_memory 看，空实例的 34.85 是噪声；used 过百 MB 且 ratio > 1.5 才动手。
  5. activedefrag 放在低峰开，它是单线程的，抢的是命令执行的 CPU。

数据结构：编码阈值与复杂度的真实代价

Posted on 2026-10-25 In 数据存储 Word count in article: 4.2k Reading time ≈ 15 mins.

Redis 的一个 hash 从 512 个 field 涨到 513 个，内存从 6.2 KB 跳到 28.8 KB——多了 1 个 field，多了 4.6 倍内存。这不是 bug，是编码切换：小对象用紧凑的 listpack 连续存储，一旦越过阈值就换成 hashtable，每个 field 都带上哈希表的开销。

本文把三种编码阈值和四种复杂度都量成数字：hash/zset/set 的三条断崖、1000 个 string 与 1 个 hash 的内存对比、以及 ZRANGE 0 -1 为什么能用 1.4 毫秒阻塞整个 Redis。全部在 Redis 7.4.11 实测。

1. 编码：内存的第一决定因素

1.1 一句话定义

Redis 的每种类型都有两套编码：元素少、值小时用紧凑结构（连续内存、无指针开销），超过阈值后自动转成通用结构（哈希表 / 跳表，查询快但每个元素都有额外开销）。

flowchart TD
    H["HASH"] --> H1{"fields > 512<br/>or value > 64B?"}
    H1 -- no --> HL["listpack<br/>~12 B/field"]
    H1 -- yes --> HH["hashtable<br/>~48 B/field"]
    Z["ZSET"] --> Z1{"members > 128?"}
    Z1 -- no --> ZL["listpack<br/>~8 B/member"]
    Z1 -- yes --> ZS["skiplist + dict<br/>~82 B/member"]
    S["SET (all ints)"] --> S1{"members > 512?"}
    S1 -- no --> SI["intset<br/>~2.6 B/member"]
    S1 -- yes --> SH["hashtable<br/>~48 B/member"]

先记住一件事：这些阈值是参数，不是常量。本文实例的实测值：

参数 本文实测 含义
hash-max-listpack-entries 512 hash 的 field 数上限
hash-max-listpack-value 64 单个 field value 的字节上限
zset-max-listpack-entries 128 zset 成员数上限
zset-max-listpack-value 64 zset 成员字节上限
set-max-intset-entries 512 整数集合上限
list-max-listpack-size -2 quicklist 单节点 8KB（负数表示按大小）

注意：hash-max-listpack-entries 在本文的 7.4.11 上是 512，而不少资料写 128。默认值随版本变，一律用 CONFIG GET 现查。

1.2 实测：三条断崖

hash（field 数量）：

fields 编码 内存 每 field
100 listpack 1,072 B 10.7 B
128 listpack 1,584 B 12.4 B
511 listpack 6,192 B 12.1 B
512 listpack 6,192 B 12.1 B
513 hashtable 28,816 B 56.2 B
1000 hashtable 48,296 B 48.3 B

512 → 513，内存 4.65 倍。注意 511 和 512 的内存相同——jemalloc 按 size class 分配，不是按字节精确切分。

hash（value 长度，字段数固定 100）：

value 长度 编码 内存
63 B listpack 7,216 B
64 B listpack 8,240 B
65 B hashtable 12,840 B

只多了 1 个字节，编码就换了。

zset（成员数量）：

members 编码 内存 每 member
128 listpack 1,072 B 8.4 B
129 skiplist 12,128 B 94 B

11.3 倍。

set（整数成员）：

members 编码 内存 每 member
512 intset 1,328 B 2.6 B
513 hashtable 24,712 B 48 B

18.6 倍——最狠的一条。

1.3 深挖：为什么 sds/quicklist/listpack 能这么省

编码 内存布局 省在哪
listpack 一块连续内存，元素紧凑排列，长度用变长整数 没有指针、没有哈希桶
intset 有序整数数组 每个元素 2/4/8 字节，无任何额外结构
quicklist 双向链表，每个节点是一个 listpack 链表只在大粒度上有指针开销
hashtable 桶数组 + 链表/红黑树 每个元素有 dictEntry、指针、对齐开销
skiplist + dict 跳表 + 哈希表双结构 同一元素存两份，内存翻倍

skiplist 为什么最贵：zset 同时维护 skiplist（排序、范围查询）和 dict（O(1) 查分数），同一个成员存两遍。这就是 82 B/member 的来源。

1.4 动手验证：探测任意 key 的编码

预期观察点：fields=512 是 listpack、fields=513 是 hashtable；内存从 6 KB 级跳到 28 KB 级。

判定标准：

  • 你的实例 hash-max-listpack-entries 不是 512 → 以你的 CONFIG GET 为准，断崖点在别处；
  • OBJECT ENCODING 报 ziplist → 你的版本是 6.x，命名不同（7.0 起统一为 listpack）。

2. 内存实测：同样数据，几种存法

2.1 1000 个字段：1000 个 string vs 1 个 hash

用 MEMORY USAGE 精确测量（不用 INFO memory 的差值，原因见 2.4）：

N hash 编码 N 个 string 1 个 hash 结论
10 listpack 640 B 208 B hash 省 68%
100 listpack 6,408 B 1,584 B hash 省 75%
500 listpack 35,208 B 10,288 B hash 省 71%
1000 hashtable 71,208 B 56,296 B hash 只省 21%

结论有两层：hash 存对象确实省内存（小对象能省 70%+），但一旦编码切换，优势从 70% 掉到 20%。「用 hash 存对象更省」这句话有前提：别越过阈值。

2.2 每元素内存成本横评

同一批 10 万量级的数据，四种结构：

结构 编码 10 万条内存 每条约
list quicklist 798,592 B 8.0 B
hash（1000 field，按比例） hashtable 48,296 B / 1000 48.3 B
set（10 万整数） hashtable 4,772,968 B 47.7 B
zset（10 万成员） skiplist 8,249,440 B 82.5 B 
flowchart LR
    L["list<br/>8 B/item"] --> H["hash<br/>48 B/item"]
    H --> S["set<br/>48 B/item"]
    S --> Z["zset<br/>82 B/item"]

zset 是 list 的 10 倍。所以「用 list 还是 zset」不只是功能选择，也是内存选择。

2.3 深挖：为什么 list 这么便宜

quicklist 是「双向链表 + 每个节点一个 listpack」。10 万条数据只产生几百个节点，链表指针开销被摊薄，真实数据紧凑地存在 listpack 里——所以每条只花 8 字节（纯数据 + 长度信息）。

反过来说，list 的代价是随机访问：LINDEX 50000 要遍历节点，是 O(N)。list 适合「两端进出」的队列，不适合「按下标随机取」。

2.4 深挖：为什么不能用 INFO memory 差值量结构大小

我第一版实验是「FLUSHALL → 记 used_memory → 建结构 → 再记 used_memory，差值即大小」，结果算出来 hash 比 1000 个 string 更费内存——和结论相反。

原因是两个：FLUSHALL 的内存是惰性释放（lazyfree-lazy-user-flush），且 jemalloc 会把释放的内存留在自己的 arena 里复用。差值里混了上一次实验的残留，符号都可能反。

方法 结果可靠性 适用
INFO memory 差值 低（受惰性释放、allocator 复用影响） 只看大趋势（几百 MB 级）
MEMORY USAGE key 高（Redis 自己计算） 单 key 精确开销
MEMORY USAGE 循环求和 高（本文做法） 多种存法对比

这条方法学比结论更重要：量 Redis 内存，优先用 MEMORY USAGE。

2.5 动手验证：量出你自己的「每 key 成本」

预期观察点：1000 个 string 约 71 KB（71 B/key），hash 约 56 KB（56 B/field）。

判定标准：

  • 单 key 开销超过 value 大小的 3 倍 → 检查是否 value 太小、key 名太长（长 key 名的开销不可忽略）；
  • 同类 key 开销差异大 → 有编码混用（部分在 listpack、部分已转 hashtable）。

3. 复杂度：O(N) 命令才是真凶

3.1 实测：每条命令实际花了多久

用「慢日志阈值调到 0」的方式抓单条命令耗时（这是给单条命令计时的实用技巧）：

命令 数据规模 实测耗时 复杂度

HGETALL 1000 field（hashtable） 46 µs O(N)
ZRANGE 0 99 10 万成员 7 µs O(log N + M)
ZRANGE 0 9999 10 万成员 127 µs O(log N + M)
ZRANGE 0 -1 10 万成员 1,447 µs O(log N + M)，M=10 万
ZSCORE 10 万成员 2 µs O(1)
ZRANK 10 万成员 12 µs O(log N)
ZADD 单条 10 万成员 18 µs O(log N)

    B --> C["O(N) small: ZRANGE 100 7us, LRANGE 100 6us"]

3.3 深挖：单线程下 1.4 毫秒意味着什么

Redis 是单线程执行命令。ZRANGE 0 -1 花 1.4 ms，这 1.4 ms 里所有其他客户端的命令都在排队。如果这个命令每秒执行 10 次，就有 14 ms/秒 被完全占用——看起来只有 1.4% 的 CPU，但 P99 已经被它拉到毫秒级。

换算成一个更有用的公式：

SMEMBERS（2.8 ms）每秒 5 次 = 14 ms/秒的「全体停顿」，足以让一个 QPS 3000 的服务出现明显毛刺。

3.4 动手验证：给你自己的命令计时

预期观察点：SLOWLOG GET 的第三个元素是微秒数；ZRANGE 0 -1 在 10 万成员上应该接近 1.5 ms。

判定标准：

  • 单条命令 > 1 ms → 不能出现在在线链路（换 ZRANGE 分页 / SSCAN 分批）；
  • 单条命令 100 µs~1 ms → 限制频率，或改成 HSCAN/SSCAN 游标；
  • 单条 < 10 µs → 随便用。

记得把阈值改回去：CONFIG SET slowlog-log-slower-than 10000。

4.1 五种类型的选择表

需求 首选 反模式

队列 / 时间线 list（两端操作） 用 list 做随机下标访问

4.2 阈值该不该调

flowchart LR
    A["Raise listpack threshold"] --> B["Less memory<br/>compact layout"]
    B --> C["Slower per command<br/>O(N) scan inside listpack"]
    C --> D{"P99 budget left?"}
    D -- yes --> E["Keep it"]

调整 收益 代价
调大 hash-max-listpack-entries 更多 hash 保持紧凑，省内存 单条命令变慢（listpack 是 O(N) 查找）；极端情况阻塞
调小 查找更快 内存翻几倍
调大 zset-max-listpack-entries 小 zset 省内存 ZADD/ZSCORE 从 O(log N) 退化成 O(N)

判断依据：如果你的 hash 是「读多、字段多、单次只取几个 field」，保持 listpack 值得（省内存）；如果是「每次都要遍历全部 field」，那早就该转 hashtable，甚至该改数据结构。

4.3 一个真实的取舍：把缓存对象拆成 hash

方案 100 万对象的预估内存 单对象更新
100 万个 string（每对象一个 JSON） ~139 B × 100 万 ≈ 133 MB 全量重写
100 万个 hash（各 10 field，listpack） ~208 B × 100 万 ≈ 200 MB 只改 1 个 field

注意第二行：小 hash 的绝对值并不比 string 小，因为它多了「一个 key 一个 dictEntry」的固定开销。真正省内存的是「1 个大 hash 装 1000 个字段」这种聚合存储，但那样又会碰到阈值和并发写冲突。

4.4 动手验证：阈值调整的 A/B

预期观察点：A 是 hashtable（约 48 KB），B 是 listpack（约 12 KB）；再用 HGET f999 对比单次查找耗时。

判定标准：

  • 内存降了但 HGET 变慢 → 典型的「用 CPU 换内存」，看你缺哪个；
  • 调整后编码没变 → 已有 key 不会自动重新编码，必须重建（DEL 后重写）。

5.4 实操建议

  1. 上线前先 OBJECT ENCODING 抽样，确认核心结构在期望的编码上——尤其是「刚好卡在阈值附近」的 hash/zset。
  2. **量内存只用 MEMORY USAGE**，别用 INFO memory 的差值，后者会被惰性释放与 allocator 复用误导。
  3. ZRANGE 0 -1、SMEMBERS、HGETALL 一律不放在在线链路，它们都是 O(N) 且实测毫秒级。
  4. 阈值调整前先算清你缺内存还是缺延迟，调大 listpack 阈值是拿单命令延迟换内存。
  5. **每季度跑一次 --bigkeys**，把「即将突破阈值」的 key 提前处理掉。

一次请求的成本账：RTT、事件循环与命令执行

Posted on 2026-10-25 In 数据存储 Word count in article: 3.7k Reading time ≈ 14 mins.

一次 GET 从客户端看是 87 微秒，而 Redis 自己执行它只花了 0.07 微秒。剩下的 99.9% 全是网络往返、内核拷贝和排队。这个 0.08% 的比例，就是本文要算的账——它决定了你的优化到底该动哪里。

本文用四组对照实验把一次请求拆开：传输层（TCP / Unix socket）、payload 大小（64B → 1MB）、pipeline 深度（1 → 64）、io-threads（1 → 4）。全部在 Redis 7.4.11 容器里实测，客户端与服务端同机。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账（本文） → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：① 测出「一次往返 31 微秒、GET 87 微秒」，本文解释这两组数差在哪；⑥ 会把 pipeline 的工程化用法（批量、事务、Lua）讲透，本文只量它的成本。

1. 把一次 GET 拆开

1.1 实测：服务端只占 0.08%

用 INFO commandstats 读服务端自己统计的每命令耗时（usec_per_call），与客户端 p50 对照：

命令 服务端 usec_per_call 客户端 p50（50 连接） 服务端占比
PING 0.04 µs 0.031 ms（单连接） ~0.13%
GET 0.07 µs 0.087 ms 0.08%
SET 0.10 µs 0.087 ms 0.11%

Redis 快到这里已经没什么可优化的了——你不可能把 0.07 微秒优化成 0.007 微秒，那对 87 微秒的总耗时毫无意义。真正的大头在别处。

1.2 四段成本模型

flowchart LR
    A["Client serialize<br/>+ syscall write"] --> B["Kernel<br/>TCP / unix socket"]
    B --> C["epoll wakeup<br/>+ command parse"]
    C --> D["Execute<br/>0.07us"]
    D --> E["Reply write<br/>+ syscall"]

1.3 深挖：为什么单连接 PING 是 31 µs，50 连接 GET 是 87 µs

两者的差值不是「GET 比 PING 慢」，而是排队：

配置 并发 观测值 主要成本
PING，1 连接 1 31 µs/次 纯 RTT（客户端→内核→Redis→回来）
GET，50 连接 50 87 µs/次 RTT + 事件循环排队 + 客户端侧调度

50 个连接同时发命令时，Redis 单线程要串行处理 50 条，第 50 条的等待时间里包含了前 49 条的处理时间。并发越高，单次延迟里「排队」的占比越大——这就是 ⑤ 要展开的「单线程排队」。

1.4 动手验证：拿到你自己的服务端执行时间

预期观察点：usec_per_call 都在 0.05~0.2 µs 之间；如果你的 Redis 上这个值到了几十微秒，说明有慢命令（如 HGETALL 大 hash）。

判定标准：

  • usec_per_call < 1 µs → 服务端不是瓶颈，去查 RTT 与命令数；
  • usec_per_call > 10 µs → 命令本身重（大 key / 复杂命令），去 ③⑤；
  • 客户端 p50 / 服务端 usec_per_call < 100 → 你的优化空间几乎全在网络层。

2.2 深挖：TCP 栈多做了什么

同样是 loopback，Unix socket 省掉的是：

开销 TCP Unix socket
连接状态机 三次握手、四次挥手、TIME_WAIT 无
校验和 每包计算 无

Nagle 算法 可能攒包（延迟确认叠加更糟） 无
端口资源 每连接占一个本地端口 无

loopback 上 36% 的差距，换成跨机房会更大——因为跨机房时 RTT 由物理距离主导，而 Unix socket 根本不允许跨机。

生产上的结论很干脆：

场景 选择 理由
应用与 Redis 同机 / 同 Pod Unix socket 省 30%+ 的延迟，还省端口
同机房跨机 TCP + 长连接 无法用 unix socket
跨机房 TCP + 长连接 + 就近部署 RTT 是物理常量，优化不了，只能减少次数

2.3 动手验证：量一次两种传输的差

预期观察点：-s 那一组高 20%~40%（本文 36%）。

判定标准：

  • 两组差距 < 10% → 你的瓶颈不在传输层，别折腾 socket；
  • -s 报 Could not connect → --unixsocketperm 没给够（容器内外用户不同）。

3.2 深挖：为什么 64B 到 1KB 吞吐完全不变

因为这一段根本没碰到带宽上限：1 KB × 31 万 = 300 MB/s，离 loopback 的 3.5 GB/s 差一个数量级，瓶颈还是每次请求的 RTT 与调度。

到了 100 KB，一条命令就是 100 KB 的内存拷贝 + 系统调用，带宽打满 → 吞吐掉到 1/8。注意 p50 只从 0.087 ms 涨到 0.247 ms（2.8 倍），而吞吐掉了 8.3 倍——因为并发 50 个连接时，大 payload 让吞吐先崩，延迟后崩。

3.3 深挖：大 value 的三重代价

代价 机制 影响
带宽 每次请求拷贝 payload 吞吐断崖（本文 8.3 倍）
内存 value 大 → jemalloc 大块分配 → 碎片 ④ 展开
阻塞 拷贝 1 MB 期间单线程在忙 其他请求排队（⑤）

生产判据：单 value 超过 10 KB 就要警惕，超过 100 KB 基本是设计问题——拆成 hash 分片，或者干脆别放 Redis。

3.4 动手验证：找到你自己的「带宽拐点」

预期观察点：吞吐在某个体积之后开始线性下降，那个点就是你的带宽拐点。

判定标准：

  • 拐点在 10 KB 以内 → 你的网络很差（跨机房），必须减小 value；
  • 拐点在 1 MB 之后 → loopback 或万兆内网，value 大小不是主要矛盾。

p50 从 87 µs 涨到 479 µs（5.5 倍），因为第一条命令要等整批发完、处理完才回来。所以：

场景 该用 pipeline 吗
批量写 1000 条用户行为 该，深度 16~100

每次只取一个值、取完立刻算 不该，p50 会翻几倍

一个常被忽略的点：pipeline 深度不是越大越好。P=16 时 p50 0.167 ms、吞吐 11.6 倍；P=64 时吞吐只多 55%，p50 却再涨 2.9 倍。工程上 16~32 是甜点区。

4.3 动手验证：量出你的甜点区

预期观察点：吞吐在 P=16~32 接近平台，p50 持续上升。

判定标准：

  • 吞吐在 P=4 就平台化 → 你是 CPU 或带宽瓶颈，不是 RTT；
  • p50 超过业务超时的 1/10 → 深度太大了，降到 16。

5.1 实测：小 value 场景没有收益

CONFIG SET io-threads 4 + io-threads-do-reads yes 之后（1 KB value）：

配置 SET rps GET rps p50
io-threads=1 294,118 308,642 0.087 ms
io-threads=4 287,356 299,401 0.087 ms

差异在噪声范围内，甚至略低。

5.2 深挖：io-threads 什么时候才有用

io-threads 把「读 socket、解析协议、写回复」这些 IO 工作分给多个线程，但命令执行仍然是单线程。所以：

场景 io-threads 有用吗 原因
小 value、高 QPS 没用（本文实测） 瓶颈在 RTT 和事件循环，IO 线程不是瓶颈
大 value、带宽打满 有用 拷贝与协议解析是主要成本
多核机器 + 大量连接 有用 分摊 epoll 与 read/write 系统调用

一个必须知道的配置：io-threads 只是设了线程数，io-threads-do-reads yes 才会让读操作也走多线程（默认 no，只多线程写）。很多人只改了前一个，然后说「开了没用」。

5.3 动手验证：验证 io-threads 是否真的生效

预期观察点：io_threads_active:1（真正生效）；1 MB value 场景下吞吐应有提升，小 value 场景基本不变。

判定标准：

  • io_threads_active:0 → 没生效，检查是否只设了 io-threads 没设 io-threads-do-reads；
  • 小 value 场景提升 < 5% → 正常，别指望它解决 RTT 问题。

1. Redis 的四种成本

1.1 一句话定义

MySQL 的成本是「读了多少页」，Redis 的成本是「往返了几次、谁在排队」。同样是 1 万次读，逐条发是 1 万次 RTT，pipeline 发是 625 次 RTT（按 16 个一批），CPU 消耗几乎一样。

成本 一句话定义 由什么决定 怎么观测 详见
网络往返（RTT） 一条命令从发出到收到回复的时间 物理距离、TCP 栈、命令条数、pipeline redis-cli --latency、benchmark 的 p50 ②⑥
单线程排队 所有命令在一个事件循环里排队 命令复杂度、大 key、阻塞命令 SLOWLOG、INFO commandstats、P99 抖动 ③⑤
内存压力 装不下就要淘汰、碎片高就要整理 key 数量、value 大小、编码方式 INFO memory、MEMORY USAGE、碎片率 ③④

1.2 为什么「Redis 很快」这句话会骗人

实测（Redis 7.4.11，容器内 loopback，客户端与服务端同机）：

场景 实测 换算到单次
PING，1 个连接 32,981 rps 31 µs / 次往返
GET，50 连接，无 pipeline 319,489 rps 87 µs / 次（含排队）
GET，50 连接，-P 16 3,703,704 rps 单次 0.27 µs（摊销后）

同一个 GET，pipeline 与否差了 11.6 倍。差的是 Redis 的执行速度吗？不是——差的是往返次数。这就是第一篇要立的第一个观念：先数往返，再谈优化。

1.3 深挖：为什么单线程还能跑到 30 万 QPS

Redis 用单线程处理命令，靠三件事把 CPU 吃满：

  1. 纯内存操作，没有磁盘等待；
  2. epoll 多路复用，一个线程管几万个连接，没有线程切换；
  3. 命令足够短，GET 的 CPU 时间在百纳秒级，所以瓶颈天然落在网络上。

代价也很明确：任何一条慢命令都会堵住所有人。这也是第⑤篇的主题——KEYS *、DEL 大 key、Lua 长脚本，都会让 P99 从 0.1ms 跳到几百毫秒，而 CPU 使用率看起来还很健康（因为只有一个核在跑）。

这里可以直接对照站内 MySQL 系列第②篇：MySQL 的六层里，「等待」是第三种成本；Redis 的「等待」更极端——只有一个线程，排队就是全局的。

1.4 动手验证：三种成本各量一次

预期观察点：--intrinsic-latency 给出的是「这台机器什么都不做时的调度抖动」（本文实测平均 34 ns、最差 88 倍）；--latency 的 avg 是几十微秒到几百微秒；benchmark 的 p50 在 0.05~0.1 ms。

判定标准：

  • --intrinsic-latency 的 max 超过 1 ms → 宿主机的调度有问题（CPU 争抢、虚拟化），先解决环境再谈 Redis；
  • --latency 的 avg 远大于 p50 → 有偶发尖刺，去 ⑤ 找阻塞命令；
  • pipeline 后 QPS 提升不到 2 倍 → 你的命令本身很重（大 value / 复杂命令），不是 RTT 主导。

2.4 动手验证：环境自检

预期观察点：redis_version:7.4.x、maxmemory:0、DBSIZE:0、PING:PONG。

判定标准：io_threads_active 为 0（io-threads=1 时不会启用多线程）；如果你打算做 ⑥ 的多线程实验，确认启动参数里已经带上 --io-threads 4，否则 CONFIG SET 也能生效但需要重启连接。

3. 基线四件套

3.1 延迟：三层要分开量

flowchart LR
    A["1 System scheduling<br/>intrinsic 34ns"] --> B["2 Redis round trip<br/>loopback 0.17ms"]
    B --> C["3 App-side P99<br/>includes pool + serialization"]
    C --> D["Where the 5ms comes from"]
层 工具 本文实测 说明
系统调度 --intrinsic-latency 3 平均 34 ns，最差 88 倍 测「机器本身抖不抖」
Redis 往返 --latency（loopback） avg 0.17 ms 含 redis-cli 自身开销
单命令往返 redis-benchmark -t ping -c 1 32,981 rps（≈31 µs） 最接近「一次 RTT」
业务视角 应用侧埋点 P99 必须自己测 含连接池、序列化、网络

判定标准：

  • 系统调度最差 > 1 ms → 换机器或解决 CPU 争抢，别调 Redis；
  • 单命令往返 31 µs（同机）而业务 P99 是 5 ms → 问题在客户端（连接池、序列化、线程池），不在 Redis。

3.2 吞吐：pipeline 是第一个倍增器

场景 实测 rps p50 相对
SET，50 连接，无 pipeline 316,456 0.087 ms 1.0×
GET，50 连接，无 pipeline 319,489 0.087 ms 1.0×
SET，-P 16 3,448,276 0.183 ms 10.9×
GET，-P 16 3,703,704 0.159 ms 11.6×

注意 p50 反而变大了（0.087 → 0.183 ms）：pipeline 用延迟换吞吐。批量发 16 条，第一条要等 16 条都处理完才回来。所以 pipeline 适合「批量写/批量读」，不适合「一次只取一个值还要立刻用」。

这些是容器内 loopback 的数字，不能当线上容量。真实环境里 RTT 由网络决定，pipeline 的收益通常更大（因为 RTT 更贵）。

3.3 内存：100 万 key 到底吃多少

状态 used_memory rss 碎片率 dataset 占比
空实例 1.02 MB 13.70 MB 13.94 —
100 万 key（64B value） 138.84 MB 151.79 MB 1.09 66.54%

换算：每个 key 约 139 字节，而 value 只有 64 字节。单 key 实测 MEMORY USAGE = 136 字节。

多出来的 72 字节是什么？key 名、dictEntry、redisObject、jemalloc 的 size class 对齐。这是 Redis 内存规划的第一个坑：按 value 大小乘 key 数量算内存，一定算少。

指标 用途 本文实测
used_memory Redis 认为用了多少 138.84 MB
used_memory_rss 操作系统看到多少 151.79 MB
mem_fragmentation_ratio rss / used 1.09（健康，1~1.5 正常）
used_memory_dataset_perc 有效数据占比 66.54%（其余是开销）
MEMORY USAGE key 单个 key 的真实开销 136 B

灌完之后性能有没有退化？ 没有：

场景 空实例 100 万 key 之后
GET 50 连接 319,489 rps 308,642 rps（-3.4%）

这就是 Redis 和 MySQL 的一个重要差异：MySQL 的大表会让你担心 B+ 树变高、Buffer Pool 装不下；Redis 的 100 万 key 对 GET 几乎没有影响，因为哈希表是 O(1)。它的上限是内存，不是「数据量」。

3.4 慢日志与延迟监控：两个默认关闭的开关

实测：DEBUG POPULATE 1000000 耗时 362 ms，被慢日志记下来了（slowlog-log-slower-than = 10000 µs）：

工具 默认状态 本文实测 建议
SLOWLOG 阈值 10 ms，只留 128 条 362 ms 的 DEBUG 被记录 线上调到 1~2 ms，条数加到 512
LATENCY MONITOR 关闭（threshold=0） LATENCY LATEST 为空 打开（阈值 10~50 ms），它记录的是「事件尖刺」
INFO commandstats 一直开 可查每个命令的调用次数与耗时 定位「谁在跑重命令」

两者的差别：SLOWLOG 记录「单条命令耗时超过阈值」，LATENCY MONITOR 记录「事件循环被阻塞的尖刺」。排查线上抖动，后者往往更有用——因为真正的问题是「所有人都在等」，而不是「某条命令自己慢」。

4.3 动手验证：复现一次「抖动」

预期观察点：--latency 的 max 会跳到 5000 ms 附近——一个命令阻塞，所有请求一起等。

判定标准：

  • max 跳到秒级 → 确认是单线程阻塞，去 ⑤ 找「谁在阻塞」；
  • max 只有几十毫秒 → 阻塞命令没落到同一个实例（检查是否连错端口/库）。

5.1 面试速答表

面试题 一句话答案
Redis 为什么快 纯内存 + epoll 单线程 + 短命令，瓶颈天然在网络不在 CPU
单线程怎么扛住高并发 一个线程处理所有命令，没有线程切换；但慢命令会阻塞所有人

空实例碎片率 13.94 正常吗 正常，rss 基数太小；灌入数据后本文是 1.09

LATENCY MONITOR 默认开吗 不开，latency-monitor-threshold=0
maxmemory=0 意味着什么 不限制内存，可能被 OOM Killer 杀
Redis 的容量上限是什么 内存，不是数据量；GET 在 1M key 时无退化

5.4 实操建议

  1. 先测三层延迟（intrinsic / loopback / 业务侧），再决定优化哪一层。
  2. 把 slowlog-log-slower-than 调到 1~2 ms，并打开 latency-monitor-threshold——默认的 10 ms 会漏掉大部分抖动。
  3. 容量按 MEMORY USAGE 抽样算，别用 value 大小乘 key 数；本文的值是 136 B / 64 B ≈ 2.1 倍。
  4. maxmemory 必须设，并明确 maxmemory-policy；noeviction 在缓存场景等于「写满即挂」。
  5. **建一份 redis-lab.md**，把「场景 / 数据量 / 参数 / 命令 / 延迟 / QPS / 内存 / 结论」记下来，后面十一篇都往里加。
