Nginx 实战指南

Posted on 2024-09-30 In 部署运维 Word count in article: 10k Reading time ≈ 38 mins.

本文是 Nginx 的入门指南。每节按「场景 → 配置 → 最小示例」的顺序讲解：先说明为什么需要这个功能，再给出最常用的配置写法，最后是一个完整可用的示例。跨域（CORS）的基础概念放在文末附录中，遇到相关配置时参考即可。

1. Nginx 能做什么

Nginx 是一款高性能的 HTTP 服务器和反向代理服务器，实际项目中它最常见的五个角色：

角色 一句话概述
反向代理 客户端只访问 Nginx，Nginx 把请求转发给内部的应用服务器，隐藏真实服务地址
负载均衡 把请求按策略分发到多台后端服务器，避免单台过载，提升吞吐量和可用性
动静分离 图片、CSS、JS 等静态资源由 Nginx 直接返回，只有动态请求才转发给后端
SSL 终结 在 Nginx 上统一终止 HTTPS 加密连接，后端只跑 HTTP，证书集中管理
缓存 把后端的响应缓存到本地磁盘，重复请求直接返回，大幅降低后端压力

2. 核心架构：为什么 Nginx 能支撑高并发

Nginx 的高并发能力来自它的多进程 + 事件驱动 + 非阻塞 IO 架构。

master-worker 模型

Nginx 启动后只有一个 master 进程和多个 worker 进程：

  • master：不处理请求，只负责读取配置文件、监听端口、管理 worker 的生命周期（启动、平滑重载、退出）。
  • worker：真正处理请求的进程。数量一般设置为 CPU 核心数（worker_processes auto;），每个 worker 完全独立，一个 worker 崩溃不会影响其他 worker，master 会自动拉起新的。

事件驱动 + 非阻塞 IO

每个 worker 内部是单线程事件循环，用操作系统的高性能 IO 多路复用机制（Linux 用 epoll，macOS/BSD 用 kqueue）同时监听成千上万个连接：

  • 一个请求来了，worker 注册事件后继续处理其他请求，不阻塞等待。
  • 与传统服务器「一个连接一个进程/线程」的模型相比，没有大量的进程创建和上下文切换开销，内存占用小、并发能力强——这正是 Nginx 能解决 C10K（万级并发）问题的根本原因。

4. 反向代理与负载均衡

场景

应用服务通常不直接暴露给客户端：一是为了隐藏真实服务器地址，方便横向扩容；二是多个后端实例（应用服务器、微服务）需要统一入口。此时 Nginx 就充当了「调度员」：接收所有请求，转发给后端，再把响应原样返回。

upstream：负载均衡策略

upstream 在 http 层定义一组后端服务器，proxy_pass 引用它的名字。5 种常用策略：

策略 写法 适用场景
轮询（默认） 不加任何指令 后端性能均匀
权重 server ... weight=3; 后端性能不均，按比例分配
IP 哈希 ip_hash; 需要会话保持：同一 IP 固定到同一台后端（登录态存在进程内存时）
最少连接 least_conn; 请求耗时差异大，按当前活跃连接数分发
随机 random;（可配 random two least_conn;） 简单均匀地随机分发

server 参数中还有两个常用的状态标记：backup（其他服务器都不可用时才启用）和 down（标记永久下线，用于平滑摘除机器）。更多参数见 upstream 官方文档。

健康检查：被动 vs 主动

  • 被动检查（开源版自带）：Nginx 通过请求失败来判定后端不可用。server 后加 max_fails=3 fail_timeout=30s，表示 30 秒内失败 3 次就把该后端标记为不可用，暂停转发 fail_timeout 时长后再重新尝试。
  • 主动检查（定时探测）：开源版 Nginx 不支持，是 Nginx Plus 的商业功能，或用第三方模块 nginx_upstream_check_module 实现。开源场景的常见替代方案：单独提供一个 /health 探活接口，配合外部监控（如 Consul、Prometheus）摘除故障节点。

长连接（keepalive）

客户端 → Nginx 和 Nginx → 后端是两条独立连接，keepalive 针对后者：每个 worker 维护一个到后端服务器的空闲连接池，请求复用连接，避免每次请求都重新建立 TCP 连接（握手开销很大）。

客户端侧由 keepalive_timeout（空闲超时）和 keepalive_requests（单连接最多请求数）控制，在 http 层统一设置即可。

超时配置

反向代理有 3 个最常用的超时，全部作用于 Nginx 与后端之间的连接：

指令 默认值 含义 建议
proxy_connect_timeout 60s 建立到后端的 TCP 连接超时 5s 足够
proxy_read_timeout 60s 两次读操作之间的空闲超时（不是总时长） 按业务接口耗时调整
proxy_send_timeout 60s 向后端发送请求时两次写操作之间的空闲超时 按业务调整

排查慢请求时经常遇到「接口本身耗时 10 秒，但 Nginx 报 504」——检查 proxy_read_timeout 是否小于接口耗时。

5. 静态资源服务与缓存

场景

页面上的图片、CSS、JS 等静态资源如果每次都由应用服务器处理，会白白消耗应用进程和数据库资源。把静态资源交给 Nginx：一是 Nginx 的文件传输效率远高于应用框架；二是可以配合强缓存让浏览器直接使用本地副本，连请求都不用发出。这类配置常用在前后端分离项目或部署了构建产物的站点上。

7. 限流

场景

活动秒杀、恶意爬虫或代码 bug 都可能让流量瞬间打满后端，导致服务雪崩。限流的作用是给入口装上「阀门」：超过阈值（每秒请求数、并发连接数）的请求直接拒绝（返回 503），保护后端不被击穿。

limit_req：请求速率限制

配置分两步：http 层定义规则，location 里引用。

  • $binary_remote_addr：按什么维度限流，最常用是客户端 IP（二进制形式省内存）。
  • zone=api:10m：规则名 + 共享内存大小。
  • rate=10r/s：速率，支持 1r/s、10r/m（每分钟 10 次）。

burst 和 nodelay 的语义：

  • **burst=20**：允许瞬间超过速率 20 个请求进入「队列」而不是直接拒绝。
  • **不加 nodelay**：队列中的请求按速率被延迟（排空），实现匀速限流。
  • 加 nodelay：队列中的请求不再人为延迟、立即处理，但超过队列容量（rate + burst）的部分依然直接返回 503。突发流量场景（如秒杀）常用 nodelay，避免请求排队造成超时堆积。

limit_conn：并发连接数限制

和 limit_req（按每秒请求数）不同，limit_conn 限制的是同一时刻的并发连接数，适合限制下载、长连接类场景：

一个 IP 打开多个浏览器标签页（比如下载大文件）就会触及该限制。

8. 日志与监控

场景

线上问题排查的第一步永远是看日志：谁在什么时候请求了什么、响应多慢、报了什么错。Nginx 的访问日志记录每个请求，错误日志记录运行期问题，配合几个命令行工具就能完成大部分排障工作。

access_log：访问日志

默认格式是综合格式（combined），生产环境一般自定义 log_format，增加响应耗时字段——这是排查慢请求的关键：

9. keepalived 高可用

场景：为什么入口要两台 Nginx

Nginx 是流量的唯一入口，它就是整个架构的单点：入口一挂，后端的应用、数据库再健康也没有意义。高可用的目标是让入口”挂了也能自动换人”——用两台（或更多）Nginx 组成主备集群，对外只暴露一个虚拟 IP（VIP），客户端永远只访问这个 VIP：

  • 正常情况下 VIP 绑定在主节点（Master）上，请求全部由它处理；
  • 主节点故障时，VIP 在几秒内漂移到备节点（Backup），客户端无感知——TCP 连接的目标地址没有变过；
  • 备节点接管后，流量全部由备机处理，直到主节点恢复（是否自动回切看配置）。

Linux 服务器上实现 VIP 漂移的标准方案是 keepalived（基于 VRRP 协议），轻量、无额外软件成本，是 Linux 运维的标配技能。

9.1 VRRP 协议原理

keepalived 的高可用能力来自它实现的 VRRP（Virtual Router Redundancy Protocol，虚拟路由冗余协议，RFC 3768），核心机制如下：

概念 说明
虚拟路由器 一组路由器（这里指跑 keepalived 的主机）对外表现为一台”虚拟路由器”，共用同一个虚拟 IP（VIP）
Master 当前持有 VIP、实际处理流量的节点
Backup 监听 Master 通告、随时准备接管的节点
优先级（priority） 0~255 的整数，越大越优先，priority 最高者当选 Master
VRRP 通告 Master 周期（advert_int，默认 1 秒）向组播地址 224.0.0.18（协议号 112）发送心跳通告
Master Down Interval 约 3 × advert_int + 随机偏移；Backup 连续这么久收不到通告，即判定 Master 失效，抢占成为新 Master

状态机很简单：节点在 Initialize → Backup ↔ Master 之间迁移。Master 崩溃后，所有 Backup 中 priority 最高（相同则 IP 最大）的节点先超时、先抢到 Master，绑定 VIP 并通过 ARP 广播通知全网”这个 IP 的 MAC 变了”，交换机/路由器随之把发往 VIP 的流量导向新节点——这就是 VIP 漂移的完整链路。

9.4 脑裂问题

脑裂（Split-Brain）：主备都认为自己是 Master、两台机器同时绑定了 VIP，流量被两台机器同时处理。对只读负载影响不大，但一旦涉及写（登录态、缓存、状态），就会出现同一请求被两台机器各处理一次、数据互相覆盖的严重问题。

常见诱因：

  1. 网络分区：两台机器间的心跳链路断了，但各自业务链路正常——备机收不到通告以为自己要接管，主机还活着也持有 VIP；
  2. 防火墙拦截 VRRP 报文：iptables/安全组没放行 224.0.0.18:112，通告发不出去；
  3. 多网卡配置错误：VRRP 通告走错了网卡（interface 写错），对端收不到；
  4. 健康检查脚本误判：脚本 bug 导致本机 priority 被反复降级/恢复，引发抢占抖动。

  1. 放行 VRRP 流量（先排查这个，最常见）：

  3. STONITH（强杀对端）：检测到对端异常时，通过 IPMI/带外管理口把对端强制断电或重启——“谁抢 VIP 就把谁打死”，这是集群防脑裂的终极手段（常见于数据库双机、Pacemaker 集群）；

  4. 仲裁（Quorum）：引入第三方仲裁（ZooKeeper、数据库、独立仲裁机），只有拿到租约的节点才有资格绑 VIP；仲裁机也不可达时两方都让出 VIP 而不是都抢占；

  5. 业务侧兜底：写操作固定走主库/固定机房，读多写少的场景脑裂危害有限。

10. OpenResty 与 Lua

10.1 OpenResty 是什么

OpenResty 是带 Lua 扩展能力的 Nginx：在标准 Nginx 基础上集成了 LuaJIT（极快的 Lua 5.1 兼容解释器）和一批精选的 Nginx 模块（核心是 ngx_http_lua_module），并随包附赠常用 Lua 库（resty.redis、resty.http、resty.lock 等）。

解决的问题：Nginx 的配置是声明式的，表达能力有限——复杂的流量控制、缓存策略、鉴权逻辑用配置拼不出来。OpenResty 允许在请求的各个处理阶段直接写 Lua 代码，把业务逻辑下沉到入口层：

  • 入口层能做的就绝不转发给后端：缓存命中直接返回、灰度分流、动态路由、分布式限流；
  • 后端只处理”真正的业务请求”，扛压能力大幅提升。

安装（Linux 用官方源，macOS 用 Homebrew）：

配置目录与 Nginx 兼容（nginx.conf 语法完全一致），只是可执行文件名是 openresty。

10.2 核心指令与执行阶段

一个 HTTP 请求在 Nginx 内部按阶段处理，Lua 指令挂在对应的阶段上：

阶段 Lua 指令 典型用途
全局初始化 init_by_lua / init_worker_by_lua 加载配置、预热连接、启动后台定时任务（健康探测等）
重写 rewrite_by_lua 改写 URI、灰度分流、校验参数后重定向
访问控制 access_by_lua 鉴权、限流（放行/拦截）
内容生成 content_by_lua 直接生成响应，或子请求转发后端
响应头过滤 header_filter_by_lua 按条件改响应头
响应体过滤 body_filter_by_lua 按块处理响应体（压缩、截断、计数）
日志 log_by_lua 请求结束后记录自定义日志、异步回填缓存

写法三种：*_by_lua_block { ... }（内联代码块，下文示例用这种）、*_by_lua_file /path/x.lua（独立文件，生产推荐）、*_by_lua '一行代码'（单行）。

附录：跨域（CORS）基础概念

跨域本身不属于 Nginx 的知识，但在实际开发中 Nginx 常被用来解决跨域问题（在响应头中追加 Access-Control-Allow-Origin 等字段、处理预检请求），因此将基础概念整理在此，供阅读正文「CORS 头配置」时参考。

跨域与同源策略

跨域（Cross-Origin）是浏览器的一个安全机制，它限制网页从一个源向另一个源发起网络请求。同源策略要求请求的 URL 和当前页面的 URL 在以下三个方面完全一致才能通信：

比较项 要求 举例
协议 相同 http vs https ❌
域名 相同 www.a.com vs api.a.com ❌
端口 相同 localhost:3000 vs localhost:8080 ❌

跨域的作用：防止恶意网站通过脚本获取用户的敏感数据，保护用户隐私和数据安全。

跨域能保护数据安全，但在实际开发中，又经常需要跨域请求资源，如前后端分离、不同微服务之间调用，因此出现了一些跨域解决方案，最常用的有如下几种：

  • CORS（跨域资源共享）：最常用的跨域解决方案。服务器在响应头中设置 Access-Control-Allow-Origin 来允许特定源的请求。
  • 代理服务器：在前端和后端之间设置一个代理服务器，前端请求代理服务器，代理服务器转发请求到后端，因为服务器之间没有同源限制。
  • WebSocket：WebSocket 协议不受同源策略限制。

简单请求 & 非简单请求

同时满足以下两个条件的属于简单请求，反之则属于非简单请求：

  • 请求方法是 HEAD、GET、POST 三种之一
  • HTTP 头信息只包含这几个字段：Accept、Accept-Language、Content-Language、Last-Event-ID，且 Content-Type 只限于 application/x-www-form-urlencoded、multipart/form-data、text/plain 三个值

简单请求

对于简单请求，浏览器会在添加 Origin 请求头后直接发出。Origin 字段用来说明请求来自哪里：协议 + 域名 + 端口。

如果 Origin 不在许可范围内，服务端仍会返回一个正常响应，但响应头不包含 Access-Control-Allow-Origin，浏览器发现后抛出一个错误给 XHR 的 error 事件。

非简单请求

对于非简单请求，浏览器会先发送预检 OPTIONS 请求，先询问服务器：当前域名是否在许可名单内，以及可以使用哪些请求方法和请求头。只有得到肯定答复，才会继续发出正式的 XHR 请求，否则报错。

这就是正文中「CORS 头配置」里 if ($request_method = OPTIONS) { return 204; } 处理预检请求的原因。
