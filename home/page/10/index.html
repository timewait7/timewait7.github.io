Dubbo 原理与实践

Posted on 2025-09-21 In 中间件 Word count in article: 8.1k Reading time ≈ 29 mins.

Dubbo 面试全攻略：RPC 框架定位、五大核心角色、服务注册与发现全流程、Dubbo/Triple/REST 协议对比、五种负载均衡、六种集群容错、服务治理实战，以及本文的灵魂——Dubbo SPI 机制深度解析（Java SPI 缺陷 → 按需加载 / IoC / Adaptive / Wrapper / Activate 八大特性）。

1. Dubbo 是什么

Dubbo 是 Apache 基金会下的高性能 Java RPC 框架，核心定位是：远程方法调用 + 服务治理。

它的定位不是全家桶式的微服务解决方案（那属于 Spring Cloud），而是一个把”服务之间如何高效、可靠、可控地互相调用”这件事做到极致的框架。

核心能力一张图：

能力分类 具体能力 Dubbo 中的实现载体
远程调用 透明 RPC（像调本地方法一样调远程） 动态代理 + 协议层（dubbo / tri / rest）
服务发现 服务注册、订阅、变更推送 Registry SPI（ZooKeeper / Nacos / Consul / Redis / K8s）
负载均衡 五种均衡策略 LoadBalance SPI（Random / RoundRobin / LeastActive / ConsistentHash / ShortestResponse）
集群容错 失败重试、快速失败、容错降级等 Cluster SPI（Failover / Failfast / Failsafe / Failback / Forking / Broadcast）
服务治理 路由、权重、灰度、降级、限流、优雅停机 Router SPI + Filter SPI + 配置中心
可观测性 调用统计、Metrics、链路追踪、QoS 控制台 Monitor + Metrics + QoS（默认端口 22222）
扩展机制 一切核心组件均可替换 SPI 机制（第 8 节重点）

与主流方案一句话对比：

  • vs gRPC：gRPC 是语言无关的高性能 RPC（HTTP/2 + Protobuf），强在跨语言互操作与性能，但服务发现、负载均衡、治理能力需要自行搭配；Dubbo 强在开箱即用的服务治理，3.x 通过 Triple 协议与 gRPC 生态打通。
  • vs Spring Cloud：Spring Cloud 以 HTTP REST 为中心，强在生态广度（网关、配置、消息等全家桶）；Dubbo 以二进制私有协议为中心，性能更高、治理能力内建（负载均衡/容错/路由/限流在框架内部完成，不依赖外部组件）。
  • 选型共识：Java 内部服务间调用、对延迟敏感 → Dubbo；跨语言、与 K8s/Envoy 生态深度整合 → gRPC；业务微服务全家桶、追求生态统一 → Spring Cloud。三者并非互斥，实践中常共存。

Dubbo 不是网关（对外 HTTP 接入需走 Triple REST 能力或独立网关）、不是配置中心（3.x 的配置中心只管理 Dubbo 自身配置）。

2. 核心架构

Dubbo 的经典架构由五大角色组成：

角色 职责
Container 服务运行容器（Spring 容器等），负责加载、启动、管理服务实例
Provider 服务提供方，暴露服务接口，向注册中心注册自己提供的服务
Consumer 服务消费方，向注册中心订阅服务，发起远程调用
Registry 注册中心，服务地址的注册与发现，地址变更时主动通知
Monitor 监控中心，异步收集调用次数、调用耗时等统计数据

一次完整调用的 6 步链路：

  1. 启动：Container 加载并启动 Provider，Provider 初始化连接、端口等资源。
  2. 注册：Provider 启动完成后，向 Registry 注册自己提供的服务 URL（协议、IP、端口、参数）。
  3. 订阅：Consumer 启动时向 Registry 订阅自己需要的服务。
  4. 通知：Registry 返回 Provider 地址列表给 Consumer；Provider 增减、下线、权重变化时，Registry 主动推送变更。
  5. 调用：Consumer 根据软负载均衡算法从地址列表中选择一个 Provider 发起调用；失败时按集群容错策略处理（重试/快速失败等）。
  6. 监控：Consumer 与 Provider 异步上报调用次数、耗时、成功失败等统计信息给 Monitor。

两个补充场景：

  • 直连模式：绕过注册中心，通过 URL 直连指定 Provider，常用于联调：@DubboReference(url = "dubbo://192.168.1.10:20880")。
  • 本地调用（injvm）：Consumer 与 Provider 同进程时，默认走 injvm 协议本地调用，不占用网络端口，也避免序列化开销。

3. 服务注册与发现

3.1 注册中心对比

维度 ZooKeeper Nacos Redis Consul
一致性 CP（ZAB 协议，写操作强一致） AP + CP 混合：注册中心走 AP，配置管理走 CP 弱一致 CP（Raft 协议）
变更通知 Watcher 机制（事件回调，客户端回调后需重新注册 Watcher） 服务端主动推送（长连接 + UDP/HTTP），数据量小时优于 Watcher pub/sub 通知不可靠，需配合主动轮询 长连接 + gossip 广播 + HTTP 轮询
数据模型 树形节点 + 临时节点（会话断开自动删除） 持久/临时实例 + 健康检查 key-value KV + 健康检查（TCP/HTTP/gRPC）
大规模场景 服务节点多时 Watcher 通知风暴，ZK 压力大（Dubbo3 应用级发现缓解） 集群部署简单，性能好 一般 一般
生态 Dubbo 传统默认选择，运维知识普及 阿里系，配置中心 + 注册中心一体，云原生友好 仅学习/简单场景 强一致、健康检查丰富

小结： 老项目多为 ZooKeeper（临时节点天然适合”服务下线即摘除”）；新项目官方推荐 Nacos（推送机制优于 Watcher，且注册/配置一体）；Redis 因通知可靠性问题不推荐生产环境作为注册中心。

3.2 服务暴露全流程

以 dubbo.registry.address=zookeeper://127.0.0.1:2181 为例：

  1. 配置解析：ServiceConfig（@DubboService 注解）读取 dubbo.application.name、dubbo.protocol.name、dubbo.registry.address 等配置。
  2. 组装 URL：生成 dubbo://192.168.1.10:20880/com.example.DemoService?anyhost=true&application=demo-provider&interface=com.example.DemoService&...，URL 是 Dubbo 的统一配置模型，后续注册、路由、负载均衡都基于它。
  3. 生成 Invoker：ProxyFactory.getInvoker(serviceImpl, DemoService.class, url) 把服务实现包装为 AbstractProxyInvoker（Invoker 是”可执行远程调用的实体”的统一抽象）。
  4. 暴露服务：Protocol.export(invoker) 交给 DubboProtocol，创建 Netty Server 绑定 20880 端口，返回 Exporter。
  5. 注册地址：RegistryFactory.getRegistry(url).register(url)，在 ZK 创建临时节点：dubbo/com.example.DemoService/providers/dubbo%3A%2F%2F192.168.1.10%3A20880%2F...。
  6. 本地副本：同时做本地暴露（injvm），供同进程 Consumer 直接调用；启动 QoS 管理端口 22222。

3.3 服务引用全流程

  1. 配置解析：ReferenceConfig（@DubboReference 注解）解析配置，构建引用 URL 与注册中心 URL。
  2. 创建引用 Invoker：Protocol.refer(DemoService.class, url)，RegistryProtocol 接管。
  3. 订阅（Subscribe）：registry.subscribe(consumerUrl)，在 ZK 持久监听 dubbo/com.example.DemoService/providers、routers、configurators 等节点。
  4. 通知（Notify）：注册中心返回 Provider URL 列表（首次订阅立即返回，之后变更增量推送）；RegistryDirectory 将 URL 列表转换为 Invoker 列表并动态维护。
  5. 集群包装：Cluster 按容错策略（如 failover）把 Invoker 列表包装成一个 ClusterInvoker——调用时先过 Router（路由过滤，如 tag 路由、条件路由），再经 LoadBalance 选一台。
  6. 生成代理：ProxyFactory.getProxy(clusterInvoker) 用 Javassist/JDK 生成接口动态代理，业务代码拿到的是代理对象，调用时经 InvokerInvocationHandler → ClusterInvoker → Filter 链 → 网络层发送。

Invoke 链路一句话： 业务方法 → 动态代理 → ClusterInvoker → Router 过滤 → LoadBalance 选点 → 出/入站 Filter 链 → 编解码 → 传输层。

4. 远程调用协议

4.1 三大协议对比

维度 Dubbo 协议 Triple 协议 REST 协议
协议配置值 dubbo tri rest
默认端口 20880 50051 8080
传输层 自定义 TCP 二进制协议（Netty） HTTP/1.1、HTTP/2 HTTP/1.1
默认序列化 Hessian2 Protobuf JSON

流式通信 不支持 支持（unary / server streaming / client streaming / 双向流） 不支持

云基础设施友好度 差（自定义二进制，网关/Envoy/K8s 无法解析治理） 好（HTTP/2 是云原生事实标准） 好
大包传输 受限（默认 payload 8MB） 有流式通道可传大数据 取决于网关/容器

4.2 Dubbo 协议：高性能但”封闭”

  • 单一长连接：Consumer 对每个 Provider 默认只建一条 TCP 连接（配置 dubbo.consumer.connections=1），所有请求在这条连接上复用，靠 requestId 关联请求与响应（16 字节固定报文头：magic 0xdabb(2B) + flag(1B) + status(1B) + requestId(8B) + bodyLength(4B)）。单连接避免了大量连接的资源开销，是 Dubbo 高性能的关键之一。
  • 局限：单连接 + 串行 IO 在大数据包、高并发大消息场景会成为瓶颈（官方建议消息体控制在 1M 内）；私有二进制协议导致跨语言、云原生场景举步维艰。

4.3 Triple 协议：为什么 Dubbo3 主推它

  1. 跨语言互操作：基于 HTTP/2 + Protobuf，与 gRPC 完全兼容，gRPC 客户端（Go/Python/Node 等）可直接调用 Dubbo 服务；Dubbo 也可以反哺 gRPC 生态。
  2. 云原生友好：HTTP/2 是网关、Ingress、Envoy、Istio、K8s 基础设施的天然标准，流量可被统一治理、观测；自定义 TCP 二进制协议对基础设施是”黑盒”。
  3. 多路复用：HTTP/2 一个连接上并发多路复用，解决大规模场景下连接数爆炸问题，也解除了 Dubbo 协议单连接的吞吐上限。
  4. 流式通信：原生支持四种调用模式，满足大文件传输、实时推送等场景。
  5. 新项目官方建议直接选 Triple；老项目可平滑升级（ext-protocol: tri + preferred-protocol: tri）。

注意：Dubbo 3.x 默认协议仍是 dubbo（兼容老用户），但官方强烈建议新项目显式配置 dubbo.protocol.name: tri。

4.4 序列化选型

序列化 性能 体积 跨语言 特点与场景
Hessian2 中等 小 中（各语言实现水平不一） dubbo 协议的默认序列化；对 POJO 友好、无需 schema，Java 内部推荐
Fastjson2 快 较大 差（仅 Java） 文本可读、调试方便；Java 内部、追求体积小且无 schema 约束时可选
Protobuf 最快 最小 强 强 schema（.proto 文件），需要代码生成；Triple/gRPC 默认序列化，跨语言首选
Java 原生 慢 中 无 有反序列化安全漏洞，禁止用于网络传输

选型建议：Java 内部 + dubbo 协议 → Hessian2（默认）；跨语言 / 用 Triple → Protobuf；对性能要求极高且都是 Java → Fastjson2（或 Kryo）；与性能、安全相关的调优参数：dubbo.protocol.payload（默认 8MB 报文上限）、dubbo.protocol.serialization（协议级默认序列化）。

5. 负载均衡

配置方式：@DubboReference(loadbalance = "leastactive")、@DubboService(loadbalance = "...")，或全局 dubbo.consumer.loadbalance=random（默认）。优先级：方法级 > 服务级 > Consumer 全局 > Provider 端。

策略 原理 什么时候用
Random（默认） 加权随机：权重越大被选中概率越高，按权重分配随机数区间 通用默认场景：集群节点性能相近、没有特殊诉求时直接用
RoundRobin 平滑加权轮询（借鉴 Nginx，3.x 重写实现，避免权重不均时请求扎堆） 请求量稳定、希望流量严格均匀分布：如无状态计算服务，按权重精确分配
LeastActive 最少活跃调用数优先，活跃数相同再按权重随机 机器性能参差不齐：性能好的机器处理快、活跃数低，自动获得更多流量，天然按能力分流
ConsistentHash 一致性哈希（默认 160 个虚拟节点），相同参数请求总是落在同一台机器 有状态服务：本地缓存热点场景（如用户数据缓存），相同入参命中同一节点提高缓存命中率
ShortestResponse 按最近滑动窗口的平均响应时间选节点（叠加权重），响应时间接近时按权重随机 请求耗时差异大、对延迟敏感：自动把流量倾斜到”当前最快”的节点，动态适应机器负载波动

面试补充：ConsistentHash 的虚拟节点是为了解决节点数少时数据倾斜；LeastActive 和 ShortestResponse 都是”自适应”策略，但前者依据并发度（活跃数），后者依据延迟。

6. 集群容错

配置方式：@DubboReference(cluster = "failover") 或 dubbo.consumer.cluster=failover（默认）。作用在 Consumer 侧，控制”一个调用在多台 Provider 之间如何处理”。

策略 行为 典型参数 什么时候用
Failover（默认） 调用失败后自动切换其他 Provider 重试 retries=2（默认，加首次共 3 次） 幂等操作（查询、幂等写）；非幂等写必须 retries=0，否则可能重复执行
Failfast 只发起一次调用，失败立即抛异常 无需配置 非幂等写操作（新增、扣款），宁可直接报错也不重复执行
Failsafe 失败直接吞掉异常，返回空结果，只记日志 无需配置 可容忍丢失的辅助操作：日志上报、审计埋点、通知统计
Failback 失败先返回空结果，失败请求进入内存队列，后台每 5 秒重试，直到成功（进程内记录，不持久化） 无需配置 最终一致性的异步通知类：如订单状态变更通知，允许延迟送达
Forking 并行调用多个 Provider，任一成功即返回 forks=2（默认并行 2 个） 对实时性要求极高且消费方资源充足：如首页聚合、秒杀查价；代价是放大请求量，有状态操作禁用
Broadcast 逐个（可配置并行）调用所有 Provider，全部成功才算成功 broadcast.fail.percent=100（3.x，允许容忍失败百分比） 需要通知所有机器同步状态：如通知所有 Provider 更新本地缓存、清理本地资源

面试补充：

  • Failover 与幂等：retries 影响的是超时/异常后的重试次数，重试会放大对 Provider 的压力，也要与超时配合设置（总耗时 ≈ 单次超时 × 重试次数）。
  • Forking 与并发：forks 超过 Provider 数时退化为全量并行。
  • 容错策略可以和方法级配置叠加：写方法 retries=0，读方法保持默认重试。

7. 服务治理

7.1 动态路由

Dubbo 3 支持条件路由、标签路由、脚本路由（不推荐）。规则通过注册中心/配置中心下发，热生效，无需重启。

  • 条件路由：=> 前匹配 Consumer，后匹配 Provider。 常用于：机房隔离、A/B 测试、故障节点摘除。
  • 标签路由（tag）：给 Provider 打标签，Consumer 按标签选组。
    • Provider 侧：dubbo.provider.tag=gray
    • Consumer 侧：dubbo.consumer.tag=gray
    • Consumer 未打 tag 时默认不匹配带 tag 的 Provider（或配置 force=false 时 fallback 到无标签节点）。

7.2 权重调整

dubbo.provider.weight=100（默认 100），调整权重影响所有加权负载均衡策略的选点概率。配合注册中心下发（configurator 规则）可动态调整，无需重启——常用于上线初期的”先小流量、后放量”。

7.3 灰度发布

  1. 新版本 Provider 打标 dubbo.provider.tag=gray 并上线（只注册、可被灰度流量命中）。
  2. 灰度 Consumer 组配置 dubbo.consumer.tag=gray，流量被标签路由导到新版本；未打标的正常流量仍走老版本。
  3. 验证通过后，逐步调低老版本权重、调高新版本权重（或逐步扩大 tag 范围）。
  4. 全量后移除 tag 配置，下线老版本。

7.4 降级

@DubboReference(mock = "...") 或 dubbo.consumer.mock，分两种前缀：

写法 语义 场景
force:return+null 强制降级：不发起任何远程调用，直接返回 大促时主动屏蔽非核心服务（如积分、营销）
fail:return+null 容错降级：调用失败后返回 null（或 mock 类逻辑），而非抛异常 核心链路依赖的旁路服务故障时，不影响主流程

也支持 mock 实现类（如 MockDemoService implements DemoService，在 RpcException 时执行兜底逻辑返回本地数据）。

7.5 限流

  • TPS 限流（内置 TpsLimitFilter，Provider 侧）：Provider URL 携带 tps.limit.rate 即自动激活；令牌桶算法，超过速率直接抛 RpcException 拒绝。
  • 复杂限流（推荐 Sentinel 接入）：按调用方限流、动态阈值、熔断等场景，使用 Sentinel 的 Dubbo Adapter，在 Provider 侧配置 QPS 阈值。
  • 自适应限流（3.x）：dubbo.provider.flowcontrol=autoConcurrencyLimiter（或 heuristicSmoothingFlowControl），基于 CPU 使用率、并发度自动调整阈值，无需人工设置。

7.6 优雅停机

通过 JVM ShutdownHook 实现（kill PID 触发，kill -9 不触发）：

  • Provider：先标记不接收新请求（新请求直接失败，让 Consumer 重试其他节点）→ 等待线程池中存量请求执行完成 → 再释放连接、注销注册。
  • Consumer：不再发起新调用 → 等待未返回的响应 → 关闭。
  • 超时兜底：dubbo.service.shutdown.wait=30000（默认 10000ms，超过则强制关闭）。

8. Dubbo SPI

8.1 Java SPI 回顾

SPI 是 Java 提供的一种服务发现机制，通过接口与实现解耦实现动态扩展。核心流程如下：

  1. 定义服务接口（如 PaymentService）
  2. 提供实现类（如 AlipayService, WechatPayService）
  3. 注册实现：在 META-INF/services/ 下创建以接口全限定名命名的文件，写入实现类全限定名
  4. 动态加载：通过 ServiceLoader 加载所有注册的实现

优势：

  • 开闭原则：新增实现无需修改核心代码
  • 解耦：接口与实现分离
  • 可插拔：通过配置文件动态替换实现

  3. ServiceLoader：核心加载工具，实现懒加载
  4. 迭代顺序：按配置文件中定义的顺序加载

实际应用场景：

  • JDBC 驱动加载（DriverManager）
  • 日志门面（SLF4J）
  • 序列化框架（Jackson）
  • Spring Boot 自动配置

通过 SPI 机制，Java 实现了真正的面向接口编程，使系统具备高度可扩展性，符合「开闭原则」。

8.2 Java SPI 的 6 个问题

  1. 效率低下（全量加载）：
    • ServiceLoader 在加载一个接口的实现时，会遍历并实例化 META-INF/services/ 目录下对应配置文件中的所有实现类。
    • 问题： 如果某个扩展点有很多实现（或者某些实现类初始化成本很高），但实际运行时只需要用到其中一个或几个，这种全量加载会造成不必要的资源消耗（内存、CPU）和启动延迟。
  2. 缺乏按需获取能力（不灵活）：
    • Java SPI 只能获取所有实现，然后由调用者遍历查找需要的那个。没有内置的机制根据名称、参数或其他条件直接获取特定的实现实例。
    • 问题： 使用起来不够方便和直观，需要额外的筛选逻辑。
  3. 不支持依赖注入：
    • 通过 SPI 加载的实现类实例，其构造函数或成员变量如果依赖其他对象，需要调用者手动设置。
    • 问题： 在复杂的框架中，扩展点实现类可能需要依赖框架内部的核心组件（如配置中心、注册中心、序列化器等），手动管理这些依赖非常繁琐且容易出错，破坏了扩展点的封装性。
  4. 不支持扩展点自适应/IoC/AOP：
    • Java SPI 是静态的，加载哪个实现在配置文件中是写死的。它无法根据运行时的参数（如方法参数、URL 参数、配置项）动态选择不同的实现。
    • 问题： 缺乏动态性，难以实现更高级的功能如适配器、包装器（AOP）、条件选择等。
  5. 配置不友好（无名称标识）：
    • 配置文件里直接写实现类的全限定名。没有为每个实现定义一个易于理解和使用的名称（Key）。
    • 问题： 配置和引用不够直观，容易出错，不利于通过配置中心动态修改。
  6. 缺乏生命周期管理：
    • Java SPI 没有提供标准的初始化和销毁回调机制。

8.3 Dubbo SPI 八大特性

Dubbo 设计了一套功能更强大、更灵活的 SPI 机制（核心在 org.apache.dubbo.common.extension 包），完美解决了上述问题：

  1. 按需加载（核心改进）：
    • Dubbo SPI 不会一次性加载和实例化所有实现类。
    • 它维护了一个映射关系：扩展点名称 (Key) -> 实现类全限定名。
    • 只有当通过名称 (key) 明确请求某个扩展点时，才会加载并实例化对应的实现类。大大提高了效率和资源利用率，加快了启动速度。
  2. 支持扩展点命名与配置化：
    • 配置文件路径：META-INF/dubbo/ 或 META-INF/dubbo/internal/ 或 META-INF/services/（兼容 Java SPI），文件名为接口全限定名。
    • 文件内容格式：key=implementation.class.name (例如：dubbo=org.apache.dubbo.rpc.protocol.dubbo.DubboProtocol)。这为每个实现赋予了明确的标识符 (key)。
  3. **强大的依赖注入 (IoC)**：
    • Dubbo SPI 在实例化扩展点实现时，会自动扫描其 setter 方法。
    • 如果 setter 方法的参数类型是另一个已知的扩展点类型，Dubbo 会自动注入该扩展点的适配实例（通常是自适应扩展点实例，见下一点）。
    • 也支持注入框架内部的核心组件（如 ApplicationModel, ModuleModel, ScopeModel 等）。
    • 优势： 解耦扩展点实现与框架内部依赖，开发者只需关注业务逻辑，依赖由框架自动注入。
  4. **自适应扩展点 (Adaptive Extension - 核心特性)**：
    • 概念： 一种特殊的扩展点，它本身通常不包含具体逻辑，而是一个动态生成的代理（编译时生成或运行时生成）。
    • 作用： 在方法被调用时，根据传入的运行时参数（通常是包含配置信息的 URL 对象或 @Adaptive 注解指定的参数），动态决定将调用委托给哪个真正的扩展点实现 (key 对应的实现)。
    • 实现方式：
      • 编译时生成： Dubbo 编译器会为标记了 @Adaptive 注解的接口方法生成代理类代码（如 Protocol$Adaptive）。
      • 运行时生成： 如果接口没有任何方法标记 @Adaptive，Dubbo 会查找该接口的默认实现（通过 @SPI 的 value 指定）。如果需要在运行时根据方法参数选择，也可以在具体实现类的方法上使用 @Adaptive（较少见）。
    • 优势： 实现了真正的运行时动态扩展选择。例如，Protocol 接口的自适应扩展点，根据 URL 中的 protocol 参数值 (dubbo, hessian, http, injvm 等）决定使用哪个具体的协议实现。这是 Dubbo 高度可扩展性的基石。
  5. **自动包装 (Wrapper - AOP)**：
    • 如果扩展点实现类的构造函数接受单个参数且是该扩展点接口类型，Dubbo 会识别它为 Wrapper 类。
    • 在加载真正的扩展点实现（称为 instance）时，Dubbo 会像”洋葱”一样，用所有找到的 Wrapper 类层层包裹这个 instance：new Wrapper1(new Wrapper2(new Wrapper3(instance)))。
    • 作用： 在不修改原始实现类代码的前提下，实现 AOP 功能。Wrapper 可以在调用真正实现的前后添加逻辑，如日志记录、监控统计、权限校验、失败重试、负载均衡（部分策略）等。Dubbo 自身的很多功能（如 Filter Chain）都是通过 Wrapper 机制实现的。
  6. **自动激活扩展点 (Activate)**：
    • 通过 @Activate 注解标记扩展点实现。
    • 可以根据给定的条件（如 URL 中的特定参数值、消费者/提供者端角色）自动激活并组合一组符合条件的扩展点实现。
    • 典型应用： Dubbo 的 Filter 链。开发者可以方便地添加自定义 Filter，并通过 @Activate 注解控制它在哪些条件下自动生效（如所有调用、特定分组、特定服务等）。
  7. 支持默认扩展点和覆盖：
    • 在 @SPI 注解中可以指定默认扩展点的 key (如 @SPI("dubbo"))。
    • Dubbo 支持通过配置（系统属性、外部配置）覆盖默认实现或已加载的实现。
  8. 缓存优化：
    • Dubbo 对加载的扩展点定义、实例（单例或原型）、自适应扩展点实例等进行了细致的缓存管理，避免重复加载和创建，提升性能。

这套机制的落地场景：本文第 5 节负载均衡、第 6 节集群容错中的每种策略，就是一个 @SPI 扩展点；@DubboReference(loadbalance = "leastactive") 里的字符串，就是扩展点 key——理解 SPI，就理解了整个 Dubbo 的配置体系。

10. 常见面试题速答

Q1：Dubbo 和 Spring Cloud 怎么选？
Dubbo 是高性能 RPC + 服务治理框架，二进制协议性能好、负载均衡/容错/限流内建；Spring Cloud 是 REST 为主的微服务全家桶，生态广但性能弱于二进制 RPC。Java 内部高并发链路用 Dubbo，跨语言/云原生用 gRPC，业务生态整合用 Spring Cloud，实际常混用。

Q2：注册中心挂了，服务还能调用吗？
能。Consumer 本地缓存了已拉取的 Provider 地址列表，已发现的服务可继续调用；只是无法感知地址变更（新节点、下线节点），且新启动的实例无法完成初始订阅。注册中心不处于调用链路上，是它高可用的设计关键。

Q3：Failover 重试会有什么风险？
重试会重复执行请求。非幂等操作（新增、扣款）必须 retries=0；幂等读可以放心重试。同时重试放大 Provider 压力，总耗时 ≈ 单次超时 × 重试次数。

Q4：Dubbo 协议为什么是单一长连接？
减少连接建立/维护开销，靠 requestId 复用一条连接多路复用请求；但大消息会阻塞同连接其他请求，官方建议消息体 1M 内，大包走 Triple 的流式能力。

Q5：为什么 Dubbo3 主推 Triple？
跨语言（gRPC 兼容）、云原生友好（HTTP/2 可被网关/Envoy/K8s 统一治理）、多路复用解决连接爆炸、原生流式通信。

Q6：负载均衡怎么选？
节点性能均衡用 Random/RoundRobin；性能参差用 LeastActive；本地缓存有状态用 ConsistentHash；延迟敏感用 ShortestResponse。

Q7：如何实现一个自定义 Filter（如统计耗时）？
实现 org.apache.dubbo.rpc.Filter，@Activate(group = "provider") 标记生效侧，在 META-INF/dubbo/org.apache.dubbo.rpc.Filter 里注册 key=实现类全限定名，SPI 自动加载进 Filter 链，无需改框架代码。

Q8：超时配置在谁那边设置？优先级？
dubbo.consumer.timeout（Consumer 侧）/ dubbo.provider.timeout（Provider 侧，作为 Consumer 缺省）。优先级：方法级 > 服务级 > Consumer > Provider > 全局默认（1000ms）。注意 Consumer 超时要大于 Provider 端实际处理时间，否则 Provider 还在执行、Consumer 已超时。

Q9：如何做灰度发布？
tag 路由：新版本 Provider 打 dubbo.provider.tag=gray，灰度 Consumer 配 dubbo.consumer.tag=gray，验证通过后逐步调权重放量，最后摘除 tag 全量。

Q10：Dubbo 接口级和服务级服务发现有什么区别？
接口级每个接口×实例都注册 URL，数据量大；应用级只注册实例、元数据放元数据中心，数据量 = 接口数 + 实例数，支撑更大规模，是 Dubbo3 的核心升级点。

Q11：什么是 Dubbo SPI 的 Adaptive 扩展点？
动态生成的代理：调用时根据运行时参数（URL 中的 key）选择真实实现。比如 Protocol 的自适应代理根据 URL 中 protocol=dubbo 委托给 DubboProtocol。它是”配置即代码、运行时多态”的关键。

Q12：zk 临时节点 + Watcher 如何支撑服务发现？
Provider 注册临时节点（会话断开自动删除，天然感知宕机）；Consumer 订阅节点并注册 Watcher，节点增删改触发回调重新拉取 + 重新注册 Watcher；Watcher 一次性是”重新注册”的原因，也是服务多时通知风暴的来源。

Elasticsearch 原理与实践

Posted on 2025-09-21 In 数据存储 Word count in article: 8.3k Reading time ≈ 30 mins.

Elasticsearch

面试考点范围：ES 的定位与 Lucene 基础、核心概念（Index/Type/Shard/Replica/倒排索引）、写入链路与可靠性（Translog/Refresh/Flush）、查询原理（Query/Filter 上下文、TF-IDF vs BM25、核心查询 DSL）、聚合（Bucket/Metric/Pipeline）、分片与集群（Yellow/Red 排查、脑裂）、索引与性能优化（映射爆炸、keyword vs text、Bulk、doc_values、堆内存、慢查询日志）、MySQL 与 ES 数据同步，以及常见速答题。

1. Elasticsearch 是什么

1.1 定位：Lucene 之上的分布式搜索引擎

Elasticsearch（下文简称 ES）是 2010 年由 Shay Banon 开源的分布式、近实时（NRT）的全文搜索引擎，基于 Java 实现。它的底层是 Apache Lucene——Doug Cutting 开发的高性能全文检索库。Lucene 本身只是一个嵌入式的 JAR 包，只解决”单机上的索引与搜索”问题；ES 在 Lucene 之上封装了分布式能力（分片、副本、集群）和 RESTful API，让全文搜索变成可以直接部署、调用的服务。

一句话：Lucene 是引擎，ES 是装了引擎的分布式整车。

1.2 全文搜索 vs 数据库搜索

面试常问”为什么不用 MySQL 的 LIKE 做搜索”，核心差异如下：

维度 MySQL（LIKE） Elasticsearch
查询方式 %关键词% 无法利用 B+ 树索引，退化为全表扫描 倒排索引直接定位词项，不扫描全表
相关性排序 不支持打分，只能按自定义字段排序 BM25 相关性打分，可控制权重
数据量级 千万级开始吃力 亿级以上，分片横向扩展
模糊能力 通配符（前导通配符同样全表扫描） 分词 + 短语/模糊/同义词，天然适合中文分词
写入一致性 强一致，写入即查得到 近实时，默认 1 秒后才可搜到（见第 3 节）

注意一个前提：ES 是搜索和聚合引擎，不是数据源。它没有跨文档事务、没有强一致保证，业务数据的主存仍然是 MySQL，ES 只是副本/索引（见第 9 节数据同步）。

1.3 适用场景

  • 站内搜索：电商商品、文档、知识库的全文检索，是 ES 的第一场景。
  • 日志与指标分析：ELK 技术栈（Elasticsearch + Logstash + Kibana），日志检索、监控大盘。
  • 聚合分析：基于海量数据的统计报表（点击、订单、访问量）。
  • 地理检索：geo_point 附近的人、门店搜索。
  • 向量检索：8.x 起支持 dense_vector 字段和 kNN 搜索，可做语义搜索、RAG 召回。
  • 不适合：强事务/多文档原子操作（无 ACID）、复杂多表关联查询（ES 的 join 能力很弱且不推荐）、低频小数据量的简单查询（杀鸡用牛刀）。

2. 核心概念

  • 文档（Document）： 数据的基本单位，通常是 JSON 格式，对应数据库中的一行记录。
  • 索引（Index）： 具有相似特征的文档集合，对应数据库中的一张表。一个索引由一个或多个分片组成。
  • 类型（Type）： 索引内部的逻辑分区，曾允许在同一索引中存储不同类型的文档（如 user、product）。版本演变：6.x 起被标记废弃（deprecated，一个索引只允许一个 type）；7.x 中正式废弃，API 默认使用 _doc 类型；8.x 中类型概念被完全移除，现在一个索引只包含一种文档类型。
  • 映射（Mapping）： 定义索引中每个字段的类型、分词器、是否索引等元数据，相当于数据库的表结构（DDL），详见第 7 节。
  • 分片（Shard）： 索引被水平分割成的子集，每个分片本身就是一个功能完整且独立的”索引”（一个 Lucene 索引）。
    • 主分片（Primary Shard）： 存储文档数据并处理索引/更新操作。索引创建时指定数量，后续不可更改（除非 Reindex）。
    • 副本分片（Replica Shard）： 主分片的拷贝，提供高可用性（主分片故障时副本可提升为主）和读取吞吐量（查询可负载均衡到所有副本）。
  • 节点（Node）： 运行中的 Elasticsearch 实例。
  • 集群（Cluster）： 一个或多个节点协同工作的集合，共同持有整个数据并提供联合索引和搜索能力。
  • 倒排索引（Inverted Index）： ES 实现快速全文搜索的核心数据结构，存储了词项（Token）到包含该词项的文档 ID 列表的映射。相比传统数据库的正排索引（文档 ID 到字段值），倒排索引天然适配”哪些文档包含某个词？”这一类查询。

2.1 倒排索引详解

  • 定义： 倒排索引是一种将文档中的词项（Token）映射到包含该词项的文档列表的数据结构，由两个核心部分组成：
    • 词项字典（Term Dictionary）： 包含所有不重复的词项，通常按字典序排序，并配合 FST（有限状态转换器） 压缩存储、常驻内存，实现 O(1) 级别的词项查找。
    • 倒排列表（Postings List）： 对于每个词项，记录包含该词项的所有文档 ID 列表，以及词项在文档中出现的位置（Position）、词频（Term Frequency）等信息，用于相关性评分和短语查询。
  • 重要性：
    • 快速定位： 直接通过词项找到包含它的文档，避免扫描全部文档。
    • 高效布尔查询： AND/OR/NOT 操作可以通过对倒排列表进行交、并、差集运算高效完成。
    • 相关性评分基础： TF-IDF、BM25 等经典评分模型严重依赖倒排索引中存储的词频（TF）、文档频率（DF/IDF）信息。
    • 支持短语查询： 利用存储的位置信息，可以精确查找相邻出现的词组（match_phrase）。

3. 写入与刷新

3.1 完整写入链路

  1. 路由： 请求到达任意节点（该节点即协调节点），根据 routing = hash(文档ID) % 主分片数 定位到主分片。
  2. 写内存 + Translog： 主分片将文档写入内存缓冲区（Indexing Buffer），同时立即追加写入事务日志（Translog）。Translog 是持久化的。
  3. Refresh： 定期（默认 1 秒）将内存缓冲区中的内容生成一个新的、可搜索的 Lucene 段（Segment），并清空缓冲区。这个过程使新写入的数据对搜索可见。 注意：此时数据还在操作系统的文件系统缓存（Page Cache）中，并未物理刷盘（fsync）。
  4. 段合并： 小段在后台按 Tiered Merge Policy 合并成大段，控制段数量（见 8.2）。
  5. Flush： 定期（默认 30 分钟，或 Translog 大小达到阈值）将段数据 fsync 落盘并截断 Translog。

这就是 ES”近实时”的原因：数据可搜索需要等一次 Refresh（1 秒级），而 Translog 只保证数据不丢，不保证立刻可见。如果需要写入后立刻可搜，可在写请求带 ?refresh=true（或 refresh=wait_for），代价是性能下降。

3.2 写入可靠性

  • 事务日志（Translog）： 所有写入操作在写入内存缓冲区的同时，会立即追加写入到事务日志中。Translog 的刷盘时机由 index.translog.durability 控制：默认 request（每个写请求都 fsync，性能换可靠性），可改为 async（默认每 5 秒批量刷盘，性能更好但断电最多丢几秒数据）。
  • 副本确认： 写入操作在主分片执行成功后，必须等待所有配置的副本分片也写入成功才返回客户端确认（除非使用 wait_for_active_shards 降低要求），确保数据冗余。
  • 故障恢复： 节点重启时，会重放 Translog 中尚未刷盘的操作来恢复数据；副本分片的存在保证了主分片丢失时数据不丢（副本提升为主分片）。
  • 兜底： 跨机房的灾难恢复靠定期快照（_snapshot API，备份到 HDFS/S3 等）。ES 不是数据库，关键数据的主存必须在 MySQL，极端情况可从源库重建索引（见第 9 节）。

4. 查询原理

4.1 一次搜索的流程

  1. 协调节点接收请求，解析 DSL，按 routing 找到目标分片，将查询广播到所有主/副本分片（默认 query_then_fetch 模式）。
  2. 各分片在自己的 Lucene 索引上本地执行查询并打分，返回 Top N 的文档 ID 和分数（默认每个分片取 from + size 条）。
  3. 协调节点合并排序所有分片的结果，取全局 Top N，进入 Fetch 阶段。
  4. 协调节点向各分片取回完整的 _source，组装后返回。

加分项：query_then_fetch 是”本地 IDF 打分”，每个分片只能基于自己的词频统计，结果与全局 IDF 有轻微偏差；dfs_query_then_fetch 会先收集全局词频再打分，更精确但多一轮通信，生产环境很少使用。

4.2 Query 上下文 vs Filter 上下文

bool 查询中的 filter 子句、constant_score、term/range 直接放在 query 里都是 Query 上下文；放在 bool.filter / bool.must_not / constant_score.filter 里则是 Filter 上下文。

维度 Query 上下文 Filter 上下文
相关性 参与 _score 计算，影响排序 不参与算分（_score 恒为 0）
缓存 不缓存 结果可缓存（节点级 Query Cache 中的位图 Bitset），同条件复用
性能 有算分开销，相对慢 更快，适合高频过滤条件
场景 全文检索、相关性排序 状态、范围、布尔标记等刚性过滤条件

最佳实践：需要算分的放 Query（如 match），不需要算分的过滤条件尽量放 Filter（如 status、price 范围、is_deleted），既省算分开销又能命中缓存。

4.3 相关性评分：TF-IDF vs BM25

  • TF-IDF：词频 × 逆文档频率 × 长度归一化。问题是词频是线性增长的，高频词（”的””手机”）在长文档中会过度主导得分。
  • BM25：在 TF-IDF 基础上引入 TF 饱和函数和 IDF 平滑，并增加可调参数 k1（默认 1.2，词频饱和速度）和 b（默认 0.75，文档长度归一化程度）。

5.2 聚合与查询的区别

  • 查询（Query）：选出符合条件的文档，返回文档本身；聚合（Aggregation）：对结果集做分组和统计，返回统计结果。类比 SQL：查询是 WHERE，聚合是 GROUP BY + 聚合函数。
  • 聚合默认作用于查询筛选后的结果集（无 query 则默认 match_all 全部文档）；聚合可以嵌套（桶内再分桶、桶内再算指标），Pipeline 聚合还能跨桶计算。
  • 聚合结果中的桶是 Top-N 近似值（先在各分片取 top，再合并），与精确分组有偏差。

5.3 聚合优化

  • text 字段不能直接聚合：聚合依赖 doc_values，text 默认没有（详见 8.3）。给字段配 keyword 子字段后用 field.keyword 聚合。
  • terms 聚合的 size 默认 10，要更多桶需显式设置；分片返回桶数由 shard_size 控制（默认约 size * 1.5 + 10），桶数很大时适当调大 shard_size 保证准确性。
  • cardinality 是近似去重：precision_threshold 默认 3000，值不超过阈值时精确，超过后基于 HyperLogLog 近似，可适当调大换取精确性。
  • 大桶数分页用 composite 聚合：terms 聚合超过 size 的桶拿不到，composite 支持 after 游标分页取全部桶。
  • 不需要聚合/排序的字段可以关闭 doc_values 省磁盘（默认开启）。
  • 聚合结果可用 Shard Request Cache 缓存（?request_cache=true，仅缓存 size: 0 的请求），适合报表类固定查询。

6. 分片与集群

6.1 分片策略

  • 主分片数量：7.x 默认 1（6.x 及更早默认 5）。合理规则：单个分片数据量控制在 10~50GB，总分片数按数据总量估算（如 300GB 数据 ≈ 10 个主分片）。
    • 分片过少：单分片查询/恢复慢，无法利用多节点并行。
    • 分片过多：每个分片都是独立的 Lucene 索引，元数据和文件句柄开销大，GC 压力大。
  • 主分片数创建后不可变：路由公式 hash(id) % 分片数 决定了它无法动态增减。要改只能 Reindex（POST /_reindex 把数据搬到新索引），或者用索引别名平滑切换。
  • 副本数量可以动态调整：PUT /index/_settings 修改 number_of_replicas，随时增减。
  • 副本上限：副本数最多为 节点数 - 1（同一份数据不能在同一个节点上有主副本两份），单节点集群配 1 个副本必然 Yellow。

6.2 副本的作用

  • 高可用：主分片故障时，副本可被提升为主分片，数据不丢、服务不中断。
  • 读扩展：查询可以负载均衡到所有主/副本分片执行，副本越多，读取吞吐越高。
  • 不承担写：索引/更新/删除请求只发主分片（副本写入由主分片转发），副本对写没有扩展作用——写瓶颈只能靠增加主分片数解决。

6.3 集群状态 Yellow 或 Red 意味着什么？如何排查？

  • Yellow：
    • 含义： 所有主分片都已分配，但至少有一个副本分片没有分配。
    • 常见原因：
      • 节点数量不足（例如，索引配置了 number_of_replicas=1，但集群只有一个节点）。
      • 新创建的索引副本分片正在初始化（短暂状态）。
      • 有节点故障，导致部分副本分片丢失（但主分片还在）。
    • 影响： 高可用性降低（丢失一个节点可能导致数据不可用），查询吞吐量可能下降（副本少）。
    • 排查： 使用 GET _cluster/allocation/explain API 查看未分配分片的具体原因；检查节点数、节点状态、磁盘空间、分片分配设置。
  • Red：
    • 含义： 至少有一个主分片没有分配（可能连带其副本也缺失）。
    • 常见原因：
      • 持有主分片的节点永久丢失，且没有可用的副本分片可以提升为主分片。
      • 磁盘空间不足导致分片无法分配。
      • 配置错误（如分片分配规则 exclude 了所有节点）。
    • 影响： 数据部分丢失或完全不可用！ 涉及该主分片的索引和搜索操作都会失败。
    • 排查： 紧急处理！立即检查 _cluster/health 和 _cat/shards?v 确认哪些索引/分片是 red。使用 GET _cluster/allocation/explain 分析未分配原因。检查节点状态、磁盘空间、日志。必要时从备份恢复或手动分配分片（风险操作）。
  • 目标： 始终追求 Green 状态。

6.4 脑裂问题

  • 定义： 在分布式系统中，当网络分区（Network Partition）发生时，集群的不同部分（节点组）可能无法互相通信。如果每个部分都认为自己是唯一可用的部分并选举出新的主节点，就会导致集群分裂成两个或多个独立运作的”脑”，各自接受写入操作，造成数据不一致和冲突。
  • ES 防止机制： 核心思想是多数派（Quorum）原则——只有包含超过半数（> N/2）主节点资格节点的节点组才能选举或维持主节点。假设有 N 个主节点资格节点：
    • 6.x 及以前（Zen Discovery）： 显式配置 discovery.zen.minimum_master_nodes = N/2 + 1（例如，3 节点集群设为 2）。
    • 7.x 起： 基于 Raft 协议的投票选举机制，discovery.zen.minimum_master_nodes 已被废弃，集群自动要求多数投票；集群首次启动时用 cluster.initial_master_nodes 列出候选主节点。
    • 8.x： 彻底移除 Zen Discovery 相关配置。
  • 效果： 网络分区时，任何节点组如果包含的主节点资格节点数不足多数（<= N/2），就无法选举新主节点或维持现有主节点状态（无法获得多数确认），从而无法提供服务或接受写操作，避免了”双主”导致的脑裂。只有拥有多数节点的分区才能正常运作。
  • 实践建议： 主节点资格节点配奇数个（生产通常 3 个专用 master 节点），并做好角色分离（7.x 起节点可配置 node.roles，把 master/data/ingest 角色分开），避免大节点既做 master 又扛数据。

dynamic 三种模式的取舍：

值 行为 适用
true（默认） 自动创建字段映射 开发期、字段完全可控
false 忽略未知字段（不索引、搜索不到） 字段不可控但不想写失败

7.2 映射爆炸

  • 定义： 当索引中包含大量唯一字段（通常是动态映射产生的）时，导致集群状态（Cluster State）变得极其庞大（可能超过数百 MB 甚至 GB），主节点在广播和维持集群状态时压力巨大，严重影响集群稳定性和性能。
  • 原因： 常见于索引日志类数据，其中每个文档都有大量不同的、不可预测的字段（如包含用户 ID 或请求 ID 的字段名）。
  • 避免：
    • 严格控制动态映射： 设置 "dynamic": "strict"（禁止未知字段）或 "dynamic": "false"（忽略未知字段，但不索引）。优先使用显式映射。
    • 限制字段总数： index.mapping.total_fields.limit 默认 1000，超限直接拒绝写入，可据此报警。
    • 使用 flattened 类型（7.2+）： 将整个 JSON 对象映射为单个 flattened 字段，避免为每个内部键创建独立字段。适用于不需要独立查询/聚合的元数据。
    • 使用 object/nested 但限制深度： 使用 index.mapping.depth.limit 控制嵌套深度（默认 20）。
    • 字段别名： 如果不同来源的字段语义相同，用别名统一映射到一个字段。
    • 合理的索引设计： 避免将差异巨大的文档类型塞进同一个索引（日志按天滚动索引也是这个道理）。

7.4 force merge、routing、index sorting

  • force merge（强制合并段）： POST /index/_forcemerge?max_num_segments=1。适合只读索引（历史归档）、删除大量文档后（真正释放磁盘空间）、以及批量导入完成后。合并是 I/O 密集型操作，不要在在线高峰对热索引执行。
  • 自定义 routing： 默认按 _id 哈希路由到分片；可通过 ?routing=user_88 指定路由键（如按用户/租户），让同一业务实体的文档落在同一分片，查询时指定 routing 只扫一个分片。代价是可能数据倾斜、routing 变化时需要 Reindex，适合租户隔离类场景。
  • index sorting（索引预排序，7.x+）： 创建索引时指定 index.sort.field（如 timestamp），写入时即按该字段排序，能显著加速时间范围查询和大范围排序（排序字段自动进入 doc_values），代价是写入性能略有下降。

8. 性能优化

8.1 Bulk API

单个请求写入性能远低于批量写入，因为每条请求都有一次网络往返和一次完整处理。Bulk API 是写入优化的第一手段：

  • 批次大小： 经验值每批 5~15MB 或 1000~5000 条（按单条大小调整），需要压测确定最优值。批次过大：占用协调节点/分片内存，单条失败整批重试代价高；批次过小：网络往返占比高，吞吐上不去。
  • 关注响应：检查响应中的 errors 字段，对失败项重试；客户端用多线程并发打满吞吐，重试用指数退避避免雪崩。
  • 配合优化：批量导入场景可临时 index.refresh_interval: -1（导入完恢复并 force merge），减少频繁 refresh 产生的小段。

8.2 段合并

  • 为什么需要： 频繁的 refresh 会产生大量小的 Lucene 段。小段过多会降低查询性能（需要打开更多文件句柄）且占用更多资源（文件描述符、内存）。删除操作只是标记文档为删除，空间不会立即释放。
  • 优点：
    • 减少段数量，提升查询速度（减少文件打开和搜索范围）。
    • 真正删除被标记删除的文档，回收磁盘空间。
    • 合并过程中优化索引结构（如压缩）。
  • 缺点：
    • 是 I/O 和 CPU 密集型操作，在合并期间可能显著影响集群性能（写入延迟、查询延迟增加）。
    • 需要额外的临时磁盘空间。
  • 调优： 默认 Tiered Merge Policy 会自动按层级合并；index.merge.scheduler.max_thread_count 默认 min(4, CPU核数/2)，机械盘环境建议调为 1；大写入任务前可临时关闭 refresh（见 8.1），完成后 _forcemerge 收尾。

8.3 doc_values vs fielddata

聚合、排序需要读取整列数据，ES 提供两种机制：

维度 doc_values fielddata
存储 列式存储，在磁盘（常驻 OS Page Cache） 内存（JVM 堆），懒加载
默认 keyword/数值/日期默认开启 默认关闭（2.0 起）
用途 聚合、排序、脚本访问 仅用于让 text 字段也能聚合（不推荐）
风险 占磁盘，可对不需要聚合的字段关闭 堆内存 OOM 的重灾区（1.x 时代默认开启，曾引发大量线上事故）

结论：聚合排序一律依赖 doc_values（配合 keyword），不要让 text 开 fielddata。确实需要对 text 做统计时，用 keyword 子字段代替。

8.4 堆内存配置

  • -Xms 与 -Xmx 设为相同值，避免运行时动态扩容触发 Full GC。
  • **不超过物理内存的 50%**（ES_JAVA_OPTS 或 jvm.options 配置），其余内存留给 OS Page Cache——段文件和 doc_values 都靠页缓存加速，这是 ES 的命根子。
  • 不要超过 32GB：超过后 HotSpot 的压缩指针（Compressed Oops）失效，指针占用翻倍，堆内存反而”缩水”。
  • 关闭 swap：bootstrap.memory_lock: true（锁内存防止被换出）。
  • 7.x 起默认使用 G1GC；indices.fielddata.cache.size 建议设置上限（默认无上限），熔断器 indices.breaker.fielddata.limit 默认保护堆的 40%。

8.6 其他常用调优

  • 磁盘水位： 磁盘使用率触发分片迁移/拒绝写入的三档阈值默认 **85% / 90% / 95%**（cluster.routing.allocation.disk.watermark.low/high/flood_stage），生产建议监控提前预警，避免集群进入只读。
  • 查询缓存： Filter 命中的结果缓存在节点级 Query Cache（默认占堆 10%，indices.queries.cache.size）；size: 0 的聚合可配 Shard Request Cache（?request_cache=true）。
  • 查询写法： 过滤条件优先进 Filter 上下文；避免 *keyword 前导通配符、宽泛正则、脚本中做重计算；深分页用 search_after（见 4.5）；multi_match 指定字段避免默认 _all 全字段检索（7.x 已移除 _all）。
  • 索引生命周期（ILM，6.6+）： 日志类数据按时间滚动索引（daily index + index.lifecycle 策略），自动完成 hot → warm → cold → delete 的分层与清理，从机制上解决索引无限增长。

9. 数据同步

业务数据的主源在 MySQL，ES 需要一份副本用于搜索，这就产生了同步问题。三种主流方案对比：

维度 Logstash（JDBC 插件） Canal（binlog 订阅） 应用双写
原理 定时轮询执行增量 SQL（sql_last_value 记录游标） 伪装 MySQL 从库解析 binlog，解析成事件后重放给 ES 业务代码写 MySQL 的同时写 ES（或发消息异步写）
实时性 秒级~分钟级（取决于轮询间隔） 准实时（binlog 推送，毫秒级） 实时
对源库侵入 无侵入（只读查询） 需开启 binlog_format=ROW，连接占用 侵入业务代码
删除同步 无法感知 DELETE（只能同步存在的数据） 天然携带 delete 事件，可同步删除 需业务显式处理删除
实现成本 最低（配置即用） 中（Canal + 自研/现成消费者） 低（代码内实现）
适用 读多写少、实时性要求不高的搜索索引 中大型系统、需要严格实时同步 小项目、团队可控的快速方案

9.1 推荐架构

  • 方案 A（首选，通用场景）： MySQL（binlog，ROW 格式）→ Canal → Kafka → 消费端（Logstash 或自研消费者）→ ES。先做一次全量初始化（快照 + Reindex），再切增量。优点是实时、不侵入业务、削峰（写入峰值被 Kafka 缓冲）、解耦。
  • 方案 B（双写 + MQ）： 业务代码先写 MySQL，成功后发消息到 MQ，消费者异步写 ES。注意不能在”一个事务里同时写 MySQL 和 ES”（跨库事务不可行），ES 写入失败绝不能回滚数据库。
  • 方案 C（快速起步）： 小项目直接用 Logstash JDBC 轮询，接受分钟级延迟和”不支持删除同步”的局限（删除用软删字段兜底）。

9.2 一致性兜底

双写/异步同步的本质是最终一致性，必须配套兜底：

  • 重试：写 ES 失败的消息进重试队列（指数退避），超过次数进死信队列人工处理。
  • 幂等：写 ES 用业务主键作为 _id，重复投递时 upsert 覆盖，天然幂等。
  • 对账：定时任务按更新时间段扫描 MySQL，与 ES 对比，发现缺失/不一致就补同步——这是最后防线，不能省。

10. 常见面试题速答

Q1：ES 为什么查询快？
倒排索引直接定位词项（O(1) 级查找），不用全表扫描；数据分片后可跨节点并行查询，协调节点合并；段文件和 doc_values 常驻 OS Page Cache，读基本不落盘；近实时架构避免了实时索引带来的写入阻塞。

Q2：为什么 ES 是”近实时”而不是实时？
写入先进内存 Buffer + Translog，要等默认 1 秒一次的 Refresh 生成新 Segment 才对搜索可见。Translog 只保证不丢数据，不保证可见性。refresh=true 可强刷但牺牲性能。

Q3：match 和 term 有什么区别？
match 会把查询串分词后做全文检索，用于 text 字段；term 不分词，按词项整体精确匹配，用于 keyword/数值字段。对 text 字段用 term 常常查不到（text 已按词项索引，term 拿完整字符串去匹配必然落空）。

Q4：深分页为什么慢？怎么解决？
from+size 需要协调节点收集每个分片的 from+size 条结果再排序，from 越大开销越大，且 max_result_window 默认上限 10000。实时翻页用 search_after（需唯一排序键），导出数据用 scroll（快照语义、非实时）。

Q5：text 字段能直接聚合/排序吗？
不能。聚合/排序依赖列式存储 doc_values，text 默认没有（fielddata 默认也关闭，且堆内存开销巨大）。做法是给字段配 keyword 子字段，用 field.keyword 聚合。

Q6：索引建好后主分片数还能改吗？
不能。分片数参与路由公式 hash(id) % 分片数，改了路由就失效。要调整只能 Reindex 到新索引（新索引别名平滑切换，注意建别名防止写入断流）。所以分片数要在创建前按数据量估算好（单分片 10~50GB）。

Q7：中文搜索怎么分词？
ES 自带 standard 分词器对中文是按单字切分，效果差。生产中常用 IK 分词器：ik_max_word 做最细粒度切分（召回高，用于索引），ik_smart 做最粗粒度切分（精确，用于搜索），再配合扩展词典维护行业词库。

Q8：写入 ES 的数据丢了怎么办？
分情况：节点重启丢数据 → 重放 Translog 恢复；节点永久宕机 → 副本提升为主分片，不丢；若主分片和副本同时丢失则数据真丢，只能从快照（_snapshot）或源库 MySQL 重建（所以业务主存永远在 MySQL，这也是第 9 节同步架构存在的原因）；写入端对失败的 Bulk 批量重试。ES 的可靠性设计是”防丢失 + 可重建”，不是数据库级的强一致。

复习路线：第 12 节讲清”是什么”，第 35 节讲清”怎么写入、怎么查、怎么统计”，第 6~8 节讲清”怎么扩容、怎么优化”，第 9 节解决”数据从哪来”，第 10 节是速答版。面试按这个顺序复述即可覆盖绝大多数 ES 问题。

1. Redis 是什么

本节回答一个问题：Redis 在整个技术栈里是什么位置，什么场景该用它、什么场景不该用它。

1.1 定位

Redis（REmote DIctionary Server）是一个基于内存的键值数据库，2009 年由 Salvatore Sanfilippo（antirez）发布，用 C 语言实现。它和传统数据库的本质区别是：数据主要放在内存里，读写是微秒到亚毫秒级；而 MySQL 这类磁盘数据库，读写是毫秒级。单实例吞吐量在万级 QPS 到十万级 QPS 之间（取决于数据规模与命令复杂度），是 MySQL 单库的几十倍到上百倍。

它同时具备以下能力，这也是它长盛不衰的原因：

  • 丰富的数据类型：String、List、Hash、Set、ZSet，以及基于它们扩展的 Bitmap、HyperLogLog、Geo、Stream（5.0 引入）。
  • 持久化：内存数据可以落盘（RDB 快照 / AOF 日志），重启不丢数据。
  • 分布式能力：主从复制、哨兵（Sentinel）、Cluster 分片（3.0 引入）。
  • 原子操作：单线程执行命令，天然没有并发竞争，INCR、Lua 脚本、MULTI/EXEC 都基于此。
  • 功能组件：分布式锁、发布订阅、延迟队列（ZSet + 轮询）、限流（INCR + 过期）等。

版本演进中与本文相关的重要节点：

1.2 与 MySQL 的对比

维度 Redis MySQL
存储介质 内存为主 磁盘为主
数据模型 键值 / 简单结构 关系模型（表、行、SQL 关联）
查询能力 按 key 操作，支持有限的范围/集合查询 复杂 SQL、多表关联、索引优化

持久化 可选，RDB/AOF（可能丢失少量数据） 默认持久化，可靠落盘
扩展方式 内存分片，水平扩展简单 分库分表、读写分离，成本高

1.3 与 Memcached 的对比

Memcached 是最早的分布式内存缓存，至今仍有使用场景，但 Redis 在功能上几乎是它的超集：

维度 Redis Memcached
数据类型 String、List、Hash、Set、ZSet 等 仅 String
持久化 支持（RDB / AOF / 混合） 不支持，重启即丢
线程模型 命令执行单线程（6.0 起网络 IO 多线程） 多线程
淘汰策略 8 种（LRU / LFU / TTL / 随机等） 仅 LRU
分布式 官方 Cluster 分片 依赖客户端一致性哈希（如 memcached 客户端、Twemproxy）
扩展功能 锁、队列、Stream、发布订阅、脚本 无
内存效率 复杂数据结构有一定额外开销 简单 KV，内存利用率高

结论：功能需要丰富、需要持久化、需要分布式能力时选 Redis；如果场景就是”极简单的 KV 缓存、数据丢了无所谓、追求极致内存效率”，Memcached 仍是合理选择。现实中绝大多数新项目直接用 Redis。

1.4 何时用、何时不用

适合用 Redis 的场景：

  • 缓存：热点数据、接口结果、会话（Session）—— 缓存命中率高的数据收益最大。
  • 计数器与实时统计：播放量、点赞、在线人数、排行榜（ZSet）。
  • 短生命周期数据：验证码、限流窗口、临时标记，配合 TTL 自动清理。
  • 分布式协调：分布式锁、分布式 ID（INCR 或 LUA）、消息队列（Stream）。
  • 数据规模可控的热数据：能放进内存的才谈得上性能优势。

不适合用 Redis 的场景：

  • 强一致性业务数据：订单、账户余额等需要事务和 ACID 的，MySQL 或专用存储更合适。
  • 复杂查询：多条件关联查询、报表分析，Redis 的数据模型支持不了，应该用关系库或 ES。
  • 超大、低频访问的数据：几十 TB 全放内存成本过高，且访问频率低时没有收益。
  • 高吞吐、需可靠持久化的消息系统：Stream 能解决一部分，但吞吐和可靠性上限不如 Kafka。

本节小结：Redis 是”内存优先、类型丰富、可持久化、可分布式”的高性能键值存储，定位是数据库的加速器与分布式协调器；它不替代数据库，而是与数据库配合。

2.3 String 的底层：SDS（Simple Dynamic String）

C 语言字符串以 \0 结尾，获取长度要遍历、不能存二进制数据、拼接容易缓冲区溢出。Redis 因此实现了 SDS，结构大致是：

SDS 相比 C 字符串的四个优势：

  1. O(1) 获取长度：STRLEN 直接读字段，不用遍历。
  2. 二进制安全：以 len 判断字符串结束，不依赖 \0，可以存图片、序列化对象等任意二进制。
  3. 杜绝缓冲区溢出：修改前检查 alloc，不足自动扩容；扩容采用空间预分配（新容量小于 1 MB 时翻倍，大于 1 MB 时额外加 1 MB），减少内存重分配次数。
  4. 惰性空间释放：缩短字符串时不立刻归还内存，留待后续拼接复用。

版本细节：Redis 3.2 之前只有一种 sdshdr；3.2 起按长度分为 sdshdr5/8/16/32/64 五种，小字符串用小 header，节省内存。String 的三种编码：整数值直接用 int（INCR 是纯算术操作）；字符串 ≤ 44 字节用 embstr（redisObject 和 SDS 一次性分配在一块连续内存，省一次内存分配）；更长用 raw（两次分配）。注意 embstr 是只读的，一旦修改就升级为 raw。

2.4 List 的底层：quicklist

纯双向链表每个节点要存 prev/next 指针，内存碎片多；纯 ziplist 又存在连锁更新问题。所以 Redis 3.2 引入 quicklist：一个双向链表，每个节点内部是一个 ziplist（7.0 起改为 listpack），两头兼顾：

  • 链式结构保证头尾操作 O(1)；
  • 节点内部压缩存储，减少指针开销和碎片；
  • list-max-listpack-size（7.0 起）控制每个节点最多存多少元素，元素很多或很大会自动拆新节点。

2.5 Hash / Set / ZSet 的小数据优化：ziplist → listpack

Hash、Set、ZSet 在数据量小时都使用紧凑编码而非哈希表或跳跃表，目的是省内存（哈希表的桶和指针开销远超数据本身）。Redis 7.0 之前是 ziplist，7.0 起全面替换为 listpack。

ziplist 的缺陷——连锁更新（cascade update）：ziplist 中每个元素都记录了前一个元素的长度（prevlen：前一个元素长度小于 254 字节时占 1 字节，否则占 5 字节）。问题出在这里：在某元素前插入一个新元素，可能导致该元素的”前一个元素长度”从 1 字节膨胀为 5 字节，元素本身变大，又引发下一个元素的 prevlen 变化……形成链式反应。最坏情况下，一次插入需要重新分配整个 ziplist 的内存，时间复杂度退化到 O(n²)。

listpack 的解决方案：元素不再记录前一个元素的长度，每个元素只在尾部记录自身的编码和长度（backlen），元素之间完全独立。任意元素的修改只影响自身，从机制上消除了连锁更新。

对比维度 ziplist listpack
元素布局 记录前一个元素的长度（prevlen） 只记录自身长度，且放在元素尾部
连锁更新 存在，最坏 O(n²) 不存在
内存开销 正常情况更紧凑 每个元素多一个 backlen 字段，略高
状态 7.0 起移除 7.0 起全面使用

连锁更新发生的概率并不高（要求一连串元素长度都在 254 字节附近），但代价是灾难性的，且难以排查。7.0 用 listpack 一劳永逸地解决，同时减少了 60% 左右的极端内存消耗——这是 7.0 最值得关注的存储层改进。

2.6 ZSet 的底层：跳跃表

ZSet 在数据量超过阈值（7.0 默认 128 个 entry 或 value 超过 64 字节）时，使用 跳跃表 + 哈希表 的组合：

  • skiplist：按 score 排序的有序链表结构，支持范围查询（ZRANGEBYSCORE）和按 rank 访问；
  • hashtable：按 member 到 score 的映射，让 ZSCORE 达到 O(1)（只靠 skiplist 需要 O(log n)）。

跳跃表本质是多层链表：每个节点以固定概率（Redis 用 p = 1/4）随机决定层数（最高 32 层），高层的”快车道”让查找可以跳跃前进，查找复杂度 O(log n)。为什么不用红黑树/AVL 树：

  1. 实现简单：插入/删除只改指针，没有旋转调整，代码量小、不易出错；
  2. 范围查询天然友好：ZSet 的核心场景是”按分数范围取一段”，skiplist 的链表结构从头到尾遍历即可，树需要中序遍历；
  3. 内存开销可预期：节点层数随机但期望值可控（约 1/(1-p) = 1.33 个指针/节点）。

2.7 Hash / Set / ZSet 的底层：哈希表与渐进式 rehash

大数据量的 Hash、Set、ZSet 底层都是 dict（哈希表）。Redis 的 dict 有两个哈希表 ht[0]、ht[1]，平时只用 ht[0]，rehash 时用 ht[1]，并用 rehashidx 记录迁移进度。

触发时机：

  • 扩容：负载因子 = used / size。没有子进程做持久化时，负载因子 ≥ 1 触发扩容（容量翻倍）；有 BGSAVE/BGREWRITEAOF 子进程时，负载因子 ≥ 5 才触发——子进程与父进程共享内存页（写时复制），此时再扩容会加剧内存页复制，代价很大。
  • 缩容：负载因子 < 0.1 时触发（4.0 引入的规则）。

渐进式 rehash 的过程：不是一次搬完所有桶（几十万条数据一次搬迁会阻塞主线程），而是：

  1. 为 ht[1] 分配容量为 ht[0] 两倍的新哈希表；
  2. rehashidx 从 0 开始，每次增删改查操作顺带迁移一个桶（把 ht[0] 中该桶的元素重新散列到 ht[1]）；
  3. 迁移期间查找需要查两张表；新插入的 key 一律写 ht[1]；
  4. 迁移完成，ht[0] = ht[1]，rehashidx 置回 -1。

Redis 7.0 做了优化：空闲时由后台定时任务持续推进 rehash，避免大哈希表在极低负载下迁移卡住。这也是面试常问的”Redis 单线程为什么不怕大集合操作”的部分答案——迁移被摊薄到每次命令里，单次命令的延迟增量很小。

3. Redis 事务、Lua 脚本与管道

单个命令天然原子，但业务经常需要”多条命令一次性搞定”。Redis 为此提供了三件武器：事务（MULTI/EXEC）、Lua 脚本、Pipeline。它们经常被混为一谈，其实语义边界完全不同：**事务提供”整体提交”，Lua 提供”真正的原子性”，Pipeline 只提供”网络上的批量”**。本节逐个讲清楚，并给出限流、扣库存等可复用的脚本。

3.2 Lua 脚本

Redis 内置 Lua 5.1 解释器，允许把一段脚本交给服务端执行。脚本执行期间服务器不处理任何其他请求，天然原子——这是 Redis 能把复杂 CAS 逻辑原子化的唯一途径（命令单线程是前提，见第 4 节）。

基础用法：

3.3 Pipeline

原理：网络往返（RTT）是吞吐的最大敌人——单条命令要”发命令 + 等回复”一次 RTT，局域网下约 0.1~0.5ms，1000 条命令串行执行就是 1000 个 RTT。Pipeline 把多条命令一次性发给服务端，服务端连续执行并缓存全部回复，一次性收回，1000 条命令只花 1 个 RTT。对”批量写缓存、批量预加载”这类场景是数量级的提升：

注意三点：第一，Pipeline 不保证原子性——命令只是”打包传输”，服务端仍逐条执行，期间其他客户端的命令可以穿插；第二，依赖上一条结果的命令不能进 Pipeline（比如”先 GET 再按结果 SET”），这类逻辑用 Lua；第三，单批命令量要控制（一次几万条会撑爆客户端发送缓冲与服务端回复缓冲），分小批发送并及时收集返回值。

4. 为什么快

本节回答一个高频面试题：Redis 为什么能达到十万级 QPS。核心是四件事叠加：数据在内存、数据结构高效、单线程事件循环、轻量协议。少了任何一个，性能都到不了这个量级。

4.1 四个因素

第一，数据在内存。 读写不涉及磁盘寻道和机械 I/O，这是秒杀 MySQL 的基础。但只有内存还不够——Memcached 也是纯内存，所以还要看后面三条。

第二，数据结构是针对场景定制的。 如第 2 节所述，SDS 让长度和拼接是 O(1)，listpack/quicklist 让紧凑存储与高效操作兼得，跳跃表让范围查询 O(log n)。绝大多数字典操作是 O(1)，且实现上做了大量内存局部性优化（如 set 内部按 key 偏移 的内存分配优化）。

第三，单线程事件循环。 Redis 的命令执行是单线程的（网络 IO 的读写部分从 6.0 起可以多线程，见 4.3），这意味着：

  • 没有锁竞争：所有命令天然串行，不存在”两个线程同时改一个数据结构”；
  • 没有上下文切换：CPU 时间全部花在业务上；
  • 命令原子：INCR、Lua 脚本不需要额外加锁就是原子的，这是分布式锁能建立在 Redis 上的前提。

第四，I/O 多路复用。 Redis 用单个线程同时监听成千上万个 socket 连接，由操作系统内核在事件发生时通知（而非逐个轮询询问）。实现层面，Redis 在 Linux 上使用 epoll，macOS/BSD 上使用 kqueue，无法使用二者时退化为 select，通过 ae_epoll.c / ae_kqueue.c / ae_select.c 隔离平台差异。

4.2 单线程的代价：慢操作清单

单线程的代价是一个慢命令会阻塞所有后续命令。以下操作必须警惕：

  1. bigkey 的读写与删除：写入大 key 要分配大块内存，删除大 key 要释放大块内存（4.0 起删除已异步化，见下；BigKey 的发现与治理见第 8 章）；
  2. O(N) 且 N 很大的命令：KEYS、SORT、SUNION、ZUNIONSTORE、LRANGE key 0 -1；
  3. 大量 key 集中过期：过期清理在命令间隙执行，同一秒过期百万 key 会卡顿；
  4. 内存淘汰：写满后每次写入都要先淘汰，频繁触发会拖慢写入；
  5. AOF 刷盘 always 模式：每次写命令都同步 fsync 到磁盘，磁盘速度远慢于内存；
  6. 主从全量同步：fork 生成 RDB 的瞬间会阻塞主线程，实例越大阻塞越久。

应对手段分两层。业务层：用 SCAN 代替 KEYS、拆散 bigkey、过期时间加随机抖动、控制 AOF 刷盘策略。框架层（Redis 本身）：

  • 4.0 引入 lazy-free：UNLINK 和 unlink/lazyfree-lazy-eviction/lazyfree-lazy-expire 等配置，把大内存释放放到后台线程（bio 线程），主线程只做”摘除引用”；
  • 6.0 引入网络 IO 多线程，见下。

4.3 6.0 多线程的边界

6.0 的多线程只做 socket 的读写（把数据从内核缓冲读到客户端缓冲区、把回复写回 socket），命令的解析与执行仍然是单线程。默认关闭，开启方式：配置 io-threads 4（建议不超过 CPU 核数，一般设为核数的一半），读线程还需要 io-threads-do-reads yes（默认只启用写线程）。

为什么只并行 IO、不并行命令执行？因为全部数据结构（dict、skiplist 等）都不是线程安全的，让命令并行执行就得给每个操作加锁：锁竞争会抵消多核收益，还丢掉”命令天然原子”这个核心卖点。而网络读写是纯内存拷贝、无共享状态，正好适合并行，能释放 CPU 在网卡吞吐上的瓶颈。实测在万级连接、大 payload 场景收益明显，普通小命令场景提升有限。

一句话概括：**6.0 用多线程解决”网络吞吐”瓶颈，用单线程保住”执行原子性”**。

本节小结：内存 + 定制数据结构 + 单线程事件循环 + 轻量协议构成 Redis 高性能的完整解释；性能上真正的敌人是慢命令和 bigkey，6.0 的线程模型只在网络层并行、命令执行保持单线程是有意为之的设计边界。

5. 持久化

本节回答一个问题：内存数据断电即失，Redis 靠什么机制保证重启后数据还能恢复，以及每种机制各丢失多少数据。

5.1 RDB：某一时刻的内存快照

RDB 是二进制快照，把某一时刻所有 key 的完整数据序列化到 dump.rdb 文件。生成方式：

  • SAVE：同步阻塞，生成期间不服务任何请求，只用于手动备份；
  • BGSAVE：fork 子进程，子进程生成快照，主进程继续服务（推荐方式）；
  • 自动触发：满足配置条件时后台生成，例如默认配置 save 900 1（900 秒内至少 1 次写入）、save 300 10、save 60 10000；
  • 其他触发点：从节点首次全量复制时、执行 shutdown 时。注意 FLUSHALL 本身不会生成 RDB，但如果之后触发了持久化，会生成一个空的快照，把此前所有数据”洗掉”——生产环境慎用。

写时复制（Copy-On-Write） 是 RDB 不阻塞服务的关键：

  • fork 瞬间子进程与父进程共享全部内存页，此时几乎无额外内存开销（fork 本身的开销来自页表复制，实例越大越久）；
  • 父进程随后收到写请求时，操作系统将被修改的内存页复制一份，父进程在副本上修改，子进程读到的仍是 fork 时刻的原始页；
  • 因此子进程看到的始终是 fork 瞬间的一致性快照，RDB 文件是原子一致的。

RDB 的优缺点：

  • 优点：文件小、加载快（直接二进制载入）、适合做离线备份与全量迁移。
  • 缺点：丢失窗口大——两次快照之间写入的数据全部丢失（默认配置下最长约 15 分钟）；fork 瞬时阻塞与写时复制的内存翻倍压力；文件是二进制，不可读不可细粒度修复。

5.2 AOF：追加写命令日志

AOF（Append Only File）不存数据，记录所有写命令本身，恢复时逐条重放。流程：写命令先追加到内存缓冲 aof_buf，事件循环结束前调用 write(2) 写入内核缓冲区，是否真正落盘由 appendfsync 决定：

appendfsync 行为 数据丢失窗口 性能
always 每个写命令都 fsync 落盘 最多丢失一次写操作 最差（磁盘速度是瓶颈）
everysec（默认） 每秒异步 fsync 一次 最多 1 秒的写入 好，推荐
no 交给操作系统决定刷盘时机 不确定，可能较多 最好

AOF 重写（rewrite）：AOF 会无限增长，需要压缩。重写是直接基于当前内存中的数据生成所需的写命令，而不是读取旧 AOF 文件做命令合并——这是理解重写高效性的关键。重写流程（BGREWRITEAOF）：

  1. fork 子进程，基于当前内存数据生成命令，写入临时文件（不碰原 AOF，因此失败也不会污染原文件，删除临时文件即可）；
  2. 重写期间父进程把新写入的命令同时记入 aof_rewrite_buf；
  3. 子进程完成后，父进程把 aof_rewrite_buf 中的增量命令追加到临时文件末尾，然后 rename(2) 原子替换原 AOF 文件。

触发条件：手动 BGREWRITEAOF，或自动满足 aof-rewrite-percentage 100（上次重写后文件体积翻倍）且超过 aof-rewrite-min-size 64mb。

AOF 文件的修复：文件损坏时启动会失败，用 redis-check-aof --fix appendonly.aof 修复（RDB 对应 redis-check-rdb）。

5.3 混合持久化（4.0 引入）

aof-use-rdb-preamble yes（5.0 起默认开启）后，AOF 文件 = RDB 快照头部 + 增量命令尾部：

  • 启动恢复时，先直接加载 RDB 部分（快），再重放尾部少量命令，恢复速度接近 RDB，丢失窗口接近 AOF；
  • 代价：文件头部是二进制，人不可读；文件依赖生成它的 Redis 版本，低版本无法加载高版本的混合文件，做跨版本迁移时要小心。

5.4 三者对比与选择

维度 RDB AOF 混合（4.0+）
内容 二进制快照 可读的写命令 RDB 头 + AOF 尾
文件体积 小 大 中
恢复速度 快 慢（逐条重放） 快（先载 RDB 再重放少量命令）
数据丢失 两次快照之间（默认最长约 15 分钟） everysec 最多 1 秒 / always 最多 1 次命令 接近 AOF
可读性 二进制 可读可审计 头部不可读
加载优先级 低（仅当 AOF 关闭时加载） 高（开启 AOF 时优先） 同 AOF

决策建议：

  • 可容忍分钟级数据丢失、看重恢复速度 → 只开 RDB，定期备份；
  • 要求秒级丢失窗口（大多数业务）→ 默认配置即可：AOF everysec + 定期 RDB 备份；
  • 追求两者兼顾 → 开启混合持久化，同时保留定时 RDB 做异地容灾；
  • 无论哪种方案，都建议定期做一次 RDB 备份并离线存放——AOF 重放依赖命令可读，文件被意外破坏时 RDB 是最后的退路。

本节小结：RDB 快照适合备份与迁移，AOF 日志适合细粒度恢复，混合持久化在 4.0 之后成为两全其美的主流选择；写时复制让 RDB 不阻塞服务，临时文件 + 原子替换让 AOF 重写安全无污染。

6. 高可用与集群

本节回答一个问题：单机 Redis 挂了怎么办，数据量超出单机内存怎么办。答案沿两条线展开：复制解决单点故障（主从 → 哨兵），分片解决容量上限（Cluster）。

6.1 主从复制

主从复制的目的：数据冗余（主挂了有副本）+ 读写分离（读请求分流到从节点）。核心机制是异步复制：

  • 全量同步：从节点第一次连接主节点，或主从链路断开太久（从节点的 offset 已不在 repl_backlog 缓冲内）。主节点 BGSAVE 生成 RDB 发给从节点，期间的新写命令记录在 repl_backlog（环形缓冲）中，RDB 发送完后再补发增量。
  • 增量同步（部分重同步）：从节点断线重连后，把自己的 replid 和复制偏移量 offset 发给主节点；主节点校验 offset 仍落在 repl_backlog 内，就把 offset 之后的命令直接补发，不用重新传 RDB。

版本节点：2.8 引入 psync 支持部分重同步；4.0 的 psync2 让从节点重启后、以及主从切换后也能尝试部分重同步（旧的 replid 会被记住）。

注意事项：

  • 复制是异步的，主从存在延迟，从节点可能读到稍旧的数据，强一致场景不能读从库；
  • 复制拓扑常用一主多从或主-从-从级联（减少主节点的 RDB 分发压力）；
  • repl-backlog-size（默认 1 MB）太小，从节点短暂断线就可能退化为全量同步。

6.2 哨兵

主从复制本身不解决”主节点挂了自动切换”。哨兵（2.8 引入，独立于数据节点的特殊 Redis 进程）负责：监控、通知、自动故障转移、对外提供最新主节点地址。

故障转移流程：

  1. 主观下线（sdown）：某个哨兵发现主节点心跳超时，标记为疑似下线；
  2. 客观下线（odown）：quorum（可配置，如 2）个哨兵都确认后，判定主节点真挂了；
  3. 选举 leader 哨兵：哨兵之间用类似 Raft 的算法选出 leader，负责本次转移；
  4. 选新主：从健康的从节点中，优先选复制偏移量最大（数据最新）的，其次按 runid 排序；
  5. 切换：新主升为主，其余从节点改为复制新主，通知客户端。

部署要点：哨兵自身要防单点，至少 3 个哨兵（奇数），quorum 通常设为 2，哨兵与数据节点分开部署。客户端不直接连主节点，而是先问哨兵 sentinel get-master-addr-by-name，主节点切换后重新获取地址。

6.3 Cluster 分片（3.0 引入）

哨兵模式下只有一个节点能写，单机内存就是容量上限。Cluster 把数据分片到多个主节点，每个主节点配若干从节点做高可用。

核心机制：

  • 槽位（slot）：整个集群固定 16384 个槽，key 通过 CRC16(key) % 16384 定位到槽，槽均匀分配给各主节点（如 3 主各约 5461 个槽）；
  • 路由：客户端访问某个 key 时，如果槽不在当前节点，节点返回 MOVED（槽已归属其他节点，客户端要更新本地路由表）；迁移期间返回 ASK（槽正在迁移，仅本次请求去目标节点，路由表不必更新）。客户端库（JedisCluster、Lettuce、Redisson）封装了这套逻辑；
  • 集群内通信：节点间用 gossip 协议（PING/PONG 心跳）交换槽位与节点状态，节点规模通常不超过 1000 个。16384 而不是 65536 个槽，就是因为槽位信息要打包进心跳消息（16384 槽的 bitmap 约 2 KB），槽越多消息越大；
  • 故障转移：与哨兵类似，从节点监测主节点失联后发起选举，多数派通过后升级为主；
  • 可用性边界：某槽的主节点和从节点全部挂掉时，集群默认停止服务（除非配置 cluster-require-full-coverage no 容忍部分不可用）。

使用约束：跨槽的多 key 操作不受支持（MGET a b 如果两个 key 落在不同槽会报错），可以用 hash tag 强制 key 归槽：{user123}:cart 和 {user123}:orders 都只对 user123 算哈希，从而落在同一槽，多 key 操作就可行。

6.4 三种架构选型

维度 主从复制 哨兵 Cluster
数据分片 无（每节点全量数据） 无 16384 槽分片
自动故障转移 无（需手动切换） 有 有
写容量 单点写 单点写 多主并发写
数据容量 单机内存 单机内存 接近所有主节点内存之和
客户端要求 普通客户端 支持 sentinel 协议 支持 cluster 协议的客户端库
适用规模 读多写少、可容忍手动切换 小规模、需要自动切换 数据量或写入量超单机

决策建议：数据量在一台机器的内存范围内，用哨兵（主从 + 自动切换）；数据量注定超过单机内存、或写入 QPS 超单机上限，直接上 Cluster（6 节点起步：3 主 3 从）。不要先主从后迁移 Cluster，成本高。

本节小结：复制解决数据冗余、哨兵解决自动故障转移、Cluster 在两者之上解决容量水平扩展，三者层层叠加；对绝大多数业务，最终形态是”Cluster 分片 + 每分片一主一从”或”哨兵托管的一主多从”。

想动手验证以上机制（docker-compose 搭建主从、哨兵配置与故障转移、分片集群创建与 MOVED 重定向），见文末附录《Redis 集群搭建实操》。

7. 缓存实战

本节回答一个问题：把 Redis 当缓存用，会遇到穿透、击穿、雪崩三类异常，分别怎么防、方案之间怎么选。先讲两个前置机制（过期删除与内存淘汰），因为它们是很多异常的底层诱因。

7.1 前置：过期键删除与内存淘汰

过期键的删除策略（针对带 TTL 的 key）：

  • 惰性删除：key 被访问时检查是否过期，过期则删除。省 CPU，但过期 key 会残留在内存里。
  • 定期删除：定时任务（默认每秒 10 次）随机抽查一批带过期时间的 key，删除其中过期的。配合惰性删除，让过期 key 不会长期占用内存。
  • 因此大量 key 设置了同一过期时间时，定期删除会在同一时刻集中工作，这是”雪崩”的一个诱因，也解释了第 4 节说的”集中过期阻塞主线程”。

内存淘汰策略（针对内存写满，maxmemory 达到上限）：不涉及过期时间，纯粹按策略逐出 key 腾出空间。

数据范围 策略 说明
全部 key allkeys-lru 淘汰最近最少使用（maxmemory-policy 默认就是这个）
全部 key allkeys-lfu 淘汰最不常使用（4.0 引入）
全部 key allkeys-random 随机淘汰
带过期时间的 key volatile-lru 在设置了 TTL 的 key 中按 LRU 淘汰
带过期时间的 key volatile-lfu 在设置了 TTL 的 key 中按 LFU 淘汰
带过期时间的 key volatile-random 在设置了 TTL 的 key 中随机淘汰
带过期时间的 key volatile-ttl 淘汰剩余 TTL 最短的
不淘汰 noeviction 写满后拒绝写入并报错（缓存场景不要用）

LRU 与 LFU 的选择：访问呈”突发热点”用 LRU（Redis 的近似 LRU，采样淘汰，不是严格 LRU）；访问呈”长期频次差异”（如部分 key 每天都高频）用 LFU，避免一次性突发数据把长期热数据挤掉。

7.2 缓存穿透

定义与根因：请求查询的 key 数据库中根本不存在，缓存里自然也没有，请求每次都穿透缓存直达数据库。攻击者或程序 bug 用随机/越界 ID（如 -1、999999999）批量请求时，数据库会被无效查询打垮。

方案一：空值缓存

数据库返回 null 时，把一个”空值占位对象”缓存一段时间，后续同样请求命中占位对象直接返回 null。注意：直接缓存 null 无法区分”缓存里没有”与”数据库也没有”，所以要用一个可序列化的标记对象：

方案二：布隆过滤器

布隆过滤器（Bloom Filter，1970 年由 Burton Bloom 提出）是一个空间极省的”存在性判断”结构：用 k 个哈希函数把元素映射到位数组的 k 个位置并置 1。查询时检查这 k 个位：任何一个为 0，元素一定不存在；全为 1，元素可能存在（有误判）。要点是：不会漏报（false negative），但可能误报（false positive），且不支持删除。放在缓存前面，先过滤掉”肯定不存在”的 key，数据库就几乎接不到无效查询。

位数组大小 m 与哈希函数个数 k 的选择公式（n 为预估元素数，p 为可接受误判率）：

  • m = -n·ln(p) / (ln2)²
  • k = (m/n)·ln2 ≈ 0.7·m/n

例如预估 100 万元素、误判率 1%，约需 1.15 MB 位数组、7 个哈希函数。

方案三：基础防护

增强请求参数复杂度（ID 用 UUID 而非自增可猜），做格式与合法性校验，配合接口限流（每 IP 每接口每秒 N 次）与短 TTL 空值。

空值缓存 每个不存在的 key 都要占缓存空间 无 最简单 key 空间小、非法请求量不大
布隆过滤器 固定 1~2 MB 级 有（只误报不漏报） 中（需预热/同步） 全量 key 集合已知且有限
参数校验 + 限流 无 无 简单 任何场景都应做的兜底

推荐组合：参数校验/限流是底线；key 集合有限且稳定时，用布隆过滤器拦掉绝大多数无效请求，再叠加”短 TTL 空值”消化误判与新增数据。空值 TTL 要短（分钟级），布隆过滤器要防”漏同步”（新增 key 必须及时 insert）。

推荐：一般场景用互斥锁（实现简单、一致性有保证，等待时间 = 重建时间，通常毫秒级）；热点 key 重建耗时很长（秒级）且读并发极高的场景（如首页大促）用逻辑过期，接受短暂旧值换取零等待。两者也可叠加”热点 key 永不过期 + 后台定时刷新”作为第三选择。

7.4 缓存雪崩

定义与根因：大量 key 在同一时刻集体失效（或 Redis 整体宕机），请求全部打到数据库，数据库压力骤增直至打垮。常见诱因：批量 key 设置了相同的过期时间（如整点缓存、setex(key, 3600, v) 且 key 在同一批写入）。

方案一：过期时间加随机抖动

方案二：多级缓存：Redis 前面加一层本地缓存（Caffeine/Guava Cache），Redis 挂了或 miss 时命中本地缓存，把穿透压力分摊掉。注意本地缓存要控制容量与一致性（短 TTL 即可；本地缓存的参数语义与两级缓存一致性设计见第 11 章）。

方案三：限流降级：网关或接口层做熔断/限流（Sentinel、Resilience4j），数据库压力过大时快速失败或返回默认值，保护数据库不被打垮。

方案四：高可用：Redis 用哨兵/Cluster 部署，避免单点宕机；数据库侧做好连接池与慢查询治理。

推荐组合：错峰过期（方案一）是成本最低的必做项；核心业务加本地缓存兜底；接口层限流是最后防线。

8. HotKey 与 BigKey

上一章解决”缓存层与存储层”之间的关系问题；这一章讨论 Redis 自身的两种”数据畸形”：HotKey（访问倾斜）与 BigKey（容量畸形）。前者打满 CPU 与网卡，后者拖垮内存与主从同步，是两类高发生产事故的根源。

8.1 HotKey

什么是 HotKey：某个 key 的访问量远超平均水平。典型场景：明星热搜、秒杀商品、热帖详情。极端情况下单个 key 的 QPS 能占到全实例的 80% 以上——集群其他节点很闲，一个节点被热点打穿，该节点宕机又可能引发连锁雪崩。判断标准：单 key QPS 显著高于实例平均（经验值：单 key QPS 超过实例总 QPS 的 10%~20% 就该治理）。

方案二：读写分离。从节点分担读流量，把热点读分流到多台从机——但只是线性扩容，治标不治本，热点 QPS 继续上涨依然会打满所有从机。

8.2 BigKey

什么是 BigKey：单个 key 的 value 过大。经验阈值（团队可自行约定）：String > 10 KB，或 Hash/List/Set/ZSet 元素数 > 5000 且整体 > 1 MB。注意与”紧凑编码的小对象”区分——listpack 阈值内的对象都没问题，问题出在”单 key 数据量超出单次操作的安全范围”。

危害（对照第 4.2 节的慢命令清单）：

  1. 阻塞主线程：读一个大 String 要把整块内存序列化并复制，写一个大 key 要分配大块内存，耗时随体积线性增长，单线程下阻塞期间所有请求都卡住；
  2. 打满带宽：一次读就传输几 MB，QPS 稍高网卡立刻打满，拖累同实例所有其他命令；
  3. 主从同步异常：全量同步时 RDB 体积变大，增量同步传播变慢，从节点持续追赶不上，最终退化为反复全量同步；
  4. 删除阻塞：DEL 释放大块内存同样耗时（4.0 起用 UNLINK 异步化）；
  5. 内存碎片：反复分配/释放大块内存加剧碎片率，见 13.5 节。

如何发现：

生产上最可靠的是第 3 种”客户端 SDK 上报”：在封装层统计每次写入的 value 大小，超阈值告警——与 HotKey 的发现共用一条上报链路。

解决方案：

  1. 拆分大 key：大 Hash 按字段拆成多个小 Hash（user:123:0 ~ user:123:63，按字段 hash 取片）；大 List 按时间/序号分桶；大 ZSet 按层级拆（如年度排行榜拆成月度）——原则是任何单 key 的操作耗时可控；
  2. 换存储：图片、视频、大 JSON 等”本质是文件”的数据放对象存储（OSS/S3），Redis 只存 URL 与元数据，这是最彻底的解法；
  3. 渐进式删除：需要清理大 key 时不要直接 DEL，用 UNLINK（4.0+，主线程只摘引用、后台线程释放内存），或在业务低峰分批删：
  1. 入口治理：在统一写入封装里对 value 大小做拦截（超阈值拒绝或告警），从源头杜绝新 BigKey 产生。

本节小结：HotKey 的解法是”本地缓存前置 + 拆分打散”，BigKey 的解法是”拆分 + 换存储 + 渐进删除”；两者的共同点是先靠监控发现、再在客户端封装层治理——把 Redis 当成可观测的系统而不是黑盒，是高级工程师的基本功。

9. 缓存一致性

本节回答一个问题：缓存与数据库双写，怎么把”不一致”控制在可接受的窗口内。先说结论：缓存与数据库无法做到强一致，业界默认目标是最终一致 + 尽量缩小不一致窗口。

9.1 两种更新顺序的对比

更新缓存与数据库只有两种顺序，各自的并发风险完全不同：

方案一：先删缓存，再更新数据库（不推荐）

问题出在删除与更新之间的空窗：

  1. 线程 A 删除缓存；
  2. 线程 A 还没更新数据库，线程 B 读缓存未命中，从数据库读到旧值并写回缓存；
  3. 线程 A 更新数据库，此时缓存里已是旧值——不一致会持续到缓存下次过期或更新。

方案二：先更新数据库，再删缓存（推荐，Cache-Aside 的标准写路径）

唯一风险是：

  1. 线程 A 读到缓存的旧值（此时更新还没发生），线程 B 更新数据库并删除缓存，线程 A 短暂使用旧值——窗口毫秒级，且旧值很快被删除；
  2. 删除缓存这步可能失败（网络抖动、Redis 宕机）——需要补偿，见 7.3。
方案 不一致窗口 风险等级 结论
先删缓存 → 更新数据库 大：可能持续到缓存过期 高（并发下长期不一致） 不推荐
先更新数据库 → 删缓存 小：毫秒级，删除成功即收敛 低（唯一风险是删除失败） 推荐

9.2 Cache-Aside 完整读写流程

缓存使用的主流模式是 Cache-Aside（旁路缓存），读写都由业务代码显式操作：

  • 读：先读缓存，命中直接返回；未命中查数据库，写回缓存并设置 TTL；
  • 写：先更新数据库，再删除缓存（下次读时重建），而不是主动写缓存——这样避免了”写缓存成功、删缓存失败”的长期脏数据，也避免了更新旧值的竞争。

为什么不”更新数据库的同时把新值写进缓存”？因为并发下无法保证”更新 DB”与”写缓存”的顺序，而写缓存的失败率远高于删缓存，且删缓存让每次写只产生一次缓存操作，代价更小。

9.3 删除失败的兜底：延迟双删与可靠补偿

延迟双删（Double Delete）：更新数据库后立即删一次缓存，延迟一段时间（经验值 500ms）再删一次。第二次删除是为了清掉”在第一次删除与数据库更新之间，被并发读重建的旧值”：

注意两点：500ms 是经验值，应大于”从库读数据 + 重建缓存”的最坏耗时（数据库主从有延迟时还要覆盖从库延迟）；双删只能降低概率，不能保证——第二次删除本身也可能失败。

更可靠的补偿方案（删除失败可重试，甚至不用依赖”删除”这个动作）：

  1. 消息队列重试：删除失败把 key 发到 MQ，消费者反复重试直至成功；
  2. Binlog 订阅（推荐做高可靠场景）：用 Canal 监听数据库 binlog，把”数据变更”作为唯一事件源，消费端异步删除缓存——天然有序、不依赖业务代码里删除是否成功，失败可重试；代价是引入额外组件。
方案 可靠性 复杂度 说明
延迟双删 中（第二次删除仍可能失败） 低 成本最低，先做这个
MQ 重试 高 中 删除失败可重试，需处理重复消费
Binlog 订阅（Canal） 高 高 事件源可靠、顺序天然，最终一致性的”正解”
短 TTL 兜底 兜底 极低 无论如何都要给缓存设 TTL，最坏情况由过期收敛

9.4 其他写策略：Write-Through 与 Write-Behind

缓存一致性的其他两种更新策略（与 Cache-Aside 并列）：

  • Write-Through（写穿透）：写请求先写缓存，缓存同步写数据库，两步都成功才算写完。读永远命中缓存，一致性最好，但每次写多一次缓存往返，写性能差。
  • Write-Behind（写回）：写请求只写缓存，异步批量落库。写性能最好，但落库延迟不可控，存在丢数据风险，且缓存与数据库可能长时间不一致。
策略 一致性 写延迟 实现复杂度 适用场景
Cache-Aside 最终一致（依赖删缓存成功 + TTL） 中 低 默认首选
Write-Through 强（同步双写） 高 中 配置类、一致性敏感且写少的场景
Write-Behind 弱（异步落库） 低 高 写放大场景、可容忍丢失（如日志、计数）
（+延迟双删） 最终一致，窗口更小 中 低 并发写读极高的互联网业务

本节小结：业界默认组合是 Cache-Aside + 先更新库再删缓存 + 延迟双删/重试补偿 + 短 TTL 兜底；强一致需求不要指望缓存方案，要么缩短 TTL 让缓存”接近不存在”，要么直接读写数据库绕过缓存。

10. 分布式锁

本节回答一个问题：多个服务实例（或线程）要互斥地操作同一资源，怎么用 Redis 实现可靠且不误伤的锁。技术演进脉络：SETNX → Redisson 看门狗 → Redlock 及其争议 → 与 ZK 锁的对比。

10.1 阶段一：SETNX 的演进与最小正确实现

SETNX 的坑：SETNX key value 只在 key 不存在时设置成功，天然适合做锁。但 SETNX + EXPIRE 两条命令不是原子的——设置成功后进程崩溃，锁没有过期时间，永久死锁。早期版本的经典 bug。

  • 误删别人的锁：锁 30 秒过期后，客户端 A 还在执行业务，客户端 B 拿到锁。A 执行完执行 DEL key，把 B 的锁删了——解锁前必须校验持有者；
  • 过期时间写死：业务执行超过 30 秒，锁被自动释放，其他客户端进入，互斥被破坏。

10.3 阶段三：主从切换丢锁与 Redlock 争议

遗留问题：锁写入主节点后，主节点还没把这条写同步到从节点就宕机了，哨兵把从节点提升为新主——新主上没有这把锁，另一个客户端成功加锁，两个客户端同时进入临界区。这就是”主从切换丢锁”。

Redlock（antirez 2015 年提出）的解法：不用主从，改用 N 个相互独立的 Redis 节点（通常 5 个，每个都是完整实例，不复制）。加锁流程：

  1. 记录本地时间 T0；
  2. 依次向 5 个节点执行 SET key value NX EX ttl，每个节点使用短连接超时（如 50ms），避免某个节点卡死拖长整体；
  3. 计算总耗时 Δ = T1 − T0：若成功节点数 ≥ 3（过半）且 Δ < 锁有效期 ttl，判定加锁成功，锁的实际有效期为 ttl − Δ；
  4. 任一条件不满足（包括中途失败、超时）则向所有节点发起解锁，清理可能已成功的残留锁。

为什么是 5 个独立节点 + 过半：任意时刻至多有一个客户端能在”多数节点”上加锁成功，而解锁也要求多数节点，从而（概率上）保证互斥，且不依赖任何单点。

争议（2016 年著名的论战）：

Martin Kleppmann 发表《How to do distributed locking》，指出 Redlock 并不安全：

  1. GC 停顿（或进程暂停）：客户端拿到锁后发生长时间 GC（几十秒），锁在此期间过期，另一个客户端拿到锁进入临界区——两个客户端同时执行，任何锁协议都无法阻止，因为锁的有效期是”自持锁客户端视角”的时间，而暂停的客户端无法感知；
  2. 时钟漂移：如果某个节点的系统时钟被 NTP 拨快，锁会提前失效，同样导致双持锁；
  3. Kleppmann 的结论是：要真正安全，必须引入 fencing token（锁服务为每次加锁发一个单调递增的令牌，资源端校验令牌，过期令牌的请求直接拒绝），而 Redlock 没有这个机制。

antirez 在《Is Redlock safe?》中回应：Redlock 解决的是”网络分区、节点故障”这类故障模型，GC 停顿问题对所有基于超时的锁都存在（ZK、etcd 一样无法免疫）；对绝大多数业务（防重复提交、抢购限流），Redlock 足够，且业务侧往往有幂等兜底。

现状结论（值得在面试中亮出的观点）：

  • 大多数团队最终用 单主 Redis + Redisson（AP 路线，高可用优先），不部署 Redlock——它需要 5 个独立节点，收益有限，且并不能给出绝对互斥；
  • 对互斥要求极高（扣款、库存扣减、唯一资源分配）的业务，用 ZK / etcd（CP 路线），并配合业务幂等（数据库唯一约束、版本号）双保险；
  • 真正的”绝对安全”只有 fencing token + 资源端校验 能做到，这与用哪个存储无关。

10.4 与 ZK 锁的对比

ZK 分布式锁的实现思路：在 /locks 下创建临时顺序节点（如 /locks/order-1/0000000005），编号最小的节点持有锁；不是最小的，就 watch 前一个节点，前一个节点被删除后唤醒再判断（只 watch 前一个节点，避免”惊群”）。临时节点随会话结束自动删除，所以客户端崩溃后锁会自动释放（session 超时可配置，默认 10 秒级）。Curator 的 InterProcessMutex 封装了这套逻辑。

维度 Redis + Redisson ZK（Curator）
一致性模型 AP（主从异步复制） CP（ZAB 协议，写入需多数派确认）
锁的自动释放 看门狗续期 + 过期时间（30s） 会话超时（临时节点自动删除）
主从切换/选主期间 可能双持锁（写未同步） 写入即多数派确认，不丢
可重入 支持 支持
性能 高（纯内存单命令） 中（每次加锁多次 RPC + 多数派）
部署成本 单实例即可 至少 3 节点集群
典型弱点 主从切换丢锁、过期时间不可控 会话超时同样受 GC 停顿影响（窗口通常更长，概率更低）

注意 ZK 也不是绝对安全：客户端 GC 停顿超过会话超时，临时节点同样会被删除、锁同样会丢。ZK 的优势是”不依赖过期时间博弈”——锁的失效由会话生命周期决定，比”30 秒写死”更可控，配合合理超时（10~30 秒）比 Redis 的 30 秒窗口更稳。

决策建议：

业务场景 推荐方案
防重复提交、限流、活动防重，可容忍极端小概率双执行 单主 Redis + Redisson（默认选择）
扣款、库存、唯一资源分配，要求严格互斥 ZK / etcd 锁 + 业务幂等（唯一约束/版本号）
绝对安全要求（如支付系统） 上述任选 + fencing token（资源端校验递增令牌）
不想引入 ZK，但 Redis 锁又不够稳 Redlock + 业务幂等兜底，或升级为数据库乐观锁

使用注意：锁的粒度要小（按订单 ID 而非用户 ID）；临界区内避免慢操作（锁内调用外部 RPC 会放大续期压力）；等待锁要有超时与失败策略，避免无限阻塞。

本节小结：锁的演进是从”能加锁”到”锁安全”的过程——SETNX 解决原子加锁，Lua 解决防误删，Redisson 看门狗解决续期与可重入，Redlock 试图解决主从切换丢锁但其安全性依赖时钟与停顿假设；对绝大多数业务，Redisson 单主锁足够，强互斥场景上 ZK/etcd 并叠加幂等。

11. Guava Cache 深入

第 7 章的雪崩方案二提到”Redis 前面加一层本地缓存”，第 8 章的 HotKey 方案一也用到它。作为独立模块，本节把 Guava Cache 讲透：参数语义、三种回收维度、异步刷新、两级缓存与一致性、和 Caffeine 的选型。Guava Cache 是 JVM 内的本地缓存（基于 ConcurrentHashMap 实现的线程安全缓存），解决的是”同一进程内高频重复读取”——纯内存读取是纳秒到微秒级，比 Redis 的毫秒级快一个数量级；代价是每个实例各存一份、进程重启即失。

11.1 核心参数

参数 语义 注意
maximumSize 最大条目数，容量维度 超限驱逐是”近似 LRU”，不是严格 LRU
maximumWeight + Weigher 按权重限制总容量 与 maximumSize 二选一
expireAfterWrite 写后固定时长过期 适合”数据有稳定更新周期”的场景；与 expireAfterAccess 互斥
expireAfterAccess 最后一次读写后滑动过期 适合会话类数据，热点 key 会被反复续命
refreshAfterWrite 写后到达时长，下次访问时触发刷新 必须配 CacheLoader；刷新窗口必须小于过期时间
weakKeys / weakValues 用弱引用持有 key / value weakKeys 用 == 比较，查询必须用同一实例，实际很少用
softValues value 用软引用（内存不足才回收） 与 weakValues 互斥
recordStats 记录命中率、加载时间 配合 cache.stats() 查看

两个关键理解：其一，过期是惰性的——Guava 没有后台扫描线程，清理发生在读写操作时顺带执行，长时间不读写的过期条目可能一直占内存（但容量上限仍是硬约束，写入时超限必驱逐）；其二，expireAfterWrite 与 refreshAfterWrite 的配合——expireAfterWrite(30min) + refreshAfterWrite(5min) 表示：写后 5~30 分钟内的访问返回旧值并触发刷新；超过 30 分钟旧值已硬过期，只能阻塞加载，刷新窗口此时已无意义。所以刷新窗口必须小于过期时间。

11.2 三种回收维度

Guava Cache 的”回收”从三个维度触发，面试时按维度展开：

  • 基于容量：maximumSize/maximumWeight，超限时驱逐”最久未使用”的条目。实现是每个 segment 内部维护一个 LRU 访问队列（双向链表），访问时 O(1) 移到队尾，驱逐时从队头取；驱逐发生在写入路径上，所以不会出现”缓存条目数长期超过上限”。
  • 基于时间：expireAfterWrite（固定时刻过期）与 expireAfterAccess（滑动窗口过期）。过期条目不是立刻删除，而是在后续读（get 时检查）和写（顺带清理）时惰性清除。
  • 基于引用：weakValues/softValues 把回收交给 GC——value 未被 GC 时缓存可复用（省重建成本），被 GC 后条目自然消失，下次访问重新加载。适合”对象可重建但重建昂贵”的场景（如大对象池）。

三者可以叠加（如”容量 + 时间”同时配置），共同构成缓存的行为边界。

11.3 CacheLoader 与 refreshAfterWrite 异步刷新

CacheLoader 把”读缓存 → 未命中查库 → 回填”三步合成一步：cache.get(key) 未命中时自动调用 load(key) 并回填。注意 getIfPresent 只查不加载，适合”未命中时自己控制逻辑”的场景。

两级缓存是”本地缓存 + Redis”的经典组合：L1 = Guava/Caffeine（JVM 内，微秒级），L2 = Redis（网络访问，毫秒级），数据库兜底。第 7 章雪崩方案二与第 8 章 HotKey 方案一用的都是这个结构，这里给出完整的读写路径：

11.5 Guava Cache vs Caffeine

Caffeine 是 Guava Cache 的继任者（作者 Ben Manes 深度参与过 Guava 缓存设计），核心改进是 W-TinyLFU 淘汰算法（窗口缓存 + 分段 LFU 的近似最小访问频次淘汰），解决了 LRU 对”长尾热点”数据命中率差的问题：

维度 Guava Cache Caffeine
淘汰算法 近似 LRU W-TinyLFU（窗口 + 频次统计）
命中率 常规数据流够用 长尾/突发数据流显著更高
并发吞吐 高 更高（更高效的哈希表实现）
异步加载 ListenableFuture + 自建线程池 内置 async 接口与调度器
维护状态 维护模式，基本无新特性 活跃迭代
API 通用 完全兼容 Guava 风格 API

选型结论：新项目直接用 Caffeine（依赖更小、命中率更高）；存量 Guava Cache 项目如果命中率不是瓶颈，没必要为迁移而迁移。注意两者都是”进程内缓存”，都没解决跨实例一致性问题——多级缓存的一致性方案（11.4）与具体选型无关。

本节小结：Guava Cache 的三维回收（容量/时间/引用）定义了它的行为边界，refreshAfterWrite 的异步刷新靠重写 reload 实现，两级缓存的价值在”本地挡高频 + Redis 挡穿透”，一致性靠”广播失效 + 短 TTL”双保险；它与 Redis 是互补而非替代关系。

12. 分布式 Session 共享

12.1 为什么需要 Session 共享

单机时代：Session 存在进程内（如 Tomcat 的 StandardSession），用户的登录状态天然随进程保存。上线集群后问题来了——负载均衡会把同一用户的连续请求分发到不同节点：在节点 A 登录后，下一个请求被分到节点 B，B 的进程里没有这个 Session，用户被要求重新登录。这就是”Session 丢失”。

两条解决路线，也是面试必背的对比：

  1. Session 集中外置：把 Session 从进程内挪到共享存储（Redis），所有节点读写同一个地方，业务代码无感知——Spring Session + Redis 的方案，本节主讲；
  2. 无状态认证：服务端不保存会话，把身份凭证签发给客户端（JWT），每次请求自带凭证，服务端验签即可——彻底摆脱”存哪里”的问题，见 12.4 的对比。

12.2 Spring Session + Redis

Spring Session 把 HttpSession 的实现替换为 Redis 后端：业务代码仍然用 request.getSession()，对应用透明，只改依赖和配置。

12.4 与 Token 认证（JWT）的对比选型

JWT（JSON Web Token）是无状态方案的代表：登录成功后服务端签发一个带签名（HS256/RS256）的令牌，内含用户标识与过期时间，客户端每次请求放在 Authorization: Bearer <token> 头里，服务端验签即信任——不需要任何会话存储。

维度 Session（Spring Session + Redis） JWT
服务端状态 有（Redis 存储） 无（令牌自包含）
登出/踢人 删 Session 立即生效 难（令牌在有效期内持续有效，需引入黑名单）
横向扩容 共享 Redis 即可 天然支持（无状态）
服务端重启 无影响（会话在 Redis） 无影响
每次请求开销 一次 Redis 读（毫秒级） 一次签名验算（CPU，微秒~毫秒级）
数据可见性 服务端可控，可存任意业务数据 令牌内容客户端可见（敏感信息勿放）
泄露风险 窃取 SessionId 即可冒用（需 HttpOnly + 定期轮换） 窃取令牌即可冒用至过期（有效期必须短）

选型结论：浏览器 + Cookie 的经典 Web 应用（登录状态、购物车）用 Spring Session——Cookie 与 SessionId 天然匹配，踢人、注销即时生效，Redis 顺手承载并发；纯 API / 移动端 / 前后端分离且服务无状态化需求强时用 JWT——无需共享存储、跨域友好；混合场景常见做法是”JWT 短有效期（如 15 分钟）+ 刷新令牌（如 7 天）”，用刷新令牌续签实现伪登出。两者不是非此即彼——很多系统是”登录会话用 Session 做、接口鉴权用 JWT 做”。

本节小结：Session 共享的本质是把”状态”从进程内搬到共享存储，Spring Session 用 Redis 实现了这一点且对业务透明；序列化选 JSON、Cookie 开 HttpOnly/Secure/SameSite 是生产底线；与 JWT 的选型看”是否要服务端可控的登出”与”客户端形态”。

13.5 内存优化

内存是 Redis 最贵的资源，优化方向按性价比排序：

  1. 小对象用紧凑编码：Hash/ZSet 在元素少时用 listpack（7.0 前为 ziplist），通过阈值配置让”小数据不升级成哈希表/跳跃表”。阈值按业务数据规模估算，设置过大反而让大对象用紧凑编码导致 O(n) 操作变慢：
  1. 共享对象池：0~9999 的整数字符串全局共享同一对象，INCR 计数、小状态标记等场景天然受益，避免大量重复分配。注意：开启 LRU/LFU 淘汰策略时该优化自动失效——淘汰算法需要每个对象独立的 LRU/LFU 字段，共享对象无法区分；
  2. String 编码选型：≤ 44 字节用 embstr（对象与 SDS 一次分配），超过升 raw；能用整数就存整数（int 编码）；

微服务架构与 Spring Cloud Alibaba

本文是”高级 Java 工程师体系课”的分布式核心章节。前半部分讲微服务架构理论（单体演进、拆分原则、SOA 对比、代价），后半部分以 Spring Cloud Alibaba 2023.x + Spring Boot 3.x 为技术栈，逐一剖析 Nacos、OpenFeign、Sentinel、Gateway、Seata、SkyWalking 六大组件的原理与实战。第 4 节（Sentinel）和第 6 节（Seata）标注为面试核心考点，涉及源码级原理，务必吃透。

环境基线：Java 17、Spring Boot 3.2.x、Spring Cloud 2023.0.x、Spring Cloud Alibaba 2023.0.1.0（内含 Nacos Client 2.3.x、Sentinel 1.8.8、Seata 1.8.x）。全部代码可在独立 Maven 工程中直接运行。

1. 从单体到微服务

1.1 单体架构的痛点

单体（Monolith）是一个进程内打包了全部业务模块（用户、订单、库存、支付……）的应用，部署时整体发布。它的问题在规模增长后集中爆发：

  • 发布耦合：任何一个模块（比如改一行文案）修改，都要重新构建、测试、发布整个应用。一次发布的风险面是全站的，某个模块的回归可能拖垮整个上线节奏。
  • 扩展性差：垂直扩展（加机器、升配置）终有天花板；水平扩展只能”整机复制”——流量集中在订单模块，却不得不把用户、支付模块一起扩容，成本高、浪费大。
  • 技术锁定：整个应用共用一套技术栈。想给搜索模块引入一个新的中间件、换一个缓存组件，都要评估对全局的影响，风险大到不敢动。
  • 可靠性相互拖累：一个模块的 OOM、死循环会拖垮整个进程；出问题时无隔离边界，故障半径=全应用。
  • 协作瓶颈：几十人同时改一个代码库，合并冲突频繁，团队规模与交付效率成反比。

1.2 微服务的核心原则

微服务（Microservices）是把应用拆分为一组小的、自治的服务，每个服务围绕业务能力独立开发、部署、演进。四条核心原则：

  1. 独立部署：每个服务有自己的构建产物、部署单元、版本、发布节奏。改动订单服务不需要重新发布用户服务。
  2. 去中心化数据：每个服务独占自己的数据库（Database per Service），服务间不共享表，只能通过 API 访问对方的数据，这是数据解耦的根本。共享数据库会导致表结构变更互相踩踏，隐性耦合。
  3. 轻量通信：服务间用轻量级通信机制（HTTP/REST、gRPC、消息队列），通常是语言无关的协议，避免重型的 ESB 中心化总线。
  4. 按业务能力组织：团队围绕业务能力而非技术分层组建，一个团队拥有服务的全部生命周期（开发、测试、运维）。

1.3 微服务 vs SOA 的区别

微服务是 SOA 的一种演进形态，二者常被拿来对比：

维度 SOA 微服务
服务粒度 粗粒度（企业级业务模块） 细粒度（单一业务能力）
通信方式 常经 ESB 企业服务总线（重量、集中） 直接轻量调用（REST/gRPC/MQ），去中心化
数据管理 常共享数据库 每服务独立数据库
治理方式 集中式（ESB 做协议转换、路由、编排） 去中心化（各服务自治）
部署方式 通常整体部署 独立部署、独立扩缩容
实施理念 自上而下的企业架构规划 自下而上的产品/业务能力导向，DevOps 文化

一句话：SOA 强调”重治理的集成”，微服务强调”轻架构的自洽”。

1.4 微服务的代价

微服务不是银弹，它把单体的问题换成了另一类问题：

  • 分布式复杂性：网络不可靠、节点间调用延迟、部分失败（Partial Failure）成为常态。服务间调用超时、重试、熔断、幂等等问题都需要专门处理。
  • 数据一致性：单体的本地事务失效，跨服务写操作必须引入分布式事务（Seata 等，见第 6 节）或最终一致性方案（本地消息表、事务消息、Saga），复杂度显著上升。
  • 运维成本：一个应用变成几十个服务，日志、监控、告警、发布、回滚、链路追踪都需要平台化支撑（这正是第 7 节可观测性的由来）。
  • 开发调试成本：本地起全套依赖复杂，联调、排查跨服务 Bug 的难度陡增。
  • 性能损耗：服务间 RPC 网络开销、序列化开销高于进程内方法调用。

决策标准：业务复杂度不足以支撑微服务治理成本时，先保持模块化单体（Modular Monolith）；微服务化应是”组织发展需要”驱动，而非”技术时髦”驱动。

2. 服务注册与发现：Nacos

2.1 Nacos 架构与部署

Nacos（Dynamic Naming and Configuration Service）是阿里开源的注册中心 + 配置中心二合一组件，是 Spring Cloud Alibaba 体系的地基。

2.1.1 核心概念

概念 说明
Namespace（命名空间） 环境隔离：dev/test/prod 各自独立，互相不可见
Group（分组） 同一命名空间下的业务分组（如 DEFAULT_GROUP、PAY_GROUP）
Service（服务名） 逻辑服务标识，spring.application.name
Cluster（集群） 服务实例按机房/可用区划分的物理分组，用于就近调用
Instance（实例） 具体注册节点：IP + Port + Metadata + 健康状态
Ephemeral（临时实例） 默认 true。客户端心跳保活，服务端不持久化，实例挂掉即被摘除

2.1.2 AP / CP 模式

Nacos 一个显著特性是同时支持 AP 和 CP，按实例类型分流：

  • 临时实例（默认）：走 Distro 协议（AP），实例数据保存在各节点内存，节点间异步同步。可用性优先，网络分区时依然可以注册（最终一致）。
  • 持久实例：走 JRaft（CP），基于 Raft 多数派提交，强一致。注册时若集群多数派不可用则注册失败。
  • 配置中心：本身走 CP（JRaft），保证配置读写强一致，避免配置”读到一半”。

这也是面试常问的”Nacos 的 CAP 定位”的答案：它不是非 A 即 C，而是按数据模型选择——注册的临时实例走 AP，持久实例与配置走 CP。对比 Eureka 纯 AP、Zookeeper/Consul 纯 CP。

2.1.3 集群部署

生产至少 3 节点（Raft 需要多数派），推荐用 MySQL 作为持久化存储（内置 Derby 仅用于单机测试），并给控制台挂 Nginx 做入口。

心跳机制：注册成功后，客户端 BeatReactor 启动定时任务，每 5 秒发送一次心跳（BeatTask → sendBeat），服务端收到后更新实例的 lastHeartBeatTime。服务端定时扫描：

  • 超过 15 秒（约 3 个心跳周期）未收到心跳 → 实例标记为 unhealthy；
  • 超过 30 秒 → 从注册表摘除，并向订阅者推送变更事件。

心跳丢失时客户端还会触发自动重新注册（if (beatNotExist) registerAgain），保证短暂网络抖动后能自愈。

临时 vs 持久实例的关键差异：

维度 临时实例（ephemeral=true） 持久实例（ephemeral=false）
一致性协议 Distro（AP） JRaft（CP）
存储 各节点内存，无持久化 持久化到 DB（Raft 日志）
健康检查 客户端主动心跳（5s） 服务端主动探测（TCP/HTTP 端口探活）
掉线处理 心跳超时自动摘除 服务端探活失败标记不健康（但保留）
适用场景 常规微服务（默认） 需要强注册语义的实例（如某些网关/特殊节点）

另外注意 Nacos 保护阈值（ProtectThreshold）：服务端把”健康实例数/总实例数”与保护阈值（0~1，默认 0）比较，当健康比例低于阈值时触发保护，即使不健康实例也继续返回流量，防止全部摘除后流量无处可去（避免雪崩时的空查询）。这是 AP 设计思想在注册中心的体现。

2.3 服务发现流程：拉取 + 推送结合

Nacos 2.x 的服务发现是 gRPC 双向流推送 + 定时拉取兜底 的组合：

  1. 订阅（subscribe）：客户端通过 gRPC 与服务端建立双向流连接（grpc:// 9848 端口），发送订阅请求，本地维护一份服务实例缓存。
  2. 服务端推送：实例注册、下线、健康状态变化都会触发 ServiceChangedEvent，服务端沿 gRPC 流立即推送变更给订阅者；客户端更新本地缓存并回调用户注册的 EventListener。
  3. 定时拉取兜底：客户端每 10 秒 主动重新查询一次，防止推送丢失导致的数据不一致。

1.x 时代的机制（UDP 推送 + 每 10s 轮询 + 长轮询降级）已退役，但”推送为主、拉取兜底“的框架思想面试常问：纯推送会丢消息（UDP 不可靠）、纯拉取有延迟，二者结合是注册/配置系统的通用答案。

2.4.2 动态刷新原理

客户端 NacosConfigService 对每个 dataId 注册长轮询：

  • 客户端发起 HTTP 长轮询请求，默认 30 秒超时（configLongPollTimeout），期间服务端若发现配置变更（比对内容 MD5），立即返回；
  • 客户端收到变更后，比较本地 MD5 → 拉取新内容 → 触发 Listener 回调；
  • @NacosValue(autoRefreshed = true) 的字段直接更新；Spring 管理的 Bean 需要 @RefreshScope 才会重建实例（因为 @Value 的注入发生在 Bean 初始化时）。

2.4.3 多环境与灰度发布

  • 多环境：用 namespace 隔离（dev / test / prod 各建一个 namespace），dataId 建议带 profile：user-service-dev.yaml、user-service-prod.yaml。

  • 敏感配置（数据库密码、密钥）建议加密存储，配合加解密插件（如 Jasypt）使用；

3. 服务调用：OpenFeign

3.1 Feign 的声明式调用原理

Feign 把 HTTP 调用抽象成声明式接口：只定义接口方法 + 注解，调用时像调用本地方法。原理分三层：

  1. 注册：@EnableFeignClients 扫描 @FeignClient 接口，Spring 容器为每个接口创建 FeignClientFactoryBean（FactoryBean，注入时生成代理）。
  2. 动态代理：Feign 为接口生成 JDK 动态代理（FeignInvocationHandler），代理内部把方法调用解析为 MethodHandler（SynchronousMethodHandler）。
  3. 契约与执行：SpringMvcContract 把 Spring MVC 注解（@GetMapping、@PathVariable、@RequestBody）翻译为 Feign 自己的 RequestTemplate；Client 真正发起 HTTP 请求（默认基于 JDK HttpURLConnection，可用 OkHttp/Apache HttpClient 替换）。

3.2 拦截器链与编解码

RequestInterceptor：在请求发出前统一加工 Header/参数，适合做认证透传、链路 ID 注入。

编解码：默认使用 Spring 的 HttpMessageConverter（JSON 用 Jackson）。返回类型上尽量用统一 Result<T> 包装（见 8.2），用 Feign 的 Decoder 把 HTTP 状态码与业务码区分开——HTTP 200 但业务失败的业务码（如 500001 用户不存在）不会被 Feign 当成异常，这点要在调用方显式判断 Result.code。

4.2 滑动窗口算法在 Sentinel 中的实现

为什么不用固定窗口：固定窗口（如每秒一个桶）在窗口边界会出现”双倍流量”穿透——前一个窗口末尾 0.9s 打了 20 个请求，后一个窗口开头 0.1s 又打 20 个，连续 1 秒内实际流量是 40，但每个窗口都判定未超限。滑动窗口通过把窗口切成多个小格子（sampleCount），随当前时间推进滚动统计，消除了边界毛刺。

4.4 熔断降级规则

熔断器状态机：CLOSED（关闭/正常）→ OPEN（打开/拒绝所有请求）→ HALF_OPEN（半开/试探）→ CLOSED。

Sentinel 的 DegradeSlot 内部维护每个资源的 CircuitBreaker 实现：

  • ResponseTimeCircuitBreaker：老版平均 RT 熔断（已废弃）。
  • ExceptionCircuitBreaker：支持三种降级策略（grade）：
    • 慢调用比例（grade=0）：count=RT 阈值（如 1000ms），slowRatioThreshold=比例阈值（如 0.6）。在统计周期内，慢调用数/总调用数 ≥ 阈值且总调用数 ≥ minRequestAmount（默认 5）→ 熔断。
    • 异常比例（grade=1）：count=异常比例阈值（如 0.5）。
    • 异常数（grade=2）：count=异常个数阈值（统计周期内异常数 ≥ N）。

半开探测（HALF_OPEN）细节：熔断后进入 OPEN 状态，所有请求直接拒绝；等待 retryTimeoutMs（等价于旧版 timeWindow 秒数）后进入 HALF_OPEN，只允许 1 个（maxAllowedRequests，默认 1）探测请求通过；探测成功（未触发异常/未慢）→ 关闭熔断恢复流量；探测失败 → 重新 OPEN 并重置计时。

4.5 热点参数限流与系统自适应限流

热点参数限流（ParamFlowSlot）：对同一个资源的不同参数值分别限流。典型场景：商品详情接口整体 QPS 不高，但某爆款商品 ID 的请求占 90%——按参数值维度精准限流。实现上为每个参数值维护独立的令牌桶/计数窗口（ParamFlowThrottle），支持 QPS 与线程数两种模式，可用 paramFlowItem 给特定参数值设置单独阈值。

注意：热点参数限流的 blockHandler 必须带 @SentinelResource 的第一个参数（goodsId）才能按参数限流，且参数个数要与接口一致。

系统自适应限流（SystemSlot）：保护整个应用进程而非单个资源，防止单接口打爆导致全应用雪崩。指标（SystemRule）：

  • highestCpuUsage：CPU 使用率阈值（如 0.8）；
  • avgRt：全局平均 RT 阈值；
  • maxThread：全局并发线程数；
  • qps：全局 QPS 阈值；
  • highestSystemLoad：系统 load1 阈值（Linux 下 1m loadavg / 核数）。

当任一指标超限，后续请求被拦截。SystemStatusListener 定时采集 OS 指标。注意这是兜底机制，阈值需要压测标定，过小会误伤正常流量。

6.1 分布式事务问题与 Seata 的解决方案

问题：微服务去中心化数据后，一个业务（下单）跨多个服务（订单库、库存库、账户库）写数据，每个服务只有本地事务，无法保证全局原子性——库存扣了、订单没建成功，数据就错了。

Seata（Simple Extensible Autonomous Transaction Architecture） 的解法是引入三个角色：

6.2 AT 模式原理

AT（Automatic Transaction）模式是 Seata 的招牌：对业务无侵入（业务只写普通 SQL），自动生成补偿数据完成二阶段。前置条件：数据源要用 Seata 的 DataSourceProxy 包装（starter 自动完成）。

一阶段（业务执行）：

  1. 解析 SQL，生成前后镜像：
    • 执行前，SELECT 出受影响行的原始数据（before image）；
    • 执行业务 SQL（本地事务内）；
    • 执行后，再次 SELECT 出该行数据（after image）；
    • 用 after image 与 DB 当前值对比校验（防并发脏写），不一致则报错回滚；
  2. 写 undo_log：把 before/after 镜像序列化，连同 branchId/XID 插入 undo_log 表（与业务 SQL 同库同事务，这是回滚数据不丢失的保证）；
  3. 获取全局锁：向 lock_table 插入该行的全局锁记录（xid + 主键），拿到全局锁才提交本地事务——防止并发事务同时改同一行导致镜像失效；
  4. 提交本地事务，上报分支注册/状态给 TC。

二阶段：

  • 全局提交（所有分支都成功）：TC 通知各 RM branchCommit——RM 异步删除 undo_log、释放全局锁（不做事后校验，因为一阶段已保证一致）。
  • 全局回滚（任一分支失败）：TC 通知各 RM branchRollback——RM 读 undo_log：
    1. 用 after image 与当前 DB 数据对比：一致 → 用 before image 生成反向 SQL（UPDATE 恢复原值 / DELETE 删掉新插入行 / INSERT 补回被删行）执行还原，然后删除 undo_log；
    2. 不一致（被其他事务改过）→ 说明发生脏写，停止回滚该行并告警（人工介入，避免覆盖别人数据）。

全局锁与死锁检测：TM 开启全局事务时会生成 全局锁有效期（默认 60 秒）。当 RM 获取某行全局锁失败（被其他全局事务持有），会根据锁 owner 的 xid 反查对方全局事务状态：若对方已进入回滚中/已结束（二阶段在释放锁），等待线程重试获取；若对方事务正常存活只是慢，则继续等待（默认重试 30 次、间隔 10ms 递增）。这就是 Seata 的死锁检测：通过查询锁持有事务的实时状态避免”无限等待”。注意全局锁是数据库行锁之外的逻辑锁，粒度是”行”，并发热点行会成为吞吐瓶颈——这是 AT 模式在热点场景（秒杀扣库存）的性能短板，可改用 TCC。

AT 模式的优缺点：

  • 优点：对业务零侵入（普通 SQL 即可）、自动生成补偿、事务中间层透明；
  • 缺点：需要 undo_log 表和全局锁表（DDL 成本）、每行数据都有锁竞争（吞吐受限）、不适合一阶段执行时间很长的场景（锁长时间占用）、依赖数据库（事务全部放在各库本地执行）。

6.3 TCC 模式原理

TCC（Try-Confirm-Cancel）把分布式事务拆成三个业务方法，由业务自己保证资源状态：

  • Try：资源检查 + 资源预留（不真正扣减，冻结）；
  • Confirm：确认提交（把冻结转成扣减），幂等；
  • Cancel：取消回滚（解冻），幂等。

三个必须掌握的状态问题（框架自动处理，但要能讲清原理）：

  1. 空回滚（Empty Rollback）：Try 请求因网络故障从未到达执行方，但 TC 已发起 Cancel。若此时执行 Cancel 业务逻辑，会对从未预留的资源做”解冻”，导致数据错乱。框架处理：Cancel 到达时先检查分支事务记录是否存在——Try 未执行则分支未注册，框架跳过 Cancel 业务方法，只记录分支状态。

  2. 悬挂（Hanging）：Try 请求延迟到达——Cancel 已经执行完毕之后 Try 才到。若执行 Try 的预留，预留的资源将永远无人释放（Confirm/Cancel 都已结束）。框架处理：Try 执行前检查分支状态——发现该分支已完成 Cancel（已回滚），则拒绝执行 Try（记录幂等标记），丢弃迟到请求。

  3. 幂等：Confirm/Cancel 可能被重试多次（网络抖动、TC 重发），业务实现必须天然幂等（用冻结状态位、唯一约束、状态机校验）。

面试对比 AT vs TCC：

维度 AT TCC
侵入性 零侵入（普通 SQL） 侵入（三个业务方法 + 资源预留设计）
一致性 依赖 undo_log 前后镜像自动补偿 业务自己控制 Try/Confirm/Cancel
性能/并发 行级全局锁，热点行是瓶颈 无行锁（预留语义由业务实现），并发高
适用场景 一般 CRUD 分布式事务 高并发热点（秒杀扣库存）、对一致性要求苛刻

6.4 Saga 模式简介

Saga 是长事务的编排模式：把一个全局事务拆成多个本地事务序列（T1, T2, …, Tn），每步提交本地事务；某步失败时，按逆序执行补偿（C1, C2, …, Ci-1）回滚已提交步骤。适合业务流程长、对实时一致性要求不高的场景（预订机票+酒店+租车、多步审批流）。

Seata 的 Saga 实现是状态机引擎：用 JSON 定义状态机（start/state/compensation 节点），seata-saga-statemachine 驱动流转，支持并行分支、补偿定义、重试。与 AT/TCC 的区别：没有全局锁和冻结概念，全程本地事务实时提交，中间态对外可见（适合”允许中间态、最终一致”的业务）；代价是补偿逻辑要业务自己写，且不可补偿的操作（发短信、扣信用分）不能放 Saga 后半段。

四大模式选型总表（必考）：

模式 一致性 侵入性 性能 适用场景
AT 强一致（锁） 无 中（全局锁） 常规 CRUD 类跨库事务
TCC 强一致（预留） 高（3 方法） 高 高并发、热点资源（库存）
Saga 最终一致 高（补偿） 高 长流程、允许中间态
XA 强一致 无（依赖数据库 XA） 低（全局锁时间长） 数据源支持 XA 的简单场景（较少使用）

8. 微服务架构设计最佳实践

8.1 服务拆分原则

以 DDD 限界上下文（Bounded Context）为边界，而不是按技术分层拆：

  • 高内聚：把”同一业务的完整能力”放进一个服务（下单、支付、库存各自的领域逻辑闭环）；
  • 低耦合：服务间通过 API/消息通信，禁止共享数据库、禁止跨库 join；
  • 数据一致性边界：一个服务独享的数据尽量自洽；强一致需求跨边界时引入 Seata（AT/TCC），能容忍最终一致的用消息（本地消息表/事务消息）；
  • 拆分禁忌：不要为了”服务多”而拆（过度拆分是分布式恶魔，多一个服务多一份链路与运维成本）；拆分的粒度应以”团队能独立交付、独立扩容、故障隔离“为标准。

一句话：先有清晰的领域建模，再有服务拆分；服务边界 = 限界上下文边界 = 数据所有权边界。

8.2 统一异常处理与返回结构

所有服务统一 Result<T> 返回结构与全局异常兜底，是微服务协作的基础契约：

约定：HTTP 状态码只表达”通信层”语义，业务码（code）表达业务语义。服务间 Feign 调用统一返回 Result<T>，HTTP 恒为 200，调用方判断 code——这样网关、日志、告警对错误类型一目了然。

8.3 分布式链路日志：MDC + TraceId

微服务排查的黄金手段：全链路同一个 TraceId。没有 SkyWalking 时用 MDC 手工实现（配合 7.3 中 SkyWalking 的 %X{tid}，或直接用下面这个自定义方案）：

  • Feign 侧用 3.2 节的 RequestInterceptor 把 MDC.get("traceId") 透传（下游 filter 读取）；
  • 日志配置 %X{traceId} 打印；
  • 注意异步场景：ThreadLocal 不跨线程，@Async/MQ 消费者里要手动传递（包装 Runnbale 或使用装饰器）——这是线上排查”日志对不上”的头号坑；
  • 消息队列场景：生产者把 traceId 塞进消息头，消费者取出来 set 到 MDC。
