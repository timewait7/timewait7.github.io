Elasticsearch 深分页问题详解

Posted on 2026-10-07 Word count in article: 5.2k Reading time ≈ 19 mins.

1. 什么是深分页问题

在 Elasticsearch 中执行分页查询时，如果 from + size 超过 10000，会直接报错：

例如：

from + size = 10010 > 10000，直接报错。

这就是 深分页问题。

2. 为什么 from + size 深分页会报错

2.1 分布式分页的执行过程

ES 是分布式的，数据分散在多个分片上。假设索引有 5 个分片，每个分片 100 万条数据，要查 from=9990, size=10（第 9991~10000 条）。

flowchart TB
    Client[客户端请求<br/>from=9990, size=10] --> Coord[协调节点 Coordinating Node]
    Coord --> S1[分片1<br/>取前10000条]
    Coord --> S2[分片2<br/>取前10000条]
    Coord --> S3[分片3<br/>取前10000条]
    Coord --> S4[分片4<br/>取前10000条]
    Coord --> S5[分片5<br/>取前10000条]
    S1 --> Merge[协调节点汇总<br/>5 × 10000 = 50000 条]
    S2 --> Merge
    S3 --> Merge
    S4 --> Merge
    S5 --> Merge
    Merge --> Sort[内存中全局排序]
    Sort --> Drop[丢弃前 9990 条]
    Drop --> Result[返回第 9991~10000 条]

2.2 问题本质

问题 说明
每个分片都要吐出前 N 条 N = from + size，分片越多，浪费越大
协调节点要汇总 汇总数据量 = 分片数 × N
全局排序 在内存里对海量数据排序，CPU、内存飙升
最后只返回少量 排序结果里绝大部分被丢弃

翻得越深，协调节点的内存和 CPU 压力越大，高并发下直接 OOM。

2.3 一个直观的例子

from size 每个分片返回 5 分片汇总 最终返回
0 10 10 50 10
990 10 1000 5000 10
9990 10 10000 50000 10
999990 10 1000000 5000000 10

最终只返回 10 条，却让每个分片都吐出 100 万条——这就是深分页的代价。

可以调大，但强烈不推荐：

调大后的后果：

flowchart TB
    Big[调大 max_result_window] --> P1[每个分片返回更多数据]
    P1 --> P2[协调节点汇总数据量暴增]
    P2 --> P3[堆内存飙升]
    P3 --> P4[GC 频繁 / 查询变慢]
    P4 --> P5[高并发下 OOM]
    P5 --> P6[集群不可用]
问题 后果
堆内存占用 每个分片都要缓存大量数据
排序开销 全局排序的文档数线性增长
网络开销 分片到协调节点传输大量数据
稳定性 高并发下容易 OOM、拖垮集群

正确做法：用 search_after、scroll、PIT + search_after 替代深分页。

4. 方案一：search_after

4.1 核心思想

不要“跳过前 N 条”，而是“从上一页最后一条之后继续取”。

类比：

  • from + size：翻书到第 1000 页，得从第 1 页开始数。
  • search_after：我记得上次读到哪一行了，直接从下一行继续。
flowchart LR
    subgraph Page1["第 1 页"]
        A1[第1条] --> A2[第2条] --> A3[第3条] --> A4[第4条] --> A5[第5条]
    end
    A5 -->|sort 值作书签| B1[search_after = 第5条的 sort 值]
    B1 --> Page2["第 2 页：从书签之后继续取"]

4.2 使用前提：必须有唯一排序字段

search_after 依赖一个稳定、唯一的排序值作为“书签”。如果排序值有重复，翻页会丢数据或重复。

4.5 分布式取数过程

search_after 每次请求都是独立的分布式查询，不依赖前一次的搜索上下文。因为书签已经过滤掉了“书签之前”的数据，每个分片只需要返回 size 条。

第一页请求（无 search_after）：

    Coord --> S2["分片2<br/>本地排序后取前 5 条"]
    Coord --> S3["分片3<br/>本地排序后取前 5 条"]

    S2 --> M
    S3 --> M

    M --> Sort["全局排序"]
    Sort --> Take["取前 5 条返回"]
    Take --> Result["返回：P001~P005<br/>最后一条 sort=[6499, P005]"]

第二页请求（带 search_after）：

flowchart TB
    Client["客户端<br/>size=5<br/>search_after=[6499, P005]"] --> Coord[协调节点]

    Coord --> S1["分片1<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]
    Coord --> S2["分片2<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]
    Coord --> S3["分片3<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]

    S1 --> M["协调节点汇总<br/>最多 15 条"]
    S2 --> M
    S3 --> M

    M --> Sort["全局排序"]
    Sort --> Take["取前 5 条返回"]
    Take --> Result["返回：P006~P010<br/>最后一条 sort=[10999, P010]"]

关键点：

  • 每个分片先根据 search_after 过滤掉已经翻过的数据。
  • 每个分片仍然只返回 size 条，不是 from+size 条。
  • 协调节点汇总后全局排序，取前 size 条。
  • 无论翻到第几页，每个分片返回的数据量都是 size 条，与页码无关，所以性能恒定。

4.6 特点

特性 说明
翻页方式 只能一页一页往后翻，不能跳页
数据实时性 每次查询实时，能看到新写入的数据
性能 每页开销恒定，与页码深度无关
内存 不需要协调节点缓存大量数据
分片状态 不保存任何搜索上下文，无状态
适用场景 App 无限滚动、下拉加载更多、逐页浏览

4.7 缺点

  • 不能跳页（用户不能点“第 100 页”）。
  • 排序字段必须唯一稳定，否则会漏数据或重复。
  • 前端需要保存上一页最后一条的 sort 值。

5. 方案二：scroll

5.1 核心思想

scroll 相当于给索引拍一张快照，然后反复从这个快照里一批一批地取数据。

类比：

  • search_after：一边看书一边翻，书的内容可能被人改了。
  • scroll：先把整本书复印一份，然后慢慢读复印件，不管原书怎么变。
flowchart TB
    Init[创建 scroll 快照] --> Snapshot[ES 生成数据快照<br/>_scroll_id = ABC]
    Snapshot --> Batch1[用 _scroll_id 取第 1 批]
    Batch1 --> Batch2[用新的 _scroll_id 取第 2 批]
    Batch2 --> Batch3[继续取第 3 批...]
    Batch3 --> Empty[直到 hits 为空]
    Empty --> Clear[手动删除 scroll]

关键点：

  • 每个分片保存一个独立的数据视图（快照）。
  • 每个分片记录自己的游标位置，后续从自己的位置继续取。
  • 协调节点不排序，只按分片顺序合并。
  • 每次请求返回一批，直到所有分片都取完。

5.5 特点

特性 说明
数据视图 快照，创建后新写入的数据看不到
翻页方式 只能顺序往后取，不能跳页
性能 适合大批量读取，每批开销稳定
资源 快照期间占用资源，需超时并主动清理
分片状态 每个分片保存搜索上下文 + 游标位置
适用场景 数据导出、全量同步、批量重建索引、离线分析

5.6 缺点

  • 数据不实时（快照）。
  • 占用资源，超时未清理会一直挂着。
  • 不适合 Web 端实时分页。

6. 方案三：PIT + search_after

6.1 核心思想

scroll 是快照，但不实时、占资源；search_after 实时、快，但没有快照一致性。

Point In Time（PIT） 是 ES 7.10 引入的方案，把两者的优点结合：

  • 有快照一致性（同一个 PIT 内数据视图固定）。
  • 又可以用 search_after 高效翻页。
  • 比 scroll 更轻量。
flowchart TB
    Open[打开 PIT] --> PIT[PIT id + 数据视图固定]
    PIT --> Query1[PIT + search_after 查第 1 页]
    Query1 --> Query2[PIT + search_after 查第 2 页]
    Query2 --> Query3[继续...]
    Query3 --> Close[关闭 PIT]

  • 协调节点汇总后全局排序，和普通 search_after 一致。

特性 说明
数据视图 PIT 打开时固定，之后新写入数据看不到
翻页方式 只能用 search_after 顺序翻页
性能 与 search_after 相当，非常快
资源 比 scroll 轻量
分片状态 每个分片保存 PIT 上下文
适用场景 深分页搜索、导出、需要一致性视图的批量操作

6.6 优势

  • 官方推荐的深分页方案（ES 7.10+）。
  • 兼顾快照一致性和高效翻页。
  • 比 scroll 更省资源。

7.4 一句话记住三种方案

  • from + size：每个分片返回 from + size 条，协调节点汇总量随页码线性增长，深分页时资源爆炸。
  • search_after：每个分片先按书签过滤，只返回 size 条，协调节点汇总量恒定，性能与页码无关。
  • scroll：每个分片创建快照并维护游标，协调节点不排序，只按分片合并，适合批量导出，但占资源、不实时。
  • PIT + search_after：每个分片创建 PIT 快照，每次查询在快照内用 search_after 过滤，只返回 size 条，兼顾一致性和性能，是 ES 7.10+ 推荐的深分页方案。

8. 常见问题与踩坑

8.1 search_after 排序值必须唯一

如果只用 price 排序，而两条记录价格相同，翻页时可能：

  • 漏掉某些数据。
  • 重复返回某些数据。

解决：加一个唯一字段（如 _id 或业务 ID）作为第二排序字段。

8.2 scroll 快照不实时

scroll 创建后，新写入的数据看不到。如果需要实时性，改用 search_after 或 PIT + search_after。

8.3 scroll 忘记清理

scroll 快照会一直占用资源，直到：

  • 超时（scroll=1m 里设定的时间）。
  • 手动 DELETE /_search/scroll。

建议：用完立即清理，或设置合理的超时时间。

8.4 PIT 忘记关闭

8.5 search_after 不能跳页

search_after 只能顺序翻页。如果业务需要跳页（如“跳到第 100 页”），要么：

  • 业务上改成“滚动加载”。
  • 用 from + size（但页数不能太深）。
  • 用其他方案（如自定义游标）。

8.6 排序字段类型问题

search_after 的值类型必须和排序字段类型匹配。例如 price 是 double，search_after 里也要是数字，不能是字符串。

8.7 深分页 + 聚合

聚合和深分页是两回事。聚合用 composite aggregation 做分页，不要用 from + size。

8.8 max_result_window 调大后依然慢

即使把 max_result_window 调到 100 万，深分页依然慢。治标不治本，还是要用 search_after 或 scroll。

9. 总结

  • from + size：简单，但深分页会拖垮集群，ES 用 10000 上限保护自己。
  • search_after：记住“上一页最后一条”，从它后面继续取，实时、快、无限深，适合逐页往后翻。
  • scroll：先拍快照，再慢慢批量取，适合一次性导出全量数据，但不实时、要清理。
  • PIT + search_after：ES 7.10+ 推荐方案，兼顾快照一致性和高效翻页，适合深分页搜索。

核心原则：能不用深分页就不用；必须深分页时，优先 search_after，导出场景用 scroll，需要一致性视图用 PIT + search_after。

一、为什么需要限流

限流的本质，是在系统容量与请求流量之间划一条明确的边界。

1.1 不做限流的三种死法

方式一：精确时间戳（内存高）

内存开销：每个请求一个 Long（8 字节）+ 队列开销。1000 QPS × 1 秒窗口 = 1000 个记录。如果窗口是 60 秒，QPS 是 1 万 → 60 万个记录 → 内存爆炸。

方式二：分桶统计（折中方案）

把窗口切成 N 个小格子（如 10 个 100ms 的格子），每个格子一个计数器。窗口内请求数 = 所有桶的 count 之和。当时间前进时，新桶加入，旧桶淘汰（环形数组实现）。

flowchart TB
    subgraph Ring["环形数组（固定大小 N）"]
        direction LR
        R1["桶0"] --> R2["桶1"] --> R3["桶2"] --> R4["..."] --> R5["桶N-1"] --> R1
    end
    T["时间前进"] --> Advance["淘汰旧桶<br/>新桶清零"]
    Advance --> Ring
    Ring --> Sum["求和 → 判断是否超限"]

精度 vs 内存的权衡：

  • 桶越多，精度越高，内存越大
  • 一般 10 个桶足够（误差 < 10%）

Sentinel 的实现：Sentinel 用的是 LeapArray + 滑动窗口，精度 1 秒分 2 个格子（500ms 一格），兼顾精度和性能。

十、常见面试问题

Q1：固定窗口的边界问题怎么解决？

答：升级到滑动窗口。滑动窗口有两种实现：

  • 精确时间戳（内存高，O(QPS × 窗口)）
  • 分桶统计（内存低，精度略低，Sentinel 用这种）

固定窗口切小粒度只能缓解，无法根治。

Q2：漏桶和令牌桶的本质区别？

答：

  • 漏桶限制流出速率，请求必须排队等待，强制平滑，不允许突发。
  • 令牌桶限制平均速率，桶容量内的突发可以立即通过，允许突发。

一句话：漏桶是”你按我的节奏走”，令牌桶是”你可以在额度内自由发挥”。

Q3：分布式限流怎么保证总量？

答：核心是集中式计数器。方案：

  1. Redis + Lua（推荐）：原子性强，一次 RTT。
  2. 分段配额：每实例预分配一段，减少 Redis 压力，但流量不均时浪费。
  3. Sentinel 集群模式：Token Server 集中发令牌。

面试重点：单机限流 × N 实例 ≠ 总量限流。

Q4：令牌桶的令牌为什么要惰性补充？

答：如果每 100ms 定时补一次令牌，需要后台定时器，N 个限流 key 就需要 N 个定时任务，资源浪费。惰性补充是每次请求时按流逝时间计算应补多少，把 O(N) 的定时成本变成 O(1) 的请求成本。

Q5：限流和熔断的区别？

答：

维度 限流 熔断
触发时机 请求到达前 调用下游失败率高时
保护对象 自己 调用方
状态 无状态/简单状态 三态（关闭/半开/打开）
恢复方式 自动（时间窗口） 需探测（半开状态试调用）

Q6：限流阈值怎么定？

答：三步法：

  1. 压测确定单机容量：P99 RT < 200ms 时的最大 QPS。
  2. 留 20% buffer：阈值 = 压测值 × 0.8。
  3. 动态调整：通过 Nacos 配置，大促前手动调整。

不要拍脑袋：max=1000 这种数字必须有压测数据支撑。

Q7：限流拦截器为什么用 ThreadLocal 记录开始时间？

答：preHandle 和 postHandle / afterCompletion 是同一个线程执行的（同步请求），用 ThreadLocal 传递状态最简单。**必须 remove()**，因为 Tomcat 线程池会复用线程，不 remove 会导致内存泄漏 + 脏数据。

注意：异步请求（Callable、DeferredResult）会切换线程，ThreadLocal 会失效，需要改用 RequestContextHolder 或 AsyncListener。

Q8：为什么 429 响应要带 Retry-After？

好处：

  • 规范客户端行为，避免盲目重试
  • 配合指数退避，保护服务端

本节要解决什么问题：一个 HTTP 请求从 Tomcat 进来，到 Controller 方法执行、再到响应返回，中间经过哪些组件、每个组件干什么。

一次请求的完整旅程

核心调度代码在 DispatcherServlet.doDispatch()：

完整九步：

  1. 请求进入 Servlet 容器（Tomcat）→ 经过 Filter 链（见第 9 节）→ 到达 DispatcherServlet。
  2. getHandler：按 HandlerMapping 链逐个尝试匹配，RequestMappingHandlerMapping 根据 @RequestMapping 注册的路由表返回 HandlerExecutionChain。
  3. getHandlerAdapter：为 Handler 找到适配器（RequestMappingHandlerAdapter）。
  4. applyPreHandle：执行拦截器链的 preHandle，任一返回 false 则请求在此中断。
  5. ha.handle：适配器调用 Controller 方法——HandlerMethodArgumentResolver 链解析参数（@RequestBody 由 HttpMessageConverter 把 JSON 反序列化为对象，@PathVariable/@RequestParam 做数据绑定与类型转换），方法执行后由 HandlerMethodReturnValueHandler 处理返回值。
  6. 返回 ModelAndView：有 @ResponseBody（或 @RestController）时返回 null 的 ModelAndView，返回值直接由 HttpMessageConverter（Jackson 的 MappingJackson2HttpMessageConverter）序列化写入响应体。
  7. applyPostHandle：拦截器 postHandle（视图渲染前回调）。
  8. processDispatchResult：若 Handler 抛异常，交给 HandlerExceptionResolver（@ExceptionHandler 在此生效）；否则进入视图解析——ViewResolver 把逻辑视图名解析为 View，渲染后输出。
  9. afterCompletion（拦截器）：请求处理完成后的清理回调，随后响应返回客户端。

MVC 九大组件完整清单

DispatcherServlet 的工作不是”硬编码”的，而是把请求处理拆成九个可插拔的组件（策略），每个组件都有默认实现、都能被用户替换——这就是 Spring MVC 扩展性的来源。九大组件与默认实现：

# 组件 职责（一句话） 默认实现
1 HandlerMapping 请求 URL → Handler 执行链（Handler + 拦截器） RequestMappingHandlerMapping（解析 @RequestMapping）、BeanNameUrlHandlerMapping 等
2 HandlerAdapter 适配不同风格的 Handler，负责参数解析与返回值处理 RequestMappingHandlerAdapter（最常用）、HttpRequestHandlerAdapter、SimpleControllerHandlerAdapter
3 HandlerExceptionResolver 处理 Handler 抛出的异常 → 错误响应 ExceptionHandlerExceptionResolver（驱动 @ExceptionHandler）、ResponseStatusExceptionResolver、DefaultHandlerExceptionResolver
4 ViewResolver 逻辑视图名 → 物理 View InternalResourceViewResolver（JSP）、ThymeleafViewResolver、ContentNegotiatingViewResolver
5 RequestToViewNameTranslator 没有显式视图名时，从请求 URL 推导视图名 DefaultRequestToViewNameTranslator（如 /orders/detail → 视图名 orders/detail）
6 LocaleResolver 解析请求所属地区（国际化） AcceptHeaderLocaleResolver（按 Accept-Language）、SessionLocaleResolver、CookieLocaleResolver
7 ThemeResolver 解析主题（UI 皮肤切换） FixedThemeResolver（固定默认主题）、SessionThemeResolver、CookieThemeResolver
8 MultipartResolver 解析文件上传请求 StandardServletMultipartResolver（Servlet 3.0+ 标准）、CommonsMultipartResolver（Apache Commons FileUpload）
9 FlashMapManager 重定向场景的参数传递（Flash Attribute：一个请求存、下一个请求取，用完即删） SessionFlashMapManager

为什么是”九大”：DispatcherServlet 的 initStrategies() 方法在启动时依次初始化这九个策略，一个不多一个不少：

默认实现的来源：每个组件的默认类写在与 DispatcherServlet 同包的 DispatcherServlet.properties 中（如 org.springframework.web.servlet.i18n.AcceptHeaderLocaleResolver）。初始化逻辑是”先容器后默认“：先从 WebApplicationContext 中找同类型的 Bean，找到就用用户配置的；找不到才 new 一个默认实现——所以覆盖九大组件 = 往容器里注册一个对应类型的 Bean，例如自定义 MultipartResolver 或替换 LocaleResolver。

面试一句话：九大组件是 DispatcherServlet 的可插拔策略点，核心流程只依赖接口（doDispatch 里只调 HandlerMapping/HandlerAdapter/HandlerExceptionResolver），换实现不需要改框架代码。

最容易搞错的几个点

  1. HandlerMapping 只负责找 Handler，不负责调用 Controller。
  2. HandlerAdapter 才负责参数解析、反射调用、返回值处理。
  3. @ResponseBody / @RestController 时，ModelAndView 是 null，不走 ViewResolver。
  4. 响应体是在 ha.handle() 里由 HttpMessageConverter 写出去的。
  5. Filter 在 DispatcherServlet 外，Interceptor 在 DispatcherServlet 内。
  6. preHandle 正序，postHandle 逆序，afterCompletion 逆序。
  7. 异常也会走 processDispatchResult，由 HandlerExceptionResolver 处理。
  8. @RequestBody 用 HttpMessageConverter，@RequestParam/@PathVariable/@RequestHeader 用 ArgumentResolver + 类型转换。
