并发性能工程：容量、压测与全系列总表

Posted on 2026-10-26 In Java Word count in article: 3.4k Reading time ≈ 12 mins.

给 2000 个请求、32 个线程，吞吐 3,891/s；加到 64 个线程，吞吐 7,299/s；再加到 128 个线程，吞吐只到 8,287/s，而 p99 从 9.7 ms 涨到 34.9 ms。这就是拐点。

这一篇是收官篇，回答「要多少线程、多大池、几张卡」：用 Little’s law 算容量、压测找拐点、量 GC 停顿对延迟的影响，最后给全系列 12 篇的总表。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM → ④ 伪共享 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程（本文·收官）

与前后篇的关系：② 的线程成本、⑧ 的池大小、⑪ 的虚拟线程，最终都收敛到本文的「容量」问题。

1. 容量三问

问题 公式 输入
要多少并发（线程/连接） L = λ × W（Little’s law） 目标 QPS、单请求耗时
要多大的池 并发数 = 池大小（IO 密集） 同上
要多少台机器 总 QPS ÷ 单机上限 单机压测拐点 
flowchart LR
    A["Target QPS (lambda)"] --> C["L = lambda x W"]
    B["Latency W"] --> C
    C --> D["Concurrency L<br/>= pool size"]
    D --> E{"CPU allows?"}
    E -- yes --> F["bounded queue +<br/>measured knee"]
    E -- no --> G["scale out / async /<br/>reduce W"]

2. Little’s law：并发 = 吞吐 × 延迟

2.1 实测验证

每个请求 = 2 ms CPU + 5 ms 睡眠（W ≈ 7~8 ms），固定 3000 个请求：

池大小 吞吐 λ（/s） p50（ms） p99（ms） λ×W（理论并发）
4 488 8.3 8.3 4.0
16 1,948 8.3 8.5 16.1
32 3,891 8.3 8.5 32.1
64 7,299 8.4 9.7 61.5
128 8,287 10.2 34.9 84.8
256 8,547 10.9 49.0 93.4

λ×W 与池大小高度吻合（4.0 vs 4、16.1 vs 16、32.1 vs 32、61.5 vs 64）——这验证了 Little’s law 可以直接用来算容量。

2.2 怎么用

场景 用法
IO 密集服务 池 = 目标QPS × 平均耗时，再用压测校准
CPU 密集服务 池 = 核数 + 1，用吞吐验证
混合 拆成两个池，分别算

3. 拐点：吞吐不涨、延迟暴涨的地方

3.1 实测曲线

池大小 吞吐 p50 p99
32 3,891 8.3 8.5
64 7,299 8.4 9.7
128 8,287 10.2 34.9
256 8,547 10.9 49.0

从 64 到 128：吞吐只涨 13%，p99 涨了 3.6 倍。这就是拐点。

flowchart LR
    A["pool 32<br/>3891/s p99 8.5"] --> B["pool 64<br/>7299/s p99 9.7<br/>KNEE"]
    B --> C["pool 128<br/>8287/s p99 34.9"]
    C --> D["pool 256<br/>8547/s p99 49.0"]
    D -.->|"+3% throughput<br/>+40% p99"| E["negative return"]

3.2 拐点由什么决定

CPU 上限：每个请求 2 ms CPU，15 核 → 理论上限 15 ÷ 0.002 = 7,500/s。

指标 数值
理论上限 7,500/s
实测拐点吞吐（pool=64） 7,299/s
实测最大吞吐（pool=256） 8,547/s

实测最大吞吐略高于理论值，因为部分请求的 CPU 时间被 sleep 切碎、核间调度有空隙。但量级完全吻合——拐点不是玄学，是 CPU 除法。

3.3 判断标准

现象 判断
加线程吞吐线性涨、p99 平稳 还没到拐点
加线程吞吐涨 < 20%、p99 涨 > 2 倍 已过拐点，回去减线程
减线程后 p99 明显下降、吞吐略降 减得对

4. GC 对并发的影响

4.1 实测：小堆 vs 大堆

32 线程、2000 个任务，每任务分配 8 MB：

堆大小 GC 次数 GC 总停顿 平均停顿 p50 p99
128 MB 267 77.3 ms 0.29 ms 2.6 ms 17.4 ms
2048 MB 46 21.2 ms 0.46 ms 1.2 ms 17.9 ms

关键观察：

现象 解释
小堆 GC 次数多 6 倍 空间小，很快填满
但单次停顿更短 Young GC 只扫存活对象，堆小扫得快
总停顿差 3.6 倍 77.3 vs 21.2 ms
p50 差 2 倍 总停顿直接吃掉吞吐
p99 几乎没变 p99 由分配/队列决定，不是 GC 
flowchart TD
    A["allocation rate high"] --> B{"heap size?"}
    B -- small --> C["frequent young GC<br/>267 times, 77ms total"]
    B -- large --> D["rare young GC<br/>46 times, 21ms total"]
    C --> E["p50 worse (2.6 vs 1.2ms)"]
    D --> F["p50 better"]
    C -.-> G["p99 unchanged:<br/>dominated by allocation + queueing"]

4.2 三个结论

结论 说明
GC 停顿会吃吞吐 77 ms 停顿占 260 ms 墙钟的 30%
大堆不一定更好 单次停顿更长（0.46 vs 0.29 ms），但次数少很多
p99 不一定是 GC 造成的 本文 p99 主要由分配与排队决定

排查顺序：先看 GC 日志确认停顿占比，再决定调堆还是调代码。别把「p99 高」直接归因于 GC。

6. 动手验证：四个可复现实验

6.1 动手验证：画吞吐-延迟曲线找拐点

预期观察点：吞吐在某个池大小后不再增长，而 p99 开始暴涨（本文拐点在 64）。

判定标准：

  • 吞吐一直线性涨 → 任务太轻，CPU 还没饱和，加大 CPU 时间；
  • p99 从一开始就高 → 队列容量或 GC 有问题，先看 6.3。

6.2 动手验证：验证 Little’s law

预期观察点：lambda*W 与 pool 接近（比值 ≈ 1.0）。

判定标准：

  • 比值远小于 1 → 线程没跑满（任务太短或队列空）；
  • 比值大于 pool → 计数口径不对（比如 p50 用了别的单位）。

6.3 动手验证：GC 停顿对并发的影响

预期观察点：小堆 GC 次数明显更多（本文 267 vs 46），p50 更差（2.6 vs 1.2 ms）。

判定标准：

  • 两者 GC 次数接近 → 分配速率太低，加大每任务分配量；
  • 小堆 p99 也明显更差 → 发生了 Full GC，检查是否有大对象晋升。

6.4 动手验证：算一次容量

预期观察点：输出需要的并发数与所需机器数。

判定标准：

  • 并发数 > 1000 → 先考虑虚拟线程（⑪）或异步化；
  • 机器数出现小数 → 向上取整，并留 30% 余量。

7. 总结

7.1 面试速答表

面试题 一句话答案
怎么算需要多少线程 L = λ × W（Little’s law），IO 密集用，CPU 密集用核数
压测拐点是什么 吞吐不再增长、延迟开始暴涨的点（本文 64 线程）
拐点由什么决定 CPU 上限：核数 ÷ 单请求 CPU 时间
小堆和大堆哪个延迟低 小堆 GC 次数多、单次短；大堆次数少、单次长（本文 p50 2.6 vs 1.2）
p99 高一定是 GC 吗 不一定，本文 p99 由分配与排队决定，GC 影响 p50
怎么判断该加机器 单机拐点吞吐 × 机器数 < 目标 QPS
线程池开多大 先用公式算，再用压测曲线校准
为什么加线程 throughput 不涨 已过 CPU 拐点，或有无界队列/锁竞争
虚拟线程改变容量公式吗 改变的是「线程成本」，不改变 CPU 上限
容量规划的第一步 先量单机上限，再乘机器数

7.2 实战避坑表

症状 原因 处理
加机器后 QPS 不涨 瓶颈在单机 CPU/锁 先优化单机（⑤⑥⑧）
p99 高但 p50 正常 队列/GC/慢依赖 看 GC 日志与排队时间
池开大反而慢 过了拐点 回到拐点附近
高峰期频繁 Full GC 分配速率过高 减少分配、调大年轻代
压测结果不可复现 没有固定环境与预热 记录环境、预热、多轮取最优

7.3 工具速查表

工具 看什么 判定标准
-Xlog:gc GC 次数与停顿 总停顿占墙钟比例
压测脚本（本文 Curve） 吞吐与 p99 拐点即最优池大小
Little’s law 并发需求 λ×W 与池大小对照
JFR 线程、锁、GC 事件 结合 ②⑩ 读法
CPU 使用率 是否到上限 接近 100% 说明该扩机器

7.4 实操建议

  1. 先用 L = λ×W 算，再用压测校准，最后留 30% 余量。
  2. 压测必须画「吞吐-p99」双曲线，只看吞吐会误导。
  3. GC 日志先看总停顿占比，再决定调堆还是调代码。
  4. 拐点之后加线程是负优化，该加机器或异步化。
  5. 把每次压测的环境与数字记下来，下次扩容才有依据。

系列完结。十二篇的因果链是一条：先量成本（①②）→ 再保证正确性（③④⑤）→ 理解机制（⑥⑦）→ 工程化（⑧⑨⑩⑪）→ 最后算容量（⑫）。

虚拟线程：pinning、吞吐与迁移代价

Posted on 2026-10-26 In Java Word count in article: 2.8k Reading time ≈ 10 mins.

虚拟线程不是「更快的线程」，是「更便宜的阻塞」。实测 2000 个 10ms 的 IO 任务：平台线程池（200 线程）126 ms，虚拟线程 23 ms——快 5.5 倍；但如果在任务里用 synchronized 包住阻塞调用，同样的 2000 个任务要 1,571 ms，慢 68 倍。

这就是 pinning：虚拟线程在 synchronized 块里阻塞时，会把它所在的载体线程一起占住，退化成平台线程。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM → ④ 伪共享 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程（本文） → ⑫ 并发性能工程

与前后篇的关系：② 的「1 MB/线程」是虚拟线程要解决的问题；⑧ 的「IO 密集池开大」在虚拟线程里换成「每个任务一个虚拟线程」。

1. 虚拟线程解决的是什么问题

问题（平台线程） 虚拟线程的做法
1 MB 栈/线程（②实测） 栈存在堆里，按需增长，初始几百字节
阻塞要占住一个 OS 线程 阻塞时 unmount，把载体线程还给调度器
线程数受内存限制（1000 线程 ≈ 1 GB） 可以创建几十万个
线程池要精细调参（⑧） 每个任务一个虚拟线程，不用池 
flowchart LR
    A["virtual thread A"] -->|mount| C1["carrier 1"]
    B["virtual thread B"] -->|blocked on IO| D["unmount"]
    D -->|free| C1
    E["virtual thread C"] -->|mount| C1
    D -.->|堆里的栈| F["continuation"]

关键概念：

术语 含义
虚拟线程 用户态调度的轻量线程
载体线程（carrier） 真正执行虚拟线程的平台线程，数量默认 = 核数
mount / unmount 虚拟线程挂到载体上 / 从载体上摘下来
pinning 虚拟线程阻塞时不能 unmount，把载体占住

2. 实测：IO 任务快 5 倍

2000 个「睡 10 ms」的任务：

方案 耗时 吞吐
平台线程池（200 线程） 126 ms 15,873 tasks/s
虚拟线程 23 ms 86,957 tasks/s
虚拟线程 + ReentrantLock（每任务独立锁） 15 ms 133,333 tasks/s 
flowchart TD
    A["2000 tasks x 10ms sleep"] --> B["platform pool(200): 126ms"]
    A --> C["virtual threads: 23ms"]
    A --> D["virtual + per-task lock: 15ms"]
    A --> E["virtual + synchronized: 1571ms"]

为什么虚拟线程快：平台线程池只有 200 个线程，2000 个任务要分 10 批；虚拟线程 2000 个可以同时「挂着睡」，只要有空闲载体就继续跑。

3. Pinning：synchronized 里的阻塞

3.1 实测：慢 68 倍

同样的 2000 个任务，只是把 sleep 包进 synchronized（每个任务用自己的 monitor，排除锁竞争）：

方案 耗时 吞吐
虚拟线程 + 普通 sleep 23 ms 86,957 tasks/s
虚拟线程 + synchronized 内 sleep 1,571 ms 1,273 tasks/s

折算：2000 个任务 × 10 ms ÷ 15 个载体 ≈ 1,333 ms，与实测 1,571 ms 吻合——虚拟线程被串行化到 15 个载体上，等于退化成平台线程池。

sequenceDiagram
    participant VT as virtual thread
    participant CR as carrier (15 total)
    participant MON as monitor
    VT->>MON: enter synchronized
    VT->>CR: Thread.sleep (blocking inside monitor)
    Note over CR: PINNED: cannot unmount
    Note over CR: 15 carriers -> only 15 concurrent tasks
    VT->>MON: exit, CR released

3.2 一个更容易踩的变体：持同一把锁睡眠

如果所有任务抢同一把锁，然后在锁内睡眠，问题比 pinning 更严重：

方案 耗时 吞吐
虚拟线程 + 各自 monitor（pinning） 1,571 ms 1,273 tasks/s
虚拟线程 + 同一把锁内睡眠 23,750 ms 84 tasks/s

23.75 秒 ≈ 2000 × 12 ms——完全串行。这不是 pinning，是锁本身把并发变成了串行。

现象 根因 修复
慢 68 倍 pinning（载体被占） 把 synchronized 换成 ReentrantLock
慢 1000 倍 锁内做阻塞 把阻塞移出临界区

JDK 21（本文） 会（JEP 444 已知限制）
JDK 24+ 不会（JEP 491 修复）

4. 规模：10 万虚拟线程 vs 1 万平台线程

方案 数量 耗时 平台线程数
虚拟线程（各睡 100 ms） 100,000 523 ms 2
平台线程 2,000 163 ms 2,000+
平台线程 10,000 635 ms 10,000+

10 万个虚拟线程只需要 2 个平台线程——这就是「虚拟线程不占 OS 线程」的直观证据。而 1 万个平台线程（-Xss512k）就要约 5 GB 虚拟内存。

5. 迁移代价：四个必须改的地方

方面 问题 改法
线程池 虚拟线程不需要池 Executors.newVirtualThreadPerTaskExecutor()
synchronized 阻塞会 pin 换 ReentrantLock
ThreadLocal 每个虚拟线程一份，数量大时内存涨 用 ScopedValue（JDK 21 预览）或减少使用
监控 线程 dump 里虚拟线程不在平台线程列表 用 JFR 的虚拟线程事件（jdk.VirtualThreadStart）

坑 说明
ThreadPoolExecutor 里跑虚拟线程 没意义（虚拟线程不需要池，池还会限制并发）
用虚拟线程做 CPU 密集任务 没收益（还是占载体），甚至更慢

7. 动手验证：四个可复现实验

7.1 动手验证：虚拟线程 vs 平台线程

预期观察点：虚拟线程耗时约为平台池的 1/5（本文 23 vs 126 ms）。

判定标准：

  • 两者接近 → 任务太少（<1000）或睡眠太短（<5ms），调度开销盖过收益；
  • 虚拟线程更慢 → 任务里有 CPU 密集计算或 pinning。

7.2 动手验证：复现 pinning

预期观察点：约 2000×10ms/15 ≈ 1,330 ms（本文 1,571 ms），比不 pin 慢几十倍。

判定标准：

  • 耗时接近 23 ms → 你的 JDK 已修复 pinning（JDK 24+），或阻塞调用能被 unmount；
  • 耗时接近 20 秒 → 所有任务抢同一把锁，那是锁串行化而不是 pinning。

7.3 动手验证：10 万个虚拟线程

预期观察点：10 万个任务约 0.5 秒完成，Thread.activeCount() 只有个位数。

判定标准：

  • Thread.activeCount() 成千上万 → 你用的是平台线程（new Thread），不是虚拟线程；
  • OOM → 堆太小，虚拟线程的栈在堆里，-Xmx 要给够。

7.4 动手验证：迁移后的对照

预期观察点：换成 ReentrantLock 后耗时回到 15~30 ms 量级。

判定标准：

  • 仍然很慢 → 你的阻塞点不在锁内（比如 Thread.sleep 之外还有别的阻塞）；
  • 变快但达不到 20 ms → 有其它 pinning 源（Object.wait、 native 方法）。

2.4 JFR 为什么抓不到

事实 解释
JFR 录制 3 秒，JavaMonitorEnter 0 事件 事件在阻塞开始时记录；线程在录制开始前就已经阻塞
死锁是「永不结束的阻塞」 事件要等阻塞结束才会被完整写出

结论：死锁用 jstack/Thread.print，JFR 用来看「还没死」的慢等待。这是两套互补的工具，不是替代关系。

超时放弃 tryLock(timeout)，失败就回滚重试 需要业务能回滚
减少锁嵌套 只锁一个资源；用无锁结构 需要重构

5.1 动手验证：复现并检测死锁

预期观察点：deadlocked=2，输出两个线程名；Thread.print 打印「谁持有谁等待」。

判定标准：

  • deadlocked=null → 两个线程没有真正交叉（加长 sleep）；
  • Thread.print 没有死锁段 → 你抓的时间点太早，等 2 秒再抓。

5.2 动手验证：统一锁顺序解决死锁

预期观察点：deadlocked=null，both finished=true。

判定标准：

  • 仍检测到死锁 → 两个线程的加锁顺序还是不一致，检查 Runnable 是否被两处复用同一顺序。

5.3 动手验证：线程泄漏与 ThreadLocal 串数据

预期观察点：未 remove 时读到 user-1（串数据）；remove 后读到 null；线程数随创建数线性上涨。

判定标准：

  • 读到 null → 你的池线程是新建的（池大小 > 任务数），把池设为 1 再试；
  • 线程数不涨 → 你可能用了虚拟线程（⑪），它们不占平台线程。

5.4 动手验证：三次采样定位卡点

预期观察点：三次采样里 worker-1 都停在同一个 waiting to lock 行。

判定标准：

  • 三次栈不同 → 线程在正常干活，不是卡死；
  • 栈里出现 Object.wait → 那是 wait/notify 等通知，不是死锁，检查是否漏了 notify。

thenApply 不一定在异步线程里跑。实测：supplyAsync(...).thenApply(...) 里，thenApply 跑在 main 线程上——因为 supplyAsync 完成得太快，回调直接由调用 thenApply 的线程执行了。

2.1 三种正确姿势

方式 用法 注意
exceptionally(fn) 返回兜底值 只处理异常，不改结果

3. 坑二：默认 commonPool 只有 14 个线程

3.1 实测

指标 实测
ForkJoinPool.commonPool().getParallelism() 14（核数 15 − 1）
40 个 500ms 阻塞任务（默认池） 1,512 ms
同样 40 个任务（专用池 40 线程） 507 ms

差 3 倍。因为 commonPool 只有 14 个线程，40 个阻塞任务要分 3 批跑（40/14 ≈ 2.86 批 × 500ms ≈ 1.43s）。

flowchart LR
    A["supplyAsync without executor"] --> B["ForkJoinPool.commonPool<br/>parallelism = cores - 1"]
    B --> C["blocking tasks occupy<br/>the shared pool"]
    C --> D["ALL other async code<br/>in the JVM slows down"]

3.2 为什么危险

commonPool 是整个 JVM 共享的：你的业务代码、某个依赖库、甚至 parallelStream() 都在用它。只要有一个人在里面做阻塞调用（DB 查询、HTTP 请求），所有人一起排队。

用法 风险
supplyAsync(fn) 用 commonPool
runAsync(fn) 用 commonPool
parallelStream() 用 commonPool
supplyAsync(fn, executor) 用你的池，推荐

规则：只要任务里可能有阻塞，就必须传自己的 Executor。

4. 坑三：thenApply 到底在哪个线程跑

4.1 实测

写法 实测线程
supplyAsync(...).thenApply(...) supply@ForkJoinPool.commonPool-worker-7 -> thenApply@**main**
supplyAsync(...).thenApplyAsync(...) supply@worker-7 -> thenApplyAsync@worker-7

thenApply 跑在 main 线程，因为 supplyAsync 在 main 调用 thenApply 之前就完成了，于是 JVM 直接在当前线程执行回调。

方法 执行线程
thenApply / thenAccept / thenRun 完成时的线程（可能是 main、可能是池线程）
thenApplyAsync / thenAcceptAsync 提交到线程池执行
thenApplyAsync(fn, executor) 指定池执行 
sequenceDiagram
    participant M as main
    participant P as commonPool
    M->>P: supplyAsync (fast task)
    P-->>M: already completed
    M->>M: thenApply runs HERE (main)
    Note over M: if callback is heavy, main thread is blocked

4.2 什么时候会出事

场景 后果
回调里有耗时操作 main 线程被占（Web 请求线程被拖慢）
回调里有 ThreadLocal 读写 读到的是 main 的上下文，不是任务的
以为回调在异步线程做 MDC 传递 日志 traceId 丢失

结论：要确定线程就用 *Async + 显式 executor；thenApply 只适合「纯内存、极快」的转换。

5. 坑四：没有超时

5.1 实测

指标 实测
任务本身耗时 2,000 ms
orTimeout(500ms) 后返回 511 ms
异常类型 TimeoutException 
flowchart LR
    A["task submitted"] --> B["orTimeout 500ms timer"]
    B -->|"timer fires first"| C["complete exceptionally<br/>TimeoutException"]
    B -->|"task finishes first"| D["normal result"]
    C --> E["join() throws CompletionException(TimeoutException)"]

5.2 注意点

问题 说明
orTimeout 不会中断任务 任务仍在后台跑（线程继续被占用）
超时后结果被丢弃 但任务本身可能已产生副作用
completeOnTimeout 不同 它给一个默认值而不是抛异常

建议：orTimeout 之外，任务内部也要有超时（HTTP 客户端超时、DB 查询超时），否则线程一直占着。

6. 坑五：CountDownLatch 与 Semaphore 误用

6.1 CountDownLatch 的三个常见错误

错误 现象 实测
await() 不带超时 永久阻塞 —
计数不匹配（少 countDown） 永久等待 await(200ms) 返回 false
多 countDown 不报错，静默忽略 3 次 countDown 后 count=0

实测：new CountDownLatch(2)，未计数时 await(200ms) 返回 false；调 3 次 countDown 也不报错（多余的一次被忽略）。

6.2 Semaphore 的坑

错误 后果
acquire() 后异常路径没 release() 许可泄漏，最终死锁
用 tryAcquire() 不加超时 拿不到就一直等
信号量当锁用 语义混乱，应使用 Lock

7. 动手验证：四个可复现实验

7.1 动手验证：异常被吞

预期观察点：isCompletedExceptionally=true，且只有 join() 那一行才打印异常。

判定标准：

  • join() 没抛 → 任务其实成功了（检查是否真抛了异常）；
  • 主线程直接崩溃 → 你在提交时就 join 了，说明没有异步。

7.2 动手验证：commonPool 被打满

预期观察点：并行度 = 核数−1（本文 14）；commonPool 耗时约为专用池的 3 倍（1,512 vs 507 ms）。

判定标准：

  • 两者耗时接近 → 任务的阻塞时间太短，加大到 1s 以上；
  • 并行度 = 核数 → 设置了 -Djava.util.concurrent.ForkJoinPool.common.parallelism。

7.3 动手验证：thenApply 的线程归属

预期观察点：thenApply 显示 main（或调用线程），thenApplyAsync 显示 commonPool-worker-*。

判定标准：

  • thenApply 也显示 worker → 任务还没完成就注册了回调（比如内部加了 sleep），换个快速任务再测；
  • 两者都在 main → 你的 supplyAsync 没有真正异步。

7.4 动手验证：超时与 CountDownLatch

预期观察点：超时在 ~500 ms 抛 TimeoutException；await(200ms) 返回 false；多调 countDown 后 count 为 0 且不报错。

判定标准：

  • 超时耗时接近 2000 ms → orTimeout 没生效（检查 JDK 版本，需 9+）；
  • await 返回 true → 计数被别处减完了，检查是否共享了同一个 latch。

8. 总结

8.1 面试速答表

面试题 一句话答案
CompletableFuture 的异常怎么处理 exceptionally / handle / whenComplete，且必须 join 或检查
不 join 会怎样 异常被吞，isCompletedExceptionally=true 但无人知晓
默认线程池是什么 ForkJoinPool.commonPool()，并行度 = 核数 − 1（本文 14）
为什么不能用 commonPool 做阻塞任务 它是全 JVM 共享的，会拖慢所有异步代码（本文慢 3 倍）
thenApply 在哪个线程执行 完成时的线程（可能是 main），要确定就用 thenApplyAsync + 显式池
怎么给异步任务加超时 orTimeout(ms) 抛异常，completeOnTimeout 给默认值
orTimeout 会中断任务吗 不会，任务继续跑，线程仍被占用
CountDownLatch 的坑 不带超时的 await 永久阻塞；计数不匹配会等死
多调 countDown 会怎样 不报错，静默忽略（本文实测 count 变 0）
Semaphore 最容易漏什么 release() 必须在 finally，否则许可泄漏
allOf 中一个失败会怎样 allOf 完成异常，但其他任务仍继续执行
thenApply 与 thenCompose 区别 前者返回普通值，后者返回 CompletableFuture（扁平化）

8.2 实战避坑表

症状 原因 处理
异步任务失败无日志 没人 join/没加 exceptionally 统一加 whenComplete + 日志
高峰期异步接口全变慢 阻塞任务挤占 commonPool 传自己的 executor
回调里的 traceId 丢了 回调跑在别的线程 用 *Async + 上下文传递
一个慢依赖拖死全链路 没有超时 orTimeout + 客户端超时
服务关闭卡住 await() 无超时 加超时 + shutdown
信号量泄漏 异常路径没 release try/finally

8.3 工具速查表

工具 看什么 判定标准
ForkJoinPool.commonPool().getParallelism() 默认池并行度 核数 − 1
JFR jdk.ThreadPoolExecutor / jdk.ForkJoinPool 池状态 队列积压 = 池太小或任务阻塞
jcmd Thread.print 线程名 commonPool-worker-* 大量 BLOCKED = 阻塞任务进了公共池
orTimeout / completeOnTimeout 超时 必须有

8.4 实操建议

  1. 所有 supplyAsync/runAsync 都传自己的 executor，禁止裸用默认池。
  2. 每个 CompletableFuture 链都要有异常处理（whenComplete 至少打日志）。
  3. 回调里要做耗时操作就用 *Async + 显式池，别赌 thenApply 在哪个线程。
  4. 所有外部依赖加超时：orTimeout 只是兜底，客户端超时才是第一道。
  5. CountDownLatch 的 await 一律带超时，Semaphore 的 release 一律放 finally。
