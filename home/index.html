Redis 集群与高可用实战：主从、哨兵与 Cluster

Posted on 2026-08-13 In 数据存储 Word count in article: 3.1k Reading time ≈ 11 mins.

单机 Redis 能用，但「扛不住」时只有两个问题：机器挂了怎么办（高可用），数据量大了怎么办（扩容）——分别对应哨兵和 Cluster。 本文按「单机 → 主从 → 哨兵 → Cluster」的演进线讲透：主从为什么选异步复制、哨兵怎么避免误判（主观下线 vs 客观下线）、Cluster 槽位怎么路由与迁移、以及脑裂在 Redis 里怎么发生。读完你能独立搭出一套哨兵集群，并能在面试中画出主从切换的完整时序。

联动：本文是 Redis 深度解析（数据结构/持久化/缓存设计）的高可用续篇；主从复制与 MySQL 高可用 的主从是同一思路；哨兵选举与 ZooKeeper 原理与实践 的选主机制呼应；脑裂防护与 ES 原理深挖 的 minimum_master_nodes 是同一个「过半」思想。

1. 定位：演进线就是面试线

Redis 高可用是一个「一步步加组件」的演进过程，每个阶段解决一个问题、引入一个新概念：

阶段 解决什么 关键机制 代价/限制
单机 基本可用 无 单点故障、容量单机上限
主从 数据冗余 + 读扩展 异步复制 主挂需人工切换
哨兵 自动故障转移 监控 + 选举 仍是单主写（写不扩容）
Cluster 自动分片扩容 槽位路由 跨槽多键操作受限

因果链：主从解决「数据不丢」和「读扛不住」→ 但切换要人工 → 哨兵自动化 → 但写仍是单点 → Cluster 分片让写也能扩容。面试答 Redis 高可用，按这条演进线讲，逻辑自动闭环。

2. 主从复制：异步复制的真相

2.1 复制流程

sequenceDiagram
    participant S as 从节点
    participant M as 主节点
    S->>M: 1. 建立连接，请求同步
    M->>S: 2. 全量同步（RDB 快照 + 缓冲）
    S->>S: 3. 载入 RDB，应用缓冲增量
    Note over M,S: 此后：M 每写一条就异步推给 S（增量同步）
机制 说明
全量同步 首次/断连太久：主节点生成 RDB 快照传输
增量同步 断连短暂：repl_backlog 缓冲补发
复制偏移量 主从各自维护 offset，比对差异

2.2 为什么默认异步复制（面试核心）

维度 异步复制 同步复制（WAIT 命令可选）
主节点写延迟 无（写完就返回） 等从节点确认
一致性 弱一致（从节点可能短暂落后） 强
故障窗口 主挂瞬间，未复制的数据丢失 不丢（但主也写不快）
生产选择 默认（性能优先） 严格不丢数据的场景（罕见）

因果链：Redis 定位是缓存/高速存储，性能优先于强一致——所以默认异步。「主节点挂了丢几秒数据」是异步复制的已知代价，用「哨兵秒级切换 + 业务容忍短暂不一致」接受它（这与 MySQL 半同步 的选择逻辑对比着看：MySQL 数据价值高所以有半同步选项，Redis 缓存容忍丢）。

2.3 动手验证：主从复制与主挂现场

观察点：主挂后从节点只读拒绝写入——「主从不做自动切换，必须靠哨兵」的现场证据。判定标准：亲手确认「主从只解决读扩展与冗余，故障转移需要哨兵」，这是理解为什么需要哨兵的第一课。

3. 哨兵：自动故障转移

3.1 三个哨兵能力 + 主观/客观下线

能力 机制
监控 每秒 PING 主从节点，检查存活
通知 主节点变化通知客户端
自动故障转移 主挂了：选举新主 → 通知其他从切换主

下线判定两级：

判定 条件 动作
主观下线（sdown） 单哨兵发现主节点超时（down-after-milliseconds） 标记 sdown，开始投票
客观下线（odown） 多数哨兵（quorum）都认为挂了 触发故障转移

因果链：单哨兵可能误判（网络抖动）→ 必须多数派确认才真切换 → quorum 防误判。这与 ES 脑裂防护、ZooKeeper 选主是同一个「过半」思想（ES 原理深挖 已讲过 minimum_master_nodes=N/2+1）。

3.2 故障转移的完整时序（面试必画）

sequenceDiagram
    participant S1 as 哨兵1
    participant S2 as 哨兵2
    participant S3 as 哨兵3
    participant A as 主节点
    participant B as 从节点B
    S1->>S1: A 超时 → 主观下线
    S1->>S2: 投票：A 挂了？
    S1->>S3: 投票：A 挂了？
    S2-->>S1: 同意
    S3-->>S1: 同意（达到 quorum=2）
    S1->>S1: A 客观下线 → 触发故障转移
    S1->>B: 选 B 为新主（slaveof no one）
    S2->>B: 其他从节点重定向到 B
    Note over S1: 客户端感知新主地址（Sentinel 客户端订阅通知）

选举规则（面试加分）：新主选择优先级 = 复制偏移量最大（数据最新）→ 优先级 → runId 最小——「数据最新者优先」防止选举后丢数据。

3.3 动手验证：模拟主挂自动切换

观察点：主节点停止后 5-10 秒内，get-master-addr-by-name 返回的不再是 6379——故障转移自动完成，无需人工。判定标准：亲手复现「主挂 → 哨兵自动选新主」，理解「哨兵把人工切换变成了自动化」。

3.4 哨兵的两大坑：脑裂与误切换

坑 场景 后果 防护
脑裂 主节点网络分区（假死），哨兵选新主；老主恢复后两个主并存 客户端写入分裂，老主数据丢失 min-replicas-to-write：主节点写前要求至少 N 个从节点可达，否则拒写
误切换 单哨兵抖动误判（quorum=1） 不必要切换、短暂不可写 quorum ≥2 且哨兵数 ≥3（奇数）

因果链：脑裂的根源是「老主不知道自己已被判死刑」——用 min-replicas-to-write 让老主在失去多数从节点时自动拒写，「宁可拒绝写入也不接受分裂」与 分布式事务 的「牺牲可用性保一致性」同理。面试答 Redis 脑裂：min-replicas-to-write + 说明「老主被分区时拒写，恢复后数据不丢」。

4. Cluster：分片让写也能扩容

4.1 槽位路由：16384 个槽

Cluster 把 key 空间切成 16384 个槽（slot），每个节点负责一段槽：

flowchart LR
    K["key"] --> H["CRC16(key) % 16384"] --> S["槽号"]
    S --> N1["节点A: 槽 0-5460"]
    S --> N2["节点B: 槽 5461-10922"]
    S --> N3["节点C: 槽 10923-16383"]
机制 说明
路由 客户端算 CRC16 找槽，槽→节点映射表（或经代理）
重定向 请求打到错误节点 → MOVED/ASK 错误告知正确节点
槽迁移 扩容/缩容时槽从旧节点搬到新节点（在线）
副本 每个节点可有从节点，主挂自动升（类哨兵，内置）

4.2 Cluster 的限制与应对

限制 原因 应对
多 key 操作受限 不同 key 在不同槽/节点 哈希标签（hash tag）：{user:1}:cart 强制同槽
跨槽事务 同上 hash tag 或应用层补偿
批量命令受限 mget 跨节点 hash tag / 客户端分片聚合

因果链：分片的代价是「数据分散」→ 关联数据必须「强制同槽」（hash tag）——面试答 Cluster 的坑，先说「多 key 操作受槽位限制」，再补「用 hash tag 让关联 key 同槽」就是完整答案。

4.3 动手验证：起一个三主三从 Cluster

观察点：CLUSTER SLOTS 显示 16384 个槽分成 3 段；-c 模式下 SET 自动完成路由与重定向。判定标准：亲手确认「Cluster 按槽路由、客户端无需知道槽映射」——扩容只迁移槽，不用改客户端（配合代理/客户端集群感知）。

5. 面试应答：Redis 高可用五连问

5.1 完整话术

面试题 回答要点
主从复制怎么工作？ 全量 RDB + 增量 backlog；默认异步（性能优先，容忍短暂落后）
为什么异步？ 同步写要等从节点确认，延迟高；Redis 缓存语义接受弱一致
哨兵怎么防误判？ 主观下线（单哨兵）→ 投票多数派 → 客观下线才切换；quorum ≥2、哨兵奇数
新主怎么选？ 复制偏移量最大（数据最新）→ 优先级 → runId
Redis 脑裂怎么防？ min-replicas-to-write：老主失去多数从节点时拒写
Cluster 怎么路由？ CRC16(key) % 16384 定槽；MOVED/ASK 重定向；hash tag 让关联 key 同槽
什么时候用 Cluster？ 数据量超单机内存或写吞吐不够；否则哨兵够用

5.2 深挖：与 MySQL 高可用的对照（跨篇联动）

维度 MySQL Redis
复制 binlog 异步/半同步（MySQL 高可用） RDB/backlog 异步
自动切换 MHA/Orchestrator 哨兵
脑裂防护 半同步 + 仲裁 min-replicas-to-write
扩容 分库分表（人工） Cluster 槽迁移（在线）
数据价值 高（强一致优先） 缓存/高速（性能优先）

一句话：MySQL 与 Redis 的高可用是同构的——复制 → 自动切换 → 脑裂防护，三件套一样，差别只在「一致性 vs 性能」的权重不同。跨库对照是面试差异化亮点：「MySQL 选半同步因为数据贵，Redis 选异步因为要快，但脑裂防护思想完全一致」。

6. 总结

6.1 面试速答表

面试题 一句话答案
主从解决什么？ 数据冗余 + 读扩展；写仍是单点，主挂需切换
复制方式？ 全量 RDB + 增量 backlog；默认异步
哨兵三能力？ 监控、通知、自动故障转移
sdown/odown？ 主观=单哨兵判定；客观=多数派确认
新主选举规则？ 偏移量最大 → 优先级 → runId
脑裂？ 老主假死被分区，恢复后拒写（min-replicas-to-write）
Cluster 槽位？ 16384 槽，CRC16(key) 路由；MOVED/ASK 重定向
多 key 受限？ hash tag {key} 强制同槽
何时用 Cluster？ 容量/写吞吐超单机；否则哨兵 + 多从够用

6.2 实战避坑表

症状 原因 处理
主挂后丢几秒数据 异步复制正常窗口 接受或上 WAIT 同步（牺牲性能）

消息队列选型与核心机制对比

Posted on 2026-08-13 In 中间件 Word count in article: 3k Reading time ≈ 11 mins.

「Kafka、RocketMQ、RabbitMQ 到底选哪个？」——这个问题答不好，是因为顺序搞反了：选型不是选名字，是选「机制」与「场景」的匹配。 本文先讲透四个核心机制（消息不丢、幂等、顺序、事务消息），再给一张决策树把选型变成套公式：吞吐要多大、延迟要多低、要不要事务消息、团队熟哪个生态。读完你不仅能答「三选一」，还能说清「为什么 Kafka 扛不住强顺序事务、为什么 RabbitMQ 到不了百万级吞吐」——这两个「为什么」才是面试的区分点。

联动：本文是 Kafka 原理与实践、RocketMQ 原理与实践 的选型总纲；事务消息与 分布式事务：从 2PC 到 Seata 的本地消息表同源；削峰场景见 秒杀系统设计（MQ 是削峰三件套之一）。

1. 定位：MQ 解决什么问题

问题 用 MQ 怎么解 例子
解耦 下游系统随时加/减，上游无感知 订单系统发消息，短信/积分/搜索各自订阅
削峰 请求先进队列，下游按自己的速率消费 秒杀 10 万 QPS 进队列，落库 1 万 QPS
异步 非核心路径不等响应 下单后异步发通知，响应从 500ms → 50ms

因果链：MQ 的本质是「缓冲 + 订阅发布」——缓冲解决削峰（生产者快、消费者慢，中间用队列吸收），订阅发布解决解耦（上游只对 topic 说话，不知道下游是谁）。面试先答这三个价值，再答选型，顺序不能反。

选型的真正前提：先懂「机制」，再谈「选型」——不知道「不丢消息」靠什么机制保证，选型就是背参数。本文 §2-§5 讲机制，§6 给决策。

2. 三巨头画像：存储模型决定一切

三个 MQ 的一切差异，根源是「消息存哪、怎么组织」：

维度 Kafka RocketMQ RabbitMQ
存储模型 分区（Partition）追加日志，顺序写磁盘 CommitLog 顺序写，消费队列是索引 队列内存/磁盘，按交换机路由
吞吐 百万级（顺序写 + 零拷贝） 十万级 万级（单机受队列数限制）
延迟 毫秒~秒级（批量攒批） 毫秒级 微秒~毫秒级（无攒批）
消息顺序 分区内有序（全局需单分区） 队列内有序 单队列有序
事务消息 不支持（2.5+ 有试验版） 原生支持（半消息+回查） 弱（插件）
延迟消息 不支持 原生支持（定时层级） 原生支持
生态 日志/流处理最强（Flink 对接） 阿里系电商场景 AMQP 标准、轻量场景

记忆锚点一句话：

  • Kafka = 日志系统：顺序写盘 + 批量 = 吞吐之王，但「批量」就是「延迟」的代价，且不支持事务消息；
  • RocketMQ = 电商系统：为交易场景设计，事务消息、延迟消息、队列有序是原生能力；
  • RabbitMQ = 消息总线：AMQP 路由灵活、延迟低，但单机吞吐是万级，集群能力弱。

面试话术：先一句话定义「存储模型决定吞吐与能力边界」，再展开三行对比——「Kafka 分区追加日志所以快，RocketMQ commitlog 所以快且能做事务，RabbitMQ 队列路由所以灵活但慢」。

3. 核心机制一：消息不丢——三端各守一段

「不丢消息」是三个环节的接力，任何一端漏守都会丢：

flowchart LR
    P["生产者<br/>ack 机制"] --> B["Broker<br/>持久化"] --> C["消费者<br/>手动 ack"]
环节 丢法 守法 代价
生产者→Broker 发送失败/异步发送丢失 ack 语义：Kafka acks=all、RocketMQ SYNC_MASTER 吞吐下降（等确认）
Broker 存储 机器重启 持久化：Kafka 多副本 ISR 同步、RocketMQ 主从同步刷盘 副本写入开销
Broker→消费者 自动 ack 后消费失败 手动 ack：处理成功才提交 offset 可能重复消费（换来不丢）

因果链核心：不丢与不重是跷跷板——「处理成功才 ack」保证不丢，但处理中崩溃 → 消息会被重新投递 → 重复消费。结论：MQ 的默认语义是 at-least-once（至少一次），「不丢」靠 ack 守，重复靠消费端幂等兜（§4）。面试答「怎么不丢消息」必须说全三端 + 一句「代价是可能重复，所以要有幂等」。

4. 核心机制二：重复消费与幂等三法

重复消费是 at-least-once 的必然产物，消费端必须幂等——三法：

幂等法 原理 适用
唯一键去重 消息带业务唯一 ID，消费时查/写去重表（唯一索引） 通用首选
数据库约束 幂等字段建唯一索引，重复插入直接报错被吞 落库类消费
状态机/版本号 处理前校验状态，已处理则跳过 订单状态流转类

动手验证：用唯一索引做幂等

观察点：同一消息投递两次，第二次 INSERT 主键冲突被捕获后直接 return。判定标准：理解「幂等是消费端职责，不是 MQ 职责」——MQ 只保证 at-least-once，Exactly-once 需要端到端幂等设计。

5. 核心机制三：顺序消息与事务消息

5.1 顺序消息：分区/队列内有序

场景 做法 代价
全局有序 单分区/单队列（吞吐降到单机） 吞吐损失大，极少用
分区有序 同一业务 key 哈希到同一分区（如订单号 → 分区） 按 key 有序，跨 key 无序
有序保证 Kafka：同 key 同分区 + 单消费者线程；RocketMQ：同 key 同队列 消费端也必须单线程

因果链：顺序消息 = 「路由同 key 到同分区」+「消费端串行处理」两步缺一不可——只路由不串行（多线程消费）顺序照样乱。面试陷阱：很多人只答「同 key 同分区」，漏了「消费端单线程」，主动补上这句是加分。

5.2 事务消息：半消息 + 回查

事务消息 = 本地事务 + 消息发送的原子性（与 本地消息表 同思路，但不用业务自己建表）：

sequenceDiagram
    participant P as 生产者
    participant MQ as MQ
    participant DB as 业务库
    P->>MQ: 1. 发送半消息（对消费者不可见）
    P->>DB: 2. 执行本地事务（写订单）
    P->>MQ: 3. 提交/回滚半消息
    MQ-->>P: 4a. 提交 → 消费者可见
    Note over MQ: 4b. 生产者挂了/超时 → MQ 回查本地事务结果
    MQ-->>P: 回查（询问本地事务成功没）

因果链：「先发半消息、后提交」把「发消息」和「业务写」变成可对齐的两步——半消息对消费者不可见，只有本地事务成功后提交才可见；生产者中途挂掉，MQ 通过回查接口（checkLocalTransaction）确认事务结果。这一机制让 RocketMQ 在「有 MQ 的强一致场景」胜出（分布式事务选型 的决策树里「有 MQ 且能最终一致」指向它）。

6. 选型决策树

6.1 决策流程

flowchart TD
    Q1{吞吐要求？} -->|百万级/日志流| K[Kafka]
    Q1 -->|十万级以下| Q2{需要事务消息或延迟消息？}
    Q2 -->|是| R[RocketMQ]
    Q2 -->|否| Q3{延迟敏感 + 路由灵活？}
    Q3 -->|是| RB[RabbitMQ]
    Q3 -->|否| R2[RocketMQ<br/>Java 生态默认选]

6.2 决策表

业务特征 选谁 理由
日志采集 / 埋点 / 流计算（Flink） Kafka 吞吐之王、分区模型天然支持流处理
电商订单 / 交易链路 / 事务消息 RocketMQ 事务消息、延迟消息、有序队列原生

已有大数据平台 Kafka 与 Flink/Spark/ClickHouse 对接最顺

一句话选型公式：日志/流 → Kafka；交易/事务 → RocketMQ；轻量解耦 → RabbitMQ；拿不准 → RocketMQ（Java 电商系事实标准）。

7. 面试应答：MQ 六连问

7.1 完整话术

面试题 回答要点
为什么用 MQ？ 解耦（订阅发布）、削峰（缓冲）、异步（不等响应）
怎么选型？ 先定吞吐量级，再对机制：日志流→Kafka，事务/延迟→RocketMQ，轻量低延迟→RabbitMQ
消息丢了怎么办？ 三端接力：producer ack（acks=all/SYNC_MASTER）、broker 持久化（ISR/主从）、consumer 手动 ack
重复消费怎么办？ at-least-once 必然重复，消费端幂等：唯一键去重/唯一索引/状态机
顺序消息怎么保证？ 同 key 同分区（路由）+ 消费端单线程（串行），两步缺一不可

7.2 深挖：Kafka 为什么做不了事务消息（跨篇联动）

维度 Kafka RocketMQ
消费进度 offset 机制 消费进度记录

典型场景 日志/流/数据管道 交易链路

一句话：Kafka 的「分区追加日志」模型为吞吐而生，事务需要「先藏后显」的元数据管理（半消息状态），与它的设计目标冲突；RocketMQ 从设计起就是「面向交易」——所以秒杀、支付这类「要吞吐又要事务」的场景，选 RocketMQ 而不是 Kafka（Kafka 原理与实践 有分区模型细节）。

分布式事务：从 2PC 到 Seata

Posted on 2026-08-13 In 分布式 Word count in article: 3.9k Reading time ≈ 14 mins.

「一个订单要扣库存、减余额、记流水，三个服务各有一个数据库，怎么保证要么全成要么全不成？」 单库事务到此失效——这不是代码问题，是「跨系统无原子性」的架构问题。本文从 2PC 的起源讲到 Seata 的落地：为什么教科书级的 XA 没人敢生产用、TCC 为什么是「业务自己写三阶段」、Saga 为什么是「一条补偿链」、以及 Seata AT 模式怎么用「全局锁 + undo 日志」做到业务零侵入。读完你能在方案评审会上说清「这个场景该用 Seata 的哪种模式、为什么」。

联动：本文是 分布式系统核心理论（CAP/BASE/一致性模型）的落地篇；事务消息方案与 ES 查询优化与实战 的本地消息表、RocketMQ 原理与实践 的事务消息同源；Seata 全局锁与 MySQL 事务原理与实践 的锁语义直接相关。

1. 定位：为什么需要分布式事务

单库事务失效的场景：微服务拆分后，「一次业务操作」跨多个服务、多个数据库，每个库自己的事务管不到别的库——「扣库存成功、减余额失败」就成了可能。

术语 一句话定义
本地事务 单个数据库内的事务（ACID）
分布式事务 跨多个数据库/服务，保证「全成或全不成」的事务
全局事务 分布式事务的总称，与「分支事务」相对
分支事务 各参与者的本地事务
协调者 统筹全局事务提交/回滚的角色

核心矛盾一句话：分布式事务的本质是「在无单点权威的分布式系统里，模拟一个全局的原子性」——但 CAP 定理说可用性、一致性、分区容错只能三选二，任何分布式事务方案都是在「牺牲一部分可用性/性能」换「全局一致」。记住这条，所有方案的取舍都能自己推出来（理论细节见 分布式系统核心理论）。

2. 2PC：两阶段提交的由来与代价

2.1 两阶段：准备 + 提交

sequenceDiagram
    participant C as 协调者
    participant A as 服务A(扣库存)
    participant B as 服务B(减余额)
    C->>A: 1. Prepare：能提交吗？
    C->>B: 1. Prepare：能提交吗？
    A-->>C: 2a. 可以（资源已锁）
    B-->>C: 2b. 可以（资源已锁）
    C->>A: 3. Commit / Rollback
    C->>B: 3. Commit / Rollback

阶段一 Prepare：协调者问每个参与者「能提交吗」，参与者执行本地事务但不提交，资源加锁，回复「可以」或「不行」。阶段二 Commit：全票通过 → 广播 Commit；有人拒绝或超时 → 广播 Rollback。

因果链：2PC 用「先锁定资源、后统一提交」实现原子性——但「锁定」是全部代价的来源：Prepare 阶段开始，所有参与者的资源一直锁着，直到阶段二结束，锁的时长 = 最慢参与者的响应时间，这就是「2PC 阻塞性」的根源。

2.2 三个致命问题（面试核心）

问题 场景 后果
阻塞 某参与者慢/挂 所有参与者资源一直锁着，拖垮全局吞吐
单点 协调者挂了 参与者不知提交还是回滚，永远等（无超时自决）
脑裂风险 阶段二网络分区 部分 Commit、部分回滚不了，数据不一致

面试必答话术：2PC（XA）是教科书方案，但三个问题让它生产上没人敢直接用——「阻塞 + 单点 + 脑裂」，本质是「把单点权威（协调者）引入分布式系统，权威自己却不可靠」。XA 协议（数据库原生支持）是 2PC 的标准实现，但因为上述原因，互联网公司几乎不用 XA，改用下面「业务化的 2PC」。

3. 3PC：多一轮预提交，解决了一半

3.1 三阶段：CanCommit → PreCommit → DoCommit

flowchart LR
    A["CanCommit<br/>先问可行性<br/>（无锁）"] --> B["PreCommit<br/>锁定资源<br/>（有超时）"] --> C["DoCommit<br/>统一提交"]

3PC 把阶段一拆成两步：

阶段 动作 与 2PC 的差异
CanCommit 问「能不能提交」（不动资源） 提前排除不可行者，缩短锁定窗口
PreCommit 锁定资源、写日志 参与者多了超时自决能力
DoCommit 提交 参与者超时后可自行提交（默认提交）

3.2 解决了什么、没解决什么

解决：参与者有超时自决机制（协调者失联超时后默认提交），缓解了协调者单点导致的无限阻塞。

没解决：超时默认提交引入新风险——协调者其实要回滚，但参与者已经提交了（网络分区下的两难：等=永远阻塞，自决=可能错）。因果链：3PC 用「减少等待」换「增加出错概率」，所以实际使用比 2PC 还少。记住结论即可：3PC 是学术改进，工程上几乎无人用，面试提到「知道它存在、知道它为什么没人用」就够了。

4. TCC：业务自己写三阶段

4.1 Try / Confirm / Cancel

TCC 是「业务化的 2PC」：不依赖数据库锁，让业务接口自己实现三个动作：

阶段 接口 业务示例（余额服务）
Try 预留资源 冻结 100 元（frozen=100，可用余额不变）
Confirm 确认提交 扣减：冻结-100，可用余额-100
Cancel 取消回滚 解冻：冻结-100，可用余额不变 
flowchart TD
    S[发起方] --> T[Try 全部成功] --> C[Confirm 全部执行] --> D[事务成功]
    T -->|任一 Try 失败| X[Cancel 全部执行] --> E[事务回滚]

4.2 TCC 的三道坎（面试深水区）

坎 问题 解法
空回滚 网络重试导致 Try 没到、Cancel 先到 Cancel 幂等 + 记录事务状态
悬挂 Try 迟到（Cancel 已完成后又来 Try） 状态机校验：已 Cancel 的事务拒绝再 Try
幂等 Confirm/Cancel 被重试执行多次 接口幂等（状态字段/版本号）

因果链：TCC 把「锁」从数据库换成了「业务预留」，不阻塞数据库、并发能力强——但代价是业务要自己写三个接口、处理空回滚/悬挂/幂等三道坎。适用场景：强一致要求高、并发大的资金类操作（账户冻结/库存预留）。面试加分点：主动说出「TCC 的三个空回滚场景」而不是只说『Try Confirm Cancel 三阶段』。

5. Saga：一条补偿链

5.1 正向执行 + 反向补偿

Saga 的核心思想：不预留、不锁定，只管正向执行；哪一步失败，就把前面所有步骤「反向补偿」一遍：

flowchart LR
    S1[扣库存] --> S2[减余额] --> S3[记流水]
    S3 -->|失败| C2[补偿：余额+100] --> C1[补偿：库存+1]
维度 特点
无锁 每步直接提交本地事务，不锁定资源
补偿 反向执行取消操作（库存加回、余额退回）
编排 两种：编排式（中心化一个 Saga 引擎指挥）/ 协同式（每个服务监听事件自己接下一棒）
一致性 最终一致（中间状态对别的事务可见）

5.2 与 TCC 的分工（面试必考）

对比 TCC Saga
预留 有（Try 冻结） 无（直接提交）
一致性窗口 短（Try→Confirm 之间） 长（全程都可能被看到中间态）
适用 强一致 + 高并发（资金） 弱一致可接受 + 长流程（订单/旅行预订）
补偿方式 Cancel 恢复预留 反向业务操作

一句话分工：TCC 适合「必须强一致但并发又高」的短操作；Saga 适合「可以最终一致」的长流程。资金用 TCC，订单/活动用 Saga——面试被问「TCC 和 Saga 怎么选」，先问一句「业务能接受最终一致吗」，答案自然出来。

6. Seata AT：全局锁 + undo 日志的「无侵入」方案

6.1 AT 模式的两件武器

AT（Auto Transaction）模式 = 自动化的 2PC：业务代码几乎不用改（只加 @GlobalTransactional），Seata 用两个机制替你完成全局原子性：

武器一：undo_log 快照。每个分支事务执行前，Seata 拦截 SQL，把「改动前的数据镜像」写入 undo_log 表；全局回滚时用镜像反向执行 UPDATE/DELETE 把数据改回去——相当于自动生成 Cancel。

武器二：全局锁。事务执行期间，Seata 锁定被改动的主键记录，其他全局事务改到同一记录必须等待，防止两个事务互相覆盖导致回滚错乱。

sequenceDiagram
    participant A as 业务应用
    participant TC as TC(全局事务协调)
    participant RM as RM(分支1: 订单库)
    participant RM2 as RM(分支2: 库存库)
    A->>TC: 1. 开启全局事务（XID）
    A->>RM: 2. 分支注册 + 执行 SQL + 写 undo_log
    A->>RM2: 3. 分支注册 + 执行 SQL + 写 undo_log
    A->>TC: 4. 提交全局事务
    TC->>RM: 5. 删 undo_log，提交
    TC->>RM2: 5. 删 undo_log，提交
    Note over TC: 任一步失败 → 各分支按 undo_log 反向执行回滚

6.2 AT 与 TCC 的对比（生产选型核心）

维度 Seata AT TCC
业务改造 零侵入（注解 + 建 undo_log 表） 手写 Try/Confirm/Cancel 三接口
锁粒度 行级（改哪锁哪） 业务预留（可按资源冻结）
性能 有 undo_log 写入开销 无日志开销，纯业务
场景 通用（大部分业务） 资金强一致 + 高并发
侵入度 全局事务是「两阶段」，冲突时等待 无等待，但代码多

因果链：AT 用「undo_log 自动补偿 + 全局锁防冲突」模拟出 2PC 的效果，把复杂度从业务代码搬进了中间件——这就是它成为生产主流的根本原因。代价是全局锁的等待开销：长事务会拖慢并发，所以 AT 也要求分支事务「短」。

6.3 动手验证：本地跑一个 Seata 最小闭环

观察点：@GlobalTransactional 方法内两个库的写操作，在第二个库抛异常时第一个库的写入被自动回滚（undo_log 反向执行）。判定标准：亲手验证「库存减了但订单插入失败 → 库存被回滚」的完整闭环，理解「业务零侵入」的真实含义。

7. 方案选型：一张决策树

7.1 决策流程

flowchart TD
    Q1{业务能接受最终一致吗？} -->|能| Q2{有现成 MQ 吗？}
    Q2 -->|有| MQ[事务消息/本地消息表<br/>推荐：最简单]
    Q2 -->|无| SAGA[Saga 补偿链]
    Q1 -->|不能，要强一致| Q3{事务短且并发高？}
    Q3 -->|是| TCC[Seata AT / TCC<br/>按侵入度选]
    Q3 -->|否| AT[Seata AT<br/>通用首选]

7.2 决策表

业务特征 首选方案 理由
弱一致可接受 + 有 MQ 事务消息/本地消息表 最简单、无中间件依赖（RocketMQ 事务消息）
弱一致 + 长流程 Saga 无锁、适合订单/旅行
强一致 + 通用业务 Seata AT 零侵入、行级锁
强一致 + 极高并发资金 TCC（或 AT + 短事务） 业务预留不阻塞库
同库多表 本地事务 别引分布式事务（最常见优化）

一句话选型：「能最终一致就消息，必须强一致就 Seata；Seata 里短事务用 AT、资金类用 TCC」。另外记住反模式：能在一个库里解决的（同库多表）绝不上分布式事务——很多「分布式事务」其实是表设计/服务拆分问题。

8. 面试应答：分布式事务六连问

8.1 完整话术

面试题 回答要点
2PC 是什么？ 准备+提交两阶段；先锁资源后统一提交；阻塞、协调者单点、脑裂三个问题，生产不用
XA 为什么没人用？ XA 是 2PC 标准实现，数据库锁资源时长=最慢参与者，互联网高并发场景扛不住
TCC 三阶段？ Try 预留 → Confirm 确认 → Cancel 回滚；注意空回滚/悬挂/幂等三道坎
TCC 和 Saga 区别？ TCC 预留锁、强一致、短操作；Saga 无锁直接提交、最终一致、长流程补偿链
Seata AT 原理？ undo_log 快照反向回滚 + 全局锁防冲突；业务零侵入（注解+建表）
怎么选型？ 能最终一致→消息；必须强一致→Seata（AT/TCC 按并发与侵入度）

8.2 深挖：与本地消息表/事务消息的对照（跨篇联动）

维度 2PC/Seata 本地消息表 事务消息（RocketMQ）
一致性强度 强一致（有锁/快照） 最终一致 最终一致
业务侵入 注解（AT）/ 三接口（TCC） 写一张消息表 一个事务消息接口
消息可靠性 无消息 消息与业务同事务 MQ 半消息+回查
适用 强一致场景 无 MQ 时的替代 有 MQ 时首选

因果链：本地消息表和事务消息的本质是「把『发消息』和『业务写』放进同一个本地事务」，用『消息一定会到』换『跨库强一致』（ES 查询优化与实战 的 Canal 同步用的就是这套思路）。面试答「消息最终一致」，能说出「消息表保证消息不丢 + 消费端幂等保证不重」两层，就是完整答案。

9. 总结

9.1 面试速答表

面试题 一句话答案
分布式事务是什么？ 跨多个库/服务保证「全成或全不成」，本质是无单点权威下模拟全局原子性
2PC 流程？ Prepare 锁定资源 → 全票通过 Commit / 任一拒绝 Rollback
2PC 三个问题？ 阻塞（锁时长=最慢者）、单点（协调者挂）、脑裂（分区后不一致）
3PC 改进了什么？ CanCommit 先问可行性 + 参与者超时自决；但自决可能提交错，工程无人用
TCC 三道坎？ 空回滚（Cancel 先到）、悬挂（Try 迟到）、幂等（重试）
Saga 是什么？ 无锁正向执行，失败逐级反向补偿；编排式/协同式
Seata AT 原理？ undo_log 快照自动反向回滚 + 全局锁防覆盖，业务零侵入
怎么选？ 最终一致→消息；强一致→Seata；资金高并发→TCC；同库→本地事务

ES 查询优化与实战：深度分页、聚合与双写一致性

Posted on 2026-08-13 In 数据存储 Word count in article: 3.7k Reading time ≈ 14 mins.

搜索系统上生产的三道坎：分页超过 1 万条怎么办？聚合为什么慢？MySQL 和 ES 数据不一致怎么收场？ 原理篇讲了 ES 为什么快、数据怎么存，本文解决「怎么查得快、查得准、查得全」：深度分页的正确姿势（search_after/scroll 的选择）、聚合的代价模型、以及双写一致性的三种架构方案。读完你能在设计评审上说清「为什么 ES 分页只支持前 1 万条」「聚合上亿数据用什么策略」，并给 MySQL→ES 同步画出一张完整的架构图。

联动：本文是 ES 原理深挖（写入链路/分片/集群健康）的实战续篇；双写一致性与 分布式系统核心理论 的最终一致性呼应；本地消息表方案与 RocketMQ 原理与实践 的事务消息是同一思路的两条实现路径。

1. 定位：这篇实战什么

原理篇回答「数据怎么存、怎么不丢」，本文回答三个「查询与同步」问题：

场景 表面现象 本文答案
分页翻到第 2 万条 报错 Result window is too large §2：from+size 的代价模型，search_after/scroll 的分工
聚合查询跑几秒 大基数聚合内存爆炸 §3：聚合原理与高基数应对
MySQL 改了 ES 没变 双写失败/不一致 §4：三种同步方案与最终一致性兜底

因果链主线：ES 的查询优化不是「调参玄学」，是「一切查询都要在多个分片上并行执行」这个架构事实的推论——深度分页贵在「每个分片都要取全量再排序」，聚合贵在「每个分片先算局部再归并」，双写难在「两个系统没有同一事务」。记住「分片并行」这四个字，所有查询优化的理由都能自己推出来。

2. 深度分页：from+size 为什么 1 万行内

2.1 代价模型：每个分片都要白干

GET /orders/_search?from=10000&size=10 为什么被拒绝（默认 max_result_window: 10000）？看它在 3 分片集群上的执行路径：

sequenceDiagram
    participant C as 协调节点
    participant S1 as 分片1
    participant S2 as 分片2
    participant S3 as 分片3
    C->>S1: 取 from+size=10010 条
    C->>S2: 取 from+size=10010 条
    C->>S3: 取 from+size=10010 条
    Note over S1: 各分片按 score 排序取前 10010
    S1-->>C: 10010 条
    S2-->>C: 10010 条
    S3-->>C: 10010 条
    Note over C: 归并 30030 条，排序，丢弃前 10000 条
    C-->>C: 最终返回 10 条

因果链：from+size 的代价是 O(from+size) × 分片数——翻到第 10 万条，每个分片都要取 10 万条到协调节点排序。这不是「ES 蠢」，是分布式查询的必然：谁也不知道全局前 10 万条分布在哪个分片，只能每片都取。这个模型下「深度分页」不是功能缺失，是代价不可接受，所以 ES 用 max_result_window 直接拦住。

三个方案的定位（面试核心）：

方案 适用场景 原理 缺点
from+size 前 10000 条（翻前 100 页） 每片取全量排序再归并 深翻页 O(from+size)×分片
search_after 实时滚动（下翻 2 万+条） 记住上页最后一条的排序值，只取「比它大」的 不能随机跳页、依赖排序值稳定
scroll 全量导出（导入导出/批处理） 生成快照游标，每次取一段 快照期间数据不变、游标耗内存

search_after 与 scroll 的核心区别一句话：search_after 是「活的」（每次重新查询，新数据能看到），scroll 是「死的」（固定快照，新写入不可见）。导出数据用 scroll（要一致性快照），实时翻页用 search_after（要新数据），两者用途完全不同。

2.2 动手验证：复现报错与 search_after 翻页

观察点：from=10001 被拒绝；search_after 用上页的 sort 值无缝续翻。判定标准：亲手触发 Result window is too large 并改用 search_after 绕过，理解「不是不能翻，是不能用 from 翻」。

2.3 避坑：search_after 的排序值陷阱

坑 表现 解法
排序值有并列 重复/漏条 加唯一字段作 tie-breaker（如 _id）
排序字段有 null 排序不稳定 用 missing:_last 固定空值位置
索引时间戳排序 翻页中途新数据插入 search_after 能看见（这是特性）；需要冻结视图则用 scroll
多字段复合排序 遗漏某字段就乱序 sort 数组里所有字段都要有值

因果链：search_after 的正确性建立在「排序值能唯一定位一条记录」上——排序值并列时它只知道「比这个值大」，不知道「比这条记录靠后」，所以必须加唯一字段 tie-breaker。这个细节是面试官最爱追问的：「search_after 有重复数据怎么办？」

3. 聚合：先局部后归并

3.1 聚合的两步模型

聚合 = 每个分片先算局部结果（bucket/metrics），协调节点再归并成全局结果——与搜索的「每片取 topN 再归并」是同一架构，但代价模型完全不同：

维度 搜索 聚合
分片结果 每片 topN（量可控） 每片全部 bucket（量=基数）
归并成本 O(topN × 分片数) O(bucket 数 × 分片数)
内存压力 排序堆 bucket 全部驻留内存

聚合慢的真正原因：高基数聚合（如按 user_id 分桶）每个分片都要建几百万个 bucket 存内存，协调节点再合并——基数 × 分片数 = 内存爆炸。这就是为什么「聚合上亿日志按 IP 分桶」会 OOM。

3.2 三招应对高基数聚合

手段 机制 适用
近似聚合（cardinality） HyperLogLog，固定内存算基数 只数「多少个」，不要明细
date_histogram 按时间分桶（桶数可控） 日志趋势分析
前置预聚合 写入时把明细聚成汇总（rollup） 上亿数据的固定报表

因果链：cardinality 是近似值（误差 1% 左右）但内存恒定——HLL 用「丢了明细换固定内存」。做报表/去重计数选它；要精确值或明细，只能 rollup 或分片预计算。面试答「聚合优化」的标准句式：「高基数聚合先问三个问题——能近似吗（cardinality）、能按时间降维吗（date_histogram）、能预计算吗（rollup）」。

3.3 动手验证：看聚合的执行与内存

观察点：cardinality 返回的 value 与真实值可能有 ±1% 偏差（HLL 精度参数 precision_threshold 默认 3000）。判定标准：能解释「为什么聚合比搜索更容易打爆内存」，并说出近似聚合的代价（不精确）。

4. MySQL 与 ES 双写一致性：三种方案与最终兜底

4.1 为什么难：两个系统没有同一事务

MySQL 写成功、ES 写失败，数据就不一致了——根源是「跨系统无原子性」：MySQL 事务管不了 ES，ES 没有事务。所有方案的本质都是在回答同一个问题：怎么把「一次业务写」变成「两次可靠写」。

4.2 三种方案对比

flowchart LR
    subgraph A["方案一：应用双写"]
        App["业务应用"] -->|1. 写 MySQL| M1[(MySQL)]
        App -->|2. 写 ES（可能失败）| E1[(ES)]
    end
    subgraph B["方案二：binlog 订阅（Canal）"]
        M2[(MySQL)] -->|binlog| C2[Canal]
        C2 -->|解析/转换| MQ2[(MQ)]
        MQ2 --> W2[同步服务]
        W2 --> E2[(ES)]
    end
    subgraph C["方案三：本地消息表"]
        M3[(MySQL)] -->|同事务写消息表| T3[本地消息表]
        T3 -->|定时扫/事务消息| MQ3[(MQ)]
        MQ3 --> W3[同步服务]
        W3 --> E3[(ES)]
    end
维度 应用双写 binlog 订阅（Canal） 本地消息表
一致性时机 实时（尽力而为） 近实时（秒级延迟） 近实时
与业务解耦 ❌ 侵入业务代码 ✅ 完全解耦 半解耦（要写消息表）
对 MySQL 的感知 无 只认 binlog（支持 ROW 格式） 无
丢失风险 应用崩溃即丢 低（Canal 有 offset） 低（消息表和业务同事务）
改造量 最小（但最脆弱） 中等（Canal+MQ+同步服务） 中等
生产推荐 小流量临时方案 主流方案 无 MQ 时的替代

因果链：三种方案的演进逻辑是「把「双写」从业务代码里一步步挪出来」——双写侵入业务（方案一）→ 用 binlog 当「MySQL 的变化通知」（方案二，业务无感知）→ 用同事务消息表保证「消息不丢」（方案三，比 Canal 简单但要多写一张表）。方案二是生产主流：Canal 订阅 binlog → MQ 削峰 → 同步服务写 ES，延迟秒级、业务零侵入、Canal 挂了对主库无影响。

4.3 最终一致性兜底：对账与修复

即使有 Canal，同步服务崩溃/ES 集群故障仍会造成短暂不一致——所以生产必须加兜底层：

层 手段 说明
重试 同步失败进重试队列，指数退避 解决瞬时故障
对账 定时任务对比 MySQL 与 ES 数据量/版本号 发现长期不一致
兜底 每日全量重建索引（reindex） 修复一切历史遗留

因果链：同步方案保证「绝大多数时间一致」，对账任务保证「发现不一致」，全量重建保证「最终一定一致」——三层叠加才是完整的最终一致性。面试答双写问题，说出「Canal + 重试 + 对账 + 定期重建」四件套，比只说 Canal 高一个档次。

4.4 动手验证：体验「双写」的脆弱

观察点：ES 拒绝写入但业务侧 MySQL 已提交——「DB 成功、ES 失败」的现场，双写方案必须自己处理这种不一致（重试/补偿/消息队列）。判定标准：理解双写方案为何脆弱——两个系统任何一方抖动，都需要人工或兜底层收尾。

5. 面试应答：查询优化四连问

5.1 完整话术

面试题 回答要点
深度分页怎么做？ from+size 只能前 1 万条（代价 O(from+size)×分片）；实时滚动用 search_after（记住排序值续翻）；全量导出用 scroll（快照游标）
search_after 和 scroll 区别？ search_after 重新查询（能看到新数据）、不能跳页；scroll 固定快照（数据冻结）、适合导出
聚合慢怎么办？ 高基数=内存爆炸；先问能近似吗（cardinality/HLL）、能时间降维吗（date_histogram）、能预聚合吗（rollup）
MySQL 与 ES 怎么同步？ 生产用 binlog 订阅（Canal→MQ→同步服务），加重试+对账+定期重建兜底；双写只适合小流量

5.2 深挖：与 MySQL 分页/主从的对照（跨篇联动）

维度 MySQL ES
分页 limit 深翻页要扫全表（MySQL 索引原理与实战） from+size 深翻页每片全量取（代价模型相同）
大数据分页正解 游标/书签（where id > last） search_after（排序值书签）
异步同步 主从 binlog 复制（MySQL 高可用） Canal 订阅 binlog 同步 ES
一致性保障 半同步/GTID 重试+对账+重建

一句话：MySQL 深分页用「书签」绕开 LIMIT 扫描，ES 用 search_after 绕开 from+size——「记住上次的位置，而不是从头上重新数」是分页优化的共同思想；ES 的 Canal 同步本质上就是「把 MySQL 的 binlog 复制架构搬到了 ES 侧」。跨库答出这层对照，面试是明显的差异化加分。

6. 总结

6.1 面试速答表

面试题 一句话答案
为什么 ES 分页限制 1 万条？ 深度分页代价 O(from+size)×分片数，每片白取全量再归并，干脆限制
search_after 怎么用？ 用上页最后一条的排序值续翻，实时数据可见；排序加唯一字段 tie-breaker
scroll 适合什么？ 全量导出/批处理，固定快照游标，游标期间数据不可变
聚合为什么慢？ 高基数 bucket 全驻内存，基数×分片数爆炸
高基数聚合怎么办？ cardinality 近似、date_histogram 降维、rollup 预聚合
MySQL→ES 怎么同步？ Canal 订阅 binlog → MQ → 同步服务；重试+对账+定期重建兜底
双写方案为什么不好？ 业务侵入 + 两个系统无同一事务，任何一方失败都要手工收尾
