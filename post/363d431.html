Elasticsearch 深分页问题详解

Posted on 2026-10-07 Word count in article: 5.2k Reading time ≈ 19 mins.

1. 什么是深分页问题

在 Elasticsearch 中执行分页查询时，如果 from + size 超过 10000，会直接报错：

例如：

from + size = 10010 > 10000，直接报错。

这就是 深分页问题。

2. 为什么 from + size 深分页会报错

2.1 分布式分页的执行过程

ES 是分布式的，数据分散在多个分片上。假设索引有 5 个分片，每个分片 100 万条数据，要查 from=9990, size=10（第 9991~10000 条）。

flowchart TB
    Client[客户端请求<br/>from=9990, size=10] --> Coord[协调节点 Coordinating Node]
    Coord --> S1[分片1<br/>取前10000条]
    Coord --> S2[分片2<br/>取前10000条]
    Coord --> S3[分片3<br/>取前10000条]
    Coord --> S4[分片4<br/>取前10000条]
    Coord --> S5[分片5<br/>取前10000条]
    S1 --> Merge[协调节点汇总<br/>5 × 10000 = 50000 条]
    S2 --> Merge
    S3 --> Merge
    S4 --> Merge
    S5 --> Merge
    Merge --> Sort[内存中全局排序]
    Sort --> Drop[丢弃前 9990 条]
    Drop --> Result[返回第 9991~10000 条]

2.2 问题本质

问题 说明
每个分片都要吐出前 N 条 N = from + size，分片越多，浪费越大
协调节点要汇总 汇总数据量 = 分片数 × N
全局排序 在内存里对海量数据排序，CPU、内存飙升
最后只返回少量 排序结果里绝大部分被丢弃

翻得越深，协调节点的内存和 CPU 压力越大，高并发下直接 OOM。

2.3 一个直观的例子

from size 每个分片返回 5 分片汇总 最终返回
0 10 10 50 10
990 10 1000 5000 10
9990 10 10000 50000 10
999990 10 1000000 5000000 10

最终只返回 10 条，却让每个分片都吐出 100 万条——这就是深分页的代价。

2.4 保护机制

ES 通过索引设置 index.max_result_window（默认 10000）限制 from + size 的最大值：

3. 为什么不建议直接调大 max_result_window

可以调大，但强烈不推荐：

调大后的后果：

flowchart TB
    Big[调大 max_result_window] --> P1[每个分片返回更多数据]
    P1 --> P2[协调节点汇总数据量暴增]
    P2 --> P3[堆内存飙升]
    P3 --> P4[GC 频繁 / 查询变慢]
    P4 --> P5[高并发下 OOM]
    P5 --> P6[集群不可用]
问题 后果
堆内存占用 每个分片都要缓存大量数据
排序开销 全局排序的文档数线性增长
网络开销 分片到协调节点传输大量数据
稳定性 高并发下容易 OOM、拖垮集群

正确做法：用 search_after、scroll、PIT + search_after 替代深分页。

4. 方案一：search_after

4.1 核心思想

不要“跳过前 N 条”，而是“从上一页最后一条之后继续取”。

类比：

  • from + size：翻书到第 1000 页，得从第 1 页开始数。
  • search_after：我记得上次读到哪一行了，直接从下一行继续。
flowchart LR
    subgraph Page1["第 1 页"]
        A1[第1条] --> A2[第2条] --> A3[第3条] --> A4[第4条] --> A5[第5条]
    end
    A5 -->|sort 值作书签| B1[search_after = 第5条的 sort 值]
    B1 --> Page2["第 2 页：从书签之后继续取"]

4.2 使用前提：必须有唯一排序字段

search_after 依赖一个稳定、唯一的排序值作为“书签”。如果排序值有重复，翻页会丢数据或重复。

推荐用业务唯一 ID + 排序字段组合：

4.4 客户端执行过程

sequenceDiagram
    participant C as 客户端
    participant ES as Elasticsearch
    C->>ES: 第 1 页查询（无 search_after）
    ES-->>C: 返回 5 条 + 每条 sort 值
    Note over C: 保存最后一条的 sort 值

    ES-->>C: 返回后 5 条 + 每条 sort 值
    Note over C: 更新书签
    C->>ES: 第 3 页查询（search_after = 上页最后 sort）
    ES-->>C: 继续返回

4.5 分布式取数过程

search_after 每次请求都是独立的分布式查询，不依赖前一次的搜索上下文。因为书签已经过滤掉了“书签之前”的数据，每个分片只需要返回 size 条。

第一页请求（无 search_after）：

flowchart TB
    Client["客户端<br/>size=5, sort=[price, product_id]"] --> Coord[协调节点]

    Coord --> S1["分片1<br/>本地排序后取前 5 条"]
    Coord --> S2["分片2<br/>本地排序后取前 5 条"]
    Coord --> S3["分片3<br/>本地排序后取前 5 条"]

    S1 --> M["协调节点汇总<br/>5+5+5 = 15 条"]
    S2 --> M
    S3 --> M

    M --> Sort["全局排序"]
    Sort --> Take["取前 5 条返回"]
    Take --> Result["返回：P001~P005<br/>最后一条 sort=[6499, P005]"]

第二页请求（带 search_after）：

flowchart TB
    Client["客户端<br/>size=5<br/>search_after=[6499, P005]"] --> Coord[协调节点]

    Coord --> S1["分片1<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]
    Coord --> S2["分片2<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]
    Coord --> S3["分片3<br/>过滤掉 ≤ [6499,P005] 的<br/>本地取前 5 条"]

    S1 --> M["协调节点汇总<br/>最多 15 条"]
    S2 --> M
    S3 --> M

    M --> Sort["全局排序"]
    Sort --> Take["取前 5 条返回"]
    Take --> Result["返回：P006~P010<br/>最后一条 sort=[10999, P010]"]

关键点：

  • 每个分片先根据 search_after 过滤掉已经翻过的数据。
  • 每个分片仍然只返回 size 条，不是 from+size 条。
  • 协调节点汇总后全局排序，取前 size 条。
  • 无论翻到第几页，每个分片返回的数据量都是 size 条，与页码无关，所以性能恒定。

与 from + size 的取数差异对比：

    subgraph FS["from + size（第 1000 页）"]
        F1["分片1<br/>取前 10000 条"] --> FM["汇总 30000 条<br/>全局排序后丢弃 9990 条"]
        F2["分片2<br/>取前 10000 条"] --> FM
        F3["分片3<br/>取前 10000 条"] --> FM
    end

    subgraph SA["search_after（第 1000 页）"]
        A1["分片1<br/>过滤后取 10 条"] --> AM["汇总 ≤30 条<br/>全局排序取前 10 条"]
        A2["分片2<br/>过滤后取 10 条"] --> AM
        A3["分片3<br/>过滤后取 10 条"] --> AM
    end

4.6 特点

特性 说明
翻页方式 只能一页一页往后翻，不能跳页
数据实时性 每次查询实时，能看到新写入的数据
性能 每页开销恒定，与页码深度无关
内存 不需要协调节点缓存大量数据
分片状态 不保存任何搜索上下文，无状态
适用场景 App 无限滚动、下拉加载更多、逐页浏览

4.7 缺点

  • 不能跳页（用户不能点“第 100 页”）。
  • 排序字段必须唯一稳定，否则会漏数据或重复。
  • 前端需要保存上一页最后一条的 sort 值。

5. 方案二：scroll

5.1 核心思想

scroll 相当于给索引拍一张快照，然后反复从这个快照里一批一批地取数据。

类比：

  • search_after：一边看书一边翻，书的内容可能被人改了。
  • scroll：先把整本书复印一份，然后慢慢读复印件，不管原书怎么变。
flowchart TB
    Init[创建 scroll 快照] --> Snapshot[ES 生成数据快照<br/>_scroll_id = ABC]
    Snapshot --> Batch1[用 _scroll_id 取第 1 批]
    Batch1 --> Batch2[用新的 _scroll_id 取第 2 批]
    Batch2 --> Batch3[继续取第 3 批...]
    Batch3 --> Empty[直到 hits 为空]
    Empty --> Clear[手动删除 scroll]

5.4 分布式取数过程

scroll 最大的特点是：第一次请求时，每个分片会创建一个搜索上下文（search context），保存当时的数据视图（快照），并维护自己的游标位置。之后每次请求都从各分片的上下文里继续取。

快照与实时写入的关系

flowchart LR
    subgraph Snapshot["scroll 快照（固定视图）"]
        D1["文档 A"]
        D2["文档 B"]
        D3["文档 C"]
    end

    subgraph RealTime["索引实时状态"]
        D1
        D2
        D3
        D4["新写入文档 D（快照看不到）"]

    Snapshot -.->|"scroll 只读快照"| Result["scroll 返回结果<br/>不含 D、E"]

关键点：

  • 每个分片保存一个独立的数据视图（快照）。
  • 每个分片记录自己的游标位置，后续从自己的位置继续取。
  • 协调节点不排序，只按分片顺序合并。
  • 每次请求返回一批，直到所有分片都取完。

5.5 特点

特性 说明
数据视图 快照，创建后新写入的数据看不到
翻页方式 只能顺序往后取，不能跳页
性能 适合大批量读取，每批开销稳定
资源 快照期间占用资源，需超时并主动清理
分片状态 每个分片保存搜索上下文 + 游标位置
适用场景 数据导出、全量同步、批量重建索引、离线分析

5.6 缺点

  • 数据不实时（快照）。
  • 占用资源，超时未清理会一直挂着。
  • 不适合 Web 端实时分页。

6. 方案三：PIT + search_after

6.1 核心思想

scroll 是快照，但不实时、占资源；search_after 实时、快，但没有快照一致性。

Point In Time（PIT） 是 ES 7.10 引入的方案，把两者的优点结合：

  • 有快照一致性（同一个 PIT 内数据视图固定）。
  • 又可以用 search_after 高效翻页。
  • 比 scroll 更轻量。
flowchart TB
    Open[打开 PIT] --> PIT[PIT id + 数据视图固定]
    PIT --> Query1[PIT + search_after 查第 1 页]
    Query1 --> Query2[PIT + search_after 查第 2 页]
    Query2 --> Query3[继续...]
    Query3 --> Close[关闭 PIT]

关键点：

  • 每个分片都在同一个 PIT 快照内查询，数据视图一致。
  • 每个分片根据 search_after 过滤掉书签之前的数据。
  • 每个分片只返回 size 条，与页码无关。
  • 协调节点汇总后全局排序，和普通 search_after 一致。

  • 兼顾快照一致性和高效翻页。

7.4 一句话记住三种方案

  • from + size：每个分片返回 from + size 条，协调节点汇总量随页码线性增长，深分页时资源爆炸。
  • search_after：每个分片先按书签过滤，只返回 size 条，协调节点汇总量恒定，性能与页码无关。
  • scroll：每个分片创建快照并维护游标，协调节点不排序，只按分片合并，适合批量导出，但占资源、不实时。
  • PIT + search_after：每个分片创建 PIT 快照，每次查询在快照内用 search_after 过滤，只返回 size 条，兼顾一致性和性能，是 ES 7.10+ 推荐的深分页方案。

8. 常见问题与踩坑

8.1 search_after 排序值必须唯一

如果只用 price 排序，而两条记录价格相同，翻页时可能：

  • 漏掉某些数据。
  • 重复返回某些数据。

解决：加一个唯一字段（如 _id 或业务 ID）作为第二排序字段。

8.2 scroll 快照不实时

scroll 创建后，新写入的数据看不到。如果需要实时性，改用 search_after 或 PIT + search_after。

8.3 scroll 忘记清理

scroll 快照会一直占用资源，直到：

  • 超时（scroll=1m 里设定的时间）。
  • 手动 DELETE /_search/scroll。

建议：用完立即清理，或设置合理的超时时间。

8.5 search_after 不能跳页

search_after 只能顺序翻页。如果业务需要跳页（如“跳到第 100 页”），要么：

  • 业务上改成“滚动加载”。
  • 用 from + size（但页数不能太深）。
  • 用其他方案（如自定义游标）。

8.6 排序字段类型问题

search_after 的值类型必须和排序字段类型匹配。例如 price 是 double，search_after 里也要是数字，不能是字符串。

8.7 深分页 + 聚合

聚合和深分页是两回事。聚合用 composite aggregation 做分页，不要用 from + size。

8.8 max_result_window 调大后依然慢

即使把 max_result_window 调到 100 万，深分页依然慢。治标不治本，还是要用 search_after 或 scroll。

9. 总结

  • from + size：简单，但深分页会拖垮集群，ES 用 10000 上限保护自己。
  • search_after：记住“上一页最后一条”，从它后面继续取，实时、快、无限深，适合逐页往后翻。
  • scroll：先拍快照，再慢慢批量取，适合一次性导出全量数据，但不实时、要清理。
  • PIT + search_after：ES 7.10+ 推荐方案，兼顾快照一致性和高效翻页，适合深分页搜索。

核心原则：能不用深分页就不用；必须深分页时，优先 search_after，导出场景用 scroll，需要一致性视图用 PIT + search_after。
