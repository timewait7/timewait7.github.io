Agent Skill开发指南（修订版）

关于本次修订：原文档内容详实、案例完整，但存在一个比较严重的问题——文档后半部分明显是由两段独立的AI对话直接拼接而成，其中一处混入了AI助手本不该展示给用户的”内部思考草稿”（类似”我们被问到……我们需要回答……回答应包含……”这种规划性文字），紧接着才是真正面向用户的回答。这类内容一旦被原样保留在正式指南里，会显得非常不专业，也会让读者困惑”这段话是写给谁看的”。除此之外，文档还存在阶段命名前后不一致、个别术语与官方说法有出入、模式来源归因不准确、装饰性emoji过多等问题。本修订版做了以下处理：① 删除了泄露的内部思考文字和聊天界面残留语句（如”本回答由AI生成””随时回来追问”），把两段内容整合成一篇统一的指南；② 统一了SDD阶段命名，并标注了与GitHub spec-kit等主流Spec-Driven Development工具的术语对照；③ 把”L1/L2/L3”的描述对齐到Anthropic官方文档的Discovery/Activation/Execution说法；④ 修正了”5种设计模式”的来源归因；⑤ 大幅减少了装饰性emoji，改用更适合阅读的文字标注。Agent Skill生态发展很快，文中涉及的目录结构、命名规则等技术细节为撰写时的快照，建议使用前对照Anthropic官方文档核实。

引言：SDD与Agent Skill

SDD的核心思路

SDD（Spec-Driven Development，规范驱动开发）是一种强调”先定义，后实现”的开发哲学：先把需求和设计写成清晰的规范文档，再让AI Agent严格依照规范去实现，而不是在信息不完整时自行猜测。这样可以让每次迭代都更精准、可预测、易于维护。

需要说明的是，”规范驱动开发”目前并没有一套被所有工具统一采用的阶段命名。以目前社区里影响力较大的GitHub spec-kit为例，其标准工作流是Specify（定义规范）→ Plan（技术规划）→ Tasks（任务拆解）→ Implement（实现）这四个阶段，外加可选的/clarify（澄清歧义）、/analyze（一致性检查）等质量门禁步骤。不同团队、不同工具在具体阶段划分上会有出入，本文后面的”实战”部分会用一个简化的三阶段版本（定义→规划→实现）来配合Skill开发场景，这是为了适配”创建一个Skill”这种相对单一的任务规模做的简化，并不是说存在某个固定不变的”四阶段标准”。

在实际操作中，SDD的理念常常和Anthropic的Agent Skill标准结合使用：用规范驱动的方式去描述”这个Skill要解决什么问题”，再把规范落地为符合Skill目录结构的文件。

Skill的核心结构

一个Skill本质上是一个文件夹，按照Anthropic的Agent Skills开放标准，通常包含以下几层：

层级 功能 内容示例
核心入口层 (SKILL.md) 提供Skill的”自我介绍”和核心指令。 name: code-reviewer，description: 当用户请求进行代码审查……时使用此技能，以及执行审查的核心指令。
技能逻辑层 存放按需加载的详细指令、流程和标准。 references/security-checklist.md 可存放审查清单、编码规范等具体内容，需要时再加载。
工具资产层 包含直接执行的外部脚本和静态资源。 scripts/analyze_complexity.py 用于执行复杂度分析等确定性任务。
资源文件层 存放输出内容所需的模板、图标等。 assets/report_template.html 存放输出内容所需的模板等资源。

渐进式加载机制

Anthropic官方把这套机制描述为三个阶段：Discovery（发现）→ Activation（激活）→ Execution（执行）。

  • Discovery（发现）：Agent启动时，只把每个已安装Skill的name和description加载进系统提示词，每个Skill大概只占几十个token，足够Agent判断”这个任务是否可能用得上它”。
  • Activation（激活）：当某个任务匹配到某个Skill的描述时，Agent才会把完整的SKILL.md正文读入上下文。
  • Execution（执行）：Agent按照指令执行任务，并按需读取scripts/、references/、assets/目录下的具体文件或运行其中的脚本——这部分内容不会被预先加载，只有真正用到时才进入上下文。

通过这套机制，Agent能在初始阶段仅加载少量核心信息，并在执行过程中按需展开详细指令和工具，有效避免了上下文窗口的过度消耗。

创建Skill的5种常见设计模式

社区里（尤其是围绕Google ADK的SkillToolset实践，以及像obra/superpowers这类开源的subagent驱动开发项目）总结出了一些反复出现的Skill内容设计模式。需要说明的是，这并不是Anthropic官方钦定的分类，不同文章给出的”五个模式”清单也略有差异（比如有的版本里第五个是”Generator/生成器模式”而不是下面的”Subagent-Driven”）。这里列出一种常见的组合，供参考：

  1. Tool Wrapper（工具封装模式）
    • 解决的问题：管理各技术栈的特定规范，避免信息过载。
    • 工作原理：将特定框架（如FastAPI、React）的API规范、最佳实践打包成Skill，只在相关任务触发时加载。
  2. Reviewer（审查员模式）
    • 解决的问题：分离审查流程和标准，实现审查流程的复用。
    • 工作原理：把通用的”多轮检查””打分”等流程固化在SKILL.md中，把可变的”安全检查清单”等审查标准放在references/目录下，实现一份Skill应对不同审查需求。
  3. Inversion（需求反转模式）
    • 解决的问题：应对模糊、不完整的需求，避免返工。
    • 工作原理：在执行任务前，Agent主动”扮演采访者”，按清单澄清用户的关键需求。
  4. Pipeline（管道模式）
    • 解决的问题：强制复杂任务的执行顺序，避免跳步。
    • 工作原理：把工作流定义为不可跳过的多个阶段，并设置硬性检查点（如”第一步完成后，必须等待用户确认，才能执行第二步”）。
  5. Subagent-Driven（子代理驱动模式）
    • 解决的问题：高效执行大型任务，解决上下文污染和并行处理问题。
    • 工作原理：为每个子任务启动一个全新的、无历史上下文干扰的子Agent，完成后做两阶段审查：先审查是否符合规范（Spec Compliance），再审查代码质量（Code Quality）。这种模式在开源项目里有时也被简称为”SDD”（Subagent-Driven Development）——注意这与前文”Spec-Driven Development”的缩写恰好相同但含义不同，阅读其他资料时留意上下文，避免混淆。

这几个模式可以组合使用，比如在一个Pipeline的最后一步嵌入Reviewer，或者在Pipeline开始前用Inversion收集必要参数。

  • 规划目录结构：
  • 明确工作流程：需求获取 → 命名建议 → 内容生成 → 创建文件 → 汇总检查。

实现：

  • 编写SKILL.md：文件头用YAML格式明确命名和描述，主体部分用Markdown格式写清楚上述规划好的工作流程。

SDD思路给Skill开发带来的核心优势是把不确定性最小化，把可控性最大化：通过建立从规范到执行的清晰路径，为AI Agent的应用开发提供了可靠的基础。

第一部分：准备工作——理解Skill的核心组成

根据Anthropic的Agent Skills开放标准，一个Skill本质上是一个文件夹，其核心结构如下：

核心设计理念：渐进式加载（Progressive Disclosure） —— Agent在初始阶段只加载SKILL.md的元数据（约几十个token），仅在需要执行任务时才加载完整内容，从而最大限度节省上下文窗口。

命名与元数据的硬性约束（按官方规范，写Skill前建议先过一遍）：

  • name：仅能使用小写字母、数字和短横线（kebab-case），长度不超过64字符，且不能使用claude、anthropic等保留词。
  • description：必须非空，长度不超过1024字符，需要同时说明”做什么”和”什么时候用”，建议包含用户可能提到的触发关键词。

第四部分：关键注意事项

元数据质量 name+description必须精确，description不超过1024字符 直接影响Agent的路由准确性

资源隔离 敏感信息放references/而非核心指令 避免API密钥等敏感信息意外加载
来源审计 只使用自己编写或来自可信来源的Skill Skill能驱动Agent执行代码和工具调用，来路不明的Skill存在安全风险

第五部分：进阶问题——能不能把具体编写工作都交给Agent？

一个很自然的问题是：上面这套流程看起来很完整，但其中包含大量人为工作，比如SKILL.md、辅助脚本、参考文档的编写。能不能我只做需求分析和架构设计，剩下的交给Agent，在和Agent的交互中完成最终的Skill开发？

答案是：完全可以。 这正是AI辅助Skill开发的标准范式——你作为”架构师”专注于需求分析和架构设计，Agent作为”实现者”承担具体的编写工作。SDD的理念本身就支持这种分工：规范交给人来定义，实现交给AI来生成，人再对照规范验收。

你的角色 vs Agent的角色

步骤 你的工作（架构师） Agent的工作（实现者）
需求分析 用自然语言说出”我要做什么” 反问澄清细节（自动）
架构设计 选择Pipeline/Reviewer等模式 提出模式建议供你确认
编写SKILL.md 无需写 自动生成完整文件
编写脚本 无需写 根据技术栈生成代码
编写参考文档 无需写 自动生成references内容
测试与调试 运行测试，描述现象 定位Bug并修改
重构优化 提出”太慢了””功能不足” 分析瓶颈并重写代码

你只需要描述意图和验收结果，Agent负责转化为可运行的Skill。
