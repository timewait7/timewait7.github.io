四、串行 vs CompletableFuture 并行 RT 对比

4.1 场景

文档详情页需聚合三路数据：文档正文（doc 服务）、分享状态（doc 服务）、审计摘要（audit 服务）。

方案 实现 RT
串行 三次 Feign 顺序调用 45ms + 60ms + 80ms = 185ms
并行 CompletableFuture + doc-executor 并发 max(45,60,80) + 调度 5ms = 85ms

4.2 并行实现要点

  • 使用 doc-executor 线程池（core=8），避免无界创建线程；
  • 用 TtlExecutorUtil.wrap 包装（ThreadPoolConfig.java:103），保证 UserContext 跨线程传递；
  • 设置总超时 200ms（CompletableFuture.get(200ms)），单路超时不拖累整体。

4.3 压测对比

方案 avg RT P99 RT TPS doc-executor 活跃线程
串行 186ms 420ms 2100 0
并行 88ms 195ms 4350 6-8
并行（无超时） 92ms 580ms 3800 8（堆积风险）

并行方案 TPS 提升 107%，但必须设置超时，否则某路慢调用会拖垮线程池。

五、压测结论与最佳实践

5.1 核心结论

  1. 三级缓存有效：L1 Caffeine 命中率 85%+，DB 回源率恒定 2%，互斥锁成功防御击穿；
  2. Tomcat max-threads=200 为最优：并非越大越好，500 时上下文切换反噬；
  3. WebSocket 单节点 5000 上限：超过需水平扩容；
  4. 并行聚合 RT 减半：CompletableFuture + 线程池隔离是 IO 密集聚合的有效手段；
  5. TCC 事务无失败：删除场景 TCC 成功率 100%（3000 并发内），Try 阶段幂等保障到位。

5.2 容量规划建议

业务量 推荐部署
500 QPS doc-service 1 副本，max-threads=200
2000 QPS doc-service 2 副本 + Redis 主从
5000 QPS doc-service 4 副本 + Sentinel 限流 + 热点降级
万人协同 collab-service 3 副本，一致性哈希路由

5.3 后续优化方向

  • L1 Caffeine 改用 W-TinyLFU 策略（已开启 recordStats，待观察命中率）；
  • 接入 Sentinel 集群限流，替代单机 Redis Lua；
  • 长尾 P99 优化：排查 3000 并发时 GC 抖动，详见《05-JVM 调优报告》。

六、压测风险与回滚

  • 压测流量打「压测标记」Header，审计服务识别后写入独立压测库，避免污染生产数据；
  • 热点降级阈值（QPS>100）在压测期间临时调高到 500，避免误降级干扰结果；
  • 压测结束立即恢复配置，K8s HPA 监控 5 分钟无异常后收尾。

本报告数据为基于架构合理推演的模拟值，上线前需在准生产环境实压校准。线程池与锁的深度分析见《04-线程与锁分析报告》。

附5、线程池隔离对比

5.1 共用线程池 vs 4 个隔离线程池

配置位置： ThreadPoolConfig.java:49-76，4 个独立线程池：

  • doc-executor：核心写（AbortPolicy，core=8,max=16,queue=2000）
  • audit-executor：异步审计（CallerRunsPolicy，core=2,max=4,queue=500）
  • search-sync-executor：MQ 消费同步 ES（DiscardOldestPolicy，core=4,max=8,queue=1000）
  • export-executor：PDF 导出（AbortPolicy，core=2,max=4,queue=200）

场景： 500 并发混合压测，其中 PDF 导出任务（重型 IO，单任务 3s）占比 5%。

方案 文档保存 TPS 审计写入 TPS 搜索同步延迟 错误率 说明
共用线程池（core=16,max=32） 980 980 450ms 1.8% 导出任务占满线程，保存/审计被阻塞
4 线程池隔离 1820 8800 60ms 0.05% 故障隔离，导出积压不影响核心

模拟数据。共用线程池时，导出任务的 3s 阻塞导致线程被占满，doc-executor 的保存任务排队，触发 AbortPolicy 抛异常，错误率飙升。

要点：

  1. 指定线程池：用 doc-executor 而非 ForkJoinPool.commonPool()（共享易被其它任务阻塞）；
  2. TTL 传递：线程池经 TtlExecutorUtil.wrap 包装（ThreadPoolConfig.java:103），UserContext 跨线程正确传递；
  3. 上下文清理：每个任务 finally { UserContext.clear(); }（DocDetailService.java:63,72,81）防泄漏；
  4. 异常隔离：exceptionally 兜底，任一失败不影响其它（DocDetailService.java:94）。

  • pool-size>100 后 TPS 下降，原因是：DB 端并发连接过多，锁争用加剧（行锁等待），InnoDB 事务调度开销变大；

8.3 调优经验总结

  1. Tomcat 线程数不是越大越好：4C 节点 200 是甜点，超过后上下文切换反噬。
  2. 线程池必须隔离：核心写、日志、搜索同步、导出四类业务 CPU/IO 特性不同，隔离避免故障传染。
  3. 连接池有拐点：HikariCP 不是越大越快，DB 端锁争用会成瓶颈，50 是 4C MySQL 的甜点。
  4. 并行编排降 RT：CompletableFuture 把串行 150ms 降至并行 50ms，但必须用独立线程池 + TTL 传递上下文。
  5. 缓存命中决定读性能：文档详情 95% 缓存命中时 TPS 5680，全回源时 TPS 仅 800。布隆过滤器 + 互斥锁重建是关键。
