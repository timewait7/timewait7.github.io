JMM：把「不可见」和「重排」亲手复现

Posted on 2026-10-25 In Java Word count in article: 3.6k Reading time ≈ 13 mins.

一个 boolean 就能让整个服务挂死，而且日志里什么都看不到。实测：把 stop 声明成普通字段，另一个线程把 stop = true 之后，读线程3 秒都没退出——JIT 把 stop 的读取提到了寄存器里，再也不去内存看。加上 volatile，同样的代码 500 毫秒内正常退出。

这篇逐个复现 JMM 的三个问题：可见性（复现了）、有序性（没复现，但要讲清为什么）、原子性（61.4% 的更新丢失）。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM：可见性与重排（本文） → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：① 说「基准会被 JIT 优化」，本文用它复现可见性 bug；④ 会接着讲「volatile 背后的缓存行」；⑤ 用本文的「volatile++ 丢更新」引出 CAS。

1. 三个问题，一张表

问题 一句话定义 本文是否复现 典型后果
可见性 一个线程改了，另一个线程看不到 ✅ 复现（3 秒未退出） 死循环、优雅停机失效
有序性 指令重排导致执行顺序与代码不一致 ❌ 10 万轮未出现 DCL 半初始化、初始化顺序错乱
原子性 复合操作被拆开执行 ✅ 复现（丢 61.4%） 计数丢失、超卖 
flowchart LR
    A["Thread A writes x=1"] --> B["CPU store buffer<br/>not flushed yet"]
    B --> C["cache line in Modified state"]
    C --> D["Thread B reads x"]
    D --> E{"sees 0 or 1?"}
    E -->|"no synchronization"| F["may see 0 (stale)"]
    E -->|"volatile / lock"| G["must see 1"]

核心认知：这三个问题都不是「代码写错了」，而是代码没有建立 happens-before 关系。JMM 只承诺：在 happens-before 关系成立的前提下，结果是对的。

2. 可见性：一个 boolean 就能让程序挂死

2.1 实测：普通字段 vs volatile

实测输出（JDK 21.0.12，aarch64，15 核）：

版本 结果 循环次数
普通字段 3 秒未退出（看门狗强制结束） —
volatile 0.5 秒内正常退出 1,998,494,873

为什么：JIT 编译后发现循环体里没有对 stopPlain 的写操作，于是把「读 stopPlain」提升到循环外（循环不变量提升），寄存器里的值永远是初始的 false。

2.2 深挖：这是 JIT 干的，不是 CPU

想确认是 JIT 而不是硬件缓存的问题，用解释模式跑一次：

运行模式 不加 volatile 原因
-Xint（解释） 会退出 每次循环都真的去读字段
默认（JIT） 不退出 读被提升到寄存器

这个对照很重要：它说明「可见性 bug 是编译期优化 + 硬件缓存共同造成的」，所以在测试环境跑不出来，不代表生产不会出。

2.3 正确的写法

写法 适用 说明
volatile 停止标志、状态位 每次读写都过内存，禁止重排
AtomicBoolean 停止标志 + 原子操作 比 volatile 多一层 CAS 封装
interrupt() 线程中断 JVM 内建机制，配合 isInterrupted()
锁 复合状态 顺带保证可见性

生产上更推荐 volatile + interrupt() 组合：标志位负责业务语义，interrupt 负责唤醒阻塞中的线程。

sequenceDiagram
    participant W as Writer
    participant M as Main Memory
    participant R as Reader
    R->>M: loop: read stop (hoisted to register)
    Note over R: JIT: read once, keep in register
    W->>M: stop = true
    M--xR: never re-read -> infinite loop
    Note over W,R: with volatile: every read hits memory

3. 有序性：重排真的会发生吗

3.1 实验设计（litmus test）

两个线程各自「写自己的变量、读对方的变量」：

每轮用屏障对齐两个线程的起点，复位变量，统计 (0,0) 出现的次数。

3.2 实测：10 万轮，0 次

指标 实测
CPU 架构 aarch64（Apple Silicon）
轮数 100,000
观察到 (0,0) 重排 0 次
总耗时 511 ms

我没能复现重排。 原因有三层：

原因 说明
屏障自带内存语义 CyclicBarrier.await() 内部有锁与 volatile 写，前后形成完整屏障
x86/arm64 都是强内存模型 只有 store→load 允许重排，窗口极窄
JIT 也可能不重排 没有收益时编译器不会动 
sequenceDiagram
    participant T1
    participant T2
    Note over T1,T2: round start (barrier = full fence)
    T1->>T1: x = 1
    T1->>T1: r1 = y
    T2->>T2: y = 1
    T2->>T2: r2 = x
    Note over T1,T2: round end (barrier again)
    Note over T1,T2: barriers kill the reorder window

3.3 深挖：没复现 ≠ 不会发生

JMM 是规范，不是实现。规范明确允许 store 与后续 load 重排（这是 DCL 单例必须加 volatile 的根因）。

事实 结论
你在自己机器上跑 10 万轮没看到 只说明你的环境窗口窄
换了 ARM 服务器、换了 JVM 版本 窗口可能变大
依赖「跑一遍没问题」上线 就是在赌

所以正确姿势是「按 happens-before 写」，而不是「跑一遍没出问题就放心」。这一条也解释了为什么有些并发 bug 只在客户现场出现。

3.4 怎么真正验证重排

方法 说明
-XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly 看真实汇编顺序（需要 hsdis 插件）
JSR-133 Cookbook 的 litmus 测试 用更贴近硬件的写法（volatile 组合）
JCStress OpenJDK 官方的并发正确性测试工具（本文未用）

本文没有 hsdis，也没有 JCStress，所以只给出「未复现」这个诚实的结论。

4. 原子性：volatile 救不了 i++

4.1 实测：4 线程丢 61.4%

写法 期望 实际 丢失
volatile int 自增 4,000,000 1,545,633 2,454,367（61.4%）
synchronized 自增 4,000,000 4,000,000 0

为什么：volCount++ 是「读 → 加 → 写」三步，volatile 只保证每一步的可见性与顺序，不保证这三步整体原子。两个线程可能同时读到 100，各自加 1 写回 101。

机制 保证什么 不保证什么
volatile 可见性、禁止重排、单个读/写原子 复合操作不原子
synchronized 互斥 + 可见性 性能开销
AtomicInteger 单变量复合操作原子 多变量组合不原子

4.2 三种修法的量级（⑤ 会展开）

修法 4 线程 200 万次的 ns/op（①实测口径） 适用
synchronized 6 临界区简单
AtomicLong 5 单变量计数
LongAdder 1 高并发计数 
flowchart TD
    A["Read x in thread B"] --> B{"any happens-before<br/>edge to the write?"}
    B -- no --> C["may see stale value"]
    B -- "volatile / lock / start / join" --> D["must see latest"]
    C --> E["bug: loop, stale flag, half-init"]
    D --> F["correct"]

5. volatile 的成本：1.56 ns/op

5.1 实测

操作 200,000,000 次耗时 折算
plain++ 2 ms 被 JIT 折叠成一次加法
volatile++ 312 ms 1.56 ns/op

读法：在无竞争的本地核上，一次 volatile 写约 1.56 ns；但真正的代价不在这 1.56 ns，而在竞争时——多个核同时写同一个 volatile 变量，缓存行会在核之间来回弹（④ 会量这个成本）。

5.2 happens-before 的六条规则（速查）

规则 内容
程序顺序 同一线程内，前面的操作 hb 后面的操作
volatile 对 volatile 变量的写 hb 后续对它的读
锁 解锁 hb 后续对同一把锁的加锁
线程启动 Thread.start() hb 新线程里的任何操作
线程终止 线程里的所有操作 hb 其他线程从 join() 返回
传递性 A hb B，B hb C ⇒ A hb C

用法：写并发代码时，逐条问「我依赖的读写之间，有哪条 hb 规则支撑？」答不上来就是 bug。

6. 动手验证：四个可复现实验

6.1 动手验证：复现可见性 bug

预期观察点：默认模式下 plain 版本 3 秒不退出；-Xint 模式下会退出；volatile 版本两种模式都正常退出。

判定标准：

  • 两种模式都不退出 → 说明不是 JIT 提升，而是别的问题（比如字段被别处写成 true）；
  • 默认模式也退出 → 你的 JVM 参数（如 -Xint、-XX:-TieredCompilation）影响了编译，换回默认再看。

6.2 动手验证：重排 litmus 测试

预期观察点：多数机器上 reorder=0（本文 aarch64 也是 0）。

判定标准：

  • reorder > 0 → 你的 CPU/JVM 真的重排了，这就是 DCL 必须加 volatile 的实证；
  • reorder = 0 → 正常，不代表安全（见 3.3）。

6.3 动手验证：volatile 的丢更新

预期观察点：volatile++ 丢失几十个百分点（本文 61.4%），synchronized++ 精确等于期望值。

判定标准：

  • volatile++ 没丢 → 线程数太少或临界区太快，加线程到 8/16 再试；
  • synchronized++ 也丢 → 你的 JVM 跑在 -Xint 之外的特殊模式，或代码里其实没加锁。

6.4 动手验证：量 volatile 的写成本

预期观察点：plain 被 JIT 折叠到几毫秒，volatile 是几百毫秒（本文 312 ms，1.56 ns/op）。

判定标准：

  • 两者都接近 0 → 循环被整体消除，把结果写进 volatile 字段再测；
  • volatile 超过 10 ns/op → 有其它线程在竞争这个变量，或 JIT 没编译热路径。

7. 总结

7.1 面试速答表

面试题 一句话答案
JMM 解决什么问题 定义多线程下读写的可见性与有序性规则（happens-before）
可见性问题怎么复现 普通 boolean 做停止标志，读线程 3 秒不退出（本文实测）
为什么加了 volatile 就好 每次读写都过内存 + 禁止重排
-Xint 下为什么不挂 解释执行没有 JIT 的循环不变量提升
重排一定会发生吗 JMM 允许，但强内存模型 + 屏障会让它极难复现（本文 10 万轮 0 次）
volatile 能保证原子性吗 不能，只保证单次读/写的原子性，volatile++ 实测丢 61.4%
volatile++ 为什么丢 读-改-写三步不原子，两个线程可能读到同一个旧值
volatile 写有多贵 本文实测 1.56 ns/op（无竞争），竞争时会因缓存行弹跳更贵
happens-before 有哪些规则 程序顺序、volatile、锁、start、join、传递性
为什么测试环境跑不出并发 bug JIT 优化、内存模型强度、时序窗口都不同
停止线程用什么 volatile 标志 + interrupt()
DCL 单例为什么要 volatile 防止「分配内存 → 赋值引用 → 初始化」被重排成「赋值引用」先发生

7.2 实战避坑表

症状 原因 处理
优雅停机后线程不退出 停止标志不是 volatile 改 volatile + interrupt()
计数偶尔少几个 volatile++ / int++ 非原子 用 Atomic* 或锁（⑤）
测试环境正常、生产偶发 依赖了「跑通即正确」 按 happens-before 写，别赌
单例返回半初始化对象 DCL 没加 volatile 加 volatile 或改静态内部类
加了 volatile 性能变差 高频写同一变量 减少写次数，或改 LongAdder

7.3 工具速查表

工具 看什么 判定标准
java -Xint 对照 JIT 与解释执行 行为不同 = JIT 优化导致
-XX:+PrintCompilation 哪些方法被编译 有编译 = JIT 介入
JCStress 并发正确性测试 官方工具，本文未用
JFR 线程阻塞与锁事件 结合 ② 的方法读

7.4 实操建议

  1. **所有跨线程共享的标志位一律 volatile**（或 Atomic*），这是最低成本的一条。
  2. volatile 只解决可见性与有序性，不解决原子性——volatile++ 一定要换成 Atomic 或锁。
  3. 别用「跑一遍没问题」验证并发正确性，要么按 hb 规则推导，要么用 JCStress。
  4. **DCL 单例加 volatile**，或者干脆用静态内部类（最简单）。
  5. 理解 -Xint 对照的价值：它能把「JIT 引起的可见性 bug」和「逻辑 bug」区分开。
