  • Server 层：连接管理、SQL 解析、优化、执行，以及所有跨引擎的通用功能（内置函数、存储过程、触发器、视图）。所有存储引擎共用这一层。
  • 存储引擎层：负责数据的实际存储与提取。插件式架构是 MySQL 最核心的设计——同样的 SQL，底层可以换成 InnoDB、MyISAM、Memory 等不同引擎。

sequenceDiagram

    Conn->>Conn: 校验用户名密码 + 权限

    P->>P: 词法分析 + 语法分析 → 语法树

    PP->>PP: 检查表/列存在性、解析别名、校验权限
    PP->>Opt: 交给优化器
    Opt->>Opt: 基于统计信息选择索引 / 连接顺序
    Opt->>E: 交给执行器

    I-->>E: 逐行返回数据
    E-->>C: 返回结果集

五个组件的关键细节：

  1. 连接器：建立连接、校验用户名密码、加载权限。连接建立后即使管理员改了权限，也要重连才生效。SHOW PROCESSLIST 可查看连接状态，空闲连接受 wait_timeout（默认 8 小时）控制。
  2. 解析器：词法分析 + 语法分析，把 SQL 拆成语法树。语法错误在这一步报出。
  3. 预处理器：检查表和列是否存在、解析别名、校验执行权限。
  4. 优化器：基于统计信息选择执行计划——决定用哪个索引、表的连接顺序、是否走索引下推等。这也是”为什么同样的 SQL 有时快有时慢”的根源。
  5. 执行器：按执行计划调用存储引擎接口，逐行判断条件并返回结果。

注：MySQL 8.0 已完全移除查询缓存；8.0 之前会先查查询缓存，命中则直接返回结果。

1.3 SQL 语句的真实执行顺序

flowchart LR
    F[FROM] --> W[WHERE]
    W --> G[GROUP BY]
    G --> H[HAVING]
    H --> S[SELECT]
    S --> D[DISTINCT]
    D --> O[ORDER BY]
    O --> L[LIMIT]
阶段 执行内容
FROM 确定数据来源表，加载到内存
WHERE 逐行过滤，不满足条件的行直接丢弃
GROUP BY 按指定列分组
HAVING 对分组结果过滤（可以使用聚合函数）
SELECT 投影出需要的列（此时才开始计算字段和别名）
DISTINCT 去重
ORDER BY 排序（可能触发 filesort）
LIMIT 截取最终返回行数

理解这个顺序的意义：WHERE 中不能使用 SELECT 中定义的别名（因为 SELECT 还没执行），而 ORDER BY、HAVING 中可以使用——因为它们执行得更晚。

1.4 一条 UPDATE 语句的执行流程

sequenceDiagram
    participant C as 客户端
    participant Conn as 连接器
    participant Opt as 优化器
    participant Exec as 执行器
    participant BP as Buffer Pool
    participant UL as undo log
    participant RLC as redo log buffer
    participant BL as binlog
    participant RL as redo log

    C->>Conn: UPDATE 语句
    Conn->>Opt: 解析 + 优化
    Opt->>Exec: 执行计划
    Exec->>BP: 定位目标行（Buffer Pool）
    Note over BP: 命中则直接用；未命中从 .ibd 加载
    BP->>UL: 写入 undo log（旧值）
    BP->>BP: 修改数据页为新值（脏页）
    BP->>RLC: 写入 redo log buffer
    Note over RLC: 两阶段提交
    RLC->>RL: Prepare: 刷 redo log 到磁盘, 标记 PREPARE
    Exec->>BL: 写入 binlog
    RL->>RL: Commit: redo log 写入 COMMIT 标记
    Exec-->>C: 返回成功
    Note over BP: 脏页由后台异步刷盘

更新语句的四个关键步骤：

  1. 缓冲池查找：先在 Buffer Pool 中查找目标行所在的数据页，不在则从 .ibd 文件加载到内存；
  2. 写 Undo Log：修改前先把旧值写入 undo log。两个目的：事务回滚时恢复旧值；其他并发事务通过 undo 版本链读到旧版本（MVCC）；
  3. 修改 Buffer Pool：把数据页中的行更新为新值，该页变为脏页；
  4. 写 Redo Log Buffer：把数据页的物理修改记入内存中的 redo log buffer。先写日志、后刷脏页，这是 WAL（Write-Ahead Logging）原则。

提交阶段（两阶段提交）：

  1. Prepare：redo log 刷盘，标记为 PREPARE；
  2. Write Binlog：Server 层写入 binlog 并刷盘；
  3. Commit：redo log 中写入 COMMIT 标记，事务正式提交。

2. 索引原理：B+ 树、聚簇索引与联合索引

2.1 为什么需要索引

MySQL 的数据以页为单位存在磁盘上（默认 16 KB/页）。一张 1000 万行的表，数据占几千个页。没有索引时，查询只能从第一页扫到最后一页，逐行判断条件——这就是全表扫描，复杂度 O(n)。

存储延迟量级（理解索引价值的前提）：

操作 延迟量级
内存访问 约 100 ns
SSD 随机读 约 0.1 ms
HDD 随机读 约 10 ms
一次磁盘 IO（读一页） 机械盘毫秒级，SSD 亚毫秒级

    subgraph NoIndex[无索引：全表扫描]
        Q1[查询 id=100 万] --> S1[从第 1 页扫到第 N 页]
        S1 --> R1[数千次磁盘 IO, O n]
    end
    subgraph WithIndex[有索引：B+ 树查找]
        Q2[查询 id=100 万] --> S2[沿 B+ 树逐层下探]
        S2 --> R2[2~3 次磁盘 IO, O log n]
    end

2.2 索引的本质：一张有序的”目录”

索引本质上是一份独立于表数据、按键排序的目录结构。索引的两个代价：

  • 空间：每个索引都是一份额外的有序结构，占用磁盘与 Buffer Pool 内存；
  • 写放大：每次 INSERT/UPDATE/DELETE 都要同步维护索引，索引越多，写入越慢。

2.3 为什么偏偏是 B+ 树

候选结构 等值查找 范围查询 磁盘友好度 结论
哈希表 O(1) 最快 不支持（无序） 一般 仅用于内存中的自适应哈希索引
二叉查找树/AVL/红黑树 O(log n) 需中序遍历 差 树高 log₂n，10 亿数据约 30 层 = 30 次 IO
B 树 O(log n) 需回溯父节点 中 所有节点都存数据，单页键少，树偏高
跳表 O(log n) 好（内存） 差 链式结构对磁盘页对齐不友好
B+ 树 O(log n) 好（叶子链表） 最好 InnoDB 的选择

2.4 B+ 树索引的底层结构

2.4.1 磁盘 IO 模型：页、树高、IO 次数

InnoDB 的索引和数据都以页为单位读写。一次索引查找的磁盘 IO 次数 ≈ 树的层数。层数就是 B+ 树的设计核心：把树做得越矮，查询就越快。

分支因子：以 8 字节 BIGINT 主键 + 6 字节页指针为例，一条索引记录约 14 字节：

层数 可支撑数据量 实际 IO 次数
2 层 1170 × 15 ≈ 1.7 万行 1 次
3 层 1170 × 1170 × 15 ≈ 2000 万行 2 次
4 层 百亿行 3 次

注意 IO 次数比层数少 1：根页常驻 Buffer Pool 内存，不需要读磁盘。

页分裂的代价：要写两个新页、改父节点，可能连锁向上分裂。插入顺序直接决定索引的健康度：

  • 顺序插入（自增主键）：永远追加在最右叶子页，空间利用率接近 100%；
  • 乱序插入（UUID 主键）：随机落在任意页，页频繁分裂，**空间利用率跌到约 50%**。

2.5 聚簇索引与非聚簇索引

2.5.1 聚簇索引：数据就是索引

聚簇索引的叶子节点直接存完整行数据。每个表只能有一个聚簇索引：

  1. 显式定义的主键；
  2. 如果没有主键，取第一个非空 UNIQUE 索引；
  3. 都没有，InnoDB 自动生成一个隐藏的 6 字节 ROWID。

2.5.2 非聚簇索引（二级索引）：列值 + 主键

二级索引的叶子节点只存两样东西：索引列的值 + 主键值。

关键细节：InnoDB 二级索引叶子存的是主键值，而不是行指针。代价是：主键越长，每个二级索引越大。

2.5.3 两种索引对比

维度 聚簇索引 二级索引
叶子节点内容 完整行数据 索引列值 + 主键值
每表数量 只能有 1 个 可以有多个
与数据关系 数据即索引，物理顺序 = 主键序 独立结构
查找路径 命中叶子即拿到整行 命中叶子只拿到主键，可能需要回表
主键值变化 — 所有二级索引需要跟着改

2.5.4 回表与覆盖索引

回表：二级索引只存”列值 + 主键”，当查询需要的字段不在索引里时，只能拿主键再到聚簇索引查一遍完整行。

flowchart LR
    Q["SELECT * WHERE name='alice'"] --> SI["走 idx_name"]
    SI --> Hit["命中 ('alice', 3)"]
    Hit --> CI["回聚簇索引查 id=3 的完整行"]
    CI --> Result["返回完整数据"]

覆盖索引：查询所需的列全部包含在索引中，无需回表。

2.5.5 主键怎么选

候选 插入顺序性 索引膨胀 结论
BIGINT 自增 顺序插入，无页分裂 8 字节，最小 首选
雪花 ID 基本有序 8 字节 分布式场景首选
UUID 完全乱序，页分裂频繁 大 避免
业务主键（长字符串） 视业务 所有二级索引跟着变大 避免

2.6 联合索引与最左前缀

2.6.1 联合索引的内部排序

联合索引 (a, b, c) 底层就是一棵 B+ 树，只是排序规则变成了先按 a 排，a 相同再按 b 排，b 相同再按 c 排。

flowchart LR
    A1["a=1, b=2"] --> A2["a=1, b=5"] --> A3["a=1, b=5, c=9"]
    A3 --> A4["a=2, b=1"] --> A5["a=2, b=3"] --> A6["a=2, b=5"]

2.6.2 最左前缀：哪些查询能用上 (a, b, c)

查询条件 能用到的索引部分 说明
a = 1 a 完整使用
a = 1 AND b = 2 a + b 完整使用
a = 1 AND b = 2 AND c = 3 a + b + c 完整使用
b = 2 无 缺最左列 a，索引失效
a = 1 AND c = 3 只用 a 跳过 b，c 无法用于索引定位
b = 2 AND a = 1 a + b 优化器会重排等值条件

两个补充规则：

  • 等值条件顺序无关：优化器会自动把等值条件按索引列序重排；
  • 范围条件后面的列”断链”：a > 1 AND b = 2 中，b 无法用于定位。等值列放前面、范围列放后面是联合索引设计的铁律。

4. 事务原理：ACID、隔离级别与实战

4.1 事务是什么：ACID 与实现机制

特性 一句话定义 靠什么实现 损坏的后果
原子性（Atomicity） 一组操作要么全成功、要么全回滚 undo log 转账只扣了钱

5. MVCC 原理：版本链 + ReadView

5.1 MVCC 定义

MVCC（Multi-Version Concurrency Control）让「读」不阻塞「写」、「写」不阻塞「读」。

flowchart LR
    subgraph MVCC[MVCC 读写不阻塞]
        W[写事务] --> NV[生成新版本]
        R[读事务] --> RS[读历史快照]
        NV -.->|不覆盖旧值| RS
    end

5.2 隐藏列与 undo log 版本链

隐藏列 作用
DB_ROW_ID 表没有主键时生成的自增 id
DB_TRX_ID 最近一次修改该行的事务 id
DB_ROLL_PTR 指向 undo log 中上一版本的回滚指针 
flowchart LR
    V3["V3: trx=60, balance=800<br/>最新版本"] --> V2["V2: trx=40, balance=900"]
    V2 --> V1["V1: trx=30, balance=1000"]
    V1 --> N1["NULL"]

5.3 ReadView：谁能看到哪个版本

字段 含义
creator_trx_id 创建 ReadView 的事务 id
m_ids 生成时刻所有活跃（未提交）事务 id 列表
min_trx_id 活跃事务中的最小 id
max_trx_id 下一个要分配的事务 id 
flowchart TD
    A[快照读：生成 ReadView] --> B[从版本链头部开始判断每个版本的 trx_id]
    B --> C{trx_id < min_trx_id?}
    C -->|是| V1[可见]
    C -->|否| D{trx_id >= max_trx_id?}
    D -->|是| I1[不可见]
    D -->|否| E{trx_id 在 m_ids 中?}
    E -->|是| I2[不可见：未提交]
    E -->|否| V2[可见]
    I1 --> F{还有更旧版本?}
    I2 --> F
    F -->|是| B
    F -->|否| N1[记录对该事务不可见]

5.4 RC 与 RR 的差别只有一句话

隔离级别 ReadView 生成时机 效果

7. 日志系统：redo log、binlog、undo log 与两阶段提交

7.1 undo log：回滚与 MVCC 的基石

undo log 记录数据被修改前的值：

  1. 事务回滚：失败时恢复原样；
  2. MVCC 快照读：其他事务通过 undo 版本链读到旧版本。

7.2 redo log 与 WAL

redo log（物理日志） 记录”在哪个数据页的哪个偏移量做了什么修改”。WAL 的核心：先落日志、再异步刷脏页。

sequenceDiagram
    participant T as 事务
    participant BP as Buffer Pool
    participant RL as redo log
    participant D as 数据文件

    T->>BP: 修改内存页
    T->>RL: 顺序写 redo log
    RL->>RL: fsync 落盘
    Note over T: 事务提交成功
    RL-->>D: 后台异步刷脏页

redo log 刷盘策略（innodb_flush_log_at_trx_commit）：

取值 行为 安全性
0 每秒写入并刷盘 最差：崩溃最多丢 1 秒事务
1 每次事务提交时写入并刷盘（默认） 最好
2 每次提交写入 OS 缓存，每秒刷盘 中

7.3 binlog 三种格式

格式 记录内容 优点 缺点
STATEMENT 原始 SQL 语句 日志小 非确定性函数可能不一致
ROW（8.0 默认） 被修改行的前后值 最安全 批量操作日志量巨大
MIXED 自动选择 兼顾 行为不完全可预期

7.4 redo log vs binlog

特性 redo log binlog
所属层级 InnoDB 层 Server 层
主要作用 崩溃恢复 主从复制、时间点恢复
日志类型 物理日志 逻辑日志

7.5 两阶段提交

sequenceDiagram
    participant C as 客户端
    participant E as InnoDB
    participant S as Server
    participant RL as redo log
    participant BL as binlog

    C->>E: COMMIT
    Note over E: Prepare 阶段
    E->>RL: 写入 redo log，标记 PREPARE
    RL->>RL: fsync 落盘
    Note over S: Write binlog 阶段
    S->>BL: 写入 binlog
    BL->>BL: fsync 落盘

7.6 崩溃恢复

崩溃发生时机 事务状态 恢复动作
redo prepare 之前 未写入 redo 直接丢弃
redo prepare 之后、binlog 写之前 PREPARE，binlog 无该事务 回滚
binlog 写完之后、redo commit 之前 PREPARE，binlog 有该事务 重做（提交）

18. 分区表：RANGE/LIST/HASH/KEY 与分库分表的边界

18.1 分区表是什么

分区表（Partitioned Table）是在单实例内部把一张大表按规则拆成多个物理文件，逻辑上仍是一张表——SQL 语句不需要改，由 MySQL 自动完成分区裁剪（Partition Pruning）。

flowchart TB
    T["逻辑表 t_order"]
    T --> P0["p202601<br/>2026 年 1 月"]
    T --> P1["p202602<br/>2026 年 2 月"]
    T --> P2["p202603<br/>2026 年 3 月"]
    T --> PN["p_max<br/>其他"]

与分库分表的本质区别：

维度 分区表 分库分表
数据分布 同一 MySQL 实例 多个实例
应用改造 无 需要中间件或应用层改造
分区键 建表时指定 由中间件路由
跨分区查询 MySQL 自动归并 中间件归并
扩容上限 单机 IOPS/CPU 可水平扩展
复杂度 低 高

核心结论：**分区表解决”单表数据量大导致查询/维护慢”，分库分表解决”单机容量/并发到顶”**。如果只是单表 1 亿行让备份、DDL、按时间查询变慢，用分区表就够；如果单机磁盘、IOPS、连接数撑不住，才上分库分表。

19. JOIN 优化：三种算法、驱动表选择与实战

19.1 JOIN 的本质：驱动表与被驱动表

所有 JOIN 都是”嵌套循环”的变种：外层表（驱动表）逐行扫描，内层表（被驱动表）按条件查找匹配行。

flowchart LR
    A["驱动表：小表"] -->|每一行| B["被驱动表：大表"]
    B --> C["按 join 条件查找匹配行"]
    C --> R["输出结果"]
    Note[小表驱动大表]

驱动表选择规则：

  • LEFT JOIN：左表是驱动表（不可交换）；
  • INNER JOIN：优化器自动选”结果集小的表”作为驱动表；
  • 目标：驱动表越小越好（减少外层循环次数）。

19.2 三种 JOIN 算法

19.2.1 Nested Loop Join（NLJ，嵌套循环）

适用条件：被驱动表的连接列有索引。

sequenceDiagram
    participant D as 驱动表（t_user 100 行）
    participant I as 被驱动表（t_order 有 user_id 索引）
    D->>I: 取 user_id=1, 走索引查 t_order
    I-->>D: 返回匹配行
    D->>I: 取 user_id=2, 走索引查 t_order
    I-->>D: 返回匹配行
    Note over D,I: 循环 100 次

复杂度：驱动表行数 × 索引查找代价（O(log n)）。效率最高。

EXPLAIN 特征：

被驱动表 t_order 的 type=ref、key=idx_user_id。

19.2.2 Block Nested Loop（BNL，块嵌套循环，5.6 引入）

适用条件：被驱动表的连接列没有索引。

MySQL 会把驱动表的结果集读入 join buffer（默认 256 KB，join_buffer_size），然后一次扫描被驱动表，把所有行与 join buffer 中的行做匹配——用内存换 IO。

    D["驱动表结果集 1000 行"] -->|一次读入| JB["Join Buffer<br/>join_buffer_size"]
    JB -->|一次扫描| I["被驱动表 100 万行"]
    I --> M["内存匹配"]
    M --> R["输出结果"]

EXPLAIN 特征：

问题：join buffer 装不下整个结果集时，会分多次扫描被驱动表（每批 256 KB），被驱动表被扫描 N 次，性能急剧下降。

19.2.3 Hash Join（8.0.18+ 引入）

适用条件：被驱动表没有索引，且等值连接。

原理：

  1. 把小表（驱动表）读入内存，构建哈希表；
  2. 扫描大表（被驱动表），每一行探测哈希表是否匹配；
  3. 输出匹配结果。

vs BNL：Hash Join 的哈希表探测是 O(1)，无需重复扫描被驱动表；BNL 需要多次扫描被驱动表，两者差距在大表场景可达数倍到数十倍。

23. 自增锁与 MDL：两个容易被忽视的并发瓶颈

23.1 自增锁（AUTO-INC Lock）

什么是自增锁：InnoDB 为 AUTO_INCREMENT 列分配自增值时使用的锁。它的粒度由 innodb_autoinc_lock_mode 控制：

模式 值 行为 场景
传统模式 0 语句级锁，语句结束才释放 5.1 前默认，兼容 binlog statement
连续模式 1 简单 INSERT 立即释放；批量插入等到语句结束 5.7 默认，性能与复制兼顾
交错模式 2 任何情况都立即释放，自增值可能不连续 8.0 默认，性能最高

并发行为对比：

自增值不连续的原因：

  1. 事务回滚：分配的 ID 不会回收；
  2. 批量插入：模式 1 下一次分配一批，但只用了部分；
  3. 交错模式：并发分配导致顺序错乱；
  4. 唯一键冲突：分配后未使用。

结论：不要依赖自增 ID 的连续性。如果需要连续 ID，用业务层编号（如订单号）。

23.2 MDL（Metadata Lock，元数据锁）

什么是 MDL：MySQL 在执行 SQL 时自动加的表结构保护锁，用于防止”查着表结构被改了”。

  • MDL 读锁：SELECT/INSERT/UPDATE/DELETE 时自动加；
  • MDL 写锁：ALTER TABLE 等 DDL 时自动加；
  • 读锁之间兼容，写锁与任何锁互斥。

23.3 MDL 阻塞真实案例

场景：一条长事务 START TRANSACTION; SELECT ... FROM t_user;（未提交），另一个会话执行 ALTER TABLE t_user ADD COLUMN xxx。

发生的事：

sequenceDiagram
    participant A as 会话 A（长事务）
    participant B as 会话 B（DDL）
    participant C as 会话 C（后续查询）
    participant MDL as MDL 队列

    A->>MDL: SELECT → 加 MDL 读锁（事务不提交，读锁不释放）
    B->>MDL: ALTER → 请求 MDL 写锁（排队等待 A 释放）
    C->>MDL: SELECT → 请求 MDL 读锁（排队在 B 后面）
    Note over MDL: MDL 是公平队列
    Note over A: 长事务未提交
    Note over C: C 被 B 阻塞，即使 B 是写锁，C 也要排在 B 后
    Note over C: 大量 C 堆积，连接池打满 → 服务雪崩

关键点：MDL 是公平队列——B 的写锁在等 A，C 的读锁必须排在 B 后面，即使读锁本来和 A 的读锁兼容。一个长事务 + 一个 DDL 就能拖垮整个库。

27.1 为什么需要在线 DDL

MySQL 5.6 引入 Online DDL 后，大部分 DDL 不再锁表，但仍有隐患：

DDL 类型 5.6 Online DDL 8.0 Instant DDL
加索引 不锁表 —
加列（末尾） 不锁表，但重建表 秒级（8.0.12+）
加列（中间） 重建表 重建表
改列类型 重建表 重建表
加外键 不锁表 —

重建表的问题：

  • 大表重建可能几小时，期间消耗 IO/CPU；
  • 需要 innodb_online_alter_log_max_size 缓冲期间的 DML，超了会失败；
  • 主从延迟：主库重建后 binlog 一次性到从库，从库延迟尖峰。

27.2 pt-online-schema-change（pt-osc）

原理：

flowchart LR

32. 分库分表扩容实战：从 8 表到 16 表

32.1 场景

t_order 按 user_id % 8 分到 8 张表，每表 2000 万行，写 QPS 接近单机上限。需要扩到 16 张表。

32.2 取模扩容的困境

原方案：user_id % 8 → 表 t_order_0 ~ t_order_7。

扩到 16 表后：user_id % 16 → 表 t_order_0 ~ t_order_15。

问题：几乎所有数据都要迁移——user_id=9 原来在 t_order_1，现在应该在 t_order_9；user_id=17 原来在 t_order_1，现在也在 t_order_1（因为 17 % 16 = 1）……只有 user_id % 8 == user_id % 16 的记录不用迁移（即 user_id % 16 < 8 的记录），约占 50%。

32.4 迁移过程中的问题

问题 1：迁移速度慢

  • 单线程迁移 8 张表 × 2000 万行 = 1.6 亿行，需要好几天；
  • 解法：多线程并行迁移，每个 user_id 独立；或用多台机器分片迁移。

问题 2：主从延迟

  • 大批量写入导致从库延迟；
  • 解法：迁移限速（每秒 N 条），监控从库延迟，超过阈值暂停。

问题 3：迁移任务中途失败

  • 解法：用 migration_progress 表记录进度，重启后从断点续传。

问题 4：数据不一致

  • 双写失败 / 迁移遗漏；
  • 解法：对账任务 + 每日全量抽样对账。

32.5 一致性哈希方案的对比

如果一开始就用一致性哈希（见第 16 章），扩 8 → 16 表只需迁移约 1/2 的数据（其实是 8 个节点变 16 个节点，迁移量 = 新节点对应的数据，约 50%）——和取模的迁移量相当。但如果只是加 1 个节点（8 → 9），一致性哈希只需迁移约 1/9，取模则需要迁移 8/9。

判断：

  • 扩容规律（如固定翻倍）：取模 + 双写迁移；
  • 不确定扩容节奏：一致性哈希 + 虚拟节点。

G.2 5.7 → 8.0 升级检查清单

1. 兼容性检查：

2. 字符集统一：

  • 5.7 默认 latin1，8.0 默认 utf8mb4；
  • 检查所有表的字符集是否一致，避免升级后乱码。

3. 认证方式：

  • 8.0 默认 caching_sha2_password；
  • 老版本客户端可能不支持，可临时改回 mysql_native_password。

4. SQL 语法兼容：

  • 关键字冲突：8.0 新增大量保留字（如 RANK、ROWS、GROUPS），检查表名/列名是否需要反引号；
  • GROUP BY 严格模式：8.0 默认 ONLY_FULL_GROUP_BY，SELECT 未聚合列会报错。

5. 复制相关：

  • SHOW SLAVE STATUS → SHOW REPLICA STATUS；
  • CHANGE MASTER TO → CHANGE REPLICATION SOURCE TO。

6. 备份兼容：

  • 5.7 的 mysqldump 可能无法恢复到 8.0；
  • 建议升级前用 8.0 的 mysqldump 备份。

7. 索引长度：

  • 8.0 索引前缀长度限制从 767 字节升到 3072 字节；
  • 之前的 VARCHAR(191) 限制可放宽到 VARCHAR(768)。

G.3 8.0 新命令速查

全文因果链回顾：

  1. 架构：Server 层管执行，引擎层管存储；一条 SQL 走连接器 → 解析器 → 优化器 → 执行器 → 引擎
  2. 索引：B+ 树（矮树 + 叶子链表）→ 聚簇索引（数据本体）+ 二级索引（列 + 主键）→ 回表/覆盖/最左前缀/ICP
  3. 事务：ACID（一致性是目标）+ 隔离级别（RC/RR 差别在 ReadView 生成时机）+ MVCC（版本链 + ReadView）
  4. 锁：行锁三形态（记录/间隙/临键）+ 意向锁 + 插入意向锁 → 死锁循环等待 + 统一顺序 + 重试
  5. 日志：undo（回滚+MVCC）+ redo（物理，崩溃恢复）+ binlog（逻辑，复制）→ 两阶段提交
  6. 内核：Buffer Pool（读写内存）+ Change Buffer（推迟随机 IO）+ AHI（加速等值）+ Doublewrite（防部分页）
  7. 优化：慢查询定位 → EXPLAIN → 索引/SQL 优化；count/分页/IN-EXISTS；连接池大小与打满排查
  8. 高可用：主从（三线程 + GTID + 半同步/MGR）+ 读写分离（动态数据源 + 延迟一致性）+ 高可用架构（MHA/MGR/InnoDB Cluster/Orchestrator）
  9. 扩展：分库分表（垂直/水平/分片算法）+ ShardingSphere（五阶段内核）+ 扩容（停机/双写/一致性哈希）
  10. 设计：范式（1NF/2NF/3NF）与反范式（用冗余换性能）
  11. 进阶：分区表（单机内拆文件）+ JOIN 三种算法 + 排序分组优化 + 字段选型 + 8.0 新特性 + 自增锁/MDL
  12. 运维：备份恢复（mysqldump/xtrabackup/PITR）+ 主从搭建 + MGR 部署 + 在线 DDL + 压测
  13. 实战：慢 SQL 优化 + 大表 DDL + 死锁排查 + 分表扩容 + 主从延迟排查
