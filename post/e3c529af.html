Zeus-Doc 数据库设计

Posted on 2026-08-06 In 项目实战 Word count in article: 6k Reading time ≈ 22 mins.

Zeus-Doc 数据库设计文档

版本：1.0.0 ｜ 更新日期：2026-07-31

相关文档：《01-系统架构》｜《06-面试手册第3问》

一、数据库选型与分片总览

Zeus-Doc 采用 MySQL 8.0 作为持久化存储，通过 ShardingSphere-JDBC 5.4.1 实现透明分库分表。核心配置位于 zeus-doc-service-doc/src/main/resources/application-sharding.yml。

1.1 库表分布全景

逻辑库 物理库 服务归属 是否分片
zeus_user zeus_user user-service 否（单库）
zeus_doc zeus_doc（ds0） doc-service 否（主表单库）
doc_history zeus_doc_history_0..3 doc-service 是（4 库 × 月表）
zeus_audit zeus_audit_0..3 audit-service 是（按租户分库）
zeus_file zeus_file file-service 否（单库）
doc_audit_cold 全库广播 audit-service 广播表

1.2 分片策略摘要（application-sharding.yml:56-101）

  • doc_history：分库列 doc_id（MOD 4），分表列 created_at（INTERVAL 按月，后缀 yyyyMM）
  • doc / share_link：不分片，落在 ds0
  • doc_audit_cold：广播表，4 库均存全量
  • 主键生成：雪花算法 SNOWFLAKE

三、各表字段说明

3.1 doc（文档主表）

字段 类型 说明
id bigint 雪花主键
tenant_id bigint 租户ID，所有查询必带
author_id bigint 创建人（KEY idx_author）
title varchar(255) 文档标题

3.2 doc_history（版本历史表，分库分表）

记录每次保存的版本快照与 OT patch。这是数据量最大的表，单租户日均 10 万条，故按 doc_id % 4 分 4 库、按 created_at 月份分表（如 doc_history_202608）。

doc_id bigint 分库列
version int 版本号
content mediumtext 快照正文
user_id bigint 创建人（KEY idx_user）
patch_text varchar OT patch 文本（diff_toText）
created_at datetime 分表列

3.3 doc_audit（审计日志表，按租户分库）

字段 类型 说明
id bigint 雪花主键
tenant_id bigint 分库列
doc_id / user_id bigint 索引
action tinyint 操作类型枚举
detail varchar(1000) JSON 快照
ip varchar(45) 操作 IP
status tinyint TCC 状态：PENDING/SUCCESS/CANCEL
created_at datetime 分表列

3.4 share_link / file / file_chunk / recycle_bin

字段见 ER 图，此处不赘述。recycle_bin 与 doc_audit 均有 status 字段承载 TCC 两阶段状态。

四、分库分表策略详解

4.1 doc_history：按 doc_id % 4 分库 + 按月分表

配置（application-sharding.yml:59-73）：

分库算法：MOD 类型，sharding-count: 4，即 库序号 = doc_id % 4。

分表算法：INTERVAL 类型，按 created_at 月份生成 yyyyMM 后缀，范围 2026-08 ~ 2027-12，间隔 1 个月。

为什么这样分：

  • 按 doc_id 分库：查某文档历史版本时只命中 1 个库，避免广播；
  • 按月分表：单表数据量控制在千万级，便于按时间范围归档冷数据；
  • doc_history 写入 QPS 高（每次保存一条），分片后单库写入压力降为 1/4。

数据节点矩阵（共 4 库 × 17 月 = 68 张物理表）：

注：doc_history 的分表区间为 202608..202712（17 张月表）；doc_audit 的分表区间为 202601..202612（12 张月表，见 04_audit_schema.sql），两者归属不同表，勿混用。

4.2 doc_audit：按 tenant_id 分库 + 按 created_at 分表

审计表按租户分库（tenant_id % 4），保证同一租户的审计数据落在同一库，便于按租户聚合查询。按 created_at 月份分表，便于按时间范围清理过期审计。

注：doc_audit 与 doc_history 分库策略不同，前者按租户（查询维度是租户），后者按文档（查询维度是文档版本），体现了「按查询维度选分片键」的原则。

注：doc_audit 的分表区间为 202601..202612（12 张月表，按 04_audit_schema.sql）；doc_history 的分表区间为 202608..202712（17 张月表），两者归属不同表，勿混用。

4.3 广播表 doc_audit_cold

冷备审计表作为广播表（application-sharding.yml:108-110），4 库均存全量。JOIN 时无需跨库，适合更新少、读多的字典/冷数据。

五、索引策略

5.1 索引设计原则

  1. 所有查询必带分片键，避免全库广播；
  2. 覆盖索引优先，减少回表；
  3. 联合索引最左前缀，区分度高的列在前。

5.2 关键索引清单

表 索引 用途
doc idx_author (author_id) 按作者查文档列表
doc idx_updated_at (updated_at) 按「最近更新」排序（游标分页）
doc uk_tenant_title (tenant_id, title) 标题唯一约束
doc_history idx_doc_version (doc_id, version) 查某文档指定版本
doc_history idx_user (user_id, deleted) 按创建人查版本历史 + 软删过滤
doc_audit idx_tenant_created (tenant_id, created_at) 租户审计按时间范围
doc_audit idx_doc_action (doc_id, action) 查某文档操作记录
share_link uk_share_code (share_code) 提取码查询
share_link idx_expire (expire_at) 过期清理定时任务
recycle_bin idx_expire (expire_at) 过期自动清理
file uk_md5 (md5) 秒传校验
file_chunk idx_file_idx (file_id, chunk_index) 分片查询

六、慢查询优化案例：OFFSET 分页 → 游标分页改写

6.1 问题现象

用户文档列表接口 GET /docs?authorId=1&page=5000&size=20，压测时 RT 高达 2.3s，SqlCostInterceptor（SqlCostInterceptor.java:73-75）捕获慢 SQL 告警：

6.2 根因分析

LIMIT 20 OFFSET 100000 在 MySQL 中需扫描 100020 行并丢弃前 100000 行，越往后翻越慢（深翻页问题）。InnoDB 二级索引回表放大 IO。

6.3 改写方案：游标分页（Keyset Pagination）

6.4 优化效果（模拟数据）

翻页深度 OFFSET 方案 RT 游标方案 RT 提升
第 1 页 12ms 8ms 33%
第 100 页 180ms 9ms 20x
第 5000 页 2300ms 10ms 230x

游标分页 RT 与翻页深度无关，始终走索引范围扫描，恒定 < 15ms。

注：本案例为 A 批次压测（模拟数据，第 5000 页深翻页场景，OFFSET 10 万行）；附5「5.3 性能对比」为另一批次（百万量级数据，第 1 万~5 万页深翻页场景），两批次页深与数据集不同，数据不直接可比。

6.5 局限

游标分页不支持跳页（只能上一页/下一页），适合移动端无限滚动场景；后台管理需要精确跳页时，可对深翻页降级为「估算 + 限制最大页数」。

七、复杂 SQL 路由过程：按 doc_id 分组查最新版本

7.1 业务场景

查询某租户下所有文档的最新版本号：

7.2 ShardingSphere 路由归并原理

doc_history 按 doc_id % 4 分库。本 SQL 不带分片键 doc_id 的等值条件，ShardingSphere 无法精确定位单库，触发全库路由，将 SQL 改写后下发到 4 个分片库：

归并（Merge）阶段：ShardingSphere 对 4 个分片返回的 GROUP BY 结果执行聚合归并：

  1. 各分片结果按 doc_id 排序（流式归并要求各分片自身有序）；
  2. 归并引擎按 doc_id 分组，对同一 doc_id 的 MAX(version) 取最大值；
  3. 输出最终合并结果。

7.3 路由归并流程图

flowchart LR
    SQL[业务 SQL<br/>GROUP BY doc_id] --> Parse[SQL 解析]
    Parse --> Route[路由引擎<br/>无分片键等值条件<br/>全库路由]
    Route --> Rewrite[SQL 改写<br/>下发 4 库]
    Rewrite --> DS0[ds0 GROUP BY doc_id]
    Rewrite --> DS1[ds1 GROUP BY doc_id]
    Rewrite --> DS2[ds2 GROUP BY doc_id]
    Rewrite --> DS3[ds3 GROUP BY doc_id]
    DS0 & DS1 & DS2 & DS3 --> Merge[归并引擎<br/>分组归并 GroupByMerge]
    Merge --> Agg[同 doc_id 取 MAX version]
    Agg --> Result[合并结果集]

7.4 优化建议

  • 带分片键查询：若能传入具体 doc_id，路由到单库，避免广播；
  • 避免跨库 GROUP BY：本例全库路由 + 归并代价高，可在 doc 主表冗余 latest_version 字段，避免查 doc_history；
  • 流式归并：ShardingSphere 对 ORDER BY + LIMIT 采用流式归并，内存占用 O(分片数) 而非 O(总行数)。

八、跨库 Join 解决方案

ShardingSphere-JDBC 不支持跨库 JOIN，本项目采用以下策略规避：

场景 方案
doc JOIN doc_history 应用层组装：先查 doc，再按 doc_id 查 history（同库）
doc JOIN user 冗余字段：doc 表冗余 user_nickname，避免 JOIN
doc_audit JOIN doc（跨服务跨库） Feign 调 doc 服务查标题，应用层组装
字典/冷数据 JOIN 广播表（doc_audit_cold），各库全量，JOIN 在单库内完成

九、数据归档与冷热分离

数据 热存储 冷存储 归档策略
doc_history 近 3 月 doc_history_YYYYMM 归档到 OSS Parquet 定时任务迁移 3 月前数据
doc_audit 近 1 年 doc_audit_YYYYMM doc_audit_cold 广播表 按年归档
recycle_bin 过期 - 物理删除 expire_at 定时清理

十、主键生成策略

统一采用雪花算法（SNOWFLAKE），配置于 application-sharding.yml:103-106：

雪花 ID = 时间戳(41bit) + workerId(10bit) + 序列号(12bit)，单机每毫秒可生成 4096 个，趋势递增利于 B+ 树插入（避免页分裂）。workerId 由 Nacos 分配，保证集群内唯一。

SnowflakeIdUtil.gen()（zeus-doc-common）在 TCC 编排中生成 auditId、recycleId（DocDeleteTccFacade.java:58-59）。

本数据库设计文档与 application-sharding.yml 配置一一对应。分片键选择与归并原理详见《06-面试手册第3问》，慢 SQL 拦截器实现见 SqlCostInterceptor.java。

附3、分库分表策略详解（补充章节）

3.1 doc_history：按 doc_id%4 分库 + 按月分表

配置文件： zeus-doc-service-doc/src/main/resources/application-sharding.yml

策略说明：

维度 分片键 算法 路由规则
分库 doc_id MOD（取模） ds{doc_id % 4}
分表 created_at INTERVAL（时间区间） doc_history_{yyyyMM}

为什么这么分？

  1. 按 doc_id 分库：历史版本查询 99% 场景是”查某文档的所有版本”，doc_id 是天然的高基数查询维度。按 doc_id%4 分库后，同一文档的所有版本落在同一库，避免跨库归并。doc_id 由雪花算法生成，分布均匀，4 库数据平衡。
  2. 按月分表：历史版本按时间持续增长，按月切分便于冷热分离（旧月表可归档/删除）。INTERVAL 算法支持范围查询路由（如查近 3 个月版本只需扫 3 张月表）。
  3. 数据节点表达式 ds$->{0..3}.doc_history_$->{202608..202712}：Groovy 表达式声明 4 库 × 17 月表共 68 个真实数据节点，ShardingSphere 自动路由。

路由示例：

  • 查 doc_id=1001, created_at=2026-08-15 → 库 ds{1001%4}=ds1，表 doc_history_202608
  • 查 doc_id=1001（不带时间）→ 库 ds1，所有月表广播

注：doc_history 的分表区间为 202608..202712（17 张月表）；doc_audit 的分表区间为 202601..202612（12 张月表），两者归属不同表，勿混用。

3.2 doc_audit：按 tenant_id%4 分库 + 按月分表

配置文件： zeus-doc-service-audit/src/main/resources/application-sharding.yml

注：doc_audit 的分表区间为 202601..202612（12 张月表，按 04_audit_schema.sql）；doc_history 的分表区间为 202608..202712（17 张月表），两者归属不同表，勿混用。

策略说明：

维度 分片键 算法 路由规则
分库 tenant_id INLINE（表达式） ds{tenant_id % 4}
分表 created_at CLASS_BASED（自定义） doc_audit_{yyyyMM}

为什么选 tenant_id 分库（而非 doc_id）？

  1. 审计日志查询以租户为维度：管理员审计页面按租户筛选”本租户所有操作记录”，tenant_id 是必带过滤条件，分库后精确命中单库。
  2. 多租户隔离：不同租户数据物理隔离，避免大租户日志拖慢小租户查询。
  3. **allow-range-query-with-inline-sharding: true**：允许 INLINE 算法处理范围查询（虽不精确路由，但避免全库广播）。
  4. 自定义 MonthlyShardingAlgorithm（CLASS_BASED）：实现 StandardShardingAlgorithm，同时支持精确分片（= created_at，命中单表）与范围分片（BETWEEN created_at，命中多月表），用于时间区间审计追溯。

绑定表优化：

doc_audit 与冷备表 doc_audit_cold 使用相同分库键 tenant_id，声明绑定表后，两者 JOIN 不会产生跨库笛卡尔积，路由到同一分片。

附5、慢查询优化案例：OFFSET 分页 → 游标分页（补充章节）

5.1 问题背景

文档列表接口原使用 LIMIT offset, size 分页。当用户深翻页（如查第 10000 页，每页 20 条）时：

执行计划（EXPLAIN）：

问题：

  1. LIMIT 199980, 20 需扫描前 199980 行再丢弃，越深翻页越慢。
  2. 虽走 idx_updated_at 索引，但需回表 200K 次判断 tenant_id/deleted。
  3. 实测：第 10000 页 RT > 1200ms（触发慢 SQL 告警，SqlCostInterceptor 拦截上报）。

5.2 游标分页优化

代码位置： DocService.listByCursor（DocService.java:135），DocMapper.selectByCursor（DocMapper.java:29）。

为什么用 id 作游标而非 updated_at？

  • id 是主键，唯一且单调递增（雪花），id < lastId ORDER BY id DESC LIMIT 20 走主键索引范围扫描，恒定扫描 20 行。
  • 若用 updated_at 作游标，同一时间戳可能有多条记录，需联合 id 做复合游标 (updated_at, id)，SQL 复杂。

优化后执行计划：

  • type=range，rows=20，只扫描满足条件的 20 行，O(1) 恒定，无论翻到第几页。

5.3 性能对比（模拟数据）

翻页深度 OFFSET 分页 RT 游标分页 RT 提升
第 1 页 8ms 5ms -
第 100 页（offset 2000） 35ms 5ms 7x
第 1000 页（offset 20000） 280ms 5ms 56x
第 10000 页（offset 200000） 1240ms 5ms 248x
第 50000 页（offset 1M） 6800ms（超时） 5ms 1360x

5.4 游标分页的代价

限制 说明 应对
不支持跳页 只能”上一页/下一页” 文档列表场景用户极少跳页，可接受
排序字段需索引 id < lastId 需走索引 主键天然有索引
反向翻页需反向游标 “上一页”需 id > firstId ORDER BY id ASC 前端记录首尾 id
