复制、哨兵与 Cluster：切一次主要多久

Posted on 2026-10-25 In 数据存储 Word count in article: 3.3k Reading time ≈ 12 mins.

Redis 的主从切换没有「秒级」这么模糊的说法，实测是 3.33 秒（哨兵）和 6.9 秒（Cluster）。这两个数字都由同一个参数决定：多久判定一个节点「死了」。

本文搭了三套真实环境：一主一从、三哨兵、六节点 Cluster（3 主 3 从），把全量同步、部分重同步、故障转移、槽路由全部跑了一遍。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster（本文） → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：⑦ 的 AOF 是「单机的后悔药」，本文的复制是「跨机器的副本」；本文的「切换窗口」是 ⑪ 分布式锁丢锁的根因，也是 ⑩ 缓存不一致的一个来源。

1. 复制：全量同步与部分重同步

1.1 PSYNC 的流程

sequenceDiagram
    participant S as Replica
    participant M as Master
    S->>M: PSYNC ? -1（首次连接）
    M-->>S: FULLRESYNC replid offset
    M->>M: BGSAVE 生成 RDB
    M-->>S: RDB 文件
    M-->>S: 期间的写命令（repl buffer）
    S->>S: 加载 RDB + 重放缓冲
    S->>M: PSYNC replid offset（断线重连）
    M-->>S: CONTINUE（增量，不传 RDB）
场景 结果 代价
首次连接 FULLRESYNC：传整个 RDB 与数据量成正比
短暂断线后重连 CONTINUE：只补 offset 之后的命令 极小
断线太久（超出 backlog） 又变成全量 大

1.2 实测：全量同步与部分重同步

搭一主一从（--replicaof r-master 6379），写入 10000 个 key：

指标 主库 从库
role master slave
connected_slaves 1 —
master_link_status — up
dbsize 10,000 10,000
master_repl_offset 535,669 535,669（slave_repl_offset）
sync_full / sync_partial_ok 1 / 0 —

offset 相等就代表追平——这是比 lag 更硬的判据（lag 是秒级粒度，offset 是字节级）。

然后重启从库，观察重连行为：

指标 重启前 重启后
sync_full 1 1（没增加）
sync_partial_ok 0 1
链路恢复耗时 — 0.31 s
从库数据 10,000 10,000（无损）

结论：短时间断线走的是部分重同步，没有重新传 RDB。这依赖 repl-backlog-size（默认 1 MB）能覆盖断线期间的写入量——如果你的写入很猛、断线又久，backlog 撑不住就会退化成全量同步。

1.3 复制延迟的三种来源

来源 表现 处理
网络 master_link_status 抖动、offset 差距波动 同机房部署
从库负载 从库在跑 BGSAVE/大查询 持久化放到专用从库（⑦）
主库写入过猛 offset 持续落后 分批写、限流

2. 哨兵：把「主从」变成「高可用」

2.1 判定与投票

flowchart TD
    A["Sentinel 每秒 PING master"] --> B{"超时 > down-after?"}
    B -- yes --> C["主观下线 s-down"]
    C --> D{"quorum 个哨兵<br/>都认为下线?"}
    D -- yes --> E["客观下线 o-down"]
    E --> F["选 leader 哨兵"]
    F --> G["提升某个 replica"]
    G --> H["其余 replica 改指向新主"]
    H --> I["通知客户端（新地址）"]

2.2 实测：3 哨兵，3.33 秒完成切换

配置：quorum 2、down-after-milliseconds 2000、failover-timeout 10000，3 个哨兵 + 1 主 1 从。

实测流程：

步骤 结果
3 个哨兵都认到 master SENTINEL get-master-addr-by-name mymaster → 172.19.0.2
已知副本数 1
kill -9 主库 —
哨兵确认新主 3.33 s，新主 172.19.0.3
从库角色 role:master
写入新主 OK

3.33 秒是怎么来的：down-after = 2000ms 判定主观下线 + quorum 内互相确认 + 选举 leader + 提升从库 + 通知其余节点。想更快就把 down-after 调小，但误判风险上升（网络抖动 1 秒就被判死，代价是一次不必要的切换）。

2.3 一个真实的坑：哨兵启动时解析不了主机名

第一次我用容器名配置：

哨兵直接启动失败：

原因：哨兵在解析配置时就要解析主机名，此时容器的 DNS 可能还没就绪。改成 IP 后立刻正常。

生产建议：哨兵配置里用 IP 或「启动时就一定能解析的域名」，不要依赖容器编排的动态名称。

2.4 哨兵的三个参数

参数 本文设置 生产建议 作用
quorum 2 哨兵数/2 + 1 多少个哨兵认为下线才算「客观下线」
down-after-milliseconds 2000 5000~30000 判定主观下线的超时
failover-timeout 10000 60000+ 切换失败后的重试间隔与总超时
parallel-syncs 1 1~2 同时向新主同步的从库数

3.3 实测：Cluster 故障转移 6.9 秒

杀掉持有 5461-10922 的主节点（--cluster-node-timeout 5000）：

指标 实测
从库被提升为新主 6.9 s
集群状态 回到 cluster_state:ok
槽覆盖 16384 全部 ok
写入 OK

为什么比哨兵慢：Cluster 的故障判定依赖 cluster-node-timeout（本文 5 秒）+ gossip 传播 + 选举，天然比「哨兵专门盯一个主」慢一截。

flowchart LR
    A["master killed"] --> B["node-timeout 5s<br/>mark pfail"]
    B --> C["gossip: majority fail"]
    C --> D["replica election"]
    D --> E["promote + take slots<br/>6.9s total"]
    E --> F["cluster_state ok"]

3.4 三种高可用方案对比

维度 主从（手工切换） 哨兵 Cluster
自动故障转移 ❌ ✅ 3.33 s（本文） ✅ 6.9 s（本文）
分片能力 ❌ ❌ ✅ 16384 槽
客户端复杂度 低 中（要问哨兵要地址） 高（要处理 MOVED/ASK）
多 key 操作 随意 随意 受槽限制
适用数据量 单机内存内 单机内存内 超过单机内存
运维复杂度 低 中 高

选型顺序：主从 → 哨兵 → Cluster。只有当数据量超过单机内存时才该上 Cluster——很多人为了「高可用」直接上 Cluster，结果是给自己加了一堆槽限制。

4. 一致性代价

4.1 异步复制的丢失窗口

Redis 复制是异步的：主库写完就回客户端，不等从库确认。所以：

场景 会丢什么
主库宕机，从库未收到最后 N 条 丢掉这 N 条（N 由网络与负载决定）
主库磁盘坏 + AOF 也没了 丢到上次 RDB/AOF
切换后旧主恢复 旧主上的数据可能被丢弃（新主成为权威）

缓解手段：

代价很直接：从库全挂时主库会拒绝写入。这是「可用性 vs 一致性」的显式选择，不是免费的。

4.2 切换瞬间会丢锁（⑪ 的伏笔）

一个具体的连锁反应：

  1. 客户端 A 用 SET lock:order 1 NX PX 30000 拿到了锁（写在主库）；
  2. 主库在把这条命令同步给从库前宕机；
  3. 哨兵把从库提升为新主——这把锁不存在了；
  4. 客户端 B 用同样的 key 加锁，成功。

于是 A 和 B 同时认为自己持有锁。这就是 ⑪ 要讲的「RedLock 争议」的现实版。

6. 动手验证：四个可复现实验

6.1 动手验证：搭一主一从并验证追平

预期观察点：master_link_status:up，两边 offset 相等。

判定标准：offset 持续不相等 → 有复制阻塞；link_status:down 查网络与 Last_IO_Error。

6.2 动手验证：验证部分重同步

预期观察点：sync_full 不变（仍为 1），sync_partial_ok 变成 1，说明走的是增量同步。

判定标准：sync_full 变成 2 → 退化成全量同步，检查 repl-backlog-size 是否太小。

6.3 动手验证：哨兵切换计时

预期观察点：本文 3.33 s 完成切换；新主 role:master 且可写。

判定标准：超过 10 s → 检查 quorum 是否满足、哨兵数量是否够、down-after 是否过大。

6.4 动手验证：验证 Cluster 重定向

预期观察点：错误节点返回 MOVED <slot> <ip:port>；-c 自动跟随成功；跨槽 MGET 报 CROSSSLOT。

判定标准：集群刚创建时 cluster_state 可能是 fail，等几秒收敛；长时间 fail 查 CLUSTER NODES 是否有节点没握手。

5. 总结

5.1 面试速答表

面试题 一句话答案
Redis 复制的流程 PSYNC → 首次 FULLRESYNC 传 RDB + 缓冲命令；断线重连 CONTINUE 增量同步
全量同步什么时候发生 首次连接，或断线超出 repl-backlog-size（默认 1 MB）
怎么判断从库追平了 master_repl_offset 与 slave_repl_offset 相等（比 lag 精确）
哨兵怎么判定主库挂了 超时 down-after → 主观下线；达到 quorum → 客观下线 → 选 leader 切换
哨兵切换要多久 本文 3.33 s（down-after 2 s、quorum 2）
哨兵配置的坑 启动时要能解析主机名，否则 FATAL；用 IP 或稳定域名
Cluster 有多少槽 16384，3 主各分 ~5461 个
客户端请求错节点会怎样 返回 MOVED <slot> <ip:port>，客户端需重定向
跨槽多 key 操作 报 CROSSSLOT，用 {} hash tag 让 key 同槽
Cluster failover 多久 本文 6.9 s（node-timeout 5 s）
为什么 Cluster 比哨兵慢 判定依赖 cluster-node-timeout + gossip + 选举
什么时候该上 Cluster 数据量超过单机内存时；只是为了高可用用哨兵就够
Redis 复制是同步的吗 异步，主库不等从库确认；可用 min-replicas-to-write 换一致性

5.2 实战避坑表

症状 原因 处理
从库频繁全量同步 backlog 太小 / 断线太久 调大 repl-backlog-size
哨兵不切换 quorum 不满足 / 只部署了 1 个哨兵 至少 3 个哨兵，奇数
哨兵启动失败 主机名解析不了 用 IP 或稳定域名
客户端切换后连不上 客户端缓存了旧主地址 用支持哨兵/集群的客户端（Jedis/Lettuce 的 sentinel 模式）
Cluster 里 MGET 报错 跨槽 hash tag 或拆分
切换后数据少了 异步复制丢失窗口 min-replicas-to-write 或接受
切换后出现双写 旧主未彻底下线 旧主降级为从库，REPLICAOF 新主

5.3 工具速查表

工具 看什么 判定标准
INFO replication role、link_status、offset offset 相等 = 追平
SENTINEL get-master-addr-by-name 当前主地址 切换后应返回新主
SENTINEL replicas 已知副本 数量要与部署一致
CLUSTER INFO cluster_state、slots_ok ok 且 16384 全覆盖
CLUSTER SLOTS 槽与节点映射 用于排查重定向
CLUSTER NODES 拓扑与角色 看谁 fail、谁被提升

5.4 实操建议

  1. 先算清你是否真的需要 Cluster。数据装得下就哨兵，装不下才 Cluster。
  2. 哨兵部署 3 个以上且奇数，quorum 取多数；配置里用 IP。
  3. 监控 offset 差而不是只看 lag，前者能提前发现复制阻塞。
  4. min-replicas-to-write 是显式取舍，开了就别抱怨「从库挂了主库不能写」。
  5. 切换演练每季度一次，并验证客户端能自动发现新主（很多故障卡在客户端缓存）。
