ES 查询优化与实战：深度分页、聚合与双写一致性

Posted on 2026-08-13 In 数据存储 Word count in article: 3.7k Reading time ≈ 14 mins.

搜索系统上生产的三道坎：分页超过 1 万条怎么办？聚合为什么慢？MySQL 和 ES 数据不一致怎么收场？ 原理篇讲了 ES 为什么快、数据怎么存，本文解决「怎么查得快、查得准、查得全」：深度分页的正确姿势（search_after/scroll 的选择）、聚合的代价模型、以及双写一致性的三种架构方案。读完你能在设计评审上说清「为什么 ES 分页只支持前 1 万条」「聚合上亿数据用什么策略」，并给 MySQL→ES 同步画出一张完整的架构图。

联动：本文是 ES 原理深挖（写入链路/分片/集群健康）的实战续篇；双写一致性与 分布式系统核心理论 的最终一致性呼应；本地消息表方案与 RocketMQ 原理与实践 的事务消息是同一思路的两条实现路径。

1. 定位：这篇实战什么

原理篇回答「数据怎么存、怎么不丢」，本文回答三个「查询与同步」问题：

场景 表面现象 本文答案
分页翻到第 2 万条 报错 Result window is too large §2：from+size 的代价模型，search_after/scroll 的分工
聚合查询跑几秒 大基数聚合内存爆炸 §3：聚合原理与高基数应对
MySQL 改了 ES 没变 双写失败/不一致 §4：三种同步方案与最终一致性兜底

因果链主线：ES 的查询优化不是「调参玄学」，是「一切查询都要在多个分片上并行执行」这个架构事实的推论——深度分页贵在「每个分片都要取全量再排序」，聚合贵在「每个分片先算局部再归并」，双写难在「两个系统没有同一事务」。记住「分片并行」这四个字，所有查询优化的理由都能自己推出来。

2. 深度分页：from+size 为什么 1 万行内

2.1 代价模型：每个分片都要白干

GET /orders/_search?from=10000&size=10 为什么被拒绝（默认 max_result_window: 10000）？看它在 3 分片集群上的执行路径：

sequenceDiagram
    participant C as 协调节点
    participant S1 as 分片1
    participant S2 as 分片2
    participant S3 as 分片3
    C->>S1: 取 from+size=10010 条
    C->>S2: 取 from+size=10010 条
    C->>S3: 取 from+size=10010 条
    Note over S1: 各分片按 score 排序取前 10010
    S1-->>C: 10010 条
    S2-->>C: 10010 条
    S3-->>C: 10010 条
    Note over C: 归并 30030 条，排序，丢弃前 10000 条
    C-->>C: 最终返回 10 条

因果链：from+size 的代价是 O(from+size) × 分片数——翻到第 10 万条，每个分片都要取 10 万条到协调节点排序。这不是「ES 蠢」，是分布式查询的必然：谁也不知道全局前 10 万条分布在哪个分片，只能每片都取。这个模型下「深度分页」不是功能缺失，是代价不可接受，所以 ES 用 max_result_window 直接拦住。

三个方案的定位（面试核心）：

方案 适用场景 原理 缺点
from+size 前 10000 条（翻前 100 页） 每片取全量排序再归并 深翻页 O(from+size)×分片
search_after 实时滚动（下翻 2 万+条） 记住上页最后一条的排序值，只取「比它大」的 不能随机跳页、依赖排序值稳定
scroll 全量导出（导入导出/批处理） 生成快照游标，每次取一段 快照期间数据不变、游标耗内存

search_after 与 scroll 的核心区别一句话：search_after 是「活的」（每次重新查询，新数据能看到），scroll 是「死的」（固定快照，新写入不可见）。导出数据用 scroll（要一致性快照），实时翻页用 search_after（要新数据），两者用途完全不同。

2.2 动手验证：复现报错与 search_after 翻页

观察点：from=10001 被拒绝；search_after 用上页的 sort 值无缝续翻。判定标准：亲手触发 Result window is too large 并改用 search_after 绕过，理解「不是不能翻，是不能用 from 翻」。

2.3 避坑：search_after 的排序值陷阱

坑 表现 解法
排序值有并列 重复/漏条 加唯一字段作 tie-breaker（如 _id）
排序字段有 null 排序不稳定 用 missing:_last 固定空值位置
索引时间戳排序 翻页中途新数据插入 search_after 能看见（这是特性）；需要冻结视图则用 scroll
多字段复合排序 遗漏某字段就乱序 sort 数组里所有字段都要有值

因果链：search_after 的正确性建立在「排序值能唯一定位一条记录」上——排序值并列时它只知道「比这个值大」，不知道「比这条记录靠后」，所以必须加唯一字段 tie-breaker。这个细节是面试官最爱追问的：「search_after 有重复数据怎么办？」

3. 聚合：先局部后归并

3.1 聚合的两步模型

聚合 = 每个分片先算局部结果（bucket/metrics），协调节点再归并成全局结果——与搜索的「每片取 topN 再归并」是同一架构，但代价模型完全不同：

维度 搜索 聚合
分片结果 每片 topN（量可控） 每片全部 bucket（量=基数）
归并成本 O(topN × 分片数) O(bucket 数 × 分片数)
内存压力 排序堆 bucket 全部驻留内存

聚合慢的真正原因：高基数聚合（如按 user_id 分桶）每个分片都要建几百万个 bucket 存内存，协调节点再合并——基数 × 分片数 = 内存爆炸。这就是为什么「聚合上亿日志按 IP 分桶」会 OOM。

3.2 三招应对高基数聚合

手段 机制 适用
近似聚合（cardinality） HyperLogLog，固定内存算基数 只数「多少个」，不要明细
date_histogram 按时间分桶（桶数可控） 日志趋势分析
前置预聚合 写入时把明细聚成汇总（rollup） 上亿数据的固定报表

因果链：cardinality 是近似值（误差 1% 左右）但内存恒定——HLL 用「丢了明细换固定内存」。做报表/去重计数选它；要精确值或明细，只能 rollup 或分片预计算。面试答「聚合优化」的标准句式：「高基数聚合先问三个问题——能近似吗（cardinality）、能按时间降维吗（date_histogram）、能预计算吗（rollup）」。

3.3 动手验证：看聚合的执行与内存

观察点：cardinality 返回的 value 与真实值可能有 ±1% 偏差（HLL 精度参数 precision_threshold 默认 3000）。判定标准：能解释「为什么聚合比搜索更容易打爆内存」，并说出近似聚合的代价（不精确）。

4. MySQL 与 ES 双写一致性：三种方案与最终兜底

4.1 为什么难：两个系统没有同一事务

MySQL 写成功、ES 写失败，数据就不一致了——根源是「跨系统无原子性」：MySQL 事务管不了 ES，ES 没有事务。所有方案的本质都是在回答同一个问题：怎么把「一次业务写」变成「两次可靠写」。

4.2 三种方案对比

flowchart LR
    subgraph A["方案一：应用双写"]
        App["业务应用"] -->|1. 写 MySQL| M1[(MySQL)]
        App -->|2. 写 ES（可能失败）| E1[(ES)]
    end
    subgraph B["方案二：binlog 订阅（Canal）"]
        M2[(MySQL)] -->|binlog| C2[Canal]
        C2 -->|解析/转换| MQ2[(MQ)]
        MQ2 --> W2[同步服务]
        W2 --> E2[(ES)]
    end
    subgraph C["方案三：本地消息表"]
        M3[(MySQL)] -->|同事务写消息表| T3[本地消息表]
        T3 -->|定时扫/事务消息| MQ3[(MQ)]
        MQ3 --> W3[同步服务]
        W3 --> E3[(ES)]
    end
维度 应用双写 binlog 订阅（Canal） 本地消息表
一致性时机 实时（尽力而为） 近实时（秒级延迟） 近实时
与业务解耦 ❌ 侵入业务代码 ✅ 完全解耦 半解耦（要写消息表）
对 MySQL 的感知 无 只认 binlog（支持 ROW 格式） 无
丢失风险 应用崩溃即丢 低（Canal 有 offset） 低（消息表和业务同事务）
改造量 最小（但最脆弱） 中等（Canal+MQ+同步服务） 中等
生产推荐 小流量临时方案 主流方案 无 MQ 时的替代

因果链：三种方案的演进逻辑是「把「双写」从业务代码里一步步挪出来」——双写侵入业务（方案一）→ 用 binlog 当「MySQL 的变化通知」（方案二，业务无感知）→ 用同事务消息表保证「消息不丢」（方案三，比 Canal 简单但要多写一张表）。方案二是生产主流：Canal 订阅 binlog → MQ 削峰 → 同步服务写 ES，延迟秒级、业务零侵入、Canal 挂了对主库无影响。

4.3 最终一致性兜底：对账与修复

即使有 Canal，同步服务崩溃/ES 集群故障仍会造成短暂不一致——所以生产必须加兜底层：

层 手段 说明
重试 同步失败进重试队列，指数退避 解决瞬时故障
对账 定时任务对比 MySQL 与 ES 数据量/版本号 发现长期不一致
兜底 每日全量重建索引（reindex） 修复一切历史遗留

因果链：同步方案保证「绝大多数时间一致」，对账任务保证「发现不一致」，全量重建保证「最终一定一致」——三层叠加才是完整的最终一致性。面试答双写问题，说出「Canal + 重试 + 对账 + 定期重建」四件套，比只说 Canal 高一个档次。

4.4 动手验证：体验「双写」的脆弱

观察点：ES 拒绝写入但业务侧 MySQL 已提交——「DB 成功、ES 失败」的现场，双写方案必须自己处理这种不一致（重试/补偿/消息队列）。判定标准：理解双写方案为何脆弱——两个系统任何一方抖动，都需要人工或兜底层收尾。

5. 面试应答：查询优化四连问

5.1 完整话术

面试题 回答要点
深度分页怎么做？ from+size 只能前 1 万条（代价 O(from+size)×分片）；实时滚动用 search_after（记住排序值续翻）；全量导出用 scroll（快照游标）
search_after 和 scroll 区别？ search_after 重新查询（能看到新数据）、不能跳页；scroll 固定快照（数据冻结）、适合导出
聚合慢怎么办？ 高基数=内存爆炸；先问能近似吗（cardinality/HLL）、能时间降维吗（date_histogram）、能预聚合吗（rollup）
MySQL 与 ES 怎么同步？ 生产用 binlog 订阅（Canal→MQ→同步服务），加重试+对账+定期重建兜底；双写只适合小流量

5.2 深挖：与 MySQL 分页/主从的对照（跨篇联动）

维度 MySQL ES
分页 limit 深翻页要扫全表（MySQL 索引原理与实战） from+size 深翻页每片全量取（代价模型相同）
大数据分页正解 游标/书签（where id > last） search_after（排序值书签）
异步同步 主从 binlog 复制（MySQL 高可用） Canal 订阅 binlog 同步 ES
一致性保障 半同步/GTID 重试+对账+重建

一句话：MySQL 深分页用「书签」绕开 LIMIT 扫描，ES 用 search_after 绕开 from+size——「记住上次的位置，而不是从头上重新数」是分页优化的共同思想；ES 的 Canal 同步本质上就是「把 MySQL 的 binlog 复制架构搬到了 ES 侧」。跨库答出这层对照，面试是明显的差异化加分。

6. 总结

6.1 面试速答表

面试题 一句话答案
为什么 ES 分页限制 1 万条？ 深度分页代价 O(from+size)×分片数，每片白取全量再归并，干脆限制
search_after 怎么用？ 用上页最后一条的排序值续翻，实时数据可见；排序加唯一字段 tie-breaker
scroll 适合什么？ 全量导出/批处理，固定快照游标，游标期间数据不可变
聚合为什么慢？ 高基数 bucket 全驻内存，基数×分片数爆炸
高基数聚合怎么办？ cardinality 近似、date_histogram 降维、rollup 预聚合
MySQL→ES 怎么同步？ Canal 订阅 binlog → MQ → 同步服务；重试+对账+定期重建兜底
双写方案为什么不好？ 业务侵入 + 两个系统无同一事务，任何一方失败都要手工收尾

6.2 实战避坑表

症状 原因 处理
Result window is too large from+size 超 1 万 改 search_after/scroll，不要只调 max_result_window（治标不治本）
search_after 翻页重复/漏条 排序值并列 sort 加唯一字段 tie-breaker
聚合 OOM 高基数 bucket 换 cardinality/date_histogram/rollup
ES 数据少一条 双写/同步失败 查重试队列；对账任务对比；必要时重建索引
同步延迟大 MQ 积压/同步服务瓶颈 监控消费 lag，扩同步服务并发
Canal 挂了对主库的影响 无（旁路解析 binlog） 放心重启，offset 续传

6.3 工具速查表

工具/API 用途
max_result_window（settings） 分页窗口上限，生产不建议调大
search_after / scroll 深翻页两件套（活视图/快照）
cardinality / date_histogram 聚合降内存两招
_cat/nodes?v&h=name,heap.percent 聚合 OOM 前观察堆内存
Canal（阿帕奇/阿里） binlog 订阅，MySQL→ES 主流同步件
对账任务 + 重建索引 最终一致性兜底两层

6.4 下一篇预告

查询篇解决「怎么查得对」，下一篇《分布式事务：从 2PC 到 Seata》解决「怎么写得对」——MySQL 事务管不了 ES，同样管不了多个微服务：2PC 为什么是「协调者的单点赌博」、TCC 为什么是「业务三阶段」、Saga 为什么是「一条补偿链」，以及 Seata 的 AT 模式怎么用全局锁做到「业务无侵入」——分布式一致性的最后一块拼图。
