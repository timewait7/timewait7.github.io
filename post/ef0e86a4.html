一、跑起来之前（环境准备）

1.1 硬件要求

配置项 要求 说明
内存 16GB 及以上（Docker 至少分 8GB） 17 个中间件容器 + 7 个微服务 JVM 同时运行；本文档实测环境为 48GB 机器 / Docker 分配 23GB
CPU 4 核及以上 8 核更流畅
磁盘 40GB 可用 镜像 + 数据卷

1.2 软件要求

逐条执行右侧命令，输出与”期望结果”一致才继续。

软件 版本要求 校验命令 期望结果
Docker Desktop 24+ docker --version Docker version 24 及以上
Docker Compose v2+ docker compose version Docker Compose version v2 及以上
JDK 17 java -version 显示 17（若为其它版本，启动脚本会自动探测 JDK 17 路径）
Maven 3.8+ mvn -version Java version: 17.x（若显示 8，检查 ~/.mavenrc 里的 JAVA_HOME）
Node.js（前端） 18+ node -v && npm -v 能输出版本号即可
curl 任意 curl --version 能输出版本号即可

⚠️ Docker Desktop 必须先打开：执行 docker info 能输出信息才算就绪；报 Cannot connect to the Docker daemon 就是没启动。

二、五步启动（复制粘贴即可）

步骤 做什么 大致耗时 完成标志
第 1 步 启动 17 个中间件 首次 5-10 分钟；之后 1-2 分钟 docker compose ps 核心中间件 healthy
第 2 步 编译打包 1-3 分钟 BUILD SUCCESS
第 3 步 启动 7 个微服务 1-3 分钟 7 个服务健康 + Nacos 注册 7 个
第 4 步 启动前端 1 分钟 浏览器能打开登录页

2.1 第 1 步：启动全部中间件（17 个容器）

启动完成后查看状态：

预期看到 17 行容器（elasticsearch8 / node-exporter / influxdb / prometheus / grafana / mysql8 / mysql-slave / redis7 / rocketmq-namesrv / skywalking-oap / minio / nacos2 / rocketmq-broker / seata-server / skywalking-ui / sentinel-dashboard / zookeeper），其中 mysql / mysql-slave / redis / nacos / es / minio / zookeeper / seata 显示 healthy 即可继续。

三个必须知道的点：

  1. 首次启动 MySQL 会初始化数据库（自动执行 deploy/sql/ 下 01-04 四个脚本，创建 11 个业务库），耗时 3-5 分钟；从库首次初始化还要从主库拉全量快照（更久）。以后启动复用数据卷，秒级完成。
  2. 若 docker compose up -d 中途报错 network ... not found：这是 Docker 网络重建竞态，再执行一次 docker compose up -d 即可；仍失败就对报错容器执行 docker compose up -d --force-recreate <容器名>。
  3. rocketmq-broker / sentinel / skywalking-oap 三个容器长期显示 unhealthy 属正常：它们的 healthcheck 命令在镜像里不存在（镜像无 netstat/curl），是已知缺陷而非故障；功能验证方法见 3.2 与 4.3。

📌 本机 MinIO 的宿主端口是 9900（API）/ 9901（Console），不是官方默认的 9000/9001——因为 9000/9001 被 gateway 和 user 服务占用。该调整在 deploy/docker/docker-compose.override.yml 中定义，docker compose 会自动叠加，无需手工干预。

五、常见问题（小白高频）

5.1 启动类问题

现象 原因 / 解决
Cannot connect to the Docker daemon Docker Desktop 没启动，打开它再执行
docker compose up -d 报 network ... not found Docker 网络重建竞态，再执行一次；仍失败 docker compose up -d --force-recreate <报错容器>
端口被占用（Address already in use / lsof -i :9000） 有旧进程在跑：先 bash deploy/scripts/start-full.sh stop，确认 docker compose ps 为空再启动
首次启动卡在 MySQL 很久 正常，initdb 需要 3-5 分钟，docker compose logs -f mysql8 可看进度
微服务启动报连不上 Nacos 中间件未就绪，等 nacos 容器 healthy 再执行第 3 步
无效的目标发行版: 17 系统 java 不是 17：检查 JAVA_HOME（启动脚本会自动找 Homebrew 的 JDK 17）
内存不足 / 容器反复重启 Docker Desktop → Settings → Resources 把内存调到 8GB+；关闭其它大内存程序

5.2 已知限制（当前版本，暂未修复）

限制 现象 原因
协同编辑经网关不可用 编辑器页面的实时协同连接失败（401） 网关 AuthGlobalFilter 只从 Authorization 头取 token，而浏览器 WebSocket 只能把 token 放在 ?token= 查询参数；且 collab 的 Netty 只处理精确路径 /ws，前端用的是 /ws/{docId}（直连 ws://localhost:9003/ws 可握手成功，说明 Netty 本身正常）。文档编辑、保存、版本历史等非协同功能不受影响
文件签名 URL 返回 403 调 /api/file/url/{fileId} 提示”无权限访问该文件” RBAC 权限种子里没有 file:download 权限，且新注册用户不分配默认角色。分片上传、秒传、合并（verify-infra.sh ② 的前几项）均正常
从库复制在重建容器后中断 SHOW REPLICA STATUS 两个 Running 为 No relay log 以容器 hostname 命名，容器重建后无法恢复。修复见 5.3
三个容器长期 unhealthy rocketmq-broker / sentinel / skywalking-oap healthcheck 命令在镜像里不存在；功能正常，验证方法见 3.2

5.3 从库复制断了怎么修

适用场景：docker compose up -d --force-recreate mysql-slave 重建过从库、或从库日志出现 Failed to create or recover replication info repositories。

根治办法（需改 compose 后重建从库）：给 mysql-slave 的 command 增加 --relay-log=zeus-slave-relay-bin，relay log 名不再随 hostname 变化。

5.4 停止与重启

数据卷保留时，重新启动后用户、文档、文件数据都还在。

6.2 kubectl apply 顺序

顺序原则：Namespace → ConfigMap/Secret → Service → StatefulSet/Deployment → HPA → Ingress。Service 先于工作负载，确保 Headless Service 就绪供 StatefulSet 解析 Pod DNS。

6.3 副本数规划（deployment.yaml）

服务 副本 端口 说明
gateway 2 9000 网关，NodePort 30000 对外
user 2 8001 鉴权
doc 3 8002 核心服务副本最多
collab 3 (StatefulSet) 8003 有状态，稳定网络标识
search 2 8004 ES 检索
file 2 8005 MinIO
audit 2 8006 审计

⚠️ K8s 集群内端口与本地 JVM 端口不同，勿混用：本地一律 900x（collab 另有 9013），集群内除 gateway（9000）外均为 80xx。

6.4 资源限制与探针（deployment.yaml）

就绪探针 initialDelay 60s < 存活探针 90s，避免启动慢被误杀。

6.6 collab 为何用 StatefulSet（statefulset.yaml 注释）

协同服务 Netty WebSocket 维持有状态长连接，会话（光标、在线用户、OT 操作序列）存 Pod 本地内存。StatefulSet 提供：

  1. 稳定网络标识：Pod 名 collab-0/1/2，DNS 可解析，客户端重连路由到同一 Pod 恢复会话；
  2. 稳定持久存储：每 Pod 独立 PVC，会话快照不丢；
  3. 有序启停：启动 0→1→2，停止 2→1→0，避免同时重启致全部会话中断。

Gateway 通过一致性哈希按 docId 路由到固定 collab Pod。

6.7 HPA 自动伸缩（hpa.yaml）

伸缩公式：目标副本 = ceil(当前副本 × 当前CPU% / 目标CPU%)。前置条件：安装 Metrics Server。

WebSocket 反代核心：

关键点：

  1. proxy_http_version 1.1：WebSocket 依赖 HTTP/1.1 Upgrade 机制；
  2. $connection_upgrade 映射表：$http_upgrade 为 websocket 时 Connection=upgrade，否则 close；

6.11 优雅停机

应用关闭流程：

  1. K8s 发送 SIGTERM（terminationGracePeriodSeconds: 30，gateway 60s）；
  2. Spring Boot 优雅停机，拒绝新请求；
  3. 线程池 waitForTasksToCompleteOnShutdown=true，等待队列任务完成（最多 30s）；
  4. Feign/Netty 连接关闭，Pod 退出。

若 30s 内未退出，K8s 发 SIGKILL 强制终止。gateway 设 60s 因需等长连接断开。
