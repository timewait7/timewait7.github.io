一条 SQL 的六层成本账：架构不是画流程图

Posted on 2026-10-24 In 数据存储 Word count in article: 5.7k Reading time ≈ 21 mins.

架构图的价值不在于「分了几层」，而在于每层各花多少时间。一条看起来朴素的 SELECT，从建立连接到把字节吐回客户端要过六道关，这六道的量级差着三个数量级：连接是毫秒级，解析是微秒级，页访问是百纳秒级，落盘是几十微秒级。搞不清钱花在哪一层，所有优化都是蒙。

本文用一条线索把六层串起来：先看清每层的成本量级，再判断你的慢查询卡在第几层，最后只改那一层。文中所有数字都在 MySQL 8.0.46 容器里实测，表是上一篇那张 100 万行的 t1。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账（本文） → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

与前后篇的关系：① 给了你「页」这把尺子，本文用它给每一层上秤；本文测出的「优化器把等值条件默认当 10%」，正是 ④ 里直方图要修的那个估算偏差。原理的完整推导回指站内《MySQL 深度解析》第 1 章，本文只关心成本。

1. 六层成本：量级差三个数量级

1.1 全景：一条 SQL 的六道关

flowchart LR
    C["1 Connection<br/>TCP + auth<br/>~ms"] --> P["2 Parser<br/>lex + syntax<br/>~us"]
    P --> O["3 Optimizer<br/>pick access path<br/>~us"]
    O --> E["4 Executor<br/>call handler API<br/>~us"]
    E --> B["5 Buffer Pool<br/>16KB page<br/>~100ns per page"]
    B --> D["6 Disk<br/>random read<br/>~50-100us"]
层 干什么 成本量级 你能改什么 详见
连接 TCP 握手、认证、会话初始化、权限装载 毫秒级 连接池、长连接、减少 TLS 往返 ⑪
解析 词法、语法、预处理（表/列是否存在、权限） 微秒级 基本改不了，只能减少语句数 —
优化 选索引、定 JOIN 顺序、估算成本 微秒级 统计信息、SQL 写法、索引结构 ④
执行 按执行计划逐行调用存储引擎 微秒级 减少返回行数与调用次数 ③
Buffer Pool 找到页、加锁、读记录 百纳秒级/页 索引、减少回表、覆盖索引 ③
磁盘 真正读一次页 几十微秒/次 加内存、冷热分离、刷盘策略 ⑦

这张表的用法很直接：你的慢查询卡在哪一行，就只优化那一行。一个 40ms 的查询，如果 35ms 花在磁盘上，你加索引是没用的；如果 35ms 花在 Buffer Pool 上（逻辑读太多），你加内存也没用。

1.2 实测：把六层的数字钉在墙上

同一个容器、同一张表（100 万行、3430 页、默认 128MB 池），把不同「深度」的语句各跑 200 次，取服务端 performance_schema 的平均耗时：

语句 经过哪几层 实测平均耗时 备注
SELECT 1 连接（已复用）+ 解析 + 优化 + 执行 10.8 µs 不碰任何表的纯开销
SELECT id FROM t1 WHERE id = ? 上面全部 + Buffer Pool 3~4 页 21.3 µs 主键等值
SELECT SUM(user_id) … user_id BETWEEN 1 AND 1000 + 索引范围扫 1 万行（覆盖） 1.17 ms 53 次逻辑读
同上但 SELECT SUM(LENGTH(c)) + 回表 1 万次 3.33 ms 31223 次逻辑读
SELECT COUNT(*) FROM t1 WHERE c = ? + 全表扫 100 万行 61.3 ms（Table scan 部分） 3430 页

把这张表竖着看，能读出三个结论：

  1. 固定开销约 11 微秒。这是 MySQL 处理任何一条语句的地板价（解析 + 优化 + 派发），它跟你查什么无关。所以「一条 SQL 发一次」的循环写法天生亏，批量接口省的不是索引，是这 11 微秒 × N。
  2. 从 21 µs 到 61 ms，差 2900 倍，而这一段的差别全部是「逻辑读多少个页」。索引能做的，就是把 3430 页压到 4 页。
  3. 同一份数据、同一批结果，SUM(user_id) 和 SUM(LENGTH(c)) 差 2.8 倍，只因为后者需要回表。这一条是第 3 节的主角。

1.3 深挖：为什么连接层贵得不成比例

在一个已复用的连接上执行 SELECT 1 是 10.8 微秒，而新建一个连接要付：三次 TCP 握手、认证往返（caching_sha2_password 要额外一轮）、会话变量初始化、权限表装载、线程创建。这一串在服务端是几毫秒，而它换来的是 11 微秒的执行——连接成本比执行成本高两个数量级。

实测对比（macOS + Docker Desktop，注意这个数字包含容器与客户端进程启动）：

单次 30.7 ms 里绝大部分是 docker exec 与 mysql 客户端进程启动，服务端只占几毫秒——这个比例本身才是重点：真正的业务代码里没有 docker exec，但同样要付客户端到服务端的网络 RTT × 2~3 次。所以「短连接」在任何网络有延迟的环境里都是灾难。

这也是连接池存在的原因，而且能解释一个常见误判：连接池打满时，接口耗时会突然从毫秒跳到秒级，因为请求在等一个「贵两个数量级」的资源。⑪ 会专门算这笔账，这里只需记住：连接是六层里唯一「用不起就别用」的一层。

再往下一层，是站内《进程与线程：从模型到调度》里算过的账：在 MySQL 里每个连接对应一个服务端线程，线程一多，上下文切换的成本就开始吃掉 CPU。线程数不是越多越好，连接池不是越大越好，两个结论来自同一个机制。

1.4 动手验证：量出你的六层

预期观察点：SELECT 1 的平均值落在 1030 µs（取决于机器与是否开 performance_schema 全部消费者），主键等值比它高 50%100%。

判定标准：

  • 两者差值在微秒级 → 你的瓶颈不在这层，往 ③ 走；
  • SELECT 1 就超过 1 ms → 先查网络 RTT 和连接池（⑪），不要碰 SQL；
  • 平均值与 P99 差 10 倍以上 → 有排队或锁等待，去 ⑥。

2. Server 层：解析、优化、执行

2.1 解析器：只做「这句话合法吗」

阶段 做什么 典型的失败
词法分析 把字符串切成 token（关键字、标识符、常量） 引号 / 反引号混用
语法分析 按语法规则建出语法树 GROUP BY 少列、ON 写错位置
预处理 检查表、列、别名是否存在，检查权限 Unknown column、权限不足

这三步是纯 CPU 操作，成本在微秒级，没有优化空间——除非你减少语句数量。一个常见的反例是在循环里拼 SQL 逐条执行，等于把 11 微秒的地板价乘以 N。

顺带说一个 8.0 的变化：查询缓存在 8.0 已被整体移除（上一篇实测 query_cache% 变量为空集），所以「同样的 SQL 第二次会变快」这句话在 8.0 上只可能来自 Buffer Pool 或操作系统缓存，不可能是 SQL 文本缓存。

2.2 优化器：六层里唯一「做决策」的地方

优化器不执行查询，它只做一件事：在若干候选执行计划里挑成本最低的那个。成本由三部分构成——读页的 IO 成本、评估条件的 CPU 成本、以及行数估算。

实测一条没走索引的等值查询，EXPLAIN FORMAT=JSON 输出如下（关键字段已标注意义）：

三个数字要读懂：

  • query_cost = 100520.60：不是毫秒，是内部成本单位。它只在自己和自己比的时候有意义。
  • filtered = 10.00：优化器认为这个等值条件能筛掉 90% 的行——因为它对 c 列没有任何统计信息（没索引、没直方图），只能用内置先验：等值条件的选择性按 10% 估。
  • rows_produced_per_join = 99663：996631 × 10%。而这条 SQL 的真实返回是 1 行——估算偏了 10 万倍。
flowchart TD
    A["SQL parsed, tree ready"] --> B["Enumerate candidate plans<br/>index scan / range / full scan"]
    B --> C["Estimate rows per plan<br/>stats or default 10%"]
    C --> D["Estimate cost<br/>read_cost + eval_cost"]
    D --> E["Pick lowest cost plan"]
    E --> F["Hand plan to executor"]
    C -.->|"no stats: filtered = 10%"| G["Estimate can be off<br/>by 100000x"]

这个 10.00 是理解「优化器为什么会选错索引」的钥匙：不是优化器笨，是它拿到的先验有多粗糙。④ 会用它自己的数据证明——同一张表加上 100 个桶的直方图后，filtered 从 10.00 变成接近真实的比例，执行计划随之改变。

优化器还有几个固定的成本常数（读一页的成本、评估一行的成本、比对一次的成本），这套常数源自早期硬件假设（随机 IO 昂贵、CPU 单核），而不是你机器上的真实延迟。你的 NVMe 盘随机读比 HDD 快一到两个数量级，但在优化器眼里两者一视同仁——这是成本模型落后于硬件的经典案例，也是为什么生产上偶尔要 FORCE INDEX，那是在用人的判断纠正模型的先验。

2.3 执行器：按计划走，不动脑

执行器拿到执行计划后，逐行调用存储引擎的 handler 接口（index_read、rnd_next、index_next 等），每调用一次至少涉及一次页访问。

维度 优化器 执行器
职责 决定「怎么查」 负责「照着查」
消耗 CPU（估算） CPU + Buffer Pool 访问
出错表现 走错索引、JOIN 顺序差 回表太多、函数调用过多
优化手段 统计信息、SQL 改写、FORCE INDEX 覆盖索引、减少行数、减少列

一个实用的判据：EXPLAIN 里的 rows 是优化器的估算，EXPLAIN ANALYZE 里的 actual rows 是执行器的实际。两者差 10 倍以上，问题在优化器（统计信息）；两者接近但都很大，问题在执行路径（索引没覆盖住）。

2.4 动手验证：看穿优化器的估算

预期观察点：第 1 步会显示 Table scan ... rows=1e+6 且 Filter 估算 rows=100000，实际只返回 1 行；第 2 步的 filtered 是 10.00；第 3 步建索引后 access_type 变成 ref，rows_examined_per_scan 变成个位数。

判定标准：filtered 恰好等于 10.00、25.00、50.00 这类整数 → 说明这个条件完全没有统计信息，纯靠先验；这是 ④ 里加直方图的第一个信号。

3. 存储引擎层：Buffer Pool 与磁盘

3.1 一次读的三种结局

flowchart TD
    R["Executor asks for page #42"] --> H1{"In Buffer Pool?"}
    H1 -- yes --> M["Read record from memory<br/>~100ns"]
    H1 -- no --> H2{"In OS page cache?"}
    H2 -- yes --> CP["Copy page into pool<br/>memory to memory"]
    H2 -- no --> IO["Disk read<br/>~50-100us"]
    IO --> CP --> M

三种结局在监控里都表现为一次逻辑读，区别只在 Innodb_buffer_pool_reads 是否增加。这解释了上一篇那个反直觉的结论：命中率 99.9% 只说明第三种结局很少发生，不说明第一种结局次数少。

结局 逻辑读 +1 物理读 +1 典型耗时 谁负责
Buffer Pool 命中 是 否 ~100 ns 索引设计
Page cache 命中 是 是（InnoDB 算一次读，但没落到盘） ~1 µs 内存与 O_DIRECT
真落盘 是 是 50~100 µs 硬件 + 缓存策略

3.2 回表：逻辑读的放大器

二级索引只存索引列 + 主键值。当查询需要索引里没有的列时，必须拿主键回聚簇索引再查一次——这就是回表。它的代价不是「多一次查找」，而是把一次顺序的索引扫描变成一万次分散的页访问。

实测（1 万行结果集，同一张表，只改 SELECT 的列）：

写法 是否回表 逻辑读 实际耗时 扫描行数
SELECT SUM(user_id) WHERE user_id BETWEEN 1 AND 1000 否（覆盖索引） 53 1.17 ms 10,000
SELECT SUM(LENGTH(c)) WHERE user_id BETWEEN 1 AND 1000 是 31,223 3.33 ms 10,000 
flowchart LR
    subgraph Covering["Covering index scan"]
        I1["idx_user_id leaf pages<br/>53 pages"] --> R1["Answer"]
    end
    subgraph BackTable["Index scan + back to table"]
        I2["idx_user_id leaf pages"] --> P2["clustered index<br/>10000 random page visits"]
        P2 --> R2["Answer"]
    end

同一批 1 万行，逻辑读差 589 倍，耗时却只差 2.8 倍。这个不对称是本文最值得记住的一课。

3.3 深挖：为什么逻辑读涨 589 倍，时间只涨 2.8 倍

因为这张表整表都在内存里（3430 页 vs 8192 页的池）。回表增加的 3 万次页访问全部命中 Buffer Pool，每次约 100 纳秒（3.33 ms ÷ 31223 ≈ 0.107 µs，其中还含排序等其他开销），所以放大了 589 倍只换来 2.8 倍耗时。

换算一下两者的单价：

操作 单价（量级） 换算
逻辑读（命中 Buffer Pool） ~100 ns 1 倍
物理读（NVMe SSD 随机） 50~100 µs 500~1000 倍

这就是「回表很慢」这句话的真实含义：只有在页不在内存时，回表的逻辑读放大才会等比例变成时间。生产库几百万行、Buffer Pool 装不下时，那 3 万次访问里有相当一部分要落盘，3.33 ms 会变成几十毫秒——同一份 SQL，本地测 3 ms，线上 80 ms，差的就是这一层。

所以「加索引 / 改覆盖索引」的收益是条件性的：数据全在内存时，它省的是 CPU 和锁竞争；数据装不下时，它省的是磁盘 IO。判断属于哪种，看 Innodb_buffer_pool_reads 有没有涨——这是上一篇那把尺子的第二次使用。

站内《文件系统与磁盘 IO》讲过 page cache 与 fsync 的成本结构，放在这里就是第 6 层的账：物理读的钱一次几十微秒，而每次 fsync 还要再付一遍。一次事务提交至少一次日志落盘，2 万 TPS 就是每秒 2 万次 fsync——⑦ 会算这笔账，并解释为什么 innodb_flush_log_at_trx_commit=1 换来的性能损失是「必需的成本」而不是「可以调的参数」。

3.4 动手验证：把回表的账算在自己机器上

预期观察点：A 的逻辑读在两位数到三位数，B 跳到四位数甚至五位数（本篇 53 → 31223），而 B 的 actual time 只涨两三倍。

判定标准：

  • B/A 的逻辑读比 > 10 → 这张表上回表很贵，优先考虑覆盖索引（③）；
  • 若 B 的 actual time 涨幅接近逻辑读的涨幅 → 说明有物理读参与，池不够（⑦）；
  • 若两者耗时都很大但逻辑读很小 → 你在等锁，去 ⑥。

再补一个「把缓存拿掉」的对照，体会第 6 层的真实价格：

判定标准：物理读开始随查询增长 → 你测到的是「线上同款」成本；物理读恒为 0 → 本地结论只能解释 CPU 与逻辑读，别拿它推生产。

4. 成本账的实战用法

4.1 同一 SQL，数据量不同，钱花在不同层

以「按用户查订单列表」为例，WHERE user_id = ? ORDER BY create_time LIMIT 20，三种数据规模下的成本分布完全不同：

数据量 索引情况 逻辑读 物理读 主要成本在 该做什么
10 万行 有 user_id 索引 个位数 0 Server 层（解析 + 优化） 别优化 SQL，优化调用次数
100 万行 有索引但需排序 几十 ~ 几百 0~少量 排序 / 临时表 让索引顺序覆盖 ORDER BY（③）
1000 万行 无合适索引 数万 数千 磁盘 建复合索引，把排序也吃掉（③④）

同一个接口，三套优化方案。这也是为什么「照着别人的 my.cnf 抄」必然失败：他调的是他那一层的钱。

4.2 判定表：症状 → 层 → 手段

症状 大概率在哪层 第一件事 别做什么
简单查询也要几十毫秒 连接 / 网络 查 RTT、连接池等待（⑪） 别加索引
SELECT 1 就慢 连接 / Server 层 看 Threads_running、CPU 别改 SQL
行数少但耗时高 优化器选错 / 锁 EXPLAIN ANALYZE 看 actual rows 别加内存
扫行数远超返回行数 索引 / 执行器 看 filtered、回表 别调参数
逻辑读高、物理读也高 Buffer Pool 查命中率、池大小（⑦） 别先改刷盘参数
逻辑读高、物理读为 0 索引设计 覆盖索引、减少回表（③） 别加内存

4.3 动手验证：定位「哪层吃掉 80%」

预期观察点：第 1 步的 avg_rows_examined / avg_rows_sent 如果大于 100，说明读了大量用不上的行；第 3 步的输出是树形的，每一行末尾的 actual time=a..b 是累计时间，父节点的总时间一定不小于子节点，找 b 增量最大的那一层。

判定标准：

  • 最大耗时在 Table scan / Index scan 节点 → 逻辑读问题（③）；
  • 最大耗时在 Sort / Temporary table 节点 → 排序没吃到索引（③④）；
  • 各节点都很快但总耗时很高 → 时间花在节点之外：锁（⑥）、网络、或客户端（⑪）。

5. 总结

5.1 面试速答表

面试题 一句话答案
一条 SQL 从客户端到返回经过哪些阶段 连接 → 解析（词法/语法/预处理）→ 优化（选执行计划）→ 执行（调 handler）→ Buffer Pool → 磁盘
MySQL 里哪一层最贵 看情况：短连接时连接层是毫秒级，比执行贵两个数量级；大表查询时磁盘是几十微秒一次，最贵
EXPLAIN 的 rows 准确吗 是优化器的估算，依据统计信息；没有统计时用内置先验（等值条件按 10% 估），可能偏 10 万倍
优化器的成本单位是毫秒吗 不是，是内部成本单位，只在计划之间比较有意义
EXPLAIN 和 EXPLAIN ANALYZE 的区别 前者给估算（rows、cost），后者给实际（actual time、actual rows）
回表为什么慢 把一次索引扫描变成 N 次分散的聚簇索引页访问；N 次里有多少物理读，才决定它有多慢
为什么本地测 3ms、线上 80ms 本地页全在 Buffer Pool，逻辑读单价 100ns；线上要落盘，物理读单价 50100µs
覆盖索引一定更快吗 数据全在内存时省的是 CPU 与锁；装不下时省的是磁盘 IO；两种收益量级不同

5.2 实战避坑表

症状 原因 处理
给 40ms 的查询加索引没用 时间花在连接或锁，不在页访问 先看 SELECT 1 的耗时与 Threads_running
filtered 永远是 10.00 该列没有统计信息，优化器用先验 建索引或加直方图（④）
优化器明显选错索引 成本模型常数落后于 SSD，或统计过期 ANALYZE TABLE，必要时 FORCE INDEX 并记录原因
加了覆盖索引性能没变 瓶颈在排序 / 临时表 / 锁 看 EXPLAIN ANALYZE 里最重的节点
本地压测完美，上线抖动 本地全命中，线上有物理读 按生产数据量造数，或把池调到装不下
盲目相信 query_cost 绝对值 它只是内部单位 只用于同一实例内比较计划

5.3 工具速查表

工具 看什么 判定标准
performance_schema.events_statements_summary_by_digest 服务端每条语句的平均耗时、扫行数 平均耗时与客户端墙钟差 10 倍 → 网络或排队
EXPLAIN FORMAT=JSON filtered、rows_examined_per_scan、read_cost/eval_cost filtered 是 10.00 这类整数 → 无统计信息
EXPLAIN ANALYZE 每个迭代器的 actual time 与 actual rows 估算与实际差 10 倍 → 优化器问题；都大 → 索引问题
Innodb_buffer_pool_read_requests / _reads 逻辑读 / 物理读 物理读占比 > 5% → 池不够
events_waits_summary_global_by_event_name 各类等待的总耗时 锁等待 / IO 等待占比 → 定位到层
Threads_running 并发执行中的线程 持续 > CPU 核数 → 在排队，不是算力不足

5.4 实操建议

  1. **先量 SELECT 1**。这个数字代表你这套环境的地板价，任何低于它的优化目标都是幻想。
  2. 把「六层」当成排查清单，每次慢查询按顺序排除：连接 → 解析 → 优化 → 执行 → 池 → 磁盘，一次只排除一层。
  3. 记住三个单价：逻辑读 100 ns、物理读 ~50100 µs、连接 ~几毫秒。三者差两个数量级，你的优化收益上限由它们决定。
  4. 遇到「估算与实际差 10 倍」，先怀疑统计信息，再怀疑索引——filtered 是整数就是证据。
  5. 每次改完，回到上一篇的基线表加一行：逻辑读、物理读、耗时。没有这三列，你无法证明自己改对了。
