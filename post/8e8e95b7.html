InnoDB 内存与刷盘：物理 IO 的钱花在哪

Posted on 2026-10-25 In 数据存储 Word count in article: 4.4k Reading time ≈ 16 mins.

前面六篇都在省「读」，这一篇看「写」。一次 COMMIT 背后至少两次落盘：redo 一次、binlog 一次。这两次 fsync 值多少钱？实测下来，把 innodb_flush_log_at_trx_commit 从 1 改成 0，单行插入 TPS 从 734 涨到 151,035——206 倍。而代价是：kill -9 之后，刚提交的 2000 行一行都不剩。

这就是本文要算的账：性能与持久性的兑换率。文中所有数字都在 MySQL 8.0.46 容器里实测，kill -9 是真杀进程后重启验证的。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘（本文） → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

与前后篇的关系：① 测到「冷启动物理读 1046、热缓存 0」，本文解释那批物理读是怎么被 redo 与 Buffer Pool 安排的；本文的 binlog 落盘是 ⑧ 复制的源头；本文的「丢数据代价」是 ⑨ 备份策略的定价依据。

1. 写路径：一次 commit 写了几次盘

1.1 WAL：先写日志，再慢慢写数据

InnoDB 改数据时不直接改磁盘上的页，而是：

  1. 把页读进 Buffer Pool（内存），在内存里改；
  2. 把「改了什么」写进 redo log（顺序写、小）；
  3. 提交时确保 redo 落盘 → 事务就算持久了；
  4. 脏页由后台线程慢慢刷回磁盘（随机写、慢）。
flowchart LR
    C["COMMIT"] --> RB["redo log buffer<br/>memory"]
    RB -->|"write()"| OS["OS page cache"]
    OS -->|"fsync()"| RD["redo file<br/>#innodb_redo"]
    C --> BB["binlog buffer"]
    BB -->|"write()"| BOS["OS page cache"]
    BOS -->|"fsync()"| BF["binlog file"]
    BP["Buffer Pool dirty pages"] -->|"background flush"| DF["data files .ibd"]

WAL 的价值：把「随机写数据页」变成「顺序写日志」。一次事务改 3 个页，日志可能只有 200 字节；如果不写日志直接刷脏页，就要 3 次随机 IO。

代价是：同一份数据写了两遍（redo + 数据页），而且 redo 也要落盘。所以「写放大」在数据库里是常态，不是 bug。

1.2 两阶段提交：redo 与 binlog 必须一致

redo 是 InnoDB 的，binlog 是 Server 层的，两者独立。为了让「主库数据和从库/备份的 binlog」一致，提交要走两阶段：

sequenceDiagram
    participant C as Client
    participant S as Server
    participant I as InnoDB
    C->>S: COMMIT
    S->>I: prepare (写 redo, 标记 prepare)
    I-->>S: ok
    S->>S: 写 binlog + fsync
    S->>I: commit (redo 标记 commit)
    I-->>C: ok

崩溃恢复时的判定很简单：

崩溃时机 redo 状态 binlog 状态 恢复动作
prepare 之前 无 无 回滚
prepare 之后、binlog 之前 prepare 无 回滚
binlog 之后、commit 之前 prepare 有 提交（redo 补 commit）
commit 之后 commit 有 无需动作

这就是「binlog 写成功但没 commit」也能恢复的原因。理解了这张表，⑧ 的主从一致性、⑨ 的 PITR 都不会再有疑问。

1.3 一次 commit 的 fsync 次数

配置 redo fsync binlog fsync 一次 commit 的 fsync 次数 丢失风险
flush=1, sync_binlog=1 每次提交 每次提交 2 不丢
flush=2, sync_binlog=1 每秒（后台） 每次提交 1 掉电丢 ~1s
flush=1, sync_binlog=0 每次提交 由 OS 决定 1 掉电丢 binlog
flush=2, sync_binlog=0 每秒 由 OS 决定 ~0 掉电丢 ~1s
flush=0, sync_binlog=0 每秒（且不 write） 由 OS 决定 0 进程崩溃就丢

实测默认值（8.0.46）：innodb_flush_log_at_trx_commit=1、sync_binlog=1、innodb_flush_method=fsync、innodb_redo_log_capacity=100MB、binlog_group_commit_sync_delay=0。

1.4 动手验证：数一数你的 fsync

预期观察点：单次插入的耗时应该在 0.5~2 毫秒量级（其中绝大部分是两次 fsync 的等待），而不是微秒级。

判定标准：

  • 3000 次插入 < 0.5 秒 → 你机器上 fsync 极便宜（内存盘/云盘缓存），要换真实磁盘复测；
  • 单次 > 5 毫秒 → 磁盘或虚拟化层很慢，生产上这样的盘撑不住高并发写入；
  • 与 1.2 节的 TPS 阶梯对照，确认你测的是「持久性成本」而不是 SQL 解析。

2. flush / sync 三档：性能与持久性的兑换率

2.1 实测 TPS 阶梯

固定 3000 次单行插入（每次独立事务），只改两个参数：

配置 耗时 TPS 相对基线 数据安全
flush=1, sync_binlog=1（默认） 4.086 s 734 1.0× 提交即持久
flush=2, sync_binlog=1 1.529 s 1,962 2.7× 掉电丢 ≤1s
flush=2, sync_binlog=0 0.128 s 23,443 32× 掉电丢 ≤1s（含 binlog）
flush=0, sync_binlog=0 0.020 s 151,035 206× 崩溃即丢

三个必须读出来的结论：

  1. sync_binlog 比 flush_log 更贵。第 2 行到第 3 行只改了 sync_binlog，TPS 从 1,962 跳到 23,443（12 倍）；而第 1 行到第 2 行改 flush_log 只有 2.7 倍。原因：binlog 的 fsync 是每次提交都做（sync_binlog=1），而 redo 在 flush=2 时交给后台每秒一次。
  2. flush=0 和 flush=2 完全不是一个量级。flush=2 至少把 redo write() 到了操作系统，进程崩溃不丢；flush=0 连 write 都不做，数据还在 MySQL 自己的内存里。
  3. 2.1 的性能是「买来的」，价格就是下面这张表。

2.2 实测：kill -9 之后还剩多少

做法：提交 N 行 → 立刻 docker kill -s KILL → 重启 → 数行数。

配置 提交耗时 提交行数 恢复后丢失
flush=0, sync_binlog=0 0.018 s 2,000 2,000（全丢）
flush=2, sync_binlog=1 0.987 s 2,000 0
flush=1, sync_binlog=1 1.401 s 2,000 0

第一行要重点看：0.018 秒「提交成功」了 2000 行，客户端收到的是 OK，但重启后一行都没有。这就是为什么 flush=0 在任何有数据价值的场景都不能用——它连「提交成功」这个承诺都不算数。

2.3 深挖：为什么 flush=2 在 kill -9 下没丢数据

这是本文最容易被误解的一点。flush=2 的语义是：**提交时 write() 到操作系统，但不 fsync()**。

崩溃类型 flush=2 会丢吗 原因
mysqld 进程崩溃（kill -9、段错误） 不会 数据已 write() 进 OS page cache，进程死了 OS 还在
操作系统崩溃 / 容器被销毁 / 掉电 会（≤1 秒） page cache 属于内存，断电即丢
磁盘故障 会 需要副本/备份兜底

所以「kill -9 测 flush=2」这个实验天然测不出丢失——我在容器里杀进程，page cache 完好无损。要验证 flush=2 的丢失，只能拔电源、杀宿主机，或者用 fsync 层面的故障注入。这一点很多文章写错，把 flush=2 说成「崩溃丢 1 秒」，准确说法是「掉电丢 1 秒」。

2.4 生产怎么选

场景 建议 理由
订单、支付、账务 flush=1 + sync_binlog=1 丢一笔都是事故，206 倍不值得
日志、行为埋点、监控数据 flush=2 + sync_binlog=0 丢 1 秒可接受，TPS 换 32 倍
批量导入、离线计算中间表 flush=2 + sync_binlog=0，导入后立即备份 临时数据，重跑即可
压测基准 保持 flush=1 用 flush=0 压出来的数字没有参考价值

一条铁律：flush=0 不要出现在任何配置模板里。它省下的不是「性能」，是「数据」。

另外两个常被一起改的参数：binlog_group_commit_sync_delay（默认 0）能让多个事务合并一次 fsync，在高并发写入时能显著提升吞吐，代价是人为增加延迟；innodb_flush_method=O_DIRECT 可以绕开 OS page cache，避免双缓存（① 提过），在专用数据库机器上通常是更好的选择。

2.5 动手验证：自己制造一次数据丢失

预期观察点：第 4 步的行数会回到第 2 步的水平，2000 行凭空消失。

判定标准：

  • 丢 0 行 → 后台刷盘刚好赶上，重跑一次或把提交量加大到 5000 行；
  • 换成 flush=1 重跑，必须丢 0 行；如果也丢，说明你改的参数没生效（用 SELECT @@GLOBAL.innodb_flush_log_at_trx_commit 确认）。

3. Buffer Pool：命中率是怎么算的

3.1 结构：一个被改造过的 LRU

Buffer Pool 按页管理（默认 16KB/页），内部是「young / old」两段式 LRU：

flowchart LR
    subgraph LRU["Buffer Pool LRU list"]
        Y["young sublist<br/>hot pages, 5/8"] --> O["old sublist<br/>cold pages, 3/8"]
    end
    NEW["new page read in"] --> O
    O -->|"accessed again<br/>after innodb_old_blocks_time"| Y
    O -->|"evicted when full"| OUT["evicted"]

为什么分成两段：全表扫描会一次性读入大量「只用一次」的页。如果纯 LRU，这些页会把热数据挤出去。分两段之后，新页先落在 old 区，只有被再次访问（且间隔超过 innodb_old_blocks_time，默认 1000ms）才会晋升 young 区。这就是「一次大查询不会把热数据全冲掉」的机制。

参数 实测默认值 作用
innodb_buffer_pool_size 128MB 池大小，生产建议内存的 50%~70%
innodb_buffer_pool_instances 8（≥1GB 时） 分段减少锁竞争
innodb_buffer_pool_chunk_size 128MB 扩容/缩容的最小单位
innodb_old_blocks_time 1000ms 新页晋升 young 的等待时间

3.2 命中率的算法与陷阱

两个陷阱：

  1. 它是「页级」指标，不是「SQL 级」。一条慢 SQL 可能命中率 100% 但读了 30 万个页（③ 的回表），所以命中率不能替代 EXPLAIN。
  2. 它的分母是请求次数，不是数据量。循环访问同一个页 100 万次，命中率也是 100%。

① 的实测正好能对照：100 万行表（3430 页）在 128MB 池里能整表装下，冷启动扫一次物理读 1046，热缓存后再扫 物理读 0，但逻辑读一次都没少。命中率只说明「要不要去磁盘」，不说明「读得多不多」。

3.3 深挖：为什么 SET GLOBAL 改不了池大小

我在 1GB 池的实例上执行：

静默无效。原因：池大小必须是 innodb_buffer_pool_chunk_size × innodb_buffer_pool_instances 的整数倍。默认 chunk 128MB，池 ≥1GB 时 instances 自动变成 8，于是最小有效值是 1024MB——任何小于它的设置都会被忽略，而且不报错。

在另一个启动参数为 --innodb-buffer-pool-size=32M --innodb-buffer-pool-instances=1 --innodb-buffer-pool-chunk-size=8M 的容器里，同样的 SET GLOBAL 就能从 32MB 长到 512MB。

生产含义：调小 Buffer Pool 不是「改个参数」这么简单，instances 是启动参数，必须改配置文件重启。很多「我调了参数怎么没变化」的困惑，根因就在这里。

3.4 change buffer 与 doublewrite

机制 解决什么问题 边界
change buffer 非唯一二级索引页不在内存时，先记变更，避免随机读 唯一索引不适用（要读页做唯一性检查）；innodb_change_buffer_max_size 实测默认 25%
doublewrite 页写一半时崩溃（torn page），用副本恢复 实测默认 ON，文件为 #ib_16384_0.dblwr；O_DIRECT 下仍需要它
redo 崩溃后重放已提交的变更 环形文件，实测容量 100MB，写满后推进检查点

doublewrite 的代价很直接：每个脏页写两次（先写 dblwr，再写数据文件）。所以它在写入密集场景是实打实的开销，但没人敢关——关掉之后一次断电就可能留下「页只写了一半」的静默损坏，比丢 1 秒数据严重得多。

3.5 动手验证：命中率阶梯

然后把池调到 512MB 再扫一次：SET GLOBAL innodb_buffer_pool_size = 536870912;（在 instances=1、chunk=8M 时有效）。

预期观察点：小池时 physical 明显大于 0、命中率掉下来；大池热起来后 physical 趋近 0。

判定标准：

  • 小池和大池的 physical 都接近 0 → 表太小，加大表或减小池；
  • SET GLOBAL 后 @@innodb_buffer_pool_size 没变 → 撞上 3.3 的 chunk 约束。

诚实说明：在 Docker Desktop（macOS）里，操作系统 page cache 会兜住一部分读，physical 的绝对值不可信。只做相对比较，要绝对值请上 Linux 物理机/云主机。

4. 崩溃恢复：redo 怎么把数据救回来

4.1 恢复流程

flowchart TD
    S["mysqld starts"] --> A["read checkpoint from redo"]
    A --> B["replay redo from checkpoint<br/>redo apply"]
    B --> C{"page corrupt?<br/>(torn page)"}
    C -- yes --> D["restore page from doublewrite"]
    C -- no --> E["continue"]
    D --> E
    E --> F["rollback uncommitted trx<br/>using undo"]
    F --> G["purge starts,<br/>history list drains"]
    G --> H["ready for connections"]

三个关键点：

  1. redo 重放是幂等的：同一个变更重放多次结果一样，所以崩溃恢复可以放心重做。
  2. doublewrite 只在「页损坏」时登场：它的作用不是加速，是保险。
  3. 未提交事务靠 undo 回滚：这就是 ⑤ 里 undo 的第二个用途（第一个是 MVCC）。

4.2 实测：kill -9 之后看恢复

预期观察点：启动日志/状态里能看到 Database was not shut down normally 之类的提示，随后是 redo apply 的进度；恢复时间与「上次检查点之后写了多少 redo」成正比。

判定标准：

  • 恢复时间突然变长 → 检查点推进不及时（大事务、刷脏跟不上），看 innodb_buffer_pool_wait_free；
  • 启动报 page corruption → doublewrite 可能被关了，或者磁盘真坏了。

5. 总结

5.1 面试速答表

面试题 一句话答案
一次 COMMIT 落几次盘 默认两次：redo fsync + binlog fsync；flush=2 或 sync_binlog=0 可减为一次
为什么要两阶段提交 redo 与 binlog 是两套日志，必须保证「要么都有、要么都没有」，否则主从/备份会不一致
binlog 写了但没 commit，恢复后算提交吗 算。redo 在 prepare 状态且 binlog 完整 → 补 commit
flush=1/2/0 区别 1：每次提交 fsync；2：每次提交 write，每秒 fsync；0：每秒由后台写，进程崩溃即丢
flush=2 丢数据的场景 掉电、OS 崩溃、容器被销毁；mysqld 进程崩溃不丢（已 write 到 page cache）
sync_binlog 为什么影响这么大 它控制每次提交是否 fsync binlog，实测从 1 改 0，TPS 提升 12 倍
实测 TPS 差多少 734 → 1,962 → 23,443 → 151,035（四档配置），最大 206 倍
WAL 解决了什么 把随机写数据页变成顺序写日志，用「多写一份日志」换「少做随机 IO」
Buffer Pool 命中率怎么算 1 - read_requests / reads，页级指标，不能替代 EXPLAIN
为什么改不小 Buffer Pool 池大小必须是 chunk_size × instances 的整数倍，小于它就静默无效，实测 1GB 池设 128MB 无效
change buffer 对唯一索引有效吗 无效，唯一性检查必须读页
doublewrite 的代价 每个脏页写两次，但能防 torn page 静默损坏

5.2 实战避坑表

症状 原因 处理
压测 TPS 很高，上线扛不住 压测用了 flush=0 压测必须与生产同档位
掉电后丢了几秒数据 flush=2 + 掉电 核心表改回 1，或用半同步/多副本兜底
写入突然变慢，磁盘 util 100% 脏页刷不过来 看 innodb_buffer_pool_wait_free、加大池或降写入

5.4 实操建议

  1. **别碰 flush=0**。它省下的不是性能，是数据；要在压测里用它，先想清楚压出来的数字能证明什么。
  2. **核心业务保持 flush=1 + sync_binlog=1**，把性能预算花在索引和架构上，而不是省 fsync。
  3. 要换吞吐，优先调 sync_binlog 与组提交，别动 flush_log——前者的丢失场景更可控。
  4. 验证持久性别只用 kill -9。它测不出 flush=2 的风险，那需要掉电级别的故障注入。
  5. **改池大小前先算 chunk × instances**，否则你会以为参数改了、其实什么都没变。
