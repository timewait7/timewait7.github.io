MCP与Agent Skill：AI Agent能力标准化的双轮驱动

Posted on 2026-05-31 In AI大模型 Word count in article: 4.6k Reading time ≈ 17 mins.

摘要

随着大语言模型从对话工具向自主智能体的演进，如何让AI高效、安全地接入外部工具和数据源，已成为工程实践中的核心挑战。在此背景下，Anthropic先后推出了Model Context Protocol（MCP）和Agent Skills两个重要技术规范。MCP定位为AI工具连接的“通用语言”，解决了外部系统接入的标准化问题；Agent Skills则聚焦于能力编排与按需加载，将复杂工作流封装为可复用的技能单元。两者并非竞争关系，而是分工明确的互补架构——MCP负责“接什么”，Skills负责“怎么用”。本文系统梳理两者的诞生背景、核心原理与协同机制，并通过流程图、时序图与深度对比，为开发者提供清晰的选型决策框架和最佳实践指南。

关键词：MCP；Agent Skills；AI Agent；工具调用；能力标准化

一、引言

大语言模型的能力边界正在被快速拓宽。从最初只能进行文本对话，到如今可以调用外部函数、访问数据库、操作文件系统，AI智能体正在成为真正的“执行者”。然而，这种能力扩展背后隐藏着一个长期被忽视的工程难题：连接碎片化。在MCP问世之前，每一个AI模型要接入一个新的工具或数据源，都需要开发一套定制的连接代码。一个团队如果同时使用Claude、GPT-4和Gemini三个模型，而工具库包含GitHub、Slack、Postgres等十个应用，就需要维护多达三十套互不兼容的集成方案。

传统API虽然稳定可靠，但在AI动态调用场景中缺乏灵活性，无法适应LLM输出的非结构化请求。OpenAI引入的Function Calling虽然允许模型调用外部函数，但它是具体实现而非通用协议，不同框架、不同模型之间的规范并不统一。正是在这种“各自为政”的混乱局面下，MCP和Agent Skills应运而生。

二、MCP：AI工具连接的“USB-C”标准

2.1 诞生背景与演进脉络

Model Context Protocol（MCP）是由Anthropic于2024年11月25日推出的开源协议，旨在实现大语言模型与外部数据源和工具的标准化集成。MCP的设计理念被业界形象地比作“AI领域的USB-C接口”——正如USB-C用一个通用端口替代了五花八门的专用充电器，MCP用一个统一协议替代了无数点对点的定制化连接。

MCP的推出恰逢其时。2024年，各大AI厂商都在探索如何让模型真正“动手做事”，但各自的方案互不兼容。Anthropic从一开始就将MCP设计为厂商中立的开放规范，这一战略眼光在随后的生态发展中得到了验证。2025年3月，OpenAI宣布其Agent SDK支持MCP协议；Google DeepMind随后将其集成到Gemini智能体栈中；微软在Copilot Studio中也加入了MCP支持。短短一年间，MCP迅速成长为智能体AI领域的事实互联标准。截至2025年3月，已有超过1000个社区服务器投入实际使用，MCP服务器的月度下载量从发布初期的约200万次飙升至2025年4月OpenAI接入后的2200万次。2025年12月，Linux基金会成立Agentic AI Foundation（AAIF），MCP被正式移交至该基金会管理，标志着其进入了更广阔的开源治理阶段。

2.2 架构设计与核心机制

MCP采用客户端-主机-服务器的三层架构，每个核心组件承担明确的职责：

  • MCP主机：面向用户的应用层，如Claude Desktop、Cursor编辑器或自定义的Python智能体。主机决定连接哪些服务器，并向用户展示工具调用的确认信息。
  • MCP客户端：运行在主机内部，每个客户端对应一台MCP服务器，通过JSON-RPC 2.0协议进行通信。
  • MCP服务器：独立进程，向外暴露一组能力，包括工具（可调用的函数）、资源（只读的数据源）和提示词模板。

MCP定义了三种核心能力原语：

  1. Tools（工具） ：可供AI模型调用的可执行函数，如查询天气、发送消息、执行计算等，并支持参数传递和结果返回。
  2. Resources（资源） ：只读数据源，如数据库记录、本地文件、API响应等，AI可以读取但不能修改。
  3. Prompts（提示词模板） ：可复用的用户交互模板，便于标准化常见对话场景。

在通信层面，MCP提供两种传输协议：

  • STDIO：主机以子进程方式启动服务器，通过标准输入输出进行JSON-RPC消息交换。适用于本地服务，零网络暴露面。
  • Streamable HTTP：用于远程调用场景，2025年3月发布的规范修订版中取代了SSE成为推荐的远程传输方式。

2.3 解决的问题与价值

MCP解决了两大核心痛点：

其一，M×N集成爆炸问题。开发者只需要为每个工具编写一次MCP服务器代码，就能供所有支持MCP协议的AI模型使用，将集成复杂度从线性增长降为常数级。

其二，上下文的“饥荒”问题。传统AI模型无法访问实时数据，被局限在用户粘贴到对话框的有限文本上。MCP通过标准化接口，让模型能够动态获取所需的上下文信息，真正打通了模型推理与真实世界之间的壁垒。

三、Agent Skills：AI能力的“模块化封装”

3.1 从Prompt到Skills的演进

如果说MCP解决了“如何连接”的问题，那么Agent Skills解决的则是“如何高效使用能力”的问题。

在MCP推出一周年之际，Anthropic发现了一个新的瓶颈：当MCP工具数量激增时，大量Token被消耗在工具定义的传递上。一个会议记录下载并转存的操作，可能因为反复传递工具定义而导致Token消耗成倍增长。

与此同时，Prompts本身也存在明显局限：Prompt是一次性注入的静态文本，会随着对话轮次的增加而被稀释，难以持久化复用。各AI框架（LangChain、AutoGen等）之间互不兼容，使得能力无法跨平台共享。

正是在这一背景下，Anthropic在2025年初提出了Agent Skills的概念。2025年12月18日，Anthropic正式将Agent Skills发布为跨平台的开放标准，同步开源了包含16个生产级技能库的参考实现。

3.2 核心架构：渐进式披露

Agent Skills采用极简但强大的设计：每个Skill就是一个文件夹，其中必须包含一个SKILL.md文件（含YAML元数据和Markdown指令），并可附带脚本、模板、文档等任意资源。

Skills的核心工作机制被称为 “渐进式披露”（Progressive Disclosure） ：

  • 第一阶段（浏览） ：Agent最初只读取Skill的YAML元数据（名称、描述、触发条件），每条Skill仅消耗约30-50个Token。
  • 第二阶段（加载） ：当用户意图匹配某个Skill时，Agent读取完整的SKILL.md文件内容，将操作指令注入推理上下文。
  • 第三阶段（使用） ：如需执行脚本或读取附带的资源文件，Agent在需要时再动态加载这些内容。

这一设计使Agent可以同时“拥有”数十个Skills，而不会造成上下文窗口的过度占用。

3.3 演进动力：从封闭到开放

Agent Skills的一大里程碑发生在2025年12月——Anthropic将其发布为开放标准。这一举措迅速得到生态响应：OpenAI随即在Codex文档中加入了Skills支持；LangChain在DeepAgents中实现了Skills集成；特赞等团队推出了首个Skills管理基础设施。截至2026年5月，主流技能共享平台上的技能数量已突破5万个。

更重要的是，Agent Skills提供了一套完整的能力治理体系：企业版用户可以集中管理技能库、控制技能发布权限、审计使用记录，使AI能力的部署从“用户自建”走向“平台化运营”。

  • MCP 负责底层执行：将每个“动作”映射到具体的工具调用，以标准化的方式与外部系统交互。

这正是业界所说的“MCP让能力变成可插拔的基础设施，Skills负责在对话中智能选择与编排”。

5.2 协作关系：不是“谁取代谁”

一个常见的误解是Skills会“淘汰”MCP。事实上，Anthropic官方的立场非常明确：Skills和MCP解决的是不同层面的问题，二者协同使用才能发挥最大价值。

可以这样理解三层架构：

  • MCP层：工具连接的基础设施，统一了“AI与外部系统如何通信”的规范。
  • Skills层：能力编排的框架，定义了“在何种条件下、按照什么顺序、以什么方式使用这些工具”。
  • Function Calling层：LLM原生能力，是前两者得以执行的底层手段。

一个精心设计的高级Skill，其底层往往就是在调用多个MCP工具。在这种架构下，Skills是“指挥官”，MCP是“执行者”，两者构成了完整的AI智能体能力闭环。

六、注意事项与最佳实践

6.1 MCP实施注意事项

安全性方面，MCP服务器通常拥有文件系统、数据库或外部API的访问权限，应将其视为不可信的执行方。实践中应注意：对MCP工具的调用权限进行分级管理（如只读与可写分离）；在主机层面实现用户确认机制，防止AI自动执行敏感操作；对MCP Server进行沙箱隔离，限制其系统资源访问。MCP主机应单独处理工具调用的身份验证和授权，不应将这些职责委托给LLM。

性能与选型方面，STDIO适用于本地服务，具有零网络风险和生命周期可控的优势，应该是默认首选。HTTP远程调用适用于跨网络场景，但需额外考虑认证、审计和速率限制等企业级需求。强烈推荐部署MCP网关来处理这些横切关注点，包括认证、审计和护栏控制，避免在每个服务器中重复实现。

设计规范方面，工具定义应包含清晰的语义化描述和准确的参数Schema，这直接影响LLM正确选择工具的准确率。每个MCP工具应保持单一职责，避免设计过于庞大臃肿的“万能工具”，以提高调用的可预测性。建议为工具添加丰富的错误信息，帮助LLM在调用失败时做出合理的恢复决策。

6.2 Skills实施注意事项

版本管理是Skills工程化的核心。建议在SKILL.md的YAML元数据中明确记录技能版本、作者、依赖关系等元信息，支持平滑升级和回滚。

Skill颗粒度设计是一大难点：技能太细会导致管理成本上升；太粗则降低了复用性。一个较为合理的实践是参考“30-50 Token元数据”原则，确保元数据足够精简，让Agent在浏览阶段就能准确判断技能是否适用。Skill正文（SKILL.md）则应当详细描述完整的操作流程、异常处理路径和预期输出格式，确保LLM即便面对不完美的输入也能给出合理的响应。

性能调优方面，应充分利用渐进式披露机制：元数据中只放最关键的信息（名称、简短描述、触发关键词），完整指令和资源都放在正文中按需加载。附带的脚本应当优先使用确定性强的代码（如Python数据处理）而非纯LLM推理，以提升结果的稳定性。

安全考量则与MCP类似，需要注意Skill中附带的脚本可能执行任意代码，应对其进行沙箱隔离和输入校验。企业环境中应建立技能审批制度，避免未经审查的Skill进入生产系统。

6.3 典型应用场景与选型建议

场景类型 推荐方案 理由
单次API调用（如查天气、发送消息） MCP直接调用 简单直接，无需Skill额外封装
企业合规工作流（如按标准做安全审查） Skill + MCP 用Skill封装流程规范，MCP负责底层工具调用
需要跨对话复用的专业能力（如数据分析模板） Skill 技能可以持久化保存，即用即加载
多智能体并行协作 MCP + A2A + Skills Skills提供能力原子，MCP作为工具总线，A2A协调智能体间通信
需要大量上下文注入的复杂任务（如长文档分析） Project + Skill Project提供持久上下文空间，Skill注入特定领域操作指令

在业界实践中，MCP多作为“工具总线”率先搭建，再在基础上引入Skills概念，最后在需要多智能体协作时补充A2A协议——这一“MCP先行→Skills叠加→A2A按需”的演进路径已被验证为稳健的工程策略。

七、结论与展望

MCP和Agent Skills共同构成了当前AI智能体能力标准化的基础框架。MCP通过统一连接协议，将AI与外部系统的集成从“各自为战”推向“标准互通”；Agent Skills通过渐进式披露的能力封装，将专业工作流从“手写Prompt”推向“工程化复用”。

两者的关系并非竞争，而是一种精妙的分工协作：MCP负责连接性（Connectivity），Skills负责能力性（Capability） 。MCP让每一种工具都可以被标准化接入，Skills让每一种专业知识都可以被标准化封装。对于AI应用开发者而言，理解并善用这两项技术，将成为构建下一代智能应用的关键能力。

展望未来，随着MCP进入Linux基金会治理、Agent Skills逐步被更多平台采纳，这两项标准化工作有望催生真正的“AI应用商店”生态——就像Android应用商店一样，开发者可以自由发布Skill和MCP Server，企业可以按需购买和部署，而AI智能体则能够自动发现、加载、调用最适合当前任务的能力组合。
