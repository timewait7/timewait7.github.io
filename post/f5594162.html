日常运维高频命令实战手册

Posted on 2026-08-22 In 部署运维 Word count in article: 16k Reading time ≈ 57 mins.

1. 系统信息与性能排查

1.1 排查顺序：先看全局，再钻进程

服务器变慢时，顺序永远是「负载 → CPU → 内存 → IO → 进程 → 线程」，从粗到细逐层收敛。四类资源的快捷判定：

graph TD
    S[Server Slow] --> L[uptime: load average]
    L --> C[top / vmstat: us sy wa]
    L --> M[free: mem and swap]
    L --> I[iostat: await and util]
    C --> P[top -Hp: hot thread]
    P --> J[jstack: match hex TID]
    I --> D[du / lsof: who writes the disk]
    M --> O[dmesg: OOMKiller]

1.2 常用选项清单

uptime / free / lscpu / nproc：系统概览

命令 核心选项 说明 使用场景
uptime — 负载、运行时长、登录用户数 第一眼看负载
-p 人性化显示运行时长 确认机器是否刚重启过
free -h 人类可读单位 看内存/Swap 占用
-m 以 MB 为单位 老脚本里常见
-s 2 每 2 秒刷新一次 实时观察内存变化
-w 把 buffers 和 cache 分列显示（默认合并） 判断 page cache 占用（内核 3.14+）
lscpu — CPU 架构、核数、NUMA 信息 确认物理核/超线程
nproc — 可用 CPU 核数 算负载基线、设线程池
uname -a 内核版本与架构 确认内核版本
ulimit -a 所有资源限制 排查 “Too many open files”
-n 最大打开文件数（nofile） 高并发服务必查

一句口诀：load average 要和 nproc 对比着看——4 核机器 load 8 说明平均有 4 个任务在排队。

top / htop：实时进程视角

命令/按键 说明 使用场景
top -c 显示完整命令行 区分同名 java 进程
top -Hp <pid> 展开该进程的所有线程 定位打满 CPU 的线程
top -u <user> 只看某用户的进程 多租户机器
top -p <pid1>,<pid2> 只看指定进程 盯住目标进程
top -b -n 1 批处理模式输出一次 写脚本采集，不能交互时用
top -d 2 刷新间隔 2 秒 降低刷新频率
top -o %MEM 按内存排序启动 内存排查
交互键 P / M / T 按 CPU / 内存 / 运行时间排序 现场切换排序
交互键 1 展开每个 CPU 核心 发现单核打满
交互键 H 线程视图开关 等价于 -H
交互键 c 完整命令行开关 等价于 -c
交互键 k 直接杀进程 应急操作
htop 彩色交互版，支持鼠标、树状视图 日常首选（需安装）

top 头部关键列：us（用户态）、sy（内核态）、wa（IO 等待）、si/so（Swap 换入换出，非零即为事故）、st（被虚拟化偷走的 CPU）。

vmstat / iostat / mpstat / sar / pidstat：采样统计视角

命令 核心选项 说明 使用场景
vmstat 1 5 每秒采样一次，共 5 次 看 r 队列、上下文切换、Swap
-s 汇总统计 开机以来的总量
-d 磁盘统计 各磁盘读写块数
-w 宽格式（列不挤在一起） 大数字时更易读
iostat -x 扩展统计（await、%util 等） 排查磁盘瓶颈必用
-z 不显示无活动的设备 输出更干净
-m 以 MB/s 显示吞吐 看带宽是否打满
-d 只看磁盘（默认含 CPU） 专注 IO
1 只写数字 = 采样间隔秒数 iostat -xz 1
mpstat -P ALL 1 每个核心的使用率 确认是否单核打满
sar -n DEV 1 网卡流量、错误包 网络吞吐排查
-u 1 CPU 使用率历史采样 复盘「昨晚 10 点为什么卡」
-r 1 内存历史采样 同上
pidstat -u -p <pid> 1 指定进程的 CPU 使用（含用户态/内核态拆分） 进程级细分
-d -p <pid> 1 指定进程的磁盘 IO 找「谁在写盘」
-w -p <pid> 1 上下文切换 线程切换风暴
-t -p <pid> 1 按线程拆分 等价于 top -Hp 的采样版

dmesg：内核日志

命令 核心选项 说明 使用场景
dmesg -T 人类可读时间戳 对照故障时间点
-w 持续输出（follow） 实时盯内核日志
-l err,warn 只看指定级别 过滤噪音
| tail -20 看最后 20 行 快速判断硬件/OOM

案例入口：dmesg -T | grep -i "out of memory" 是确认 OOM Killer 是否出手的第一条命令。

1.3 生产实践案例：服务器卡顿，页面打开缓慢

场景：业务反馈服务器卡顿，页面打开缓慢。

处理结果：发现是某个定时任务与业务高峰叠加，临时降低任务频率，并优化了代码中的死循环。

复盘结论：r 队列、us/sy、单核打满这三条线索都指向 CPU 竞争；如果 wa 高而 us 低，方向就要换到磁盘。

1.4 动手验证：亲手复现一次「CPU 打满」

预期观察点与判定标准：

观察点 正常 异常判定
uptime 的 load 1 分钟值 ≈ 任务数 持续 > 核数 × 1.5 视为过载
us（用户态） 与业务量匹配 yes 这类纯计算会顶到接近 100%
wa（IO 等待） 个位数 持续 > 20% 说明磁盘是瓶颈
si/so（Swap） 0 只要非零，立即查内存
r 列（vmstat） ≤ 核数 持续 > 核数 = 有任务排队

更贴近生产的做法是用 stress-ng --cpu 4 --timeout 60s 造多核负载，观察 mpstat -P ALL 的均衡性。

2. 文件与权限基础

2.1 常用选项清单

ls / cd / pwd：目录浏览

命令 核心选项 说明 使用场景
ls -l 长格式（权限、大小、时间） 查看文件详情
-a 含 . 开头的隐藏文件 查看隐藏配置
-h 人类可读大小（K/M/G） 看文件大小必加
-t / -r 按修改时间排序 / 反向 找最新/最旧文件
-S 按大小排序 找大文件
-d 显示目录本身而非内容 ls -ld /data/www 查目录权限
常用组合 ls -lah 全部文件 + 人类可读 + 详情 每天必用
ls -lht 按时间排序 日志目录找最新
ls -ltr 按时间倒序（最旧在最上） 找最旧文件
cd ~ / - / .. 主目录 / 上次目录 / 上级目录 cd - 在两目录间跳
pwd -P 物理路径（不显示软链） 确认软链背后的真实路径

cp / mv / rm：复制、移动与删除

命令 核心选项 说明 使用场景
cp -i 覆盖前询问 防止覆盖重要配置，建议设别名
-u 只复制更新的文件 增量部署：只覆盖改动过的静态资源
-r / -a 递归（-a 保留权限、时间戳、软链） 备份整个项目目录
-b 覆盖前自动备份（~ 后缀） 改配置前的保险
-p 保留属主/权限/时间戳 跨机器拷文件
mv -i 覆盖前询问 防止误覆盖
-u 只移动更新的文件 合并两个目录
-b 覆盖前备份 同上
rm -i 逐个询问 救命选项
-r 递归删除目录 极度危险，执行前先 ls 一遍
-f 强制，不提示 与 -i 相反，脚本里慎用
-- 结束选项标志 删除 -file.txt 这类怪文件名

rm 安全习惯：rm -rf 前先把命令里的 rm -rf 换成 ls -ld 跑一遍确认路径，再改回来。删除大量文件用 find ... -delete 更有审查痕迹。

chmod / chown：文件权限

命令 核心用法 说明 生产场景
chmod chmod 755 file 数字模式 脚本加执行权限
chmod u+x file 符号模式 精确控制
chmod -R 755 dir/ 递归 批量修复
chmod --reference=模板 目标 参考复制权限 快速对齐
chown chown user:group file 改属主属组 部署后修正归属
chown -R user:group dir/ 递归 批量
chown --reference=模板 目标 参考复制 —

权限数字速查：4=r、2=w、1=x；755 = 用户 rwx、组 r-x、其他 r-x；644 = 用户 rw-、组 r–、其他 r–；600 = 仅属主读写（密钥文件必须 600）。

find：按条件查找

用法 说明 生产场景
find /path -name "*.log" 按文件名 查找日志文件
find /path -iname "*.log" 忽略大小写 同上
find /path -type f / -type d 按类型 只找文件/目录
find /path -size +100M 按大小 找出大文件清理磁盘
find /path -mtime -7 / +7 修改时间 7 天内 / 超过 7 天 清理旧日志
find /path -mmin -30 按分钟 定位「刚刚被改的文件」
find /path -maxdepth 2 限制递归深度 避免扫全盘
find /path -delete 直接删除匹配项 比 -exec rm 快且安全
find /path -exec {} \; 对每个结果执行命令 逐个处理，慢但安全
find /path -exec {} + 批量传给命令一次执行 批量操作，效率高
find /path -print0 | xargs -0 处理含空格/换行的文件名 生产必用，防文件名炸裂

对照：-exec {} \; 每个文件 fork 一次，1 万个文件就是 1 万次进程创建；-exec {} + 和 xargs 会攒批，数量级更快。

tar：打包压缩（基础用法）

格式 打包（创建） 解包 查看内容 生产场景
.tar.gz tar -czvf 包.tar.gz 源目录/ tar -xzvf 包.tar.gz tar -tzvf 包.tar.gz 最常用，发布 Java/Go/Node 应用
.tar.bz2 tar -cjvf 包.tar.bz2 源目录/ tar -xjvf 包.tar.bz2 tar -tjvf 包.tar.bz2 压缩率更高，适合归档
.zip zip -r 包.zip 源目录/ unzip 包.zip -d 目标目录/ unzip -l 包.zip 跨平台（Windows/Linux 通用）

补充选项：

选项 说明
tar -C /target 解压到指定目录：tar -xzvf 包.tar.gz -C /target/
tar --exclude='*.log' 打包时排除
tar --strip-components=1 解压时去掉一层目录（解 jar 包/发布包常用）

tar -czvf = Create Zip Verbose File；tar -xzvf = eXtract。口诀：c 创建、x 解压、t 查看、f 指定文件名必须放最后。

ln：软链接（版本切换必备）

命令 说明 生产场景
ln -s 源文件 链接名 创建软链接（存路径） JDK/应用版本切换、统一日志路径
ln -sfn 新目标 链接名 覆盖已有软链（-n 防止跟进目录） 版本切换标准写法：ln -sfn /opt/jdk-17 /opt/java

一句话区别：软链接存的是路径，原文件删了就失效（ls -l 显示 ->）。目录不能建硬链接。

2.2 动手验证：文件名带空格时，两种写法差在哪

判定标准：写法 A 输出 4 行（app、log、1.log……被空格切开），写法 B/C 输出 2 行完整文件名。**只要管道下游是 rm/mv/chmod，就必须用 -print0 | xargs -0 或 -exec**。

3. 文本处理与日志分析

命令组装成管道才是战斗力：grep 过滤 → awk 取列 → sort | uniq -c 统计 → sort -rn | head 取 TOP N。本章先给每个命令的选项清单，再给一套「日志分析管道」实战。

3.1 常用选项清单

grep：按行搜索

核心选项 说明 使用场景
-i 忽略大小写 搜索不区分大小写
-r / -R 递归搜索目录（-R 跟进软链） 全项目找调用
-v 反向匹配 过滤注释行、空行
-c 统计匹配行数 统计错误条数
-n 显示行号 定位代码行
-l / -L 只显示匹配/不匹配的文件名 快速定位哪些文件包含关键字
-q 静默（只看退出码） 脚本判断存在性
-A 5 / -B 5 / -C 5 匹配行的后 5 行 / 前 5 行 / 前后各 5 行 看错误上下文
-o 只打印匹配部分 提取 IP、时间等片段
-E 扩展正则（ERE） 用 |、+、?、{}
-F 固定字符串（faster） 关键字里有正则元字符
-P PCRE 正则 用 \d、\s、环视
-w / -x 整词 / 整行匹配 防止 user 命中 username
-m 10 最多匹配 10 行就停 大文件里只要前几条
--include='*.log' 只搜某类文件 配合 -r
--exclude-dir=.git 排除目录 配合 -r
--color=auto 高亮匹配 交互查阅

组合口诀：grep -rn --include='*.java' "关键字" . 是最常用的「全项目找代码」；日志分析里 grep -c 计数、grep -A/-B 看上下文。

awk：字段提取与统计

核心模型：逐行读取 → 按分隔符切分 → 用 $1、$2…… 访问每一列。

概念 说明 示例
$0 整行 {print $0}
$1…$N 第 N 列 {print $1}
$NF 最后一列 {print $NF}
NF / NR / FNR 列数 / 行号 / 当前文件行号 {print NR, $1}
FS / OFS 输入/输出分隔符 -F: 或 BEGIN{FS=":"}

5.4 深挖：ExitCode 137 与容器 OOM

容器进程退出码不是随便编的：137 = 128 + 9，即被 SIGKILL 杀死。在容器里，能发出 SIGKILL 的通常就是内核 OOM Killer——因为 cgroup 的内存上限触发了内核的强制回收。串起来的因果链：

cgroup 限制了容器可用内存 → 进程超限时内核在 cgroup 内选「最胖」的进程杀 → 容器主进程（PID 1）被杀 → docker ps 显示 Exited (137) / K8s 显示 OOMKilled。

证据 来源 含义
docker inspect -f '{{.State.ExitCode}}' = 137 Docker 被 SIGKILL
kubectl describe pod 里 Reason: OOMKilled K8s 明确是内存超限
dmesg -T | grep -i oom 内核 宿主层面 OOM（可能是整机，不一定是容器）
docker stats 的 MEM USAGE / LIMIT Docker 实时逼近上限
JVM 场景：-XX:MaxRAMPercentage JVM 容器内默认只按 25% 限额用堆，堆外（元空间/线程栈/直接内存）超了照样 137

与 Docker 容器实战 里 cgroup 章节的呼应：--memory 限制的是整个 cgroup（堆 + 堆外 + 页缓存），不是 JVM 堆。Java 应用在 K8s 里 OOMKilled，一半的锅要分给「堆外内存没算进 limit」。

9.3 深挖：TIME_WAIT 与 CLOSE_WAIT 是两回事

ss -s 里两个高频「异常」，机制完全不同：

状态 谁产生的 机制 正确处理
TIME_WAIT 主动关闭方 等 2MSL（约 60 秒）确保最后的 ACK 到达、旧包在网络中消散 大量短连接客户端角色（网关、爬虫）会攒；用连接池/长连接减少，内核调优是运维的活
CLOSE_WAIT 被动关闭方 对端已 FIN，本端应用没有调用 close() 这是应用 bug：连接池没归还、异常分支没关流；ss -tnp state close-wait 找到进程去查代码

TIME_WAIT 不是故障，是协议在保证可靠性。作为后端，你该关注的是 CLOSE_WAIT 高 → 自己的代码漏关了连接，这是真正的 BUG。TIME_WAIT 高 → 说明你的服务短连接过多，方向是上连接池/长连接，而不是去改内核参数（那是运维的活）。

10.4 深挖：cron 的环境为什么和登录时不一样

cron 不经过登录流程，**不会读 /etc/profile、~/.bashrc**，拿到的是一份极简环境（PATH 通常只有 /usr/bin:/bin）。这是「手动执行成功、cron 执行失败」的第一大原因。四类差异与对策：

差异 表现 对策
PATH 不同 command not found 脚本开头 source /etc/profile，或全用绝对路径
工作目录不同 相对路径文件找不到 开头 cd /data/scripts
没有终端 tput、read、交互命令失败 脚本里禁用交互
环境变量缺失 JAVA_HOME 等未定义 在 crontab 顶部或脚本里显式定义

调试口诀：cron 任务就是「无 TTY、无 profile、无工作目录」的三无进程。写定时脚本时把自己当成一个刚登录的陌生用户来考虑。

load average 多少算高？ 和 nproc 对比：持续超过核数说明有任务在排队，超过 1.5 倍视为过载
vmstat 的 r 列、b 列分别是什么？ r = 可运行队列长度（含运行中+等待 CPU），b = 不可中断睡眠（多为 IO 等待）
iostat 的 %util 和 await 哪个更可信？ await（平均等待毫秒数）更可信；%util 在 NVMe 多队列下会失真
df 显示满但 du 加起来不大，为什么？ 三种可能：删除未释放的文件（lsof +L1）、文件系统保留块、目录被挂载覆盖
TIME_WAIT 和 CLOSE_WAIT 的区别？ TIME_WAIT 是主动关闭方等 2MSL（协议的可靠性保证）；CLOSE_WAIT 是被动关闭方应用没调 close，是 bug
SIGTERM 和 SIGKILL 的区别？ 15 可被捕获、进程能优雅清理；9 不可捕获、直接杀，先 15 后 9
kill -0 是干什么的？ 不发信号只做存在性检查，脚本探活的基础
为什么 cron 里执行脚本总失败？ cron 没有登录环境（无 profile、PATH 极短、无工作目录），用绝对路径或显式 source
find 配 xargs 为什么必须加 -print0/-0？ 文件名含空格/换行时会被二次切分，-print0 用 NUL 分隔才安全
容器 ExitCode 137 是什么？ 128+9 = 被 SIGKILL，容器里通常是 cgroup 内存超限触发内核 OOM Killer
CrashLoopBackOff 的排查顺序？ get pods → describe（看 Events/Reason）→ logs --previous → 查 resources limit
top -Hp 找到的 TID 怎么用？ 转十六进制后在 jstack 里搜 nid=0x...，栈顶即热点方法
jstat -gcutil 看什么？ O 区（老年代）使用率持续高位 + FGC 频繁增长 = 内存问题或 GC 参数问题
Arthas 的 redefine 有什么限制？ 只能改方法体，不能改签名/字段；且是临时的，重启即失效
git reset --soft/--mixed/--hard 区别？ soft 只动 HEAD；mixed（默认）再退暂存区；hard 连工作区一起丢
已推送的提交写错了怎么救？ 用 git revert 生成反向提交；改写公共历史必须 --force-with-lease 且通知协作者
误删分支/误 reset 怎么恢复？ git reflog 找 sha，重建分支或 reset 回去（未提交的改动无法找回）

11.2 实战避坑表

症状 原因 处理
rm 后磁盘空间不降 进程仍持有已删除文件的 fd lsof +L1 找进程 → 重启进程或 truncate 其 /proc/<pid>/fd/n
清空日志后 nginx 不再写日志 文件 inode 被换掉（用了 rm 而非 truncate） 用 truncate -s 0 清空；已发生的用 nginx -s reopen
定时任务到点没执行 cron 环境/PATH/工作目录与登录不同，或脚本无执行权限 查 /var/log/cron（RHEL）/syslog（Debian），脚本里用绝对路径并重定向日志
crontab -r 一把清空 该命令没有确认提示 定期 crontab -l > backup；手滑后从备份或 /var/spool/cron/ 恢复
JVM 容器里被杀但日志干净 被 SIGKILL，没机会写日志 查 exit code 137 / describe 的 OOMKilled / dmesg，并检查堆外内存
Java 进程 OOMKilled 但堆没满 --memory 限制的是整个 cgroup（堆+堆外+页缓存） 给 MaxRAMPercentage 留出堆外空间，或提高 limit
K8s 改了 deployment 没生效 镜像 tag 未变（如都用 latest） 用不可变 tag / digest；rollout status 确认发布完成
jmap -heap 报 attach 失败 部分 JDK 版本/容器权限限制 换 jcmd <pid> GC.heap_info

git pull 产生一堆 merge 提交 默认 merge 策略 个人分支 git pull --rebase，或配置 pull.rebase=true

11.4 实操建议

  1. 把这份手册当成索引而不是教材：遇到故障先看 11.3 的工具速查表定位「用什么工具」，再回对应章节看选项和案例。
  2. 动手验证章节至少做一遍：CPU 打满、删除文件未释放、cron 环境差异、jstack 定位热点、误删分支复活，这五个实验覆盖了最高频的排查范式。
  3. 危险命令三件套：rm -rf 前替换成 ls -ld 预览、find ... \| xargs 必加 -print0/-0、truncate -s 0 优先于 rm 清日志。
  4. 排查留痕：每个生产问题的「症状 → 工具 → 根因 → 处理」四行记进自己的知识库，三个月后你就是团队里查得最快的人。

生产环境执行操作前，请务必确认影响范围并做好备份。
