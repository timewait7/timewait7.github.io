Java 侧：连接池打满与 @Transactional 失效的真相

Posted on 2026-10-25 In 数据存储 Word count in article: 3.8k Reading time ≈ 14 mins.

数据库很健康，接口却全量超时——这类故障的根因大多不在 MySQL，而在应用侧的连接池与事务边界。连接池是个排队系统：池里有几个连接，决定了你的系统最多能并发几个「数据库等待」；@Transactional 是个代理：绕过代理的调用，事务根本不存在。

本文用可运行的 Java 代码（JDK 21 + HikariCP 5.0.1 + Spring 6.1.6 + MySQL 8.0.46）把两件事量成数字：池大小 2/8/20 对应的吞吐与 P99，以及六种 @Transactional 写法的真实提交结果——其中四种会「悄悄失效」，数据照样落库。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池与事务（本文） → ⑫ 容量与分库分表

与前后篇的关系：② 测出「一次连接建立是毫秒级、一条语句是微秒级」，本文解释为什么连接必须复用；⑤ 讲的事务机制，在本文变成「代理没生效，事务就没开」；⑩ 的 MDL 雪崩，最终会在这里表现为连接池打满。

1. 连接池是个排队系统

1.1 连接为什么必须复用

② 的实测：新建连接要付 TCP 握手 + 认证，服务端几毫秒；而一条已建立连接上的 SELECT 1 只要 10.8 微秒。差两个数量级。

flowchart LR
    T["32 app threads"] --> Q["HikariCP queue"]
    Q --> P["pool: N connections"]
    P --> DB["MySQL server"]
    DB --> P --> Q --> T
    Q -.->|"no idle connection<br/>and pool full"| W["wait up to<br/>connectionTimeout"]
    W -.->|"exceeded"| E["SQLTransientConnectionException"]

关键认知：池不是缓存，是限流器。它的作用是「限制同时打到 MySQL 的连接数」，而不是「越多越快」。

1.2 HikariCP 关键参数（实测默认值）

用 HikariCP 5.0.1 初始化一个只设了 URL 的池，读出的解析后默认值：

参数 实测默认 含义 实践建议
maximumPoolSize 10 池上限 按 QPS × 平均耗时 估，别拍脑袋
minimumIdle 10（等于 max） 最小空闲 与 max 相等可避免抖动，但要接受启动即建连
connectionTimeout 30000 ms 拿连接的等待上限 业务超时通常 1~3 s，这里要同步调小
idleTimeout 600000 ms 空闲连接回收 默认即可
maxLifetime 1800000 ms 连接最长寿命 要小于 MySQL wait_timeout（默认 8 小时）
keepaliveTime 0（关闭） 保活探测 走 NAT/LB 时可开
validationTimeout 5000 ms 校验连接可用 通常不用改
leakDetectionThreshold 0（关闭） 连接泄漏检测 排查泄漏时临时设为 20~60 s

1.3 池大小怎么算

小学算术：池大小 ≈ 目标 QPS × 单请求在库里的平均耗时（秒）。

场景 目标 QPS 单请求耗时 需要连接数
后台管理 50 10 ms 0.5 → 1~2
普通业务接口 200 20 ms 4
有慢查询（未优化） 200 200 ms 40
秒杀扣减 2000 5 ms 10

这张表最有用的一行是第三行：慢查询会直接放大连接需求。一条 200 ms 的 SQL 在 200 QPS 下需要 40 个连接，而 MySQL 的默认 max_connections 是 151（实测），几个这样的接口就能把实例连接数打满。所以「加连接数」永远是最后手段，先优化 SQL。

1.4 实测：池大小 vs 吞吐 vs P99

32 个线程、240 次请求，每次执行 SELECT SLEEP(0.05)（模拟 50 ms 的慢查询）：

池大小 总耗时 吞吐（rps） p50 p99
2 6,337 ms 37.9 52 ms 6,176 ms
8 1,624 ms 147.8 51 ms 1,622 ms
20 775 ms 309.7 51 ms 757 ms

三个结论：

  1. 吞吐 ≈ 池大小 / 单请求耗时。池 2 → 理论 40 rps，实测 37.9，几乎完全吻合。
  2. p50 一直是 51 ms，与池大小无关；p99 从 6.2 秒降到 0.76 秒。池小不会让单次查询变慢，只会让排队变长。
  3. p99 和 p50 的差距就是排队时间的上界。看到 p50 正常、p99 爆炸，第一反应应该是「池/线程池在排队」，而不是「数据库有问题」。

1.5 动手验证：量出你自己系统的池需求

预期观察点：p50 稳定在你设定的 50 ms 左右，p99 随池变小而成倍增加。

判定标准：

  • rps ≈ poolSize / 平均耗时 → 池就是瓶颈，加池或优化 SQL；
  • rps 不随池增大而上升但仍低于目标 → 瓶颈不在池（CPU、下游、锁）；
  • p99 / p50 > 10 且两者都不是 50 ms → 有 GC 或网络抖动，用 jstack/async-profiler 看。

2. 池打满：从「慢」到「全量失败」

2.1 实测：等待 2 秒后抛异常

池大小 2，先占满 2 个连接，再申请第 3 个（connectionTimeout=2000）：

注意异常类型：SQLTransientConnectionException，不是 SQLException 的泛化错误。如果你的全局异常处理把它归到「系统异常」里打了一条日志，很可能连告警都没配——这就是「池打满了没人知道」的原因。

另一个实测细节：第一次跑压测时我把 connectionTimeout 设在 3 秒，池大小为 2、32 个线程，结果大量请求直接超时——池小不只是变慢，是在并发高时直接失败。

2.2 打满的三个真实原因

原因 特征 定位手段
慢 SQL Threads_running 不高，但单个查询耗时长；activeConnections 长期等于 max 慢日志、EXPLAIN（④）
连接泄漏 activeConnections 只增不减，重启后恢复 leakDetectionThreshold + 线程栈
事务过长 事务里包了 RPC/批量处理（⑤） 查 innodb_trx 的 age_s
连接数配置过小 并发一上来就等，SQL 本身很快 对比 1.4 的公式

2.3 排查顺序

flowchart TD
    A["接口大面积超时"] --> B{"DB 侧<br/>Threads_running 高吗"}
    B -- 高 --> C["慢 SQL / 锁等待<br/>看 digest 与 data_lock_waits"]
    B -- 低 --> D{"Hikari<br/>activeConnections = max?"}
    D -- 是 --> E{"waiting 线程多吗"}
    E -- 是 --> F["池不够或连接泄漏<br/>看 leakDetectionThreshold"]
    E -- 否 --> G["事务太长：在等 RPC 或下游"]
    D -- 否 --> H["不是连接池，查 GC/线程池/下游"]

第一原则：池打满时先看 HikariPool 的 activeConnections 和等待线程数，不要先看 GC。 GC 高是结果，不是原因。

2.4 动手验证：复现一次打满

预期观察点：第 3 次 getConnection() 在 2 秒后抛 SQLTransientConnectionException；10 秒后日志里出现泄漏告警，带获取连接的调用栈。

判定标准：

  • 有泄漏告警 → 按堆栈找没 close 的分支（常见于 try 外提前 return）；
  • 没有泄漏告警但 activeConnections 长期满 → 是慢 SQL 或长事务，不是泄漏。

3. @Transactional 失效：六种写法实测

3.1 原理：你调用的不是原对象

sequenceDiagram
    participant Caller
    participant Proxy as Spring Proxy
    participant Target as YourService
    participant TM as TransactionManager
    Caller->>Proxy: service.doWork()
    Proxy->>TM: begin()
    Proxy->>Target: doWork()
    Target-->>Proxy: return / throw
    Proxy->>TM: commit() / rollback()
    Note over Target: this.other() bypasses proxy<br/>-> no new transaction

@Transactional 靠代理生效。三类情况代理拦不住：① 同类内部自调用；② 方法不是 public（CGLIB 无法覆盖）；③ 对象不是 Spring 管理的 Bean。

3.2 实测：六种写法的提交结果

同一张表、同一个数据库，每条 case 插一行后故意抛异常，然后另开连接查这行还在不在：

# 写法 实测结果 是否符合预期
1 自调用 this.txMethod() rows=1（已提交） ❌ 静默失效
2 private 方法加 @Transactional rows=1（已提交） ❌ 静默失效
3 抛受检异常 Exception rows=1（已提交） ❌ 默认不回滚
4 异常在方法内部被 catch 吞掉 rows=1（已提交） ❌ 事务照常提交
5 抛 RuntimeException（正解） rows=0（已回滚） ✅
6a 外层事务（内层 REQUIRES_NEW 失败） rows=1（已提交） ✅ 外层不受影响
6b 内层 REQUIRES_NEW 抛异常 rows=0（已回滚） ✅ 独立事务回滚

六条里有四条是「看起来有事务、实际没有」。 这就是为什么「我明明加了注解」和「数据还是写进去了」能同时成立。

3.3 逐条解释

① 自调用：this.txMethod() 走的是原始对象，不经过代理，所以那个 @Transactional 完全没执行。修法：拆到另一个 Bean，或注入自身代理（@Lazy 注入自己 / AopContext.currentProxy()）。

② private：CGLIB 通过继承生成子类来拦截，private 方法无法被覆盖。Spring 6 会忽略它，不会报错。

③ 受检异常：@Transactional 的 rollbackFor 默认只有 RuntimeException 和 Error。抛 Exception 时事务照常提交。修法：@Transactional(rollbackFor = Exception.class)。

④ 内部 catch：事务管理器只看到「方法正常返回」，于是提交。要局部失败不影响整体，用 REQUIRES_NEW 把内层独立出去。

⑤ 正解：运行时异常向外抛，代理捕获后 rollback。

**⑥ REQUIRES_NEW**：内层挂起外层事务、独立开一个，失败只回滚自己；外层捕获后继续提交。适合「记录日志/埋点不能拖垮主流程」的场景。

3.4 传播行为速查

传播行为 有外层事务时 典型用途
REQUIRED（默认） 加入外层 绝大多数业务
REQUIRES_NEW 挂起外层，新建 日志、审计、独立补偿
NESTED 保存点 局部失败可回滚到保存点
SUPPORTS 加入；无则非事务 查询
NOT_SUPPORTED 挂起外层 一定要脱离事务的操作
MANDATORY 必须在外层内，否则报错 强制调用方开事务
NEVER 有外层就报错 禁止事务的只读操作

3.5 动手验证：跑通这六个 case

预期观察点：case1/2/3/4 的 COUNT(*) 都是 1，case5 是 0，case6b 是 0。

判定标准：

  • 你以为有事务、COUNT(*)=1 → 代理没生效，按 3.3 的顺序查；
  • 想确认某个方法是否真的开了事务 → 在方法里 SELECT TRX_ID FROM information_schema.innodb_trx WHERE trx_mysql_thread_id = CONNECTION_ID()，或开 logging.level.org.springframework.transaction=DEBUG。

4. 动态数据源与事务边界

4.1 为什么「事务里切库」会失效

sequenceDiagram
    participant App
    participant DS as RoutingDataSource
    participant Tx as TransactionManager
    participant M as Master
    participant S as Replica
    App->>Tx: @Transactional begin
    Tx->>DS: getConnection()
    DS->>M: connect (write)
    Note over Tx: connection bound to transaction
    App->>DS: switch to replica
    DS-->>App: ignored - connection already bound
    App->>M: SELECT goes to master
现象 原因 处理
事务内切从库不生效 连接在事务开始时已绑定 切库发生在事务外（先查询后开事务）
事务方法里读写都走主库 同上 写后读走主库是有意为之，保证一致性
主从延迟读到旧数据 复制延迟（⑧） 强制走主库，或按 GTID 等待

结论：@Transactional + 动态数据源，路由只在事务开始时决定一次。想「读走从库、写走主库」，必须保证读操作在事务外，且能接受延迟。

4.2 主从路由的一致性代价

方案 一致性 实现成本 适用
全部走主库 强 0 写多、强一致
读写分离（无补偿） 弱 低 读多、能容忍延迟
写后强制读主（时间窗） 中 低 用户刚提交后跳转详情页
按 GTID 等待 强 高 强一致读

5. 总结

5.1 面试速答表

面试题 一句话答案
连接池越大越好吗 不是。吞吐 ≈ 池大小 / 单请求耗时，超过数据库承载能力只会把排队搬进 MySQL
池大小怎么定 QPS × 平均耗时，再留 20%~30% 余量；先优化 SQL 再谈加池
HikariCP 默认最大连接数 10（实测解析后值），connectionTimeout 默认 30 秒
池打满的表现 activeConnections = max + 线程等待，最终抛 SQLTransientConnectionException
怎么发现连接泄漏 开 leakDetectionThreshold，看告警里的持有堆栈
@Transactional 为什么失效 代理没拦住：自调用、非 public、非 Bean、异常被吞、受检异常、传播设置
受检异常会回滚吗 默认不会，只有 RuntimeException / Error 触发回滚，需 rollbackFor
自调用怎么解决 拆 Bean、注入自身代理、AopContext.currentProxy()
REQUIRES_NEW 用在哪 日志/审计等「失败也不能拖垮主流程」的独立事务
为什么事务里切数据源不生效 连接在事务开始时已绑定到事务管理器
读写分离怎么保证一致性 写后时间窗内强制读主，或按 GTID 等待

5.2 实战避坑表

症状 原因 处理
接口超时但数据库指标正常 连接池排队 看 activeConnections 与等待线程数
池打满无告警 SQLTransientConnectionException 没被单独监控 按异常类型配告警
加了 @Transactional 仍脏数据 自调用 / private / 吞异常 用 3.2 的六个 case 自测
事务提交了但日志里报错 受检异常 + 默认不回滚 加 rollbackFor = Exception.class
重启后连接泄漏消失 泄漏在代码里（未 close） 开泄漏检测，按堆栈修
从库读不到刚写的数据 主从延迟 写后读主，或按 GTID 等待

5.3 工具速查表

工具 看什么 判定标准
HikariPoolMXBean activeConnections / threadsAwaitingConnection 长期等于 max = 打满
leakDetectionThreshold 泄漏告警栈 有告警就是真泄漏
jstack 线程卡在哪 大量线程停在 getConnection = 池瓶颈
logging.level.org.springframework.transaction=DEBUG 事务 begin/commit/rollback 没有 begin 日志 = 代理没生效
information_schema.innodb_trx 事务年龄 age_s 大 = 长事务（⑤）

5.4 实操建议

  1. 池大小按公式算一次，再和实际值对比。多数系统的池是「抄来的 10 或 20」，不是算出来的。
  2. connectionTimeout 必须小于业务超时，否则请求会先被业务打挂，再被池打挂一次。
  3. 把 SQLTransientConnectionException 单独配告警，它的语义是「池满了」，可直接指向容量问题。
  4. 写一个 @Transactional 自测用例集（就是 3.2 那六个），放在项目里，比 Code Review 可靠。
  5. 事务里禁止 RPC、文件 IO、循环查询——这条在第⑤篇说过，在这里它直接表现为连接池占用时长。
