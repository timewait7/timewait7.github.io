Tomcat 深度解析：连接器、类加载与调优排障

Posted on 2026-08-13 In 框架 Word count in article: 6.2k Reading time ≈ 22 mins.

「你的应用是怎么跑起来的？」——Spring Boot 内嵌的 Tomcat 替你回答了这个问题的全部复杂度，但面试官问的就是这些被藏起来的细节：一个 HTTP 请求从网线到你的 Controller 经历了什么？为什么 Tomcat 要打破双亲委派？maxThreads/maxConnections/acceptCount 三个参数怎么配合？

本文按 「整体架构 → 线程模型 → 请求处理 → 类加载 → 调优排障」 五层讲透 Tomcat：每个概念配可运行验证 + Mermaid 图，读完你能在面试中画出请求旅程图，并在线上「Tomcat 线程打满/连接堆积」时知道先看什么。

1. 定位：Tomcat 在面试里的三个位置

面试问题 本质考点 本文章节
Tomcat 的架构？一个请求怎么走？ 连接器 + 容器两段式，IO 线程与业务线程分离 §2、§4
maxThreads / maxConnections / acceptCount 什么关系？ 连接缓冲深度与线程模型的配合 §3
Tomcat 为什么打破双亲委派？ 类加载器的隔离设计 §5

因果链主线：Tomcat 的全部设计都围绕一个矛盾——「Web 容器要同时服务很多请求（并发），但每个请求的 IO 很慢（网络）」。解法有两条：

  1. IO 线程只做读写不干活，业务线程池干活（连接器两段式）；
  2. 应用之间/应用与容器之间的类要隔离（WebappClassLoader）。

记住这两条，所有参数和机制都能推出来。

2. 整体架构：连接器 + 容器

2.1 两段式架构全景

Tomcat 的核心抽象只有两个：Connector（连接器） 和 Container（容器）。这是整个 Tomcat 的骨架。

flowchart LR
    Client[客户端<br/>浏览器/curl] -->|TCP 连接| Acceptor

    subgraph Connector["Connector 连接器"]

        Poller[Poller<br/>NIO Selector 多路复用]
        Worker[Worker 线程池<br/>maxThreads]
        Acceptor --> Poller --> Worker
    end

    Worker -->|Request/Response| Engine

    subgraph Container["Container 容器"]
        direction TB
        Engine[Engine<br/>顶层容器]
        Host[Host<br/>虚拟主机]
        Context[Context<br/>Web 应用]
        Wrapper[Wrapper<br/>Servlet 包装]
        Engine --> Host --> Context --> Wrapper
    end

    Wrapper -->|service| Servlet[Controller/Servlet<br/>业务代码]
    Servlet -.响应.-> Worker
    Worker -.写回 socket.-> Client

    style Connector fill:#e1f5ff

两个半场分工：

组件 职责 关注点
Connector 网络 IO + 协议解析，把 socket 变成 Request/Response 对象 端口监听（如 8080）、HTTP/1.1、HTTP/2、AJP
Container 请求分发 + Servlet 生命周期，从 Engine 逐层下钻到 Wrapper 应用隔离、路由、Servlet 管理

IO 与业务彻底分离——这是 Tomcat 能扛高并发的架构根基。

2.2 容器分层：Engine → Host → Context → Wrapper

容器为什么要分四层？一句话：分层是为了「多应用共存 + 每个应用独立管理」。

组件 职责 对应关系 数量
Engine 顶层容器，处理所有请求入口 一个 Tomcat 一个 1
Host 虚拟主机，按域名区分 server.xml 里一个 <Host> 0..N
Context 一个 Web 应用（一个 WAR/应用目录） Spring Boot 内嵌时就是你的应用 0..N
Wrapper 一个 Servlet 的包装 Spring MVC 的 DispatcherServlet 0..N

因果链：容器分层粒度 = 「一个 Tomcat 可以跑多个应用（多 Context），一个应用由多个 Servlet 组成」。

Spring Boot 内嵌 Tomcat 的区别：

  • 独立部署：多 Host 多 Context，Tomcat 独立进程；
  • 内嵌部署：单 Context（你的应用），Tomcat 生命周期由 Spring Boot 管理；
  • 但分层结构不变——Engine → Host → Context → Wrapper 依然存在。

2.3 动手验证：看一个请求的旅程

观察点：

  • lsof -i :8080 能看到 ESTABLISHED 连接（Acceptor 接收）；
  • Tomcat 是普通 Java 进程（一切跑在 JVM 上）。

判定标准：理解「Tomcat = 一个 Java 程序，用线程处理并发，用 socket 收发数据」——它没有魔法，就是 JVM 上的多线程网络程序，所以 Java 并发编程的线程模型知识全部适用。

3. 连接器：NIO 线程模型与三大参数

3.1 三个线程的职责分工

Tomcat NIO 连接器内部有 三类线程：

线程 职责 数量 阻塞点
Acceptor 只做 accept() 拿新连接 1 个（每端口） accept() 系统调用
Poller NIO Selector 多路复用，检测 socket 可读/可写 1-2 个（每端口） selector.select()
Worker 线程池 解析请求、执行业务 maxThreads（默认 200） 业务代码（用户逻辑） 
flowchart TB
    subgraph OS["操作系统"]
        TCP1[TCP 连接1]
        TCP2[TCP 连接2]
        TCPN[TCP 连接N]
    end

    subgraph Connector["NIO Connector"]
        A[Acceptor<br/>1 个线程<br/>循环 accept]
        Q[Poller 队列<br/>PollerEvent]
        P[Poller<br/>1-2 个线程<br/>Selector 轮询]
        W[Worker 线程池<br/>maxThreads=200]

        A -->|注册到 Poller| Q
        Q --> P
        P -->|socket 可读<br/>交给 Worker| W
    end

    subgraph Biz["业务处理"]
        S[Servlet.service]
        B[业务逻辑<br/>DB/缓存/API]
        S --> B
    end

    TCP1 --> A
    TCP2 --> A
    TCPN --> A
    W --> S
    B --> W

    style A fill:#ffe6e6
    style P fill:#e6f0ff
    style W fill:#e6ffe6

因果链：

  • NIO 模型下「一个 Poller 线程服务几千个连接」（Selector 多路复用）；
  • 所以 maxThreads 是「同时处理的请求数」，不是「连接数上限」；
  • 连接可以有几万个，同时干活的最多 200 个，其余在队列等待。

3.2 一次请求在连接器中的完整生命周期

把上面的三类线程串起来，一个请求从到达 socket 到进入业务代码，经历的完整步骤：

sequenceDiagram
    participant C as Client
    participant OS as 内核 TCP 队列
    participant A as Acceptor
    participant P as Poller
    participant W as Worker 线程
    participant S as Servlet

    C->>OS: 三次握手，连接建立
    Note over OS: 连接进入 accept 队列<br/>（acceptCount 控制长度）
    A->>OS: accept() 取连接
    A->>P: 注册 SocketChannel 到 Poller
    Note over P: Selector 轮询<br/>等待可读事件
    C->>P: 发送 HTTP 请求数据
    P->>P: select() 返回可读
    P->>W: 提交 SocketProcessor 到线程池
    Note over W: 从队列取任务<br/>若队列满 → 拒绝
    W->>W: 解析 HTTP 协议<br/>生成 Request/Response
    W->>S: 调用 service()
    S->>S: 执行业务逻辑
    S-->>W: 返回响应
    W-->>C: 写回 socket

关键理解：

  1. Acceptor 只负责 accept()，不做任何 IO 读写；
  2. Poller 用 Selector 管理成千上万个连接，只检测「谁就绪了」；
  3. Worker 从线程池取任务，才真正解析协议 + 执行业务。

这就是「IO 与业务分离」的落地方式。

3.3 maxThreads / maxConnections / acceptCount 三参数详解

参数 含义 默认值 超了会怎样
acceptCount TCP accept 队列长度（OS 层 backlog） 100 队列满 → connection refused（直接拒绝新连接）
maxConnections 连接器保持的最大连接数（含等待中的） 10000（NIO） 满了不再 accept，连接在 accept 队列排队
maxThreads 工作线程池上限，同时处理的请求数 200 线程全忙 → 新请求在等待队列（内部队列）排队

更细的补充：

  • acceptCount 是 OS 层参数：本质是 listen(fd, backlog) 的 backlog，Linux 下会被 net.core.somaxconn 截断；
  • maxConnections 是 Tomcat 层参数：达到上限后，Tomcat 不再从 OS 队列里 accept，新连接积压在 OS 队列；
  • maxThreads 是业务层参数：线程全忙时，请求进入 Tomcat 内部的 TaskQueue（默认无界）排队——无界队列意味着不会拒绝，只会越堆越多直到超时。

3.4 三级缓冲的排队模型

这是面试必画图——三个参数构成 三级缓冲，从外到内依次是：

flowchart TB
    New[新连接到达] --> Q1{OS accept 队列<br/>长度 = acceptCount<br/>默认 100}
    Q1 -->|队列满| R1[connection refused<br/>客户端收到 RST]
    Q1 -->|有空位| Q2{Tomcat 连接数<br/>< maxConnections?<br/>默认 10000}
    Q2 -->|已达上限<br/>不再 accept| Q1
    Q2 -->|未达上限| Q3{有空闲 Worker 线程?<br/>maxThreads 默认 200}
    Q3 -->|线程空闲| Run[立即处理]
    Q3 -->|线程全忙| Q4[Tomcat 内部 TaskQueue<br/>默认无界]
    Q4 -->|线程空闲后取任务| Run
    Q4 -.超时未处理.-> Timeout[请求超时<br/>connectionTimeout]

    style Q1 fill:#ffe6e6
    style Q2 fill:#fff4e6
    style Q3 fill:#e6f0ff
    style Q4 fill:#e6ffe6
    style R1 fill:#ffcccc
    style Timeout fill:#ffcccc

因果链：三参数是三级缓冲：

  • maxThreads 管「同时干活的」（最内层）；
  • maxConnections 管「连接能堆多少」（中间层）；
  • acceptCount 管「拒绝前的最后缓冲」（最外层）。

压测时先触达哪个，取决于负载形态：

负载形态 先触达 现象
请求密集但执行快 maxThreads 内部队列堆积，响应变慢
连接数暴涨（慢客户端多） maxConnections 新连接不 accept，OS 队列堆积
洪峰涌入 acceptCount connection refused

3.5 动手验证：压测观察三参数排队

观察点：

  • jstack 里 http-nio-8080-exec-N 线程数变化；
  • ab 结果里的 failed/complete 比例。

判定标准：能说出「调 maxThreads 是调吞吐上限，调 acceptCount 是调拒绝时机」——**别一压测失败就盲目调 maxThreads**。

4. 请求处理：Pipeline 与 Servlet 生命周期

4.1 Valve 责任链

容器每一层（Engine/Host/Context/Wrapper）都有一条 Pipeline，请求逐层穿过 Valve（责任链模式）：

flowchart LR
    Req[Request] --> EP[Engine Pipeline]
    EP --> EV1[Engine Valve]
    EV1 --> HP[Host Pipeline]
    HP --> HV1[Host Valve<br/>AccessLogValve]
    HV1 --> CP[Context Pipeline]
    CP --> CV1[Context Valve]
    CV1 --> WP[Wrapper Pipeline]
    WP --> WV1[Wrapper Valve]
    WV1 --> Filter[FilterChain<br/>Spring MVC]
    Filter --> Servlet[DispatcherServlet]
    Servlet --> Resp[Response]

    style EP fill:#e6f0ff
    style HP fill:#e6f0ff
    style CP fill:#e6f0ff
    style WP fill:#e6f0ff
    style Servlet fill:#ffe6e6

Valve vs Filter 的区别：

维度 Valve Filter
定义位置 Tomcat 容器层 Servlet 规范层
配置方式 server.xml / context.xml web.xml / @WebFilter
作用范围 整个容器（所有应用） 单个 Web 应用
典型用途 AccessLog、RemoteAddr 编码、鉴权、跨域

这是 AOP 思想的容器版——Spring 的拦截器是同一模式。

4.2 Servlet 三段生命周期

阶段 时机 说明
init 首次请求或启动时 只执行一次，做初始化
service 每次请求 线程池中的线程并发调用（多线程共享实例）
destroy 应用卸载 只执行一次，释放资源 
stateDiagram-v2
    [*] --> 未初始化
    未初始化 --> 初始化中: 首次请求 / load-on-startup
    初始化中 --> 就绪: init() 完成
    就绪 --> 服务中: service() 被调用
    服务中 --> 就绪: 请求结束
    就绪 --> 销毁: 应用卸载 / 容器关闭
    销毁 --> [*]: destroy() 完成

    note right of 服务中
        单实例，多线程并发
        service() 被线程池调用
        实例字段 = 共享状态
    end note

因果链（面试高频）：Servlet 是 单实例多线程——一个 Servlet 实例被所有请求共享，实例变量必须线程安全。

面试答「为什么 Controller 不该有实例变量」：

「单实例多线程 + 线程池并发调用，实例字段就是竞态源。」

常见误区：

  • ❌ @Service 里加 int count = 0; → 线程不安全；
  • ✅ 用 ThreadLocal 或者无状态设计；
  • ✅ 需要状态就用外部存储（Redis/DB）。

4.3 动手验证：看 Servlet 实例与线程

观察点：

  • instance= 每次一样 → 单实例；
  • thread= 每次不同 → 线程池并发。

判定标准：亲眼确认「Servlet 实例只有一个、线程是池里随便抽的」，理解实例变量的危险性。

5. 类加载：为什么打破双亲委派

5.1 双亲委派机制回顾

JVM 默认的类加载器层次（自顶向下）：

flowchart TB
    App[Application ClassLoader<br/>AppClassLoader<br/>加载 classpath]
    Ext[Extension ClassLoader<br/>ExtClassLoader<br/>加载 java.ext.dirs]
    Boot[Bootstrap ClassLoader<br/>C++ 实现<br/>加载 rt.jar / java.base]

    App -->|父| Ext
    Ext -->|父| Boot

    style Boot fill:#ffe6e6
    style Ext fill:#fff4e6
    style App fill:#e6ffe6

双亲委派规则：收到类加载请求时，先委托父加载器加载，父加载器加载不了才自己加载。

flowchart TB
    Start[需要加载 com.example.Foo] --> C1[AppClassLoader]
    C1 -->|委托| C2[ExtClassLoader]
    C2 -->|委托| C3[Bootstrap]
    C3 -->|找不到| C2
    C2 -->|找不到| C1
    C1 -->|自己找 classpath| Result[加载成功]

    style Start fill:#e6f0ff
    style Result fill:#e6ffe6

目的：保证核心类不被篡改（java.lang.String 永远由 Bootstrap 加载）。

5.2 Tomcat 的 WebappClassLoader 如何打破

Tomcat 的 WebappClassLoader 对 Web 应用类目录中的类，先自己找，找不到再委派父加载器：

flowchart TB
    Start[需要加载 com.example.Foo] --> Check{是否 JVM 核心类?<br/>java.* / javax.*}
    Check -->|是| Delegate1[委派给父加载器<br/>Bootstrap/Ext]
    Check -->|否| Check2{是否 Tomcat 容器类?<br/>org.apache.catalina.*}
    Check2 -->|是| Delegate2[委派给 Common ClassLoader]
    Check2 -->|否| Local[从 WEB-INF/classes<br/>WEB-INF/lib 自己加载]
    Local -->|找不到| Delegate3[再委派父加载器]
    Delegate1 --> End[加载完成]
    Delegate2 --> End
    Delegate3 --> End

    style Local fill:#e6ffe6
    style Check fill:#ffe6e6
    style Check2 fill:#ffe6e6

为什么这样设计？两个核心原因：

理由 场景 双亲委派的问题
应用类隔离 同一 Tomcat 部署两个应用，各自带不同版本的 Spring 双亲委派会让先加载的版本被所有应用共享，版本冲突
热部署 应用重新部署时旧类加载器整体作废换新的 双亲委派下父加载器会缓存类，无法替换

边界（面试要答全）：

  • 对应用类（WEB-INF/classes、WEB-INF/lib）：先自己加载；
  • 对 javax.servlet.* 等 Servlet 规范类：仍然委派（容器自身规范类不能重载）；
  • 对 java.* 等 JVM 核心类：仍然委派 Bootstrap。

完整答案：『打破双亲委派有两个原因——多应用类隔离 + 热部署；但规范类与核心类仍走委派』，两个原因 + 边界都说全才是完整答案。

5.4 热部署与类加载器泄漏

热部署的原理：应用重新部署时，Tomcat 会丢弃旧的 WebappClassLoader 整个实例，创建新的加载器重新加载类。

sequenceDiagram
    participant Admin as 管理员
    participant Tomcat as Tomcat
    participant Old as 旧 WebappClassLoader
    participant New as 新 WebappClassLoader
    participant App as 应用

    Admin->>Tomcat: 重新部署 /app
    Tomcat->>Old: 停止所有 Servlet
    Tomcat->>Old: destroy() 释放资源
    Tomcat->>Old: 丢弃引用，等待 GC
    Note over Old: 如果无外部引用<br/>GC 会回收整个加载器<br/>连带所有类
    Tomcat->>New: 创建新 WebappClassLoader
    New->>App: 重新加载所有类
    App-->>Admin: 部署完成

类加载器泄漏：如果应用里有线程/ThreadLocal/静态变量持有 WebappClassLoader 的引用，旧加载器无法被 GC，导致 Metaspace OOM。

常见泄漏源：

  • ThreadLocal 未清理，且线程是 Tomcat 线程池的；
  • DriverManager 注册的 JDBC 驱动（Tomcat 会警告）；
  • 定时器线程未停止；
  • 自定义 ClassLoader 未释放。

排查方式：jmap -clstats <pid> 看类加载器数量，或 jcmd <pid> GC.class_stats。

6.1 调优参数速查

因果链（排障核心）：Tomcat 故障的本质只有三类——

  1. 线程池耗尽（业务慢/死锁）；
  2. 连接池耗尽（连接泄漏）；
  3. accept 队列满（洪峰/慢客户端）。

**先判断是哪一类，再对症调参，不要一慢就调 maxThreads**。

6.3 动手验证：制造并定位线程池耗尽

观察点：

  • 线程数到 maxThreads 后请求开始排队；
  • jstack 显示线程全在业务代码里 → 瓶颈是业务慢，不是容器参数。

判定标准：能说出「调 maxThreads 是治标，治本是查业务为什么慢」——容器参数只决定排队深度，不决定处理速度。

7. 面试应答：Tomcat 五连问

7.1 完整话术

面试题 回答要点
Tomcat 架构？ 连接器 + 容器两段式：Connector 管 IO 与协议解析，Container（Engine→Host→Context→Wrapper）管分发与 Servlet 生命周期
NIO 线程模型？ Acceptor 收连接 → Poller 多路复用 → 工作线程池执行业务，IO 与业务分离
三参数关系？ maxThreads 管同时干活数、maxConnections 管连接上限、acceptCount 管拒绝前缓冲；三级缓冲
为什么打破双亲委派？ 多应用类隔离 + 热部署；但规范类与核心类仍委派
Servlet 为什么单实例多线程？ 容器设计如此；实例变量是共享状态，必须线程安全
内嵌 Tomcat 与独立部署区别？ 架构相同；内嵌单 Context、生命周期由 Spring Boot 管理

7.2 深挖：与 Netty 的对照

flowchart LR
    subgraph Tomcat["Tomcat 线程模型"]
        TA[Acceptor] --> TP[Poller]
        TP --> TW[Worker 线程池<br/>可阻塞]
        TW --> TB[业务代码]
    end

    subgraph Netty["Netty 线程模型"]
        NB[Boss EventLoop] --> NW[Worker EventLoop<br/>不可阻塞]
        NW --> NH[ChannelHandler]
        NH --> NH2[业务处理<br/>必须快速返回]
    end

    style TW fill:#e6ffe6
    style NW fill:#ffe6e6
维度 Tomcat Netty
定位 Web 容器（HTTP 应用服务） 通用网络框架（任意协议）
线程模型 Acceptor + Poller + 工作线程池 Boss + Worker EventLoop
IO 模型 NIO（BIO 可切换） NIO/EPOLL 原生
业务执行 线程池（可阻塞） EventLoop 内不可阻塞（阻塞会拖死同 EventLoop 的所有连接）
并发规模 万级连接 十万级连接

一句话：Tomcat 是「Netty 思想的服务化产物」——都用多路复用 + 线程池，但 Tomcat 允许业务线程阻塞（用线程池隔离），Netty 的 EventLoop 模型不允许（阻塞即灾难）。

面试被问「Tomcat 和 Netty 的线程模型区别」，答出「业务可阻塞 vs 不可阻塞」就是区分点。

8. 总结

8.1 面试速答表

面试题 一句话答案
请求怎么走完 Tomcat？ 连接器收连接+解析 → 容器分发（Engine→Host→Context→Wrapper）→ Servlet 处理 → 原路返回
为什么 NIO 能扛大并发？ Poller 一个线程 Selector 管理几千连接，工作线程只处理就绪请求
maxThreads 是多少？ 默认 200，同时处理请求数上限，不是连接数上限
connection refused 是哪个参数满了？ acceptCount 队列满（TCP backlog 层）
打破双亲委派为了什么？ 应用类隔离 + 热部署；JVM 核心类与规范类仍委派
Servlet 生命周期？ init 一次 → service 多线程并发 → destroy 一次
压测慢先查什么？ 先分三类：线程池耗尽/连接池耗尽/accept 队列满，别盲目调 maxThreads

8.2 实战避坑表

症状 原因 处理
一压测就 500 线程池拒绝（RejectedExecutionException） 查业务耗时，必要时 maxThreads 配合调
connection refused 频繁 acceptCount 满了 加大 + 客户端 keep-alive 复用连接
偶发超时 慢客户端占连接 调小 connectionTimeout
重启后偶发类找不到 应用类加载顺序 检查是否依赖了 WebappClassLoader 的隔离边界
实例变量错乱 Servlet 单实例多线程共享状态 去掉实例可变字段，用 ThreadLocal/无状态
端口被占 内嵌 Tomcat 端口冲突 检查 server.port 与已启动实例
Metaspace OOM 类加载器泄漏（热部署多次后） 检查 ThreadLocal、JDBC 驱动、定时器
