Tomcat 深度解析：连接器、类加载与调优排障

Posted on 2026-08-13 In 框架 Word count in article: 12k Reading time ≈ 44 mins.

「你的应用是怎么跑起来的？」——Spring Boot 内嵌的 Tomcat 替你回答了这个问题的全部复杂度，但面试官问的就是这些被藏起来的细节：一个 HTTP 请求从网线到你的 Controller 经历了什么？为什么 Tomcat 要打破双亲委派？maxThreads / maxConnections / acceptCount 三个参数怎么配合？Spring Boot 是怎么把 Tomcat 嵌进来的？

本文按 「定位 → 整体架构 → 启动流程 → 连接器线程模型 → 请求处理 → 类加载 → Spring Boot 内嵌 → Session/安全/日志 → 调优排障 → 生产部署 → 面试应答」 十一层讲透 Tomcat：每个概念配可运行验证 + Mermaid 图，读完你能在面试中画出请求旅程图，并在线上「Tomcat 线程打满 / 连接堆积 / 类加载泄漏」时知道先看什么。

1.2 因果链主线

Tomcat 的全部设计都围绕一个矛盾——「Web 容器要同时服务很多请求（并发），但每个请求的 IO 很慢（网络）」。解法有两条：

  1. IO 线程只做读写不干活，业务线程池干活（连接器两段式）；
  2. 应用之间 / 应用与容器之间的类要隔离（WebappClassLoader）。

记住这两条，所有参数和机制都能推出来。

2.4 独立部署 vs Spring Boot 内嵌

维度 独立部署 Spring Boot 内嵌
Tomcat 位置 独立进程，应用打成 WAR 丢进 webapps Tomcat 作为依赖打进应用的 jar
启动方式 catalina.sh start java -jar app.jar
Host / Context 多 Host、多 Context 单 Host、单 Context（你的应用）
生命周期 Tomcat 管理应用 Spring Boot 管理 Tomcat
配置方式 server.xml、context.xml application.yml、WebServerFactoryCustomizer
部署灵活度 一个 Tomcat 部署多个应用 一个应用一个进程，天然隔离
典型场景 传统企业应用、多应用共用 Tomcat 微服务、Spring Cloud、K8s

但分层结构不变——Engine → Host → Context → Wrapper 依然存在，只是内嵌模式下 Engine 和 Host 是默认创建的空壳。

2.5 动手验证：看一个请求的旅程

观察点：

  • lsof -i :8080 能看到 ESTABLISHED 连接（Acceptor 接收）；
  • Tomcat 是普通 Java 进程（一切跑在 JVM 上）。

判定标准：理解「Tomcat = 一个 Java 程序，用线程处理并发，用 socket 收发数据」——它没有魔法，就是 JVM 上的多线程网络程序，所以 Java 并发编程的线程模型知识全部适用。

4. 连接器：NIO 线程模型、协议与三大参数

4.1 三个线程的职责分工

Tomcat NIO 连接器内部有 三类线程：

线程 职责 数量 阻塞点
Acceptor 只做 accept() 拿新连接 1 个（每端口） accept() 系统调用
Poller NIO Selector 多路复用，检测 socket 可读/可写 1-2 个（每端口） selector.select()
Worker 线程池 解析请求、执行业务 maxThreads（默认 200） 业务代码（用户逻辑）

因果链：

  • NIO 模型下「一个 Poller 线程服务几千个连接」（Selector 多路复用）；
  • 所以 maxThreads 是「同时处理的请求数」，不是「连接数上限」；
  • 连接可以有几万个，同时干活的最多 200 个，其余在队列等待。

4.2 一次请求在连接器中的完整生命周期

把上面的三类线程串起来，一个请求从到达 socket 到进入业务代码，经历的完整步骤：

sequenceDiagram
    participant C as Client
    participant OS as 内核 TCP 队列
    participant A as Acceptor
    participant P as Poller
    participant W as Worker 线程
    participant S as Servlet

    C->>OS: 三次握手，连接建立
    Note over OS: 连接进入 accept 队列<br/>（acceptCount 控制长度）
    A->>OS: accept() 取连接
    A->>P: 注册 SocketChannel 到 Poller
    Note over P: Selector 轮询<br/>等待可读事件
    C->>P: 发送 HTTP 请求数据
    P->>P: select() 返回可读
    P->>W: 提交 SocketProcessor 到线程池
    Note over W: 从队列取任务<br/>若队列满 → 拒绝
    W->>W: 解析 HTTP 协议<br/>生成 Request/Response
    W->>S: 调用 service()
    S->>S: 执行业务逻辑
    S-->>W: 返回响应
    W-->>C: 写回 socket

关键理解：

  1. Acceptor 只负责 accept()，不做任何 IO 读写；
  2. Poller 用 Selector 管理成千上万个连接，只检测「谁就绪了」；
  3. Worker 从线程池取任务，才真正解析协议 + 执行业务。

这就是「IO 与业务分离」的落地方式。

4.3 NIO 连接器内部组件

Tomcat NIO 连接器的核心内部类：

组件 职责
NioEndpoint NIO 连接器实现，管理 Acceptor / Poller / Worker
Acceptor 独立线程，循环调用 serverSocket.accept()
Poller 独立线程，持有 Selector，轮询就绪的 SocketChannel
PollerEvent Acceptor 注册连接的事件，放入 Poller 的队列
SocketProcessor 可运行任务，提交到 Worker 线程池执行协议解析
Http11Processor HTTP/1.1 协议解析器，生成 Request / Response
NioChannel 封装 SocketChannel + SocketBufferHandler
NioSelectorPool Selector 池，用于阻塞写（大响应时）

为什么 Poller 只有 1-2 个线程却能管几千连接？

因为 NIO 的 Selector.select() 是多路复用——一个线程就能监听成千上万个 Channel 的可读/可写事件。这是 NIO 相对 BIO 的核心优势。

4.4 三大参数详解

参数 含义 默认值 超了会怎样
acceptCount TCP accept 队列长度（OS 层 backlog） 100 队列满 → connection refused（直接拒绝新连接）
maxConnections 连接器保持的最大连接数（含等待中的） 10000（NIO） 满了不再 accept，连接在 accept 队列排队
maxThreads 工作线程池上限，同时处理的请求数 200 线程全忙 → 新请求在等待队列（内部队列）排队

更细的补充：

  • acceptCount 是 OS 层参数：本质是 listen(fd, backlog) 的 backlog，Linux 下会被 net.core.somaxconn 截断；
  • maxConnections 是 Tomcat 层参数：达到上限后，Tomcat 不再从 OS 队列里 accept，新连接积压在 OS 队列；
  • maxThreads 是业务层参数：线程全忙时，请求进入 Tomcat 内部的 TaskQueue（默认无界）排队——无界队列意味着不会拒绝，只会越堆越多直到超时。

相关参数补充：

参数 默认值 说明
minSpareThreads 10 最小空闲线程数，低于此值会创建新线程
threadPriority 5 线程优先级

keepAliveTimeout 同 connectionTimeout keep-alive 超时
maxKeepAliveRequests 100 单连接最多复用多少次
maxHttpHeaderSize 8192 HTTP 头最大字节数
maxPostSize 2MB POST 表单最大字节数

默认是单例（@Controller / @RestController 默认 singleton）。所以 Controller 不能有非线程安全的实例变量——这是 Spring 与 Tomcat 的联合约束。

Tomcat 的 WebappClassLoader 对 Web 应用类目录中的类，先自己找，找不到再委派父加载器：

    Start[需要加载 com.example.Foo] --> Check{是否 JVM 核心类?<br/>java.* / javax.*}

    Delegate3 --> End

为什么这样设计？两个核心原因：

理由 场景 双亲委派的问题
应用类隔离 同一 Tomcat 部署两个应用，各自带不同版本的 Spring 双亲委派会让先加载的版本被所有应用共享，版本冲突
热部署 应用重新部署时旧类加载器整体作废换新的 双亲委派下父加载器会缓存类，无法替换

边界（面试要答全）：

  • 对应用类（WEB-INF/classes、WEB-INF/lib）：先自己加载；
  • 对 javax.servlet.* 等 Servlet 规范类：仍然委派（容器自身规范类不能重载）；
  • 对 java.* 等 JVM 核心类：仍然委派 Bootstrap。

完整答案：『打破双亲委派有两个原因——多应用类隔离 + 热部署；但规范类与核心类仍走委派』，两个原因 + 边界都说全才是完整答案。

6.4 热部署与类加载器泄漏

热部署的原理：应用重新部署时，Tomcat 会丢弃旧的 WebappClassLoader 整个实例，创建新的加载器重新加载类。

sequenceDiagram
    participant Admin as 管理员
    participant Tomcat as Tomcat
    participant Old as 旧 WebappClassLoader
    participant New as 新 WebappClassLoader
    participant App as 应用

    Admin->>Tomcat: 重新部署 /app
    Tomcat->>Old: 停止所有 Servlet
    Tomcat->>Old: destroy() 释放资源
    Tomcat->>Old: 丢弃引用，等待 GC
    Note over Old: 如果无外部引用<br/>GC 会回收整个加载器<br/>连带所有类
    Tomcat->>New: 创建新 WebappClassLoader
    New->>App: 重新加载所有类
    App-->>Admin: 部署完成

类加载器泄漏：如果应用里有线程 / ThreadLocal / 静态变量持有 WebappClassLoader 的引用，旧加载器无法被 GC，导致 Metaspace OOM。

常见泄漏源：

  • ThreadLocal 未清理，且线程是 Tomcat 线程池的；
  • DriverManager 注册的 JDBC 驱动（Tomcat 会警告）；
  • 定时器线程未停止；
  • 自定义 ClassLoader 未释放；
  • 第三方库缓存了类加载器引用（如日志框架、Fastjson 的 ASM 缓存）。

排查方式：

Tomcat 自带的泄漏检测：context.xml 中配置 <Context clearReferencesStopThreads="true"> 可在应用停止时强制停止泄漏线程（有风险，生产慎用）。

因果链（排障核心）：Tomcat 故障的本质只有四类——

  1. 线程池耗尽（业务慢/死锁）；
  2. 连接池耗尽（连接泄漏）；

  4. 类加载器泄漏（Metaspace OOM）。

9.3 动手验证：制造并定位线程池耗尽

观察点：

  • 线程数到 maxThreads 后请求开始排队；
  • jstack 显示线程全在业务代码里 → 瓶颈是业务慢，不是容器参数。

判定标准：能说出「调 maxThreads 是治标，治本是查业务为什么慢」——容器参数只决定排队深度，不决定处理速度。

现象：应用运行一段时间后，数据库连接池耗尽，或者 Tomcat 连接数异常增长。

11.4 深挖：常见追问

Q1：Tomcat 的 maxThreads 设置多少合适？

没有固定值。IO 密集型可以 CPU × 2 以上（甚至 500+），CPU 密集型不超过 CPU 核数。关键看业务耗时：如果单请求 10ms，200 线程理论 QPS = 20000；如果单请求 1s，200 线程 QPS 只有 200。先压测，再定参。

Q2：Tomcat 为什么默认 maxThreads=200？

历史经验值。200 线程对多数 Web 应用足够，且不会因为线程过多导致上下文切换开销。但现代高并发场景常调到 400~800。

Q3：Tomcat 的 Connector 可以配多个吗？

可以。一个 Service 可以有多个 Connector（如 HTTP 8080 + HTTPS 8443 + AJP 8009），共享同一个 Engine。但生产建议只开必要的。

Q4：Tomcat 的 Session 和 Cookie 关系？

Session 存在服务端，通过 JSESSIONID Cookie 关联客户端。Cookie 被禁用时可用 URL 重写（;jsessionid=xxx），但不安全，生产建议只用 Cookie。

Q5：Tomcat 支持 HTTP/2 吗？

支持（Tomcat 8.5+）。配置 server.http2.enabled=true 或 <Connector><UpgradeProtocol className="org.apache.coyote.http2.Http2Protocol"/></Connector>。但 HTTP/2 需要 HTTPS 才生效（浏览器限制）。

Q6：Tomcat 的 WAR 和 JAR 部署区别？

WAR 是传统 Java Web 应用打包方式，丢进 webapps 自动解压部署；JAR 是 Spring Boot 内嵌方式，java -jar 启动。WAR 适合多应用共用 Tomcat，JAR 适合微服务独立部署。
