Pipeline、事务与 Lua：原子性和 RTT 怎么兼得

Posted on 2026-10-25 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

Redis 的事务没有回滚。 这不是 bug，是设计取舍：MULTI 里 SET 成功、INCR 失败，EXEC 之后 SET 的值照样在库里——本文实测，GET 回来的是 hello，而 EXEC 的返回里躺着一条 ERR value is not an integer。

这一篇把三种「批量 + 原子」手段量清楚：MULTI/EXEC、WATCH 乐观锁、Lua 脚本。1000 次 INCR 的实测是 105 ms（逐条）→ 2.2 ms（pipeline）→ 2.9 ms（MULTI + pipeline），而 Cluster 下 Lua 还有一个硬约束：所有 key 必须落在同一个槽。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua（本文） → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：② 测出 pipeline 能提升 18 倍，本文把它和事务组合起来量；⑤ 说「Lua 不可打断」，本文给出边界与 Cluster 限制；⑪ 的分布式锁用到的 SET NX + Lua 释放，就是本文机制的工程化。

1. 三个需求，三种手段

需求 手段 是否原子 省 RTT
批量发命令，少等几次 pipeline ❌ 不保证 ✅ 最强
多条命令当一组执行 MULTI/EXEC ⚠️ 部分（不回滚） ✅ 配合 pipeline
「先判断再修改」不被打断 Lua 或 WATCH ✅ Lua 真原子 ✅ 一次往返

先记住这张表：pipeline 解决「网络」，MULTI 解决「打包」，Lua 解决「判断+修改」的原子性。三者不是替代关系。

1.1 实测：1000 次 INCR 的三种写法

同一个实例、同一个客户端（loopback）：

写法 总耗时 每次操作 相对逐条
逐条 INCR 104.9 ms 105 µs 1×
pipeline（一次发 1000 条） 2.2 ms 2.2 µs 48×
MULTI + pipeline + EXEC 2.9 ms 2.9 µs 36×

三个可以直接拿走的数字：

  1. 逐条 105 µs/次，其中 Redis 执行 INCR 只要 0.1 µs 左右（② 实测），99.9% 是往返；
  2. pipeline 把 105 µs 摊到 2.2 µs；
  3. **MULTI 的代价是 32%**（2.2 → 2.9 ms）——事务不是免费的，它要在服务端维护队列与状态。
flowchart LR
    A["1000 INCR<br/>sequential 104.9ms"] --> B["pipeline<br/>2.2ms (48x)"]
    B --> C["MULTI + pipeline<br/>2.9ms (36x)"]
    C -.->|"+32% overhead"| D["atomic grouping<br/>but no rollback"]

2. MULTI/EXEC：不是事务，是「排队后一起执行」

2.1 机制：先入队，EXEC 才执行

sequenceDiagram
    participant C as Client
    participant R as Redis
    C->>R: MULTI
    R-->>C: OK
    C->>R: SET mykey hello
    R-->>C: QUEUED
    C->>R: INCR mykey
    R-->>C: QUEUED
    C->>R: EXEC
    R-->>C: [OK, ERR value is not an integer]
    Note over R: both commands run,<br/>no rollback on the failed one

MULTI 之后命令只是入队，EXEC 时才按顺序一次性执行。执行期间不会插入其他客户端的命令——这一点保证了「不被别人打断」，但不保证「失败就撤销」。

2.2 实测：运行期错误不回滚

实测输出：

INCR 失败了，但 SET mykey hello 已经落库。 这就是「Redis 事务不支持回滚」的具体表现。

2.3 实测：入队期错误会让整个事务作废

实测输出：

错误类型 发生时机 结果
命令不存在、参数个数不对 入队时 EXECABORT，全部不执行
类型错误、key 不存在等 执行时 该条报错，其他照常生效

这一对差异要背下来：入队期错误是「事务级失败」，执行期错误是「单命令失败」。

2.4 深挖：为什么 Redis 不回滚

回滚需要 undo 日志或 MVCC（MySQL 的那套，见 MySQL 系列 ⑤）。Redis 的定位是「极简 + 极快」，加回滚意味着：

代价 说明
内存 每条命令都要保留旧值
复杂度 回滚逻辑要处理所有数据结构
性能 写路径变重，失去「单线程无锁」的优势

所以官方的态度很明确：要么在应用层保证命令不会失败（先检查类型），要么用 Lua 做「检查 + 执行」的原子组合。

2.5 隔离性：EXEC 期间不会被插队，但 MULTI 到 EXEC 之间会

阶段 其他客户端能否插入
MULTI → EXEC 之间（还在入队） 能（你的命令还没执行，别人的命令照常执行）
EXEC 执行期间 不能（单线程连续执行）
Lua 执行期间 不能

这意味着：如果你在 MULTI 和 EXEC 之间读取外部状态，读到的可能已经过期——这正是 WATCH 要解决的问题。

3. WATCH：乐观锁

3.1 机制与实测

sequenceDiagram
    participant A as Client A
    participant B as Client B
    participant R as Redis
    A->>R: WATCH balance
    A->>R: GET balance -> 100
    B->>R: SET balance 999
    A->>R: MULTI
    A->>R: SET balance 50
    A->>R: EXEC
    R-->>A: (nil)  <- aborted, nobody executed

实测（两个连接）：

场景 EXEC 返回 最终值
期间被其他客户端改过 None（nil） 999（A 的写入未生效）
期间没人改 ['OK'] 77

3.2 正确用法：重试循环

3.3 局限：冲突率高时重试很贵

场景 冲突率 建议
分散的用户余额 低 WATCH 够用
秒杀热点库存 极高 用 Lua（一次成功，不重试）
批量对账 低 WATCH + 批量

判据：如果同一秒内有几十个请求改同一个 key，WATCH 的重试次数会急剧上升；这类热点应该用 Lua 把「判断 + 修改」压成一次原子操作。

4. Lua：把多步变成一步

4.1 实测：Lua 的错误同样不回滚

实测输出：

和 MULTI 一样：脚本出错前的写入不回滚。 想做到「要么全成要么全不成」，脚本必须自己保证操作不会在中途失败（例如先用 TYPE 检查）。

4.2 实测：Lua 做库存扣减

库存 100，连续扣 1000 次：

指标 实测
成功次数 100（一次不多、一次不少）
剩余库存 0
总耗时 119 ms（1000 次）
单次 119 µs（含往返）

为什么它比 WATCH 靠谱：WATCH 在冲突时要重试，而 Lua 在服务端一次完成「读 - 判断 - 减」，天然没有重试成本。这也是秒杀类场景的标准做法。

4.3 深挖：Cluster 下所有 key 必须在同一个槽

单机版随便写，集群版有硬约束。实测一个 cluster-enabled 实例上的槽计算：

key 槽
mykey 14687
user:1:name 12440
user:2:name 15992（不同槽）
{user:1}:name 10778
{user:1}:age 10778（同槽 ✅）

跨槽执行脚本，实测报错：

{} 叫 hash tag：只对花括号里的内容计算 CRC16。所以「同一个用户的数据要原子操作」时，key 应设计成 {user:1}:name、{user:1}:age。

flowchart LR
    K1["user:1:name<br/>slot 12440"] --> N1["Node A"]
    K2["user:2:name<br/>slot 15992"] --> N2["Node B"]
    K3["{user:1}:name<br/>slot 10778"] --> N3["Node C"]
    K4["{user:1}:age<br/>slot 10778"] --> N3
    N1 -.->|"CROSSSLOT"| N2

4.4 危险：脚本不可中断

⑤ 实测过：300 万次空循环的脚本阻塞 4 ms。Lua 的危险在于它没有超时（有 busy-reply-threshold，默认 5 秒后才开始报 busy，但执行不会停），一旦脚本里有 O(N) 操作，就是整实例停顿。

脚本内操作 风险
固定几次 GET/SET 安全
循环遍历大集合 危险（O(N)）
循环里多次 redis.call 次数 × 单次耗时，叠加
KEYS / SMEMBERS 全量 禁止

5. 组合姿势

5.1 什么时候用哪个

场景 选择 理由
批量写 1000 条日志 pipeline 不需要原子
转账（扣 A 加 B） Lua 需要「判断 + 修改」原子
读-改-写且冲突低 WATCH + MULTI 实现简单，重试少
热点库存扣减 Lua 冲突率高，不能重试
缓存批量预热 pipeline 纯写，无原子需求
分布式锁释放 Lua（比较 value 再删） 必须原子（⑪）

5.2 三个常见错误

错误 后果 正确做法
pipeline 里夹 WATCH WATCH 在 pipeline 中语义混乱，容易误判冲突 WATCH 单独发，再开 MULTI + pipeline
Lua 里做全量遍历 阻塞整实例 拆成 SCAN + 多次调用
依赖 MULTI 回滚 数据半提交 用 Lua 或应用层补偿

5.3 与 MySQL 系列对照

维度 MySQL（⑤） Redis（本文）
原子性实现 undo 回滚 + redo 持久 单线程连续执行，无回滚
隔离性 MVCC + 锁 单线程天然串行
「事务」语义 全成功或全失败 只有「连续执行」，失败不撤销
判断+修改 SELECT ... FOR UPDATE Lua 或 WATCH

一句话：MySQL 的事务是「要么全成要么全不成」，Redis 的事务是「中间不会被打断，但可能一半成功」。

7. 动手验证：四个可复现实验

7.1 动手验证：量一次 pipeline 的加速比

预期观察点：-P 16 的 rps 是 -P 1 的 10 倍以上（本文 11~18 倍），同时 p50 变大。

判定标准：提升不到 2 倍 → 瓶颈不在 RTT（可能是大 value 或 CPU）。

7.2 动手验证：验证运行期错误不回滚

预期观察点：EXEC 返回 1) OK 2) (error) ERR value is not an integer，GET mykey 仍是 hello。

判定标准：如果 GET 是 nil，说明你在 MULTI 之前就有语法错误，或事务根本没执行。

7.3 动手验证：验证 WATCH 的乐观锁

预期观察点：A 的 EXEC 返回 (nil)，说明事务被取消，balance 保持 999。

判定标准：返回 OK → 说明 B 的修改发生在 A 的 WATCH 之前或 EXEC 之后，时序没构造对。

7.4 动手验证：验证跨槽限制

预期观察点：两个 {user:1}:* 返回同一个槽号；跨槽 EVAL 返回 CROSSSLOT 错误。

判定标准：单机实例不支持 CLUSTER KEYSLOT（报 cluster support disabled），需要 --cluster-enabled yes 的实例。

6. 总结

6.1 面试速答表

面试题 一句话答案
Redis 事务支持回滚吗 不支持。执行期错误只让该条失败，其他照常生效（实测 SET 生效、INCR 报错）
入队期错误会怎样 EXECABORT，整个事务都不执行
MULTI 能省 RTT 吗 要配合 pipeline；实测 1000 次 INCR 从 105 ms 降到 2.9 ms（36×）
MULTI 比 pipeline 多多少开销 实测多 32%（2.9 ms vs 2.2 ms）
WATCH 是什么 乐观锁：被监视的 key 在 EXEC 前被改过，EXEC 返回 nil
WATCH 适合什么场景 冲突率低的读-改-写；冲突高用 Lua
Lua 是原子的吗 是（单线程连续执行，不被打断），但出错前的写入不回滚
Lua 在 Cluster 下的限制 所有 key 必须同一个槽，用 {hash tag} 保证
跨槽执行脚本会怎样 实测报 CROSSSLOT Keys in request don't hash to the same slot
秒杀扣库存用哪个 Lua，一次原子完成「读-判断-减」，实测 1000 次只成功 100 次
Lua 有什么风险 不可中断，O(N) 脚本会阻塞整实例（⑤ 实测 300 万次循环 4 ms）
pipeline 和 Lua 怎么选 只省 RTT 用 pipeline；需要原子逻辑用 Lua

6.2 实战避坑表

症状 原因 处理
事务里一半成功 依赖了 Redis 的回滚 用 Lua 或应用层补偿
EXEC 返回 nil WATCH 的 key 被改过 加重试循环
秒杀超卖 用了「读 + 判断 + 写」非原子 改 Lua
Cluster 迁移后脚本报错 key 跨槽 加 {} hash tag
偶发整实例卡顿 Lua 里有 O(N) 拆脚本，限迭代次数
pipeline 后数据不一致 误以为 pipeline 是原子的 pipeline 只省网络，不保证原子

6.3 工具速查表

工具 看什么 判定标准
MULTI / EXEC 打包执行 返回 nil = 被 WATCH 取消
WATCH 乐观锁 冲突率高就换 Lua
EVAL / EVALSHA 原子逻辑 用 SCRIPT LOAD + EVALSHA 省带宽
CLUSTER KEYSLOT key 落在哪个槽 同槽才能一起原子操作
INFO commandstats eval 的耗时 usec_per_call 高的脚本要拆
SLOWLOG 脚本总耗时 > 10 ms 的脚本不进在线链路

6.4 实操建议

  1. 别把 MULTI 当事务用。它只保证「不被打断」，不保证「失败回滚」。
  2. 批量优先 pipeline，需要原子再叠加 MULTI，两者用同一个连接。
  3. 「判断 + 修改」一律 Lua（扣库存、限额、锁释放），并保证 key 同槽。
  4. 集群下先设计 key 的 hash tag，否则上线后改 key 名就是数据迁移。
  5. **脚本里禁止 O(N)**，并给脚本加「最多操作 N 个 key」的自我保护。
