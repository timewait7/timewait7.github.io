单线程：为什么快，什么时候会卡

Posted on 2026-10-25 In 数据存储 Word count in article: 4k Reading time ≈ 15 mins.

一条 KEYS * 让 Redis 卡了 117 毫秒，而这段时间里所有客户端的 PING 最大延迟正好也是 117 毫秒。这不是巧合，是单线程的物理事实：Redis 执行一条命令时，其他所有请求排队。

本文把「阻塞」从形容词变成数字：用探针客户端每 100 微秒发一次 PING，另一边执行 KEYS *、DEL 大 key、重 Lua、BGSAVE，测出每种操作的阻塞时长——从 156 毫秒到 7 微秒，差四个数量级。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞（本文） → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：③ 算出「DEL 100 万 field 的 hash 会读多少内存」，本文把它换算成「阻塞 156 毫秒」；④ 的「Lua 绕过 maxmemory」在本文变成「Lua 阻塞主线程」。

1. 单线程的本质

1.1 一个循环，一次一条命令

flowchart LR
    E["epoll_wait<br/>等待就绪 fd"] --> R["read 请求"]
    R --> P["解析协议"]
    P --> X["执行命令<br/>（单线程，不可打断）"]
    X --> W["写回复"]
    W --> E
    X -.->|"执行期间<br/>其他请求全部排队"| Q["其他客户端"]
阶段 谁在做 能否并行
等待连接就绪 epoll（主线程） 是（内核）
读 socket / 解析协议 主线程（可用 io-threads 分担） 是（可选）
执行命令 主线程 否
写回复 主线程（可用 io-threads） 是（可选）

关键：io-threads 能分担读写，但命令执行永远只有一个线程（② 的实测也证明了小 value 场景开 io-threads 没有收益）。

1.2 为什么这样还能快

原因 数字
纯内存 GET 服务端执行 0.07 µs（② 实测）
无锁无切换 单线程，没有上下文切换与锁竞争
命令短 一条命令几十纳秒到几十微秒

代价也很明确：没有「抢占」，谁在执行谁就独占。你的 KEYS 跑了 117 ms，其他 1000 个客户端就等 117 ms。

本文的实测反复验证了这一点（KEYS 服务端 116.7 ms ↔ PING 最大 117.1 ms；DEL 156 ms ↔ PING 最大 164.7 ms）。所以「Redis 变慢了」可以用一句话诊断：找到那条正在执行的慢命令。

2. 六种阻塞源，六个数字

2.1 总表

测试方法：一个 Python 探针客户端每约 100 µs 发一次 PING（单连接，loopback），另一个连接执行被测命令。

阻塞源 规模 服务端耗时 探针观测的 PING max
基线（无阻塞） — — 5.4 ms（p99 213 µs）
KEYS * 100 万 key 116.7 ms 117.1 ms
DEL 大 hash 100 万 field / 53 MB 156.0 ms 164.7 ms
UNLINK 同一个 key 同上 0.007 ms 无尖刺
重 Lua 脚本 300 万次空循环 4.0 ms 4.26 ms
BGSAVE（fork） 140 MB 数据集 fork 停顿为主 1.78 ms 
flowchart TD
    B["Blocking sources"] --> K["KEYS *<br/>117 ms"]
    B --> D["DEL big key<br/>156 ms"]
    B --> L["Heavy Lua<br/>4 ms"]
    B --> F["fork / BGSAVE<br/>1.8 ms @140MB"]
    B --> S["Swap / AOF rewrite / THP<br/>not measured here"]
    D -.->|"UNLINK same key"| U["0.007 ms"]

2.2 KEYS *：116 毫秒，而且是 O(N) 全量

指标 实测
返回条数 1,000,000
服务端耗时（SLOWLOG） 116,663 µs
探针 PING max 117,114 µs

它的问题不只是慢，而是「一次返回全部」：100 万个 key 的名称要一次性拼进回复缓冲区，内存与带宽同时被吃掉。生产上应该用 SCAN：

方式 单次耗时 对主线程的影响
KEYS * 116.7 ms（100 万 key） 一次阻塞 117 ms
SCAN 0 COUNT 1000 微秒级 分 N 次，每次几乎无感

2.3 DEL 大 key：156 毫秒 vs UNLINK 的 7 微秒

同一个 100 万 field 的 hash（53 MB）：

命令 服务端耗时 机制
DEL bighash 155,975 µs（156 ms） 同步释放所有 field，主线程全程参与
UNLINK bighash 7 µs 只从 keyspace 摘除，内存在后台线程释放 
flowchart LR
    subgraph DEL["DEL (sync free)"]
        D1["remove ref"] --> D2["free every field<br/>in main thread"] --> D3["156 ms block"]
    end
    subgraph UNL["UNLINK (async free)"]
        U1["remove ref"] --> U2["hand list to<br/>background thread"] --> U3["7 us, no block"]
    end

两万倍的差距。而且 UNLINK 之后内存也会还回来（本文实测 1 秒内 used_memory 回到 1.47 MB），只是「还」的动作不在主线程。

场景 用哪个
删除大 key（hash/list/zset/set 元素多） UNLINK
删除普通小 key 都行，DEL 更直观
Redis 6.0 之前 只能 DEL，所以要避开大 key

2.4 重 Lua：4 毫秒，但会叠加

300 万次空循环的 Lua 脚本：服务端 4,032 µs，探针 max 4,260 µs。

单看 4 ms 不吓人，但要知道两件事：

  1. 脚本内不能被打断，脚本里做 1 万次 GET 就是 1 万次串行操作；
  2. 脚本会随访问量叠加：每秒 100 次这样的脚本 = 每秒 400 ms 被占用（40% 的 CPU 时间），P99 必然劣化。

⑥ 会专门讲「Lua 什么时候安全、什么时候危险」。

2.5 fork：本文 1.8 毫秒，生产可能是几十毫秒

BGSAVE（140 MB 数据集、100 万 key）实测：

指标 实测
rdb_last_cow_size 909,312 B（约 0.9 MB）
rdb_last_bgsave_time_sec < 1 s
探针 PING max 1.78 ms

fork 的停顿与数据集大小成正比（要复制页表），本文 140 MB 只能体现 1.8 ms；生产上 10 GB 数据集 fork 常见几十毫秒。这也是「Redis 内存不要超过物理内存 60%~70%」的原因之一（④ 提过）。

2.6 没实测但必须知道的三种

阻塞源 机制 怎么发现
Swap 内存被换到磁盘，访问延迟从纳秒变毫秒 used_memory vs 机器内存；vmstat 的 si/so
AOF rewrite fork + 大量写盘 INFO persistence 的 aof_rewrite_in_progress
透明大页（THP） fork 与内存分配延迟抖动 cat /sys/kernel/mm/transparent_hugepage/enabled

3. 怎么发现阻塞

3.1 三个工具，三种视角

工具 记录什么 本文实测
SLOWLOG 单条命令耗时 > 阈值（默认 10 ms） 捕获 KEYS 116,663 µs
LATENCY MONITOR 事件循环被阻塞的尖刺 捕获 command 事件 110 ms
探针客户端 业务视角的 P99 本文的 Python 探针

3.3 深挖：SLOWLOG 为什么会漏

漏报原因 说明 对策
阈值 10 ms 太高 5 ms 的命令不记，但足够让 P99 翻倍 降到 1~2 ms
只记命令本身 fork 停顿、swap 不计入 同时开 LATENCY MONITOR
只留 128 条 高峰期被冲掉 slowlog-max-len 调到 512~1024
Lua 脚本只记总时长 脚本里的子命令不可见 用 SCRIPT 拆分 + 监控

3.4 动手验证：写一个探针，测你自己的阻塞

用它跑一次「基线」和一次「执行 KEYS *」，对比 max。

预期观察点：基线的 max 在几毫秒内（客户端自身抖动）；执行 KEYS * 时 max 跳到与服务端耗时同量级（本文 117 ms）。

判定标准：

  • max 与某条命令的 SLOWLOG 时长吻合 → 就是它阻塞的；
  • max 大但没有慢命令 → 查 fork、swap、THP；
  • p99 高但 max 不高 → 不是单条阻塞，是持续的 CPU 压力（② 的排队）。

4. 治理：把 O(N) 从主线程挪走

4.1 命令替换表

危险命令 复杂度 替代 说明
KEYS * O(N) SCAN 游标 分批，单次可控
HGETALL 大 hash O(N) HSCAN / HMGET 指定字段 见 ③ 实测 46 µs@1000 field
SMEMBERS 大 set O(N) SSCAN ③ 实测 2.8 ms@10 万
DEL 大 key O(N) UNLINK 本文 156 ms → 7 µs
FLUSHALL / FLUSHDB O(N) FLUSHALL ASYNC 异步释放
ZRANGE 0 -1 O(N) 分页 ZRANGE start stop ③ 实测 1.4 ms@10 万
大 Lua 脚本 不可打断 拆分 + 分批 ⑥ 展开 
flowchart TD
    A["Suspect a slow operation"] --> B{"is it O(N)?"}
    B -- yes --> C{"can it be batched?"}
    C -- yes --> D["SCAN / HSCAN / SSCAN<br/>or paginate"]
    C -- no --> E["Move to replica<br/>or offline job"]
    B -- no --> F{"big key delete?"}
    F -- yes --> G["UNLINK"]
    F -- no --> H["check fork / swap / THP"]

4.2 大 key 是万恶之源

大 key 同时制造三种问题：阻塞（DEL/HGETALL）、内存不均（Cluster 倾斜）、网络拥塞（一次返回太多）。

判定 阈值（经验）
string value > 10 KB
hash/set/zset 元素 > 5000
list 元素 > 10000
总大小 > 1 MB

4.3 fork 与持久化的优化

手段 效果 代价
在从库做 RDB/AOF 主库不 fork 从库延迟（⑧）
关 THP fork 更快、延迟更稳 需要宿主权限
控制 RDB 频率 减少 fork 次数 恢复点变旧（⑦）
内存不超过 70% COW 有空间，fork 更快 需要容量规划（⑫）

4.4 架构层：按业务隔离

做法 解决什么
缓存与队列分实例 队列的 LPUSH 高峰不拖累缓存
大 key 业务单独实例 避免一个大 key 拖垮全站
读多写少用副本 阻塞只影响副本（注意一致性）

4.5 动手验证：验证 UNLINK 真的不阻塞

预期观察点：cmdstat_unlink 的 usec 是个位数（本文 7 µs），探针 max 与基线相当。

判定标准：

  • UNLINK 的 usec > 1000 → 你删的是「很多个小 key」（UNLINK 对多 key 仍是逐个摘除），改用管道分批；
  • 探针仍有尖刺 → 尖刺来自后台释放线程争抢，或另有阻塞源。

6. 动手验证：四个可复现实验

6.1 动手验证：用探针测基线延迟

预期观察点：基线 p50 约 100 µs、max 在几毫秒内（客户端自身抖动）。

判定标准：基线 max 就超过 10 ms → 先解决宿主/客户端问题，再谈 Redis 阻塞。

6.2 动手验证：复现 KEYS * 的阻塞

预期观察点：KEYS 的服务端耗时约 116 ms，探针的 max 与它同量级（本文 117 ms）。

判定标准：探针 max 与命令耗时吻合 = 单线程被这条命令占住；若 max 远小于命令耗时，说明请求没打到同一实例。

6.3 动手验证：对比 DEL 与 UNLINK

预期观察点：DEL 的 usec 约 15 万（156 ms），UNLINK 是个位数（本文 7 µs）。

判定标准：UNLINK 也超过 1 ms → 你删的是「很多个小 key」，需要分批删而不是一次删一批。

6.4 动手验证：让 LATENCY MONITOR 抓住阻塞

预期观察点：LATENCY LATEST 返回 command 事件，耗时约 110 ms；LATENCY HISTORY 能看到历史峰值。

判定标准：返回空 → 阈值设得太高（事件没被记录）或监控没开启；把它调到 10~50 ms 再试。

5. 总结

5.1 面试速答表

面试题 一句话答案
Redis 单线程为什么快 纯内存 + epoll + 短命令，执行一条 GET 只要 0.07 µs
单线程的代价是什么 没有抢占，一条慢命令让所有客户端排队
KEYS * 有多慢 100 万 key 实测服务端 116.7 ms，所有客户端同时卡住 117 ms
为什么用 SCAN 不用 KEYS SCAN 游标分批，单次耗时可控；KEYS 一次返回全部
DEL 大 key 为什么危险 同步释放，100 万 field 的 hash 实测 156 ms
UNLINK 为什么快 只摘除引用，内存交给后台线程释放，实测 7 µs
Lua 脚本会阻塞多久 300 万次空循环实测 4 ms；脚本不可打断，且随 QPS 叠加
fork 会阻塞吗 会，阻塞时间与数据集大小成正比；本文 140MB 仅 1.8 ms
SLOWLOG 和 LATENCY MONITOR 区别 前者记命令耗时，后者记事件循环尖刺；后者能抓到 fork/swap
怎么证明是某条命令阻塞的 探针的 PING max 与那条命令的服务端耗时吻合
大 key 的判定标准 string > 10KB、集合类 > 5000 元素、总大小 > 1MB
生产上怎么避免阻塞 SCAN/UNLINK/分页/拆大 key/把重活挪到副本

5.2 实战避坑表

症状 原因 处理
全站 P99 突然几百毫秒 有人在跑 KEYS / HGETALL 大 key 慢日志 + LATENCY MONITOR 定位，禁用命令
删除大 key 时接口超时 DEL 同步释放 换 UNLINK，或分批删除
定时任务跑完就抖 任务是 O(N) 遍历 改 SCAN，限速
SLOWLOG 里什么都没有 阈值 10ms 太高，或阻塞来自 fork/swap 阈值降到 1~2ms，开延迟监控
内存下降但 RSS 不降 后台释放 + 碎片（④） 正常现象，activedefrag 收尾

5.3 工具速查表

工具 看什么 判定标准
SLOWLOG GET 单命令耗时 有 > 10ms 的命令就要处理
LATENCY LATEST 事件尖刺 有记录 = 主线程被卡过
INFO commandstats 每命令总耗时与次数 找高频 + 高耗时的组合
--bigkeys 大 key 超过 1MB / 5000 元素要拆
探针客户端 业务视角 P99/max max 与某命令耗时吻合 = 定位成功
INFO persistence rdb_last_fork_usec fork 时间增长要关注

5.4 实操建议

  1. **线上禁用 KEYS**，用 SCAN；能用 rename-command 禁掉最好。
  2. **删除一律用 UNLINK**，这是零成本的 2 万倍提升。
  3. 慢日志阈值调到 1~2 ms，并开 latency-monitor-threshold（10~50 ms）。
  4. **定期 --bigkeys**，大 key 是阻塞、倾斜、带宽三个问题的共同源头。
  5. 把重活挪到副本或离线：RDB 备份、大范围扫描、批量清理。
