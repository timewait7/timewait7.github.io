第一部分：基础篇

1. Redis 定位与选型

1.1 Redis 的本质

Redis（REmote DIctionary Server）是一个基于内存的键值数据库，2009 年由 Salvatore Sanfilippo（antirez）用 C 语言发布。数据主要放在内存里，读写是微秒到亚毫秒级。单实例吞吐量在万级 QPS 到十万级 QPS 之间，是 MySQL 单库的几十倍到上百倍。

它同时具备以下能力：丰富的数据类型（String、List、Hash、Set、ZSet、Bitmap、HyperLogLog、Geo、Stream）、持久化（RDB/AOF）、分布式能力（主从、哨兵、Cluster）、原子操作（单线程执行）、功能组件（分布式锁、发布订阅、延迟队列、限流）。

1.4 何时用、何时不用

适合：缓存、计数器与实时统计、短生命周期数据、分布式协调、规模可控的热数据。

不适合：强一致性业务、复杂查询、超大低频数据、高吞吐可靠消息系统。

面试追问：为什么 Redis 单机可以做到 10 万 QPS，MySQL 只有几千？

三个原因：一是数据在内存（微秒级访问 vs 毫秒级磁盘 IO）；二是 Redis 命令简单（单 key 操作 vs SQL 解析、优化、多表关联）；三是单线程无锁（无锁竞争、无上下文切换 vs 行锁、MVCC、连接池竞争）。

2.5 List 的底层：quicklist

纯双向链表每个节点要存 prev/next 指针，内存碎片多；纯 ziplist 又存在连锁更新问题。Redis 3.2 引入 quicklist，把两者的优点结合起来。

三个设计要点：

  1. **链式结构保证头尾操作 O(1)**：LPUSH/RPUSH/LPOP/RPOP 只涉及头尾节点；
  2. 节点内部压缩存储：每个节点是一个 listpack（7.0 前是 ziplist），大幅减少指针开销；
  3. 节点大小可控：list-max-listpack-size（默认 128）控制每个节点最多存多少元素，超过则拆分新节点——避免单个节点过大导致插入需要大块内存分配。

2.6 Hash / Set / ZSet 的小数据优化：ziplist → listpack

Hash、Set、ZSet 在数据量小时都使用紧凑编码（ziplist，7.0 起为 listpack）而非哈希表或跳跃表，目的是省内存。

ziplist 的缺陷——连锁更新（cascade update） ：

ziplist 中每个元素都记录了前一个元素的长度（prevlen：前一元素长度 < 254 字节时占 1 字节，否则占 5 字节）。在某元素前插入新元素，可能导致该元素的”前一元素长度”从 1 字节膨胀为 5 字节，元素变大，又引发下一个元素的 prevlen 变化……形成链式反应。

flowchart TB
    subgraph ZiplistProblem[ziplist 连锁更新问题]
        direction LR
        E1["元素 A<br/>prevlen=1"] --> E2["元素 B<br/>prevlen=1<br/>len=250"]
        E2 --> E3["元素 C<br/>prevlen=1"]
        E3 --> E4["元素 D<br/>prevlen=1"]
    end

    Insert[在 B 前插入新元素<br/>B 的 prevlen 从 1 字节膨胀为 5 字节] -.->|链式反应| Cascade["B 变大 → C 的 prevlen 变 5 → C 变大 → D 的 prevlen 变 5 ...<br/>最坏 O(n²)"]

    style Insert fill:#ffe6e6
    style Cascade fill:#ffe6e6

listpack 的解决方案：

元素不再记录前一个元素的长度，每个元素只在尾部记录自身的编码和长度（backlen），元素之间完全独立。任意元素的修改只影响自身，从机制上消除了连锁更新。

    subgraph Listpack[listpack 元素独立]
        direction LR
        LE1["元素 A<br/>[data][backlen]"] --> LE2["元素 B<br/>[data][backlen]"] --> LE3["元素 C<br/>[data][backlen]"]
    end

    Note[修改任意元素<br/>只影响自身]

    style Note fill:#e6ffe6
对比维度 ziplist listpack
元素布局 记录前一个元素的长度（prevlen） 只记录自身长度，放在元素尾部
连锁更新 存在，最坏 O(n²) 不存在
内存开销 正常情况更紧凑 每个元素多一个 backlen，略高
状态 7.0 起移除 7.0 起全面使用

2.7 ZSet 的底层：跳跃表

ZSet 在超过阈值时使用 跳跃表 + 哈希表 的组合：

  • skiplist：按 score 排序，支持范围查询（ZRANGEBYSCORE）和按 rank 访问；
  • hashtable：按 member 到 score 的映射，让 ZSCORE 达到 O(1)。

跳跃表结构：

为什么不用红黑树/AVL 树：

  1. 实现简单：插入/删除只改指针，没有旋转调整，代码量小、不易出错；
  2. 范围查询天然友好：ZSet 的核心场景是”按分数范围取一段”，skiplist 的链表结构从头到尾遍历即可，树需要中序遍历；
  3. 内存开销可预期：节点层数随机但期望值可控（约 1/(1-p) = 1.33 个指针/节点）。

2.8 哈希表与渐进式 rehash

大数据量的 Hash、Set、ZSet 底层都是 dict。Redis 的 dict 有两个哈希表 ht[0]、ht[1]，平时只用 ht[0]，rehash 时用 ht[1]，rehashidx 记录迁移进度。

stateDiagram-v2
    [*] --> 稳态: 只用 ht[0]
    稳态 --> 触发扩容: 负载因子 ≥ 1<br/>(有子进程时 ≥ 5)
    触发扩容 --> 迁移中: 为 ht[1] 分配 2 倍容量<br/>rehashidx = 0
    迁移中 --> 迁移中: 每次操作顺带迁移一个桶<br/>新写入一律写 ht[1]
    迁移中 --> 稳态: 全部迁移完成<br/>ht[0] = ht[1], rehashidx = -1

迁移期间的读写规则：

flowchart TB
    Request[客户端请求]
    Request --> Op{操作类型?}
    Op -->|查找| Both["先查 ht[0]<br/>未命中再查 ht[1]"]
    Op -->|插入| H1["一律插入 ht[1]"]
    Op -->|删除| Both2["两张表都要删"]
    Op -->|rehash 触发| Migrate["迁移 rehashidx 桶<br/>rehashidx++"]

触发时机：

  • 扩容：负载因子 = used / size。没有子进程做持久化时，负载因子 ≥ 1 触发扩容（容量翻倍）；有 BGSAVE/BGREWRITEAOF 子进程时，负载因子 ≥ 5 才触发——子进程与父进程共享内存页（写时复制），此时再扩容会加剧内存页复制；
  • 缩容：负载因子 < 0.1 时触发（4.0 引入的规则）。

为什么做渐进式 rehash？ 一次性 rehash 一个几十万 key 的哈希表会阻塞主线程几百毫秒，单线程架构下会卡死所有请求。渐进式把成本摊薄到每次操作，单次命令的延迟增量很小。

Redis 7.0 的优化：空闲时由后台定时任务持续推进 rehash，避免大哈希表在极低负载下迁移卡住。

5.5 6.0 多线程的边界

开启方式：

为什么只并行 IO、不并行命令执行？

全部数据结构都不是线程安全的，让命令并行执行就得给每个操作加锁：锁竞争会抵消多核收益，还丢掉”命令天然原子”这个核心卖点。网络读写是纯内存拷贝、无共享状态，正好适合并行。

一句话概括：**6.0 用多线程解决”网络吞吐”瓶颈，用单线程保住”执行原子性”**。
