第一部分：基础篇

1. Redis 定位与选型

1.1 Redis 的本质

Redis（REmote DIctionary Server）是一个基于内存的键值数据库，2009 年由 Salvatore Sanfilippo（antirez）用 C 语言发布。数据主要放在内存里，读写是微秒到亚毫秒级。单实例吞吐量在万级 QPS 到十万级 QPS 之间，是 MySQL 单库的几十倍到上百倍。

它同时具备以下能力：丰富的数据类型（String、List、Hash、Set、ZSet、Bitmap、HyperLogLog、Geo、Stream）、持久化（RDB/AOF）、分布式能力（主从、哨兵、Cluster）、原子操作（单线程执行）、功能组件（分布式锁、发布订阅、延迟队列、限流）。

1.4 何时用、何时不用

适合：缓存、计数器与实时统计、短生命周期数据、分布式协调、规模可控的热数据。

不适合：强一致性业务、复杂查询、超大低频数据、高吞吐可靠消息系统。

面试追问：为什么 Redis 单机可以做到 10 万 QPS，MySQL 只有几千？

三个原因：一是数据在内存（微秒级访问 vs 毫秒级磁盘 IO）；二是 Redis 命令简单（单 key 操作 vs SQL 解析、优化、多表关联）；三是单线程无锁（无锁竞争、无上下文切换 vs 行锁、MVCC、连接池竞争）。

2.5 List 的底层：quicklist

纯双向链表每个节点要存 prev/next 指针，内存碎片多；纯 ziplist 又存在连锁更新问题。Redis 3.2 引入 quicklist，把两者的优点结合起来。

三个设计要点：

  1. **链式结构保证头尾操作 O(1)**：LPUSH/RPUSH/LPOP/RPOP 只涉及头尾节点；
  2. 节点内部压缩存储：每个节点是一个 listpack（7.0 前是 ziplist），大幅减少指针开销；
  3. 节点大小可控：list-max-listpack-size（默认 128）控制每个节点最多存多少元素，超过则拆分新节点——避免单个节点过大导致插入需要大块内存分配。

2.6 Hash / Set / ZSet 的小数据优化：ziplist → listpack

Hash、Set、ZSet 在数据量小时都使用紧凑编码（ziplist，7.0 起为 listpack）而非哈希表或跳跃表，目的是省内存。

ziplist 的缺陷——连锁更新（cascade update） ：

ziplist 中每个元素都记录了前一个元素的长度（prevlen：前一元素长度 < 254 字节时占 1 字节，否则占 5 字节）。在某元素前插入新元素，可能导致该元素的”前一元素长度”从 1 字节膨胀为 5 字节，元素变大，又引发下一个元素的 prevlen 变化……形成链式反应。

flowchart TB
    subgraph ZiplistProblem[ziplist 连锁更新问题]
        direction LR
        E1["元素 A<br/>prevlen=1"] --> E2["元素 B<br/>prevlen=1<br/>len=250"]
        E2 --> E3["元素 C<br/>prevlen=1"]
        E3 --> E4["元素 D<br/>prevlen=1"]
    end

    Insert[在 B 前插入新元素<br/>B 的 prevlen 从 1 字节膨胀为 5 字节] -.->|链式反应| Cascade["B 变大 → C 的 prevlen 变 5 → C 变大 → D 的 prevlen 变 5 ...<br/>最坏 O(n²)"]

    style Insert fill:#ffe6e6
    style Cascade fill:#ffe6e6

listpack 的解决方案：

元素不再记录前一个元素的长度，每个元素只在尾部记录自身的编码和长度（backlen），元素之间完全独立。任意元素的修改只影响自身，从机制上消除了连锁更新。

        direction LR

2.8 哈希表与渐进式 rehash

大数据量的 Hash、Set、ZSet 底层都是 dict。Redis 的 dict 有两个哈希表 ht[0]、ht[1]，平时只用 ht[0]，rehash 时用 ht[1]，rehashidx 记录迁移进度。

stateDiagram-v2
    [*] --> 稳态: 只用 ht[0]
    稳态 --> 触发扩容: 负载因子 ≥ 1<br/>(有子进程时 ≥ 5)
    触发扩容 --> 迁移中: 为 ht[1] 分配 2 倍容量<br/>rehashidx = 0
    迁移中 --> 迁移中: 每次操作顺带迁移一个桶<br/>新写入一律写 ht[1]
    迁移中 --> 稳态: 全部迁移完成<br/>ht[0] = ht[1], rehashidx = -1

迁移期间的读写规则：

flowchart TB
    Request[客户端请求]
    Request --> Op{操作类型?}
    Op -->|查找| Both["先查 ht[0]<br/>未命中再查 ht[1]"]
    Op -->|插入| H1["一律插入 ht[1]"]
    Op -->|删除| Both2["两张表都要删"]
    Op -->|rehash 触发| Migrate["迁移 rehashidx 桶<br/>rehashidx++"]

触发时机：

  • 扩容：负载因子 = used / size。没有子进程做持久化时，负载因子 ≥ 1 触发扩容（容量翻倍）；有 BGSAVE/BGREWRITEAOF 子进程时，负载因子 ≥ 5 才触发——子进程与父进程共享内存页（写时复制），此时再扩容会加剧内存页复制；
  • 缩容：负载因子 < 0.1 时触发（4.0 引入的规则）。

为什么做渐进式 rehash？ 一次性 rehash 一个几十万 key 的哈希表会阻塞主线程几百毫秒，单线程架构下会卡死所有请求。渐进式把成本摊薄到每次操作，单次命令的延迟增量很小。

Redis 7.0 的优化：空闲时由后台定时任务持续推进 rehash，避免大哈希表在极低负载下迁移卡住。

为什么只并行 IO、不并行命令执行？

全部数据结构都不是线程安全的，让命令并行执行就得给每个操作加锁：锁竞争会抵消多核收益，还丢掉”命令天然原子”这个核心卖点。网络读写是纯内存拷贝、无共享状态，正好适合并行。

7. 内存管理与淘汰策略

本节整合了 Redis 缓存淘汰策略的完整内容：maxmemory 配置、8 种策略选型、近似 LRU 与 LFU 的实现差异。

7.1 为什么内存必须设上限

内存淘汰（memory eviction） 是 Redis 在内存写满时，按配置的策略删除一部分 key 来腾出空间的机制。它是缓存场景的最后一层保险：不配置，Redis 会被系统 OOM Killer 直接杀进程。

7.1.1 maxmemory：Redis 的内存天花板

不设 maxmemory 的后果：Redis 吃满机器内存后，OS 的 OOM Killer 会直接 kill 掉 redis-server 进程（类比 Java 应用 -Xmx 设太大、堆外内存失控被容器 OOM kill），主从全部挂掉，未落盘数据全部丢失。生产环境这是第一优先级配置。

类比 Java 应用 Redis
内存上限 -Xmx / 容器 limit maxmemory
超限行为 抛 OOM 异常（可捕获） 按策略淘汰 key，或拒绝写入
失控后果 被容器 OOM kill 被系统 OOM Killer 杀进程

7.3 八种淘汰策略全景

7.3.1 速查表（面试核心考点）

策略 作用范围 淘汰依据 引入版本 典型场景
noeviction 全部 key 不淘汰，写满报错 一直 队列、计数器等写失败可重试
allkeys-lru 全部 key 最近最少使用 一直 通用缓存，最常用
volatile-lru 带 TTL 的 key 最近最少使用 一直 缓存带过期 + 少量长驻 key
allkeys-random 全部 key 随机 一直 key 可重建、淘汰成本均等
volatile-random 带 TTL 的 key 随机 一直 会话 token 类
volatile-ttl 带 TTL 的 key 剩余 TTL 最短 一直 数据有明确时效
allkeys-lfu 全部 key 访问频次最低 4.0 长尾热点
volatile-lfu 带 TTL 的 key 访问频次最低 4.0 带 TTL 的长尾热点

命名规律：前缀 allkeys- 管全部 key，volatile- 只管带过期时间的 key；后缀 -lru 看最近访问、-lfu 看访问频次、-random 随机、-ttl 看剩余寿命。

7.3.2 volatile-* 的隐藏降级

volatile-* 系列有个大坑：如果带 TTL 的 key 一个都没有（或没有可淘汰的），行为退化成 noeviction——写满直接报错。

真实场景：某天排查发现缓存全部写不进去，配置明明是 volatile-lru，查下来是业务方刚把 key 的 TTL 全去掉了。结果整个 Redis 变只读，线上炸了才反应过来。

口诀：volatile 系列依赖 TTL，TTL 没设，策略就失效。

7.3.3 allkeys 与 volatile 怎么选

核心区别一句话：allkeys- 保护的是”内存不超限”，volatile- 保护的是”带 TTL 的 key 优先存活”**。如果缓存数据和不过期数据混用同一个实例（比如有人把配置、统计也塞 Redis），必须用 volatile-*，否则淘汰可能把不该删的业务数据删掉。

7.4 近似 LRU：用采样换精度

7.4.1 为什么不做严格 LRU

严格 LRU 需要维护双向链表，每次访问把节点移到队首，每个 key 额外占两个指针的开销。Redis 的 key 数量以百万计，这个成本不可接受；链表在 RDB 持久化、主从复制时也会引入额外复杂度。所以 Redis 选择近似 LRU（approximate LRU）：只记录”上次访问时间”，淘汰时抽样比较。

7.4.2 数据结构：RedisObject 的 24bit 时钟

每个 value 对象（RedisObject）里有一个 24bit 的 lru 字段：

  • LRU 模式：存上次访问时间（秒级时钟 LRU_CLOCK，约 194 天轮回一次）。
  • LFU 模式：拆成 16bit 时间 + 8bit 频次计数器（见 7.5）。

每次 key 被访问（GET/SET 等），lru 字段刷新为当前时钟。

7.4.3 淘汰算法：采样取最老

flowchart LR
    subgraph Space[Key space]
        K1[key1 lru=100]
        K2[key2 lru=50]
        K3[key3 lru=200]
        K4[key4 lru=180]
        K5[key5 lru=90]
    end
    S[Random sample N=5] --> V[Pick key with oldest lru<br/>--> key2]
    V --> E[Evict key2]
    style K2 fill:#f9d0c4
  1. 从键空间随机取 N 个 key（N = maxmemory-samples，默认 5）。
  2. 在 N 个里挑 lru 最小（最久没访问）的淘汰。
  3. 淘汰后内存还不够，重复该过程。

采样数越大越接近严格 LRU，但每次淘汰的 CPU 成本越高。Redis 5.0 起引入淘汰池（eviction pool）：上一轮采样过的候选 key 保留在池中，下一轮优先从池里挑，跨轮次累积样本，近似精度进一步提升（6.0 对池大小做了动态调整）。

7.5 LFU：频次才是真相

7.5.1 LRU 的致命场景

LRU 只看”最近访问”，不看”访问了多少次”。一次突发热点（秒杀、新闻爆点）就能让一批 key 变成”最近访问”，随后把真正长期高热的 key 挤掉——等热点过去，缓存里全是没人再看的 key。

这个痛点 Java 开发者也不陌生：Caffeine 的 W-TinyLFU 淘汰算法就是针对 LRU 对”长尾热点”命中率差才诞生的，思路同源。

7.5.2 同一个字段，两种读法

Redis 4.0 起，LFU 模式下 24bit 的 lru 字段被拆成两部分：

位段 名称 含义
高 16bit ldt（last decrement time） 上次衰减时间的分钟级时钟
低 8bit logc（logistic counter） 对数计数器，0~255

8bit 只能记 255 次访问，不够用，所以用对数计数器（logistic counter）：访问次数越多，计数器增长越慢——用概率递增代替每次访问 +1。

7.5.4 衰减：避免”曾经热过”的 key 霸占缓存

LFU 只有递增没有衰减，一个 key 早年火过一次就会一直霸占缓存（访问量早已回落也不淘汰）。所以 ldt 出场：每隔 lfu-decay-time 分钟（默认 1），logc 减半，让热度随时间冷却，冷门但持续访问的 key 才有机会浮现。

参数 默认值 说明
lfu-log-factor 10 计数器增长速度。越大增长越慢、能表达更大的访问量；越小越容易被高访问 key 快速顶到 255
lfu-decay-time 1 计数器减半的间隔（分钟），0 表示不衰减

lfu-log-factor 不同取值下，计数器到达某值需要的真实访问次数（Redis 官方文档数据）：

factor 100 次 1000 次 10 万次 100 万次 1000 万次
0 104 255 255 255 255
1 18 49 255 255 255
10（默认） 10 18 142 255 255
100 8 11 49 143 255

高频热点 key 容易顶到 255——所有 key 都是 255 就分不出高下，这时调大 factor 拉开差距。

7.6 实战选型：项目里到底配什么

7.6.1 决策表

业务形态 推荐策略 理由
通用缓存（读多写少、key 同质化） allkeys-lru 简单可靠，80% 的场景首选
部分 key 长期高频（榜单、用户画像） allkeys-lfu 长尾热点命中率更高
全部 key 带 TTL、生命周期短（验证码、会话） volatile-lru / volatile-ttl 只淘汰缓存，不碰长驻数据
缓存与持久数据混用同一实例 volatile-lru 保护不过期数据不被淘汰
key 均可重建、淘汰成本均等 allkeys-random 淘汰开销最小
数据不能丢，写失败要立刻感知 noeviction 用异常暴露容量问题

选型口诀：没把握就 allkeys-lru；有长尾热点换 allkeys-lfu；混用持久数据必须 volatile。

7.6.2 三个真实场景

  • 登录 token（TTL 短、无差别）：volatile-random 即可，谁被淘汰无所谓，反正过期快。
  • 电商秒杀（短时突发热点）：用 allkeys-lru。LFU 会把秒杀 key 的计数器顶到高位，热点过后长期霸占缓存，反而有害。
  • 用户画像/推荐位（长期频次差异大）：allkeys-lfu，避免一波流量把常驻热 key 挤掉。

7.6.3 验证：用数据说话

上线后观察两天：evicted_keys 平稳且被淘汰的都是冷 key，说明策略选对了；如果出现热 key 被淘汰（业务告警）或 evicted_keys 陡增，先扩 maxmemory，再考虑换策略。

7.6.4 避坑清单（面试也常问）

症状 原因 处理
缓存写满后大量写入报 OOM 策略是 noeviction，或 volatile-* 但 key 没带 TTL 换成 allkeys-lru，或给 key 补 TTL
突发流量后热 key 命中率骤降 LRU 被”一波流”污染 评估换 allkeys-lfu
写入延迟毛刺明显 每次写前都要先淘汰，可能多轮采样删除 提高 maxmemory 余量，或写操作错峰
主从行为不一致 淘汰只在主节点触发 正常现象，从库同步主库数据；不要只在从库配不同策略
内存碎片率长期偏高 频繁淘汰 + 大 key 释放 开启 activedefrag，或检查内存分配策略

7.7 内存优化配置

7.8 本节小结

三个收获：淘汰只发生在写路径、volatile-* 依赖 TTL 且可能静默降级、LRU 看”最近” LFU 看”频次”，两者的实现都是近似方案（采样 + 概率计数）。

实操建议按优先级：

  1. **先设 maxmemory**，这是 Redis 生产环境的第一道保险，没有上限，策略都是空谈。
  2. 默认 allkeys-lru 起步，出问题再换，不要一上来就 LFU——LFU 有 lfu-log-factor 和 lfu-decay-time 两个参数要调。
  3. **缓存与存储数据混用的实例必须用 volatile-***。
  4. 上线后盯 evicted_keys 和命中率，策略选对的标准是”被淘汰的都是冷 key”。

第三部分：高可用篇

8. 主从复制与哨兵

单机 Redis 能用，但「扛不住」时只有两个问题：机器挂了怎么办（高可用），数据量大了怎么办（扩容）——分别对应哨兵和 Cluster。 本节按「单机 → 主从 → 哨兵」的演进线讲透主从复制、哨兵故障转移，以及脑裂防护。

8.1 定位：演进线就是面试线

Redis 高可用是一个「一步步加组件」的演进过程，每个阶段解决一个问题、引入一个新概念：

阶段 解决什么 关键机制 代价/限制
单机 基本可用 无 单点故障、容量单机上限
主从 数据冗余 + 读扩展 异步复制 主挂需人工切换
哨兵 自动故障转移 监控 + 选举 仍是单主写（写不扩容）
Cluster 自动分片扩容 槽位路由 跨槽多键操作受限

因果链：主从解决「数据不丢」和「读扛不住」→ 但切换要人工 → 哨兵自动化 → 但写仍是单点 → Cluster 分片让写也能扩容。面试答 Redis 高可用，按这条演进线讲，逻辑自动闭环。

8.2.1 复制流程

8.2.2 为什么默认异步复制（面试核心）

维度 异步复制 同步复制（WAIT 命令可选）

生产选择 默认（性能优先） 严格不丢数据的场景（罕见）

因果链：Redis 定位是缓存/高速存储，性能优先于强一致——所以默认异步。「主节点挂了丢几秒数据」是异步复制的已知代价，用「哨兵秒级切换 + 业务容忍短暂不一致」接受它（这与 MySQL 半同步的选择逻辑对比着看：MySQL 数据价值高所以有半同步选项，Redis 缓存容忍丢）。

8.2.3 动手验证：主从复制与主挂现场

观察点：主挂后从节点只读拒绝写入——「主从不做自动切换，必须靠哨兵」的现场证据。判定标准：亲手确认「主从只解决读扩展与冗余，故障转移需要哨兵」，这是理解为什么需要哨兵的第一课。

8.3 哨兵：自动故障转移

8.3.1 三个哨兵能力 + 主观/客观下线

9.2 Hash Tag

{user100} 只对花括号内的内容算哈希，让多个 key 落在同一槽。

9.3 Cluster 的限制与应对

限制 原因 应对
多 key 操作受限 不同 key 在不同槽/节点 哈希标签（hash tag）：{user:1}:cart 强制同槽
跨槽事务 同上 hash tag 或应用层补偿
批量命令受限 mget 跨节点 hash tag / 客户端分片聚合

因果链：分片的代价是「数据分散」→ 关联数据必须「强制同槽」（hash tag）——面试答 Cluster 的坑，先说「多 key 操作受槽位限制」，再补「用 hash tag 让关联 key 同槽」就是完整答案。

Guava Cache 和 Caffeine 的区别？ Caffeine 用 W-TinyLFU，命中率更高
Spring Session 的序列化选什么？ JSON

分布式 ID 三种方案？ INCR、号段模式、雪花算法
