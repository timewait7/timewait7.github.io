Kubernetes 入门与实战

Posted on 2025-11-15 In 容器与编排 Word count in article: 6.4k Reading time ≈ 23 mins.

面向 Java 开发者的一篇 K8s 入门文章：从架构原理讲起，以 Spring Boot 应用部署为主线，覆盖网络、存储、可观测性与常见问题排查。

1. 为什么需要 Kubernetes

从 Docker 到 K8s：单机到多机编排的演进

作为 Java 开发者，你一定经历过这样的阶段：

阶段一：裸机部署。 把 Jar 包 scp 到服务器，nohup java -jar app.jar & 启动，进程挂了靠人肉重启，端口冲突靠口头约定。

阶段二：Docker。 解决了”环境不一致”的问题——镜像打包了 JDK、依赖、配置，docker run 一下就跑起来。但 Docker 只解决”怎么跑”，不解决”跑在哪、跑几个、挂了怎么办”。

阶段三：Docker Compose。 可以用一份 YAML 描述多个容器（MySQL + Redis + App），一键启动。但 Compose 是单机的，服务多起来之后：

  • 无法跨多台机器调度
  • 没有自动故障恢复
  • 没有滚动更新
  • 没有服务发现与负载均衡

阶段四：Kubernetes。 K8s 把”多台机器”抽象成一个资源池，你只需要声明”我想要什么”（声明式配置），K8s 负责”怎么达成”（控制循环）。

K8s 的核心价值

能力 说明 对 Java 开发者的意义
声明式配置 用 YAML 描述期望状态，而非一步步执行命令 配置即代码，可以走 Git 版本管理、Code Review
自愈 容器崩溃自动重启、节点宕机自动迁移 Pod 不再需要人肉守护进程
自动扩缩容 按 CPU/内存或自定义指标水平伸缩（HPA） 应对突增流量不用半夜起来加机器
服务发现与负载均衡 Service 提供稳定的虚拟 IP，自动转发 服务间调用不再硬编码 IP
滚动更新与回滚 新版本分批上线，失败自动回退 发布变成 kubectl rollout 一条命令

一句话总结：Docker 解决”怎么打包”，K8s 解决”怎么运维”。 打包你已经在做了，运维这件事交给 K8s。

2. 核心概念与架构

2.1 架构图

  • Control Plane（控制平面）：集群的”大脑”，负责决策（调度、状态维护、对外暴露 API）。生产环境通常 3 个副本高可用部署。
  • Worker Node（工作节点）：集群的”手脚”，真正跑你的业务容器。

2.2 核心组件

组件 职责 通俗理解
API Server 集群唯一的操作入口，提供 REST API，所有组件（包括 kubectl）都通过它通信 集群的”行政中心”，所有状态变更都要它批准
etcd 分布式键值存储，保存集群全部状态 集群的”数据库”，保存着”世界应该是什么样”
Scheduler 为新 Pod 选择合适的节点 集群的”调度员”，看哪台机器资源够、亲和性满足
Controller Manager 运行各种控制器，让”当前状态”收敛到”期望状态” 集群的”纠偏员”，发现偏离就修复
kubelet 节点上的代理，负责启动/停止 Pod，向 API Server 汇报状态 节点的”管家”，执行控制平面下达的指令
kube-proxy 维护节点上的网络规则，实现 Service 的负载转发（iptables/IPVS） 节点的”路由器”

2.3 一个 Pod 的创建流程

你在终端执行 kubectl create -f deployment.yaml 之后发生了什么：

  1. kubectl → API Server：kubectl 把 Deployment 对象通过 HTTPS 发给 API Server，API Server 校验并存入 etcd。
  2. Deployment Controller（属于 Controller Manager）发现”期望的副本数是 3，实际是 0”，于是创建 ReplicaSet。
  3. ReplicaSet Controller 发现”期望 3 个 Pod，实际 0 个”，于是创建 3 个 Pod 对象（此时 Pod 处于 Pending）。
  4. Scheduler 监听到新 Pod，为每个 Pod 选择合适的节点，把调度结果写回 etcd（Pod 绑定到某节点）。
  5. kubelet 从 API Server 感知到本节点有新 Pod，通知容器运行时（containerd）拉取镜像并创建容器。
  6. 容器启动后，kubelet 持续汇报状态（Running/Ready），控制面确认”期望状态已达成”。

整个过程都是控制器驱动的：没有谁命令谁，每个组件都在 watch 状态变化，然后朝着期望状态收敛。

2.4 Pod：最小的调度单元

  • Pod 是 K8s 中最小的调度和部署单元，一个 Pod 可以包含一个或多个容器。
  • 同一 Pod 内的容器共享网络命名空间（共享 IP、端口空间）和存储卷（Volume），通过 localhost 即可互相访问。
  • 容器崩溃时，kubelet 会重启它（RestartPolicy），但 Pod 整体不会重建——Pod 是”金丝雀”，即使容器反复重启，Pod 仍在原节点原地运行。
  • **永远不要让一个 Pod 只包含一个临时容器概念上的”多个进程”**——合理设计是多进程拆分到多个容器。

Sidecar 模式：一个 Pod 里除了主容器，再放一个”辅助容器”来扩展功能，二者共享网络与存储。典型场景：

  • 日志采集：主容器写日志文件，Sidecar（Filebeat）转发到 Elasticsearch
  • 代理注入：主容器被代理劫持流量，实现服务网格（见 4.3）
  • 配置刷新：Sidecar 监听配置变更并 reload 主容器

2.5 Service：稳定的访问入口

Pod 的 IP 是动态的（重建就变），所以不能直接用 Pod IP 通信。Service 提供稳定的虚拟 IP（ClusterIP），通过 Label Selector 选择后端 Pod，实现服务发现与负载均衡。

Service 类型 作用 使用场景
ClusterIP（默认） 集群内部虚拟 IP，仅集群内可访问 微服务之间互相调用
NodePort 在每台节点上开放一个端口（30000-32767），外部可通过 节点IP:NodePort 访问 测试环境、临时暴露
LoadBalancer 依赖云厂商，自动创建负载均衡器（SLB）并绑定外部 IP 云上生产环境
ExternalName 把 Service 映射到外部域名（CNAME），集群内可通过别名访问外部服务 对接外部老系统、第三方 API

流量转发原理（kube-proxy）：kube-proxy 监听 Service/Endpoint 变化，在每台节点上维护规则：

  • iptables 模式：为每个 Service 生成一组 iptables 规则，DNAT 到随机选择的后端 Pod IP。简单稳定，但更新大量规则时性能一般。
  • IPVS 模式：在内核实现负载均衡，支持多种调度算法（rr、lc 等），规则更多、吞吐更高。生产环境推荐。

3. 核心工作负载

3.1 Deployment：无状态应用首选

  • Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。这是一个两层结构：Deployment 负责”版本”，ReplicaSet 负责”副本数”。
  • 滚动更新（RollingUpdate）：默认更新策略，先起新 Pod，等就绪后再销毁旧 Pod，分批进行，全程服务不中断。
  • 回滚：每次发布都会记录历史版本（revision），kubectl rollout undo deployment/xxx 一键回到上个版本。

3.2 StatefulSet：有状态服务

数据库、消息队列等有状态服务需要稳定的网络标识和持久存储，StatefulSet 提供：

  • 稳定的 Pod 名称：Pod 名为 name-0、name-1、name-2，顺序创建、逆序删除，重建后名称不变。
  • 稳定的网络标识：配合 Headless Service（ClusterIP 为 None），可用 podname.svcname 直连某个实例。
  • 稳定的存储：每个 Pod 绑定独立的 PVC（持久卷声明），Pod 重建后数据不丢。

K8s 官方不提供内置的数据库，但可以通过 StatefulSet + Operator 方式部署（如 redis-operator、clickhouse-operator）。对大多数应用，数据库建议使用云厂商托管服务（RDS），自己运维 StatefulSet 的成本很高。

3.3 DaemonSet：每节点一个 Pod

  • DaemonSet 保证每个节点上运行一个 Pod 副本（新节点加入自动补上）。
  • 典型用途：日志采集 Agent（Filebeat/Fluentd）、监控 Agent（node-exporter）、网络插件（Calico/Felix）。

3.4 Job 与 CronJob

  • Job：执行一次性任务（批处理、数据迁移、备份），任务成功完成即退出，失败可自动重试（backoffLimit）。
  • CronJob：按 Cron 表达式定时执行 Job（定时同步、每日报表），格式与 Linux crontab 相同：*/5 * * * *。

4. 网络

4.1 网络插件：Flannel / Calico

K8s 网络模型要求：每个 Pod 都有独立 IP，且任意 Pod 间可直接通信（无需 NAT）。这个能力由 CNI（Container Network Interface）插件实现，常见两类：

Flannel（Overlay 网络）

  • 在每个节点上维护一个子网，Pod IP 跨节点访问时通过 VXLAN 隧道封装转发。
  • 简单、稳定、性能略低（封装开销），适合中小规模集群。

Calico（纯三层网络）

  • 基于 BGP 协议直接路由，不用隧道封装，性能更好；天然支持网络策略（NetworkPolicy）做微隔离。
  • 生产环境主流选择。

4.2 Ingress 与 Ingress Controller

Service 只解决”到哪个 Pod”，而 **Ingress 解决”从外部怎么进来”**：七层（HTTP/HTTPS）路由，按域名/路径把请求分发到不同的 Service。

理解要点：Ingress 只是声明（一份 YAML），真正干活的是 Ingress Controller（Nginx Ingress、Traefik、云厂商 SLB）。工作流程：

TLS 终止：HTTPS 证书放在 Ingress 上，Ingress Controller 负责解密，转发给后端的是 HTTP，后端服务不需要自己处理证书。

4.3 Service Mesh 简介

Service Mesh 把网络能力（限流、熔断、重试、灰度、链路追踪）从业务代码中剥离出来，下沉到 Sidecar 代理（Envoy）：

  • 每个 Pod 注入一个 Envoy 代理容器，所有进出流量都经代理转发。
  • 控制平面（如 Istiod）统一下发规则，实现流量的精细治理。
  • 与 K8s 的关系：Service Mesh 是 K8s 之上的附加层，用 Sidecar 注入（MutatingWebhook）实现，对业务代码零侵入。

对 Java 开发者来说：Service Mesh 相当于把 Spring Cloud 的 Ribbon/Hystrix/Feign 能力挪到了基础设施层。学习成本较高，中小团队建议先用好 K8s 原生能力（探针、HPA、rollout），再引入 Mesh。

5. 存储

5.1 Volume 类型

容器文件系统是临时的（容器重启数据就丢），Volume 用于给容器挂载持久或共享存储：

类型 生命周期 场景
emptyDir 随 Pod 创建/删除，容器间共享 同一 Pod 内容器交换数据（Sidecar 日志采集）
hostPath 节点目录，跨 Pod 不共享 单节点测试、读宿主机日志
nfs 网络文件系统，跨节点共享 自建 K8s 的共享存储
PVC 持久卷声明，数据保留 数据库、文件服务

5.2 PV 与 PVC

  • PV（PersistentVolume）：集群里的存储资源，由管理员（或云厂商）提供，比如一块 100Gi 的云盘。
  • PVC（PersistentVolumeClaim）：应用声明”我要一块 10Gi 读写的存储”，K8s 自动把满足条件的 PV 绑定给 PVC。

供给方式：

  • 静态供给：管理员预先创建 PV，PVC 去匹配（按容量、访问模式、StorageClass）。
  • 动态供给（推荐）：PVC 指定 storageClassName，K8s 通过 CSI 驱动自动创建云盘/NFS 目录，用完删除 PVC 即回收。

5.3 ConfigMap 与 Secret

把配置从镜像中剥离出来，实现配置与代码解耦：

  • ConfigMap：存放普通配置（明文），如 application.yml 片段、环境变量。
  • Secret：存放敏感信息（Base64 编码存储，仅存储层编码而非加密，生产需配合加密插件），如数据库密码、Token。

6.3 健康检查：三种探针

探针（Probe）是 K8s 判定容器健康的手段，Spring Boot 应用配合 spring-boot-starter-actuator，暴露 /actuator/health 即可。

探针 用途 失败后果 建议
startupProbe 判断应用是否启动完成 失败则重启容器（替代早期版本的 initialDelaySeconds） 慢启动应用（如 Spring Cloud 拉配置）必须配置，failureThreshold 给足
readinessProbe 判断应用是否就绪可接流量 失败则从 Service 端点中摘除（不重启） 依赖数据库/缓存就绪后才能接流量，必须配置
livenessProbe 判断应用是否存活 失败则重启容器 配置时务必小心：不要在探针路径上做重操作，避免”探针慢导致误杀”

最佳实践：

  • 启动慢的 Spring Boot 应用：startupProbe 探测 /actuator/health，periodSeconds 5、failureThreshold 30（即最多等 150 秒），启动完成后 liveness/readiness 才开始工作。
  • livenessProbe 与 readinessProbe 共用 /actuator/health 即可；如需区分，readiness 可以带组件状态（如数据库），liveness 只查应用本身存活。
  • 不要把 /actuator/health 之外的重接口当探针路径。

6.4 资源限制与 JVM 内存设置

requests 与 limits：

  • requests：调度依据。K8s 按 requests 计算节点资源是否足够，Pod 可能获得超过 requests 的资源。
  • limits：硬上限。CPU 超限会被限流（throttling）；内存超限容器会被 OOMKilled（详见 8.3）。

7. 可观测性

7.1 日志

基础用法：

日志采集（EFK/ELK）：Pod 删除后日志就没了，生产环境需要集中采集。常见方案：

  • 架构：Fluentd/Filebeat（DaemonSet 形式采集）→ Elasticsearch → Kibana。
  • 采集方式：容器 stdout/stderr → 节点 Docker/containerd 日志目录 → Fluentd 转发。Java 应用把日志打到 stdout 即可，不要写本地文件，否则采集要额外配置。

7.2 监控：Prometheus + Grafana

标准监控方案：

  • node-exporter（DaemonSet）：采集节点指标（CPU、内存、磁盘、网络）。
  • cadvisor / kubelet metrics：采集 Pod 与容器指标。
  • Prometheus：抓取指标并存储，内置 Alertmanager 告警。
  • Grafana：可视化仪表盘，社区有大量现成模板（如 8932 号的 Java 指标面板）。

Java 应用接入：

Prometheus 通过 ServiceMonitor（Prometheus Operator 生态）或静态配置抓取 /actuator/prometheus 指标。即可看到 JVM 堆内存、GC 次数、线程数、HTTP 请求量等指标。

7.3 健康检查与就绪探针的最佳实践（小结）

  1. 三种探针分工明确：startup 管启动、readiness 管流量、liveness 管重启，不要混用。
  2. 探针路径必须轻量：探针只查存活/就绪，不做重操作（不要调数据库做 liveness 检查——数据库抖动会导致容器被反复重启）。
  3. 配置探针超时与容错：timeoutSeconds、failureThreshold 给足，避免慢启动被误杀。
  4. 探针失败要有区分：依赖缺失（DB 连不上）→ readiness 失败（摘流量），而不是 liveness 失败（重启也起不来，还会雪崩）。
  5. 每次发布前在测试环境验证探针路径确实可用（curl http://localhost:8080/actuator/health）。

8.3 OOMKilled 与资源限制

症状：Pod 反复重启，kubectl get pod 状态显示 OOMKilled。

排查与解决：

解决思路：

  • 容器被 OOMKilled 但 JVM 没报 OOM：非堆内存超了。检查 limits 与 JVM 参数比例（MaxRAMPercentage 不要超过 80%），检查是否有堆外内存大户（连接池、DirectBuffer、ThreadLocal 无清理）。
  • JVM 堆 OOM：内存泄漏排查（heap dump 分析），或确实需要调大 limits——但先加探针和限流，不要盲目加内存。
  • CPU throttling：CPU 超限不会杀死容器但会严重变慢（GC 变慢、响应超时），用 kubectl top pod 观察实际用量，合理设置 requests/limits。

小结

给 Java 开发者的学习路线建议：

  1. 先跑通：Docker Desktop 或 minikube，用第 6 节的 YAML 把 Spring Boot 应用部署起来。
  2. 理解三大抽象：Pod（调度单元）、Deployment（无状态应用）、Service（访问入口），掌握 8.1 的三板斧排查。

  4. 最后进阶：StatefulSet、Service Mesh、自定义 CRD——等前 3 步都踩过坑再学。

K8s 的学习曲线确实陡，但它解决的是分布式部署的通用问题——掌握之后，部署、扩容、发布这些曾经头疼的事，都会变成几行 YAML 和一条命令。
