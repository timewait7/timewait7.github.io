容量规划与分片：什么时候才该上 Cluster

Posted on 2026-10-25 In 数据存储 Word count in article: 3.9k Reading time ≈ 14 mins.

「Redis 扛不住了」这句话，八成是「key 太多」或「value 太大」，而不是「QPS 太高」。实测单实例 GET 在 8 个并发连接时就到了 27.5 万 rps，加到 128 连接也只到 32.9 万（+19%），而 p50 从 0.023 ms 涨到 0.199 ms（8.6 倍）——加并发不会让单实例更快，只会让延迟变高。

这一篇是收官篇，回答三个问题：单实例的上限在哪、什么时候该分片、分片之后要多付什么代价。最后附全系列 12 篇的总表。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片（本文·收官）

与前后篇的关系：② 的 QPS 基线、③ 的编码阈值、④ 的淘汰与碎片，共同决定本文的「天花板」；⑧ 的 Cluster 是分片的实现，本文回答「什么时候才该用它」。

1. 单实例的三个上限

flowchart TD
    A["Single Redis instance"] --> Q["QPS ceiling<br/>~30 万 GET/s（本文）"]
    A --> M["Memory ceiling<br/>keys x per-key bytes"]
    A --> C["Connection ceiling<br/>maxclients 10000（实测）"]
    Q --> S1["more clients != more QPS<br/>only more latency"]
    M --> S2["eviction / OOM / 碎片"]
    C --> S3["Too many connections"]

1.1 QPS：8 个连接就到顶了

单实例、10 万 key 已预热、GET 压测：

并发连接 QPS p50
1 32,916 0.031 ms
8 275,103 0.023 ms
32 310,078 0.055 ms
64 322,581 0.103 ms
128 328,947 0.199 ms

读法：

  1. 8 个连接就把单核吃满了（27.5 万 rps）；
  2. 从 8 加到 128，QPS 只涨 19%，p50 涨了 8.6 倍；
  3. 所以「加连接数」在单实例上不是扩容，是用延迟换一点点吞吐。

这是 loopback 的数字，生产环境受网络与客户端影响会更低；但「拐点在个位数到几十个连接」这个结论是普适的——因为 Redis 执行命令只有一个线程。

1.2 内存：按 key 数算，不是按 value 大小算

实测（MEMORY USAGE 抽样）：

value 大小 单 key 实际占用 额外开销 1 亿 key 估算
64 B 128 B 64 B 11.9 GB
1 KB 1,328 B 304 B 123.7 GB
10 KB 12,336 B 2,096 B 1,148.9 GB

三个必须知道的点：

  1. 小 value 的开销占比最高（64B 的 value 实际占 128B，开销 100%）；
  2. 大 value 有 jemalloc size class 效应（10 KB → 12 KB 桶，多 20%）；
  3. 1 亿个 10 KB 的 key 要 1.1 TB 内存——这时候必须分片，不是为了 QPS。

容量公式：

1.3 连接数：10000 是默认上限

指标 实测
maxclients 10000
单连接内存开销 约几十 KB（输入/输出缓冲 + 客户端结构）

10000 个连接 × 几十 KB 也是几百 MB，所以「连接数」既是限制也是内存成本。

1.4 该扩容的信号

信号 阈值 该做什么
QPS 到拐点 单实例 ~30 万（本文） 加从库（读扩展）或分片
内存接近上限 used_memory > maxmemory 的 80% 加内存、调淘汰、清理大 key
淘汰持续发生 evicted_keys 持续增长 先算真实容量（本文 1.2）
单 key 过大 > 10 KB 或集合 > 5000 拆 key（③）
fork 停顿明显 rdb_last_fork_usec 增长 减小实例内存、把持久化挪到从库
连接数接近上限 接近 10000 加连接池上限管理，或分实例

2. 分片：什么时候该上 Cluster

2.1 决策路径

flowchart TD
    A["Capacity alert"] --> B{"CPU-bound?<br/>QPS at knee"}
    B -- yes --> C["Read scaling:<br/>replicas + client routing"]
    C --> D{" writes also hot?"}
    D -- yes --> E["Sharding"]
    B -- no --> F{"memory-bound?"}
    F -- yes --> G{"can we shrink keys?<br/>TTL / big key split"}
    G -- yes --> H["Fix data model first"]
    G -- no --> E
    E --> I["Choose shard key,<br/>then reshard plan"]

判断顺序：先确认是 CPU 还是内存瓶颈 → 能靠读扩展/数据治理解决就不分片 → 都不行才分片。

2.2 三种分片方式

方式 扩容影响 客户端复杂度 适用
客户端分片（取模） 换 N 就全量迁移 高（业务自己算路由） 早期、分片数固定
代理分片（Codis/Twemproxy） 中 低（客户端无感） 已有代理层
Redis Cluster 槽迁移，可在线 中（要处理 MOVED/ASK） 主流选择

2.3 分片键：三个判据

判据 好 坏
均匀 用户 ID 哈希 状态、地区
查询能定位单片 user:{id}:profile 只有 SCAN 类需求
允许跨片？ 单 key 操作 跨片 MGET/Lua（⑥ 实测 CROSSSLOT）

hash tag 是分片设计的一部分：{user:1}:name 与 {user:1}:age 会落到同一个槽（⑧ 实测：都是 10778），这是「同一实体的多字段需要原子操作」的前提。

2.4 分片的真实代价

代价 具体表现 缓解
跨片操作 MGET/Lua 报 CROSSSLOT hash tag、应用侧拆分
多一次重定向 请求打错节点返回 MOVED，客户端重试 Smart client 缓存槽映射
运维复杂 扩缩容、槽迁移、故障转移 用成熟方案 + 演练
一致性变难 跨片事务不可用 业务拆分、最终一致
监控维度变多 要按节点看命中率/内存 统一看板

一个常被忽略的成本：MOVED 重定向意味着一次请求变成两次往返。⑧ 的实测里，SET user:1 在错误节点上直接返回：

客户端要再发一次。按 ② 的「一次往返 31 µs」算，每次重定向多一次 RTT；如果客户端不做槽缓存，所有请求都多一次 RTT，吞吐直接腰斩。

3.1 一张表算清

输入 取值 来源
目标 QPS 例如 50 万 业务预估
单实例 QPS 上限 例如 20 万（保守） 本文 1.1 实测打折
需要实例数（读） 3 主 + 3 从 主从分摊读
key 数量 例如 2 亿 业务
单 key 内存 例如 1.3 KB（1KB value） 本文 1.2
裸内存 2 亿 × 1.3 KB ≈ 260 GB 计算
加副本与碎片（×2.5） ≈ 650 GB 经验系数
单机内存上限 例如 64 GB 硬件
分片数 650 / 64 ≈ 11 → 12 片 向上取整

结论：这个场景需要 12 个分片（可以 12 主 + 12 从），而不是「加一台更大的机器」。

4.1 十二篇一览

# 篇目 一句话核心 给你的能力 关键实测
① 从这里开始：把 Redis 变成你的实验台 先数往返，再谈优化 能搭环境、跑基线、分清三种成本 PING 31 µs；1M key 139 B/key
② 一次请求的成本账 服务端执行只占 0.08% 能判断瓶颈在网络还是执行 pipeline 48×；unix socket 1.36×
③ 数据结构与编码 一个 field 能让内存涨 4.6 倍 能选编码、避开断崖 hash 512→513 涨 4.65×；zset 11.3×
④ 内存、淘汰与碎片 maxmemory 不等于安全 能配淘汰、能收碎片 Lua 绕过 maxmemory 写出 34 MB；defrag 回收 128 MB
⑤ 单线程与阻塞 一条慢命令让所有人排队 能定位并消除阻塞 KEYS 116 ms；DEL vs UNLINK 156 ms vs 7 µs
⑥ Pipeline、事务与 Lua Redis 事务不回滚 能选对原子性方案 1000 INCR：105→2.9 ms；Lua 扣减 100/1000
⑦ 持久化 kill -9 测不出 everysec 的丢失 能配 RDB/AOF、算丢失窗口 always 487 µs/op；AOF 18.6→4.3 MB
⑧ 复制、哨兵与 Cluster 切换时间由超时参数决定 能搭高可用、判断切换窗口 哨兵 3.33 s；Cluster 6.9 s
⑨ 缓存三大问题 缓存问题本质是数据库容量问题 能防穿透/击穿/雪崩 穿透 9,241 DB QPS；布隆误判 1.5%
⑩ 缓存与数据库一致性 先删缓存再更库 100% 出错 能选对更新顺序 60 轮并发：B 策略 60/60 不一致
⑪ 分布式锁与限流 锁适合防重复，不适合防并发写 能写出正确的锁与限流器 脑裂双锁；固定窗口 2× 超发
⑫ 容量规划与分片（本文） 加并发不加吞吐 能算容量、决定是否分片 8 连接即拐点；1 亿 key 1.1 TB

6. 动手验证：四个可复现实验

6.1 动手验证：测出你自己实例的 QPS 拐点

预期观察点：QPS 在 8~32 连接后平台化，p50 随连接数上升（本文 27.5 万 → 32.9 万，p50 0.023 → 0.199 ms）。

判定标准：QPS 随连接数持续增长 → 你的实例还有余量；QPS 下降 → 有 CPU 争抢或客户端瓶颈。

6.2 动手验证：按 key 数估算内存

预期观察点：64B→128B、1KB→1328B、10KB→12336B（本文）。

判定标准：实测值远大于 value → 有 jemalloc size class 取整，评估容量时要按实测乘 key 数。

6.3 动手验证：验证 hash tag 同槽

预期观察点：两个 {user:1}:* 槽号相同（本文 10778），user:2:name 不同（15992）。

判定标准：两个 hash tag key 槽号不同 → 花括号位置写错了（必须包住要哈希的部分）。

6.4 动手验证：算一次容量

预期观察点：输出应给出「QPS 需求」与「内存需求」两行，取较大者作为分片数。

判定标准：两者数量级差异很大 → 说明瓶颈单一，先按瓶颈那一侧扩容，别盲目分片。

5. 总结

5.1 面试速答表

面试题 一句话答案
单实例 Redis 能扛多少 QPS 本文 loopback 实测 ~33 万 GET/s，8 个连接就到拐点
加连接能提升 QPS 吗 几乎不能：8→128 连接 QPS +19%，p50 +8.6 倍
内存怎么估算 key 数 ×（value 按 size class 取整 + 64~300 B）× 副本 × 碎片系数
1 亿个 key 要多少内存 64B value 约 11.9 GB；10KB value 约 1.1 TB（本文实测）
什么时候该分片 QPS 到拐点且读扩展无效，或内存超过单机
Redis Cluster 有什么代价 跨槽操作受限、MOVED 多一次 RTT、运维复杂
分片键怎么选 均匀、查询必带、尽量单 key 操作
hash tag 是什么 {user:1} 只对花括号内计算槽，保证同实体的 key 同槽
为什么加了并发反而更慢 单线程排队，p50 上升
maxclients 默认多少 10000（本文实测）

5.2 实战避坑表

症状 原因 处理
加机器后 QPS 没涨 瓶颈在单实例 CPU/单 key 热点 分片或拆热点
内存按 value 算总超 忽略 key 开销与 size class 用 MEMORY USAGE 抽样（③）
分片后大量跨片报错 分片键与查询不匹配 重设计 key 或加 hash tag
分片后吞吐反而降 客户端没缓存槽映射，每次 MOVED 用 Smart Client
扩容迁移影响在线 槽迁移没限流 分批迁移 + 低峰执行

5.3 工具速查表

工具 看什么 判定标准
redis-benchmark -c QPS 与 p50 随并发变化 QPS 平台化 = 到拐点
MEMORY USAGE 单 key 实际内存 乘 key 数估容量
INFO memory used / rss / 碎片 80% 上限需扩容
CONFIG GET maxclients 连接上限 10000，接近要处理
CLUSTER KEYSLOT 槽归属 验证 hash tag
INFO commandstats 每命令耗时 找热点命令

5.4 实操建议

  1. 先算容量再谈分片：QPS、内存、连接数三个维度分别算，缺哪个补哪个。
  2. 单实例的 QPS 拐点比你想象的早（本文 8 个连接），别用「加连接」当扩容。
  3. 内存按 key 数 × 单 key 实际占用估，别用 value 大小乘（会差 2 倍以上）。
  4. 分片键必须在查询里出现，否则跨片查询会让分片失去意义。
  5. 分片前先做大 key 清理与 TTL 治理，否则分片只会把问题放大。

系列完结。十二篇的因果链是一条：先量（①）→ 算账（②）→ 数据与内存（③④）→ 单线程与原子性（⑤⑥）→ 持久化与高可用（⑦⑧）→ 应用模式（⑨⑩⑪）→ 最后才谈容量（⑫）。
