TCP 协议：可靠传输的代价

Posted on 2026-08-13 In 计算机网络 Word count in article: 4k Reading time ≈ 14 mins.

TCP（Transmission Control Protocol）是传输层的可靠字节流协议：用序号、确认、重传、窗口四套机制，把不可靠的网络变成「有序、不丢、不重」的字节流。 可靠是有代价的——握手延迟、确认往返、拥塞退避，每一个都是「性能 vs 可靠性」的显式权衡。本文回答四个问题：连接怎么建立和拆除、可靠性靠什么保证、为什么 TCP 有时快不起来、状态机怎么变成线上事故——并对照 TIME_WAIT/CLOSE_WAIT 堆积、SYN 洪泛、TCP_NODELAY 这些生产场景，看机制如何长成排查手段。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（本文：可靠传输与代价） → ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 从输入 URL 到页面展示全链路（串讲收官）。

1. 三次握手与四次挥手：连接的建立与拆除

1.1 三次握手：互相确认序号

连接建立的本质是双方同步序号——后续所有可靠性都建立在序号上。三次握手每次交换的都是「我的初始序号 + 我确认收到你的」：

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: SYN seq=100 (SYN_SENT)
    S->>C: SYN+ACK seq=300 ack=101 (SYN_RECV)
    C->>S: ACK seq=101 ack=301 (ESTABLISHED)
    Note over C,S: ESTABLISHED: 双方都确认了对方序号
  • 第 1 次（SYN）：客户端说「我想连，我的起始序号是 100」
  • 第 2 次（SYN+ACK）：服务端说「收到，我的起始序号是 300，请确认 101」
  • 第 3 次（ACK）：客户端说「确认 301」——只有第 3 次到达，服务端才确认「客户端确实活着」

1.2 为什么是三次而不是两次

两次握手无法防御「迟到的旧 SYN」：若客户端某次连接的超时 SYN 在网络里游荡，1 秒后才到服务端，服务端回 SYN+ACK 并建立连接、占用资源——而客户端根本不知道这回事（它早已放弃）。三次握手中客户端第 3 次的 ACK 携带了「我确实在发起这次连接」的确认，服务端收到它才分配连接资源，旧 SYN 永远等不到第 3 次 ACK，自然超时释放。

深挖：这直接决定了半连接与全连接队列的设计——服务端收到 SYN 只进半连接队列（内核管理，还没分配完整连接），收到第 3 次 ACK 才移入全连接队列（应用层 backlog 参数），accept() 从全连接队列取。两个队列的容量就是两个不同的攻击面（§4.2 展开）。

1.3 四次挥手：半关闭的两段告别

sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: FIN (FIN_WAIT_1)
    S->>C: ACK (CLOSE_WAIT / FIN_WAIT_2)
    S->>C: FIN (LAST_ACK)
    C->>S: ACK (TIME_WAIT 2MSL / CLOSED)

挥手是四次而不是三次，因为 TCP 支持半关闭：收到 FIN 只代表对方「不再发」，本端可能还有数据要发。于是「FIN → ACK」（对方发完）和「FIN → ACK」（本端发完）是两对独立的过程。生产上的时间点：先收到 FIN 的一方进入 CLOSE_WAIT，最后发送 FIN 的一方进入 TIME_WAIT。

1.4 深挖：TIME_WAIT 为什么必须等 2MSL

主动关闭方最后发 ACK 后进入 TIME_WAIT，等待 2 倍 MSL（报文最大生存时间，Linux 默认 60 秒），两个原因：

  1. 保证最后的 ACK 到达：ACK 可能丢失，对方会重发 FIN——TIME_WAIT 期间内核能重发 ACK；
  2. 防止旧报文污染新连接：网络中可能还游荡着这条连接的迟到报文（序号可能撞上新连接的序号），等 2MSL 让它们自然消亡。

因果链：TIME_WAIT 是「防迟到报文」的安全收尾，所以它不能通过调小端口或缩短等待来根治——高并发短连接服务的 TIME_WAIT 堆积（操作系统系列第 5 篇 §5.1 的端口耗尽事故）正解是连接复用：HTTP keep-alive、连接池把短连接变长连接，让 TIME_WAIT 根本不产生。机制决定解法，这是最典型的一例。

1.5 动手验证：亲眼看到握手与挥手

观察点：抓包里依次出现 S（SYN）→ S.（SYN+ACK）→ .（ACK）→ 数据 → 挥手时 F/F./F.P. 序列。判定标准：每 4 个包一组对应一次连接，三次握手 3 个包 + 挥手 4 个包清晰可见即验证通过。顺手看 ss -tan | grep 45681，客户端断开后服务端进入 CLOSE_WAIT——状态机不是背的，是观察出来的。

2. 可靠传输：序号、确认与重传

2.1 序号与累计确认

发送方给每个字节编号（seq），接收方回「下一个期望的字节号」（ack）。累计确认：ack=501 表示「500 之前都收到了，请从 501 开始发」——接收方不需要逐字节确认，一个 ack 覆盖之前全部。这是 TCP 高效的根本：确认开销与数据量无关，与「空洞」次数有关。

2.2 三种重传：从傻等到智能

重传机制 触发条件 代价
超时重传 发出去没等到 ACK，RTO 到期 慢（RTO 通常 200ms 起，指数退避）
快速重传 收到 3 个重复 ACK 快（不用等超时，立刻知道丢了）
SACK 收到带 SACK 选项的 ACK（报告空洞范围） 最快（只重传丢失的段，不重传全部）

深挖：快速重传是怎么「不超时就知道丢了」的——接收方收到乱序数据会立刻回「期望序号」的重复 ACK，发送方连收 3 个重复 ACK 就断定丢包（而不是等 RTO）。SACK 更进一步，接收方用选项字段报告「我收了 1-500 和 800-1000，缺 501-799」——发送方精确补缺。这就是为什么生产内核都默认开 SACK（tcp_sack=1），跨洋传输尤其依赖它——重传粒度从「整条」降到「一段」，吞吐差距能到数倍。

2.3 滑动窗口：流量控制

接收方在 ACK 里携带自己的接收窗口（rwnd），宣告「你最多再发这么多，我缓存放得下」——发送方的发送窗口 = min(自己的拥塞窗口 cwnd, 对方的 rwnd)。这就是流量控制：保护接收方不被撑爆。

因果链：窗口是「字节流没有消息边界」的机制源头——内核按窗口大小打包发送，应用层 write 的数据被切成段、段又可能被合并（回看第 1 篇 §5.2 的粘包拆包）。流量控制管「发多少」，拥塞控制管「发多快」，一个是接收方视角，一个是网络视角——两个窗口，两种保护对象。

2.4 动手验证：把确认和重传抓出来看

观察点：tcp_sack 为 1 说明 SACK 生效——之后所有重传都是「选择性补缺」而非整段重传。判定标准：内核参数为 1 + 抓包能看到 ACK 里带 SACK 选项，即验证了第 2.2 节的机制在当前系统是活的。

3. 拥塞控制：为什么 TCP 快不起来

3.1 慢启动与拥塞避免

拥塞窗口（cwnd）决定发送速率，算法分两段：

flowchart LR
    subgraph SS["Slow start (cwnd doubles each RTT)"]
        A1["cwnd=10 -> 20 -> 40 -> ..."]
    end
    subgraph CA["Congestion avoidance (cwnd +1 each RTT)"]
        B1["linear growth until packet loss"]
    end
    A1 -->|"hit ssthresh"| B1
    B1 -->|"packet loss: ssthresh = cwnd/2, cwnd reset"| A1
  • 慢启动：cwnd 从 10 段（RFC 6928）开始，每个 RTT 翻倍——指数增长，快速探测带宽；
  • 拥塞避免：涨到 ssthresh 后每个 RTT 只 +1——线性试探，逼近丢包边缘；
  • 丢包即信号：超时或 3 个重复 ACK 都判定网络拥塞，ssthresh 减半、cwnd 重置——这就是「TCP 快不起来」的机制根源：它靠丢包探测带宽，一旦探测到就退避，天然保守。

3.2 深挖：BDP——为什么「加了带宽还是慢」

BDP（带宽延迟积）= 带宽 × RTT：一秒钟「在路上」的数据量。要让链路打满，发送窗口必须 ≥ BDP，否则无论带宽多大，每个 RTT 只发得出一窗数据：

RTT 100Mbps 链路的 BDP 需要的窗口
10ms（同城） 125KB 默认窗口可能够用
100ms（跨洋） 1.25MB 必须调大 socket 缓冲区
500ms（卫星/跨洲） 6.25MB 远超默认，不调就永远跑不满

因果链：跨洋传输慢的根因往往不是带宽，是「窗口 < BDP」——Linux 的 tcp_rmem/tcp_wmem 上限（默认最大 4-6MB）在百兆跨洋链路下刚好不够。生产调优方向：确认 rmem/wmem 上限 ≥ BDP、开 tcp_window_scaling（默认已开）、或接受「长肥管道」的物理上限。面试答「为什么加了带宽没用」的正确姿势就是背出 BDP 公式并算出窗口需求。

3.3 深挖：Nagle 与延迟 ACK——小包的隐形敌人

  • Nagle 算法：小包（< MSS）要等「前面数据的 ACK 全部回来」或「缓冲凑满 MSS」才发——避免一堆小包占满带宽；
  • 延迟 ACK：接收方攒最多 40ms 再回 ACK——减少 ACK 数量。

两者叠加产生40ms 级的额外延迟（小请求被 Nagle 摁住、ACK 被延迟等），对 RPC/Redis 这类低延迟交互是灾难。解法：**TCP_NODELAY 关掉 Nagle（socket 选项 SO_TCP_NODELAY）——Netty 默认开启、Redis 服务端默认开启，这就是为什么它们响应快。因果链**：Nagle 是为「带宽利用率」设计的历史包袱，低延迟场景要显式关掉——「优化带宽的机制在延迟敏感场景变成负担」，这是 TCP 设计权衡的又一例。

3.4 动手验证：测量「窗口 < BDP」的直觉

观察点：算出 RTT 后立刻估算「这条链路要打满需要多大窗口」，再对比本机默认缓冲上限。判定标准：当「BDP 需求 > 默认上限」时你就预见到了「加带宽不加窗口没用」的生产结论——这就是公式变判断力。

4. 状态机排查：从状态堆积到生产事故

4.1 深挖：CLOSE_WAIT 堆积——代码泄漏的信号

CLOSE_WAIT = 对方发了 FIN，本端没调用 close()——连接「半死不活」地挂在那里。这是应用代码问题（不是内核问题）：读流没读完就放弃、异常路径忘了关闭、连接池里的连接没有 close。症状特征：ss -tan 里 CLOSE_WAIT 数量只增不减，lsof 看每个 fd 都对应同一个业务线程——排查方向是代码的关闭路径，不是调内核参数。

因果链：CLOSE_WAIT 是「TCP 半关闭机制 × 应用忘记关闭」的交叉产物——机制本身是正确的（等本端把数据发完），代价是泄漏必须由应用显式管理；Java 侧 try-with-resources、finally 关闭、连接池 testOnReturn 都是对「close 是义务」的工程化。

4.2 深挖：SYN_RECV 堆积——半连接队列溢出

ss -tan 大量 SYN_RECV = 服务端发了 SYN+ACK 但等不到第 3 次 ACK——半连接队列被占满。两个原因：

原因 特征 处理
SYN Flood 攻击 源 IP 随机、半连接数突增 内核 SYN cookies（tcp_syncookies=1）自动防；前置四层 LB 抗流量
backlog 太小 正常流量也堆半连接 调大 tcp_max_syn_backlog + 应用 backlog（Tomcat acceptCount、Netty SO_BACKLOG）

因果链：半连接队列是「三次握手分两阶段设计」的直接产物（§1.2）——攻击者只发 SYN 不发 ACK，就能占满队列让正常连接进不来；SYN cookies 的解法是「服务端不存半连接状态，把状态编码进 SYN+ACK 的序号里」——用机制绕过机制。

4.3 动手验证：复现 CLOSE_WAIT 堆积

观察点：20 个客户端断开后，ss -tan 里 45680 端口挂着 20 个 CLOSE_WAIT——服务端「没关」连接的现场。判定标准：CLOSE_WAIT 数量与客户端数一致即复现成功；修法就是把 // 不读不关 换成 finally 里 close——一次复现胜过十行背默。

5. 总结

5.1 面试速答表

面试题 一句话答案
三次握手为什么不是两次？ 防迟到的旧 SYN：服务端收到第 3 次 ACK 才确认「客户端真的在发起连接」，旧 SYN 等不到 ACK 自然释放
四次挥手为什么是四次？ TCP 支持半关闭，「对方发完」和「本端发完」是两对独立的 FIN/ACK
TIME_WAIT 为什么等 2MSL？ 保证最后 ACK 能重发 + 防迟到旧报文污染新连接；正解是连接复用不是调短
超时重传和快速重传的区别？ 超时靠 RTO 到期（慢），快速重传靠 3 个重复 ACK（快），SACK 只补丢失段（最快）
流量控制和拥塞控制的区别？ rwnd 保护接收方（发多少），cwnd 保护网络（发多快），发送窗口 = min 两者
为什么加带宽还是慢？ BDP = 带宽 × RTT，窗口 < BDP 就打不满链路，先算窗口需求
Nagle 为什么是低延迟敌人？ 小包被摁住等 ACK，叠加延迟 ACK 产生 40ms 级延迟；TCP_NODELAY 关闭
CLOSE_WAIT 堆积说明什么？ 收到 FIN 没调 close()——应用代码泄漏，不是内核问题

5.2 实战避坑表

症状 原因 处理
高并发短连接服务端口耗尽 TIME_WAIT 堆积占满端口范围 连接复用（keep-alive/连接池），别调小 TIME_WAIT
CLOSE_WAIT 只增不减 代码没关连接/连接池泄漏 排查关闭路径；try-with-resources；池参数
connect 超时但服务在跑 半连接/全连接队列溢出 看 SYN_RECV 数量；开 syncookies；调大 backlog
跨洋传输打不满带宽 窗口 < BDP 调大 tcp_rmem/wmem 上限；确认 window scaling 开启
小请求延迟稳定 40ms Nagle + 延迟 ACK 叠加 开 TCP_NODELAY（Netty/Redis 默认已开）
丢包后吞吐暴跌 无 SACK，整条重传 确认 tcp_sack=1

5.3 工具速查表

工具 看什么 对应机制
tcpdump S/S./F 序列、重传、SACK 握手/挥手/重传
ss -tan 各状态计数、五元组 状态机
ss -s TIME_WAIT/CLOSE_WAIT 总数 状态堆积

lsof -i 连接与进程的对应 排查归属

实操建议：

  1. 每台服务器 sysctl 核一遍：tcp_sack=1、tcp_syncookies=1、tcp_window_scaling=1 三件套，其余别乱调。
  2. 所有 Java socket/框架（Netty、Spring 连接池）确认走默认即已开 TCP_NODELAY；自定义 socket 记得显式设。
  3. 高并发短连接服务的架构决策（keep-alive、连接池、四层 LB 长连接转发）全部源于「TIME_WAIT 机制 + 端口资源」这笔账，选型时先算账。
