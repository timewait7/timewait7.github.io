限流算法详解

Posted on 2026-10-03 Word count in article: 6.5k Reading time ≈ 24 mins.

一、为什么需要限流

限流的本质，是在系统容量与请求流量之间划一条明确的边界。

1.1 不做限流的三种死法

mindmap
  root((不做限流))
    被刷爆
      恶意爬虫
      刷单脚本
      正常用户被挤出
    被秒杀打崩
      流量是日常 1000 倍
      连接池耗尽
      系统雪崩
    被下游拖死
      下游只有 100 QPS
      上游重试风暴
      级联故障

1.2 限流 vs 其他稳定性手段

flowchart LR
    A[请求到达] --> B{限流}
    B -- 通过 --> C[业务逻辑]
    B -- 拒绝 --> D[快速失败 429]
    C --> E{调用下游}
    E -- 成功 --> F[返回]
    E -- 失败率高 --> G[熔断]
    G --> H[降级兜底]
    H --> F
手段 触发时机 作用方向
限流 请求到达前 主动拒绝，保护系统
熔断 调用下游失败率高时 快速失败，保护调用方
降级 系统压力大 / 依赖不可用 关闭非核心，保核心
隔离 一直存在 资源不共享，限制爆炸半径

一句话：限流是”预先划定的容量”，降级是”故障时的保底”，熔断是”故障后的止损”，隔离是”故障前的预案”。

2.2 对比表格

算法 原理 优点 缺点 适用场景
固定窗口 每秒计数，超限拒绝 实现简单，内存 O(1) 窗口边界突发（59s 和 01s 各 100 次可绕过） 粗略限流、日志采样

关键认知：

  • 漏桶 vs 令牌桶：漏桶限制的是”流出速率”，令牌桶限制的是”平均速率 + 突发上限”。
  • 固定窗口 vs 滑动窗口：前者是后者的粗糙近似，后者精度更高但内存开销大。

3.1 固定窗口计数器

致命缺陷：窗口边界问题

sequenceDiagram
    participant U as 用户请求
    participant W1 as 窗口1 (0~1s)
    participant W2 as 窗口2 (1~2s)

    Note over W1: 阈值 100
    U->>W1: 0.9s 来了 100 个请求
    W1-->>U: 全部通过 ✅

    W2-->>U: 全部通过 ✅

改进方向：

  • 把窗口切小（如 100ms），代价是精度提升有限
  • 直接升级到滑动窗口

3.2 滑动窗口

原理图

flowchart LR
    subgraph SW["滑动窗口（动态右移）"]
        direction LR
        B1["桶1<br/>100ms"] --> B2["桶2<br/>100ms"] --> B3["桶3<br/>100ms"] --> B4["桶4<br/>100ms"] --> B5["桶N<br/>100ms"]
    end
    NOW(("当前时刻")) -.右边界.-> B5
    subgraph WIN["窗口内统计 = 所有桶 count 之和"]
    end

方式一：精确时间戳（内存高）

内存开销：每个请求一个 Long（8 字节）+ 队列开销。1000 QPS × 1 秒窗口 = 1000 个记录。如果窗口是 60 秒，QPS 是 1 万 → 60 万个记录 → 内存爆炸。

方式二：分桶统计（折中方案）

把窗口切成 N 个小格子（如 10 个 100ms 的格子），每个格子一个计数器。窗口内请求数 = 所有桶的 count 之和。当时间前进时，新桶加入，旧桶淘汰（环形数组实现）。

flowchart TB
    subgraph Ring["环形数组（固定大小 N）"]
        direction LR
        R1["桶0"] --> R2["桶1"] --> R3["桶2"] --> R4["..."] --> R5["桶N-1"] --> R1
    end
    T["时间前进"] --> Advance["淘汰旧桶<br/>新桶清零"]
    Advance --> Ring
    Ring --> Sum["求和 → 判断是否超限"]

精度 vs 内存的权衡：

  • 桶越多，精度越高，内存越大
  • 一般 10 个桶足够（误差 < 10%）

Sentinel 的实现：Sentinel 用的是 LeapArray + 滑动窗口，精度 1 秒分 2 个格子（500ms 一格），兼顾精度和性能。

3.3 漏桶

原理图

flowchart TB
    Req["请求<br/>↓↓↓"] --> Bucket
    subgraph Bucket["漏桶（容量 = 缓冲区大小）"]
        direction TB
        W["水位"]
        Hole["底部小孔"]
    end
    Bucket -- "固定速率流出" --> Down["下游服务"]
    Bucket -. "桶满则溢出（拒绝）" .-> Overflow["拒绝"]

核心特征

流出速率恒定，无论进来多少，下游看到的永远是稳定速率。

伪代码

时序图

sequenceDiagram
    participant U as 突发流量（100 个请求）
    participant B as 漏桶
    participant D as 下游（10 QPS）

    U->>B: T=0s 涌入 100 个
    B->>B: 水位上升到容量上限
    loop 每秒
        B->>D: 匀速漏出 10 个
    end
    Note over U,D: 通过曲线：恒定 10 QPS<br/>突发被强制平滑

适用场景

  • 调用第三方 API（对方有严格速率限制）
  • 保护数据库（不希望瞬间大批量写入）
  • 流量整形（把突发流量整形为平滑流量）

缺点

  • 突发流量会被”卡”在桶里，用户感知延迟增加
  • 秒杀场景下，用户等了半天还是被拒绝 → 体验差

3.4 令牌桶

原理图

flowchart TB
    Gen["令牌生成器<br/>固定速率 r/s"] -- "放入令牌" --> Bucket
    subgraph Bucket["令牌桶（容量 C）"]
        T["🪙 🪙 🪙 🪙 🪙<br/>最多 C 个"]
    end
    Req["请求到达"] -- "取 1 个令牌" --> Bucket
    Bucket -- "取到" --> Pass["✅ 通过"]
    Bucket -- "取不到" --> Reject["❌ 拒绝"]

与漏桶的本质区别

flowchart LR
    subgraph LB[漏桶]
        direction TB
        L1["进入"] --> L2["等待/排队"] --> L3["恒定速率流出"]
    end
    subgraph TB[令牌桶]
        direction TB
        T1["进入"] --> T2{"桶内有令牌?"}
        T2 -- 有 --> T3["立即通过（突发）"]
        T2 -- 无 --> T4["立即拒绝"]
    end
维度 漏桶 令牌桶
限制对象 流出速率 平均速率
突发支持 ❌ 强制平滑 ✅ 桶容量内允许突发
请求处理 入桶等待（或拒绝） 立即决策（取到/取不到）
用户体验 延迟增大 突发时响应快

伪代码

令牌补充过程（惰性补充）

sequenceDiagram
    participant R as 请求
    participant TB as 令牌桶

    Note over TB: 初始 tokens=C
    R->>TB: T=0s 请求 1
    TB->>TB: 补令牌: min(C, C+0*rate) = C
    TB->>TB: tokens = C-1 → 通过

    R->>TB: T=0.1s 请求 2
    TB->>TB: 补令牌: min(C, (C-1)+0.1*rate)
    TB->>TB: tokens -= 1 → 通过

    Note over R,TB: 空闲一段时间

    R->>TB: T=10s 请求 N
    TB->>TB: 补令牌: min(C, 0+10*rate) = C
    Note over TB: 上限封顶，不会无限累积

关键设计点

  1. 惰性补充：不需要后台定时器，每次请求时按流逝时间计算应补充多少令牌。
  2. 上限封顶：Math.min(capacity, ...) 保证令牌不会无限累积。
  3. **synchronized**：单机版保证线程安全；分布式场景必须用 Redis + Lua。

参数示例

  • 容量 10，速率 5/s
  • 瞬间来 20 个请求：前 10 个立即通过（消耗桶内令牌），之后按每秒 5 个放行
  • 通过曲线：突发 10 + 匀速 5/s

四、为什么秒杀选令牌桶

秒杀的特点是「开闸瞬间所有用户同时涌来」——流量曲线不是平滑的，而是脉冲式的。

4.1 各算法在秒杀场景的表现

flowchart TB
    Sp["秒杀开场瞬间<br/>10 万请求"] --> FW
    Sp --> SW
    Sp --> LB
    Sp --> TB

    FW["固定窗口<br/>边界问题导致不公平"]
    SW["滑动窗口<br/>精度高但无突发能力"]
    LB["漏桶<br/>强制平滑，用户等待久"]
    TB["令牌桶<br/>✅ 允许桶内突发，快速放量"]

    style TB fill:#9f9,stroke:#333
    style FW fill:#f99,stroke:#333
    style SW fill:#fc9,stroke:#333
    style LB fill:#fc9,stroke:#333
算法 开场瞬间表现 问题
固定窗口 第 1 秒内只放 100 个，其余拒绝 边界问题导致不公平
滑动窗口 精度高，但依然严格限制 无突发能力，用户感知差
漏桶 强制平滑，大量请求排队 用户等半天还是失败，体验差
令牌桶 桶内令牌瞬间放量 需要预估桶容量

4.2 令牌桶的秒杀策略

sequenceDiagram
    participant U as 10 万用户
    participant TB as 令牌桶(容量=1万,速率=5000/s)
    participant S as 库存系统

    U->>TB: T=0s 同时涌入 10 万
    TB-->>U: 前 1 万个（桶内令牌）立即通过
    TB-->>U: 其余 9 万个立即拒绝（快速失败）
    TB->>S: 平滑放量 5000/s

    Note over U,S: 设计哲学：<br/>1. 前 1 万快速通过，让"有能力的用户"进得来<br/>2. 后续平滑放量，保护下游库存<br/>3. 快速失败，不占连接

五、分布式限流：单机限流 × N 实例 = 灾难

5.1 问题本质

单机限流（如 Guava RateLimiter、本地令牌桶）在分布式下各算各的。

flowchart TB
    LB["负载均衡"] --> A["实例A<br/>限流100<br/>收到300 → 拒200"]
    LB --> B["实例B<br/>限流100<br/>收到50 → 浪费50"]
    LB --> C["实例C<br/>限流100<br/>收到100 → 满载"]
    LB --> D["实例D<br/>限流100<br/>收到550 → 拒450"]

    Note["目标：全集群 1000 QPS<br/>实际：10 台 × 100 = 1000 QPS<br/>问题：流量不均 → 明明有余量却拒绝"]

    style A fill:#fdd
    style B fill:#dfd
    style D fill:#fdd

根本原因：单机限流是实例级的，不是服务级的。

5.2 分布式限流方案对比

方案 原理 优点 缺点
Redis + Lua 集中式计数/令牌桶 精确，易实现 Redis 是瓶颈，网络 RTT
Redis + 分段 每实例分配一段配额 减少 Redis 压力 流量不均时浪费
Nginx + Lua 网关层限流 挡在最前面 单点，需集群化
Sentinel 集群模式 Token Server 集中发令牌 成熟方案 需要额外部署
一致性哈希 按 key 路由到固定实例 无中心 扩缩容麻烦

5.3 Redis + Lua 的原子性

sequenceDiagram
    participant C as 客户端
    participant R as Redis
    participant L as Lua 脚本

    Note over C,R: ❌ 错误：两条命令之间可能被其他请求插入
    C->>R: INCR key
    R-->>C: 1
    Note over C,R: ← 此处被其他请求插入！
    C->>R: EXPIRE key 1

    Note over C,R: ✅ 正确：Lua 脚本原子执行
    C->>R: EVALSHA script 1 key 100 1
    R->>L: 单线程执行 INCR + EXPIRE + 判断
    L-->>R: return 1
    R-->>C: 1

Lua 脚本（固定窗口版）：

Lua 脚本的优势：

  • Redis 单线程执行 Lua，天然原子
  • 一次网络往返，减少 RTT
  • 脚本可缓存，后续调用只传 SHA1

6.1 分层架构图

八、限流与降级的联动

8.1 核心理念

限流是「预先划定的容量」，降级是「故障时的保底」——两者必须联动。

当限流指标（拒绝率）超过阈值，说明系统真被打到了，触发降级——关闭非核心功能（购物车、推荐位、评论），把资源全部让给下单链路。

十、常见面试问题

Q1：固定窗口的边界问题怎么解决？

答：升级到滑动窗口。滑动窗口有两种实现：

  • 精确时间戳（内存高，O(QPS × 窗口)）
  • 分桶统计（内存低，精度略低，Sentinel 用这种）

固定窗口切小粒度只能缓解，无法根治。

Q2：漏桶和令牌桶的本质区别？

答：

  • 漏桶限制流出速率，请求必须排队等待，强制平滑，不允许突发。
  • 令牌桶限制平均速率，桶容量内的突发可以立即通过，允许突发。

一句话：漏桶是”你按我的节奏走”，令牌桶是”你可以在额度内自由发挥”。

flowchart LR
    subgraph LB[漏桶]
        L1["请求"] --> L2["排队"] --> L3["匀速流出"]
    end
    subgraph TB[令牌桶]
        T1["请求"] --> T2["查令牌"] --> T3{"有?"} --> |有| T4["立即通过"]
        T3 --> |无| T5["立即拒绝"]
    end

Q3：分布式限流怎么保证总量？

答：核心是集中式计数器。方案：

  1. Redis + Lua（推荐）：原子性强，一次 RTT。
  2. 分段配额：每实例预分配一段，减少 Redis 压力，但流量不均时浪费。
  3. Sentinel 集群模式：Token Server 集中发令牌。

面试重点：单机限流 × N 实例 ≠ 总量限流。

Q4：令牌桶的令牌为什么要惰性补充？

答：如果每 100ms 定时补一次令牌，需要后台定时器，N 个限流 key 就需要 N 个定时任务，资源浪费。惰性补充是每次请求时按流逝时间计算应补多少，把 O(N) 的定时成本变成 O(1) 的请求成本。

Q5：限流和熔断的区别？

答：

维度 限流 熔断
触发时机 请求到达前 调用下游失败率高时
保护对象 自己 调用方
状态 无状态/简单状态 三态（关闭/半开/打开）
恢复方式 自动（时间窗口） 需探测（半开状态试调用） 
stateDiagram-v2
    [*] --> Closed: 初始
    Closed --> Open: 失败率超阈值
    Open --> HalfOpen: 等待时间到
    HalfOpen --> Closed: 探测成功
    HalfOpen --> Open: 探测失败

Q6：限流阈值怎么定？

答：三步法：

  1. 压测确定单机容量：P99 RT < 200ms 时的最大 QPS。
  2. 留 20% buffer：阈值 = 压测值 × 0.8。
  3. 动态调整：通过 Nacos 配置，大促前手动调整。

不要拍脑袋：max=1000 这种数字必须有压测数据支撑。

Q7：限流拦截器为什么用 ThreadLocal 记录开始时间？

答：preHandle 和 postHandle / afterCompletion 是同一个线程执行的（同步请求），用 ThreadLocal 传递状态最简单。**必须 remove()**，因为 Tomcat 线程池会复用线程，不 remove 会导致内存泄漏 + 脏数据。

注意：异步请求（Callable、DeferredResult）会切换线程，ThreadLocal 会失效，需要改用 RequestContextHolder 或 AsyncListener。

Q8：为什么 429 响应要带 Retry-After？

答：HTTP 标准里，429 表示 “Too Many Requests”，配合 Retry-After 头告诉客户端多久后重试：

好处：

  • 规范客户端行为，避免盲目重试
  • 配合指数退避，保护服务端
