死锁与线程泄漏：从 jstack 到 JFR

Posted on 2026-10-26 In Java Word count in article: 2.8k Reading time ≈ 10 mins.

死锁能被 JVM 直接检测出来：ThreadMXBean.findDeadlockedThreads() 返回 2 个线程，jcmd Thread.print 直接打印 Found one Java-level deadlock 和完整的「谁在等谁」链条。但JFR 抓不到已经发生的死锁（实测 jdk.JavaMonitorEnter 0 事件），因为它只记录「从录制开始后新发生的等待」。

这篇把两类事故做成可复现实验：死锁（两锁反序）和线程泄漏（池外建线程、ThreadLocal 不 remove），并给出 5 分钟内定位的完整链条。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度 → ③ JMM → ④ 伪共享 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏（本文） → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：⑧ 讲「池怎么配」，本文讲「池用错会怎样」；⑨ 的 await() 无超时是同一类「无限等待」。

1. 两类事故，一眼区分

事故 表现 关键证据
死锁 服务卡住、CPU 不高、线程不结束 Thread.print 里的 Found one Java-level deadlock
线程泄漏 线程数持续上涨、内存上涨 ThreadCount 增长、jcmd Thread.print 里同名线程成百上千
ThreadLocal 泄漏 请求间数据串了、内存不释放 池线程复用后读到上个任务的值

    B -- no --> C["thread dump: BLOCKED?"]
    C -- yes --> D["deadlock or lock contention"]
    C -- no --> E["WAITING / TIMED_WAITING<br/>(await, park, IO)"]
    B -- yes --> F["thread count growing?"]
    F -- yes --> G["thread leak / pool explosion"]
    F -- no --> H["GC / spin / contention"]

2.3 死锁形成的时序

sequenceDiagram
    participant T1 as worker-1
    participant A as Lock A
    participant B as Lock B
    participant T2 as worker-2
    T1->>A: lock A (ok)
    T2->>B: lock B (ok)
    T1->>B: lock B -> BLOCKED
    T2->>A: lock A -> BLOCKED
    Note over T1,T2: circular wait = deadlock

2.4 JFR 为什么抓不到

事实 解释
JFR 录制 3 秒，JavaMonitorEnter 0 事件 事件在阻塞开始时记录；线程在录制开始前就已经阻塞
死锁是「永不结束的阻塞」 事件要等阻塞结束才会被完整写出

结论：死锁用 jstack/Thread.print，JFR 用来看「还没死」的慢等待。这是两套互补的工具，不是替代关系。

2.5 三种解法

解法 做法 代价
统一锁顺序 所有线程按同一顺序加锁 需要全局约定，跨模块难统一
超时放弃 tryLock(timeout)，失败就回滚重试 需要业务能回滚
减少锁嵌套 只锁一个资源；用无锁结构 需要重构

实测「统一锁顺序」：

版本 检测结果
反序加锁 findDeadlockedThreads 返回 2 个线程，两线程都不结束
统一先 A 后 B findDeadlockedThreads 返回 null，两线程正常结束

3. 线程泄漏：池外建线程

3.1 实测：300 个线程

已建线程 JVM 线程总数 基线
100 107 7
200 207 7
300 307 7

每个线程 1 MB 栈（②实测）→ 300 个线程约 300 MB 内存，且都在 sleep，什么也没干。如果持续创建（比如每个请求 new Thread），几小时内就会 unable to create native thread。

3.2 三种泄漏源

泄漏源 原因 处理
池外 new Thread 每个请求/任务新建 全部改为线程池提交
Executors.newCachedThreadPool max=Integer.MAX_VALUE，无界 换固定池 + 有界队列（⑧）
ScheduledExecutorService 未关闭 定时任务持续创建 服务关闭时 shutdown

3.3 ThreadLocal 泄漏：池线程串数据

这是最隐蔽的一种，因为线程数不会涨，但会「读到别人的数据」：

实测：

步骤 结果
任务 1 设置 user-1，不 remove —
任务 2（同一池线程）读取 user-1（串数据）
正确做法：finally { USER.remove(); } 后 下一个任务读到 null 
sequenceDiagram
    participant P as pool thread
    participant TL as ThreadLocalMap
    P->>TL: task1: set("user-1")
    Note over TL: no remove
    P->>TL: task2: get() -> "user-1" (leak!)
    Note over P: same thread, same map
    P->>TL: task3: set + finally remove
    P->>TL: task4: get() -> null

为什么危险：在 Web 应用里，池线程被复用，user-1 的上下文会泄漏到下一个用户的请求上——越权就是这么来的。

4. 5 分钟定位链条

flowchart LR
    A["alert: hang or slow"] --> B["jcmd Thread.print<br/>grep deadlock"]
    B -->|found| C["fix lock order / tryLock"]
    B -->|not found| D["grep BLOCKED count"]
    D -->|many| E["reduce critical section"]
    D -->|none| F["grep thread count by name"]
    F -->|growing| G["find new Thread() calls"]
    F -->|stable| H["JFR: ThreadPark / monitor enter"]
    H --> I["3x jstack sampling"]
步骤 命令 看什么
1 jcmd <pid> Thread.print 是否 Found one Java-level deadlock
2 jcmd <pid> Thread.print | grep "BLOCKED" 大量 BLOCKED = 锁竞争
3 jcmd <pid> Thread.print | grep -c "leak-" 同名线程成百上千 = 泄漏
4 jcmd <pid> JFR.start duration=30s filename=x.jfr 慢等待（ThreadPark、JavaMonitorEnter）
5 jstack 三次采样（间隔 5s） 哪个栈帧一直不变 = 卡住的位置

「三次采样」是最实用的技巧：如果某个线程在三次 dump 里都在同一行等待，基本可以确定卡在那里。

5. 动手验证：四个可复现实验

5.1 动手验证：复现并检测死锁

预期观察点：deadlocked=2，输出两个线程名；Thread.print 打印「谁持有谁等待」。

判定标准：

  • deadlocked=null → 两个线程没有真正交叉（加长 sleep）；
  • Thread.print 没有死锁段 → 你抓的时间点太早，等 2 秒再抓。

5.2 动手验证：统一锁顺序解决死锁

预期观察点：deadlocked=null，both finished=true。

判定标准：

  • 仍检测到死锁 → 两个线程的加锁顺序还是不一致，检查 Runnable 是否被两处复用同一顺序。

5.3 动手验证：线程泄漏与 ThreadLocal 串数据

预期观察点：未 remove 时读到 user-1（串数据）；remove 后读到 null；线程数随创建数线性上涨。

判定标准：

  • 读到 null → 你的池线程是新建的（池大小 > 任务数），把池设为 1 再试；
  • 线程数不涨 → 你可能用了虚拟线程（⑪），它们不占平台线程。

5.4 动手验证：三次采样定位卡点

预期观察点：三次采样里 worker-1 都停在同一个 waiting to lock 行。

判定标准：

  • 三次栈不同 → 线程在正常干活，不是卡死；
  • 栈里出现 Object.wait → 那是 wait/notify 等通知，不是死锁，检查是否漏了 notify。

6. 总结

6.1 面试速答表

面试题 一句话答案
死锁的四个必要条件 互斥、持有并等待、不可剥夺、循环等待
怎么检测死锁 ThreadMXBean.findDeadlockedThreads() 或 jcmd Thread.print
jcmd 输出里怎么看死锁 搜 Found one Java-level deadlock，看「held by」链条
JFR 能抓死锁吗 抓不到已经发生的死锁（本文实测 0 事件），只能看新的慢等待
怎么避免死锁 统一锁顺序、tryLock 超时、减少锁嵌套
线程泄漏怎么发现 ThreadCount 持续上涨、Thread.print 同名线程成百上千
300 个线程占多少内存 约 300 MB 栈（1 MB/线程，本文实测）
ThreadLocal 为什么要 remove 池线程复用会串数据（实测读到上个任务的 user-1）
ThreadLocal 会内存泄漏吗 会，key 是弱引用但 value 强引用，线程不结束就不释放
三次采样有什么用 三次 dump 在同一行 = 确定卡死位置
wait 与 BLOCKED 的区别 wait 等通知（WAITING），BLOCKED 等锁
死锁和活锁的区别 死锁互相等，活锁互相让（都在跑但没进展）

6.2 实战避坑表

症状 原因 处理
服务卡住、CPU 低 死锁或无限 await Thread.print 抓死锁
线程数缓慢上涨 池外建线程 / 缓存池无界 改固定池 + 有界队列
请求间数据串了 ThreadLocal 没 remove finally 里 remove
OutOfMemoryError: unable to create native thread 线程数 × 栈超限 减线程、降 -Xss、用虚拟线程
await() 永不返回 计数不匹配 加超时 + 检查计数
死锁偶发、无法复现 锁顺序依赖执行时序 统一顺序 + tryLock 超时

6.3 工具速查表

工具 看什么 判定标准
ThreadMXBean.findDeadlockedThreads() 死锁线程 id 非 null 即死锁
jcmd <pid> Thread.print 死锁段、BLOCKED 有 Found one Java-level deadlock
jcmd <pid> JFR.start 慢等待事件 只对「录制开始后」的等待有效
三次 jstack 采样 是否卡在同一帧 三次相同 = 卡死
jcmd <pid> VM.native_memory summary Thread 区域 2 中实测 1 MB/线程

6.4 实操建议

  1. 上线前做一次「锁顺序审计」，所有多锁路径统一顺序。
  2. **禁止池外 new Thread**，代码扫描规则就能拦住。
  3. **ThreadLocal 必须 finally remove**，或用 ScopedValue（JDK 21 预览）。
  4. Thread.print 存三份，间隔 5 秒，比对栈帧是最快的定位方法。
  5. JFR 用来抓「慢」而不是「死」，死锁用 Thread.print。
