进程与线程：从模型到调度

Posted on 2026-08-12 In 操作系统 Word count in article: 4.9k Reading time ≈ 18 mins.

进程（process）是正在运行的程序实例：程序是磁盘上的静态代码，进程是它被加载进内存后的一套完整运行环境。同一个程序可以同时跑出多个进程——开两个 IDE 窗口就是两个进程。本文回答三个问题：进程/线程/协程到底是什么、CPU 怎么把时间分给它们、切换到底贵在哪——并对照你天天用的技术（线程池大小、虚拟线程、容器 PID 1、Go 的 goroutine），看这些设计怎么从本文的机制里长出来。

系列地图（操作系统）：① 进程与线程（本文：执行单元与调度） → ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（等待数据的方式）→ ⑤ Linux 资源排查实战（工具收拢）。本文的切换成本是 ④ 里「BIO 为什么不行」的根因，本文的栈内存是 ② 里「线程多了为什么 OOM」的依据。

1. 进程模型：正在运行的程序

1.1 程序的四个组成部分

一个进程由四部分构成：

组成 内容 说明
程序代码 指令序列 只读段，可共享（同一程序多进程共享代码段）
地址空间 虚拟内存布局 代码段、数据段、堆、栈
运行状态 寄存器、程序计数器 中断/切换时用于保存现场
系统资源 文件描述符、信号、IPC 打开的文件、管道、socket

内核用进程控制块（PCB，Process Control Block）统一管理进程的一切，Linux 里叫 task_struct：PID、状态、寄存器快照、内存映射、打开的文件表、CPU 使用统计……可以把它理解为进程在操作系统里的「档案袋」。

flowchart TD
    PCB["Process Control Block<br/>(task_struct)"] --> ID["PID / PPID"]
    PCB --> STATE["Process state<br/>R / S / D / Z / T"]
    PCB --> REGS["Register file & PC<br/>(context save area)"]
    PCB --> MEM["Memory mapping<br/>code / data / heap / stack"]
    PCB --> FILES["Open file descriptors"]
    PCB --> STAT["CPU time & scheduling info"]
    PCB --> IPC["Signals / semaphores / pipes"]

注意 PCB 存在内核内存里，用户程序访问不到——这是第 4 节要讲「分态」的原因之一。

1.2 生命周期：五个状态

进程一生在几个状态间迁移，ps 输出的 S 列就是当前状态：

stateDiagram-v2
    [*] --> New: fork()
    New --> Ready: accepted by scheduler
    Ready --> Running: schedule
    Running --> Ready: time slice expired
    Running --> Blocked: I/O wait
    Blocked --> Ready: I/O complete
    Running --> Zombie: exit()
    Zombie --> [*]: reaped by parent (wait)
状态 含义 ps 标识
就绪（Ready） 一切就绪，只等 CPU R
运行（Running） 正在 CPU 上执行 R
阻塞（Blocked） 等 I/O 或锁 S（可中断睡眠）/ D（不可中断）
僵尸（Zombie） 已退出、等父进程回收 Z
孤儿（Orphan） 父进程先死，被 1 号进程收养 无专门标识

僵尸进程是「已退出但还没被父进程 wait() 回收」的进程：不占 CPU 不占内存（PCB 还占着），但 PID 不释放，多了会耗尽 PID 上限。父进程用 wait()/waitpid() 收尸，Java 里对应的就是 Process.waitFor()。父进程先死了怎么办？孤儿进程由 1 号进程（init/systemd）自动收养回收——所以孤儿不可怕，僵尸要防。

Java 里反而不容易造出僵尸——JDK 的 Process 内部有 reaper 线程自动 waitpid 回收子进程。真正常见的坑是「起了子进程但没人读它的输出流」：子进程写满管道缓冲区（64KB）后永久阻塞，表现为整个流程卡死（1.3 有实验）。僵尸进程更多出现在 C/Shell 场景（1.3 给造法）。

2. 线程：进程内的执行流

线程（thread）是 CPU 调度的最小单位，进程是资源分配的最小单位。一个进程可以有多个线程：共享进程的地址空间和文件描述符，各自独立持有栈和寄存器。

共享（进程级） 独占（线程级）
代码段、数据段 栈（调用现场）
堆（new 出来的对象） 寄存器
文件描述符 线程局部存储（TLS）
信号处理、全局变量 调度上下文（PC、SP） 
flowchart LR
    subgraph Process[Process address space]
        CODE["Code & data"] --- HEAP["Heap"]
        FILES["File descriptors"]
    end
    subgraph T1["Thread 1"]
        S1["Stack & registers"]
    end
    subgraph T2["Thread 2"]
        S2["Stack & registers"]
    end
    CODE --- T1
    CODE --- T2
    HEAP --- T1
    HEAP --- T2
    FILES --- T1
    FILES --- T2

2.1 三种线程模型

模型 调度在哪 代表 特点
1:1 内核线程 内核 Linux pthread、Java 平台线程 内核原生支持，但每个线程都占内核资源
M:N 用户线程 用户态库 Java 早期绿色线程（已废弃） 灵活但调度映射复杂，难调优
协程/虚拟线程 用户态 + JVM Go goroutine、Java 虚拟线程 栈上调度，阻塞不占内核线程，百万级并发

Java 平台线程是 1:1 内核线程——每 new 一个 Thread 就创建一个内核线程，所以线程数量上不去；Java 虚拟线程（JDK 21 正式版）是 JVM 用户态调度的协程：线程数可以到几十万，阻塞 I/O 时让出底层载体线程（carrier thread），这就是「百万并发」的来源。

对照 Go 的 goroutine（面试常被连起来问）：Go 的 GMP 模型和虚拟线程同构——G（goroutine）= 虚拟线程，M（machine）= 载体线程，P（processor）= 调度器配额。G 在 channel/syscall 上阻塞时让出 M，M 挂上别的 G 继续跑；Go 不区分「平台线程/虚拟线程」，所有 goroutine 默认都在这个模型里。区别在阻塞边界：Java 虚拟线程遇到 synchronized 会 pin 住载体线程（JDK 21 已基本修复），Go 没有这个历史包袱——所以「Go 天然高并发」的底层原因，就是它从语言诞生起就建在协程模型上。

2.2 为什么线程比进程轻

创建进程要分配/复制地址空间（fork 走写时拷贝），创建线程只是多一个栈和一份调度上下文；切换进程要换页表（TLB 全部失效重载），切换线程共享同一地址空间，只换栈指针和寄存器。一句话：线程省掉了「换地址空间」这个最贵的步骤。

top -Hp <jvm_pid> 按线程查看（PID 列实际是 TID）；jstack <pid> 输出每个 Java 线程的栈，状态列能直接对上内核状态：

jstack 状态 内核状态 典型场景
RUNNABLE R 正在计算；I/O 轮询（epoll 等待）也算 RUNNABLE
TIMED_WAITING（sleep/park） S Thread.sleep、LockSupport.parkNanos
WAITING（park） S 等 join、condition 的 await
BLOCKED S 等 synchronized 监视器锁

一个常见误判：top 看 Java 进程 CPU 高，top -Hp 发现只有少数 TID 在忙——说明瓶颈在锁竞争或单线程阻塞，线程池开再大也没用，要先看 jstack 找锁。

虚拟线程的并发上限实验（JDK 21+）：

同样「10 万个线程睡 1 秒」：平台线程先撞上限，虚拟线程几秒内起完、内存低一个数量级——这就是 1:1 内核线程模型和协程模型的分水岭，也是高并发网关（Netty 连接层 + 虚拟线程业务层）新架构的底气。

3. 调度：CPU 时间怎么分

调度器（scheduler）负责从就绪任务里选一个上 CPU。单核机器上「同时运行」其实是时间片轮流，调度器决定谁先、谁多、谁被饿死。

3.1 调度算法演进

算法 思路 优点 缺点
FCFS 先来先服务 按到达顺序 简单、公平 长任务堵住短任务（护航效应）
SJF 最短作业优先 先跑最短的 平均等待最小 需预知运行时间，长任务饿死
RR 时间片轮转 固定时间片轮换 响应快 时间片大小难定：太大退化成 FCFS，太小切换开销爆炸
优先级调度 高优先级先跑 满足交互需求 低优先级饿死，需老化机制
MLFQ 多级反馈队列 多级队列 + 动态升降级 兼顾交互与吞吐 参数多，难调
CFS 完全公平（Linux） 按 vruntime 红黑树取最小 公平、O(log n) 不是硬实时

3.2 Linux CFS：把公平量化成 vruntime

Linux 默认调度器 CFS（Completely Fair Scheduler）把「公平」量化成 vruntime（虚拟运行时间）：每个进程按权重累积 vruntime，谁 vruntime 最小谁上 CPU。就绪队列用红黑树按 vruntime 排序，取最左节点 O(log n)。权重由 nice 值决定：nice 越大权重越小、vruntime 涨得越快——nice 0 的进程比 nice 19 的「值钱」得多。

flowchart TD
    A["CPU tick / new task arrives"] --> B["Compute vruntime for each runnable task"]
    B --> C["Pick task with min vruntime<br/>(leftmost in red-black tree)"]
    C --> D["Run for time slice"]
    D --> E{"Preempted or<br/>slice expired?"}
    E -- No --> D
    E -- Yes --> A

一个反直觉但重要的点：CFS 是「按比例分」而不是「轮流分」——睡眠（I/O 等待）期间 vruntime 不涨，所以 IO 密集进程醒来后天然排前面，响应快；CPU 密集进程也不会被饿死，只是分到的比例低。

3.3 上下文切换：切换到底贵在哪

上下文切换（context switch）是把 CPU 从当前任务切到另一个任务的完整过程，发生在时间片耗尽、任务主动让出（I/O、锁等待）或中断时。

切换类型 成本量级 拆解
进程切换 1-10 µs 保存/恢复寄存器 + 切换页表（TLB 全失效）+ 内核态进出
线程切换 0.5-2 µs 同进程：只换寄存器快照和栈，不碰页表
系统调用 0.1-1 µs 只进出内核态，不换任务

所以线程数量远超 CPU 核数时，大量时间花在切换而不是干活上——这就是「线程池核心线程数 ≈ CPU 核数（CPU 密集）或 ×(1+IO 等待/计算比)（IO 密集）」的底层依据。

真实场景：压测 TPS 上不去，vmstat 1 里 cs（context switch）列每秒几十万——线程池 300 线程跑 8 核机器，大半时间在切线程。缩到 40 线程后 TPS 反而翻倍。排查命令：pidstat -w 1 看自愿/非自愿切换，/proc/<pid>/status 里的 voluntary_ctxt_switches 字段。

低延迟服务（如网关）把自身进程 nice 调高、把批处理任务（日志压缩、报表）nice 调低，让 CFS 把时间片多分给前者——「按 vruntime 分时间」在生产里的直接用法。

真实复盘案例：某服务 8 核机器，线程池 300 线程，TPS 卡在 4000 上不去；vmstat 1 显示 cs 每秒 30 万+，pidstat -w 显示每个 worker 每秒上万次非自愿切换（时间片被抢）。线程池缩到 64 后 cs 降到 5 万，TPS 升到 9000。排查链路固定为：vmstat 1 看 cs → top -Hp 确认线程数 → 调线程池 → 复测 cs 与 TPS。

判定标准：cs 超过「核数 × 2 万/秒」（8 核约 16 万）就要警惕切换占比过高；vmstat 里 %sy（内核态时间）占比异常高，也常是切换或 syscall 过多的信号。

4. 用户态与内核态：系统调用的代价

用户态（user mode）与内核态（kernel mode）是 CPU 的两种特权级别：内核态能执行特权指令（访问硬件、改页表），用户态不行。用户程序想动硬件，必须通过系统调用（syscall）请内核代劳。分态的目的是安全和隔离：你写的代码不能直接改别人的内存、不能直接写硬盘。

4.1 系统调用链路

Java 里一次文件读取，底层链路是这样的：

sequenceDiagram
    participant Java as Java (user mode)
    participant Libc as glibc (user mode)
    participant Kernel as Kernel (kernel mode)
    participant Disk as Disk / Page Cache
    Java->>Libc: FileInputStream.read()
    Libc->>Kernel: syscall read(fd, buf, len)
    Kernel->>Disk: page cache lookup / device I/O
    Disk-->>Kernel: data
    Kernel-->>Libc: copy to user buffer, return len
    Libc-->>Java: bytes

每发一次 syscall 就有一次用户态↔内核态切换。态切换本身不重（亚微秒级），重的是它打断 CPU 流水线、每次都要校验参数和权限。由此推出两个工程结论：

  • 读 1 字节和读 4KB 都是 1 次 read syscall——缓冲（BufferedInputStream）的意义就在这里：把 N 次小 syscall 合并成一次大的；
  • 高性能框架都在「少 syscall」上做文章：批量读写、mmap、sendfile 零拷贝（一次 syscall 在内核态内完成磁盘→socket 拷贝，详见操作系统系列的 IO 模型篇）。

4.2 两种模式的对照

维度 用户态 内核态
权限 受限指令集 特权指令（I/O、内存管理、中断）
谁在跑 业务代码、JVM 内核代码、驱动
进入方式 正常执行 系统调用 / 中断 / 异常
崩溃影响 只崩自己的进程 可能崩整个系统

5. 总结与避坑清单

5.1 面试速答表

面试题 一句话答案
进程和线程的区别？ 进程是资源分配单位，线程是调度单位；线程共享进程的地址空间和文件描述符，各自独立栈和寄存器
为什么线程比进程轻？ 创建省了地址空间复制（写时拷贝），切换省了页表刷新（TLB）
线程切换开销多大？ 微秒级：寄存器 + 栈 + 内核态进出；进程切换还多一次页表切换
协程和线程的区别？ 协程在用户态调度，不依赖内核，创建/切换成本低一个数量级，适合 IO 密集
Java 线程是哪种模型？ 平台线程 1:1 内核线程；虚拟线程（JDK 21）是 JVM 调度的协程
什么是僵尸进程？ 已退出但父进程没 wait() 回收，PCB 未释放；孤儿进程由 init 收养，僵尸必须防

症状 原因 处理
TPS 上不去，vmstat 的 cs 每秒几十万 线程过多，大量时间花在上下文切换 按核数与 IO 密集度收缩线程池；新项目优先虚拟线程
起了子进程后主流程卡死 没人读子进程输出流，管道缓冲写满（64KB）后子进程阻塞 起线程消费输出流；用完 waitFor() 并关闭流
内存充足但 new Thread 报 OOM 进程线程数 / 虚拟内存受限（ulimit -u） 检查 ulimit；或换虚拟线程
线程池开满 2000 线程响应反而更差 切换开销 > 并发收益 线程数 ≈ CPU 核数 × (1 + IO 等待占比 / CPU 占比)

5.3 工具速查表

工具 看什么 对应本节概念
ps -eo pid,ppid,stat,cmd 进程状态、父子关系、僵尸 1. 进程模型
top -Hp <pid> 每个线程的 CPU 占用 2. 线程、3. 调度
jstack <pid> Java 线程栈与状态 2. 线程（映射内核状态）
vmstat 1 / pidstat -w 1 每秒切换次数 / 自愿·非自愿切换 3. 上下文切换
nice / renice 调度权重（top 的 NI 列） 3. CFS 权重
strace -c syscall 类型与次数 4. 用户态/内核态

三个收获：进程管资源、线程管执行、调度管时间；切换成本从大到小是 进程切换 > 线程切换 > 系统调用；Java 的并发问题最终都能映射到这几层上——线程池大小、虚拟线程选型、进程卡死排查，根因都在本节讲的内核机制里，排查工具见上表。

实操建议：

  1. 压测先看 vmstat 1 的 cs 列，切换率异常高先缩线程池，不要先加并发。
  2. 用了 Runtime.exec() / ProcessBuilder 一定 waitFor() + 关流，防僵尸进程。
  3. 新项目 IO 密集型并发优先评估虚拟线程（JDK 21+），平台线程留给 CPU 密集和需要可控栈的场景。
