Redis 缓存淘汰策略解析

Posted on 2026-08-12 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

内存淘汰（memory eviction） 是 Redis 在内存写满时，按配置的策略删除一部分 key 来腾出空间的机制。它是缓存场景的最后一层保险：不配置，Redis 会被系统 OOM Killer 直接杀进程。本文讲透三件事：maxmemory 怎么配、8 种策略怎么选、近似 LRU 和 LFU 的实现差异在哪。

1. 为什么内存必须设上限

1.1 maxmemory：Redis 的内存天花板

Redis 是一个基于内存的键值数据库，数据主要放在内存里，读写是微秒到亚毫秒级。内存是稀缺资源，所以必须给 Redis 划一条内存上限（maxmemory），超过上限后的写入会触发内存淘汰（memory eviction）——按策略删除一部分 key，腾出空间继续写入。

不设 maxmemory 的后果：Redis 吃满机器内存后，OS 的 OOM Killer 会直接 kill 掉 redis-server 进程（类比 Java 应用 -Xmx 设太大、堆外内存失控被容器 OOM kill），主从全部挂掉，未落盘数据全部丢失。生产环境这是第一优先级配置。

类比 Java 应用 Redis
内存上限 -Xmx / 容器 limit maxmemory
超限行为 抛 OOM 异常（可捕获） 按策略淘汰 key，或拒绝写入
失控后果 被容器 OOM kill 被系统 OOM Killer 杀进程

1.3 内存去哪了：used_memory 口径

INFO memory 里需要关注几个指标：

指标 含义 关注点
used_memory 实际占用内存（含碎片） 与 maxmemory 对比，接近即触发淘汰
used_memory_human 人类可读版本 快速目检
maxmemory_policy 当前淘汰策略 确认配置生效
mem_fragmentation_ratio 内存碎片率 长期 >1.5 且伴随频繁淘汰，说明碎片严重

注意：已过期但还没被删掉的 key 依然占用内存并计入 used_memory。惰性删除与主动清理都有延迟，所以内存紧张时可能”提前”触发淘汰——这也是后面 volatile 策略坑的根源之一。

2.1 完整链路

flowchart TD
    subgraph READ[Read Path]
        A[Client GET key] --> B{Key exists?}
        B -- Yes --> C[Return value, cache hit]
        B -- No --> D[Query MySQL, write back]
    end
    subgraph WRITE[Write Path]
        E[Client SET / LPUSH / HSET ...] --> F{used_memory > maxmemory?}
        F -- No --> G[Execute write directly]
        F -- Yes --> H{Policy = noeviction?}
        H -- Yes --> I[Return error<br/>OOM command not allowed]
        H -- No --> J[Sample N keys, pick victim by policy]
        J --> K[Evict victim, free memory]
        K --> G
    end

两个要点：

  • 读请求（GET）永不触发淘汰。淘汰只发生在写路径，且在命令执行之前检查。
  • 检查带冗余缓冲（slop），避免 used_memory 在边界抖动时反复触发淘汰。

2.2 淘汰 vs 过期删除：两条腿走路

  • 过期删除：针对设置了 TTL 的 key，到点删除。惰性删除（访问时发现过期顺手删）+ 主动清理（每 100ms 随机抽 20 个带 TTL 的 key，过期占比超 25% 就继续抽）。
  • 内存淘汰：针对内存写满，与 TTL 无关，纯粹按策略选 key 逐出。
flowchart LR
    subgraph Lazy[Lazy Deletion]
        L1[Access expired key] --> L2[Delete and return nil]
    end
    subgraph Active[Active Expire Cycle]
        A1[Every 100ms] --> A2[Sample 20 keys with TTL]
        A2 --> A3{Expired ratio > 25%?}
        A3 -- Yes --> A2
        A3 -- No --> A4[Sleep]
    end
    subgraph Eviction[Memory Eviction]
        E1[used_memory > maxmemory] --> E2[Evict by maxmemory-policy]
    end

3. 八种淘汰策略全景

3.1 速查表（面试核心考点）

策略 作用范围 淘汰依据 引入版本 典型场景
noeviction 全部 key 不淘汰，写满报错 一直 队列、计数器等写失败可重试
allkeys-lru 全部 key 最近最少使用 一直 通用缓存，最常用
volatile-lru 带 TTL 的 key 最近最少使用 一直 缓存带过期 + 少量长驻 key
allkeys-random 全部 key 随机 一直 key 可重建、淘汰成本均等
volatile-random 带 TTL 的 key 随机 一直 会话 token 类
volatile-ttl 带 TTL 的 key 剩余 TTL 最短 一直 数据有明确时效
allkeys-lfu 全部 key 访问频次最低 4.0 长尾热点
volatile-lfu 带 TTL 的 key 访问频次最低 4.0 带 TTL 的长尾热点

命名规律：前缀 allkeys- 管全部 key，volatile- 只管带过期时间的 key；后缀 -lru 看最近访问、-lfu 看访问频次、-random 随机、-ttl 看剩余寿命。

3.2 volatile-* 的隐藏降级

volatile-* 系列有个大坑：如果带 TTL 的 key 一个都没有（或没有可淘汰的），行为退化成 noeviction——写满直接报错。

真实场景：某天排查发现缓存全部写不进去，配置明明是 volatile-lru，查下来是业务方刚把 key 的 TTL 全去掉了。结果整个 Redis 变只读，线上炸了才反应过来。

口诀：volatile 系列依赖 TTL，TTL 没设，策略就失效。

3.3 allkeys 与 volatile 怎么选

核心区别一句话：allkeys- 保护的是”内存不超限”，volatile- 保护的是”带 TTL 的 key 优先存活”**。如果缓存数据和不过期数据混用同一个实例（比如有人把配置、统计也塞 Redis），必须用 volatile-*，否则淘汰可能把不该删的业务数据删掉。

4. 近似 LRU：用采样换精度

4.1 为什么不做严格 LRU

严格 LRU 需要维护双向链表，每次访问把节点移到队首，每个 key 额外占两个指针的开销。Redis 的 key 数量以百万计，这个成本不可接受；链表在 RDB 持久化、主从复制时也会引入额外复杂度。所以 Redis 选择近似 LRU（approximate LRU）：只记录”上次访问时间”，淘汰时抽样比较。

4.2 数据结构：RedisObject 的 24bit 时钟

每个 value 对象（RedisObject）里有一个 24bit 的 lru 字段：

  • LRU 模式：存上次访问时间（秒级时钟 LRU_CLOCK，约 194 天轮回一次）。
  • LFU 模式：拆成 16bit 时间 + 8bit 频次计数器（第 5 节讲）。

每次 key 被访问（GET/SET 等），lru 字段刷新为当前时钟。

4.3 淘汰算法：采样取最老

flowchart LR
    subgraph Space[Key space]
        K1[key1 lru=100]
        K2[key2 lru=50]
        K3[key3 lru=200]
        K4[key4 lru=180]
        K5[key5 lru=90]
    end
    S[Random sample N=5] --> V[Pick key with oldest lru<br/>--> key2]
    V --> E[Evict key2]
    style K2 fill:#f9d0c4
  1. 从键空间随机取 N 个 key（N = maxmemory-samples，默认 5）。
  2. 在 N 个里挑 lru 最小（最久没访问）的淘汰。
  3. 淘汰后内存还不够，重复该过程。

采样数越大越接近严格 LRU，但每次淘汰的 CPU 成本越高。Redis 5.0 起引入淘汰池（eviction pool）：上一轮采样过的候选 key 保留在池中，下一轮优先从池里挑，跨轮次累积样本，近似精度进一步提升（6.0 对池大小做了动态调整）。

4.4 参数与效果

maxmemory-samples 与严格 LRU 的差距 淘汰耗时
3 明显有差距 最低
5（默认） 约 90% 以上的效果 低
10 几乎无差别 中

注意 maxmemory-samples 不支持 CONFIG SET 在线修改，属于重启生效的配置项，改之前先看运维窗口。

5. LFU：频次才是真相

5.1 LRU 的致命场景

LRU 只看”最近访问”，不看”访问了多少次”。一次突发热点（秒杀、新闻爆点）就能让一批 key 变成”最近访问”，随后把真正长期高热的 key 挤掉——等热点过去，缓存里全是没人再看的 key。

这个痛点 Java 开发者也不陌生：Caffeine 的 W-TinyLFU 淘汰算法就是针对 LRU 对”长尾热点”命中率差才诞生的，思路同源。

5.2 同一个字段，两种读法

Redis 4.0 起，LFU 模式下 24bit 的 lru 字段被拆成两部分：

位段 名称 含义
高 16bit ldt（last decrement time） 上次衰减时间的分钟级时钟
低 8bit logc（logistic counter） 对数计数器，0~255

8bit 只能记 255 次访问，不够用，所以用对数计数器（logistic counter）：访问次数越多，计数器增长越慢——用概率递增代替每次访问 +1。

5.4 衰减：避免”曾经热过”的 key 霸占缓存

LFU 只有递增没有衰减，一个 key 早年火过一次就会一直霸占缓存（访问量早已回落也不淘汰）。所以 ldt 出场：每隔 lfu-decay-time 分钟（默认 1），logc 减半，让热度随时间冷却，冷门但持续访问的 key 才有机会浮现。

参数 默认值 说明
lfu-log-factor 10 计数器增长速度。越大增长越慢、能表达更大的访问量；越小越容易被高访问 key 快速顶到 255
lfu-decay-time 1 计数器减半的间隔（分钟），0 表示不衰减

lfu-log-factor 不同取值下，计数器到达某值需要的真实访问次数（Redis 官方文档数据）：

factor 100 次 1000 次 10 万次 100 万次 1000 万次
0 104 255 255 255 255
1 18 49 255 255 255
10（默认） 10 18 142 255 255
100 8 11 49 143 255

高频热点 key 容易顶到 255——所有 key 都是 255 就分不出高下，这时调大 factor 拉开差距。

5.5 观测与排查

6. 实战选型：项目里到底配什么

6.1 决策表

业务形态 推荐策略 理由
通用缓存（读多写少、key 同质化） allkeys-lru 简单可靠，80% 的场景首选
部分 key 长期高频（榜单、用户画像） allkeys-lfu 长尾热点命中率更高
全部 key 带 TTL、生命周期短（验证码、会话） volatile-lru / volatile-ttl 只淘汰缓存，不碰长驻数据
缓存与持久数据混用同一实例 volatile-lru 保护不过期数据不被淘汰
key 均可重建、淘汰成本均等 allkeys-random 淘汰开销最小
数据不能丢，写失败要立刻感知 noeviction 用异常暴露容量问题

选型口诀：没把握就 allkeys-lru；有长尾热点换 allkeys-lfu；混用持久数据必须 volatile。

6.2 三个真实场景

  • 登录 token（TTL 短、无差别）：volatile-random 即可，谁被淘汰无所谓，反正过期快。
  • 电商秒杀（短时突发热点）：用 allkeys-lru。LFU 会把秒杀 key 的计数器顶到高位，热点过后长期霸占缓存，反而有害。
  • 用户画像/推荐位（长期频次差异大）：allkeys-lfu，避免一波流量把常驻热 key 挤掉。

6.3 验证：用数据说话

上线后观察两天：evicted_keys 平稳且被淘汰的都是冷 key，说明策略选对了；如果出现热 key 被淘汰（业务告警）或 evicted_keys 陡增，先扩 maxmemory，再考虑换策略。

6.4 避坑清单（面试也常问）

症状 原因 处理
缓存写满后大量写入报 OOM 策略是 noeviction，或 volatile-* 但 key 没带 TTL 换成 allkeys-lru，或给 key 补 TTL
突发流量后热 key 命中率骤降 LRU 被”一波流”污染 评估换 allkeys-lfu
写入延迟毛刺明显 每次写前都要先淘汰，可能多轮采样删除 提高 maxmemory 余量，或写操作错峰
主从行为不一致 淘汰只在主节点触发 正常现象，从库同步主库数据；不要只在从库配不同策略
内存碎片率长期偏高 频繁淘汰 + 大 key 释放 开启 activedefrag，或检查内存分配策略

7. 总结与实操建议

三个收获：淘汰只发生在写路径、volatile-* 依赖 TTL 且可能静默降级、LRU 看”最近” LFU 看”频次”，两者的实现都是近似方案（采样 + 概率计数）。

实操建议按优先级：

  1. **先设 maxmemory**，这是 Redis 生产环境的第一道保险，没有上限，策略都是空谈。
  2. 默认 allkeys-lru 起步，出问题再换，不要一上来就 LFU——LFU 有 lfu-log-factor 和 lfu-decay-time 两个参数要调。
  3. **缓存与存储数据混用的实例必须用 volatile-***。
  4. 上线后盯 evicted_keys 和命中率，策略选对的标准是”被淘汰的都是冷 key”。
