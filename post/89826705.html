Docker 容器实战

Posted on 2024-12-16 In 部署运维 Word count in article: 11k Reading time ≈ 38 mins.

1. Docker 解决什么问题

“在我机器上能跑啊？” —— 开发环境装好了、测试也通过了，换一台机器（同事的电脑、测试服务器、生产服务器）就各种报错：JDK 版本不对、依赖缺失、系统库没有、配置文件忘改……环境差异是软件交付路上最常见的坑。

Docker 的解法是：把应用和它的完整运行环境（代码、运行时、依赖、配置、启动脚本）一起打包成一个镜像（Image）。镜像是不可变的、自包含的，在任何装了 Docker 的机器上，都能以完全一致的方式运行 —— 这就是 一次构建，处处运行（Build Once, Run Anywhere），彻底告别在我机器上能跑。

和虚拟机相比，Docker 共享宿主机内核、以进程级隔离运行，因此：

对比 Docker 容器 虚拟机
隔离粒度 进程级（共享内核） 整机级（完整操作系统）
启动速度 秒级 分钟级
镜像/磁盘占用 几十 MB ~ 几百 MB 几个 GB 起步
单机密度 轻松几十上百个 通常个位数

虚拟机每个都是完整操作系统，隔离更强但也更重；容器共享内核，更轻更快，但必须在 Linux 上运行（macOS/Windows 通过虚拟机跑 Linux 内核间接运行），且隔离强度弱于虚拟机 —— 运行不可信代码等安全要求极高的场景仍需虚拟机。

Docker 的整体架构：

三个角色：

  • Docker daemon（守护进程）：运行在宿主机上，真正负责管理镜像、容器、网络、数据卷
  • Docker client（客户端）：我们敲的 docker 命令，本质是把指令发给 daemon 执行（可以连本地或远程的 daemon）
  • Registry（镜像仓库）：存放、分发镜像的地方，默认是 Docker Hub，企业内部通常搭私有仓库

2.3 资源分配与 VirtioFS

  • 调整资源分配：Settings > Resources 中根据 Mac 配置合理分配 CPU 和内存（建议不超过总内存的 50%）；开启 Resource Saver mode，容器空闲时自动停止 Linux 虚拟机，节省资源
  • Apple Silicon（M1/M2/M3）文件系统优化：Settings > General 中启用 VirtioFS（文件共享加速），并开启 Rosetta 2 支持以兼容 x86 镜像

3. 核心概念：镜像与容器

镜像 = 类，容器 = 实例

面向对象里，类是定义好的模板，实例是运行中的对象。Docker 里同理：

概念 类比 说明
镜像（Image） 类 只读的静态模板，包含应用和它的完整运行环境
容器（Container） 实例 镜像运行起来的进程，有独立的可写文件层，可以启动/停止/删除

同一个镜像可以启动任意多个容器，互不影响；容器删了重建，镜像毫发无损。也正因为如此，容器天然是临时、无状态的 —— 需要持久保存的数据（数据库文件、日志）必须放到数据卷里（见第 5 节）。

镜像分层：联合文件系统

镜像不是一个大文件，而是一层层只读层堆叠而成（底层机制叫联合文件系统 UnionFS）：

  • 镜像里的每一层，都对应 Dockerfile 里的一条指令（如 RUN、COPY），层与层之间是叠加关系
  • 容器启动时，Docker 在镜像层之上再加一层可写层（容器层），容器运行期间对文件的读写都发生在这层
  • 容器层不会修改任何镜像层：对某个文件做修改时，先把这个文件复制到容器层再改，这就是写时复制（Copy-on-Write）。容器一删，可写层随之消失，镜像完好无损

这种”分层 + 写时复制”的设计带来三个直接好处：

  1. 省空间：多个镜像共用相同的基础层（比如都基于 openjdk），磁盘上只存一份
  2. 构建、传输快：层可以复用，构建时命中缓存、推送仓库时只传变化的层
  3. 升级轻量：应用升级往往只新增一层，不用把整个环境重新打包

5. 数据卷

为什么需要数据卷

  1. 容器是临时的：删除容器，它的可写层数据一并消失。而 MySQL 的数据、应用日志必须持久保存
  2. 容器内改文件不方便：改 nginx 配置、换静态页面都要 exec 进容器，不如直接在宿主机上改
  3. 多容器需要共享文件：比如日志采集、静态资源

三种挂载方式

方式 写法 特点 适用场景
命名卷（Volume） -v 卷名:/容器目录 由 Docker 管理，数据存在 /var/lib/docker/volumes/卷名/_data 持久化核心数据，如数据库数据目录
绑定挂载（Bind Mount） -v /宿主机绝对路径:/容器目录 直接映射宿主机目录，在宿主机上就能改文件 配置文件、源码、nginx 静态页面
临时挂载（tmpfs） --tmpfs /容器目录 存在内存里，不落盘，容器重启即消失 临时敏感数据（密码、token），不想写磁盘

数据卷相关命令：

命令 说明
docker volume create 创建数据卷
docker volume ls 查看数据卷
docker volume rm 删除数据卷
docker volume prune 清除未使用的数据卷
docker volume inspect 查看数据卷详情

如何选择

  • 数据库、消息队列等核心数据 → 命名卷（推荐，交给 Docker 管理，docker volume prune 不会误删在用的卷）；想直接看文件、备份方便也可以用 bind mount
  • 需要频繁在宿主机上改动的文件（nginx 配置与页面、应用配置文件） → 绑定挂载
  • 只希望进程短暂使用、绝不落盘的敏感数据 → tmpfs

指令 作用 示例

重点：CMD 与 ENTRYPOINT 的区别和组合用法

两者都定义容器启动命令，区别在于能否被覆盖：

  • CMD：默认命令。docker run 镜像 参数 会把 CMD 整体替换掉 —— 比如 CMD ["java","-jar","/app.jar"] 时执行 docker run docker-demo --server.port=8081，实际启动的命令变成了 --server.port=8081，jar 根本起不来
  • ENTRYPOINT：入口命令，固定不可被覆盖（只有显式 --entrypoint 才能改）

所以最常见的组合用法是：ENTRYPOINT 固定主命令，CMD 提供默认参数：

这样 docker run docker-demo 等价于 java -jar /app.jar --server.port=8080；docker run docker-demo --server.port=8081 则等价于 java -jar /app.jar --server.port=8081 —— 主命令固定、参数可改，灵活又安全。

另外注意命令形式：推荐上面这种 exec 形式（JSON 数组）。shell 形式（CMD java -jar /app.jar）会被 /bin/sh -c 包裹，容器里 PID 1 是 sh 而不是 java，信号转发、优雅退出都会有坑。

构建最佳实践

  1. 利用构建缓存：把不常变的指令（依赖声明、基础镜像）放前面，常变的（源码、配置文件）放后面。COPY 的文件一变化，它以及它之后的所有层缓存都会失效

  3. 最小化层数：多条命令用 && 串在一条 RUN 里，并顺手清理缓存文件：

    注意别为了合并牺牲可读性

  4. 多阶段构建 + 精简基础镜像（jre 而不是 jdk、alpine 系），把镜像体积压到最小

7. 网络

Docker 网络模式

模式 说明 使用场景
bridge（默认） 容器接入 Docker 的虚拟网桥 docker0，每个容器有独立 IP，容器间可互通；对外访问需 -p 端口映射 单机上的绝大多数场景
host 容器与宿主机共享网络栈，直接用宿主机 IP 和端口 对网络性能要求高、端口必须固定不变的场景
none 容器完全没有网络 纯计算任务、安全性要求极高、不想有任何网络暴露
overlay 跨主机容器组网，构成一个虚拟网络 多机集群（Swarm / K8s 场景）

默认情况下，所有容器都是以 bridge 方式连接到 Docker 的一个虚拟网桥上，如下图：

自定义网络

通过默认网桥连接的容器之间只能通过 IP 互相访问，但如果容器重启，IP 地址变了，相关的 IP 配置未同步修改，就会导致容器之间不通。解决办法是创建自定义网络，并将需要互相访问的容器加入该网络 —— 同一自定义网络内的容器，Docker 内置 DNS，直接用容器名就能互相访问（比如应用配置 jdbc:mysql://mysql:3306），完全不受 IP 变化的影响。

Docker 常用网络命令：

命令 说明
docker network ls 查看所有网络
docker network create 创建网络
docker network rm 删除指定网络
docker network prune 清除未使用网络
docker network connect 使指定容器加入网络
docker network disconnect 使指定容器离开网络
docker network inspect 查看网络详细信息

PS：方式一会同时加入默认网络 docker0 和指定网络，方式二只会加入指定网络。

端口映射

  • -p 宿主机端口:容器端口：如 docker run -d -p 80:80 nginx，访问宿主机 80 端口即到达容器 80 端口
  • 端口冲突：宿主机的端口是全局资源，多个容器不能同时占用同一个宿主机端口，所以常见 -p 8080:80 这种错开写法
  • -P：把镜像 EXPOSE 声明的端口自动映射到宿主机的随机高位端口
  • host 模式下容器直接用宿主机端口，不需要也不能做端口映射
  • 默认 bridge 网络下，容器端口只有映射后才能被宿主机外部访问；而同一网络内的容器之间，直接用容器端口互访，无需映射

端口冲突（address already in use）

现象：启动容器时报 bind: address already in use，例如：

原因：宿主机端口是全局资源，已被其他进程或容器占用。

解决：

  1. 找出占用端口的进程：

    记下 PID 和进程名。

  2. 终止占用进程（如果非必需）：sudo kill -9 <PID>

  3. 如果是会自动重启的系统服务（如 MySQL、Zookeeper）：

    • Homebrew 安装的：brew services stop <服务名>
    • DMG 安装的：系统偏好设置里停止并取消”开机自启”，或 sudo launchctl unload -w /Library/LaunchDaemons/<plist文件名>.plist

  4. 不想停主机服务就改映射端口：修改 docker-compose.yml 的 ports，例如 "3306:3306" 改为 "3307:3306"，应用改用新端口连接

常见案例：mysqld 占用 3306、本地 Zookeeper（Java 进程）占用 2181。

僵尸容器

现象：docker compose up -d 卡在 Recreate，最终报错：

原因：容器内 PID 1 进程未正确处理子进程信号，导致子进程变为僵尸（zombie），Docker 无法正常停止容器。

解决：

  1. 强制删除：docker rm -f <容器名或ID>。如果仍有残留，重启 Docker Desktop（菜单点击 Restart，或 sudo killall -HUP dockerd）。

  2. **永久解决：加 init: true**，让 tini 作为 init 进程自动回收僵尸进程：

    用 docker run 则加 --init 参数。

  3. 重新启动容器，问题不再复现。

11. Harbor 私有仓库

11.1 Harbor 是什么：企业级镜像仓库

Docker Hub 拉取慢、私有镜像不想放公网、团队需要权限管理和安全扫描——于是有了 Harbor：开源的企业级镜像仓库（原 VMware 发起，现为 CNCF 项目）。它在标准 Docker Registry 之上补齐了企业需要的能力：

  • 项目管理与权限：镜像按项目（Project）隔离，角色分项目管理员/开发者/访客；
  • 镜像漏洞扫描：内置 Trivy，push 后自动/手动扫描 CVE；
  • 镜像复制：跨机房/跨地域同步（主备、多集群）；
  • 审计与配额：操作日志、项目镜像数量/大小配额。

Harbor 2.x 的组件架构：

组件 职责
Nginx 代理 统一入口，443 终结 TLS，按路径路由到 Core/Registry/Portal
Core 服务 业务 API + Web UI 后端：项目、用户、权限、复制规则、GC 管理
Registry 镜像本体存储（Docker 标准 Registry v2，OCI 兼容），存于 data_volume
Database（PostgreSQL） 元数据：项目/用户/角色/复制规则/扫描报告
Redis 缓存与异步任务队列
Jobservice 执行复制、垃圾回收、扫描等后台任务
Trivy 镜像漏洞扫描器（install.sh --with-trivy 可选安装）

11.3 镜像推送流程

往 Harbor 推一个镜像的标准流程（角色：开发者 + 项目权限）：

  • 命名规范：<仓库地址>/<项目名>/<镜像名>:<标签>，prod 就是项目名；
  • 项目权限：项目分公开（无需登录可拉）与私有（必须登录且有权限）；成员角色：项目管理员（管理成员/复制规则/GC）、开发者（push/pull）、访客（只能 pull）；
  • 推送后可到 UI 上查看该镜像的漏洞扫描结果（Trivy），高危漏洞可配策略阻止部署；
  • 只读拉取给 CI/CD 用机器人账号（UI 里创建，专用于流水线，密码定期轮换）。

11.4 镜像复制与垃圾回收

镜像复制（Replication）：把镜像从本 Harbor 同步到另一个 Harbor（或 Docker Hub/阿里云），适合主备机房、多地域分发。UI 操作路径：项目 → 复制管理 → 新建规则：

  • 源/目标：选远端地址（如 https://harbor-bak.example.com）与凭据；
  • 过滤条件：按项目/仓库名/标签前缀选择要复制的镜像；
  • 触发方式：手动、事件驱动（新镜像 push 后立即复制）或定时（如每天凌晨跑增量同步）。

垃圾回收（Garbage Collection）：镜像被删除后，底层的 blob（数据块）不会立即释放——只有被 GC 清理后磁盘才会收回。UI 操作路径：管理 → 垃圾回收 → 新建任务（立即或定时）。

  • GC 期间 Registry 组件会被置为只读，业务低峰期执行；
  • 配合保留策略（按数量/按时间保留每个仓库最近 N 个镜像）自动清理历史版本，磁盘占用才能稳得住。

  • 定期清理：无用镜像、容器和构建缓存会持续占用磁盘，养成定期执行 docker system prune 的习惯（命令见第 4 节）
  • 备份数据卷：重要数据用数据卷持久化（见第 5 节）并定期备份
  • 关注官方更新：Docker 新版本会修复安全漏洞和性能问题，及时升级
