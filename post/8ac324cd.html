从这里开始：把并发 bug 变成可复现的实验

Posted on 2026-10-25 In Java Word count in article: 4.3k Reading time ≈ 16 mins.

并发问题之所以难查，是因为它们不报错、只「偶尔不对」。可见性问题跑一万次都对，第一万零一次卡死；伪共享不会让程序变慢 10 倍，只会让 CPU 使用率莫名 300%。这类问题靠读代码看不出来，只能靠可复现的实验。

本文是「Java 并发实战路线」第一篇，只做三件事：把并发的成本拆成三个变量、搭好 JDK 21 的实验台（JFR + jcmd + JOL）、跑出第一组基线数字。后面十一篇的每个结论都会回到这组数字上对照。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线（本文） → ② 线程与调度成本 → ③ JMM：可见性与重排 → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与站内《Java 并发编程：从 JMM 到虚拟线程的系统化实战》的分工：那边是 18 章的知识地图（当字典查），这边是实验手册（按顺序练）。本文对应那边第 1 章「三个核心问题」与第 3 章「线程基础」。

1. 并发的成本只有三个变量

1.1 一句话定义

一个并发问题，永远落在三件事上：共享的可变状态（要不要同步）、线程的调度（切换多少钱）、内存的可见性（写得对不对）。所有优化也都是这三个方向：减少共享、减少切换、减少等待。

成本 一句话定义 由什么决定 怎么观测 详见
创建/销毁 每个线程都要申请栈与内核资源 线程数、平台 Thread.start() 耗时、JFR 线程事件 ②⑧
上下文切换 CPU 换一个线程要保存/恢复现场 线程数 > 核数、锁竞争、阻塞调用 JFR jdk.ThreadPark、perf sched ②⑥
同步/竞争 抢锁、CAS 自旋、缓存行争用 共享粒度、临界区大小 基准对比、jstack 的 BLOCKED ⑤⑥
可见性成本 内存屏障、禁止重排 volatile / CAS / 锁 反汇编、基准对比 ③ 
flowchart LR
    A["Shared mutable state"] --> B["Synchronization cost<br/>lock / CAS / barrier"]
    C["Threads > cores"] --> D["Scheduling cost<br/>context switch"]
    E["Cross-core cache"] --> F["Visibility cost<br/>cache line ping-pong"]
    B --> G["Latency & throughput"]
    D --> G
    F --> G

先记住一句话：并发的性能问题，本质是「同一份数据被多个核访问」。不共享，就没有成本；一共享，成本由缓存一致性协议决定，而不是由你的代码行数决定。

1.2 实测基线（JDK 21.0.12，15 核）

在一台 15 核的机器上跑出来的四个数字：

指标 实测值 怎么测的
创建+启动+回收一个线程 32 µs 顺序创建 1 万个线程，取 2 轮最优
一次 park/unpark 切换 2.43 µs 两线程真实阻塞/唤醒，10 万次
CPU 密集任务加速比（15 线程） 12.68× 单线程 279 ms → 15 线程 22 ms
4 线程共享计数器 见下表 每种写法 3 轮取最优

共享计数器的四种写法（4 线程 × 200 万次）：

写法 ns/op 最优耗时 相对
synchronized 6 55 ms 6×
AtomicLong 5 47 ms 5×
LongAdder 1 8 ms 1×
线程本地（无共享） 0 0 ms —

这张表就是全系列的起点：同样一个「加一」，写法不同差 6 倍；而无共享时成本是 0（被 JIT 优化掉了，见 3.3）。

1.3 三个数字能推出什么

你看到的现像 用哪个数字解释
线程池开到 200 反而更慢 切换 2.43 µs × 切换频率；核数只有 15
每秒创建几千个线程 32 µs × 5000 = 160 ms/秒 纯粹花在创建上
CAS 计数器在 32 线程下崩了 ⑤ 会测：竞争下 CAS 的失败重试成本
加了 synchronized 吞吐掉一半 临界区里如果有 IO，锁的持有时间被放大

2. 搭实验台

2.1 环境：一个 JDK 就够，工具是自带的

实测：5 秒的 profile 录制产出 361 KB 的 .jfr 文件，jfr summary 能直接看事件统计；jcmd Thread.print 能抓到线程状态（RUNNABLE / TIMED_WAITING / BLOCKED）。

flowchart LR
    J["Your JVM<br/>(JDK 21)"] --> C["jcmd<br/>thread dump / JFR control"]
    J --> F["JFR events<br/>park / monitor / gc / io"]
    F --> A["jfr print / summary<br/>or JMC"]
    C --> S["jstack output<br/>deadlock detection"]
    J -.-> M["Micro benchmarks<br/>hand-written or JMH"]

2.2 工具可用性实测（别假设有）

工具 本文环境 用途 没有时的兜底
JDK 21 ✅ 21.0.12.1 基线（虚拟线程 GA、偏向锁已移除） —
JFR / jcmd ✅ 自带 事件、线程栈、火焰图 —
JOL（jol-core） ✅ 本地 .m2 有 0.17 看对象头与锁状态（⑥） jcmd VM.info + 打印对象
JMH ❌ 本地仓库没有 权威微基准 手写基准 + 预热 + 多轮取最优，并在文中标注

本文所有微基准都是手写的，不是 JMH——这个差异必须说清，因为手写基准更容易被 JIT 骗（见 2.4）。

2.3 手写基准的四条纪律

纪律 做法 不做的后果
预热 先跑几轮 JIT 编译，再计时 测到的是解释执行，慢 10 倍
多轮取最优 至少 3 轮，取最小值（不是平均） 被 GC、其它进程干扰拉高
消费结果 把结果写进 volatile 静态字段 JIT 把整个循环删掉（3.3 的 0 ns/op）
报告口径 写清线程数、数据量、硬件 数字不可比 
flowchart LR
    A["Write bench"] --> B["Warm up<br/>JIT compiles hot paths"]
    B --> C["Run N reps"]
    C --> D["Take min<br/>(not avg)"]
    D --> E["Consume result<br/>(volatile sink)"]
    E --> F["Record env<br/>cores / JDK / heap"]

2.4 反面教材：我第一版基准测出的「10 倍加速比」

第一版我用了很小的任务（单线程 20 ms），结果是：

三个数字全是错的，原因各不相同：

错误数字 真实原因
8 线程 10× 加速 任务太小（20ms），JIT 与 GC 噪声盖过真实耗时
无共享 0 ns/op 循环被 JIT 判定为死代码，整个删掉了
切换 87 ns 我让线程自旋等标志位，测到的是缓存行在核间传递，不是线程切换

修正后（放大任务到 279 ms、把结果写进 volatile、用真实 park/unpark）才得到本文表格里的数字：切换 2.43 µs，比 87 ns 慢 28 倍。

这就是「可复现实验」的意义：不是跑出一个数字就完事，而是要能解释这个数字为什么是这个量级。

2.5 动手验证：验证你的基准有没有被 JIT 优化

预期观察点：有 sink = x 时约几百毫秒；注释掉之后耗时接近 0（JIT 判定为死代码，整个循环消失）。

判定标准：

  • 两次耗时差不多 → 你的基准本来就没被优化（或者跑了 -Xint，那是解释执行，慢 10 倍以上）；
  • 第二次也是几百毫秒 → 说明 x 有副作用没被消除，检查是否真注释掉了。

3. 基线四件套

3.1 创建：一个线程 32 µs

指标 实测
单线程创建+回收 32 µs
1 万个顺序创建总耗时 ≈ 320 ms

换算到生产：如果每秒新建 5000 个线程（比如 new Thread 处理请求），就有 160 ms/秒 花在创建上，CPU 有效利用率直接掉一截。这也是线程池存在的第一个理由。

3.2 切换：一次真实切换 2.43 µs

指标 实测
一次 park/unpark 切换 2,426 ns（2.43 µs）
切换次数 100,000
自旋方式的「假切换」 87 ns（第一版，错）

为什么差 28 倍：自旋时线程一直在 RUNNABLE，另一核只是拿到缓存行；park/unpark 是真的把线程挂起、由内核重新调度，涉及 futex/condvar 与调度器。

换算：每秒 10 万次切换 = 0.24 秒纯切换开销。线程数开到核数的 10 倍以上时，这个成本会吃掉大部分 CPU。

3.3 加速比：15 核能拿到 12.68 倍

线程数 耗时 加速比 效率
1 279 ms 1× 100%
2 148 ms 1.89× 94%
4 76 ms 3.67× 92%
8 37 ms 7.54× 94%
15 22 ms 12.68× 85%

读法：纯 CPU 密集任务在 15 核上能拿到 12.68 倍，效率 85%——剩下的 15% 花在任务分发、GC、以及最后几个线程的收尾上。这是「理论上限」的实测值，任何带共享状态的任务都会低于它。

为什么「无共享 0 ns/op」是假的：JIT 发现每个线程只写自己的数组、而数组只被主线程读一次，于是把整个循环消除。修正方法是把结果写进 volatile 静态字段（本文的 SINK），让 JIT 不敢删。

3.4 竞争：同样的加一，差 6 倍

写法 ns/op 说明
synchronized（4 线程） 6 中等竞争，锁大部分时间没被抢
AtomicLong（4 线程） 5 CAS 失败重试，比锁略快
LongAdder（4 线程） 1 分段累加，写扩散到不同缓存行
线程本地 0（被优化） 无共享 = 无同步

注意：这是「4 线程中等竞争」的数字。⑤ 会测 32/64 线程的曲线——竞争加剧时，AtomicLong 会明显退化，而 LongAdder 几乎线性。

3.5 动手验证：跑出你自己的四个基线

预期观察点：jfr summary 里能看到 jdk.ThreadPark、jdk.JavaMonitorEnter、jdk.GCPhasePause 等事件；Thread.print 里 worker 线程状态是 RUNNABLE。

判定标准：

  • JFR 文件为空或没有事件 → 检查 settings=profile 是否生效（jfr summary 会列出事件类型）；
  • Thread.print 报连接失败 → pid 拿错了（jcmd -l 可能列出多个 Java 进程）。

3.6 动手验证：量你自己的线程创建与切换

预期观察点：线程创建在 2050 µs/个，切换在 15 µs/次（取决于机器与内核）。

判定标准：

  • 切换 > 20 µs → 机器有虚拟化层或 CPU 争抢严重（容器配额、其他进程）；
  • 切换 < 200 ns → 你的线程在自旋而不是真的挂起，检查是否用了 park；
  • 两个数字都远大于本文 → 先查宿主机负载，再谈 JVM 参数。

4. 这套基线怎么用

4.1 判断表

症状 大概率是哪类成本 第一件事 别做什么
加线程后吞吐不涨、CPU 高 切换 + 竞争 看核数 vs 线程数，测加速比 别继续加线程
单次请求偶发变慢 锁竞争 / GC JFR 看 JavaMonitorEnter 与 GC 别先改代码逻辑
CPU 使用率 300% 但业务量不大 自旋 / 频繁 CAS 失败 ⑤ 的竞争曲线 别以为是「多核利用好」
创建线程的地方很多 32 µs × 频率 换线程池 别调大堆内存
不知道从哪查起 — 先跑本文四个基线 别凭感觉调优

4.3 动手验证：用 JFR 抓一次锁竞争

预期观察点：jdk.JavaMonitorEnter 事件数量巨大（几十万到上百万），每条带 duration 与 monitorClass，能直接看到「等锁花了多久」。

判定标准：

  • 没有该事件 → 锁没竞争（线程数不够，或临界区外的工作太多）；
  • 事件很多但 duration 都很小（< 1 µs）→ 竞争不激烈，瓶颈不在锁；
  • duration 到毫秒级 → 临界区里有慢操作（IO、日志），要缩小临界区。

4.4 判断树：先查哪一类成本

flowchart TD
    A["并发性能问题"] --> B{"CPU 使用率高吗"}
    B -- 高 --> C{"线程数 > 核数 2 倍以上?"}
    C -- 是 --> D["调度成本<br/>减线程 / 换异步"]
    C -- 否 --> E["自旋或 CAS 竞争<br/>看 5 的曲线"]
    B -- 低 --> F{"吞吐也低?"}
    F -- 是 --> G["阻塞等待<br/>JFR ThreadPark / IO"]
    F -- 否 --> H["正常，只是延迟毛刺<br/>看 GC"]

4.2 与 MySQL / Redis 系列的同一套方法

维度 MySQL ① Redis ① Java 并发（本文）
先量什么 逻辑读/物理读 RTT/内存 创建/切换/竞争
基线工具 performance_schema INFO/redis-benchmark JFR/jcmd
成本量级 页 100ns~100µs 往返 31µs 切换 2.4µs、创建 32µs
共同结论 没有基线就没有优化 同 同

三个系列的收官篇都是「找拐点、算容量」，因为软件性能的尽头是同一件事：知道自己的上限在哪。

5. 总结

5.1 面试速答表

面试题 一句话答案
并发问题的本质是什么 共享可变状态下的原子性、可见性、有序性
创建一个线程要多久 本文实测 32 µs（创建+启动+回收）
一次线程切换要多久 本文实测 2.43 µs（真实 park/unpark）
多线程一定更快吗 纯 CPU 密集 15 核可到 12.68×；共享状态多则会倒退
为什么无共享时开销是 0 JIT 会把无用计算删掉，基准必须消费结果
微基准为什么容易错 JIT 优化、缺少预热、GC 干扰、死代码消除
JMH 解决什么问题 预热、分叉、死代码消除、统计——手写基准的坑它都填了
JFR 能看什么 线程 park、锁进入、GC、IO、异常，是 JDK 自带的生产级工具
jcmd Thread.print 和 jstack 区别 同一个东西，jcmd 是统一入口
该看 CPU 使用率还是线程数 看「线程数 / 核数」与切换成本，CPU 高可能只是自旋

5.2 实战避坑表

症状 原因 处理
基准跑出离谱的加速比 任务太小、JIT 噪声 放大任务到几百毫秒
基准显示 0 开销 死代码被消除 结果写入 volatile 字段
「切换」只要 87 ns 线程在自旋，不是真切换 用 LockSupport.park 测
两台机器数字对不上 核数、JDK、容器配额不同 记录环境，只做相对比较
JFR 文件没内容 没等录制结束就 dump duration 到期或显式 JFR.dump

5.3 工具速查表

工具 看什么 判定标准
jcmd -l 所有 JVM 进程 找不到 pid 就查不到一切
jcmd <pid> Thread.print 线程状态与栈 BLOCKED 多 = 锁竞争
jcmd <pid> JFR.start/dump 事件录制 5 秒 profile 约几百 KB
jfr summary 事件类型与数量 没有 jdk.ThreadPark 说明没抓到阻塞
-XX:+PrintCompilation JIT 编译与去优化 用于验证基准是否被优化
手写基准 + volatile sink 微基准 必须预热 + 多轮取最优

5.4 实操建议

  1. 先在自己的机器上跑一遍四个基线，把数字记下来——后面十一篇都要跟它对照。
  2. 微基准必须做三件事：预热、多轮取最优、消费结果；否则数字不可信。
  3. 记住两个量级：创建 32 µs、切换 2.43 µs。任何「加线程/加池」的方案都要先按这两个数字算账。
  4. **用 JFR 而不是只看 top**：CPU 高可能是自旋，线程多可能是阻塞，只有事件能区分。
  5. **建一份 concurrency-lab.md**，记录「场景 / 线程数 / 数据量 / 环境 / 数字 / 结论」。
