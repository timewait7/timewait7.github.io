持久化：RDB、AOF 与丢失窗口

Posted on 2026-10-25 In 数据存储 Word count in article: 3.9k Reading time ≈ 14 mins.

appendfsync always 让每次写入从 103 微秒变成 487 微秒——慢了 4.7 倍，换来的却是「kill -9 三档都不丢数据」的同一个结果。持久化的代价与收益，只有把「每秒能写多少」和「会丢多少」放在同一张表里才看得清。

本文做了三组实验：三档 appendfsync 的写入开销、真 kill -9 后的存活条数、以及 AOF 从 18.6 MB 重写成 4.3 MB 的全过程。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口（本文） → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：⑤ 测出 fork 的停顿（BGSAVE 1.78 ms @140MB），本文把 fork 放到 AOF 重写里看代价；⑧ 的复制本质是「另一份持久化的数据流」，两者一起构成「数据不丢」的完整答案。

1. 三种持久化，三种保护范围

1.1 RDB / AOF / 混合

flowchart LR
    subgraph RDB["RDB (snapshot)"]
        R1["fork"] --> R2["child writes dump.rdb<br/>binary snapshot"] --> R3["restart: load whole file"]
    end
    subgraph AOF["AOF (append log)"]
        A1["every write appends<br/>to aof buffer"] --> A2["flush to OS<br/>+ fsync by policy"] --> A3["restart: replay commands"]
    end
    subgraph HY["Hybrid (7.x default for AOF)"]
        H1["rewrite = RDB preamble<br/>+ incremental AOF"] --> H2["restart: load rdb + replay tail"]
    end
维度 RDB AOF（混合）
文件内容 二进制快照 RDB 前缀 + 命令追加
丢失窗口 上次快照之后（分钟级） everysec 时 ≤1 秒
恢复速度 快（直接加载） 慢（要重放命令，混合模式接近 RDB）
文件大小 小（本文 4.3 MB / 20 万 key） 未重写时大（18.6 MB），重写后 4.3 MB
写入开销 低（只有 fork） 取决于 appendfsync
适用 缓存、可重建的数据 不能丢的数据

1.2 默认值（实测）

参数 实测默认 含义
appendonly no 默认不开 AOF，只用 RDB
appendfsync everysec 每秒 fsync（开了 AOF 时生效）
aof-use-rdb-preamble yes 重写时用 RDB 作前缀（混合持久化）
auto-aof-rewrite-percentage 100 AOF 增长到基线的 2 倍时触发重写
auto-aof-rewrite-min-size 64 MB 小于 64MB 不自动重写
save 3600 1 300 100 60 10000 RDB 三条触发规则

第一行最容易被忽略：默认配置下你的 Redis 只有 RDB，崩溃会丢「上次快照之后」的全部写入。要 AOF 必须显式 appendonly yes。

2. appendfsync 三档：性能与丢失窗口

2.1 实测写入开销（3000 次顺序 SET）

模式 总耗时 每次操作 相对 everysec 每次写做 fsync？
always 1.46 s 487 µs 4.7× 是
everysec 0.36 s 103 µs 1.0× 每秒一次
no 0.35 s 116 µs 1.1× 从不（交给 OS） 
flowchart LR
    subgraph AL["always"]
        A1["write"] --> A2["fsync"] --> A3["reply<br/>487us"]
    end
    subgraph ES["everysec"]
        E1["write"] --> E2["reply<br/>103us"] --> E3["fsync every 1s<br/>in background"]
    end
    subgraph NO["no"]
        N1["write"] --> N2["reply<br/>116us"] --> N3["OS decides<br/>when to flush"]
    end

always 与 everysec 差 4.7 倍——差的正是每次写一个 fsync。这个数字和 MySQL 的「flush_log_at_trx_commit=1 vs 2」是同一类账（MySQL 系列 ⑦）。

2.2 实测：kill -9 之后三档都没丢

每次：写入 3000 条 → 立刻 docker kill -s KILL → 重启 → 数 DBSIZE：

模式 写入 恢复耗时 存活 丢失
always 3000 0.11 s 3000 0
everysec 3000 0.11 s 3000 0
no 3000 0.11 s 3000 0

为什么三档都不丢：Redis 在每一轮事件循环结束时都会把 AOF 缓冲 write() 到操作系统。kill -9 只杀进程，操作系统的 page cache 还在，数据不会消失。fsync 保证的是「写到磁盘介质」，而不是「写进 OS」。

2.3 深挖：kill -9 ≠ 掉电

这是本文最重要的一条，也是很多文章写错的地方：

崩溃类型 always everysec no
进程崩溃（kill -9、段错误） 0 丢失 ≈0 丢失（本文实测 0） ≈0 丢失
OS 崩溃 / 掉电 0 丢失 ≤1 秒 最多约 30 秒（OS 脏页回写周期）
磁盘损坏 可能全丢 可能全丢 可能全丢

所以「everysec 会丢 1 秒」这句话的前提是掉电，不是进程崩溃。 要验证它，只能拔电源或做 OS 级故障注入——容器里 kill -9 测不出来。

2.4 一次「看起来丢了」的实验：流水线中途 kill

我用流水线发 100,000 条 SET（不等回复），0.35 秒时 kill -9，恢复后：

指标 值
客户端已发送 100,000
恢复后存活 32,420

这个 32,420 不能解读成「持久化丢了 67,580 条」。里面混着两类：

类别 是否算持久化丢失
服务端还没执行（还在 socket 缓冲里） ❌ 不算，客户端本来就没收到确认
已执行、但 AOF 缓冲还没写到 OS ✅ 算（但窗口是「一个事件循环」级别）

要在实验里精确区分这两类，必须在每次写入后读回复（everysec 下会让窗口缩小到一个循环周期，几乎测不到）。这正是「丢失窗口」的真实含义：它不是一个固定的秒数，而是「多久没落盘」的概率分布。

2.5 动手验证：量你自己的写入开销

预期观察点：always 的耗时是 everysec 的 3~5 倍（本文 4.7 倍）。

判定标准：

  • always 与 everysec 差距 < 2 倍 → 你的磁盘很快（NVMe/内存盘），或者 fsync 被文件系统吞了；
  • no 比 everysec 还慢 → 测量噪声，或 AOF 重写正在跑（INFO persistence 看 aof_rewrite_in_progress）。

3. AOF 重写：18.6 MB 变成 4.3 MB

3.1 实测：20 万 key（35 MB 内存）

指标 实测
AOF（未重写，逐条命令） 18.6 MB
RDB 快照 4.3 MB
BGSAVE 耗时 0.35 s
BGREWRITEAOF 耗时 0.36 s
重写后（混合模式） base.rdb 4.3 MB + 0 B incr
COW 内存 573 KB

为什么 AOF 会大：它记录的是「每条写命令」，同一个 key 被改 10 次就有 10 条记录；重写是「按当前状态重新生成最小命令集」，所以能压缩到接近 RDB 的大小。

flowchart LR
    A["AOF 18.6MB<br/>per-command log"] --> B["fork child"]
    B --> C["rewrite: dump current state<br/>as RDB preamble"]
    C --> D["base.rdb 4.3MB<br/>+ tail commands"]
    D --> E["atomic switch<br/>old files removed"]

3.2 混合持久化：为什么 base 是 .rdb

实测文件列表：

因为 aof-use-rdb-preamble yes（实测默认）：重写时先写一个 RDB 作为基础，再把重写期间的新命令追加在后面。好处是恢复速度接近 RDB，同时保留 AOF 的「最后一段不丢」。

3.3 重写的代价：fork + COW

代价 说明 本文实测
fork 停顿 与数据集大小成正比 20 万 key 时几乎无感
COW 内存 重写期间新写入会触发页复制 573 KB（写入少时很小）
磁盘 IO 顺序写一个新文件 4.3 MB / 0.36 s

注意：重写期间的写入会同时写「旧 AOF」和「重写缓冲」，所以写入量大时 COW 内存会显著上升——这也是 ④ 说「内存不要超过物理内存 70%」的原因之一。

3.4 动手验证：观察一次重写

预期观察点：aof_rewrite_in_progress:1 期间 aof_current_size 继续增长，结束后 aof_base_size 变成新的基线。

判定标准：

  • 重写时间随数据量线性增长 → 正常；
  • 重写时 P99 抖动明显 → fork 停顿，考虑在从库做持久化（⑧）；
  • aof_current_size 不降 → 重写失败，看日志 INFO persistence 的 aof_last_bgrewrite_status。
flowchart TD
    S["Redis restart"] --> Q{"appendonly on?"}
    Q -- no --> R["load dump.rdb<br/>0.26s for 200k keys"]
    Q -- yes --> H{"aof-use-rdb-preamble"}
    H -- yes --> P["load base rdb<br/>then replay incr tail<br/>0.28s"]
    H -- no --> A["replay every command<br/>slower on big data"]

4. 恢复：RDB 0.26 s vs AOF 0.28 s

20 万 key（35 MB 内存）实测：

持久化 文件 恢复就绪耗时 加载条数
纯 RDB 4.3 MB 0.26 s 200,000
AOF（混合） 4.3 MB base 0.28 s 200,000

在混合持久化下，两者几乎没有差别——因为 AOF 的主体也是一个 RDB。

规模 RDB 恢复（外推） 纯 AOF（无混合）
20 万 key / 35MB 0.26 s（实测） 0.28 s（实测，混合）
1000 万 key / 2GB 十几秒 可能几十秒到分钟级（要重放命令）

结论：恢复速度主要看「数据量」和「是否混合」，纯 AOF 的逐条重放在大实例上会明显更慢。

5. 线上怎么配

5.1 按数据价值选

场景 推荐配置 理由
纯缓存（可重建） RDB（默认），不丢也能回源 省 AOF 的写入开销
缓存 + 少量不可重建数据 AOF everysec + 混合 ≤1 秒窗口，性能损失小
当存储用（队列、计数） AOF always 或 everysec + 从库 487 µs/op 换确定性
强一致要求 不要用 Redis 见 ⑪ 的 RedLock 争议

5.2 必须监控的字段

字段 含义 异常判断
rdb_last_bgsave_status 上次 BGSAVE 是否成功 非 ok 要立刻查
rdb_last_fork_usec 上次 fork 耗时 持续增长 = 数据集变大
rdb_last_cow_size COW 内存 接近数据量 = 写入太猛
aof_last_bgrewrite_status 重写结果 非 ok = 磁盘/内存问题
aof_current_size AOF 当前大小 持续增长 = 重写没触发
aof_pending_rewrite 是否在排队重写 长时间 1 = 重写跟不上写入

5.3 与 MySQL 系列对照

维度 MySQL（⑦） Redis（本文）
持久化机制 redo + binlog，双写 RDB 快照 / AOF 追加
每次提交落盘 默认 flush=1 + sync_binlog=1（两次 fsync） always（一次 fsync）
性能差距 734 → 1962 TPS（flush 1→2） 103 → 487 µs/op（everysec → always）
kill -9 会丢吗 flush=1 不丢、flush=2 不丢、flush=0 全丢 三档都不丢（都 write 到 OS）
掉电会丢吗 flush=2 丢 1 秒 everysec 丢 1 秒
文件膨胀 binlog 自动轮转 AOF 需重写

一个反直觉的差异：MySQL 的 flush=0 连 write() 都不做，进程崩溃就丢；Redis 的 no 仍然每轮 write()，所以进程崩溃不丢。同样是「最不安全档」，Redis 比 MySQL 安全一档。

7. 动手验证：四个可复现实验

7.1 动手验证：量三档 fsync 的写入开销

预期观察点：always 约 1.4 s、everysec 约 0.36 s、no 约 0.35 s（本文）。

判定标准：always 与 everysec 差距 < 2 倍 → 磁盘或文件系统把 fsync 吞了，需换真实磁盘复测。

7.2 动手验证：kill -9 之后数存活条数

预期观察点：DBSIZE 仍为 3000（本文三档都 0 丢失）。

判定标准：丢了数据 → 检查是否 appendonly no（默认就是 no），或 kill 前有未落盘的缓冲。

7.3 动手验证：观察一次 AOF 重写

预期观察点：aof_rewrite_in_progress 从 1 回到 0，aof_base_size 变成新的基线，文件从 18.6 MB 级降到 4.3 MB 级。

判定标准：重写后文件没变小 → 数据本身就这么大（没有冗余命令），或重写失败（查 aof_last_bgrewrite_status）。

7.4 动手验证：对比恢复时间

预期观察点：20 万 key 时 AOF 恢复约 0.28 s、纯 RDB 约 0.26 s（本文）。

判定标准：恢复时间随数据量线性增长 → 大实例要开混合持久化（aof-use-rdb-preamble yes）。

6. 总结

6.1 面试速答表

面试题 一句话答案
RDB 和 AOF 怎么选 能重建的数据用 RDB；不能丢的用 AOF（混合模式），恢复快且窗口小
appendfsync 三档区别 always 每次 fsync；everysec 每秒；no 交给 OS。实测 487 / 103 / 116 µs per op
everysec 会丢多少 掉电丢 ≤1 秒；进程崩溃几乎不丢（数据已 write 到 OS）
kill -9 会丢数据吗 实测三档都 0 丢失；因为 kill 只杀进程，page cache 还在
什么情况才会丢 1 秒 OS 崩溃 / 掉电 / 宿主机被强杀
AOF 为什么需要重写 记录的是命令，同一 key 多次修改会冗余；本文 18.6 MB → 4.3 MB
重写的代价 fork + COW 内存 + 磁盘 IO；COW 实测 573 KB（20 万 key）
混合持久化是什么 AOF 的主体用 RDB 格式（aof-use-rdb-preamble yes），恢复速度接近 RDB
AOF 和 RDB 恢复谁快 混合模式下几乎一样（本文 0.28 s vs 0.26 s）；纯 AOF 大实例会慢很多
默认开 AOF 吗 不开，appendonly no 是默认值
生产怎么配 缓存用 RDB；队列/计数用 AOF everysec + 从库；强一致别用 Redis
监控哪些字段 rdb_last_bgsave_status、aof_last_bgrewrite_status、aof_current_size、rdb_last_cow_size

6.2 实战避坑表

症状 原因 处理
重启后丢了几分钟数据 只开了 RDB 开 AOF 或用 SAVE 提频
AOF 文件涨到几十 GB 重写没触发（阈值 64MB/100%） 调 auto-aof-rewrite-*，或手动 BGREWRITEAOF
写入突然变慢 有人把 appendfsync 改成 always 检查配置变更记录
重写期间 P99 抖动 fork + COW 在从库做持久化，或降低写入峰值
重启加载很久 纯 AOF 且数据量大 开混合持久化（aof-use-rdb-preamble yes）
磁盘突然满 RDB + AOF + 重写临时文件同时存在 清理旧文件，监控 aof_current_size

6.3 工具速查表

工具 看什么 判定标准
INFO persistence 各持久化的状态与大小 任何 *_status 非 ok 都要处理
CONFIG GET appendfsync 当前策略 always 要有性能预算
BGSAVE / BGREWRITEAOF 手动触发 观察 in_progress 与耗时
SAVE 阻塞式快照 禁止在线使用（会阻塞主线程）
rdb_last_fork_usec fork 耗时趋势 持续增长 = 数据量在涨
aof_pending_rewrite 重写排队 长期 1 = 重写跟不上

6.4 实操建议

  1. 先确认你的实例到底开没开 AOF，appendonly no 是默认值，很多人以为开了。
  2. 缓存用 RDB 就够，别为了「保险」给纯缓存加 AOF，白白付出写入开销。
  3. **要确定性就用 always**，但先测你的磁盘能不能承受 4~5 倍的写入成本。
  4. **定期观察 aof_current_size**，重写阈值（64 MB / 100%）对高写入实例可能太宽松。
  5. 持久化放在从库做，主库只负责服务请求（⑧ 会讲主从架构）。
