Linux 资源排查实战

Posted on 2026-08-12 In 操作系统 Word count in article: 2.9k Reading time ≈ 11 mins.

资源排查是「指标 → 机制 → 根因」的翻译工作：top、vmstat、iostat 暴露的是现象，机制在前四篇（切换成本、页表与缺页、页缓存与 fsync、epoll 等待），根因藏在两者的交叉处。本文把操作系统系列的六件套工具（ps/top/vmstat/iostat/strace/ss + jstack/jstat）收拢成 CPU、内存、IO、连接四类故障的定位流程，用三个真实案例走完「症状 → 工具 → 根因 → 处理」全链路。

系列地图（操作系统）收官：① 进程与线程（执行单元与调度）→ ② 内存管理（地址空间与物理内存）→ ③ 文件系统与磁盘 IO（数据落盘）→ ④ IO 模型（等待数据的方式）→ ⑤ 本文：把前四篇的机制变成排查工具链。

1. 排查方法论：先全局，再局部

1.1 四类故障的入口

故障面 第一眼指标 入口命令
CPU load、%us/%sy top、vmstat 1
内存 available、si/so free -h、vmstat 1
IO %util、await、bo iostat -x 1、vmstat 1
连接 estab、TIME_WAIT、fd ss -s、ulimit -n

排查原则：先全局扫描定方向（30 秒），再钻局部锁根因。全局扫描就是一套固定命令：

load 高不等于 CPU 忙：load = 可运行（R）+ 不可中断（D）进程数。R 多说明 CPU 排队（换更好的机器/降并发），D 多说明进程卡在 IO/内核（盘、锁、swap）——方向完全不同，这是第一个要翻译的指标。

1.2 动手验证：跑一次完整的全局扫描

对照输出理解每一列：r（就绪队列）、b（阻塞在 IO）、cs（切换/秒，第 1 篇）、si/so（换页，第 2 篇）、bo（刷盘块数，第 3 篇）、us/sy（用户/内核时间占比）。一个命令序列，四篇机制全覆盖——这就是工具链收拢的含义。

2.2 深挖：Java 服务 CPU 100% 的两张脸

业务线程在烧：top -Hp 看到业务线程（如 http-nio-*）长时间 RUNNABLE，jstack 定位到热点方法（大循环、正则回溯、序列化）。GC 线程在烧：jstat 显示 FGCT（Full GC 累计时间）持续增长——此时烧核的不是业务代码而是回收本身（堆过小、对象泄漏）。同一症状（CPU 高）两种根因，分岔点就在 top -Hp 后线程是谁。

2.3 动手验证：模拟一次 CPU 打满并定位

判定标准：%us 高 = 用户态（业务/GC），%sy 高 = 内核态（切换过多、syscall 密集，回看第 1 篇 §3.4）；GC 占用超过 20% 时间，先解决内存问题再谈代码优化。

4.2 深挖：iowait 高的三种真相

现象 真相 验证
%util 100%、await 高 盘真忙 iostat 看磁盘型号与队列
%util 不高但 iowait 高 盘没忙，是进程在等（锁、swap、网络） vmstat 的 b 列 + pidstat -d 对账
NVMe 上 %util 100% 现代盘并发高，util 定义过时，不代表饱和 看 avgqu-sz 与延迟分布

IO 高不一定是 IO 问题：swap 换页（内存问题）和锁等待（并发问题）都会表现为「进程 D 状态/阻塞」，但盘根本不忙——翻译指标时先排除这两类伪装。

4.3 动手验证：压一次盘并解读

对照第 3 篇：oflag=direct 绕过页缓存（§2.3），所以 %util 真实反映磁盘；去掉 oflag 再跑，%util 大幅下降——同一份写入，缓冲与否差出一倍磁盘占用，这就是「先查请求模式，再骂盘慢」的实操依据。

5. 连接类故障：TIME_WAIT 与端口耗尽

5.1 高并发短连接的经典事故

TIME_WAIT 是主动关闭方的收尾状态（持续 2MSL ≈ 60 秒）：短连接服务（每请求一个连接，连接由服务端主动关闭）高并发时，TIME_WAIT 连接堆积，占满本地端口范围（/proc/sys/net/ipv4/ip_local_port_range，默认约 2.8 万个）——新连接没有可用本地端口，ss -s 里 timewait 数量暴涨 + 业务报连接失败。

5.2 深挖：为什么连接要复用

TIME_WAIT 设计的本意是防「迟到旧报文污染新连接」（第 4 篇 TCP 状态机的安全收尾）。生产解法不是调小端口而是连接复用：HTTP keep-alive / 连接池把「短连接」变「长连接」——这正好呼应第 4 篇：连接数是 fd 数、是线程数的直接消耗者，复用连接等于同时省掉 TIME_WAIT、fd 和握手开销（三次握手也是一次 RTT）。连接池参数（maxTotal/minIdle）背后的机制，就是 TIME_WAIT 与端口范围。

6. 真实案例复盘：三次「症状 → 工具 → 根因」

6.1 案例一：TPS 上不去，cs 每秒 30 万

环节 内容
症状 8 核机器 TPS 卡 4000，压测曲线有平台期
工具 vmstat 1 看到 cs 30 万+（第 1 篇 §3.4 的判定标准：8 核 × 2 万 = 16 万已超标）；pidstat -w 每个 worker 上万次非自愿切换
根因 线程池 300 线程远超核数，大量时间在抢时间片
处理 线程池缩到 64，cs 降到 5 万，TPS 升到 9000

6.2 案例二：容器里 Java 无日志消失

环节 内容
症状 K8s pod 重启，应用无异常日志
工具 dmesg 找到 Killed process ... java, oom_score_adj=1000（第 2 篇 §4.3）；cgroup 核对 limits.memory=1g
根因 只设了 -Xmx1g，RSS = 堆 + Metaspace + 直接内存 > 1g，被 cgroup 限杀
处理 改 -XX:MaxRAMPercentage=75，观察 memory.current 稳定在限额 80% 以内

6.3 案例三：写日志把磁盘打满

环节 内容
症状 高峰期应用卡顿，iostat %util 100%，但盘是 NVMe 不该这么慢
工具 pidstat -d 锁定日志进程；iostat 里 w/s 突刺与业务时间轴吻合（第 3 篇 §2.4 回写风暴特征）；strace 看到大量 fsync
根因 logback immediateFlush=true 逐条 fsync（第 3 篇 §4.1 的百倍差）+ 脏页阈值触发批量回写
处理 immediateFlush=false + 批量刷，%util 从 100% 降到 20%

三个案例的共同模式：入口指标 → 对应篇目的机制 → 参数/架构修正——工具只是入口，判断力来自「这个指标背后是哪一层机制」。

7. 总结：操作系统系列收官

7.1 六件套工具总表

工具 看什么 判定标准 对应篇目
top / top -Hp 进程/线程 CPU %sy 高查切换与 syscall ① ④
vmstat 1 cs、si/so、r/b、us/sy cs > 核数×2 万/秒；si/so 非零即事故 ① ②
free -h / cgroup available、容器真实占用 看 available 不看 free；容器看 memory.current ②
iostat -x %util、await、w/s util 高先排除 swap 与锁 ③
strace -c syscall 类型与次数 读/写/futex 计数异常 ① ③
ss -s / ulimit -n 连接状态、fd 配额 timewait 堆积查端口与连接复用 ④
jstack / jstat Java 线程栈、GC CPU 高先分「业务线程 vs GC」 ① ②

7.2 面试速答表

面试题 一句话答案
load 高代表什么？ R + D 状态进程数；R 多 CPU 排队，D 多 IO/内核阻塞，方向不同
CPU 高怎么定位？ top → top -Hp → TID 转 hex → jstack 匹配 nid；先排除 GC
容器里 top 显示的内存是？ 宿主机视角；容器真实占用看 cgroup memory.current
iowait 高就是盘慢？ 不一定——swap 换页和锁等待也会伪装成 IO 阻塞，先看盘 util
TIME_WAIT 堆积怎么办？ 连接复用（keep-alive/连接池）优于调端口；TIME_WAIT 是安全收尾
排查第一件事是什么？ 全局扫描 + dmesg（内核级事件经常被忽略）

7.3 系列收官：五篇一条链

篇目 一句话核心 给你的能力
① 进程与线程 进程管资源、线程管执行、调度管时间 线程池大小、虚拟线程选型有依据
② 内存管理 地址空间是承诺、RSS 是现实 OOM 排查、容器内存配置不再靠猜
③ 文件系统 write 返回 ≠ 落盘，fsync 是取舍点 刷盘策略、零拷贝选型有依据
④ IO 模型 等待数据的方式决定架构 线程模型、连接上限有依据
⑤ 本文 指标要翻译回机制 故障定位从「试」变成「推」

实操建议（收尾三件事）：

  1. 把第 1 节的全盘扫描命令存成 sos.sh，任何故障先跑一遍再说话——30 秒定方向。
  2. 每次排障记录「症状 → 工具 → 根因 → 处理」四行，积累成自己的判定标准表。
  3. 回到第 1 篇的结论：所有性能问题的本质都是「资源与机制的错配」——切换成本、缺页、fsync、唤醒，选对机制比调大资源重要。

命令速查联动：本文讲「指标怎么翻译成机制」，命令本身的用法见 Linux 基础与 Shell 编程（速查手册，§8 有完整定位流程）——排查现场两篇配合：本文定方向，速查篇查命令。
