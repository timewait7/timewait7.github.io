Zeus-Doc 架构设计与技术选型

Posted on 2026-08-06 In 项目实战 Word count in article: 5.9k Reading time ≈ 21 mins.

一、项目概述

Zeus-Doc 是面向多租户企业的知识库文档中台，提供文档创作、协同编辑、全文检索、文件存储、审计追溯等完整能力。系统采用 Spring Cloud 微服务架构，按业务边界拆分为 6 大核心服务 + 1 个网关，背后由 MySQL、Redis、Elasticsearch、MinIO、RocketMQ 等中间件支撑。

核心业务能力：

  • 文档 CRUD + 版本管理（全量快照 + Diff-Match-Patch 增量补丁）
  • 三级缓存（Caffeine → Redis → MySQL）+ 布隆过滤器 + 互斥锁重建
  • 实时协同编辑（Netty WebSocket + OT 算法合并）
  • ES 全文检索（高亮 + 聚合 + Sentinel 熔断降级）
  • 大文件分片上传 + 零拷贝合并（MinIO）
  • 审计日志分库分表（ShardingSphere）+ Seata TCC 分布式事务

二、需求分析与系统边界

1.1 业务背景

Zeus-Doc 是面向中大型企业的「知识库文档中台」，提供文档全生命周期管理：创建、富文本/Markdown 编辑、多人协同编辑、版本回溯、全文检索、文件附件、细粒度权限审计与回收站。系统采用 SaaS 多租户模型，需要支撑单租户日均 50 万次文档读、峰值 3000 QPS、千人同时在线协同编辑。

1.2 核心功能需求

模块 关键需求 性能指标
文档管理 CRUD、版本历史、回收站、分享链接 读 RT < 50ms（命中缓存）
协同编辑 实时多人协同、OT 冲突合并 WebSocket 5000 连接/节点
全文检索 ES 倒排、高亮、聚合 搜索 RT < 200ms
文件存储 大文件分片上传、断点续传 单文件最大 2GB
审计日志 全量行为留痕、租户隔离 异步落库不阻塞主流程
用户权限 RBAC + 租户隔离 JWT 鉴权 < 5ms

1.3 系统边界

  • 做：文档中台业务能力、多租户隔离、跨服务最终一致事务、协同编辑冲突合并。
  • 不做：即时通讯（IM）、视频会议、OA 审批流；这些由上游系统通过 OpenAPI 接入。

1.4 非功能性约束

  • 可用性 ≥ 99.9%，核心读链路支持同城双活；
  • 数据一致性：金融级强一致非目标，业务最终一致 + 审计可追溯即可；
  • 可扩展性：水平扩容无状态化，分库分表承载亿级 doc_history。

五、微服务拆分说明

4.1 拆分原则

  1. 领域驱动（DDD）：按业务领域而非技术分层拆分；
  2. 生命周期独立：每个服务可独立部署、扩容、故障隔离；
  3. 数据 ownership：每个服务独占自己的数据库，跨服务仅通过 RPC/MQ 通信。

4.2 职责边界矩阵

服务 核心领域 数据所有权 对外能力
user 用户/租户 zeus_user 库 登录、RBAC、租户管理
doc 文档聚合根 zeus_doc / zeus_doc_history_0..3 分片 文档 CRUD、版本、缓存、TCC 分支
collab 协同会话 Redis（会话态） WebSocket、OT 合并、在线广播
search 检索索引 Elasticsearch 全文检索、聚合统计
file 对象存储 MinIO 上传/下载/秒传/分片
audit 审计/回收站 zeus_audit 分片库 审计查询、回收站恢复、TCC 编排

4.3 服务间依赖

依赖方向严格单向：gateway → 各业务服务；doc → audit（Feign，TCC 分支）；doc → collab（协同触发）；doc → search（MQ 异步解耦）。审计侧 DocDeleteTccFacade 作为 TCC 编排方开启 @GlobalTransactional，doc 侧 DocDeleteTccActionImpl 作为分支参与同一 XID，XID 经 Feign 拦截器透传，不存在反向同步依赖。

六、技术选型决策理由

3.1 为什么选 MySQL 而非 MongoDB

维度 MySQL 8.0 MongoDB
事务 强 ACID，InnoDB 行锁 4.0+ 多文档事务性能差
生态 DBA 成熟、运维成本低 适合 schema-free 场景
一致性 文档元数据强一致要求高 最终一致为主
分片 ShardingSphere-JDBC 透明路由 内置 sharding 但运维黑盒

结论：文档元数据、审计、回收站需强事务保证（删除走 TCC 跨库），MySQL 更稳妥。文档正文虽是「大文本」，但正文存储于 Redis/MinIO 缓存层，DB 只存元数据 + 摘要，MySQL 完全胜任。MongoDB 在 schema 多变场景更优，本项目 schema 稳定，故不选。

3.2 为什么选 MinIO 而非 FastDFS

维度 MinIO FastDFS
协议 标准 S3 API 私有协议
运维 单二进制、K8s 友好 Tracker/Storage 双角色复杂
生态 SDK 丰富、SDK 兼容 AWS 文档少、社区萎缩
高可用 纠删码 Erasure Coding 主备复制
活跃度 持续更新（8.5.11） 维护停滞

结论：MinIO 提供 S3 兼容 API，未来可无缝迁移至 OSS/S3；FastDFS 社区活跃度低且无 K8s 原生支持。MinIO 纠删码以 50% 冗余实现高可用，性价比优于三副本。

3.3 为什么选 Tomcat

  • 协同服务已用 Netty：collab 服务长连接用 Netty，HTTP 接入层用 Tomcat 避免技术栈分裂。
  • 生态成熟：jstack/arthas/GC 调优经验沉淀多，max-threads/max-connections/accept-count 三参数模型清晰（见 application.yml 第 3-11 行）。
  • 压测拐点可控：见《03-性能压测报告》，max-threads=200 时 TPS 拐点出现，调到 500 边际收益递减。
  • Undertow 内存更省但调参黑盒，Netty 自建 HTTP 栈开发成本高，权衡后选 Tomcat。

3.4 关键中间件版本对齐（pom.xml 第 36-61 行）

Spring Cloud Alibaba 2023.0.1.0 与 Spring Boot 3.2.5 / Spring Cloud 2023.0.1 严格对齐（2023.x 线），JDK 17。Seata 2.0.0 支持 TCC 增强，ShardingSphere 5.4.1 支持 INTERVAL 分表算法。

选型理由补充

1. 主存储：MySQL 8.0 而非 MongoDB

决策维度 MySQL 8.0（采用） MongoDB
团队熟悉度 高，DBA/运维链路成熟 中等，需重建排障体系
事务能力 InnoDB 强一致性事务，原生 XA 4.0+ 多文档事务性能损耗大、限制多
分库分表生态 ShardingSphere-JDBC 深度实践，JDBC 层透明路由 自带分片，但跨片事务与 Join 弱
业务匹配 文档元数据强关系（doc↔user↔share↔audit），需多表 Join 与外键约束 文档正文 JSON 字段可由 MySQL JSON 类型承载
运维成本 主从/备份/监控/慢查询工具链完善 内存控制、分片平衡需额外投入

结论： 文档元数据、分享链接、审计日志等核心数据有强一致性和关系约束需求，ShardingSphere 在 JDBC 层做分片对应用透明（application-sharding.yml 配置即可路由），团队掌握度高，因此选 MySQL 作为主存储。文档正文（Quill Delta JSON）以 TEXT 列存储，必要时可下沉到对象存储。

2. 对象存储：MinIO 而非 FastDFS

决策维度 MinIO（采用） FastDFS
协议标准 原生 S3 兼容，SDK 生态丰富 私有协议，SDK 封闭
部署运维 单二进制、轻量、容器友好 Tracker/Storage 双角色，部署复杂
签名 URL S3 Presigned URL 开箱即用，前端直传 需自实现 token 机制
生态兼容 与 Spring/AWS SDK/avectl 无缝 需专用客户端
高可用 纠删码 + 多副本，跨机房易扩展 组间同步机制较弱

结论： 文件服务需要”前端直传 + 签名 URL + 分片上传”能力，MinIO 的 S3 兼容性让这些能力开箱即用，且部署轻量、与 Spring 生态集成度高。ZeroCopyStorage（zeus-doc-service-file/.../minio/ZeroCopyStorage.java）通过 FileChannel.transferFrom 调用 Linux sendfile 实现分片零拷贝合并，与 MinIO 配合良好。

3. Web 容器：Tomcat 而非 Undertow/Netty

决策维度 Tomcat（采用） Undertow Netty（裸）
Spring Boot 默认 是，零配置即可用 需替换 starter 需自行实现 HTTP 协议栈
调优深度 max-threads/max-connections/accept-count 三参数模型清晰，社区文档丰富 参数少但调优经验稀缺 完全自定义，开发成本高
监控诊断 内置 Processor/RequestProcessor JMX 指标完善 指标偏少 需自建监控
业务匹配 文档服务为典型”请求-响应”短连接业务，Tomcat NIO 完全胜任 性能略优但收益有限 适合长连接（已用于协同服务）

结论： 文档/搜索/审计等 HTTP 服务用 Tomcat（Spring Boot 默认），协同服务用 Netty 处理 WebSocket 长连接，各取所长。Tomcat 调优空间充分，详见 application.yml:3-11（max-threads=200, max-connections=10000, accept-count=100）及性能压测报告。

flowchart TD
    Req[HTTP 请求到达] --> DS[DispatcherServlet.doDispatch]
    DS --> GH[① getHandler<br/>HandlerMapping 返回 HandlerExecutionChain<br/>含拦截器链]

    RL -- 通过 --> Cid["@CurrentUserId 参数解析<br/>HandlerMethodArgumentResolver<br/>从 UserContext 注入 userId"]

    PDR --> After[⑦ triggerAfterCompletion<br/>逆序 afterCompletion]
    After --> Remove[RateLimitInterceptor:97<br/>START_TS.remove 防泄漏]
    Remove --> Done[请求结束]
    Ret429 --> After

关键点说明：

  1. 拦截位置：@RateLimit 在 applyPreHandle 阶段执行（RateLimitInterceptor.java:53），早于 Controller 方法。限流 key = 接口 + userId/IP（RateLimitInterceptor.java:69），避免单用户刷爆全局限流。
  2. 限流算法：Redis Lua 脚本原子执行 incr + expire（固定窗口），DefaultRedisScript 注入保证原子性。
  3. @CurrentUserId 解析器：在 getHandlerAdapter 后、handle 前由 HandlerMethodArgumentResolver 解析参数，从 UserContext.currentUserId() 取值注入。
  4. ThreadLocal 清理：START_TS 必须在 afterCompletion remove（RateLimitInterceptor.java:97），否则线程池线程复用导致内存泄漏（详见《05-JVM 调优报告》ThreadLocal 泄漏章节）。
  5. 中断语义：preHandle 返回 false 时 postHandle 不执行，但 afterCompletion 仍对已通过 preHandle 的拦截器执行（清理资源）。

8.1 TCC 三大坑与防御（DocDeleteTccActionImpl.java:14-20 注释）

坑 场景 防御方案
幂等 Confirm/Cancel 重试 xid+branchId 记录状态，已执行直接 return
空回滚 Try 超时未执行但 Cancel 调用 检测 Try 是否执行过，未执行则 return
悬挂 Cancel 先于 Try（网络延迟） Try 前检查是否已 Cancel，已 Cancel 拒绝 Try

8.2 为什么选 TCC 而非 AT

审计表跨库分片 + 回收站单表 + 文档库，涉及异构存储与高并发写。AT 模式依赖 undo_log 全局锁，并发写性能差；TCC 业务层控制资源冻结（PENDING 状态），无全局锁性能更优。见 DocDeleteTccFacade.java:30-34 注释。

8.3 关键代码定位

  • 全局事务开启：DocDeleteTccFacade.java:53 @GlobalTransactional(timeoutMills = 60000, name = "zeus-doc-delete-audit-tx")
  • Try 三分支编排：DocDeleteTccFacade.java:70, 83, 89
  • Doc 分支 Try：DocDeleteTccActionImpl.java:32-46（逻辑删除 + Feign 调 audit 预记录）
  • Confirm：DocDeleteTccActionImpl.java:49-55（幂等确认审计状态）
  • Cancel：DocDeleteTccActionImpl.java:58-67（restore 恢复 + 删除预记录）

十三、高可用与容灾

9.1 无状态化

业务服务（user/doc/collab/search/file/audit）无本地会话状态，会话存 Redis，支持 K8s 水平扩缩容。collab 的 WebSocket 会话通过一致性哈希路由 + Redis pub/sub 跨节点广播。

9.2 限流降级三道防线

  1. Gateway 全局限流：Sentinel 集群限流，挡住异常流量；
  2. 接口级限流：@RateLimit 注解 + Redis Lua（RateLimitInterceptor）；
  3. 热点降级：QPS>100 的热点文档仅查 L1+L2 不回源 DB（CacheService.shouldOnlyHitCache）。

9.3 优雅关闭

线程池配置 setWaitForTasksToCompleteOnShutdown(true) + awaitTerminationSeconds=30（ThreadPoolConfig.java:100-101），Spring Boot 优雅停机 + K8s preStop hook 等待 30s 处理完在途请求。

十四、非功能性设计

维度 方案
高可用 服务多副本 + Nacos 注册；MySQL 主从；Redis 哨兵/集群；ES 多分片副本；MinIO 纠删码

容错 Sentinel 熔断降级 + 本地兜底缓存；Hystrix/Fallback；RocketMQ 重试 + 死信队列

十六、架构决策记录

编号 决策 理由
ADR-01 Caffeine + Redis + MySQL 三级缓存 兼顾纳秒级响应与分布式一致性
ADR-02 ShardingSphere-JDBC 而非 Proxy 无中间代理层，延迟低，部署简单
