JVM 原理与调优

Posted on 2025-07-26 In Java Word count in article: 19k Reading time ≈ 1:11

本文覆盖 JVM 内存模型、对象生命周期、类加载机制、性能指标与调优方法论、垃圾回收、内存溢出排查、调优实战案例七大模块。每一节都按”为什么需要了解 → 怎么工作的 → 面试怎么答“组织，力求背得下来、讲得清楚、用得上。

1. JVM 内存模型

为什么需要了解：几乎所有 JVM 问题——OOM、GC 停顿、调优——最后都会落到”某块内存区域的数据太多或回收太慢“上。背出五个区域的名字没有价值，面试官真正想听的是：你写的每一个变量、每一个 new 出来的对象，在 JVM 里到底待在哪、由谁负责回收、什么时候会出问题。

1.1 运行时数据区全景

JVM 规范把运行时内存划分为 6 个区域（HotSpot 是其中最常见的实现）：

内存区域 存什么 线程私有/共享 抛出的异常 一句话本质
程序计数器（PC Register） 当前线程正在执行的字节码指令地址 私有 无（唯一不会 OOM 的区域） 线程切换后能”接上”执行到哪了
虚拟机栈（VM Stack） 每个方法调用对应一个栈帧（局部变量表、操作数栈、动态链接、方法出口） 私有 StackOverflowError（深度超限）/ OutOfMemoryError（申请不到栈） 方法的调用与返回
本地方法栈（Native Method Stack） native 方法（如 C 实现的 Object.hashCode 底层）的栈 私有 同虚拟机栈 给 native 方法用的栈
堆（Heap） 所有对象实例和数组 共享 OutOfMemoryError: Java heap space GC 的主战场
方法区（Method Area） 类元数据、运行时常量池、方法字节码、静态变量 共享 OutOfMemoryError: Metaspace 类的”档案室”
运行时常量池（在方法区内） 编译期生成的字面量和符号引用 + 运行期新放入的常量 共享 OutOfMemoryError 常量与引用

三个容易搞混的点：

  1. 方法区是规范，永久代/元空间是实现。JVM 规范只规定了”方法区该存什么”，没规定怎么存。HotSpot 在 JDK 7 及以前用永久代（PermGen）实现（占据堆空间），JDK 8 起用元空间（Metaspace）实现（使用本地内存）。其他 JVM（如 JRockit）从来没有永久代。

  2. 程序计数器是唯一不会 OOM 的区域，因为它是所有区域中唯一规定不依赖内存大小、只存一个地址的地方。注意：执行 native 方法时，PC 值是”未定义”（undefined），因为 native 方法不是字节码，不靠 PC 记录执行位置。

  3. 栈帧里存的是什么：局部变量表（基本类型、引用类型，以 slot 为单位，long/double 占两个 slot）、操作数栈（字节码指令计算的临时区，iadd 就是把栈顶两个数弹出去相加再压回）、动态链接（指向运行时常量池中该方法的引用，实现多态）、方法出口（返回时知道回哪去）。栈默认大小约 1MB（-Xss 调整），这也是递归默认只能到几千层的原因。

面试怎么答：先给出”线程私有三个：程序计数器、虚拟机栈、本地方法栈；线程共享三个：堆、方法区、运行时常量池”的骨架，再补一句”私有区域的异常要么是深度溢出要么是申请不到空间，共享区域的异常都是内存不足”，最后点出”方法区是规范，元空间是 HotSpot 的实现”——这三点讲全，区域问题基本满分。

1.2 堆内存细分

为什么需要了解：堆是 99% 的 OOM 发生地，也是 GC 的主战场。不弄清堆的内部结构，就解释不了”为什么 Minor GC 这么快””对象什么时候进老年代””大对象有什么坑”。

新生代（Young Gen）：绝大多数对象”朝生夕死”，在这里诞生和死亡。

  • Eden 区：几乎所有新对象都在这里分配。
  • S0 / S1（两个 Survivor 区）：Minor GC 时把存活对象复制进其中一个，两个区交替充当 From/To，保证任意时刻有一个 Survivor 是空的，供复制算法使用。
  • 默认比例 Eden : S0 : S1 = 8 : 1 : 1（-XX:SurvivorRatio=8），新生代实际可用空间是 90%——复制算法”浪费”的那 10% 就是那个永远空着的 To Survivor。

为什么是两个 Survivor 而不是一个：复制算法需要一个完全空闲的目标区来承接存活对象。如果只有一个 S，上一轮存活下来的对象和这一轮 Eden 里的存活对象会撞在一起——S 既是源又是目标，没法操作。两个 S 轮转，还能顺便给对象”记年龄”：每熬过一轮 Minor GC 年龄 +1，年龄够了就晋升老年代，避免对象过早晋升。

TLAB（Thread Local Allocation Buffer，线程本地分配缓冲）：

  • 堆是线程共享的，如果所有线程都去竞争同一个”堆顶指针”，分配对象会变成高并发热点。
  • 解决：每个线程在 Eden 里预申请一块私有缓冲区（TLAB），对象分配优先在自己的 TLAB 里做——只移动自己这块缓冲区的 top 指针，无需加锁。默认开启（-XX:+UseTLAB）。
  • 放不下 TLAB 的大对象退回堆上直接分配；再大（超过 -XX:PretenureSizeThreshold，默认 0 即不启用）则直接进老年代，避免它在 Eden 和 Survivor 之间反复搬运（此参数只对 Serial / ParNew 生效，G1 用的是 Humongous Region 机制）。

老年代（Old Gen）：存放多次 Minor GC 后仍存活的对象、大对象。回收频率低。默认 新生代 : 老年代 = 1 : 2（-XX:NewRatio=2）。

字符串常量池的位置变迁（重点考点）：

版本 字符串常量池位置 运行时常量池位置 关键事件
JDK 6 及以前 方法区（永久代） 方法区（永久代） 池在永久代，Full GC 才回收，intern() 大量使用时易 PermGen OOM
JDK 7 堆（JEP 223） 方法区（永久代） 移到堆后，Minor GC 就能回收无用字符串，OOM 风险大降
JDK 8 起 堆 方法区（元空间） 永久代整体移除

String.intern() 的跨版本行为对比（面试高频，原文精华保留）：

一句话总结：JDK 7 前 intern() 是”复制”（池里存副本），JDK 7 起是”存引用”（池里放堆对象地址）。

进阶题：String s = new String("a") + new String("a") 一共创建几个对象（JDK 8 下经典答案是 6 个，不计 StringBuilder 内部 char[] 则为 5 个）：

创建的对象 数量 说明
常量池中的 "a" 1 两处字面量指向同一个常量池项
堆上的 new String("a") 2 每次 new 都是新实例
StringBuilder 1 编译器自动生成的拼接容器
StringBuilder 内部的 char[] 1 默认容量 16 的 char[]（可选计入）
toString() 产生的 "aa" 1 新堆对象，不在常量池中（所以 s == "aa" 为 false）

版本差异（加分项）：JDK 9 起（JEP 280）+ 编译为 invokedynamic + StringConcatFactory，JDK 9~14 默认仍基于 StringBuilder（计数同上）；JDK 15 起默认改为 StringConcatHelper 直接操作 byte[]，不再创建 StringBuilder 对象。另外 JDK 9 还引入了 -XX:+CompactStrings（JEP 254），String 内部由 char[] 改为 byte[] + 编码标记，只含 ASCII 的字符串省一半内存。

面试怎么答：先说三件套”Eden 8 + S0/S1 各 1”，解释两个 Survivor 是复制算法运转的前提；再讲 TLAB 解决的是”并发分配的无锁化”；最后主动抛出 intern() 的 JDK6/7/8 对比，并补一句”JDK 7 把字符串常量池移进堆，就是为了让 Minor GC 也能回收它”——这一问就答成了体系。

1.3 元空间 vs 永久代

为什么需要了解：-XX:MaxPermSize 和 -XX:MaxMetaspaceSize 是两道非常常见的面试/实战题，而且”元空间默认无限”这句话一半对一半错——它确实无限，但有个触发阈值会悄悄引起 Full GC。

为什么从永久代迁移到元空间（JEP 122）：

  1. 永久代大小难以预估：类元数据（尤其 CGLIB 动态代理、JSP 编译、反射生成类）的数量运行期不可预测。-XX:MaxPermSize 设小了频繁 Full GC 甚至 OOM，设大了浪费内存。
  2. 字符串常量池放永久代易 OOM：大量 intern() 会撑爆固定大小的永久代，JDK 7 先把字符串池移进堆，JDK 8 干脆把整个永久代移除。
  3. 回收负担重：永久代与堆混在一起，永久代不足会触发 Full GC，且需要带整理的回收才能调整大小，代价高。
  4. 融合 JRockit：Oracle 合并 HotSpot 与 JRockit（JRockit 没有永久代），统一用元空间实现更平滑。

对比表：

对比项 永久代（PermGen） 元空间（Metaspace）
存在版本 JDK 7 及以前，JDK 8 被彻底移除 JDK 8 起
物理位置 堆的一部分（HotSpot 实现） 本地内存（native memory），不占用堆
默认大小 固定上限，需 -XX:MaxPermSize 指定（默认约 64~82M） 无上限，自动扩容，仅受物理内存约束
存放内容 类元数据 + 字符串常量池 + 静态变量 仅类元数据；字符串池已在堆（JDK 7 起），静态变量对象也在堆
回收与调优 大小难预估、回收效率低，容易 OOM 类元数据回收更彻底，可按需扩容
调优参数 -XX:PermSize / -XX:MaxPermSize -XX:MetaspaceSize（GC 触发阈值）/ -XX:MaxMetaspaceSize（上限）

参数陷阱（必考）：-XX:MetaspaceSize（默认约 21M）不是上限，而是触发阈值——类元数据使用量达到它时，会触发一次 Full GC 去回收类元数据；真正的上限是 -XX:MaxMetaspaceSize，默认不设置（即”无限”，只受进程可寻址内存约束）。配套参数：-XX:MinMetaspaceFreeRatio / -XX:MaxMetaspaceFreeRatio 控制 Full GC 后元空间的扩容/收缩比例；-XX:CompressedClassSpaceSize（默认 1GB）限制压缩类指针空间。

元空间的 OOM 场景：动态生成类不受控——CGLIB/ByteBuddy 代理、JSP 首次访问编译、Groovy 脚本热加载、应用热部署且不卸载旧类加载器。症状是 java.lang.OutOfMemoryError: Metaspace，排查重点是”谁在不停造新类”，而不是堆。

面试怎么答：答案四段式——① 永久代是方法区在 HotSpot 的实现，元空间是它的替代；② 迁移原因：大小难预估、字符串池拖累、回收代价高、融合 JRockit；③ 关键差异：本地内存、默认无上限；④ 参数考点：MetaspaceSize 是触发阈值不是上限。再主动补一句”实际中元空间 OOM 常见于动态代理和热部署”。

2. 对象的生命周期

为什么需要了解：new 一个对象背后发生的事、对象在内存里长什么样、JVM 怎么找到它、它什么时候进老年代——这四件事串起来就是”一个 Java 对象的一生”。面试官问对象相关问题时，八成在问这条流水线的某个环节。

2.1 对象创建过程

以 new 指令为例（HotSpot 视角，五步）：

  1. 类加载检查：new 指令在常量池中定位类的符号引用，检查该类是否已加载、解析、初始化。未加载则先执行类加载流程（见第 3 章），并判断类是否可被实例化（接口、抽象类会抛 InstantiationError）。
  2. 分配内存：在堆上为对象划分空间。分配方式取决于堆是否规整：
    • 指针碰撞（Bump the Pointer）：堆规整（复制/整理算法回收后），空闲内存是连续的一块，只需把指针往空闲方向挪动对象大小。Serial、ParNew 等带整理能力的收集器用它。
    • 空闲列表（Free List）：堆不规整（标记-清除回收后），JVM 维护一张空闲块列表，从中找一块足够大的分给对象。CMS 用它。
    • 并发安全：要么 CAS + 失败重试，要么用 TLAB（每个线程在 Eden 预分配私有缓冲，分配时不竞争堆顶指针）。
  3. 初始化零值：将分配到的内存（实例字段区）全部置零（0、null、false），保证对象字段在不赋初值时可直接使用（int 为 0 而不是垃圾值）。
  4. 设置对象头：写入对象所属类的元数据指针（Klass Pointer）、对象的 GC 分代年龄（0）、锁状态等（见 2.2）。
  5. 执行 <init> 构造方法：按程序员写的构造逻辑初始化实例字段，new 完成，返回引用。

面试怎么答：按五步背，但重点讲第二步——主动说出”指针碰撞 vs 空闲列表取决于堆是否规整，而堆是否规整取决于收集器算法；并发分配靠 CAS 和 TLAB 解决”——这比背流程更能体现理解深度。

2.2 对象的内存布局（Mark Word + Klass Pointer + 实例数据 + 对齐填充）

一个对象在堆里占三块（HotSpot 64 位 JVM）：

组成部分 大小 内容
对象头：Mark Word 8 字节 对象自身的运行时数据：哈希码（延迟计算）、GC 分代年龄（4 bit）、锁状态标志位（无锁 01 / 偏向锁 101 / 轻量级锁 00 / 重量级锁 10 / GC 标记 11）、偏向锁线程 ID、epoch 等
对象头：Klass Pointer 4 字节（开启压缩）或 8 字节 指向方法区中类元数据的指针，JVM 靠它知道对象是哪个类的实例
实例数据（Instance Data） 不定 对象的实例字段值，按类型分配（long/double 8 字节、int 4 字节、引用类型按压缩指针 4 字节等）
对齐填充（Padding） 0~7 字节 对象大小必须是 8 字节的整数倍，不足则补齐（64 位 HotSpot 默认对象对齐）

关键细节：

  • 压缩指针：-XX:+UseCompressedOops 默认开启（64 位且堆 ≤ 32GB），对象引用由 8 字节压到 4 字节，堆 32G 的机器实际能装的引用量翻倍。开启后对象头固定 12 字节（8 + 4），加填充后正好 16 字节对齐。
  • Mark Word 是锁状态的总开关：synchronized 锁升级（偏向 → 轻量 → 重量）的所有信息都写在 Mark Word 的比特位里（详见并发篇）。这也是为什么 Mark Word 里同时要塞哈希码、年龄和锁标志——一个字节能表达的东西都挤在一起。
  • GC 年龄只有 4 bit：最大只能记到 15，所以 -XX:MaxTenuringThreshold 的合法上限是 15（CMS 下默认 6）。

面试怎么答：画一遍三块结构图，然后强调两点——① Mark Word 是一把锁 + GC 信息复用的小仓库（哈希码延迟计算、年龄 4 bit、锁标志位）；② 压缩指针让引用 8 字节变 4 字节，前提是堆 ≤ 32G。

2.3 对象的访问定位（句柄 vs 直接指针）

对象创建出来，栈上的引用（reference）怎么找到堆里的对象？两种设计：

对比项 句柄访问（Handle） 直接指针访问（Direct Pointer）
结构 reference → 句柄池 →（对象实例指针 + 类型指针） reference 直接指向对象地址，对象头里带 Klass Pointer
寻址次数 两次（先找句柄，再找对象） 一次
GC 移动对象时 只改句柄池里的指针，reference 不用动 必须更新所有引用该对象的 reference
优点 GC 效率高（对象移动无感） 速度快（少一次指针定位）、实现简单
缺点 慢（多一次寻址） GC 移动对象时要额外修正引用
谁在用 早期一些 JVM（如 JVM 规范示例） HotSpot 采用直接指针

HotSpot 选择直接指针的原因：访问对象是最高频的操作，少一次指针跳转意味着整体访问速度更快；配合压缩指针（UseCompressedOops）还能弥补直接指针内存占用高的劣势。代价是 GC 移动对象（复制、整理）时必须同时修正栈/堆里的引用——HotSpot 通过”遍历 GC Roots 时更新引用”来承接这个成本。

面试怎么答：两句搞定——“句柄访问两次寻址但 GC 移动对象无感；直接指针一次寻址但 GC 要修引用。HotSpot 选直接指针，因为对象访问是最高频操作，速度优先，压缩指针解决了内存占用问题。”

对象晋升路径全景图：

三个容易答不全的点：

  1. 动态年龄判断：不是只有”年龄到 15 才晋升”。如果 S 区里同一年龄的对象加起来已经占了 Survivor 一半空间，说明这些对象大概率会长期存活，就直接把 ≥ 这个年龄的对象全部晋升，避免它们在 S 区里挤占复制算法的目标空间。
  2. 空间分配担保（HandlePromotionFailure）：Minor GC 前，JVM 要确认老年代是否装得下”这次可能晋升的所有对象”。历史上有 -XX:HandlePromotionFailure 参数，JDK 6 Update 24 之后该参数已失效，规则变为：只要老年代连续空间大于新生代对象总大小或历次晋升的平均大小，就允许 Minor GC；否则改为 Full GC。
  3. 大对象直接进老年代：-XX:PretenureSizeThreshold（如 -XX:PretenureSizeThreshold=3m）让超过 3MB 的对象直接进老年代，避免大对象在 Eden 与 Survivor 间反复复制、以及大对象晋升时触发过早的 Full GC。注意它只对 Serial / ParNew 生效，G1 用 Humongous Region 承担同样职责。

面试怎么答：顺着路径图讲：Minor GC 存活 → S 区轮转 + 年龄累加 → 两条晋升通道（年龄达标、动态年龄判定）→ 一条直达通道（大对象）→ 最后补一句担保机制——“老年代空间不够时 Minor GC 会升级为 Full GC”，这条流水线就完整了。

3. 类加载机制

为什么需要了解：类加载器决定了”你的代码如何被找到和执行”，是 JVM 与外部世界的第一道边界。框架（Spring、Tomcat、MyBatis）底层大量依赖类加载器，SPI 机制、热部署、JDBC 驱动加载都建立在这套机制上。

3.1 类的生命周期

一个类从字节码变成可执行代码，经历 7 个阶段（前 5 个合称”类加载过程”）：

① 加载（Loading）：通过全限定名获取类的二进制字节流（.class 文件、JAR、网络、运行时动态生成——CGLIB 就是这样造类的）；把字节流转化为方法区（元空间）的运行时数据结构；在堆中生成 java.lang.Class 对象作为访问入口。

② 验证（Verification）：字节码安全校验：文件格式（魔数 0xCAFEBABE）、元数据（父类、接口合法性）、字节码（操作数栈类型是否匹配）、符号引用（能否找到对应类/方法）。防止加载恶意字节码破坏 JVM。

③ 准备（Preparation）：为静态变量分配内存并设零值（0、null、false）。注意两个坑：

  • 此刻还没有执行任何 Java 代码，public static int x = 100; 在准备阶段 x 是 0，真正的 100 要等初始化阶段执行 <clinit> 才写入；
  • 特例：static final 常量（编译期可确定的）会直接赋真实值。

④ 解析（Resolution）：把常量池中的符号引用（如 java/lang/System 的名字）替换为直接引用（内存地址/偏移量）。HotSpot 默认把解析推迟到第一次真正使用时（惰性解析），invokedynamic（Lambda、字符串拼接）更是要到运行期才解析。

⑤ 初始化（Initialization）：执行 <clinit>()——静态变量赋值 + 静态代码块。触发条件（主动使用，6 种）：

  1. new、getstatic、putstatic、invokestatic（创建实例、读写静态字段、调用静态方法）；
  2. 反射调用（Class.forName("...") 默认 initialize=true 会初始化；ClassLoader.loadClass() 不会）；
  3. 初始化子类时，先初始化其父类；
  4. 程序主类（main 方法所在类）；
  5. JDK 7 起，invokedynamic 指令解析出的目标方法句柄对应的类；
  6. JDK 8 起，实现类初始化前，若接口定义了 default 方法，接口会先被初始化。

⑥ 使用（Using）：正常执行。

⑦ 卸载（Unloading）：类要被卸载，需同时满足三个条件：该类的所有实例都被回收、该类的 Class 对象不可达、加载它的类加载器不可达（第三条是热部署能释放旧代码的关键——Tomcat 每部署一次就新建一个 WebAppClassLoader，停止应用后旧加载器连同它加载的类一起被回收）。

Class.forName() 和 ClassLoader.loadClass() 的区别（高频题）：

对比项 Class.forName() ClassLoader.loadClass()
触发阶段 加载 + 链接 + 初始化（默认执行 <clinit> 静态块） 只加载 + 链接（不初始化，首次主动使用才初始化）
典型用途 JDBC 老驱动 Class.forName("com.mysql.jdbc.Driver") 注册驱动 框架按需加载类（Spring、反射场景）
是否可控 重载 forName(name, initialize, loader) 可关掉初始化 本身不初始化

面试怎么答：七阶段（或五阶段）流程 + 一个区分题。重点：准备阶段给静态变量的是零值不是初值；static final 常量例外；主动使用 6 种情形能列举 3 种以上即可，最好带出”初始化子类先初始化父类”。

3.2 类加载器（Bootstrap → Platform → Application，JDK 9+ 的模块化类加载器）

JDK 9+ 的结构（JEP 220 / JEP 261，模块化后）：

类加载器 加载内容 父加载器
Bootstrap ClassLoader java.base、java.lang 等基础模块（JVM 自带，C++ 实现，null 表示） 无
Platform ClassLoader（平台类加载器） java.sql、java.xml 等 SE 平台模块（由 Extension 改名而来） Bootstrap
Application ClassLoader（应用类加载器） classpath / module-path 上的应用类 Platform
自定义 ClassLoader 用户指定路径 Application（或自定义）

JDK 8 及以前的结构（面试常考对照）：

类加载器 加载路径 父加载器
Bootstrap ClassLoader JRE/lib/rt.jar 等核心库 无（顶级）
Extension ClassLoader JRE/lib/ext 扩展库 Bootstrap
Application ClassLoader 应用类路径（ClassPath） Extension
自定义 ClassLoader 用户自定义路径 Application

版本差异必考点：从 JDK 9（JEP 220） 起，扩展机制被模块系统（JPMS）取代：Extension ClassLoader 改名为 Platform ClassLoader，rt.jar 被拆分为 jmods 模块——**rt.jar 文件已不存在**。老资料里”JRE/lib/rt.jar“的说法在 JDK 9+ 已失效。

面试怎么答：JDK 8 说”Bootstrap → Extension → Application”，JDK 9+ 说”Bootstrap → Platform → Application”，并主动点出”rt.jar 没了、Extension 改名叫 Platform”，一句话体现版本意识。

3.3 双亲委派模型

双亲委派：一个类加载器收到加载请求，先把请求委派给父加载器，父加载器再往上委派，直到 Bootstrap；只有父加载器返回”找不到”，才轮到子加载器自己尝试加载（findClass）。

ClassLoader.loadClass() 的核心逻辑（流程控制）：

为什么需要双亲委派（三个理由）：

  1. 安全性：java.lang.String 必须由 Bootstrap 加载。如果没有委派，应用可以自定义一个恶意 java.lang.String 顶替核心类；有了委派，所有 java.* 类最终都回到 Bootstrap，杜绝篡改。
  2. 避免重复加载：同一个类在 JVM 中”类全名 + 加载它的类加载器”共同决定唯一性。委派保证应用里的类都落到同一个加载链上，不会出现”两个一模一样的类”互相 instanceof 失败的诡异问题。
  3. 模块化/隔离的基础：虽然委派是”由上而下统一”，但它同时为”由下而上隔离”（容器、OSGi）提供了扩展点。

双亲委派的缺点/局限：父加载器加载不了”只对子加载器可见”的类——这正是 SPI 和 Web 容器场景需要打破它的原因。

如何打破双亲委派（四种方式）：

  1. **重写 loadClass()**：直接改流程控制，先自己加载、失败再委派（或反之）。
  2. 线程上下文类加载器（TCCL）：用于 SPI（JDBC、JNDI 等），见 3.4。
  3. 容器类加载器：Tomcat 的 WebAppClassLoader 就是典型——为了”每个 Web 应用能加载自己 WEB-INF/classes 和 WEB-INF/lib 里不同版本的类”，它把顺序颠倒过来：先看自己是否已加载，再尝试自己加载（应用类），找不到才委派父加载器；但 java.* 等 JVM 核心类仍然强制先委派父类，避免破坏基础库。
  4. OSGi / 模块化框架：每个 bundle 一个类加载器，完全自定义加载顺序（类可以依赖声明关系加载）。

loadClass() 和 findClass() 的区别（高频题）：

特性 loadClass() findClass()
职责 控制加载流程（委派机制） 实现具体加载逻辑（读字节流、defineClass）
重写必要性 通常不重写（保持委派模型） 自定义类加载器时必须重写
双亲委派角色 实现委派逻辑 被委派机制调用（父加载失败后才调用）
典型用途 类加载入口 自定义类加载器扩展资源获取方式

面试怎么答：先讲流程（findLoadedClass → 父加载器递归 → 自己 findClass），再答”为什么”（安全 + 不重复加载），最后主动给”打破”的两种标准答案——重写 loadClass 和线程上下文类加载器，并举 Tomcat 的例子说明”为什么需要打破”（应用隔离）。

3.4 线程上下文类加载器

问题背景：双亲委派是”父优先”，但存在一类场景反过来——由高层（父加载器加载的）代码去加载低层（子加载器才可见）的实现类。典型是 JDBC：

  • DriverManager 在 java.base 模块里，由 Bootstrap 加载；
  • MySQL 驱动 com.mysql.cj.jdbc.Driver 在应用的 classpath 里，只有 Application 类加载器（App ClassLoader）能找到；
  • Bootstrap 按双亲委派永远委派不到 App ClassLoader（委派方向是向下的，找不到就放弃）。

解决方案：线程上下文类加载器（Thread Context ClassLoader）

  • 每个线程有一个 contextClassLoader（默认继承父线程的，初始默认是 App ClassLoader）；
  • 高层代码拿不到低层实现时，通过 Thread.currentThread().getContextClassLoader() **反过来借用”当前线程的类加载器”**去加载实现类；
  • 这就是 SPI（Service Provider Interface） 机制的基石：JDBC、JNDI、JAXP、JMS 等所有”核心 API 在 JDK、实现由厂商提供”的标准接口，都靠它工作。
  • 调用链：DriverManager.getConnection() → Class.forName(driverClass, true, Thread.currentThread().getContextClassLoader())。JDBC 4.0 之后靠 META-INF/services/java.sql.Driver 自动发现驱动，ServiceLoader 同样借助上下文加载器完成加载。

面试怎么答：一句话点破本质——“双亲委派是向下委派，SPI 需要向上借用，所以引入了线程上下文类加载器”；再举 JDBC 的例子（Bootstrap 加载的 DriverManager 要用 App 加载器加载 MySQL 驱动），最后提一句 Tomcat 和 JDK 9+ 模块化后该机制依旧存在（java.sql 模块在 Platform 层，驱动仍在 classpath）。

4. 垃圾回收

为什么需要了解：GC 是 JVM 面试的重灾区——从”对象怎么算死”到”谁负责收”再到”怎么调”，层层递进。面试官问 GC 的潜台词是：你能不能定位线上停顿/OOM 问题，而不只是背名词。

4.1 如何判断对象已死

引用计数法

每个对象维护一个计数器，被引用 +1，引用失效 -1，计数为 0 即回收。简单高效，但无法解决循环引用：

这就像两个已经没人要的东西互相”抱着取暖”，谁都不敢收。因此主流 JVM（HotSpot）都不用它，改用可达性分析。

可达性分析

从一组称为 GC Roots 的根对象出发，沿引用链向下搜索，不可达的对象即为垃圾。GC Roots 包括：

GC Roots 来源 说明
虚拟机栈中引用的对象 栈帧局部变量表、操作数栈里的引用（正在执行的方法局部变量）
本地方法栈中引用的对象 JNI 引用的对象
元空间/方法区中静态属性引用的对象 static 变量（如 static Map 缓存——这就是静态缓存泄漏时它”永垂不朽”的原因）
元空间/方法区中常量引用的对象 常量池里的引用（如被 intern() 驻留的字符串）
被 synchronized 持有锁的对象 monitor 关联的对象
活跃线程（Thread）对象 所有未被 stop 的线程
JVM 内部引用 基本类型包装类缓存（IntegerCache）、常驻异常对象（NullPointerException 等）、系统类加载器加载的类等

两次标记与 finalize() 的废弃

宣告一个对象真正死亡，在历史上要经过两次标记：

  1. 第一次标记：从 GC Roots 出发，不可达的对象被标记，若其重写且未执行过 finalize()，被放入 F-Queue 队列；
  2. 第二次标记：JVM 用低优先级 Finalizer 线程执行 F-Queue 中的 finalize()，如果对象在方法中把自己重新赋值给某个引用（”自救”），就会被移出队列存活下来；否则彻底死亡。每个对象的 finalize() 只会执行一次。

为什么要废弃 finalize()（JDK 9 起弃用，JDK 18 经 JEP 421 进一步标记移除）：

  • 执行时机不确定：对象”死亡”到 finalize() 执行之间可能隔很久，资源迟迟不释放；
  • 性能差：Finalizer 线程 + F-Queue 队列带来额外开销，重写 finalize 的对象回收变慢；
  • “自救”反模式：能复活对象听起来酷，但会导致对象被反复回收、行为不可预测；
  • 替代方案：try-with-resources（确定性释放）和 **java.lang.ref.Cleaner**（JDK 9 引入，基于虚引用实现，DirectByteBuffer 清理堆外内存就是用它）。

四种引用类型

引用类型 回收时机 用途 实现类
强引用 永不回收（OOM 也不收） 日常 new 的对象；静态集合缓存不清理就会泄漏 Object
软引用（SoftReference） 内存不足、OOM 之前回收 内存敏感缓存：能利用内存就留着，内存紧张自动释放 SoftReference
弱引用（WeakReference） 下一次 GC 即回收（不管内存够不够） WeakHashMap（键是弱引用）、ThreadLocalMap 的 key WeakReference
虚引用（PhantomReference） 回收后通知（get() 恒为 null，无法用它取对象） 跟踪对象回收时机：堆外内存清理（DirectByteBuffer + Cleaner） PhantomReference

三个必答细节：

  1. 软引用的版本差异：JDK 8 及以前按”最近一次 GC 后存活时间”判定（-XX:SoftRefLRUPolicyMSPerMB，默认 1000ms/MB）；JDK 9 起改为基于堆使用率——堆使用率低于 50% 时软引用对象不回收，该参数不再生效。
  2. **虚引用必须配合 ReferenceQueue**：对象被回收后，虚引用会被放入队列，清理线程从队列取出引用，知道”对象死了”，再去释放关联的堆外资源。DirectByteBuffer 本身只有几十字节，但它关联的堆外内存可能很大——JVM 靠 Cleaner（内部是 PhantomReference）在 DirectByteBuffer 回收时调用 unsafe.freeMemory 释放堆外内存。
  3. ThreadLocal 泄漏的引用层面解释：ThreadLocalMap 的 key（ThreadLocal 本身）是弱引用，但 value 是强引用——所以线程池中长期存活的线程里，ThreadLocal 用完不 remove()，value 就永远被强引用着（key 变 null 也没用），这就是经典泄漏点。

面试怎么答：引用计数法一句话带过（”有循环引用问题，所以不用”）；可达性分析讲清 GC Roots 的 6~7 类来源；四种引用按”回收时机 + 用途”讲，务必带出虚引用的实际案例（DirectByteBuffer 堆外内存）；最后主动说”finalize 已废弃，JDK 9 弃用、JEP 421 标记移除，现在用 Cleaner 和 try-with-resources”。

4.2 垃圾收集算法

漫画式理解三种基本算法（讲给面试官听，比背定义生动得多）：

🗑️ 标记-清除（Mark-Sweep）：像整理旧书架——先把要留下的书一本本贴上标签（标记），然后把没贴标签的统统扔进垃圾桶（清除）。问题在于：扔完书之后，书架上空出来的位置东一块西一块（内存碎片），下次想放一套大百科（大对象）时，可能找不到连续的空间——单个空位加起来够大，但拼不成一整块。

📦 标记-复制（Copying）：干脆把房间一分为二，平时只用一半。要打扫时，把幸存的东西全部搬到另一半，然后把这一半直接清空（顺便全屋无碎片，因为搬过来的时候是紧挨着摆的）。缺点很明显：一半房间常年空着（空间利用率 50%）。新生代把它改良成 8:1:1，只浪费 10%，而且幸存对象本来就少，搬起来快——完美契合”朝生夕死”。

🚚 标记-整理（Mark-Compact）：把幸存的书一本一本往墙根推，全部挤得整整齐齐，腾出一整块连续空间。解决了碎片问题，代价是搬运很慢（所有存活对象都要移动）。适合”幸存者多”的区域——老年代。

对比表：

算法 步骤 优点 缺点 适用场景
标记-清除 标记存活 → 清除垃圾 实现简单、不移动对象 内存碎片；标记/清除两次扫描 CMS 的老年代（配合”碎片整理”兜底）
标记-复制 存活对象复制到空闲区 → 整区清空 无碎片、分配只动指针、回收快 浪费空间（需要一块空区） 新生代（8:1:1 只浪费 10%）
标记-整理 标记存活 → 向一端移动 → 清边界外 无碎片、适合存活率高的区域 移动对象成本高、停顿长 老年代（Serial Old、Parallel Old）

分代收集（为什么这样设计）：基于两个经验假说——弱分代假说（绝大多数对象朝生夕死）和强分代假说（熬过多次 GC 的对象更可能继续存活）。于是：新生代存活率低 → 复制算法，快、无碎片；老年代存活率高 → 标记-清除/标记-整理，避免反复搬运。不同区域用不同算法，整体效率最高——这就是分代收集的全部理由。G1 之后的收集器在物理上不再连续分代，但”把存活率不同的对象分开处理”的思想没变（Region 逻辑分代）。

面试怎么答：先画漫画（三个比喻），再落到对比表，最后一句升华：”分代收集不是一种算法，而是’把对象按存活概率分组，各组用最合适的算法’的工程策略。”把”复制算法只浪费 10% 而不是 50%”讲出来，就能体现你看过源码而非背过八股。

注意：Parallel Scavenge 与其他收集器不同，它关注”吞吐量”（吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC 时间)），而不是停顿时间——这是它和 CMS/G1 的定位分野。

CMS：四个阶段详解、优缺点、为什么被废弃

CMS（Concurrent Mark Sweep）是 JDK 5 引入的第一款真正并发的老年代收集器，目标：最短停顿时间（互联网应用优先响应速度）。基于标记-清除算法，回收分 4 个阶段：

  1. 初始标记（Initial Mark，STW）：只标记 GC Roots 直接关联的对象。速度极快，停顿很短。
  2. 并发标记（Concurrent Mark）：从初始标记的对象出发，与用户线程并发做可达性分析，标记所有存活对象。不 STW，但会抢占 CPU。
  3. 重新标记（Remark，STW）：修正并发标记期间用户线程运行导致的引用变化（用增量更新 Incremental Update 记录新引用）。停顿比初始标记长。
  4. 并发清除（Concurrent Sweep）：与用户线程并发清理垃圾、回收内存。

优点：只有初始标记和重新标记两个短暂 STW，整体停顿低。

缺点（为什么最终被 G1 取代）：

  • 内存碎片：标记-清除不整理内存，长时间运行产生大量碎片，大对象无法分配时提前触发 Full GC；
  • 占用 CPU：并发阶段抢占 CPU（默认并发线程数 = (CPU核数+3)/4），CPU 核数少时吞吐量明显下降；
  • 浮动垃圾：并发标记/清除期间新产生的垃圾只能等下次回收，必须预留空间（默认老年代用到 -XX:CMSInitiatingOccupancyFraction=92% 就触发 CMS，留 8% 给浮动垃圾）；
  • Concurrent Mode Failure：并发清除期间老年代空间不足，CMS 退化为 Serial Old 单线程 Full GC（标记-整理），停顿时间极长——CMS 最怕的灾难场景；
  • 版本路线：JDK 9（JEP 291）标记弃用，JDK 14（JEP 363）正式移除。经典参数 -XX:+UseConcMarkSweepGC 已不存在。

G1：Region 布局、Young GC / Mixed GC / Full GC、RSet 和 SATB

G1（Garbage First）是 JDK 7u4 正式提供、JDK 9（JEP 248）起成为默认收集器，目标：在可预测的停顿时间内完成回收，是 CMS 的官方继任者。

Region 化堆布局：把整个堆划分为约 2048 个大小相等、逻辑连续的 Region（默认 1MB~32MB，-XX:G1HeapRegionSize 指定）。每个 Region 运行期动态扮演 Eden / Survivor / Old 角色——物理上不再连续分代，逻辑上仍分代。超过 Region 一半大小的对象放入 Humongous Region（大对象区），避免大对象在 Region 间复制。

回收过程：

  1. Young GC（STW）：回收所有 Eden + Survivor Region，存活对象复制到新的 Survivor Region，熬过阈值的晋升到 Old Region。Eden Region 越多，耗时越长。
  2. 并发标记（Concurrent Marking）：与用户线程并发标记全堆存活对象，为 Mixed GC 做准备。
  3. Mixed GC（STW）：只回收”垃圾占比最高、回收收益最大”的老年代 Region——这就是 “Garbage First” 的含义——而不是回收整个老年代，从而把停顿控制在目标内。回收对象按”收益/成本”排序，取性价比最高的集合。
  4. Full GC（兜底）：并发标记失败或 Humongous 分配失败时，退化为单线程 Full GC（标记-整理），停顿极长，应尽量避免（大堆上 G1 的 Full GC 通常意味着 OOM 前的信号）。

两个关键数据结构（G1 的精华考点）：

  • RSet（Remembered Set，记忆集）：记录”其他 Region 对当前 Region 的引用“。回收某个 Region 时只需扫描它的 RSet，就能知道”谁引用了我”，避免回收时全堆扫描（尤其是”收集新生代时要扫整个老年代”这个代价）。由写屏障（Write Barrier）在引用写入时维护，代价是额外的写操作开销（Card Table 精化）。
  • SATB（Snapshot-At-The-Beginning，起始快照）：并发标记基于”GC 开始时的堆快照“工作，通过 pre-write 屏障记录并发期间”被覆盖的旧引用值”——这样即使并发期间对象被重新引用，也不会被误判为垃圾。相比 CMS 的增量更新（记录新值、重新标记时要重新扫描根），SATB 更保守，停顿更可预测。

停顿模型：-XX:MaxGCPauseMillis（默认 200ms）给出停顿目标，G1 后台统计每个 Region 的回收耗时与收益，每次 Mixed GC 按性价比挑选 Region 集合，使总停顿贴近目标（软实时）。

为什么 G1 取代 CMS：停顿可预测（Region 增量回收 vs CMS 无法控制停顿）；无碎片（复制/整理回收）；支持超大堆（TB 级，RSet 避免全堆扫描）；SATB + RSet 的正确性机制比 CMS 增量更新更完善。

简要：ZGC 和 Shenandoah

收集器 版本路线 核心机制 解决什么问题
ZGC JDK 11 实验（JEP 333），JDK 15 生产可用（JEP 377） 着色指针（Colored Pointers）：64 位指针的高位存 4 位元数据（标记位、重映射位等）+ 读屏障；并发移动对象（并发整理） 停顿时间与堆大小无关：无论 4G 还是 16TB 堆，停顿都小于 1ms，且支持超大堆
Shenandoah JDK 12 实验（JEP 189），JDK 15 生产可用（JEP 379） Brooks 转发指针 + 读屏障：对象移动时在原位置留一个”指向新家的路标” 同样实现低停顿 + 并发整理；Red Hat 主导，被阿里云等大规模落地

两者与 G1 的本质区别：回收（甚至整理、移动对象）全程与用户线程并发，几乎不需要 STW，把停顿从”几十毫秒”压到”亚毫秒”。它们共同的代价是读屏障带来的访问开销（每次访问对象都要多一次判断）。

快速判断健康度的口诀：Minor GC 频繁但堆用量回收后回不到低位 → 对象分配太快或新生代太小；Full GC 频繁且回收量小 → 老年代有存活对象堆积（内存泄漏的特征：FGCT 只涨不降）；GC 停顿超预期 → 看是堆太大、晋升太多还是收集器选择问题。

调优思路（不是调参数本身，而是”先确认目标，再选收集器，最后微调参数”）：

  1. 确认目标：要延迟（响应时间敏感，如在线交易）还是要吞吐（后台批处理）？堆内存在多大范围（64 位服务器上大堆常见）？
  2. 选收集器：JDK 8 默认 Parallel（吞吐）；延迟敏感换 G1（-XX:+UseG1GC）；大堆 + 亚毫秒停顿上 ZGC（-XX:+UseZGC）；小堆小机器 Serial 反而更好。

面试怎么答：参数能精确说出”-XX:+UseG1GC、-XX:MaxGCPauseMillis=200、-XX:InitiatingHeapOccupancyPercent=45“；日志能当场拆解一行（前 → 后 → 总容量 → 耗时）；调优背出”目标 → 选收集器 → 微调”的顺序，并强调”-Xms 与 -Xmx 相等、一次只改一个参数”的工程纪律。

6. 性能指标与调优方法论

为什么需要了解：调优不是”把参数调得好看”，而是”让系统达到业务要求的性能”。不理解 RT/TPS 这些指标，就没有量化目标；不会压测，就不知道系统真实容量。这一章先把”指标 → 目标 → 压测验证”的闭环补齐，第 7 章的实战案例全部建立在这套方法论上。

6.1 RT、TPS、QPS、并发数——四个核心指标

RT（Response Time，响应时间）：一个请求从发出到收到完整响应的时间。两个要点：

  • 看分位值而不是平均值：平均 RT 会被长尾请求严重污染——1% 的请求耗时 5s，其余 99% 只要 10ms，平均值也会被拉到 60ms 左右，完全反映不了真实体验。业界看 p95 / p99 / p999（95%/99%/99.9% 的请求分别在多少毫秒内完成），压测报告里”avg=45ms, p99=180ms”比”avg=45ms”信息量大得多。
  • RT 要分段定位：全链路 RT = 网络 + 网关 + 应用 + DB/缓存 + 下游。调优前先用 traceId/日志把耗时拆开，90% 的”接口慢”慢在 DB 或下游，而不是 JVM——别一上来就调 GC。

TPS（Transactions Per Second，每秒事务数）：每秒完成多少笔业务事务。强调”事务”是有业务语义的完整操作（一次下单 = 校验 + 扣库存 + 建订单），不是单条 SQL，也不是单个 HTTP 请求。

QPS（Queries Per Second，每秒查询数）：每秒完成的读请求数。实践中 QPS 常被泛化为”每秒请求数”（含读含写），与 TPS 混用也没关系——面试讲清楚”TPS 强调事务完整性，QPS 强调请求吞吐“即可。

并发数（Concurrency）：同一时刻在途（已发出、未返回）的请求数，也就是系统同时处理的请求总数。注意它不等于”线程数”——同步模型下一个线程处理一个在途请求，异步模型下（NIO、协程）一个线程可以同时驱动多个在途请求。

四个指标之间的关系（Little 定律）：

并发数 = TPS × RT

这是排队论 Little 定律的直接应用：系统每秒完成 1000 个事务、每个事务耗时 100ms，则在途请求数 = 1000 × 0.1 = 100。反过来可反推容量：

RT 目标 TPS 需要的并发数
50ms 10,000 500
100ms 5,000 500
100ms 10,000 1,000
200ms 10,000 2,000

两个经典用法：

  1. 估算容量：目标 QPS 10000、压测测得 RT 100ms → 至少需要 1000 个并发槽位（线程池/连接池的配置参考）。
  2. 判断瓶颈：RT 不变、TPS 不再随并发上升 → 已到系统极限；TPS 下降、RT 暴涨 → 某个环节开始排队（线程池打满、连接池耗尽、GC 停顿），要找瓶颈而不是盲目加线程。

面试怎么答：先报四个定义，再主动给出 Little 定律公式和一个换算例子（”目标 QPS 1 万、RT 100ms，并发就是 1000”），最后补一句”平均 RT 没有意义，看 p99”——公式 + 分位数意识都拿出来，这题就完整了。

6.2 3S 定理（Speed、Scalability、Stability）

性能测试的三个维度，简称 3S：

维度 含义 怎么验证
Speed（性能） 单机/单实例的处理能力：RT 与吞吐（TPS） 单机压测，确认 RT 分位值与最大 TPS
Scalability（可扩展性） 加机器，吞吐能否近似线性增长 1 台 → 2 台 → 4 台压测，画吞吐增长曲线
Stability（稳定性） 长时间运行（72h+）后性能不退化、资源水位稳定 长稳压测：观察 GC、内存、线程、连接池水位

三个维度有优先级：先单机性能（Speed）打底，再验证水平扩展（Scalability），最后长稳（Stability）兜底。每个维度都有一个经典翻车案例：

  • 扩展性失败：1 台机器 TPS 1000，4 台只有 2000 而不是 4000——瓶颈在共享资源（DB 连接数、Redis 带宽、分布式锁、热点数据），这就是”加了机器没效果”的真相；
  • 稳定性失败：压测 12 小时后 TPS 逐步下滑——典型是泄漏：内存泄漏（老年代持续增长）、线程池泄漏（活跃线程只增不降）、连接池泄漏（连接数涨满）。

面试怎么答：3S 三个词 + 一句话”先单机性能、再扩展性、后稳定性”，并各举一个翻车案例（加机器吞吐不翻倍 → 查共享资源；长时间压测吞吐下降 → 查泄漏），比单纯背缩写打动人。

6.3 梯度压测（200 → 500 → 1000 → 2000 → 5000）

为什么用梯度：一上来直接上高并发，系统直接雪崩，什么信息都拿不到。梯度压测的意义是**找到”拐点”**——吞吐不再随并发上升、甚至开始下降的那个点，它定义了系统的真实容量。

标准流程：

  1. 冒烟压测：小并发（如 200）跑通链路，确认功能与监控正常；
  2. 梯度加压：200 → 500 → 1000 → 2000 → 5000 线程逐档施压，每档持续 3~5 分钟（让系统进入稳态），逐档记录 TPS、RT 分位、错误率；
  3. 找拐点：TPS 曲线从”线性上升”转为”走平或下降”的那一档就是容量上限——继续加压只会让 RT 恶化、错误率飙升；
  4. 资源画像：每档同步观察 CPU、内存、GC、线程池活跃线程、DB 连接池、MQ 积压，定位瓶颈环节；
  5. 结论输出：给出”最大支撑 TPS、对应 RT p99、瓶颈在 X”，并预留 30%~50% 余量作为生产容量目标——压测极限值直接当线上水位，一个抖动就挂了。

典型拐点场景：

现象 瓶颈
TPS 走平但 RT 缓慢上升，CPU 已打满 计算密集：应用线程/GC 是瓶颈
TPS 走平，活跃线程数打满，RT 陡增 同步阻塞：下游（DB/接口）慢，线程在等
TPS 下降，GC 停顿变长，老年代持续上升 内存问题：晋升过快、泄漏
错误率突然升高，大量超时 达到某资源上限（连接池耗尽、限流阈值）

面试怎么答：讲”梯度 + 拐点 + 余量”三件事——“从 200 逐档加到 5000，每档记录 TPS 和 RT 分位，找到吞吐拐点，按拐点值预留 30~50% 作为容量目标”，再补一句”拐点通常对应一个具体瓶颈（线程池/连接池/GC），压测的目的就是把它找出来”。

6.4 压测工具简介（JMeter / wrk / ab）

工具 特点 适用场景
JMeter GUI 配置测试计划，线程组/定时器/断言/聚合报告插件丰富，支持分布式压测（主控 + 多台施压机） 完整链路压测、接口回归、需要断言与报表的正式压测
wrk 单机轻量、基于 epoll 多路复用，C 编写，施压机资源占用极低，自带 RT 分位统计（--latency） 单接口高并发快速压测（网关、单服务）
ab（Apache Bench） 最简单：-n 请求总数 + -c 并发数，一条命令出结果 冒烟验证、快速看个大概

压测的三个纪律：

  1. 施压机与目标机分离：施压机资源不够会先把自己压垮，结果失真；并发大时用多台施压机 + JMeter 分布式；
  2. 并发模型要匹配：wrk/ab 的并发是”连接并发”，JMeter 的线程组是”线程并发”，换工具换模型，数字不能直接对比；
  3. 压测要带真实依赖：单接口 → 核心链路（混合比例）→ 全链路，全链路必须带真实的 DB/缓存/下游，否则测出的容量和线上无关。

面试怎么答：三个工具各一句——“ab 冒烟、wrk 单接口高并发、JMeter 全链路带断言报表”，再强调”施压机和目标机分离、压测要带真实下游依赖”，工具题就过关了。

7. 调优实战案例

为什么需要了解：前面讲的是”是什么、怎么看”，这一章讲”怎么调”。三个案例覆盖三大典型诉求——吞吐量优先（后台批处理）、响应时间优先（在线接口）、稳定性优先（死锁排查），每个案例都遵循第 6 章的方法论：先定目标 → 选收集器 → 参数微调 → 用日志和监控验证。

7.1 吞吐量优先案例（Parallel Scavenge + Parallel Old）

场景描述：后台批处理服务，每天凌晨跑全量报表生成与积分批量计算，运行窗口 2 小时。业务要求：在窗口期内跑完所有任务，单位时间处理量（吞吐）越高越好；单次 GC 停顿允许达到秒级（没有人等着它）。堆内存 8G（-Xms8g -Xmx8g），JDK 8。

选型：Parallel Scavenge + Parallel Old（-XX:+UseParallelGC）。JDK 8 默认组合，多线程并行回收、不追求低停顿，正是”高吞吐 + 容忍停顿”场景的标准答案。依据是吞吐量公式：

吞吐量 = 用户代码运行时间 /（用户代码运行时间 + GC 时间）
Parallel 的目标是让 GC 时间占比尽量小，而不是让单次停顿尽量短——这是它与 CMS/G1 的分野。

关键参数：

参数 作用 本案例取值
-XX:+UseParallelGC 选用 Parallel Scavenge + Parallel Old 必选
-Xmn4g 新生代 4G（案例关键：批处理产生大量”朝生夕死”对象） 4g
-XX:MaxGCPauseMillis=500 停顿目标（配合自适应策略调整堆布局） 500ms
-XX:GCTimeRatio=19 吞吐目标：GC 时间占比 ≤ 1/(1+19) = 5% 19

调优过程（GC 日志前后对比）：

优化前（默认配置，新生代被自适应策略压缩到约 260M，老年代被撑到 96%+）：

问题解读：Full GC 每 5 分钟一次、每次 3 秒以上，回收量却极小（老年代回收后几乎不降）——不是”垃圾多”，而是老年代里全是还活着的批处理对象。大量本应在新生代就死掉的对象因为新生代太小被过早晋升，把老年代撑满，Full GC 变成”定时打卡”，吞吐损失惨重。

优化后（-Xmn4g 扩大新生代，GCTimeRatio=19）：

解读：新生代扩到 4G 后，绝大多数临时对象死在新生代（回收后堆从 4.4G 降到 700M，老年代仅约 250M），只剩 0.18 秒的 Minor GC，Full GC 归零。总 GC 时间从”每小时约 36 秒 + 每 5 分钟一次 3 秒的 Full GC”降到”每小时约 20 秒纯 Minor GC”，报表窗口期提前 25 分钟跑完。

jstat 监控输出与分析：

分析要点：优化后 FGC 列恒为 0、FGCT 不再增长，O 列稳定在 40% 上下——晋升速度与处理速度匹配，系统进入良性循环。FGCT 只涨不降 + O 列居高不下，永远是 Full GC 问题的第一诊断信号（呼应第 6 章的泄漏排查）。

小结：吞吐优先场景三板斧——① 选 Parallel 系；② 把新生代调大，让”朝生夕死”的对象死在新生代；③ 用 GCTimeRatio 明确吞吐目标。判断吞吐调优是否成功，看 FGCT 增速和窗口期总时长，而不是看单次停顿。

7.2 响应时间优先案例（G1）

场景描述：交易查询接口服务，对外 SLA 是 p99 < 500ms。流量 24 小时持续，峰值 3000 QPS，堆 8G。业务要求：任何请求都不能被长 GC 停顿”惩罚”——接口超时的直接损失是上游重试和用户流失。

选型：G1（-XX:+UseG1GC）。理由：可预测停顿模型（Region 增量回收 + 停顿目标），用”吞吐略降”换”停顿可控”，正对响应时间敏感的在线服务。JDK 9+ 默认即 G1，JDK 8 需显式开启。

关键参数：

参数 作用 本案例取值
-XX:+UseG1GC 启用 G1 必选
-XX:MaxGCPauseMillis=200 停顿目标：单次 GC 尽量 ≤ 200ms 200
-XX:InitiatingHeapOccupancyPercent=45 堆使用率达 45% 即启动并发标记（为 Mixed GC 备料） 45
-XX:G1HeapRegionSize Region 大小（默认自动；大对象多时可显式设 8m/16m） 自动

调优过程（Parallel → G1 的 GC 暂停时间对比）：

指标 优化前（Parallel + Parallel Old） 优化后（G1）
单次 Young GC ~80ms ~50ms
偶发 Full GC 每 23 天一次，**25 秒**，期间接口集体超时 无（Mixed GC 兜底，峰值 ~180ms）
p99 RT 峰值时段 800ms~1.2s（被 Full GC 污染） 稳定 < 300ms
接口超时率 峰值时段 0.5%~1% < 0.01%

为什么 G1 能把停顿压住：Full GC 是 G1 的灾难（单线程标记-整理），正常的 GC 压力被拆成 Young GC + Mixed GC 两路消化——Young GC 只回收 Eden/Survivor Region（快）；Mixed GC 每次只挑”垃圾占比最高的一批老年代 Region”（-XX:G1MixedGCLiveThresholdPercent 控制），把一次大停顿拆成多次小停顿。InitiatingHeapOccupancyPercent=45 意味着堆用到 45% 就开始并发标记、提前为 Mixed GC 备好料，避免堆被撑满后被迫 Full GC。

G1 调优的两个观察点：

  1. 看停顿分布（GC 日志 -Xlog:gc*）：停顿是否逼近 MaxGCPauseMillis；Young GC 停顿超标，说明 Eden Region 太多（调小 -XX:G1NewSizePercent）或晋升量大、复制耗时大；
  2. 看 Mixed GC 周期：GC 日志出现频繁的 to-space exhausted（复制目标空间不足）或 Evacuation Failure，说明回收速度赶不上分配速度——调高 InitiatingHeapOccupancyPercent 提前启动标记，或调大堆。

小结：响应时间优先场景三板斧——① 选 G1；② MaxGCPauseMillis 定停顿目标；③ InitiatingHeapOccupancyPercent 提前备料，让 GC 压力”日常消化”，不给 Full GC 登场的机会。切换收集器后必须用日志验证停顿分布，不是切了就完事。

7.3 死锁排查完整案例（jstack + Arthas）

场景描述：订单服务线上偶发”部分请求永久卡死”——不超时、不报错，每个卡死的请求占用一个线程且不释放，线程数只涨不降，最终打满线程池导致服务不可用。重启恢复，几小时后复发。经典死锁特征：请求不是变慢，而是永远等不到。

第一步：构造死锁 demo（复现现场）

第二步：第一次 jstack 采样

解读 “Found one Java-level deadlock”：jstack 会遍历所有线程的 monitor 持有/等待关系，自动发现锁等待环（A 等的锁被 B 持有、B 等的锁被 A 持有）并直接打印死锁链。看到这段输出就是死锁实锤。两个关键信息：

  • waiting to lock <对象地址> 与 locked <对象地址>：每个线程在等哪把锁、持有哪把锁，环一眼画出来；
  • 栈顶方法（DeadlockDemo.java:11 / :22）：死锁发生在哪两行代码，直接定位到业务代码。

第三步：第二次 jstack 采样（对比确认）

为什么必须采两次：单次采样只能说明”此刻有两个线程在互相等待”——也许是瞬时竞争，下一秒就结束了。死锁是持久的：30 秒后再次采样，同一对线程还阻塞在同一对锁上、栈顶方法完全一样，才能确认是死锁而不是偶发阻塞。对比两份 dump 重点看三点：① 线程名一致；② 锁对象地址一致；③ 栈顶方法一致。

第四步：Arthas thread -b 确认

thread -b（blocked thread）直接找出阻塞其他线程的锁与持有者，一条命令定位死锁环；配合 dashboard 能看到两个线程 BLOCKED 状态卡死不动。

局限提醒：jstack 的自动死锁检测只覆盖 synchronized monitor。用 ReentrantLock 等 AQS 锁导致的死锁，线程状态是 WAITING (parking) 而不是 BLOCKED，jstack 通常不会打印 “Found one Java-level deadlock”——这时靠两次采样对比（同一批线程长期 WAITING）+ Arthas thread -b（它会分析 java.util.concurrent 的锁等待关系）来定位。

第五步：修复方案

死锁的根治方向是消除锁等待环，三个方案按推荐度排序：

方案一：统一锁获取顺序（最推荐，根因修复）——所有线程按同一顺序加锁，环不存在：

方案二：tryLock 超时放弃（无法统一顺序时的兜底）——用 ReentrantLock 替换 synchronized，拿不到锁就放弃而不是无限等待：

方案三：消除嵌套锁（结构性修复）——检查两个锁保护的临界区是否真的需要嵌套：能合并成一把锁就合并，能用 CAS/原子类就无锁化，别让加锁顺序成为业务代码的隐性契约。
