在线 DDL：一次加索引如何堵死整张表

Posted on 2026-10-25 In 数据存储 Word count in article: 3.6k Reading time ≈ 13 mins.

DDL 的危险不在「执行慢」，而在「排队等」。一条 ALTER TABLE 本身可能只要 3 秒，但它会先在 MDL 队列里排一个 EXCLUSIVE 请求；后面的所有查询——包括普通 SELECT——都会排在它后面。于是「3 秒的变更」变成「3 分钟的故障」。

本文用 200 万行、106MB 的表把这件事量成数字：7 种 DDL 的耗时、哪些会让写入阻塞、阻塞多久。实测最有说服力的一组对比是：ADD INDEX 期间插入 0.05 秒完成（在线），MODIFY COLUMN 触发的 COPY 重建期间插入等了 3.62 秒（锁表）。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁 → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL（本文） → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

1. DDL 的三种执行方式

1.1 COPY / INPLACE / INSTANT

flowchart LR
    subgraph COPY["COPY (rebuild + lock)"]
        C1["create temp table"] --> C2["copy all rows"] --> C3["rename, drop old"]
    end
    subgraph INPLACE["INPLACE (rebuild, online)"]
        I1["rebuild in place<br/>concurrent DML allowed"] --> I2["apply online log"]
    end
    subgraph INSTANT["INSTANT (metadata only)"]
        N1["change data dictionary"] --> N2["done in ms"]
    end
算法 做什么 并发 DML 耗时量级 典型操作
COPY 建新表、全量拷贝、改名 不允许（默认锁写） 与数据量成正比 改列类型、改字符集、加主键
INPLACE 原地重建或仅改元数据 允许（LOCK=NONE） 与数据量成正比 加/删索引、调整列顺序
INSTANT 只改数据字典 允许 毫秒级，与数据量无关 加列、删列（8.0.29+）、改默认值

1.2 实测：七种 DDL 的真实代价

表：200 万行、106MB，Buffer Pool 1GB，本地 SSD。

DDL 实际算法 耗时 期间写入
ADD COLUMN c1 INT（末尾） INSTANT 0.035 s 不阻塞
ADD COLUMN c2 INT AFTER id INSTANT 0.005 s 不阻塞
DROP COLUMN c1 INSTANT 0.051 s 不阻塞
MODIFY remark VARCHAR(64) → VARCHAR(128) INPLACE（仅元数据） 0.002 s 不阻塞
ADD INDEX idx_user (user_id) INPLACE LOCK=NONE 1.557 s 不阻塞（插入 0.05 s 完成）
MODIFY status TINYINT → SMALLINT COPY（INPLACE 不支持） 3.695 s 阻塞 3.62 s
同上，加 ALGORITHM=COPY 显式 COPY 3.695 s 阻塞

三条能直接拿走的知识：

  1. 加列/删列在 8.0 是毫秒级，而且 8.0.29 之后连「插在中间」也支持 instant（实测 AFTER id 0.005 s）。
  2. 加索引要读全表（1.557 s / 2M 行），但在线，不阻塞写入。
  3. 改列类型绝大多数要 COPY，会锁表——TINYINT → SMALLINT 实测直接报 ALGORITHM=INPLACE is not supported。

1.3 深挖：为什么有些 MODIFY 是 0.002 秒，有些要重建

关键在于存储格式有没有变：

变更 存储格式 结果
VARCHAR(64) → VARCHAR(128)（utf8mb4） 两者都是 2 字节长度前缀 只改元数据，0.002 s
VARCHAR(64) → VARCHAR(200) 同上 同上，元数据级
TINYINT → SMALLINT 1 字节 → 2 字节 必须重建
utf8mb4 → latin1 字符集变了 必须重建
INT → BIGINT 4 字节 → 8 字节 必须重建

判据：字节宽度或编码变了就要重建；只是「上限放宽但宽度不变」可以只改元数据。所以「改字段长度」在线上是相对安全的，「改字段类型」基本等于重建。

1.4 8.0 instant DDL 的边界

能 INSTANT 不能 INSTANT
在末尾加列 加/删索引
在中间加列（8.0.29+） 改列类型
删列（8.0.29+） 改字符集
改列默认值 改 ROW_FORMAT
重命名列（8.0 起部分支持） 加主键

一个必须知道的限制：instant 加列有上限（每张表最多 64 次 instant 变更），超过之后需要一次重建来「整理」。所以频繁 instant 加列不是无限的。

1.5 动手验证：先探测算法，再执行

预期观察点：加列应在 0.1 秒内完成；MODIFY 类型变更会直接报 1846。

判定标准：

  • 加列超过 1 秒 → 你的实例可能不是 8.0 或表上有不支持 instant 的约束；
  • 报 1846 → 这个变更必须 COPY，按「锁表变更」处理（走 3.2/3.3 的方案）。

2. MDL：一行 ALTER 如何堵住整张表

2.1 队列是 FIFO，不允许插队

flowchart LR
    A["Trx A<br/>SELECT in open transaction<br/>MDL SHARED_READ GRANTED"] --> T["Table big"]
    B["ALTER TABLE<br/>MDL EXCLUSIVE PENDING"] -->|"queued behind A"| T
    C["Session C<br/>plain SELECT<br/>MDL SHARED_READ"] -->|"queued behind B"| T
    C -.->|"blocked, then 1205"| X["timeout"]

MDL 队列不允许后来的读绕过前面的写请求，这是为了防饥饿。代价就是：一个 DDL 在排队，后面所有的读一起排队。

2.2 实测：阻塞链长什么样

会话 A 开事务只做一次 SELECT（持有 SHARED_READ），会话 B 执行 ALTER TABLE big ADD COLUMN note3 ...，然后查 sys.schema_table_lock_waits：

读法：

  • waiting_pid=22 是 ALTER，它要 EXCLUSIVE，被 blocking_pid=21（那个没提交的事务）的 SHARED_READ 挡住；
  • waiting_pid=NULL 的行是还在排队、尚未分配线程 id 的查询（普通 SELECT），它们排在 ALTER 后面。

第三个会话执行普通 SELECT（lock_wait_timeout=2）的实测结果：

一条 SELECT 被一条还没执行的 DDL 挡了 2 秒。如果这个 DDL 因为前面有长事务而排 10 分钟，后面的查询就排 10 分钟。

2.3 深挖：为什么 innodb_lock_wait_timeout=2 没生效

第一节的 COPY 实验里，我把 innodb_lock_wait_timeout 设成 2，插入却等了 3.62 秒才成功（DDL 结束时放行）。原因：

等待类型 受哪个参数控制 默认值
InnoDB 行锁等待 innodb_lock_wait_timeout 50 秒
MDL 等待 lock_wait_timeout 31536000 秒（一年）

COPY 重建时持有表的 MDL EXCLUSIVE，插入要等的是 MDL，不是行锁。所以 innodb_lock_wait_timeout=2 完全不起作用——这就是为什么很多「我设了超时怎么还在卡」的问题找不到原因。

2.4 DDL 前的 Checklist（照着跑）

检查项 阈值 不通过怎么办
长事务 age_s > 5 等它结束或 KILL（注意大事务回滚耗时）
MDL PENDING 任意 停止发新 DDL，等队列清空
算法 是否 INSTANT/INPLACE COPY 必须走变更窗口或 gh-ost
表大小 CPU 估算时间 2M 行约 1.5 s（加索引），按比例外推

2.5 动手验证：复现 MDL 阻塞

预期观察点：C 在 2 秒后返回 ERROR 1205；期间查 sys.schema_table_lock_waits 能看到 A→B→C 的三层排队。

判定标准：

  • C 立即成功 → A 的事务已提交，或 A 用的是自动提交（autocommit=1 的 SELECT 不持有 MDL）；
  • C 报 1205 且 B 一直 PENDING → 这就是线上雪崩的起点，立刻处理 A。

3. 大表变更的三种方案

3.1 原生 DDL 够用吗

场景 原生 DDL 判断
加列/删列 INSTANT，毫秒级 直接用
加索引（几百万行） INPLACE，秒级 直接用，避开业务高峰
加索引（上亿行） INPLACE，分钟~小时 考虑 gh-ost + 低峰窗口
改列类型 COPY，锁表 必须用影子表方案
改字符集 COPY，锁表 必须用影子表方案

3.2 pt-online-schema-change：触发器 + 影子表

sequenceDiagram
    participant App
    participant Orig as orders (original)
    participant Shadow as _orders_new (shadow)
    App->>Orig: normal DML
    Note over Orig,Shadow: step 1 create shadow table with new schema
    Note over Orig,Shadow: step 2 create triggers INSERT/UPDATE/DELETE -> shadow
    Note over Orig,Shadow: step 3 copy old rows in chunks
    App->>Orig: DML also replayed to shadow by triggers
    Note over Orig,Shadow: step 4 RENAME TABLE swap
维度 说明
原理 建影子表 + 三个触发器 + 分批拷贝 + 原子 RENAME
优点 不锁表、支持所有变更类型
风险 触发器带来的额外写入开销；表必须有主键或唯一索引；外键需额外处理
关键参数 --chunk-time、--max-load、--critical-load

3.3 gh-ost：读 binlog，不建触发器

sequenceDiagram
    participant App
    participant Orig as orders
    participant Ghost as _orders_gho
    participant BL as binlog
    App->>Orig: DML
    Orig->>BL: row events
    BL->>Ghost: apply changes (gh-ost reads binlog)
    Note over Ghost: copy rows in chunks, throttled by load
    Note over Orig,Ghost: atomic RENAME at cutover
维度 gh-ost pt-osc
同步机制 读 binlog 回放 触发器
对主库写压力 小（无触发器） 大（每行额外触发器写）
可暂停/限流 支持（throttle） 支持（--max-load）
需要主键 是 是
外键 不支持 需额外处理
适用 大表、写密集 中小表、兼容性更好

诚实标注：本文实测的是原生 DDL（第 1、2 节）。pt-osc 与 gh-ost 未在本文环境实测（工具未安装），上面的对比属于原理与文档知识。上线前请在自己的环境跑一次演练，重点验证「触发器开销」与「cutover 瞬间的锁」。

3.4 变更窗口怎么估

数据量 原生 ADD INDEX 建议窗口 备注
100 万行 ~0.8 s（本文 2M 行 1.557 s 折算） 任意 直接执行
1000 万行 ~8 s 低峰 仍建议低峰，避免 MDL 排到长事务后面
1 亿行 ~80 s + IO 压力 低峰 + 限流 用 gh-ost，可暂停
改列类型 与数据量成正比，且锁表 必须影子表 原生 COPY 会锁写

估算公式：耗时 ≈ 表大小 / 扫描速度，扫描速度受 Buffer Pool、磁盘、并发写影响，实测值只能做数量级参考。

4. 一次 P0 复盘（用本文实测数据拼合）

时刻 事件 现象
T0 运维发起 ALTER TABLE orders ADD INDEX ... DDL 进入 MDL 队列
T0 队列前面有一个未提交的事务（报表导出） DDL 变成 PENDING
T0+5s 应用查询开始变慢 所有 SELECT 排在 DDL 后面
T0+30s 连接池打满 接口大面积超时（⑪ 的因果）
T0+90s DBA 杀掉报表事务 DDL 执行 1.5 秒后完成
T0+95s 业务恢复 累计故障 95 秒

根因：不是 DDL 慢，是「DDL 排在一个长事务后面」，而队列 FIFO 让所有读跟着排队。

处置顺序（可照抄）：

  1. KILL 掉阻塞的事务（先确认不是核心批处理）；
  2. 观察 sys.schema_table_lock_waits 是否清空；
  3. DDL 执行完后确认 metadata_locks 无 PENDING；
  4. 复盘：把 2.4 的 Checklist 写进发布流程，缺一项不许发。

5. 总结

5.1 面试速答表

面试题 一句话答案
DDL 的三种算法 COPY（重建+锁写）、INPLACE（重建但可并发 DML）、INSTANT（只改元数据）
8.0 加列为什么快 INSTANT 只改数据字典，实测 200 万行 0.035 s；8.0.29+ 支持中间插入
加索引会锁表吗 不会，ADD INDEX 是 INPLACE + LOCK=NONE，实测期间插入 0.05 s 完成
改列类型为什么慢 字节宽度变了必须重建，TINYINT→SMALLINT 强制 COPY，实测锁写 3.62 s
VARCHAR(64)→VARCHAR(128) 要重建吗 不用，长度前缀字节数没变，实测元数据级 0.002 s
MDL 是什么 元数据锁，保护表结构；普通 SELECT 也要加 SHARED_READ
为什么一条 SELECT 会被 DDL 挡住 MDL 队列 FIFO，读请求不允许插到等待的 EXCLUSIVE 前面
为什么设了 innodb_lock_wait_timeout 还卡 等的是 MDL，受 lock_wait_timeout 控制（默认一年）
DDL 前必须查什么 长事务 + MDL PENDING + 算法支持情况
gh-ost 和 pt-osc 的区别 gh-ost 读 binlog 回放（无触发器），pt-osc 用触发器同步
instant 加列有上限吗 有，每表最多 64 次 instant 变更，之后需要一次重建

5.2 实战避坑表

症状 原因 处理
DDL 一直 PENDING 不报错 前面有长事务，lock_wait_timeout 默认一年 查 innodb_trx，处理长事务
DDL 一发业务全卡 MDL 队列雪崩 立刻杀掉阻塞事务，恢复后重发
改列类型锁表几分钟 走了 COPY 改用 gh-ost 或低峰执行
ALGORITHM=INPLACE 报 1846 该变更不支持 inplace 按 COPY 处理，评估窗口
加索引后写入变慢 索引写放大（③） 评估是否必要，清理冗余索引
instant 加列失败 超过 64 次上限 做一次重建整理

5.3 工具速查表

工具 看什么 判定标准
ALTER TABLE ... ALGORITHM=... 支持的算法 报 1846 = 只能 COPY
sys.schema_table_lock_waits 谁堵谁 有输出 = 已经开始排队
performance_schema.metadata_locks MDL 明细 有 PENDING = 不能发新 DDL
information_schema.innodb_trx 长事务 age_s > 5 需处理
information_schema.tables 表大小 用来估算 COPY 耗时

5.4 实操建议

  1. 先问「这个变更能不能 INSTANT」。加列/删列在 8.0 就是毫秒级，别用重工具。
  2. DDL 前跑 2.4 的两条查询，把「长事务为零、MDL 无 PENDING」作为发布门禁。
  3. **显式设 lock_wait_timeout**，别让 DDL 无限排队——排队本身就是故障。
  4. 超过 1000 万行的加索引放低峰，1 亿行以上用 gh-ost 并限流。
  5. 改列类型一律视为锁表变更，走影子表方案，不用原生 DDL 赌运气。
