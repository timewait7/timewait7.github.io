第一部分：Spring 全景

1. Spring 概述：IoC 容器解决了什么问题

本节要解决什么问题：Spring 首先是个 IoC 容器——回答”对象的创建与依赖装配为什么不能靠 new”。

1.1 没有 IoC 的日子

传统写法中，对象之间的依赖由调用方直接 new 出来：

这个写法有四个致命问题：

  1. 强耦合：UserService 直接依赖 UserDao 的构造细节，换实现（如从 JDBC 换成 MyBatis、换成 Mock）必须改代码。
  2. 创建顺序敏感：DataSource 的初始化参数一旦变化，所有依赖它的对象都要跟着改。
  3. 难以单测：无法把 Mock 对象塞进去，测试只能打真实数据库。
  4. 生命周期无人管理：谁负责释放连接？谁保证全应用只有一个 DataSource 实例？

1.2 控制反转与依赖注入

IoC（Inversion of Control，控制反转）：把”对象的创建与装配”这一控制权从调用方手里反转给容器。调用方不再 new，而是声明”我需要什么”，容器负责创建并送上门。

DI（Dependency Injection，依赖注入）：IoC 的一种实现方式——容器在创建 Bean 时，把它的依赖通过构造器、Setter 或字段注入进去。面试中两者常被混用，严格说 DI 是 IoC 的具体落地手段。

容器侧只需声明一次装配规则：

flowchart TB
    subgraph Traditional[传统 new 方式]
        US1[UserService] -->|直接 new| UD1[UserDao]
        UD1 -->|直接 new| DS1[DataSource]
    end

    subgraph IoC[IoC 容器方式]
        Container[IoC 容器] -->|创建 + 注入| US2[UserService]
        Container -->|创建 + 注入| UD2[UserDao]
        Container -->|创建| DS2[DataSource]
        US2 -.->|声明依赖| UD2
        UD2 -.->|声明依赖| DS2
    end

1.3 为什么需要 DI

  • 解耦：面向接口编程，替换实现（Redis 换本地缓存、MySQL 换 PG）只改配置不改业务代码。
  • 可测试性：测试时注入 Mock 依赖，无需起真实服务。
  • 集中管理生命周期：单例、原型、请求作用域等由容器统一管理，连接池等资源有统一的释放时机。
  • 可替换性：同类型多个 Bean 时用 @Primary / @Qualifier 声明优先与选择规则。

**一句话回答面试题”Spring 是什么”**：Spring 是一个 IoC 容器（管理对象的创建与依赖）+ AOP 框架（实现横切逻辑复用），并在此基础上构建了 MVC、事务管理、数据访问、消息等一整套生态；Spring Boot 则在框架之上提供了”约定优于配置”的自动装配能力。

第二部分：IoC 容器深度解析

3. IoC 容器与 Bean 生命周期

本节要解决什么问题：容器拿到一个类的声明之后，是如何把它变成一个可用的 Bean 的？Bean 的一生有几个关键节点？开发者能在哪些节点插手？

3.1 BeanFactory 与 ApplicationContext

维度 BeanFactory ApplicationContext
定位 最底层容器，提供最基础的 getBean 能力 BeanFactory 的子接口，增强版容器（超集）
实例化时机 懒加载：getBean 时才创建单例 预加载：启动 refresh() 时创建大部分单例（可用 @Lazy 关闭）
自动注册后处理器 不自动注册 BeanPostProcessor 启动时自动注册（如 AutowiredAnnotationBeanPostProcessor），所以 @Autowired 在 ApplicationContext 下开箱即用
额外能力 无 事件发布（ApplicationEventPublisher）、国际化（MessageSource）、资源加载（ResourceLoader）、环境抽象（Environment）、AOP 自动配置
典型实现 DefaultListableBeanFactory AnnotationConfigApplicationContext、ClassPathXmlApplicationContext

关键记忆点：ApplicationContext 是 BeanFactory 的子接口；所有容器能力的最终落点在 DefaultListableBeanFactory。

4.4 循环依赖与三级缓存

4.4.1 什么是循环依赖

创建 A 需要先注入 B，创建 B 又需要注入 A，形成死循环。Spring 对单例 Bean 的字段/Setter 注入循环依赖有解，方案是三级缓存。

4.4.2 三级缓存的结构

级别 字段 存储内容 作用
一级 singletonObjects 走完完整生命周期的 Bean 最终对外提供的”成品”
二级 earlySingletonObjects 已从三级取出并确定要暴露的早期引用 防止同一 Bean 的 ObjectFactory 被重复执行
三级 singletonFactories 惰性执行的 ObjectFactory 延迟决策：真正发生循环依赖时才调用 
flowchart TB
    Q[getSingleton beanName] --> L1{一级缓存有?}
    L1 -->|有| R[返回成品]
    L1 -->|无| L2{二级缓存有?}
    L2 -->|有| R2[返回早期引用]
    L2 -->|无| L3{三级缓存有?}
    L3 -->|有| F[执行 ObjectFactory<br/>getEarlyBeanReference]
    F -->|命中切点| P[返回 AOP 代理]
    F -->|未命中| Raw[返回原始对象]
    P --> Move[放入二级缓存<br/>移除三级]
    Raw --> Move
    Move --> R3[返回]
    L3 -->|无| Null[返回 null]

4.4.3 为什么需要三级缓存（核心考点）

常见追问：二级缓存看起来就够了，为什么一定要三级？关键在于 AOP。

代理对象是在 initializeBean() 的 BeanPostProcessor 后置处理阶段才创建的，而循环依赖发生时，B 在 A 的属性注入阶段就必须要拿到 A 的引用——此时 A 还不知道自己是否会被代理。

  • 若只有一级缓存（实例化后直接暴露裸对象）：B 拿到的是裸 A，而最终对外的是代理 A，注入的引用与最终 Bean 不一致，AOP 全部失效。
  • 若只有二级缓存：为了拿到代理，就只能无条件地对所有 Bean 提前执行代理逻辑。这不仅让没有循环依赖的 Bean 白白被提前代理，还会与 initializeBean 阶段的正常代理逻辑重复。

4.5.1 构造器注入的循环依赖

4.5.2 Prototype 作用域的循环依赖

原型 Bean 每次 getBean 都会新建实例且不参与任何缓存，循环依赖时双方都处于”创建中”状态，同样抛异常。

4.5.3 其他边界情况

9. AOP 原理与代理机制

9.1 AOP 核心概念

术语 含义 示例
切面（Aspect） 横切逻辑 + 切入点的组合 LogAspect
切点（Pointcut） 匹配哪些方法 execution(* com.example.service.*.*(..))
通知（Advice） 在切点上的动作 @Before / @AfterReturning / @AfterThrowing / @After / @Around
连接点（JoinPoint） 被拦截的方法调用点 每个匹配到的方法
织入（Weaving） 把切面逻辑应用到目标对象的过程 Spring 通过动态代理在运行时织入

五种通知的执行顺序：

sequenceDiagram

    participant B as @Before

    participant D as @After

    T-->>C: 正常返回

    D->>A: 执行 @After
    A->>A: end（后）

9.2 JDK 动态代理 vs CGLIB

维度 JDK 动态代理 CGLIB
原理 生成实现同一接口的代理类 生成目标类的子类，覆写非 final 方法
前提条件 目标类必须实现接口 目标类不能是 final，方法不能是 final/private
代理对象类型 与目标实现同一接口 是目标类的子类

Spring 的选择逻辑（DefaultAopProxyFactory）：

规则：目标是接口或已有代理 → JDK；否则只要 proxyTargetClass=true 或无接口 → CGLIB。

Spring Boot 2.x 起默认 CGLIB：

  • 避免类型转换错误（JDK 代理只能赋给接口引用）；
  • 现代代码普遍不为每个类写接口；
  • @Configuration 的 CGLIB 增强需要类级代理。

9.3 代理的创建时机与流程

与循环依赖的联动：正常 Bean 在 postProcessAfterInitialization 创建代理；发生循环依赖的 Bean 则在 getEarlyBeanReference 提前创建。

@Transactional、@Async 走的是同一套代理机制，失效场景与 AOP 一致。

9.4 AOP 失效场景汇总

生效的前提条件：

条件 说明
目标对象是 Spring Bean 需通过容器获取实例
方法需为 public 非 public 方法无法被代理
避免类内部自调用 必须通过代理对象调用方法
非 final 类/方法 CGLIB 要求方法可被重写
正确配置切点 表达式需匹配到目标方法

失效场景逐个展开：

  1. 同类内部自调用（最高频）：

解决方式：

  • 拆 Bean；
  • 注入自身代理：@Autowired @Lazy private OrderService self;；
  • AopContext.currentProxy()（需 @EnableAspectJAutoProxy(exposeProxy = true)）。
  1. private 方法：静默失效。
  2. final 类 / final 方法：CGLIB 无法继承/覆写。
  3. 切点表达式写错：不报错，只是不织入。
  4. 对象未交给 Spring 管理：new OrderService()。
  5. 代理机制局限：Spring AOP 只能织入 Spring Bean 的方法调用。

32. 常见 Spring 面试题速答

32.1 IoC / 容器

Q：IoC 和 DI 是什么？
A：IoC 是把对象创建与装配的控制权反转给容器；DI 是它的实现方式。详见第 1 章。

Q：BeanFactory 与 ApplicationContext 的区别？
A：ApplicationContext 是 BeanFactory 的子接口。BeanFactory 懒加载；ApplicationContext 预加载单例，自动注册后处理器，提供事件、国际化等能力。详见 3.1。

Q：容器启动时做了什么？
A：解析配置类 → 注册 BeanDefinition → 注册 BeanPostProcessor → 预实例化单例 → 发布 ContextRefreshedEvent。详见第 5 章。

Q：如何发布和监听事件？
A：ApplicationEventPublisher.publishEvent + @EventListener / @TransactionalEventListener。详见第 8 章。

32.2 生命周期 / 作用域

Q：Bean 生命周期关键节点？
A：实例化 → 属性填充 → Aware 回调 → postProcessBeforeInitialization → @PostConstruct → InitializingBean → init-method → postProcessAfterInitialization（AOP 代理）→ 就绪；销毁：@PreDestroy → DisposableBean → destroy-method。详见 3.3。

Q：单例与原型区别？
A：单例全容器一个实例；原型每次新实例，容器不管理销毁。详见 3.4。

Q：Spring Bean 线程安全吗？
A：不是 Spring 保证的。无状态单例安全；有状态需原子类/ThreadLocal/无状态设计。详见 3.4。

Q：怎么把原型 Bean 注入单例 Bean？
A：@Lookup、ObjectProvider<T>、@Scope(proxyMode = TARGET_CLASS)。详见 3.4。

Q：BeanFactory 和 FactoryBean 的区别？
A：BeanFactory 是容器接口；FactoryBean 是生产对象的 Bean。详见 3.6。

32.3 依赖注入

Q：@Autowired 与 @Resource 的区别？
A：来源、默认策略（按类型 vs 先名称后类型）、@Primary 支持、构造器支持。详见 4.1。

Q：同类型多个 Bean 怎么注入？
A：@Qualifier、@Primary、@Priority，或字段名与 Bean 名一致。详见 4.2。

Q：为什么推荐构造器注入？
A：不可变、必填、可测试；循环依赖会启动报错，帮助尽早暴露问题。详见 4.3。

Q：循环依赖为什么需要三级缓存？
A：核心是延迟”是否创建 AOP 代理”的决策。详见 4.4。

Q：构造器注入的循环依赖怎么办？
A：改字段注入，或加 @Lazy；Boot 2.6+ 默认禁止。详见 4.5。

32.4 AOP

Q：JDK 代理与 CGLIB 的区别？Spring Boot 默认用哪个？
A：JDK 要求接口；CGLIB 生成子类。Boot 2.x 起默认 CGLIB。详见 9.2。

Q：代理在 Bean 生命周期哪一步创建？
A：正常 Bean 在 postProcessAfterInitialization；循环依赖提前在 getEarlyBeanReference。详见 9.3。

Q：AOP 哪些情况会失效？
A：同类自调用、private/final 方法、非容器 Bean、切点表达式不匹配。详见 9.4。

Q：AOP 责任链怎么执行的？
A：DefaultAdvisorChainFactory 组装 → ReflectiveMethodInvocation.proceed() 递归放行 → 洋葱式嵌套。详见第 10 章。

32.5 事务

Q：@Transactional 什么时候失效？
A：同类自调用、非 public、异常被吞、受检异常未配 rollbackFor、final 方法、多线程、MyISAM 表、非容器 Bean。详见 21.4。

Q：7 种传播行为是什么？
A：REQUIRED（默认）、REQUIRES_NEW、NESTED、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。详见 21.2。

Q：MySQL 默认隔离级别？三大并发问题？
A：REPEATABLE_READ；脏读、不可重复读、幻读。详见 21.3。

32.6 Spring Boot

Q：Spring Boot 自动配置原理？
A：@EnableAutoConfiguration 导入 AutoConfigurationImportSelector，读取 .imports 文件，按 @Conditional 评估后注册 Bean。详见第 17 章。

Q：@ConditionalOnMissingBean 的作用？
A：用户没自定义时才注册默认 Bean——“用户可覆盖”的开关。详见第 18 章。

Q：Spring Boot 启动流程？
A：创建 SpringApplication → 准备 Environment → 创建 ApplicationContext → prepareContext → refresh → afterRefresh。详见第 16 章。

Q：怎么写自定义 Starter？
A：两个模块，@ConfigurationProperties + @AutoConfiguration + .imports 注册文件。详见第 20 章。

D.2 关键记忆点

  • AOP 代理在步骤 12 创建：所以在 @PostConstruct（步骤 9）里调用被代理的方法不会走切面；
  • 销毁回调对 prototype 无效：容器不管理 prototype Bean 的完整生命周期；
  • **@PostConstruct 在 Boot 3 来自 jakarta.annotation**。

全文因果链回顾：

  1. IoC 基础：IoC 是控制反转，DI 是它的实现；容器管理 Bean 的创建、装配、生命周期
  2. Bean 生命周期：11 个阶段，关键节点是实例化 → 属性填充 → 初始化 → AOP 代理 → 就绪
  3. 循环依赖：三级缓存（singletonObjects / earlySingletonObjects / singletonFactories），核心是延迟 AOP 代理决策；构造器注入、Prototype 无法解决
  4. AOP：JDK 代理（有接口）/ CGLIB（无接口），代理时机在 postProcessAfterInitialization；失效场景：自调用、private/final、非容器 Bean
  5. AOP 责任链：DefaultAdvisorChainFactory 组装 + ReflectiveMethodInvocation 递归放行，洋葱式嵌套
  6. Spring MVC：九大组件 + DispatcherServlet.doDispatch() 三步走；参数解析靠 HandlerMethodArgumentResolver 链
  7. Spring Boot：@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan；自动配置靠 AutoConfigurationImportSelector 读取 .imports 文件
  8. 条件装配：@ConditionalOnMissingBean 是”用户可覆盖”的关键
  9. 事务：AOP + TransactionInterceptor，连接绑 ThreadLocal；传播行为、隔离级别、失效场景
  10. 缓存抽象：@Cacheable / @CachePut / @CacheEvict，缓存穿透/击穿/雪崩的解决方案
  11. 异步与调度：@Async + 自定义线程池 + AsyncUncaughtExceptionHandler；@Scheduled + cron + 分布式锁
  12. 拦截机制：Filter（Servlet 层）/ Interceptor（MVC 层）/ AOP（方法层）
  13. 异常处理：@RestControllerAdvice + @ExceptionHandler + 错误码规范
  14. Spring 6 / Boot 3 新特性：Jakarta EE 9+ 迁移、GraalVM Native Image、虚拟线程、HTTP Interface、函数式 Bean 注册
