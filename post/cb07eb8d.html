分布式锁与限流：从 SET NX 到 Redisson

Posted on 2026-10-25 In 数据存储 Word count in article: 3.5k Reading time ≈ 13 mins.

SET NX 只能保证「同一时刻只有一个客户端能写进去」，它不保证「这把锁一直属于你」。本文实测了三种锁失效：用 DEL 释放会把别人的锁删掉；任务执行时间超过 TTL 会出现两个持有者；主库宕机 + 旧主未隔离（脑裂）时，两个节点上会各有一把同名锁，两个客户端同时认为自己独占。

后半篇换到限流：固定窗口在边界上能放行 2 倍的请求（实测 100/s 的限制放行了 200 个），滑动窗口与令牌桶分别是 100 和 117。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流（本文） → ⑫ 容量规划与分片

与前后篇的关系：锁的释放用 ⑥ 的 Lua 原子性；「切换丢锁」是 ⑧ 异步复制的必然结果；限流器是 ⑨ 雪崩的兜底手段。

1. 一把合格的锁需要四个属性

属性 含义 不做会怎样
互斥 同一时刻只有一个持有者 SET NX 保证
超时 持锁者崩溃后能自动释放 死锁，谁也别想拿
持有者标识 释放时能确认「是我的锁」 误删别人的锁（2.1）
可重入（可选） 同一线程可重复获取 自己把自己锁死 
stateDiagram-v2
    [*] --> Free: 无锁
    Free --> Held: SET NX PX ok
    Held --> Held: 续期（watchdog）
    Held --> Free: Lua 校验后 DEL
    Held --> Free: TTL 到期（持有者崩了）
    Held --> HeldByOther: TTL 到期但业务还在跑
    HeldByOther --> [*]: 双持有者（危险）

2. 三个必踩的坑

2.1 用 DEL 释放，会删掉别人的锁

问题：c1 以为自己还持有锁，实际上锁已经被 c2 删掉并抢走。

正确释放：用 Lua 校验 value 再删（原子）：

实测：

操作 返回 含义
用别人的 value 释放 0 拒绝，锁没被删
用自己的 value 释放 1 成功删除

2.2 任务超时：锁自动过期，出现两个持有者

实测结果：

观察点 结果
c1 任务还在跑（已 500ms） 是
c2 是否拿到锁 是
当前锁的持有者 c2
c1 尝试释放（Lua 校验） 0（拒绝）

这是最危险的场景：两个客户端同时在执行「只允许一个人做」的操作（扣库存、重复下单）。Lua 校验至少避免了 c1 误删 c2 的锁，但无法阻止两个业务同时在跑。

解法 做法 代价
watchdog 自动续期 后台线程每 1/3 TTL 续一次 续期线程崩了照样失效（Redisson 方案）
任务幂等 + 状态机 业务自己防重复 需要业务改造
长 TTL + 业务超时 TTL 远大于任务时间 TTL 过长会拖慢故障恢复

2.3 主从切换：两个节点各有一把同名锁（实测）

先说我没复现出来的那个实验：在 loopback 上，SET 之后立刻断链、立刻杀主，从库已经同步了这把锁（复制延迟 <1ms），所以哨兵提升后 B 拿不到锁。

但这不代表安全——一旦网络有延迟或从库在阻塞，这个窗口就会打开。而下面这个场景一定能复现：

实测输出：

检查点 结果
新主上的锁 B-owner
旧主重启后的角色 master
旧主是否还能加锁 OK
旧主上的锁 A-owner

两个节点各持一把同名锁，两个客户端同时认为自己独占。这不是 Redis 的 bug，是「没有被隔离的旧主」+「异步复制」的必然结果。

flowchart LR
    A["Client A<br/>lock:job = A-owner"] --> M1["Old master<br/>(not fenced)"]
    B["Client B<br/>lock:job = B-owner"] --> M2["New master<br/>(promoted replica)"]
    M1 -.->|"no replication"| M2
    M1 --> D1["Both believe exclusive"]
    M2 --> D1

工程上的解法只有两个方向：

方向 做法
隔离旧主（fencing） 切换时强制旧主 readonly、或直接断电/销毁；应用侧只认 VIP
放弃「绝对互斥」的假设 业务幂等 + 唯一约束兜底（数据库唯一索引是最后防线）

3. 从 SET NX 到 Redisson

能力 原生 SET NX Redisson
互斥 ✅ ✅
超时 手动设 PX ✅
安全释放 自己写 Lua ✅ 内置
自动续期 ❌ 自己写线程 ✅ watchdog（默认 30s TTL，每 10s 续）
可重入 ❌ ✅ 用 Hash 记录重入次数
等待/公平 ❌ 自己轮询 ✅ 提供 tryLock(waitTime) 与公平锁 
sequenceDiagram
    participant T as Business thread
    participant W as watchdog
    participant R as Redis
    T->>R: SET lock NX PX 30000
    W->>W: schedule at TTL/3 (10s)
    W->>R: PEXPIRE lock 30000（续期）
    T->>R: Lua 校验+DEL（业务结束）
    Note over W: 业务线程结束后取消续期

watchdog 的边界：它靠 JVM 里的定时线程续期。如果进程被 kill -9 或长时间 GC，续期停止，锁到期自动释放——这是设计意图（防止死锁），但也意味着业务必须幂等。

4. RedLock 的争议在争什么

观点 主张 核心论据
antirez（RedLock） 向 N 个独立 Redis 加锁，多数成功即视为持有 单点故障下仍能互斥
Kleppmann RedLock 不能保证「锁的持有者一定是执行者」 依赖时钟假设；GC 停顿会让持有者失去锁而不自知

争论的本质不是「RedLock 实现得好不好」，而是「你到底需不需要一把绝对安全的锁」：

你的需求 建议
防止重复执行（可幂等） 单实例 SET NX + 幂等 + 唯一索引兜底
互斥访问共享资源（不可幂等） 需要 fencing token（每次加锁递增的版本号，下游校验）
强一致（金融扣减） 别用 Redis 锁，用数据库行锁/事务（MySQL 系列 ⑤⑥）

一句话：Redis 锁适合「防重复」，不适合「防并发写」。后者要靠数据库约束或 fencing。

5. 限流：三种算法的实测

5.1 固定窗口：边界上能放行 2 倍

按秒取整计数（key = prefix .. floor(now/1000)），在「秒边界前后」各打 100 个请求：

算法 边界前放行 边界后放行 合计（limit=100/s）
固定窗口（按秒取整） 100 100 200（2 倍超发）
滑动窗口（ZSET） 100 0 100

固定窗口的问题：跨边界的那一瞬间，两个窗口各自独立计数，实际速率可以是限制值的 2 倍。

5.2 滑动窗口：精确但占内存

维度 表现
精度 高（严格 ≤ limit/window）
内存 每个请求一条 ZSET 成员（限流值 × 窗口内请求数）
适用 中小流量、要精确控制

5.3 令牌桶：允许突发

实测（capacity=100、rate=100/s，150ms 内两批共 200 个请求）：

算法 放行 说明
令牌桶 117 100 个初始令牌 + 150ms 补的 ~15 个
固定窗口 100（同窗口内） 首批用完后同一窗口内全拒

令牌桶的价值是「允许突发」：只要桶里有令牌，瞬时就能通过。适合「平时低流量、偶发峰值」的接口。

    subgraph FW["Fixed window"]
        F1["counter per second"] --> F2["boundary: 200 allowed<br/>for limit 100"]

    subgraph SW["Sliding window"]
        S1["ZSET of timestamps"] --> S2["strictly 100 allowed"]
    end
    subgraph TB["Token bucket"]

5.4 三种算法对比

算法 精度 内存 突发能力 实现复杂度 适用
固定窗口 低（边界 2 倍） 一个计数器 无 最低 粗粒度限制
滑动窗口 高 O(limit) 无 中 精确限流
令牌桶 中（允许突发） 两个字段 有 中 允许峰值的场景
漏桶 高（匀速） 队列 无（削峰） 中 需要平滑输出

5.5 动手验证：边界突发

预期观察点：固定窗口的放行数是滑动窗口的 2 倍。

判定标准：

  • 固定窗口放行 ≈ 2×limit → 边界问题成立，换滑动窗口或令牌桶；
  • 两者都只放行 100 → 你的窗口是「首次请求开始计时」，不是「按秒取整」，问题被掩盖了；
  • 令牌桶放行 ≈ limit + rate×间隔 → 正常（突发能力）。

7. 动手验证：四个可复现实验

7.1 动手验证：对比 DEL 与 Lua 释放

预期观察点：DEL 直接把锁删掉；Lua 用别人的 value 返回 0，TTL 仍大于 0。

判定标准：Lua 返回 1 → 你的 value 比较写错了（比如没传对 ARGV）。

7.2 动手验证：复现锁过期后的双持有

预期观察点：第二次 SET NX 成功，GET 返回 owner-B——A 的任务还在跑但锁已易主。

判定标准：第二次失败 → TTL 还没到，把 sleep 加长。

7.3 动手验证：验证限流边界超发

预期观察点：固定窗口放行 200（2 倍），滑动窗口只放行 100（本文）。

判定标准：固定窗口也只放行 100 → 你的窗口是「首次请求开始计时」，不是按秒取整，边界问题被掩盖。

7.4 动手验证：量一次限流脚本的开销

预期观察点：usec_per_call 应在几十微秒内；本文 Lua 单次约 119 µs（含网络）。

判定标准：超过 1 ms → 脚本里有 O(N) 操作（比如遍历 ZSET 全量），需要改结构。

6. 总结

6.1 面试速答表

面试题 一句话答案
Redis 分布式锁怎么实现 SET key value NX PX ttl 加锁，Lua 校验 value 后删除
为什么释放要用 Lua DEL 会误删别人的锁；Lua 校验持有者，实测用别人的 value 返回 0
锁的 value 用什么 唯一标识（UUID + 线程 id），用于校验持有者
锁超时了怎么办 watchdog 自动续期（Redisson 每 TTL/3 续一次）
任务超过 TTL 会怎样 两个客户端同时持锁（实测），必须业务幂等
主从切换会丢锁吗 会。脑裂时旧主未隔离，两节点各有一把同名锁（实测）
RedLock 安全吗 争议在于时钟假设与 GC 停顿；强一致场景别用 Redis 锁
分布式锁的最佳兜底 数据库唯一索引/行锁 + 业务幂等
固定窗口的问题 边界处可放行 2 倍（实测 100/s 放行 200）
滑动窗口怎么实现 ZSET 存时间戳，ZREMRANGEBYSCORE + ZCARD
令牌桶和滑动窗口的区别 令牌桶允许突发（实测 117/100ms），滑动窗口严格匀速
限流器放在哪一层 网关（全局限流）+ 服务（精细化），Redis 做集中计数

6.2 实战避坑表

症状 原因 处理
同一任务被重复执行 锁 TTL 短于任务时长 watchdog 续期 + 业务幂等
锁永远释放不了 持有者崩溃且没设 TTL 必须设 PX
误删别人的锁 用 DEL 释放 改 Lua 校验 value
切换后两个客户端同时持锁 脑裂 / 旧主未隔离 fencing + 只认 VIP + 数据库兜底
限流在整点被突破 固定窗口边界 换滑动窗口/令牌桶
限流后正常请求被拒 桶容量太小或速率太低 调 capacity 与 rate，区分突发与持续

6.3 工具速查表

工具 看什么 判定标准
SET NX PX 返回值 是否加锁成功 nil = 已被占用
Lua 释放脚本返回值 是否自己的锁 0 = 不是自己的
TTL lock:key 剩余时间 接近 0 说明快过期
Redisson 的 isLocked() 锁状态 排查残留锁
Redis INFO commandstats EVAL 耗时 限流脚本要轻（<100µs）

6.4 实操建议

  1. **锁一定带 PX**，并且用 Lua 校验 value 再释放，这两条是底线。
  2. 锁的 TTL 要小于业务超时，配合 watchdog；业务必须幂等。
  3. 别指望 Redis 锁解决强一致，关键资源用数据库约束 + fencing token。
  4. 限流优先用令牌桶或滑动窗口，固定窗口的 2 倍超发在秒杀场景是致命的。
  5. 限流要分层：网关做粗粒度、服务做细粒度，并用 Redis 做集中计数。
