Kafka 深度解析：原理、实践与面试指南

Posted on 2025-07-26 In 中间件 Word count in article: 11k Reading time ≈ 41 mins.

1. Kafka 定位：消息队列还是事件流平台

1.1 定位演变：从消息队列到事件流平台

Kafka 诞生于 LinkedIn（2011 年开源），最初是日志聚合场景的消息队列。现在官方定位是分布式事件流平台（Event Streaming Platform），核心差异在于存储模型：

维度 传统消息队列（RabbitMQ） Kafka
消息消费后 从队列删除 保留在磁盘上，按保留策略过期删除
存储模型 传输通道 追加写日志（append-only log）
重复消费 不支持 支持（回退 offset 重放）
多消费者组 需要 fanout 配置 天然支持，每个组独立消费
吞吐量 万级/秒 单机百万级/秒

这意味着什么？ Kafka 不仅是”传输通道”，更是一个”可回放的事件日志”。同一份数据可以被实时计算、离线数仓、监控告警等多个消费者组独立消费，互不影响。

1.3 与 RocketMQ、RabbitMQ 的选型对比

维度 Kafka RocketMQ RabbitMQ
定位 分布式事件流平台 分布式消息队列（Java 生态） 轻量消息中间件（AMQP）
吞吐 单机百万级/秒 十万~百万级/秒 万级/秒
顺序消息 分区内有序 队列内有序 单队列有序
事务消息 面向流处理的精确一次（EOS） 原生半消息 + 回查机制 无
延迟/定时消息 无原生支持 原生延迟级别/定时消息 借助 TTL + 死信交换机实现
适用场景 日志、指标、事件流、大数据管道 交易类、强事务要求 中小规模、路由灵活

选型一句话：吞吐和事件流优先 Kafka；交易场景需要原生事务/延迟消息优先 RocketMQ；轻量灵活、生态简单优先 RabbitMQ。

面试追问：RocketMQ 事务消息流程与 Kafka 的区别？

RocketMQ 先发”半消息”（对消费者不可见），执行本地事务后提交 Commit/Rollback 指令。Broker 收到回查请求时反向询问 Producer 本地事务最终状态。Kafka 的事务机制不覆盖外部系统，定位不同。

面试追问：Broker 选举机制对比？

Kafka 由 Controller 从 ISR 中选举新 Leader（一致性优先，宁可分区不可用也不选落后副本）。RocketMQ 主从切换在 DLedger 模式下走 Raft 多数派选举，兼容模式下为异步复制、手动/自动切换。

面试话术：

“我们选 Kafka 主要是因为日志和事件流场景，吞吐量要求高，而且需要多消费者组独立消费。如果是交易类需要事务消息的场景，会优先考虑 RocketMQ。”

2.2 逐个拆解

概念 是什么 关键点
Topic 消息的逻辑分类 类比数据库表
Partition Topic 的物理切分单元，磁盘上是一个日志目录 存储单位 + 并行单位 + 顺序保证单位
Replica 每个 Partition 有 N 个副本，分布在不同的 Broker 上 一个 Leader（读写）+ 多个 Follower（只同步）
ISR 与 Leader 保持同步的副本集合 只有 ISR 中的副本才有资格当选新 Leader
Controller 集群中枢，负责 Broker 上下线感知、Leader 选举、元数据变更 KRaft 模式下由 Controller Quorum 通过 Raft 选举产生
Coordinator 管理消费者组的成员关系、触发 Rebalance、接收 offset 提交 每个消费者组对应一个 Coordinator

Partition 的三个角色：

flowchart TB
    Partition[Partition]
    Partition --> Role1[存储单位<br/>消息按 offset 递增追加<br/>写入顺序 = 存储顺序]
    Partition --> Role2[并行单位<br/>Partition 之间读写独立<br/>可分布在多台 Broker 上]
    Partition --> Role3[顺序保证单位<br/>Kafka 只保证分区内有序<br/>跨分区无全局顺序]

Coordinator 的两类角色：

类型 职责 位置
Group Coordinator 管理消费者组的成员关系、触发 Rebalance、接收 offset 提交 hash(groupId) % 50（__consumer_offsets 默认 50 个分区）
Transaction Coordinator 管理事务状态 存储在 __transaction_state topic

面试追问：如何保证消息全局有序？

如果要求全局有序，只能把 Topic 设置为 1 个 Partition。但这意味着牺牲并行度，吞吐量会大幅下降。实际生产中更常见的做法是：用 Key 哈希把同一业务实体的消息路由到同一 Partition，保证业务级别的有序，而不是全局有序。

2.3 动手验证：查看 Topic 和 Partition 分布

观察点：Leader 列显示每个 Partition 的 Leader 在哪个 Broker；Replicas 列显示副本分布；Isr 列显示当前同步的副本集合。如果某个副本不在 ISR 中，说明它已经滞后。

3. 高吞吐原理：为什么 Kafka 能扛百万级 QPS

3.1 四大核心支柱总览

Kafka 的高吞吐不是靠”某个黑科技”，而是四个机制叠加的结果：

flowchart TB
    HighThroughput[Kafka 高吞吐]
    HighThroughput --> Pillar1[顺序写入<br/>append-only log<br/>避免磁盘随机寻址]
    HighThroughput --> Pillar2[PageCache<br/>操作系统页缓存<br/>避开 JVM GC]
    HighThroughput --> Pillar3[零拷贝<br/>sendfile<br/>减少 CPU 拷贝和上下文切换]
    HighThroughput --> Pillar4[批量 + 压缩<br/>batch.size + linger.ms<br/>端到端压缩]
    HighThroughput --> Pillar5[分区并行<br/>多分区分布多 Broker<br/>读写多路并行]

3.2 顺序写

为什么快：磁盘顺序写可达 150~200 MB/s（机械盘），随机写只有几 MB/s。Kafka 只做追加写（append-only），把”读改写”变成”写尾指针”。

怎么实现：每条消息追加到当前活跃的日志段（Segment）末尾；Segment 按 log.segment.bytes（默认 1GB）滚动切分。

生产配置：无需特殊配置。注意一个常见误区——不能因为”顺序写快”就认为数据已持久化，可靠性仍要依靠 acks 和副本数（第 5 节）。

3.3 PageCache

为什么快：Kafka 把读写都交给操作系统 Page Cache。写先落到 Page Cache 由内核异步刷盘，读命中 Cache 时就是纯内存操作。

怎么实现：数据不经过 JVM 堆，全部走内核 Page Cache。这让 Kafka 的 JVM 堆可以保持很小（生产建议 4~8GB），避免大堆 GC 停顿。

flowchart LR
    subgraph JVM["JVM 堆"]
        Heap[JVM Heap<br/>4-8GB]
    end

    subgraph OS["操作系统"]
        PageCache[Page Cache<br/>剩余内存]
        Disk[磁盘]
    end

    Write[写入消息] --> PageCache
    PageCache -->|异步刷盘| Disk
    Read[读取消息] --> PageCache
    PageCache -->|未命中| Disk
    PageCache -.->|不经过| Heap

生产配置：JVM 堆不要盲目调大，防止堆挤占 Page Cache 空间；日志目录建议独立挂盘。

3.4 零拷贝 sendfile

为什么快：传统”读文件 → 发给 socket”路径要经过 4 次拷贝和多次上下文切换。sendfile 让内核直接把 Page Cache 中的数据 DMA 到网卡，全程 2 次拷贝。

flowchart LR
    subgraph Traditional["传统方式 4 次拷贝"]
        D1[磁盘] --> K1[内核缓冲区]
        K1 --> U1[用户缓冲区]
        U1 --> S1[Socket 缓冲区]
        S1 --> N1[网卡]
    end

    subgraph ZeroCopy["零拷贝 2 次拷贝"]
        D2[磁盘] --> K2[PageCache]
        K2 --> N2[网卡]
    end

面试追问：零拷贝是完全没有拷贝吗？

不是。零拷贝是指没有 CPU 参与的拷贝。DMA（直接内存访问）拷贝仍然存在，但 DMA 拷贝不需要 CPU 参与，不消耗 CPU 资源。

3.5 批量 + 压缩

批量发送：Producer 把多条消息攒成一个批次再发送，减少网络往返次数。

参数 默认值 作用 调优建议
batch.size 16KB 一个批次的最大字节数 调大到 64KB-1MB
linger.ms 0 批次等待时间 调到 5-100ms
fetch.min.bytes 1 消费者拉取批次最小字节数 调大到 1MB
fetch.max.wait.ms 500ms 攒批最长等待 延迟敏感调小

压缩：Kafka 支持在批次级别压缩（compression.type=lz4/snappy/zstd），压缩后再发送，Broker 端不解压直接存储，Consumer 端解压。

3.6 分区并行

为什么快：单分区是单线程顺序写，吞吐上限受单块磁盘 IOPS 限制。把 Topic 拆成 N 个 Partition 分布在 M 台 Broker 上，读写多路并行，吞吐理论上可以线性扩展。

生产配置：分区数是吞吐规划的核心参数——先估单分区吞吐（如 5~10 MB/s），再按总吞吐需求定分区数。

面试追问：分区数是不是越多越好？

不是。分区数过多会放大元数据规模、文件句柄数、Rebalance 时间，以及 Leader 选举开销。经验值：分区数与预期吞吐匹配即可，单 Broker 数千分区以内是常见规模。

4. 物理存储：一条消息落盘后长什么样

4.1 Segment 文件结构

Kafka 的 Topic 数据按分区存储，一个分区对应磁盘上的一个目录：

每个 Segment 由三个文件组成：

文件 内容
.log 消息本体，二进制追加写
.index offset → 物理位置 的稀疏索引
.timeindex 时间戳 → offset 的索引

文件名的 20 位数字 = 段内第一条消息的绝对 offset。只有最后一个段是活跃段（active segment），消息只追加到活跃段。

4.2 稀疏索引原理

一个 1GB 的 .log 文件里要定位 offset 37281 之后的第 10 条消息，不可能从文件头逐条扫。.index 就是干这个的，但它不是”每条消息一条索引”，而是稀疏索引：

  • 每写入 4KB（log.index.interval.bytes）数据，才在 .index 追加一条记录；
  • 每条记录 8 字节：relative offset（4 字节）+ position（4 字节）。
flowchart LR
    Query["查找 offset 2500"] --> FindSeg["根据段文件名<br/>找到目标 Segment"]
    FindSeg --> Binary["在 .index 二分查找<br/>≤ 2500 的最大条目"]
    Binary --> GetPos["拿到物理 position<br/>(2300, 8192)"]
    GetPos --> Scan["从 .log 偏移 8192<br/>顺序扫到 2500"]

稀疏索引让索引体积缩小上百倍，代价只是最多多扫 4KB 数据。

4.3 日志清理策略：delete vs compact

消息消费完不会消失，什么时候真正删除由清理策略决定：

维度 delete（默认） compact
保留语义 保留最近 N 小时/字节 保留每个 key 的最新值
删除单位 整个 Segment（按时间/大小） 段内逐条（按 key）
代价 低 cleaner 线程 CPU 开销
典型应用 日志、指标、事件 配置、快照、状态数据

delete 策略：按时间/大小过期删除。log.retention.hours（默认 168，即 7 天）或 log.retention.bytes。适合”过了保留期就不需要”的数据。

compact 策略：按 key 保留最新值。永远保留每个 key 的最新一条消息，key 的旧值被压缩删除。写入 value = null 的消息表示删除该 key（tombstone）。适合”最终状态”类数据。

4.4 磁盘布局与 Leader 分布

多目录均衡：log.dirs=/data/kafka1,/data/kafka2 把分区目录分散到多块磁盘。Broker 创建新分区时，选择当前文件数最少的目录。

Leader 分区的轮询放置：创建 Topic 时，Controller 会把各分区的 Leader 尽量均匀分配到所有 Broker（优先选副本最少的 Broker），Follower 跟随放置并尽量满足机架感知。

5. 消息可靠性：三个环节怎么保证不丢

5.1 三种投递语义

语义 含义 实现方式
at-most-once 可能丢，但不会重复 acks=0
at-least-once 不会丢，但可能重复 Kafka 默认
exactly-once 不丢不重 幂等 + 事务 + 消费端配合

5.2 acks 三种模式

acks 值 含义 可靠性 吞吐 适用场景
0 发出即认为成功，不等待确认 最低 最高 日志采集、监控指标
1 等待 Leader 落盘确认 中 中 一般业务
all / -1 等待所有 ISR 副本同步完成 最高 最低 金融、支付、订单 
flowchart LR
    subgraph Acks0["acks=0"]
        P0[Producer] -->|发出即返回| B0[Broker]
    end

    subgraph Acks1["acks=1"]
        P1[Producer] -->|等待 Leader 确认| B1[Leader]
    end

    subgraph AcksAll["acks=all"]
        P2[Producer] -->|等待所有 ISR 确认| B2[Leader]
        B2 -->|同步| F2[Follower 1]
        B2 -->|同步| F3[Follower 2]
    end

5.3 ISR 最小副本数

acks=all 的语义是”ISR 全部写入”，但 ISR 是动态收缩的——如果副本都挂得只剩 Leader 自己，acks=all 实际退化成 acks=1。所以必须有 min.insync.replicas 卡住底线。

flowchart TB
    Producer[Producer 发送消息] --> Check{ISR 中副本数<br/>>= min.insync.replicas?}
    Check -->|是| Write[Leader 写入成功<br/>等待 ISR 同步]
    Check -->|否| Reject[拒绝写入<br/>返回 NOT_ENOUGH_REPLICAS]
    Write --> Ack[返回成功给 Producer]

生产配置：replication.factor=3 搭配 min.insync.replicas=2。含义是：写入成功的消息必然存在 2 份副本，任意一台 Broker 故障都不丢。

面试追问：RF=3, min.insync.replicas=2, 宕机几台会不可用？

最多宕机 1 台。因为 3 副本中如果有 2 台宕机，ISR 中只剩 1 个副本，小于 min.insync.replicas=2，Leader 会拒绝写入。所以 3 副本 + min.insync=2 的方案，容忍 1 台 Broker 故障。

5.4 副本同步与高水位（LEO / HW）

这是 Kafka 一致性的核心考点：

概念 含义 维度
LEO 副本本地日志下一条待写入的 offset 单副本维度
HW 所有 ISR 副本 LEO 的最小值 分区（ISR 集合）维度 
flowchart LR
    subgraph Leader[Leader 副本]
        L_LEO[LEO = 10]
    end
    subgraph F1[Follower 1]
        F1_LEO[LEO = 9]
    end
    subgraph F2[Follower 2]
        F2_LEO[LEO = 8]
    end

    HW[HW = min 9, 8, 10 = 8]

    Leader --> HW
    F1 --> HW
    F2 --> HW

    Consumer[消费者只能读到 offset < 8 的消息]
    HW --> Consumer

核心规则：

  • 消费者只能读到 HW 之前的消息；
  • Follower 同步追上 Leader 的 LEO 后，Leader 会推进 HW。

面试追问：为什么消费者不能读到 HW 之后的消息？

因为 HW 之后的消息虽然写入了 Leader，但还没被所有 ISR 副本确认。如果消费者能读到，Leader 一宕机这些已读数据就凭空消失了。HW 定义了”已提交”的线。

5.5 三环节不丢失方案

Producer 环节：

  • acks=all + min.insync.replicas=2（前提 RF=3）；
  • 配置 retries 和 retry.backoff.ms；
  • enable.idempotence=true；
  • send() 的回调必须检查异常并告警。

Broker 环节：

  • replication.factor=3、min.insync.replicas=2、unclean.leader.election.enable=false；
  • Broker 侧不需要追求逐条 fsync——副本冗余已经保证了”至少两份”。

Consumer 环节：

  • enable.auto.commit=false，业务处理成功之后手动 commitSync()；
  • 处理完一批再提交该批最后一条 offset；
  • 实现 ConsumerRebalanceListener，在 onPartitionsRevoked 中把已处理的 offset 提交掉。

一句话总结生产配置：RF=3、min.insync.replicas=2、unclean.leader.election.enable=false、acks=all、enable.idempotence=true、消费者手动提交。

6. 消息不重复：幂等生产者、消费者去重、事务

6.1 为什么会产生重复

在 at-least-once 语义下，重复是结构性的：

  • 生产者重试：消息已写入 Broker，但 ack 在网络中丢失，Producer 重试导致同一条消息写入两次；
  • 消费者提交失败：处理成功但 offset 提交失败，重平衡后从旧 offset 重新拉取。

6.2 幂等生产者

为什么需要：重试和去重是矛盾的——不重试会丢，重试会重。幂等机制让”重试”和”不重”同时成立。

怎么实现：Producer 启动时向 Broker 申请一个唯一的 Producer ID；发往每个分区的消息携带单调递增的序列号。Broker 记录每个 (PID, 分区) 最近写过的序列号，重复序列号直接忽略。

局限：去重范围是单个 Producer 会话、单个分区。进程重启后 PID 变化，去重失效；跨分区不去重。

生产配置：enable.idempotence=true 是生产必选项。

6.3 消费者端去重

为什么需要：Kafka 的事务只能覆盖 Kafka 内部。消费逻辑一旦牵涉外部系统（数据库、ES、调用下游 API），”不重复”必须由业务侧自己保证。

怎么实现：

  • 消息中携带全局唯一业务 ID（订单号、支付流水号）；
  • 处理前查重：SELECT ... WHERE order_id = ? 已存在则跳过；
  • 数据库唯一约束兜底：INSERT 违反唯一键即视为重复；
  • 需要”只处理一次”的状态机用条件更新。

6.4 事务消息

为什么需要：幂等只解决”单分区去重”，解决不了”多个分区的写入要么全成功要么全失败”的问题。

怎么实现：事务由 Transaction Coordinator 协调。Producer 开启事务后，写入的分区都在事务内标记；commitTransaction() 时协调者推进事务状态。消费者设置 isolation.level=read_committed 时，只能读到已提交事务内的消息。

维度 幂等 事务
解决的问题 重试导致的重复 多分区/多 Topic 原子写入 + 消费提交原子化
覆盖范围 单 Producer 会话、单分区 事务内所有分区、所有 Topic
对外保证 不丢不重（分区内） 流处理 exactly-once（Kafka 内部）
局限 跨会话、跨分区不去重 不覆盖外部系统

面试回答模板：幂等是”去重”，事务是”原子性”；跨 Kafka 与外部系统的最终一致性，靠业务幂等兜底。

7. 消息顺序性：分区内有序

7.1 分区内有序的原理

Kafka 的顺序保证是”单分区内严格有序“：

  • 写入侧：消息按 offset 追加到分区日志尾部，写入顺序即物理存储顺序；
  • 消费侧：同一个分区的消息只被组内一个消费者实例消费，poll() 按 offset 顺序返回。

跨分区没有全局顺序（全局有序只能单分区 + 单消费者，等于放弃并行，生产上极少需要）。

7.2 用 key 保证同一实体的消息有序

业务上有序的最小单位是”同一个实体”（同一个订单、同一个用户）。默认分区器对 key 做 murmur2 哈希取模选分区，相同 key 必然进同一分区。

key 的选择：业务实体 ID（订单号、用户 ID）。注意 key 的均匀性——热点 key 会造成分区倾斜。

7.3 乱序场景与处理

乱序场景 原因 处理
生产者重试 max.in.flight.requests.per.connection > 1 开启幂等，或设为 1
消费者多线程 单分区被多个线程并发处理 分区内单线程，或按 key 哈希路由到固定线程
失败重投 重试消息排在后继消息后面 重试消息保持原 key，同 key 串行重试

面试追问：Rebalance 会破坏顺序吗？

不会。只要 offset 提交正确，分区易主后新消费者从已提交位置继续，不会跳过也不会回头。真正会破坏顺序的是”提交 offset 后继续处理”这种错误写法。

8. 消费者组：Rebalance、分配策略与 Lag 监控

8.1 为什么需要消费者组

单消费者处理能力有限，且单点故障即消费中断。消费者组让 N 个实例协作消费一个 Topic：每个 Partition 同一时刻只被组内一个实例消费；实例宕机时分区自动转移。

flowchart TB
    subgraph Topic[Topic: orders]
        P0[Partition 0]
        P1[Partition 1]
        P2[Partition 2]
    end

    subgraph CG[Consumer Group]
        C0[Consumer 0]
        C1[Consumer 1]
    end

    GC[Group Coordinator] -->|Rebalance| CG
    GC -->|offset 提交| Off[__consumer_offsets]

    C0 --> P0
    C0 --> P2
    C1 --> P1

    style GC fill:#fff4e6

8.2 Rebalance 的触发条件

  • 组成员变化：新消费者加入、消费者主动离开、消费者崩溃；
  • 订阅的 Topic 分区数变化：kafka-topics.sh --alter --partitions 扩容分区；
  • 订阅范围变化：正则订阅匹配到新 Topic；
  • 消费速度过慢被踢出：max.poll.interval.ms（默认 5 分钟）内未调用 poll()，协调者认为消费者”卡死”。

Rebalance 期间组内消费整体暂停，因此频繁 Rebalance 是消费抖动和积压的头号元凶。

8.3 三种分区分配策略

策略 原理 优缺点
RangeAssignor（默认） 按 Topic 逐个排序分配 分区数不能整除时倾斜
RoundRobinAssignor 所有分区合并成环，轮流分配 整体均衡，但分区迁移多
StickyAssignor 均衡 + 最小化分区迁移 Rebalance 时尽量保留原分配
CooperativeStickyAssignor（推荐） Sticky + 增量式 Rebalance 全组不需要 stop-the-world

生产推荐：显式配置 partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor。

8.4 静态成员

group.instance.id 给消费者一个固定身份。普通消费者每次重启都是”新成员”，必然触发 Rebalance；静态成员离线时，Coordinator 会保留其分区所有权直到 session.timeout.ms 超时。适合发布频繁或对 Rebalance 敏感的线上服务。

8.5 Consumer Lag 监控

定义：某分区上”消费者已提交的 offset”与”分区当前 LEO”之差，即未消费的消息数量。

Lag 持续增长的常见原因：

  • 消费者实例数小于分区数；
  • 单条消息处理慢；
  • max.poll.records 太大导致单次 poll 处理超时；
  • 分区分配不均。

处理手段：

  • 扩容消费者（加到分区数为止）；
  • 提升单消费者吞吐（批处理、异步化）；
  • 调 fetch.min.bytes / fetch.max.wait.ms；
  • 排查下游故障。

面试话术：

“Lag 排查先看分配是否均匀，再看单条处理耗时，最后调参。实例数不能超过分区数，超过的消费者拿不到分区，白加。”

9. KRaft 架构：为什么去掉 ZooKeeper

9.1 ZooKeeper 模式的问题

Kafka 2.7 及之前，元数据全部依赖外部 ZooKeeper：

  • 两套系统、两套一致性协议：元数据变更先写 ZK，再同步给 Broker，链路长、延迟高；
  • 运维复杂：ZK 集群本身要 3/5 节点部署、监控、升级；
  • 扩展性天花板：集群规模被 ZK 的元数据能力卡死。

9.2 KRaft 的实现

KRaft 把 ZooKeeper 的职责收编为 Kafka 内部的 Controller Quorum（Raft 组）：

        C1[Controller 1<br/>Active]

        C3[Controller 3<br/>Hot Standby]
    end

        B1[Broker 1]

        B3[Broker 3]
    end

    MetaLog[__cluster_metadata<br/>append-only log]

    C1 -->|Raft 复制| C2
    C1 -->|Raft 复制| C3
    C1 -->|写入| MetaLog
    MetaLog -.->|元数据增量同步| B1
    MetaLog -.->|元数据增量同步| B2
    MetaLog -.->|元数据增量同步| B3

    style C1 fill:#e6ffe6
    style C2 fill:#e6f0ff
    style C3 fill:#e6f0ff
  • Controller 选举：奇数个 Controller 节点组成 Raft Quorum，通过 Raft 协议选出唯一的 Active Controller；
  • 元数据日志：所有元数据变更作为消息追加到单分区的 __cluster_metadata 日志中；
  • 部署形态：小集群可合设 process.roles=broker,controller；生产推荐独立 Controller Quorum。

9.3 版本演进与现状

  • 2.8 引入 KRaft 预览（KIP-500）；
  • 3.0 支持新集群使用；3.3 正式 GA；
  • 3.5 起 ZooKeeper 模式标记为废弃；
  • Kafka 4.0 已彻底移除 ZooKeeper。

面试结论：新集群一律用 KRaft，ZooKeeper 模式已退出历史舞台。

10. 实战排障：消息积压、重复消费、Leader 抖动

10.1 消息积压

flowchart TB
    Start[消息积压] --> S1[kafka-consumer-groups.sh --describe<br/>看各分区 Lag]
    S1 --> S2{Lag 分布}
    S2 -->|均匀增长| S2a[整体消费能力不足<br/>扩容消费者]
    S2 -->|集中在少数分区| S2b[分配不均或 key 热点<br/>检查分区策略]
    S2 -->|伴随频繁 Rebalance| S2c[max.poll.interval.ms 超时<br/>调大或优化单条处理速度]

处理手段（按优先级）：

  1. 扩容消费者：加到分区数为止；
  2. 提升单条处理速度：批量化、异步化、优化下游；
  3. 调参：fetch.min.bytes / fetch.max.wait.ms 攒批拉取；
  4. 极端情况临时跳堆：seekToEnd() 跳过积压（只适用于可丢场景）；
  5. 长期方案：拆 Topic、增加分区、改造消费链路。

10.2 重复消费

定位原因：

  • 看 ConsumerRebalanceListener 的 revoke/assign 日志；
  • 看是否 max.poll.interval.ms 超时踢组；
  • 看 offset 提交代码是否在异常路径漏提交。

处理：

  • 手动提交且处理成功后再提交；
  • 小批量频繁提交，缩小重复窗口；
  • 静态成员（group.instance.id）减少非必要 Rebalance；
  • 业务幂等兜底是最终防线。

10.3 Leader 抖动

现象：kafka-topics.sh --describe 看到 ISR 反复收缩扩大，伴随 UnderReplicatedPartitions 指标抖动。

常见根因：

  • 网络抖动：Follower 拉取超时被移出 ISR；
  • Broker 负载过高 / Full GC；
  • 磁盘慢；
  • 配置过紧。

排查与处理：查 Broker 日志中的 “ISR shrinks/expands”，对应时间点查 GC 日志、网络重传、磁盘 IO 等待；对慢盘下线隔离；把 replica.lag.time.max.ms 适度调大。

10.4 消费失败重试与死信队列

先澄清：Kafka Broker 没有原生死信机制。死信是消费者侧的一种通用模式：**重试 N 次仍失败的消息，写入一个专门的”死信 Topic”**。

面试一句话：Kafka 的可靠性链路是”acks=all + ISR + 手动提交”保证不丢，业务侧”幂等去重”保证不重，处理失败的消息用”重试 Topic + 死信 Topic”隔离兜底，死信必须有告警和人工介入。

11.1 Producer 参数优化表

参数 默认值 作用 调优建议

11.3 常见性能问题

Producer 发送慢 / 吞吐低：

  • 检查攒批参数：batch.size 和 linger.ms 是否太小；
  • 日志报 TimeoutException：看 buffer.memory 是否打满；
  • 单分区写入是瓶颈：增加分区数；
  • 对照检查压缩率。

Consumer 消费慢 / 消息积压：

  • 实例数 < 分区数：消费并发上限就是分区数；
  • 单条处理慢：批处理、异步化、优化下游；
  • 拉取效率低：fetch.min.bytes 太小。

11.4 延时队列在 Kafka 中的实现方案

Kafka 原生没有 RocketMQ 那种”延迟消息”功能，生产实现普遍是业务侧方案：

方案一：时间轮 + 延迟 Topic：专门建一个 delay-topic，消息体里携带”目标执行时间”；延迟消费者 poll 出来后判断是否到期，未到期就不提交并睡眠等待，到期后写入真正的业务 Topic。

方案二：分级延迟 Topic（生产常用） ：按档位建多个延迟 Topic：delay-5s、delay-30s、delay-1m、delay-10m、delay-1h……每档一个消费者，到期即转投下一级或业务 Topic。

flowchart LR
    P[Producer] --> D5[delay-5s]
    D5 -->|5s 到期| Biz[业务 Topic]
    D5 -->|未到期留在本档| D5
    D5 -->|已超 30s| D30[delay-30s]
    D30 --> Biz
    Biz --> C[业务消费者]

12. 面试速答表

面试题 一句话答案
Kafka 定位？ 分布式事件流平台，消息写入 append-only log，消费不删除，按保留策略过期
Topic / Partition / Replica 关系？ Topic 逻辑分类，Partition 物理切分，Replica 副本分布在不同 Broker
ISR 是什么？ 与 Leader 保持同步的副本集合，只有 ISR 中的副本才有资格当选新 Leader
Controller 和 Coordinator 区别？ Controller 管集群元数据，Coordinator 管消费者组成员关系和 offset
为什么 Kafka 快？ 顺序写 + PageCache + 零拷贝 + 批量压缩 + 分区并行
零拷贝是完全没有拷贝吗？ 不是，是没有 CPU 参与的拷贝，DMA 拷贝仍然存在
消息不丢怎么保证？ acks=all + min.insync.replicas=2 + 手动提交 offset
acks=all 一定不丢吗？ 不一定，ISR 只剩 Leader 时退化为 acks=1，需要 min.insync.replicas 卡底线
LEO 和 HW 的区别？ LEO 是副本下一条待写入位置，HW 是所有 ISR 副本 LEO 的最小值，消费者只能读 HW 以下
消息重复怎么解决？ 幂等生产者 + 消费端业务去重（唯一约束/条件更新）
幂等和事务的区别？ 幂等是去重（单分区），事务是原子性（多分区）；跨外部系统靠业务幂等兜底
如何保证消息有序？ 同一 key 哈希到同一分区，分区内有序；全局有序只能单分区
Rebalance 触发条件？ 成员变化、分区数变化、订阅变化、max.poll.interval.ms 超时
如何减少 Rebalance？ CooperativeStickyAssignor + 静态成员 group.instance.id
KRaft 是什么？ 去掉 ZooKeeper，Controller Quorum 通过 Raft 管理元数据，Kafka 4.0 已移除 ZK
消息积压怎么处理？ 先看 Lag 分布（均匀 vs 集中），再扩容消费者/提升单条处理速度/调参
死信队列怎么实现？ Kafka 没有原生死信，消费者侧重试 N 次后写入专门死信 Topic
分区数怎么规划？ 先估单分区吞吐（5~10 MB/s），按总吞吐定分区数；单 Broker 数千分区以内
延时队列怎么实现？ 时间轮 + 延迟 Topic，或分级延迟 Topic（生产常用）

全文因果链回顾：

  1. 定位：Kafka 不是传统 MQ，是事件流平台 → 消息保留 + 多组独立消费；
  2. 概念：Topic/Partition/Replica/ISR → 逻辑与物理的映射；
  3. 高吞吐：顺序写 + PageCache + 零拷贝 + 批量压缩 + 分区并行；
  4. 可靠性：acks=all + min.insync.replicas + 手动提交 → 三环节不丢；
  5. 不重复：幂等 + 消费端去重 + 事务 → at-least-once 到 exactly-once；
  6. 顺序性：同一 key 哈希到同一分区 → 业务级有序；
  7. 消费者组：Rebalance 是积压头号元凶 → CooperativeSticky + 静态成员减少停顿；
  8. KRaft：ZooKeeper 已移除 → Controller Quorum 通过 Raft 管理元数据。
