一次请求的成本账：RTT、事件循环与命令执行

Posted on 2026-10-25 In 数据存储 Word count in article: 3.7k Reading time ≈ 14 mins.

一次 GET 从客户端看是 87 微秒，而 Redis 自己执行它只花了 0.07 微秒。剩下的 99.9% 全是网络往返、内核拷贝和排队。这个 0.08% 的比例，就是本文要算的账——它决定了你的优化到底该动哪里。

本文用四组对照实验把一次请求拆开：传输层（TCP / Unix socket）、payload 大小（64B → 1MB）、pipeline 深度（1 → 64）、io-threads（1 → 4）。全部在 Redis 7.4.11 容器里实测，客户端与服务端同机。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账（本文） → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：① 测出「一次往返 31 微秒、GET 87 微秒」，本文解释这两组数差在哪；⑥ 会把 pipeline 的工程化用法（批量、事务、Lua）讲透，本文只量它的成本。

1. 把一次 GET 拆开

1.1 实测：服务端只占 0.08%

用 INFO commandstats 读服务端自己统计的每命令耗时（usec_per_call），与客户端 p50 对照：

命令 服务端 usec_per_call 客户端 p50（50 连接） 服务端占比
PING 0.04 µs 0.031 ms（单连接） ~0.13%
GET 0.07 µs 0.087 ms 0.08%
SET 0.10 µs 0.087 ms 0.11%

Redis 快到这里已经没什么可优化的了——你不可能把 0.07 微秒优化成 0.007 微秒，那对 87 微秒的总耗时毫无意义。真正的大头在别处。

1.2 四段成本模型

flowchart LR
    A["Client serialize<br/>+ syscall write"] --> B["Kernel<br/>TCP / unix socket"]
    B --> C["epoll wakeup<br/>+ command parse"]
    C --> D["Execute<br/>0.07us"]
    D --> E["Reply write<br/>+ syscall"]
    E --> F["Client parse"]
段 成本量级 你能改什么 本文实验
客户端序列化 + 系统调用 几微秒 减少调用次数 pipeline
内核传输（TCP / unix） 10~30 µs（同机） 换 unix socket、长连接 实验一
epoll 唤醒 + 命令解析 1~5 µs 减少命令数、避免大命令 实验四
命令执行 0.07 µs 几乎无法优化 —
回复传输 与 payload 成正比 减小 value 实验二

这张表就是全文的结论：优化 Redis 请求，改的是「段数」和「每段的字节数」，不是「执行速度」。

1.3 深挖：为什么单连接 PING 是 31 µs，50 连接 GET 是 87 µs

两者的差值不是「GET 比 PING 慢」，而是排队：

配置 并发 观测值 主要成本
PING，1 连接 1 31 µs/次 纯 RTT（客户端→内核→Redis→回来）
GET，50 连接 50 87 µs/次 RTT + 事件循环排队 + 客户端侧调度

50 个连接同时发命令时，Redis 单线程要串行处理 50 条，第 50 条的等待时间里包含了前 49 条的处理时间。并发越高，单次延迟里「排队」的占比越大——这就是 ⑤ 要展开的「单线程排队」。

1.4 动手验证：拿到你自己的服务端执行时间

预期观察点：usec_per_call 都在 0.05~0.2 µs 之间；如果你的 Redis 上这个值到了几十微秒，说明有慢命令（如 HGETALL 大 hash）。

判定标准：

  • usec_per_call < 1 µs → 服务端不是瓶颈，去查 RTT 与命令数；
  • usec_per_call > 10 µs → 命令本身重（大 key / 复杂命令），去 ③⑤；
  • 客户端 p50 / 服务端 usec_per_call < 100 → 你的优化空间几乎全在网络层。

2. 变量一：传输层

2.1 实测：Unix socket 快 36%

传输 PING 吞吐（50 连接） 相对
TCP 127.0.0.1:6379 295,858 rps 1.00×
Unix socket /tmp/redis.sock 403,226 rps 1.36× 
flowchart LR
    subgraph TCP["TCP path"]
        C1["client"] --> K1["TCP stack<br/>checksum, ack, Nagle"] --> R1["redis"]
    end
    subgraph UNIX["Unix socket path"]
        C2["client"] --> K2["kernel socket buffer<br/>no TCP state machine"] --> R2["redis"]
    end

2.2 深挖：TCP 栈多做了什么

同样是 loopback，Unix socket 省掉的是：

开销 TCP Unix socket
连接状态机 三次握手、四次挥手、TIME_WAIT 无
校验和 每包计算 无
拥塞控制 / 滑动窗口 有 无
Nagle 算法 可能攒包（延迟确认叠加更糟） 无
端口资源 每连接占一个本地端口 无

loopback 上 36% 的差距，换成跨机房会更大——因为跨机房时 RTT 由物理距离主导，而 Unix socket 根本不允许跨机。

生产上的结论很干脆：

场景 选择 理由
应用与 Redis 同机 / 同 Pod Unix socket 省 30%+ 的延迟，还省端口
同机房跨机 TCP + 长连接 无法用 unix socket
跨机房 TCP + 长连接 + 就近部署 RTT 是物理常量，优化不了，只能减少次数

2.3 动手验证：量一次两种传输的差

预期观察点：-s 那一组高 20%~40%（本文 36%）。

判定标准：

  • 两组差距 < 10% → 你的瓶颈不在传输层，别折腾 socket；
  • -s 报 Could not connect → --unixsocketperm 没给够（容器内外用户不同）。

3. 变量二：payload 大小

3.1 实测：从 RTT 主导切到带宽主导

value 大小 SET rps GET rps GET p50 估算带宽
64 B 274,725 318,471 0.087 ms ~20 MB/s
1 KB 294,118 308,642 0.087 ms ~300 MB/s
100 KB 29,586 37,313 0.247 ms ~3.7 GB/s
1 MB 2,915 3,431 0.495 ms ~3.4 GB/s 
flowchart LR
    A["64B-1KB<br/>QPS flat ~310k<br/>RTT bound"] --> B["100KB<br/>QPS 37k<br/>~3.7 GB/s"]
    B --> C["1MB<br/>QPS 3.4k<br/>~3.4 GB/s"]

3.2 深挖：为什么 64B 到 1KB 吞吐完全不变

因为这一段根本没碰到带宽上限：1 KB × 31 万 = 300 MB/s，离 loopback 的 3.5 GB/s 差一个数量级，瓶颈还是每次请求的 RTT 与调度。

到了 100 KB，一条命令就是 100 KB 的内存拷贝 + 系统调用，带宽打满 → 吞吐掉到 1/8。注意 p50 只从 0.087 ms 涨到 0.247 ms（2.8 倍），而吞吐掉了 8.3 倍——因为并发 50 个连接时，大 payload 让吞吐先崩，延迟后崩。

3.3 深挖：大 value 的三重代价

代价 机制 影响
带宽 每次请求拷贝 payload 吞吐断崖（本文 8.3 倍）
内存 value 大 → jemalloc 大块分配 → 碎片 ④ 展开
阻塞 拷贝 1 MB 期间单线程在忙 其他请求排队（⑤）

生产判据：单 value 超过 10 KB 就要警惕，超过 100 KB 基本是设计问题——拆成 hash 分片，或者干脆别放 Redis。

3.4 动手验证：找到你自己的「带宽拐点」

预期观察点：吞吐在某个体积之后开始线性下降，那个点就是你的带宽拐点。

判定标准：

  • 拐点在 10 KB 以内 → 你的网络很差（跨机房），必须减小 value；
  • 拐点在 1 MB 之后 → loopback 或万兆内网，value 大小不是主要矛盾。

4. 变量三：pipeline 深度

4.1 实测：4 倍深度换 3.4 倍吞吐

pipeline 深度 SET rps GET rps GET p50 相对 P=1
1 297,619 308,642 0.087 ms 1.0×
4 1,020,408 1,086,957 0.095 ms 3.5×
16 3,124,999 3,571,429 0.167 ms 11.6×
64 4,170,667 5,560,889 0.479 ms 18.0×

4.2 深挖：pipeline 拿延迟换吞吐

sequenceDiagram
    participant C as Client
    participant R as Redis
    Note over C,R: P=1: 4 commands = 4 round trips
    C->>R: cmd1
    R-->>C: ok
    C->>R: cmd2
    R-->>C: ok
    Note over C,R: P=4: 1 round trip, buffered
    C->>R: cmd1..cmd4
    R-->>C: 4 replies

p50 从 87 µs 涨到 479 µs（5.5 倍），因为第一条命令要等整批发完、处理完才回来。所以：

场景 该用 pipeline 吗
批量写 1000 条用户行为 该，深度 16~100
一次读 100 个 key 的详情页 该，用 MGET 或 pipeline
每次只取一个值、取完立刻算 不该，p50 会翻几倍
事务（MULTI/EXEC） 必须配合 pipeline 才有意义（⑥）

一个常被忽略的点：pipeline 深度不是越大越好。P=16 时 p50 0.167 ms、吞吐 11.6 倍；P=64 时吞吐只多 55%，p50 却再涨 2.9 倍。工程上 16~32 是甜点区。

4.3 动手验证：量出你的甜点区

预期观察点：吞吐在 P=16~32 接近平台，p50 持续上升。

判定标准：

  • 吞吐在 P=4 就平台化 → 你是 CPU 或带宽瓶颈，不是 RTT；
  • p50 超过业务超时的 1/10 → 深度太大了，降到 16。

5. 变量四：io-threads

5.1 实测：小 value 场景没有收益

CONFIG SET io-threads 4 + io-threads-do-reads yes 之后（1 KB value）：

配置 SET rps GET rps p50
io-threads=1 294,118 308,642 0.087 ms
io-threads=4 287,356 299,401 0.087 ms

差异在噪声范围内，甚至略低。

5.2 深挖：io-threads 什么时候才有用

io-threads 把「读 socket、解析协议、写回复」这些 IO 工作分给多个线程，但命令执行仍然是单线程。所以：

场景 io-threads 有用吗 原因
小 value、高 QPS 没用（本文实测） 瓶颈在 RTT 和事件循环，IO 线程不是瓶颈
大 value、带宽打满 有用 拷贝与协议解析是主要成本
多核机器 + 大量连接 有用 分摊 epoll 与 read/write 系统调用

一个必须知道的配置：io-threads 只是设了线程数，io-threads-do-reads yes 才会让读操作也走多线程（默认 no，只多线程写）。很多人只改了前一个，然后说「开了没用」。

5.3 动手验证：验证 io-threads 是否真的生效

预期观察点：io_threads_active:1（真正生效）；1 MB value 场景下吞吐应有提升，小 value 场景基本不变。

判定标准：

  • io_threads_active:0 → 没生效，检查是否只设了 io-threads 没设 io-threads-do-reads；
  • 小 value 场景提升 < 5% → 正常，别指望它解决 RTT 问题。

6. 成本账怎么用

6.1 四个变量的优先级

变量 收益上限（本文实测） 代价 什么时候动
pipeline 18×（P=64）/ 11.6×（P=16） p50 上升 批量场景，第一优先
payload 减小 8~10×（100KB → 1KB） 改数据模型 value 超过 10 KB 时
unix socket 1.36× 只能同机 同机部署时
io-threads < 5%（小 value）/ 有（大 value） 多线程复杂度 带宽打满时

6.2 判断流程

症状 先动哪个变量
QPS 上不去、单次延迟低 pipeline 或加并发
单次延迟高、QPS 上不去 查 payload 大小与慢命令
同机部署但延迟仍高 换 unix socket
CPU 单核 100% 且 value 大 io-threads

6.3 与 MySQL 系列的对照

维度 MySQL（②） Redis（本文）
服务端执行占比 SELECT 1 10.8 µs，占比高 0.07 µs，占比 0.08%
主要成本 逻辑读（页） 网络往返（次）
第一个倍增器 索引 pipeline
第二个倍增器 覆盖索引 减小 payload

同一套方法论，不同的成本项：MySQL 优化「读多少页」，Redis 优化「发多少次、每次多大」。

7. 总结

7.1 面试速答表

面试题 一句话答案
Redis 一次请求的时间花在哪 99.9% 在传输与排队，命令执行只占 0.08%（实测 0.07 µs / 87 µs）
为什么 PING 只要 31 µs 而 GET 要 87 µs 后者是 50 连接并发，多了排队；单连接下两者都接近 RTT
Unix socket 比 TCP 快多少 同机实测 1.36 倍，省掉 TCP 状态机与校验和
value 从 1KB 涨到 100KB 会怎样 吞吐掉 8.3 倍（从 RTT 主导切到带宽主导）
pipeline 为什么能提升 18 倍 把 N 次 RTT 合成 1 次；但 p50 上升 5.5 倍，是拿延迟换吞吐
pipeline 深度多少合适 16~32；P=64 只多 55% 吞吐，p50 再涨 2.9 倍
io-threads 为什么常常没用 命令执行仍是单线程；小 value 场景瓶颈在 RTT，不在 IO
io-threads-do-reads 是什么 让读也走多线程，默认 no；不设它 io-threads 只作用于写
大 value 有什么代价 带宽、内存碎片、单线程拷贝阻塞，三重叠加
怎么判断瓶颈在网络还是执行 对比客户端 p50 与 INFO commandstats 的 usec_per_call

7.2 实战避坑表

症状 原因 处理
开了 io-threads 没效果 只设了线程数，没开 io-threads-do-reads 两个都设，用 INFO threads 确认
pipeline 之后接口反而变慢 单条请求要等整批返回 只对批量接口用，或降低深度
QPS 上不去但 CPU 不满 RTT 或客户端侧瓶颈 加 pipeline、减少命令数
单次延迟突然到几百毫秒 有大 value 或大 key --bigkeys、SLOWLOG
同机部署延迟仍高于预期 走了 TCP 而非 unix socket 换 -s 连接
压测数字漂亮但线上差 压测同机 loopback，线上跨机 RTT 高 按真实 RTT 折算 pipeline 收益

7.3 工具速查表

工具 看什么 判定标准
INFO commandstats usec_per_call > 1 µs 说明命令本身重
redis-benchmark -P pipeline 深度对吞吐/p50 吞吐平台化 + p50 上升 = 到甜点区
redis-benchmark -d payload 大小 吞吐线性下降 = 带宽瓶颈
redis-benchmark -s unix socket 比 TCP 高 20%~40% 才正常
INFO threads io_threads_active 0 = 没生效
SLOWLOG 超过阈值的命令 出现大 value 命令就要拆

7.4 实操建议

  1. 先算比例：客户端 p50 除以 usec_per_call，如果大于 100，说明优化空间在网络层，别去改数据结构。
  2. 批量场景优先上 pipeline，深度 16~32，并用 p50 验证没有超时风险。
  3. value 控制在 10 KB 内，超过就考虑拆 hash 或换存储。
  4. 同机部署优先 unix socket，这是零成本的 30%。
  5. io-threads 只在带宽打满时开，并且两个参数一起设。

下一篇预告：③《数据结构：编码阈值与复杂度的真实代价》。本文说「命令执行只花 0.07 微秒」，但那是 GET——下一篇换成一个 hash 从 128 个 field 涨到 129 个，同样的 HSET 为什么会突然变慢、内存为什么会翻倍，以及为什么「用 hash 存对象的 1000 个字段」有时比 1000 个 string 更省内存。
