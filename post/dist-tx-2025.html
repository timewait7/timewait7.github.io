分布式事务：从 2PC 到 Seata

Posted on 2026-08-13 In 分布式 Word count in article: 3.9k Reading time ≈ 14 mins.

「一个订单要扣库存、减余额、记流水，三个服务各有一个数据库，怎么保证要么全成要么全不成？」 单库事务到此失效——这不是代码问题，是「跨系统无原子性」的架构问题。本文从 2PC 的起源讲到 Seata 的落地：为什么教科书级的 XA 没人敢生产用、TCC 为什么是「业务自己写三阶段」、Saga 为什么是「一条补偿链」、以及 Seata AT 模式怎么用「全局锁 + undo 日志」做到业务零侵入。读完你能在方案评审会上说清「这个场景该用 Seata 的哪种模式、为什么」。

联动：本文是 分布式系统核心理论（CAP/BASE/一致性模型）的落地篇；事务消息方案与 ES 查询优化与实战 的本地消息表、RocketMQ 原理与实践 的事务消息同源；Seata 全局锁与 MySQL 事务原理与实践 的锁语义直接相关。

1. 定位：为什么需要分布式事务

单库事务失效的场景：微服务拆分后，「一次业务操作」跨多个服务、多个数据库，每个库自己的事务管不到别的库——「扣库存成功、减余额失败」就成了可能。

术语 一句话定义
本地事务 单个数据库内的事务（ACID）
分布式事务 跨多个数据库/服务，保证「全成或全不成」的事务
全局事务 分布式事务的总称，与「分支事务」相对
分支事务 各参与者的本地事务
协调者 统筹全局事务提交/回滚的角色

核心矛盾一句话：分布式事务的本质是「在无单点权威的分布式系统里，模拟一个全局的原子性」——但 CAP 定理说可用性、一致性、分区容错只能三选二，任何分布式事务方案都是在「牺牲一部分可用性/性能」换「全局一致」。记住这条，所有方案的取舍都能自己推出来（理论细节见 分布式系统核心理论）。

2. 2PC：两阶段提交的由来与代价

2.1 两阶段：准备 + 提交

sequenceDiagram
    participant C as 协调者
    participant A as 服务A(扣库存)
    participant B as 服务B(减余额)
    C->>A: 1. Prepare：能提交吗？
    C->>B: 1. Prepare：能提交吗？
    A-->>C: 2a. 可以（资源已锁）
    B-->>C: 2b. 可以（资源已锁）
    C->>A: 3. Commit / Rollback
    C->>B: 3. Commit / Rollback

阶段一 Prepare：协调者问每个参与者「能提交吗」，参与者执行本地事务但不提交，资源加锁，回复「可以」或「不行」。阶段二 Commit：全票通过 → 广播 Commit；有人拒绝或超时 → 广播 Rollback。

因果链：2PC 用「先锁定资源、后统一提交」实现原子性——但「锁定」是全部代价的来源：Prepare 阶段开始，所有参与者的资源一直锁着，直到阶段二结束，锁的时长 = 最慢参与者的响应时间，这就是「2PC 阻塞性」的根源。

2.2 三个致命问题（面试核心）

问题 场景 后果
阻塞 某参与者慢/挂 所有参与者资源一直锁着，拖垮全局吞吐
单点 协调者挂了 参与者不知提交还是回滚，永远等（无超时自决）
脑裂风险 阶段二网络分区 部分 Commit、部分回滚不了，数据不一致

面试必答话术：2PC（XA）是教科书方案，但三个问题让它生产上没人敢直接用——「阻塞 + 单点 + 脑裂」，本质是「把单点权威（协调者）引入分布式系统，权威自己却不可靠」。XA 协议（数据库原生支持）是 2PC 的标准实现，但因为上述原因，互联网公司几乎不用 XA，改用下面「业务化的 2PC」。

3. 3PC：多一轮预提交，解决了一半

3.1 三阶段：CanCommit → PreCommit → DoCommit

flowchart LR
    A["CanCommit<br/>先问可行性<br/>（无锁）"] --> B["PreCommit<br/>锁定资源<br/>（有超时）"] --> C["DoCommit<br/>统一提交"]

3PC 把阶段一拆成两步：

阶段 动作 与 2PC 的差异
CanCommit 问「能不能提交」（不动资源） 提前排除不可行者，缩短锁定窗口
PreCommit 锁定资源、写日志 参与者多了超时自决能力
DoCommit 提交 参与者超时后可自行提交（默认提交）

3.2 解决了什么、没解决什么

解决：参与者有超时自决机制（协调者失联超时后默认提交），缓解了协调者单点导致的无限阻塞。

没解决：超时默认提交引入新风险——协调者其实要回滚，但参与者已经提交了（网络分区下的两难：等=永远阻塞，自决=可能错）。因果链：3PC 用「减少等待」换「增加出错概率」，所以实际使用比 2PC 还少。记住结论即可：3PC 是学术改进，工程上几乎无人用，面试提到「知道它存在、知道它为什么没人用」就够了。

4. TCC：业务自己写三阶段

4.1 Try / Confirm / Cancel

TCC 是「业务化的 2PC」：不依赖数据库锁，让业务接口自己实现三个动作：

阶段 接口 业务示例（余额服务）
Try 预留资源 冻结 100 元（frozen=100，可用余额不变）
Confirm 确认提交 扣减：冻结-100，可用余额-100
Cancel 取消回滚 解冻：冻结-100，可用余额不变 
flowchart TD
    S[发起方] --> T[Try 全部成功] --> C[Confirm 全部执行] --> D[事务成功]
    T -->|任一 Try 失败| X[Cancel 全部执行] --> E[事务回滚]

4.2 TCC 的三道坎（面试深水区）

坎 问题 解法
空回滚 网络重试导致 Try 没到、Cancel 先到 Cancel 幂等 + 记录事务状态
悬挂 Try 迟到（Cancel 已完成后又来 Try） 状态机校验：已 Cancel 的事务拒绝再 Try
幂等 Confirm/Cancel 被重试执行多次 接口幂等（状态字段/版本号）

因果链：TCC 把「锁」从数据库换成了「业务预留」，不阻塞数据库、并发能力强——但代价是业务要自己写三个接口、处理空回滚/悬挂/幂等三道坎。适用场景：强一致要求高、并发大的资金类操作（账户冻结/库存预留）。面试加分点：主动说出「TCC 的三个空回滚场景」而不是只说『Try Confirm Cancel 三阶段』。

5. Saga：一条补偿链

5.1 正向执行 + 反向补偿

Saga 的核心思想：不预留、不锁定，只管正向执行；哪一步失败，就把前面所有步骤「反向补偿」一遍：

flowchart LR
    S1[扣库存] --> S2[减余额] --> S3[记流水]
    S3 -->|失败| C2[补偿：余额+100] --> C1[补偿：库存+1]
维度 特点
无锁 每步直接提交本地事务，不锁定资源
补偿 反向执行取消操作（库存加回、余额退回）
编排 两种：编排式（中心化一个 Saga 引擎指挥）/ 协同式（每个服务监听事件自己接下一棒）
一致性 最终一致（中间状态对别的事务可见）

5.2 与 TCC 的分工（面试必考）

对比 TCC Saga
预留 有（Try 冻结） 无（直接提交）
一致性窗口 短（Try→Confirm 之间） 长（全程都可能被看到中间态）
适用 强一致 + 高并发（资金） 弱一致可接受 + 长流程（订单/旅行预订）
补偿方式 Cancel 恢复预留 反向业务操作

一句话分工：TCC 适合「必须强一致但并发又高」的短操作；Saga 适合「可以最终一致」的长流程。资金用 TCC，订单/活动用 Saga——面试被问「TCC 和 Saga 怎么选」，先问一句「业务能接受最终一致吗」，答案自然出来。

6. Seata AT：全局锁 + undo 日志的「无侵入」方案

6.1 AT 模式的两件武器

AT（Auto Transaction）模式 = 自动化的 2PC：业务代码几乎不用改（只加 @GlobalTransactional），Seata 用两个机制替你完成全局原子性：

武器一：undo_log 快照。每个分支事务执行前，Seata 拦截 SQL，把「改动前的数据镜像」写入 undo_log 表；全局回滚时用镜像反向执行 UPDATE/DELETE 把数据改回去——相当于自动生成 Cancel。

武器二：全局锁。事务执行期间，Seata 锁定被改动的主键记录，其他全局事务改到同一记录必须等待，防止两个事务互相覆盖导致回滚错乱。

sequenceDiagram
    participant A as 业务应用
    participant TC as TC(全局事务协调)
    participant RM as RM(分支1: 订单库)
    participant RM2 as RM(分支2: 库存库)
    A->>TC: 1. 开启全局事务（XID）
    A->>RM: 2. 分支注册 + 执行 SQL + 写 undo_log
    A->>RM2: 3. 分支注册 + 执行 SQL + 写 undo_log
    A->>TC: 4. 提交全局事务
    TC->>RM: 5. 删 undo_log，提交
    TC->>RM2: 5. 删 undo_log，提交
    Note over TC: 任一步失败 → 各分支按 undo_log 反向执行回滚

6.2 AT 与 TCC 的对比（生产选型核心）

维度 Seata AT TCC
业务改造 零侵入（注解 + 建 undo_log 表） 手写 Try/Confirm/Cancel 三接口
锁粒度 行级（改哪锁哪） 业务预留（可按资源冻结）
性能 有 undo_log 写入开销 无日志开销，纯业务
场景 通用（大部分业务） 资金强一致 + 高并发
侵入度 全局事务是「两阶段」，冲突时等待 无等待，但代码多

因果链：AT 用「undo_log 自动补偿 + 全局锁防冲突」模拟出 2PC 的效果，把复杂度从业务代码搬进了中间件——这就是它成为生产主流的根本原因。代价是全局锁的等待开销：长事务会拖慢并发，所以 AT 也要求分支事务「短」。

6.3 动手验证：本地跑一个 Seata 最小闭环

观察点：@GlobalTransactional 方法内两个库的写操作，在第二个库抛异常时第一个库的写入被自动回滚（undo_log 反向执行）。判定标准：亲手验证「库存减了但订单插入失败 → 库存被回滚」的完整闭环，理解「业务零侵入」的真实含义。

7. 方案选型：一张决策树

7.1 决策流程

flowchart TD
    Q1{业务能接受最终一致吗？} -->|能| Q2{有现成 MQ 吗？}
    Q2 -->|有| MQ[事务消息/本地消息表<br/>推荐：最简单]
    Q2 -->|无| SAGA[Saga 补偿链]
    Q1 -->|不能，要强一致| Q3{事务短且并发高？}
    Q3 -->|是| TCC[Seata AT / TCC<br/>按侵入度选]
    Q3 -->|否| AT[Seata AT<br/>通用首选]

7.2 决策表

业务特征 首选方案 理由
弱一致可接受 + 有 MQ 事务消息/本地消息表 最简单、无中间件依赖（RocketMQ 事务消息）
弱一致 + 长流程 Saga 无锁、适合订单/旅行
强一致 + 通用业务 Seata AT 零侵入、行级锁
强一致 + 极高并发资金 TCC（或 AT + 短事务） 业务预留不阻塞库
同库多表 本地事务 别引分布式事务（最常见优化）

一句话选型：「能最终一致就消息，必须强一致就 Seata；Seata 里短事务用 AT、资金类用 TCC」。另外记住反模式：能在一个库里解决的（同库多表）绝不上分布式事务——很多「分布式事务」其实是表设计/服务拆分问题。

8. 面试应答：分布式事务六连问

8.1 完整话术

面试题 回答要点
2PC 是什么？ 准备+提交两阶段；先锁资源后统一提交；阻塞、协调者单点、脑裂三个问题，生产不用
XA 为什么没人用？ XA 是 2PC 标准实现，数据库锁资源时长=最慢参与者，互联网高并发场景扛不住
TCC 三阶段？ Try 预留 → Confirm 确认 → Cancel 回滚；注意空回滚/悬挂/幂等三道坎
TCC 和 Saga 区别？ TCC 预留锁、强一致、短操作；Saga 无锁直接提交、最终一致、长流程补偿链
Seata AT 原理？ undo_log 快照反向回滚 + 全局锁防冲突；业务零侵入（注解+建表）
怎么选型？ 能最终一致→消息；必须强一致→Seata（AT/TCC 按并发与侵入度）

8.2 深挖：与本地消息表/事务消息的对照（跨篇联动）

维度 2PC/Seata 本地消息表 事务消息（RocketMQ）
一致性强度 强一致（有锁/快照） 最终一致 最终一致
业务侵入 注解（AT）/ 三接口（TCC） 写一张消息表 一个事务消息接口
消息可靠性 无消息 消息与业务同事务 MQ 半消息+回查
适用 强一致场景 无 MQ 时的替代 有 MQ 时首选

因果链：本地消息表和事务消息的本质是「把『发消息』和『业务写』放进同一个本地事务」，用『消息一定会到』换『跨库强一致』（ES 查询优化与实战 的 Canal 同步用的就是这套思路）。面试答「消息最终一致」，能说出「消息表保证消息不丢 + 消费端幂等保证不重」两层，就是完整答案。

9. 总结

9.1 面试速答表

面试题 一句话答案
分布式事务是什么？ 跨多个库/服务保证「全成或全不成」，本质是无单点权威下模拟全局原子性
2PC 流程？ Prepare 锁定资源 → 全票通过 Commit / 任一拒绝 Rollback
2PC 三个问题？ 阻塞（锁时长=最慢者）、单点（协调者挂）、脑裂（分区后不一致）
3PC 改进了什么？ CanCommit 先问可行性 + 参与者超时自决；但自决可能提交错，工程无人用
TCC 三道坎？ 空回滚（Cancel 先到）、悬挂（Try 迟到）、幂等（重试）
Saga 是什么？ 无锁正向执行，失败逐级反向补偿；编排式/协同式
Seata AT 原理？ undo_log 快照自动反向回滚 + 全局锁防覆盖，业务零侵入
怎么选？ 最终一致→消息；强一致→Seata；资金高并发→TCC；同库→本地事务

9.2 实战避坑表

症状 原因 处理
全局事务回滚了但数据没回来 undo_log 表没建/被删 建 undo_log 表；检查表结构一致
事务极慢 全局锁等待长事务 分支事务必须短；改 TCC 或消息方案
同库多表也上了 Seata 方案滥用 同库用本地事务，别引分布式事务
TCC Cancel 执行了两次 网络重试 Cancel 接口幂等
消息最终一致丢数据 消息表/事务消息没兜底 消费端幂等 + 重试队列 + 对账
Seata 版本升级不兼容 undo_log 字段差异 按对应版本建表脚本执行

9.3 工具速查表

工具 用途
Seata（AT/TCC/Saga） 分布式事务主流框架，AT 零侵入
RocketMQ 事务消息 消息最终一致首选
本地消息表 无 MQ 时的最终一致替代
XA（数据库原生） 2PC 标准实现，了解即可
Saga 引擎（Seata Saga/自研） 长流程编排
