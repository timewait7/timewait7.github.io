从输入 URL 到页面展示全链路

Posted on 2026-08-13 In 计算机网络 Word count in article: 3.5k Reading time ≈ 13 mins.

从输入 URL 到页面展示，是一次横跨五层模型、四个网络环节、两个进程域的完整旅程：DNS 解析、TCP 握手、TLS 协商、HTTP 请求、服务端处理、响应渲染——每一站都在前四篇讲过机制，本文把这条链完整走一遍：每一步消耗多少个 RTT、卡在哪个队列、优化的杠杆在哪。读完你会获得一张「全链路地图」：任何页面慢的问题，都能钉在图上某一站，说出它背后的机制和改法。

系列地图（计算机网络）：① 网络分层（网络长什么样）→ ② TCP 协议（可靠传输与代价）→ ③ HTTP 协议（应用层之王）→ ④ DNS 与网络排查实战（工具收拢）→ ⑤ 本文：全链路串讲，系列收官。

1. 全链路总览：一次请求的完整旅程

1.1 全景图：十二个环节

sequenceDiagram
    participant B as Browser
    participant D as DNS resolver
    participant S as Server
    B->>D: 1. resolve example.com (T1: DNS)
    D-->>B: IP + TTL (T1 done, cached)
    B->>S: 2. SYN (T2: TCP handshake, 1 RTT)
    S->>B: SYN+ACK
    B->>S: ACK
    B->>S: 3. TLS ClientHello (T3: TLS, 1-2 RTT)
    S->>B: ServerHello + cert
    B->>S: keys (T3 done)
    B->>S: 4. GET / HTTP/1.1 (T4: request/response, 1+ RTT)
    S-->>B: 200 + body (T4 done)
    Note over B: 5. parse & render (T5: local)
  • T1 DNS：可缓存（第 4 篇的 TTL 机制），首访耗 1 个查询 RTT；
  • T2 TCP：三次握手 = 1 个 RTT（第 2 篇）；
  • T3 TLS：1.3 版 1 个 RTT、1.2 版 2 个 RTT（第 3 篇 §4.1）；
  • T4 HTTP：请求-响应至少 1 个 RTT（第 3 篇）；
  • T5 渲染：本地计算，不耗网络 RTT。

性能总账 = RTT 数量 × RTT 大小：跨洋场景单个 RTT 约 100-200ms，一次完整首访 = 4-6 个 RTT ≈ 0.5-1.2 秒，这还没算服务端处理时间。所有网络优化手段（第 2 篇的连接复用、第 3 篇的 TLS 1.3/HTTP/2、第 4 篇的 DNS 缓存）都在做同一件事：削减 RTT 数量。

1.2 动手验证：curl 把时间拆开

观察点：第二次运行时 dns 明显变小（系统 DNS 缓存命中，第 4 篇 §1.3 的缓存层级）、tcp 变小（连接复用，第 3 篇 §2.1 的 keep-alive）——同一台机器两次访问，机制在悄悄给你省钱。判定标准：两次 dns/tcp 出现可观察差异即验证了缓存与复用机制；tls 与 ttfb 的差值就是「TLS 握手 + 服务端处理」两个 RTT 段。

2. 请求出发：从域名到加密通道

2.1 DNS 与连接建立：三个待机环节

  1. 输入 URL → IP：先查浏览器缓存，再查系统缓存，最后问递归服务器（第 4 篇 §1.3 四级缓存）——TTL 决定这次查询是否真实发生；
  2. TCP 握手：SYN/SYN+ACK/ACK 一个 RTT，顺带完成 MSS 协商（第 2 篇 §1.1/§2.2 的 1460 边界）；
  3. TLS 协商：证书链验证 + 密钥交换（第 3 篇 §4.1），TLS 1.3 压缩到 1 个 RTT。

2.2 深挖：「少一个 RTT」的三代努力

手段 省掉的 RTT 机制
HTTP keep-alive 后续请求 2 个 RTT 连接复用（第 3 篇 §2.1）
TLS 1.3 会话恢复（0-RTT） 重访 1-2 个 RTT 缓存会话密钥，ClientHello 直接带数据
TCP Fast Open / HTTP/3 QUIC 新连接 1 个 RTT 握手与首包数据合并发出（第 3 篇 §2.3）

因果链：三代优化是「第 2 篇 BDP 视角」的连续应用——RTT 是网络物理上限（光速 × 距离），协议层只能「少往返、多利用往返」；keep-alive 是复用已付出的握手，0-RTT 是提前预支握手结果。面试答「怎么优化首屏」先答 RTT 账，再答具体手段，是区分「背方案」和「懂机制」的分水岭。

2.3 动手验证：把首次访问和二次访问的握手差拍下来

观察点：二次访问的 tcp/tls 耗时断崖式下降——连接复用的现场。判定标准：第二次 total 明显小于第一次即通过；若 tcp 仍是完整 RTT，说明服务器没开 keep-alive（老版本配置的典型坑）。

3. 请求到达服务端：链路上的每个队列

3.1 网关链路：请求先过几道「分流器」

URL 解析出的 IP 大概率不是业务服务器，而是 LB：四层 LB 按五元组转发（第 1 篇 §5.1），七层 LB 按 URL 路由，CDN 在前面按地域拦截静态请求（第 3 篇 §3.2）。一次请求的网络旅程 = 客户端 → CDN/LB → 业务网关 → 应用服务器，每一跳都是一次 TCP 连接（或复用）。

3.2 深挖：一次请求在服务端过五道队列

请求进入服务器后，要穿过五道队列才能被业务代码处理：

flowchart LR
    SYNQ["1. half-open queue<br/>(SYN, kernel, Ch.2)"] --> ACCQ["2. accept queue<br/>(backlog, Ch.2)"]
    ACCQ --> THREAD["3. thread pool queue<br/>(OS series Ch.1)"]
    THREAD --> APP["4. app business logic"]
    APP --> DB["5. DB/MQ queue<br/>(if any)"]
队列 归属 溢出的表现 机制出处
半连接队列 内核 connect 超时、SYN_RECV 堆积 第 2 篇 §4.2
全连接队列（backlog） 内核+应用 accept 延迟、连接被丢 第 2 篇 §1.2
线程池队列 应用 排队等待、RT 上升 操作系统系列第 1 篇
中间件队列 应用/中间件 背压、丢弃 操作系统系列第 3 篇

因果链：服务端延迟 = 五道队列的排队时间之和——排查「接口慢」先问「慢在哪个队列」：ss -tan 看 SYN_RECV/ESTABLISHED 堆积（前两道，内核视角），jstack 看线程池排队（第三道，JVM 视角），DB 慢查询日志看第五道——每道队列对应一套工具和一种机制，这就是第 4 篇「分层定位」在服务端的镜像。

3.3 动手验证：看一个请求在服务端留下的时间戳

观察点：ttfb（首字节）≈ 200ms + RTT——服务端处理时间直接进了 TTFB。判定标准：ttfb ≈ 0.2s 即验证了「响应时间 = 网络 RTT + 服务端排队/处理」；再把 sleep 改成 0 对比，TTFB 骤降——这就解释了为什么「接口慢」先查服务端而不是网络。

4. 响应与渲染：最后一公里的两个世界

4.1 响应路径：缓存决定「走网络还是走本地」

响应回来先过浏览器缓存判断：强缓存命中（Cache-Control 有效期内）根本不发请求；协商缓存命中回 304 只传头（第 3 篇 §3.1）——缓存是页面里唯一「不花钱的环节」，优先级永远最高。

4.2 深挖：渲染是另一条「流水线」

拿到 HTML 后，浏览器本地执行：解析 HTML 建 DOM、解析 CSS 建 CSSOM → 合并成 Render Tree → Layout 计算几何 → Paint 绘制。关键资源（CSS 阻塞渲染、JS 阻塞解析）会卡住流水线——渲染阶段的性能问题和网络无关，但优化目标和网络一致：减少环节、减少体积：

手段 省什么 机制
合并/压缩 CSS JS 请求数与体积 少 RTT、少解析
CDN 分发静态资源 网络距离 DNS 就近（第 4 篇）+ HTTP 缓存（第 3 篇）
字体/图片懒加载 首屏资源数 渲染树更快完整
HTTP/2 并发上限 单连接多路复用（第 3 篇 §2.2）

4.3 动手验证：用浏览器瀑布图验证「排队与复用」

打开 DevTools → Network → 勾选「Disable cache」刷新两次：第一次全部资源耗时高（无缓存 + 串行握手），第二次明显降低（缓存 + 连接复用）。观察点：瀑布图里每个资源的时间条由 Queued/Stalled/DNS/Connect/Request/Response 组成——这就是 §1.1 的 RTT 账在浏览器里的可视化。判定标准：能读出「二次访问 DNS 段消失、Connect 段只剩一个」即掌握读图能力。

5. 全链路优化：每个环节的杠杆

5.1 优化杠杆表：把「慢」钉在图上

环节 慢的症状 杠杆 机制出处
DNS dns 时间长 预解析（dns-prefetch）、TTL 合理设置 第 4 篇
TCP connect 长 keep-alive、连接池、QUIC 第 2/3 篇
TLS appconnect 长 TLS 1.3、会话恢复 第 3 篇
网络 RTT 各段都长 CDN 就近、回源优化 第 1/4 篇
服务端 ttfb 长 队列排查（§3.2）、缓存 操作系统系列
传输体积 response 长 压缩、HTTP/2 第 3 篇
渲染 total 长但网络短 关键渲染路径优化 本文 §4.2

5.2 深挖：延迟预算——从感受倒推预算

性能优化的第一步不是优化，是定预算：首屏目标 2 秒 → 拆给各环节（DNS 0.2s + 握手 0.2s + 首包 0.5s + 渲染 0.8s + 余量）→ 各环节对照预算找超标项。因果链：预算制把「页面慢」变成「某环节超预算」——这与第 4 篇分层定位法（第 3 篇 §3.1）是同一方法论的两副面孔：一个是排障定位，一个是目标管理。线上实践常配合 Web Vitals（LCP/FID/CLS）监控，把「用户感受到的慢」翻译成「哪个环节的预算被击穿」。

5.3 动手验证：本地完整复现一次「优化前 → 优化后」

观察点：每次请求 tcp 都完整计一次——HTTP/1.0 短连接模式 = 每次请求付一次握手；对比 §2.3 的 baidu 二次访问，同一台机器两种世界观。判定标准：tcp 每次都非零即复现了「无 keep-alive 的代价」，而 2.3 的对比数据就是 keep-alive 的价值证明——本节实验给「为什么 HTTP/1.1 默认 keep-alive」提供了亲手数据。

6. 总结：计算机网络系列收官

6.1 面试速答总复习（跨五篇）

面试题 一句话答案 出处
输入 URL 后发生什么？ DNS（T1）→ TCP 握手（T2）→ TLS（T3）→ HTTP 请求响应（T4）→ 渲染（T5），性能账 = RTT 数量 × RTT 大小 本文 §1
为什么分层？ 关注点分离，每层只解决一类问题，换实现不影响其他层 第 1 篇
三次握手为什么不是两次？ 防迟到旧 SYN，服务端收到 ACK 才确认客户端活着 第 2 篇
TIME_WAIT 怎么治？ 机制是防旧报文污染；正解是连接复用（keep-alive/连接池） 第 2/3 篇
HTTP/2 和 HTTP/3 区别？ 2 解决应用层队头阻塞（多路复用），3 换 QUIC 连传输层队头阻塞一起解决 第 3 篇
强缓存和协商缓存？ 强缓存不发请求；协商缓存发请求拿 304（只传头） 第 3 篇
DNS 切换 IP 生效慢？ 四级缓存按 TTL 倒计时，生效时间 = 最高 TTL 的缓存过期时间 第 4 篇
网络故障排查第一步？ 定层：dig → nc → openssl → curl，永远不跳层 第 4 篇
接口慢先查什么？ 服务端五道队列（半连接/全连接/线程池/应用/DB），每道一套工具 本文 §3.2
首屏优化从哪开始？ 定延迟预算 → 按 RTT 账找超标环节 → 缓存/复用/就近三件套 本文 §5.2

6.2 实战避坑总表

症状 原因 处理
页面偶发白屏/超时 DNS 或握手环节抖动 按 §1.2 计时拆段，钉住抖动的段
静态资源慢但接口快 未走 CDN / 缓存头缺失 CDN + 内容寻址（第 3 篇 §3.2）
二次访问还是慢 keep-alive/缓存未生效 检查服务器 Connection 头与 Cache-Control
接口 ttfb 高但 curl 网络快 服务端队列排队 jstack 线程池 + DB 慢查询（§3.2）
页面首屏一堆请求排队 HTTP/1.1 并发上限 上 HTTP/2（第 3 篇 §2.2）

6.4 全系列收官：五篇一条链

篇目 一句话核心 给你的能力
① 网络分层 每层只解决一类问题，边界决定选型 端口/IP/MAC 分清，LB 选型有依据
② TCP 协议 可靠有代价：握手、重传、拥塞都是权衡 状态机与连接堆积能排查
③ HTTP 协议 应用层语义：缓存、无状态、协议演进 缓存/Cookie/HTTPS 配置有依据
④ DNS 与排查 解析链路 + 分层定位法 域名问题 30 秒定层
⑤ 本文 一次请求走完全链，性能账 = RTT 账 任何页面慢都能钉在图上

实操建议（收官三件事）：

  1. 把 §1.2 的计时命令存成 pagecheck.sh，任何「页面慢」先跑一遍，把 dns/tcp/tls/ttfb 四段数值留档对比。
  2. 给自己的核心页面写一份延迟预算（§5.2），每次改动对照预算验证——没有预算的优化是玄学。
  3. 回到第 1 篇的结论：分层模型不只是考试题，它是排查顺序、选型依据和性能账本——本文走完的每一步，都是那五层在真实世界里的一次工作。
