缓存三大问题：穿透、击穿、雪崩的量化与解法

Posted on 2026-10-25 In 数据存储 Word count in article: 3.6k Reading time ≈ 13 mins.

缓存不是「读不到就查库」这么简单。实测一组数字：全命中时数据库压力是 0 QPS；一旦换成「查不存在的数据」，同样的并发把 9,241 QPS 全打到 MySQL 上——而 MySQL 单机点查的拐点大约 5 万（MySQL 系列 ⑫ 实测），也就是说这一个接口就能吃掉近五分之一的总容量。

这篇用真实的 Redis + MySQL 环境，把穿透、击穿、雪崩三种问题各跑一遍，并量化四种解法的效果。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线 → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题（本文） → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与前后篇的关系：本文的「互斥重建」用 ⑥ 的 SET NX；「缓存挂了数据库扛不扛得住」要回看 MySQL 系列 ③④ 的索引能力与 ⑫ 的容量拐点；⑩ 讲更新顺序，⑪ 讲锁的实现细节。

1. 三个问题，三张位置图

问题 一句话定义 触发条件 数据库压力
穿透（penetration） 查不存在的数据，缓存永远不命中 恶意攻击、脏 ID 每个请求都打库
击穿（breakdown） 单个热 key 失效瞬间，大量请求同时回源 热点 key 过期 瞬时尖刺
雪崩（avalanche） 大量 key 同时失效，或缓存整体不可用 TTL 集中、实例宕机 持续高压 
flowchart LR
    C["Client"] --> R{"Redis 命中?"}
    R -- hit --> OK["返回"]
    R -- miss --> D["查 MySQL"]
    D --> W["回写缓存"]
    P["穿透：key 根本不存在<br/>永远 miss"] -.-> D
    B["击穿：热 key 刚过期<br/>并发同时 miss"] -.-> D
    A["雪崩：大量 key 同时过期<br/>或 Redis 挂了"] -.-> D

2. 穿透：查不存在的数据

2.1 实测：全命中 vs 全穿透

环境：Redis 7.4.11 + MySQL 8.0，users 表 10 万行，50 线程、每场景 5 秒，客户端复用连接。

场景 总请求 QPS 未命中 DB 查询 DB QPS
A 全命中（1000 个热 key） 78,374 15,669 0 0 0
B 穿透（1 万个不存在的 id，不缓存空值） 46,446 9,241 46,446 46,446 9,241

两条结论：

  1. 缓存正常工作时，数据库压力是 0——这就是缓存的价值；
  2. 穿透时，每一个请求都变成一次数据库查询，且 QPS 从 15,669 掉到 9,241（-41%），因为数据库比 Redis 慢一个数量级。

2.2 解法一：缓存空值

把「查不到」也缓存起来（值为空字符串，短 TTL）：

场景 总请求 QPS DB 查询 DB QPS 相对穿透
B 无保护 46,446 9,241 46,446 9,241 —
C 空值缓存（TTL 5s） 63,443 12,634 10,011 1,994 DB -78%

代价：如果攻击者每次用不同的随机 ID，空值缓存也挡不住（缓存会被垃圾 key 填满）。这时需要布隆过滤器或参数校验。

2.3 解法二：布隆过滤器

用 Redis 的 bitmap 实现一个 100 万位、3 个哈希函数的布隆过滤器，预先把 10 万个存在的 id 写进去：

场景 总请求 QPS DB 查询 DB QPS 误判
D 布隆过滤器 36,446 12,053 554 183 1.5% 
flowchart LR
    Q["查询 id"] --> BF{"布隆过滤器<br/>说存在?"}
    BF -- "不存在（确定）" --> N["直接返回空<br/>不查库"]
    BF -- "可能存在（概率）" --> DB["查 MySQL"]
    DB --> W["回写缓存"]

554 次 DB 查询来自误判（3 个 bit 都被别的 id 置位了）。误判率可以用公式估算：

实测 554/36,446 = 1.52%，和公式吻合。

方案 DB 压力 代价 适用
空值缓存 -78% 缓存可能被垃圾 key 占满 ID 空间有限、可枚举
布隆过滤器 **-98%**（554/46,446） 需要维护位图、有误判 恶意随机 ID、ID 空间大
参数校验 视情况 只能挡明显非法的 第一道防线

2.4 动手验证：在你自己的库上复现穿透

预期观察点：用一个不存在的 ID 循环压测，INFO stats 的 keyspace_misses 与 MySQL 的 Questions 同步增长。

判定标准：

  • MySQL Questions 增速 ≈ 应用 QPS → 完全穿透，必须加保护；
  • 加了空值缓存后 MySQL 增速降到 1/5 以下 → 生效；
  • 空值缓存也挡不住 → 请求的 ID 是随机的，上布隆过滤器。

3. 击穿：热 key 失效的瞬间

3.1 实测：50 并发同时重建

把数据库查询人为加 50ms 延迟（模拟慢 SQL），然后让热点 key 失效，50 个线程同时来：

方案 请求 未命中 DB 查询
无互斥（各自回源） 48,264 50 50
互斥重建（SET NX） 49,097 442 2

50 → 2，25 倍差距。关键在于：如果没有互斥，50 个线程会同时发起 50 条相同的慢查询，数据库瞬间多出 50 个 50ms 的查询；并发再高一点，连接池就被打满（MySQL 系列 ⑪ 的因果）。

3.2 互斥重建的实现

sequenceDiagram
    participant A as Thread A
    participant B as Thread B
    participant R as Redis
    participant D as MySQL
    A->>R: GET hot:1 -> nil
    B->>R: GET hot:1 -> nil
    A->>R: SET lock:hot:1 1 NX EX 3 -> OK
    B->>R: SET lock:hot:1 1 NX EX 3 -> nil
    A->>D: SELECT ...（50ms）
    B->>B: sleep 5ms，回头再读缓存
    A->>R: SET hot:1 value EX 60
    A->>R: DEL lock:hot:1
    B->>R: GET hot:1 -> value

两个必须注意的点：

问题 后果 对策
锁没有超时 回源线程崩了，锁永久占住，所有请求都拿不到 EX 必须设，且大于最长回源时间
没抢到锁的线程直接返回 null 用户看到「数据不存在」 短暂自旋 + 重试读缓存，或返回降级数据

3.3 另一种解法：逻辑过期

不删 key，而是把「过期时间」放在 value 里；读到过期数据时，先返回旧值，再异步触发重建。

方案 一致性 延迟 实现复杂度
互斥重建 强（等新值） 一个回源周期 低
逻辑过期 弱（短暂返回旧值） 无等待 中（要异步线程池）

选型：能接受「短暂旧数据」用逻辑过期（比如商品详情）；必须读到最新值的用互斥重建。

3.4 动手验证：量一次击穿

预期观察点：无互斥时，MySQL 的 Questions 会在 key 失效的瞬间跳一下（等于并发数）；有互斥时只跳 1~2。

判定标准：

  • 跳变量 ≈ 并发线程数 → 没有互斥，必须修；
  • 跳变量 ≈ 1 → 互斥生效；
  • 跳变量远大于并发数 → 有别的原因（比如缓存写回失败、内存淘汰）。

4. 雪崩：大规模同时失效

4.1 实测：1 万个 key 同时失效

场景 请求 未命中 DB 查询 DB QPS
1 万个 key 同时失效 30,324 9,581 9,581 3,194
只有 20% 失效（模拟抖动） 45,026 2,003 2,003 668

同时失效让数据库压力涨到 4.8 倍，而且这不是瞬时尖刺——9,581 次查询分布在 3 秒里，持续压着数据库。

4.2 解法一：TTL 抖动

做法 失效分布 峰值压力
固定 TTL 同一秒集中失效 高
TTL ± 10% 抖动 摊到 10 分钟内 低

4.3 解法二：多级缓存 + 限流兜底

flowchart LR
    C["Client"] --> L1["本地缓存<br/>(Caffeine)"]
    L1 -- miss --> L2["Redis"]
    L2 -- miss --> DB["MySQL"]
    L2 -.->|"Redis 整体不可用"| FUSE["熔断/限流"]
    FUSE --> FALLBACK["返回降级数据或排队"]
手段 作用 代价
本地缓存（Caffeine） Redis 挂了还有一层 一致性问题（多实例）
限流（Sentinel/令牌桶） 保护数据库不被打穿 部分请求被拒
熔断 数据库撑不住时快速失败 用户看到降级页
预热 发布/重启后先灌热点 需要知道热点是什么

4.4 动手验证：制造一次雪崩

预期观察点：删除后的一段时间内，MySQL 的 Questions 增速是正常时的数倍，且 SHOW PROCESSLIST 里出现大量相同的查询。

判定标准：

  • MySQL QPS 涨到平时的 3 倍以上 → 雪崩成立，需要 TTL 抖动；
  • MySQL QPS 没变 → 你的 key 没有集中失效，或者根本没缓存。

5. 生产组合方案

5.1 一张决策表

问题 首选 兜底 备注
穿透 参数校验 + 空值缓存 布隆过滤器 随机 ID 攻击必须上布隆
击穿 互斥重建（SET NX） 逻辑过期 锁必须带超时
雪崩 TTL 抖动 多级缓存 + 限流 还要考虑 Redis 整体挂掉

5.2 与 MySQL 系列的联动

问题 本文实测 MySQL 侧的对应能力
穿透打到 9,241 DB QPS 一个接口占单机拐点（约 5 万）的 18% 索引与慢查询优化（③④）
击穿瞬间 50 个慢查询 连接池被占满的风险 池大小与等待（⑪）
雪崩 3,194 DB QPS 持续 3 秒 需要限流兜底 容量规划（⑫）

核心认知：缓存的三大问题，本质都是「数据库的容量问题」。缓存只是把请求挡在数据库前面，挡不住的部分会以 QPS 的形式砸到 MySQL 上。

7. 动手验证：四个可复现实验

7.1 动手验证：用量化方式复现一次雪崩

预期观察点：删除后的一段时间内 MySQL Questions 增速是平时的数倍（本文雪崩时 DB QPS 3,194，仅 20% 失效时 668）。

判定标准：增速没变 → key 没有集中失效，或者请求没打到缓存旁路逻辑上。

6. 总结

6.1 面试速答表

面试题 一句话答案
穿透、击穿、雪崩的区别 穿透是查不存在的数据；击穿是单个热 key 失效；雪崩是大量 key 同时失效
穿透怎么解决 参数校验、空值缓存（实测 DB -78%）、布隆过滤器（实测 DB 554 次，误判 1.5%）
击穿怎么解决 互斥重建（SET NX，实测 DB 50 → 2）或逻辑过期
雪崩怎么解决 TTL 抖动、多级缓存、限流熔断、缓存预热
互斥重建的锁要注意什么 必须设超时（EX），否则回源失败会锁死；没抢到锁的线程要自旋重试
逻辑过期和互斥重建怎么选 能接受旧数据用逻辑过期（无等待），要最新值用互斥重建
布隆过滤器为什么会误判 多个 key 的哈希位重叠；误判率由位数、哈希函数数、元素数决定
布隆过滤器能删除元素吗 不能（标准布隆），需要用计数布隆或定期重建
空值缓存有什么风险 攻击者用随机 ID 会占满缓存，必须配合布隆或校验
缓存全命中时数据库压力是多少 0（实测 78,374 请求，DB 查询 0）
穿透对数据库的真实影响 实测 9,241 DB QPS，约占 MySQL 单机点查拐点的 18%
雪崩时数据库压力涨多少 1 万 key 同时失效实测 DB QPS 3,194，是 20% 失效时的 4.8 倍

6.2 实战避坑表

症状 原因 处理
数据库 QPS 莫名其妙很高 大量请求穿透 查 keyspace_misses，加空值缓存或布隆
某个 key 失效瞬间接口超时 击穿，大量并发回源 互斥重建 + 锁超时
每天固定时间数据库压力暴涨 批量 key 同时过期 TTL 加随机抖动
加了空值缓存也没用 请求的是随机 ID 上布隆过滤器 + 参数校验
Redis 挂了业务直接崩 没有降级与本地缓存 多级缓存 + 限流 + 熔断
互斥锁不释放 回源线程异常退出 EX 超时 + finally 释放

6.3 工具速查表

工具 看什么 判定标准
INFO stats keyspace_hits / keyspace_misses 命中率骤降 = 穿透或雪崩
MySQL Questions 数据库查询增速 与应用 QPS 同步 = 全穿透
SHOW PROCESSLIST 大量相同查询 击穿/雪崩的现场证据
慢日志 回源查询 回源慢会放大击穿影响
布隆位图 BITCOUNT 位图饱和度越高，误判率越高

6.4 实操建议

  1. 给每个缓存 key 加 TTL 抖动，这是成本最低、收益最大的一条。
  2. 热点 key 用互斥重建，锁一定带 EX，没抢到锁的线程自旋重试。
  3. 对外接口先做参数校验，ID 格式不对直接拒绝，比任何缓存保护都便宜。
  4. 监控 keyspace_misses 的突增，它是穿透和雪崩最早的症状。
  5. 永远假设 Redis 会挂：本地缓存 + 限流 + 降级，三件套至少有两件。
