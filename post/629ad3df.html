MySQL 索引原理与实践

Posted on 2026-08-11 In 后端开发 , 数据存储 , MySQL Word count in article: 3.1k Reading time ≈ 11 mins.

索引（index）是数据库为加速查询而建立的有序数据结构，本质上是拿额外的存储空间和写入开销，换查询时少读数据。MySQL 默认存储引擎 InnoDB 的索引底层是 B+ 树，这决定了索引的绝大多数行为——包括怎么走索引、为什么会失效。本文按「底层结构 → 聚簇与非聚簇 → 实践要点」三层展开，读完你就能看懂 EXPLAIN 的输出，并在建表时说出每一条索引该不该建。

索引的本质（总览）

1. 为什么索引能加速查询

没有索引时，MySQL 只能全表扫描：把表的数据页从头读到尾，逐行比对条件。数据量从十万涨到千万，扫描成本线性增长。有了索引，查询变成「先走 B+ 树定位，再取数据」，查询成本从全表 O(n) 降为树高 O(log n) 级别的磁盘 IO。

数据量 全表扫描 走主键索引
10 万 扫描全部数据页 2~3 次磁盘 IO，毫秒级
1000 万 扫描全部数据页，秒级以上 3~4 次磁盘 IO，毫秒级

代价也要说清楚：每建一个索引，插入、更新、删除时都要多维护一棵 B+ 树，写入变慢、占用空间变大。

口诀：索引是空间换时间，换的是查询时间，付的是写入代价。

底层结构：B+ 树（面试核心考点）

2. B+ 树：为什么 MySQL 选它

B+ 树是一种多路平衡搜索树，所有数据都存在叶子节点，叶子节点之间用链表相连。 数据库的瓶颈在磁盘 IO，而 B+ 树的每个节点就是一个数据页（page，默认 16KB），能装成百上千个索引键，所以千万级数据树高也只有 34 层——查找一次最多 34 次磁盘 IO。

2.1 从二叉搜索树到 B+ 树

结构 1000 万数据下的查找 范围查询 数据存放位置
二叉搜索树 最坏退化成链表 O(n) 不稳定 所有节点
红黑树 约 23 层，23 次磁盘 IO 需要中序遍历 所有节点
B+ 树 34 层，34 次磁盘 IO 叶子链表顺序遍历 全部在叶子节点
Hash 索引 等值 O(1) 不支持 哈希桶

二叉搜索树不控制树高，红黑树控制了但每层只放一个键，树太高。B+ 树一个节点塞几百个键，树矮；范围查询靠叶子链表一次遍历就能搞定，而 Hash 索引只能做等值匹配——这正是 MySQL 默认用 B+ 树的原因。

2.2 B+ 树长什么样

    Root --> I2["12, 16, 20"]
    Root --> I3["24, 28"]
    I1 --> L1["1, 4"]
    I1 --> L2["5, 8"]
    I2 --> L3["9, 12"]
    I2 --> L4["13, 16"]
    I2 --> L5["17, 20"]
    I3 --> L6["21, 24"]
    I3 --> L7["25, 28"]
    L1 ---|next| L2
    L2 ---|next| L3
    L3 ---|next| L4
    L4 ---|next| L5
    L5 ---|next| L6
    L6 ---|next| L7

看图记住三个特征：

  1. 所有数据在叶子节点，非叶子节点只存「目录」键，不存数据，所以一个页能装更多键，树更矮；
  2. 叶子节点从小到大有序，且用链表串起来（InnoDB 中是双向链表），范围查询找到起点后顺着链表走即可；
  3. 树高就是磁盘 IO 次数，24 层意味着查找固定 34 次 IO，与数据量几乎无关。

2.3 一次索引查找的完整路径



graph TD
    A["SQL: SELECT * FROM user WHERE id = 10086"] --> B["IO 1: load root page"]
    B --> C["compare 10086, go to child 13~20"]
    C --> D["IO 2: load internal page"]
    D --> E["compare, go to leaf page 13~20"]
    E --> F["IO 3: load leaf page"]
    F --> G["binary search in page, found row"]
    G --> H["return full row"]

每层节点内做二分查找，找到下一个指针所在的页号，再把这个页加载进内存（IO），重复直到叶子页，页内二分定位到具体行。页是磁盘与内存交互的最小单位，这个细节后面回表时还会用到。这也是为什么主键查询快的直观原因：3 次 IO 就拿到整行。

聚簇索引与非聚簇索引（面试核心考点）

3. 聚簇索引：主键索引

聚簇索引（clustered index）的叶子节点直接存放整行数据，数据行的物理顺序与索引键顺序一致。 InnoDB 的主键索引就是聚簇索引，一张表有且只有一个——因为一行数据只有一份，物理上只能排成一种顺序。

聚簇索引的取值规则：

  1. 表有主键，用主键建聚簇索引；
  2. 没有主键，用第一个非空唯一索引（unique not null）建；
  3. 都没有，InnoDB 生成隐藏的 6 字节 rowid 建。

4. 非聚簇索引：二级索引

非聚簇索引（secondary index，也叫二级索引/辅助索引）的叶子节点存的是索引键 + 主键值，不是整行数据。 InnoDB 中除主键索引外，所有普通索引、唯一索引、联合索引都是二级索引。

4.1 回表：二级索引查询的本质

用二级索引查到主键后，再拿主键去聚簇索引查整行数据，这个过程叫回表（table lookup）。 所以一条走二级索引的 SELECT * 查询实际要查两棵树。如果查询的列全在二级索引里，就不用回表——这就是 6.3 的覆盖索引。



graph TD
    A["SELECT * FROM user WHERE age = 22"] --> B["search secondary index on age"]
    B --> C["found: age=22, pk=2"]
    C --> D{"need columns not in index?"}
    D -->|"Yes"| E["table lookup by pk=2 in clustered index"]
    E --> F["return full row"]
    D -->|"No: covering index"| G["return from index directly"]
    G --> F

4.2 聚簇 vs 非聚簇，一张表讲完

维度 聚簇索引 非聚簇索引
叶子节点存什么 整行数据 索引列 + 主键
每张表数量 只有 1 个 可以有多个
查询整行 定位即得，无需二次查询 需要回表
数据物理顺序 与主键一致 与索引键无关
典型代表 主键索引 普通索引、唯一索引、联合索引

口诀：主键查一次，二级索引查两次（一次找主键，一次回表）。

实践：建索引与避坑（实战重点）

5. 索引失效的常见场景

索引失效的本质只有一类：无法在 B+ 树上按序二分定位。要么条件列被函数包住导致顺序被打乱，要么条件跳过了联合索引的最左列。高频场景如下：

写法 失效原因 正确处理
WHERE name LIKE '%张%' 前导模糊无法二分定位 改成前缀匹配 '张%'；真要模糊搜用全文索引
WHERE phone = 13800138000（phone 是 varchar） 隐式类型转换，列被套函数 字符串加引号：'13800138000'
WHERE DATE(create_time) = '2026-08-11' 对列使用函数 改写范围查询：create_time >= '2026-08-11' AND create_time < '2026-08-12'
WHERE a = 1 OR b = 2（只有 a 有索引） OR 两侧必须都能走索引 拆成两条 SQL 或 UNION ALL
WHERE a = 1 ORDER BY b（只有单列索引 a） 排序列不在索引里 建联合索引 (a, b)

6. 建索引的实践要点

6.1 哪些列适合建索引

判断标准就两条：用得多（出现在 WHERE/ORDER BY/GROUP BY/JOIN 中）和区分度高（cardinality 高，即该列取值种类多）。性别、状态这类只取两三个值的列，即使查得多也不值得建——走索引扫出来的行占比太高，优化器宁愿全表扫描。字符串长列（如邮箱、URL）建前缀索引，用前 N 个字符做索引键，省空间：

6.2 联合索引与最左前缀

联合索引（composite index）是把多个列按顺序组合成一棵 B+ 树，树的排序规则按列的先后顺序逐级生效，因此只有从最左列开始连续使用的查询才能命中——这就是最左前缀原则。

以 (a, b, c) 为例：

查询条件 是否命中 说明
WHERE a = 1 命中 用了最左列
WHERE a = 1 AND b = 2 命中 最左前缀
WHERE a = 1 AND b = 2 AND c = 3 命中 用满整棵索引树
WHERE c = 3 AND a = 1 命中 优化器会重排条件，只要有 a
WHERE b = 2 不命中 跳过了 a
WHERE a = 1 AND c = 3 部分命中 a 走索引，c 在索引层过滤（依赖 5.6+ 索引下推）

设计顺序记住一句：等值条件放前面，范围条件放后面，区分度高的放前面。 例如查询基本是 WHERE status = ? AND create_time BETWEEN ...，就把 status 放前面、create_time 放后面，范围列一旦用了 BETWEEN 就断了排序连续性，放最后损失最小。

6.3 覆盖索引：少一次回表

覆盖索引（covering index）是指查询所需的列全部包含在某个索引中，查完索引直接返回，不需要回表。 这是性价比最高的一类优化：

6.4 不要过度索引

索引不是越多越好，每加一个索引，INSERT/UPDATE/DELETE 就多维护一棵树，唯一索引还要多做一次去重检查。常见过度索引：单列索引 (a)、(b) 并存的同时又建了 (a, b)；低区分度列建索引；全表唯一性用代码保证却建一堆唯一索引。大表上加索引是 DDL，会锁表或影响线上，务必在低峰期用 ALTER TABLE ... ADD INDEX（InnoDB 8.0 原生支持在线 DDL）分步执行。

7. 最佳实践清单

  1. 索引优先给 WHERE/ORDER BY/JOIN 中的列，且区分度要高；
  2. 能用联合索引别用多个单列索引，设计按「等值在前、范围在后」；
  3. 高频查询用覆盖索引，把回表省掉；
  4. 主键用自增或雪花 ID，别用 UUID 随机串——随机主键插入会频繁页分裂，写入性能明显变差；
  5. 每条慢 SQL 先 EXPLAIN，看 key、rows、Extra（出现 Using filesort、Using temporary 就要优化）；
  6. 字符串长列用前缀索引，杜绝隐式类型转换和列上套函数。

总结

本文三条主线：B+ 树决定了索引「矮树 + 有序叶子 + 链表」的形态，所以查找固定 3~4 次 IO、范围查询天然高效；聚簇与非聚簇的区别在于叶子节点存整行还是存主键，决定了回表的存在；实践要点归结为一句话——让查询能按序走完 B+ 树，别让函数、前导模糊、跳列破坏顺序，再用联合索引和覆盖索引把树的价值榨干。

实际项目里建议按这个顺序排查问题：先 EXPLAIN 确认是否走索引（key 非空），再看 rows 是否与预期相符，最后看 Extra 有没有 filesort 和临时表。索引设计放在建表阶段一次性想清楚，比上线后反复加索引省得多。
