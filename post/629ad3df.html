MySQL 索引原理与实践

Posted on 2026-08-11 In 后端开发 , 数据存储 , MySQL Word count in article: 7.5k Reading time ≈ 27 mins.

本文是《MySQL 原理与优化》的索引专题深挖篇，把该文第 2 章”索引”展开成完整知识体系：B+ 树的底层结构为什么长这样、聚簇索引与非聚簇索引的本质区别、以及日常建索引时真正管用的实践要点。索引是 MySQL 面试的必考区，也是 1-3 年 Java 后端从”会写 SQL”到”会优化 SQL”的分水岭——多表 join 能写出来是基本功，慢 SQL 能自己建索引治好才是进阶。

本文按”为什么需要索引 → B+ 树底层结构 → 聚簇与非聚簇 → 联合索引与最左前缀 → EXPLAIN 与索引失效 → 建索引实践”六章组织，每章末尾给结论，第 7 章是高频面试速答。全文默认讨论 InnoDB 引擎 + MySQL 5.7/8.0。

1. 为什么需要索引

1.1 没有索引的查询：全表扫描

MySQL 的数据以页为单位存在磁盘上（默认 16 KB/页，innodb_page_size）。一张 1000 万行的表，数据占几千个页。没有索引时，查询只能从第一页扫到最后一页，逐行判断条件——这就是全表扫描，复杂度 O(n)，一次查询就是几千次磁盘 IO。

几个关键数字，记住它们才能理解索引的价值：

存储/操作 延迟量级
内存访问 约 100 ns
SSD 随机读 约 0.1 ms
HDD 随机读 约 10 ms
一次磁盘 IO（读一页） 机械盘毫秒级，SSD 亚毫秒级

一次全表扫描 = 数千次这样的随机 IO。而索引的目标，是把”扫几千页”变成”读 2~3 个页”。

1.2 索引的本质：一张有序的”目录”

索引本质上是一份独立于表数据、按键排序的目录结构，类似新华字典的拼音检字表：

  • 没有检字表：从第 1 页翻到第 900 页找”栈”字；
  • 有检字表：先定位”zhan”在拼音表的哪个区间，再翻到对应正文页。

数据库索引同理：先在索引里用二分查找定位到目标键，再顺着指针拿到数据所在页。查找次数从 O(n) 降到 O(log n)，而且是页级的 log n——这正是 B+ 树多叉设计的用武之地（见第 2 章）。

当然索引不是免费的午餐，它有两个代价：

  • 空间：每个索引都是一份额外的有序结构，占用磁盘与 Buffer Pool 内存；
  • 写放大：每次 INSERT/UPDATE/DELETE 都要同步维护索引，索引越多，写入越慢（详见 6.3）。

1.3 为什么偏偏是 B+ 树

工程师拿到”有序目录”的需求，天然会想到几类候选结构。逐一排除：

候选结构 等值查找 范围查询 磁盘友好度 结论
哈希表 O(1)，最快 不支持（无序） 一般 InnoDB 仅在内存中用自适应哈希索引加速热点页，不做持久化索引
二叉查找树/AVL/红黑树 O(log n) 需要中序遍历 差 树高 log₂n，10 亿数据约 30 层 = 30 次磁盘 IO；且平衡调整频繁
B 树 O(log n) 需要回溯父节点 中 所有节点都存数据，单页装下的键少，树偏高（对比见 2.5）
跳表 O(log n) 好（内存中） 差 链式结构对磁盘页对齐不友好，Redis 的 ZSet 用在内存场景
B+ 树 O(log n) 好（叶子链表顺序扫） 最好 InnoDB 的选择

结论：等值、范围、磁盘 IO、写入稳定性四者权衡下来，B+ 树是磁盘数据库索引的最优解。为什么这么说，第 2 章把它的底层结构拆开看。

2. B+ 树索引的底层结构

2.1 先理解磁盘 IO 模型：页、树高、IO 次数

InnoDB 的索引和数据都以页为单位读写，一次磁盘 IO 至少读一个页。所以一次索引查找的磁盘 IO 次数 ≈ 树的层数。层数就是 B+ 树的设计核心：把树做得越矮，查询就越快。

B+ 树的层数由”每个页能装多少键”决定，这个数字叫分支因子。以 8 字节的 BIGINT 主键 + 6 字节页指针为例，一条索引记录约 14 字节：

也就是说，一个非叶子页能带 1170 个孩子。树的容量是几何级数增长的：

层数 可支撑数据量（按叶子页 15 行/页估算） 实际 IO 次数
2 层 1170 × 15 ≈ 1.7 万行 1 次
3 层 1170 × 1170 × 15 ≈ 2000 万行 2 次
4 层 百亿行 3 次

注意 IO 次数比层数少 1：根页常驻 Buffer Pool 内存，不需要读磁盘。所以 1000 万行的表按主键查，真实磁盘 IO 只要 2 次。这就是”3 层 B+ 树支撑千万级数据”这句话的来历。

2.2 B+ 树长什么样

两个核心设计：

  • 内部节点只存键 + 指针。一个页能装下 1170 个键，整棵树被压得很矮——这是 B+ 树 vs B 树最大的区别（2.5 详述）；
  • 所有数据都在叶子节点，叶子之间用链表串联。范围查询找到起点后，沿链表顺序往下读即可，天然支持顺序扫描。

2.3 页内二分查找

B+ 树的查找分两个阶段：沿树逐层下探（每次读一页），在页内二分查找（内存操作）。

2.4 插入与页分裂

B+ 树的插入规则很简单：找到应插入的叶子页，放进去；页满了就分裂成两页，并把新的最小键上提到父节点（父节点可能继续分裂，向上递归）。

页分裂的代价很大——要写两个新页、改父节点，可能连锁向上分裂。所以插入顺序直接决定索引的健康度：

  • 顺序插入（自增主键）：永远追加在最右叶子页，只有这一个页反复分裂，代价最小，叶子页空间利用率接近 100%；
  • 乱序插入（UUID 主键）：随机落在任意页，页频繁分裂，分裂后两页都只装一半数据——空间利用率跌到约 50%，索引膨胀一倍，还会产生大量碎片。

这一条直接导出了第 3 章的结论：主键不要用 UUID。

2.5 B+ 树 vs B 树：好在哪里

对比维度 B 树 B+ 树 对磁盘数据库意味着什么
数据存储位置 所有节点都存数据 只有叶子节点存数据 B+ 树单页能装更多键，树更矮，IO 更少
单页键容量 少（每条记录 14B+行数据） 多（纯键 + 指针） 同样 2000 万行，B 树要多 1~2 层
范围查询 要回溯父节点、中序遍历 叶子链表顺序扫描 id > 100 的效率高一个量级
全表扫描 需要遍历整棵树 直接扫叶子链表，近似顺序读 顺序 IO 比随机 IO 快几个数量级
写放大 中间节点存数据，更新频繁 内部节点纯指针，结构稳定 支持更高并发写入

本节小结：B+ 树用”非叶子纯索引 → 高分支因子 → 矮树”换来更少的磁盘 IO；用”叶子链表”换来高效的范围查询和顺序读。这两个特性叠加，就是 InnoDB 把它选为默认索引结构的全部理由。

3. 聚簇索引与非聚簇索引

3.1 聚簇索引：数据就是索引

聚簇索引（Clustered Index，InnoDB 中即主键索引）的叶子节点直接存完整行数据。也就是说，InnoDB 的表数据本身就是一棵 B+ 树——数据物理上按键有序组织，这叫索引组织表（Index-Organized Table）。

每个表只能有一个聚簇索引，由 InnoDB 按以下优先级自动决定：

  1. 显式定义的主键；
  2. 如果没有主键，取第一个非空 UNIQUE 索引；
  3. 都没有，InnoDB 自动生成一个隐藏的 6 字节 ROWID 作为聚簇索引（表结构设计缺陷，见 3.5）。

聚簇索引叶子页里除了业务列，还藏着 InnoDB 的隐藏列（trx_id 事务 ID、roll_pointer 回滚指针），MVCC 的版本链就挂在它们上面——这是《MySQL 原理与优化》事务章节的内容，此处不展开。

3.2 非聚簇索引（二级索引）：列值 + 主键

二级索引（Secondary Index，又称非聚簇索引/辅助索引）的叶子节点只存两样东西：索引列的值 + 主键值。

一个关键细节（面试常考）：InnoDB 二级索引叶子存的是主键值，而不是行指针（MyISAM 的索引叶子存的是行指针/文件偏移）。为什么？因为聚簇索引里数据页分裂、移动是常态，如果二级索引存指针，每次数据挪动都要回写所有二级索引；而主键值永远不变。代价是：主键越长，每个二级索引越大——这是 3.5 主键要短的核心原因。

一张表可以建多个二级索引，它们与数据的物理顺序无关，各自独立。

3.3 两种索引对比

维度 聚簇索引（主键索引） 二级索引（非聚簇索引）
叶子节点内容 完整行数据 索引列值 + 主键值
每表数量 只能有 1 个 可以有多个
与数据关系 数据即索引，物理顺序 = 主键序 独立结构，与物理顺序无关
查找路径 命中叶子即拿到整行 命中叶子只拿到主键，可能需要回表
创建方式 主键自动生成 CREATE INDEX 显式创建
主键值变化 — 所有二级索引需要跟着改

3.4 回表与覆盖索引

回表是这两个概念之间的”差价”，一句话定义：二级索引只存”列值 + 主键”，当查询需要的字段不在索引里时，只能拿主键再到聚簇索引查一遍完整行，这次”回头”就是回表。

每次回表都是一次聚簇索引查找（约 1~2 次磁盘 IO）。如果命中了 100 行，就是 100 次回表——这就是大范围查询慢的真相。

覆盖索引：查询所需的列全部包含在索引中，无需回表。它不是一个新索引类型，而是一种”索引刚好够用”的状态：

注意二级索引天然包含主键，所以”查 id + 查索引列”这类查询几乎总是可以做成覆盖索引。设计实践里，用空间换回表是有性价比的（见 6.2 覆盖性原则）。

3.5 主键怎么选：自增 vs UUID vs 业务主键

结合 2.4 的页分裂和 3.2 的”叶子存主键”，主键选择可以一次性推出来：

候选 插入顺序性 索引膨胀 结论
BIGINT 自增 顺序插入，无页分裂 8 字节，二级索引最小 首选
雪花 ID（BIGINT） 基本有序，可接受 8 字节 分布式场景首选
UUID（36 字符串/16B binary） 完全乱序，页分裂频繁，碎片多 大，且乱序会加剧膨胀 避免
业务主键（如 18 位身份证号） 视业务而定 长字符串，所有二级索引跟着变大 避免，用唯一索引约束替代

实践结论：

  • 主键用无业务含义的 BIGINT 自增（单机）或雪花 ID（分布式），一列定生死：乱序、过长都是慢性病，上线后很难改；
  • 业务上的唯一性（身份证号、手机号、订单号）用 UNIQUE 索引约束，而不是塞进主键；
  • 主键与唯一索引的语义区别：主键不能为 NULL，唯一索引允许 NULL（且多个 NULL 不冲突）。

本节小结：聚簇索引 = 整张表的数据本体；二级索引 = “索引列 + 主键”的副本。两者之间的差价是回表，覆盖索引是抹平差价的手段；而主键的选择（顺序、长度）决定所有二级索引的生死。

4. 联合索引与最左前缀

4.1 联合索引的内部排序

联合索引 (a, b, c) 底层就是一棵 B+ 树，只是排序规则变成了先按 a 排，a 相同再按 b 排，b 相同再按 c 排：

这个”字典序”就是最左前缀原则的全部来源：索引能用来定位的条件，必须是从最左列开始的一段连续前缀。因为索引里的顺序是”先 a 后 b 后 c”，只给 b 的值，索引无法知道去哪一区间找。

4.2 最左前缀：哪些查询能用上 (a, b, c)

查询条件 能用到的索引部分 说明
a = 1 a 完整使用
a = 1 AND b = 2 a + b 完整使用
a = 1 AND b = 2 AND c = 3 a + b + c 完整使用
b = 2 无 缺最左列 a，索引失效（全表扫描或索引全扫）
a = 1 AND c = 3 只用 a 跳过 b，c 无法用于索引定位（5.6+ 可被索引下推部分挽回，见 4.3）
b = 2 AND a = 1 a + b 优化器会重排等值条件，等价于 a=1 AND b=2

两个补充规则：

  • 等值条件顺序无关：优化器会自动把等值条件按索引列序重排，所以 b=2 AND a=1 和 a=1 AND b=2 效果一样；
  • 范围条件后面的列”断链”：a > 1 AND b = 2 中，a 用于索引定位，但 b 无法用于定位——索引定位只能在第一个范围条件上停止（b=2 只能退化为索引层过滤，8.0 前回表后过滤，8.0 中可被 ICP 拦截，见 4.3）。所以等值列放前面、范围列放后面是联合索引设计的铁律（见 6.2）。

4.3 索引下推（ICP）：把过滤提前到索引层

MySQL 5.6 引入的索引下推（Index Condition Pushdown），解决的是”联合索引部分失效”场景下的回表浪费：

  • 5.6 之前：引擎层把 name LIKE '张%' 命中的所有记录（含 age != 30 的）全部回表，由 Server 层过滤 age = 30——假设命中 1 万条，就回表 1 万次；
  • 5.6 之后（ICP）：引擎层在**遍历二级索引时直接判断 age = 30**，只把满足条件的行回表——假设只剩 50 条，就回表 50 次。

执行计划里看到 Extra: Using index condition 即命中 ICP。注意前提：过滤条件里的列（这里的 age）必须是索引列。

4.4 索引与排序：ORDER BY 免排序

B+ 树的叶子天然有序，所以只要排序字段是联合索引的一个连续前缀，ORDER BY 就能直接按索引顺序取数据，省掉 filesort（内存/磁盘排序，代价很高）：

看到 Extra: Using filesort 就要警惕——它通常意味着一次额外的排序开销，优先考虑把排序列放进索引（或调整索引列序）。

本节小结：联合索引 = 一棵按”字典序”排序的树；最左前缀是它的使用规则，等值前置、范围后置是它的设计规则；ICP 在索引层提前过滤，覆盖索引/索引序消灭回表与 filesort——这四个机制全部围绕”减少聚簇索引访问”服务。

5. EXPLAIN 与索引失效排查

5.1 EXPLAIN 速查

慢 SQL 排查的第一动作永远是 EXPLAIN SELECT ...。重点看五个字段：

字段 含义 怎么看
type 访问类型，从好到坏：system > const > eq_ref > ref > range > index > ALL ALL（全表扫描）和 index（全索引扫描）是优化信号
key 实际用到的索引 NULL 说明没用索引
key_len 索引实际用到的字节数 比设计值短，说明只用了部分前缀（列没吃满）
rows 估算扫描行数 越大越慢，与实际返回行数差距过大说明统计不准
Extra 附加信息 见下表

Extra 常见取值：

Extra 取值 含义
Using index 覆盖索引，无回表（好）
Using index condition 索引下推生效（好）
Using where 存储引擎返回后 Server 层过滤（可能回表）
Using filesort 需要额外排序（差）
Using temporary 需要临时表（差，常见于 GROUP BY 没用上索引）

key_len 计算示例（面试手算题）：utf8mb4 字符集下 VARCHAR(32) 可空列，32 × 4 + 2（变长长度字节）+ 1（NULL 标记）= 131 字节。联合索引 (a, b) 的 key_len 只等于 a 的长度，说明 b 没用上。

5.2 索引失效场景清单

场景 示例 原因与正解
对索引列做函数/运算 WHERE DATE(create_time) = '2026-08-01' 索引存的是列原值，无法按函数结果定位。正解：create_time >= '2026-08-01' AND create_time < '2026-08-02'，或 8.0 函数索引
隐式类型转换 字符串列 WHERE phone = 13800000000（数值） 列上发生类型转换，见 5.3
LIKE '%xx' 前导模糊 WHERE name LIKE '%张' 无法确定扫描起点。张% 可以走 range
OR 连接非索引列 WHERE name = 'a' OR age > 30（age 无索引） 优化器无法保证只走 name 索引。正解：拆两条 SQL 或给 age 建索引
违反最左前缀 联合索引 (a,b,c) 查 WHERE b = 2 见 4.2
范围条件断链 WHERE a > 1 AND b = 2 b 无法用于定位，只能过滤（等值列放前，见 4.2）
NOT IN / != / NOT LIKE WHERE status != 1 非绝对失效：返回比例高时优化器主动选全表扫描，比例低时可能走 range，取决于统计信息
数据量过小 几千行的表 优化器认为全表扫描更快（扫描几个页 vs 走索引还要回表），是合理决策，不是 bug

两个常见误解要澄清：

  • IS NULL 走不走索引？ 走。InnoDB 二级索引允许存 NULL，IS NULL 是 ref 级别的索引查找；
  • != 一定失效？ 不一定。它是优化器基于成本的选择，与数据分布有关——用 EXPLAIN 验证而不是背结论。

5.3 隐式类型转换：最容易踩的坑

MySQL 的规则：字符串列与数值比较时，字符串被转换为数值——转换发生在列上，索引失效；数值列与字符串比较时，字符串被转成数值，列不受影响，索引可用。

实践规则：Java 里用 MyBatis/JPA 传参时，phone 这类字符串字段传参类型必须和列类型一致（DTO 里是 String），否则会掉进这个坑且线上很难发现。排查技巧：EXPLAIN 里 key 为 NULL 但条件明明有索引，先检查类型。

5.4 优化器选错索引

优化器基于统计信息（采样估算行数）选索引，统计不准确时可能选错：

统计信息与真实分布差太远、或者优化器对”回表成本”的估算有误时，选错就发生了。另外 8.0 可以用 EXPLAIN ANALYZE 拿到实际执行耗时，比看估算 rows 更可靠。

本节小结：看 type 是否 ALL、key 是否 NULL、Extra 是否有 filesort/temporary 三个信号；失效排查按”函数/运算 → 隐式转换 → LIKE → OR → 最左前缀 → 范围断链”的顺序过一遍；选错索引先 ANALYZE TABLE，FORCE INDEX 是最后手段。

6. 日常建索引的实践要点

6.1 建索引的决策流程

不要”凭感觉建索引”，按下面的流程走：

  1. 定位慢 SQL：开启慢查询日志（long_query_time = 1，或阈值按业务调），或用 performance_schema/监控平台捞 Top SQL；
  2. EXPLAIN 分析：确认是不是全表扫描（type = ALL）、有没有 filesort、rows 是否过大；
  3. 设计索引：把 SQL 的 WHERE 等值列、JOIN 关联列、ORDER BY 排序列、GROUP BY 列列出来，按 6.2 的规则排成联合索引；
  4. 验证：EXPLAIN 对比建索引前后的 type、rows、Extra，确认覆盖到查询；
  5. 上线观察：索引对写放大有代价，上线后观察慢日志和写入延迟，确认收益 > 成本。

6.2 选列与排序的四个原则

① 区分度优先：索引的价值在于”过滤”，区分度低的列（性别、状态位）单独建索引收益极低——过滤完还是半张表。用 SHOW INDEX FROM t 看 Cardinality（估算基数），基数/总行数越大越好。区分度低的列适合放在联合索引靠后的位置做等值过滤（见③）。

② 等值列在前，范围/排序列在后：等值条件（=）能精确确定扫描区间，范围条件（>、BETWEEN、LIKE 'x%'）会让后面的列断链。排序/分组列放在最后，顺便免掉 filesort（4.4）。

③ 尽量让查询覆盖：查询只返回索引列的列时，把高频 SELECT 的列塞进索引尾部队列，用空间换回表。典型：列表页查 (id, name, status)，就建 (name, status) 或让联合索引带上它们。

④ 先查后建，宁缺毋滥：没有慢 SQL 就没有索引需求；小表（万行以内）全表扫描只有几个页的 IO，索引的收益可以忽略，别为”仪式感”建索引。

6.3 索引的成本：为什么不能建太多

每个索引都是一份独立的排序副本，代价具体到数字：

  • 写放大：一条 INSERT 要写 1 份聚簇索引 + N 份二级索引；UPDATE 修改了索引列，对应索引也要改；DELETE 同理。索引从 3 个加到 8 个，写入开销接近翻倍；
  • 空间：每加一个索引，就是表数据的 20%~100% 的额外存储（取决于列宽），同时挤占 Buffer Pool 内存，降低缓存命中率；
  • 唯一索引更贵：插入前要立即判断唯一性，无法利用 change buffer 的延迟合并（普通二级索引可以）。

量化建议：单表索引控制在 5~6 个以内，能用联合索引覆盖的查询就不要拆成多个单列索引。

6.4 冗余索引与维护

  • 联合索引吞并单列索引：有 (a, b) 就没必要保留单列 (a)——前者完全覆盖后者的能力。但 (b, a) 与 (a, b) 是两种不同结构，别删错；
  • 8.0 的 INVISIBLE 索引：拿不准要不要删的索引，先 ALTER TABLE ... ALTER INDEX idx INVISIBLE 无痛隐藏，观察一段时间没有报错再 DROP，比直接删安全得多；
  • 索引碎片：页分裂会留下碎片。SHOW TABLE STATUS LIKE 't_order' 看 Data_free，碎片明显时 OPTIMIZE TABLE t_order 重建表（注意锁表时间，选业务低峰）；
  • 前缀索引：超长字符串（URL、邮箱）建 url(20) 前缀索引，但会损失区分度，且无法用于覆盖索引和 ORDER BY——权衡后使用；
  • 8.0 函数索引：CREATE INDEX idx_date ON t ( (DATE(create_time)) )，专门兜底”函数查询”场景，但优先还是改写 SQL。

7. 面试高频题速答（1-3 年档）

问题 速答
为什么 InnoDB 用 B+ 树而不是 B 树？ 内部节点不存数据 → 单页键多 → 树矮 IO 少；叶子链表 → 范围查询和顺序扫描高效；写放大更小
聚簇索引和非聚簇索引的区别？ 聚簇叶子存整行、每表一个、决定物理顺序；二级索引叶子存”列值 + 主键”、可多个、与物理顺序无关
为什么二级索引存主键而不是行指针？ 数据页移动/分裂时主键不变，避免级联更新所有二级索引；代价是主键越长索引越大
什么是回表和覆盖索引？ 二级索引缺字段时拿主键回头查聚簇索引叫回表；查询列全在索引里则无需回表（Extra: Using index）
联合索引 (a,b,c)，WHERE b=1 AND c=2 能用吗？ 不能定位，最左列缺失；只能全索引扫描，8.0 下可被 ICP 在索引层过滤
索引下推解决什么问题？ 让二级索引遍历时直接过滤部分失效的索引列，减少回表次数（Extra: Using index condition）
什么场景索引会失效？ 函数/运算、隐式类型转换、LIKE '%x'、OR 非索引列、违反最左前缀、范围后断链
自增主键 vs UUID？ 自增顺序插入无页分裂、索引小；UUID 乱序导致页分裂、碎片、空间利用率掉到 50% 附近
索引是不是越多越好？ 不是。每个索引都是写放大 + 空间成本，单表 5~6 个为常见上限，用联合索引替代多个单列索引
唯一索引和普通索引怎么选？ 需要业务防重/唯一约束用唯一索引；否则用普通索引（可走 change buffer，写入更便宜）

8. 总结

一条主线串起全文：B+ 树用”矮树 + 叶子链表”把磁盘 IO 次数从 O(n) 压到 O(层数)；聚簇索引就是表数据本体，二级索引是”列 + 主键”的副本，回表是两者之间的差价；联合索引按字典序组织，最左前缀决定能用不能用，等值前置决定用得好不好；EXPLAIN 的 type/key/Extra 三件套 + 隐式转换、函数、LIKE 这些失效清单，是排查慢 SQL 的标准动作；最后落到实践：先慢日志，后 EXPLAIN，再按”区分度、列序、覆盖、成本”四原则建索引。

索引优化是 MySQL 学习中性价比最高的投入——它不需要改代码，不需要扩机器，一条 CREATE INDEX 常常把慢 SQL 从秒级降到毫秒级。但这张”免费的优化券”也有规则：建错了（冗余、过度）会拖垮写入，建歪了（列序、类型）等于没建。
