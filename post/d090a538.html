锁、死锁与 MDL：一次变更如何堵死整张表

Posted on 2026-10-25 In 数据存储 Word count in article: 4.4k Reading time ≈ 16 mins.

上一篇说「当前读要加锁」，本篇回答加多少。一行 WHERE id = 5 FOR UPDATE 可能只锁一条记录，也可能锁住一个区间；而 WHERE c = 5（c 上有非唯一索引）锁的是「记录 + 两侧间隙」。范围锁错了，插入就会被莫名阻塞；锁的顺序错了，就会死锁。

本文用 performance_schema.data_locks 把加锁范围直接查出来（不用猜），再复现一次真死锁并逐行读日志，最后演示一个更常见的生产事故：一条 ALTER TABLE 排在长事务后面，把整张表的查询全堵死。所有数据都是 MySQL 8.0.46 容器里的实测。

系列地图（高性能 MySQL 实战路线，12 篇）

① 实验台与基线 → ② 六层成本账 → ③ 索引与 Schema → ④ 优化器与慢查询 → ⑤ 事务与 MVCC → ⑥ 锁与死锁（本文） → ⑦ 内存与刷盘 → ⑧ 复制与高可用 → ⑨ 备份与恢复 → ⑩ 在线 DDL → ⑪ Java 侧连接池 → ⑫ 容量与分库分表

与前后篇的关系：⑤ 的「快照读不加锁」解释了为什么普通 SELECT 不挡写入，本文解释当前读到底挡了什么；本文的 MDL 只讲「为什么会堵」，gh-ost / 在线变更的完整方案在 ⑩。

1. 三种行锁：锁的是索引，不是行

1.1 三个概念

InnoDB 的行锁加在索引记录上，不是加在「行」这个抽象概念上。这就是为什么「没走索引的 UPDATE 会锁很多行」——它扫到哪，就锁到哪。

锁 锁什么 典型触发
记录锁（Record Lock） 索引上的一条记录 唯一索引等值命中
间隙锁（Gap Lock） 两条记录之间的空隙，不锁记录本身 唯一索引等值未命中、范围条件
Next-Key Lock 记录锁 + 它前面的间隙 非唯一索引等值/范围（RR 默认行为） 
flowchart LR
    subgraph IDX["Primary index leaf pages: 1 ... 5 ... 10 ... 15"]
        G1["gap (1,5)"] --> R5["record 5"]
        R5 --> G2["gap (5,10)"] --> R10["record 10"]
        R10 --> G3["gap (10,15)"] --> R15["record 15"]
    end
    N["Next-Key on 10 = gap (5,10) + record 10"] -.-> G2
    N -.-> R10

1.2 实测：同一条 SELECT，锁的范围四种

准备一张表：主键 id、非唯一索引 c、唯一索引 k，数据是 1/5/10/15/20：

四种写法，各开一个事务执行 FOR UPDATE，然后查 data_locks：

写法 实测锁 被阻塞的插入 没被阻塞的插入
WHERE id = 5（唯一索引命中） PRIMARY X,REC_NOT_GAP on 5 更新 id=5 插入 id=7 成功
WHERE id = 7（唯一索引未命中） PRIMARY X,GAP 在 10 之前 插入 id=7 被阻塞 —
WHERE c = 5（非唯一索引） idx_c X on 5,5 + idx_c X,GAP（5,10）+ PRIMARY X,REC_NOT_GAP on 5 插入 c=6 被阻塞 插入 c=11 成功
范围 WHERE id > 5 逐条 next-key（本文没测，原理同第三行） 区间内插入 区间外插入

第一行是最反直觉的：唯一索引等值命中时，InnoDB 会退化成纯记录锁（REC_NOT_GAP），不锁间隙。所以 SELECT * FROM tl WHERE id = 5 FOR UPDATE 不影响别人插入 id = 7。

第三行的三个锁要连起来看：

  • idx_c X on 5,5：非唯一索引上的 next-key，锁住记录 5 前后
  • idx_c X,GAP on 10,10：锁住 (5,10) 这段空隙
  • PRIMARY X,REC_NOT_GAP on 5：回表锁住真实行

这就是「WHERE c = 5 会把 (5,10) 之间的插入全堵住」的机制——间隙锁锁的是空隙，不是记录，所以 INSERT c = 6 会卡住，而 INSERT c = 11 不受影响。

1.3 加锁范围的推导规则

flowchart TD
    S["Current read with condition"] --> Q1{"unique index,<br/>equality?"}
    Q1 -- "hit" --> A["Record lock only<br/>REC_NOT_GAP"]
    Q1 -- "miss" --> B["Gap lock<br/>X,GAP"]
    Q1 -- "no" --> Q2{"non-unique index?"}
    Q2 -- yes --> C["Next-Key locks<br/>record + gap"]
    Q2 -- "no index at all" --> D["Scan + lock every row<br/>effectively table-wide"]
    C --> E["also lock clustered index<br/>for the matched rows"]

记住一条：间隙锁只在 REPEATABLE READ 及以上级别生效，READ COMMITTED 下基本没有间隙锁（除了外键/唯一性检查）。所以「把隔离级别降到 RC 能减少锁冲突」这句话是对的，代价是放弃可重复读（⑤ 讲过代价）。

1.4 为什么「没走索引」等于锁全表

UPDATE tl SET c = 1 WHERE k = 'no-such-value' 如果 k 上没有索引：InnoDB 只能全表扫描，扫过的每一行都会加锁（RR 下是 next-key），等于锁住整张表。此时任何插入都可能被阻塞。

生产上的典型症状：「一个按非索引字段跑批的 UPDATE，把整张表锁了 30 秒」。诊断方法就是看 data_locks 里 LOCK_DATA 有多少条记录——几百条基本可以确定是全表扫。

1.5 动手验证：自己画出加锁范围

预期观察点：WHERE c = 5 应该出现三条记录（idx_c X / idx_c X,GAP / PRIMARY X,REC_NOT_GAP）；换成 WHERE id = 5 只应该有一条 PRIMARY X,REC_NOT_GAP。

判定标准：

  • 你预测的范围与 LOCK_DATA 不一致 → 先把推导规则（1.3）走一遍再试；
  • 出现几十条 LOCK_DATA → 这条 SQL 没走索引，先修索引（③）再谈锁。

2. 锁等待与死锁

2.1 等待不是死锁，两者要分开看

维度 锁等待 死锁
触发 想拿的锁被别人持有 两个以上事务循环等待
表现 阻塞到超时 InnoDB 主动检测并回滚一个
报错 ERROR 1205 Lock wait timeout exceeded ERROR 1213 Deadlock found when trying to get lock
超时时间 innodb_lock_wait_timeout，实测默认 50 秒 无超时，立即检测（innodb_deadlock_detect 默认 ON）
处理 找到持锁的长事务 调整加锁顺序或缩小事务

2.2 实测一次 ABBA 死锁

两个事务反序更新同一批行，是最经典的模式：

flowchart LR
    A["Trx A<br/>holds row 1<br/>wants row 10"] -->|"waits for"| B["Trx B<br/>holds row 10<br/>wants row 1"]
    B -->|"waits for"| A

会话 A：UPDATE ... WHERE id = 1; → 睡 4 秒 → UPDATE ... WHERE id = 10;
会话 B：UPDATE ... WHERE id = 10; → UPDATE ... WHERE id = 1;

实测结果是 A 被选为牺牲者：收到 ERROR 1213，整个事务回滚（id=1 上它做的修改被撤销），而 B 被阻塞的那条语句在 A 回滚后拿到锁并提交。表里最终的值验证了这一点：id=1 变成 2001、id=10 变成 2010，都只体现 B 的 +2000——A 的两处修改被整体撤销了。

步骤 看什么 本例结论
1 谁在等谁 事务 1843 持有 …0a，等 …01
2 另一个事务的 HOLDS / WAITING 段 事务 1842 持有 …01，等 …0a → 闭环成立

hex 怎么读：InnoDB 对整数主键做了符号位翻转（保证按字节比较时负数排在正数前），所以 0x8000000a 去掉最高位就是 0x0a = 10。看到 8000000a 就念「10 号记录」。

2.4 四类高频死锁模式

模式 触发场景 机制 处理
ABBA 反序更新 两个事务按不同顺序更新多行 循环等待（本文实测） 统一加锁顺序（按主键排序后批量更新）
唯一键冲突插入 并发 INSERT ... ON DUPLICATE KEY UPDATE 或先查后插 插入意向锁 + 唯一性检查互相等待 提前加锁（SELECT ... FOR UPDATE）或改为 INSERT IGNORE 后重试
间隙锁插入 一个事务范围锁，另一个插入落在间隙 gap 锁与插入意向锁冲突 降低隔离级别到 RC，或缩小范围条件
主从不一致引发的 从库回放时行序不同 并行复制下加锁顺序不同 谨慎使用并行复制（⑧）

2.5 动手验证：造一次死锁

预期观察点：其中一个会话返回 ERROR 1213；日志里两个事务的 HOLDS 与 WAITING 互为对方持有的记录。

判定标准：

  • 只有一个报 1213，另一个正常提交 → 正常，InnoDB 只回滚代价小的那个；
  • 两个都报 1213 → 说明涉及的资源更多，检查是否还有第三个事务参与；
  • 日志里没有 LATEST DETECTED DEADLOCK 段 → 死锁发生在很久以前，SHOW ENGINE INNODB STATUS 只保留最近一次。

3. MDL：为什么一条 ALTER 能堵死整张表

3.1 两种锁，两套规则

行锁保护「数据」，MDL（Metadata Lock）保护「表结构」。两者完全独立：

维度 行锁 MDL
保护对象 行数据 表结构（列、索引）
加锁时机 当前读 / 写 任何访问表的语句，包括普通 SELECT
持有到何时 事务结束 语句结束（普通查询）或事务结束
等待变量 innodb_lock_wait_timeout（默认 50s） lock_wait_timeout（默认 31536000s，等于「永远等」）

关键差异：普通 SELECT 不加行锁，但要加 MDL 共享锁。这就是为什么「我只查了一下」也会参与 MDL 排队。

会话 C 执行一条普通 SELECT（lock_wait_timeout = 3）：

flowchart LR
    A["Trx A: SELECT in open trx<br/>MDL SHARED_READ GRANTED"] --> T["Table tl"]
    B["ALTER TABLE<br/>wants MDL EXCLUSIVE<br/>PENDING"] -->|"queued behind A"| T
    C["Session C: plain SELECT<br/>wants MDL SHARED_READ"] -->|"queued behind B"| T
    C -.->|"blocked 3s, then 1205"| X["timeout"]

这就是 MDL 雪崩的完整机制：A 只是查了一下，但事务没提交 → B 的 ALTER 排队等 → C 的 SELECT 排在 B 后面（MDL 队列是 FIFO，不允许插队）→ 后续所有查询全部堆积。一条 ALTER，堵住整张表，而且和行锁、和 SQL 快慢都没关系。

3.3 MDL 冲突矩阵（简化）

语句 需要的 MDL 与 ALTER 冲突 与普通 SELECT 冲突
普通 SELECT SHARED_READ 冲突（被 ALTER 挡） 不冲突
INSERT / UPDATE / DELETE SHARED_WRITE 冲突 不冲突
ALTER TABLE EXCLUSIVE 冲突 冲突

3.4 为什么 DDL 前必须查「长事务」

检查项 SQL 阈值
长事务 SELECT * FROM information_schema.innodb_trx ORDER BY trx_started age_s > 5 就要等或杀
已有 MDL 等待 SELECT * FROM performance_schema.metadata_locks WHERE LOCK_STATUS='PENDING' 有 PENDING 绝不能发新 DDL
表上活跃连接 SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_NAME='tl' AND LOCK_STATUS='GRANTED' 有 GRANTED 的 LONG 事务需评估

3.5 动手验证：复现 MDL 阻塞链

预期观察点：C 大约 3 秒后返回 ERROR 1205；期间 metadata_locks 里能看到 SHARED_READ GRANTED + EXCLUSIVE PENDING 并存。

判定标准：

  • C 立即成功 → A 的事务已经结束，或 A 用的是自动提交（autocommit=1 的 SELECT 不持有 MDL）；
  • C 卡住且 B 一直在 PENDING → MDL 队列成型，这就是线上雪崩的起点。

4. 排障手册：从告警到根因

4.1 三条命令定位

视图 用途 关键列
sys.innodb_lock_waits 行锁等待关系 waiting_pid / blocking_pid / sql_kill_blocking_query
sys.schema_table_lock_waits MDL 等待关系 waiting_pid / blocking_pid
performance_schema.data_locks 加锁明细 LOCK_MODE / LOCK_DATA
performance_schema.metadata_locks MDL 明细 LOCK_TYPE / LOCK_STATUS

sys.innodb_lock_waits 甚至直接给你生成好 KILL 语句（sql_kill_blocking_connection），但别在生产上闭眼执行——先看清它是不是批处理的主事务。

4.2 一个真实的因果链（本文实测的拼合）

时刻 事件 现象
T0 会话 A 开了事务查了一次表 持有 MDL SHARED_READ
T0+2s 运维发了 ALTER TABLE EXCLUSIVE PENDING
T0+4s 业务查询全部卡住 队列 FIFO，SELECT 排在 DDL 后面
T0+30s 连接池被打满 应用侧开始超时（⑪）
T0+60s DBA KILL 掉 A DDL 执行，业务恢复

根因不是 DDL，也不是 DDL 慢，而是「DDL 前面有一个没提交的事务」。这条链在线上非常常见，而且每次复盘都会被误判成「DDL 把库搞挂了」。

5. 总结

5.1 面试速答表

面试题 一句话答案
InnoDB 有哪几种行锁 记录锁、间隙锁、Next-Key Lock（记录 + 前面间隙），另有插入意向锁
唯一索引等值命中加什么锁 纯记录锁（REC_NOT_GAP），不锁间隙，实测插入相邻记录不受影响
唯一索引等值未命中加什么锁 间隙锁（X,GAP），实测插入该值被阻塞
非唯一索引等值加什么锁 Next-Key（记录 + 两侧间隙），实测 WHERE c=5 挡住 (5,10) 内的插入
为什么没走索引的 UPDATE 会锁全表 全表扫过的每一行都加 next-key 锁
间隙锁在 RC 下还有吗 基本没有，RC 只锁匹配行；代价是放弃可重复读
锁等待和死锁的区别 1205 是等待超时（默认 50s），1213 是死锁（立即检测并回滚一个）
死锁日志怎么读 看两个事务的 HOLDS / WAITING 是否互为对方，hex 值去掉最高位即主键值
怎么避免 ABBA 死锁 统一加锁顺序（按主键排序批量更新）、缩短事务
MDL 是什么 元数据锁，保护表结构；普通 SELECT 也会加 SHARED_READ
为什么 ALTER 会堵死整张表 DDL 要 EXCLUSIVE，排在长事务后面；后续查询 FIFO 排在 DDL 后面
lock_wait_timeout 和 innodb_lock_wait_timeout 区别 前者管 MDL 等待（默认近乎无限），后者管行锁等待（默认 50s）

5.2 实战避坑表

症状 原因 处理
插入莫名被阻塞，但没锁冲突 落在间隙锁范围里 查 data_locks 的 LOCK_DATA，调整范围条件或降 RC
ERROR 1213 偶发 反序更新 / 唯一键冲突 统一加锁顺序，或缩短事务重试
ERROR 1205 批量出现 有长事务持锁 查 innodb_trx 的 age_s，杀源头
DDL 一发就雪崩 DDL 前有未提交事务 DDL 前跑 3.4 的两条检查
DDL 一直 PENDING 但不报错 lock_wait_timeout 默认近乎无限 显式设置超时，别让它无限等
KILL 后锁还在 大事务回滚需要时间 等回滚完成，KILL 不是立刻生效

5.3 工具速查表

工具 看什么 判定标准
performance_schema.data_locks LOCK_MODE / LOCK_DATA 出现 X,GAP = 有间隙锁；记录数多 = 扫太多行
performance_schema.data_lock_waits 等待关系 有记录 = 正在互相等
performance_schema.metadata_locks LOCK_STATUS 有 PENDING = MDL 队列已成型
sys.innodb_lock_waits 谁堵谁 + 现成的 KILL 语句 先确认不是核心批处理
sys.schema_table_lock_waits MDL 谁堵谁 DDL 前必看
SHOW ENGINE INNODB STATUS LATEST DETECTED DEADLOCK 只保留最近一次，要抓就趁早

5.4 实操建议

  1. 写完 FOR UPDATE 就问一句：这个条件走的是唯一索引等值吗？是 → 只锁一行；不是 → 先看 data_locks 再上线。
  2. 批量更新按主键排序。这一条能消掉大部分 ABBA 死锁，成本几乎为零。
  3. 业务侧把锁等待超时调到 3~5 秒，别用默认 50 秒——长等待会连带打满连接池。
  4. DDL 前必跑两条检查（长事务 + MDL PENDING），并把 lock_wait_timeout 显式设小。
  5. 间隙锁不是 bug。它是 RR 保证可重复读的代价；要消掉它，改隔离级别或改索引设计，不要指望调参数。
