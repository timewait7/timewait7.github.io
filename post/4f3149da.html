线程与调度：一次上下文切换值多少钱

Posted on 2026-10-25 In Java Word count in article: 3.1k Reading time ≈ 11 mins.

「多开线程」在 CPU 密集场景下，收益到核数就结束了。实测：15 核机器上，1→15 线程带来 12.86 倍加速；但从 15 加到 16/32/64，吞吐不升反降到 11.5 倍左右——多出来的线程只是让 CPU 在切换上多花钱。

这一篇把「线程成本」拆成三块量清楚：栈内存、上下文切换、锁竞争，并用 JFR 证明竞争确实发生了（4 线程 0 次等锁事件，64 线程 17,051 次，单次等待 10 ms）。

系列地图（Java 并发实战路线，12 篇）

① 实验台与基线 → ② 线程与调度（本文） → ③ JMM：可见性与重排 → ④ 伪共享与缓存行 → ⑤ 原子性与 CAS → ⑥ 锁的演化 → ⑦ AQS 与并发容器 → ⑧ 线程池参数 → ⑨ 并发工具与异步编排 → ⑩ 死锁与线程泄漏 → ⑪ 虚拟线程 → ⑫ 并发性能工程

与前后篇的关系：① 量出「创建 32 µs、切换 2.43 µs」，本文看这两个成本在多线程下的累积效应；⑧ 会把本文的结论落到线程池参数上。

1. 线程的三笔开销

开销 量级 与什么成正比 怎么观测
创建/销毁 32 µs/个（①实测） 线程创建频率 代码或 JFR jdk.ThreadStart
栈内存 1 MB/线程（-Xss1m 实测） 线程总数 NMT Thread (reserved)
上下文切换 2.43 µs/次（①实测） 切换频率 = f(线程数, 阻塞) JFR jdk.ThreadPark、JFR jdk.JavaMonitorEnter 
flowchart LR
    T["More threads"] --> S["Stack memory<br/>1MB each"]
    T --> C["Scheduling<br/>2.43us per switch"]
    T --> L["Lock contention<br/>monitor enter waits"]
    S --> O["OOM: unable to create native thread"]
    C --> P["Throughput plateau"]
    L --> Q["Throughput collapse"]

第一笔账最容易被忽略：一个线程默认 1 MB 栈，1000 个线程就是 1 GB，而且这部分内存不在堆里，-Xmx 管不到它。

1.1 实测：1000 个线程的真实内存（NMT）

用 -XX:NativeMemoryTracking=summary 看 JVM 自己统计的内存：

配置 线程数 Thread 区域 折算每线程
-Xss1m 1,018 1,067,110 KB ≈ 1.02 GB ≈ 1 MB
-Xss256k 1,018 292,198 KB ≈ 285 MB ≈ 284 KB

换算：1000 个线程在默认配置下吃掉 1 GB 内存，还没算堆和元空间。这就是「java.lang.OutOfMemoryError: unable to create native thread」最常见的成因——不是堆不够，是栈 + 线程数超了。

2. CPU 密集：峰值就在「核数」那一刻

2.1 实测：15 核的曲线

固定总工作量（12 亿次 sqrt 累加），用不同线程数分摊，3 轮取最优：

线程数 墙钟(ms) 吞吐（M work/s） 加速比
1 540 2,222 1.00×
2 282 4,255 1.91×
4 148 8,108 3.65×
8 73 16,438 7.40×
15 42 28,571 12.86×
16 47 25,532 11.49×
24 46 26,087 11.74×
32 47 25,532 11.49×
64 46 26,087 11.74× 
flowchart LR
    A["1 thread<br/>540ms"] --> B["8 threads<br/>73ms (7.4x)"]
    B --> C["15 threads<br/>42ms (12.86x) PEAK"]
    C --> D["16-64 threads<br/>~46ms (11.5x) plateau"]
    D -.->|"+6% threads<br/>-11% throughput"| E["pure switching overhead"]

2.2 深挖：为什么 16 线程就掉下来了

原因 说明
核数只有 15 第 16 个线程必须等某个核空出来
切换有成本 每次 2.43 µs，线程多了切换次数上升
缓存局部性变差 线程在不同核间迁移，L1/L2 命中率下降
调度抖动 线程不是均匀完成的，尾部线程拖后腿

关键结论：CPU 密集任务的线程数 ≈ 核数，最多 +1。加到 32/64 只是让「吞吐从 12.86× 掉到 11.5×」，是负优化。

3. 阻塞型任务：线程数可以远超核数

3.1 实测：400 个 10 ms 的睡眠任务

线程数 墙钟(ms) 吞吐（tasks/s） 相对 1 线程
1 4,703 85 1.0×
4 1,171 342 4.0×
16 299 1,338 15.7×
64 82 4,878 57×
128 48 8,333 98×
256 35 11,429 134×

和 CPU 密集完全相反：任务在睡眠时不占 CPU，线程可以开到 256 甚至更多，吞吐接近线性增长。

3.2 深挖：阻塞型任务的真实上限

上限 数值 后果
内存 1 MB/线程 1000 线程 = 1 GB
下游容量 数据库连接数、下游 QPS 线程再多也只是排队
线程创建 32 µs/个 频繁创建池外线程很贵
调度 2.43 µs/次 数千线程时切换成本可观

所以「IO 密集就把线程池开大」只对了一半：开大能提升吞吐，但天花板由内存和下游决定，不是 CPU。

4. 竞争：线程越多反而越慢

4.1 实测：64 线程比 4 线程做得更少

同一个「synchronized 自增」任务，跑 8 秒：

线程数 8 秒内完成的增量次数
4 127,590,775
64 118,195,274

**64 个线程比 4 个线程少做了 7.4%**。多出来的线程没有带来吞吐，反而因为抢锁、切换、缓存行争用，把整体拖慢了。

4.2 JFR 读法：0 次 vs 17,051 次等锁

开启 JFR 录制（settings=profile），读 jdk.JavaMonitorEnter 事件：

线程数 jdk.JavaMonitorEnter 事件数 事件总大小
4 0 0
64 17,051 374,791 字节

4 线程时一次都没等到锁（15 核够用，锁几乎不冲突）；64 线程时发生 17,051 次等锁，单次等待长达 10 ms：

sequenceDiagram
    participant A as Thread-48
    participant B as Thread-49
    participant L as Monitor
    B->>L: 持有锁（执行 count++）
    A->>L: 尝试获取 -> 阻塞
    Note over A: duration = 10.0 ms
    B->>L: 释放
    L-->>A: 获得锁，继续

读法：duration 就是「等锁时长」。如果它到了毫秒级，说明临界区里有慢操作（IO、日志、复杂计算），或者线程数远超核数。

flowchart TD
    A["Task is CPU-bound?"] -->|yes| B["threads = cores + 1<br/>measured knee at 15"]
    A -->|no, blocking| C["threads = cores x (1 + W/C)"]
    C --> D{"memory allows?<br/>1MB per thread"}
    D -->|no| E["reduce -Xss<br/>or use virtual threads"]
    D -->|yes| F{"downstream allows?"}
    F -->|no| G["limit by downstream<br/>not by threads"]
    F -->|yes| H["measure curve,<br/>take the knee"]

5. 线程数怎么定

5.1 两个公式

场景 公式 例子
CPU 密集 线程数 = 核数 + 1 15 核 → 16
IO 密集 线程数 = 核数 × (1 + 等待时间/计算时间) 15 × (1 + 9/1) = 150
混合 按业务拆分池，别混用 计算池 16 + IO 池 100

验证方法：压测时逐步加线程，画「线程数-吞吐」曲线，拐点处的线程数就是答案（本文 2.1 的 15）。

5.2 三种场景的对照

场景 线程数建议 依据（本文实测）
纯 CPU 计算 核数 + 1 15 线程 12.86×，16 线程掉到 11.49×
阻塞等待（IO/锁） 核数 × (1 + W/C) 256 线程吞吐是 1 线程的 134 倍
共享锁竞争 越少越好 64 线程比 4 线程少做 7.4%

6. 动手验证：四个可复现实验

6.1 动手验证：量线程的栈内存

预期观察点：-Xss1m 时 Thread 区域约 1 GB（1018 个线程 × 1 MB），-Xss256k 时约 285 MB。

判定标准：

  • 折算每线程远大于 -Xss 值 → 还有别的线程或 guard page 开销；
  • 创建 1000 线程就 OOM → 你的容器内存限制太小，或 -Xss 太大。

6.2 动手验证：画你自己的线程数-吞吐曲线

预期观察点：耗时在 线程数 = 核数 处最小，之后基本不再下降。

判定标准：

  • 线程数超过核数后还能明显变快 → 你的任务不是纯 CPU 密集（有阻塞）；
  • 曲线全程单调下降但效率很低 → 检查是否每次都重新创建线程池（创建成本 32 µs/线程）。

6.3 动手验证：用 JFR 抓竞争

预期观察点：4 线程 0 次等锁事件，64 线程上万次；同时 64 线程的总计数比 4 线程更少。

判定标准：

  • 两种线程数都有大量事件 → 你的锁竞争严重，先缩小临界区；
  • 64 线程计数反而更多 → 临界区太短，竞争还没成型，加大临界区再试（或增加线程数）。

6.4 动手验证：阻塞任务的线性增长

预期观察点：吞吐随线程数近似线性增长（本文 1 线程 85 tasks/s → 256 线程 11,429 tasks/s）。

判定标准：

  • 加到某点后吞吐不再增长 → 碰到下游或内存上限，不是线程不够；
  • 线程数很大时耗时反而上升 → 创建/调度成本超过收益。

7. 总结

7.1 面试速答表

面试题 一句话答案
一个线程占多少内存 默认 1 MB 栈（-Xss1m），1000 线程约 1 GB（NMT 实测）
线程越多越快吗 CPU 密集到核数为止（15 核 12.86×，16 线程掉到 11.49×）
IO 密集能开多少线程 由内存与下游决定，不是 CPU；256 线程实测是 1 线程的 134 倍吞吐
线程数怎么算 CPU 密集 = 核数+1；IO 密集 = 核数 ×(1+W/C)
为什么线程多了反而慢 切换（2.43 µs/次）+ 锁竞争 + 缓存局部性变差
怎么证明存在锁竞争 JFR 的 jdk.JavaMonitorEnter，看事件数与 duration
竞争时 64 线程一定比 4 线程快吗 不一定，实测 64 线程少做 7.4% 的工作
unable to create native thread 是什么 栈内存 + 线程数超限，不是堆不够
用 -Xss 调小栈有什么代价 栈溢出（递归、深调用链）风险上升
怎么看线程的真实开销 -XX:NativeMemoryTracking=summary + jcmd VM.native_memory summary

7.2 实战避坑表

症状 原因 处理
加线程后吞吐不涨 到核数了 减线程，或换异步模型
64 线程比 8 线程还慢 锁竞争/切换 缩小临界区，减少共享
unable to create native thread 线程数 × 栈 > 容器内存 调小 -Xss 或用虚拟线程
CPU 使用率很高但吞吐低 自旋、切换、GC JFR 看 JavaMonitorEnter 与 GC
线程池忽快忽慢 池大小与负载不匹配 压测画曲线找拐点（6.2）

7.3 工具速查表

工具 看什么 判定标准
jcmd VM.native_memory summary Thread 区域大小 约 1 MB/线程（-Xss1m）
jcmd Thread.print 线程状态分布 BLOCKED 多 = 锁竞争
JFR jdk.JavaMonitorEnter 等锁次数与时长 duration 到 ms 级要处理
JFR jdk.ThreadPark park 次数 大量 = 阻塞式等待
线程数-吞吐曲线 拐点 拐点即最优线程数

7.4 实操建议

  1. CPU 密集任务线程数 = 核数 + 1，别凭感觉写 200。
  2. IO 密集按公式算，再用压测校准——公式给起点，曲线给答案。
  3. 1000 线程 = 1 GB 栈，容器里跑多线程服务先算这笔账。
  4. 看到 unable to create native thread 先查 -Xss 与线程数，别加堆。
  5. 用 JFR 而不是猜：jdk.JavaMonitorEnter 的 duration 是锁竞争最直接的证据。
