从这里开始：把 Redis 变成你的实验台

Posted on 2026-10-25 In 数据存储 Word count in article: 4.3k Reading time ≈ 16 mins.

Redis 的慢只有四个来源：网络往返次数、单线程排队、内存压力、持久化停顿。它不是「算得慢」——一条 GET 在 Redis 里执行只要几百纳秒，你从客户端测到的 0.087 毫秒里有 99% 是网络与排队。

本文是「Redis 实战路线」第一篇，做三件事：把 Redis 的成本拆成四项、搭一台可以随便压的实例、跑出你的第一组基线（延迟 / 吞吐 / 内存 / 慢日志）。后面十一篇的每个结论都会回来跟这组数字对照。

系列地图（Redis 实战路线，12 篇）

① 实验台与基线（本文） → ② 一次请求的成本账 → ③ 数据结构与编码 → ④ 内存、淘汰与碎片 → ⑤ 单线程与阻塞 → ⑥ Pipeline、事务与 Lua → ⑦ 持久化与丢失窗口 → ⑧ 复制、哨兵与 Cluster → ⑨ 缓存三大问题 → ⑩ 缓存与数据库一致性 → ⑪ 分布式锁与限流 → ⑫ 容量规划与分片

与站内《Redis 深度解析》的分工：那边是 20 章的知识地图，当字典查；这边是实验手册，按顺序练。本文对应那边的第 1 章定位与第 5 章单线程。

1. Redis 的四种成本

1.1 一句话定义

MySQL 的成本是「读了多少页」，Redis 的成本是「往返了几次、谁在排队」。同样是 1 万次读，逐条发是 1 万次 RTT，pipeline 发是 625 次 RTT（按 16 个一批），CPU 消耗几乎一样。

成本 一句话定义 由什么决定 怎么观测 详见
网络往返（RTT） 一条命令从发出到收到回复的时间 物理距离、TCP 栈、命令条数、pipeline redis-cli --latency、benchmark 的 p50 ②⑥
单线程排队 所有命令在一个事件循环里排队 命令复杂度、大 key、阻塞命令 SLOWLOG、INFO commandstats、P99 抖动 ③⑤
内存压力 装不下就要淘汰、碎片高就要整理 key 数量、value 大小、编码方式 INFO memory、MEMORY USAGE、碎片率 ③④
持久化停顿 fork、AOF fsync、rewrite 持久化配置、写入量 SLOWLOG、INFO persistence、P99 ⑦ 
flowchart LR
    C["Client call"] --> N["Network RTT<br/>10us~1ms"]
    N --> Q["Event loop queue<br/>single thread"]
    Q --> E["Command exec<br/>100ns~100ms"]
    E --> M["Memory<br/>alloc / evict / frag"]
    E --> P["Persistence<br/>fork / fsync"]
    M --> R["Reply"]
    P --> R
    R --> N

1.2 为什么「Redis 很快」这句话会骗人

实测（Redis 7.4.11，容器内 loopback，客户端与服务端同机）：

场景 实测 换算到单次
PING，1 个连接 32,981 rps 31 µs / 次往返
GET，50 连接，无 pipeline 319,489 rps 87 µs / 次（含排队）
GET，50 连接，-P 16 3,703,704 rps 单次 0.27 µs（摊销后）

同一个 GET，pipeline 与否差了 11.6 倍。差的是 Redis 的执行速度吗？不是——差的是往返次数。这就是第一篇要立的第一个观念：先数往返，再谈优化。

1.3 深挖：为什么单线程还能跑到 30 万 QPS

Redis 用单线程处理命令，靠三件事把 CPU 吃满：

  1. 纯内存操作，没有磁盘等待；
  2. epoll 多路复用，一个线程管几万个连接，没有线程切换；
  3. 命令足够短，GET 的 CPU 时间在百纳秒级，所以瓶颈天然落在网络上。

代价也很明确：任何一条慢命令都会堵住所有人。这也是第⑤篇的主题——KEYS *、DEL 大 key、Lua 长脚本，都会让 P99 从 0.1ms 跳到几百毫秒，而 CPU 使用率看起来还很健康（因为只有一个核在跑）。

这里可以直接对照站内 MySQL 系列第②篇：MySQL 的六层里，「等待」是第三种成本；Redis 的「等待」更极端——只有一个线程，排队就是全局的。

1.4 动手验证：三种成本各量一次

预期观察点：--intrinsic-latency 给出的是「这台机器什么都不做时的调度抖动」（本文实测平均 34 ns、最差 88 倍）；--latency 的 avg 是几十微秒到几百微秒；benchmark 的 p50 在 0.05~0.1 ms。

判定标准：

  • --intrinsic-latency 的 max 超过 1 ms → 宿主机的调度有问题（CPU 争抢、虚拟化），先解决环境再谈 Redis；
  • --latency 的 avg 远大于 p50 → 有偶发尖刺，去 ⑤ 找阻塞命令；
  • pipeline 后 QPS 提升不到 2 倍 → 你的命令本身很重（大 value / 复杂命令），不是 RTT 主导。

2. 搭实验台

2.1 起一个能随便压的实例

两点说明：

  • 端口用 6380，避开本机可能存在的 6379；
  • --enable-debug-command yes 是为了用 DEBUG POPULATE、DEBUG SLEEP、DEBUG JMAP 这类造数与故障注入命令——生产绝对不要开（它能让任何人触发崩溃或阻塞）。

实测版本：Redis 7.4.11，jemalloc 5.3.0，standalone。

2.2 先把默认值查清楚（实测）

不要抄文档，直接问实例：

参数 本文实例实测 含义 对你的影响
maxmemory 0 不限制内存 不设上限 = 随时可能被 OOM Killer 干掉
maxmemory-policy noeviction 写满后拒绝写入 缓存场景几乎一定要改
appendonly no 默认只开 RDB 崩溃会丢最后一次快照之后的数据
appendfsync everysec 每秒刷盘 最多丢 1 秒（⑦ 实测）
save 3600 1 300 100 60 10000 RDB 三条规则 三者触发任一即落盘
io-threads 1 只用主线程做 IO 带宽打满时它是瓶颈（⑥ 会试多线程）
slowlog-log-slower-than 10000 µs 只记 10ms 以上的命令 99% 的「慢」它看不见
latency-monitor-threshold 0 延迟监控关闭 尖刺无记录
hash-max-listpack-entries 512 hash 编码切换阈值 见 ③（注意：不同版本默认值不同，以 CONFIG GET 为准）
zset-max-listpack-entries 128 zset 编码阈值 同上
set-max-intset-entries 512 set 整数集合上限 同上
list-max-listpack-size -2 quicklist 单节点 8KB 影响大 list 的内存

这张表最该记住的两行：maxmemory = 0 和 slowlog-log-slower-than = 10000。前者意味着你的 Redis 随时可能被系统杀掉，后者意味着 10ms 以下的抖动你永远看不见——而线上投诉往往就是 5ms 变 50ms。

2.3 三个会浪费你半小时的坑

坑 现象 处理
Docker 的端口映射抬高 RTT 宿主机连容器比容器内 loopback 慢一个量级 测「Redis 本身」用容器内；测「业务侧」用宿主机，两组都记
DEBUG 命令默认禁用 DEBUG POPULATE 报 ERR DEBUG command not allowed 启动加 --enable-debug-command yes，仅测试环境
空实例的碎片率毫无意义 mem_fragmentation_ratio: 13.94 别慌：used 1MB、rss 13.7MB，分母太小。灌入数据后再看（本文灌完是 1.09）

2.4 动手验证：环境自检

预期观察点：redis_version:7.4.x、maxmemory:0、DBSIZE:0、PING:PONG。

判定标准：io_threads_active 为 0（io-threads=1 时不会启用多线程）；如果你打算做 ⑥ 的多线程实验，确认启动参数里已经带上 --io-threads 4，否则 CONFIG SET 也能生效但需要重启连接。

3. 基线四件套

3.1 延迟：三层要分开量

flowchart LR
    A["1 System scheduling<br/>intrinsic 34ns"] --> B["2 Redis round trip<br/>loopback 0.17ms"]
    B --> C["3 App-side P99<br/>includes pool + serialization"]
    C --> D["Where the 5ms comes from"]
层 工具 本文实测 说明
系统调度 --intrinsic-latency 3 平均 34 ns，最差 88 倍 测「机器本身抖不抖」
Redis 往返 --latency（loopback） avg 0.17 ms 含 redis-cli 自身开销
单命令往返 redis-benchmark -t ping -c 1 32,981 rps（≈31 µs） 最接近「一次 RTT」
业务视角 应用侧埋点 P99 必须自己测 含连接池、序列化、网络

判定标准：

  • 系统调度最差 > 1 ms → 换机器或解决 CPU 争抢，别调 Redis；
  • 单命令往返 31 µs（同机）而业务 P99 是 5 ms → 问题在客户端（连接池、序列化、线程池），不在 Redis。

3.2 吞吐：pipeline 是第一个倍增器

场景 实测 rps p50 相对
SET，50 连接，无 pipeline 316,456 0.087 ms 1.0×
GET，50 连接，无 pipeline 319,489 0.087 ms 1.0×
SET，-P 16 3,448,276 0.183 ms 10.9×
GET，-P 16 3,703,704 0.159 ms 11.6×

注意 p50 反而变大了（0.087 → 0.183 ms）：pipeline 用延迟换吞吐。批量发 16 条，第一条要等 16 条都处理完才回来。所以 pipeline 适合「批量写/批量读」，不适合「一次只取一个值还要立刻用」。

这些是容器内 loopback 的数字，不能当线上容量。真实环境里 RTT 由网络决定，pipeline 的收益通常更大（因为 RTT 更贵）。

3.3 内存：100 万 key 到底吃多少

状态 used_memory rss 碎片率 dataset 占比
空实例 1.02 MB 13.70 MB 13.94 —
100 万 key（64B value） 138.84 MB 151.79 MB 1.09 66.54%

换算：每个 key 约 139 字节，而 value 只有 64 字节。单 key 实测 MEMORY USAGE = 136 字节。

多出来的 72 字节是什么？key 名、dictEntry、redisObject、jemalloc 的 size class 对齐。这是 Redis 内存规划的第一个坑：按 value 大小乘 key 数量算内存，一定算少。

指标 用途 本文实测
used_memory Redis 认为用了多少 138.84 MB
used_memory_rss 操作系统看到多少 151.79 MB
mem_fragmentation_ratio rss / used 1.09（健康，1~1.5 正常）
used_memory_dataset_perc 有效数据占比 66.54%（其余是开销）
MEMORY USAGE key 单个 key 的真实开销 136 B

灌完之后性能有没有退化？ 没有：

场景 空实例 100 万 key 之后
GET 50 连接 319,489 rps 308,642 rps（-3.4%）

这就是 Redis 和 MySQL 的一个重要差异：MySQL 的大表会让你担心 B+ 树变高、Buffer Pool 装不下；Redis 的 100 万 key 对 GET 几乎没有影响，因为哈希表是 O(1)。它的上限是内存，不是「数据量」。

3.4 慢日志与延迟监控：两个默认关闭的开关

实测：DEBUG POPULATE 1000000 耗时 362 ms，被慢日志记下来了（slowlog-log-slower-than = 10000 µs）：

工具 默认状态 本文实测 建议
SLOWLOG 阈值 10 ms，只留 128 条 362 ms 的 DEBUG 被记录 线上调到 1~2 ms，条数加到 512
LATENCY MONITOR 关闭（threshold=0） LATENCY LATEST 为空 打开（阈值 10~50 ms），它记录的是「事件尖刺」
INFO commandstats 一直开 可查每个命令的调用次数与耗时 定位「谁在跑重命令」

两者的差别：SLOWLOG 记录「单条命令耗时超过阈值」，LATENCY MONITOR 记录「事件循环被阻塞的尖刺」。排查线上抖动，后者往往更有用——因为真正的问题是「所有人都在等」，而不是「某条命令自己慢」。

3.6 动手验证：跑出你的基线档案

预期观察点：四个数字各就位；SLOWLOG LEN 在空实例上是 0。

判定标准：

  • 吞吐低于 10 万 rps（同机 loopback）→ 检查 CPU 限流、容器配额；
  • 碎片率 > 1.5 → 有大量删除或大 key 分配不均（④ 讲）；
  • SLOWLOG LEN 持续增长 → 有命令超过 10 ms，先抓出来看是谁。

把结果填进自己的档案，后面每篇加一行：

场景 数据量 参数 命令 延迟 QPS 内存 结论
空实例 0 默认 PING 31 µs 32,981 1.02 MB 地板价
100 万 key 1M × 64B 默认 GET 87 µs 308,642 138.84 MB 无退化，139 B/key
pipeline 1M × 64B -P 16 GET 159 µs 3,703,704 138.84 MB 吞吐 11.6×
慢命令 1M 默认 DEBUG POPULATE 362 ms — — 被慢日志捕获

4. 基线怎么用

4.1 一张判断表

flowchart TD
    T["Latency spike"] --> Q1{"all endpoints<br/>at once?"}
    Q1 -- yes --> Q2{"CPU near 100%?"}
    Q2 -- yes --> A["Single-thread busy<br/>find the heavy command"]
    Q2 -- no --> B["Blocked by slow cmd<br/>SLOWLOG / LATENCY"]
    Q1 -- no --> C["RTT x command count<br/>count the calls"]
    C --> D["pipeline / batch / local cache"]
症状 大概率是哪类成本 第一件事 别做什么
所有接口 P99 一起涨，CPU 不高 单线程被阻塞 SLOWLOG GET / LATENCY LATEST 别加机器
只有某个接口慢 RTT / 命令条数 数这条链路发了几次 Redis 命令 别调 maxmemory
偶发尖刺，均值正常 fork / 大 key / 淘汰 看 INFO persistence 的 latest_fork_usec 别急着换集群
内存持续上涨 无上限 / 无 TTL INFO keyspace 的 expires、--bigkeys 别先加内存
写入报 OOM command not allowed noeviction 且打满 设 maxmemory-policy（④） 别以为加内存能根治

4.2 与 MySQL 系列的三个联动

联动点 说明
方法论一致 MySQL ① 的「先量再改」在这里复用：延迟分三层、吞吐看拐点、内存看开销
缓存是 MySQL 的前置 ⑨ 会实测「缓存挂了，MySQL 扛不扛得住」——那篇要靠 MySQL ③④ 的索引判断兜底能力
一致性是跨组件的 ⑩ 的「先删缓存还是先更库」本质是 MySQL ⑤ 的事务提交时机问题

4.3 动手验证：复现一次「抖动」

预期观察点：--latency 的 max 会跳到 5000 ms 附近——一个命令阻塞，所有请求一起等。

判定标准：

  • max 跳到秒级 → 确认是单线程阻塞，去 ⑤ 找「谁在阻塞」；
  • max 只有几十毫秒 → 阻塞命令没落到同一个实例（检查是否连错端口/库）。

5. 总结

5.1 面试速答表

面试题 一句话答案
Redis 为什么快 纯内存 + epoll 单线程 + 短命令，瓶颈天然在网络不在 CPU
单线程怎么扛住高并发 一个线程处理所有命令，没有线程切换；但慢命令会阻塞所有人
为什么 pipeline 快 把 N 次 RTT 合成 1 次；实测 11.6 倍（本文环境）
Redis 的延迟由什么构成 网络往返 + 事件循环排队 + 命令执行 + 内存分配 + 持久化停顿
100 万 key 占多少内存 本文实测 138.84 MB（64B value），约 139 B/key，是 value 的 2 倍多
key 的内存开销包含什么 key 名、dictEntry、redisObject、jemalloc 对齐
空实例碎片率 13.94 正常吗 正常，rss 基数太小；灌入数据后本文是 1.09
SLOWLOG 默认阈值 10000 µs（10 ms），只保留 128 条
LATENCY MONITOR 默认开吗 不开，latency-monitor-threshold=0
maxmemory=0 意味着什么 不限制内存，可能被 OOM Killer 杀
Redis 的容量上限是什么 内存，不是数据量；GET 在 1M key 时无退化
怎么确认问题在 Redis 还是客户端 分别测 intrinsic / loopback / 业务侧三层延迟

5.2 实战避坑表

症状 原因 处理
宿主机测出 1ms，容器内 0.1ms Docker 端口映射与 NAT 分层测，别混用
DEBUG 命令报错 默认禁用 测试实例加 --enable-debug-command yes
内存按 value 算，上线就 OOM 忽略了每 key 的 70+ 字节开销 用 MEMORY USAGE 抽样乘 key 数
慢日志里什么都没有但确实慢 阈值 10ms 太高 调到 1~2ms，并开 LATENCY MONITOR
灌数慢 逐条 SET DEBUG POPULATE（测试）或 pipeline / --pipe
空实例碎片率告警 分母太小 灌入数据后再看

5.3 工具速查表

工具 看什么 判定标准
--intrinsic-latency 系统调度抖动 max > 1ms 说明环境有问题
--latency Redis 往返 avg 与 p50 差距大 = 有尖刺
redis-benchmark -P pipeline 前后吞吐 提升 < 2× = 命令本身重
INFO memory used / rss / 碎片率 碎片率 > 1.5 需关注
MEMORY USAGE 单 key 开销 乘 key 数 = 真实容量
SLOWLOG 超阈值命令 持续增长 = 有重命令
LATENCY LATEST 事件尖刺 空 = 没开监控

5.4 实操建议

  1. 先测三层延迟（intrinsic / loopback / 业务侧），再决定优化哪一层。
  2. 把 slowlog-log-slower-than 调到 1~2 ms，并打开 latency-monitor-threshold——默认的 10 ms 会漏掉大部分抖动。
  3. 容量按 MEMORY USAGE 抽样算，别用 value 大小乘 key 数；本文的值是 136 B / 64 B ≈ 2.1 倍。
  4. maxmemory 必须设，并明确 maxmemory-policy；noeviction 在缓存场景等于「写满即挂」。
  5. **建一份 redis-lab.md**，把「场景 / 数据量 / 参数 / 命令 / 延迟 / QPS / 内存 / 结论」记下来，后面十一篇都往里加。
