Maven 依赖管理精要

Posted on 2025-02-26 In 开发工具 Word count in article: 3.6k Reading time ≈ 13 mins.

Maven 是一个 项目管理和构建工具，主要用于 Java 项目的依赖管理、构建自动化以及项目生命周期管理。

坐标与仓库

Maven 用 坐标 唯一定位一个构件（jar、war、pom）：

坐标要素 说明 命名规范
groupId 组织/公司唯一标识 反域名，如 com.company、org.apache
artifactId 项目/模块名 小写中划线，如 spring-boot-starter-web
version 版本号，分 RELEASE 与 SNAPSHOT 语义化版本 1.2.3，快照加 -SNAPSHOT
packaging 打包方式：jar（默认）/ war / pom 父模块为 pom，Web 应用为 war
classifier（可选） 同版本下的变体，如 sources、javadoc、all 一般由插件生成，手工很少写

仓库体系（三级）：

  • 本地仓库：默认 ~/.m2/repository，下载过的构件缓存于此，首次拉取慢、之后秒级。
  • 中央仓库：Maven 官方仓库（repo.maven.apache.org），国内直连慢，一般配阿里云镜像。
  • 私服：公司内部构件仓库，承担「下载代理 + 内部构件发布」双重职责，CI 构建必须依赖它。

SNAPSHOT 与 RELEASE：

  • RELEASE（如 1.0.0）：版本固定，本地缓存后不再重复下载；对外发布、下游依赖用它。
  • SNAPSHOT（如 1.0.0-SNAPSHOT）：开发期版本，Maven 每次构建会检查远程仓库是否有更新（默认 24 小时策略，-U 强制刷新）；多团队联调时依赖方必须用它才能拿到最新代码。
  • 发布正式版本前把 -SNAPSHOT 去掉再 deploy。

依赖范围

scope 元素声明依赖的作用范围，决定依赖在编译、测试、运行哪个阶段可见：

依赖范围 说明
compile scope元素的缺省值。编译、测试、运行阶段都会引入
test 测试阶段引入（JUnit、Mockito、Testcontainers 等）
provided 编译、测试阶段引入，运行期由容器（如 Tomcat 的 servlet-api）提供
runtime 测试、运行阶段引入，编译期不需要（如 JDBC 驱动）
system 用于添加本地 jar，不推荐使用（不参与依赖传递，需配 systemPath，换机器就废）
import 与 dependencyManagement 元素配合使用，其功能是将目标 pom.xml 文件中 dependencyManagement 的配置导入合并到当前 pom.xml 的 dependencyManagement 中

选型口诀：编译要用的写 compile，只有测试用写 test，运行环境自带的写 provided，运行期才加载的写 runtime。

依赖传递

有三个模块A、B、C，A依赖B，B依赖C，C是否能传递到A，取决于B依赖C时使用的依赖范围和配置。

传递规则：

B 依赖 C 时的范围 能否传递到 A 说明
compile 可以传递 C 会被 A 引入，且对 A 编译可见
runtime 可以传递 C 会被 A 引入，但仅在 A 运行时可见
test 不可以传递 test 范围只对声明它的模块（B）的测试生效
provided 不可以传递 由运行环境提供，无需向下游传递
system 不可以传递 本地 jar，不参与传递

optional 为 true 的依赖不能传递：

optional 表示该依赖只是当前模块的可选实现（如 SLF4J 的多个绑定、数据库驱动的多种实现），下游模块需要使用时必须自行显式声明，避免传递出无用的依赖。

依赖冲突

当直接依赖和间接依赖引用了同一个依赖的不同版本时，最终生效的版本由 Maven 的依赖调解决定：

  • 最短路径原则

A 到 jackson-databind 有两条依赖路径：A->B->C->jackson-databind（如 2.14.0）和 A->jackson-databind（如 2.15.0）。路径短的胜出，最终 A 依赖 jackson-databind 的 2.15.0 版本。

  • 声明顺序原则

当 A 到 jackson-databind 的依赖路径长度一样（A->B->jackson-databind 和 A->C->jackson-databind）时，最短路径原则不适用。此时先声明的依赖生效：B 先声明则使用 B 传递的版本，C 先声明则使用 C 传递的版本。

  • 排除传递依赖：exclusions

如果不想让某个传递依赖进入依赖树，可以用 exclusions 显式排除：

常用于：排除重复的日志实现、排除冲突的传递版本、精简依赖树。

冲突排查实操：

  1. mvn dependency:tree 查看完整依赖树，定位同一依赖的多个版本（重点看 - (conflict) 标记和已被剪枝的版本）。
  2. 运行期报 NoSuchMethodError / ClassNotFoundException：通常是依赖树里同时存在新老版本，低版本抢先被加载。用 mvn dependency:tree -Dverbose 找 class 的来源 jar，在最短路径上 exclusions 掉旧版。
  3. mvn dependency:analyze 分析「未使用的已声明依赖」和「使用中却未声明（仅靠传递）的依赖」——后者是隐患，应显式声明。
  4. 用 maven-enforcer-plugin 在构建期强制版本一致性，冲突直接构建失败，而不是等运行期炸：

dependencyManagement：统一管理依赖版本

dependencyManagement 的作用是只声明版本，不引入依赖。子模块声明同名依赖（不写版本号）时，统一使用这里声明的版本：

使用要点：

  • 父模块集中声明所有依赖的版本，子模块引用同名依赖时**无需再写 version**，实现多模块版本统一管理，避免版本不一致。
  • 子模块可以覆盖父模块声明的版本（显式写上 version 即可）。
  • 与 import 范围配合可以导入 BOM（如 Spring Boot 的 spring-boot-dependencies），导入后当前 pom 即拥有 BOM 中全部依赖的版本声明。

依赖冲突解决优先级（从高到低）：

  1. dependencyManagement 中声明的版本（强制指定，优先于依赖调解结果，除非子模块显式覆盖）
  2. 最短路径原则
  3. 声明顺序原则

exclusions 不参与版本选择，用于在规则之外手动剔除多余的传递依赖。

生命周期与常用命令

Maven 有三套互不干扰的生命周期，每套由若干阶段（phase）串联：

生命周期 阶段（按顺序） 用途
clean clean 删除 target/，清掉上次构建产物
default validate → compile → test → package → verify → install → deploy 主构建流程，执行某阶段会自动执行它之前的全部阶段
site site / site-deploy 生成/发布项目文档站点（较少用）

常用命令：

命令 效果
mvn clean 清空 target
mvn compile 编译 main 代码
mvn test 跑测试（含编译）
mvn package 打包为 jar/war（会先执行 test 阶段，可加参数跳过）
mvn install 打包并安装到本地仓库（多模块项目模块间依赖的基础）
mvn deploy 打包并发布到远程仓库/私服
mvn clean install 最常用组合：全量构建
mvn clean install -DskipTests 跳过测试编译+执行，快速构建
mvn clean install -Dmaven.test.skip=true 连测试代码都不编译（最激进）
mvn -U clean install 强制刷新 SNAPSHOT/远程元数据
mvn -o clean install 离线构建（只使用本地仓库，断网排障用）
mvn -q clean install 静默模式，只输出错误
mvn -T 1C clean install 并行构建（每 CPU 核一个线程），大项目提速明显
mvn package -Dspring.profiles.active=prod 打包时向应用传系统属性

多模块构建：在父 pom 目录执行 mvn clean install 会按依赖顺序构建全部子模块，但只想构建某个模块时：

参数 含义
-pl moduleA 只构建 moduleA（projects list）
-pl moduleA -am 构建 moduleA 及其依赖的模块（also make）
-pl moduleA -amd 构建 moduleA 及其依赖它的模块（also make dependents）

注意：只 -pl 不 -am 时，模块间依赖若不在本地仓库会构建失败——所以多模块开发的标准姿势是先全量 install 一次，之后增量用 -pl -am。

多模块项目

多模块工程同时利用 聚合 与 继承 两种机制（父 pom 通常两者兼顾）：

  • 聚合（<modules>）：父 pom 知道有哪些子模块，一条命令构建全部；不要求子模块继承父 pom（独立项目也能聚合）。
  • 继承（<parent>）：子模块获得父 pom 的 properties、dependencyManagement、插件配置；不要求父 pom 聚合子模块。
  • 子模块不写 groupId/version 时自动继承父值；写了 relativePath 说明父 pom 在本地路径（多模块目录结构），packaging 为 pom 的模块不能有其他内容被打包。

常用插件

插件是 Maven 的能力扩展点，核心场景配置如下：

插件 场景 关键点
maven-compiler-plugin 编译 配 Java 版本；**用 release 而不是 source+target**（release 同时限制编译期 API）
maven-surefire-plugin 跑单元测试 默认跑 *Test.java；支持 JUnit 4/5；失败即构建失败
maven-failsafe-plugin 跑集成测试 跑 *IT.java，mvn verify 阶段执行
spring-boot-maven-plugin Spring Boot 可执行 jar repackage 生成含依赖的 fat jar
maven-assembly-plugin 自定义分发包 打 zip/tar 带脚本、配置、依赖
maven-shade-plugin 打 uber-jar（fat jar） 非 Spring Boot 场景合并所有依赖成一个 jar；可配 relocation 避冲突
maven-source-plugin 发布源码 jar 配合私服发布 -sources.jar
maven-javadoc-plugin 发布文档 jar 发布到中央仓库必配
maven-enforcer-plugin 构建期规则校验 Java 版本、依赖收敛、禁止重复依赖
versions-maven-plugin 依赖版本管理 mvn versions:display-dependency-updates 看可升级项，versions:use-latest-versions 批量升级
maven-dependency-plugin 依赖分析/拷贝 dependency:copy-dependencies 拷出全部依赖 jar（离线部署场景）

构建加速与疑难杂症

提速三板斧：

  1. 只跑需要的阶段和模块：-pl/-am + -DskipTests，别动不动全量 clean install。
  2. 并行构建：-T 1C（CPU 核数线程），多模块项目提速 2~4 倍。
  3. 本地仓库缓存：依赖别反复下载，CI 里配好镜像；-o 离线跑纯本地构建。

高频问题对照表：

症状 原因 处理
构建报 PKIX path building failed 私服/镜像证书问题 下载证书 keytool -importcert 导入 JDK cacerts
jar is empty / 找不到主类 fat jar 未配置 mainClass 配 maven-jar-plugin 的 mainClass 或 Spring Boot 插件
中文乱码 未配 UTF-8 <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding> + compiler 加 -encoding
改了依赖版本不生效 本地仓库缓存了旧版 mvn -U 强制刷新，或删 ~/.m2/repository 对应目录
Could not resolve dependencies 私服没这构件 / 账号无权限 确认私服代理配置与 servers 认证
测试时 ClassNotFoundException 某依赖只在 test 范围 改 compile 或检查依赖传递
构建很快但代码没生效 增量构建没编到 clean 后重新构建，排除 target 缓存

依赖管理最佳实践清单

  1. **版本全部走 <properties>**，一个版本只在一处定义。
  2. Spring Boot 项目先引 BOM（spring-boot-dependencies），自己只覆盖确有需求的版本。
  3. **内部多模块共享版本用父 pom 的 dependencyManagement**，子模块不写 version。
  4. dependency:tree 是排查依赖问题的第一工具，冲突没闹明白前不要动手改 pom。
  5. exclusions 要带注释说明为什么排除，三个月后没人记得。
  6. 对外发布的公共模块：optional 标注可选依赖、配 maven-source-plugin 出源码、上 enforcer 校验。
  7. 依赖数量克制：每个依赖都是攻击面（CVE 面）和维护成本，dependency:analyze 定期清无用依赖。
  8. 升级依赖前看 release notes，优先升 security 相关；用 versions:display-dependency-updates 定期体检。
