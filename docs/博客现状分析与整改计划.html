质量：核心五篇（基础/并发/JVM/Spring/MyBatis）是全文「答案库」级——「为什么需要 → 怎么实现 → 代码示例」三段式，可面试复述。抽查 Java 核心基础，版本演进表、动机分析、面试官考察点拆解均在。
系统性：主线完整（语言 → 并发 → JVM → 框架），但设计模式无专篇（核心基础内仅零散提及），Java 网络编程（NIO/BIO/AIO）散在并发与 Netty 中无独立入口。

1.2 整改计划

新建（优先级最高）：

  • [P0] 设计模式 1 篇（2-3 万字）：覆盖面试 15 个高频模式（单例/工厂/策略/模板/代理/观察者/装饰器/责任链等），每个配「为什么需要 → JDK/Spring 里的真实应用 → 代码示例 → 面试话术」。理由：面试必考，且能联动 MyBatis（代理）、Spring（模板/工厂）已有文章。
  • [P0] Java NIO/网络编程 1 篇（2 万字）：BIO/NIO/AIO 演进 + 多路复用，作为「并发 → Netty」的桥接。理由：与 Netty 深度解析（6.8w）联动，面试高频但当前无落点。

优化：

  • [P1] 「项目面试准备指南」4.6k 字过薄，与 Zeus 的「项目面试实战手册」5w 字重复——建议合并进 Zeus 手册或删除，避免两处不一致。
  • [P1] 导航页「Java 后端面试导航」在构建后不再随文章更新，需季度核对链接。

文章 字数 质量

质量：MySQL 四件套（原理/索引/事务/高可用）成体系，覆盖索引优化、事务隔离、分库分表、慢查询。Redis 深度解析 13 章「是什么→怎么实现→为什么快→怎么不丢→怎么扛故障→怎么用」，是全文范本。ES 明显偏薄：1.9 万字停在入门（倒排索引/分词/基本查询），缺写入原理（refresh/flush/translog）、深度分页（search_after）、集群（分片/副本/脑裂）、与 MySQL 双写一致性。
系统性：MySQL+Redis 双主线完整；ES 是短板；分布式理论独立成篇（CAP/BASE/一致性）为分库分表与后续分布式提供理论底座。

2.2 整改计划

新建：

  • [P1] ES 补强 2 篇：《ES 原理深挖》（写入链路 refresh/segment/translog、分片与副本、脑裂与集群健康）2 万字 + 《ES 查询优化与实战》（深度分页、聚合、与 MySQL 双写一致性方案）2 万字。理由：数据存储分类下唯一单薄项，后端面试「ES 为什么快」必问。
  • [P2] Redis 补充 1 篇：《Redis 集群与高可用实战》（主从/哨兵/Cluster 部署与故障切换全流程）2.5 万字。理由：深度解析里集群是概念章，缺实战章；面试「哨兵 vs Cluster 怎么选」高频。

优化：

  • [P1] 「Redis 淘汰策略」11.8k 与深度解析第 6 章内存淘汰存在重叠，建议明确分工（深度解析讲机制，独立篇讲选型对比与生产案例）或合并。

质量：Netty 6.8w 旗舰级（Reactor 模型/ByteBuf/编解码/零拷贝）。MQ 两篇覆盖各自架构与使用。
系统性：缺消息队列选型对比（Kafka vs RocketMQ vs RabbitMQ，事务消息/顺序消息/消费语义差异）——这是面试高频「你们为什么选 X 不选 Y」，当前要靠读者自己读完两篇再总结。Dubbo/ZK 是 2021-2022 风格的老框架，与 Spring Cloud Alibaba 篇联动 OK，但缺「Dubbo vs Spring Cloud 选型」视角。

3.2 整改计划

新建：

  • [P1] 《消息队列选型与核心机制对比》1 篇（2.5 万字）：Kafka/RocketMQ/RabbitMQ 三选一决策树 + 事务消息实现对比 + 顺序消息 + 消费幂等/重试。理由：把中间件分类的散点收拢成决策能力，直接服务「二八原则」里的选型类面试题。

优化：

  • [P2] Dubbo 篇补充「与 Spring Cloud 对比、当前生态位置」小节，避免老框架内容造成误判过时。

8. AI 大模型（20 篇，28.4 万字）

8.1 现状

C. 入门/综述类（4 篇，2.7 万字，质量 ★★★☆☆）：AI 大模型核心概念综述 5.3k、Agent 安全与防护 5.3k、Spring AI 与 LangChain4j 实战 8.4k、LLM 评测 5.9k——单篇体量偏小，属「扫盲」水平。

8.2 整改计划

格式整改（最高优先）：

  • [P0] 5 篇项目文档重写为教程体（每个 2-3 万字）：保留实战内容，改成「背景 → 架构 → 核心实现（关键代码摘录）→ 踩坑 → 延伸」结构，标题中文化（如「从零实现一个 MCP 文件服务器」）。理由：这 11.5 万字是全站唯一「格式不达标」的存量，不整改就白写了。至少先处理 ticket-agent-mcp(ts)（4.6w 最完整）一篇打样，其余跟进。
  • 若重写工作量大，退路：合并 py/ts 两版 ticket-agent 为 1 篇。

新建：

  • [P2] 本分类已是「超出二八线」的增量资产（面试几乎不考 AI 大模型），维持骨架即可，新增优先级最低。若要写，补《AI 在 Java 后端的落地实践》（RAG 服务化/向量检索上生产）1 篇 2 万字，与主分类（Java 后端）形成联动。
